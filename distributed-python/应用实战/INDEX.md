## 每篇的固定结构

| 小节 | 内容要求 |
|------|----------|
| 场景 | 具体到"谁在什么时候遇到什么现象"，带量化锚点（QPS、耗时、错误率） |
| 基础版 | 能跑但会出问题的写法，附真实运行输出 |
| 演进 1 | 触发问题 → 只解决这一个问题的最小改动 |
| 演进 2（+） | 再暴露一个更深的问题 → 综合版改动 |
| 分步设计图 | 每演进一步一张 `assets/app-step{N}-{主题}.svg`，图后跟一句话读图指引 |
| 收尾对照表 | 三个版本的差异、各自代价、什么时候可以退回简单版 |

## 落盘前自检（每篇必过 7 条）

- [ ] 场景有量化锚点，不是"提升性能"这类空话
- [ ] 基础版真的能跑，贴的是真实输出不是编的
- [ ] 演进至少 2 跳，每跳都由一个具体故障/瓶颈触发
- [ ] 每步一张 SVG 分步设计图 + 一句话读图指引
- [ ] 收尾对照表含"什么时候可以退回简单版"
- [ ] 无真实凭据、真实 IP、真实域名（用 `<YOUR_API_KEY>` / `192.0.2.x` / `example.com`）
- [ ] 代码块标了实测环境，跑不了的标 `⚠️ 未实测` 并说明原因

## 与课文的分工

课文负责讲清"为什么"，应用实战负责演示"怎么一步步改到位"。同一段代码不重复贴：课文给最小可验证片段，应用实战给完整可运行版本。应用实战不替代课文，也不替代 Phase 3 的综合实战项目。
