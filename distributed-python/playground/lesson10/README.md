## 实测基准数据

环境：Linux / Python 3.12.3。

### m1 · 双写四种组合

```
C1 库成 + 消息成      订单 1｜下游 1｜一致
C2 库成 + 消息未成    订单 1｜下游 0｜✗ 丢事件
C3 库败 + 消息成      订单 0｜下游 1｜✗ 幽灵事件
C4 库败 + 消息未成    订单 0｜下游 0｜一致

R2 发送塞进事务块      订单 0｜下游 1｜→ 包在事务里也回滚不了
R3 放大 500 笔        丢 69 + 幽灵 10 = 79 笔 / 15.8%，告警 0
```

### m2 · 发件箱与中继

```
R1  双写 + 发送前崩溃      订单 1｜下游 0｜✗ 丢事件
R1  发件箱 + 发送前崩溃    订单 1｜待发 1｜重启补发 → 下游 1｜✓
R1b 业务写失败（qty=0）    订单 0、outbox 0 → 一起回滚
R2  中继发完未标记就崩     同一条投递 2 次
R3  高水位中继            连跑 3 轮发出 0 条，id=1 永久卡住
R4  两个中继并发扫 20 条   实际投递 40 次
R5  不清理                5 批累计 500 行
```

### m3 · 幂等消费

```
R1  18 次投递 / 10 条唯一
    S1 裸消费 扣 18｜S2/S3/S4 扣 10
R2  S3 分两个事务：m2 崩溃后重投被跳过 → 库存 999（应为 998）✗
    S4 同事务：m2 崩溃后重投正常扣 → 998 ✓
R2b 先查再改并发：A、B 都查到 None → 各自扣减成功 → 扣减量 2，处理日志 2 行
R3  去重键用投递序号：同一条投 4 次 → 去重表 4 行 → 扣 4 次
R4  去重表增长：5 批累计 500 行
```

### app10 · 三跳演进（200 笔，seed=7）

故障注入比例：提交后崩溃 5%｜通道不可用 8%｜中继发完未标记 10%｜消费端提交前崩溃 10%｜通道重复投递 15%

```
做法                订单   库存扣减   应扣   偏差   待发   终态
第 1 步 双写         200      203    200    +3     0    ✗
第 2 步 + 发件箱      200      230    200   +30     0    ✗
第 3 步 + 幂等消费    200      200    200    +0     0    ✓
```

## 三处最容易看错的地方

**第 1 步的 +3 是净值，不是"基本对了"。** 它是丢事件（少扣）与重复投递（多扣）互相抵消的结果。只看总量核对，这一步会伪装成没问题 —— 这恰恰是双写最危险的地方。

**m2 的 R3 需要特别理解。** sqlite 同一时刻只允许一个写者，脚本用"乱序可见"等价演示"id 顺序 ≠ 提交顺序"。这个缺陷在 PostgreSQL / MySQL 的真并发下同样存在，而且更容易触发。

**第 3 步的 0 偏差依赖一个显式设计。** 消费端崩溃时不能标记 outbox，要留待重投。这不是自带的，是代码里 `if ok and not faults["relay"][idx]` 这个判断做的。漏了它，丢事件会从发件箱这头重新长出来。

## 复跑

```bash
cd playground/lesson10
python3 m1_dual_write_matrix.py
python3 m2_outbox_relay.py
python3 m3_idempotent_consumer.py
python3 app10_outbox_journey.py
```

每个脚本都会在 `/tmp` 下建独立目录，互不干扰；重跑结果一致（`m1` 的放大实验和 `app10` 用固定 seed）。

**临时目录会自动清理**：脚本退出时删除自己建的 `/tmp` 目录。需要保留现场排查时，加 `--keep` 或设 `KEEP_TMP=1`，目录会保留并打印路径。这一条是卫生处理时补的——首版每次运行都留下一个目录，反复调参攒了 18 个。
