## 装什么（最小集）

本课程全部代码只依赖下面这几样。**没有 Django、没有 Celery、没有 Kubernetes**——这门课讲的是"多台机器之间会出什么问题"，不是"怎么部署一套集群"。

| 要用在哪 | 包 / 工具 | 本次实测版本 | 为什么需要它 |
|---|---|---|---|
| 全程 | Python | 3.12.3（最低 3.11） | 课 2 会用 `asyncio.TaskGroup`，它是 3.11 才有的 |
| 阶段 2 | `grpcio` | 1.85.1 | gRPC 运行时：channel、stub、server |
| 阶段 2 | `grpcio-tools` | 1.85.1 | 带 `protoc` 编译器，把 `.proto` 生成 `_pb2.py` |
| 阶段 2 | `httpx` | 0.28.1 | 对比 REST 与 gRPC 时的 HTTP 客户端，支持超时与 async |
| 阶段 3 | `redis` | 8.1.0 | 分布式锁、幂等去重表都用它当共享存储 |
| 阶段 4 | `opentelemetry-api` / `-sdk` | 1.45.2 | 课 14 的 traceId 传播，只用 API 层，不接后端 |
| 阶段 3 | Redis 服务 | 7.4.11（容器） | 上面那个 `redis` 包只是客户端，还需要一个真服务 |

**不用装**：消息队列、注册中心、服务网格、K8s。这些在课里只作概念对照出现，跑不到你的机器上。

> 一句提醒：`grpcio` 和 `grpcio-tools` 的版本**必须一致**。不是"建议"，是生成出来的代码会自己检查——文末「常见安装坑」第 3 条有它的真实报错原文。

## 怎么装

### 主路径：标准库 venv（最普适）

```bash
# 1. 建环境（目录名用 .venv，是社区惯例，也让 git 自动忽略）
python3 -m venv .venv

# 2. 激活（Linux / macOS）
source .venv/bin/activate

# 3. 确认现在用的是虚拟环境里的 python
which python
```

实测输出（路径随你的位置变化）：

```text
/abs/path/to/your-project/.venv/bin/python
```

Windows 侧换成：

```bat
py -m venv .venv
.venv\Scripts\activate
```

激活不是必需的——官方文档明确写了「你完全可以在唤起 Python 时指明虚拟环境的解释器完整路径」。但激活更省事，本课程后续命令都默认已激活。

先落一份 `requirements.txt`（版本钉死，下次重装不用靠回忆）：

```text
grpcio==1.85.1
grpcio-tools==1.85.1
httpx==0.28.1
redis==8.1.0
opentelemetry-api==1.45.2
opentelemetry-sdk==1.45.2
```

然后一次装齐：

```bash
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
```

实测装完的结果（`pip list` 摘录，按字母序）：

```text
grpcio                             1.85.1
grpcio-tools                       1.85.1
httpx                              0.28.1
opentelemetry-api                  1.45.2
opentelemetry-sdk                  1.45.2
protobuf                           7.36.2
redis                              8.1.0
```

注意 `protobuf` 你没有显式安装——它是 `grpcio-tools` 的依赖，被自动带进来的。这解释了一个常见困惑：**`protobuf` 版本不匹配时，报错里提到的是一个你没装过的包**。

> 为什么钉 `1.85.1` 而不是装最新：课程里所有 gRPC 结论都基于这一版实测。等 gRPC 升级到 1.9x 时，跟着升 `grpcio` 与 `grpcio-tools` **两个一起**即可。

### 备选 A：uv（更快，且能顺便管 Python 版本）

```bash
uv venv --python 3.12
source .venv/bin/activate
uv pip install -r requirements.txt
```

一句话差异：`uv` 装包快一个数量级，还能直接拉一个本机没有的 Python 版本；代价是多一个工具要维护。**装出来的还是同一个 venv**，后面所有命令不用改。

### 备选 B：Redis 用 Docker 起（推荐，比本机装省事）

```bash
docker run -d --name dp-redis -p 6379:6379 redis:7-alpine
```

实测容器内版本：

```text
Redis server v=7.4.11 sha=00000000:0 malloc=jemalloc-5.3.0 bits=64 build=40ff01a501d8e4b6
```

一句话差异：本机装（`apt install redis-server`）会污染系统、卸载麻烦；Docker 起一个隔离实例，`docker rm -f dp-redis` 就干净了。**课程只在课 10、课 11 真正连 Redis**，现在不起也行。

## 验证：装好了吗

把下面这段存成 `selfcheck.py`，跑一遍：

```python
"""课程环境自检：逐项确认后续课要用的能力真的可用。"""
import importlib
import sys

CHECKS = [
    ("Python >= 3.11", lambda: sys.version_info >= (3, 11), "asyncio.TaskGroup 从 3.11 起才有"),
    ("httpx 可导入", lambda: importlib.import_module("httpx") is not None, "阶段 2 的 HTTP 客户端"),
    ("grpc 可导入", lambda: importlib.import_module("grpc") is not None, "阶段 2 的 gRPC 运行时"),
    ("protoc 插件可导入", lambda: importlib.import_module("grpc_tools.protoc") is not None, "阶段 2 的代码生成"),
    ("redis 可导入", lambda: importlib.import_module("redis") is not None, "阶段 3 的锁与去重"),
    ("opentelemetry 可导入", lambda: importlib.import_module("opentelemetry.sdk") is not None, "阶段 4 的链路追踪"),
]


def main() -> int:
    failed = 0
    for name, check, why in CHECKS:
        try:
            ok = check()
        except Exception as exc:  # 导入失败也算不通过
            ok = False
            why = f"{why}（{type(exc).__name__}: {exc}）"
        print(f"{'PASS' if ok else 'FAIL'}  {name:<24} {why}")
        failed += 0 if ok else 1
    print(f"\n{len(CHECKS) - failed}/{len(CHECKS)} 项通过")
    return 1 if failed else 0


if __name__ == "__main__":
    raise SystemExit(main())
```

实测输出：

```text
PASS  Python >= 3.11           asyncio.TaskGroup 从 3.11 起才有
PASS  httpx 可导入                阶段 2 的 HTTP 客户端
PASS  grpc 可导入                 阶段 2 的 gRPC 运行时
PASS  protoc 插件可导入             阶段 2 的代码生成
PASS  redis 可导入                阶段 3 的锁与去重
PASS  opentelemetry 可导入        阶段 4 的链路追踪

6/6 项通过
```

退出码 `0` 表示全绿。`FAIL` 行末尾会带上异常类型，直接看出缺哪个包。

### 再确认一件事：protoc 真的能生成代码

光"能 import"不代表能编译。跑一次真实编译（课 5 才会细讲，这里只验证工具链）：

```bash
# 建一个最小 proto
cat > ping.proto <<'EOF'
syntax = "proto3";
package probe;
service Ping { rpc Say (PingRequest) returns (PingReply); }
message PingRequest { string msg = 1; }
message PingReply { string msg = 1; }
EOF

mkdir -p proto_out
python -m grpc_tools.protoc -I. --python_out=proto_out --pyi_out=proto_out \
    --grpc_python_out=proto_out ping.proto
ls -1 proto_out
```

实测产物：

```text
ping_pb2.py
ping_pb2.pyi
ping_pb2_grpc.py
```

三个文件都在 = 工具链完整。`ping_pb2.pyi` 是类型桩，给 IDE 和 mypy 用的，**不是必需的**，但加上后编辑器能补全。

再验证一次版本与序列化：

```bash
python -c "import grpc, google.protobuf; print('grpcio', grpc.__version__); print('protobuf', google.protobuf.__version__)"
```

```text
grpcio 1.85.1
protobuf 7.36.2
```

### 如果要用 Redis，再确认一次连通

下面按课程默认端口 6379 写（`docker run` 那行也是这个端口）：

```bash
python -c "
import redis
r = redis.Redis(host='127.0.0.1', port=6379, socket_connect_timeout=2)
print('ping ->', r.ping())
"
```

```text
ping -> True
```

> 实测时本机已有别的 Redis 占着 6379，改用 `-p 6399:6379` 起容器并把 `port` 换成 `6399` 才跑通——所以你看到的 `True` 是这条链路通了的证据，端口号按你自己起的那个填。这也是上表最后一条坑的现场演示：**端口冲突不会报错，只会让你连到别人的 Redis 上**（课 11 讲分布式锁时，这个"连错实例"会变成真实的正确性问题）。

## 常见安装坑

这四条都是本次实测踩到的原样报错，不是"听说"。

| 症状（报错关键字） | 原因 | 解法 |
|---|---|---|
| `error: externally-managed-environment` … `× This environment is externally managed` | 系统 Python（Debian / Ubuntu 24.04+）禁止 pip 直接装到全局，防止把系统包搞坏 | **别加 `--break-system-packages` 硬来**。建 venv 再装，或改用 `pipx` 装 CLI 类工具 |
| `ModuleNotFoundError: No module named 'grpc'` | 装了，但当前 shell 没激活 venv，用的是系统 python | `source .venv/bin/activate`，再用 `which python` 确认路径里有 `.venv` |
| `RuntimeError: The grpc package installed is at version … but the generated code in xxx_pb2_grpc.py depends on grpcio>=…` | `grpcio-tools` 比 `grpcio` 新，生成代码要求的运行时版本高于已装的 | 两个包**装成同一版本**：`pip install grpcio==1.85.1 grpcio-tools==1.85.1` |
| `docker: Error response from daemon: … Bind for 0.0.0.0:6379 failed: port is already allocated` | 本机已有别的 Redis（或上次容器没删）占着 6379 | 换端口 `-p 6380:6379`，或 `docker rm -f <旧容器名>` 先清掉 |

第三条值得多看两眼——它不是模糊的"可能不兼容"，而是生成文件开头就写死的运行时校验：

```python
GRPC_GENERATED_VERSION = '1.85.1'
...
if _version_not_supported:
    raise RuntimeError(
        f'The grpc package installed is at version {GRPC_VERSION},'
        + ' but the generated code in ping_pb2_grpc.py depends on'
        + f' grpcio>={GRPC_GENERATED_VERSION}.'
        + f' Please upgrade your grpc module to grpcio>={GRPC_GENERATED_VERSION}'
        + f' or downgrade your generated code using grpcio-tools<={GRPC_VERSION}.'
    )
```

这就是为什么"两个包版本必须一致"在这门课里是硬约束，而不是经验之谈：**生成代码自带守卫，不匹配就当场抛错**。课 5 会再遇到它一次。

## ⚠️ 本课不解决的事
