# 设计决策 · 分布式任务调度器的协调层

> 每个决策点都**真有争议**——换个人来可能选另一个方案，且也有道理。唯一正确答案不算决策点。

## 决策 1：协调服务到底用哪个（ZK / etcd / Redis / 不引入）

**候选方案**：

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| A · **ZooKeeper + Curator** | 3 节点 ZK，Java 侧用 Curator 配方；本题 Python 侧用 kazoo | 选主/锁/配置三件事**一站式**；Curator/kazoo 配方成熟（避开手写坑）；临时节点天然做成员感知；zxid 提供**全序 token** 可做 fencing | 要运维一套 JVM 集群；事务日志需专用盘（课 7 三张账单） |
| B · **Redis（已在用）** | `SET NX PX` 做锁，自身选主靠 Redlock 或单实例 | **零新组件**，运维成本最低；延迟最低（~0.5–2ms） | 单实例锁在故障转移场景被官方定性 **SAFETY VIOLATION**；**无全序 token，无法做 fencing**；无原生成员感知（要自建心跳） |
| C · **etcd** | 3 节点 etcd，用 lease + revision 做锁与选主 | 云原生/Go 栈最对口；revision 可做 fencing；已有 K8s 就有运维能力 | 本题是 Python/Java 栈，无专职 Go 运维；无内置"配置中心"治理能力（无控制台/版本/灰度） |
| D · **不引入，用 K8s 内建** | 用 K8s Lease（coordination.k8s.io）做选主 | 零额外组件 | 只解决选主，**锁与配置推送仍要另想办法**；跨语言客户端不如 ZK 成熟 |

**最终选择**：**A · ZooKeeper（实验用 kazoo 实现；若你是 Java 栈生产环境，选 Curator）**

**选择理由**：本项目要同时做三件事——**选主 + 分布式锁（含 fencing）+ 动态配置**。能一个组件全做掉、且**原生支持 fencing token** 的只有共识型服务（ZK 用 zxid / etcd 用 revision）。Redis 便宜但**给不出全序 token**（课 12 反直觉三：资源层要校验就得先有号），在"库存扣减"这个正确性场景直接出局；etcd 能做但团队栈不对口；K8s Lease 只解决选主。

**为此付出的代价**：引入一套要运维的 JVM 集群——**这就是课 7 的三张账单**（硬件：事务日志专用盘；运维：清快照、盯 watch 数；人力：学 ZAB/会话/Watch 三个新概念）。而且 ZK 是**为 KB 级协调数据设计的**（内置 1MB sanity check），你**不能**顺手把任务执行日志塞进 ZK。

**什么时候该改选另一个**：
- 若你的任务**全是幂等的**（重跑一次无所谓）→ **Redis `SET NX PX` 就够**（课 12 场景 C 场景 1），此时 ZK 的运维成本远大于收益
- 若团队是 **Go 栈 / 已在 K8s 上且有 etcd 运维能力** → **etcd**，revision 同样能做 fencing
- 若**只需要选主**（锁和配置另有方案）且跑在 K8s → **K8s Lease**，零组件

## 决策 2：锁分几档——是一把锁统一管，还是按后果分级

**候选方案**：

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| A · **统一用 ZK 强锁** | 所有任务（含幂等对账）都走 ZK 互斥锁 + fencing | 简单一致，**一套代码**；不会出现"该强的地方弱了" | 幂等任务也被过半写拖慢（每次锁要写盘+过半确认）；**成本错配**——为不需要的保证付了钱 |
| B · **按后果分级** | 幂等任务（对账）用 Redis 轻量锁；非幂等任务（库存）用 ZK 锁 + fencing | **成本与风险匹配**：只在真正需要正确性的地方付过半写的代价 | 两套代码路径，要维护两套；开发者要能正确判断"我这任务幂等吗"——**判断错就用错了档** |
| C · **统一用 Redis 锁** | 所有任务都用 Redis，靠业务幂等兜底 | 最便宜最快 | 非幂等任务一旦遇到故障转移→**写坏数据**（官方定性 SAFETY VIOLATION） |

**最终选择**：**B · 按后果分级**

**选择理由**：核心判据来自课 11 决策树的 **Q4**——"**丢锁的后果是效率问题还是正确性问题**"。对账任务重复执行只是多跑一次（效率），库存扣减重复执行会超卖（正确）。用一把锁统一管，要么**为效率问题付了正确性的钱**（方案 A 的成本错配），要么**为正确性问题省了钱**（方案 C 的数据风险）。

**为此付出的代价**：两套代码路径 + **要求开发者能正确分类**。这是真实且常被低估的成本——很多团队选 B，结果有人把非幂等任务归到了轻量档。缓解办法：把"是否幂等"作为**任务注册时的显式字段**（强制声明），并让轻量档的 API 名字自带警告（如 `lock_if_idempotent()`）。

**什么时候该改选另一个**：
- 若你**无法保证**开发者能正确分类（团队流动性大、无 code review）→ 退回 **A 统一强锁**，用成本换"不会用错"
- 若**所有任务都幂等**（如纯报表生成）→ **C 统一 Redis**，一分钱不花

## 决策 3：配置放哪——塞进 ZK，还是用专用配置中心

**候选方案**：

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| A · **塞进 ZK**（watch 配方） | 配置存 ZNode，用 `get_data` + watch 推送 | **不引入新组件**；与选主/锁同一套基础设施；强一致 | **无版本/回滚/灰度/权限/控制台**，全要自建；ZK 是 KB 级设计，配置多了撑堆（内存数据库） |
| B · **专用配置中心**（Nacos/Apollo） | 配置交给 Nacos/Apollo，ZK 只管选主与锁 | 秒级长轮询推送、**版本回滚、灰度、权限审计、控制台、客户端缓存兜底**全都有 | 多一套组件要运维；与 ZK 职责切分要划清楚 |
| C · **本地文件 + 发版** | 改配置重新发版 | 最简单 | **改一次要发版**——不满足"动态下发"需求，直接出局 |

**最终选择**：**A · 塞进 ZK**（**本项目限定条件下**），但**明确标注这是有条件的结论**

**选择理由**：本项目配置量小（几十个开关/阈值）、无审计合规要求、团队不想再引入一套组件——这正是课 12 场景 B 里"**基础设施/元数据类配置**"的定位：量少、要求强一致、本来就该和集群状态放一起。而且 demo 要能一键跑起来，多用一套组件就多一个启动依赖。

**为此付出的代价**：没有版本回滚和灰度——**改错一个阈值只能手动改回去**，且改配置的人没有审计记录。另外配置 watch 是**一次性**的（课 5），回调里忘了重新注册就会**静默丢失后续通知**——这是本项目最容易写错的地方（见反例对照）。

**什么时候该改选另一个**：
- 一旦出现**"要按环境隔离""要灰度""要审计谁改的""要一键回滚"**任一需求 → 立刻换 **B（Nacos/Apollo）**（课 12 场景 B 结论：配置管理是独立赛道，专用工具更省事）
- 若配置项超过**几百个**或单条超过 **KB 级** → 换 B，别撑 ZK 的堆

## 📌 三个决策的共同教训

| 决策 | 表面在选什么 | 实际在判断什么 |
|------|-------------|---------------|
| 1 · 协调服务 | 用哪个组件 | **这个场景真正的约束**（要不要 fencing / 团队栈 / 运维能力） |
| 2 · 锁分档 | 锁的实现 | **丢锁是效率问题还是正确性问题**（课 11 Q4） |
| 3 · 配置放哪 | 存在哪 | **配置是"基础设施元数据"还是"业务治理对象"** |

**一句话**：三个决策都不是"哪个技术更好"，而是"**在我的约束下哪个总成本最低**"——这正是课 10（结论不可外推）和课 11（决策树）反复强调的。**本文件的结论在你换一个项目时很可能翻转**，可移植的是上面这三行"实际在判断什么"，不是"选了 A"。
