# 反例对照 · 分布式任务调度器的协调层

> 不是"错误示例"，而是**看起来能跑、实际很糟**的版本——只有这样才能教会"为什么最佳实践是最佳实践"。
> 下面每个反例**都能跑通**，甚至在 demo 里表现得比正确版本还"简洁"。

## ❌ 反例 1：抢锁时"大家都盯着同一把锁"（羊群效应）

```python
# ❌ 反例：所有等待者都 watch 同一个锁节点
def acquire_lock_bad(zk, lock_path):
    while True:
        try:
            zk.create(lock_path, b"1", ephemeral=True)   # 抢到了
            return True
        except NodeExistsError:
            # 所有没抢到的都盯着这一个节点 —— 惊群！
            event = threading.Event()
            if zk.exists(lock_path, watch=lambda e: event.set()):
                event.wait()      # 锁一释放，成百上千个等待者同时被唤醒
            # 被唤醒后全部蜂拥去 create，只有 1 个成功，其余白跑
```

> 它**能跑通**：3 个节点时毫无感觉，功能完全正确。问题在规模。

## ❌ 反例 2：锁不传 token，资源层裸写（fencing 缺失）

```python
# ❌ 反例：拿到锁就直接写，不校验 token
def deduct_stock_bad(zk, lock, order_id):
    with lock:                      # 以为"持有锁 = 安全"
        stock = read_stock()        # 此刻进程 GC 暂停 30 秒…
        # 租约早已过期，别人已经拿到锁并改了库存
        write_stock(stock - 1)      # 我醒来自认有锁，继续写 → 超卖！
```

> 它**能跑通**：压测 1000 次可能一次都不出错——因为 GC 暂停是罕见事件。**偶发的正确性问题最难发现**，也是危害最大的。

## ❌ 反例 3：配置 watch 忘了重新注册（一次性通知）

```python
# ❌ 反例：watch 只注册一次
@zk.DataWatch("/config/task_switch")
def on_config_change(data, stat):
    global task_switch
    task_switch = json.loads(data)      # 只回调一次！
    # 忘了：watch 是一次性的（课 5），第二次变更再也收不到
```

> 它**能跑通**：第一次改配置生效了，你会以为功能做好了。第二次改配置**静默失效**——没有任何报错。

## ❌ 反例 4：把任务执行日志塞进 ZK（误用为存储）

```python
# ❌ 反例：拿 ZK 当数据库
zk.create("/tasks/logs/2026-08-31/001", big_json_2MB)   # 2MB 日志
# ZK 内置 1MB sanity check（jute.maxbuffer 默认 1048575 字节）→ 直接报错
# 即使调大，ZK 是内存数据库，整棵树在堆里 → 撑爆堆 → OOM
```

> 它**能跑通**：小日志没问题。等日志积累到几十 MB，ZK 全体成员几乎同时 OOM。

## 🔍 逐条对比

| # | 维度 | ❌ 反例 | ✅ 正确做法 | 为什么糟 |
|---|------|---------|------------|----------|
| 1 | **锁竞争** | 所有等待者 watch 同一把锁 | **排队，只 watch 前驱**（最小序号的前一个） | 1000 个等待者时，锁释放瞬间 ZK 收到 1000 个 create 请求 + 1000 个 watch 事件——**Watch 风暴**（课 8 ZOOKEEPER-1177：单 watch 约 100 字节，2 亿条 1.2G+）。正确做法只惊醒**一个** |
| 2 | **锁的正确性** | 拿到锁就写，不传 token | 锁服务发**单调 token**（ZK 用 czxid），**每次写资源都带上，资源层拒绝更旧者** | 租约锁挡不住"进程暂停→租约过期→自认有锁继续写"（Kleppmann：no matter what lock service you use）。**真正的互斥在资源层**，不在锁服务 |
| 3 | **配置推送** | watch 只注册一次 | 回调里**重新注册**（或用 3.6+ 持久 watch） | watch 是**一次性**的，忘了重注册就**静默丢失**后续所有变更——没有报错，只是配置再也不生效 |
| 4 | **数据边界** | 拿 ZK 存业务日志/大对象 | 只存 **KB 级协调数据**（选主标记、锁、开关） | ZK 为协调数据设计（官方：通常以 KB 计，内置 1MB sanity check），且**整棵树在堆里**——撑大就 GC 压力→OOM，且全体成员几乎同时 OOM |
| 5 | **成员感知** | 轮询 get_children 判断谁活着 | 用**临时节点** + watch 子节点变化 | 轮询有延迟且白耗请求；临时节点会话一断自动消失，是**权威的存活信号**。但要注意：断连期间收不到任何 watch（课 5 safe mode），重连后要**全量重新同步**而非增量信任 |
| 6 | **连接上限** | 每个任务开一个新 ZK 连接 | **复用**一个长连接（每个 ZK handle 就是一个会话） | 单 IP 默认上限 `maxClientCnxns=60`，容器环境多 Pod 共享宿主 IP 极易触顶，且**服务端静默拒绝**（日志才有 `Too many connections from /IP - max is 60`） |

## 💡 一句话教训

**能跑通 ≠ 能扛住；差别在于失败时怎么表现。**

- 反例 1 在 **1000 个竞争者**时崩（规模）
- 反例 2 在 **GC 暂停那一秒**崩（罕见但致命）
- 反例 3 在**第二次改配置**时崩（静默失效）
- 反例 4 在**数据量涨到几十 MB** 时崩（慢性死亡）

四个反例的共同点：**happy path 全过，都在边界条件上翻车**——这正是"课堂只演 happy path"的缺口，也是课 8《经典的坑》和 Phase 5 排障手册存在的理由。
