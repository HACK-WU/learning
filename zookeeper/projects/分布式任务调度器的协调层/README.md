# 实战项目：分布式任务调度器的协调层

> 所属课程：ZooKeeper ｜ 学习目标：**决策参考 + 动手实操**（既产出可运行代码，也产出选型决策文档）｜ 预计耗时：6–8 小时
> 对应收官交付物：课 12 演练 B 要求的《协调服务选型决策》

## 🎯 一句话需求

为一个**多副本部署的定时任务调度器**设计并实现协调层——保证同一时刻只有一个节点执行任务、节点上下线能被自动感知、任务配置可动态下发，**并产出一份能向团队汇报的选型决策文档**。

## ✅ 目标与非功能约束

**功能目标**：

1. **主节点选举**：3 个调度器副本中自动选出 1 个 Leader 执行任务，Leader 挂掉后 30 秒内自动接管
2. **分布式互斥**：对账任务（幂等）与库存扣减任务（非幂等）两套不同的锁策略，后者必须带 fencing token
3. **成员感知 + 动态配置**：Worker 上下线被自动感知（临时节点），任务开关/阈值可动态下发且服务端挂了也能靠本地缓存启动

**非功能约束**（≥2 项）：

- **可维护性**：协调层与业务解耦，锁接口封装后底层从 ZK 换 etcd 对业务透明
- **错误处理**：区分"效率问题"（重跑一次无所谓）与"正确性问题"（写坏数据不可接受），两者用不同强度的方案
- **成本**：不引入新组件——若平台已内建能力就用内建的（对应课 12 场景 A 的结论）

## 🚀 运行方式

```bash
# 1) 起一个 3 节点 ZK 集群（Docker，仅本地实验用）
docker compose up -d

# 2) 装依赖
pip install kazoo==2.11.0

# 3) 开三个终端，分别起 3 个调度器副本
python 实现/scheduler.py --node-id worker-1
python 实现/scheduler.py --node-id worker-2
python 实现/scheduler.py --node-id worker-3
# 预期：只有一个终端打印 [LEADER] 我在执行任务，另两个打印 [FOLLOWER] 待命

# 4) 杀掉 Leader 那个终端，观察 30 秒内另一个副本接管
# 预期：另一个终端从 FOLLOWER 变为 LEADER 并开始执行

# 5) 验证 fencing（非幂等任务）
python 实现/stock_task.py
# 预期：模拟"进程暂停→租约过期→自认有锁继续写"时，资源层用 token 挡住旧写入
```
