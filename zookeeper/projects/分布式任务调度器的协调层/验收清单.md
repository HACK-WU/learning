# 验收清单 · 分布式任务调度器的协调层

> 逐项自测。**全部勾选才算真的做成了**——不是"跑起来就行"。

## 功能验收

- [ ] 起 3 个副本，**恰好 1 个**打印 `[LEADER]`，另 2 个打印待命（验证选主唯一性）
- [ ] 杀掉 Leader 进程，**30 秒内**另一个副本自动接管并打印 `⭐ 我是 Leader`（验证故障接管）
- [ ] 每个副本都在 `/scheduler/workers/` 下创建了**临时**节点；杀掉进程后该节点**自动消失**（`zkCli.sh ls /scheduler/workers` 验证）
- [ ] 幂等对账任务：持锁执行，重复触发不会并发（用 `zkCli.sh ls /scheduler/locks` 观察锁节点）
- [ ] 非幂等库存任务：跑 `stock_task.py`，正确版最终**未被旧持有者写坏**（token 被拒）
- [ ] 配置变更：`zkCli.sh set /scheduler/config/task_switch '{"enable_reconcile":false,...}'`，**连续改两次都能收到**（验证 watch 已重注册，不是一次性）

## 非功能验收

- [ ] **规模**：竞争者增到 20 个时，锁释放瞬间 `echo mntr | nc localhost 2181 | grep zk_watch_count` **不爆炸**（对比反例 1 的惊群版）
- [ ] **正确性**：模拟进程暂停 3 秒后继续写 → 资源层**拒绝**并打印 `🚫 拒绝写入：token=... < 已见最大 ...`
- [ ] **可用性**：ZK 集群停掉后，服务**仍能靠本地缓存启动**（不抛异常，用上次配置运行）
- [ ] **故障独立性**（可选）：3 节点集群停 1 个，集群仍可写（验证 2F+1 过半派）

## 理解验收（能说清才算会）

- [ ] 能说清**决策 1** 为什么选 ZK，以及"任务全幂等时该改选 Redis"的翻转条件是什么
- [ ] 能说清**决策 2** 为什么要按后果分级，以及"团队无法正确分类时该退回统一强锁"的理由
- [ ] 能说清**决策 3** 为什么本项目把配置塞 ZK，以及出现"要灰度/要审计"时为什么必须换 Nacos/Apollo
- [ ] 能说清反例 1（惊群）错在哪，以及它"能跑通"的原因（3 个节点时无感）
- [ ] 能说清反例 2（无 fencing）为什么**压测可能 1000 次都不出错**却依然致命
- [ ] 能说清这句话：_"锁服务不是锁，资源层拒绝旧 token 才是锁"_ —— 以及为什么**第三方 API 不支持条件写时，换 etcd/ZK 都没用**
- [ ] 能说清 watch 为什么必须重注册，以及断连重连后为什么要**全量重读**而不是只信增量
