## 🚫 适用边界与反模式

### 什么时候不该用它

> "不该用"比"怎么用"更值钱——这是从"会用"到"用对"的分界线。

| 场景 | 为什么不适合 | 该用什么替代 |
|------|-------------|-------------|
| **纯 K8s 单集群的服务发现** | K8s 已内建：CoreDNS 监视 API 为**每个 Service 自动建 DNS 记录**，Pod 不自己注册，**只有 readinessProbe 通过的 Pod 才收流量**。再引入注册中心是重复实现平台能力 | **K8s Service + CoreDNS**（课 12 场景 A）；跨集群/与 VM 互访时才回到 Nacos/Consul |
| **业务配置治理**（要灰度/审计/回滚/控制台） | ZK 无版本回滚、无灰度、无权限审计、无控制台；且是**内存数据库**，配置撑大堆会 OOM | **Nacos（求简）/ Apollo（求全）**；ZK 只留"基础设施元数据类配置"（课 12 场景 B） |
| **存业务数据 / 大对象 / 日志** | 官方定位：为存储**协调数据**设计，通常以 **KB 计**；内置 **1MB sanity check**（`jute.maxbuffer` 默认 1048575 字节）防止被当大数据存储 | 数据库 / 对象存储 |
| **只要个幂等任务的互斥** | 丢锁只是"效率问题"（重跑一次无所谓），ZK 的过半写成本远大于收益 | **Redis `SET NX PX` + 看门狗**（课 12 场景 C 场景 1） |
| **资源层不支持条件写的互斥** | fencing 靠**资源层拒绝旧 token**；资源层不配合时，换 etcd/ZK **都没用** | 改造成**幂等**（唯一键/流水号去重），或引入串行化中间层（课 12 案 3） |
| **团队无运维能力 / 想零运维** | 三张账单：事务日志需**专用盘**、默认不清快照（operator 责任）、要盯 watch 数与堆 | 云托管协调服务，或直接用平台内建能力 |

### 高频反模式（能跑，但迟早出事）

1. **所有等待者 watch 同一把锁**：3 个节点无感，竞争者变多时锁释放瞬间惊醒全群 → **Watch 风暴**（ZOOKEEPER-1177：单 watch 约 100 字节，2 亿条 1.2G+）。→ 正确：**排队，只 watch 前驱**（课 6/课 8）
2. **watch 只注册一次**：第一次变更生效，之后**静默失效**（watch 是一次性的）→ 正确：回调里**重新注册**，或用 3.6+ 持久 watch
3. **拿到锁就裸写，不传 token**：happy path 全过，遇到"进程 GC 暂停→租约过期→自认有锁继续写"就写坏数据。→ 正确：锁服务发**单调 token**（ZK 用 czxid / etcd 用 revision），**每次写都带上，资源层拒绝更旧者**
4. **把 ZK 当数据库存日志**：小日志没事，积累到几十 MB 后全体成员**几乎同时 OOM**（内存数据库 + 共享同一棵树）→ 正确：只存 KB 级协调数据
5. **每个任务开一个新连接**：单 IP 默认上限 `maxClientCnxns=60`，容器环境多 Pod 共享宿主 IP 极易触顶，且**服务端静默拒绝** → 正确：**复用长连接**
6. **与高 IO 组件共享磁盘**：事务日志要 fsync，与 DataNode/Kafka 共享盘会导致 fsync 超时 → 节点假死、频繁切主 → 正确：**dataLogDir 独占低延迟盘**

## 🔥 高频故障模式

> 每条固定五段式：症状 → 根因 → 排查路径 → 修复 → 预防。症状均为可观测。

### 故障模式 1：写停顿 / fsync 告警（磁盘 IO 瓶颈）

- **症状（可观测）**：日志出现 `fsync-ing the write ahead log in SyncThread:0 took 1234ms which will adversely effect operation latency`；`zk_outstanding_requests` 持续非 0 并攀升；**写延迟飙升但 follower 读延迟正常**
- **根因**：每次写都要在 leader 与过半 follower 上 **fsync 事务日志**才能 ACK。磁盘慢（共享盘 / 云盘 IOPS 突发额度耗尽 / 硬件退化）时，整条写路径阻塞。该告警阈值 `fsync.warningthresholdms` 默认 **1000ms**——**已达专用 SSD 正常值的 200–1000 倍**
- **排查路径**：
  1. `grep "fsync-ing the write ahead log" zookeeper.log | tail -20` 确认告警频率
  2. `iostat -x 1 5` 看事务日志盘的 `%util` 是否接近 100
  3. 检查 `zoo.cfg` 中 **dataLogDir 是否与 dataDir 分离**、是否与其他高 IO 组件共享盘
  4. 云环境检查 EBS gp2/gp3 **突发额度是否耗尽**
- **修复**：把 `dataLogDir` 迁到**独占的低延迟盘**（这是 ZK 写路径稳定性**影响最大的一项改动**）；云上提升预置 IOPS 或换 io2/gp3 提高基线；临时缓解可增大 `tickTime`/`syncLimit`（需滚动重启，只是把阈值放宽、不治本）
- **预防**：`dataLogDir` 与 `dataDir` 分离且独占；把 `zk_fsynctime` p99 当一等信号监控（**>50ms 即预警，持续 >200ms 进入心跳丢失风险带**）

> ⚠️ 排障易踩的坑：该告警有个**长期存在的拼写错误**——官方写的是 `adversely effect`（不是 affect）。用 `grep "adversely affect"` 会**漏掉所有行**。
> 对应速查条目：[09-排障速查手册.md · 症状 1](09-排障速查手册.md)

### 故障模式 2：GC 停顿级联（JVM STW 引发会话过期与重选举）

- **症状（可观测）**：会话**成批**过期、`zk_num_alive_connections` 呈 V 形（骤降后反弹）、无网络原因却发生 leader 变更、`zk_jvm_pause_time_ms` p99 与 `zk_avg_latency` **同步上升而磁盘 IO 平稳**
- **根因**：Full GC 冻结整个进程——不发心跳、不处理请求、不过半 ACK。若暂停超过 `syncLimit × tickTime`（默认 **10 秒**），follower 判定 leader 死亡并发起选举；客户端心跳窗口内收不到响应则会话过期、**临时节点消失**、watch 批量触发
- **排查路径**：
  1. `echo mntr | nc localhost 2181 | grep -E 'zk_.*jvm_pause'` 看暂停时间（**该指标需 3.6+**；低版本只能靠 GC 日志，故 GC 日志必须常开）
  2. `jstat -gcutil` 看 Old 区是否触顶、Full GC 是否频繁
  3. 检查堆是否够：`zk_znode_count`、`zk_approximate_data_size` 是否已长进堆预算
  4. 检查 THP（`cat /sys/kernel/mm/transparent_hugepage/enabled`）与 swap（`swappiness`）
- **修复**：先治数据树（清理无界 znode）或换收集器（G1GC/ZGC），**再**考虑加堆——堆越大单次 Full GC 越长
- **预防**：禁用 THP 与 swap；GC 日志常开；`zk_jvm_pause_time_ms` p99 应**远低于** `minSessionTimeout`（默认 `2 × tickTime = 4000ms`）

> 对应速查条目：[09-排障速查手册.md · 症状 2](09-排障速查手册.md)

### 故障模式 3：连接被静默拒绝（maxClientCnxns 触顶）

- **症状（可观测）**：客户端报 connection refused / 超时；服务端日志 `Too many connections from /IP - max is 60`；**但 `zk_num_alive_connections` 看起来正常**（因为限制是**按源 IP** 计的）
- **根因**：`maxClientCnxns` 默认 **60/单 IP**。容器环境多 Pod 共享宿主 IP、或 NAT 网关后多个 JVM，极易触顶。**超限后新连接被静默拒绝**（默认无客户端可见错误）
- **排查路径**：
  1. 服务端日志搜 `Too many connections`
  2. 客户端侧 `netstat -n | grep :2181 | wc -l` 数实际连接
  3. 在问题宿主上 `netstat -nape | awk '{if ($5=="zk_ip:2181") print $4,$9}' | sort | uniq -c` 定位是哪个进程在开连接
- **修复**：提高 `maxClientCnxns`（如 200，或设 0 取消限制）后滚动重启；**根因通常是客户端连接泄漏**——每个 ZK handle 就是一个会话，只应在收到 **SESSION_EXPIRED** 时新建会话
- **预防**：复用长连接；监控 `zk_connection_rejected`（生产任何非 0 速率都要告警）；容器环境提前调高该值

> 对应速查条目：[09-排障速查手册.md · 症状 3](09-排障速查手册.md)

### 故障模式 4：会话过期风暴（临时节点惊群）

- **症状（可观测）**：大量客户端同时报 `KeeperErrorCode = Session expired`；`zk_num_alive_connections` V 形；`zk_ephemerals_count` 骤降、`zk_stale_sessions_expired` 跳升；`zk_packets_sent` 激增（watch 通知）而无对应 receive
- **根因**：网络事件 / LB 空闲超时 / 客户端 GC 导致**大批会话同时过期** → 临时节点被批量删除、watch 批量触发、所有客户端**同时重连**（thundering herd）。下游反应最剧烈：Kafka 注销 broker、HBase 重分配 region、**全机群的锁丢失**
- **排查路径**：
  1. 先确认**触发源是否还在**（网络分区 / 客户端 GC / leader 切换循环）——源还在就会不断自续
  2. `zk_outstanding_requests` 是否逼近 `globalOutstandingLimit`（默认 1000）→ leader 被重连潮打满
  3. `zk_connection_rejected` 是否非 0 → 重连又被 maxClientCnxns 挡住
  4. 检查 **LB 空闲超时**是否短于协商后的会话超时（空闲的 ZK 连接被 LB 掐断）
- **修复**：先止血（修网络 / 让客户端降堆压 / 解决 leader 抖动）；必要时在网络层限速重连；风暴后若 `zk_ephemerals_count` 不回落而连接数已恢复 → 怀疑**陈旧临时节点**，用 `dump` 确认所属会话已消失后手工清理（⚠️ 破坏性操作，需与业务方确认）
- **预防**：`dataLogDir` 独占低延迟盘（fsync 停顿是 leader 切换的主因，leader 切换是会话风暴的主因）；客户端把 LB 空闲超时调到大于会话超时；协商后的会话超时被服务端钳在 `[2×tickTime, 20×tickTime]`，客户端请求更短会**静默拿到下限**

> 对应速查条目：[09-排障速查手册.md · 症状 4](09-排障速查手册.md)

### 故障模式 5：无法加载数据库 / 启动即崩

- **症状（可观测）**：启动日志 `FATAL Unable to load database on disk` + `java.io.IOException: Failed to process transaction type: 2 error: KeeperErrorCode = NoNode`；或 `Unreasonable length = 1048583`
- **根因**：两类——① 事务日志/快照**损坏**（磁盘满、非正常关机）；② **`Unreasonable length`** 是 jute 反序列化时长度超限：`jute.maxbuffer` 默认 **1048575 字节（1MB）**，服务端允许客户端写入比它能读回的更大的 znode（ZOOKEEPER-1513 相关）
- **排查路径**：
  1. 看 FATAL 行的具体 IOException 类型
  2. `Unreasonable length` → 检查是否有超大 znode；客户端日志搜 `Packet len is out of range`
  3. 损坏 → 确认**另外两个节点是否健康**
- **修复**：
  - 损坏且**其他节点健康**：备份后清空该节点 `version-2` 目录，重启让它从 leader 全量同步
  - `Unreasonable length`：调大 `jute.maxbuffer`（客户端与服务端**都要一致**，否则客户端能写、服务端读不回），但**根本解是别往 ZK 放大对象**
- **预防**：配置 `autopurge`（默认**不清理**，是 operator 责任）；监控 `dataDir`/`dataLogDir` 磁盘余量；禁止写入超过 KB 级的数据

> 对应速查条目：[09-排障速查手册.md · 症状 5](09-排障速查手册.md)

### 故障模式 6：反复重选举（选举风暴）

- **症状（可观测）**：多节点 `zk_looking_count` 在**同一时间窗内**递增；`zk_sum_leader_unavailable_time` 持续增长（写入不可用）；节点卡在 LOOKING
- **根因**：三类主因按概率排——① **fsync 停顿**（最常见）；② **GC 暂停**超过 `syncLimit × tickTime`；③ **网络/端口问题**（两个集群端口 2888/3888 **必须两两互通**，只通一个会导致"能选出主但故障后无法重选"）。版本相关：3.5.7 及更早的 3 节点集群有 ZOOKEEPER-2164（leader 关闭时剩余两节点投票超时），已在 3.5.8/3.6.1/3.7.0 修复；服务网格 sidecar（Envoy/Istio）引入的连接超时也会触发（ZOOKEEPER-3923）
- **排查路径**：
  1. 确认是风暴还是单次——多节点同窗口递增才是循环
  2. 把选举时间戳与 `zk_p99_fsynctime` 对齐 → 相关则是磁盘
  3. 与 `zk_p99_jvm_pause_time_ms` 对齐 → 相关则是 GC
  4. 都无关 → 查 `zk_p99_quorum_ack_latency` 是否特定 follower 尖刺；检查**两两端口连通性**与 DNS
- **修复**：按根因分别治（分离 dataLogDir / 调 GC / 修网络与防火墙）；若为已知版本缺陷则升级
- **预防**：把 fsync 与 GC 暂停当一等信号；`zk_looking_count` 按**速率**告警（绝对值无意义）；在维护窗口**主动演练** failover（停 leader 进程，确认在预期时间内重选——⚠️ 会真实停止写入，仅低峰做）

> 对应速查条目：[09-排障速查手册.md · 症状 6](09-排障速查手册.md)

## ✅ 落地 Checklist

> 投产 / 上线前逐项打勾。

**硬件与部署**
- [ ] `dataLogDir` 与 `dataDir` **分离**，事务日志盘**独占低延迟设备**，不与高 IO 组件共享
- [ ] 集群规模 **2F+1**（3 或 5），具备故障独立性（不同机架/交换机/电源）
- [ ] 禁用 swap 与 Transparent Huge Pages
- [ ] 堆大小按 znode 数/连接数/watch 数评估并压测（常见 2–4GB 起）

**配置**
- [ ] 配置 `autopurge.snapRetainCount` / `autopurge.purgeInterval`（**默认不清理**）
- [ ] 4lw 白名单已配（3.5.3+ 默认仅 `srvr`），`mntr`/`stat` 可用
- [ ] `maxClientCnxns` 按容器/NAT 场景调高（默认 60/单 IP）
- [ ] 客户端与服务端 `jute.maxbuffer` **一致**（若确有大 znode）
- [ ] 防火墙放行 **2181（客户端）、2888（follower→leader）、3888（选举）**，且**两两互通**

**可观测**
- [ ] 采集 `zk_fsynctime` p99、`zk_jvm_pause_time_ms` p99（最常被漏采的两个）
- [ ] 采集 `zk_outstanding_requests`、`zk_looking_count`（按速率）、`zk_sum_leader_unavailable_time`
- [ ] 采集 `zk_znode_count`、`zk_approximate_data_size`（数据树慢性增长）
- [ ] 告警：`zk_connection_rejected` 非 0、无 leader 超 60s、磁盘余量

**客户端**
- [ ] **复用长连接**，不每次任务新建 handle
- [ ] 只在收到 **SESSION_EXPIRED** 时新建会话（不是任何连接状态变化都新建）
- [ ] watch 回调里**重新注册**；重连后**全量重读**而非只信增量
- [ ] 会话超时与 LB 空闲超时对齐（LB 超时 > 会话超时）
- [ ] 非幂等临界区**传 fencing token 到资源层**并校验
- [ ] 客户端 GC 日志开启（客户端 GC 是全机群会话过期的首要根因）

**预案**
- [ ] 回滚预案已就绪（配置变更可快速回退）
- [ ] 故障演练记录（停 leader 验证重选时间）
- [ ] 陈旧临时节点的**人工清理流程**已与业务方对齐（破坏性操作）

## 📰 真实事故案例复盘

### 案例 1：GitHub 双主事故（2020-10-09）

- **经过**：例行升级中重新供给 ZooKeeper 节点时，**新主机加入过快**，导致选出了第二个 leader，形成一个逻辑上独立的第二 ZK 集群。随后一个 Kafka broker 连到了这个新集群并**自举为 Kafka controller**，于是出现两个 Kafka 集群向客户端提供冲突的集群状态
- **根因**：供给流程问题——节点加入过快，bootstrap 代码误判集群无主而触发选举；新节点占多数选出新 leader
- **损失**：约 **10%** 的后台任务服务写请求失败，持续 **2 小时 32 分**；因客户端重试与冗余队列存在，**无任务丢失**
- **教训**：① **集群扩缩容/升级要放慢节奏并自动化**，别一次加太多节点；② 这正是课 1"双主故障之夜"的现实版——**协调层出现两个权威，比协调层挂掉更危险**；③ Kafka 侧的教训是要有 DLQ 与幂等消费兜底
- **来源**：[GitHub Availability Report: October 2020](https://github.blog/2020-11-04-github-availability-report-october-2020)（核查于 2026-08）

### 案例 2：PagerDuty 的 "poison packet"（2015）

- **经过**：压测环境的 ZK 集群出现随机**全集群锁死**。表象是客户端锁超时、每个客户端到各节点有**几十个活跃会话**（正常仅 2 个），最终撞上单节点会话数上限。重启集群能恢复但无法复现，一度担心会发生在生产
- **根因**：**四个 bug 叠加**——两个在 ZooKeeper，两个在 Linux 内核。直接触发是 leader 日志里的 `java.lang.OutOfMemoryError: Java heap space`（栈在 `BinaryInputArchive.readString`）；深层涉及 IPSec NAT-T 传输模式下**不校验 TCP 校验和**（RFC 3948），导致损坏的包被当作合法数据传给 ZK，ZK 按长度字段读出一个巨大字符串 → OOM
- **损失**：压测环境集群锁死；生产环境侥幸未触发（发现及时）
- **教训**：① **客户端会话数异常膨胀**是重要信号，别只盯服务端；② "随机全集群锁死"这类现象往往是**多因叠加**，单看一层无解；③ 堆 OOM 的栈指向 `readString` 时，要怀疑**输入数据本身已损坏**而非单纯堆不够
