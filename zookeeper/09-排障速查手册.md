## 🔴 症状 1：写停顿 / fsync 超时

**一眼识别**：日志 `fsync-ing the write ahead log in SyncThread:0 took 1234ms which will adversely effect operation latency`；`zk_outstanding_requests` 持续非 0 并攀升；**写延迟飙升但 follower 读延迟正常**

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 若磁盘被其他进程打满：临时移走高 IO 负载；云盘突发额度耗尽则临时提升 IOPS | 写延迟回落，`zk_outstanding_requests` 归零 |
| 定位 1 | `grep "fsync-ing the write ahead log" zookeeper.log \| tail -20` | 出现该行即确认；**注意官方拼写是 `effect` 不是 `affect`**，grep 时用 effect |
| 定位 2 | `iostat -x 1 5` 看事务日志盘 | `%util` 接近 100 → 磁盘瓶颈 |
| 定位 3 | 检查 `zoo.cfg` 的 `dataLogDir` 是否与 `dataDir` 分离、是否共享盘 | 未分离或共享 → 根因在此 |
| 修复 | 把 `dataLogDir` 迁到**独占低延迟盘**；云上提升预置 IOPS | fsync p99 降到 <50ms，告警消失 |
| 若无效 | → 转「**症状 6**」（fsync 停顿常表现为反复重选举）/ 转 `debug` 现场排查 | — |

> **临时缓解**（不治本，需滚动重启）：增大 `tickTime` / `syncLimit`，把心跳预算放宽。
> **预防**：`dataLogDir` 独占且与 `dataDir` 分离；把 `zk_fsynctime` p99 当一等信号（>50ms 预警，持续 >200ms 进入心跳丢失风险带）
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 1

## 🔴 症状 2：GC 停顿级联（会话成批过期 + 无因切主）

**一眼识别**：会话**成批**过期；`zk_num_alive_connections` 呈 V 形（骤降后反弹）；无网络原因却发生 leader 变更；**`zk_jvm_pause_time_ms` p99 与 `zk_avg_latency` 同步上升，而磁盘 IO 平稳**

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 若暂停持续：临时减小数据树（清理无界 znode）或摘掉该节点流量 | 暂停时间下降，会话停止过期 |
| 定位 1 | `echo mntr \| nc localhost 2181 \| grep -E 'zk_.*jvm_pause'`（**3.6+**） | p99 逼近 `2×tickTime`(默认 4000ms) → 确认 GC 是根因 |
| 定位 2 | `jstat -gcutil <pid> 1000 5` | Old 区持续接近 100%、FGC 频繁 → 堆不足或泄漏 |
| 定位 3 | `cat /sys/kernel/mm/transparent_hugepage/enabled`；`cat /proc/sys/vm/swappiness` | THP=always 或 swappiness 高 → 暂停被放大 |
| 修复 | 先治数据树或换收集器（G1GC/ZGC），**再**考虑加堆 | `zk_jvm_pause_time_ms` p99 远低于 4000ms |
| 若无效 | → 转「**症状 4**」（会话过期风暴是 GC 的下游后果）/ 转 `debug` | — |

> ⚠️ **加堆的陷阱**：堆越大单次 Full GC 越长。优先治数据树、换收集器，**最后**才加堆。
> **预防**：禁用 THP 与 swap；GC 日志常开；把 `zk_jvm_pause_time_ms` p99 纳入监控（这是**最少被采集**的关键指标）
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 2

## 🟡 症状 3：连接被静默拒绝

**一眼识别**：客户端报 connection refused / 超时；服务端日志 `Too many connections from /x.x.x.x - max is 60`；**但 `zk_num_alive_connections` 看起来正常**

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 在 `zoo.cfg` 提高 `maxClientCnxns`（如 200，或 0 取消限制）后**滚动重启** | 客户端恢复连接 |
| 定位 1 | 服务端日志搜 `Too many connections` | 出现即确认（**限制是按源 IP 计的**） |
| 定位 2 | 客户端宿主：`netstat -n \| grep :2181 \| wc -l` | 数出实际连接数 |
| 定位 3 | `netstat -nape \| awk '{if ($5=="<zk_ip>:2181") print $4,$9}' \| sort \| uniq -c` | 定位是哪个进程在开大量连接 |
| 修复 | 调高 `maxClientCnxns`；**根因通常是客户端连接泄漏**——修客户端：复用长连接，只在 **SESSION_EXPIRED** 时新建会话 | 连接数稳定，`zk_connection_rejected` 归零 |
| 若无效 | → 转「**症状 4**」（重连潮会再次撞上此限制）/ 转 `debug` | — |

> ⚠️ **容器环境特别提示**：多 Pod 共享宿主 IP 时，默认 60 **极易**触顶，且新连接被**静默拒绝**（服务端默认无客户端可见错误）。
> **预防**：监控 `zk_connection_rejected`（生产任何非 0 速率都告警）；容器环境提前调高该值
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 3

## 🔴 症状 4：会话过期风暴（临时节点惊群）

**一眼识别**：大量客户端同时报 `KeeperErrorCode = Session expired`；`zk_ephemerals_count` 骤降、`zk_stale_sessions_expired` 跳升；`zk_packets_sent` 激增（watch 通知）而无对应 receive

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | **先掐断触发源**：修网络分区 / 让客户端降堆压 / 解决 leader 抖动。源还在就会不断自续 | 新会话停止过期 |
| 定位 1 | 检查 `zk_outstanding_requests` 是否逼近 `globalOutstandingLimit`(默认 1000) | 逼近 → leader 被重连潮打满 |
| 定位 2 | 检查 `zk_connection_rejected` 是否非 0 | 非 0 → 重连又被 maxClientCnxns 挡住（转**症状 3**） |
| 定位 3 | 检查 **LB 空闲超时**是否短于协商后的会话超时 | LB 掐断空闲 ZK 连接 → 会话丢失 |
| 修复 | 修触发源；必要时在网络层限速重连（临时防火墙规则控速，需与业务方协同） | 连接数回到基线，`zk_ephemerals_count` 恢复 |
| 若无效 | 风暴后 `zk_ephemerals_count` 不回落而连接数已恢复 → **陈旧临时节点**：`echo dump \| nc ... ` 确认会话已消失后手工删除（⚠️ 破坏性，需与业务方确认） | — |

> ⚠️ **ZK 恢复 ≠ 下游恢复**：Kafka（KRaft 前）会注销 broker 并触发分区 leader 变更；HBase 会重分配 region；**全机群的锁都会丢**。要分别盯下游。
> **预防**：`dataLogDir` 独占；客户端 LB 空闲超时 > 会话超时；协商超时被服务端钳在 `[2×tickTime, 20×tickTime]`，客户端请求更短会**静默拿到下限**
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 4

## 🔴 症状 5：无法加载数据库 / 启动即崩

**一眼识别**：启动日志 `FATAL Unable to load database on disk`；伴随 `java.io.IOException: Failed to process transaction type: 2 error: KeeperErrorCode = NoNode`，或 `java.io.IOException: Unreasonable length = 1048583`

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 该节点先不启动，确认**另外两个节点健康**（`echo stat \| nc <ip> 2181`） | 集群仍有过半可用，业务未中断 |
| 定位 1 | 看 FATAL 行的 IOException 类型 | `NoNode` → 日志/快照损坏；`Unreasonable length` → znode 超 1MB |
| 定位 2 | `Unreasonable length`：客户端日志搜 `Packet len is out of range` | 出现 → 写入了超过 `jute.maxbuffer` 的 znode |
| 修复 A（损坏） | **备份后**清空该节点 `version-2`（快照+事务日志），重启 → 从 leader 全量同步 | 节点重新加入并同步完成 |
| 修复 B（超大） | 调大 `jute.maxbuffer`（**客户端与服务端必须一致**），但根本解是**别往 ZK 放大对象** | 能读回该 znode |
| 若无效 | → 转 `debug` 现场取证（可能需从备份恢复） | — |

> ⚠️ 清空 `version-2` 是**有损操作**，仅在**其他节点健康**时做，且必须先备份。
> **预防**：配置 `autopurge`（**默认不清理，是 operator 责任**）；监控磁盘余量；禁止写入超过 KB 级数据
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 5

## 🔴 症状 6：反复重选举（选举风暴）

**一眼识别**：多节点 `zk_looking_count` 在**同一时间窗内**递增；`zk_sum_leader_unavailable_time` 持续增长（写入不可用）；节点反复在 LOOKING/FOLLOWING/LEADING 间切换

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 若为计划内滚动重启：抑制选举告警，用 `zk_sum_leader_unavailable_time` 兜底；非计划则先定位 | 区分"正常维护"与"真风暴" |
| 定位 1 | 多节点同窗口递增才是**循环**；单节点递增可能只是它重启了 | 确认真风暴 |
| 定位 2 | 把选举时间戳与 `zk_p99_fsynctime`、`grep "fsync-ing the write ahead log"` 对齐 | fsync 尖刺紧邻每次 LOOKING → **磁盘**是触发源（转**症状 1**） |
| 定位 3 | 与 `zk_p99_jvm_pause_time_ms` 对齐（阈值 `syncLimit×tickTime`，默认 10s） | GC 暂停临近 10s → **GC** 是触发源（转**症状 2**） |
| 定位 4 | 都无关 → 查 `zk_p99_quorum_ack_latency`；检查 **2888/3888 是否两两互通**（只通一个会"能选出主但故障后无法重选"）；检查 DNS 与 sidecar（Envoy/Istio，ZOOKEEPER-3923） | 定位网络/端口问题 |
| 修复 | 按根因分别治：分离 dataLogDir / 调 GC / 修网络与防火墙；已知版本缺陷（3.5.7 及更早 3 节点，ZOOKEEPER-2164）→ 升级到 3.5.8+/3.6.1+/3.7.0+ | 选举停止，`zk_looking_count` 速率归零 |
| 若无效 | → 转「**症状 7**」/ 转 `debug` | — |

> **预防**：fsync 与 GC 暂停当一等信号；`zk_looking_count` 按**速率**告警（绝对值无意义）；维护窗口主动演练 failover（⚠️ 会真实停止写入，仅低峰做）
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 6

## 🔴 症状 7：仲裁丢失 / 选举端口不通

**一眼识别**：**无**任何节点报 `zk_server_state = leader` 超过 60s；多节点卡在 LOOKING；日志 `Cannot open channel to N at election address`；写请求全部失败

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 恢复失联节点（重启 / 修网络）；若无法立即恢复，业务侧降级为只读 | 至少 `floor(N/2)+1` 个节点互通 |
| 定位 1 | `echo srvr \| nc <每个节点> 2181 \| grep Mode` | 全部 `looking` 或无 leader → 确认仲裁丢失 |
| 定位 2 | 在每个节点测**两两**连通：`nc -vz <peer_ip> 2888` 与 `nc -vz <peer_ip> 3888` | 3888（选举端口）不通 → 根因 |
| 定位 3 | 若用主机名配置：`nslookup <peer_host>` | DNS 抖动会被误判为网络分区 |
| 修复 | 放行 3888（选举）与 2888（follower→leader）**两两互通**；修 DNS 或改用 IP | 重新选出 leader，写入恢复 |
| 若无效 | → 转 `debug` 现场取证 | — |

> ⚠️ **本手册唯一"看起来像网络问题但常是配置问题"的条目**：只通 2181 不通 3888 时，集群**平时完全正常**，直到需要选举才暴露。
> **预防**：部署后例行验证**两两**端口连通（不只从 leader 往外测）；告警"无 leader 超 60s"
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 6

## 📌 排查通用起手式（症状未命中索引时用）

```bash
# 1) 角色与存活
for h in zk1 zk2 zk3; do echo "== $h =="; echo srvr | nc $h 2181 | grep -E 'Mode|Connections|Latency'; done

# 2) 关键指标快照
echo mntr | nc localhost 2181 | grep -E 'zk_(server_state|outstanding_requests|num_alive_connections|connection_rejected|znode_count|approximate_data_size|ephemerals_count|watch_count)'

# 3) 暂停与磁盘（3.6+）
echo mntr | nc localhost 2181 | grep -E 'zk_.*(jvm_pause|fsynctime)'

# 4) 日志关键行
grep -E "fsync-ing|Too many connections|Unable to load|Unreasonable length|Cannot open channel|LOOKING|LEADING|FOLLOWING|OutOfMemoryError" zookeeper.log | tail -40

# 5) 系统与磁盘
iostat -x 1 3 ; df -h ; top -b -n 1 | head -20
```

> 查不到对应症状？→ **转 `debug` skill 现场取证**。本手册只预演**领域典型**失败模式，不负责定位你此刻的具体 bug。
