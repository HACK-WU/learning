# 反例对照：为什么“能跑”还不够

反例的共同特点是：开发环境里看起来合理，单用户测试也能通过；一旦遇到并发、
故障、恢复或租户边界，就失去原本的保证。阅读每一条时，先指出它破坏了哪个
不变量，再看项目实现如何补回。

## 1. 只保留 nightly pg_dump

~~~bash
0 3 * * * pg_dump -Fc order_service > /backup/order_service.dump
~~~

| 对照项 | 反例 | 项目做法 |
|---|---|---|
| 恢复粒度 | 只能回到某个 dump 时刻 | base backup + WAL 可回到命名恢复点 |
| 全局对象 | 角色/表空间不在普通 dump 中 | 单独保存 globals-only |
| 恢复速度 | 大库逻辑重放较慢 | 额外准备物理 base backup |
| 证明方式 | “文件存在” | 独立恢复库并查询行数，隔离实例做 PITR |

文件大小正常不等于恢复可用。至少要定期做一次真实恢复并记录耗时。

## 2. 先 SELECT 库存，再在应用里 UPDATE

~~~sql
BEGIN;
SELECT stock FROM orders.products WHERE product_id = 101;
-- 应用层判断 stock >= 1
UPDATE orders.products SET stock = stock - 1 WHERE product_id = 101;
COMMIT;
~~~

两个会话可能读到同一个旧值，然后都执行扣减。事务保证了各自的原子性，却没有
自动把跨语句的业务判断变成一个不可分割的不变量。

项目用：

~~~sql
UPDATE orders.products
SET stock = stock - wanted_quantity
WHERE product_id = wanted_product
  AND stock >= wanted_quantity
RETURNING product_id;
~~~

对同一商品的最后一件库存，scripts/concurrency.sh 实测 A=true、B=false、最终
库存为 0。若约束跨多行，还要设计锁顺序或重试策略；不能机械套用这一条 SQL。

## 3. 只靠每个接口都加 tenant_id

~~~sql
SELECT *
FROM orders.orders
WHERE tenant_id = :tenant_id
ORDER BY created_at DESC;
~~~

这条查询本身没有错，问题是系统里总会出现一条忘记谓词的导出、统计或新接口。
它把安全边界变成开发者记忆题。

项目做法是应用权限、RLS 和测试三层叠加。tenant_a_app 与 tenant_b_app
直接查询订单表时各自只能看到自己的行；postgres 管理员查询全量是明确的
超级用户例外。FORCE RLS 也不是“超级用户防火墙”，生产管理员身份必须另行
控制和审计。

## 4. 备库 streaming 就认为“已经安全”

~~~sql
SELECT state
FROM pg_stat_replication;
-- streaming
~~~

streaming 只说明当前有 WAL 流动，不代表：

- 已经没有 replay lag；
- 复制槽不会无限保留 WAL；
- WAL 归档没有连续失败；
- promote 后旧主库已经被隔离；
- 业务刚写入的数据已经可从备库读到。

项目巡检同时看 application_name、state、sync_state、三种 lag、槽 active 和
retained_wal；切换流程明确先 fencing，再 promote，再改流量入口。

## 5. archive_command 用 true“先让它不报错”

~~~conf
archive_command = 'true'
~~~

退出码总是 0，主库会认为每段 WAL 都已经成功归档；但实际上恢复端找不到文件，
PITR 链路在最需要它时断裂。项目使用“目标文件不存在才复制”的演示命令，并把
归档失败指标放进验收。生产环境应把归档目标换成持久、异地、可监控的介质。

## 6. 旧主库还活着就直接 promote

~~~bash
pg_ctl promote -D /var/lib/postgresql/data
# 立刻把客户端切到新主库
~~~

如果旧主库仍能接受写入，两个节点会形成两个时间线上的写分叉。项目不实现自动
切换，正是为了让 fencing 成为显式步骤：停止/隔离旧主库，确认客户端不会继续
写旧入口，再 promote 并重新建立复制。自动 HA 需要把这一顺序交给有仲裁和隔离
能力的编排器，而不是省略它。

## 7. 用 pg_restore -t 只恢复一张表

~~~bash
pg_restore -d order_service_restore -t orders.orders order_service.dump
~~~

表数据可能被恢复，但依赖的 schema、类型、函数、序列、外键和权限不一定齐全；
“单表恢复”不是“单表及其所有依赖恢复”。项目的自动验收使用完整 dump 恢复到
独立数据库；局部恢复只作为明确知道依赖图后的手术，不当作默认恢复策略。

## 8. 连接池把所有会话状态当成可复用

~~~sql
SET search_path = tenant_a;
PREPARE recent_orders AS
  SELECT * FROM orders.orders ORDER BY created_at DESC LIMIT 10;
~~~

若连接池复用会话而未清理状态，下一租户可能继承 search_path；若使用事务池，
依赖会话状态的 prepared statement、临时表或 LISTEN 也可能失效。项目不内置
PgBouncer，但设计决策要求在选择事务池前逐项审查这些状态，并由 RLS 作为最终
租户边界之一。

## 9. 反例使用纪律

反例不是让学习者在生产库上故意执行事故。可以用本项目的初始化卷、独立恢复库、
事务回滚和隔离容器来复现；每次实验都要保留“触发条件—观测证据—恢复动作—
残留风险”四列记录。
