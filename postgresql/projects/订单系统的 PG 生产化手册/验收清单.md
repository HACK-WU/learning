# 订单系统的 PG 生产化手册 · 验收清单

这份清单不是“看过文档”的清单，而是“执行过、看到证据、能解释边界”的清单。
建议先不看设计决策结论，完成每项后再回看原因。所有命令都从本文件所在项目的
实现目录执行。

## A. 环境与可复现性

- [ ] docker info 成功，Docker daemon 可用。
- [ ] docker compose -p pg-capstone -f docker-compose.yml config --quiet 成功。
- [ ] 宿主机 15432、15434 可用，或已在 .env 修改为不冲突端口。
- [ ] bash scripts/up.sh 成功，primary 与 standby 均为 healthy。
- [ ] 能解释为什么 down -v 只允许对 pg-capstone 执行。

~~~bash
cd postgresql/projects/订单系统的\ PG\ 生产化手册/实现
docker info
docker compose -p pg-capstone -f docker-compose.yml config --quiet
bash scripts/up.sh
~~~

## B. 业务数据正确性

- [ ] orders、order_items、order_events 的行数相等或符合本项目种子关系。
- [ ] 每个订单的 total_amount 都能由明细的 quantity × unit_price 重算。
- [ ] 同一 idempotency_key 调用两次 place_order，返回同一个 order_id。
- [ ] 订单状态、库存非负、金额精度等 CHECK/UNIQUE/FK 约束存在并能解释。
- [ ] 能用 order-report.sql 输出键集分页、窗口排名、递归分类树和 JSONB 标签。

~~~bash
bash scripts/verify.sh
docker compose -p pg-capstone -f docker-compose.yml exec -T primary \
  psql -X -U postgres -d order_service -f /dev/stdin < sql/order-report.sql
~~~

## C. 并发、事务与安全

- [ ] 两个并发会话竞争一件库存时，恰好一个返回 true，最终库存为 0。
- [ ] 能说明条件 UPDATE 如何把“库存足够”和“扣减”合并成一个写条件。
- [ ] 能指出若约束扩展到多行，何时需要锁顺序、SELECT FOR UPDATE 或重试。
- [ ] tenant_a_app 只能读租户 A，tenant_b_app 只能读租户 B。
- [ ] app_runtime 不是超级用户，业务写入经由安全定义函数。
- [ ] 能解释 FORCE RLS 对表所有者、超级用户和 BYPASSRLS 角色的边界。
- [ ] 能解释为什么演示凭据不能直接用于生产。

~~~bash
bash scripts/concurrency.sh
bash scripts/verify.sh
~~~

## D. 复制与故障切换

- [ ] standby 的 pg_is_in_recovery() 为 true。
- [ ] primary 的 pg_stat_replication 中 application_name 为
  pg-capstone-standby 且 state 为 streaming。
- [ ] 物理复制槽 active，能观察 retained WAL。
- [ ] primary 与 standby 的订单行数最终一致。
- [ ] 能说清 walreceiver、startup、walsender 各自处于哪一侧。
- [ ] 能说明异步复制存在 RPO 窗口，streaming 不等于“数据已安全”。
- [ ] 能写出 promote 前必须执行的 fencing、流量切换和回切步骤。

~~~bash
docker compose -p pg-capstone -f docker-compose.yml exec -T primary \
  psql -X -U postgres -d order_service -c \
  "SELECT application_name,state,sync_state FROM pg_stat_replication;"
docker compose -p pg-capstone -f docker-compose.yml exec -T primary \
  psql -X -U postgres -d order_service -c \
  "SELECT slot_name,active FROM pg_replication_slots;"
~~~

## E. 备份、恢复与 PITR

- [ ] bash scripts/backup.sh 生成 custom dump、globals.sql 和非零大小的
  base.tar.gz。
- [ ] bash scripts/restore-logical.sh 在独立恢复库恢复成功，并输出订单行数。
- [ ] 能说明普通 pg_dump 为什么不等于角色/表空间/全局对象备份。
- [ ] bash scripts/pitr.sh 能从基础备份和 WAL 归档启动隔离恢复实例。
- [ ] PITR 在命名恢复点停止，恢复点前 3 行存在，事故后的第 4 行不存在。
- [ ] 能说明 recovery.signal、restore_command、recovery_target_name 和
  timeline 在这次演练中分别做什么。
- [ ] 能指出归档命令“总是返回成功但没有真正复制文件”的风险。

~~~bash
bash scripts/backup.sh
bash scripts/restore-logical.sh
bash scripts/pitr.sh
~~~

## F. 监控与性能

- [ ] monitor.sql 能看到连接等待、复制延迟/槽、WAL/checkpoint、表统计、
  数据库命中率和 pg_stat_statements。
- [ ] 能把症状“请求卡住”分流到连接、锁等待、复制、IO、慢语句五个入口。
- [ ] slow-query.sql 的真实计划能看到复合索引或 Index Only Scan；知道
  enable_seqscan=off 只用于证明索引可用，不能当生产调优开关。
- [ ] 能说明小表选 Seq Scan 可能是成本模型的合理决定。
- [ ] 能说明 n_dead_tup、autovacuum、ANALYZE 与统计信息之间的关系。

~~~bash
docker compose -p pg-capstone -f docker-compose.yml exec -T primary \
  psql -X -U postgres -d order_service -f /dev/stdin < sql/monitor.sql
docker compose -p pg-capstone -f docker-compose.yml exec -T primary \
  psql -X -U postgres -d order_service -f /dev/stdin < sql/slow-query.sql
~~~
