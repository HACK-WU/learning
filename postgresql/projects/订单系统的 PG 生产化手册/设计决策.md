# 设计决策记录

设计原则：先写业务不变量，再选 PostgreSQL 机制；先写失败时怎么办，再写正常
路径；所有“高可用”“安全”“备份”都必须有可观察证据。

## 决策 1：备份只做逻辑，还是逻辑 + 物理 + WAL？

### 选择

本项目三者都做：

- pg_dump custom 格式 + pg_restore：用于迁移、局部恢复和独立恢复库验证。
- pg_dumpall --globals-only：补上角色、密码和全局对象；单独的 pg_dump 不含它们。
- pg_basebackup + WAL 归档：用于整库物理恢复与 PITR。

### 为什么

三者解决的问题不同。逻辑备份能按对象恢复，但大库恢复速度与依赖顺序是成本；
物理备份启动快，却绑定大版本和数据目录结构；PITR 能把时间点放在误删之前，但
它要求基础备份之后的 WAL 链完整可取。只选一种，故障类型一变化就会失去能力。

### 代价与替代

这套方案要维护三条验证链、消耗更多存储，也必须监控 archive_command 的失败。
小型开发库可以只做逻辑备份；超大生产库可以由备份平台接管物理备份与 WAL，但
仍要保留一次真实恢复演练。若只需要跨版本迁移，逻辑备份通常比物理备份合适。

### 验收证据

scripts/backup.sh 生成三种文件；restore-logical.sh 在独立数据库恢复；pitr.sh
从基础备份和归档 WAL 恢复到 before_capstone_incident，且事故后的第 4 行不存在。

## 决策 2：异步复制、同步复制，还是自动 HA 编排？

### 选择

演练实现选择一主一备、异步物理流复制、物理复制槽和手工提升。真实生产建议按
业务 RPO/RTO 决定是否加同步副本和故障转移编排器；不把本项目的 Compose
脚本冒充自动 HA。

### 为什么

异步复制不把主库提交延迟绑在备库上，适合学习和大多数读扩展场景，但最后一段
未送达 WAL 可能丢失。同步复制能把提交确认与同步备库绑定，降低 RPO，却把备库
故障转化成写入延迟或阻塞。自动 HA 能缩短人工反应时间，但还要解决仲裁、脑裂、
fencing、服务发现和回切。

### 代价与替代

当前选择的代价是手工故障切换、异步 RPO 窗口和备库不保证读后写一致。若业务合同
要求接近零数据丢失，增加同步备库并明确 synchronous_commit / quorum；若要求
无人值守故障转移，增加 Patroni 类编排与外部仲裁，并先做双主防护演练。

### 不变量

- 写流量只有一个受信任 Primary。
- promote 前必须隔离或 fencing 旧 Primary。
- Standby 的 streaming、slot active、replay gap 和归档失败都必须进入监控。

## 决策 3：库存扣减用先查后改、行锁，还是条件 UPDATE？

### 选择

使用单条原子条件更新：

~~~sql
UPDATE orders.products
SET stock = stock - quantity
WHERE product_id = wanted_product
  AND stock >= quantity
RETURNING product_id, stock;
~~~

项目函数 orders.reserve_stock() 返回布尔值；返回 true 才继续创建订单明细。

### 为什么

数据库会在更新目标行上完成必要的行级冲突处理，并把“库存足够”与“扣减”放进
同一个写条件。两个并发会话争夺最后一件商品时，一个更新一行，另一个更新零行，
不会因为都先读到 1 而超卖。

### 代价与替代

条件 UPDATE 最适合一个局部库存不变量；若一次订单要锁定多个资源，必须规定锁
顺序或考虑 SELECT FOR UPDATE，避免死锁。若业务需要跨多行的复杂约束，可以考虑
更高隔离级别并准备 serialization failure 重试；不能因为“用了事务”就假定任意
业务不变量自动成立。

### 反例

先 SELECT stock，再在应用层判断，最后 UPDATE，是典型竞态窗口。对照实测见
反例对照.md 和 scripts/concurrency.sh。

## 决策 4：租户隔离用应用 WHERE、独立数据库，还是 RLS？

### 选择

订单表启用 RLS 和 FORCE RLS；tenant_a_app / tenant_b_app 各有显式策略，
策略把当前角色名映射到租户。应用运行角色不直接获得任意表写权限，统一调用
安全定义函数 place_order()。

### 为什么

应用过滤是必要的，但单靠每个 endpoint 都记得加 WHERE 是“漏一处就越权”的
脆弱边界。RLS 把租户谓词放到数据库层，报表角色和写函数还可以按职责获得更
小权限。独立数据库隔离更强，但租户数量增加后迁移、连接和运维成本明显上升。

### 代价与替代

RLS 会增加策略测试、角色上下文传递和排障复杂度；表所有者通常绕过 RLS，
超级用户和 BYPASSRLS 角色也不能被 FORCE RLS 当成安全边界，所以管理员连接
必须受控。若租户少且合规要求强，可选每租户数据库/集群；若只做单租户内部
系统，普通授权可能已足够。

### SECURITY DEFINER 纪律

- 函数内固定 search_path 为 pg_catalog, orders。
- 不接受任意表名或 SQL 片段。
- 只给应用执行函数的权限，不把基础表写权限顺手开放。
- 必须同时测试 tenant_a、tenant_b、postgres 三种身份，明确超级用户例外。

## 决策 5：大版本升级用 pg_upgrade、逻辑复制，还是 dump/restore？

### 选择矩阵

| 场景 | 首选 | 关键理由 | 主要代价 |
|---|---|---|---|
| 同机/同类存储、数据量大、停机窗口可接受 | pg_upgrade | 快，复用数据文件 | 需兼容扩展；新集群统计信息要重建 |
| 跨主机或要求低停机、可双写/追平 | 逻辑复制 | 可在线搬迁、可渐进切换 | 双写冲突、DDL、序列和一致性操作复杂 |
| 数据量小、迁移窗口宽 | dump/restore | 最直观、可重排对象 | 慢，需处理角色/权限/依赖 |

本项目不运行大版本升级，因为实现基线固定为 PG 17；但交付决策不能把
“pg_upgrade 更快”当成无条件答案。选定方案前还要做扩展兼容、回滚窗口、统计
信息重建和切换后验证。

## 6. 连接池的保留决策

应用连接必须有上限，项目把 max_connections 设为 50 并保留连接管理入口，
没有把客户端连接数无限透传给数据库。若引入 PgBouncer：

- 事务池适合无会话状态的短请求，可提高连接复用；
- 会话池适合临时表、session GUC、预备语句等依赖会话状态的应用；
- 切换到事务池前，必须逐项审查 SET、临时表、LISTEN、prepared statement
  和 advisory lock 的使用。

这是一个有条件的选择，不是“连接池一定更快”。

## 7. 结论

本项目把高风险能力做成了可运行的最小闭环：原子写入、RLS、异步复制、三类
备份、PITR 和巡检。它刻意把自动 HA、TLS、外部备份存储和连接池产品化留作
生产设计的下一阶段，防止学习工程在边界外做出虚假的安全承诺。
