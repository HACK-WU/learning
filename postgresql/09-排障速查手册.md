# PostgreSQL 排障速查手册

> 定位：使用态 QRH。你可以从症状直接跳到 S01-S10。每一项都按“先止血 → 一眼识别 → 分支定位 → 修复 → 升级出口”排列。
>
> 安全边界：生产环境先执行只读检查；终止会话、删除复制槽、切换主库、修改同步策略、删除归档文件都必须走已批准的变更或应急流程。示例账号、服务名和端口均为演示值。

## 0. 使用方法

### 先止血

1. 记下故障开始时间、受影响实例、业务症状和最近一次成功操作。
2. 暂停会放大故障的动作：批量写入、报表流量、自动重试、旧主写入或危险清理任务。
3. 只读采集会话、锁、复制、WAL、磁盘和日志证据。
4. 只有确认动作目标、回滚方法和业务影响后，才执行终止、删除、提升或降级。

## S01 备份成功但恢复缺角色或依赖

### 一眼识别

“导出成功”只证明文件生成，不证明新实例可用。看到 owner、role、extension、schema、sequence 或 permission denied 错误时，优先按 S01 处理。

### 先止血

- 停止在唯一生产库上反复试恢复；复制备份到隔离的临时实例。
- 保留原始 dump、globals、校验值和恢复日志。
- 不要为了让 restore 通过而把目标库临时开放成超级用户并把这个状态带入生产。

### 分支定位与动作

| 如果看到 | 先做什么 | 然后做什么 |
|---|---|---|
| role 或 owner 不存在 | 检查 globals 是否存在并读取角色清单 | 先创建角色，再恢复数据库对象 |
| extension 或类型不存在 | 对照源库扩展清单和目标库版本 | 在目标库安装兼容扩展，再重做恢复 |
| 单表恢复后约束、序列异常 | 停止局部补丁式恢复 | 用依赖清单决定补对象，或改做整库恢复 |
| restore 退出码为 0 但业务登录失败 | 用业务角色实际登录 | 验证 schema、表权限、默认权限和连接参数 |

~~~bash
pg_restore --list order.dump
psql -f globals.sql postgres
pg_restore --exit-on-error --dbname=order_restore order.dump
~~~

### 修复后验收

- 业务角色能登录。
- 关键表、序列、约束、函数和扩展存在。
- 订单查询、扣库存和租户隔离最小旅程通过。
- 恢复记录包含 dump、globals、版本、耗时和行数。

### 无法确认时的升级出口

缺少 globals、扩展版本不兼容或无法确定局部对象依赖时，停止继续操作，交给数据库负责人按整库恢复或重新建立基线处理。

来源：[实战经验 F01](08-实战经验.md#故障模式-f01备份成功但恢复时才发现缺角色或缺依赖) · [课 14](stages/5-运维与生产化/lessons/lesson-14-备份与恢复.md) · [项目恢复脚本](<projects/订单系统的 PG 生产化手册/实现/scripts/restore-logical.sh>)

## S02 PITR 成功但恢复到错误时间点

### 一眼识别

恢复实例正常启动、日志显示 recovery complete，但误删数据仍在，或目标点之后的事务也出现了。这里的关键不是“能启动”，而是“时间线和业务断言是否吻合”。

### 先止血

- 恢复实例先保持只读，不切换为生产写入口。
- 冻结“目标时间”的解释：时区、边界是否包含、事件发生时间和提交时间。
- 保存 recovery 日志、基础备份时间、WAL 范围和目标配置。

### 分支定位与动作

| 如果看到 | 先做什么 | 然后做什么 |
|---|---|---|
| 缺少目标时间前的行 | 检查目标时间是否早于事务提交时间 | 重新以明确时区和边界恢复 |
| 目标点后的行出现 | 检查 target 时间、WAL 和 timeline | 重新选择目标点并验证前后标记事务 |
| 日志显示找不到 WAL | 停止继续重放 | 评估从主库或其他归档介质补齐，不能假设连续 |
| 数据对了但新恢复实例写入异常 | 检查 timeline 和写入路由 | 隔离恢复实例，确认提升和路由步骤 |

~~~sql
SELECT pg_is_in_recovery();
SELECT pg_last_wal_replay_lsn();
~~~

### 修复后验收

- 用一条唯一标记事务验证目标点之前和之后的结果。
- 日志记录目标时区、目标参数、timeline 和恢复完成时间。
- 生产切换前完成只读验收和单一写入口确认。

### 无法确认时的升级出口

无法证明缺失 WAL 的连续性，或两条 timeline 已经产生业务分叉时，停止切换，进入数据仲裁和恢复负责人流程。

来源：[实战经验 F02](08-实战经验.md#故障模式-f02pitr-恢复完成了但停在了错误的时间点) · [课 14](stages/5-运维与生产化/lessons/lesson-14-备份与恢复.md) · [项目 PITR 脚本](<projects/订单系统的 PG 生产化手册/实现/scripts/pitr.sh>)

## S03 归档开启但 WAL 没有可靠落盘

### 一眼识别

archive_mode 是 on，但归档目录没有新文件，或 pg_stat_archiver.failed_count 持续增加。不要只看配置，要同时看统计、目录和容量。

### 先止血

- 暂停会清理归档目录的任务。
- 记录 failed_count、last_failed_wal、last_failed_time 和磁盘使用率。
- 不要手工删除 pg_wal 中的文件来“腾空间”。

### 分支定位与动作

| 如果看到 | 先做什么 | 然后做什么 |
|---|---|---|
| failed_count 增长 | 检查 archive_command 返回码、权限和目标容量 | 修复目标后用新 WAL 验证归档 |
| 统计无变化且目录无文件 | 检查是否真的产生新 WAL、配置是否 reload | 验证配置生效，再制造可控写入 |
| 目录有文件但恢复找不到 | 对照文件名、校验值和 WAL 时间范围 | 标记归档链路断点，重新建立基线 |
| 目标是远端存储 | 检查网络、挂载和幂等覆盖规则 | 按传输链路恢复，不在主库上绕过校验 |

~~~sql
SELECT archived_count, failed_count, last_archived_wal,
       last_failed_wal, last_failed_time
FROM pg_stat_archiver;
~~~

### 修复后验收

- 新产生的 WAL 在归档目标出现。
- 统计中的 last_archived_wal 前进，failed_count 不再增长。
- 用一次 PITR 演练证明归档文件确实可读可用。

### 无法确认时的升级出口

若关键时间段 WAL 已经缺失，立即标注 PITR RPO 受损，通知业务和负责人，重新做可恢复基线；不要宣称“备份仍然有效”。

来源：[实战经验 F03](08-实战经验.md#故障模式-f03归档看似开启wal-却没有可靠落盘) · [课 14](stages/5-运维与生产化/lessons/lesson-14-备份与恢复.md)

## S04 备库在运行但没有流复制

### 一眼识别

standby 的进程或容器是 running，不等于复制链路健康。备库 pg_stat_wal_receiver 返回 0 行，或主库 pg_stat_replication 没有目标，优先按 S04。

### 先止血

- 从备库摘除报表和读流量，避免使用陈旧数据。
- 不要直接删除备库数据目录；先保留日志和复制状态。
- 记录主库、备库、端口、LSN 和最后一次健康时间。

### 分支定位与动作

| 如果看到 | 先做什么 | 然后做什么 |
|---|---|---|
| 主库没有 standby 行 | 检查备库连接串、HBA、监听和网络 | 修复认证或网络后重连 |
| 主库有发送端，备库无接收端 | 检查备库日志和 primary_conninfo | 修复连接参数和复制用户 |
| 接收端存在但回放落后 | 比较 sent、write、flush、replay LSN | 降低备库负载并评估 WAL 是否足够 |
| WAL 已不在主库 | 停止局部修复 | 重新做 base backup 重建备库 |

~~~sql
SELECT * FROM pg_stat_replication;
SELECT * FROM pg_stat_wal_receiver;
~~~

### 修复后验收

- 主库有目标 standby，备库有 wal receiver。
- replay LSN 持续前进，延迟低于业务阈值。
- 重新验证关键表行数和只读查询一致性。

### 无法确认时的升级出口

复制链路已断且所需 WAL 缺失时，执行备库重建流程；在重建完成前不要把它列为可切换节点。

来源：[实战经验 F04](08-实战经验.md#故障模式-f04备库存在但实际上没有在流复制) · [课 15](stages/5-运维与生产化/lessons/lesson-15-复制与高可用.md) · [项目验收脚本](<projects/订单系统的 PG 生产化手册/实现/scripts/verify.sh>)

## S05 复制槽导致 WAL 和磁盘持续增长

### 一眼识别

pg_wal 增长、磁盘告警，且 pg_replication_slots 中某个 slot 的 restart_lsn 长时间不动。常见组合是 active=false + 下游已经废弃。

### 先止血

- 暂停非必要的大批量写入和日志放大任务。
- 立即确认磁盘余量、增长速度和 slot owner。
- 禁止直接删除 pg_wal 文件；禁止未确认归属就删除 slot。

### 分支定位与动作

| 如果看到 | 先做什么 | 然后做什么 |
|---|---|---|
| slot active=true 且下游仍需要 | 联系下游 owner | 恢复消费者，让 restart_lsn 推进 |
| slot active=false 且业务已废弃 | 留存 slot 详情和批准记录 | 删除明确无主的 slot |
| 下游要恢复但 WAL 快缺失 | 评估剩余 WAL 与恢复时间 | 尽快恢复或重建下游，必要时重新基线 |
| 磁盘已接近满 | 先保护主库可写空间 | 按应急预案处置无主 slot 和临时写入 |

~~~sql
SELECT slot_name, slot_type, active, restart_lsn,
       wal_status, safe_wal_size
FROM pg_replication_slots;
~~~

### 修复后验收

- restart_lsn 推进或已按批准流程删除无主 slot。
- pg_wal 增长回到可解释范围，磁盘有安全余量。
- 下游 CDC 或备库恢复并完成数据一致性校验。

### 无法确认时的升级出口

无法确认 slot 的业务归属，或磁盘已无安全余量时，升级给数据库负责人和业务 owner共同决策；不要自行删除。

来源：[实战经验 F05](08-实战经验.md#故障模式-f05复制槽把-wal-越积越多磁盘最终被打满) · [课 15](stages/5-运维与生产化/lessons/lesson-15-复制与高可用.md)

## S06 新主已提升但旧主仍接受写入

### 一眼识别

看到 promote 或 pg_is_in_recovery() = false，只能证明某个实例已不是 standby；若旧主仍在连接池、负载均衡或网络可达，就仍有 split brain 风险。

### 先止血

- 立即冻结双边写入，保留两边 timeline、LSN、连接和最近写入时间。
- 从服务发现、负载均衡、连接池和防火墙四层确认旧主流量。
- 不要把两边数据直接合并，也不要覆盖任一数据目录。

### 分支定位与动作

| 如果看到 | 先做什么 | 然后做什么 |
|---|---|---|
| 旧主仍有业务连接 | 摘除旧主写入口并清理连接池 | 只保留新主写入 |
| 旧主无应用连接但网络可达 | 执行批准的 fencing | 再开放新主流量 |
| 两边已有不同写入 | 停止自动回切 | 进入数据仲裁和业务补偿 |
| 新主回放未验收 | 保持写入口关闭 | 先做数据和单写入口验收 |

~~~sql
SELECT pg_is_in_recovery();
SELECT timeline_id, checkpoint_lsn, redo_lsn
FROM pg_control_checkpoint();
~~~

### 修复后验收

- 只有一个写入口和一个接受业务写入的 primary。
- 旧主已隔离，旧连接已失效，服务发现指向新主。
- 旧主后续按新主 base backup 重建，不直接回接。

### 无法确认时的升级出口

确认已经双写或 timeline 分叉时，停止自动化故障转移，升级给数据负责人、业务负责人和变更负责人共同仲裁。

来源：[实战经验 F06](08-实战经验.md#故障模式-f06提升新主后旧主仍然接受写入) · [课 15](stages/5-运维与生产化/lessons/lesson-15-复制与高可用.md) · [项目验收清单](<projects/订单系统的 PG 生产化手册/验收清单.md>)

## S07 同步复制导致写入等待

### 一眼识别

数据库进程正常、资源不高，但提交路径长时间不返回；同步备库恢复或切换策略后，写入延迟下降。不要把这种保护性等待直接判为数据库崩溃。

### 先止血

- 记录等待会话、业务错误率、同步候选和 RPO 影响。
- 暂停重试风暴和非关键批处理。
- 未经批准不要永久关闭同步复制。

### 分支定位与动作

| 如果看到 | 先做什么 | 然后做什么 |
|---|---|---|
| synchronous standby 不可用 | 验证是否为预期保护行为 | 恢复备库或按批准策略降级 |
| 备库可用但 flush 延迟大 | 检查备库 IO、网络和负载 | 修复备库瓶颈 |
| 等待事件是锁而非同步 | 转到 [S08](#s08-慢请求其实在等待锁) | 按阻塞链处理 |
| 降级后业务恢复 | 记录 RPO 变化 | 故障恢复后复原同步策略 |

~~~sql
SELECT pid, state, wait_event_type, wait_event, query
FROM pg_stat_activity
WHERE state <> 'idle';
~~~

### 修复后验收

- 提交延迟恢复到阈值内。
- 同步候选状态、RPO 和降级时间已记录。
- 备库重新健康后恢复原保护策略并验证。

### 无法确认时的升级出口

如果团队无法在“写入可用性”和“提交丢失风险”之间做出已授权选择，升级给业务 owner；数据库值班人员不要单方面改保护级别。

来源：[实战经验 F07](08-实战经验.md#故障模式-f07同步复制让写入停顿团队却误以为数据库挂了) · [课 15](stages/5-运维与生产化/lessons/lesson-15-复制与高可用.md)

## S08 慢请求其实在等待锁

### 一眼识别

接口慢、CPU 不高，pg_stat_activity 显示 wait_event_type = Lock，或者存在长事务、idle in transaction。此时先找 blocker，不要先建索引。

### 先止血

- 限制批量任务、DDL 和自动重试，防止阻塞链扩大。
- 记录 blocked pid、blocking pid、用户、SQL、xact_start 和业务请求。
- 终止会话前确认事务回滚代价和业务负责人。

### 分支定位与动作

| 如果看到 | 先做什么 | 然后做什么 |
|---|---|---|
| blocker 是 idle in transaction | 联系连接 owner 并按预案终止 | 修复事务边界和连接池复用 |
| blocker 是 DDL | 确认维护窗口和回滚方式 | 取消、完成或延后 DDL |
| wait_event 不是 Lock | 继续看连接、IO、CPU 和计划 | 不要强行按锁问题修复 |
| 阻塞消除后仍慢 | 执行 EXPLAIN (ANALYZE, BUFFERS) | 再决定索引、SQL 或统计信息动作 |

~~~sql
SELECT pid, pg_blocking_pids(pid) AS blockers,
       usename, state, wait_event_type, wait_event,
       xact_start, query_start, query
FROM pg_stat_activity
WHERE state <> 'idle'
ORDER BY xact_start NULLS LAST;
~~~

### 修复后验收

- blocker 消失，blocked 会话完成或被安全取消。
- 应用事务不再长期 idle in transaction。
- 真正的执行计划问题若存在，已用计划证据而非猜测修复。

### 无法确认时的升级出口

无法判断某个 blocker 是否可终止，或事务包含未补偿业务操作时，保留证据并升级给应用 owner 与数据库 owner共同决定。

来源：[实战经验 F08](08-实战经验.md#故障模式-f08慢查询其实是在等锁不是在跑坏计划) · [课 16](stages/5-运维与生产化/lessons/lesson-16-监控与性能.md) · [项目慢查询脚本](<projects/订单系统的 PG 生产化手册/实现/sql/slow-query.sql>)

## S09 PG17 监控 SQL 按旧字段失效

### 一眼识别

采集器报 column does not exist，或面板长时间 No data。PG 17 的统计职责和字段可能与旧版本不同，先定位版本和真实视图，再改查询。

### 先止血

- 标记受影响面板和告警为“观测失真”，不要把 No data 当作零。
- 保留采集器报错、数据库版本和最后一个正常指标时间。
- 升级期间不删除旧面板，直到新指标完成校验。

### 分支定位与动作

| 如果看到 | 先做什么 | 然后做什么 |
|---|---|---|
| column does not exist | 查询目标 PG 大版本与视图定义 | 对照 PG 17 官方视图改字段 |
| SQL 能跑但无数据 | 检查权限、过滤条件和采集时间 | 以可控事件验证指标变化 |
| exporter 报错但面板正常 | 检查缓存和时间序列更新时间 | 修复采集链路，不相信旧缓存 |
| 只有一个面板异常 | 对照查询、变量和版本映射 | 修复该面板并加回归测试 |

~~~sql
SELECT version();
SELECT * FROM pg_stat_checkpointer;
SELECT * FROM pg_stat_io LIMIT 1;
~~~

### 修复后验收

- 采集器无错误，查询返回非空结果。
- 人为制造可控事件后，指标按预期变化。
- 面板、告警、版本说明和测试一起更新。

### 无法确认时的升级出口

无法确认指标含义是否等价时，暂时标记告警不可用并升级；不要用旧字段“凑出一个看似相近的数字”。

## S10 RLS 或安全函数边界错误

### 一眼识别

真实租户角色查询自己的数据为 0 行，或者能查询其他租户数据；SECURITY DEFINER 函数在某个 search_path 下正常、换环境后行为异常。优先按“角色—schema—表—policy—函数”五层排查。

### 先止血

- 立即停止可疑租户接口或降级到已验证的隔离路径。
- 保留 current_user、session_user、角色属性、policy、函数定义和审计记录。
- 不要用超级用户验证后就宣布隔离正确；超级用户不能代表租户角色。

### 分支定位与动作

| 如果看到 | 先做什么 | 然后做什么 |
|---|---|---|
| 自己租户也查不到 | 检查 schema USAGE、表 SELECT 和 policy 条件 | 用真实租户角色逐层补齐最小权限 |
| 能看到其他租户 | 检查表 owner、BYPASSRLS、FORCE RLS 和 USING | 收紧角色并补双租户负向测试 |
| 写入可改 tenant_id | 检查 WITH CHECK | 限制写入条件并验证跨租户 UPDATE |
| 安全函数结果异常 | 检查固定 search_path、限定对象名、EXECUTE | 修复函数安全边界并撤销 PUBLIC 权限 |

~~~sql
SELECT current_user, session_user;
SELECT rolname, rolsuper, rolbypassrls
FROM pg_roles
WHERE rolname = current_user;
~~~

### 修复后验收

- 租户 A 只能读写 A，租户 B 只能读写 B。
- 租户 A 不能通过修改参数、写入 tenant_id 或函数调用触达 B。
- 管理员路径单独验收，且不会成为普通应用连接角色。

### 无法确认时的升级出口

发现可能越权时，先按安全事件处理：停用路径、保留审计证据、通知安全与业务负责人；不要边猜边修改 policy。

## 3. 交班与复盘模板

发生需要升级的故障时，用下面的最小字段交班：

| 字段 | 内容 |
|---|---|
| 时间线 | 开始时间、发现时间、当前时间，注明时区 |
| 影响 | 受影响接口、租户、读写能力、数据风险 |
| 实例 | 当前 primary、standby、版本、连接入口 |

| 已执行动作 | 止血动作、变更人、时间、结果、回滚方式 |
