# PostgreSQL 实战经验

> 定位：学习态。把课程里的概念压缩成“线上先看什么、为什么会这样、怎样避免再犯”的故障模式。
>
> 适用版本：PostgreSQL 17.x；本文的命令、视图和字段以本课程的 PG 17.11 实测环境为基线。生产环境若是其他大版本，先核对对应版本文档。
>
> 证据纪律：带有“本项目实测”的结论来自《订单系统的 PG 生产化手册》实现目录；其余结论均回指课程课件和 PostgreSQL 官方文档。示例中的主机名、端口、账号只用于演示，不代表真实生产凭据。

## 1. 先建立一张故障地图

生产问题通常不是单个参数错了，而是“目标没有说清楚”：

| 目标 | 先问的问题 | 主要证据 |
|---|---|---|
| 能不能恢复 | 备份文件是否存在，最近一次恢复演练是什么时候 | dump、globals、恢复日志、演练记录 |
| 能恢复到哪里 | 需要整库恢复、单表恢复，还是恢复到某一时刻 | RPO、RTO、WAL 连续性、时间线 |
| 能不能接管 | 备库是否真的追上，提升后旧主是否被隔离 | replication、replay LSN、fencing |
| 能不能继续写 | 写入停顿是同步复制保护，还是锁、连接、磁盘问题 | wait_event、连接数、WAL、磁盘 |
| 数据是否越权 | 查询结果错误来自应用过滤、RLS、角色属性，还是函数权限 | current_user、rolbypassrls、policy、search_path |
| 慢在哪里 | 是执行计划慢，还是排队等待资源 | pg_stat_activity、wait_event、EXPLAIN |

排障顺序固定为：

1. 保护数据和业务：先止血，禁止扩大故障面。
2. 采集只读证据：时间、实例、会话、WAL、复制、磁盘。
3. 用证据分支：不要把“看起来像”当成根因。
4. 修复后复测：恢复、复制、权限和并发都要验证最终状态。
5. 把结果写回 runbook：故障不能只留在聊天记录里。

快速入口见 [排障速查手册](09-排障速查手册.md)；需要在设计阶段比较多条路线时，见 [场景解法库](10-场景解法库.md)。

## 2. 十个高频生产故障模式

### 故障模式 F01：备份成功，但恢复时才发现缺角色或缺依赖

**症状**

- pg_dump 或 pg_dumpall 返回成功，文件大小也正常。
- 新环境执行 pg_restore 时出现 owner、role、extension、schema 权限相关错误。
- 表数据可能恢复了，但应用连接失败，或函数、默认权限、跨表依赖不完整。

**根因**

逻辑备份不是一个“只要有数据文件就够了”的整体。单库 dump 通常关注数据库对象和数据；全局对象、角色、表空间、密码属性等可能需要单独保存。只恢复某一张表还可能遗漏类型、函数、序列、约束和扩展依赖。备份命令成功，只能说明导出阶段完成，不能证明恢复目标可用。

**诊断路径**

1. 记录备份类型、生成时间、源库大版本和目标库大版本。
2. 分别检查业务 dump、globals 文件、扩展清单和数据库级参数。
3. 在临时实例执行全量恢复，再用业务查询验证行数、序列、约束、角色登录和最小权限。
4. 若只恢复局部对象，先列出依赖图，再决定是补依赖还是改用整库恢复。

**修复**

- 建立“业务 dump + globals + 恢复脚本”的配套产物。
- 恢复时先创建角色、扩展和目标数据库，再导入对象与数据。
- 恢复后执行最小业务旅程，而不是只看 pg_restore 的退出码。
- 对必须单表恢复的场景，明确允许的依赖范围和人工补齐步骤。

**预防**

- 每个备份周期至少做一次自动化恢复抽样；每个版本升级前做一次全量演练。
- 把恢复时间、恢复行数、关键约束和登录验证写成验收清单。
- 备份文件、globals、校验值和保留期限放在同一份清单里。

**来源与证据**

- 课程：[课 14《备份与恢复》](stages/5-运维与生产化/lessons/lesson-14-备份与恢复.md)
- 本项目：[backup.sh](<projects/订单系统的 PG 生产化手册/实现/scripts/backup.sh>)、[restore-logical.sh](<projects/订单系统的 PG 生产化手册/实现/scripts/restore-logical.sh>)；本项目实测同时产出 custom dump、globals 和 physical base.tar.gz，并完成逻辑恢复。
- 官方：[Backup and Restore](https://www.postgresql.org/docs/17/backup.html)

### 故障模式 F02：PITR 恢复完成了，但停在了错误的时间点

**症状**

- 恢复实例能启动，日志也显示 recovery complete，但业务仍包含误删后的数据，或缺少本应保留的事务。
- 恢复到某个时间点时，结果在边界附近反复变化。
- 新恢复实例的 timeline、恢复日志和预期目标时间对不上。

**根因**

PITR 的目标不是“把最近的备份打开”，而是“从基础备份沿连续 WAL 重放到指定时间线和目标”。目标时间区间、时区、事务提交时间、恢复信号位置、归档 WAL 完整性任何一个不明确，都可能得到一个合法但错误的状态。恢复完成只代表重放结束，不代表业务验收正确。

**诊断路径**

1. 先冻结恢复目标说明：目标时间使用 UTC 还是本地时区，目标是包含还是不包含边界事务。
2. 检查基础备份时间、WAL 起止范围、恢复日志中的 timeline 和 recovery target。
3. 在恢复实例执行关键业务断言：误删行不存在、误删前已提交行存在、恢复后的新写入禁止混入原时间线。
4. 若结果不符，换一个明确的目标时间重做，比较恢复前后事务边界。

**修复**

- 使用明确的 recovery target 配置，并把时区写入 runbook。
- 为演练准备一条带唯一标记的测试事务，验证能否恢复到它之前和之后。
- 恢复成功后先以只读方式验收，确认后再决定是否提升为新主。
- 为新时间线建立单独的归档目录和审计记录。

**预防**

- 定期做“指定时间点恢复”，不能只做 base backup 解压测试。
- 为 RPO 写成可测量的分钟数，为 RTO 写成从故障发现到业务可写的时间。
- 所有恢复日志和目标参数与演练结果一并留存。

**来源与证据**

- 课程：[课 14《备份与恢复》](stages/5-运维与生产化/lessons/lesson-14-备份与恢复.md)
- 本项目：[pitr.sh](<projects/订单系统的 PG 生产化手册/实现/scripts/pitr.sh>)；本项目实测恢复到目标点，恢复行数为 3，目标点之后的第 4 行不存在，日志出现 recovery stopping、new timeline 和 archive recovery complete。
- 官方：[Continuous Archiving and Point-in-Time Recovery](https://www.postgresql.org/docs/17/continuous-archiving.html)

### 故障模式 F03：归档看似开启，WAL 却没有可靠落盘

**症状**

- archive_mode 为 on，但归档目录没有新文件，或归档延迟持续增加。
- pg_stat_archiver 的 failed_count 增长，last_failed_time 更新。
- 备份文件存在，但用它做 PITR 时找不到关键 WAL。

**根因**

archive_command 的返回码是归档链路的关键契约。命令返回成功却没有把文件安全写入目标位置，或者目标目录权限、空间、挂载、网络存储发生问题，都会让“开启归档”变成假象。另一个常见误区是只看配置，不看归档统计和实际文件。

**诊断路径**

1. 只读查看 archive_mode、archive_command、archiver 统计和磁盘空间。
2. 对照 last_archived_wal、last_failed_wal、failed_count 与归档目录实际文件。
3. 检查归档目标是否可写、是否被清理任务误删、是否跨主机传输失败。
4. 先确认故障时间段缺失的 WAL 是否还能从主库 pg_wal 或备份介质找回。

**修复**

- 修复目录、权限、容量或传输链路，并验证命令对重复文件的幂等行为。
- 对关键归档目标增加校验、监控和失败告警。
- 不要手工删除主库仍可能需要的 WAL；保留策略应与复制槽、备库和备份窗口联动。
- 缺失 WAL 时标记 PITR 能力受损，重新建立可恢复基线。

**预防**

- 监控 failed_count、last_failed_time、归档延迟、归档目录容量。
- 用带唯一事务标记的演练验证“写入—归档—恢复”全链路。
- 把归档目标当作生产数据资产，采用独立权限、容量和生命周期策略。

**来源与证据**

- 课程：[课 14《备份与恢复》](stages/5-运维与生产化/lessons/lesson-14-备份与恢复.md)
- 本项目：[pitr.sh](<projects/订单系统的 PG 生产化手册/实现/scripts/pitr.sh>)、[验收清单](<projects/订单系统的 PG 生产化手册/验收清单.md>)。
- 官方：[Archiving of WAL Segments](https://www.postgresql.org/docs/17/continuous-archiving.html#BACKUP-ARCHIVING-WAL)

### 故障模式 F04：备库存在，但实际上没有在流复制

**症状**

- standby 容器或服务是 running，业务健康检查也通过，但 pg_stat_wal_receiver 返回 0 行。
- 主库 pg_stat_replication 没有目标备库，或 replay_lag 持续变大。
- 备库可以查询旧数据，团队误以为“有备库就等于有高可用”。

**根因**

进程存活和复制链路存活是两件事。备库可能因 primary_conninfo、密码、pg_hba.conf、网络、端口、复制槽或 wal_keep_size 配置不一致而没有连接主库。即使连接成功，回放延迟也可能超过业务允许的 RPO。

**诊断路径**

1. 在备库看 pg_stat_wal_receiver；在主库看 pg_stat_replication 和发送/回放 LSN。
2. 核对 primary_conninfo、复制用户属性、pg_hba.conf、监听地址和端口。
3. 比较 sent_lsn、write_lsn、flush_lsn、replay_lsn，并确认延迟是否持续增长。
4. 检查备库数据目录是否来自正确的基础备份，复制槽是否指向该备库。

**修复**

- 先恢复链路：网络、认证、HBA、连接串和目录权限按证据修复。
- 延迟过大时限制非必要查询，避免在落后备库上承担报表流量。
- 若 WAL 已缺失，不要强行“补几行”；重新做 base backup 并重建备库。
- 将“流复制连接 + 延迟阈值 + 业务读一致性”纳入健康检查。

**预防**

- 监控主库发送端、备库接收端、回放 LSN 和延迟。
- 定期演练备库重建与提升，不把 running 当作健康。
- 复制用户只授予复制需要的权限，避免用超级用户掩盖配置错误。

**来源与证据**

- 课程：[课 15《复制与高可用》](stages/5-运维与生产化/lessons/lesson-15-复制与高可用.md)
- 本项目：[verify.sh](<projects/订单系统的 PG 生产化手册/实现/scripts/verify.sh>)；本项目实测主备同步，复制检查为 1，主备订单行数均为 12003。
- 官方：[Monitoring](https://www.postgresql.org/docs/17/monitoring.html)、[Streaming Replication](https://www.postgresql.org/docs/17/warm-standby.html#STREAMING-REPLICATION)

### 故障模式 F05：复制槽把 WAL 越积越多，磁盘最终被打满

**症状**

- pg_wal 目录持续增长，磁盘使用率告警。
- 某个 replication slot 的 restart_lsn 长时间不动，slot 仍显示 active=false。
- 删除备库或停掉 CDC 消费者后，主库写入变慢甚至因磁盘耗尽不可用。

**根因**

复制槽以“下游还需要”为理由保留 WAL。下游永久失联、消费者不再使用、slot 被遗忘时，主库无法知道它已没有价值。复制槽比短暂的网络抖动更可靠，但也把“下游必须被治理”变成了主库的容量责任。

**诊断路径**

1. 查看 pg_replication_slots 的 slot_name、active、restart_lsn、wal_status 和 safe_wal_size。
2. 把 restart_lsn 与当前 WAL LSN、磁盘增长速度、下游最后消费位置对照。
3. 确认 slot 所属业务：物理备库、逻辑订阅、CDC 还是遗留对象。
4. 先评估下游是否还能恢复；删除 slot 前必须确认不会破坏仍需的增量链路。

**修复**

- 下游可恢复时，恢复消费者或重建备库，让 slot 继续推进。
- 下游已废弃时，按变更流程删除 slot，并为新链路重新建立基线。
- 立即释放磁盘压力时，优先清理明确无主的 slot 和无效消费者；不要直接删除 pg_wal 文件。
- 为 slot 增长设置告警和自动升级出口。

**预防**

- 给每个 slot 写 owner、用途、创建时间、下游地址和删除条件。
- 监控 slot 的 restart_lsn 距离、WAL 保留量、磁盘剩余空间。
- 下游停止发布时同步撤销 slot，备库重建时执行旧 slot 清理检查。

**来源与证据**

- 课程：[课 15《复制与高可用》](stages/5-运维与生产化/lessons/lesson-15-复制与高可用.md)
- 官方：[Replication Slots](https://www.postgresql.org/docs/17/warm-standby.html#STREAMING-REPLICATION-SLOTS)、[pg_replication_slots](https://www.postgresql.org/docs/17/view-pg-replication-slots.html)

### 故障模式 F06：提升新主后旧主仍然接受写入

**症状**

- 新主已对外提供写入，但旧主仍可连接、仍有应用流量或仍被负载均衡发现。
- 两边各自产生新订单，重新接回时无法自动合并。
- 团队只完成了 promote，没有完成网络、服务发现和写入隔离。

**根因**

故障转移是“选主 + fencing + 路由切换 + 数据验收”的组合动作。PostgreSQL 的 promote 只改变实例角色，不会自动关闭旧主上的应用连接，也不会替换 DNS、VIP、连接池或服务发现。没有 fencing，就存在 split brain。

**诊断路径**

1. 先冻结双边写入，记录两台实例的 timeline、LSN、应用连接和最后写入时间。
2. 从网络层、连接池和数据库层确认旧主是否仍可接收业务写入。
3. 校验新主已完成必要 WAL 回放，并确认单一写入口。
4. 若数据已分叉，不要直接把两边目录互相覆盖；先进入数据仲裁和恢复流程。

**修复**

- 先执行旧主 fencing：摘除流量、撤销写入路径、隔离网络或关闭旧实例。
- 再提升新主，切换服务发现，并清理连接池中的旧连接。
- 通过唯一订单号、时间线和关键表校验新主状态。
- 旧主重新加入前，按新主的 base backup 重建，不把分叉旧主直接当备库。

**预防**

- 把 fencing 写入自动化脚本和验收清单，不把 promote 当作完整故障转移。
- 演练“主库故障—旧主隔离—新主写入—旧主重建—回切”的闭环。
- 对写入口增加单点护栏，例如只允许当前 primary 的服务地址进入连接池。

**来源与证据**

- 课程：[课 15《复制与高可用》](stages/5-运维与生产化/lessons/lesson-15-复制与高可用.md)
- 本项目：[验收清单](<projects/订单系统的 PG 生产化手册/验收清单.md>)中的“提升前 fencing”与“回切前重建”条目。
- 官方：[Failover](https://www.postgresql.org/docs/17/warm-standby.html#WARM-STANDBY-FAILOVER)

### 故障模式 F07：同步复制让写入停顿，团队却误以为数据库挂了

**症状**

- 主库进程正常、CPU 和磁盘不高，但 INSERT 或 UPDATE 长时间不返回。
- pg_stat_activity 显示会话处于等待，和 synchronous standby、WAL flush 相关。
- 暂停备库或断开同步链路后，主库写入恢复；恢复链路后又出现等待。

**根因**

同步复制把“备库已确认”放进提交路径，换来更低的复制丢失风险，也把备库故障变成写入可用性风险。若同步备库不可用、确认级别过高或同步候选配置错误，主库会按设计等待，而不是异常崩溃。

**诊断路径**

1. 先确认等待会话、事务持续时间和应用超时，区分同步等待与锁等待。
2. 查看 synchronous_standby_names、同步备库状态、写入和 flush LSN。
3. 对照业务 RPO：此刻是否真的要求提交必须被备库确认。
4. 检查备库是否只是查询压力过高、网络抖动，还是已失去复制能力。

**修复**

- 短期按已批准的降级策略恢复可写性，例如切换异步模式或选择健康同步候选。
- 修复备库、网络或连接池后再恢复同步保护。
- 不要在没有记录 RPO 影响的情况下永久关闭同步复制。
- 对提交延迟设置告警，区分数据库不可用与保护策略正在生效。

**预防**

- 用业务等级区分同步复制范围，不要求所有非关键写入都用最高保护级别。
- 预先定义“同步备库失联时是否降级”的决策人、时限和回滚动作。
- 演练同步备库故障，记录主库写延迟和业务错误率。

**来源与证据**

- 课程：[课 15《复制与高可用》](stages/5-运维与生产化/lessons/lesson-15-复制与高可用.md)
- 官方：[Synchronous Replication](https://www.postgresql.org/docs/17/warm-standby.html#SYNCHRONOUS-REPLICATION)

### 故障模式 F08：慢查询其实是在等锁，不是在跑坏计划

**症状**

- 应用端报告某个 SQL 慢，但数据库 CPU 不高。
- pg_stat_activity 的 wait_event_type 为 Lock，或出现 transactionid、relation 等等待事件。
- 找到一个长事务或 idle in transaction 后，终止它，业务延迟立刻下降。

**根因**

执行时间和排队时间混在了一起。一个本来只需毫秒完成的 UPDATE，可能等待另一个未提交事务释放行锁；DDL、长事务、未关闭游标和连接池中的 idle in transaction 也会让后续请求排队。只看 EXPLAIN 而不看实时会话，会把锁问题误修成索引问题。

**诊断路径**

1. 先看 pg_stat_activity 的 state、query_start、xact_start、wait_event_type 和 wait_event。
2. 找到 blocker 与 blocked 的关系，确认阻塞链和事务所有者。
3. 检查 blocker 是否来自 DDL、批量更新、应用异常退出或连接池。
4. 阻塞消除后再用 EXPLAIN (ANALYZE, BUFFERS) 判断剩余的计划问题。

**修复**

- 按业务影响取消或终止明确失控的会话；先保留 pid、用户、SQL 和事务时间证据。
- 给应用事务设置合理的 statement_timeout、lock_timeout 和 idle_in_transaction_session_timeout。
- 拆分大事务、避免在事务内调用外部服务，并为变更脚本安排维护窗口。
- 真正存在计划问题时，再补索引、改写 SQL 或更新统计信息。

**预防**

- 监控阻塞链、长事务、idle in transaction 和锁等待时长。
- 慢查询看两张图：执行计划图与实时等待图。
- 将“先判断是否在等待”加入所有数据库慢请求 runbook。

**来源与证据**

- 课程：[课 16《监控与性能》](stages/5-运维与生产化/lessons/lesson-16-监控与性能.md)
- 本项目：[slow-query.sql](<projects/订单系统的 PG 生产化手册/实现/sql/slow-query.sql>)；本项目实测的订单查询最终得到 Index Only Scan，但这不能替代对锁等待的实时检查。
- 官方：[pg_stat_activity](https://www.postgresql.org/docs/17/monitoring-stats.html#MONITORING-PG-STAT-ACTIVITY)、[Explicit Locking](https://www.postgresql.org/docs/17/explicit-locking.html)

### 故障模式 F09：监控 SQL 按旧版本字段写，PG 17 上直接失效

**症状**

- 监控查询启动即报 column does not exist。
- 团队把 pg_stat_bgwriter 里的旧检查点字段照搬到 PG 17，得到空指标或错误指标。
- 数据库本身正常，但监控面板显示 No data，告警规则全部沉默。

**根因**

系统视图不是永恒不变的业务表。PostgreSQL 大版本可能拆分统计视图、重命名字段或调整统计职责。PG 17 的检查点相关指标已由 pg_stat_checkpointer 承担一部分职责；监控 SQL 若不绑定版本、没有回归检查，就会在升级后“看起来有面板，实际上没有观测”。

**诊断路径**

1. 记录数据库大版本和报错字段，确认是语法、视图还是权限问题。
2. 用 \d+ 或官方版本文档核对目标视图的真实字段。
3. 检查 exporter、面板和告警规则是否同时升级，避免只改一个查询。
4. 用一个可控事件验证指标真的会变化，例如产生检查点、执行备份或制造慢查询。

**修复**

- 为 PG 17 改用对应的 pg_stat_checkpointer、pg_stat_io 等视图和字段。
- 在查询中保留版本注释或按大版本分支，禁止静默吞掉字段错误。
- 为监控 SQL 加最小集成测试：能执行、有非空结果、时间序列有新点、告警能触发。
- 面板迁移期间保留旧指标与新指标的映射说明。

**预防**

- 升级前做 observability compatibility review，不能只测业务 SQL。
- 将监控查询当作版本化代码，与数据库镜像一起测试。
- 监控“采集器是否报错”和“指标是否长时间不变”，两者缺一不可。

**来源与证据**

- 课程：[课 16《监控与性能》](stages/5-运维与生产化/lessons/lesson-16-监控与性能.md)
- 本项目：[monitor.sql](<projects/订单系统的 PG 生产化手册/实现/sql/monitor.sql>)；本项目以 PG 17.11 实测查询并使用 PG 17 的统计视图。
- 官方：[Cumulative Database Statistics](https://www.postgresql.org/docs/17/monitoring-stats.html)、[pg_stat_checkpointer](https://www.postgresql.org/docs/17/monitoring-stats.html#MONITORING-PG-STAT-CHECKPOINTER-VIEW)

### 故障模式 F10：RLS 或安全函数配置正确，业务却看到 0 行或越权行

**症状**

- 租户角色查询自己的订单返回 0 行，表 owner 或管理员却能看到数据。
- 应用用一个“能看到所有租户”的角色连接，代码过滤一处遗漏就发生越权。
- SECURITY DEFINER 函数在测试账号下正常，换 search_path、对象名或调用者后出现错误或泄露。

**根因**

RLS 不是自动打开的“租户开关”。角色需要通过 schema USAGE、表权限、RLS policy 等多层门槛；表 owner 和带 BYPASSRLS 属性的角色可能绕过策略。安全定义函数还叠加了函数 owner、search_path、对象解析和 EXECUTE 权限问题。只测试超级用户，无法验证隔离边界。

**诊断路径**

1. 以真实租户角色连接，分别记录 current_user、session_user、rolbypassrls 和查询结果。
2. 检查 schema USAGE、表 SELECT/INSERT/UPDATE 权限、ALTER TABLE ENABLE/FORCE ROW LEVEL SECURITY。
3. 检查 policy 的 USING 与 WITH CHECK 是否覆盖读写路径，尤其是租户字段写入。
4. 对 SECURITY DEFINER 函数核对固定 search_path、限定对象名、调用权限和返回数据范围。

**修复**

- 使用最小权限登录角色，并在安全测试中覆盖租户 A、租户 B、无租户和管理员角色。
- 对需要约束表 owner 的场景评估 FORCE ROW LEVEL SECURITY。
- 函数设置安全的 search_path，优先使用 schema-qualified 名称，并撤销 PUBLIC 的 EXECUTE。
- 将“看不到别人的数据”和“不能写入别人的 tenant_id”都写入验收。

**预防**

- 每次 schema 或 policy 变更都跑双租户负向测试。
- 监控异常的跨租户访问拒绝和管理员角色使用。
- 把应用过滤视为体验优化，把 RLS 或独立数据库视为隔离边界；不要混为一谈。

**来源与证据**

- 课程：[课 17《扩展与安全》](stages/5-运维与生产化/lessons/lesson-17-扩展与安全.md)
- 本项目：[02-grants.sql](<projects/订单系统的 PG 生产化手册/实现/primary/initdb/02-grants.sql>)、[verify.sh](<projects/订单系统的 PG 生产化手册/实现/scripts/verify.sh>)；本项目实测租户 A/B 行数为 6002/6001，均通过数据库侧隔离验证。
- 官方：[Row Security Policies](https://www.postgresql.org/docs/17/ddl-rowsecurity.html)、[Function Security](https://www.postgresql.org/docs/17/perm-functions.html)

## 3. 经验化验收清单

### 备份与恢复

- [ ] 是否能回答“最近一次可恢复点是什么”，而不只是“备份文件还在”？
- [ ] 是否同时保存逻辑 dump、globals、必要扩展和恢复说明？
- [ ] 是否在临时实例完成过逻辑恢复？
- [ ] 是否完成过指定时间点恢复，并验证目标点前后事务？
- [ ] 是否监控归档失败、WAL 缺失、备份过期和恢复演练失败？

### 复制与高可用

- [ ] 主库与备库是否都能提供复制状态证据？
- [ ] 是否有明确 RPO、RTO、提升条件和 fencing 步骤？
- [ ] 是否监控复制延迟、slot 保留量和 WAL 磁盘压力？
- [ ] 是否演练过旧主隔离、连接池切换、旧主重建与回切？
- [ ] 同步复制失联时，业务降级策略是否由人和脚本共同确认？

### 性能、监控与安全

- [ ] 慢请求是否先区分锁等待、连接排队、IO、CPU 和计划问题？
- [ ] 监控查询是否绑定 PG 大版本，并能验证“采集成功且指标变化”？
- [ ] 是否以真实最小权限角色测试 RLS 的读隔离和写约束？
- [ ] 安全函数是否固定 search_path、限定对象名并收紧 EXECUTE？
- [ ] 每次故障是否留下时间线、证据、动作、结果和后续预防项？
