## 🚫 适用边界与反模式

### 什么时候不该用 PromQL / Prometheus

> "不该用"比"怎么用"更值钱——这是从"会用"到"用对"的分界线。

| 场景 | 为什么不适合 | 该用什么替代 |
|------|-------------|-------------|
| **要 100% 精确的计费/对账数据** | Prometheus 是**采样**存储：抓取间隔 15s，抓取失败就丢点；查询窗口外的样本不参与计算。L8 实测 `[1m]` 只有 4 个点，速率会跳 | 账单系统用业务数据库的精确流水，Prometheus 只做趋势参考 |
| **要保存原始事件明细** | 指标是**聚合后的数字**，不是事件本身。「哪个用户 3 点 14 分失败了」指标答不了 | 日志（ELK / Loki）+ 链路追踪（Jaeger） |
| **高基数字段的分析**（user_id / order_no） | 每个取值都是一条新序列。L2 埋的炸弹：历史上多次 Prometheus OOM 事故的根因就是标签基数失控 | 日志与数仓 |
| **需要亚秒级精度的告警** | 抓取间隔 + 评估间隔 + `for` 的叠加，最快也是十几秒级 | 客户端埋点直报 / 流式计算（Flink） |
| **长期（年级）数据归档** | 本地存储默认保留 15 天，长期存储成本陡增 | Thanos / Mimir / VictoriaMetrics 做长期存储 |
| **百分比/分位数的跨实例平均** | 分位数**不可加**。把 3 个实例的 P95 求平均是数学上错误的操作（L10） | 先 `sum by (le)` 合并桶，再算分位数 |

### 高频反模式（能跑，但迟早出事）

1. **全站聚合做告警阈值**：把 2.56% 的接口错误率稀释成全站 0.83%，故障永远不触发 → 改用 `by (method, path)` 分路径（实战项目决策 3 实测）
2. **窗口拍脑袋取 `[1m]`**：15s 抓取下只有 4 个样本点，单个慢请求就能让错误率从 0 跳到 25% → 窗口至少 4 倍抓取间隔（L8/L11）
3. **用 `rate()` 套 Gauge**：内存 Gauge 波动触发重置补偿，实测算出 7,000 多万 bytes/s 的荒唐值（L8） → Gauge 直接查，不套 rate
4. **分位数先算后聚合**：各实例各算一个 P95 再平均 → 数学错误，必须先 `sum by (le)` 合并（L10）
5. **匹配器不收窄 `job`**：`up` 全局 6 行（含 node/prometheus/cadvisor），不带 job 会把监控组件自己算进来（实测）
6. **面板用 5s 刷新 + 6h 范围**：实测 P95 面板每分钟 6,000 万样本读取（L12） → 刷新改 30s，重查询上 recording rules
7. **告警规则不加 `for`**：毛刺也能叫醒人，L11 实测同一段曲线 `for:1m` 从 21 段压到 8 段
8. **阈值贴着日常水位定**：实测 50ms 阈值在 51.8~54.2ms 水位下 73/73 全超 = 永久 firing 的狼来了（L11）

## 🔥 高频故障模式

> 每条固定**五段式**：症状 → 根因 → 排查路径 → 修复 → 预防。
> 全部症状均为**可观测**的具体现象，实测依据标注在数据里。

### 故障模式 1：查询返回空表，但服务明明是好的

- **症状（可观测）**：SLO 合规率面板显示 **0%**（或整块面板空白）；单独查 `_count` 有数据、查 bucket 序列也有数据，但两者一相除就没了
- **根因**：`le` 标签匹配了一个**不存在的桶**。匹配器匹配不到返回 **0 行，且不报错**——这是 PromQL 的静默失败。本环境桶是 ×1.5 递增，**`le="0.1"` 这个桶不存在**（实测：0.0985 的下一个是 0.1478）

  实测对照：
  ```promql
  sum(rate(demo_api_request_duration_seconds_bucket{job="demo",le="0.1"}[5m]))                  # 0 行 ← 静默失败
  sum(rate(demo_api_request_duration_seconds_bucket{job="demo",le="0.09852612533569335"}[5m]))   # 1 行，141.54
  ```

- **排查路径**：
  1. 先跑 `count by (le) (demo_api_request_duration_seconds_bucket{job="demo"})`，列出所有真实存在的桶边界
  2. 确认你要的阈值落在哪两个桶之间
  3. 用**最接近且真实存在**的那个桶（宁可比目标略严，不要凭直觉写整数）
- **修复**：把 `le="0.1"` 改成实际存在的桶值；若 SLO 必须用精确 100ms，改为在**埋点时补一个 0.1 桶**（实战项目 `exporter_app.py` 已示范）
- **预防**：任何用到 `le` 的查询，先跑一次 `count by (le) (...)` 确认桶存在；把常用桶值做成 recording rule 的注释

> 对应速查条目：[09-排障速查手册.md](09-排障速查手册.md) · 症状 1

### 故障模式 2：面板数字和告警对不上（面板 2.5%，告警不响）

- **症状（可观测）**：面板显示某接口错误率 2.56%，但告警从未触发；或反过来，告警 firing 但面板找不到对应的高值曲线
- **根因**：**面板与告警用了不同的查询**。常见三种差异：① 窗口不同（面板 `[5m]`、告警 `[1m]`）② 粒度不同（面板分路径、告警全站）③ 一个用了预聚合序列、另一个直算
- **排查路径**：
  1. 把告警 expr 的阈值去掉，直接贴到演练场跑，对比结果行数与数值
  2. 检查两侧的 `by` / `without` 标签是否一致（L7/L9）
  3. 检查窗口是否一致、`job` 是否都收窄
  4. 若用了 recording rules，确认两侧读的是同一条序列
- **修复**：让面板与告警**读同一条预聚合序列**（实战项目 recording-rules.yaml 规则 2、4 的设计意图）；或至少保证 expr 主体一致，只有阈值不同
- **预防**：把「告警 expr 去阈值 = 面板 expr」定为团队约定；在告警 annotations 里写明对应面板链接

> 对应速查条目：[09-排障速查手册.md](09-排障速查手册.md) · 症状 2

### 故障模式 3：全站指标风平浪静，用户却在投诉

- **症状（可观测）**：全站错误率 0.83%、全站 P95 52ms，都在安全线内；但用户投诉某功能不可用
- **根因**：**聚合过度把信号降没了**。短板路径被其他健康路径稀释——实测 `POST /api/foo` 错误率 2.56%、`/api/bar` SLO 合规率仅 97.66%，全站聚合后完全看不出来
- **排查路径**：
  1. 把全站查询加上 `by (path)` 或 `by (method, path)` 重新跑
  2. 看**最大值**而不是平均值：排序后取第一条
  3. 对延迟类，对比「平均 vs P95 vs P99」的差距（实测平均 17.4ms < P95 52ms < P99 65.3ms → 右偏分布，长尾真实存在）
- **修复**：面板与告警都改为分路径粒度；全站指标只作为「总览速读」，不作为判定依据
- **预防**：任何比率类指标，默认同时准备「全站」与「分路径」两个版本；告警一律用分路径

> 对应速查条目：[09-排障速查手册.md](09-排障速查手册.md) · 症状 3

### 故障模式 4：分位数算出 27 行（或返回空表）

- **症状（可观测）**：跑 `histogram_quantile` 期望 1 行，结果返回 27 行；或加了聚合后返回**空表**
- **根因**：两种相反的错误，都源于 `le` 的处理：
  - **27 行**：忘记 `sum by (le)`，直接对 `rate(...)` 求分位数 → 每条序列各算一个 P95（实测 27 行，值从 0.0001 到 0.2129）
  - **空表**：聚合时吞掉了 `le`（如 `sum by (path)` 没带 le）→ 分位数函数找不到 le 标签，返回空表（实测 0 行，且**不报错**）

  实测对照：
  ```promql
  histogram_quantile(0.95, rate(demo_api_request_duration_seconds_bucket{job="demo"}[5m]))                # 27 行
  histogram_quantile(0.95, sum by (path) (rate(demo_api_request_duration_seconds_bucket{job="demo"}[5m]))) # 0 行 ← 吞了 le
  histogram_quantile(0.95, sum by (le)  (rate(demo_api_request_duration_seconds_bucket{job="demo"}[5m]))) # 1 行 ✅
  ```
- **排查路径**：
  1. 先看结果行数：27 行 = 漏了聚合；0 行 = 聚合吞了 le
  2. 检查 `by` 后面**必须包含 `le`**（分路径时是 `by (le, path)`）
  3. 检查 `histogram_quantile` 的输入是否还带 `le` 标签
- **修复**：统一写成 `histogram_quantile(φ, sum by (le, ...) (rate(..._bucket[5m])))`
- **预防**：把正确写法存为团队 snippet；记住口诀「**先聚合 le，再算分位数**」（L10）

> 对应速查条目：[09-排障速查手册.md](09-排障速查手册.md) · 症状 4

### 故障模式 5：服务挂了，告警却集体沉默

- **症状（可观测）**：服务完全不可用，但所有业务告警（错误率、延迟）**一条都没响**；面板曲线**断掉**而不是掉到 0
- **根因**：**序列消失了**。Prometheus 抓不到就不产生样本，于是 `P95 > 0.1`、`错误率 > 5%` 这类表达式因为「没有序列满足条件」而返回空表——空表 = 不触发。这就是 L11 讲的**压轴悖论**：最严重的故障，告警反而最安静
- **排查路径**：
  1. 查 `up{job="demo"}`：如果返回 0 行或值全为 0 → 实例级失联
  2. 查 `absent(up{job="demo"})`：如果返回 1 行值 1 → 连 up 序列都没了（抓取配置被删 / 服务整体下线）
  3. 看面板曲线是「断掉」还是「掉到 0」——断掉就是序列消失的指纹
- **修复**：建立**三层防线**（L11）：`up == 0`（单实例）→ `sum without(instance)(up) == 0`（全挂）→ `absent(up)`（连指标都没了）
- **预防**：任何服务上线必须同时配这三条；定期演练「杀掉全部实例」验证告警是否真的响

> 对应速查条目：[09-排障速查手册.md](09-排障速查手册.md) · 症状 5

### 故障模式 6：浏览器卡死 / Prometheus 变慢（查询把自己打爆）

- **症状（可观测）**：打开某块面板后标签页卡死十几秒；或 Prometheus 响应变慢、`prometheus_rule_evaluation_duration_seconds` 升高
- **根因**：查询输出行数或读取样本数失控。实测三档（6 小时范围）：
  - 忘聚合上图 @60s = **702 行 / 253,422 点 / 2.6 秒**
  - 忘聚合上图 @15s = **702 行 / 1,011,582 点 / 11 秒**
  - 正确聚合版本 = 1 行 / 361 点 / 0.37 秒

  而服务端视角更惊人：P95 流水线单步读 **14,040 样本**，6h@60s 面板一次刷新读 **5,068,440 样本**（L12）
- **排查路径**：
  1. 看结果行数：> 100 行就要警惕，> 700 行基本是忘了聚合
  2. 用 `?stats=all` 看 `totalQueryableSamples`（服务端读取样本数），对比单步基线
  3. 检查面板刷新间隔与时间范围：5s + 6h 是危险组合
- **修复**：出口加 `sum by` 聚合；缩小时间范围或拉大步长；刷新间隔改 30s；重查询上 recording rules
- **预防**：面板评审时查「输出行数」与「刷新间隔」两项；单序列输出超过 11,000 点会被 Prometheus 直接拒绝（`exceeded maximum resolution of 11,000 points per timeseries`），注意这个保险丝**只挡点数，不挡样本读取**

> 对应速查条目：[09-排障速查手册.md](09-排障速查手册.md) · 症状 6

### 故障模式 7：rate 算出荒唐数字（几千万 bytes/s）

- **症状（可观测）**：`rate(某指标[5m])` 返回几千万甚至上亿的值，与物理常识严重不符（内存不可能 7000 万 bytes/s）
- **根因**：对 **Gauge**（可增可减的瞬时值）套了 `rate()`。rate 内含 Counter 重置补偿逻辑，遇到 Gauge 的正常下降会误判为「计数器重置」，于是用当前值去补偿，得出天文数字。L8 实测：对 `demo_memory_usage_bytes{type="used"}` 套 rate 得到 **7,043 万~7,769 万** bytes/s
- **排查路径**：
  1. 看指标名与类型：Counter 通常 `_total` / `_count` / `_sum` 结尾，Gauge 是裸名或 `_bytes` / `_usage`
  2. 跑裸查询看数值是否在合理量级
  3. 确认这个指标语义上是「累计量」还是「当前量」
- **修复**：Gauge 类指标直接查询，或套 `avg_over_time` / `max_over_time`（不是 rate）
- **预防**：指标命名遵守规范（Counter 带 `_total`）；埋点时就声明类型（实战项目 `exporter_app.py` 已示范）

> 对应速查条目：[09-排障速查手册.md](09-排障速查手册.md) · 症状 7

### 故障模式 8：告警反复横跳（firing → resolved → pending → firing）

- **症状（可观测）**：同一条告警在短时间内反复 firing / resolved；`ALERTS_FOR_STATE` 的时间戳不断被重置
- **根因**：**阈值贴着日常水位**，指标在阈值附近来回跨越。L11 实测：`DemoServiceHighLatency`（P99 > 0.2）在阈值附近横跳，经历 pending → firing → resolved 的完整来回
- **排查路径**：
  1. 取该指标最近 6 小时曲线，看水位区间（如 P95 水位 51.8~54.2ms）
  2. 对比阈值：若阈值落在水位区间内或紧贴边界 → 必然横跳
  3. 检查 `for` 时长是否足够吸收波动
- **修复**：二选一或同时——① 把阈值移到水位的 2 倍以外（安全边际）② 加长 `for`（L11 实测 `for:5m` 能把 21 段毛刺压到 0 段）
- **预防**：定阈值前先**看一周水位曲线**，而不是拍脑袋；阈值与水位至少留 2 倍空间

> 对应速查条目：[09-排障速查手册.md](09-排障速查手册.md) · 症状 8

## ✅ 落地 Checklist

> 写查询 / 配告警 / 上面板前逐项打勾。

**查询层面**

- [ ] 窗口 ≥ 4 倍抓取间隔（15s 抓取 → `[5m]` 起步）
- [ ] 匹配器收窄了 `job`（避免混入监控组件自身的序列）
- [ ] 分位数查询是**先 `sum by (le)` 再 `histogram_quantile`**
- [ ] 用到的 `le` 桶值**真实存在**（跑 `count by (le)` 验证过）
- [ ] Counter 用 `rate()`，Gauge 不用
- [ ] 比率类查询两侧 `by` / `without` 标签对齐

**告警层面**

- [ ] 每条都有 `for`（最短 30s，毛刺多的用 5~15m）
- [ ] 每条都有 `severity` 分级
- [ ] 阈值离日常水位 ≥2 倍安全边际
- [ ] 配了三层可用性防线（`up == 0` / 全挂 / `absent()`）
- [ ] annotations 模板化（`{{ $labels.x }}` + `{{ $value }}`），值班员能据此找到面板
- [ ] 有元告警（基数爆炸检测）

**面板层面**

- [ ] 每块面板只回答一个业务问题，图例每行都是业务结论
- [ ] 输出行数 < 100（> 700 说明漏了聚合）
- [ ] 刷新间隔 ≥ 30s
- [ ] 单位换算正确（延迟用毫秒，比率用 percent）
- [ ] 阈值线来自 SLO，不是拍脑袋

**成本层面**

- [ ] 重查询（单步 > 5000 样本）已上 recording rules
- [ ] 用 `?stats=all` 量过实际样本读取数（优化效果要量出来，不能靠感觉）
- [ ] 定期跑基数审计 `count by (标签) (...)`，监控序列数增长
