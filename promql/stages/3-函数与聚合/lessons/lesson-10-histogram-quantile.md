# L10 histogram_quantile：算出 P95 延迟

> 阶段 3 · 函数与聚合 | 零基础 + 实操 | 预计 50 分钟

## 第一幕：平均 16.5ms，用户为什么还在骂

L9 结尾留了张支票：「平均延迟其实你已经会了：`_sum ÷ _count`，就差临门一脚」。先兑现——L3 的三件套里，`_count` 数请求次数（L8 已用熟），`_sum` 记录所有请求的**总耗时**，两个都套上 L8 的 rate 再相除（除法是 L7 学的）：

```promql
sum(rate(demo_api_request_duration_seconds_sum[5m])) / sum(rate(demo_api_request_duration_seconds_count[5m]))
```

→ **16.5ms**。分路径看：`/api/bar` 约 23.8ms、`/api/foo` 约 12.6ms、`/api/nonexistent` 约 0.02ms。报告写好了：平均延迟 16.5ms，相当健康。

但用户投诉没停。问题出在哪？做个思想实验：**99 个 10ms 的请求 + 1 个 2000ms 的请求，平均 29.9ms**——听着完全能接受，可真有一位用户盯着屏幕等了 2 秒。平均值把「大多数人的体验」和「最差的那批体验」搅在一起打成桨糊，它回答不了「到底有多少人在忍受慢」。

监控里问长尾的正确姿势是分位数：**P95 = 95% 的请求都快于这个值**。服务等级目标（SLO）几乎都拿 P95/P99 写条款，没人拿平均值写——因为平均值会骗人，分位数不会。

要算 P95，`_sum ÷ _count` 这条路到头了（两个总数还原不出分布）。好在 L3 埋的另一半家底今天到期：`_bucket` 的 le 阶梯。

> ⚠️ **数值波动提示（本课尤其重要）**：演示环境的流量会缓慢「呼吸」——L9 备课时总 QPS ≈ 213，本课备课期间同一查询在 141~213 之间起伏（30 分钟窗口 207、1 小时窗口 176，窗口平均值的差异本身就说明流量在变）。本课所有数字均为**备课实测**，你跑出来偏差百分之几十都正常——看量级与相对关系，别逐位对答案。

## 第二幕：打开 _bucket，看清 le 阶梯

L3 验证四你瞄过一眼「一堆 `le=` 曲线」，现在正式拆开。收窄到一条序列，看它的原始数字：

```promql
demo_api_request_duration_seconds_bucket{instance="demo-service-0:10000",method="GET",path="/api/foo",status="200"}
```

→ 26 行（备课实测，节选）：

| le（桶边界，秒） | 计数 |
|------|------|
| 0.0001 ~ 0.0038 | 0 |
| 0.0058 | 13 |
| 0.0086 | 231,074 |
| 0.013 | 6,558,874 |
| 0.0195 | 6,677,605 |
| 0.0292 | 6,809,260 |
| 0.0438 | 7,098,379 |
| 0.0657 | 7,098,397 |
| 0.0985 ~ 1.68 | 7,098,402（平台） |
| +Inf | 7,098,404 |

（桶边界按 ×1.5 递增：0.0058 → 0.0086 → 0.013 → … → 1.68，原始值带浮点尾巴，表中四舍五入。）

三个结构事实，每个都是后面要用到的零件：

- **累积式**：le 越大计数越大——每个观测值会同时计入**所有边界 ≥ 它的桶**（L3 埋的种子发芽）。好处有两个：任意区间的请求数 = 本档计数 − 上一档计数，两行减法就能还原；而且每个桶本身都是 Counter（只增不减），L8 的 rate 招式直接复用。
- **`le="+Inf"` 恒等于 `_count`**：这条序列 `_count` = 7,098,404，`+Inf` 桶 = 7,098,404，逐位相等——∞ 是兜底边界，任何观测都 ≤ ∞，所以它就是「总次数」的分身。
- **桶边界在服务端定死**（L3 说过）：查询端只能在现成边界里做文章，这决定了后面分位数的分辨率上限。

顺带算笔账：27 条序列 × 26 个桶 = **702 行**——`_bucket` 一族比 `_count`（27 行）胖了 26 倍，这就是「存分布」的存储代价。

**彩蛋（长尾的显微镜）**：看表格末尾——1.68 桶计数 7,098,402，`+Inf` 桶 7,098,404。这条序列的一生（约 710 万次请求）里，有 **2 次**请求比 1.68 秒还慢。平均值对这 2 次毫无感觉（摊到 710 万次里连 0.001ms 都凑不出），但这就是某位用户「你们系统卡死了」的完整证据链。分位数，就是为揪出这种事而发明的。

## 第三幕：histogram_quantile——在阶梯上找分位线

L3 承诺过：「想知道为什么累积式桶能算出 P95，L10 用 histogram_quantile() 揭晓」。揭晓：**三步，跟查成绩单一模一样**——你知道全班人数和每个分数档的累积人数，要找「第 95% 名」的分数：

1. **定名次**：总数 × φ。P95 → 把所有观测按快慢排队，站在 95% 位置的那一个
2. **找桶**：沿阶梯从下往上数，数到名次时落在哪一档
3. **桶内插值**：档内假设均匀分布，按名次在档内的比例折算位置

用备课实测的汇总阶梯手算一遍。先把 702 行压回阶梯（跨实例汇总，L9 的 sum，注意分组键）：

```promql
sum by (le) (rate(demo_api_request_duration_seconds_bucket[5m]))
```

→（速率阶梯，单位：次/秒，节选）

| le | 累积速率 |
|------|------|
| 0.0195 | 119.11 |
| 0.0292 | 126.39 |
| 0.0438 | 131.12 |
| 0.0657 | 141.94 |
| 0.0985 | 141.95 |
| +Inf | 141.95 |

手算 P95：

- 名次 = 0.95 × 141.95（总数，`+Inf` 桶）≈ **134.85**
- 找桶：le=0.0438 处才 131.12（不够），le=0.0657 处 141.94（超了）→ 名次落在 **(43.8ms, 65.7ms] 桶**
- 插值：43.8 + (134.85 − 131.12) / (141.94 − 131.12) × (65.7 − 43.8) = 43.8 + 0.345 × 21.9 ≈ **51.4ms**

机器对照：

```promql
histogram_quantile(0.95, sum by (le) (rate(demo_api_request_duration_seconds_bucket[5m])))
```

→ **51.37ms**。手算 51.35，机器 51.37——差的 0.02 纯粹是我中间步骤四舍五入的误差，对上了。这条查询就是生产环境分位数的标准形态，本质是三课工具的流水线组装：

```mermaid
flowchart LR
    B["_bucket<br/>范围向量 · 702 行"] -->|"rate（L8）<br/>Counter 变速率"| R["瞬时向量 · 桶速率"]
    R -->|"sum by (le)（L9）<br/>跨 27 序列汇总，保住阶梯"| S["瞬时向量 · 汇总阶梯"]
    S -->|"histogram_quantile(φ)（L10）<br/>名次→找桶→插值"| Q["每标签组 1 行分位数"]
    style Q fill:#dcfce7
```

数据形态主线（L4 开的那条）在阶段 3 收官合拢：rate 吃范围向量吐瞬时，聚合吃瞬时吐瞬时，histogram_quantile 吃**带 le 标签的瞬时向量**、吐每标签组一行的瞬时向量——三段流水线首尾相接，一气呵成。

### 全家福与分路径

P95 只是会员之一，把 φ 换成不同值（同刻实测）：

| 分位 | 值 | 读法 |
|------|------|------|
| P50 | 12.6ms | 一半请求比这快（中位数） |
| P90 | 33.4ms | 每 10 个请求约有 1 个更慢 |
| P95 | 51.4ms | 每 20 个请求约有 1 个更慢（SLO 常客） |
| P99 | 62.8ms | 每 100 个请求约有 1 个更慢（长尾探测仪） |

对照第一幕：平均 16.5ms。排序看：P50（12.6）< 平均（16.5）< P90（33.4）——**分布右偏**的经典形状，少数慢请求把平均值往右拽、却拽不动中位数。「平均挺健康的啊」这句话，在 P90 面前现出原形：**10% 的请求超过 33ms，5% 超过 51ms**。

分路径版（分组键加个 path，L9 语法学以致用）：

```promql
histogram_quantile(0.95, sum by (le, path) (rate(demo_api_request_duration_seconds_bucket[5m])))
```

| path | 平均 | P50 | P95 | P99 |
|------|------|------|------|------|
| /api/bar | 23.8ms | 17.2ms | 60.4ms | 64.6ms |
| /api/foo | 12.6ms | 11.2ms | 27.2ms | 39.5ms |
| /api/nonexistent | 0.02ms | 0.1ms | 0.1ms | 0.1ms |

`/api/bar` 平均 23.8ms 看着还行，P95 一拉出来：**二十分之一的请求超过 60ms**——平均值报表完全隐身的尾巴。L9 的彩蛋 `/api/nonexistent` 这次贡献了另一个极端：404 快到三个分位数全部报 0.1ms（为什么连平均都对不上？实操思考题见）。

### 两条性质（手算过程直接看出来）

- **结果是近似值**：插值建立在「桶内均匀分布」的假设上，桶越宽越糙。极端案例就在眼前——nonexistent 的所有请求全挤进第一个桶（le=0.0001），桶内没有任何梯度可插值，分位数只能报桶边界 0.1ms。分辨率的天花板由桶边界决定，这是 Histogram 与生俱来的属性。
- **`+Inf` 桶兜底**：如果名次一路数到 `+Inf` 桶才够（分位数比最大有限桶还靠右），实测函数返回**最大有限桶的边界值**（备课实测：单序列取 P99.99999，返回 1.68s——恰好是 1.68 桶的边界）。意思是「至少这么慢，具体多慢，桶罩不住」。生产上看到 P99 长期贴着最大有限桶，第一反应不该是改查询，而是**服务端的桶边界漏掉了长尾**，得加更高的桶。

📚 **官方文档**：[histogram_quantile 函数](https://prometheus.io/docs/prometheus/latest/querying/functions/#histogram_quantile)、[Histogram 指标类型](https://prometheus.io/docs/prometheus/latest/concepts/metric_types/#histogram)

## 第四幕：两个经典翻车 + 一个易混

### 翻车一：le 被聚合吞了

```promql
histogram_quantile(0.95, sum by (path) (rate(demo_api_request_duration_seconds_bucket[5m])))
```

→ **空表**（0 行；裸 `sum(...)` 不带 by 同款空表，均实测）。`by (path)` 白名单没写 le——L9 的规矩「by 是白名单，没列的标签全扔」在此应验：阶梯被压扁成一行，没有档可数，histogram_quantile 直接罢工。

这是 L9「扔掉的标签回不来」的 histogram 版教训：**le 是阶梯的骨架，聚合必须保住它**——by 白名单里写上 le，或 without 黑名单别碰 le。修好就是第三幕的分路径版（`by (le, path)`）。

### 翻车二：忘套 rate

```promql
histogram_quantile(0.95, sum by (le) (demo_api_request_duration_seconds_bucket))
```

→ 53.2ms，不报错——裸 Counter 也是瞬时向量（L8 老知识），语法完全合法。但它算的是「**开机以来所有请求**」的终生分位数：备课实测它 ≈ 53ms、当时的正确写法 ≈ 55ms，差不多纯属环境流量结构长期稳定的巧合；生产上流量结构一变（新版本引入慢查询），终生分位数被几十亿条历史样本钉死，**永远追不上现实**。规矩和 L8/L9 一脉相承：Counter 先 rate，再聚合，再算分位。

### 易混：quantile 聚合器 ≠ histogram_quantile

L9 冷门家族点名过的 `quantile` 聚合器，跟今天的主角是重名亲戚，实测对照：

```promql
quantile(0.95, rate(demo_api_request_duration_seconds_count[5m]))     → 24.95（次/秒）
histogram_quantile(0.95, sum by (le) (rate(demo_api_request_duration_seconds_bucket[5m])))  → 51.4ms
```

前者把 **27 条序列各自的 QPS 值**放一起排序取第 95% 名——回答「哪条序列的速率排在 95% 位」；后者从**桶计数重建几十万个请求的延迟分布**再取分位——回答「95% 的请求多快」。一个给已有的数字排序，一个从人口普查表反推。对「请求延迟」这个问题，前者毫无意义（对 QPS 值排序跟延迟无关），只有后者是对的。

### 顺手回收 L3 的 Summary 对比

L3 说「Summary 的分位数客户端预计算、跨实例不可聚合；Histogram 查询时算、可聚合，现代实践优先 Histogram」。今天你能看透 why 了：`sum by (le)` 把 27 条序列的桶**计数相加**，阶梯依然成立，分位数照样能算——桶是可加的；而每实例预计算好的 P95（一个数字）之间，无论相加还是平均都不等于总体的 P95——**预计算的分位数不可加**。这就是那句「P95 的平均不是 P95」的数学底层。

（中间形态顺带一提：不套 sum 直接 `histogram_quantile(0.95, rate(..._bucket[5m]))` 也完全合法——27 行，每条序列各自的 P95。想看单实例明细时用。）

## 收束与预告

本课的心智模型，五句话：

- **一个家族回答两类问题**：平均延迟用 `_sum ÷ _count`（精确值），分位数用 `_bucket` 阶梯 + `histogram_quantile`（近似值）——Histogram 三件套没有一个是多余的
- **histogram_quantile 三步**：名次 = φ × 总数 → 沿阶梯找桶 → 桶内线性插值；结果永远受桶分辨率约束（全挤一个桶只能报桶边界，掉进 +Inf 只能报最大有限桶边界）
- **生产公式是三课流水线**：`rate`（L8，Counter 变速率）→ `sum by (le)`（L9，跨序列汇总且保住阶梯骨架）→ `histogram_quantile(φ)`
- **两大翻车**：聚合吞掉 le → 空表（le 是骨架）；忘套 rate → 终生分位数（不报错但语义错）
- **quantile 聚合器 ≠ histogram_quantile**：前者给已有的数字排序，后者从桶计数反推分布；桶可加、预计算分位数不可加，这是 Histogram 胜过 Summary 的底层原因

**位置与伏笔**：阶段 3 到此收官。「日常 80% 的查询套路」三组工具全部就位——rate 系列（L8）、聚合系列（L9）、histogram_quantile（L10）。三段流水线 `rate → sum by → histogram_quantile` 就是你未来在生产面板上写得最多的那类查询。下一站阶段 4，L11 把查询变成真正的生产件：**从查询到告警规则**——把「P95 > 100ms」写成一条会报警的规则（`expr` + `for` + 标签），顺带学会不让告警变成风暴。你的 P95 51.4ms，很快就有用武之地。
