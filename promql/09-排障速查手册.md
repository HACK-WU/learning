> **怎么用**：出事了别从头读。按索引表找**症状**，翻到对应条目照做。
> **想懂为什么**：每个条目末尾有原理链接，事后再看 [08-实战经验.md](08-实战经验.md)。
> **查不到**：→ 转 `debug` skill 现场取证。

> 紧急度：🔴 立即处理（业务已受损）｜ 🟡 尽快处理（有风险未爆发）｜ ⚪ 有时间再看（体验 / 优化）

## 🔴 症状 1：桶不存在导致静默失败

**一眼识别**：SLO 合规率显示 0% 或面板空白；查 `_count` 有数据、查 bucket 也有数据，一相除就没了。**不报任何错**。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 若该面板用于对外汇报，先撤下或标注「数据异常」 | 不再有人依据错误数字决策 |
| 定位 1 | 跑 `count by (le) (你的bucket指标)` | 列出全部真实存在的桶边界 |
| 定位 2 | 检查你写的 `le="X"` 是否在上一步列表中 | 不在 → 就是它 |
| 修复 | 改用**最接近且真实存在**的桶值 | 查询返回 1 行，数值回到 99% 量级 |
| 若无效 | → 检查 `_count` 分母是否为 0（服务真的没流量） | — |

```promql
# 本环境实测：0.1 这个桶不存在（阶梯 ×1.5：0.0985 → 0.1478）
sum(rate(..._bucket{le="0.1"}[5m]))                   # 0 行 ← 静默失败
sum(rate(..._bucket{le="0.09852612533569335"}[5m]))   # 1 行 ✅
```

> **预防**：任何用到 `le` 的查询，先跑一次 `count by (le) (...)`。
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 1

## 🔴 症状 2：面板与告警查询不同源

**一眼识别**：面板显示错误率 2.56%，告警从未触发；或告警 firing 但面板找不到对应曲线。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 以**面板数字为准**做人工判断，暂停信任该告警 | 决策基于可见的真实数据 |
| 定位 1 | 把告警 expr 的阈值（`> X`）去掉，贴到演练场跑 | 得到无阈值的原始值 |
| 定位 2 | 对比两者：① `by`/`without` 标签 ② 时间窗口 ③ 是否都收窄 `job` | 至少有一处不同 |
| 定位 3 | 若用了 recording rules，确认两侧读同一条序列 | 命名应一致 |
| 修复 | 让告警与面板**共用同一条预聚合序列** | 数字完全一致 |
| 若无效 | → 转「症状 8」（可能是阈值问题而非口径问题） | — |

> **预防**：约定「告警 expr 去掉阈值 = 面板 expr」。
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 2

## 🔴 症状 3：聚合过度稀释了短板

**一眼识别**：全站错误率 0.83%、全站 P95 52ms 都正常，但用户投诉某功能不可用。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 立刻按路径下钻，定位受影响接口 | 找到具体是哪个接口 |
| 定位 1 | 把查询加上 `by (path)` 或 `by (method, path)` 重跑 | 各路径数值分开 |
| 定位 2 | 按数值**降序**看第一条 | 实测：POST /api/foo 2.56%，是全站 0.83% 的 3 倍 |
| 定位 3 | 延迟类对比「平均 vs P95 vs P99」 | 实测 17.4 < 52 < 65.3ms → 右偏，长尾真实存在 |
| 修复 | 面板与告警均改为分路径粒度 | 短板路径暴露出来 |
| 若无效 | → 转「症状 1」（可能是桶问题让合规率失真） | — |

```promql
# 全站（会被稀释）
sum(rate(..._count{status=~"5.."}[5m])) / sum(rate(..._count[5m])) * 100
# 分路径（能定位）
sum by (method, path) (rate(..._count{status=~"5.."}[5m])) / sum by (method, path) (rate(..._count[5m])) * 100
```

> **预防**：比率类指标默认准备「全站 + 分路径」两个版本，告警一律用分路径。
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 3

## 🟡 症状 4：le 标签处理错误（27 行或空表）

**一眼识别**：`histogram_quantile` 返回 **27 行**（期望 1 行），或返回**空表**（0 行，不报错）。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 若该分位数用于告警，先确认告警状态是否可信 | 避免误判当前服务状态 |
| 定位 1 | 看返回行数 | 27 行 → 漏了聚合；0 行 → 聚合吞了 le |
| 定位 2 | 检查 `sum by (...)` 里**有没有 `le`** | 分路径时应是 `by (le, path)` |
| 修复 | 统一写成下面第三行的形式 | 返回 1 行（或按路径 3 行） |
| 若无效 | → 转「症状 1」（检查桶值是否存在） | — |

```promql
histogram_quantile(0.95, rate(..._bucket[5m]))                 # 27 行 ❌ 漏聚合
histogram_quantile(0.95, sum by (path) (rate(..._bucket[5m]))) # 0 行 ❌ 吞了 le
histogram_quantile(0.95, sum by (le, path) (rate(..._bucket[5m]))) # ✅
```

> **预防**：口诀「**先聚合 le，再算分位数**」。
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 4

## 🔴 症状 5：服务挂了，告警却集体沉默

**一眼识别**：服务完全不可用，所有业务告警（错误率、延迟）**一条都没响**；面板曲线**断掉**而非掉到 0。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 立即人工确认服务状态并启动应急预案（别等告警） | 止损动作不依赖监控系统 |
| 定位 1 | 查 `up{job="你的job"}` | 0 行或值全为 0 → 实例级失联 |
| 定位 2 | 查 `absent(up{job="你的job"})` | 返回 1 行值 1 → 连 up 序列都没了 |
| 定位 3 | 看面板曲线是「断掉」还是「掉到 0」 | 断掉 = 序列消失的指纹 |
| 修复 | 补全三层防线：`up == 0` / `sum without(instance)(up) == 0` / `absent(up)` | 任一死法都有对应告警 |
| 若无效 | → 检查 Alertmanager 是否正常（告警产生了但没发出去） | — |

> **预防**：任何服务上线必须同时配三条可用性告警；定期演练「杀掉全部实例」验证。
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 5

## 🔴 症状 6：查询把自己打爆（浏览器卡死 / Prometheus 变慢）

**一眼识别**：打开某块面板后标签页卡死十几秒；或报错 `exceeded maximum resolution of 11,000 points per timeseries`。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 关掉该面板（或把时间范围缩到 1h 以内） | Prometheus 负载立即下降 |
| 定位 1 | 看结果行数 | > 100 行要警惕，> 700 行是漏了聚合 |
| 定位 2 | 用 `?stats=all` 看 `totalQueryableSamples` | 对比单步基线（P95 流水线 14,040） |
| 定位 3 | 检查刷新间隔 × 时间范围组合 | 5s + 6h 是危险组合 |
| 修复 | ① 出口加 `sum by` 聚合 ② 刷新改 30s ③ 重查询上 recording rules | 输出 1~10 行，耗时降到百毫秒级 |
| 若无效 | → 转 `debug` skill 现场取证 | — |

```text
实测三档（均为 6 小时范围、P95 类查询）：
  忘聚合 @60s = 702 行 / 253,422 点 / 2.6 秒        ← 数字为返回给客户端的数据点数
  忘聚合 @15s = 702 行 / 1,011,582 点 / 11 秒       ← 卡死元凶
  正确聚合    = 1 行 / 361 点 / 0.37 秒
```

> 💡 口径提示：这里的「点数」是**返回给客户端的数据点数**（行数 × 每序列点数），决定浏览器卡不卡。
> 另一笔账是「服务端读取的样本数」（`?stats=all` 的 `totalQueryableSamples`），决定 Prometheus 累不累。
> 优化时两笔都要看，但症状不同：卡死看前者，变慢看后者。

> ⚠️ 11,000 点上限是保险丝，它**只挡点数，不挡样本读取**——百万样本的账单照付不误。
> **预防**：面板评审查「输出行数」与「刷新间隔」两项。
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 6

## 🟡 症状 7：rate 算出几千万的荒唐值

**一眼识别**：`rate(某指标[5m])` 返回几千万甚至上亿，与物理常识严重不符（如内存 7,000 万 bytes/s）。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 撤下使用该值的面板/告警，避免误导 | 不再有荒唐数字对外展示 |
| 定位 1 | 判断指标类型：Counter 还是 Gauge | Counter 常带 `_total`/`_count`/`_sum`；Gauge 是裸名或 `_bytes` |
| 定位 2 | 跑裸查询看数值量级 | 若裸值已经巨大 → 是 Counter 累计量，用 rate 正确 |
| 修复 | Gauge 类**不用 rate**：直接查，或改 `avg_over_time` / `max_over_time` | 数值回到合理量级 |
| 若无效 | → 检查是否抓取间隔与窗口不匹配（窗口 < 4 倍间隔） | — |

> **预防**：指标命名遵守规范（Counter 带 `_total`）；埋点时就声明类型。
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 7

## 🟡 症状 8：告警反复横跳

**一眼识别**：同一条告警短时间反复 firing / resolved；`ALERTS_FOR_STATE` 时间戳不断被重置。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 若已被叫醒多次，先对该告警**静默**（Alertmanager Silence），避免持续打扰 | 值班恢复 |
| 定位 1 | 取该指标最近 6 小时曲线，看水位区间 | 如 P95 水位 51.8~54.2ms |
| 定位 2 | 对比阈值与水位区间 | 阈值落在区间内或紧贴边界 → 必然横跳 |
| 修复 | ① 阈值移到水位的 **2 倍以外** ② 加长 `for`（实测 `for:5m` 把 21 段毛刺压到 0 段） | 告警稳定，不再来回 |
| 若无效 | → 转「症状 2」（可能是口径不一致导致的异常值） | — |

```text
实测对照（L11）：
  阈 值 50ms（贴水位）→ 73/73 点全超 = 永久 firing（狼来了）
  阈 值 55ms（略高于水位）→ 0/73 = 摆设，永不响
  SLO 100ms（2 倍边际）→ 正确姿势
```

> **预防**：定阈值前先看**一周水位曲线**，而不是拍脑袋。
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 8

## ⚪ 症状 9：向量类型不匹配报错

**一眼识别**：报错 `expected type range vector in call to function "rate", got instant vector`，或反过来 `expected type instant vector`。

| 步骤 | 动作 | 预期 |
|------|------|------|
| 定位 | 看报错提到的函数名 | 判断该函数需要哪种向量 |
| 修复 1 | `rate` / `increase` / `irate` / `*_over_time` 需要**范围向量** → 加 `[5m]` | `rate(x[5m])` |
| 修复 2 | 聚合函数（`sum`/`avg`…）与 `histogram_quantile` 需要**瞬时向量** → 去掉 `[5m]` 或把 range 函数放外层 | `sum(rate(x[5m]))` |
| 若无效 | → 转 `debug` skill | — |

```promql
rate(demo_api_request_duration_seconds_count)        # ❌ 缺 [5m]
rate(demo_api_request_duration_seconds_count[5m])    # ✅
sum(rate(demo_api_request_duration_seconds_count[5m]))  # ✅ 外层聚合收瞬时向量
sum(demo_api_request_duration_seconds_count[5m])     # ❌ 聚合不吃范围向量
```

> **预防**：记口诀「**rate 吃范围，聚合吃瞬时**」。
> **原理**：→ 见 [L4 讲义](stages/2-核心语法/lessons/lesson-04-瞬时向量与范围向量.md)

## ⚪ 症状 10：多对一未加 group_left

**一眼识别**：报错 `multiple matches for labels: many-to-one matching must be explicit (group_left/group_right)`。

| 步骤 | 动作 | 预期 |
|------|------|------|
| 定位 | 判断左右两边哪个序列多 | 如左 3 行（按实例）、右 1 行（num_cpus） |
| 修复 | 在「多」的一侧加 `group_left`（或 `group_right`） | 报错消失，返回左侧的行数 |
| 定位 2 | 若结果为空表 → 标签没配上，用 `on (...)` 显式指定配对标签 | 返回预期行数 |
| 若无效 | → 转 `debug` skill | — |

```promql
# ❌ 左侧 3 行（3 实例）对右侧 1 行（num_cpus）→ 多对一报错
sum by (instance) (rate(demo_cpu_usage_seconds_total{mode!="idle"}[5m])) / demo_num_cpus
# ✅ 加 group_left（左侧多，故 left）
sum by (instance) (rate(demo_cpu_usage_seconds_total{mode!="idle"}[5m])) / on (instance) group_left demo_num_cpus
```

> **预防**：做向量匹配前先分别查左右两侧的行数，预判是不是多对一。
> **原理**：→ 见 [L7 讲义](stages/2-核心语法/lessons/lesson-07-向量匹配.md)

## 🚑 通用止血动作（不确定是哪类问题时，先把损失停下）

| 场景 | 止血动作 | 代价 |
|------|----------|------|
| 刚改了规则/面板就出问题 | 回滚到上一个版本 | 丢失新改动 |
| 某块面板拖垮 Prometheus | 关闭该面板或缩小时间范围至 1h | 暂时失去该视图 |
| 告警风暴刷屏 | 在 Alertmanager 对低优先级告警设 Silence | 可能漏掉真实信号 |
| 告警该响没响（症状 5） | **人工介入**，不要等监控 | 依赖人的发现 |
| 数字明显荒谬（症状 7） | 撤下面板/告警，标注「数据异常」 | 暂时失去该指标 |

> **已收录 10 条**。宁缺毋滥——凑不满就如实写数字，不硬凑凑数条目。
> **证据纪律**：本手册每条「症状—根因—修复」均有**演练场实测依据**或对应课程讲义支撑；无实测依据的内容未收录（如事故案例复盘，仅在 `08-实战经验.md` 中如实标注留空）。
