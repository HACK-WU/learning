# 验收清单 · demo 服务可观测性体系

> 逐项自测。**全部勾选才算真的做成了**——不是「跑起来就行」。
> 全部操作在 https://demo.promlens.com/ 完成，无需本地环境。

## 功能验收

- [ ] **摸清家底**：跑通 `up{job="demo"}` 得到 3 行、`count(...)` 得到 27，并说出 27 = 3 path × 2 method × 2 status 的构成
- [ ] **发现桶陷阱**：跑 `count by (le) (demo_api_request_duration_seconds_bucket{job="demo"})`，指出 **0.1 这一档不存在**，并说出 100ms SLO 该用哪个桶近似（`0.09852612533569335`）
- [ ] **流量**：跑出总 QPS（约 130 量级）与分路径 QPS，说出哪个接口扛主要流量
- [ ] **错误率**：分别跑出全站（约 0.83%）与分路径（POST 类约 2.5%）错误率，**说出为什么全站数字会骗人**
- [ ] **延迟**：跑出全站 P95（约 52ms）、分路径 P95（bar 62.5 / foo 27.2）、平均延迟（约 17.4ms），并说出「平均 < P95」说明什么（右偏分布，长尾存在）
- [ ] **SLO 合规率**：跑出全站 99.12% 与分路径（bar 97.66%），**指出唯一不达标的路径**
- [ ] **饱和度**：跑出 CPU 使用率（约 50%）与磁盘水位（约 82%），说出磁盘距预警线还有几个点
- [ ] **告警现状**：跑 `count by (alertname) (ALERTS{alertstate="firing"})`，说出当前哪几条在 firing

## 非功能验收

- [ ] **成本**：对 P95 面板估算一次刷新的样本读取量（361 步 × 14,040 = **约 506 万**），并说出至少两种降本手段（拉长刷新间隔 / recording rules）
- [ ] **正确性**：确认所有分位数查询都是**先 `sum by (le)` 再 `histogram_quantile`**（顺序错了输出 27 行且不可加总）
- [ ] **语义**：确认所有查询都带 `job="demo"` 收窄——说出不带会混入什么（node/prometheus/cadvisor）
- [ ] **降噪**：检查 [实现/rules.yaml](实现/rules.yaml) 每一条：是否有 `for`？是否有 `severity`？阈值与实测水位是否留 ≥2 倍安全边际？
- [ ] **可维护性**：说出预聚合命名 `demo:api_latency_p95_seconds:histogram_quantile` 的三段分别代表什么（级别:名字:窗口）

## 理解验收（能说清才算会）

- [ ] 说清**决策 1**：为什么 SLO 判定用「桶占比」而不是 P95？（答对要点：① 分位数不可加 ② 桶里没有 100ms）
- [ ] 说清**决策 1 的翻转条件**：什么情况下该改回纯 P95？
- [ ] 说清**决策 2**：为什么只预聚合 3~5 条而不是全部？（答对要点：优化要做在刀刃上，Gauge 类本身很便宜）
- [ ] 说清**决策 3**：为什么告警按分路径而不是全站？（答对要点：0.83% 会把 2.56% 稀释掉）
- [ ] 说清**反例第 5 条**为什么最危险：`le="0.1"` 查不到时**返回 0 行而不报错**，会导致合规率算出 0%（假故障）
- [ ] 说出**高基数红线**：哪三类字段绝不能进标签（user_id / request_id / trace_id），以及高基数信息该放哪里（日志与链路追踪）
