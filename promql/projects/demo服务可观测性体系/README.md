# 实战项目：demo 服务可观测性体系（SLO 驱动的监控闭环）

> 所属课程：PromQL 系统学习 ｜ 学习目标：动手实操 ｜ 预计耗时：3–4 小时
> 项目性质：**查询侧为主**（演练场可跑）+ 埋点侧纸面（本机无 Python 环境，见「运行方式」）

## 🎯 一句话需求

为 demo 服务建一套**能真正值班用**的可观测性体系：从指标语义出发，定义 SLO，写出黄金四指标面板、分级告警规则，并让每一条查询都过成本关——而不是拼一堆看起来很专业、出事时却找不到重点的图表。

## ✅ 目标与非功能约束

**功能目标**

1. 定义 demo 服务的 SLO（延迟 + 可用性），并算出当前达标情况
2. 产出「服务概览页」面板规格（流量 / 错误 / 延迟 / 饱和度 / 告警数）
3. 产出一套分级告警规则（critical / warning），每条都带 `for` 与降噪理由
4. 对每条核心查询做成本审计，标出哪些必须预聚合

**非功能约束**（≥2 项，本项目 4 项）

| 约束 | 具体要求 |
|------|----------|
| **性能（成本）** | 单块面板单次刷新 ≤ 50 万样本读取；6h 范围面板不得出现 700+ 行输出（L12 事故标准） |
| **正确性（语义）** | 延迟 SLO 必须用**可聚合**的口径（分位数不可先聚合后平均，L10） |
| **可维护性** | 指标命名遵循 `级别:名字:窗口`；每条规则带 `summary`/`description`；面板 expr 与规则 expr 同源复用 |
| **稳定性（降噪）** | 告警必须带 `for`；不得出现「阈值贴水位」的规则（L11 狼来了标准） |

## 🚀 运行方式

本项目**主战场是演练场**——所有核心查询都已实测，你打开就能跑、能对照。

```text
1. 打开 https://demo.promlens.com/
2. 按 实现/queries.md 的顺序逐条粘贴执行（每条都标注了预期输出）
3. 用 实现/rules.yaml 对照演练场预置的 5 条生产规则，逐条说出你的规则差异与理由
4. 用 实现/dashboard.md 的规格表，在纸上（或真实 Grafana）组装服务概览页
5. 埋点代码 实现/exporter_app.py 为纸面交付物（本机无 Python，见下）
```

> **环境说明（重要）**：本项目备课机**未安装 Python 与 Docker**（已实测确认），因此分两部分：
> - **查询侧（主战场、全部已实测）**：`queries.md` / `rules.yaml` / `dashboard.md` / `recording-rules.yaml` —— 在演练场逐条可跑，这是项目的主体
> - **埋点侧（纸面交付物、未运行验证）**：`实现/exporter_app.py` —— 按 prometheus-client 官方 API 编写（库版本 0.26.0，2026-07-25 发布，Python ≥3.9，核查于 2026-08），需在有 Python 的环境运行。**它只影响「数据怎么产生」，不影响本项目的查询能力**
>
> **预期结果**：跑完 `queries.md` 全部条目，你能回答三个问题——服务现在健康吗？哪个接口是短板？哪条查询最贵？

## 💡 为什么这个项目不是玩具

四个约束同时压着你：**SLO 必须可聚合**（否则面板数字对不上）、**桶边界不由你定**（实测发现 100ms 没有对应桶）、**告警不许吵**（`for` 与阈值水位）、**查询成本有上限**（L12 的事故标准）。这四条里任何一条单独看都不难，同时满足才叫工程。
