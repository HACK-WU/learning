# 设计决策 · demo 服务可观测性体系

> 每个决策点都**真有争议**——换个人来可能选另一个方案，且也有道理。

## 决策 1：SLO 用「分位数阈值」还是「桶占比」

### 候选方案

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| **A · 分位数阈值** | P95 延迟 > 100ms 就算违规 | 直观、人人听得懂；业界最常见的写法 | 分位数**不可加**：不能先算各实例 P95 再平均（L10）；且受桶边界精度限制 |
| **B · 桶占比（burn rate 口径）** | 统计「延迟 ≤ 阈值的请求数 ÷ 总请求数」，要求 ≥ 99% | **可加可聚合**，任意维度切片都对得上；可直接驱动错误预算 | 语义绕一层：「99% 的请求 ≤ 100ms」不如「P95 = 100ms」直观 |
| **C · 两者都上** | 面板放 P95 给人看，SLO 用桶占比做判定 | 兼顾可读性与正确性 | 两套口径要解释关系，维护成本翻倍 |

### 最终选择

**C（两者都上）**，但**分工明确**：P95 只负责「给人看趋势」，桶占比负责「判定达标与否」。

### 选择理由

本项目踩到了一个**实测发现**，它直接否掉了纯 A 方案：demo 服务的桶阶梯是 ×1.5 递增，**根本没有 `le="0.1"` 这个桶**（实测桶边界：`0.09852612533569335` 的下一个是 `0.14778918800354002`）。所以「100ms」只能近似为最接近的 98.5ms 桶——这个坑在 L10 叫「桶分辨率天花板」，当时是概念，本项目里它是**必须绕开的硬约束**。

而桶占比方案天然免疫这个问题：它不问「100ms 在哪一档」，只问「进这个桶的有多少」。实测数据（备课当场抓取）：

```text
全站合规率（≤98.5ms 桶）   = 99.12%     # 违规 0.88%，约 1.14 QPS
分路径合规率：/api/foo = 100%  /api/nonexistent = 100%  /api/bar = 97.66%
```

注意第三条——**只有 `/api/bar` 不达标**。这个结论用桶占比分路径一查就出来，用全站 P95（52ms，远低于 100ms）根本看不出来：全站平均值把短板路径**稀释**了。这是本项目最重要的一条实战洞察。

### 为此付出的代价

1. 要维护两套查询，且得向同事解释「为什么面板写 52ms、SLO 却说 99.12%」
2. 桶阈值写死成 `le="0.09852612533569335"` 这种长小数，可读性差——**若桶边界变更，这条查询会静默失效**（返回空表而非报错，因为匹配器匹配不到就 0 行）

### 什么时候该改选另一个

- **只关心趋势、不做 SLO 判定**（内部看板）：改选纯 A，省掉一半维护量
- **桶边界正好有整数值**（如自定义 `le="0.1"`）：A 方案精度问题消失，纯 A 更简单
- **团队已有 SLO 平台**（如 Sloth、OpenSLO 生成器）：直接用其生成规则，本决策退化为「遵循平台约定」

## 决策 2：预聚合（recording rules）做多少

### 候选方案

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| **A · 不预聚合** | 面板与告警各自直接算 | 零维护，改查询即时生效 | 面板每 5 秒重算一次流水线；实测 P95 面板 6h@60s 单次读取 **506 万样本** |
| **B · 全量预聚合** | 所有面板查询都先存成 recording rule | 查询端成本最低 | 规则变多，评估压力大；**查询与规则易漂移**（改了规则忘了改面板） |
| **C · 只预聚合「重且稳定」的** | 只把高频复用 + 计算昂贵的 3 条做成规则，其余直算 | 收益集中、维护量小 | 需要判断哪些「重且稳定」，有主观成分 |

### 最终选择

**C**，只预聚合 3 条：`QPS`、`分路径错误率`、`分路径 P95`（见 [实现/recording-rules.yaml](实现/recording-rules.yaml)）。

### 选择理由

用 L12 实测的成本账本做判断依据——**成本 = 单步成本 × 步数 × 刷新频率**，三条指标同时满足「贵」和「稳」：

| 查询 | 单步读取样本 | 谁在用 | 是否预聚合 |
|------|------|------|:---:|
| P95 流水线 | **14,040** | 面板 + 告警 + 临时查询（≥3 处） | ✅ |
| 分路径错误率 | 540 × 2（分子分母） | 面板 + 告警 | ✅ |
| QPS | 540 | 面板 + 告警 + 容量分析 | ✅ |
| 内存使用率 | ~12 条序列 | 仅面板 1 处 | ❌ 直算 |
| 告警数 `count(ALERTS)` | 个位数 | 仅面板 1 处 | ❌ 直算 |

反过来看被否的 B 方案：`demo_memory_usage_bytes` 这类查询本身就读 12 条序列（L12 实测裸查级别），预聚合省下的成本抵不上新增的维护负担——**优化要做在刀刃上，不是所有查询都值得预聚合**。

### 为此付出的代价

1. 面板与告警必须**改为读预聚合序列**，否则优化白做（要求团队有这个纪律）
2. 预聚合引入了**最多一个评估间隔（15s）的延迟**——告警的及时性略微下降
3. 演示环境没有 recording rules（实测 rules API 仅有 5 条 alerting），本项目只能纸面交付，无法端到端验证

### 什么时候该改选另一个

- **服务规模小、面板少**（< 5 块板、无大范围查询）：改选 A，省掉整套规则维护
- **告警对及时性极度敏感**（秒级熔断）：预聚合的 15s 延迟不可接受，该条改回直算
- **有 Thanos / Mimir 等长期存储**：预聚合策略要下沉到 ruler 层统一做，本决策属于平台职责

## 决策 3：告警按「全站」还是「分路径」粒度

### 候选方案

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| **A · 全站一条** | `sum(...5xx) / sum(...) > 阈值` | 一条规则覆盖全部；规则文件短 | **短板被稀释**：实测全站 0.83%，而 /api/bar 已达 2.5%，全站阈值根本不会响 |
| **B · 分路径（method×path）** | `sum by (method,path) (...) > 阈值` | 精确定位到接口；实测能抓出 /api/bar | 序列多 → 告警条数多；路径新增时自动覆盖（也可能误伤） |
| **C · 分路径 + 抑制全站** | 分路径告警为 critical，全站告警仅作兜底且被抑制 | 既精确又有兜底 | 需要 Alertmanager 配置抑制规则（本课程范围外） |

### 最终选择

**B（分路径）**，并在文档里注明 C 是进阶方向。

### 选择理由

实测数据直接判了 A 死刑：

```text
全站错误率        = 0.83%（安全）
分路径：POST /api/foo = 2.56%   POST /api/bar = 2.24%   GET /api/foo = 0.74%   GET /api/bar = 0.38%
```

全站 0.83% 看着风平浪静，可 POST 类接口已经 2.5% 了——**如果阈值定在 1%，全站规则永远不会响，而此时真实故障已经存在两小时**（演练场预置的 `DemoServiceHighErrorRate` 正是分路径粒度，实测正在 firing 的正是 `POST /api/foo` 与 `POST /api/bar` 两条，且已持续近 2 小时）。这就是 L11 说的「聚合是降噪器」的反面：**聚合过度会把信号也降没了**。

### 为此付出的代价

1. 告警条数随接口数增长——目前 4 条（2 path × 2 method），接口翻倍告警也翻倍
2. 新接口上线会自动纳入告警，若其错误率天然偏高（如依赖不稳定），会造成噪声
3. 要求 `for` 与阈值设得更讲究，否则分路径的毛刺会比全站更多（单点样本少 → 波动大）

### 什么时候该改选另一个

- **接口数极多且同质**（如 200 个 CRUD 接口）：改选 A + 分路径只做面板不做告警，否则告警风暴
- **已有 Alertmanager 且配了抑制**：升级到 C，全站告警兜底兜住「新接口漏配」的情况
- **只想快速上线**：先用 A 跑起来，观察一周后再按实际错误率分布决定是否细分
