# HTTP 实战经验

> 这份材料讲的是课堂不教的那一半：什么时候不该用、会怎么崩、崩了怎么查。
> 出事时别翻这份，翻 [09-排障速查手册](09-排障速查手册.md)；这里保留“为什么”，手册只保留动作。

## 怎么使用

课程已经把一次请求拆成报文、连接、安全、缓存、代理、协议、认证与浏览器策略。真正上线后，故障通常不是“某个知识点忘了”，而是多个层次同时出现：浏览器说跨域，网关说 403，源站日志却没有请求；客户端说慢，服务端说 50 ms；证书已经换了，只有部分机器报错。

本篇把这些交叉处收束成 8 个故障模式。每条都遵循：**症状（可观测）→ 根因 → 排查路径 → 修复 → 预防**。示例中的数值是便于识别的示例信号，不是某个线上系统的事故数据。

### 适用边界与反模式

| 场景 | 为什么不能只靠本篇 | 应该补什么 |
|---|---|---|
| DNS、TCP 丢包、操作系统内核参数的深层问题 | HTTP 只能看到请求生命周期的一部分 | 转网络层抓包、系统指标或 `debug` 现场取证 |
| 业务超时、数据库锁、线程池耗尽 | HTTP 状态码和 Timing 只能证明边界，不能替代业务 profiling | 转应用 APM、数据库与线程池证据 |
| 没有可观测性、没有请求 ID 的生产故障 | 任何“看起来像”的根因都无法复核 | 先补请求 ID、响应头、代理日志和结构化指标 |
| 直接用 `-k`、关闭认证或把 CORS 改成 `*` 作为长期修复 | 这些动作可能让症状消失，却削弱信任边界 | 回到证书、认证、来源白名单和回滚方案 |

高频反模式：

1. **只盯状态码**：看到 500 就认定是源站；实际上可能是代理生成的 502，或缓存层返回了旧错误页。正确做法是同时记录响应头、请求 ID、Via/Server-Timing 和各层日志。
2. **先改配置再找证据**：连续改 CORS、缓存和代理头，最后没人知道哪次变更起效。正确做法是先保留原始请求/响应，再一次只改一个变量。
3. **用“能通”代替“可信”**：`curl -k`、放宽证书校验、信任用户提交的 `X-Forwarded-For` 都可能让测试通过，却把攻击面留到生产。
4. **把总耗时当根因**：总耗时是结果，不是位置；至少拆成重定向、DNS、连接、TLS、首字节和内容下载几个段。

## 🔥 高频故障模式

### 故障模式 1：认证状态码错位——401、403 和“根本没到应用”混在一起

- **症状（可观测）**：客户端收到 401 或 403；401 响应可能带 `WWW-Authenticate`，403 通常表示服务器理解了请求但拒绝授权；服务端应用日志有时完全没有对应请求；同一 URL 在浏览器、curl 和网关后结果不一致。
- **根因**：401 通常指向“缺少有效认证凭据或认证未通过”，403 指向“身份已识别但没有足够权限”；反向代理、API 网关和应用都可能生成状态码。若请求在代理层就被拦截，应用自然没有日志。
- **排查路径**：
  1. 保存不带敏感值的请求方法、URL、状态码、`WWW-Authenticate`、`Via`、请求 ID 和时间；不要把 token 原文写入日志。
  2. 用占位凭据分别验证“无凭据 / 格式错误 / 已认证但无权限 / 正常权限”四个分支，比较响应头和应用是否收到请求。
  3. 沿请求 ID 对齐 CDN/网关、应用认证中间件和授权日志；若边缘有响应而源站没有，先查代理策略。
- **修复**：恢复正确的 `Authorization` 或 Cookie 传递链；让认证层按约定返回 401 与 `WWW-Authenticate`，授权层返回 403；修正网关与应用的权限映射。不要把所有失败改成 200，也不要为了绕过 401 关闭认证。
- **预防**：为认证与授权建立可重复的四分支测试；响应保留请求 ID 和安全的拒绝原因；给网关生成的响应加可识别的内部事件字段；敏感凭据只存在于受控 secret 存储。

> 对应速查条目：[09-排障速查手册](09-排障速查手册.md) 的故障模式 1。
>
> **证据来源**： [RFC 9110 §15.5.2（401）](https://httpwg.org/specs/rfc9110.html#status.401)、[RFC 9110 §15.5.4（403）](https://httpwg.org/specs/rfc9110.html#status.403)、[MDN HTTP authentication](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Authentication)（官方文档核查于 2026-09）。

### 故障模式 2：CORS 预检失败——浏览器报错，但 curl 看起来正常

- **症状（可观测）**：浏览器控制台出现 CORS error；Network 面板里先有 `OPTIONS`，状态为 401/403 或缺少 `Access-Control-Allow-*`；实际 `POST` 可能根本没有发出；同一 URL 用 curl 直接请求返回 200。
- **根因**：CORS 是浏览器对跨源读取的安全约束，不是服务端“是否能收到 HTTP 请求”的约束。所谓 CORS safelisted（浏览器允许直接发送的一组简单方法/头部组合）之外的请求，或带凭据的组合，可能触发预检；预检必须在浏览器继续发送实际请求前得到允许。若网关把 `OPTIONS` 当作需要业务 token 的普通接口，或返回了 `Access-Control-Allow-Origin: *` 与凭据组合，浏览器会阻断。
- **排查路径**：
  1. 先在浏览器 Network 中单独打开 `OPTIONS`，记录 `Origin`、`Access-Control-Request-Method`、`Access-Control-Request-Headers` 和响应中的允许字段。
  2. 对照实际请求的 method、非 safelisted headers 和是否携带 credentials；确认预检与实际响应是否都包含正确的来源响应头。
  3. 逐层检查 CDN/网关/应用是否放行 `OPTIONS`，以及缓存是否按 `Origin` 区分；curl 测试时手动带 `Origin`，不要把“curl 能收到响应”当成浏览器通过。
- **修复**：只允许明确的来源、方法和请求头；预检路径免受不必要的业务认证拦截但仍遵守边缘访问策略；凭据场景返回具体来源而不是 `*`，并按实现情况加入 `Vary: Origin`；确保实际响应也带允许来源。
- **预防**：把“预检 + 实际请求 + 凭据 + 错误响应”作为一组契约测试；在开发环境记录浏览器控制台与完整请求链；CORS 白名单配置走版本控制，禁止临时改成全开放。

> 对应速查条目：[09-排障速查手册](09-排障速查手册.md) 的故障模式 2。
>
> **证据来源**： [MDN CORS guide](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS)、[WHATWG Fetch Standard CORS protocol](https://fetch.spec.whatwg.org/#http-cors-protocol)（官方文档核查于 2026-09）。

### 故障模式 3：缓存错配——内容“偶尔旧”、用户之间互相看到结果

- **症状（可观测）**：发布后部分用户仍拿到旧 JavaScript；带用户身份的接口在不同用户间出现错误复用；响应出现 `Age`、`X-Cache: HIT` 或 304，但源站刚刚已经更新；不同 `Origin` 的响应却共享同一缓存对象。
- **根因**：缓存键、新鲜度（freshness）和验证条件没有与内容的个性化维度匹配。HTML、带 hash 的静态资源和用户私有数据的缓存策略不同；`Vary` 缺失会让共享缓存忽略影响响应的请求头；仅写 `ETag` 只能支持验证，不等于允许长期新鲜复用。
- **排查路径**：
  1. 先对同一 URL 使用两个明确的请求上下文，记录 `Cache-Control`、`ETag`、`Age`、`Vary`、`Date` 和缓存状态；确认响应是否包含用户或来源相关内容。
  2. 第一次请求用全新缓存，第二次带 `If-None-Match`，第三次更换影响内容的请求头；比较 200/304、响应体和缓存键命中情况。
  3. 沿 CDN → 反向代理 → 应用逐层比对策略；确认发布是否完成 purge、版本化 URL 或回源验证，而不是只看浏览器强制刷新。
- **修复**：私有或个性化响应默认禁止共享缓存；静态文件采用内容指纹后再配长 freshness；需要共享但随请求头变化的响应补齐 `Vary` 和正确缓存键；用 `no-cache` 表达“可存但复用前验证”，不要误用为“完全不缓存”。
- **预防**：把缓存策略按资源类型写成表；为“新发布、不同用户、不同来源、304 验证、CDN purge”建立回归测试；监控命中率同时监控错误复用和 stale 命中。

> 对应速查条目：[09-排障速查手册](09-排障速查手册.md) 的故障模式 3。
>
> **证据来源**： [RFC 9111 HTTP Caching](https://httpwg.org/specs/rfc9111.html)、[MDN HTTP caching](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Caching)、[MDN `Vary`](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Vary)（官方文档核查于 2026-09）。

### 故障模式 4：慢请求只看总耗时——把等待源站当成下载慢

- **症状（可观测）**：总耗时从约 200 ms 上升到数秒，但下载字节数和带宽正常；或页面瀑布图显示 `Waiting for server response` 很长；也可能是首字节很快、内容下载很慢。只看一个 `time_total` 无法区分这些情况。
- **根因**：请求耗时由多个阶段组成：重定向、DNS、连接、TLS、发送、等待首字节和下载。不同阶段的证据属于不同责任边界；例如 TTFB 高可能是应用排队或上游等待，下载慢可能是响应太大或链路吞吐不足。
- **排查路径**：
  1. 用浏览器 Timing 或 curl `-w` 记录分段时间；HTTP 明文连接不要把 `time_appconnect=0` 误解为 TLS 失败，而要按协议判断该字段是否适用。
  2. 若 TTFB 高，带请求 ID 对齐网关、应用和上游服务的服务端耗时；若接收阶段高，再看响应大小、内容编码、连接复用和客户端网络。
  3. 对比同 URL 的缓存命中、协议版本、冷连接/复用连接和不同响应大小；只改变一个变量并留下原始样本。
- **修复**：针对证据所在阶段修复：复用连接、减少重定向、启用合适的内容编码、缩小响应或调整缓存；若根因在应用/数据库，转应用与数据层处理。不要因为 TTFB 高就盲目换 HTTP/3，也不要因为下载慢就只加应用实例。
- **预防**：统一记录 `time_connect`、`time_appconnect`、`time_starttransfer`、`time_total`、响应字节数和协议；把 TTFB、下载耗时与总耗时分开设阈值；保留可复现的 curl 命令和 HAR。

> 对应速查条目：[09-排障速查手册](09-排障速查手册.md) 的故障模式 4。
>
> **证据来源**： [curl `--write-out` documentation](https://curl.se/docs/manpage.html#-w)、[Chrome DevTools Network features](https://developer.chrome.com/docs/devtools/network/)（官方文档核查于 2026-09）。

### 故障模式 5：代理链信任污染——`X-Forwarded-For` 被当成用户自报地址

- **症状（可观测）**：审计日志中的客户端 IP 可以被请求头任意改写；限流、地理策略或管理员白名单对同一请求给出不一致结果；应用看到的 scheme 是 HTTP，但用户实际从 HTTPS 进入；多层代理后 `Forwarded`/XFF 链长度异常。
- **根因**：转发头描述的是请求经过的代理链，但“哪个代理有权限写入或覆盖它”是部署契约，不是客户端头部天然可信。若边缘代理直接把用户提交的值传给应用，应用就把不可信输入当成了身份事实。
- **排查路径**：
  1. 在受控测试请求中分别不带、带单个和带多个转发头，记录边缘、网关和应用三处看到的链；示例使用 `192.0.2.10` 等文档保留地址。
  2. 对照实际拓扑，列出每一跳谁追加、谁覆盖、谁删除；检查应用是否只信任来自已认证代理连接的最后一跳/约定位置。
  3. 比较访问日志、TLS 终止点、重定向生成的 scheme 与限流键；若公网客户端能改变结果，先判定为信任边界缺陷。
- **修复**：在可信入口清理外部提交的转发头，由每个可信代理按约定追加/覆盖；应用只解析明确格式并只信任已知代理链；不要把 `X-Forwarded-For` 直接当作认证因子。
- **预防**：把代理拓扑和头部契约纳入部署测试；为“直连应用、单代理、多代理、伪造头”建立测试；日志同时记录连接对端与解析后的客户端地址，便于发现链污染。

> 对应速查条目：[09-排障速查手册](09-排障速查手册.md) 的故障模式 5。
>
> **证据来源**： [RFC 7239 Forwarded HTTP Extension](https://www.rfc-editor.org/rfc/rfc7239.html)、[MDN `Forwarded`](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Forwarded)、[MDN `X-Forwarded-For`](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/X-Forwarded-For)（官方文档核查于 2026-09）。

### 故障模式 6：HTTP/3 发布后部分客户端失败——把“支持”误当成“必达”

- **症状（可观测）**：部分移动网络或企业网络访问变慢/失败；客户端先尝试 HTTP/3，随后回落到 HTTP/2 或 HTTP/1.1；服务端显示 UDP/443 没有到达或 QUIC 握手失败；关闭 HTTP/3 广告后同一请求恢复。
- **根因**：HTTP/3 使用 QUIC/UDP，能否使用取决于客户端、服务端/CDN、路径上的 UDP/443 和实际协商。HTTP/3 的流级优势不能修复应用慢、错误缓存或不可达的网络路径；发布 Alt-Svc/HTTP/3 能力也不等于所有请求都会走 H3。
- **排查路径**：
  1. 记录客户端最终协商协议、回落过程、网络类型和时间窗口；不要只根据服务端“已开启”下结论。
  2. 分别测试 HTTP/1.1、HTTP/2 和 HTTP/3 的连接结果、首字节和错误；确认 UDP/443、防火墙、负载均衡和证书配置在同一入口生效。
  3. 观察回落是否正常；若 H3 失败但 H2/H1 也失败，问题不应继续归因于 H3 单层。
- **修复**：先恢复可靠的 H2/H1 回退，再按区域、运营商和客户端灰度 H3；修正 UDP/443 和 QUIC 终止配置，确认回落链路；必要时暂时撤回 H3 广告。不要用强制 H3 作为唯一入口。
- **预防**：把最终协商协议和回落率纳入监控；按真实网络分组验证；为 HTTP/3 保留 H2/H1 回退和可逆发布开关，并把升级收益限定为有测量证据的场景。

> 对应速查条目：[09-排障速查手册](09-排障速查手册.md) 的故障模式 6。
>
> **证据来源**： [RFC 9114 HTTP/3](https://httpwg.org/specs/rfc9114.html)、[RFC 9000 QUIC](https://www.rfc-editor.org/rfc/rfc9000.html)、[MDN HTTP/3](https://developer.mozilla.org/en-US/docs/Glossary/HTTP_3)（官方文档核查于 2026-09）。

### 故障模式 7：证书校验失败——把“不安全地通过”当成修复

- **症状（可观测）**：浏览器显示证书名称不匹配、过期、链不受信或用途不符合；curl/SDK 报 TLS certificate verify failed；某些客户端通过而另一些客户端失败；使用 `curl -k` 后请求表面恢复。
- **根因**：客户端校验证书链、有效期、主机名/SAN、用途与本地信任库；不同客户端/系统的信任根和校验策略可能不同。`-k`/不校验只跳过验证，不会让证书变得可信，且会隐藏真正的部署错误。
- **排查路径**：
  1. 先保留原始错误、访问的主机名、客户端版本和证书链摘要；生产请求禁止把 `-k` 当默认诊断参数。
  2. 用 `openssl s_client -connect example.com:443 -servername example.com` 查看服务端实际发送的链；再分别核对 SAN、有效期、链顺序和客户端信任库。
  3. 检查是否只有某个入口、CDN、代理或旧客户端失败；把“证书内容正确”和“入口实际送出正确证书”分开验证。
- **修复**：在正确入口部署覆盖实际主机名的证书和完整链，更新受控客户端信任库或修正本地开发 CA；修复 SNI/路由与证书绑定。不要关闭校验、不要把自签证书的根私钥复制到生产。
- **预防**：证书到期与链完整性监控；在浏览器、curl、SDK 和代理环境中做续期回归；本地开发证书与生产信任根完全分离，敏感私钥不进课程示例或仓库。

> 对应速查条目：[09-排障速查手册](09-排障速查手册.md) 的故障模式 7。
>
> **证据来源**： [RFC 9525 Service Identity in TLS](https://www.rfc-editor.org/rfc/rfc9525.html)、[RFC 5280 PKIX Certificate and CRL Profile](https://www.rfc-editor.org/rfc/rfc5280.html)、[curl TLS certificate verification](https://curl.se/docs/sslcerts.html)（官方文档核查于 2026-09）。

### 故障模式 8：HTTP/1.1 报文边界或持久连接错误——请求“挂住”而不是立刻报错

- **症状（可观测）**：客户端等待直到超时；同一 keep-alive 连接上的第二个请求读到错位内容；代理记录 `400`、`408` 或 `502`；抓包发现 `Content-Length`、`Transfer-Encoding: chunked` 与实际字节边界不一致；关闭连接复用后症状减轻。
- **根因**：HTTP/1.1 需要明确消息边界；错误的 `Content-Length`、非法的分块编码或代理对 hop-by-hop 头处理不一致，会让接收方不知道一条消息何时结束。持久连接复用会把边界错误带到下一个请求，形成“偶发”错位。
- **排查路径**：
  1. 先保存原始字节或 `curl --trace-ascii`，核对状态行、头部终止空行、Content-Length/分块终止和连接关闭位置。
  2. 对同一接口分别使用单请求新连接与 keep-alive；若只有复用失败，优先查前一条响应是否完整消费。
  3. 沿应用 → 反向代理 → CDN 比较是否重复设置或改写 `Content-Length`/`Transfer-Encoding`；不要只看框架层的响应对象。
- **修复**：由单一层负责生成并校验消息边界；不要同时发送互相冲突的 framing 头；正确完成 chunked 终止并让代理按 HTTP/1.1 规范处理；在无法立即修复的发布版本上回滚或临时关闭复用作为止血，但要保留性能代价记录。
- **预防**：用包含空正文、固定长度、分块、keep-alive 和异常断开的一组协议测试覆盖代理链；升级代理后做原始报文回归；对超时、连接复用关闭率和 framing 错误设告警。

> 对应速查条目：[09-排障速查手册](09-排障速查手册.md) 的故障模式 8。
>
> **证据来源**： [RFC 9112 HTTP/1.1 §6 Message Body Length](https://httpwg.org/specs/rfc9112.html#message.body.length)、[RFC 9112 §7 Transfer Codings](https://httpwg.org/specs/rfc9112.html#transfer.codings)、[curl trace options](https://curl.se/docs/manpage.html#--trace-ascii)（官方文档核查于 2026-09）。
