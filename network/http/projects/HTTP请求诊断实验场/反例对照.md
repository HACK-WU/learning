# 反例对照：能跑不等于做对

`实现/bad_server.py` 也能启动，也能对 curl 返回一段文字，但它把状态语义、CORS、缓存和可观测性都压扁了。故障发生时，调用方只能得到“200 + maybe ok”，无法知道下一步该做什么。

## 反例如何运行

只绑定本机，阅读时可以启动：

```bash
python3 'network/http/projects/HTTP请求诊断实验场/实现/bad_server.py'
curl -i 'http://127.0.0.1:8766/auth'
```

按 `Ctrl-C` 停止。不要把这个文件部署到真实环境。

## 逐条对照

| 维度 | 反例 `bad_server.py` | 正例实验场 | 为什么反例糟 |
|---|---|---|---|
| 错误语义 | 缺认证也返回 200 | 401 / 403 / 200 分支 | 客户端无法区分补凭证、无权限和成功，重试策略也会失真 |
| CORS | 无条件 `Access-Control-Allow-Origin: *` | 只回显明确允许的来源，并带 `Vary: Origin` | 一旦接口带用户凭证，通配符不能表达最小权限；动态来源还可能被共享缓存混用 |
| 性能观测 | 所有请求固定 sleep 800ms | 分开记录连接、TTFB、正文读取、总耗时，并提供 `Server-Timing` | 只能看到“总共慢”，无法判断是连接、服务端准备还是正文传输 |
| 缓存 | 没有 `ETag` 和缓存策略 | API 条件验证，带 hash 静态资源长期缓存 | 重复下载与旧内容风险都无法被验证或解释 |
| 响应边界 | 没有 `Content-Length`，依赖连接关闭 | 明确 `Content-Length` | 持久连接或代理场景下更难判断正文在哪里结束 |
| 并发模型 | 单线程 `HTTPServer` | `ThreadingHTTPServer` | 一个慢请求会阻塞另一个请求，容易把服务排队误判成业务慢 |
| 交接能力 | 没有病例断言和回归测试 | `run_cases.py` + `test_project.py` | 修一次问题后没有证据确认其他语义是否被破坏 |

## 反例的关键代码为什么“看似合理”

```python
time.sleep(0.8)
self.send_response(200)
self.send_header("Access-Control-Allow-Origin", "*")
self.end_headers()
self.wfile.write(b"maybe ok\\n")
```

它满足“有响应”这个最低要求，却没有回答四个关键问题：

1. 请求到底成功了吗，还是认证失败了？
2. 哪个来源被允许读取，是否带凭证？
3. 慢在哪个阶段？
4. 下一次请求能不能复用或验证已有副本？

## 什么时候反例仍有价值

它适合作为第一眼对照：让学习者用 curl 观察“只有 200 和一段文本”的信息贫困。它不适合做基线、压测目标、认证示例或 CORS 配置模板。
