# 证据卡示例

> 这是一次本地运行的样例记录，不是生产基线。时间数字会因机器、进程调度和运行方式变化；真正排障时应保留自己的请求时间、协议和环境。

## 卡片 1：页面慢

| 字段 | 记录 |
|---|---|
| 现象 | 订单页面被反馈“打开很慢” |
| 请求 | `GET /api/redirect`，随后 `GET /api/slow` |
| 响应 | 第一个请求 302，`Location: /api/orders?source=redirect`；慢请求 200，正文 44 字节 |
| 时间/协议 | 本次样例：slow connect 0.10ms、TTFB 82.63ms、body 44.97ms、total 127.60ms；本地 HTTP/1.1 |
| 关键头部 | `Server-Timing: app;dur=80, body;dur=40`、`Cache-Control: no-store` |
| 假设 | 先有重定向成本，随后主要等待发生在首字节前；正文读取也有独立延迟 |
| 动作 | 先确认是否必须重定向，再查服务端准备时间；不直接把压缩或 HTTP/3 当第一修复 |
| 验证 | 取消重定向或降低 `header_delay_ms`，重新比较 TTFB；降低 `body_delay_ms`，比较正文读取段 |
| 回滚 | 保留原路由和响应语义，只撤回实验参数或暂时关闭优化 |

## 卡片 2：登录失效

| 字段 | 记录 |
|---|---|
| 现象 | 客户端说“登录失效”，但没有说明凭证是否发出 |
| 请求 | `GET /api/auth` 三次：无头部、错误 Bearer、占位 Bearer |
| 响应 | 无凭证 → 401 + `WWW-Authenticate`；错误凭证 → 403；占位凭证 → 200 |
| 时间/协议 | 三次均为本地 HTTP/1.1，正文均能读完；诊断时不打印认证正文 |
| 假设 | 401 说明认证材料缺失/无效；403 说明凭证已到达但不被接受；不能把两者都归因于 CORS |
| 动作 | 先在请求证据中确认凭证载体和是否发送，再查 token 生命周期、权限和服务端校验 |
| 验证 | 只改变 `Authorization` 头，不改变 URL，观察 401→403→200 是否符合预期 |
| 回滚 | 不盲目重试或更换认证模型；撤回错误的客户端凭证注入，恢复已知有效配置 |

## 卡片 3：跨源与重复下载

| 字段 | 记录 |
|---|---|
| 现象 | 页面跨源调用失败，或每次刷新都下载相同订单/静态资源 |
| 请求 | 先 OPTIONS 预检，再带 Origin + Authorization 的 POST；另测 GET + ETag |
| 响应 | 允许来源预检 → 204，实际 POST → 201；恶意来源预检 → 403；GET 首次 200，条件请求 304 |
| 关键头部 | `Access-Control-Allow-Origin: http://localhost:5173`、`Vary: Origin`、`ETag: "orders-demo-v1"` |
| 假设 | CORS 是“页面能否读取”的浏览器策略；缓存是“副本是否需要重新验证”的另一条链路，不能混为一个错误 |
| 动作 | 对凭证接口使用明确来源和允许头部；API 采用 `no-cache` + ETag；带内容指纹的静态资源采用 immutable |
| 验证 | 分别换来源、换预检请求头、带/不带 `If-None-Match`，逐项观察状态码和响应头 |
| 回滚 | 若来源配置错误，退回上一版允许列表；若发布无法保证 hash 变化，撤回 immutable，改用验证或短 TTL |

## 卡片 4：协议升级决策

| 字段 | 记录 |
|---|---|
| 现象 | 团队提议“直接切 HTTP/2 或 HTTP/3”来解决所有慢请求 |
| 请求/响应 | 当前项目本地基线是 HTTP/1.1；已能观察状态码、缓存和时间分段 |
| 证据缺口 | 尚未测真实链路的 h1.1/h2/h3 协商、客户端支持、CDN/代理兼容、UDP/443 路径和失败回退 |
| 假设 | 如果主要瓶颈在服务端处理、重定向或缓存未命中，升级传输协议不会直接消除它 |
| 动作 | 保留 HTTP/1.1 回退，先在同一请求、同一客户端、同一路径采集协议与 Timing 对照 |
| 验证 | 只有当数据证明连接/多路复用/弱网恢复是主要瓶颈，且依赖链路支持目标协议，才做小比例灰度 |
| 回滚 | 维持 h1.1 可用；升级失败或收益不成立时撤销灰度，不让协议升级成为单点故障 |
