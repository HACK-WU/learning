# 设计决策

本项目的决策不是寻找唯一正确答案，而是说明：在当前目标、约束和证据下为什么选 A，放弃 B 付出了什么代价，以及什么时候应该反过来选。

## 决策一：本地服务用标准库 `ThreadingHTTPServer`，还是直接上 ASGI/真实网关

### 候选方案对比

| 方案 | 优点 | 代价 |
|---|---|---|
| Python 标准库 `ThreadingHTTPServer` | 零第三方依赖、启动快、路由和字节级行为透明 | 不代表生产并发模型，不提供 HTTP/2/3、TLS、限流和完整中间件生态 |
| ASGI 框架 | 更接近现代 Web 服务，异步和中间件生态更完整 | 需要依赖与环境管理，框架行为会遮住本课要观察的报文细节 |
| 直接接入 Nginx/CDN | 能观察真实中间层 | 环境复杂，故障来源增多，初学者难以判断是应用还是基础设施 |

### 最终选择

选标准库 `ThreadingHTTPServer`，并显式把它标成教学基线。

### 选择理由

本项目的首要目标是观察状态码、头部、正文边界和时间分段，而不是证明某个生产框架的吞吐。标准库让每个现象都能在几十行代码中找到对应来源，也让运行命令在 macOS 上保持可复现。

### 为此付出的代价

它不能证明真实生产栈的线程池、异步调度、TLS 终止、HTTP/2 多路复用或代理行为。`client.py` 每次独立连接也会牺牲连接复用场景的真实性。

### 什么情况下该改选另一个

如果目标变成验证高并发、TLS 终止、真实反向代理、HTTP/2/3 协商或生产部署，应改用 ASGI + 反向代理，并把标准库实验保留为最小可复现故障源。

## 决策二：认证示例用 Bearer 头，还是 Cookie/Session

### 候选方案对比

| 方案 | 优点 | 代价 |
|---|---|---|
| `Authorization: Bearer` | curl 与脚本容易复现，凭证是否发送一眼可见，适合 API 联调 | 客户端必须自行管理生命周期；不能代表浏览器 Cookie 的 SameSite、Secure、HttpOnly 行为 |
| Cookie + Session | 浏览器会自动携带，适合传统 Web 会话；服务端可集中撤销 | 受域、路径、SameSite、Secure、跨源凭证和 CSRF 影响，脚本复现更容易漏条件 |
| JWT 放在 Cookie 或头部 | 可做无状态校验，跨服务携带方便 | 令牌撤销、轮换、泄露窗口和“签名不等于加密”都增加设计成本 |

### 最终选择

病例代码选 Bearer 头；Cookie/Session 的选型保留在课程第 13 课和本决策记录中，不把两个状态模型混写成一个实现。

### 选择理由

这个项目要先让学习者看懂 401 challenge、403 authorization 和 200 success 的差异。显式头部让“凭证是否到达服务端”成为可直接验证的证据，也避免自动化脚本被浏览器 Cookie 策略干扰。

### 为此付出的代价

项目不能直接证明浏览器 Cookie 是否被域、路径或 SameSite 拦截，也没有覆盖 Session 存储、注销和多实例共享状态。

### 什么情况下该改选另一个

如果主要使用者是同站浏览器页面、需要 HttpOnly 防止脚本读取凭证，并且服务端有可靠的 Session 存储，应优先评估 Cookie + Session；若是跨服务 API 或非浏览器客户端，则 Bearer 更容易明确管理。

## 决策三：缓存采用“HTML/API 验证 + hash 静态资源 immutable”，还是全部 no-store

### 候选方案对比

| 方案 | 优点 | 代价 |
|---|---|---|
| 全部 `no-store` | 最不容易读到旧数据，配置简单 | 每次都回源，浪费带宽和延迟；无法体现缓存层级的收益 |
| 全部长期缓存 | 命中率高、请求少 | HTML、用户数据和发布回滚容易读到旧副本，存在语义风险 |
| 按资源性质分层 | HTML/API 可验证，带版本的静态资源可长期复用 | 发布流程必须保证 hash 变化，策略需要逐类审查 |

### 最终选择

项目使用第三种：`/api/orders` 返回 `ETag` + `Cache-Control: no-cache`，`/static/app.abc123.js` 返回 `max-age=31536000, immutable`。

### 选择理由

它能在同一个实验场里真实看到 200 → 304 的协商缓存，也能对比“URL 带内容版本后才适合长期缓存”。缓存决策建立在内容是否用户相关、URL 是否可变和发布流程是否可靠上。

### 为此付出的代价

需要维护资源指纹和发布清理策略；`no-cache` 仍会产生验证请求，并不是零网络成本。

### 什么情况下该改选另一个

支付、授权、隐私响应通常不应进入共享缓存；如果发布系统不能保证文件名随内容变化，不能贸然使用长期 immutable，应退回较短 TTL 或验证策略。

## 决策四：协议先升级，还是先保留 HTTP/1.1 基线

### 候选方案对比

| 方案 | 可能收益 | 需要承担的风险 |
|---|---|---|
| 立即强制 HTTP/2 或 HTTP/3 | 可能改善多请求复用或弱网体验 | 客户端、代理、CDN、UDP/443、证书和回退链路可能不兼容；瓶颈若在 TTFB/应用则收益有限 |
| 保留 HTTP/1.1，先测量 | 结果容易复现，有明确回退基线 | 暂时放弃潜在协议收益，需要额外采集协商与分段耗时 |
| 分流灰度升级 | 能在真实流量比较 | 观测、回滚、样本和代理配置更复杂 |

### 最终选择

本地项目保留 HTTP/1.1，输出连接、TTFB、正文读取和总耗时；真实升级前再对 h1.1/h2/h3 采集同一请求、同一客户端和同一链路的对照数据。

### 选择理由

“慢”首先是证据问题。若主要时间在服务端准备或缓存未命中，换协议不会自动修复；若是多请求竞争、连接建立或丢包恢复，再评估协议升级才有因果依据。

### 为此付出的代价

本项目不能在当前无额外协议服务的前提下给出 h2/h3 的实测收益，只能给出测量清单和回退条件。

### 什么情况下该改选另一个

当真实链路已确认客户端、服务端、CDN 和代理都支持目标协议，且基线数据明确显示连接/多路复用/弱网恢复是主要瓶颈时，可以先小比例灰度，并保留 HTTP/1.1 回退。
