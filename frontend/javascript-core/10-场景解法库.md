## 场景 1｜批量任务从 100 涨到 100000

**场景**：一个批处理脚本，原来跑 100 个任务好好的。现在数据量涨到 10 万个，一跑就超时——**总耗时正好等于单任务耗时 × 10 万**。加机器、加 CPU 都没用，因为并发度恒为 1，资源根本没吃掉。

### 🔒 先自己想

第一反应是"改成 `Promise.all` 一把梭"？先问自己：**10 万个 Promise 同时挂在内存里会怎样？下游扛得住 10 万并发吗？**

<details>
<summary>💡 提示（思考方向）</summary>

- 串行的问题在"并发度 = 1"，那**正确的并发度**应该是多少？谁来决定这个数？
- 一批任务里总有快慢，用"批"做单位会不会有队头阻塞？
- 任务失败了怎么办？一个失败要不要中断整批？
- 如果任务是**持续流入**的（不是一次性数组），"分批"这个思路还成立吗？
- 如果任务本身是 CPU 密集的，并发还有意义吗？

</details>

<details>
<summary>📖 展开解法</summary>

### 解法一览

| 解法 | 怎么做 | 代价 | 适用边界 |
|---|---|---|---|
| **A. `Promise.all` 一把梭** | `await Promise.all(tasks.map(fn))` | 瞬时并发 = 任务数；10 万个 Promise 同时挂内存；下游大概率先崩 | 任务数 ≤ 几百，且确认下游扛得住 |
| **B. 并发上限（信号量 / worker 池）** | 固定 N 个"槽位"，空一个补一个 | 要自己实现或引库；N 需要压测调，拍脑袋容易拍错 | **通用默认解**；尤其适合**持续流入**的任务流 |
| **C. 分批 + 逐批 await** | 每批 k 个，`Promise.all` 一批再下一批 | 批内快的要等慢的（**队头阻塞**），吞吐不如 B | 实现最简单；任务耗时**均匀**时够用 |
| **D. 生成器 + 流式产出（背压）** | async generator 边产边消费，由下游控制节奏 | 心智负担高，调试链路长 | 数据量极大 / 内存受限 / 需要边产边输出 |
| **E. 错误与超时策略**（与上面任一组合） | `allSettled` 收集全部结果 / 重试 + 退避 / 每个任务超时 | 语义复杂度上升，要写清"失败到底算什么" | **任何生产场景都该配** |

### 推荐路径（递进，不是一次全上）

1. **先用 A 验证正确性**——确认任务之间确实没有依赖，并发是安全的
2. 数量涨到几千 → 换 **C**（改动最小，`chunk` 一下就行）
3. 吞吐不够 / 任务耗时不均 → 换 **B**（真正的并发上限，吞吐最高）
4. 规模到内存都吃紧 → 上 **D**
5. **E 从第一天就要配**：没有超时和错误策略的并发，等于把故障放大 N 倍

### 实测参考（12 个任务 × 50ms，Node v22.14.0）

| 写法 | 耗时 | 说明 |
|---|---|---|
| 串行 | 742 ms | ≈ 12 × 50 |
| `Promise.all` | 62 ms | 并发 12，但数量大时不适用 |
| 并发上限 3 | 247 ms | ≈ 4 × 50 |
| 并发上限 5 | 184 ms | ≈ 3 × 50 |

### 知识点挂钩

- [课 8 Promise 与 async/await](stages/3-异步与现代语法/lessons/lesson-08-Promise与async-await.md) —— `all` / `allSettled` / `race` 的语义差异；`await` 阻塞的是"当前函数的剩余部分"
- [课 3 作用域与闭包](stages/1-值与作用域/lessons/lesson-03-作用域与闭包.md) —— 活动计数器天然是个闭包状态
- [课 9 现代语法与内置数据结构](stages/3-异步与现代语法/lessons/lesson-09-现代语法与内置数据结构.md) —— async generator
- [实战项目《异步任务编排器》](projects/异步任务编排器/设计决策.md) —— 并发机制三选一的完整权衡、超时真取消 vs 假取消

### 不适用边界

- **任务之间有顺序依赖**（后一个要用前一个的结果）→ 串行是**正确答案**，别并发
- **任务本身是 CPU 密集** → 单线程上并发没有意义，转**场景 2**
- **下游有速率限制**（比如 API 限 10 QPS）→ 并发上限必须 ≤ 限额，且要配退避重试

</details>

## 场景 2｜一个接口把主线程卡住 3 秒

**场景**：某个接口 P99 从 50ms 涨到 3s，**所有**接口一起变慢（不只是这一个），CPU **单核** 100%。加了机器也没用——因为 Node 是单线程，多出来的核根本用不上。进一步排查发现：**耗时与请求里某个字符串字段的长度强相关**，短输入一切正常。

### 🔒 先自己想

"加机器"显然是错答案（单线程）。那有哪些方向？在想"怎么挪走计算"之前，先问一句：**这个计算真的需要这么久吗？**

<details>
<summary>💡 提示（思考方向）</summary>

- 耗时跟**输入长度**强相关，而且不是线性相关——这暗示了什么？
- "挪到别的线程"和"让这个计算变快"，哪个成本低？
- 如果这个计算必须跑 3 秒，能不能不让它**连续**跑 3 秒？
- 数据一定要**整体**载入内存才能处理吗？
- 相同输入反复计算，能不能直接记住结果？

</details>

<details>
<summary>📖 展开解法</summary>

### 解法一览

| 解法 | 怎么做 | 代价 | 适用边界 |
|---|---|---|---|
| **A. 换算法（含改写正则 + 限制输入长度）** | 去掉嵌套量词、改线性算法；对用户可控输入设长度上限 | 需要真的理解复杂度来源；正则改写要回归测试防语义漂移 | **永远先试这个**——成本最低、收益最大 |
| **B. 流式处理** | 大报文 / 大文件用流边读边处理，不整体载入 | 代码从"一次性拿到结果"变成"处理事件"，心智负担上升 | 数据量本身大（大 JSON、大文件） |
| **C. `worker_threads` 挪走** | 重计算丢给 worker，主线程继续响应 | 有序列化与进程间通信成本；调试变复杂；不能共享内存（除非用 `SharedArrayBuffer`） | 计算量确实降不下来，且结果可以异步等 |
| **D. 分片让出主线程** | 把大循环切成小块，每块之间 `setImmediate` 让事件循环喘口气 | 总耗时不变甚至略增，只是**把卡顿打散** | 改不动算法、又不能开 worker 时的兜底 |
| **E. 缓存** | 相同输入直接返回上次结果 | 要处理失效与内存占用 | 输入重复率高（如模板渲染、报表） |

### 推荐路径

1. **先做 A**——尤其当"耗时与输入长度强相关"时，八成是复杂度问题（典型：灾难性回溯）
2. 数据量本身大 → **B**
3. 算法已最优但计算量仍在 → **C**
4. **D 只在以上都不可行时**用（它是把 3 秒的卡顿打散成 30 次 100ms，用户体感好了，总吞吐没变）
5. **E 作为叠加优化**，别指望它掩盖复杂度问题

### 硬证据：先怀疑正则（ReDoS 实测，Node v22.14.0）

| 模式 | 输入 | n=500 | n=1000 | n=2000 | n=4000 |
|---|---|---|---|---|---|
| `/.*.*=.*;/`（嵌套量词） | `"x=" + "x"×n` | 25.5 ms | 182.9 ms | 1400.8 ms | **11815.9 ms** |

> 输入翻 8 倍，耗时翻 **463 倍**（≈ O(n³)）。**4000 个字符就能吃掉主线程 11.8 秒。**

| 模式 | n=24 | n=26 |
|---|---|---|
| `/^(a+)+$/` | 49.4 ms | **201.1 ms** |
| `/^a+$/`（去掉嵌套） | 0.001 ms | 0.002 ms（**n=4000 也只要 0.003 ms**） |

**结论**：改写模式 + 限制输入长度，能把 11.8 秒压到微秒级——比开十个 worker 都管用。

### worker 解法实测

worker 干 558ms 重活的同时，**主线程定时器仍滴答了 36 次** → 事件循环完全没被阻塞。

### 知识点挂钩

- [课 7 事件循环](stages/3-异步与现代语法/lessons/lesson-07-事件循环.md) —— 为什么一段同步代码能让**所有**请求变慢
- [课 8 Promise 与 async/await](stages/3-异步与现代语法/lessons/lesson-08-Promise与async-await.md) —— 并发不等于并行：单线程上并发只是**交错**，不减少总计算量
- [课 11 错误处理与调试](stages/4-工程化与运行时/lessons/lesson-11-错误处理与调试.md) —— 用 `--cpu-prof` / `monitorEventLoopDelay` 找热点

### 不适用边界

- **耗时来自 I/O 等待**（下游慢）→ 计算类优化全部无效，应该去查下游
- **分片（D）不是性能优化**：它不改变总耗时，只改变卡顿的分布。别拿它交差
- 若计算需要频繁共享大量状态 → worker 的序列化成本可能吃掉收益

</details>

## 场景 3｜快速点击，旧响应覆盖了新响应

**场景**：搜索框，用户连着改了三次关键词（"ja" → "java" → "javascript"）。三个请求并发发出去，**"ja" 的响应最后才回来**，结果列表显示的是"ja"的结果——而输入框里已经写着"javascript"了。用户看到的是"我搜的和显示的不是一回事"。

### 🔒 先自己想

"加个防抖"是最常见的第一反应。但请想清楚：**防抖能不能根治这个问题？**

<details>
<summary>💡 提示（思考方向）</summary>

- 防抖减少的是**请求数量**，但两个请求还是会并发。请求数从 3 降到 2，竞态消失了吗？
- 关键洞察：**网络不保证响应顺序**。那"谁的结果该被采用"这件事，应该由谁来判断？
- 请求发出去了但结果不要了——能不能让它**别浪费带宽**直接取消？
- 如果业务要求"每一次点击的结果都要保留"（比如批量操作），那么"丢弃旧结果"还是对的吗？

</details>

<details>
<summary>📖 展开解法</summary>

### 解法一览

| 解法 | 怎么做 | 代价 | 适用边界 |
|---|---|---|---|
| **A. 请求序号 / 版本号**（正确性保证） | 每次发起记一个自增 id，响应回来时 `if (id !== latestId) return;` 直接丢弃 | 请求仍在飞，带宽没省；要小心闭包捕获的是不是最新 id | **必须做**，这是正确性的底线 |
| **B. `AbortController` 取消** | 发起新请求前 `controller.abort()` 掉上一个 | 需要下游 API 真的支持 `signal`；只取消客户端，服务端可能已经处理了 | 下游支持取消时，**省带宽 + 省服务端资源** |
| **C. 防抖 / 节流** | 等用户停手 300ms 再发请求 | 增加感知延迟；**不解决竞态**，只是让竞态更少发生 | 作为**第一层减量**，不能作为唯一手段 |
| **D. 不可变快照 + 单一提交点** | 所有响应先写入一次性的状态快照，只有一个地方负责提交到 UI | 需要状态管理约定；对简单页面偏重 | 状态复杂、多个异步源写同一份状态时 |
| **E. 队列串行化** | 请求排队，前一个完成才发下一个 | 延迟叠加，用户等待变长 | 请求必须严格按序生效的场景 |

### 推荐路径

1. **A 先上**（正确性底线，代码量最小，十几行）
2. **C 叠加**（减量：少发请求 = 少烧钱 + 少竞态）
3. **B 再叠加**（下游支持就上，省带宽省服务端）
4. D / E 只在中大型状态管理里才需要考虑

> ⚠️ **只做 C 不做 A 是典型错误**：防抖把并发从 3 降到 2，竞态依然存在，只是更难复现——**偶发 bug 比必现 bug 更难查**。

### 知识点挂钩

- [课 3 作用域与闭包](stages/1-值与作用域/lessons/lesson-03-作用域与闭包.md) —— `latestId` 就是一个闭包状态；注意别捕获成发起时的旧值
- [课 8 Promise 与 async/await](stages/3-异步与现代语法/lessons/lesson-08-Promise与async-await.md) —— **`Promise.all` 失败时其他请求并未被取消**，只是结果被丢弃
- [实战项目《异步任务编排器》](projects/异步任务编排器/设计决策.md) —— 超时真取消（`race` 判定 + `abort` 通知）vs 假取消

### 不适用边界

- **业务要求保留每一次结果**（批量下载进度、日志上报）→ A 的"丢弃旧结果"就是错的，应该按序号**归并**而不是丢弃
- **请求有副作用**（下单、扣款）→ 客户端丢弃响应**不等于**服务端没执行。这类场景要在服务端做幂等，不能只靠前端

</details>

## 场景 4｜长期运行的服务，RSS 每天涨 100MB

**场景**：一个常驻的 Node 服务，RSS 从启动时的 100MB 开始，**每天稳定涨 100MB，GC 之后也不回落**，一周后 OOM 重启。日志里最后刷的是 `Mark-Compact` 密集出现，然后 `FATAL ERROR: Reached heap limit`，退出码 134。

### 🔒 先自己想

第一反应可能是"把 `--max-old-space-size` 调大"。先问自己：**这解决的是症状还是病因？** 另外，在动手改代码之前，你打算怎么**证明**是哪里泄漏的？

<details>
<summary>💡 提示（思考方向）</summary>

- "GC 后不回落"这件事，本身就是一个**判定工具**——它排除了什么可能？
- 泄漏的本质是"**有人还引用着它**"。那么问题变成：怎么找到那个"谁"？
- 泄漏对象通常有四种典型来源（本课讲过），逐个对照你的代码
- 如果这个内存是**必须缓存**的（比如热点数据），那它不算泄漏，但需要一个什么约束？
- 如果定位成本太高，有没有**架构层面**的止损手段？

</details>

<details>
<summary>📖 展开解法</summary>

### 解法一览

| 解法 | 怎么做 | 代价 | 适用边界 |
|---|---|---|---|
| **A. 堆快照对比定位**（先定位，再动手） | 取两次快照（间隔一个业务高峰），DevTools Memory 面板 **Comparison** 视图看"新增对象数"排行 → 看 **Retainers** 找持有链 | 大快照文件很占磁盘（本课实测 88.17 MB）；需要能复现的窗口 | **任何泄漏排查的第一步** |
| **B. `WeakMap` 化** | 给对象挂元数据一律用 `WeakMap`，对象回收时条目自动消失 | 键必须是对象；**不可遍历、没有 `size`** | 泄漏源是"给对象附加元数据"时 |
| **C. 有界缓存（LRU / TTL）** | 缓存加容量上限与淘汰策略 | 要处理"淘汰了又要重算"的抖动；命中率需要观察 | 内存是**有意**占用的（热点数据），只是没有上限 |
| **D. 显式生命周期（`close()` / `dispose()`）** | 资源持有者实现 `close()`，配 `try...finally` 保证调用 | 需要全链路遵守约定，漏一处就白搭 | 定时器、监听器、订阅、文件句柄 |
| **E. 拆分进程 / 定期重启**（兜底） | 把易泄漏的模块拆成独立进程，或定时自杀重启 | 不解决泄漏，只是让它来不及爆 | **临时止血**，不能当最终方案 |

### 推荐路径

1. **先做 A，拿到证据再动手**——凭猜改代码的命中率极低
2. 按定位结果对症下药：元数据类 → **B**；缓存类 → **C**；资源类 → **D**
3. **E 只作为临时止血**，且必须同时挂上"根因未修"的待办

### 四种典型泄漏对照（课 12 实测数字）

| 类型 | 实测表现 | 修复手段 |
|---|---|---|
| 意外全局变量 | 4.2 → 19.5 MB | 加 `'use strict'` |
| 定时器未清理 | 4.3 → 19.6 MB | `clearInterval` / `AbortController` |
| 闭包持大对象 | 4.3 → 19.6 MB（修复版**压根不涨**） | 缩小捕获范围 |
| 无界 `Map` 缓存 | 156.9 MB vs `WeakMap` 95.9 MB（**差值 61.0 MB**） | `WeakMap` 或 LRU |

### 判定技巧

用 `node --expose-gc` 跑，手动 `global.gc()` 之后看内存：
- **回落** → 不是泄漏，只是还没触发 GC（先别慌）
- **不回落** → 确认泄漏，继续用 A 定位

> ⚠️ `FinalizationRegistry` **不能**用来做确定性清理——规范**不保证**清理回调被调用（课 12 已核实 MDN 原文）。

### 知识点挂钩

- [课 12 内存·性能与选型收束](stages/4-工程化与运行时/lessons/lesson-12-内存性能与选型收束.md) —— 可达性回收、四种泄漏的复现与修复、堆快照对比法
- [课 3 作用域与闭包](stages/1-值与作用域/lessons/lesson-03-作用域与闭包.md) —— 闭包为什么会让变量活得更久
- [课 9 现代语法与内置数据结构](stages/3-异步与现代语法/lessons/lesson-09-现代语法与内置数据结构.md) —— `Map` vs `WeakMap` 的强/弱引用差异

### 不适用边界

- **`--max-old-space-size` 调大只是延后 OOM**，不解决泄漏，还可能掩盖问题直到更糟的时刻爆发
- 若内存上涨是**业务量上涨**带来的（不是泄漏），正确答案是扩容或加缓存上限，不是查泄漏

</details>

## 场景 5｜给对象附加"私有"元数据

**场景**：你在写一个库，需要给**调用方传进来的对象**附加一些内部状态（比如"这个对象上次处理到哪了"、"它的缓存结果是什么"）。约束有三条：① 不能改动对象的结构（调用方会遍历、会序列化）；② 对象被回收时，你附加的数据也必须能回收（不能泄漏）；③ 调用方不该轻易看到这些内部数据。

### 🔒 先自己想

最直觉的做法是 `obj.__myCache = {...}`。想一下这三条约束里，哪条会最先破？如果用 `Map` 把对象当键存起来，又破了哪条？

<details>
<summary>💡 提示（思考方向）</summary>

- `obj.x = v` → 违反约束 ①（污染结构，且 `for...in` / `JSON.stringify` 都会带出来）
- `Map` 存 `[obj, data]` → 违反约束 ②（`Map` 对键是**强引用**，对象永远不会被回收）
- 那么需要一个"**键是弱引用**"的 Map —— 它叫什么？代价是什么？
- 如果这些对象是你**自己写的类**的实例，是不是有更直接的办法？
- "私有"这个词，你需要的到底是**防误用**还是**防恶意**？

</details>

<details>
<summary>📖 展开解法</summary>

### 解法一览

| 解法 | 怎么做 | 代价 | 适用边界 |
|---|---|---|---|
| **A. `WeakMap`**（默认解） | `const meta = new WeakMap(); meta.set(obj, data);` | 键**必须是对象**；**不可遍历、没有 `size`、无法清空** | **通用默认解**：外部对象 + 需要随对象回收 |
| **B. class 私有字段 `#x`** | 类里声明 `#cache`，只有类内部能访问 | 只适用于**你自己写的类**；外部传入的对象用不了 | 对象由你定义的场景（**真私有**，外部拿不到） |
| **C. `Symbol` 键** | `obj[mySym] = data` | **破坏了约束 ①**（仍在对象上，`getOwnPropertySymbols` 能看到）；且仍是强引用；不是真私有 | 需要数据**随对象一起序列化 / 可调试可见**时 |
| **D. 闭包内 `Map` + 显式清理** | 闭包持有 `Map`，对外暴露 `get/set/delete` | 强引用，忘了 `delete` 就泄漏；需要自己管理生命周期 | 键是字符串（`WeakMap` 用不了）时，必须配 LRU 上限 |
| **E. 外部注册表 + 显式 `dispose`** | 独立注册表 + 调用方显式清理 | 依赖调用方守约，漏调用就泄漏 | 需要能遍历 / 统计 / 批量清理的场景 |

### 推荐路径

1. **默认 A（`WeakMap`）**——三条约束里 ①② 它天然满足
2. 对象是你自己的类 → **B**（私有性最强，语法最干净）
3. 键是字符串 → 只能用 **D**，但**必须配容量上限**，否则就是场景 4 的泄漏
4. C 只在"必须随对象序列化"或"调试时要看得见"时考虑，且要清楚它**不是真私有**

### 关键取舍：`WeakMap` 为什么不能遍历？

这不是缺陷，是**设计上的必然**：如果能遍历，就意味着引擎必须知道"所有键"——那就得对键保持某种引用，弱引用就不成立了。**弱引用与可遍历，二者不可兼得。**

### 知识点挂钩

- [课 9 现代语法与内置数据结构](stages/3-异步与现代语法/lessons/lesson-09-现代语法与内置数据结构.md) —— `Map` vs `WeakMap` 的强/弱引用实测对比
- [课 6 原型与类](stages/2-函数与对象/lessons/lesson-06-原型与类.md) —— `#x` 私有字段（类外访问是**解析期 SyntaxError**，`try/catch` 抓不到）
- [课 3 作用域与闭包](stages/1-值与作用域/lessons/lesson-03-作用域与闭包.md) —— 闭包内持有容器
- [实战项目《异步任务编排器》](projects/异步任务编排器/设计决策.md) —— 缓存的 LRU vs WeakMap 决策点

### 不适用边界

- **需要遍历 / 需要 `size` / 需要批量清空** → `WeakMap` 直接出局，用 `Map` + 上限
- **键是字符串**（如 URL、ID）→ `WeakMap` 用不了，用 `Map` + LRU
- 需要**防恶意**级别的私有 → JS 没有这种机制，`#x` 也只是防误用（工具层面仍可绕过）

</details>

## 场景 6｜把回调风格的老 API 改造成 Promise

**场景**：项目里有一批老的回调风格 API（`(err, data) => {}` 风格，或者事件风格的 `on('done')`）。你想统一成 `async/await` 写法，并且要求：**出错时能追溯到根因**（不能只看到一个 "something went wrong"）。

### 🔒 先自己想

手写 `new Promise` 是最容易想到的。但请先回答：**executor 里面抛的错和 executor 外面（异步回调里）抛的错，Promise 都能接住吗？** 想清楚再往下看。

<details>
<summary>💡 提示（思考方向）</summary>

- Node 内置就有把 `(err, data)` 风格转成 Promise 的工具，叫什么？它省掉的到底是什么？
- 事件型 API（`on('done')` / `on('error')`）和回调型 API 的改造难度一样吗？监听器要不要清理？
- "追溯根因"这件事，错误链的哪个特性（ES2022 新增）能帮上忙？
- 手写 `new Promise` 时，最常见的两个坑是什么？（提示：一个关于**漏掉分支**，一个关于**错误捕获范围**）
- 万一 API 既不回调也不报错（超时了），你的 Promise 会怎样？

</details>

<details>
<summary>📖 展开解法</summary>

### 解法一览

| 解法 | 怎么做 | 代价 | 适用边界 |
|---|---|---|---|
| **A. 找库的 promises 版本** | 如 `require('fs/promises')`，很多库都自带 | 不是所有库都有 | **永远第一个找这个**——官方实现比自己写可靠 |
| **B. `util.promisify`** | `const read = promisify(fs.readFile)` | 只认标准的 `(err, value)` 回调约定；非标准约定要自定义 `promisify.custom` | 标准 error-first 回调风格 |
| **C. 事件型 API：`once()` + 超时 + 清理** | 监听 `done` / `error` 两个事件，`Promise.race` 加超时，`finally` 里移除监听器 | 代码量最大；容易漏清理监听器（这正是泄漏来源） | 事件风格 API（流、子进程、消息队列） |
| **D. 手写 `new Promise`** | 自己包一层 | **两个高危坑**（见下）；能用 A/B/C 就别用 | 以上都不适用时的最后手段 |
| **E. 用 `cause` 串错误链** | `new Error('读取配置失败', { cause: err })` | 需要 ES2022+；下游要会读 `cause` | **与上面任一组合**，解决"追溯根因" |

### 手写 `new Promise` 的两个高危坑（实测确认）

| 坑 | 表现 | 正确写法 |
|---|---|---|
| **漏掉分支** | 只在成功分支 `resolve`，失败分支什么都不做 → Promise **永远 pending**，`await` 静默挂死，**零报错** | 每个分支都要 `resolve` 或 `reject` |
| **接不住 executor 外的错** | `new Promise((resolve) => { setTimeout(() => { throw e }) })` —— Promise **接不住** executor 之外的异步错误，永远 pending；那个 `throw` 会冒成 `uncaughtException` | 异步回调里手动 `try/catch` 后 `reject(e)` |

### 推荐路径

1. **先找 A**（库的 promises 版本）
2. 没有就用 **B**（`util.promisify`）
3. 事件型 API 用 **C**（记得配超时和监听器清理）
4. **D 是最后手段**，写的时候先写 `reject` 分支，再写成功分支
5. **无论如何都配 E（`cause`）**——这才是"错误可追溯"的答案

### 知识点挂钩

- [课 8 Promise 与 async/await](stages/3-异步与现代语法/lessons/lesson-08-Promise与async-await.md) —— Promise 三态、`await` 语义
- [课 11 错误处理与调试](stages/4-工程化与运行时/lessons/lesson-11-错误处理与调试.md) —— `Error.cause`（ES2022）串错误链、自定义错误类、`try` 抓不到异步错误
- [课 12 内存·性能与选型收束](stages/4-工程化与运行时/lessons/lesson-12-内存性能与选型收束.md) —— 监听器未清理导致的泄漏

### 不适用边界

- **回调会被多次触发**（如进度事件）→ Promise 只能 settle 一次，这种情况该用**事件流 / async generator**，不是 Promise
- **需要中途取消** → Promise 本身没有取消语义，要用 `AbortController`
- 若老 API 的回调约定**不标准**（比如 `(data, err)` 顺序反了）→ `promisify` 会静默出错，必须看清楚约定再套

</details>

## 场景 7｜模块循环依赖导致启动崩溃

**场景**：项目启动就报错 `ReferenceError: Cannot access 'a' before initialization`，或者某个导入的值是 `undefined` 但没报错。画了一下 import 关系——**A 导入 B，B 又导入 A**，成环了。

### 🔒 先自己想

最常见的"土办法"是调整 import 顺序，试到能跑为止。先问自己：**这解决的是问题本身，还是只是让这次碰巧没炸？** 另外，为什么有时候报 `ReferenceError`，有时候只是 `undefined`？

<details>
<summary>💡 提示（思考方向）</summary>

- 报错说 "before initialization" —— 这是哪个机制在起作用？（提示：不是"变量不存在"）
- 为什么 `export const` 会抛错，而 `export var` 只是得到 `undefined`？
- 为什么**把访问放到函数里**就没事了？
- 两个模块互相需要对方的东西，这在**设计上**通常意味着什么？是不是有个东西被放错了地方？
- 除了"挪代码"和"延迟访问"，还有没有**架构层面**的防线？

</details>

<details>
<summary>📖 展开解法</summary>

### 解法一览

| 解法 | 怎么做 | 代价 | 适用边界 |
|---|---|---|---|
| **A. 提取第三模块**（首选） | 把 A 和 B 都需要的那部分挪到新模块 C，A、B 都改成依赖 C | 要动 import 关系；可能需要拆分文件 | **首选根治方案**；只要能抽出公共部分 |
| **B. 延迟访问**（止血） | 不在模块顶层访问导入值，改到**函数内部**再访问 | 只是绕开时序问题，**环仍然存在**；下次改代码可能又踩 | 临时止血 / 确实无法拆分的场合 |
| **C. 依赖倒置（注入）** | 不 import 具体实现，改为由上层传入（参数 / 工厂 / 容器） | 结构改动较大，需要重新梳理依赖方向 | 需要真正解耦时（插件、可替换实现） |
| **D. 合并模块** | A 和 B 本来就该在一起 → 合成一个文件 | 文件可能变大 | 拆分本身就不合理（过度拆分）时 |
| **E. lint 禁止环**（长期防线） | 引入依赖图检查（如 `eslint-plugin-import` 的 `no-cycle`） | 存量环会一次性暴露出来，需要排期清理 | **应该一直开着**，防止新的环产生 |

### 为什么 `const` 报错而 `var` 只是 `undefined`？（课 10 实测三种表现）

| 情形 | 表现 |
|---|---|
| `export const` + **顶层同步访问** | ❌ `ReferenceError: Cannot access 'a' before initialization`（TDZ） |
| `export var` + 顶层访问 | ⚠️ 得到 `undefined`（`var` 提升时已初始化，不进 TDZ） |
| **延迟访问**（放在函数里，调用时已初始化） | ✅ 完全正常 |

> 这解释了为什么"调整 import 顺序"能碰巧跑通——它改变的是**谁先完成初始化**，不改环本身。**下次有人加一行顶层访问，又会炸。**

### 推荐路径

1. **A 优先**（提取第三模块）——环消失，根治
2. 需要解耦 → **C**（依赖倒置）
3. 确实拆不动 → **D**（合并）
4. **B 只是止血**，用了就记一条技术债
5. **E 从第一天就开**——它防的是"下次"

### 知识点挂钩

- [课 10 模块化](stages/4-工程化与运行时/lessons/lesson-10-模块化.md) —— ESM 实时绑定 vs CJS 值拷贝；循环依赖三种表现的实测
- [课 1 变量与类型](stages/1-值与作用域/lessons/lesson-01-变量与类型.md) —— TDZ 与"变量不存在"的区别

### 不适用边界

- **CJS 的循环依赖表现完全不同**（拿到的是已完成部分的**值拷贝**，不是实时绑定）——排查前先确认你的模块系统
- 如果环是**跨层**的（比如业务模块 ← → 基础设施模块），那已经不是循环依赖问题，是**分层被破坏**，要按架构问题处理

</details>
