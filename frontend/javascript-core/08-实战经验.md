## 一、适用边界：什么时候「别这么用」

> **"不该用"比"怎么用"更值钱**——这是从"会用"到"用对"的分界线。

| 机制 | 别用它的场景 | 换成什么 | 为什么 |
|---|---|---|---|
| JS 主线程 | CPU 密集：大批量计算、大报文同步解析、图像处理、复杂正则 | `worker_threads` / 换算法 / 流式 | 一个同步任务独占整个线程，期间所有请求一起排队（故障模式 6） |
| 手写 `new Promise` | 能用 `async` 函数或 `util.promisify` 表达时 | `async` / `promisify` | 手写极易漏掉某个分支的 `resolve`/`reject`（故障模式 4） |
| `Promise.all` | 任务数不受控（几千到几万） | 并发上限（信号量 / worker 池）/ 分批 | 瞬时并发打满，下游先崩，且错误难定位（故障模式 1） |
| `JSON.parse(JSON.stringify(x))` | 对象含 `Date`/`Map`/`Set`/`undefined`/循环引用 | `structuredClone` | 静默改坏数据，只有循环引用会报错（故障模式 8） |
| `{...obj}` 浅拷贝 | 需要**独立副本**的嵌套对象 | `structuredClone` / 逐层重建 | 只复制第一层，嵌套仍共享（故障模式 9） |
| `try/catch` | 包异步回调里的错误 | Promise 的 `.catch` + 全局兜底 | `try` 的作用域是"栈帧存在的时间"，异步回调早就不在栈上了 |
| 嵌套量词正则 | 接受用户可控输入 | 改写为具体模式 + 输入长度上限 | 回溯爆炸，输入翻 8 倍耗时翻 463 倍（故障模式 7） |
| `==` | 除了 `x == null` 之外的一切 | `===`；`NaN` / `-0` 用 `Object.is` | `==` 的隐式转换表是坑的来源 |
| `FinalizationRegistry` | 需要**确定性**清理资源 | `try...finally` / 显式 `close()` | **规范不保证清理回调被调用**（课 12 已核实 MDN 原文） |
| `AbortSignal.timeout()` 单独使用 | **脚本 / CLI / 一次性任务**里作为唯一挂起的异步 | `setTimeout` 做哨兵 | 它的内部定时器是 **unref 的**，进程没别的句柄时超时**根本不触发**（实测，见故障模式 4） |
| `WeakMap` | 需要遍历、需要 `size`、键是字符串 | `Map` | 不可遍历、无 `size` 是设计取舍，不是缺陷 |
| 手写原型链继承 | 新项目 | `class extends` | 可读性与可维护性全面落后（课 6 五种继承横评） |

### 🐞 反模式速查（每条都有实测数字）

| 写法 | 实际结果 | 该怎么写 |
|---|---|---|
| `[10, 9, 1].sort()` | `[1, 10, 9]` —— 默认按**字符串**比较 | `.sort((a, b) => a - b)` |
| `['1','7','11'].map(parseInt)` | `[1, NaN, 3]` —— `parseInt` 收到 `(值, 索引, 数组)` 三个参数 | `.map((n) => parseInt(n, 10))` |
| `0.1 + 0.2 === 0.3` | `false`（`0.30000000000000004`） | 金额用**整数分**；比较用 `Math.abs(a-b) < Number.EPSILON` |
| `delete arr[1]` | `[1, <1 empty item>, 3]`，`length` 仍是 3，`map` 跳过空洞 | 删元素用 `splice` |
| `null == undefined` | `true`（但 `null === undefined` 是 `false`） | `x == null` 是唯一可接受的 `==` 惯用法 |
| `NaN === NaN` | `false` | `Number.isNaN(x)` 或 `Object.is(x, NaN)` |
| `0 === -0` | `true`（但 `Object.is(0, -0)` 是 `false`） | 需要区分 ±0 时用 `Object.is` |

### 故障模式 1｜循环里 `await`，批量任务退化成串行

**症状**：批量任务总耗时 ≈ **单任务耗时 × 任务数**；任务数翻倍，总时长也翻倍；但 CPU 和下游负载都很低（因为并发度恒为 1）。

**根因**：`await` 阻塞的是**当前 async 函数的剩余部分**。放在 `for` 循环体里，意味着"启动下一个任务"这件事本身被排在上一个任务完成之后——任务之间**完全不重叠**，并发度 = 1。

**排查路径**：
1. 量一下：总耗时 ÷ 任务数，看是否接近单任务耗时
2. 在循环里打时间戳，看任务**启动时刻**是均匀铺开的，还是严格串行排队
3. 换成 `Promise.all` 跑一次，若耗时降一个数量级 → 确认

**修复**：
- 无依赖、数量可控 → `await Promise.all(tasks.map(fn))`
- 无依赖、数量大 → 并发上限（信号量 / worker 池），见实战项目《异步任务编排器》
- 有依赖或需要限速 → 这才该串行，但要**显式写明**为什么

**预防**：写循环前先问一句"这些任务之间有依赖吗？"没有就不串行。Code Review 把 `for (...) { await ... }` 当红灯。

**【证据】实测（Node v22.14.0）** —— 12 个任务 × 50ms：

| 写法 | 实测耗时 | 说明 |
|---|---|---|
| 串行 `for` + `await` | **742 ms** | ≈ 12 × 50 |
| `Promise.all` | **62 ms** | ≈ 1 × 50，但瞬时并发 12 |
| 并发上限 3 | **247 ms** | ≈ 4 × 50 |
| 并发上限 5 | **184 ms** | ≈ 3 × 50 |

### 故障模式 2｜把 `async` 回调塞进 `forEach`，异步等于没发生

**症状**：`forEach` 之后的同步代码先执行，收集结果的数组是**空的**；等一会儿数据又"自己出现了"；`try/catch` 包不到回调里的错。

**根因**：`forEach` 的返回值是 `undefined`，它**忽略回调的返回值**——回调返回的那个 Promise 没有人 `await`，也就没人等它、没人接它的 rejection。同理 `reduce` 的累加器如果初值不是 Promise，最终得到的是一个 **Promise 而不是数字**。

**排查路径**：在紧跟其后的同步代码里 `console.log(结果数组.length)` → 为 0 即中招。

**修复**：
- 真要串行 → `for...of` + `await`
- 要并发 → `await Promise.all(items.map(...))`
- 要累加 → `reduce` 的初值必须是 `Promise.resolve(0)`，且每步 `await`

**预防**：**数组方法里出现 `async` 回调，除非外层有 `await Promise.all(...)`，一律视为 bug。** 这是团队约定，不是风格偏好。

**【证据】实测（Node v22.14.0）**：

```
forEach 之后立刻打印: []          ← 异步没被等待
50ms 之后再打印     : [1,2,3]

reduce(async, Promise.resolve(0)) → 6                （正确）
reduce(async, 0)                  → [object Promise] （得到 Promise，不是数字）
```

### 故障模式 3｜一个没人接的 rejection 干掉整个 Node 进程

**症状**：进程突然退出，**退出码 1**；日志里出现 `ERR_UNHANDLED_REJECTION` 和那行 `Error: xxx`。最迷惑的是——**同步代码其实全都跑完了**（错误是在本轮微任务清空之后才抛的），所以看起来是"功能都执行了，然后进程死了"。

**根因**：Node 自 **v15** 起，`--unhandled-rejections` 的默认值是 `throw`：没有 handler 的 rejection 会被**提升为 uncaught exception**。注册 `unhandledRejection` handler 后不再崩溃。

**排查路径**：
1. 看退出码是不是 1
2. 看日志是不是以 `ERR_UNHANDLED_REJECTION` 开头
3. 全局搜 `new Promise` / `async` 调用点，找既没有 `.catch`、也没被 `try { await }` 包裹的

**修复**：
- 单点 → 加 `.catch` 或 `try { await ... } catch`
- 兜底 → `process.on('unhandledRejection', (reason, promise) => { 记录; 决定重启还是降级 })`
- 浏览器侧 → `window.addEventListener('unhandledrejection', ...)`
- ⚠️ **兜底不等于处理**：只打日志不决策，会把故障模式 4 变成完美的静默挂死

**预防**：所有 `async` 入口函数外层包一层 catch；CI 的冒烟测试断言"进程退出码必须为 0"。

**【证据】实测（Node v22.14.0）**：

| 场景 | 退出码 |
|---|---|
| `Promise.reject(new Error())` 无人接 | **1**（进程崩溃） |
| 注册 `process.on('unhandledRejection')` 后 | **0**（存活） |

**【来源】** Node.js 官方文档（`--unhandled-rejections` 自 v15 起默认 `throw`，对应 nodejs/node commit `3b10f7f933`）+ 本机实测复现。

### 故障模式 4｜Promise 永不 settle，`await` 静默挂死

> **这是最难查的一类：没有任何报错、没有任何日志、CPU 几乎为空。**

**症状**：请求永远不返回、任务永远不完成、**零报错零日志**；进程也不退出（只要还有别的活跃句柄）。

**根因**（两种，机理完全不同）：

| 成因 | 机理 | 实测表现 |
|---|---|---|
| **(a) 漏了 resolve/reject** | `new Promise` 里只在部分分支 `resolve`，失败分支既没 `resolve` 也没 `reject` → 永远 pending | 看门狗打印 `finished = false`，**全程无任何报错** |
| **(b) executor 之外抛的错** | `new Promise((resolve) => { setTimeout(() => { throw ... }) })` —— Promise **接不住 executor 之外的异步错误**，`p` 永远 pending；那个 `throw` 冒成 `uncaughtException` | 无兜底时进程崩溃（退出码 1）；**有兜底且兜底只打日志 → 变成"永不 settle + 看不到真错误"的完美静默** |

**排查路径**：
1. 用 `Promise.race([p, 超时哨兵])` 判定 `p` 到底有没有 settle
2. 检查 `new Promise` 的**每一个分支**是否都有 `resolve` 或 `reject`
3. 全局兜底里务必同时打印 `promise` 对象，不能只打 `reason`

**修复**：
- 所有路径都要 settle（养成"先写失败分支"的习惯）
- 异步回调里的错误手动 `try/catch` 后 `reject(e)`
- **给所有外部调用加超时**——超时不是可选配置，是默认配置

**⚠️ 但"加超时"本身有个坑（实测，Node v22.14.0）**：`AbortSignal.timeout()` 的内部定时器是 **unref 的**——它**不会阻止进程退出**。

> **unref 是什么（白话）**：Node 判断"进程该不该退出"的方式，是数一数还有没有**活跃句柄**（定时器、socket、server……）。`unref` 相当于给这个定时器贴了个标签——**"我干活，但别把我算进去"**。于是 Node 数完发现"没事可干了"，直接退出，那个定时器连同它的超时逻辑一起蒸发。

决定性实验（全程不注册任何其他定时器 / 句柄，看 50ms 后是否触发）：

| 唯一挂起的东西 | 结果 |
|---|---|
| `AbortSignal.timeout(50)` | ❌ **abort 不触发，进程直接退出（exit 0）** |
| `setTimeout(..., 50)` | ✅ 正常触发 |

- **常驻服务**（有 HTTP server / 定时器等活跃句柄）→ `AbortSignal.timeout` 完全正常，放心用
- **脚本 / CLI / 一次性任务 / 单测**里，若它是唯一挂起的东西 → **超时根本不会触发**，进程静默退出。你以为加了保护，实际什么都没保护
- 稳妥写法：用 `setTimeout` 做哨兵，或确保进程另有活跃句柄
- ⚠️ 这是 **Node 侧行为**（浏览器没有"进程退出"概念，不适用）
- 💡 顺带记住：**"没保存 signal 的引用会被 GC 掉"这个猜测是错的**——实测即使强制 `gc()` 也照常触发，真因是 unref

**预防**：能用 `async` 函数就别手写 `new Promise`；手写的每一个 `new Promise` 都配一个超时（并确认这个超时**真的会触发**）。

### 故障模式 5｜方法提取丢 `this`

**症状**：`TypeError: Cannot read properties of undefined (reading 'name')`；非严格模式下 `this` 悄悄变成 `globalThis`；箭头函数当对象属性时拿到的是**外层的** `this`。

**根因**：`this` 由**调用点**决定，不看函数"出生在哪"。`const f = obj.method` 之后 `f()` 是裸调用 → 严格模式下 `this` 为 `undefined`。**解构赋值、当回调传参、取出后延迟调用，全都会丢。**

**排查路径**：报错行是不是"某个对象的方法"？这个方法有没有被当值传出去过？

**修复**：

| 手段 | 适用 |
|---|---|
| `f.bind(obj)` | 反复用同一个实例 |
| 箭头包装 `() => obj.method()` | 当回调传出去 |
| class 里用**类字段箭头函数** | 组件回调、事件处理器 |
| `f.call(obj)` / `f.apply(obj)` | 一次性调用 |

> ⚠️ **立即执行陷阱**：`setTimeout(fn.call(o), ms)` 传的是**调用结果**不是函数——括号一加就当场执行了。

**预防**：把方法当值传递时一律显式绑定；class 里需要当回调的方法直接写成箭头字段。

**【证据】实测（Node v22.14.0，严格模式）**：

```
obj.greet()                → hi alice
const f = obj.greet; f()   → TypeError: Cannot read properties of undefined (reading 'name')
箭头函数作为对象属性        → hi undefined   （拿到的是外层 this）
f.bind(obj)()              → hi alice
f.call(obj)                → hi alice
```

### 故障模式 6｜一段同步代码把事件循环卡死

**症状**：**所有**请求的 P99 一起飙升（不是某一个接口慢）；定时器大幅延迟；健康检查超时导致实例被摘除；CPU **单核** 100%。

**根因**：JS 只有一个调用栈。任何同步代码（大循环、大报文同步解析、复杂正则、同步加密）都会**独占**整个线程，期间所有宏任务和微任务全部排队等着。

**排查路径**：用 `perf_hooks.monitorEventLoopDelay`——**这是唯一能直接量化"事件循环被堵了多久"的官方手段**，比看 CPU 更准：

```js
const { monitorEventLoopDelay } = require('perf_hooks');
const h = monitorEventLoopDelay({ resolution: 10 });
h.enable();
// ... 跑一段时间 ...
h.disable();
console.log((h.max / 1e6).toFixed(1), 'ms');   // 最大值 = 最长的一次堵塞
console.log((h.percentile(99) / 1e6).toFixed(1), 'ms');
```

**【证据】实测（Node v22.14.0）**：主线程阻塞 300ms 时：

```
min = 14.8ms | mean = 38.9ms | max = 316.4ms | p99 = 316.4ms | 采样数 = 13
```

同时一个期望 0ms 触发的定时器，**实际延迟 302ms**。

**修复**：

| 手段 | 适用 |
|---|---|
| **分片**（`setImmediate` / 定时器切块让出主线程） | 中等耗时、可以切成小步 |
| **`worker_threads`** | 重计算，且结果可以异步等 |
| **换算法** | 复杂度本身有问题（见故障模式 7） |
| **流式处理** | 大报文 / 大文件，不必整体载入 |

**实测 worker 解法**：worker 干 558ms 重活的同时，**主线程定时器仍滴答了 36 次** → 事件循环完全没被阻塞。

**预防**：请求路径上禁止无上限的同步循环；大 JSON 用流式解析；对用户可控的输入设长度上限。

> 📖 回指：[课 7 事件循环](stages/3-异步与现代语法/lessons/lesson-07-事件循环.md)

### 故障模式 7｜CPU 打满的元凶，可能只是一条正则（ReDoS）

**症状**：某个接口的耗时与**某个输入字段的长度**强相关——短输入一切正常，长输入直接秒级；CPU 100%，而不是在等 I/O。

**根因**：JS 的正则引擎（V8 Irregexp）是**回溯型**。含**嵌套量词**（`(a+)+`、`.*.*=.*;`）的模式在匹配失败时，步数呈多项式甚至指数级爆炸。

**【证据】实测（Node v22.14.0）** —— 输入翻 8 倍，耗时翻 **463 倍**：

| 模式 | 输入 | n=500 | n=1000 | n=2000 | n=4000 |
|---|---|---|---|---|---|
| `/.*.*=.*;/`（Cloudflare 同款结构） | `"x=" + "x"×n` | 25.5 ms | 182.9 ms | 1400.8 ms | **11815.9 ms** |

> 输入长度每翻一倍，耗时约 **×7~8**（≈ O(n³)）。**4000 个字符就能吃掉主线程 11.8 秒。**

| 模式 | n=24 | n=26 |
|---|---|---|
| `/^(a+)+$/`（经典嵌套量词） | 49.4 ms | **201.1 ms**（多 2 个字符，涨 4 倍） |
| `/^a+$/`（去掉嵌套，改写后） | 0.001 ms | 0.002 ms（**n=4000 也只要 0.003 ms**） |

**排查路径**：
1. 二分法缩短可疑输入，看耗时是否**断崖式**下跌（线性下跌是正常处理量，断崖 = 回溯爆炸）
2. 用正则静态分析工具（如 `recheck` 系）扫源码里的嵌套量词
3. 检查正则的输入是否**用户可控**

**修复**：
- **改写为更具体的模式**，去掉嵌套量词（实测 `.*.*=.*;` → `^[^=]*=[^;]*$` 后降到微秒级）
- **限制输入长度**（这是成本最低的一道保险）
- 放 worker + 超时兜底
- 极端场景换有**线性时间保证**的引擎（Cloudflare 事后就是这么做的，见事故案例）

**预防**：**任何接受用户输入的正则，禁止出现嵌套量词。** Code Review 把 `.*` 连用、`(x+)+`、`(x*)*` 当红灯。

> 📌 **这条是课外补充**：正则**不在**本课程大纲内（课程聚焦语言核心，见 [`01-学习路径总览.md`](01-学习路径总览.md) 的「课程边界」）。之所以收录，是因为它是"事件循环被阻塞"**最常见的真实成因之一**，且与 [课 7 事件循环](stages/3-异步与现代语法/lessons/lesson-07-事件循环.md) 直接相关——不学它，故障模式 6 就只剩一半答案。

### 故障模式 8｜用 JSON 往返做"深拷贝"，数据被静默改坏

> 最阴险的地方：**它不会报错**（循环引用除外），数据是被**悄悄**改坏的。

**症状**：字段莫名其妙消失；`Date` 变字符串后下游调 `.getTime()` 报 `xxx.getTime is not a function`；`NaN` 变成 `null`；`Map`/`Set` 变成空对象 `{}`；遇到循环引用直接 `TypeError: Converting circular structure to JSON`。

**根因**：`JSON.stringify` 只认 JSON 的数据模型（对象 / 数组 / 字符串 / 数字 / 布尔 / null）。超出这个模型的值**静默丢弃或降级**，只有循环引用会报错。

**【证据】实测（Node v22.14.0）**：

| 原始类型 | `JSON.parse(JSON.stringify(x))` 之后 |
|---|---|
| `Date` | `"2026-01-01T00:00:00.000Z"` —— **变成字符串** |
| `undefined` 字段 | **字段直接消失**（`'k' in obj` 为 false） |
| 函数 / `Symbol` 字段 | **字段直接消失** |
| `NaN` / `Infinity` | `null` |
| `Map` / `Set` / `RegExp` | `{}` —— 变成空普通对象 |
| 循环引用 | `TypeError: Converting circular structure to JSON` |

**对照：`structuredClone`（实测）**

| 检查项 | 结果 |
|---|---|
| `Date` 仍是 `Date` | ✅ |
| `Map` 仍是 `Map` / `Set` 仍是 `Set` | ✅ |
| 支持循环引用（结构被保留） | ✅ |
| 深拷贝独立（改副本不影响原对象） | ✅ |
| 克隆**函数** | ❌ `DOMException: could not be cloned` |
| 克隆 **Symbol** | ❌ `DOMException: could not be cloned` |

**排查路径**：对可疑字段在拷贝前后各打一次 `typeof` 和 `Object.prototype.toString.call()`。

**修复**：
- 纯数据 → **`structuredClone`**（Node 17+，浏览器 2022-03 起 Baseline）
- 需要精确控制（如保留原型、处理特殊类）→ 手写递归或成熟库
- ⚠️ `structuredClone` 也**不克隆函数与 Symbol**，且**丢掉原型链**（结果是普通对象）——这两条是边界，不是 bug

**预防**：**把"深拷贝"当成一个需要选型的决策，而不是一行语法。**

> 📖 回指：[课 2 值的复制与比较](stages/1-值与作用域/lessons/lesson-02-值的复制与比较.md) · [课 9 现代语法与内置数据结构](stages/3-异步与现代语法/lessons/lesson-09-现代语法与内置数据结构.md)

### 故障模式 9｜浅拷贝共享引用，改 A 动了 B

**症状**：改了新对象的嵌套字段，回头发现原对象也被改了；配置被污染；"我明明没动过那个变量"。

**根因**：`{...obj}` / `Object.assign({}, obj)` / `arr.slice()` 只复制**第一层**。嵌套的子对象复制的是**指针**，新旧对象共享同一个子对象。

**【证据】实测（Node v22.14.0）**：

```
const defaults = { opts: { retries: 3 } };
const merged = { ...defaults };
merged.opts.retries = 99;
defaults.opts.retries  →  99    ← 原对象被改了（嵌套层共享）

const top = { retries: 3 };
const m2 = { ...top };
m2.retries = 99;
top.retries  →  3               ← 顶层不受影响（第一层是独立副本）
```

**排查路径**：改值前后打印两侧的嵌套字段；或直接比较引用 `a.nested === b.nested`。

**修复**：
- 要完全独立的副本 → `structuredClone`
- 只想改一层且保持不可变 → **显式逐层重建**：`{ ...obj, nested: { ...obj.nested, k: v } }`
- 函数式写法惯例：**改嵌套时只重建路径上的对象**

**预防**：写下 `{...x}` 的时候默念一句"只复制一层"。

> 📖 回指：[课 2 值的复制与比较](stages/1-值与作用域/lessons/lesson-02-值的复制与比较.md) · [课 9 现代语法与内置数据结构](stages/3-异步与现代语法/lessons/lesson-09-现代语法与内置数据结构.md)

### 故障模式 10｜TDZ：`Cannot access 'x' before initialization`

**症状**：`ReferenceError: Cannot access 'later' before initialization`。

> ⚠️ 它和"变量没定义"的 `ReferenceError: x is not defined` **不是一回事**——后者的变量压根不存在，前者的变量**已经存在，只是还没初始化**。

**根因**：`let` / `const` 声明的变量在进入作用域时就**创建了绑定**，但在执行到声明语句之前处于**暂时性死区（TDZ）**，此时**连 `typeof` 都会抛错**（`var` 则是 `undefined`，因为提升时顺带初始化了）。

**【证据】实测（Node v22.14.0）** —— 三种触发方式：

```
声明前访问 let 变量   → ReferenceError: Cannot access 'later' before initialization
typeof 也触发 TDZ     → ReferenceError: Cannot access 'later2' before initialization
参数默认值互相引用     → ReferenceError: Cannot access 'b' before initialization
```

**排查路径**：看报错的变量名，确认是不是"用在了声明之前"——三种常见形态：
1. 代码顺序问题（函数在声明之前被调用）
2. **ESM 循环依赖**（`export const` + 顶层同步访问，课 10 实测）
3. 参数默认值互相引用

**修复**：
- 代码顺序 → 把声明提到使用之前
- 循环依赖 → 见 [`10-场景解法库.md`](10-场景解法库.md) 场景 7 的三个解法
- 参数默认值 → 调换参数顺序或改在函数体内处理

**预防**：函数里别引用后面才声明的模块级 `const`；**循环依赖一律视为设计问题，不要靠"调整 import 顺序"糊过去**。

> 📖 回指：[课 1 变量与类型](stages/1-值与作用域/lessons/lesson-01-变量与类型.md) · [课 10 模块化](stages/4-工程化与运行时/lessons/lesson-10-模块化.md)

## 三、落地 Checklist

### ✍️ 写代码时（每次提交前扫一遍）

- [ ] 循环里没有裸 `await`（除非确实需要串行，且已写明原因）
- [ ] 数组方法里没有无人等待的 `async` 回调
- [ ] 每个 `async` 入口函数外层都有 catch
- [ ] 手写的每个 `new Promise`，所有分支都 `resolve`/`reject`，且**配了超时**
- [ ] 外部调用（网络 / 数据库 / 子进程）都有超时
- [ ] 深拷贝用的是 `structuredClone`（而非 JSON 往返），且确认对象里没有函数 / Symbol
- [ ] `{...x}` 的地方确认过"只复制一层"是不是你想要的
- [ ] 用户可控输入上的正则**没有嵌套量词**，且有长度上限
- [ ] 定时器 / 事件监听器 / 订阅都有对应的清理路径
- [ ] 长期存活的容器（`Map` / 数组 / 缓存）有**上限**或淘汰策略
- [ ] 方法被当值传递时已显式绑定 `this`
- [ ] 没有依赖 `==` 的隐式转换（`x == null` 除外）

### 🚀 上线前

- [ ] 注册了 `process.on('unhandledRejection')` 和 `uncaughtException` 兜底，且兜底里**有明确的决策**（重启 / 降级），不是只打日志
- [ ] 接入了事件循环延迟监控（`monitorEventLoopDelay`），且有告警阈值
- [ ] 内存有基线与告警（`process.memoryUsage().heapUsed` 长期趋势）
- [ ] 冒烟测试断言**进程退出码为 0**（能挡住故障模式 3）
- [ ] 测试里至少有一条"**大输入下的耗时上限**"用例（能挡住故障模式 7 —— Cloudflare 的单元测试全绿，恰恰是因为只测了功能没测 CPU）
- [ ] 有回滚路径，且**回滚耗时 ≤ 发布耗时**

## 四、真实事故案例复盘

### Cloudflare 全球 502（2019-07-02，中断 27 分钟）

**【来源】** Cloudflare 官方复盘博客《Details of the Cloudflare outage on July 2, 2019》（核查于 2026-09，一手来源，非二手转述）

**时间线（UTC）**：

| 时刻 | 事件 |
|---|---|
| 13:42 | 工程师通过自动化流程部署一条 WAF Managed Rule（XSS 检测规则） |
| 13:45 | 首个 PagerDuty 告警（WAF 外部合成测试失败），随后全球流量下跌、大面积 502、各 PoP 报告 CPU 耗尽 |
| 14:00 | 定位到 WAF 是问题源头，排除攻击可能（Performance 团队拉了实时 CPU 数据） |
| 14:07 | 执行全局 WAF 终止（global terminate） |
| 14:09 | 流量与 CPU 恢复正常 |
| 14:52 | 确认根因并修复，全球重新启用 WAF |

**根因链**（官方列出 11 条收敛因素，这里取与 JS 开发最直接相关的 4 条）：

1. 一条正则写成了 `.*(?:.*=.*)` 这种**会灾难性回溯**的结构
2. 几周前一次"让 WAF 更省 CPU"的重构，**误删**了防止正则过度消耗 CPU 的保护机制
3. 所用的正则引擎（PCRE）是回溯型，**没有复杂度保证**
4. 测试套件**不检测 CPU 消耗**——单元测试全绿，因为只测了"该拦的是否拦住、该放的是否放过"

**⚠️ 技术栈差异（必须说清，别被带偏）**：Cloudflare 的 WAF 用的是 **Lua + PCRE，不是 JavaScript**。

**但机制完全同源——都是回溯型正则引擎。** 本文件故障模式 7 的实测直接证明了这一点：同样的 `.*.*=.*;` 结构在 **V8 上**，4000 字符就能吃掉主线程 **11.8 秒**。在 Cloudflare 的场景里，这意味着每个 CPU 核都被一条规则钉死在 100%，HTTP/HTTPS 服务全部饿死。

**三条能直接搬进你自己项目的教训**：

| # | 教训 | 落地动作 |
|---|---|---|
| 1 | **测试套件必须有"耗时"这一维** | Cloudflare 的单元测试全绿却挡不住事故——因为它们只断言功能。你的测试里至少加一条"大输入下的耗时上限" |
| 2 | **保护机制被误删 = 事故** | 那个 CPU 保护是在一次"优化性能"的重构中被顺手删掉的。任何性能保护代码都要有测试兜住，否则迟早被当成无用代码清掉 |
| 3 | **能全球秒推的能力，也要能全球秒撤** | 他们的 Quicksilver 能在 p99 2.29 秒内把变更推到全球每台机器，但回滚要跑两次完整 WAF 构建。**发布速度与回滚速度必须匹配** |

**官方整改**（抄作业清单）：换用 re2 或 Rust regex 引擎（**两者都有运行时复杂度保证**）→ 规则纳入 staged rollout（而非全球直推）→ 测试套件加入性能剖析 → 逐条复查全部 3,868 条规则。

> 💡 **顺带记住那个 1968 年的答案**：官方复盘附录指出，避免回溯的正解 Ken Thompson 在 1968 年就给出了——把正则转成 NFA 并同时跟踪多个状态，匹配时间**与输入长度成线性**。JS 生态里换引擎不现实，所以你的武器是：**改写模式 + 限制输入长度 + 超时兜底**。
