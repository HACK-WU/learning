# 设计决策

> 本文件记录本项目中的 **3 个真权衡点**。
> 每个都用五段式写：**候选方案对比 → 最终选择 → 选择理由 → 为此付出的代价 → 什么情况下该改选另一个**。
>
> ⚠️ 判定「真权衡」的标准：**换个人来，可能选另一个方案，而且也有道理**。把"唯一正确答案"包装成决策点不算。

---

## 决策点 1：并发调度用哪种机制？

### 候选方案对比

| | **A. 活动计数 + 等待队列**（Semaphore） | **B. 递归 Promise 链** | **C. Worker 池** |
|---|---|---|---|
| 思路 | 数着当前几个在跑，超了就排队，有人释放就唤醒队首 | 递归地"跑完一个再拉下一个" | 预先起 N 个工人，每个工人循环从队列里取活 |
| 代码量 | 中（约 60 行） | 小（约 10 行） | 中大（约 80 行，还要管工人生命周期） |
| 能否加优先级 | ✅ 改队列的取出策略即可 | ❌ 链条固定，插不进去 | ✅ 队列换个取法即可 |
| 能否观测状态 | ✅ `active` / `pending` 一目了然 | ❌ 只能外部自己数 | ✅ |
| 任务持续流入 | 一般（排队唤醒模型） | 差 | **✅ 天然契合**（工人一直在取） |
| 能否取消排队中的任务 | 要额外记 handle | ❌ | ✅ 不取就不跑 |
| 典型使用者 | `p-limit` | 不少人的第一版实现 | 线程池 / 消费者组 |

### 最终选择

**A. 活动计数 + 等待队列**（见 `src/semaphore.js`）

### 选择理由

1. **本项目的形状是"批量任务"**，不是"持续流入的任务流"。一次性给一批任务、等它们跑完 —— C 的"工人常驻"优势完全用不上，反而要额外管理工人的创建与退出。
2. **需要暴露 `active` / `pending`**。这一点在课 12 里特别重要：**内存与性能问题，第一要务是"看得见"**。B 只能让使用者自己在外部数，等于把观测责任甩出去。
3. **A 的等待队列是一个显式数组**，未来要加优先级、去重、超时丢弃，都只改这一处。B 的递归链条把这些可能性都封死了。

### 为此付出的代价

1. **手写释放逻辑，漏一次就死锁**。名额必须归还，所以 `semaphore.run()` 用 `try...finally` 包住（课 11）—— 少一次 `release()`，并发数就永久少一，队列后面的任务永远醒不过来。
2. **释放函数必须做成幂等**。`#makeRelease()` 里那个 `released` 闭包变量（课 3）就是为此存在的：调用方重复调用不能把计数搞乱。
3. 相比 B，代码量大了约 6 倍。

### 什么情况下该改选另一个

| 情况 | 改选 | 理由 |
|---|---|---|
| 任务是**持续流入**的（如 Web 服务器的请求排队） | **C（Worker 池）** | "工人取活"比"排队唤醒"更贴合，还能平滑应对突发流量 |
| 只是想快速限流，不需要观测、优先级、动态加任务 | **B（递归 Promise 链）** | 代码量小一个数量级，够用就别过度设计 |
| 需要**取消还在排队**的任务 | **C** | A 要额外记 handle 才能删队列元素；C 里"不取"就等于取消 |

## 决策点 2：超时怎么做到「真取消」？

### 候选方案对比

| | **A. 只用 `Promise.race`** | **B. 只用 `AbortController`** | **C. race 判定 + abort 通知** |
|---|---|---|---|
| 到点一定返回 | ✅ | ❌ 任务不理会就永远不返回 | ✅ |
| 任务真的停下来 | ❌ **假取消** | ✅（前提：任务配合） | ✅（前提：任务配合） |
| 要求任务配合 | 不需要 | **需要** | 需要（但不配合也能降级工作） |
| 实现复杂度 | 3 行 | 简单 | 中等，**且顺序敏感** |
| 错误语义 | 明确的 `TimeoutError` | `AbortError` | 明确（但要小心实现顺序） |

**本机实测的关键证据**（`examples/demo.js` 场景 3，超时设 80ms、任务本身 2000ms）：

```
[真取消] 外层收到: TimeoutError — 任务超时（80ms）
[真取消] 超时后仍活着的底层定时器: 0  ← 立刻归零，资源马上释放
[假取消] 外层收到: TimeoutError — 任务超时（80ms）
[假取消] 超时后仍活着的底层定时器: 1  ← 它还在后台倒数 600ms
```

**两次外层拿到的错误完全一样**（都是 `TimeoutError`）—— 区别只发生在看不见的底层：假取消下，那个任务还挂着一个 600ms 的定时器没清理。这就是课 12 讲的**泄漏 ②**：不清理的定时器会把整个回调闭包一直留着。

### 最终选择

**C. `Promise.race` 负责"到点判定"，`AbortController` 负责"通知收手"**（见 `src/timeout.js`）

### 选择理由

1. **A 单独用在生产环境就是埋雷**：你以为任务停了，其实它还在打下游、还占着资源。上面的实测把这个"看不见"的差别摆到了台面上（0 vs 1）。
2. **B 单独用无法保证"到点返回"**：任务若不理会 `signal`，就永远不会超时 —— 超时机制本身就失效了。
3. **C 是二者的最小可行组合**，也是标准 API 的思路（`fetch` + `AbortSignal.timeout()` 就是这个模式）。

### 为此付出的代价

1. **实现顺序敏感**。`src/timeout.js` 里那两行的顺序不能换：

   ```js
   reject(new TimeoutError(...));   // ① 先让 race 判定为「超时」
   controller.abort();              // ② 再通知任务收手
   ```

   反过来写会怎样？`controller.abort()` 会**同步**触发任务的 abort 监听，任务随即 `reject(AbortError)`，于是 `race` 先拿到 `AbortError` 而不是 `TimeoutError`。后果很实际：**上层就分不清"超时"和"主动取消"了** —— 而这两者在课 11 的错误边界里是不同的决策（`isRetryable` 里超时可重试、取消不该重试）。

2. **真取消依赖任务配合**。任务不读 `signal` 时，C 会**静默退化**成 A —— 外层看起来一切正常，底层其实还在跑。这个"静默退化"是本方案最危险的地方，只能靠约定与代码审查兜底。

### 什么情况下该改选另一个

| 情况 | 改选 | 理由 |
|---|---|---|
| 任务完全无法中断（黑盒第三方调用，没有 signal 参数） | **接受 A**，但必须在文档写明「超时 ≠ 任务停止」 | 没有更好的选择，但**不能假装它是真取消** |
| 任务本身就是 `fetch` / `fs.promises` 等支持 signal 的标准 API | **直接用 `AbortSignal.timeout(ms)`**，连 race 都不用写 | Node 20+ / 现代浏览器原生支持，比手写少一层 |
| 需要"超时后仍继续跑，只是不等它了" | **A** | 这是明确的设计意图（fire-and-forget），不是缺陷 |

## 决策点 3：结果缓存用什么？

### 候选方案对比

| | **A. 无界 Map / 普通对象** | **B. 有界 Map + LRU 淘汰** | **C. `WeakMap`** |
|---|---|---|---|
| 写法 | 最简单 | 中等（要写淘汰逻辑） | 最简单 |
| 内存 | ❌ **只增不减 = 泄漏** | ✅ 有上限，可控 | ✅ 自动清理 |
| 键的类型 | 任意（Map）/ 字符串数字（对象） | 任意 | **必须是对象** |
| 能否遍历 / 拿 size | ✅（Map） | ✅ | ❌ |
| 能否主动清空 | ✅ | ✅ | ❌ |
| 典型使用者 | 初学者的第一版 | 大多数生产缓存 | "给别人的对象附加数据" |

### 最终选择

**B. 有界 `Map` + LRU 淘汰**（见 `src/cache.js`）

### 选择理由

1. **本项目的缓存 key 是业务字符串**（调用方通过 `cacheKey` 传入），不是对象 —— **C 直接用不了**。`WeakMap` 的键必须是对象，这是硬性限制（课 9）。
2. **A 直接排除**：它就是课 12 泄漏 ④ 的原型 —— 一个永不清理的容器。而且普通对象还额外撞原型链（`cache['constructor']` 会命中 `Object.prototype` 上的东西）。
3. **B 的淘汰逻辑可以很短**：利用 Map 的**插入顺序**（课 9），"命中后先删再插"就等于"挪到队尾"，队首自然是最久未用的。

### 为此付出的代价

1. **每次命中都要做一次"先删再插"**。虽然是 O(1)，但比"读一下就返回"多两步。
2. **上限 `max` 需要拍脑袋**。太小 → 频繁淘汰，缓存命中率低；太大 → 内存占用高。这个参数没有通用最优解，只能按实际负载调。
3. **key 的正确性责任被推给了调用方**。本实现里 `cacheKey` 由使用者提供：给错了会导致缓存串味（两个不同任务共用一份结果）或失效。库本身无法校验。
4. **会淘汰掉仍然有用的数据**。LRU 只关心"最近用没用过"，不关心"重算一次有多贵"。

### 什么情况下该改选另一个

| 情况 | 改选 | 理由 |
|---|---|---|
| 缓存的键**天然是对象**（给某个 DOM 节点 / 请求对象 / 实体附加元数据） | **立刻换 C（`WeakMap`）** | 零维护且不会泄漏 —— 这正是课 9、课 12 反复讲的**通用解** |
| 需要按**时间**过期（TTL），而不是按"最近使用" | **换成 TTL 缓存**（每条记过期时间 + 惰性删除/定时扫描） | LRU 解决不了"数据会变陈旧"的问题 |
| 数据量极小、生命周期与进程一致（如启动时的配置表） | **A 也无所谓** | 此时的"不释放"就是设计的一部分，不算泄漏 |
| 需要"重算成本越高越该留下" | **换成分级/带权重的缓存**（如按 cost 排序淘汰） | LRU 的"最近用过"和"值得留下"不是一回事 |

## 附：本项目刻意**没有**做的决策

写清楚"没做什么"和"做了什么"同样重要 —— 这些都是真实的工程范围问题，不是遗漏：

| 没做 | 原因 |
|---|---|
| 不做持久化 | 超出"语言核心"范围，会引入 I/O 与序列化，把注意力从语言机制上带走 |
| 不做分布式调度 | 需要外部协调服务，与本课程边界（DOM/框架/后端 API 不在范围内）冲突 |
| 不引入任何第三方依赖 | 一是零依赖最能体现"语言核心"；二是避免 `node_modules/` 污染产物仓库 |
| 不上 TypeScript | 按课 12 的判断条件：单人练手项目 + 依赖生态为空 + 目标是练 JS 本身 → 不上。真要上，见课 12「翻转点」 |
