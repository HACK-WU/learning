# 反例对照：一个「能跑」但很糟的任务队列

> 这份文档的价值在于：**反例不是写错的代码，而是能跑通 happy path 的代码**。
> 明显有语法错误的东西没有教学价值 —— 真正害人的是那些"测了一下没问题"就上线的写法。
>
> 完整可运行版本：[`实现/examples/bad-queue.js`](实现/examples/bad-queue.js)（`node examples/bad-queue.js`）

---

## 反例本体（核心片段）

```js
const jobs = [['A', 60], ['B', 30], ['C', 90], ['D', 20]];
const results = [];

// ❌ BAD 1：没有并发上限
try {
  // ❌ BAD 2：try/catch 包在 forEach 外面
  jobs.forEach(async ([id, ms]) => {
    if (ms > 80) {
      // ❌ BAD 3：抛字符串
      throw `${id} 太慢了`;
    }
    await sleep(ms);
    results.push(id);
  });
} catch (e) {
  console.log('接住了：', e);      // ← 永远不会执行
}

await sleep(200);                   // ❌ BAD 4：用 sleep 猜时间
```

**实测输出**（`node examples/bad-queue.js`）：

```
--- BAD 1~3：并发、错误捕获、抛什么 ---
  完成的（顺序随机）: D, B, A
  兜底接到的: C 太慢了
  ↑ C 失败了，但主流程毫发无伤地继续跑完 —— 错误被静默吞掉。
    更糟的是：如果没装 unhandledRejection 兜底，进程在这里就退出了（退出码 1）。
    而且兜底接到的只是一个字符串，没有 stack，查不到是哪一行。
```

**注意看**：这个 bad 脚本里**已经装了** `unhandledRejection` 兜底才跑得下去。不装会怎样？**进程直接崩溃，退出码 1** —— 这是课 11 知识点 2 讲的两套兜底之一。

## 逐条对比

### ① 没有并发上限

| | 反例 | 正确做法 |
|---|---|---|
| 做法 | `jobs.forEach(async ...)` 一次性全部发出 | 用 `Semaphore` 限制同时执行的数量 |

**为什么能跑通**：4 个任务、每个几十毫秒，当然没问题。

**为什么糟**：这段代码的行为**随输入规模突变**。4 个任务 = 4 个并发；4 万个任务 = 4 万个并发 —— 文件描述符耗尽、下游被打崩、内存飙升，全都在"任务变多"的那一刻集中爆发。**在小样本测试里，这个缺陷是隐形的。**

**回扣**：课 7 事件循环、课 8 并发控制、[设计决策.md 决策点 1](设计决策.md)

---

### ② `try...catch` 包在 `forEach` 外面

| | 反例 | 正确做法 |
|---|---|---|
| 做法 | `try { arr.forEach(async () => { throw ... }) } catch {}` | `Promise.allSettled(...)` 或在 async 函数内部 try |

**为什么能跑通**：`try` 块同步执行完了，没有任何错误 —— 于是看起来"没报错"。

**为什么糟**：`forEach` 只是**同步地**把回调挨个调一遍，它**不 await** 任何东西。回调里的 `throw` 发生在若干毫秒之后，那时 `try` 所在的函数早就跑完了 —— **栈上根本没有 catch 在等它**（课 11 知识点 2 的核心结论）。

结果就是：**错误被静默吞掉**。上面的实测里，C 失败了，但主流程"毫发无伤"地继续跑完，还打印出了"D, B, A"。线上最难受的就是这种 —— 不是崩溃，是**数据悄悄少了一条**，没人知道。

**回扣**：课 11 知识点 2（`try` 的作用域是"栈帧存在的时间"）

---

### ③ 抛字符串而不是 `Error`

| | 反例 | 正确做法 |
|---|---|---|
| 做法 | `throw \`${id} 太慢了\`` | `throw new TimeoutError(...)` |

**为什么能跑通**：`throw` 后面跟什么都能跑（ES3 就定下的宽松传统）。

**为什么糟**（课 11 实测）：

| throw 的值 | `e.message` | `e.stack` |
|---|---|---|
| `'出错了'` | `undefined` | **`undefined`** |
| `new Error('出错了')` | `'出错了'` | 完整的调用栈 |

兜底接到的那个"字符串"**没有 stack** —— 你在日志里只能看到 `C 太慢了`，**查不到是哪一行抛的**。而且 `catch` 里只要写 `e.message` 或者 `instanceof` 判定，行为都和 Error 不一样。

**回扣**：课 11 知识点 1（`throw` 什么才有用）

---

### ④ 用 `sleep` 猜时间

| | 反例 | 正确做法 |
|---|---|---|
| 做法 | `await sleep(200); // 猜应该都跑完了` | `await Promise.allSettled(...)` |

**为什么能跑通**：任务都在 200ms 内跑完了。

**为什么糟**：这是把**并发正确性**建立在**时序猜测**上。任务一变慢就漏数据；任务一变快就白等。更隐蔽的是：它在负载高时会间歇性失败 —— 本地测十次都对，上线后偶尔少数据，**完全无法复现**。

**回扣**：课 8（`allSettled` vs `all`）、课 7（别依赖时序）

---

### ⑤ 无界缓存 + 用普通对象当 Map

| | 反例 | 正确做法 |
|---|---|---|
| 做法 | `const cache = {}; cache[key] = value;` 永不清理 | `Map` + 上限 + LRU 淘汰（键是对象时用 `WeakMap`） |

**实测**：`cache['constructor'] 的类型: function` —— 普通对象的键会命中原型链上的属性。

**为什么糟**（两条独立的毛病）：

1. **只增不减 = 内存泄漏**。这就是课 12 泄漏 ④ 的标准形态：一个永不清理的容器。它不会报错，只会让你的进程在跑了一天之后被 OOM killer 干掉。
2. **普通对象当 Map 用**：键只能是字符串/数字；`cache['constructor']`、`cache['toString']` 这类键会撞上 `Object.prototype`；也没有 `size`。

**回扣**：课 9（Map vs Object）、课 12 泄漏 ④、[设计决策.md 决策点 3](设计决策.md)

---

### ⑥ 定时器不清理

| | 反例 | 正确做法 |
|---|---|---|
| 做法 | `setInterval(...)` 起完就不管 | `clearInterval` / `clearTimeout`，并在 `finally` 里做 |

**为什么糟**（课 12 泄漏 ②）：定时器只要还挂着，**它的回调就活着；回调活着，回调闭包引用的所有东西就都活着**。上面那个 `setInterval` 的回调虽然什么都不做，但它让事件循环永远有事可做 —— **进程退不出去**。

反例脚本里我被迫在演示完立刻 `clearInterval`，否则这个脚本会一直挂着不退出。

**回扣**：课 12 泄漏 ②、本课 `src/timeout.js` 的 `finally { clearTimeout }` 与 `removeEventListener`

---

### ⑦ 把方法提取出来传进回调

| | 反例 | 正确做法 |
|---|---|---|
| 做法 | `const inc = counter.inc; inc();` | `counter.inc.bind(counter)`，或写成箭头函数属性 |

**实测**：`裸调用 counter.inc → TypeError: Cannot read properties of undefined (reading 'n')`，`counter.n = 0`（本该是 1）。

**为什么糟**：`this` **看调用点，不看出生地**（课 5 知识点 1）。`counter.inc()` 这个"点"是 `this` 的唯一来源；一旦写成 `const inc = counter.inc`，这个"点"就没了，`this` 变成 `undefined`（严格模式）或 `globalThis`（非严格）。

**为什么这条最坑**：它在**严格和非严格模式下的表现不一样**，在浏览器和 Node 里也可能不一样 —— 你测的时候没炸，换个环境就炸。

**回扣**：课 5 知识点 1（隐式丢失）、本课 `demo.js` 场景 7（`queue.run` 提取后报 `Cannot read properties of undefined (reading '#defaults')`）

## 一图对照总结

| # | 反例做法 | 表象 | 真实后果 | 回扣 |
|---|---|---|---|---|
| ① | 无并发上限 | 小规模正常 | 规模一大就打崩下游 | 课 7/8 |
| ② | try 包 forEach | 一句"没报错" | **错误被静默吞掉，数据悄悄少一条** | 课 11 |
| ③ | 抛字符串 | 能抛能接 | **没有 stack，定位不到行** | 课 11 |
| ④ | sleep 猜时间 | 本地十次都对 | 高负载时**间歇性丢数据**，无法复现 | 课 7/8 |
| ⑤ | 无界缓存 | 短期无感 | 跑一天后被 OOM 干掉 | 课 9/12 |
| ⑥ | 定时器不清理 | 功能正常 | 进程退不出去，闭包一直占着 | 课 12 |
| ⑦ | 方法提取传回调 | 有时能跑 | 换环境就 `TypeError` | 课 5 |

> 💡 **这七条的共性**：**没有一条会在小规模测试中暴露**。
> 它们全都是"规模上来了 / 时间跑久了 / 换个环境了"才发作 —— 这也正是为什么课 12 要教你看**趋势**和**引用图**，而不是看某个瞬间的数字。
