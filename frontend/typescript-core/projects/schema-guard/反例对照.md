# 反例对照：能跑，但很糟

> 对应 `实现/examples/bad-schema-guard.ts`（运行 `npm run bad`）。
>
> ⚠️ 那个脚本会以 **exit 0 正常结束**——如果你只看「能不能跑」，下面这 7 条问题**一条都发现不了**。它们只在真实使用里才咬人。
> 这就是课 12 的题眼：**CI 全绿 ≠ 没有 bug**。类型检查、单元测试、代码审查都拦不住「看起来能跑」的坏设计。

每条反例：**坏写法 → 为什么坏 → 正确写法（本项目对应位置）→ 它对应哪一课**。

---

## BAD 1：用 `as` 断言代替校验

**坏写法**：`const user = raw as BadUser`，然后直接 `user.age.toFixed(2)`。

**为什么坏**：`as` 是「我向编译器保证」，编译器信了你，然后**什么都不做**。`{"age":"18"}` 里的 `age` 是字符串，`toFixed` 在运行时才炸。这是课 6 信任边界的反面教材：`as` 把 `unknown` 的「不确定」伪装成了「确定」，其实什么都没验。

**正确写法**：`parse(userSchema, raw)`，拿到 `ParseResult`，判 `ok` 再取 `value`。运行时真的逐字段验过了。

**对应课**：课 6（信任边界）｜ 落点：`src/parse.ts` 的 `parse()`。

---

## BAD 2：用 `any` 让所有校验「通过」

**坏写法**：`function badParseAnything(_s, v): any { return v as any }`。

**为什么坏**：`any` 是「关掉类型系统」。返回值是 `any`，后面不管写什么都不会报错，错误一路带到线上。这是课 6 的「any 传染性」——一旦 `any` 进入，整条链路上的类型检查全部失效，而且是**静默**的。

**正确写法**：入口收 `unknown`，校验通过后收窄成 `Infer<S>`。`unknown` 逼你**先验再用**，`any` 让你**不验就用**。

**对应课**：课 6（any vs unknown）｜ 落点：`src/parse.ts` 的参数 `value: unknown`。

---

## BAD 3：schema 和 interface 各写一份，慢慢不同步

**坏写法**：schema 里加了 `vip` 字段，interface 忘了改，两份定义漂移。

**为什么坏**：**没有任何一行代码会报错**。schema 有 3 个字段、interface 只有 2 个，编译器不会提醒你。运行时拿到的 `vip` 在类型上「不存在」，用的时候要么再 `as`，要么干脆漏掉。这是「重复的单一事实源」——重复越多，漂移越狠，而且全程静默。

**正确写法**：类型从 schema **推导**（`Infer<S>`），schema 是唯一事实源，加字段类型自动跟着走。

**对应课**：课 9（类型推导）｜ 落点：`src/infer.ts`，决策点 2 的核心论据。

---

## BAD 4：只报第一条错误

**坏写法**：校验函数 `return` 第一条错误就停。

**为什么坏**：4 个字段全错，只报出 1 个。调用方要「改一个、跑一次、再改一个」反复 5 轮才知道全貌。这是可观测性缺陷（课 12）：错误信息不完整，等于把「调试成本」转嫁给调用方。

**正确写法**：**不短路**，`check()` 递归收集**所有**错误再一次性返回。`run.ts` 里有断言「5 个字段全错时 `errors.length >= 5`」。

**对应课**：课 12（可观测性）｜ 落点：`src/check.ts` 的「不短路」设计。

---

## BAD 5：只查 top-level 的 typeof，嵌套结构完全没看

**坏写法**：`typeof value === "object"` 就返回通过。

**为什么坏**：`{ profile: { name: 123 } }` 通过校验，但里面的 `name` 是 number 它一点都不知道。浅校验给的是**虚假的安全感**——外层看着对，内层全是坑。

**正确写法**：递归校验，`array` 逐项、`object` 逐字段，路径一路拼接下去（`profile.level` 这种完整路径）。

**对应课**：课 5（收窄）+ 递归｜ 落点：`src/check.ts` 的 `check()` 递归 + `withPath`。

---

## BAD 6：switch 没有穷尽性兜底，新增 kind 静默漏掉

**坏写法**：`default: return "unknown"` 把新加的 `date` kind 吞了，而且不报错。

**为什么坏**：将来给 schema 加一种 kind，所有 switch 的 `default` 分支都**静默**返回兜底值，没人会发现「这里忘了处理」。这是「未来会咬人的 bug」——现在跑得通，加一个枚举值就漏。

**正确写法**：`default` 分支写 `const _exhaustive: never = schema`，新增 kind 时这一行**编译报错**，逼你把所有分支都补上。

**对应课**：课 5（穷尽性检查）｜ 落点：`src/check.ts` 和 `src/schema.ts` 的 `default` 分支。

---

## BAD 7：为了「通用」把 API 写成没人看得懂的形状

**坏写法**：`OverGeneric<T, U extends keyof T, V extends T[U]>`——三个参数，报错信息里全是 T/U/V。

**为什么坏**：能编译，但没人会用。这是课 13 的典型红灯：**「需要注释才能解释这个类型在干什么」，就是过度设计**。类型体操的收益是「消除重复 + 精确表达」，一旦它自己成了理解障碍，就违背了初衷。

**正确写法**：本项目整个 `Infer<S>` 只有一个类型参数 `S`，一层分发 + 一层映射，一眼能看懂在干嘛。**体操的复杂度必须和它解决的问题成正比**。

**对应课**：课 13（类型体操值不值）｜ 落点：`src/infer.ts` 的简洁性，决策点 2 的七步第 3 步。

## 一眼对照表

| # | 坏习惯 | 一个词概括 | 正确姿势 | 课 |
|---|--------|-----------|---------|-----|
| BAD 1 | `as` 当校验 | 假装验证 | `parse()` 返回 Result | 6 |
| BAD 2 | `any` 一撒 | 关掉类型 | `unknown` + 收窄 | 6 |
| BAD 3 | 两份定义 | 静默漂移 | `Infer<S>` 单一事实源 | 9 |
| BAD 4 | 只报第一条 | 挤牙膏 | 不短路，一次报全 | 12 |
| BAD 5 | 只看一层 | 虚假安全 | 递归 + 完整路径 | 5 |
| BAD 6 | 无兜底 switch | 未来漏 | `never` 穷尽性检查 | 5 |
| BAD 7 | 过度泛型 | 自嗨 | 复杂度与收益成正比 | 13 |

> 这 7 条的共同点：**没有一条会被「编译通过」或「测试通过」拦住。** 它们是「设计」层面的问题，只能靠「对照好实现 + 想清楚为什么」来避免。这也是本门课「决策参考」目标想教的东西。
