# 验收清单：怎么确认自己真的做成了

> 三个层级，层层递进：**L1 跑得通 → L2 看得懂 → L3 改得动**。
> 前两级看「做没做完」，第三级看「懂没懂」——只会跑通不算会，**改得动才算**。

---

## L1 · 跑得通（机械验收）

```bash
cd 实现
npm install
npm run ci
```

| 检查项 | 预期 | 实测 |
|---|---|---|
| `typecheck` | exit 0 | |
| `typecheck:lib`（纯净度闸门） | exit 0 | |
| `test` | `17 通过 / 0 失败` | |
| `npm run demo` | 7 个场景输出，无异常 | |

> `npm run bad` 的 exit 0 是**故意**的——它要证明「只看能不能跑，一条问题都发现不了」。验收时请停下来想 30 秒：这是不是就是课 12 说的「CI 全绿、线上全红」？

## L2 · 看得懂（理解验收）

不看参考实现，能回答下面每个问题，才算「看懂了」：

1. **为什么 `parse()` 返回 `ParseResult` 而不是直接抛异常？** 说出「预期内的事不该用异常表达」这层意思。
2. **`src/parse.ts` 里那唯一一处 `as Infer<S>` 为什么是「可以接受」的断言？** 因为它集中在边界、且被 `test/` 的断言测试覆盖——对照 BAD 1。
3. **为什么类型要从 schema 推导，而不是手写 interface？** 说出「单一事实源」「两份定义会静默漂移」——对照 BAD 3。
4. **`tsconfig.src.json` 为什么单独存在？** 说出「库的环境无关性要由编译器强制，而不是口头承诺」——决策点 3。
5. **`default` 分支里的 `const _exhaustive: never = schema` 是干嘛的？** 说出「新增 kind 时逼编译器报错」——对照 BAD 6。

> 这 5 问分别对应 5 个知识点：判别式联合、信任边界、类型推导、类型分层、穷尽性检查。答不上哪一题，就回那一课补。

## L3 · 改得动（能力验收）

> 每个挑战都对应一个**真实的工程决策**。动手改之前，先想「我要动哪几个文件、哪几处会编译报错」，改完再对照。

### 挑战 1：加 union 字段（`string | number`）

给 `Schema` 加一种能表示「字符串或数字」的字段。

- **提示**：要改 `schema.ts`（新 kind + builder）、`infer.ts`（新分支）、`check.ts`（新校验分支）、`describe.ts` 的 describe。
- **关键体会**：`switch` 的 `never` 穷尽性检查会**逐个文件**告诉你「这里还没改」——这就是穷尽性检查的价值，一次改全，不会漏。
- **决策点**：union 字段的类型是 `string | number`，收窄时你会不会掉进「联合类型的校验顺序」陷阱？

### 挑战 2：加 optional 字段

让 `object` 支持「可选字段」（比如 `profile` 可缺省）。

- **提示**：`ObjectSchema<F>` 的字段怎么标记可选？`Infer` 的映射类型要处理 `?`。
- **坑**：项目开了 `exactOptionalPropertyTypes`（课 10），builder 里 `minLength === undefined ? {...} : {...}` 的写法会因为这个开关出问题——体会「严格开关不是免费的」。

### 挑战 3：加自定义校验（如 email 格式）

让 `string()` 能传一个自定义 predicate（比如校验邮箱格式）。

- **决策点**：自定义校验逻辑是「运行时」的事，**类型推导帮不上忙**——`Infer` 推不出「这是合法 email」。想想怎么在 `check()` 里扩展，同时**不动** `Infer`。
- **关键体会**：这是「类型管不住外部数据」的又一实例——类型只能管「是不是 string」，管不了「是不是合法邮箱」。

### 挑战 4：加 record/map 字段（`Record<string, T>`）

让 schema 支持「字段名不固定的对象」（比如 `Record<string, number>`）。

- **提示**：`Infer` 的 object 分支目前用「映射类型遍历已知字段」，对「任意键」要换成索引签名。
- **决策点**：`Object.entries(schema.fields)` 这种遍历对「任意键」schema 还成立吗？校验逻辑要改哪几行？

### 挑战 5：给错误加「多语言 / 自定义 message」

现在 `ParseError.message` 是英文硬编码（`expected string, got number`），改成可注入的。

- **决策点**：错误消息是「库的职责」还是「调用方的职责」？库里内置一套默认，调用方能覆盖，这个边界怎么划？
- **提示**：想想 `ParseError` 要不要加个 `code` 字段，让调用方能**程序化**判断错误类型（而不是 match 字符串）。

### 挑战 6：要不要加 tsconfig `paths` 别名

本项目内部 `import` 用的是**相对路径**（`../src/index.js`）。要不要换成 `paths` 别名（课 11）？

- **决策点**：先想清楚 `paths` 是「编译期」的事，**运行时还要靠 `imports` 字段或打包器**（课 11 实测过：只配 `paths` 不配运行时，`node dist` 会 ERR_MODULE_NOT_FOUND）。
- **结论倾向**：一个 6 模块的小库，相对路径反而最省事——**「能用」不等于「该用」**，这是课 11 决策参考的直接应用。
