> 每个决策点走**五段式**：背景 → 选项 → 权衡 → 决策 → 后果与回看。

## 决策点 1：校验失败，返回值还是抛异常？

### 背景

`parse()` 拿到不合法数据时，有两种根本不同的表达方式。这个选择决定整个 API 的**气质**，也决定调用方写代码时「顺不顺手、会不会漏」。

### 选项

| | 选项 A：返回值 | 选项 B：抛异常 |
|---|---|---|
| 表达 | `parse(s, v): ParseResult<Infer<S>>`（判别式联合） | `parse(s, v): Infer<S>`，失败 `throw SchemaGuardError` |
| 调用方拿到 | `{ ok: true, value }` 或 `{ ok: false, errors }` | 要么值、要么异常飞走 |

### 权衡

**选项 A（返回值）**
- ✅ 编译器**逼**调用方处理失败：不判 `r.ok` 就拿不到 `value`（判别式联合 + 穷尽性检查，阶段 2）
- ✅ 「失败」被建模成**正常业务流的一部分**，而不是意外
- ❌ 每次都要 `if (r.ok)`，样板多一点，调用方可能嫌烦

**选项 B（抛异常）**
- ✅ 调用方直接拿值，代码干净
- ✅ 适合「数据不合法就该崩」的场景（启动参数、内部配置）
- ❌ 没人记得 `catch`，异常一路抛到顶层才炸
- ❌ **TS 不会提醒你「这个函数可能抛」**——没有 checked exception，类型系统在这件事上完全失明

### 决策

**默认 `parse()` 走返回值（选项 A），同时提供 `parseOrThrow()` 和 `assert()` 作为便捷入口（选项 B）。**

核心论据一句话：**校验的失败不是「意外」，是「预期内的输入」；预期内的事不该用异常表达，异常应该留给「程序员的 bug」。**

而课 6 的信任边界决定了：本库面对的是**外部数据**（`JSON.parse`、网络响应、用户输入），它们「不合法」是常态而非意外。所以默认姿势必须是「逼你处理失败」的那一个。

### 后果与回看

- 四个入口的分工（**这是「两个都提供」而不是「二选一」**）：
  - `parse()` —— 返回值，默认姿势，适合外部数据
  - `is()` —— 只要布尔 + 类型收窄（类型守卫，阶段 2）
  - `assert()` —— 断言函数，失败就抛（阶段 2）
  - `parseOrThrow()` —— 拿值，失败就抛，适合「不合法就该崩」
- 代价：`parse()` 调用方必须写 `if (r.ok)`。这个「摩擦」**是刻意的优点**，不是缺陷。
- ⏳ 什么情况要重开：如果将来所有调用方都只用 `parseOrThrow`，说明默认值设反了，要回头把它改成默认。

## 决策点 2：`Infer<S>` 这套类型体操，值不值得写？

### 背景

从 schema 自动推导类型，是本项目最「炫」的部分，也是**课 13 的题眼**——类型体操到底值不值。必须正面回答，不能「因为我会写，所以写」。

### 选项

| | 选项 A：写 `Infer<S>` | 选项 B：不写，调用方手写 interface |
|---|---|---|
| 类型哪来 | 从 schema 自动推导（单一事实源） | 调用方手写，`parseAs<T>(s, v): ParseResult<T>` 强转 |
| 代码位置 | `src/infer.ts` | 没有 infer.ts，`parse.ts` 变成 `parseAs` |

### 权衡（用课 13 的「七步放弃标准」逐条过）

> 课 13 的核心产出是「七步放弃标准」——**按顺序问自己，任何一个「否」就停手**。这里逐条过 `Infer<S>`，看它卡在哪一步。

| 步 | 课 13 七步放弃标准 | 本项目 `Infer<S>` 实情 | 结论 |
|---|---|---|---|
| ① | 手写类型能不能解决？能 → 手写 | 能（`cost.cjs` 的 manual 对照组就是手写 interface），但手写 = schema + interface **两份定义**，会静默漂移（BAD 3） | 手写能解决，但引入「漂移」风险，不满足「到此为止」的前提 |
| ② | 能不能用「代码生成」解决？能 → 生成 | 不能。schema 是**代码里手写定义的值**（`object({...})`），不是外部事实（OpenAPI / DB 表），没有可生成的输入 | 生成不适用 |
| ③ | 是不是「调用点极多 + 手写会漏」？不是 → 别写 | 是。每个 schema 都要一份对应类型，几十上百处，手写必漏（BAD 3 的 `vip` 字段就是漏） | ✅ 过 |
| ④ | 能写成尾递归吗？不能 → 重新设计 | `Infer<Inner>[]` 严格说不是「分支直接递归」的纯尾递归，但 `depth.cjs` 实测实例化 >1000 层仍通过——**卡住的是结构比较（约 100 层报 TS2321），不是实例化** | ✅ 实测不构成瓶颈 |
| ⑤ | 算不出来时有兜底吗？没有 → 补上再写 | 兜底是 `: never`，会静默（课 13 实测）；靠 ⑥ 的类型测试兜住这个静默风险 | ✅ 靠 ⑥ 兜住 |
| ⑥ | 配了类型测试吗？没有 → 补上再写 | ✅ `test/types.test.ts`：`Equals` + `Expect` + 负向对照（`@ts-expect-error` 那行证明判定真会抓错） | ✅ 过 |
| ⑦ | 团队里至少两个人看得懂吗？不是 → 别写 | 一层条件类型分发 + 一层映射类型，一眼能懂；**前提是保持简单**（不加 union / optional） | ✅ 过 |

七步过完，**没有一步是「否」**——① 的「手写能解决」被 BAD 3 的漂移否决，② 生成不适用，③~⑦ 全过。所以按课 13 标准，该写。

**补充：编译期代价实测（`test/cost.cjs`，2026-09-04）**——七步里没有单独的「性能」这一步，但「性能」是最常见的反对理由，单独测：

```
生成 150 个文件 x 2 个变体（gym / manual），运行时校验逻辑完全相同

gym    （Infer<S> 推导）  = 173 ms  (min of 3)
manual （手写 interface）= 200 ms  (min of 3)
差值 = -26 ms，比值 = 0.87x
```

两个项目的运行时校验**完全复用同一份 `src/check.ts`**，唯一差别是编译期怎么拿类型。结果：**gym 反而略快，但 -26ms 落在噪声范围内。**

> **诚实的说法是「两者没有可测量的编译期差异」，而不是「体操更快」。**
> 这个结论和课 13 的「复杂体操 2.9x 更慢」**不矛盾**，而是互补：
> **「类型体操有代价」要加一个限定——复杂体操才有可测量的代价；简单体操的代价可能小到测不出来。**

### 决策

**写（选项 A）。**

核心论据**不是**「体操很酷」，而是：**「schema 是唯一事实源」**。一旦 schema 和类型分开维护，就掉回 BAD 3 的坑——那个坑是**静默的**（两份定义慢慢漂移，没有一行代码报错），比「体操复杂」可怕得多。而本项目的体操足够简单，简单到编译期代价测不出来（0.87x），所以「性能」这个常见的反对理由**在本项目里不成立**。

### 后果与回看

- ⚠️ **边界必须写清**：这个结论只对「简单体操」成立。课 13 实测「复杂体操」扣除基线后 46ms vs 135ms（约 2.9x）。判断标准就是课 13 的七步放弃标准——将来加 union / optional 时，④（尾递归 / 深度）和 ⑦（看得懂）最可能先亮红灯，那时候重新过一遍七步。
- 实测的意外：`test/depth.cjs` 发现限制**不在「能不能推出来」**（实例化 >1000 层仍通过），**而在「能不能比」**（结构比较约 100 层后报 **TS2321**，不是课 13 的 TS2589）。这个边界已写进 `infer.ts` 注释，并诚实标注「我一开始凭课 13 印象写错成 TS2589，实测纠正了」。
- ⏳ 什么情况要重开：将来给 schema 加 union / optional 字段时，`Infer` 的映射类型要处理「可选」「联合」，复杂度上升，必须**重新过一遍七步**。

## 决策点 3：库要不要依赖环境类型（Node）？

### 背景

写 `src/` 时，能不能用 `console`、`process`、`Buffer`？这看起来是「配置细节」，实际决定**这个库能不能在浏览器 / Deno / Bun / 边缘函数里跑**。

### 选项

| | 选项 A：默认 `types: ["node"]` | 选项 B：src 用 `types: []`（环境无关） |
|---|---|---|
| 写代码 | 随便用 Node API，顺手 | src/ 里碰 Node API 就报错，受限 |
| 配置 | 一份 `tsconfig.json` 走天下 | 两份：开发用 `tsconfig.json`，纯净度用 `tsconfig.src.json` |
| 库的适用范围 | 绑死 Node | 浏览器 / Deno / Bun / 边缘都能用 |

### 权衡

**选项 A**
- ✅ 一份配置，省事；src/ 里能 `console.log` 调试
- ❌ 库**不知不觉**用上 Node API 而不自知（哪天写了 `process` / `Buffer` 也没人提醒）
- ❌ 一旦有浏览器用户，全部返工；而「校验器」这种库天然该是环境无关的

**选项 B**
- ✅ **编译期就保证 src/ 不碰任何 ambient 类型**：`types: []` 下用 `console` 直接报 TS2591 / TS2584（课 11 实测），不是「我承诺」，是「编译器强制」
- ✅ 库的适用范围最大
- ❌ 要维护两份 tsconfig + `ci` 里多一步 `typecheck:lib`；src/ 里没法直接 `console.log` 调试

### 决策

**选 B。**

核心论据：**「库作者多付一点配置成本，换取使用方的无限环境」是一笔不对称的好交易。**

更关键的是，选 B 不是「我口头说自己环境无关」，而是用 `typecheck:lib` 这一道**编译期闸门**强制兑现——`types: []` 下只要 src/ 碰了 Node API，CI 就红。这符合本课一贯的立场：**把「原则」变成「能跑、会红、拦得住」的检查**。

### 后果与回看

- 代价：`npm run ci` 里多一步 `typecheck:lib`（`tsc -p tsconfig.src.json`）；src/ 里的调试全部靠 `test/` 和 `examples/`。
- 意外收获：这道「纯净度闸门」是课 15「**边界类型不该渗进领域层**」的编译器版本——一个架构原则，被翻译成了一条可执行的 CI 门禁。
- ⏳ 什么情况要重开：如果这个库**就是**给 Node 专用（要读文件、要 stream），那选项 A 反而更诚实。「先问使用场景再选」不是口号，是这句话本身。
