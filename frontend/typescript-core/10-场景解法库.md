## 场景 1｜这个项目到底该不该上 TS？

**场景**：你接手一个项目（可能是新的，也可能是跑了多年的老 JS），要拍板"该不该上 TypeScript、上多严"。周围有人说"不上 TS 就是裸奔"，也有人说"上了 TS 全是类型体操、开发变慢"。你要给团队一个**有依据的结论**，而不是跟风。

### 🔒 先自己想

第一反应是"当然上啊"？先问自己：**这个项目的规模、生命周期、团队、数据来源，四条里哪几条在替"上 TS"投票，哪几条在反对？** 如果答案全看心情，说明你还没想清。

<details>
<summary>💡 提示（思考方向）</summary>

- "上 TS"的成本主要在**前期标注 + 构建 + 学习曲线**，收益在**后期多人协作 + 重构 + 公共 API**。你的项目偏前期还是偏后期？
- 有些项目类型收益天然低：一次性脚本、几周就扔的原型、单人几百行。它们"该不该上"？
- 数据**全来自外部且形状不稳**的项目，TS 的收益有什么特殊之处？
- "上 TS"和"上多严"是两个问题——有没有可能"上，但上得轻"？
- 团队没人愿意维护类型时，硬上会怎样？

</details>

<details>
<summary>📖 展开解法</summary>

### 判断条件一览（复用课 15 清单，口径一致）

**先看「算不算得上」**：

| 信号 | 倾向 |
|------|------|
| 多人长期维护（≥2 人，≥1 年） | ✅ 上 |
| 对外提供公共 API / SDK | ✅ 上（类型即文档） |
| 项目足够大（几千行以上，跨模块） | ✅ 上 |
| 一次性脚本 / 原型 / 演示 / 竞赛 | ❌ 不上 |
| 生命周期 < 几周 | ❌ 不上 |
| 单人维护且几百行以内 | ➖ 可不上 |
| 团队没人愿意维护类型 | ⚠️ 先小范围试点 |
| 构建/工具链不支持 | ➖ 用 JSDoc 路线 |
| 数据来源全外部、形状不稳定 | ✅ 上，但**必须配运行时校验** |

**再看「上多严」**：新项目 `strict: true` 全开；老项目六步渐进；对外库公开 API 严格；脚本工具 `strict: true` 即可不必上高阶开关。

### 解法一览（三个大方向，含代价与边界）

| 解法 | 怎么做 | 代价 | 适用边界 |
|---|---|---|---|
| **A. 完整上 TS** | `strict` 全开 + 全量标注 + 类型进 CI | 前期标注成本、构建成本、学习曲线 | 多人长期 / 公共 API / 大项目 |
| **B. JSDoc + `checkJs`** | 不改构建，用 JSDoc 注解 + `checkJs` 拿类型检查 | 表达力弱于 TS、生态支持少、复杂泛型抓不住 | 工具链不支持 TS、或只想先试水 |
| **C. 不上 TS，靠运行时校验 + 测试** | 保持 JS，用 schema 校验 + 测试 + 评审兜逻辑 | 缺编译期契约，重构靠人肉 | 一次性脚本 / 短命原型 / 单人小项目 |

### 推荐路径（递进）

1. **先用上面的信号表给项目"定个性"**——是长期资产还是短命脚本
2. 长期资产 → **A**（完整上）；短命脚本 → **C**，别纠结
3. 工具链卡住 / 只想试水 → **B**（JSDoc 路线），收益验证后再决定是否升级到 A
4. 数据全外部 → 无论选 A/B/C，**运行时校验都要上**（这是最稳的"类型 + 校验 + 测试"组合）

### 知识点挂钩

- [课 15 决策收束：什么时候不该上 TS](stages/5-深入与架构/lessons/lesson-15-大型项目类型架构与选型收束.md) —— 四维度权衡 + 三条替代方案
- [课 6 信任边界：类型从哪来](stages/2-收窄与控制流/lessons/lesson-06-any·unknown·never与信任边界.md) —— "数据全外部"为什么尤其需要运行时校验
- [课 12 工具链集成与团队协作](stages/4-工程化与类型声明/lessons/lesson-12-工具链集成与团队协作.md) —— JSDoc 路线的收益边界（课 12/15 实测）

### 什么情况下此方案不适用

- **"团队没人愿意维护类型"时硬上完整 TS** → 类型会烂尾（一堆 `any`），反而更糟。此时该 B 试水或 C 兜底
- **"数据形状完全不可预测"时只上 TS 不做运行时校验** → 编译期类型是幻觉，运行时照样崩（见故障模式 1）

### 做错会踩的坑

→ 关联 [`08-实战经验.md`](08-实战经验.md) 的故障模式 1、2（上了 TS 却用 `as`/`any` 糊，等于花钱买了个假安全感）

</details>

## 场景 2｜外部 JSON 形状天天变，怎么守住运行时

**场景**：你的服务依赖一个第三方接口，返回的 JSON 结构**经常变**（字段改名、类型从 `string` 变 `number`、有时整段缺失）。你已经上了 TS，写了 `interface User`，但运行时还是偶尔崩——因为类型在编译期"相信"了那个接口，运行时的真实数据没人管。

### 🔒 先自己想

"我写了 `interface` 就够了"是最常见的错觉。先问自己：**编译期的 `interface User` 和运行时真正进来的那个 JSON，中间隔了什么？谁在保证它们一致？**

<details>
<summary>💡 提示（思考方向）</summary>

- `JSON.parse` 的返回类型是什么？为什么不能直接 `as User`？
- "校验"和"断言"的区别是什么？哪个真的能拦住运行时错误？
- 校验逻辑能不能**自动生成**，而不是每个字段手写一遍？
- 校验失败的时点在哪——是"用之前校验一次"，还是"入口处校验"？
- 类型定义和校验逻辑会不会**漂移**（你改了 `interface`，忘了改校验）？

</details>

<details>
<summary>📖 展开解法</summary>

### 解法一览

| 解法 | 怎么做 | 代价 | 适用边界 |
|---|---|---|---|
| **A. `as` 断言（最差）** | `JSON.parse(...) as User` | 零成本，但**零保护**——编译期自欺欺人 | 几乎不适用（内部可控数据除外） |
| **B. 手写类型守卫** | `function isUser(x: unknown): x is User` 逐字段校验 | 字段多时冗长；改类型要同步改守卫，易漂移 | 字段少（几个）、形状稳定 |
| **C. 运行时 schema 库**（如 zod / io-ts） | 写一份 schema，**同时**得到类型 + 校验 | 引入依赖 + 学习成本；schema 与 TS 类型是两份"定义"心智 | **通用默认解**；数据全外部、形状多变时 |
| **D. 代码生成**（从 schema / 接口定义生成类型 + 校验） | 单一事实源（schema 或 OpenAPI），生成 TS 类型 + 校验器 | 要维护生成链路 | 有 OpenAPI / 契约源时最干净 |

### 推荐路径

1. **外部数据入口，永远先 `unknown`**——这一步免费，先做
2. 字段少 → **B**（手写守卫）；字段多 / 形状多变 → **C**（schema 库）
3. 有 OpenAPI / 契约源 → **D**（生成，杜绝"类型与校验漂移"）
4. **A 永远不要出现在信任边界**——它只适合"类型系统比运行时更精确"的内部场景

### 知识点挂钩

- [课 6 信任边界：类型从哪来](stages/2-收窄与控制流/lessons/lesson-06-any·unknown·never与信任边界.md) —— 外部数据进来是 `unknown`，边界处收敛
- [课 3 类型断言与 satisfies](stages/1-类型思维启蒙/lessons/lesson-03-对象类型与结构化类型.md) —— `as` 是承诺不是检查
- [实战项目《schema-guard》](projects/schema-guard/README.md) —— 运行时校验 + 类型守卫的完整工程实践

### 什么情况下此方案不适用

- **数据来自你自己系统的内部模块**（不是外部边界）→ 类型已经可靠，运行时校验是多余开销
- **校验逻辑会拖慢热路径** → 大报文高频校验的成本要评估，必要时只校验关键字段

### 做错会踩的坑

→ 关联 [`08-实战经验.md`](08-实战经验.md) 的故障模式 1（`as` 洗白外部数据 → 运行时 `TypeError`）

</details>

## 场景 3｜几万行老 JS 项目要迁 TS

**场景**：一个跑了几年的 JS 项目，几万行、几十个模块，全是没有类型的。团队决定迁 TS，但**不能停下来重写**——业务还在跑，需求还在加。你要设计一条**渐进迁移**路径。

### 🔒 先自己想

"一次性全迁"是不是听起来最彻底？先问自己：**几万行代码一次性加类型，编译一次要多久？中间业务要上线怎么办？** 还有，从哪个文件开始迁，有关系吗？

<details>
<summary>💡 提示（思考方向）</summary>

- 迁移时 `.js` 和 `.ts` 能共存吗？靠哪个配置项？
- 从"被依赖最少"的文件开始迁，还是"依赖别人最多"的？为什么顺序重要？
- `any` 在迁移中扮演什么角色——是敌人还是过渡工具？
- `strict` 是一上来全开，还是渐进开？先开哪个开关性价比最高？
- 迁移期间怎么防止"新的无类型代码"继续产生？

</details>

<details>
<summary>📖 展开解法</summary>

### 解法一览

| 解法 | 怎么做 | 代价 | 适用边界 |
|---|---|---|---|
| **A. `allowJs` 混编 + 从叶子迁** | 开 `allowJs` 让 `.js`/`.ts` 共存，从**被依赖最少的叶子模块**开始迁 | 混合期维护两套；迁移周期长 | **通用默认解**；大项目渐进迁 |
| **B. 一次性全迁** | 整个项目一次改成 `.ts` 并标注 | 前期工作量巨大；中途无法上线；容易烂尾 | 小项目（几百行） |
| **C. JSDoc 路线先铺** | 先给 `.js` 加 JSDoc 注解 + `checkJs`，拿到类型检查后再逐步转 `.ts` | 表达力弱；复杂泛型搞不定 | 想先不碰构建、先拿收益 |
| **D. 边界优先** | 先给"对外边界/公共 API"补类型，内部后补 | 边界类型会"倒逼"内部补 | 有清晰边界 / SDK 的项目 |

### 推荐路径（递进）

1. **开 `allowJs`**，让混编成为可能
2. **从叶子开始迁**（A）：类型信息只能自下而上流动，从叶子迁第 2 步就能报错，跳过叶子先迁入口则 0 错（课 15 实测）
3. 迁移期 `strict: false`，迁完一块收紧一块
4. **`any` 当中转站**，但每个都配 TODO、迁移完成后清零
5. 最后一步才开全量 `strict`

### 知识点挂钩

- [课 15 JS → TS 渐进迁移](stages/5-深入与架构/lessons/lesson-15-大型项目类型架构与选型收束.md) —— 迁移顺序的实测依据（1 错 vs 0 错）
- [课 10 严格性开关族与渐进收紧](stages/4-工程化与类型声明/lessons/lesson-10-tsconfig与编译配置.md) —— `strict` 六步渐进
- [课 6 any：逃生舱与传染性](stages/2-收窄与控制流/lessons/lesson-06-any·unknown·never与信任边界.md) —— `any` 作为中转站而非终点

### 什么情况下此方案不适用

- **小项目（几百行）** → 一次性全迁（B）更快，别为了"渐进"而拖
- **团队没人能持续跟进迁移** → 混编会永远停在"迁了一半"，先评估要不要迁

### 做错会踩的坑

→ 关联 [`08-实战经验.md`](08-实战经验.md) 的故障模式 2（迁移期的 `any` 不清理，类型检查形同虚设）

</details>

## 场景 4｜类型体操到底该不该写

**场景**：团队里有人想用类型体操实现一个"编译期校验"——比如"传错字段名就编译不过"的复杂条件类型。写完确实很炫，但编译变慢、别人看不懂。你要判断：**这个体操该不该写？**

### 🔒 先自己想

"类型越强越好"是本能反应。先问自己：**这个问题能不能用更简单的办法解决？** 类型体操的三张账单（编译变慢 / 静默失败 / 团队维护不了）你愿意付吗？

<details>
<summary>💡 提示（思考方向）</summary>

- 这个类型**必须由编译器算**，还是可以手写 / 用代码生成？
- "调用点极多 + 手写会漏"是写体操的**唯一**强理由——你的场景满足吗？
- 递归能不能尾递归？算不出来有没有兜底？配了类型断言测试吗？
- **至少两个人看得懂吗**？看不懂的体操是负债不是资产
- 编译变慢的代价，值不值这个"编译期约束"？

</details>

<details>
<summary>📖 展开解法</summary>

### 解法一览

| 解法 | 怎么做 | 代价 | 适用边界 |
|---|---|---|---|
| **A. 手写类型** | 直接把需要的类型写出来 | 会漏、维护要同步 | 形状固定、调用点不多 |
| **B. 代码生成** | 从外部事实（schema / 接口定义）生成类型 | 要维护生成链路 | 类型来自**外部事实**时几乎总是更优 |
| **C. 类型体操** | 递归/条件类型在编译期算 | 编译变慢（复杂体操约 2.9x）、可能静默退化、团队看不懂 | **仅当**调用点极多 + 手写会漏 + 能尾递归 + 有兜底 + 有测试 + 有人看得懂 |
| **D. 运行时校验替代** | 把"编译期约束"降级为运行时校验 | 错误发现从编译期挪到运行时 | 编译期约束收益有限、且体操代价过高时 |

### 推荐路径（先过七步放弃标准）

按顺序问自己，**任何一个「否」就停手**：

1. 手写类型能不能解决？能 → **A**
2. 能不能用代码生成解决？能 → **B**（来自外部事实时几乎总是生成更优）
3. 是不是"调用点极多 + 手写会漏"？不是 → 别写
4. 能写成尾递归吗？不能 → 重新设计（否则约 50 层就爆）
5. 算不出来时有兜底吗？没有 → 补上再写
6. 配了类型测试吗？没有 → 补上再写
7. 团队里至少两个人看得懂吗？不是 → 别写，或先教会一个人

> 前两步（手写 / 生成）就能拦下大多数冲动。**七步里任何一个「否」，体操就不该写。**

### 知识点挂钩

- [课 13 类型体操的代价与可读性底线](stages/5-深入与架构/lessons/lesson-13-类型体操进阶.md) —— 三大账单 + 七步放弃标准
- [课 9 条件类型与 infer](stages/3-泛型与类型编程/lessons/lesson-09-类型编程三件套与内置工具类型.md) —— 体操的技术底座

### 什么情况下此方案不适用

- **类型来自外部事实**（API 定义、数据库 schema）→ 生成（B）优于体操，体操是"重复造轮子"
- **简单体操**（一层 `Partial` / `Pick`）→ 随便写，代价测不出来（实战 0.87x）；**复杂递归体操**才需要过七步

### 做错会踩的坑

→ 关联 [`08-实战经验.md`](08-实战经验.md) 的故障模式 3（静默退化 `never`）、4（递归爆栈 TS2589）

</details>

## 场景 5｜升级 TS 7 后，工具链崩了

**场景**：你兴冲冲把项目升级到 TypeScript 7，结果 `typescript-eslint` 直接报错——装依赖时 `ERESOLVE`，强装后运行报"does not support TS 7.0"。ESLint、ts-node 这类工具用不了了。你要设计一条**TS 7 下的工具链兼容**方案。

### 🔒 先自己想

"先别升 TS 7，等工具适配"是最稳的，但也是最保守的。先问自己：**哪些工具真的依赖 TS 7 的 API？哪些只是"顺路"用一下 TS？** 有没有办法**让工具和你的代码用不同版本的 TS**？

<details>
<summary>💡 提示（思考方向）</summary>

- 判断一个工具"要不要 TS 7"，关键看什么？（提示：它要不要 `import "typescript"`）
- npm 能不能让**两个不同版本的同名包**共存？怎么操作？
- 有些工具其实**不依赖 TS 的 API**——它们转译就行，和 TS 版本无关。你的工具链里哪些是这种？
- "等官方适配"和"现在就迁移"的取舍，取决于什么？

</details>

<details>
<summary>📖 展开解法</summary>

### 解法一览

| 解法 | 怎么做 | 代价 | 适用边界 |
|---|---|---|---|
| **A. 等工具适配，暂用 TS 6** | 停留在 TS 6，等 typescript-eslint / ts-node 等适配 TS 7 | 享受不到 TS 7 的构建提速 | 对 TS 7 无刚需、工具链重 |
| **B. npm 别名并存**（官方推荐） | `"typescript" → @typescript/typescript6`（给工具）、`"@typescript/native" → typescript@7`（给你） | 配置绕一点；要理解两套 TS 并存 | **想现在就上 TS 7 且不能丢工具** |
| **C. 换掉依赖 TS API 的工具** | 用 tsx 替代 ts-node、用 esbuild/swc 做转译 | 要迁移工具链配置 | 工具本身可替换时 |

### 推荐路径

1. **先判断你工具链里谁真的需要 TS API**：要 `import "typescript"` 的（ts-node、typescript-eslint、Volar）→ TS 7 下不可用；不要的（esbuild、swc、tsx、Vite）→ 与 TS 版本无关
2. 刚需 TS 7 的提速 → **B**（别名并存），这是官方给的过渡方案
3. 工具可替换 → **C**（ts-node 换 tsx 等）
4. 工具链重、又不急 → **A**（暂用 TS 6，等适配）

### 知识点挂钩

- [课 12 ESLint 与 typescript-eslint](stages/4-工程化与类型声明/lessons/lesson-12-工具链集成与团队协作.md) —— typescript-eslint 的 peer 范围 + 别名并存实测
- [课 12 运行与构建工具分工](stages/4-工程化与类型声明/lessons/lesson-12-工具链集成与团队协作.md) —— "要不要 TS API"这条判据

### 什么情况下此方案不适用

- **项目用了 Vue / MDX / Astro / Svelte / Angular 模板**（依赖 TS API 的工作流）→ 这些在 TS 7 下暂只能走 TS 6，别硬上
- **团队不熟悉 npm 别名** → 别名并存的配置心智负担不小，先确认有人能维护

### 做错会踩的坑

→ 关联 [`08-实战经验.md`](08-实战经验.md) 的故障模式 5（工具链切换时若漏掉 `tsc --noEmit`，会变成"只转译不检查"）

</details>

## 场景 6｜给一个没有类型的第三方库补类型

**场景**：项目里用了一个没有官方类型的 JS 库（没发 `.d.ts`，`@types` 里也没有）。现在到处是 `any`，或者干脆报"找不到类型声明"。你要给它补类型。

### 🔒 先自己想

"那就 `declare module 'xxx'` 全标 `any` 呗"是最快但最糟的答案。先问自己：**这个库的哪些 API 是你真正在用的？** 全量补 vs 只补你用到的，成本差多少？

<details>
<summary>💡 提示（思考方向）</summary>

- 补类型的粒度可以"只补你用到的"，还是必须全量？影响后续维护吗？
- 全局声明、模块声明、声明合并，三种写法分别对应什么场景？
- `any` 声明和"精确声明"的差别，会在哪一天反噬？
- 如果你会长期用这个库，值不值得**往上游提 PR**（补进 `@types`）？

</details>

<details>
<summary>📖 展开解法</summary>

### 解法一览

| 解法 | 怎么做 | 代价 | 适用边界 |
|---|---|---|---|
| **A. `declare module` 全标 `any`** | `declare module 'xxx'` 里一切 `any` | 最快，但类型检查对这一块失效（回到故障模式 2） | 临时跑通 / 短期用 |
| **B. 手写 `.d.ts` 只补用到的 API** | 项目里写 `.d.ts`，只声明你实际调用的方法签名 | 只覆盖用到的部分；库升级可能要同步 | **通用默认解**；用到的 API 有限 |
| **C. 完整手写 `.d.ts` + 提 PR** | 完整补类型，并往上游（库或 `@types`）提 PR | 工作量最大；要维护 | 长期重度使用、且社区需要 |
| **D. 换一个有类型的库** | 换成有官方类型或 `@types` 的替代品 | 要迁移调用代码 | 库本身可替换时 |

### 推荐路径

1. **先查有没有现成类型**（库自带 / `@types`）——有就直接用，别手写
2. 没有 → **B**（手写 `.d.ts`，只补用到的），用 `unknown` 而非 `any` 标注不确定的返回值
3. 长期重度使用 → 升级到 **C**，把类型贡献回社区（也降低自己维护成本）
4. 库太小众 / 太烂 → **D**（换库）

### 知识点挂钩

- [课 11 声明文件 .d.ts 与 declare](stages/4-工程化与类型声明/lessons/lesson-11-模块与声明文件.md) —— 全局声明 / 模块声明 / 声明合并三种写法
- [课 6 any vs unknown](stages/2-收窄与控制流/lessons/lesson-06-any·unknown·never与信任边界.md) —— 不确定返回值用 `unknown` 而非 `any`

### 什么情况下此方案不适用

- **库 API 极其庞大** → 全量手写（C）成本不可控，优先 B 或 D
- **库本身依赖 TS API 的复杂泛型** → 手写 `.d.ts` 可能补不准，宁可 `unknown` + 边界收窄

### 做错会踩的坑

→ 关联 [`08-实战经验.md`](08-实战经验.md) 的故障模式 9（`.d.ts` 与实现漂移，补全给错方法）、2（`any` 声明传染）

</details>

## 场景 7｜monorepo 里的类型，到底该放哪一层

**场景**：你的项目是多包 monorepo（十几个包，互相依赖）。类型定义现在有两种摆法：① 全塞进一个 `shared` 包集中管理；② 各包放各包的、只在边界共享。你要决定**类型怎么分层放置**，才能既不重复、又别让"改一个类型"引爆全场。

### 🔒 先自己想

"集中放一个 `shared` 最干净、不重复"是第一直觉。先问自己：**改一个共享类型的成本是什么？** 如果每次改 `shared` 都要重建所有下游包，还值得"集中"吗？

<details>
<summary>💡 提示（思考方向）</summary>

- "类型"有很多种：领域模型、边界 DTO、内部实现类型。它们该**放一起**还是**分层放**？
- 集中放置的优点是"不重复"，代价是什么？（提示：改动的**爆炸半径**）
- 有没有一种"分层"能既复用、又隔离改动？
- 一个类型改动会波及多少包，这个"波及"是**编译期**的（重建慢）还是**语义**的（谁该知道）？

</details>

<details>
<summary>📖 展开解法</summary>

### 解法一览

| 解法 | 怎么做 | 代价 | 适用边界 |
|---|---|---|---|
| **A. 全塞 `shared` 集中管理** | 所有类型进一个 `shared` 包，各包引用 | 改一个类型，所有下游包**全量重建**（实测净重建是分层的 3.7x~5.7x） | 类型少、下游少、改动不频繁 |
| **B. 分层放置** | 领域层 / 边界层 / DTO 分开，各层就近放 | 可能有少量重复（边界类型的投影） | **通用默认解**；包多、改动频繁 |
| **C. 每包独立 + 边界共享** | 各包类型自洽，只在**边界**共享 DTO | 边界类型要维护一份"对外契约" | 强隔离、包之间耦合低 |

### 推荐路径

1. **类型分层先行**：领域类型（内部实现）、边界类型（跨包契约）、DTO（对外传输）三层分开——课 15 的三层划分
2. 默认 **B**（分层放置），让改动只波及"真正依赖它的下游"
3. 边界类型（跨包共享的）才放共享处，但**克制**——共享类型越少，爆炸半径越小
4. 只有类型极少、下游极少时才用 **A**（集中）

### 知识点挂钩

- [课 15 类型的分层与放置](stages/5-深入与架构/lessons/lesson-15-大型项目类型架构与选型收束.md) —— 三层划分 + 共享类型克制的实测依据（3.7x~5.7x 重建）
- [课 15 公开 API 的类型设计](stages/5-深入与架构/lessons/lesson-15-大型项目类型架构与选型收束.md) —— 边界 DTO 即契约

### 什么情况下此方案不适用

- **类型数量极少 + 下游极少** → 分层是过度设计，A（集中）更简单
- **包的领域类型高度耦合** → 硬分层会造出一堆"投影"重复，此时要审视包边界是否合理

### 做错会踩的坑

→ 关联 [`08-实战经验.md`](08-实战经验.md) 的故障模式 10（共享/边界类型加必填字段 = 破坏性变更，波及所有下游）

</details>
