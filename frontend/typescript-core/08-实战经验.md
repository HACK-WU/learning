## 一、适用边界与反模式

> **"不该用"比"怎么用"更值钱**——这是从"会用"到"用对"的分界线。

### 什么时候「别急着上 TS」

| 信号 | 倾向 | 为什么 |
|---|---|---|
| 一次性脚本 / 原型 / 演示 / 竞赛 | ❌ 不上 | 类型标注的认知成本收不回，脚本的生命周期短到不值得 |
| 生命周期 < 几周 | ❌ 不上 | 同上 |
| 单人维护且几百行以内 | ➖ 可不上 | JSDoc + `checkJs` 能拿到大半收益，还不用改构建 |
| 多人长期维护 / 公共 API / 大项目 | ✅ 上 | 类型即契约，收益随规模与协作放大 |

> 完整判断条件清单见 [`10-场景解法库.md`](10-场景解法库.md) 的「场景 1」，与课 15 口径一致（**先自己想，再看清单**）。本文件只点"最该停手的四种情况"，不重复展开。

### 高频反模式（TS 特性层面的误用，每条都回指课时）

| 反模式 | 为什么常见 | 后果 | 正确做法 |
|---|---|---|---|
| 外部数据直接 `as T` 断言 | 图省事，"我知道它长啥样" | 编译全绿、运行时 `TypeError`（故障模式 1） | 入口 `unknown` + 运行时校验，见课 6 |
| 拿 `any` 糊过报错 | 急着跑通 | 一处 `any` 沿数据流扩散，类型检查形同虚设（故障模式 2） | `unknown` + 收窄；`any` 只当中转站且立即收窄 |
| 把业务规则全塞进类型体操 | "越强越好" | 静默退化成 `never` 还不报错（故障模式 3）、编译变慢（故障模式 4） | 课 13 七步放弃标准 |
| 默认用 `enum` | 从别的语言带过来的习惯 | 留下运行时对象（TS 唯一的擦除例外）；`const enum` 在 `isolatedModules` 下直接受限 | 默认字面量联合 / `as const` 数组，见课 4 |
| 用 `{}` / `Object` 当"任意对象"类型 | 以为"空对象 = 任意对象" | 它其实是**黑洞**，几乎什么都收（故障模式 7） | `unknown` / `Record<string, unknown>` / 精确接口 |
| 用 `@ts-ignore` 压报错 | 图快 | 下次真错了它也不报，且不记录原因 | `@ts-expect-error`（错了会提醒你删），见课 10 |
| 让构建工具跳过类型检查 | 觉得 `tsc` 太慢 | CI 全绿、线上全红（故障模式 5） | `tsc --noEmit` 独立且可见地进 CI，见课 12 |
| 照 5.x 老教程配 TS 7 | 教程没更新 | 一堆硬错误直接编译失败（故障模式 6） | 按 TS 7 新默认配，见课 10 |

### 故障模式 1｜`as` 断言把外部数据"洗白"，运行时 `TypeError`

**症状**：类型检查**全部通过**，代码上线后报 `TypeError: Cannot read properties of undefined (reading 'xxx')`；出错点往往在"你以为已经校验过"的那一层之后。

**根因**：`as` 是**承诺**，不是**检查**。`JSON.parse(...) as User` 只是告诉编译器"相信我"，编译后这行断言被完全擦除——运行时该是什么还是什么。外部数据（网络响应 / `JSON.parse` / 用户输入）的真实形状没人保证，`as` 却在编译期把它"洗"成了可信类型。

**排查路径**：
1. 报错点往上追一层，看数据是不是来自 `JSON.parse` / 网络 / 跨模块边界
2. 搜代码里 `as ` 断言，重点看断言的**右侧类型**是不是"精确业务类型"（如 `User`）而左侧是 `any`/`unknown`
3. 把断言改成 `satisfies` 或运行时校验，看是否暴露出真实的形状不匹配

**修复**：
- 入口一律 `unknown` → 写**类型守卫**（`is User`）或运行时校验后收窄
- 需要更强的校验（字段类型 / 可选 / 嵌套）→ 用运行时 schema 库（见场景解法库「场景 2」）
- `satisfies` 用于"校验对象字面量是否符合某类型，但保留字面量"，不替代运行时校验

**预防**：**信任边界处，`as` 一律视为红灯。** 团队约定：外部数据进入系统的唯一合法通道是"`unknown` → 运行时校验 → 精确类型"，`as` 只允许在"类型系统比运行时更精确"的内部场景（如类型体操的结果断言）。

**【证据】实测（课 6）**——同一个 `JSON.parse('{"profile": null}')`：

| 处理方式 | 运行时表现 |
|---|---|
| 只有 `as User` 断言 | `TypeError`（读到 `profile.nickname` 时崩） |
| 加上类型守卫 | 可控的业务错误（在边界处就被拦住） |

> 📖 回指：[课 6 any·unknown·never 与信任边界](stages/2-收窄与控制流/lessons/lesson-06-any·unknown·never与信任边界.md) · [课 3 类型断言与 satisfies](stages/1-类型思维启蒙/lessons/lesson-03-对象类型与结构化类型.md) · [实战项目《schema-guard》](projects/schema-guard/README.md)

### 故障模式 2｜`any` 传染，一处 `any` 全链路失守

**症状**：你改了一个接口的字段（改名 / 删字段 / 改类型），**编译器一声不吭**，于是"改完就跑"的代码上线后崩。你排查时发现：报错点离你改的地方隔了好几层。

**根因**：`any` 会沿数据流**扩散**。一个返回 `any` 的函数，它的调用方拿到的是 `any`，调用方再往下传还是 `any`——类型检查在这条链路上**整体关闭**。你改的是上游，但上游的"类型"是 `any`，下游根本感知不到变化。

**排查路径**：
1. 报错链路上逐层看函数签名，找第一个返回 `any` 或参数是 `any` 的
2. 用 `npx tsc --noEmit` 全量查，把 `any` 出现点列出来（开启 `noImplicitAny` 后更明显）
3. 把可疑 `any` 改成 `unknown`，看下游哪里报错——报错点就是"类型信息丢失的边界"

**修复**：
- 源头 `any` → `unknown`（逼下游显式收窄）
- 渐进迁移中，`any` 只允许当**中转站**：拿到后**立即**在最近处收窄成精确类型，不让它继续流
- 团队规范：`eslint` 的 `@typescript-eslint/no-explicit-any` 设 error（`no-unsafe-assignment` 系列更强）

**预防**：**`any` 是"我需要马上回来修"的标记，不是"我放弃了"的标记。** 每写一处 `any` 配一条 TODO，Code Review 把裸 `any` 当红灯。

> 📖 回指：[课 6 any：逃生舱与传染性](stages/2-收窄与控制流/lessons/lesson-06-any·unknown·never与信任边界.md) · [课 15 JS → TS 渐进迁移](stages/5-深入与架构/lessons/lesson-15-大型项目类型架构与选型收束.md)

### 故障模式 3｜类型体操静默退化成 `never`，万能赋值、零报错

> **这是类型体操最贵的代价，比"报错难读"严重得多。**

**症状**：一段精心写的条件类型，在某条输入上"算不出来"，但**编译器什么都没报**——它静默退化成 `never`。而 `never` 可以赋给**任何**类型，于是错误一路绿灯。你以为类型挡住了，实际什么都没挡住。

**根因**：条件类型在"无法求值"或"命中 `never` 分支"时，结果往往是 `never`。`never` 是**底部类型**，可赋给一切，所以"算错了"和"没算"在类型层面都表现为"合法"。

**排查路径**：
1. 给复杂类型配**类型断言测试**（`Equals` / `Expect`），而不是 `as` 断言（`as unknown as` 会蒙混过关）
2. 对可疑结果用 `IsNever` 显式探测，看它到底是不是 `never`
3. 给条件类型**补兜底分支**：`X extends Y ? A : B` 的 `B` 是不是覆盖了"算不出来"的情况

**修复**：
- 每个递归条件类型配**兜底**（不能让结果裸落在 `never` 上）
- 断言用 `Equals` + `Expect` 精确判定，并补一条**负向对照**（证明断言真的会抓错）
- 回到课 13 七步标准：如果"算不出来"会发生，且你没法兜底 → **别写这个体操**

**【证据】实测（课 13）**：

```
pick(obj, "user.profile.nickname")  赋给 string  → 不报错（退化成 never 后万能赋值）
用 IsNever 二次验证                       → 确认是 never
```

### 故障模式 4｜类型体操递归爆栈（TS2589）/ 编译变慢

**症状**：`tsc` 报 `TS2589: Type instantiation is excessively deep and possibly infinite`；或者编译耗时明显上升（复杂体操比手写慢约 2.9x）。

**根因**：类型递归有**深度上限**。非尾递归约 50 层、尾递归约 1000 层就触发 `TS2589`（实测值，TS 内部是启发式阈值，随版本变）。此外，类型求值本身有成本——递归条件类型、多次 `infer`、长字符串操作都会拖慢 Check 阶段。

**排查路径**：
1. 看报错是不是 `TS2589`，定位到哪个类型别名
2. 确认递归是不是**尾递归**（尾递归能到约 1000 层，非尾递归约 50 层）
3. `tsc --diagnostics` 看 Instantiations / Check time 是否异常

**修复**：
- 非尾递归 → 改成**尾递归**（分支直接递归即可被优化，TS 4.5+）
- 加**兜底**防止无限递归
- 已经逼近上限 → 回到课 13 七步标准，考虑手写 / 生成替代

**预防**：写递归类型前先问"能不能尾递归？有没有兜底？"（这正是七步标准的第 ④⑤ 条）。

**【证据】实测（课 13）**：

| 构造 | 结果 |
|---|---|
| 非尾递归 48 层 | ✅ 通过 |
| 非尾递归 49 层 | ❌ `TS2589` |
| 尾递归 999 层 | ✅ 通过 |
| 尾递归 1000 层 | ❌ `TS2589` |

### 故障模式 5｜构建工具"只转译不检查"，CI 全绿、线上全红

**症状**：CI 全绿，代码正常上线，然后线上报**类型错误**——比如 `total = "0100"`（字符串当数字）、某个枚举值写错却没人拦。你回看构建日志，类型检查根本没跑过。

**根因**：esbuild / swc / tsx / Vite 这类工具**只转译（擦掉类型）不检查**——它们的职责是把 TS 变 JS 跑起来，快是快，但类型错误会被**静默放过**。只有 `tsc` 才真正做类型检查。工具链里如果只有"转译"，等于类型系统从未运行。

**排查路径**：
1. 看 CI 配置里有没有**独立的 `tsc --noEmit`** 步骤（很多项目把它合进了 build，或根本没加）
2. 本地跑 `npx tsc --noEmit`，看是否突然冒出一堆错
3. 查构建工具配置：`esbuild` / `swc` / `tsx` / `vite` 转译时都**不检查类型**

**修复**：
- CI 里加一条**独立且可见**的 `tsc --noEmit` 步骤（与 build 分开，失败就红）
- 本地开发用编辑器（TS 7 的 VS Code 原生扩展）实时看类型
- 注意 `tsc --noCheck`（只转译不检查）——它存在但 `--help` 里查不到，别被误用

**预防**：**"构建通过" ≠ "类型通过"。** 团队约定：typecheck 是独立 gate，不依附 build；pre-commit 也挂 `tsc --noEmit`。

**【证据】实测（课 12）**：

| 案例 | 表现 |
|---|---|
| `total = "0100"`（字符串当数字） | 转译工具放行，`tsc` 才报 |
| `PAYD`（枚举值写错） | 同上，CI 全绿、线上红 |

### 故障模式 6｜TS 7 照 5.x 老教程配置，一堆硬错误

**症状**：初始化项目后 `tsc` 直接报错，错误码是 `TS5108` / `TS5102` / `TS5090` / `TS5112` 之类，报错信息指向 `tsconfig.json` 里的某个选项（如 `baseUrl`、`target: es5`、`moduleResolution: node`）。

**根因**：TS 7 改了一大批**默认值**（`strict` 默认开、`rootDir` 默认 `./`、`types` 默认 `[]`），并把一批旧选项变成**硬错误**（`target: es5`、`moduleResolution: node/node10/classic`、`baseUrl` 等）。市面上大量教程仍停留在 5.x，照抄配置就会撞墙。

**排查路径**：
1. 看错误码是不是 `TS510x` / `TS5090` / `TS5112` 系列
2. 打开 `tsconfig.json`，逐个对照报错指向的选项，删掉已废弃/变硬错误的项
3. 用 `npx tsc --init` 生成一份 TS 7 的新模板，对照差异

**修复**：
- 删除 TS 7 已废弃的选项（`baseUrl` 改用 `paths` 的绝对写法、`moduleResolution` 改用 `bundler`/`nodenext`、`target` 用现代值）
- 按 TS 7 新默认重写一份最小 `tsconfig.json`（课 1 给的就是 TS 7 可用版）

**预防**：**配 TS 7 前，先确认教程写的是哪个大版本。** 遇到 "TS 5 配置" 字样的教程，选项要逐条过 TS 7 兼容性。

**【证据】实测（课 10）**——10 份 `tsconfig.json` 实跑，报错码与官方描述吻合：`TS5108` / `TS5102` / `TS5090` / `TS5112`。

### 故障模式 7｜类型太宽（`{}`）成了黑洞，编译放行、运行时崩

**症状**：一个本该被类型拦住的错误值，**类型检查通过了**，运行时崩。你回头看类型定义，发现某个位置用的是 `{}` / `Object` / 或某个"看起来很宽"的类型。

**根因**：`{}`（空对象类型）在 TS 里**不是**"空对象"，而是"**除 `null` / `undefined` 之外的一切值**"。同理 `Object` 也收几乎所有值。把它们当"任意对象"用，等于把这一层类型检查**整体放空**——任何值都能塞进去。结构化类型下，"宽类型"的每个成员都是这个黑洞的入口。

**排查路径**：
1. 报错点上溯，看类型定义的哪个字段是 `{}` / `Object` / `ReactNode` 这类宽类型
2. 确认这个值到底该是什么精确形状，把它收窄成接口 / 联合 / `Record<string, unknown>`
3. 如果值是外部数据 → 回到故障模式 1，运行时校验

**修复**：
- `{}` / `Object` → `unknown`（逼你收窄）或精确接口
- "任意键值对象" → `Record<string, unknown>`（至少值被约束为 `unknown`）
- 复用了第三方宽类型（如 `React.ReactNode`）→ 在**你的边界**收窄，不直接透传

**预防**：**看到 `{}` / `Object` 当类型，默认它是 bug。** 精确的类型才拦得住错误，宽类型只是"编译期不报错"的幻觉。

> 📖 回指：[课 3 结构化类型系统](stages/1-类型思维启蒙/lessons/lesson-03-对象类型与结构化类型.md) · 真实案例见本文件「四、真实事故案例复盘」

### 故障模式 8｜`Object.keys` 返回 `string`，不能直接索引回对象

**症状**：`Object.keys(obj).map(k => obj[k])` 报类型错误（`k` 是 `string`，不能索引 `obj`）；或你为绕开它写了 `as keyof`，埋下运行时隐患。

**根因**：`Object.keys` 的返回值类型是 `string[]`，**不是** `(keyof T)[]`。这是 TS 官方的**有意为之**——因为 JS 里对象可能带运行时额外键（原型 / 枚举），`Object.keys` 无法静态保证返回的键一定属于 `keyof T`。`for...in` 同理。

**排查路径**：
1. 报错点在"用 `Object.keys`/`for...in` 的结果去索引同一个对象"
2. 确认键来源：是对象自身可枚举键，还是可能混入原型键

**修复**：
- 安全遍历对象条目 → `Object.entries(obj)`（返回 `[string, unknown][]`，仍要收窄值）
- 确定键就是 `keyof T` 且能接受断言 → 收窄到 `keyof T`（但理解这仍是承诺，见故障模式 1）
- 更稳 → 用 `Record<string, T>` 明确值类型，或改用 `Map`

**预防**：**把 `Object.keys` 的返回当成 `string[]`，不要默认它能索引回对象。** 这是 TS 官方文档明确的设计取舍，不是 bug。

> 📖 回指：[课 3 对象类型：interface 与 type](stages/1-类型思维启蒙/lessons/lesson-03-对象类型与结构化类型.md) · [课 8 泛型约束与 keyof](stages/3-泛型与类型编程/lessons/lesson-08-泛型基础.md)

### 故障模式 9｜声明文件 `.d.ts` 与实现漂移，补全给出不存在的方法

**症状**：编辑器自动补全提示一个方法名（或类型），你照着写，编译**通过**，运行时报 `xxx is not a function`。你翻源码才发现：那个方法根本不存在，是 `.d.ts` 写错了。

**根因**：`.d.ts` 是**手写的对外类型声明**，与 JS 实现**没有强制同步机制**——编译器只信 `.d.ts`，不去验证它和实现是否一致。一旦 `.d.ts` 与实现漂移（拼写错 / 签名过期），类型检查会"诚实地"通过一个错误的契约。

**排查路径**：
1. 运行时报 `is not a function` 或"属性不存在"，但类型检查一直通过
2. 找到这个类型来自哪个 `.d.ts`（第三方 `@types` 还是你项目里的 `declare module`）
3. 打开 `.d.ts` 与对应 JS 实现，逐个方法名 / 签名比对

**修复**：
- 第三方 `@types` 漂移 → 升级/降级 `@types` 版本，或项目里写 `declare module` 覆盖
- 自己维护的 `.d.ts` → 建立"类型与实现一起改"的约定（改实现必须同步改 `.d.ts`）
- 兜底 → 在边界处做运行时校验，不盲信声明（见故障模式 1）

**预防**：**把 `.d.ts` 当成需要测试的代码，而不是"顺便写写的注释"。** 对外库尤其——`.d.ts` 就是你的 API 契约，错了会一路误导所有调用方。

> 📖 回指：[课 11 声明文件 .d.ts 与 declare](stages/4-工程化与类型声明/lessons/lesson-11-模块与声明文件.md) · [课 15 公开 API 的类型设计](stages/5-深入与架构/lessons/lesson-15-大型项目类型架构与选型收束.md) · 真实案例见本文件「四、真实事故案例复盘」

### 故障模式 10｜公开 API 加必填字段 = 破坏性变更（TS2741）

**症状**：升级了某个依赖的版本，自己项目突然报一堆 `TS2741: Property 'xxx' is missing in type ...`，而且全是"别人传给你"的参数缺字段。

**根因**：`interface` 加一个**必填**字段，是**破坏性变更**——所有"构造这个对象传给该接口"的下游都会编译失败。因为结构化类型下，多一个必填字段意味着"旧的对象不再满足新的形状"。这是 TS 里最容易被低估的破坏性变更之一。

**排查路径**：
1. 看是不是升级依赖后冒出的 `TS2741`
2. 定位到新加的必填字段，看它到底是"所有调用方都该有"还是"可选"

**修复**：
- 新字段如果"不是每个调用方都有" → 用**可选字段** `?`，或给默认值
- 如果确实要必填 → 这是 major 版本变更，按语义化版本升级并**显式通知**下游
- 对外库：`.d.ts` 里加必填字段前，评估下游影响面（这就是课 15「加必填 = major」的实证）

**预防**：**给公开类型加字段时，先问"这个字段所有老调用方都有吗？"没有 → 可选。** 对外 API 的类型演进要按"破坏性变更"的严重度来管理。

> 📖 回指：[课 15 公开 API 的类型设计](stages/5-深入与架构/lessons/lesson-15-大型项目类型架构与选型收束.md) · [课 3 结构化类型系统](stages/1-类型思维启蒙/lessons/lesson-03-对象类型与结构化类型.md)

## 四、真实事故案例复盘

### 案例 1｜`React.ReactNode` 是"黑洞"：类型太宽，编译放行、运行时崩

**【来源】** Kball（Dev.to）一手复盘文章《The React.ReactNode type is a black hole》+ JS Party #213 讨论（核查于 2026-09；一手开发者自述，非二手转述）。

**经过**：某次国际化重构后，一个 React 组件在运行时抛异常。排查发现：一个 `description: string | React.ReactNode` 的 prop，被传进了一个 `TranslatedText` 类实例——而 `TranslatedText` 根本不可渲染。

**根因**：`React.ReactNode` 的定义链里有 `ReactFragment = {} | ReactNodeArray`。那个 `{}`（空对象类型）在 TS 里是"**除 `null`/`undefined` 外的一切**"，于是 `ReactNode` 几乎什么都收——包括不可渲染的 `TranslatedText`。**类型系统"诚实地"放行了本该拦住的值。**

**损失**：一个本应被类型系统在编译期拦住的运行时崩溃，在生产环境真实发生。

**教训**（可迁移到你的项目）：

| # | 教训 | 落地动作 |
|---|---|---|
| 1 | **宽类型（`{}`）是黑洞，不是安全网** | 复用第三方类型前，看清楚它的定义链里有没有 `{}`/`any` 这种"漏"；有 → 在你的边界收窄 |
| 2 | **"编译通过" ≠ "类型足够严"** | 类型再严，也只是"你写得多严"。太宽的定义给的是**假安全感** |
| 3 | **类型检查跑着，不代表它拦得住** | 定时 review 你依赖的**类型定义**，而不仅是你的业务代码 |

> ⏳ **置信度说明**：本案例为开发者一手博客自述，非学术/官方复盘；但其机制（`{}` 空对象类型的黑洞行为）是 TS 的**确定行为**，可独立验证。

### 案例 2｜d3 声明文件的拼写错误：`theshold` 骗过编译器

**【来源】** 学术论文《Checking Correctness of TypeScript Interfaces for JavaScript Libraries》（Aarhus University，cs.au.dk）（核查于 2026-09）。

**经过**：d3.js 的 `.d.ts` 声明文件里，`d3.scale.threshold` 被误拼成 `theshold`。后果是：编辑器自动补全会建议 `d3.scale.theshold()`，**类型检查通过**，但运行时报错——因为真实实现里没有 `theshold` 这个方法。

**根因**：`.d.ts` 是**手写声明**，与 JS 实现**没有自动同步机制**。编译器只信 `.d.ts`，不去验证声明与实现是否一致。一个拼写错误就能让"错误的契约"被诚实执行。该论文还指出：d3 的 `.d.ts` 有 1800 行测试代码，这个 bug 依然漏了。

**教训**：

| # | 教训 | 落地动作 |
|---|---|---|
| 1 | **声明文件需要测试，不是"顺便写写"** | 对外库的 `.d.ts` 要有"类型 + 实现"一致性检查（哪怕只是关键方法的抽样比对） |
| 2 | **自动补全 ≠ 真相** | 补全给出的方法，运行时可能不存在（故障模式 9） |
| 3 | **别盲信第三方类型** | 可疑处的运行时校验，是对 `.d.ts` 漂移的最后防线 |
