## 三、bkiam 链路：日志为空，但组件是真活的

### 3.1 可疑现象

```text
bkiam-saas-beat   日志只有 2 行（仅 Python 3.6 弃用警告）
bkiam-saas-worker 日志停在 [queues] 段，没有 celery@... ready 行
```

对比 apigateway 有明确 `ready`，bkiam **没有**。这时候不能因为它 `Running` 就算过。

### 3.2 我的第一次误判方向

先用 `ps aux` 查进程，报错：

```text
exec: "ps": executable file not found in $PATH
```

容器里**没有 ps**。改用 `/proc` 遍历，成功：

```text
1:  bash /app/bin/start_celery.sh
11: /opt/venv/bin/python3 /opt/venv/bin/celery -A config worker -l INFO
15: /opt/venv/bin/python3 /opt/venv/bin/celery -A config worker -l INFO
16: /opt/venv/bin/python3 /opt/venv/bin/celery -A config worker -l INFO
```

进程在（concurrency=2 + 主进程）。**无探针容器内查进程要用 `/proc`，别依赖 `ps`。**

### 3.3 根因：Python 3.6 stdout 块缓冲

```text
PYTHON 相关 env: 无（PYTHONUNBUFFERED 未设置）
```

Python 3.6 + 无 `PYTHONUNBUFFERED` + stdout 不是 tty → **块缓冲（4KB 一刷）**。
celery banner 只写了 3KB 左右，没到 4KB 就一直卡在缓冲区里。

所以：**不是没启动，是日志没刷出来**。

### 3.4 用客观证据判定（不靠日志）

**证据 1 —— rabbitmq 侧有真实连接**

```text
vhost  user   name                                    state
bkiam  bkiam  192.168.53.36:51286 -> 192.168.109.191:5672  running
```

**证据 2 —— 队列有活跃消费者**

```text
queue_name  consumer_tag  ack_required  active
bk_iam      None3         true          true
celeryev... None2         false         true
```

**证据 3 —— 触发真实任务后队列 0 积压**

```text
TASK_ID=975f3b08-cf8a-4fc8-b79f-2ffd4eb41a6d   ← 发送成功
bk_iam   messages=0  consumers=1               ← 被消费，无积压
```

**证据 4 —— DB 侧**

```text
bkiam_saas 库表数 = 74
```

### 3.5 一个未解释的现象（如实记录）

`celery inspect ping` 返回：

```text
Error: No nodes replied within time constraint   (exit 69)
```

我没能确定根因。已知线索：
- worker 日志明确写了 `task events: OFF`（未开 `-E`），但 inspect 走的是 broadcast/pidbox，理论上不受此影响；
- broker vhost、app 名（`-A config`）我核对过与 worker 启动命令一致；
- 但 `-A bkiam` 报 module not found，说明 app 名解析仍可能与 worker 内部注册名不完全一致。

**结论：inspect 这条路在本环境没走通，但不影响判定** —— 上面 4 条证据（连接、消费者、任务消费、DB）已构成完整闭环，比 inspect 更直接。

按既有纪律：**修不好的东西不假装修好，如实记录 + 说明为何不影响结论。**

## 七、本批沉淀

1. **容器内查进程用 `/proc`，没有 `ps` 是常态**（精简镜像）。

2. **Python 老版本容器日志"为空"先怀疑块缓冲**，看有没有 `PYTHONUNBUFFERED`；
   判定存活要去 broker/DB/队列侧取客观证据，不能只看 stdout。

3. **查依赖用 grep 模糊匹配，别猜全名**。
   本环境 `bk-mysql8`、`bk-etcd`、`bk-apigateway-dashboard` 都不带我猜的前后缀。

4. **`Running + restarts=0` 不等于业务可用**，但反过来"日志为空"也不等于故障 —— 两个方向都要有客观证据才下结论。

5. **beat 用 DatabaseScheduler 是强证据**：能读到调度表并 Sending due task，说明 DB 连接是通的。
