## 一、发现的问题：上次探针还原只做了一半

### 1.1 盘点脚本抓到的异常

```text
[未还原] 11 个:
   bk-repo-bkrepo-auth      init=120 fail=12
   bk-repo-bkrepo-docker    init=120 fail=12
   ...
```

`initialDelaySeconds` 已还原成 120（原始值），但 **`failureThreshold` 还是 12，原始值是 5**。

也就是说：第 4 批为了保活把 `fail` 从 5 放宽到 12，
上次还原时只改了 `init`，**漏了 `fail`**。

### 1.2 为什么之前没发现

上次还原后我验证的是「`init` 是否等于原值」，
**没有逐字段对照**。只看一个字段，就以为整条探针还原了。

**教训：还原配置要做「全字段对照」，不能只验改过的那一个字段。**

### 1.3 原值从哪来（不猜）

从 helm release 的 secret 里解出权威 manifest：

```bash
kubectl get secret -n blueking sh.helm.release.v1.bk-repo.v1 \
  -o jsonpath='{.data.release}' | base64 -d | base64 -d | gunzip
```

解析结果（12 个 deploy 全量）：

```text
bk-repo-bkrepo-auth          init=120  fail=5  period=15
bk-repo-bkrepo-gateway       init=60   fail=5  period=15   ← gateway 出厂就是 60
bk-repo-bkrepo-generic       无 livenessProbe              ← 出厂设计
其余 9 个                     init=120  fail=5  period=15
```

### 1.4 修复 + 复核

```bash
kubectl patch deploy -n blueking <name> --type=json \
  -p '[{"op":"replace",
        "path":"/spec/template/spec/containers/0/livenessProbe/failureThreshold",
        "value":5}]'
```

11 个全部 OK。复检：

```text
放宽值残留: 0        ← 全命名空间 deploy 扫描，init=180 或 fail=12 均为 0
```

终态与 helm 原值**逐字段一致**。

## 四、本轮沉淀

1. **还原配置要全字段对照，别只验改过的那个**。
   本轮就是只看了 `init` 漏了 `fail`，差点留下一个"看起来还原了其实没有"的环境。

2. **改过什么要记账**。
   第 4 批放宽时改了两个字段（init、fail），
   但还原清单里只记了一个 —— 改动的时候就应该把"改了哪几个字段、原值多少"一次性记全。

3. **原值从 helm release secret 取，不猜、不凭印象**。
   `sh.helm.release.v1.<release>.v1` → base64×2 → gunzip → manifest，
   这是本环境下唯一权威来源（网络受限拉不到 chart）。

4. **`generic` 无探针是出厂设计，不是遗漏**。
   排查时容易把它当成"忘了配"，实际 helm 原值就没有。
