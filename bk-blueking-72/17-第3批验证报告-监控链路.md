## 一、本批解决的问题

### 1.1 kafka CrashLoopBackOff（核心难题）

**现象**：
```text
bk-kafka-0   0/1   CrashLoopBackOff
Liveness probe failed: dial tcp 192.168.109.132:9092: connection refused
Container kafka failed liveness probe, will be restarted
```

**根因（关键洞察）**：Kafka **不是崩溃，是被探针误杀**。

同一份日志里可以看到 Kafka 正在正常工作：
```text
INFO [GroupCoordinator 0]: Stabilized group
     bkmonitorv3_transfer0bkmonitor_10130 generation 5
     (__consumer_offsets-9)
```
它在处理监控 transfer 的 consumer group rebalance —— 说明服务在跑，
只是 9092 端口还没开就被判定失败。

**探针配置（原值）**：
```json
livenessProbe:  {"initialDelaySeconds": 10, "failureThreshold": 3,
                 "periodSeconds": 10, "tcpSocket": {"port": "kafka-client"}}
readinessProbe: {"initialDelaySeconds": 5,  "failureThreshold": 6,
                 "periodSeconds": 10, "tcpSocket": {"port": "kafka-client"}}
```
→ **40 秒内 9092 不开就被杀**。Kafka 冷启动要加载几十个
`__consumer_offsets` 分区，远超 40 秒。全量启动时资源竞争更慢，必死。

**解法**（两步，缺一不可）：
```bash
# 1. 腾内存：裁掉第 4/5 批组件（bk-repo 13 个 + applog logstash）
#    内存 39G → 31G，available 3G → 11G

# 2. 放宽探针
kubectl patch sts -n blueking bk-kafka --type='json' -p='[
  {"op":"replace","path":"/spec/template/spec/containers/0/livenessProbe/initialDelaySeconds","value":180},
  {"op":"replace","path":"/spec/template/spec/containers/0/livenessProbe/failureThreshold","value":12},
  {"op":"replace","path":"/spec/template/spec/containers/0/readinessProbe/initialDelaySeconds","value":60},
  {"op":"replace","path":"/spec/template/spec/containers/0/readinessProbe/failureThreshold","value":30}
]'
kubectl delete pod -n blueking bk-kafka-0
```

**结果**：
```text
bk-kafka-0   1/1   Running   0 (restarts=0)   3m28s
9092 OPEN
Events: 只有 Scheduled/Pulled/Created/Started，无任何 probe 失败
```

⚠️ **这是验证手段，不是生产配置**。留证后应还原为原值：
`initialDelaySeconds: 10 / failureThreshold: 3`。

## 七、本批沉淀的方法论

1. **CrashLoopBackOff 先分辨是被杀还是真崩**：看 Events 有无
   `Liveness probe failed` + `Killing`。有 = 探针问题，改探针而不是改代码。
2. **探针预算要算**：`initialDelaySeconds + failureThreshold × periodSeconds`
   是组件的"启动宽限期"。慢启动组件（Kafka/Spring）必须放宽。
3. **腾内存优先于改配置**：本轮先裁掉 14 个非本批组件释放 8G，
   kafka 启动速度立刻改善。资源竞争会放大一切启动问题。
4. **分批启动要控制尖峰**：每 6 个等 40 秒，比一次性起 23 个安全得多。
5. **000 不等于故障**：先看有没有 ingress/Service，再判断服务是否异常。
