## 三、分批策略（可复用）

按依赖顺序切批，**验证完即裁**：

```text
第1批 存储层  ── 全程保留（后续每批都依赖）
第2批 认证网关 ── 全程保留（所有页面的入口）
第3批 业务核心 ── 验完保留核心，裁告警链路
第4批 制品库  ── 验完全裁 12 个（回收 6G）
第5批 日志    ── 验完裁 logstash，filebeat 保留（直连 ES 不占资源）
第6批 节点管理 ── 验完裁 7 个 worker，保留 api/saas
第7批 告警链路 ── 验完裁 24 个（回收 3G）
第8批 权限/网关 ── 验完裁 4 个
```

**内存曲线**（实测）：

```text
全量启动  42G  ← 无冗余，必崩
   ↓ 分批    39G   裁监控/制品库
   ↓         32G   裁 bkrepo 12 个（回收 6G）
   ↓         35G   起日志(logstash +1G)
   ↓         35G   起 nodeman(+1G)
   ↓         39G   起 alarm 24 个(+3G)
   ↓         36G   裁 alarm、裁第8批
```

峰值控制在 **39G 以内**，始终留 3G 以上余量，**全程未触发节点 OOM**。

## 四、最重要的发现：探针误杀是主因

全量启动时的 CrashLoop，**根因不是组件崩溃，是探针误判**。

| 组件 | 探针原值 | 实际启动耗时 | 结果 |
|---|---|---|---|
| `bk-kafka` | liveness init=**10s** | 加载 `__consumer_offsets` 远超 10s | 无限重启 |
| `bk-repo-opdata` | liveness init=120s | Spring 上下文初始化 **10.3s** | CrashLoop |
| `bk-redis` | liveness init=**5s** | 实际 **55 秒** | 退出 137 |
| `logstash` | liveness init=**300s** | JVM | ✅ 一次就起，从未被杀 |

**logstash 出厂配 300s，一次没被杀** —— 这反证了关键判断：
**不是蓝鲸组件都难起，是 kafka（10s）、redis（5s）那几个默认值太激进。**

第 6、7、8 批共 41 个组件**全部无探针**，因此全部一次启动成功、0 CrashLoop，
进一步印证了这个结论。

### 处置与还原（含一次自我纠错）

验证期临时放宽至 180s，验证完成后全部还原为 chart 原值：

```text
kafka   liveness : init=10   failure=3   ✅ 已还原
bkrepo  liveness : init=120  failure=5   ✅ 已还原（gateway 为 60）
logstash / nodeman / alarm / 第8批 : 未修改 ✅ 无需还原
```

> 补充：`bk-repo-bkrepo-generic` 是**双容器** Pod（`plugin-gitci` 无探针 + `generic` init=120/fail=5），
> 早期报告里写的"generic 无探针"是对 `plugin-gitci` 那个容器的误读，实际业务容器 `generic` 有探针且已还原。

⚠️ **第一次还原只做了一半**：只还原了 `initialDelaySeconds`，
漏了 `failureThreshold`（仍是放宽后的 12，原值 5）。
原因是"只验证了改过的那一个字段"，没有全字段对照。

**修正**：从 helm release secret 解出权威 manifest 逐字段对照后补还原，
终检 **残留 = 0**。

原值来源（网络受限拉不到 chart，这是本环境唯一权威途径）：

```bash
kubectl get secret -n blueking sh.helm.release.v1.bk-repo.v1 \
  -o jsonpath='{.data.release}' | base64 -d | base64 -d | gunzip
```

还原后 kafka 持续 `restarts=0` —— 它已完成冷启动、端口已开，还原不会重新触发杀戮。

⚠️ **下次 `helm upgrade` 会覆盖回原值**，届时若再跑全量需重新评估。这是环境特性，不是缺陷。

## 五、方法论沉淀（比结论更值钱）

### 1. 唯一标记法 —— 验证数据链路的最强证据

不要只看 Pod Ready，要追一条真实数据走完全程：

```bash
MARK="BATCH5-E2E-$(date +%s)"
kubectl exec -n blueking <pod> -- sh -c "echo '[$MARK] test' > /proc/1/fd/1"
sleep 60
curl -u elastic:$EP "http://ES:9200/_search?q=$MARK&pretty"
→ "value" : 1, "_index" : "bk_paas3_app-2026.09.24"
```

证明的是"数据真走完全程"，不是"进程活着"。第 3 批 kafka、第 5 批日志都用的这招。

### 2. 副本为 0 ≠ 链路不通

起 logstash **之前** ES 里已有数据：

```text
bk_paas3_ingress_grokfailure-2026.09.24   docs=103
bk_paas3_ingress_grokfailure-2026.09.23   docs=25,731
```

filebeat 直连 ES，logstash 只是旁路管道。**判断链路要看数据（索引文档数），不能数 Pod。**

### 3. 401 / 302 / 403 / 业务异常 都可能是健康信号

| 批次 | 响应 | 含义 |
|---|---|---|
| 4 | Docker Registry `401 + WWW-Authenticate` | 协议实现正确 |
| 6 | nodeman `3800018 Only from ESB/APIGW` | 网关鉴权生效 |
| 7 | transfer `401 Unauthorized` | 数据入口鉴权生效 |

**看到非 200 先问"这个响应在协议里意味着什么"，别急着判故障。**

### 4. ERROR 计数 ≠ 故障

第 6 批 `backend-api` ERROR=3，逐条查证：三条是**同一次请求**（均 12:20:10）的完整堆栈，
内容是 `plugin bk-collector is not exist`，业务校验正常拒绝。
**看 ERROR 要看时间和内容，不能只数数。**

### 5. DB 级验证比日志硬

```python
# 第6批
Cloud.objects.values_list('bk_cloud_id','bk_cloud_name')  → [(90000001, '未分配')]
# 第7批
StrategyModel.objects.count()  →  12   ← 与日志 "0/12" 完全吻合
```

日志说成功只是程序自己认为成功，**DB 里有记录才是闭环**。两者对不上说明事务回滚了。

### 6. 起组件之前先查探针

第 6 批（7 个）、第 7 批（24 个）、第 8 批（4 个）起之前先查探针，
发现全无探针 → 一次全起、不分批，全部 1/1。
前三批是"起了崩、崩了才查"，白费两轮。

### 7. 凭据不要靠猜

ES 凭据**不在** Helm 标准命名 `*-es-elastic-user` 里，
而在 `bk-elastic-elasticsearch` 的 `elasticsearch-password` key。

```bash
kubectl get secret -n blueking -o json | python3 -c "
import json,sys
d=json.load(sys.stdin)
for it in d.get('items',[]):
    n=it['metadata']['name']
    if 'elast' in n.lower():
        print(n,'keys=',list(it.get('data',{}).keys()))
"
```

### 8. 还原配置要全字段对照

改了哪几个字段、原值是多少，**改动时就要一次性记全**。
只验改过的字段会留下"看起来还原了其实没有"的环境。

## 六、踩过的坑（按代价排序）

| # | 坑 | 现象 | 正解 |
|---|---|---|---|
| 1 | 探针误杀 | kafka/opdata/redis 无限 CrashLoop | 先腾内存，再放宽探针（且必须还原） |
| 2 | 探针只还原一半 | `fail` 仍为 12 | 全字段对照 helm release manifest |
| 3 | `kubectl logs deploy/xxx` | 24 个组件日志全空 | 多 Pod 时匹配错，用 `grep "^app-"` 取精确名 |
| 4 | 猜组件名 | `bk-mysql`/`bk-etcd` 报"不存在" | 实际是 `bk-mysql8`/`bk-etcd`，用 `grep -i` |
| 5 | deployment 名 ≠ svc 名 | DNS 解析失败 | `kubectl get svc \| grep 关键词` |
| 6 | 容器无 `ps` | `exec: "ps": not found` | 遍历 `/proc/[0-9]*/cmdline` |
| 7 | Python 3.6 块缓冲 | 日志看着是空的 | 查 `PYTHONUNBUFFERED`；去 broker/DB 侧取证据 |
| 8 | `echo $?` 接管道 | 取到 `head` 的退出码 | 用独立 curl Pod 取真实 HTTP 码 |
| 9 | celery app 名猜错 | `-A config.settings` ModuleNotFound | 先 `cat start_celery.sh` 确认 `-A config` |
| 10 | 内存被节点容器吞掉 | 裁减后 `free` 数字不变 | 看节点容器自身占用，不只算 Pod |

**其中 3~9 是同一类错误：凭习惯猜，没先读被测对象的实际定义。**
这印证了既有铁律 —— **数字异常时先怀疑测量方法，再怀疑被测对象**。

## 九、一句话总结

八批验证走完，**未验证组件归零，探针残留归零**。
真正的收获不是"蓝鲸能跑起来"，而是三条可迁移的判断纪律：

1. **"Pod Ready" ≠ "链路验证成功"** —— 前者是进程活着，后者是业务走通。
2. **看到异常先核验测量方法，再核验被测对象** —— 8 批里 7 次"故障"是测法错误。
3. **修不好的东西不假装修好** —— 要么真修好，要么显式记录"未修复 + 原因 + 替代方案"。
