# 28 - 证书与密钥清单（PKI 全景 + 复现指引）

> **为什么有这篇**：`assets/config-backup/blueking/environments/default/cert/` 下有 24 个文件，其中 14 个是私钥或密钥库
> （`git check-ignore` 实测：8 个 `.key` + 2 个 `.p12` + 2 个 `.keystore` + 2 个 `.truststore`）。
> 这些**不纳入 git**（见 `.gitignore`），但"有哪些、干什么用、换环境怎么来"必须说清楚，否则备份包丢了就等于整套 PKI 失传。
> 本文所有 subject / issuer / 有效期均为 `openssl x509 -noout` 实测，非推断。

---

## 一、先纠正一个容易犯的错

看到 `generate_rsa_keypair.sh`、`generate_jobGateway_tls_cert.sh` 两个脚本，很容易得出
"证书都是部署时本地随机生成的，丢了无所谓"的结论。

**这个结论是错的。** 实测证据：

| 观察 | 说明 |
|---|---|
| `gseca.crt` 有效期 `2019-02-25 → 2119-02-01` | 100 年，2019 年签发，**不是本次部署生成** |
| `job_ca.crt` 有效期 `2019-02-25 → 2119-02-01` | 同上，签发时间比本次部署早 7 年 |
| `gse_server.crt` 有效期 `2026-09-22 → 2076-09-09` | 本次部署签发，但仍由 2019 年的老 CA 签 |

**结论**：**CA 根证书是安装包预置的固定资产**，只有叶子证书（server/agent/client）是部署时用预置 CA 签发的。
这决定了——

- 丢了**叶子证书**：重跑生成脚本即可，因为 CA 还在。
- 丢了**CA 根证书 + CA 私钥**：整套信任链要重建，所有已签发叶子证书全部作废，agent 侧也要重新下发 CA。

⚠️ **关键缺口**：本次备份里 `gseca.crt` / `job_ca.crt` 只有**公钥证书，没有对应的 CA 私钥**
（目录里不存在 `gseca.key` / `job_ca.key`）。
即：**CA 私钥从未离开过部署机，本备份不具备"重新签发证书"的完整能力**，
只能复用现有 CA 公钥做验签。换环境复现时若需新建 CA，会得到一个**全新的信任域**，与旧 agent 不互信。

## 二、两个信任域

蓝鲸 7.2 CE 在此环境有**两套独立的 PKI**，互不信任，务必分清：

### 信任域 A：GSE（GSEROOTCA）

| 项 | 值 |
|---|---|
| CA 证书 | `gseca.crt` |
| subject / issuer | `C=CN, ST=GD, L=SZ, O=ieg, OU=bluking, CN=GSEROOTCA`（自签） |
| 有效期 | 2019-02-25 → 2119-02-01 |
| CA 私钥 | ❌ 不在备份中 |

签发的叶子证书（均为 `2026-09-22 07:02:42~43` 签发，2076-09-09 到期）：

| 证书 | CN | 配对私钥 | 用途 |
|---|---|---|---|
| `gse_server.crt` | `GSE_SERVER` | `gse_server.key` | GSE 服务端身份，agent/调用方验证服务端用 |
| `gse_agent.crt` | `GSE_AGENT` | `gse_agent.key` | Agent 身份证书，GSE 验证 agent 身份用 |
| `gse_api_client.crt` | `GSE_API_CLIENT` | `gse_api_client.key` | 调用 GSE API 的客户端身份（双向 TLS 的客户端侧） |
| `gse_esb_api_client.crt` | `GSE_ESB_API_CLIENT` | `gse_esb_api_client.key` | **ESB 组件**调用 GSE 时使用的专属客户端身份 |
| `license_cert.cert` | `license` | `license_prv.key` | 许可证服务身份 |
| `platform.cert` | `platform` | `platform.key` | 平台服务身份 |

### 信任域 B：JOB（JOBROOTCA）

| 项 | 值 |
|---|---|
| CA 证书 | `job_ca.crt` |
| subject / issuer | `C=CN, ST=GD, L=SZ, O=ieg, OU=bluking, CN=JOBROOTCA`（自签） |
| 有效期 | 2019-02-25 → 2119-02-01 |
| CA 私钥 | ❌ 不在备份中 |

签发的叶子证书：

| 证书 | CN | 配对私钥 | 用途 |
|---|---|---|---|
| `job_esb_api_client.crt` | `JOB_ESB_API_CLIENT` | `job_esb_api_client.key` | ESB 调用 JOB 的客户端身份 |
| `job_server.p12` / `job_server.keystore` | `bk-job-gateway` | 内嵌 | JOB 网关 HTTPS 服务端证书 + 私钥（PKCS12 / JKS 两种格式） |
| `job_server.truststore` | — | — | JOB 侧信任库，存放信任的 CA（JKS 格式） |

⚠️ **注意跨信任域**：`gse_esb_api_client.crt` 由 **GSEROOTCA** 签，`job_esb_api_client.crt` 由 **JOBROOTCA** 签。
ESB 去调 GSE 和去调 JOB，**用的是两张不同 CA 下的证书**，排障时极易混淆。

## 三、特殊文件（不是 X.509，别按证书理解）

| 文件 | 实测形态 | 说明 |
|---|---|---|
| `cert_encrypt.key` | 45 字节，base64：`QhEoq6k15fdWR/jpAbOvNlXI/Ol+erqRpZHjVy25Ww4=` | **32 字节对称密钥**，不是 RSA 私钥。用于加密配置项。<br>⚠️ **丢了它，用它加密的密文永久解不开**——这是本目录里唯一"丢了真会出事"的文件 |
| `gse_job_api_client.p12` | PKCS12 密钥库 | JOB API 客户端身份，给 GSE 侧调用 JOB 用 |
| `gse_job_api_client.keystore`<br>`gse_job_api_client.truststore` | JKS 格式 | 同上内容的 Java 密钥库形态 + 信任库 |
| `md5.txt` | 920 字节 | 19 个文件的 MD5 校验清单，用于校验备份完整性 |
| `job_server.truststore` | JKS，883 字节 | 与 `job_server.p12` 同批生成（09-22 15:03:23） |

**p12 / keystore 的密码**：由 `generate_jobGateway_tls_cert.sh` 用 `openssl rand -base64 32 | tr -dc '[:alnum:]' | head -c 24`
**随机生成并写进 values.yaml 的 base64**，**不单独落盘**。
所以这些密钥库文件本身不含密码，密码在 Helm values 里——**只拷文件不拷 values，等于拿到一把没钥匙的锁**。

## 四、文件时间戳透露的生成批次

```
09-22 14:37:18  ← 19 个文件（第一批：证书主体，openssl 批量签发）
09-22 15:03:23  ← 4 个文件（第二批：cert_encrypt.key + 3 个 JKS 密钥库）
```

第二批比第一批晚 26 分钟，说明**JKS 密钥库是在证书之后由 keytool 单独转换生成的**，
且 `cert_encrypt.key` 与它们同期——推测是配置加密环节。

## 五、换环境复现时会怎样

分三种情况，**结论不同**：

### 情况 1：全新部署（推荐，也是绝大多数场景）

从官方安装包走标准部署流程，安装包**自带 2019 年的 GSEROOTCA / JOBROOTCA**
（因为本次环境的这两个 CA 就是 2019 年的，说明是随包分发）。
部署脚本会：

1. 用包内 CA 签发新的叶子证书（新私钥、新 CN 相同但密钥不同）
2. 用 `generate_jobGateway_tls_cert.sh` 生成新的 job gateway p12/keystore + 随机密码
3. 生成新的 `cert_encrypt.key`

✅ **你把本目录全删了也能复现**，且功能完全正常。
❌ 但**agent 不与旧环境互信**（如果旧环境的 agent 还要连新 GSE，需重新下发 CA）。

### 情况 2：想"原样复刻"这套密钥

❌ **做不到**。缺 CA 私钥（`gseca.key` / `job_ca.key` 从未备份），无法签发同样信任链下的证书。

### 情况 3：只想恢复配置、不管密钥

✅ 可以。values.yaml 里引用证书的地方，用新生成的证书 base64 替换即可，
部署的 Helm chart 会正常渲染。**这是本文档建议的默认路径**。

## 六、应该保存什么、可以丢什么

| 类别 | 建议 | 理由 |
|---|---|---|
| 本文档（28 号） | ✅ 必存 | PKI 结构、信任域、复现路径，纯知识资产，无敏感信息 |
| `md5.txt` | ✅ 可存 | 仅校验和，无敏感信息，能验证备份完整性 |
| 叶子私钥与密钥库（14 个） | ❌ 不入库 | 换环境可重生成；入库则永久留历史。`git check-ignore` 已验证全部命中 |
| `cert_encrypt.key` | ⚠️ 单独另存 | 丢了密文解不开，是唯一"不可再生且不可恢复"的 |
| p12 / keystore 密码 | ⚠️ 单独另存 | 随机生成不落盘，只在 values.yaml 里 |
| CA 根证书公钥 | ✅ 可存 | 公钥非敏感，且是排障时判断信任链的依据 |

## 七、复现操作步骤

假设在全新环境从零部署：

```bash
# 1. 走官方标准部署流程（安装包自带 CA，会自动签发全套叶子证书）
#    无需手工准备 cert 目录

# 2. 若需单独重生成 JOB 网关证书（例如证书过期）
cd blueking/scripts
./generate_jobGateway_tls_cert.sh -f ../environments/default/bkjob-values.yaml.gotmpl
#    注意：不加 --force 时，若 values 里已有该 key 会报错退出（防覆盖保护）

# 3. 若需重生成 apigateway 网关 RSA keypair
./generate_rsa_keypair.sh ../environments/default/bkapigateway_builtin_keypair.yaml.gotmpl
#    注意：脚本会先读取已有配置复用，只有全新 system 才 openssl genrsa 2048

# 4. 校验新证书链（-CAfile 用对应的 CA）
openssl verify -CAfile gseca.crt  gse_server.crt
openssl verify -CAfile job_ca.crt job_esb_api_client.crt
```

**依赖**：`openssl`、`keytool`（JDK 提供）、`yq`（写 YAML 时必需）、`jq`（可选，仅 JSON 格式化）。

## 八、排障速查

| 现象 | 可能原因 | 查法 |
|---|---|---|
| agent 连不上 GSE | agent 侧 CA 与服务端证书不同域 | `openssl verify -CAfile gseca.crt gse_server.crt` |
| ESB 调 GSE 403 / 握手失败 | ESB 用的是 `gse_esb_api_client`，CA 是 GSEROOTCA，别拿 job_ca 去验 | 看证书 CN 前缀 |
| JOB 网关 HTTPS 起不来 | p12 密码与 values 里不一致（密码随机生成，容易漏同步） | 核对 values 的 `gatewayConfig.server.ssl.keystore.password` |
| 配置项解不开 | `cert_encrypt.key` 被换过 | 该文件必须与原加密时一致 |
| 想确认某证书归哪个 CA | 看 issuer 的 CN | `openssl x509 -in X.crt -noout -issuer` |

## 九、本文的证据边界

以下为**实测确认**：所有 subject / issuer / 有效期、文件字节数、`cert_encrypt.key` 的形态、两批时间戳、CA 私钥缺失。

以下为**合理推断，未实测验证**：
- CA 根证书"随安装包分发"——依据是 2019 年签发时间早于本次部署 7 年，但**未实际解压安装包确认**
  （安装目录 `/root/bk72` 在本次核查时已不存在）。
- `cert_encrypt.key` "用于加密配置项"——依据是其形态为对称密钥且文件名含 encrypt，**未找到消费它的代码位置**。
- 叶子证书由本地签发而非安装包预置——依据是 notBefore 为 `2026-09-22`（部署当天），但**生成它的具体脚本未定位到**
  （`generate_jobGateway_tls_cert.sh` 的 CA_CN 是 `JOBROOTCA` 且输出到 values base64，与 cert 目录的落盘形态不同，
  更可能是另一个未备份的脚本）。

若将来拿到安装包，应回补上述三项验证。
