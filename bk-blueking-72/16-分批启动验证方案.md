# 分批启动验证方案（Rollout-and-Prune）

> ⚠️ **本文档状态：历史快照（过时时点 2026-09-23）**
>
> 分批验证的**方案**文档。实际执行结果见各批报告与 [25-部署验收总报告](25-部署验收总报告-全8批合并.md)。
>
> **最新终态请看**：[25-部署验收总报告-全8批合并.md](25-部署验收总报告-全8批合并.md)（2026-09-24，实测）


> 提出时间：2026-09-24
> 思路来源：用户 —— "一次性全部启动不行，那就分批启动，启动一批删掉一批"
> 目标：在 43 GiB 内存上限内，**让每一个组件都至少成功启动过一次**，从而完整验证部署流程

---

## 一、为什么这个思路是对的（实测依据）

### 1.1 内存是硬约束

```text
blueking 全量 requests    34.04 GiB
WSL 可用                  43 GiB
结论：理论够，但无冗余，启动峰值必超限
```

### 1.2 探针踩踏是真正的杀手（本轮新发现）

全量启动时，组件不是"起不来"，是**启动慢于探针超时被误杀**：

```text
bk-kafka-0
  Liveness probe failed: dial tcp 192.168.109.132:9092: connection refused
  Container kafka failed liveness probe, will be restarted     ← 被杀
  但日志显示：Kafka 实际正在处理 bkmonitor transfer 的 consumer
             group rebalance，说明它在正常工作，只是还没开端口
```

`bkrepo-opdata` 同理：Spring `WebApplicationContext` 初始化耗时 **10.3 秒**，
未就绪即被探针判定失败。

**分批启动 → 每批组件独占内存与 CPU → 启动速度加快 → 探针不再误杀。**

### 1.3 已验证：内存充足后组件会自愈

`wsl --shutdown` 后内存从 42G → 1G，重启后：

| 组件 | 之前 | 现在 |
|---|---|---|
| `bkiam-search-engine-0` | CrashLoopBackOff | **1/1 Running** ✅ |
| `bkiam-search-engine-rbac-0` | CrashLoopBackOff | **1/1 Running** ✅ |
| 页面 | 部分 000 | **200 / 302 全通** ✅ |

**证明：这些组件没有配置问题，纯粹是资源问题。**

## 二、分批原则

### 原则 1：按依赖顺序（不是按字母、不是按大小）

```text
第0批 存储层   mysql / mongodb / redis / rabbitmq / zookeeper / etcd
第1批 基础服务  bkauth / bkiam / bkssm / bk-consul / apigateway
第2批 业务核心  cmdb / user / paas3 / nodeman / gse
第3批 监控     bk-monitor（数据面 → web → 告警）
第4批 制品库   bk-repo（13 个组件，内存大户）
第5批 日志     bk-log / applog
```

### 原则 2：每批启动后"确认成功"再进下一批

**确认标准（缺一不可）**：
1. Pod `READY = 期望副本数`
2. 无 CrashLoopBackOff
3. 页面/接口实测可达（该批有页面的话）
4. 记录证据（截图或 curl 结果）

### 原则 3：确认后即可裁掉，释放内存给下一批

**裁之前必须留证**：
- 组件名 + 版本
- 启动成功截图/curl 结果
- 关键日志片段
- 若有坑：坑的现象 + 解法

## 三、执行手册（可直接照抄）

### 3.1 前置：干净起点

```bash
# Windows PowerShell（需用户授权）
wsl.exe --shutdown

# 重启后
docker start k8s-c1-calico-control-plane k8s-c1-calico-worker k8s-c1-calico-worker2
sleep 100
kubectl get nodes   # 期望 3 个 Ready
```

### 3.2 单批启动模板

```bash
NS=blueking

# 1. 只启动本批（其余保持 0）
kubectl scale deploy -n $NS --replicas=1 <本批组件...>

# 2. 等待并观察
kubectl rollout status deploy -n $NS <组件名> --timeout=600s

# 3. 确认成功
kubectl get pods -n $NS -l app=<组件> --no-headers
curl -s -o /dev/null -w '%{http_code}' http://<域名>/   # 期望 200/302

# 4. 留证后裁掉
kubectl scale deploy -n $NS --replicas=0 <本批组件...>

# 5. 确认内存已释放
free -g
```

### 3.3 探针踩踏的应对（关键技巧）

若某组件反复被探针杀死，说明它启动慢于 `initialDelaySeconds`。
**分批后大多自愈**；若仍失败，临时放宽探针：

```bash
kubectl patch deploy -n $NS <组件> --type='json' -p='[
  {"op":"replace","path":"/spec/template/spec/containers/0/livenessProbe/initialDelaySeconds","value":180},
  {"op":"replace","path":"/spec/template/spec/containers/0/readinessProbe/initialDelaySeconds","value":180}
]'
```

⚠️ 这是**验证手段**，不是生产配置。留证后应还原。

## 五、批次清单（建议）

### 第 0 批：存储层（必须最先，且全程保留）

```text
bk-mysql8 / bk-mongodb / bk-redis-master / bk-redis-cluster
bk-rabbitmq / bk-zookeeper / bk-etcd / bk-elastic-elasticsearch
```
> **不裁**，后续批次都依赖它。

### 第 1 批：认证与网关

```text
bkauth / bkiam / bkiam-search-engine / bkiam-transfer / bkssm
bk-apigateway-* / bk-ingress-nginx
```

### 第 2 批：业务核心

```text
bk-cmdb-* / bk-user-* / bkpaas3-* / bk-nodeman-* / bk-gse-*
```

### 第 3 批：监控（本轮重点，因为有 kafka 依赖）

```text
先：bk-kafka（放探针，确认 9092 通）
再：bk-monitor-transfer / ingester / unify-query / api
再：bk-monitor-web / web-query-api / grafana
后：bk-monitor-alarm-*（26 个，验证完即裁）
```

### 第 4 批：制品库

```text
bk-repo-bkrepo-gateway → auth → generic → repository
→ docker / maven / npm / pypi / helm（同类，可任选 2-3 个验证）
→ job / replication / opdata
```
> **优化建议**：13 个组件按制品格式横向切分，**验证 3 个即可证明流程**，
> 不必全跑（docker + maven + helm 覆盖三种典型格式）。

### 第 5 批：日志

```text
bk-applog-* / bk-log-*
```
