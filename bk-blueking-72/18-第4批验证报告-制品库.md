## 二、opdata CrashLoopBackOff 解决

**上一批遗留问题**：`bk-repo-bkrepo-opdata` CrashLoopBackOff，
根因是 Spring 启动耗时 10.3 秒完成 WebApplicationContext，被探针误杀。

**本批做法（前置预防）**：起组件**之前**统一放宽探针，不是等它崩了再修。

```bash
for d in $(kubectl get deploy -n blueking -o name | grep bkrepo); do
  kubectl patch $d -n blueking --type='json' -p='[
    {"op":"replace","path":"/spec/template/spec/containers/0/livenessProbe/initialDelaySeconds","value":180},
    {"op":"replace","path":"/spec/template/spec/containers/0/livenessProbe/failureThreshold","value":12}
  ]'
done
```

结果：11 个组件有探针全部放宽（`generic` 无探针），
`opdata` 起后 60 秒内 0/1 → 再 90 秒后 **1/1 Ready**，未再崩溃。

⚠️ 同 kafka，这是**验证手段**，留证后应还原。

## 三、端到端验证：Docker Registry v2 协议

**决定性证据**（不是 Pod Ready，是真实协议响应）：

```http
GET /v2/  →  HTTP/1.1 401 Unauthorized
Docker-Distribution-Api-Version: registry/2.0
WWW-Authenticate: Bearer realm="http://bkrepo.paas.example.com/docker/v2/auth",
                  service="bkrepo", scope="repository:*/*/tb:push,pull"
```

三个要素全部正确：
1. `Docker-Distribution-Api-Version: registry/2.0` —— 协议版本头合规
2. `WWW-Authenticate: Bearer` —— 标准 Bearer 挑战
3. `realm` 指向 bkrepo 自己的 auth 端点，`service=bkrepo`

**`docker push` 正是靠这个 401 + WWW-Authenticate 触发认证流程的。**
这证明 Docker 制品库不是"能 ping 通"，而是**协议实现正确**。

### 其他服务响应

```text
auth        → 401 {"code":401,"message":"Authorization value [empty auth header]
                   is not a valid scheme."}      ← 鉴权在工作
repository  → 404 {"code":250129,"message":"Request url[...] not found","traceId":"..."}
                                                  ← 路由存在，路径未猜中
generic     → 404 同上（根路径未定义，需具体仓库路径）
maven/pypi  → 404 同上
gateway:8081 → 302 Location: http://bkrepo.paas.example.com/ui/   ← UI 入口
gateway:8080 → 502 （nginx 默认 server 无 upstream，非故障）
```

**关键辨析**：404/401 在此处**全部是服务正常工作的证据**，不是故障：
- `000` = 连接失败（服务没起）
- `404` = 路由通了、路径不存在
- `401` = 服务在跑、拒绝了无凭据请求

## 四、验证手法的一次自我纠错

第一次验证用了 `wget ... | head -3; echo "exit=$?"`，
输出一串 `exit=0` 看似通过 —— **但 `exit=$?` 取的是 `head` 的退出码，不是 wget 的**，
这是典型的假阳性。

**纠正**：改用独立 curl Pod 做真实 HTTP 调用：

```bash
kubectl run curltest --rm -i --restart=Never --image=curlimages/curl:8.5.0 -n blueking -- \
  curl -s -w '\nHTTP=%{http_code}\n' --max-time 12 'http://目标服务/路径'
```

这拿到了真实状态码和响应体，才发现了 401/404 背后
"服务其实在工作"的真相。**教训：验证工具的退出码要确认取的是谁。**

## 六、本批沉淀

1. **预防优于修复**：知道某组件会慢启动，就在起它之前放宽探针，
   而不是等 CrashLoop 再救。第 3 批 kafka 是"救"，第 4 批 opdata 是"防"。
2. **401/404 不等于故障**：必须看响应体。结构化 JSON + traceId、
   Docker v2 协议头，都是"服务健康"的强证据，比 200 更有说服力。
3. **验证工具的退出码要溯源**：`echo $?` 前面接了管道时，
   取到的是最后一个命令的退出码。
4. **制品库可以按格式裁剪**：docker/maven/helm/npm/pypi 是同类服务
   按格式横向切分，验证 2-3 个典型格式即可证明部署正确。
