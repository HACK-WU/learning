## 二、意外发现：日志链路其实早就在工作

起 logstash **之前**查 ES，发现已经有真实数据：

```text
bk_paas3_ingress_grokfailure-2026.09.24    docs=103       ← 今天
bk_paas3_ingress_grokfailure-2026.09.23    docs=25,731    ← 昨天
.monitoring-beats-7-2026.09.24             docs=4,425
```

**filebeat 一直在采集 ingress 日志并直写 ES**，即使 logstash 副本为 0。
原因是 filebeat 的 output 配置直连 ES，logstash 只是旁路管道之一。

这修正了一个可能的误判：**组件副本为 0 ≠ 链路不通**。
判断链路要看数据，不能只看 Pod 数量。

### ES 状态 yellow 的辨析

```json
"status" : "yellow",
"number_of_nodes" : 3,
"number_of_data_nodes" : 1,
"unassigned_shards" : 31
```

yellow 是**单数据节点放不下副本分片**导致的，是单机部署的必然结果，
**不是故障**。主分片 36 个全部 active，数据可读写。

## 三、ES 凭据的获取路径

ES 开了 X-Pack 安全认证，匿名请求返回：

```json
{"error":{"type":"security_exception",
 "reason":"missing authentication credentials for REST request",
 "header":{"WWW-Authenticate":"Basic realm=\"security\" charset=\"UTF-8\""}},
 "status":401}
```

**凭据不在 Helm 标准命名 `*-es-elastic-user` 里**，而是在：

```bash
kubectl get secret -n blueking bk-elastic-elasticsearch \
  -o jsonpath='{.data.elasticsearch-password}' | base64 -d
```

（key 是 `elasticsearch-password`，不是 `elastic`）

**排查手法**：不要猜 secret 名字，直接列所有含关键字的 secret 及其 keys：

```bash
kubectl get secret -n blueking -o json | python3 -c "
import json,sys
d=json.load(sys.stdin)
for it in d.get('items',[]):
    n=it['metadata']['name']
    if 'elast' in n.lower():
        print(n,'keys=',list(it.get('data',{}).keys()))
"
```

## 四、端到端验证：真实追踪一条日志

**做法**：打一个带唯一标记的字符串，追它在 ES 里出现。

```bash
MARK="BATCH5-E2E-$(date +%s)"
kubectl exec -n blueking bk-applog-bkapp-logstash-0 -- \
  sh -c "echo '[$MARK] batch5 e2e test' > /proc/1/fd/1"
sleep 60
# 在 ES 全索引搜这个标记
curl -u elastic:$EP "http://ES:9200/_search?q=$MARK&pretty"
```

**结果**：

```json
"total" : { "value" : 1 },
"_index" : "bk_paas3_app-2026.09.24"
```

**唯一命中 1 条，落在今天的 app 日志索引里。**

完整链路确认：

```text
容器 stdout
  → filebeat-stdout 采集
  → logstash 管道（stdout pipeline）处理
  → 写入 ES 索引 bk_paas3_app-2026.09.24
```

验证后该索引文档数 2,171（验证前 2,143，新增了真实业务日志）。

### logstash 健康佐证

```text
logstash API (9600)  -> HTTP 200
pipelines API        -> 返回 3 个管道（stdout / json / ingress）
日志尾部             -> 只有 ecs_compatibility deprecation WARN，无 ERROR
```

## 五、logstash 为何没有被探针杀

前几批 kafka、opdata 都是被 liveness 探针误杀。
这次检查发现 logstash **出厂配置就合理**：

```json
"livenessProbe":  { "initialDelaySeconds": 300, "failureThreshold": 3 },
"readinessProbe": { "initialDelaySeconds": 60,  "successThreshold": 3 }
```

`initialDelaySeconds: 300` —— 给 JVM 留了 5 分钟。

**这反证了前几批的修改方向是对的**：慢启动组件本来就该配长延迟，
蓝鲸自己的 logstash 就是这么配的，只是 kafka/opdata 的默认值太激进。

⚠️ 因此**本批不需要还原任何探针**（未修改）。

## 七、本批沉淀

1. **副本为 0 不等于链路不通**：filebeat 直连 ES，logstash 为 0 时日志照常入库。
   判断链路状态必须查数据（索引文档数），不能只数 Pod。
2. **yellow 不等于故障**：单数据节点场景下副本分片必然无法分配，
   只要主分片 active 就可用。要看 `unassigned_shards` 的成因再下结论。
3. **凭据获取不要靠猜**：列出 secret 的 keys 再取值，
   比试各种 Helm 命名惯例快且可靠。
4. **唯一标记法是验证数据链路的最强证据**：比看 Pod Ready 强得多，
   它证明的是"数据真的走完了全程"，而不是"进程活着"。
5. **长 initialDelay 是慢启动组件的正解**：logstash 出厂 300s 从未被误杀，
   说明不是"蓝鲸配得不好"，是 kafka/opdata 那几个默认值激进（40s/10s）。
