### 3.2 术语澄清：bk_monitorv3 不是 chart 名

**`bk_monitorv3` 是 SaaS 应用代号**（桌面图标、应用 ID 用它），**不是 helm chart 名**。

真正的 chart 与 release 名是：

```text
chart:  blueking/bk-monitor
release: bk-monitor
```

官方 `04-bkmonitor.yaml.gotmpl` 写的就是 `chart: blueking/bk-monitor`。

> 此前"helm repo 里的 bk-monitor 3.8.27 与 bk_monitorv3 不是同一套"是**错的**。
> 它们是同一套：bk-monitor 是后台 chart，bk_monitorv3 是它在桌面上暴露的应用名。
> 添加桌面图标的命令用的正是 `-a "bk_monitorv3"`。

### 3.2 另一个易混淆点：bkauth 与 bk_auth

集群已装 `bk-auth`，**官方目录里没有 `bkauth` 这个目录名**（是 `bk_apigateway` 等的支撑件，
实际已随其他模块装入）。不要因为"目录里没有"就判定缺失。

## 五、坑：helm status 是 failed，但组件其实在跑

盘点时发现一个重要现象，容易误判：

```text
bk-cmdb      STATUS=failed    ← helm 说失败
bk-cmdb-*    1/1 Running      ← 实际全在跑
```

**23 个 release 中有 12 个标 `failed`，但 133 个 Pod 异常为 0。**

**原因**：helm 的 `failed` 是**最后一次 helm 操作的退出状态**（多为安装时 Job 超时），
不代表当前运行时状态。这批 release 是此前排障时通过直接修 Pod/Job 恢复的，helm 状态未同步。

> **判断组件是否可用，看 Pod 状态，不要看 helm status。**
> 此点与 09-排障速查手册的"Job Failed 别全盘否定，要逐容器查 exitCode"同源。
