## 五、两次测量方法错误（本批最重要的教训）

### 5.1 `kubectl logs deploy/xxx` 匹配错 Pod

第一次查日志，**24 个组件全部返回空**。差点判成"组件没工作"。

排查发现：

```text
$ kubectl logs -n blueking deploy/bk-monitor-alarm-beat
Found 31 pods, using pod/bk-monitor-prom-agg-gateway-5d54655f8d-2d7bj  ← 抓错了！
```

`ps aux` 一看，容器内进程是 `prom-aggregation-gateway`，根本不是 beat。

**原因**：`deploy/xxx` 语法在有多 Pod 匹配时会挑一个，名字相近的会被误选。

**修正**：用精确 Pod 名或标签选择器

```bash
pod=$(kubectl get pod -n $NS --no-headers | grep "^$app-" | head -1 | awk '{print $1}')
kubectl logs -n $NS $pod --tail=25
```

修正后 8 个组件日志全部拿到，且证明它们都在正常工作。

**这印证了既有铁律：数字异常时先怀疑测量方法，再怀疑被测对象。**

## 六、401 也是健康信号（第三次遇到）

推送测试指标给 transfer：

```text
push EXC: HTTP Error 401: Unauthorized
```

**这不是失败，是鉴权生效。** transfer 需要 data_id 令牌才接收数据。

同类证据在三批里都出现过：

| 批次 | 响应 | 含义 |
|---|---|---|
| 第 4 批 | Docker Registry `401 + WWW-Authenticate` | 协议实现正确 |
| 第 6 批 | nodeman `3800018 Only from ESB/APIGW` | 网关鉴权生效 |
| 第 7 批 | transfer `401 Unauthorized` | 数据入口鉴权生效 |

**规律：看到非 200，先问"这个响应在协议里意味着什么"，别急着判故障。**

要真正推数据需要配置 data_id 令牌，那属于配置范畴，不是验证范畴 ——
验证的目标是"证明链路通"，401 已经证明了入口健康。

## 八、本批沉淀

1. **"Pod Ready" ≠ "链路验证成功"** —— 第 3 批把两者混为一谈，

   起之前先查探针，这条在第 6、7 批都验证了。

5. **日志里的数字要去 DB 对齐** —— `0/12` 里的 12 查库确认是真有 12 个策略，
   且都 enabled。发布的 0 是"无数据流入"，不是"策略没配"。
