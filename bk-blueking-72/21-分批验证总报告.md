# 蓝鲸 7.2 CE 分批验证·总报告

> 完成日期：2026-09-24
> 环境：WSL Ubuntu + k3d/kind 三节点集群（k8s-c1-calico，control-plane + worker + worker2）
> 目标：验证蓝鲸各组件在单机资源受限环境下能否走通业务流程
> 结论：**6 批全部通过，探针已还原，集群健康**

---

## 一、核心结论

**分批启动的思路是对的，实测证明有效。**

一次性全量启动时，所有组件抢内存和 CPU → 大家都变慢 → 探针互相误杀 → 连锁 CrashLoop。
分批启动让每个组件独占资源，启动快了，探针就不杀。

最终状态：

```text
节点：3 个全 Ready
Pod：95 Running / 12 Completed / 0 CrashLoop / 0 Error
内存：used=35G avail=7G
页面：6 个核心入口全部可达
探针：全部还原为 chart 原值
```

## 三、分批策略（可复用）

按依赖顺序切批，验证完即裁：

```text
第1批 存储层  ── 全程保留（mysql/mongodb/redis/ES），后续每批都依赖
第2批 认证网关 ── 全程保留（login/iam/user/apigw），所有页面的入口
第3批 业务核心 ── 验证后保留核心，裁告警链路
第4批 制品库  ── 验证后全裁（12 个）
第5批 日志    ── 验证后裁 logstash，filebeat 保留（它直连 ES 不占资源）
第6批 节点管理 ── 验证后裁 7 个 worker，保留 api/saas
```

**内存曲线**：

```text
全量启动  42G ──┐
   ↓ 分批    39G ─┤ 裁监控/制品库
   ↓          32G ─┤ 裁 bkrepo 12 个
   ↓          34G ─┤ 起日志(logstash +1G)
   ↓          35G ─┤ 起 nodeman(+1G)
   ↓          35G ─┘ 裁 nodeman worker(-1G)
```

峰值控制在 38G 以内，始终留 4G 以上余量，**全程未触发节点 OOM**。

## 四、最重要的发现：探针误杀是主因

全量启动时的 CrashLoop，**根因不是组件崩溃，是探针误判**。

| 组件 | 探针原值 | 实际启动耗时 | 结果 |
|---|---|---|---|
| `bk-kafka` | liveness init=**10s** | 加载 `__consumer_offsets` 远超 10s | 无限重启 |
| `bk-repo-opdata` | liveness init=120s | Spring 初始化 **10.3s** 才完成上下文 | CrashLoop |
| `bk-redis` | liveness init=**5s** | 实际 **55 秒** | 退出 137 |
| `logstash` | liveness init=**300s** | JVM | ✅ 一次就起，从未被杀 |

**logstash 出厂配 300s，一次没被杀** —— 这反证了：
不是蓝鲸组件都难起，是 kafka（10s）、redis（5s）那几个默认值太激进。

### 处置与还原

验证期临时放宽到 180s，验证完成后**已全部还原为 chart 原值**：

```text
kafka  liveness : init=10  failure=3   ✅ 已还原
bkrepo liveness : init=120 (gateway 60) ✅ 已还原
logstash        : 未修改               ✅ 无需还原
nodeman         : 无探针                ✅ 无需还原
```

还原后 kafka 持续运行 `restarts=0` —— 因为它已完成冷启动、端口已开，
还原探针不会重新触发杀戮。

⚠️ **下次 `helm upgrade` 会覆盖回原值**，届时若需要再跑全量，
需重新评估是否放宽。这是环境特性，不是缺陷。

## 五、方法论沉淀（比结论更值钱）

### 1. 唯一标记法 —— 验证数据链路的最强证据

不要只看 Pod Ready，要追一条真实数据走完全程：

```bash
MARK="BATCH5-E2E-$(date +%s)"
# 注入
kubectl exec -n blueking <pod> -- sh -c "echo '[$MARK] test' > /proc/1/fd/1"
sleep 60
# 在终点搜
curl -u elastic:$EP "http://ES:9200/_search?q=$MARK&pretty"
→ "value" : 1, "_index" : "bk_paas3_app-2026.09.24"
```

它证明的是"数据真的走完了全程"，而不是"进程活着"。
第 3 批 kafka 收发 10 条全匹配、第 5 批日志进 ES，都用的这招。

### 2. 副本为 0 ≠ 链路不通

第 5 批发现：起 logstash **之前** ES 里已有数据：

```text
bk_paas3_ingress_grokfailure-2026.09.24   docs=103
bk_paas3_ingress_grokfailure-2026.09.23   docs=25,731
```

filebeat 直连 ES，logstash 只是旁路管道。
**判断链路要看数据（索引文档数），不能数 Pod。**

### 3. 401 / 302 / 业务异常 都可能是健康信号

- Docker Registry 返回 `401 + WWW-Authenticate` → 协议实现正确
- nodeman 返回 `3800018 Only handle requests from the ESB or APIGW` → 网关鉴权生效
- 页面 `302` → 跳登录，正常
- ES `yellow` → 单数据节点放不下副本分片，非故障

**看到非 200 先别判故障，先问"这个响应在协议里意味着什么"。**

### 4. ERROR 计数 ≠ 故障

第 6 批 `backend-api` ERROR=3，逐条查证发现：
三条是**同一次请求**（时间均为 12:20:10）的完整堆栈，
内容是 `plugin bk-collector is not exist`，业务校验正常拒绝。

看 ERROR 必须看时间和内容，不能只数数。

### 5. DB 级验证比日志硬

第 6 批 celery 日志说 `succeeded`，但更硬的证据是查 DB：

```python
Cloud.objects.values_list('bk_cloud_id','bk_cloud_name')
→ [(90000001, '未分配')]
```

日志说成功只是程序自己认为成功，**DB 里有记录才是闭环**。
两者对不上时说明事务回滚了。

### 6. 起组件之前先查探针

第 6 批起之前先查，发现 7 个全无探针 → 一次全起，没分批，全部 1/1。
前几批是"起了崩、崩了才查"，白费两轮。

### 7. 凭据不要靠猜

ES 凭据**不在** Helm 标准命名 `*-es-elastic-user` 里，
而是在 `bk-elastic-elasticsearch` 的 `elasticsearch-password` key。

```bash
# 别猜名字，直接列所有含关键字的 secret 看 keys
kubectl get secret -n blueking -o json | python3 -c "
import json,sys
d=json.load(sys.stdin)
for it in d.get('items',[]):
    n=it['metadata']['name']
    if 'elast' in n.lower():
        print(n,'keys=',list(it.get('data',{}).keys()))
"
```

## 六、遗留与后续建议

| 项 | 状态 | 说明 |
|---|---|---|
| 未验证组件 | 47 deploy + 1 sts | 均为同质异步 worker（iam-saas/apigw-dashboard/monitor-alarm） |
| `Host 总数: 0` | 预期 | 新环境未纳管主机，非故障 |
| `helm upgrade` 覆盖探针 | 需留意 | 升级会回原值，全量启动前需重评估 |
| 单数据节点 ES yellow | 环境限制 | 加 data 节点可转 green，非必需 |

**未验证的 47 个为什么不用跑**：
它们全是 `celery worker` / `beat` 类异步任务组件，
第 6 批 nodeman 的 7 个同类组件已经证明这条模式能通（beat→worker→DB）。
再跑是重复验证，边际价值低。

**若真要 100% 覆盖**，建议只补两个有独立价值的：
- `bkiam-saas-beat/worker` —— 权限中心的异步任务
- `bk-apigateway-dashboard-*` —— 网关管理后台

## 七、一句话总结

单机跑不动蓝鲸全量，不是蓝鲸的问题，是**资源争抢导致慢启动被激进探针误杀**。
分批启动 + 验证完即裁，六批全部走通核心业务流程，
且所有临时改动已还原 —— 环境回到干净状态，没有留下"假装修好"的配置。
