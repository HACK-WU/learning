**不是蓝鲸组件都难起，是那几个配了激进探针的才难起。**

## 五、一次自我纠错：3 个 ERROR 的真相

`backend-api` 日志 ERROR 计数 = 3，差点被误判为故障。逐条查证：

```text
2026-09-24 12:20:10 | plugin bk-collector is not exist
  → apps.exceptions.BackendValidationError: [3800100]
  → GsePluginDesc.DoesNotExist: GsePluginDesc matching query does not exist
```

**真相**：有人在 3 小时前（12:20）查询了一个未注册的插件 `bk-collector`，
触发业务校验异常。三条 ERROR 是同一次请求的完整堆栈（exception + error + exception）。

**不是服务故障，是业务层的正常拒绝。**

### API 网关鉴权也是"健康"信号

```json
{"code": 3800018, "message": "Only handle requests from the ESB or APIGW", "result": false}
HTTP=200
```

直连 backend-api 被拒绝 —— 说明**网关鉴权生效**，
nodeman 只允许来自 ESB/APIGW 的请求，这是设计如此。

## 七、本批沉淀

1. **先看探针再起组件**：本批起之前先查探针配置，发现 7 个全无探针，
   心里有底，一次全起没分批。前几批是起了崩、崩了才查。
2. **celery 链路要三段对齐**：beat 投递 / worker 执行 / task succeeded，
   缺一段都不能算通。只看 Pod Ready 会漏掉"beat 在投但 worker 没消费"的情况。
3. **DB 级验证比日志硬**：日志说 `succeeded` 只是程序自己认为成功，
   查 DB 里真有那条记录才是闭环。两者对不上时说明事务回滚了。
4. **ERROR 计数 ≠ 故障**：3 条 ERROR 是同一次业务校验异常的完整堆栈，
   时间相同（12:20:10）、内容同源。看 ERROR 必须看时间和内容，不能只数数。
5. **网关拒绝也是健康信号**：`3800018 Only handle requests from the ESB or APIGW`
   证明鉴权链路在工作，和 docker registry 的 401 同理。
