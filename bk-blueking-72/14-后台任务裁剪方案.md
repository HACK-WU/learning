## 一、分类方法与实测结果

### 1.1 判定依据：有没有 Service

用 Service 的 selector 反查 deploy —— **有 Service 说明提供 HTTP 或被访问（影响页面），
没有 Service 说明是纯后台消费者**。

实测结果：

```text
总 deploy:              109
有 Service（前台）:      70   ← 保留
无 Service（纯后台）:     39   ← 可关候选
```

### 1.2 诚实标注：一个分类误差

`bk-user-api-worker` / `bk-user-api-beat` 被判为"有 Service"，
是因为它们与 `bk-user-api-web` **共享同一组 label**，Service `bkuserapi-web` 的 selector 粒度粗，
把它们一起选中了。**它们实际是后台任务，不是被 HTTP 访问的。**

同理 `bkiam-worker`、`bkpaas3-apiserver-worker` 也是这个情况。

> 所以"有 Service"是**保守判定**，实际可关的比 39 更多。
> 本文档按保守口径走，避免误关。

## 三、三档裁剪建议

### 方案 A · 保守（只关明确无害的）

关闭 `bk-nodeman` 的 4 个 sync + bkiam-saas 2 个 + apigw 2 个 + monstache
**省约 1.2 GiB**，功能影响最小。

### 方案 B · 推荐（关全部 39 个后台任务）

**省 8.20 GiB**，页面全部可访问，只是后台任务（告警动作、主机同步、celery 定时任务）不跑。

> 对"探索搭建步骤与排错"的目标，这个档位最合适 ——
> 前台全在，能看能点；后台不跑，省内存。

### 方案 C · 激进（B + 停 bk-repo 13 个组件）

额外再省一轮，但制品库功能会缺失。**暂不推荐**，除非内存仍然吃紧。

## 四、执行方式（两种方式，都需备份先行）

### 4.1 快速版：kubectl scale（可逆，但不持久）

```bash
kubectl scale deploy -n blueking --replicas=0 <deploy-name>
```

恢复：

```bash
kubectl scale deploy -n blueking --replicas=1 <deploy-name>
```

> ⚠️ 缺点：helm 配置里仍是 1，下次 `helmfile sync` 会被拉回来。
> 适合临时试验。

### 4.2 持久版：改 helmfile（配置=状态一致）

在对应 `values.yaml.gotmpl` 里把 worker 的 `replicaCount` 改为 0，
或在 helmfile 的 release 上加 `installed: false`。

> 改前必须备份（已完成，见 [13-配置备份与离线复现档案.md](13-配置备份与离线复现档案.md)）。
> ⚠️ 注意 5.1 坑：helm 状态不一致时跑 sync 有风险。

## 五、风险提示

1. **关掉 alarm-detect / alarm-trigger 后，监控页面仍可看历史数据，但不再产生新告警。**
   这是"保留监控、关后台"的必然代价，符合你的取舍。
2. **`bk-cmdb-monstache` 关掉后，CMDB 数据不再同步到 ES**，CMDB 的全文检索会失效/数据陈旧。
   若你常用 CMDB 搜索，把它留在保留名单。
3. **worker 关掉后，依赖 celery 的异步操作会静默堆积**（不报错，但不执行）。
   排错时若发现"点了没反应"，先查 worker 是不是被关了。
