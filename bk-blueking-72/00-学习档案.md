## 一、为什么要先扩容 WSL 内存

### 1.1 发现的问题

首次环境勘察结果：

| 项 | 数值 | Lite 要求 | 结论 |
|---|---|---|---|
| WSL 总内存 | 31 Gi | — | — |
| **可用内存** | **7.3 Gi** | ≥ 8 GB（基础版） | ❌ 不达标 |
| Swap | 8 GB 且**已用满** | — | ⚠️ 已在换页 |
| CPU | 20 核 | 4 核 | ✅ |
| 磁盘 | 722 G 可用 | 20 GB | ✅ |
| Docker | 29.4.1 | ≥ 20.10.23 | ✅ |

### 1.2 根因：WSL2 默认只给宿主机一半内存

WSL2 的默认规则是**最多取宿主机物理内存的 50%**。本机 64 GB，所以 WSL 只拿到 32 GB。

这不是配置错误，是微软的默认值。官方文档 `memory` 项明确写着：默认值为 Windows 总内存的 50%。

### 1.3 更麻烦的是：容器把内存吃光了

即便扩了容，如果 WSL 里跑着一堆容器，可用内存依然紧张。勘察时发现：

- 运行中容器 **119 个**
- 来源：Kafka 3 节点、kind K8s 集群 4 个、Doris、Thanos + Mimir、几十个 Prometheus/Grafana
- 全部是历史课程遗留

所以策略是**扩容 + 清理双管齐下**。

## 二、扩容操作

### 2.1 配置文件

路径：`C:\Users\<用户名>\.wslconfig`（原本不存在，属新建）

```ini
[wsl2]
memory=48GB
swap=8GB
localhostForwarding=true

[experimental]
autoMemoryReclaim=gradual
```

参数说明：

- `memory=48GB`：64 GB 机器给 Windows 留 16 GB
- `swap=8GB`：交换空间
- `localhostForwarding=true`：WSL 端口转发到宿主机 localhost
- `autoMemoryReclaim=gradual`：让 Linux 页缓存缓慢归还 Windows，缓解 Vmmem 只涨不落

`processors` 保持默认（WSL 空闲时会让出 CPU，Lite 只要 4 核）。

### 2.2 生效方式

**必须 `wsl --shutdown`**，配置仅在 VM 完整重启后生效：

```powershell
wsl --shutdown
```

### 2.3 效果

| 项 | 扩容前 | 扩容后 |
|---|---|---|
| 总内存 | 31 Gi | **47 Gi** |
| 可用内存 | 7.3 Gi | **40 Gi** |
| Swap 占用 | 8 GB 用满 | **0** |
| 运行中容器 | 119 | 7 |

## 三、踩坑：`灾难性故障 Wsl/Service/E_UNEXPECTED`

### 3.1 现象

写完 `.wslconfig` 后执行 `wsl`，报：

```
灾难性故障
错误代码: Wsl/Service/E_UNEXPECTED
```

### 3.2 排查（先核验，不瞎猜）

第一反应是"配置写坏了"，于是核验文件字节内容：

```
5B 77 73 6C 32 5D 0D 0A 6D 65 6D 6F 72 79 3D 34
```

解析：`5B 77 73 6C 32 5D` = `[wsl2]`，**无 UTF-8 BOM**，纯 ASCII，102 字节。

结论：**文件没坏**，不是我写错了。

继续查：

- 磁盘：C 盘 510 GB 可用，D 盘 2724 GB 可用 → 不是磁盘满
- WSLService 状态：Running → 服务没挂
- WSL 版本：2.6.3.0，正常

### 3.3 真实原因与解法

这是 **WSL 在切换 VM 内存规格时的瞬时故障**。

解法：

```powershell
wsl --shutdown
```

之后重启即自愈，无需修复配置文件。

**教训**：遇到这类报错，先核验文件本身（BOM / 编码 / 语法），再查环境（磁盘 / 服务 / 版本），别急着改配置。凭直觉改，可能把对的改坏。

## 四、端口冲突与规避

### 4.1 冲突情况

Lite 用 Traefik 做网关，默认要 80/443。探测发现：

| 端口 | 状态 | 占用者 |
|---|---|---|
| 80 | OCCUPIED | `k8s-c1-calico-control-plane` 容器 |
| 443 | OCCUPIED | `k8s-c1-calico-control-plane` 容器 |
| 6379 | OCCUPIED | 宿主机 redis-server |
| 8080 | free | — |

### 4.2 解法：用环境变量改端口

`bootstrap.sh` 里：

```bash
readonly DEFAULT_PORT=443
```

但支持环境变量覆盖（第 646 行非交互分支会读取）：

```bash
export HOST_IP=<本机IP>
export TRAEFIK_WEB_PORT=8080
```

注意：脚本**没有 `--port` 命令行参数**，只能通过环境变量设置。命令行参数只有 `--opspilot` / `--mlops` / `--mlflow` / `--vllm` 等。

这样既避开 80/443 冲突，又不用动已有的 K8s 集群。

## 五、安装脚本的真实形态

### 5.1 一行命令背后是什么

官方安装命令：

```bash
curl -sSL https://bklite.ai/install.run | bash -
```

下载到的 `install.run` 只有 **86 行**，它不是完整安装脚本，而是个**自解压包**：

```bash
INSTALL_PATH=/opt/bk-lite

export PAYLOAD=$(
cat <<EOF
H4sIAAAAAAAAA+y9e1tT17Ywfv7Op5iNdCPsJgG8tJtdel7EaDlF4AC2u8e6YyBLzDYkaRK0FnkftIKg3KwXVPBaEKsVsBdFLvo870c5zUrCX/0KvzHmmHOtuSJ2Op+f+d5N2cfm7XWvI455phjjD
EOF
)

unpack_payload() {
  local out_dir="${1:-$INSTALL_PATH}"
  mkdir -p "$out_dir"
  echo $PAYLOAD | base64 -d | tar -xzf - -C "$out_dir"
}

install() {
    cd "$INSTALL_PATH"
    bash bootstrap.sh "$@"
}
```

流程：base64 解码 → tar 解压到 `/opt/bk-lite` → 执行 `bootstrap.sh`。

前置检查命令：`tar base64 awk docker openssl`。

### 5.2 解压后内容

```
Readme.md
bin/
bootstrap.sh      ← 2911 行
compose/          ← infra/server/monitor/log/postgres/web/mlflow/vllm
conf/
```

**技巧**：可以只解压不安装，便于审计源码：

```bash
mkdir -p /tmp/bklite-src
sed -n '41p' install.run | base64 -d | tar -xzf - -C /tmp/bklite-src
```

## 六、核心踩坑：镜像拉取被重置

### 6.1 现象

首次安装 76 秒后失败：

```
failed to copy: read tcp 172.26.238.136:43108->180.111.196.17:443: read: connection reset by peer
```

### 6.2 定位过程

**第一步**：确认目标 IP 是谁

`180.111.196.17` 不是 Docker Hub 的地址段。查 bootstrap.sh 第 14 行：

```bash
readonly DEFAULT_REGISTRY_BASE="bk-lite.tencentcloudcr.com/bklite"
```

→ 是**腾讯云 TCR（容器镜像服务）**，Lite 默认镜像源。

**第二步**：确认是不是网络完全不通

- 域名可解析：`115.159.130.215`
- `/v2/` 接口返回 401（registry 正常响应）
- 实测已成功拉取 2 个镜像（14 MB、154 MB）

→ **网络能通，小流量没问题**

**第三步**：确认失败规律

日志里有 **115 次 `Download complete`**，但只有 2 个镜像落盘。说明：

> **所有 layer 都下载完了，但在最后组装（failed to copy）阶段被掐断**

**第四步**：确认并发是诱因

bootstrap.sh 第 2363 行用的是 `docker compose pull` —— **并发拉取 45 个镜像，且脚本内没有任何重试机制**，一个失败整体退出。

### 6.3 根因

持续大流量触发了网络中间设备（防火墙/代理）的限流或中断。

- 小镜像（14 MB、154 MB）→ 正常
- 大镜像、高并发 → 组装阶段被 reset
- 目标 IP 固定 `180.111.196.17:443`

### 6.4 解法：串行 + 重试

`docker compose pull` 并发太高且无重试，改为**逐个串行拉取，每个最多重试 3 次**：

```bash
while read -r img; do
  [ -z "$img" ] && continue
  for attempt in 1 2 3; do
    if timeout 300 docker pull "$img"; then
      echo "OK $img (第${attempt}次)"; break
    fi
  done
done < imglist.txt
```

脚本见 [prepull.sh](assets/prepull.sh)。

## 八、经验沉淀

1. **WSL 内存不是你想用多少就有多少**——默认只给宿主机 50%，跑容器前先扩容。
2. **`灾难性故障` 不等于配置文件坏了**——先核验字节内容（BOM/编码），再查磁盘与服务。
3. **安装脚本要审计再执行**——`install.run` 是自解压包，可只解压看源码。
4. **并发拉取大镜像容易被掐**——`docker compose pull` 无重试，改成串行 + 重试能救回大部分。
5. **"Download complete" 不等于镜像可用**——还要看组装阶段是否成功。
6. **端口冲突优先改自己的端口**——别轻易停掉别人的服务。

**两个真实陷阱（本课核心）**：

1. **8 个 release 全 `failed`，但不是失败** —— `timeout: 600s` 撞上镜像拉取 2 分钟/Pod × 11 个并发。helm 超时只是"不再等待"，K8s 继续起 Pod。判据要看 `kubectl get pods`，不看 `helm list`。

2. **退出码 137 不是 OOM** —— 容器无 limits、节点 39G 可用、无 OOM 事件，四条证据全否定。真凶是 livenessProbe（`initialDelaySeconds=5`），redis 55 秒没起来就被判死。K8s 事件原文 `failed liveness probe` 才是权威证据。

## C. 新增经验沉淀

7. **`release failed` 不等于部署失败** —— 先分辨是超时还是错误（`context deadline exceeded` vs `invalid/not found`）。
8. **退出码是结果不是原因** —— 137 至少两个来源（OOM / 探针 kill），靠事件原文区分。
9. **省事的选择往往是对的** —— 跳过官方 localpv 用集群现有 StorageClass，规避了 401 授权坑，PVC 100% Bound。
10. **先渲染算账再动手** —— 事前算出 3.06Gi，事后实测只用了 4%，避免盲目加资源。

## E. 阶段四：全栈联调排障（2026-09-23 已完成）

**起点**：128 Pod，20+ 异常。**终点**：**131 Pod，0 异常**。

### E.1 三层根因（主案例）

| 层 | 表象 | 根因 | 修法 |
|---|---|---|---|
| 1 | 5 个 `*-apigw-sync` Pod 报 nginx 404 | `bkapi.paas.example.com` 在 16 个 ingress 里无路由 | 补 Ingress → `bk-apigateway-bkapi:80` |
| 2 | 9 个 paas3 Pod 卡 `Init:0/1` | 同 Job 三容器中仅 `apiserver-bkrepo-init` exit=1 | 单独起探针拿真实报错 |
| 3 | `admin:blueking` 认证失败 | **`bkrepo.user` 集合 count=0**，用户从未创建 | 补跑官方 init-mongodb Job |

第三层是核心：试了 8 个密码全 401，查 mongodb 才发现**用户表是空的** —— 任何密码都会失败。

**为什么用户没创建**：chart 有 `templates/init-job/init-mongodb.yaml`（post-install hook，`before-hook-creation` 跑完即删），但实际 values 里 `config.init keys = ['bcs','entrance']`，**没有 mongodb**，该 Job 从未执行，现场无痕迹。

**修法**：不手工 INSERT，而是补跑官方 Job（镜像 `bkrepo-init:v3.3.1-beta.1`，内含 `init-data.js`）。结果 `user 0→5`、`role 0→12`、`admin:blueking → 200`、Job Complete、9 Pod 全释放。

> 5 个用户里只有 `admin`/`system` 是官方脚本建的（created 字段空），另外 3 个（`bkpaas3`/`bksaas-addons`/`bklesscode`）带时间戳，是业务组件后续自建。故 user 数从 2 涨到 5 可作为"整条链路已通"的就绪信号。

### E.2 新增经验沉淀

11. **认证失败先查"对象存不存在"，别查"凭据对不对"** —— 空表让所有密码都失败，试多少遍都白搭。
12. **Job Failed 别全盘否定** —— 逐容器查 exitCode，往往三容器里只有一个失败。
13. **Job 失败了要问"前置数据本该由谁创建"** —— helm hook + `before-hook-creation` 最容易静默失踪。
14. **修的时候补跑官方动作，不手工写数据** —— 手工写的密码哈希可能与官方不一致，升级就崩。
15. **helm release secret 是部署事实的唯一真相源** —— `sh.helm.release.v1.<rel>.v1`（gzip+双重 base64）记录**实际生效**的 values，比翻 values.yaml 可靠。
16. **nginx 404 ≠ 应用 404** —— 前者说明压根没路由，后者是应用返回的 API_NOT_FOUND，区分它们能省一半时间。
17. **改配置前先备份，且备份要能被文档引用** —— 备份放 WSL 内只能就地回滚，拉一份到工作区才能随项目走、写进文档。
18. **"有没有 Service"是区分前台/后台的可靠判据** —— 但要警惕共享 label 导致的误判，宁可保守。
19. **下载来源要写进文档，不能只写版本号** —— 有 repo URL + index.yaml + 本地 tgz 路径，离线也能复现部署流程。

### E.12 经验沉淀（第 20~26 条）

20. **"Pod Ready" ≠ "链路验证成功"** —— 前者是进程活着，后者是业务走通。第 3 批把两者混写，告警链路缺口藏了 3 批才发现。
21. **唯一标记法**是验证数据链路的最强证据 —— 注入带唯一字符串的数据，到终点侧检索它，证明"数据真走完全程"。
22. **副本为 0 ≠ 链路不通** —— filebeat 直连 ES，logstash 只是旁路管道。判断链路要看**索引文档数**，不能数 Pod。
23. **401 / 302 / 403 / 业务异常都可能是健康信号** —— Docker Registry 401、nodeman `3800018`、transfer 401 都是鉴权生效。**看到非 200 先问协议含义。**
24. **ERROR 计数 ≠ 故障** —— 第 6 批 ERROR=3 实为同一次请求的完整堆栈，业务校验正常拒绝。看 ERROR 要看**时间和内容**。
25. **DB 级验证比日志硬** —— 日志说成功只是程序自己认为成功，DB 里有记录才是闭环。第 7 批日志 `0/12` 与 DB `count=12` 吻合才是真证据。
26. **起组件之前先查探针** —— 前三批是"起了崩、崩了才查"白费两轮；第 6/7/8 批先查再起，41 个组件一次全起、0 CrashLoop。

**一句话总结**：八批走完，未验证组件归零、探针残留归零。真正的收获不是"蓝鲸能跑起来"，
而是三条纪律 —— **先核验测量方法再核验被测对象；修不好的不假装修好；改动时就要记全字段原值**。

**GSE 403 根因最终锁定**（2026-09-23，第三轮，闭环验证）：

**根因是 ESB 签名密钥与 GSE 校验密钥不是一对**（不是权限、不是服务未就绪）：

| 对象 | 公钥 md5 |
|---|---|
| ESB 签发用（`FunctionController.jwt::private_public_key`） | `0e82d670218b3380bcbc15d87625a81e` |
| `bk-esb` / `apigw` gateway | `0e82d670...`（**与 ESB 一致**） |
| `bk-gse` gateway = GSE 容器证书 | `0e18be8a0f385db7ba21c81b58fcc265`（**与 ESB 不同**） |

**闭环验证**（ESB 容器内实测，可复现）：用 ESB 私钥签（RS512）→ 用 ESB 公钥验 ✅ 通过；
用 GSE 公钥验 ❌ `InvalidSignatureError`。

**为什么只有 bk-gse 中招**：官方同步命令 `sync_esb_jwt_key_to_gateway` 只同步
`SYNC_ESB_JWT_KEY_GATEWAY_NAMES` 里列出的 gateway，而该设置**只有 `bk-esb` 和 `apigw`，
不含 `bk-gse`** —— 所以 bk-gse 保留了 `sync-builtin-gateway` 写入的自己那把。

**前两轮为什么查错**：一直在比对 apigateway 与 GSE（二者本来就一致），
忽略了**真正的签发方是 ESB**，而 ESB 的密钥存在它自己的表里，从未被纳入比对。

**修复方案**：A. 把 `bk-gse` 加入 `SYNC_ESB_JWT_KEY_GATEWAY_NAMES` 后重跑同步（推荐）；
B. 换 ESB 的密钥为 bk-gse 那对；C. 给 GSE 换证书。均需改集群状态，**未执行，待授权**。

详见 [09-排障速查手册.md](09-排障速查手册.md) 6.12（根因）与 6.11（四次误判纠错）。

### E.5 实战经验要点（详见 08）

**做对的 4 个决策**：

1. **复用集群现有 StorageClass**（`standard`，provisioner 实测为 `rancher.io/local-path`），不装官方 localpv → 14/14 PVC Bound，零授权问题。少一个组件就少一个失败点。
2. **先渲染算账再部署** —— 事前算出 3.06Gi，实测只占 4%，部署时才能分辨哪些异常是真问题。
3. **大镜像串行 + 重试 3 次** —— 16 个镜像救回 15 个，其中 postgres / pgvector 是第 2 次才成功。
4. **补跑官方 init Job，不手工 INSERT** —— 保证与官方基线逐字节一致。

**做错的 3 个地方**：

1. 一看到 137 就判 OOM（真凶是 `initialDelaySeconds=5` 的探针）—— 若直接加内存，问题不消失且排查方向彻底跑偏。
2. 试了 8 个密码才想到查 `user.count()`（实际为 0，任何密码都失败）。
3. 探针打印"成功"就信了（`--dry-run true` 在 argparse 里非空字符串即真，压根没调 API）。

> 后两条是同一个病根：**用"看起来对"替代"验证过对"**。解法是找独立的、不可伪造的证据源。

**环境硬事实**：WSL2 默认只给宿主机一半内存（必须 `wsl --shutdown` 才生效）；80/443 被 kind control-plane 占用（改自己端口，别停别人的服务）；大流量触发中间设备限流（`Download complete` ≠ 镜像可用）。
