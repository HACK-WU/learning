## 一、适用边界与反模式

> **"不该用"比"怎么用"更值钱。** 这是从"会用"到"用对"的分界线。

### 五个反模式（别在这些场景用 Doris）

| # | 反模式 | 实测证据 | 该用什么 |
|---|--------|---------|---------|
| 1 | 拿 Doris 当 KV 点查用 | 🟢 **5.7-6.6 ms/次，约 148-176 QPS**；Redis 0.1 ms，**差 50 倍**（课 12） | Redis |
| 2 | 拿 Doris 当 OLTP 用 | 🟢 **`ROLLBACK` 静默无效**——转账后 ROLLBACK，钱扣了账加了，什么都没撤，**且不报错**（课 12） | MySQL / PostgreSQL |
| 3 | 高频单行删改 | 🟢 Unique 表标记删除堆积，compaction 跟不上；MOW 落盘 14,659 行 vs MOR 物理行 29,104 行（课 3） | MySQL / PostgreSQL |
| 4 | 拿 Doris 当消息队列 / 流计算引擎 | ⚪ 无订阅语义、无 exactly-once 投递保证；Routine Load 是消费不是发布 | Kafka / Flink |
| 5 | 滥用大宽表 | 🟢 列数翻 13 倍、耗时从 0.13 s 涨到 0.51 s（**4 倍**）；且让 Schema Change 变重（课 7、课 11） | 按查询模式拆表 |

**正面判断条件**（同时满足才该用）：查询以**聚合 / 扫描**为主、单次涉及**大量行**、写入以**批量 / 流式**为主、能容忍**秒级**数据可见延迟。

### 三条容易被忽略的边界

**其一，"查询快"的前提是查询模式对。** 课 7 那张表是全课程最反直觉的：同一张表、同样 200 万行、同样 `COUNT+SUM`，只改 SELECT 的列数——磁盘读只多 1.5 倍，耗时却多 52 倍。瓶颈**不在磁盘 IO，在解压、内存拷贝、传递**。这意味着"扫描慢就买更快的 SSD"是无效投入，钱应该花在**少扫几列**上。

**其二，协议兼容不等于能力等价。** Doris 兼容 MySQL 协议（`SELECT VERSION()` 报告自己是 5.7.99），这让迁移无痛，但也让人误以为它支持事务。它不支持。课 12 的 `ROLLBACK` 测试就是这条边界的实证。

**其三，存算分离的卖点是弹性，不是性能。** 课 12 实测：聚合查询本地 0.16-0.20 s vs 共享存储 0.20-0.23 s（1.2 倍，几乎无差），但明细查询 0.13-0.15 s vs 0.40-0.42 s（**3 倍**）。聚合瓶颈在计算、列式 parquet 只需传少数列；明细涉及的列都得读，且无本地 page cache 兜底。

## 二、高频故障模式（10 条）

> 每条五段式：**症状（可观测）→ 根因 → 排查路径 → 修复 → 预防**。
> 症状全部可观测——写"服务很慢"无效，要写"P99 从 50 ms 涨到 3 s，且 CPU 正常"这种。

### 故障模式 1 · 实时写入"慢性失血"：事务堆积 + 版本碎片化 + 连接池耗尽

**症状**：🔵 数据量小到丢人（<100 条/分钟，约 1.7 条/秒）的系统，投产几天后三连报错：
`current running txns on db X is 1000, larger than limit 1000` → `tablet version too many` → 获取连接失败（连接池超时）。
**Doris 全程没崩，查询业务一直是通的，只是延迟一天天变慢。**

**根因**：每条消息被拆成 3 个单条事务打过去。导入事务是"按次付费"而非"按行付费"——每次事务都要走一遍开启事务 → 规划分发 → 写盘 → 提交发布的固定开销。
🟢 本机实测同样 1000 行：1000 次单行 INSERT **34.42 秒**，1 次批量 INSERT **1.03 秒**，1 次 Stream Load（**10000 行**，10 倍数据）**0.17 秒**（课 6）。

**排查路径**：
1. 看 `SHOW PROC '/transactions'` 或用 `max_running_txn_num_per_db` 对比当前事务数——触发上限说明事务粒度太细
2. 看 `SHOW TABLETS FROM tbl` 的 `VersionCount`——版本数持续上涨说明写入批次太碎
3. 数一下客户端每秒发起多少次写入——根的源头在这里

**修复**：**攒批**。把 N 次小事务合并成 1 次大事务，省下的是 N-1 次固定开销。具体：客户端攒批（按行数或时间窗口取大者）、或启用 Group Commit、或改走 Routine Load 让 Doris 自己攒。

**预防**：压测时**只看"有没有报错"是不够的**。原案例压测跑了几小时无报错就判定通过——但事务数和版本数是**累积型指标**，压测时长不够就暴露不出来。压测必须监控**趋势**（事务数 / 版本数 / 连接数的斜率），而不只是终态。

> 📌 **这条最贵的教训**：这是一个"慢性失血的病"，不是"当场暴毙的事故"。
> 报错出现时已经晚了，趋势指标才是早期信号。
> 来源：[生产 Doris 实时写入翻车复盘（稀土掘金，2026-08-31）](https://juejin.cn/post/7680059849690398755)

### 故障模式 2 · FE 内存泄漏 OOM：会话集合堆积到 1.8 亿条

**症状**：🔵 FE 运行约 14 天后 `java.lang.OutOfMemoryError: Java heap space`，被 `OnOutOfMemoryError=kill -9` 杀死。
崩溃前：**Full GC 每约 2 分钟一次，堆反复顶到 32 GB，GC 后堆底仍有约 25 GB 活对象**（这是泄漏的确定性信号——正常 GC 后堆底应该回到低位）。
MAT 分析 30.46 GB 堆转储：**`Env.aliveSessionSet` 堆积约 1.8 亿条会话 UUID 字符串，占 32 GB 堆的约 98.5%**。

**根因**：FE 内部高频创建 `ConnectContext` 的组件（统计任务、Routine Load、Group Commit、HTTP 接口、PLSQL、MV 等 40+ 处），加上 `FrontendServiceImpl.forward()` 三参构造导致的设计性泄漏。
**与业务客户端基本无关**——三个高流量用户即使所有连接全部泄漏，14 天也仅约 11.6 万条，占泄漏总量 **0.06%**。
清理逻辑自身存在"整体拷贝"缺陷：`getAllAliveSessionIds()` 做 `new ArrayList(aliveSessionSet)` → `Arrays.copyOf` 申请 1.44 GB 连续数组，集合增大后**清理动作本身就会 OOM 自爆**。

**排查路径**：
1. 看 `fe.gc.log`——GC 后堆底是否持续走高（泄漏特征），而非 GC 后回到低位（正常）
2. 抓 Heap Dump 用 Eclipse MAT 分析，看 Dominator Tree 里谁是最大对象
3. 看堆里的 `String` 对象数量和占比

**修复**：🔵 增大堆到 48 GB **只能延缓，不能根治**——这是代码级缺陷，须升级到修复版本。短期缓解是定期重启 FE（配合 FE 高可用避免单点）。

**预防**：
- 监控 **Full GC 频率 + GC 后堆底水位**的斜率，这两个是泄漏的早期信号，比 OOM 早几天
- FE 必须奇数个部署（选举要求"超过半数"，**2 台容错能力和 1 台一样是 0**），这样单台 FE 需要重启时不影响服务
- 定期重启 FE 作为运维常规动作，别等 OOM

> 来源：[Apache Doris GitHub Issue #67199](https://github.com/apache/doris/issues/67199)，事故时点 2026-08-17 10:55(+08:00)，版本 doris-3.1.4-rc02

### 故障模式 3 · 静默失败：脏数据被吞，Status 却报 Success

> 这是全课程最贵的一类：**命令对了，但你对系统的假设错了。四个静默失败只可能被 `SELECT` 抓到，不可能被返回码抓到。**

**症状**：🟢 导入报 `Status: Success`、`NumberFilteredRows: 0`，但表里的数据是 NULL 或数量不对。四种表现：
- 🟢 **脏数据静默转 NULL**：`strict_mode` 默认 `false`，`amount` 收到 `'123abc'` 转成 NULL，**不计入 FilteredRows**（课 6 实测）
- 🟢 **"单行"DELETE 删了一批**：`DELETE FROM dwd_orders WHERE order_id = 7088` 实际删 **331 行**——`order_id` 只在当天唯一，`distinct_oid` 仅 52784 vs 9999563 行（Task 5 实测）
- 🟢 **分区 MV 刷不出数据**：`CREATE` 成功、`REFRESH` 成功、`SHOW PARTITIONS` 显示 28 个分区全 NORMAL，但 `SELECT COUNT(*)` 是 **0**（Task 5，6 组对照实测）
- 🟢 **RESTORE 恢复出空表**：`replication_num` 默认 **3** 且不沿用原表，语句提交时**不报错**，失败信息藏在 `SHOW RESTORE` 的 Status 列（课 11 实测）

**根因**：三类不同，但共同点是**系统照做了你写的话，而不是你想要的事**。
`DELETE` 那条尤其典型：DWD 的唯一键是 `(order_date, user_id, order_id)`，`order_date` 已是第一列，所以 `order_id` 只需在同一天内唯一。这个建模决定当时完全正确，但半年后没人记得，写 `WHERE order_id = x` 时脑子里想的是"全局主键"。
**在 MySQL 里这会因为没有主键直接报错，在 Doris 的 Unique 表里它安静地执行完，返回 OK。**

**排查路径**：
1. 对导入：不看 `Status`，看 `NumberLoadedRows` 是否等于源端行数；更可靠的是**落库后对账**（`SUM` 金额，不能只 `COUNT(*)`）
2. 对删改：执行前先 `SELECT COUNT(*) WHERE <同样的条件>` 看影响范围
3. 对 MV / 备份：逐分区 / 逐表验证**有数据**，不能只看命令返回码

**修复**：逐条对症——生产显式设 `strict_mode:true`；对 Unique 表做删改 WHERE 必须给全唯一键所有列；MV 交付前逐分区验证；RESTORE 必须显式写 `replication_num`。

**预防**：**验证要看数据对不对，不只是看有没有报错。** 这条已固化为全课程方法论第二条。

### 故障模式 4 · 内存超限：MEM_LIMIT_EXCEEDED

**症状**：🟢 查询报 `[MEM_LIMIT_EXCEEDED]Allocator mem tracker check failed, failed alloc size 4.00 MB`。
关键特征：**报错来得快**——🟢 限 384 MB + spill=OFF 时，0.22-0.24 秒就失败（课 10 实测）。

**根因**：查询中间结果超出内存限额。两种典型：高基数 `GROUP BY`（hash 表撑爆）、大表 Join 的中间结果（🟢 课 8 实测：`orders` 按 `province` 自关联产出 **156 亿行**，耗时 4 分 44 秒）。

**排查路径**：
1. 读报错里的 `peak used` 和 `limit` 的比值——**超了一点点**开 spill 就能救；**超了好几倍**得改 SQL 或加内存
2. 用 Profile 看哪个算子内存占用最高（看 `ExecTime` vs `WaitForDependency` 判是它自己慢还是等上游）
3. 检查 Join 键基数：**先问中间结果有多少行，再问用哪个策略**

**修复**：三档递进——
① 开 `enable_spill=true`（🟢 实测 5.24-11.85 秒成功，但**慢 17-39 倍**，是兜底不是优化）
② 改 SQL（减少 GROUP BY 基数、把 Join 前置过滤下推）
③ 加内存或拆查询

**预防**：
- ⚠️ **`enable_spill` 出厂默认是 `false`**，生产建议显式打开——不开的话超限直接失败，没有任何降级空间
- ⚠️ **spill 不是万能的，代价高度非线性**：🟢 `orders` 自关联在 128 MB 直接报错（0.22 秒）、256 MB **挣扎 88.63 秒后仍报错**、512 MB 成功但要 **480 秒**、1024 MB 成功只要 **1.06 秒**。这个梯度说明「稍微超一点点开 spill」可行，「超了很多倍」开 spill 只是把快速失败变成慢速失败
- 用 Workload Group 给不同业务设不同 `exec_mem_limit`，别让一个 Ad-hoc 查询打垮整个集群

### 故障模式 5 · 队列两兄弟：`is full` vs `timeout`

**症状**：两种报错极易混淆，但根因和处置**完全不同**：
- 🟢 `query waiting queue is full, queue capacity=0, waiting num=0`
- 🟢 `query queue timeout, timeout: 1000 ms`

**根因**：都是 Workload Group 的并发控制生效，但卡在不同阶段。
`is full` = **不让进**（队列长度是 0，连排队资格都没有）；`timeout` = **进来了但等不及**（排上了但 `queue_timeout` 毫秒内没轮到）。
🟢 实测三场景：`max_concurrency=1, queue=0` → 3 条并发 2 条被拒（0.1 秒内失败）；`queue=5, timeout=10s` → 3 条全成功（0.97/1.75/2.64 秒）；`queue=5, timeout=1s` → 有人排队超时被拒。

**排查路径**：读报错关键字即可区分，不需要额外诊断。**记忆口诀：`is full` 是"不让进"，`timeout` 是"进来了但等不及"。**

**修复**：
| 报错 | 该调什么 |
|------|---------|
| `queue is full` | `max_queue_size`（调大，让超出的请求能排队） |
| `queue timeout` | `queue_timeout`（调大，让它多等）**或** `max_concurrency`（调大，让队列消化更快） |

**预防**：⚠️ **出厂默认值是坑**：`max_concurrency` 等于没限制、`max_queue_size` **是 0**、`queue_timeout` 是 0。完全不配会得到"要么全跑、要么直接拒绝"的极端行为。
按业务类型配：BI 报表（交互）`max_queue_size` 小、`queue_timeout` 3-5 秒——用户等 3 秒就跑了，不如快速失败；ETL 批处理 `max_queue_size` 大、`queue_timeout` 长——任务可以慢慢跑，失败了反而麻烦。
⚠️ **BI 场景看到 `timeout` 不该简单调大 timeout**，正确做法可能是调大 `max_concurrency` 让吞吐上去。

### 故障模式 6 · 副本不可用：BE 宕机后的两个报错阶段

**症状**：🟢 BE 宕机后，扫数据的查询报错分两阶段：
- 心跳窗口内（约 10-20 秒）：`RpcException UNAVAILABLE`
- 心跳超时后：`tablet xxx has no queryable replicas`
🟢 自愈耗时实测 **45 秒**（课 9）。

**根因**：副本数是"请求"不是"保证"。🟢 声明 3 副本在只有 2 台 BE 时照样建表成功，但只落地 6 个副本（= 分桶数）。
判定集群有没有冗余不能看建表语句，要看 `SHOW PROC '/statistic'` 的 `TabletNum` vs `ReplicaNum`——本机 shop 库 **643/643，零冗余**。
**"查询没断"的真相**：查询能不能跑取决于**数据住在哪**，不取决于**有几个副本**。

**排查路径**：
1. `SHOW PROC '/backends'` 看 BE 存活状态
2. ⚠️ **不要用 `SELECT COUNT(*)` 验证数据可查**——🟢 它走元数据行数优化、根本不扫 BE，**宕机了照样返回值**（课 9 自主发现，前九课均未注意）。必须用 `LIMIT` 明细或 `SUM()` 全表聚合
3. `SHOW PROC '/statistic'` 看 `TabletNum` vs `ReplicaNum` 判断冗余度

**修复**：单节点故障 Doris 会自动补副本（🟢 实测 45 秒，全程无人工操作）。需要人工的是：确认副本补齐、确认数据均衡（`balance_slot_num_per_path` 默认 **1**，每块盘同时只搬 1 个 tablet，大集群均衡会很慢）。

**预防**：
- ⚠️ **反亲和是硬规则**：同一 Tablet 的多个副本不能落同一台物理机，`ALTER TABLE ... SET ('replication_num'='2')` 会直接报 `Failed to find enough backend ... or maybe all be on same host`。**这意味着单容器里的"多副本抗宕机"压根测不了**
- 监控优先级：副本健康 > 磁盘水位 > 错误率（课 11）

### 故障模式 7 · 分桶键选错导致数据倾斜

**症状**：🟢 查询并行度上不去、部分节点忙死部分空闲。`SHOW TABLETS` 看各 tablet 行数差异巨大。

**根因**：分桶键选了低基数列。🟢 实测对比（课 4）：
- `HASH(province) BUCKETS 8`，数据只有 8 个省 → **倾斜比 3.00，且 8 个桶里 4 个是空的**
- `HASH(user_id) BUCKETS 8`，183 万个不同值 → **倾斜比 1.006**

**排查路径**：`SHOW TABLETS FROM tbl` 看各 tablet 的 `RowCount`，算最大/最小比值。

**修复**：只能重建表改分桶键（分桶数可以 ALTER，分桶键不能）。

**预防**：**分桶键的选择方法是看基数，不是拍脑袋**。选高基数 + 常用过滤列。
⚠️ 顺带一条：🟢 分桶数对耗时**无影响**（1/4/8/16 桶均约 0.19 秒），真正影响并行度的是**扫描器数量**——课 7 实测调大 `parallel_pipeline_task_num` 后 Scan `ExecTime` 从 16.26 ms 降到 2.85 ms（5.7 倍），但查询 `Total` 192 ms → 191 ms 几乎没变，证据是 `RowsProduced` 里 `sum = max = 2.0M`，**扫描器只有 1 个**。

### 故障模式 8 · 分区粒度与查询模式错配

**症状**：🟢 分区很细但查询反而没变快，tablet 数量暴涨，元数据压力增大。

**根因**：分区不是越细越好。🟢 实测（课 4）：按天分区查一个月要扫 **240 个 tablet**，按月分区只要 **8 个**，**差 30 倍**；tablet 总数从 360 膨胀到 **2920（8 倍）**。

**排查路径**：用 EXPLAIN 看 `partitions=N/M` ——🟢 正确裁剪时是 `1/45`，扫描量从 2050 万降到 84 万（**减少 24.3 倍**）。

**修复**：调整分区粒度匹配查询模式；或用动态分区让 Doris 自动管理。

**预防**：
- 分区粒度必须匹配查询模式，不要盲目按天
- ⚠️ **动态分区会以「今天」为基准建范围**，历史数据落在范围外会被 strict mode 静默过滤——🟢 实测 25 个月数据 **0 行导入、0 报错**（课 4）。灌历史数据前先确认分区范围

### 故障模式 9 · 语法 / 版本不兼容：报错文不对题

> **报错信息与真实原因不对应，是这类故障最恶心的地方。**

**症状**：🟢 4.1.3 实测的报错原文照录：
| 场景 | 报错原文 | 真实原因 |
|------|---------|---------|
| Workload Group 用了旧属性 | `Property memory_limit is not supported, maybe it is deprecated` | `memory_limit`/`cpu_share`/`cpu_hard_limit`/`enable_memory_overcommit`/`tag` **全部已废弃** |
| S3 TVF 缺 `use_path_style` | `Property minio.endpoint is required.` | **它说缺 endpoint，真正缺的是 `use_path_style='true'`** |
| `CREATE REPOSITORY ... IF NOT EXISTS` | `mismatched input 'IF' expecting {...}` | 4.1.3 **不支持** `IF NOT EXISTS` |
| `CANCEL ALTER ... WHERE JobId=x` | `mismatched input 'WHERE' expecting {<EOF>, ';'}` | 4.1.3 **不支持** WHERE 子句 |
| Key 列顺序不对 | `Key columns should be a ordered prefix of the schema` | Key 必须是建表语句**最前面**的几列 |
| chinese parser 查询 | `chinese tokenizer dict file not found: /opt/be2/dict/jieba.dict.utf8` | 🟢 BE 上 `/opt/be2/dict/` 目录压根不存在，**且表里有数据才报错、空表查询返回 0** |

**根因**：版本演进中语法和属性名变了，而报错信息没有同步跟上。S3 那条尤其典型——它报"A 缺失"，实际缺的是 B。

**排查路径**：遇到文不对题的报错，回到根本问题上：**这个语法 / 属性在当前版本到底支不支持？** 别在报错字面意思上打转。

**修复**：查对应版本的官方文档确认语法；中文分词是**运维动作**（装 jieba 字典或挂载），SQL 解决不了，`all-in-one` 镜像默认不带。

**预防**：升级前过一遍 release note 的废弃项；把版本相关的坑记进团队 runbook（本课程的 `final-课程手册.md`「常考不能/不支持」段就是这么来的）。

### 故障模式 10 · 导入链路不通：Kafka 连不上 / 导入幂等误用

**症状**：
- 🟢 Routine Load 作业直接 `PAUSED`，报错 `Broker transport failure`
- 🟢 `Status: Label Already Exists`，`TxnId: -1`，行数没变

**根因**：
- Kafka 连不上：🟢 **Doris 跑在容器里，它的 `127.0.0.1` 是容器自己**，不是宿主机上的 Kafka。而且 Kafka 返回的 `advertised.listeners` 如果是 `localhost:9092`，Doris 拿着这个地址去连，连的还是自己
- Label 幂等：这是**机制生效**不是故障。同一 label 已成功过 → 直接返回 `Label Already Exists`，不重复导入（label 生命周期默认保留 3 天，由 `label_keep_max_second` 控制）

**排查路径**：
1. Routine Load：`SHOW ROUTINE LOAD` 看 `State` 和 `ReasonOfStateChanged`
2. 网络：`SHOW ROUTINE LOAD` 的 `Statistic` 里看是否 `CONNECT_FAIL`
3. Label：看 `TxnId` 是否 `-1`

**修复**：
- Kafka：两个容器放同一个 Docker 网络；`KAFKA_ADVERTISED_LISTENERS` 设为 Doris 能解析的主机名（如 `kafka:9092`）
- Label：⏳ **重试时保持 Label 不变**，让幂等机制保护你。**如果脚本因为超时重试而自动换 Label 重发，就会造成数据重复**——🟢 实测换 label 重新导入，行数从 10000 变 20000。这是重复数据最常见的来源

**预防**：
- Docker 环境 Kafka 连不上，**九成是 `advertised.listeners` 配了 `localhost`**
- ⚠️ Routine Load 的 `max_filter_ratio` 默认 **1.0**（与 Stream Load 的默认 **0** 相反），且 `max_batch_rows` 有 **200000 硬下限**，ALTER 改小直接报错。生产务必显式设 `strict_mode:true` 并按需调整 `max_filter_ratio`

## 三、落地 / 上线 Checklist

> 投产前必查。分四组：**建模 / 导入 / 查询 / 运维**。

### 建模

- [ ] 数据模型选对（Duplicate 安全牌 / Unique 要更新 / Aggregate 维度固定）
- [ ] 分桶键是**高基数列**（实测倾斜比 < 1.1），不是拍脑袋选的
- [ ] 分区粒度**匹配查询模式**（不是越细越好；按天查一月 240 tablet vs 按月 8 tablet）
- [ ] Key 列在建表语句**最前面**且顺序与查询前缀匹配
- [ ] 副本数显式设置（生产 3，单机 1），并验证 `TabletNum` vs `ReplicaNum` 确有冗余
- [ ] 动态分区范围**覆盖历史数据**（否则 strict mode 静默过滤，0 行导入 0 报错）
- [ ] 索引用量已评估存储代价（实测加 2 个索引存储 **×3.9**）

### 导入

- [ ] 写入是**攒批**的，不是逐行 INSERT（实测 1000 次单行 34.42 秒 vs 1 次 Stream Load 1 万行 0.17 秒）
- [ ] `strict_mode` 显式设为 `true`
- [ ] Routine Load 的 `max_filter_ratio` 显式设置（默认是 1.0，不是 0）
- [ ] 导入后**对账**：`NumberLoadedRows` 等于源端行数，且落库后用 `SUM` 核对金额
- [ ] 重试逻辑**保持 Label 不变**（换 Label 会重复导入）
- [ ] 有事务数 / 版本数 / 连接数的**趋势监控**（不只是终态）
- [ ] 压测时长足够暴露累积型指标（原案例压测几小时通过，投产几天后炸）

### 查询

- [ ] 只 SELECT 需要的列（实测扫 1 列 0.13 s vs 扫 13 列 0.51 s）
- [ ] Join 键基数和中间结果规模已评估（实测 24 万行 53 ms vs 156 亿行 4 分 44 秒）
- [ ] `enable_spill` 显式打开（出厂默认 false）
- [ ] Workload Group 已配置：`max_concurrency` / `max_queue_size` / `queue_timeout` 按业务类型区分
- [ ] 慢查询有 Profile 采集（`SET enable_profile=true`）和分析路径

### 运维

- [ ] FE **奇数个**部署（2 台容错能力 = 1 台 = 0）
- [ ] 备份已验证可恢复（**RESTORE 必须显式写 `replication_num`**，默认 3 不沿用原表）
- [ ] 监控优先级：副本健康 > 磁盘水位 > 错误率
- [ ] FE 有 Full GC 频率 + GC 后堆底水位的**趋势监控**（泄漏早期信号，比 OOM 早几天）
- [ ] 大查询有隔离（实测有隔离 vs 无隔离相差约 6 倍）
- [ ] 升级顺序已确认：BE → FE Observer → FE Follower → FE Master
- [ ] 中文分词需求已确认 jieba 字典已装（是运维动作，SQL 解决不了）

## 四、真实事故案例复盘（2 个，均已联网核查）

> 规范允许 1-3 个。这里选两个与本课程知识点**强相关**的，都能直接对应到故障模式。

### 案例一 · 每秒不到 2 条数据，把 Doris 写"崩"了

**时点**：🔵 2026-08-31 公开复盘 ｜ **规模**：<100 条/分钟（约 1.7 条/秒），3 张动态分区表

**经过**：架构简单到"不可能出错"——自研消费框架从 Kafka 消费写入 Doris，逻辑就是解析、查一下、插两张表。压测跑了几小时无报错，判定通过。**投产几天后报错一天比一天凶**：事务堆积超限 `current running txns on db X is 1000` → `tablet version too many` → 连接池耗尽。

**根因**：🟢 每条消息被拆成 3 个单条事务打过去。这正好撞成本课程课 6 的第一原则——**导入事务是"按次付费"而非"按行付费"**。本机实测的对比数字可以直接量化这个错误：同样 1000 行，逐行 34.42 秒，攒批 1.03 秒，Stream Load 1 万行只要 0.17 秒。

**最值得记的一句**：原文作者说——*"Doris 并没有崩溃，查询业务一直是通的，只是查询延迟一天天变慢。一个慢性失血的'病'，而不是当场暴毙的'事故'。"*

**对应**：故障模式 1 ｜ 课 6（导入全家桶）
**来源**：[生产 Doris 实时写入翻车复盘（稀土掘金，2026-08-31）](https://juejin.cn/post/7680059849690398755)

### 案例二 · FE 内存泄漏 OOM：1.8 亿条会话堆积

**时点**：🔵 2026-08-17 10:55(+08:00) ｜ **版本**：doris-3.1.4-rc02，FE 堆 32 GB，运行约 14 天

**经过**：FE 频繁 Full GC（每约 2 分钟一次，GC 后堆底仍有约 25 GB），最终 `OutOfMemoryError` 被 `kill -9`。MAT 分析 30.46 GB 堆转储，定位到 `Env.aliveSessionSet` 堆积约 1.8 亿条会话 UUID，占堆的约 98.5%。

**根因**：FE 内部 40+ 处高频创建 `ConnectContext` 的组件 + `FrontendServiceImpl.forward()` 三参构造的设计性泄漏。**与业务客户端基本无关**（三个高流量用户 14 天仅贡献 0.06%）。清理逻辑自身有"整体拷贝"缺陷，集合增大后清理动作本身会 OOM。

**最值得记的一句**：🔵 *"增大堆至 48 GB 只能延缓，不能根治。"* ——这是代码级缺陷，须升级。短期只能靠定期重启 + FE 高可用兜底，这正好印证了课 9 那条 **FE 必须奇数个**（2 台容错能力 = 1 台 = 0）。

**与本课程的关系**：这条**不是**本课程知识点能预防的（是版本缺陷），但**监控能提前发现**——Full GC 频率 + GC 后堆底水位的斜率，比 OOM 早几天报警。

**对应**：故障模式 2 ｜ 课 9（FE 高可用）
**来源**：[Apache Doris GitHub Issue #67199](https://github.com/apache/doris/issues/67199) / [mail-archive](https://mail-archive.com/commits@doris.apache.org/msg762025.html)

## 五、本文档没覆盖什么（诚实边界）

**以下五条要么本机测不了、要么不属于"经验"范畴，如实标注，不要当成普遍规律**：

| 项 | 为什么没覆盖 | 补测条件 |
|----|-------------|---------|
| Workload Group 的 CPU 配额 | 🟢 本机 cgroup 只读挂载，改不了 | 物理机或 cgroup 可写容器 |
| 多副本抗宕机（3 副本宕 1 台查询不断） | 🟢 2 台 BE 在同一 host，触发反亲和，声明 3 副本只落地 6 个 | 多台真机 |
| 存算分离的实际代价 | 🟢 本机 `RemoteUsedCapacity = 0.000`，是存算一体架构 | 需另部署 cloud mode |
| 分区裁剪的**性能**收益 | 🟢 只有 2050 万行，固定开销 0.13 秒吃掉差异；EXPLAIN 的 `partitions=1/45` 是确定性证据 | 数据量上亿 |
| ClickHouse / ES / Hive 横向对比 | 🟢 本机没有这些容器 | 需另起容器 |

**另外两条诚实的说明**：
1. 故障模式 2（FE OOM）的根因是 **3.1.4 版本缺陷**，本机环境是 4.1.3，**未复现**。收录它是因为它展示了"泄漏的监控信号"这个通用模式，不是让你照着修 3.1.4
2. 故障模式 1、2 的**根因结论来自联网核查的原文作者**，本机只验证了其中的"攒批代价"这一环（课 6 实测）。两者互相印证，但并非本机端到端复现
