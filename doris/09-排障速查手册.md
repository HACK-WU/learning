## 🔴 条目 1 · 事务堆积超限 + 版本碎片化

**一眼识别**：`current running txns on db X is 1000, larger than limit 1000`；伴随 `tablet version too many` 和连接池超时。
**关键特征：Doris 通常不崩，查询业务一直通，只是延迟一天天变慢——这是慢性失血，不是当场暴毙。**

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 立刻把客户端写入**改成攒批**（按行数或时间窗口取大者），或先停掉部分写入任务降低事务产生速率 | 事务数停止上涨，开始回落 |
| 定位 1 | `SHOW PROC '/transactions'` 看当前事务数与 `max_running_txn_num_per_db` 的差距 | 触顶说明事务粒度太细 |
| 定位 2 | `SHOW TABLETS FROM <tbl>` 看 `VersionCount` 是否持续上涨 | 持续上涨 = 写入批次太碎 |
| 定位 3 | 数客户端每秒发起多少次写入：若 QPS≈消息数×每消息事务数，根因确认 | 每条消息拆成多个事务 = 最贵的姿势干最少的活 |
| 修复 | 客户端攒批，或启用 Group Commit，或改走 Routine Load 让 Doris 自己攒 | 🟢 实测同样 1000 行：逐行 34.42 秒 → 攒批 1.03 秒 → Stream Load 1 万行 0.17 秒 |
| 若无效 | → 转 `debug` 现场排查客户端连接与写入路径 | — |

**预防**：监控**趋势**（事务数 / 版本数 / 连接数的斜率），不只是终态。压测时长要足够暴露累积型指标——原案例压测几小时通过，投产几天后炸。
**原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 1

## 🔴 条目 2 · FE 内存泄漏 / OOM

**一眼识别**：`fe.gc.log` 里 Full GC 频繁（如每约 2 分钟一次）**且 GC 后堆底仍维持高位**（如 25 GB/32 GB）；最终 `java.lang.OutOfMemoryError: Java heap space`，FE 被 `kill -9`。
**GC 后堆底持续走高是泄漏的确定性信号**——正常情况 GC 后应该回到低位。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 重启 FE。若为单点，先补 Observer/Follower 再重启；若为集群，逐台重启（**最后动 Master**） | FE 恢复，堆回到低位 |
| 定位 1 | 看 `fe.gc.log`：GC 后堆底水位的**斜率**（隔天对比，不是看单次） | 单调上涨 = 泄漏；平稳 = 正常 |
| 定位 2 | 抓 Heap Dump 用 Eclipse MAT 分析 Dominator Tree | 定位最大对象持有者。已知案例是 `Env.aliveSessionSet` 堆积会话 UUID |
| 定位 3 | 确认版本是否命中已知缺陷（3.1.4-rc02 有此问题） | 命中 → 升级是根治手段 |
| 修复 | 短期：定期重启 FE（配合高可用避免单点）。根治：**升级版本** | ⚠️ 🔵 增大堆（32 GB→48 GB）**只能延缓，不能根治** |
| 若无效 | → 抓 Heap Dump 提 Apache Doris GitHub Issue | — |

**预防**：监控 Full GC 频率 + GC 后堆底水位的斜率，这两个比 OOM 早几天报警。FE 必须**奇数个**部署（2 台容错能力 = 1 台 = 0），这样单台需要重启时不影响服务。
**原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 2

## 🔴 条目 3 · 静默失败：数据被吞但报成功

> **全课程最贵的一类。命令都对了，错的是你对系统的假设——只可能被 `SELECT` 抓到，不可能被返回码抓到。**

**一眼识别**（四种表现，任选一条命中即入此条目）：
- 导入报 `Status: Success`、`NumberFilteredRows: 0`，但落库值是 `NULL`
- `DELETE FROM ... WHERE <条件>` 影响行数远超预期
- MV / 备份：`CREATE`、`REFRESH`、`SHOW PARTITIONS` 全成功，但 `SELECT` 出来 **0 行或空表**
- 任何"命令全绿但数据不对"的情形

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | **先确认影响面**，别急着重跑：`SELECT COUNT(*) WHERE <同样条件>` 看命中范围；对账用 `SUM(金额)` 而非 `COUNT(*)` | 拿到准确的受损行数 |
| 定位 1 — 导入脏数据 | 检查是否设了 `strict_mode` | 🟢 默认 `false`：类型不匹配静默转 NULL 且**不计入 FilteredRows**。生产应显式 `strict_mode:true` |
| 定位 2 — DELETE 删多了 | 检查 WHERE 是否给全了**唯一键的所有列** | 🟢 实测 `WHERE order_id = 7088` 删了 331 行——`order_id` 只在当天唯一 |
| 定位 3 — MV 空 | 逐分区 `SELECT COUNT(*)` 验证；`SHOW PARTITIONS FROM <mv>` 查真实分区名（**MV 分区名 ≠ 基表分区名**） | 🟢 实测 28 个分区全 NORMAL 但 6 组对照全 0 行 |
| 定位 4 — RESTORE 空 | `SHOW RESTORE` 看 **Status 列** | 🟢 `replication_num` 默认 **3** 且不沿用原表，失败信息藏在这里，提交时不报错 |
| 修复 | 逐条对症：设 `strict_mode:true` / WHERE 补全唯一键 / MV 改非分区或逐分区刷新 / RESTORE 显式写 `'replication_num'='1'`（按实际 BE 数） | 数据可查且对账通过 |
| 若无效 | → 转 `debug` 现场取证 | — |

**预防**：**验证要看数据对不对，不只是看有没有报错。** 对 Unique 表做删改，WHERE 必须给全唯一键所有列；对 MV，交付前逐分区验证；对备份，恢复后立刻用 `SUM()` 对账（**不能用 `COUNT(*)`**——它走元数据优化，宕机了照样返回值）。
**原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 3

## 🔴 条目 4 · 内存超限 `MEM_LIMIT_EXCEEDED`

**一眼识别**：`[MEM_LIMIT_EXCEEDED]Allocator mem tracker check failed, failed alloc size X MB`。
**报错来得快**——🟢 限 384 MB + spill=OFF 时 0.22-0.24 秒就失败。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | ① 杀掉该查询；② 若反复发生，先用 Workload Group 限制其内存，避免打垮集群 | 集群其他业务不受影响 |
| 定位 1 | 读报错里的 `peak used` 与 `limit` 的**比值** | 超一点点 → 开 spill 能救；超好几倍 → 得改 SQL 或加内存 |
| 定位 2 | 抓 Profile 看哪个算子内存最高（`ExecTime` 大 = 它自己慢；`WaitForDependency` 大 = 等上游） | 定位到具体算子 |
| 定位 3 | 若是 Join：算 Join 键基数，估计中间结果行数 | 🟢 同为 Shuffle，24 万行 53 ms vs 156 亿行 4 分 44 秒 |
| 修复 — 分支判定 | **若 peak/limit < 约 1.5** → 开 `SET enable_spill=true`<br>**若 peak/limit > 2** → 改 SQL（降 GROUP BY 基数 / Join 前置过滤下推）或加内存<br>**若是 Ad-hoc 查询** → 用 Workload Group 单独限内存 | 🟢 spill 实测 5.24-11.85 秒成功但**慢 17-39 倍**，是兜底不是优化 |
| 若无效 | → 转 `debug` 分析 Profile 与数据分布 | — |

**预防**：
- ⚠️ **`enable_spill` 出厂默认 `false`**，生产建议显式打开——不开就没有任何降级空间
- ⚠️ **spill 代价高度非线性**：🟢 128 MB 直接报错（0.22 秒）、256 MB **挣扎 88.63 秒后仍报错**、512 MB 成功但要 **480 秒**、1024 MB 成功只要 **1.06 秒**。超了很多倍时，开 spill 只是把快速失败变成慢速失败
**原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 4

## 🟡 条目 5 · 队列两兄弟：`is full` vs `timeout`

**一眼识别**（**读关键字即可区分，无需额外诊断**）：

| 报错原文 | 含义 |
|---------|------|
| `query waiting queue is full, queue capacity=0, waiting num=0` | **不让进**——队列长度是 0，连排队资格都没有 |
| `query queue timeout, timeout: 1000 ms` | **进来了但等不及**——排上了但超时了 |

**记忆口诀：`is full` 是"不让进"，`timeout` 是"进来了但等不及"。**

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 若业务已受损：调大该组的 `max_concurrency` 立即放行 | 查询开始执行 |
| 定位 | 读报错关键字分支：含 `is full` → 走 A；含 `timeout` → 走 B | 见下 |
| 修复 A（`is full`） | 调大 `max_queue_size` | 超出的请求能排队。🟢 实测 `queue=0` → 3 条并发 2 条被拒；`queue=5` → 3 条全成功 |
| 修复 B（`timeout`） | 调大 `queue_timeout` **或** 调大 `max_concurrency` | 🟢 实测 `queue=5,timeout=10s` 全成功；`timeout=1s` 有人被拒 |
| 若无效 | → 检查是否整体资源不足（该调机器，不是调参数） | — |

**预防**：
- ⚠️ **出厂默认值是坑**：`max_concurrency` 等于没限制、`max_queue_size` 是 **0**、`queue_timeout` 是 0。完全不配会得到"要么全跑、要么直接拒绝"的极端行为，生产必须显式配
- 按业务类型配：BI 报表（交互）→ `max_queue_size` 小、`queue_timeout` 3-5 秒（用户等 3 秒就跑了，不如快速失败让他重试）；ETL 批处理 → `max_queue_size` 大、`queue_timeout` 长（任务可以慢慢跑，失败了反而麻烦）
- ⚠️ **BI 场景看到 `timeout` 不该简单调大 timeout**，正确做法可能是调大 `max_concurrency` 让吞吐上去
**原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 5

## 🔴 条目 6 · 副本不可用 / BE 宕机

**一眼识别**（两阶段，看宕机时长判断在哪个阶段）：
- 心跳窗口内（约 10-20 秒）：`RpcException UNAVAILABLE`
- 心跳超时后：`tablet xxx has no queryable replicas`
- 建表/改副本数时：`Failed to find enough backend ... or maybe all be on same host`

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 确认业务影响面：⚠️ **不要用 `SELECT COUNT(*)` 验证**——它走元数据优化，宕机了照样返回值。用 `SELECT * LIMIT 10` 或 `SUM()` 全表聚合 | 拿到真实的可查性结论 |
| 定位 1 | `SHOW PROC '/backends'` 看 BE 存活状态 | 确认哪些 BE 挂了 |
| 定位 2 | `SHOW PROC '/statistic'` 看 `TabletNum` vs `ReplicaNum` | 比值 = 1 说明**零冗余**（副本数是"请求"不是"保证"） |
| 定位 3 | 若是反亲和报错：确认是否所有 BE 在同一台物理机 | 同一 Tablet 的多个副本**不能**落同一台物理机 |
| 修复 — 分支判定 | **若 BE 只是重启/临时故障** → 等自愈，🟢 实测 **45 秒**，全程无人工操作<br>**若 BE 永久故障** → `ALTER SYSTEM DECOMMISSION BACKEND`（先迁数据，可 `CANCEL`），**别用 `DROP`**（会被拒绝并要求故意拼错成 `DROPP`）<br>**若是反亲和限制** → 加真机，单容器里多副本抗宕机压根测不了 | 副本补齐，数据可查 |
| 若无效 | → 检查磁盘（`SHOW PROC '/backends'` 的 `UsedPct`）与 BE 日志 `be.WARNING` | — |

**预防**：监控优先级：副本健康 > 磁盘水位 > 错误率。均衡限速默认 `balance_slot_num_per_path = 1`（每块盘同时只搬 1 个 tablet），大集群均衡会很慢，扩容要预留时间。
**原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 6

## 🟡 条目 7 · 数据倾斜（分桶键选错）

**一眼识别**：查询并行度上不去、部分节点忙死部分空闲；`SHOW TABLETS` 看各 tablet 行数差异巨大。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 短期限流该表的大查询，避免单节点被打爆 | 集群整体稳定 |
| 定位 | `SHOW TABLETS FROM <tbl>` 看各 tablet 的 `RowCount`，算 max/min 比值 | 🟢 `province`（8 个值）倾斜比 **3.00** 且 8 个桶里 4 个空；`user_id`（183 万值）**1.006** |
| 修复 | **分桶键不能 ALTER，只能重建表**改分桶键后重灌 | 倾斜比降到 1.1 以下 |
| 若无效 | → 检查是否还有分区粒度问题（转条目 8） | — |

**预防**：分桶键选**高基数 + 常用过滤列**，判据是看基数不是拍脑袋。
⚠️ 顺带排查：若倾斜正常但并行度仍上不去，看 Profile 里 Scan 的 `RowsProduced` 是否 `sum = max`（说明**扫描器只有 1 个**，调 `parallel_pipeline_task_num` 对查询总耗时无效——🟢 实测 Scan `ExecTime` 降 5.7 倍但 `Total` 192 ms → 191 ms 几乎没变）。
**原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 7

## ⚪ 条目 8 · 分区粒度与查询模式错配

**一眼识别**：分区很细但查询没变快，tablet 数量暴涨，元数据压力大。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 无需止血（不直接影响可用性） | — |
| 定位 | EXPLAIN 看 `partitions=N/M` 和 tablet 总数 | 🟢 正确裁剪是 `1/45`，扫描量 2050 万 → 84 万（**减少 24.3 倍**）；按天查一月要扫 **240 个 tablet** vs 按月 **8 个**（差 30 倍） |
| 修复 — 分支判定 | **若查询常跨长周期** → 改粗粒度（按月/按周）<br>**若查询总带时间过滤** → 保持细粒度但确认裁剪生效<br>**若历史数据导不进** → 检查动态分区范围（🟢 实测 25 个月数据 **0 行导入、0 报错**） | 扫描单元数下降 |
| 若无效 | → 转条目 7（数据倾斜） | — |

**预防**：分区粒度必须匹配查询模式。⚠️ 动态分区以「今天」为基准建范围，灌历史数据前先确认分区范围覆盖。
**原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 8

## ⚪ 条目 9 · 语法 / 版本不兼容（报错文不对题）

> ⚠️ **报错信息与真实原因不对应，是这类最恶心的地方。别在报错字面意思上打转。**

**一眼识别**（4.1.3 实测报错原文 → 真实原因）：

| 报错原文 | 真实原因 |
|---------|---------|
| `Property memory_limit is not supported, maybe it is deprecated` | `memory_limit`/`cpu_share`/`cpu_hard_limit`/`enable_memory_overcommit`/`tag` **全部已废弃**，改用百分比系列 |
| `Property minio.endpoint is required.` | **它说缺 endpoint，真正缺的是 `'use_path_style'='true'`** |
| `Can not build s3(): props must contain uri` | 必须用 `'uri'` 属性，不能写 `s3.endpoint`+`s3.bucket` |
| `mismatched input 'IF' expecting {...}` | 4.1.3 不支持 `IF NOT EXISTS` / `IF EXISTS`（仓库语句）。**重复建仓库时看到这个是正常的** |
| `mismatched input 'WHERE' expecting {<EOF>, ';'}` | 4.1.3 不支持 `CANCEL ALTER ... WHERE JobId=x`，只能用 `FROM db.tbl` |
| `Key columns should be a ordered prefix of the schema` | Key 列必须是建表语句**最前面**的几列且顺序一致 |
| `chinese tokenizer dict file not found: /opt/be2/dict/jieba.dict.utf8` | BE 缺 jieba 字典，**且表里有数据才报错、空表查询返回 0** |
| `SHOW MATERIALIZED VIEWS` 语法错误 | 用 `SHOW CREATE MATERIALIZED VIEW <name>` 或 `SHOW TABLES` |

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 无（不影响可用性，除非是功能不可用） | — |
| 定位 | 回到根本问题：**这个语法 / 属性在当前版本到底支不支持？** 查对应版本官方文档 | 确认是版本差异还是用法错误 |
| 修复 — 分支判定 | **属性废弃** → 换成百分比系列（`min/max_cpu_percent` 等）<br>**S3/MinIO** → 补 `'uri'` 和 `'use_path_style'='true'`<br>**不支持的语法** → 换等价写法或去掉<br>**中文分词** → **运维动作**：装 jieba 字典或挂载，`all-in-one` 镜像默认不带，SQL 解决不了 | 语句执行成功 |
| 若无效 | → 转 `debug` 或提 Issue | — |

**预防**：升级前过一遍 release note 的废弃项；把版本相关的坑记进团队 runbook。
**原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 9

## 🔴 条目 10 · 导入链路不通（Kafka 连不上 / Label 幂等）

**一眼识别**：
- Routine Load `State: PAUSED`，报错 `Broker transport failure` 或 `CONNECT_FAIL`
- `Status: Label Already Exists`，`TxnId: -1`，行数没变

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 若 Kafka 链路断了：确认 Kafka retention 未过，位点停了数据还在（位点与数据在**同一事务**提交），可 `RESUME` 后补消费 | 🟢 实测 Lag 300 → RESUME 后归 0 |
| 定位 1 | `SHOW ROUTINE LOAD` 看 `State` 与 `ReasonOfStateChanged` | 拿到具体失败原因 |
| 定位 2 — 网络 | 看 `Statistic` 是否 `CONNECT_FAIL`；检查 `advertised.listeners` | 🟢 **Doris 在容器里，它的 `127.0.0.1` 是容器自己**。配了 `localhost:9092` → Doris 连的是自己 |
| 定位 3 — Label | 看 `TxnId` 是否 `-1` | 是 → 幂等拦截，**这是机制生效不是故障** |
| 修复 — 分支判定 | **Kafka 连不上** → 两容器放同一 Docker 网络 + `KAFKA_ADVERTISED_LISTENERS=PLAINTEXT://kafka:9092`（Doris 能解析的主机名）<br>**Label 幂等** → 想重导就换 label；**想重试就保持 label 不变**<br>**脏数据导致 PAUSED** → 清洗数据或按需调 `max_filter_ratio` | 链路恢复 |
| 若无效 | → 转 `debug` 抓 Routine Load 作业详情 | — |

**预防**：
- Docker 环境 Kafka 连不上，**九成是 `advertised.listeners` 配了 `localhost`**
- ⚠️ **重试必须保持 Label 不变**。若脚本因超时重试而自动换 Label，会造成数据重复——🟢 实测换 label 重导，行数从 10000 变 20000。这是重复数据最常见的来源
- ⚠️ **Routine Load 的 `max_filter_ratio` 默认 1.0**（与 Stream Load 的默认 **0** 相反），且 `max_batch_rows` 有 **200000 硬下限**，ALTER 改小直接报错。生产务必显式设 `'strict_mode'='true'` 并监控 `errorRows`
**原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 10

## 快速参考卡（贴在显示器上那种）

**三条铁律**

1. **验证要看数据对不对，不只是看有没有报错** —— 四个静默失败都只可能被 `SELECT` 抓到
2. **`COUNT(*)` 不能用来验证数据可查** —— 它走元数据优化，宕机了照样返回值，用 `LIMIT` 或 `SUM()`
3. **先止血后定位** —— 线上没时间先搞清楚再动手

**三个最阴的默认值**

| 参数 | 默认值 | 该改成 |
|------|--------|--------|
| `strict_mode` | `false`（脏数据静默转 NULL） | `true` |
| `enable_spill` | `false`（超限直接失败） | `true` |
| `max_queue_size` | `0`（超额直接拒绝） | 按业务类型配 |

**两个"与直觉相反"**

- Routine Load 的 `max_filter_ratio` 默认 **1.0**，Stream Load 的是 **0** —— **两者相反**
- FE 必须**奇数个** —— 2 台的容错能力和 1 台一样是 **0**

**一个动作口诀**

> 导入慢 → **攒批**；查询慢 → **少扫几列**；Join 慢 → **先问中间结果有多少行**。
