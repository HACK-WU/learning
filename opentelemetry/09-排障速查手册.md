# OpenTelemetry 排障速查手册

> **机长 QRH 式**：先止血，再诊断，每条症状 30 秒内可执行。
> 出事时用这份；想理解"为什么会这样"翻 [`08-实战经验.md`](./08-实战经验.md)。
>
> **紧急度图例**：🔴 数据失真或成本失控，立即处理 ｜ 🟡 功能受损但可绕过 ｜ ⚪ 预期行为，别当故障查
>
> **17 条症状按「数据链路」从上游到下游排列**，不确定查哪条时先看分组：
> - **1-3 数据到不了后端**：插桩没生效 / 服务名没设 / 后端不支持该信号
> - **4-5 采样**：静默全量（烧钱）/ 错误 trace 丢失
> - **6-8 数据对了但读错**：trace 点不开 / 属性名变了 / 指标与 trace 口径不同
> - **9-10 分析视角错了**：P99 被低估 / N+1 该看 Self Time
> - **11-17 Collector 运维**：配置、日志、脱敏、OOM、属性、组件、测量自欺
>
> ⏱️ 时间紧时**先扫所有 🔴**，再处理 🟡。⚪ 那两条（症状 8）不是故障，别浪费时间。

## 🔴 症状 1：程序没报错，后端一条数据都没有

**第一原则**：OTel 用 **warning 而不是异常**处理"你不该这么做"的调用。`force_flush()` 返回 `True` 什么都不证明——实测五种错误配置下**全部返回 True，数据全部静默丢弃**。

| 步骤 | 动作 | 预期 |
|---|---|---|
| **止血** | 确认是否有其他数据源可交叉验证；**不要**根据缺失的数据做决策 | 决策不依赖失真数据 |
| 定位 1 | **查后端**：`curl -s localhost:16686/api/services \| head` | 没有你的 service → 插桩或导出环节断了 |
| 定位 2 | 服务名显示为 `unknown_service` | → 转**症状 2** |
| 定位 3 | 检查协议与端口是否**成对** | gRPC→**4317**；HTTP→**4318 且路径带 `/v1/traces`** |
| 定位 4 | 检查是否只设了 `ENDPOINT` 没设 `PROTOCOL` | `OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4318` **不会**自动切 HTTP，默认仍是 gRPC |
| 定位 5 | 自动插桩场景查 Resource 有无 `telemetry.auto.version` | 没有 → **缺 `opentelemetry-distro`**，只装了 instrumentation 的话 provider 不导出 |
| 定位 6 | 手动插桩场景查 provider 类型 | 是 `ProxyTracerProvider` → `set_tracer_provider` 未生效 |
| 修复 | 显式设 `OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf`；补装 distro | 后端出现该 service |
| 若无效 | → 转**症状 3**（Collector 收到了但后端不收该信号） | — |

```bash
# 后端是唯一可信判据，不要看退出码
curl -s localhost:16686/api/services | python -m json.tool | head

# 协议与端口必须成对
export OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf
export OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4318
```

> ⚠️ **老教程会骗你**："未初始化时是 `NoOpTracerProvider`"在 **1.44.0** 上已过时，实际是 **`ProxyTracerProvider`**。按 NoOp 去查会白跑。
>
> 对应 [`08-实战经验.md`](./08-实战经验.md) 故障模式 1。

## 🟡 症状 2：服务名显示 `unknown_service`

| 步骤 | 动作 | 预期 |
|---|---|---|
| **止血** | 无需止血，但**所有服务挤在同一名下会彻底失去分辨能力**，尽快修 | — |
| 定位 1 | 查环境变量 `OTEL_SERVICE_NAME` 是否设置 | 未设 → 确认根因 |
| 定位 2 | 查代码里 Resource 是否带 `service.name` | 环境变量与代码**二选一即可**，两处都没设才会 unknown |
| 定位 3 | 自动插桩场景确认 distro 已装 | 缺 distro 时 Resource 属性也少 |
| 修复 | 设 `OTEL_SERVICE_NAME=your-service` 或在 Resource 里显式声明 | 后端显示真实服务名 |
| 若无效 | → 转**症状 1**（可能是数据根本没到） | — |

## 🔴 症状 3：后端明明收到了，但查不到该信号

**三层各自"成功"，只有最后一层知道数据没了**——而它说话的声音传不到你耳朵里。

| 步骤 | 动作 | 预期 |
|---|---|---|
| **止血** | 确认该信号是否有其他后端兜底（如日志同时发 Loki 和 Jaeger） | 关键日志不丢 |
| 定位 1 | 用 `debug` exporter 确认 Collector **收到没有** | 收到 → 问题在后端；没收到 → 转症状 1 |
| 定位 2 | **查后端是否支持该信号** | 实测 Jaeger 对 `/v1/logs` 返回 **404 Unimplemented**，Collector 侧显示 `n_spans=1 / n_logs=0`，应用侧退出码 0、无报错 |
| 定位 3 | 三个信号**分别**验证 | 不要因为 trace 通了就认为 log 也通 |
| 修复 | 为该信号换支持它的后端：日志走 **Loki / ELK**，不要把日志发给 Jaeger | 数据可见 |
| 若无效 | → 确认 Collector pipeline 里该信号的 receiver/exporter 都配了 | — |

```yaml
# debug exporter 是判断"Collector 到底收没收到"的最短路径
exporters:
  debug:
    verbosity: detailed   # basic 只打摘要，看不到内容（见症状 12）
service:
  pipelines:
    logs:
      receivers: [otlp]
      exporters: [debug, loki]
```

> 对应 [`08-实战经验.md`](./08-实战经验.md) 故障模式 2。

## 🟡 症状 4：配了采样，span 数一点没少

⚠️ **这是方向相反的静默失败**：它不是"数据丢了"，而是"**省钱配置彻底失效，你在全量烧钱**"。

| 步骤 | 动作 | 预期 |
|---|---|---|
| **止血** | 若成本已失控，先在 Collector 侧补一个 `probabilistic_sampler` 兜底 | 出流量立即下降 |
| 定位 1 | **去后端核对实际保留率**（唯一可信判据） | 预期保留数 vs 实际保留数 |
| 定位 2 | 采样器名**逐字核对** | 是 `trace_id_ratio` 不是 `traceidratio`；拼错会静默回退成 `ParentBased` |
| 定位 3 | 检查参数是否合法数字 | 实测 `ARG=not-a-number` → 回退成 **1.0（全量）** |
| 定位 4 | 确认决策发生在哪一层 | SDK（头部）还是 Collector（尾部） |
| 修复 | 修正采样器名与参数；用后端实测保留率**反推验证** | 保留率符合预期 |
| 若无效 | → 转**症状 5**（可能 SDK 与 Collector 采样职责冲突） | — |

```bash
# 采样配置变更必须做保留率回归：改完去后端数一遍
# 不是看配置写对了就算完
curl -s 'localhost:16686/api/traces?service=my-svc&limit=1000' \
  | python -c "import sys,json; print(len(json.load(sys.stdin)['data']))"
```

> 对应 [`08-实战经验.md`](./08-实战经验.md) 故障模式 3。

## 🔴 症状 5：错误 trace 保留数远低于预期

**两个独立根因，别混着查**：①SDK 先丢了一刀，Collector 只能在残羹里挑；②多副本 Collector 把 span 拆散了。

| 步骤 | 动作 | 预期 |
|---|---|---|
| **止血** | 若关键错误链路完全无 trace，先临时把 SDK 改成 `always_on` | 恢复可观测性（成本上升，事后回调） |
| 定位 1 | 查 **SDK 侧**采样配置 | **要用尾部采样，SDK 必须是 `always_on`**——否则 head 丢掉的 90% 根本走不到 Collector |
| 定位 2 | 查是否**多副本 Collector** 直接做尾部采样 | 同一 trace 的 span 散落在不同实例，每个实例都看不到完整 trace，**两个 Collector 日志都只有 `Everything is ready`，毫无异常** |
| 定位 3 | 用后端实测保留率倒推 | 错误 trace 应接近 **100/100**；实测 head 10%+tail 只有 **11/100**，普通 trace **0/100** |
| 修复 | SDK 设 `always_on`；两层 Collector + **load balancing exporter** 按 trace_id 一致性哈希 | 错误 trace 回到 100/100 |
| 若无效 | → 转**症状 4**（可能采样器名/参数本身就错了） | — |

```yaml
# 第一层：按 trace_id 路由，保证同一 trace 落到同一第二层实例
exporters:
  loadbalancing:
    routing_key: traceID
    protocol:
      otlp:
        tls:
          insecure: true      # 注意层级：在 protocol.otlp 之下
    resolver:
      static:
        hostnames: [gateway-a:4317, gateway-b:4317]
```

**实测对照**（同批 300 条：100 错误 / 100 慢 600ms / 100 普通）：

| 配置 | 错误 | 慢 | 普通 |
|---|---|---|---|
| 纯尾部 | **100/100** | **100/100** | 8/100 |
| 纯头部 10% | 11/100 | 12/100 | 10/100 |
| **head 10% + tail** | **11/100** | 12/100 | **0/100** |

> 对应 [`08-实战经验.md`](./08-实战经验.md) 故障模式 4、反模式 3 与反模式 7。

## 🟡 症状 6：日志有 trace_id，但点不开

⚠️ **这是预期行为不是 bug**。先分清两个问题：**"日志关联失效"（trace_id 为空）** vs **"trace 点不开"（trace_id 有效但该 trace 未采样）**。

| 步骤 | 动作 | 预期 |
|---|---|---|
| **止血** | 无需止血。若该类请求必须可跳转，用头部采样**强制保留** | 关键请求可追溯 |
| 定位 1 | 确认日志里 trace_id **是否有值** | 有值 → 关联本身没坏，是 trace 未被采样 |
| 定位 2 | 用该 trace_id 直接去 trace 后端搜索 | 搜不到 → 确认该 trace 未采样 |
| 定位 3 | 区分 exemplar 的判据 | 日志关联看**span context 是否有效**；exemplar 看 **SAMPLED 位是否置位**。`always_off` 是"创建 span 但不置 SAMPLED 位" |
| 修复 | 预期行为。若需保证跳转，对该类请求用 `ParentBased` + 自定义 sampler 强制保留 | 关键请求可跳转 |
| 若无效 | → 转**症状 8**（可能是指标口径问题而非关联问题） | — |

**实测**（三组子进程隔离，每组 200 次请求）：

| 采样配置 | 采样 span 数 | 日志带 trace_id | exemplar |
|---|---|---|---|
| `always_on` | 200/200 | **200 条（100%）** | 有 |
| `ratio_10pct` | 25/200 | **200 条（100%）** | 少 |
| **`always_off`** | 0/200 | **200 条（100%）** | **0** |

> ✅ **准确表述**：降采样**不丢**日志与请求的对应关系，**但那个 trace_id 在后端点不开**。
> 团队里流传的"降采样会让日志关联失效"是错的。
>
> 对应 [`08-实战经验.md`](./08-实战经验.md) 故障模式 5。

## 🔴 症状 7：升级插桩库后看板少一半

⚠️ **弃用是静默的——连 warning 都没有**。

| 步骤 | 动作 | 预期 |
|---|---|---|
| **止血** | 回滚插桩库版本，或临时切 `http/dup` 档双写 | 看板恢复（体积翻倍，短期可接受） |
| 定位 1 | 把 span 属性 **dump 出来对比新旧版本** | 看到属性名变化 |
| 定位 2 | 查 `OTEL_SEMCONV_STABILITY_OPT_IN` 当前档位 | ⚠️ **分域独立**——`http` 管不了 `database` |
| 定位 3 | 逐个改看板/告警规则的查询条件到新名 | 查询恢复 |
| 修复 | 短期 `http/dup` 双写过渡；长期改完查询条件后切 `http` 档 | 数据正常、体积回落 |
| 若无效 | → 确认不是 Collector 的 transform processor 改名导致 | — |

**实测**（Flask 插桩 5 档）：

| 档位 | 属性数 | 说明 |
|---|---|---|
| `default` | **13 个，其中 11 个是旧名** | 数据完全正常 |
| `http` | **10 个全新名** | 旧名全没了 |
| `http/dup` | **22 个**（13 旧 + 9 新） | 双写，体积翻倍 |
| `database` | 对 HTTP 属性**毫无影响** | 证明开关分域独立 |

**主要迁移**：`http.method`→`http.request.method` ｜ `http.status_code`→`http.response.status_code` ｜ `http.url`→`url.full` ｜ `http.target`→`url.path` + `url.query`

```bash
export OTEL_SEMCONV_STABILITY_OPT_IN=http/dup   # 迁移期双写
```

> 对应 [`08-实战经验.md`](./08-实战经验.md) 故障模式 6。

## ⚪ 症状 8：指标告警响了，trace 搜不到

✅ **这不是故障，是采样链路的诊断信号**。看到这个现象先确认采样率，**不要怀疑数据丢了**。

| 步骤 | 动作 | 预期 |
|---|---|---|
| **止血** | 无需止血 | — |
| 定位 1 | 确认采样率 | 实测 10000 次请求、采样率 0.1% → 被采样 span 仅 **11 条**，而 Histogram `count` 仍是 **10000** |
| 定位 2 | 从指标反查 trace 时优先用 **exemplar** | exemplar 数量与采样率成正比；采样率极低时可能**一条都没有** |
| 定位 3 | 确认团队是否理解这个口径差异 | 值班同学常误判为数据丢失 |
| 修复 | 按 exemplar 需求量**反推采样率** | 问题从"采样率怎么定"变成"**要多少条可跳转链接**" |
| 若无效 | → 转**症状 6**（可能是 trace_id 有效但 trace 未采样） | — |

> 📌 **在告警规则里写明"指标全量、trace 采样"的口径差异**，避免值班误判。
>
> 对应 [`08-实战经验.md`](./08-实战经验.md) 故障模式 7。

## 🔴 症状 9：P99 很健康，用户却投诉慢

⚠️ **低估比高估危险得多**：高估让你虚惊一场，低估让你在监控上看到"还行"而放过真实问题。

| 步骤 | 动作 | 预期 |
|---|---|---|
| **止血** | 立即改用原始数据或日志重新统计真实 P99 | 拿到真实数字 |
| 定位 1 | 查用的是显式桶还是指数桶 | 显式桶 → 继续定位 2 |
| 定位 2 | 查**最大桶边界是否覆盖真实最大值** | 超出最大桶的值被算进最大桶、用桶上界代表它。实测 E 场景真实 20s 被砍成 10s |
| 定位 3 | 对比原始数据算出的 P99 与监控显示值 | 实测显式桶最坏误差 **−50.0%**，指数桶最坏 **−2.2%** |
| 修复 | 改用 **Exponential Histogram**（自适应，实测窄区间场景 scale 自动从 3 升到 8） | 长尾不再被低估 |
| 若无效 | → 转**症状 10**（可能是个别请求被 N+1 拖慢，被平均值掩盖） | — |

⚠️ **默认是显式桶，不是指数桶**——本机实测：不配 `View` 时得到的是**显式桶，15 个默认边界**（`0, 5, 10, 25, 50, 75, 100, 250, ...`）。想用指数桶**必须显式配 `View`**，光省略参数是没用的。

```python
# ✅ 指数桶：必须靠 View + ExponentialBucketHistogramAggregation
from opentelemetry.sdk.metrics import MeterProvider
from opentelemetry.sdk.metrics.view import (
    View,
    ExponentialBucketHistogramAggregation,
)

provider = MeterProvider(
    metric_readers=[reader],
    views=[
        View(
            instrument_name="request_duration",
            aggregation=ExponentialBucketHistogramAggregation(),
        )
    ],
)

# 实测（本机 2026-09-04，5 个样本 0.5/5/20/500/20000 ms）：
#   不配 View                -> EXPLICIT     15 个默认边界
#   View + Exponential...    -> EXPONENTIAL  scale=3
#   View + Explicit...       -> EXPLICIT     自定义边界数
```

> 📌 **注意**：`create_histogram()` 的参数名是 **`explicit_bucket_boundaries_advisory`**（带 `_advisory` 后缀），它是"建议值"——最终用不用由 `View` 决定。而聚合类的导入路径是 `opentelemetry.sdk.metrics.view`，**不是** `sdk.metrics.aggregation`（该模块在本机 1.44.0 中不存在）。
>
> 对应 [`08-实战经验.md`](./08-实战经验.md) 故障模式 8。

## 🟡 症状 10：按最慢 span 优化，延迟没改善

**N+1 类问题的每一次调用都不慢，异常的是次数本身。**

| 步骤 | 动作 | 预期 |
|---|---|---|
| **止血** | 若已定位到循环调用，先加缓存或批量化 | 延迟下降 |
| 定位 1 | **用 Self Time 聚合，不要用"最慢单个 span"** | Self Time = 自身 duration − 子 span 占用时间 |
| 定位 2 | 看 span 数量是否异常膨胀 | 实测 **15 → 214** 是关键信号 |
| 定位 3 | 同名 span 出现高频次（如 ×200） | 直接判定为循环内调用 |
| 修复 | 批量查询替代循环单查 | 端到端延迟回落 |
| 若无效 | → 转**症状 17**（可能是测量方式本身有问题） | — |

**实测三种视角的对比**（端到端 2616 ms，正常 140 ms）：

| 视角 | 结果 | 为什么错 |
|---|---|---|
| ① 最慢单个 span | 48.2 ms（`payment.charge`） | 每次 `db.query.rule` 只有 23 ms，**没有一个异常值** → 指向错误的服务 |
| ② 同名 span 累计 duration 榜首 | `POST /checkout` 2616 ms | 入口 span duration 包含全部子 span，**父子重叠被重复计入**，入口 span 永远是第一名，等于什么都没说 |
| ✅ ③ **Self Time 聚合** | `db.query.rule` **×200 累计 2518.8 ms** | 剔除重叠后 200 次重复调用暴露出来，**占端到端 96%** |

> 📌 **把"Self Time 聚合"作为 trace 分析的默认第一视图。**
>
> 对应 [`08-实战经验.md`](./08-实战经验.md) 故障模式 9。

## 🔴 症状 13：脱敏没生效，PII 外泄

| 步骤 | 动作 | 预期 |
|---|---|---|
| **止血** | **立即断开该 pipeline 的对外导出**，避免继续外泄 | 泄漏停止 |
| 定位 1 | 查 Processor **顺序** | **脱敏必须排在 transform 迁移之后** |
| 定位 2 | 检查 transform 是否新生成了敏感字段 | 实测：transform 新生成的 `url.query` 会躲过排在它前面的脱敏 |
| 定位 3 | 评估已外泄范围 | 通知相关方 |
| 修复 | 把脱敏 processor 移到 transform 之后 | 新生成字段也被脱敏 |
| 若无效 | → 检查是否有第二个 pipeline 绕过脱敏直连后端 | — |

```yaml
processors:
  transform:        # 1. 先迁移/重命名字段
    # ...
  redaction:        # 2. 再脱敏（顺序错了新字段就漏网）
    allow_all_keys: false
    blocked_values: ["password", "token", "id_card"]
service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [transform, redaction]   # 顺序即执行顺序
      exporters: [otlp/http]
```

## 🟡 症状 14：容器里 OOM，但 memory_limiter 配了很大

| 步骤 | 动作 | 预期 |
|---|---|---|
| **止血** | 调低容器内存限制或临时减少 pipeline 并发 | 不再 OOM |
| 定位 1 | 查 `memory_limiter` 用的是绝对值还是百分比 | 容器里写死绝对值，**读到的是宿主机内存**，不是容器 limit |
| 定位 2 | 对比容器 limit 与 limiter 阈值 | limiter 阈值 > limit → OOM 前根本不会触发 |
| 修复 | 容器里一律用**百分比**（如 `limit_percentage: 75`） | 按容器实际 limit 生效 |
| 若无效 | → 查是否是 queue 积压（sending_queue 无上限会吃内存） | — |

```yaml
processors:
  memory_limiter:
    check_interval: 1s           # 多久检查一次内存占用
    limit_percentage: 75         # ✅ 容器里用百分比，按容器 limit 算
    spike_limit_percentage: 15   # 尖峰缓冲：超过 limit 后再吃多少才开始拒数据
    # limit_mib: 4096            # ❌ 容器里读到的是宿主机内存
```

> 📌 三个字段要配套：`check_interval` 决定检测频率，`limit_percentage` 是硬阈值，`spike_limit_percentage` 是尖峰缓冲。只写 `limit_percentage` 会走默认值，行为可能与预期不符。
>
> 对应 [`08-实战经验.md`](./08-实战经验.md) 上线 Checklist「Collector 管道」组。

## 🟡 症状 15：加了新属性但后端看不到

| 步骤 | 动作 | 预期 |
|---|---|---|
| **止血** | 无需止血 | — |
| 定位 1 | 查 `resource` processor 用的是 `insert` 还是 `upsert` | **`upsert` 只在键已存在时生效**，加新属性会静默无效 |
| 定位 2 | 确认该属性名是否本来就不存在 | 不存在 + upsert = 什么都不做 |
| 修复 | 加新属性改用 **`insert`** | 属性出现 |
| 若无效 | → 检查属性是否被下游 transform/redaction 删掉 | — |

```yaml
processors:
  resource:
    attributes:
      - key: deployment.environment
        value: production
        action: insert     # ✅ 加新属性用 insert
        # action: upsert   # ❌ 键不存在时静默无效
```

## 🔴 症状 17：实验结果自洽但结论错误

⚠️ **不只被测系统会骗你，测量工具本身也会**。实测三个实例：课 6 分流实验因同进程二次 `set_tracer_provider` 被拒得到「两边 0 条」；课 8 查 exemplar 恒为 0 耗时 **11 轮**，根因是 `InMemoryMetricReader` 的 exemplar **一次性**——`force_flush()` 会消费掉它，读第二次归零；实战项目 Top-3 排序把父子重叠的入口 span 排在最前。

| 步骤 | 动作 | 预期 |
|---|---|---|
| **止血** | **停止基于该结论做任何决策** | 不再放大错误 |
| 定位 1 | **复制原脚本做减法**，远优于重写脚本做加法 | 课 8 前八轮"逐个加条件"全败，C9 改为"复制课 7 脚本做减法"才定位到 |
| 定位 2 | **所有变量排除后结论仍不变时，怀疑观测方式本身** | 你看到的"异常"可能是测量方式造出来的 |
| 定位 3 | 检查前人的结论——**前人的结论没错，错的是你这一轮的测量姿势** | 避免推翻正确结论 |
| 定位 4 | 具体到 `InMemoryMetricReader`：record 后立刻读、读一次、**绝不 flush 后读** | exemplar 不再归零 |
| 修复 | 换观测方式重做实验 | 结论与事实一致 |
| 若无效 | → 转 `debug` skill 现场取证 | — |

> 📌 **当实验结果非常自洽、完美符合预期时，反而要怀疑**。真实系统很少这么干净。
>
> 对应 [`08-实战经验.md`](./08-实战经验.md) 故障模式 10。

## 🚑 通用止血动作（不确定是哪类问题时，先把损失停下）

| 场景 | 止血动作 | 代价 |
|---|---|---|
| 数据可能失真，有人正据此做决策 | 撤下相关面板并标注「数据异常」 | 暂时失去可见性 |
| 成本失控（采样失效） | Collector 侧补 `probabilistic_sampler` 兜底 | 数据完整性下降 |
| PII 已外泄 | **立即断开该 pipeline 的对外导出** | 该链路数据中断 |
| 配置改了行为不变 | 回滚配置 + 查残留容器占端口 | 回到旧状态 |
| 关键链路完全无 trace | 临时把 SDK 改成 `always_on` | 成本上升，事后记得回调 |
| 怀疑测量工具本身有问题 | 停止基于该结论决策，换观测方式重做 | 结论延后 |
| 以上都无法定位 | → 转 `debug` skill 现场取证 | — |
