## 场景 1：要接入一个新服务

**一句话**：自动插桩给你骨架，手动插桩给你血肉。

### 约束清单

接入前先确认这几项，缺一项后面都会返工：

| 约束 | 怎么确认 | 不满足的后果 |
|---|---|---|
| 服务名可唯一标识该服务 | 能说出一个不会被复用、不含环境信息的名字 | 多服务挤在 `unknown_service` 下，彻底失去分辨能力 |
| 语言有官方自动插桩 | 查 [opentelemetry.io/docs/zero-code](https://opentelemetry.io/docs/zero-code/) | 只能手动插桩，工作量上翻 |
| 导出路径可达 Collector | `curl` 探 4317（gRPC）/ 4318（HTTP） | 静默零数据（症状 1） |
| 能装 `opentelemetry-distro` | 不只是 `opentelemetry-instrumentation` | 缺它则 provider 不导出，静默零数据 |
| 已知哪些是"业务黑洞" | 列出出事时必须知道但框架看不到的字段 | 只看见 HTTP 500，看不见是哪条规则拒的 |

### 设计要点

**1. 命名先行**：`service.name` 用环境变量显式设，环境差异（dev/prod）放 `deployment.environment` 属性，**不要**塞进服务名。

```bash
export OTEL_SERVICE_NAME=payment-service
export OTEL_RESOURCE_ATTRIBUTES=deployment.environment=prod
```

**2. 自动插桩打底**：装 `opentelemetry-distro`，用 `opentelemetry-instrument` 启动。这一步拿到框架层（HTTP、DB 客户端、消息队列）的骨架。

**3. 手动插桩补业务语义**：自动插桩只知道"有个 HTTP 请求"，不知道"哪个用户、哪笔订单、走了哪个分支"。在这些位置补手动：

```python
from opentelemetry import trace

tracer = trace.get_tracer(__name__)

def checkout(order: Order):
    with tracer.start_as_current_span("checkout") as span:
        # 业务语义：自动插桩看不到这些
        span.set_attribute("order.id", order.id)
        span.set_attribute("order.amount", float(order.amount))
        span.set_attribute("user.tier", order.user.tier)
        for rule in rules:
            with tracer.start_as_current_span("db.query.rule") as rs:
                rs.set_attribute("rule.id", rule.id)   # 实战项目靠这个定位 N+1
                hit = rule.match(order)
```

**4. 自动 + 手工混合时先探测 Provider**：这是最容易踩的坑——手工初始化会**覆盖**自动插桩建好的 provider，导致 resource 全部丢失，且**只打一行日志**。

```python
# ✅ 正确：已存在就复用
from opentelemetry import trace
from opentelemetry.sdk.trace import TracerProvider

if not isinstance(trace.get_tracer_provider(), TracerProvider):
    trace.set_tracer_provider(TracerProvider())
```

**5. 三个信号分别验证**：trace 通了不等于 log 也通。每个信号单独验一次后端。

### 验收标准

- [ ] 后端 `GET /api/services` 里出现该 `service.name`（**唯一可信判据，不是退出码**）
- [ ] Resource 里能看到 `telemetry.auto.version`（证明 distro 生效）
- [ ] 至少 3 个业务关键字段能在 span 上查到
- [ ] trace / metric / log 三个信号**分别**验证过后端能收
- [ ] 自动 + 手工混合场景：Resource 属性未丢失

### 回链

- 数据没到 → [09 症状 1](./09-排障速查手册.md#-症状-1程序没报错后端一条数据都没有)（静默零数据）
- 服务名是 `unknown_service` → [09 症状 2](./09-排障速查手册.md#-症状-2服务名显示-unknown_service)
- 只靠自动插桩 → [08 反模式 2](./08-实战经验.md#高频反模式能跑但迟早出事)
- 后端收不到某信号 → [09 症状 3](./09-排障速查手册.md#-症状-3后端明明收到了但查不到该信号)

## 场景 2：要接一个新后端 / 要换后端

**一句话**：这正是上 OTel 的核心收益——**改一行配置，不是改几百个服务的代码**。

### 约束清单

| 约束 | 怎么确认 | 不满足的后果 |
|---|---|---|
| 目标后端**支持哪些信号** | 查后端文档或实测发一条 | Jaeger 收 logs 返回 404 Unimplemented，静默丢弃 |
| Collector 有对应 exporter | `docker run --rm <img> components` | core 版没有 contrib 的 exporter |
| 协议与端口成对 | gRPC **4317** / HTTP **4318** | 混用则静默零数据 |
| 是否需要数据格式转换 | 目标后端是否原生收 OTLP | 不是原生则需转换层 |

### 设计要点

**1. 双写过渡，不要直接切**：先把新后端加进 exporters 列表，与旧后端并行跑一段时间，确认无误再摘掉旧的。

```yaml
exporters:
  otlp/jaeger:
    endpoint: jaeger:4317
    tls:
      insecure: true
  otlp/newbackend:            # 新增，旧的不动
    endpoint: newbackend:4317
    tls:
      insecure: true
service:
  pipelines:
    traces:
      receivers: [otlp]
      exporters: [otlp/jaeger, otlp/newbackend]   # 双写
```

**2. 换后端不需要动应用代码**——这是 OTel 相对直接插桩的核心价值。应用只认 OTLP，后端差异全部收敛在 Collector。

**3. 三个信号可能要拆到不同后端**：实测 Jaeger 不支持 logs。常见组合：

| 信号 | 常用后端 |
|---|---|
| trace | Jaeger / Tempo / 商业 APM |
| metric | Prometheus / VictoriaMetrics |
| log | Loki / ELK |

**4. 已有 Prometheus + Grafana 的团队不必全量迁移**：OTel 可导出 Prometheus 格式，**既有看板无需改动**。

### 验收标准

- [ ] 新后端能查到该 `service.name` 的数据
- [ ] 双写期间两个后端数据量一致（差异 > 1% 要查）
- [ ] 应用代码**零改动**
- [ ] 摘掉旧后端后无告警失败

### 回链

- 后端收不到某信号 → [09 症状 3](./09-排障速查手册.md#-症状-3后端明明收到了但查不到该信号)
- 组件不存在 → [09 症状 16](./09-排障速查手册.md#-症状-16collector-报组件不存在--组件行为与文档不符)
- 选型判据 → [`final-课程手册.md`](./final-课程手册.md#二选型决策条件)

## 场景 3：要做成本治理（采样与数据量）

**一句话**：先量后省。**要用尾部采样，SDK 必须 `always_on`**。

### 约束清单

| 约束 | 怎么确认 | 不满足的后果 |
|---|---|---|
| 当前实际数据量与成本 | 实测每 span 约 **600 B**（未压缩实测 **959 B**） | 无法评估采样收益 |
| 哪些 trace **必须**保留 | 列出：错误、慢请求、关键业务（如支付） | 省钱省掉了排障能力 |
| 决策发生在一层还是两层 | SDK 头部 / Collector 尾部 | 头尾串联是双重代价 |
| Collector 是否多副本 | 多副本直接做尾部采样会拆散 trace | 错误 trace 静默消失 |

### 设计要点

**1. 尾部采样的前提：SDK 必须 `always_on`**

这是最容易搞错的一条。SDK 先按 10% 丢掉 90% 的 span，Collector 只能在这 10% 的残羹里挑——**实测错误 trace 保留数从纯尾部的 100/100 掉到 11/100，普通 trace 掉到 0/100**。

```bash
# ✅ 尾部采样场景
export OTEL_TRACES_SAMPLER=always_on
```

```yaml
# 决策权完整交给 Collector
processors:
  tail_sampling:
    decision_wait: 10s        # 等 trace 完整，太短会拆散长链路
    policies:
      - name: keep-errors
        type: status_code
        status_code:
          status_codes: [ERROR]
      - name: keep-slow
        type: latency
        latency:
          threshold_ms: 500
      - name: keep-sample-of-rest
        type: probabilistic
        probabilistic:
          sampling_percentage: 1
```

**2. 多副本 Collector 必须先做一致性哈希**

同一 trace 的 span 散落在不同实例，每个实例都看不到完整 trace，**两个 Collector 日志都只有 `Everything is ready`，毫无异常**。

```yaml
exporters:
  loadbalancing:
    routing_key: traceID      # 按 trace_id 哈希，同一 trace 落到同一实例
    protocol:
      otlp:
        tls:
          insecure: true
    resolver:
      static:
        hostnames: [gateway-a:4317, gateway-b:4317]
```

**3. 成本模型用实测字节数校准**，不要用拍脑袋的数。

**4. 改完必须做保留率回归**——去后端数一遍，不是看配置写对了就算完。

```bash
curl -s 'localhost:16686/api/traces?service=my-svc&limit=1000' \
  | python -c "import sys,json; print(len(json.load(sys.stdin)['data']))"
```

### 验收标准

- [ ] 采样器名与参数逐字核对过（**拼错会静默回退全量，是烧钱不是丢数据**）
- [ ] 后端实测保留率符合预期（错误 trace 应接近 100/100）
- [ ] 多副本场景已配 load balancing
- [ ] 成本模型已用实测字节数校准
- [ ] 关键请求（支付等）已用头部采样强制保留

### 回链

- 配了采样但 span 没少 → [09 症状 4](./09-排障速查手册.md#-症状-4配了采样span-数一点没少)（静默全量，烧钱）
- 错误 trace 大量丢失 → [09 症状 5](./09-排障速查手册.md#-症状-5错误-trace-保留数远低于预期)
- 头尾串联 → [08 反模式 3](./08-实战经验.md#高频反模式能跑但迟早出事)
- 多副本拆散 → [08 反模式 7](./08-实战经验.md#高频反模式能跑但迟早出事)

## 场景 4：要加自定义指标

**一句话**：先过「**能列进一张表吗**」这道闸，再决定放哪。

### 约束清单

| 约束 | 怎么确认 | 不满足的后果 |
|---|---|---|
| 每个标签的**基数** | 估算该字段有多少个不同取值 | 序列数爆炸，放大倍数**恒等于**维度基数 |
| 是否已有 semconv 可用 | 查 [semantic-conventions](https://github.com/open-telemetry/semantic-conventions) | 命名不一致，跨服务对不齐 |
| 用哪种 Instrument | 见下方选型表 | 用错类型导致看板算错 |
| 是否需要分位数 | P99 还是平均值 | 显式桶会把长尾低估 |

### 设计要点

**1. 基数闸门（最重要的一条）**

实测：5 路由 × 3 状态码 = 15 条序列；加 10000 个 `user.id` 变成 **150,000 条**。**放大倍数恒等于加进去的维度基数**，且指标每个序列常驻内存、只要还在上报就永不释放。

> 🚦 **判定规则**：问自己"这个字段的取值能列进一张表吗"。`http.status_code`（几个）可以；`user.id`（几万）不行；`url.path`（带 ID 的）不行。

| 字段类型 | 放哪里 |
|---|---|
| 低基数（状态码、方法、服务名） | ✅ 指标标签 |
| 高基数（user.id、order.id、url.path） | ❌ 指标 → 放**日志或链路属性** |

**2. Instrument 选型**

| 你要表达什么 | 用这个 | 注意 |
|---|---|---|
| 累加且只增不减（请求数、错误数） | `Counter` | — |
| 可增可减（队列长度、连接数） | `UpDownCounter` | ⚠️ 导出为 **`gauge`** 不是 counter，看板算法要相应调整 |
| 当前瞬时值（CPU、内存） | `Gauge` / `ObservableGauge` | 异步型用**回调**采集，不阻塞请求路径 |
| 分布（延迟、包大小） | `Histogram` | 见下条 |

**3. Histogram 必须显式配指数桶**

⚠️ **默认不是指数桶**——实测不配 View 时得到的是**显式桶、15 个默认边界**。显式桶会把长尾低估，**实测最坏误差 −50.0%**（20s 被算成 10s），而指数桶最坏仅 **−2.2%**。

```python
from opentelemetry.sdk.metrics import MeterProvider
from opentelemetry.sdk.metrics.view import (   # 注意：不是 sdk.metrics.aggregation
    View,
    ExponentialBucketHistogramAggregation,
)

provider = MeterProvider(
    metric_readers=[reader],
    views=[
        View(
            instrument_name="payment_amount",
            aggregation=ExponentialBucketHistogramAggregation(),
        )
    ],
)
```

**4. 两个类型陷阱**

- **`UpDownCounter` 导出为 `gauge`，不是 counter**。看板如果按 counter 算（如 `rate()` 求增量）会得到错误结果，必须改成直接取值或 `delta` 类函数。

  ```python
  # 队列长度：可增可减
  queue_depth = meter.create_up_down_counter("queue.depth", "items", "Queue depth")
  # 导出后类型是 gauge —— 看板要用 current value，不要用 rate()
  ```

- **异步 Instrument 用回调采集**，`Observable*` 系列在采集周期到点时调用回调取值，不阻塞请求路径；同步 `Gauge` 则需要在业务代码里主动 `set()`。

- **单位后缀会被自动追加**：实测 `payment_amount` → `payment_amount_CNY`、`user_profile_query_duration_ms` → `..._ms_milliseconds`。**查询侧要知晓**。
- **导出间隔默认 60000 ms**：实验场景要设 `OTEL_METRIC_EXPORT_INTERVAL=5000`，否则等一分钟才看到数据。

### 验收标准

- [ ] 所有标签过了一遍「能列进一张表吗」
- [ ] Histogram 已显式配指数桶
- [ ] 指标名的单位后缀已知晓，查询条件已对齐
- [ ] `UpDownCounter` 的看板按 gauge 计算
- [ ] 导出间隔已按场景设置

### 回链

- 高基数 → [08 反模式 4](./08-实战经验.md#高频反模式能跑但迟早出事)
- P99 被低估 → [09 症状 9](./09-排障速查手册.md#-症状-9p99-很健康用户却投诉慢)
- 指标有数但 trace 搜不到 → [09 症状 8](./09-排障速查手册.md#-症状-8指标告警响了trace-搜不到)（**预期行为，不是故障**）

## 场景 5：要加自定义链路与业务属性

**一句话**：业务语义只能手动补，命名优先走 semconv。

### 约束清单

| 约束 | 怎么确认 | 不满足的后果 |
|---|---|---|
| 哪些位置是"业务黑洞" | 出事时必须知道、但框架看不到的字段 | 看得见 HTTP 500，看不见是哪条规则拒的 |
| 属性命名是否已有 semconv | 查语义约定 | 跨服务对不齐，且升级时被重命名 |
| span 粒度 | 一个业务操作一个 span，还是一个循环一次 | 粒度过粗定位不到，过细则 span 数爆炸 |

### 设计要点

**1. 优先用 semconv 已有的名字**，不要自造。`http.request.method` 这类标准名跨服务可对齐；自造的升级时还可能被重命名（见场景 8）。

**2. 循环内创建 span 要警惕 N+1**。这是实战项目最大的收获：

```python
# ❌ 反例：循环内逐条查，产生 200 个 span
for rule in rules:                      # 200 条规则
    with tracer.start_as_current_span("db.query.rule"):
        db.query(rule.id)               # 每次 23 ms，看着都不慢

# ✅ 正解：批量查询，一个 span
with tracer.start_as_current_span("db.query.rules.batch"):
    db.query_batch([r.id for r in rules])
```

**为什么循环内的"每个 span 都不慢"最难发现**：端到端 2616 ms，最慢的单个 span 只有 48.2 ms——**没有一个异常值**。真正的问题是**次数**，不是单次耗时。

> 📌 **trace 分析的默认第一视图应该是「Self Time 聚合」，不是「最慢单个 span」**。Self Time = 自身 duration − 子 span 占用时间，剔除父子重叠后，200 次重复调用会暴露出来。

**3. 属性不要塞高基数字段做指标的标签**（同场景 4），但**链路属性可以**——链路不产生常驻内存的时间序列。

### 验收标准

- [ ] 每个业务关键分支都有 span 覆盖
- [ ] 属性名优先取自 semconv
- [ ] 循环内没有创建 span（或有充分理由）
- [ ] trace 分析默认视图是 Self Time 聚合

### 回链

- N+1 定位不到 → [09 症状 10](./09-排障速查手册.md#-症状-10按最慢-span-优化延迟没改善)
- 只靠自动插桩 → [08 反模式 2](./08-实战经验.md#高频反模式能跑但迟早出事)

## 场景 6：要做脱敏与合规

**一句话**：**脱敏必须排在 transform 迁移之后**。

### 约束清单

| 约束 | 怎么确认 | 不满足的后果 |
|---|---|---|
| 哪些字段是 PII | 列出：password、token、id_card、手机号、邮箱 | 外泄即合规事故 |
| Pipeline 里有没有 transform | transform 会**新生成**属性 | 新属性躲过脱敏 |
| 脱敏粒度 | 全删 / 哈希 / 掩码 | 全删则无法排障 |
| 是否有管道绕过脱敏 | 检查有没有第二个 pipeline 直连后端 | 脱敏形同虚设 |

### 设计要点

**1. Processor 顺序是硬约束**

实测：transform 新生成的 `url.query` 会**躲过排在它前面的脱敏**，PII 直接外泄。

```yaml
processors:
  transform:        # 1. 先迁移/重命名字段
    # ...
  redaction:        # 2. 再脱敏（顺序错了新字段就漏网）
    allow_all_keys: false
    blocked_values: ["password", "token", "id_card"]
service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [transform, redaction]   # 顺序即执行顺序
      exporters: [otlp/http]
```

**2. 脱敏的收益：改 Collector 配置，不改应用代码**——这是 OTel 相对直接插桩的又一核心价值。

**3. 检查所有 pipeline**，确保没有绕过脱敏的旁路。

### 验收标准

- [ ] 脱敏排在 transform **之后**
- [ ] 构造含 PII 的测试数据，在后端**确认查不到明文**
- [ ] transform 新生成的字段也已脱敏
- [ ] 无 pipeline 绕过脱敏

### 回链

- PII 外泄 → [09 症状 13](./09-排障速查手册.md#-症状-13脱敏没生效pii-外泄)（**止血第一步是断开对外导出**）
- 顺序错 → [08 反模式 8](./08-实战经验.md#高频反模式能跑但迟早出事)

## 场景 7：要上生产（Collector 拓扑与容量）

**一句话**：两层网关 + load balancing 哈希 + 百分比限流。

### 约束清单

| 约束 | 怎么确认 | 不满足的后果 |
|---|---|---|
| 是否多副本 Collector | 多副本做尾部采样必须先哈希 | trace 被拆散，错误 trace 静默消失 |
| 容器内存 limit | 决定 `memory_limiter` 阈值 | 用绝对值会读到宿主机内存 |
| 组件稳定性 | `docker run --rm <img> components` | 凭记忆必错，需按「组件 × 信号」逐个查 |
| 是否需要队列缓冲 | 后端抖动时是否可接受丢数据 | 无上限队列会吃内存 |

### 设计要点

**1. 两层拓扑**

```yaml
# 第一层（Agent / Gateway）：按 trace_id 路由
exporters:
  loadbalancing:
    routing_key: traceID
    protocol:
      otlp:
        tls:
          insecure: true
    resolver:
      static:
        hostnames: [gateway-a:4317, gateway-b:4317]
```

**2. `memory_limiter` 在容器里必须用百分比**

```yaml
processors:
  memory_limiter:
    check_interval: 1s           # 检测频率
    limit_percentage: 75         # ✅ 按容器 limit 算
    spike_limit_percentage: 15   # 尖峰缓冲
    # limit_mib: 4096            # ❌ 容器里读到的是宿主机内存
```

**3. Processor 标准顺序：`memory_limiter` 必须在最前**

它要保护的是**后续所有环节**——排在后面就失去了限流意义。

```yaml
service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [memory_limiter, transform, redaction, batch]  # memory_limiter 在最前
      exporters: [otlp/http]
```

**4. 配置改动先 validate**

```bash
docker run --rm -v "${PWD}/config:/conf" otel/opentelemetry-collector-contrib:0.160.0 \
  validate --config /conf/collector.yaml
# 无输出 = 通过
```

**5. 组件稳定性逐个查，不凭记忆**

```bash
docker run --rm otel/opentelemetry-collector-contrib:0.160.0 components | head -50
```

### 验收标准

- [ ] 多副本已配 load balancing（做尾部采样时）
- [ ] `memory_limiter` 用百分比且三个字段配套
- [ ] 配置改动跑过 validate
- [ ] 组件稳定性按「组件 × 信号」查过
- [ ] `debug` exporter 的 verbosity 已按需要设置（`basic` 只打摘要）

### 回链

- OOM → [09 症状 14](./09-排障速查手册.md#-症状-14容器里-oom但-memory_limiter-配了很大)
- 配置不生效 → [09 症状 11](./09-排障速查手册.md#-症状-11collector-起不来--配置改了不生效)
- 日志无输出 → [09 症状 12](./09-排障速查手册.md#-症状-12collector-日志没有任何输出)
- 完整基线 → [`08-实战经验.md`](./08-实战经验.md#-落地--上线-checklist)

## 场景 8：要升级版本

**一句话**：dump 属性 diff，看板纳入版本控制，**弃用是静默的**。

### 约束清单

| 约束 | 怎么确认 | 不满足的后果 |
|---|---|---|
| 当前 semconv 版本 | 实测本机 **0.65b0**（含 beta 标记） | 无法判断升级影响 |
| 看板/告警用了哪些属性名 | 这些查询条件必须纳入版本控制 | 升级后看板少一半且无人知 |
| 升级涉及哪些域 | `OTEL_SEMCONV_STABILITY_OPT_IN` **分域独立** | 配了 `http` 管不了 `database` |

### 设计要点

**1. 升级前先 dump 一份属性清单**，升级后 diff。这是唯一能发现静默变更的方法——**弃用连 warning 都没有**。

**2. 用 `http/dup` 双写过渡**

实测 Flask 插桩五档对照：

| 档位 | 属性数 | 说明 |
|---|---|---|
| `default` | **13 个，其中 11 个是旧名** | 数据完全正常 |
| `http` | **10 个全新名** | 旧名全没了 |
| `http/dup` | **22 个**（13 旧 + 9 新） | 双写，体积翻倍 |
| `database` | 对 HTTP 属性**毫无影响** | 证明开关分域独立 |

```bash
export OTEL_SEMCONV_STABILITY_OPT_IN=http/dup   # 迁移期双写
```

**3. 主要迁移对照**

| 旧名 | 新名 |
|---|---|
| `http.method` | `http.request.method` |
| `http.status_code` | `http.response.status_code` |
| `http.url` | `url.full` |
| `http.target` | `url.path` + `url.query` |

**4. 稳定性必须按「信号 × 语言」逐格查**。看到"Logs 已 Stable"不代表能用——Python / JS 的 Logs SDK 仍是 Development，Go 是 Beta。

### 验收标准

- [ ] 升级前后属性清单已 diff
- [ ] 看板与告警的属性名已纳入版本控制
- [ ] 迁移期用 `http/dup` 双写，切档前确认查询条件已改为新名
- [ ] 已知晓 `OTEL_SEMCONV_STABILITY_OPT_IN` 分域独立
- [ ] 稳定性按「信号 × 语言」查过，不是只看规范层

### 回链

- 看板少一半 → [09 症状 7](./09-排障速查手册.md#-症状-7升级插桩库后看板少一半)
- 规范稳定 ≠ 全部稳定 → [08 反模式 6](./08-实战经验.md#高频反模式能跑但迟早出事)

## 场景 9：存量系统要渐进迁移

**一句话**：双发 → 桥接 → 灰度 → 收敛。**老应用一字不改**。

### 约束清单

| 约束 | 怎么确认 | 不满足的后果 |
|---|---|---|
| 存量系统是否还在迭代 | 冻结期系统迁移收益覆盖不了成本 | 白投入 |
| 老链路是否有自定义协议 | 决定用桥接还是双发 | 桥接接不住私有协议 |
| 灰度粒度 | 按服务 / 按流量百分比 | 无法回滚 |
| 双轨期有多长 | 两套并行 = 双倍成本 | 成本失控 |

### 设计要点

**1. 四步走**

| 步骤 | 做法 | 目标 |
|---|---|---|
| ① 双发 | 新老两条链路并行上报 | 验证新链路数据完整性 |
| ② 桥接 | 接收端做协议桥接，**老应用一字不改** | 应用零改动 |
| ③ 灰度 | 按服务或流量百分比切 | 可回滚 |
| ④ 收敛 | 摘掉老链路 | 成本回落 |

**2. 冻结期系统不要迁**。老系统即将下线或不再迭代，双轨期成本覆盖不了收益。

**3. 已有 Prometheus + Grafana 的团队**：不必全量迁移，OTel 可导出 Prometheus 格式，既有看板无需改动——从"新增服务用 OTel"开始渐进。

### 验收标准

- [ ] 双发期间两条链路数据量一致（差异 > 1% 要查）
- [ ] 桥接阶段老应用代码零改动
- [ ] 灰度可按服务或流量回滚
- [ ] 收敛后老链路已摘除，成本回落

### 回链

- 选型判据 → [`final-课程手册.md`](./final-课程手册.md#二选型决策条件)
- 不该上的信号 → [`08-实战经验.md`](./08-实战经验.md#什么时候不该上-otel)

## 场景 10：要接告警与看板

**一句话**：三个信号口径不同，**别混着算**。

### 约束清单

| 约束 | 怎么确认 | 不满足的后果 |
|---|---|---|
| 指标是否全量、trace 是否采样 | 实测 10000 请求、采样 0.1% → span 仅 **11 条**，count 仍是 **10000** | 值班误判为数据丢失 |
| 告警用的是哪个口径 | 指标算还是 trace 算 | P99 与体感不符 |
| 是否需要 exemplar 跳转 | 从指标跳 trace 的链接 | 采样率极低时 exemplar 可能一条都没有 |

### 设计要点

**1. 三个信号的口径差异（最容易误判的一条）**

| 信号 | 是否采样 | 含义 |
|---|---|---|
| 指标 | **全量** | count 恒等于真实请求数 |
| trace | **采样** | 只有被采样的能查到 |
| 日志 | 全量 | 但日志里的 trace_id **可能点不开** |

> ⚠️ **指标告警响了但 trace 搜不到，这是预期行为，不是故障**。实测 10000 次请求、采样率 0.1% 时被采样 span 仅 11 条，而 Histogram 的 `count` 仍是 10000。

**2. 在告警规则里写明口径差异**，避免值班误判。

**3. 降采样后 trace_id 在日志里仍然有效，但在后端点不开**——准确表述是这一句，团队里流传的"降采样会让日志关联失效"是**错的**（实测三组配置下日志带 trace_id 恒为 200/200）。

**4. 需要 exemplar 跳转时，按需求量反推采样率**——问题从"采样率怎么定"变成"**要多少条可跳转链接**"。

**5. P99 用指数桶算**。显式桶会把长尾低估（实测最坏 −50.0%），你会在监控上看到"还行"而放过真实问题。

### 验收标准

- [ ] 告警规则里写明了「指标全量、trace 采样」的口径差异
- [ ] 团队已知晓降采样后 trace_id **有效但点不开**
- [ ] P99 基于指数桶计算
- [ ] 关键请求已用头部采样强制保留
- [ ] exemplar 需求量已反推出采样率

### 回链

- 指标有数 trace 搜不到 → [09 症状 8](./09-排障速查手册.md#-症状-8指标告警响了trace-搜不到)
- 日志 trace_id 点不开 → [09 症状 6](./09-排障速查手册.md#-症状-6日志有-trace_id但点不开)
- P99 低估 → [09 症状 9](./09-排障速查手册.md#-症状-9p99-很健康用户却投诉慢)

## 🧭 跨场景的三条设计原则

1. **改动尽量收敛在 Collector**——换后端、脱敏、采样、过滤，都应该只改配置而不改应用代码。**凡是"必须改应用代码才能做成"的需求，先怀疑是不是设计错了**

2. **高基数是唯一的硬性约束**——成本、内存、序列数，几乎所有规模问题最后都会归结到基数。加任何字段前先问「能列进一张表吗」

3. **验证的唯一可信判据是后端**——不是退出码、不是 `force_flush()` 的返回值、不是"没有报错"。每个场景的验收标准第一条都是这一条
