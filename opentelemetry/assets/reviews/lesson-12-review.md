### 🔴 P1-2：11.4 把"查询耗时"与"排查总耗时"混淆，可能误导

**位置**：11.4 示例演示 → 实测排查耗时

**问题**：35.1 ms 是**机器查询**耗时，但表格下方直接推出"164 分钟 → 约 10 分钟"。若不显式区分，学员会以为"35 毫秒就能排查完"，这是过度承诺。

**修复**：已加警告块显式区分三层——

> ⚠️ **必须诚实说明**：这 35 ms 只是**查询耗时**，不是"排查总耗时"。人还要读、要判断、要决定加索引。

并在表格后追加：

> **注意那个"3 分钟没变"**：修复时间不会因为可观测性变好而缩短。**可观测性优化的是"找到根因"，不是"解决问题"。** 把 164 分钟说成"能变成 3 分钟"是不诚实的营销话术。

以及更保守的真实预期：**端到端通常 30～60 分钟（含发布验证流程）**。

## 事实核查专项（骨架硬性约束）

骨架要求：**Profiles 稳定状态必须重查**、**eBPF 在 WSL 的支持情况须实测**。

### 核查 1：Profiles 稳定状态

| 来源 | 状态 |
|------|------|
| 官方规范页 `opentelemetry.io/docs/specs/otel/profiles/` | **`Status: Alpha`** |
| 官方概念页 `opentelemetry.io/docs/concepts/signals/profiles/` | **`Status: Alpha`** |
| 概念页页脚变更记录 | `Last modified March 23, 2026: Update profiles status to Alpha (#9457)` |
| 官方语言 SDK 页 `opentelemetry.io/api/` | Go=Beta；Java/Python=Development；其余 `-`；**无 Stable** |
| Profiling SIG 公告 | "should not be used for critical production workloads" |

**结论：骨架记录的"目标 2026 Q3 GA"未兑现。** 2026-09-04 核查时仍为 Alpha，最后状态变更停留 2026-03-23（五个多月未推进）。

**冲突处置**：搜索中出现的二手文章称"已 Beta""GA 目标 Q4 2026"，**与官方一手来源冲突，讲义以官方为准并显式标注冲突**。

### 核查 2：WSL eBPF 支持情况

| 检查项 | 结果 |
|--------|------|
| WSL2 内核 | 6.6.87.2-microsoft-standard-WSL2 |
| `CONFIG_BPF_SYSCALL` | `y` |
| BTF `/sys/kernel/btf/vmlinux` | 存在，6,050,732 字节 |
| `CapEff` | `000001ffffffffff`（含 CAP_BPF + CAP_SYS_ADMIN） |
| `bpf()` 系统调用 | 可达（空 attr 返回 EINVAL=22，非 EPERM） |
| bcc 编译 + kprobe 挂载 | **成功**，6 秒捕获 180 次 clone 事件 |
| perf CPU_CLOCK 采样剖析 | **成功**，6 秒 11,877 样本 / 535 栈 |

**结论：骨架预判"可能不支持、须降级为认知层讲解"不成立——实测支持，已升级为真机演示。**
