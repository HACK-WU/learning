## 二 · 通用前提

### ⚠️ 四条必读

**1. 所有 Python 走 WSL**（Windows 无 Python 运行时）

```bash
wsl -d Ubuntu -- /root/otel-course/lab03/.venv/bin/python <脚本>
```

**2. PowerShell 会破坏内联 bash 的引号与重定向**

含 `|`、`>`、`$`、反引号的命令，一律写成 `.sh` 文件再执行。
本课踩过多次：`sed '$p'` 里的 `$` 被吃掉、`grep -A6` 的管道被 PowerShell 抢走、
`docker ps --format "{{.Status}}"` 的花括号被当代码块。

**3. 配置校验先用 `validate`，别直接起容器**

```bash
docker run --rm -v <conf目录>:/conf \
  otel/opentelemetry-collector-contrib:latest \
  validate --config /conf/xxx.yaml
```

无输出 = 通过（rc=0）。**已实测确认它真的在校验**：
故意写不存在的 processor 时返回 rc=1，并列出全部合法值。

**4. 管道截断用 PowerShell 的 `Select-Object`，不要用 WSL 内的 `head`**

```powershell
wsl -d Ubuntu -- <命令> | Select-Object -First 20
```

### 网络与容器

所有 Collector 容器接入 `otel-lab06-net`，Jaeger 在该网络内地址为 `jaeger-lab03`。

## 客户端

**文件**：`l10_send.py` ｜ **依赖**：`opentelemetry-sdk` + `opentelemetry-exporter-otlp-proto-grpc`

发送 3 条 span，分别用于验证不同效果：

| # | span | 携带 | 用途 |
|---|---|---|---|
| 1 | `GET /users/:id` | 旧 semconv 属性 + `user.email` + `authorization` + `db.statement` | 验证迁移与脱敏 |
| 2 | `GET /healthz` | `http.route=/healthz` | 验证 filter 丢弃 |
| 3 | `POST /orders` | `status_code=500`，无 `http.url` | 验证 `where` 守卫生效 |

```bash
PY=/root/otel-course/lab03/.venv/bin/python
wsl -d Ubuntu -- $PY /mnt/d/projects/learning/.probe/l10_send.py \
  --endpoint localhost:36337 --service my-test

# 参数
#   --endpoint    Collector OTLP gRPC 地址（默认 localhost:36317）
#   --service     service.name（每组实验用独立值，避免 Jaeger 按服务名累加）
#   --no-healthz  不发第 2 条
#   --sleep       flush 等待秒数（默认 3.0）
```

> ⚠️ **每组实验用独立 `service.name`**：Jaeger 按服务名累加，
> 复用同一个名字会让多组实验的数据混在一起（这是课 6 就踩过的坑）。

## 实验 2：脱敏 + 过滤

**文件**：`l10_e2_attributes.sh` ｜ **端口**：36327

处理器：`filter/healthz` → `attributes/sanitize`

实测效果（对比基线四处变化）：

| 效果 | 证据 |
|---|---|
| 过滤 | `/healthz` 消失（3 → 2 条） |
| delete 脱敏 | `authorization` **完全消失** |
| hash 脱敏 | `user.email` → SHA256 `ff8d9819...` |
| insert 富化 | 多出 `deployment.environment=prod` |

### 🔴 关键发现：attributes 做不了重命名

最初按课 9 的思路写了 `action: update` + `new_key`，直接被拒：

```
'actions[3]' has invalid keys: new_key
```

枚举全部 action 后确认 0.160.0 只支持 7 个：

| action | 是否接受 value | 说明 |
|---|---|---|
| `insert` | 是 | 不存在才加 |
| `update` | 是 | 存在才改 |
| `upsert` | 是 | 都行 |
| `delete` | **否** | 删除 |
| `hash` | **否** | SHA256 哈希 |
| `extract` | 否（用 pattern） | 正则抽取 |
| `convert` | 否（用 converted_type） | 类型转换 |

**`rename` / `move` / `copy` 都不存在。**
这正好印证课 9 的 4.2 结论：**重命名是 transform 的活。**

> 💡 复现方法（`l10_probe_actions.sh`）：逐个 action 试 validate，看是否被拒。

## 实验 3：语义迁移（课 9 遗留配置落地）

**文件**：`l10_e3_transform.sh` ｜ **端口**：36337

这是**本课最有价值的一项**：课 9 的 `l9-semconv-migrate.yaml` 只写了 1:1 改名，
1:N 拆分被注释掉了（原话："真实配置须用 regex 或 split，见课 10 的 9.3"）。
本实验补齐了它。

### 实测结果

```
输入：http.target=/users/42?page=1
输出：url.path=/users/42  +  url.query=page=1     ← 1:N 拆分首次跑通

1:1 改名：http.method          → http.request.method
          http.status_code     → http.response.status_code
          http.url             → url.full
          db.statement         → db.query.text
```

**幂等性验证**：`POST /orders` 没有 `http.url`，输出里就没有 `url.full`——
`where` 守卫正确阻止了空转。

### 🔴 关键发现：OTTL 写法与直觉不同

试了 5 种写法，只有 2 种可用：

| 写法 | 结果 |
|---|---|
| `Split(attr, "?")[0]` | ✅ 可用 |
| `split(attr, "?")[0]`（小写） | ❌ 函数不存在（**大小写敏感**） |
| `attr matches "\\?"` | ❌ **没有 `matches` 操作符** |
| `ExtractPatterns(...).p` | ❌ 语法错误（点号取值不支持） |
| `IsMatch(attr, "\\?")` | ✅ 可用（正则条件判断用这个） |

> 💡 复现方法（`l10_probe_ottl.sh`）。

### 迁移其它属性时

课 9 核对过官方有 **14 条** HTTP 弃用属性，本实验只迁移了 4 条。
补其余规则时注意：

- 1:1 的照抄本实验的 `where` 守卫模式
- `http.target` 用 `Split`
- `http.host` 是 1:3 带条件迁移，**无法用纯 OTTL 表达**，需人工判断语义

## 实验 4：完整管道 + 顺序敏感

**文件**：`l10_e4_pipeline.sh` ｜ **端口**：36347（正确）/ 36357（错误顺序）

正确顺序：

```yaml
processors: [filter/healthz, transform/semconv, attributes/sanitize, resource/env, batch]
```

| 顺序 | 组件 | 理由 |
|---|---|---|
| 1 | `filter` | 先丢噪声，减少后续处理量 |
| 2 | `transform` | 语义迁移 |
| 3 | `attributes` | **脱敏必须在迁移之后** |
| 4 | `resource` | 资源级富化 |
| 5 | `batch` | 攒批靠近 exporter |

### 对照实验证明顺序敏感

两个配置唯一区别：脱敏和迁移的先后。

| 组 | 顺序 | 结果 |
|---|---|---|
| A | `filter → transform → attributes` | 脱敏生效，`authorization` 消失 |
| B | `attributes → transform` | **`url.query=page=1` 依然存在** |

B 组为什么漏：脱敏规则要删 `url.query`，但它跑在 transform 之前，
而 `url.query` 恰恰是 transform 生成的。

> 📌 **这是"配置里明明写了脱敏、实际却漏了"的典型。**
> 排查顺序问题时，看输出里那个属性是在哪一步被创建的。

## 实验 5：换后端不改代码

**文件**：`l10_e5_backend.sh` ｜ **端口**：36367（Jaeger）/ 36377（file）

两个 Collector 的 `receivers` 部分**完全相同**，只有 exporter 不同：

```yaml
# 后端 1
exporters:
  otlp/jaeger:
    endpoint: jaeger-lab03:4317
    tls:
      insecure: true

# 后端 2
exporters:
  file:
    path: /out/traces.jsonl
```

实测：同一个 `l10_send.py`（应用侧零改动）打到两个 Collector，两个后端都收到数据。

### 🔴 两个环境坑

**坑 1：file exporter 不能输出到 `/mnt/d`**

```
error: can't set mode on new logfile /out/traces.jsonl:
       chmod /out/traces.jsonl: operation not permitted
```

file exporter 创建文件后会 `chmod`，而 Windows 的 9P 文件系统不支持。

**坑 2：也不能用 `/root` 下的目录**

```
error: open /out/traces.jsonl: permission denied
```

`/root` 是 700 权限，而容器内以非 root 用户运行。

**解法**：用 `/var/tmp/l10out` 这类权限宽松的 **WSL 原生 ext4** 目录。

## 实验 6：富化

**文件**：`l10_e6_enrich.sh` ｜ **端口**：36387

**A. 静态富化（实测有效）**

```yaml
resource/static:
  attributes:
    - key: deployment.environment
      value: prod
      action: upsert
    - key: service.namespace
      value: shop
      action: upsert
    - key: cloud.region
      value: ap-guangzhou
      action: upsert
```

实测资源属性多了三项。**注意加在 Resource 上**（服务级），不是 span 上（请求级）。

**B. k8sattributes（只验配置）**

```yaml
k8sattributes:
  auth_type: serviceAccount
  extract:
    metadata: [k8s.pod.name, k8s.namespace.name, k8s.deployment.name, k8s.node.name]
  pod_association:
    - sources:
        - from: resource_attribute
          name: k8s.pod.ip
```

> ⚠️ **本机无 K8s 集群**，此配置仅通过 `validate`，**未验证实际富化效果**。
> 生产使用前必须在真实 K8s 环境验证。

## 实验 7：稳定性加固

**文件**：`l10_e7_reliability.sh` ｜ **端口**：36397 / 13133 / 1777

```yaml
processors:
  memory_limiter:
    check_interval: 1s
    limit_percentage: 80
    spike_limit_percentage: 20
  batch:
    send_batch_size: 100
    timeout: 5s

extensions:
  health_check:
    endpoint: 0.0.0.0:13133
  pprof:
    endpoint: 0.0.0.0:1777
```

实测（容器限内存 512MiB）：

```
Memory limiter configured  total_memory_mib=512
                           limit_mib=409  spike_limit_mib=102  check_interval=1
```

health_check：

```
GET /  →  {"status":"Server available","upSince":"...","uptime":"8.29s"}
```

> 🔴 **为什么必须用百分比**：容器里 `limit_mib: 400` 读的是**宿主机内存**，
> 不是容器限额。上面日志证明用百分比时正确读到了 512MiB 并算出 409MiB。

## 五 · 常见组合流程

**场景 1：搭一条新管道**

```bash
# 1. 先跑最小管道确认通路
bash l10_e1_minimal.sh
# 2. 发数据看基线
python l10_send.py --endpoint localhost:36317 --service baseline
# 3. 加 processor，每次加一个，用 validate 校验后再起容器
# 4. 对照基线输出确认效果
python l10_logs.py <容器名>
```

**场景 2：排查"脱敏配了但没生效"**

```bash
# 按这个顺序查：
# ① 属性名对不对（脱敏名单用的是迁移前还是迁移后的名字？）
# ② processor 顺序对不对（脱敏是否在 transform 之后？）
# ③ delete/hash 是否误加了 value 字段（会被拒）
# 复现对照实验：
bash l10_e4_pipeline.sh   # e4a 正确 vs e4b 错误
```

**场景 3：升级 Collector 前**

```bash
# 1. 查当前用到的组件稳定性等级
python l10_parse_components.py
# 2. 查是否有相关 CVE（官方页面 + GHSA）
# 3. 查组件是否改名（新旧名目前都可用，但新配置用新名）
bash l10_probe_names3.sh
# 4. 用 validate 校验现有配置
docker run --rm -v <conf>:/conf <新版本镜像> validate --config <path>
```
