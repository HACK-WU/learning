所有脚本都在 `D:/projects/learning/.probe/`，配置文件在 `D:/projects/learning/.probe/l11conf/`。

### 运行环境

```bash
# Python 脚本用 WSL 里的虚拟环境
wsl -d Ubuntu -- /root/otel-course/lab03/.venv/bin/python /mnt/d/projects/learning/.probe/<脚本>.py

# Shell 脚本（推荐这样跑，避免 PowerShell 抢管道）
wsl -d Ubuntu -- bash /mnt/d/projects/learning/.probe/<脚本>.sh
```

> ⚠️ **PowerShell 会破坏 bash 命令**（本课踩到第 3 次）：`grep -A6` 的管道被抢、
> `$(...)` 被当变量、`> /dev/null` 被当成 Windows 路径。
> **一律写成 `.sh` 文件执行**，不要在 PowerShell 命令行里直接拼 bash。

## 二、可复用工具（8 个）

### 1. `l11_cost.py` —— 成本估算模型 ⭐ 最常用

**用途**：把课 11 的成本公式变成可计算、可改参数的工具。

```bash
# 四档预设场景对比（推荐第一次跑这个）
python l11_cost.py --scenario all

# 只跑一档预设
python l11_cost.py --scenario mid

# 代入自己的参数
python l11_cost.py --services 80 --qps 30 --spans 12 --sample 0.05 --filter-rate 0.4
```

**参数表**：

| 参数 | 含义 | 默认值 | 怎么得到 |
|------|------|-------|---------|
| `--scenario` | 预设场景 small/mid/large/naive/all | mid | — |
| `--services` | 服务数 | 随场景 | 数一遍 |
| `--qps` | 每服务 QPS | 随场景 | 监控里的 RPS |
| `--spans` | 每请求 span 数 | 随场景 | 抽样看几条 trace |
| `--bytes-per-span` | 每 span 字节 | **600** | **实测：落盘字节 ÷ span 数** |
| `--sample` | 采样率 | 随场景 | 你的采样配置 |
| `--filter-rate` | 过滤率 | 随场景 | 你的 filter 配置 |

**输出**：四档场景的日均/年化/月成本 + Cardinality 基数表 + 杠杆排序。

**可迁移场景**：任何需要估算可观测性支出的场合；换后端只需改单价。
**注意**：`--bytes-per-span` 的 600 B 是假设开了压缩（实测未压缩是 959 B）。
**务必代入自己实测的值**。

### 2. `l11_send.py` —— 实验客户端 ⭐ 最常用

**用途**：向任意 Collector 发送可预测的三类 span（正常/噪声/异常），用于观察治理效果。

```bash
# 默认：20 业务 + 10 healthz + 4 个 500 错误
python l11_send.py --endpoint http://localhost:37318 --service my-test

# 实验 3 用法：150 条业务 span，user.id 分布在 50 个值上
python l11_send.py --endpoint http://localhost:37367 --service l11-card \
  --normal 150 --healthz 0 --bad 0 --users 50
```

**参数表**：

| 参数 | 含义 | 默认值 |
|------|------|-------|
| `--endpoint` | Collector OTLP HTTP 端点 | `http://localhost:37318` |
| `--service` | service.name（**多组实验务必不同**） | `l11-demo` |
| `--normal` | 正常业务 span 数 | 20 |
| `--healthz` | `/healthz` 噪声 span 数 | 10 |
| `--bad` | 慢/错 span 数（500 + duration_ms） | 4 |
| `--users` | >0 时给每条 span 打 `user.id`（高基数维度） | 0 |
| `--mode` | `simple`（立即导出）或 `batch` | `simple` |

**为什么默认用 `simple`**：`batch` 模式是异步的，会干扰实验计数。做性能测试时才用 `batch`。

**可迁移场景**：任何需要给 Collector 灌测试数据、验证 filter/sampler 效果的场合。

---

### 3. `l11_components.py` —— 组件稳定性解析器 ⭐ 修掉了课 10 的坑

**用途**：按 `kind` 分区解析 `otelcol components` 输出，输出目标组件的稳定性等级。

```bash
python l11_components.py
python l11_components.py otel/opentelemetry-collector-contrib:0.160.0
```

**为什么需要它**：课 10 用 awk 提取时，因为 `prometheus` 在 receivers 和 exporters 段同名，
把 `filter` 的 Alpha 误读成了 Beta。这个脚本按 kind 分区，杜绝抓错行。

**输出示例**：

```
receivers   otlp                       logs=Stable,  metrics=Stable, traces=Stable
processors  filter                     logs=Alpha,   metrics=Alpha,  traces=Alpha
processors  transform                  logs=Beta,    metrics=Beta,   traces=Beta
processors  tail_sampling              logs=Undefined, metrics=Undefined, traces=Beta
processors  probabilistic_sampler      logs=Alpha,   metrics=Undefined, traces=Beta
extensions  health_check               extension=Alpha
```

**可迁移场景**：升级 Collector 版本后核对组件稳定性；评估某个组件能否上生产。

### 4. `l11_list_all.py` —— 组件名清单

**用途**：列出全部组件名，用于核实"某个组件到底存不存在、叫什么名字"。

```bash
python l11_list_all.py
python l11_list_all.py k8s loadbal sampl
```

**为什么需要它**：本课发现**凭记忆写组件名必错**——
实际是 `k8s_attributes`（不是 `k8sattributes`）、`load_balancing`（exporter，不是 processor）、
`span_metrics`/`service_graph`（connector，不是 processor）。

**可迁移场景**：写配置前先确认组件名；排查"unknown type"报错。

### 5. `l11_query.py` —— Jaeger 落库统计

**用途**：查询指定 service 在 Jaeger 里的 trace/span 数，以及 `/healthz`、500 错误的条数。

```bash
python l11_query.py l11-topoA l11-topoB l11-topoC
```

**输出**：

```
service        traces     spans      healthz    bad500
------------------------------------------------------------
l11-topoA      34         34         10         4
l11-topoB      34         34         10         4
l11-topoC      14         14         0          3
```

**可迁移场景**：验证 filter/sampler 是否真的减少了落库量。
**注意**：Jaeger 按服务名累加，多组实验必须用不同的 `service.name`。

---

### 6. `l11_validate.sh` —— 批量配置校验

**用途**：一次校验多个 Collector 配置。

```bash
bash l11_validate.sh
```

**输出**：每个文件一行 `[validate OK]` 或 `[validate FAIL]` + 错误详情。

**可迁移场景**：改配置后的第一道检查。
**注意**：validate 只查结构和字段名，**不查业务逻辑**（filter 条件写反了它查不出来）。

---

### 7. `l11_negative.sh` —— 反例验证 ⭐ 方法论工具

**用途**：确认 `validate` 的"通过"是可信的。

**为什么需要它**：`validate` 无输出 + rc=0 就代表通过——但"无输出"本身就不可信。
必须造反例确认它真在校验。

```bash
bash l11_negative.sh
```

**它造的两个反例**：

| 反例 | 做法 | 期望 |
|------|------|------|
| `l11-bad-processor.yaml` | 引用不存在的 processor | rc=1，且列出全部合法值 |
| `l11-bad-ottl.yaml` | OTTL 写成小写 `split()` | rc=1，报 converter 名必须大写 |

**可迁移场景**：任何"工具说通过但我还不确定"的场合。这是课 10 沉淀的方法论，本课复用。

---

### 8. `l11_k8s_probe.sh` —— K8s 可行性评估

**用途**：评估一台机器能不能跑起 K8s 集群（决定要不要做 Operator 实测）。

```bash
bash l11_k8s_probe.sh
```

**检查项**：已有工具 / kind 可用性 / docker.sock / 内存 CPU / 节点镜像可拉取性。

**可迁移场景**：换机器做 K8s 实验前的预检。
**注意**：kind 需要约 **16 GB 可用内存**（本课机器 31.8 GB 总内存、16 GB 可用）。

## 六、组合流程

### 流程 A：验证一个 filter 到底省了多少

```bash
# 1. 改配置里的 filter 条件
vim l11conf/l11-e2-filtercost.yaml

# 2. 同步 + 校验 + 反例确认 + 跑实验（一步到位）
bash l11_e2_filtercost.sh

# 3. 看输出的两个文件大小
#    过滤率 = 1 - (filtered / nofilter)
```

### 流程 B：评估一个维度该不该加进指标

```bash
# 1. 起两个 Collector，唯一变量是 dimensions
bash l11_e3_final.sh

# 2. 看序列数比值
#    序列数比 = 高基数序列数 / 低基数序列数 = user_id 的基数
```

### 流程 C：排查"我的自动注入没生效"

```bash
# 1. CR 在吗？（必须早于应用）
kubectl --context kind-otel-l11 get instrumentation -n <ns>

# 2. init container 在吗？
kubectl --context kind-otel-l11 get pod -n <ns> -l app=<app> \
  -o jsonpath='{range .items[*]}init={range .spec.initContainers[*]}{.name}{end}{"\n"}{end}'

# 3. 环境变量对吗？
kubectl --context kind-otel-l11 exec -n <ns> deploy/<app> -- env | grep OTEL_

# 4. agent 加载了吗？（报 "Overriding of current TracerProvider" 就是加载了）
kubectl --context kind-otel-l11 exec -n <ns> deploy/<app> -- python -c "
from opentelemetry import trace
from opentelemetry.sdk.trace import TracerProvider
trace.set_tracer_provider(TracerProvider())"

# 5. 框架在覆盖范围内吗？（换 Flask 试试）
```
