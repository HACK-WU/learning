## 🚫 适用边界与反模式

### 什么时候不该上 OTel

**先找"不该上"的信号**——这些情形上 OTel 是净亏损：

- **单服务单后端，且短期没有换后端的打算**。直接插桩到该后端更省事，Collector 这一层是纯成本
- **团队无法接受 Collector 的运维成本**。多一层_stateful 组件就多一份故障面，先解决运维能力再谈架构
- **你要的是"开箱即用的告警规则与看板模板"**。那是商业 APM 或后端产品的职责，OTel 不构成可观测性，**它只解决"数据怎么出来"**
- **存量系统处于冻结期**。老系统即将下线或不再迭代，迁移收益覆盖不了双轨期的成本

**该上的信号**：

- 在用多个后端，或在考虑换后端（换后端 = 改一行配置，不是改几百个服务的代码）
- 跨语言技术栈，需要统一的插桩与命名
- 被"三个控制台来回切"折磨过——这就是课 1 那 164 分钟
- 需要在**不改应用代码**的前提下做脱敏、过滤、采样、富化

> 📌 **最常见的误判**：把 OTel 当成"Prometheus / Jaeger 的替代品"。错在混淆了三层——OTel 覆盖**采集层（第 1 层）与管道层（第 2 层）**，不覆盖**存储分析层（第 3 层）**。**你替换的是前两层，第三层该用什么还用什么。**

### 高频反模式（能跑，但迟早出事）

**反模式 1：把 OTel 当后端用**

表现：问"OTel 的看板在哪""OTel 怎么配告警"。
后果：期待落空后判定"OTel 不好用"。
正解：OTel 是管道，终端必须有 Jaeger / Prometheus / Loki / 商业后端。**Collector 的 `debug` exporter 只能看数据长什么样，不能当查询界面。**

**反模式 2：自动插桩一把梭，不补手动**

表现：`opentelemetry-instrument` 一挂就以为完事了。
后果：只知道框架层（HTTP、DB 客户端），不知道**业务语义**——哪个用户、哪笔订单、走了哪个分支。出事时看得见"HTTP 500"，看不见"是风控规则 R-17 拒的"。
数据：实战项目里定位 N+1 靠的正是手动加的 `db.query.rule` 属性。
正解：**自动插桩给你骨架，手动插桩给你血肉**；在业务黑洞处补手动。

**反模式 3：头尾采样串联，以为双保险**

表现：SDK 设 `trace_id_ratio=0.1`，Collector 再挂 `tail_sampling`。
后果：head 已丢的 90% 根本走不到 Collector，tail 只能在残羹里挑。实测普通 trace 保留数从纯尾部的 8/100 掉到 **0/100**。
正解：**要用尾部采样，SDK 必须 `always_on`**，把决策权完整交给 Collector。

**反模式 4：高基数字段塞进指标标签**

表现：`user.id`、`order.id`、`url.path` 直接做 attribute。
后果：序列数爆炸。实测 5 路由 × 3 状态码 = 15 条，加 10000 个 `user.id` 变成 **150,000 条**，**放大倍数恒等于加进去的维度基数**。指标每个序列常驻内存且只要还在上报就永不释放。
正解：**能列进一张表的字段才能放进指标标签**。高基数字段放日志或链路属性。

**反模式 5：只看"程序有没有报错"**

表现：跑完脚本看到退出码 0 就认为数据到了。
后果：本课记录 **9 个静默失败**，全部是"每一层都成功、只有后端知道数据没了"。
正解：**唯一可信判据是后端**。详见[故障模式 1](#故障模式-1程序没报错但后端一条数据都没有)。

**反模式 6：规范稳定 = 全部稳定**

表现：看到"Logs 已 Stable"就上生产。
后果：Python / JS 的 Logs SDK 仍是 Development，Go 是 Beta；本机 semconv 包还是 **0.65b0**。
正解：**稳定性必须按「信号 × 语言」逐格查**；说"稳定"必须指明是哪一层。

**反模式 7：Collector 多副本直接做尾部采样**

表现：Gateway 层起 3 个副本分担流量，配 `tail_sampling`。
后果：**同一 trace 的 span 散落在不同 Collector 实例，每个实例都看不到完整 trace**，尾部决策直接失效——错误 trace 静默消失。两个 Collector 日志都只有 `Everything is ready`，毫无异常。
正解：第一层用 **load balancing exporter** 按 trace_id 做一致性哈希，保证同一 trace 的 span 落到同一个第二层实例。

> ⚠️ **这是与反模式 3 不同的独立触发条件**：反模式 3 是「SDK 先丢了一刀」，本条是「Collector 自己把 trace 拆散了」。两者都会让尾部采样失效，但根因与解法完全不同，**别混着记**。

**反模式 8：Processor 顺序随手排**

表现：脱敏写在 transform 迁移前面。
后果：transform 新生成的 `url.query` 躲过脱敏，PII 直接外泄。
正解：**脱敏必须排在 transform 迁移之后**。已实证（课 10 对照实验 e4a / e4b）。

**反模式 9：把 Profiles 放进关键定位链路**

表现：因为"第四信号听起来高级"就依赖它排障。
后果：Profiles 仍为 **Alpha**，官方明确不建议用于关键生产负载；且本机 Collector 0.160.0 **没有 profiles pipeline**。
数据：实战项目三种故障全部靠 trace + metric 定位成功，eBPF 只到"python3 占 5% CPU"这个进程级结论。
正解：非关键环境试点等 GA，不要放进关键链路。

## 🔥 高频故障模式



### 故障模式 1：程序没报错，但后端一条数据都没有

- **症状（可观测）**：应用正常退出、退出码 0、`force_flush()` 返回 **True**；后端 `GET /api/services` 里**没有你的 service**，或显示 `unknown_service`；无任何 ERROR 日志
- **根因**：OTel 倾向于用 **warning 而不是异常**来处理"你不该这么做"的调用。三种典型触发：
  - **协议错配**：`OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4318` **不会**自动切成 HTTP（默认 gRPC），报 `Failed parsing HTTP/2` 但程序照常返回 200
  - **端口错配**：4317（gRPC）与 4318（HTTP）不可混用；HTTP 路径必须带 `/v1/traces`
  - **缺 distro**：只装 `opentelemetry-instrumentation` 而没装 `opentelemetry-distro` 时，`opentelemetry-instrument` **只加载插桩库、不配置 SDK 导出器**，provider 仍是 `ProxyTracerProvider`、`trace_id=0`

  实测（课 3）：五种错误配置下 `force_flush()` **全部返回 `True`**，数据**全部静默丢弃**。
  实测（课 5）：缺 distro 时 `is_recording=False`，装上后 Resource 多出 `telemetry.auto.version=0.65b0`——**这是自动插桩指纹，可作为是否生效的判据**。

- **排查路径**：
  1. **先查后端，不要看日志**。`GET /api/services` 有没有你的 `service.name`？没有 → 插桩或导出环节断了
  2. 服务名显示为 `unknown_service` → `service.name` 没设（环境变量或代码二选一）
  3. 检查协议与端口是否成对：gRPC→4317，HTTP→4318 **且路径带 `/v1/traces`**
  4. 自动插桩场景查 Resource 里有没有 `telemetry.auto.version`，没有就是缺 distro
  5. 手动插桩场景查 provider 类型：是 `ProxyTracerProvider` 说明 `set_tracer_provider` 没生效（**注意：不是 `NoOpTracerProvider`**，老教程的说法在 1.44.0 上已过时）
- **修复**：显式设 `OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf`；自动插桩场景补装 `opentelemetry-distro`
- **预防**：**把"跑通 ≠ 送到"定为团队第一约定**。任何验证脚本的最后一步必须是查后端，不能是看退出码。这条贯穿 12 课，是 OTel 实践的第一方法论

> 对应速查条目：`09-排障速查手册.md` · 症状 1（待产出）

### 故障模式 2：数据在 Collector 收到了，后端却查不到

- **症状（可观测）**：应用侧全程无感知；Collector 日志显示正常接收；但后端对应信号**条数为 0**
- **根因**：**导出器成功、Collector 收到、数据在后端被静默丢弃**。三层各自"成功"，只有最后一层知道数据没了，而它说话的声音传不到你耳朵里。

  实测（课 8）：Jaeger 对 `/v1/logs` 返回 **404 Unimplemented**，Collector 侧显示 `n_spans=1 / n_logs=0`，应用侧退出码 0、无任何报错。

- **排查路径**：
  1. 先确认 Collector 收到没有——用 `debug` exporter 或看 Collector 日志的接收计数
  2. 收到了但后端没有 → **查后端是否支持该信号**。这是最容易被忽略的一层：不是所有后端都收所有信号
  3. 三个信号分别验证：trace / metric / log 各查一次，不要因为 trace 通了就认为 log 也通
- **修复**：为该信号换一个支持它的后端（日志走 Loki / ELK，不要把日志发给 Jaeger）
- **预防**：**接入新信号时，先单独验证"后端收不收"，再谈字段与关联**。课 8 的第二幕困惑全部源于把"后端不收"误判为"关联没配好"

> 对应速查条目：`09-排障速查手册.md` · 症状 2（待产出）

### 故障模式 3：采样配了，但数据一点没少（静默全量）

- **症状（可观测）**：配了 `trace_id_ratio` 采样，后端 span 数**没有下降**；成本账单照旧；无任何报错
- **根因**：**采样器名写错或参数非法 → 静默回退全量**。这是最容易误解的一种失败——它不是"数据丢了"，而是"省钱配置彻底失效"，你以为在采样，其实在全量收。

  实测（课 6）：`trace_id_ratio` 拼错 → 回退成 `ParentBased`；`ARG=not-a-number` → 回退成 **1.0（全量）**。

- **排查路径**：
  1. **去后端核对实际保留率**，这是唯一可信判据。算一下：预期保留数 vs 实际保留数
  2. 采样器名逐字核对（是 `trace_id_ratio` 不是 `traceidratio`）
  3. 环境变量参数是否为合法数字
  4. 确认采样决策发生在哪一层：SDK（头部）还是 Collector（尾部）
- **修复**：修正采样器名与参数；用后端实测保留率反推验证
- **预防**：**采样配置变更必须做"保留率回归"**——改完配置去后端数一遍，而不是看配置写对了就算完。**同样是静默失败，这一类方向相反**：它不丢数据，它烧钱

> 对应速查条目：`09-排障速查手册.md` · 症状 3（待产出）

### 故障模式 4：头尾采样串联后，错误 trace 反而消失了

- **症状（可观测）**：挂了 `tail_sampling` 想保住全部错误 trace，结果错误 trace 保留数**远低于预期**，甚至不如纯头部采样
- **根因**：**head 已经丢掉的 90% 根本走不到 Collector**，tail 只能在残羹里挑。这是双重代价，不是双保险。

  实测（课 6，同批 300 条 trace：100 错误 / 100 慢 600ms / 100 普通）：

  | 配置 | 错误 | 慢 | 普通 |
  |------|------|-----|------|
  | 纯尾部 | **100/100** | **100/100** | 8/100 |
  | 纯头部 10% | 11/100 | 12/100 | 10/100 |
  | **head 10% + tail** | **11/100** | 12/100 | **0/100** |

  多副本场景还有第二个根因：同一 trace 的 span 散落在不同 Collector 实例，**每个实例都看不到完整 trace**，尾部决策直接失效。

- **排查路径**：
  1. 查 SDK 侧采样配置——**要用尾部采样，SDK 必须是 `always_on`**
  2. 多副本场景查 span 是否按 trace_id 路由到了同一实例
  3. 用后端实测保留率倒推：错误 trace 保留数应接近 100%，不是 11%
- **修复**：SDK 设 `always_on`；两层 Collector + **load balancing exporter** 按 trace_id 一致性哈希
- **预防**：**把"SDK 与 Collector 的采样职责"写成一行注释放在配置里**。这两层谁做什么，接手的人三秒内必须看懂

> 对应速查条目：`09-排障速查手册.md` · 症状 4（待产出）

### 故障模式 5：降采样后，日志里的 trace_id 点不开了

- **症状（可观测）**：日志 100% 带 `trace_id` 字段，但在后端点击跳转**显示"未找到该 trace"**
- **根因**：**日志关联与 exemplar 用的是两个不同判据**。
  - 日志关联判据：**span context 是否有效**
  - exemplar 判据：**SAMPLED 位是否置位**

  `always_off` 是"创建 span 但不置 SAMPLED 位"，所以 trace_id 有效而 exemplar 不生成。

  实测（课 8，三组子进程隔离，每组 200 次请求）：

  | 采样配置 | 采样 span 数 | 日志带 trace_id | exemplar |
  |---------|-------------|----------------|----------|
  | `always_on` | 200/200 | **200 条（100%）** | 有 |
  | `ratio_10pct` | 25/200 | **200 条（100%）** | 少 |
  | **`always_off`** | 0/200 | **200 条（100%）** | **0** |

- **排查路径**：
  1. 确认日志里 trace_id 是否有值——**有值说明关联本身没坏**
  2. 去 trace 后端直接用该 trace_id 搜索，确认是不是这条 trace 没被采样
  3. 区分两个问题：**"日志关联失效"（trace_id 为空）** vs **"trace 点不开"（trace_id 有效但该 trace 未采样）**
- **修复**：这是预期行为，不是 bug。若要保证关键请求可跳转，对该类请求用**头部采样强制保留**（`ParentBased` + 自定义 sampler）
- **预防**：**修正团队里流传的误解——"降采样会让日志关联失效"是错的**。准确说法是：降采样不丢日志与请求的对应关系，**但那个 trace_id 在后端点不开**

> 对应速查条目：`09-排障速查手册.md` · 症状 5（待产出）

### 故障模式 6：升级插桩库后，看板数据少了一半

- **症状（可观测）**：升级 `opentelemetry-instrumentation-*` 后，看板曲线**突然少一半**或查询条件全部失效；数据本身看起来正常，无任何报错
- **根因**：**语义约定属性名变更，且弃用是静默的——连 warning 都没有**。

  实测（课 9，Flask 插桩 5 档）：

  | 档位 | 属性数 | 说明 |
  |------|--------|------|
  | default | **13 个，其中 11 个是旧名** | 数据完全正常 |
  | `http` | **10 个全新名** | 旧名全没了 |
  | `http/dup` | **22 个**（13 旧 + 9 新） | 双写，体积翻倍 |
  | `database` | 对 HTTP 属性**毫无影响** | 证明开关分域独立 |

  主要迁移：`http.method`→`http.request.method` ｜ `http.status_code`→`http.response.status_code` ｜ `http.url`→`url.full` ｜ `http.target`→`url.path` + `url.query`

- **排查路径**：
  1. 先查是不是属性名变了——把 span 属性 dump 出来对比新旧版本
  2. 查 `OTEL_SEMCONV_STABILITY_OPT_IN` 当前档位（**注意分域独立**，`http` 管不了 `database`）
  3. 用 `http/dup` 档双写过渡，同时保留新旧两套名
  4. 看板/告警规则里的查询条件逐个改成新名
- **修复**：短期用 `http/dup` 双写；长期改查询条件到新名后切 `http` 档
- **预防**：**把"升级插桩库"当作变更管理，不是依赖更新**。升级前 dump 一份属性清单做 diff；看板与告警规则的属性名要纳入版本控制

> 对应速查条目：`09-排障速查手册.md` · 症状 6（待产出）

### 故障模式 7：指标说有问题，trace 却找不到

- **症状（可观测）**：告警响了（错误率/延迟超阈值），按时间去 trace 后端搜，**找不到对应的 trace**
- **根因**：**指标永不采样，trace 被采样了**。两者统计口径天然不同。

  实测（课 7）：10000 次请求、trace 采样率 0.1% → 被采样 span 仅 **11 条**（0.11%），Histogram 的 `count` 仍是 **10000**（全量），exemplar 仅 **1** 条。

- **排查路径**：
  1. **这不是故障，是采样链路的诊断信号**。看到这个现象先确认采样率，不要怀疑数据丢了
  2. 从指标反查 trace 时，优先用 **exemplar**（指标→trace 的跳转链接）——但要注意 exemplar 数量与采样率成正比，采样率低时 exemplar 很少
  3. 采样率极低时，exemplar 可能一条都没有。**此时提高采样率或用头部采样强制保留该类请求**
- **修复**：按 exemplar 需求量反推采样率——问题从"采样率怎么定"转化为"**要多少条可跳转链接**"
- **预防**：**在告警规则里说明"指标全量、trace 采样"这个口径差异**，避免值班同学误判为数据丢失

> 对应速查条目：`09-排障速查手册.md` · 症状 7（待产出）

### 故障模式 8：P99 看起来很健康，但用户投诉很慢

- **症状（可观测）**：监控显示 P99 在正常范围，用户持续投诉超时
- **根因**：**显式桶 Histogram 的边界设置导致长尾被低估，且方向是低估**。

  实测（课 7，5 场景 × 10000 样本，真实 SDK 聚合）：显式桶 P99 最坏误差 **−50.0%**（E 场景 20s 被砍成 10s），指数桶最坏 **−2.2%**。

  **低估比高估危险得多**——高估会让你虚惊一场，低估让你在监控上看到"还行"而放过真实问题。

- **排查路径**：
  1. 查 Histogram 用的是显式桶还是指数桶
  2. 显式桶场景：查最大桶边界是否覆盖了真实最大值。**超出最大桶的值会被算进最大桶，用桶上界代表它**
  3. 对比原始数据算出的 P99 与监控显示值
- **修复**：改用 **Exponential Histogram**（自适应，实测窄区间场景 scale 自动从 3 升到 8，E 场景仅 2 个非空桶且按需分配）；或重新设定显式桶边界
- **预防**：**新指标显式配指数桶**。显式桶只在你知道精确分布区间、且需要跨系统对齐固定边界时才用

  > ⚠️ **「默认」不是指数桶**（本机实测 2026-09-04，Python SDK 1.44.0）：不配 `View` 时得到的是**显式桶、15 个默认边界**（`0, 5, 10, 25, 50, 75, 100, 250, ...`）。指数桶**必须显式配 `View` + `ExponentialBucketHistogramAggregation()`**，光省略参数是没用的。聚合类导入路径为 `opentelemetry.sdk.metrics.view`；`create_histogram()` 的参数名是 `explicit_bucket_boundaries_advisory`（带 `_advisory`，意为"建议值"，最终用不用由 View 决定）。详见 [`09-排障速查手册.md`](./09-排障速查手册.md) 症状 9。

> 对应速查条目：`09-排障速查手册.md` · 症状 8（待产出）

### 故障模式 9：最慢的 span 不是问题所在

- **症状（可观测）**：按最慢单个 span 排序，指向某个服务；照着优化后**端到端延迟没有任何改善**
- **根因**：**N+1 类问题的每一次调用都不慢，异常的是次数本身**。

  实测（实战项目）：端到端 2616 ms（正常 140 ms），span 总数 **15 → 214**。

  | 视角 | 结果 | 为什么错 |
  |------|------|---------|
  | ① 最慢单个 span | 48.2 ms（`payment.charge`） | 每次 `db.query.rule` 只有 23 ms，**没有一个异常值** → 指向错误的服务 |
  | ② 同名 span 累计 duration 榜首 | `POST /checkout` 2616 ms | 入口 span duration 包含全部子 span，**父子重叠被重复计入**，入口 span 永远是第一名，等于什么都没说 |
  | ✅ ③ **Self Time 聚合** | `db.query.rule` **×200 累计 2518.8 ms** | Self Time = 自身 duration − 子 span 占用时间。剔除重叠后 200 次重复调用暴露出来，**占端到端 96%** |

- **排查路径**：
  1. **永远用 Self Time 聚合，不要用"最慢单个 span"**，更不要用"同名 span 累计 duration"
  2. 看 span 数量是否异常膨胀（15 → 214 是关键信号）
  3. 同名 span 出现高频次（×200）时，直接判定为循环内调用
- **修复**：批量查询替代循环单查（N+1 的标准解法）
- **预防**：**把"Self Time 聚合"作为 trace 分析的默认第一视图**。这个结论不依赖本项目——任何 trace 分析里，只要出现"一个操作被执行了很多次"，单看最慢 span 就会漏判

> 对应速查条目：`09-排障速查手册.md` · 症状 9（待产出）

### 故障模式 10：测量工具自己骗了你

- **症状（可观测）**：实验数据**自洽但错误**——多个指标互相印证，看起来无懈可击，结论却与事实相反
- **根因**：**不只被测系统会骗你，测量工具本身也会**。本课三个实例：

  1. **课 6**：第一版分流实验因同进程二次 `set_tracer_provider` 被拒，得到「两边 0 条」的**自洽假结论**
  2. **课 8**：排查 exemplar 恒为 0 耗时 **11 轮**，前八轮做"加法"（逐个加条件）全败；C9 改为"复制课 7 脚本做减法"才定位到 `InMemoryMetricReader` 的 exemplar 是**一次性**的——`force_flush()` 会把它消费掉，读第二次归零
  3. **实战项目**：Top-3 span 排序把父子重叠的入口 span（`POST /checkout` 2616 ms）排在最前，差点漏判 N+1

  **共同结构**：你看到的"异常"其实是测量方式造出来的，不是被测系统的。

- **排查路径**（课 8 提炼的三条方法论）：
  1. **复制原脚本做减法**，远优于重写脚本做加法
  2. **所有变量排除后结论仍不变时，怀疑观测方式本身**
  3. 前人的结论没错，**错的是你这一轮的测量姿势**
- **修复**：具体到课 8——`InMemoryMetricReader` 的 exemplar 读一次就没了，正确姿势是 record 后立刻读、读一次、绝不 flush 后读
- **预防**：**当实验结果非常自洽、完美符合预期时，反而要怀疑**。真实系统很少这么干净

> 对应速查条目：`09-排障速查手册.md` · 症状 10（待产出）

- [ ] 采样配置变更后做过**保留率回归**（去后端数一遍，不是看配置写对了就算完）
- [ ] 多副本 Collector 已配 **load balancing exporter** 按 trace_id 一致性哈希
- [ ] 成本模型已用实测字节数校准（每 span 约 600 B；实测未压缩 959 B）

### 指标与 Cardinality

- [ ] 所有指标标签过了一遍「**能列进一张表吗**」——`user.id`、`order.id`、`url.path` 一律不进指标
- [ ] 新指标已**显式配指数桶**（`View` + `ExponentialBucketHistogramAggregation()`；显式桶会把长尾低估，实测最坏 −50.0%）。注意**默认不是指数桶**
- [ ] 已知晓 `UpDownCounter` 导出为 **`gauge`**（不是 counter），看板计算方式已相应调整

- [ ] 升级插桩库前 **dump 一份属性清单做 diff**
- [ ] 看板与告警规则里的属性名**已纳入版本控制**
- [ ] 迁移期用 `http/dup` 双写过渡，切档前确认查询条件已改为新名
- [ ] 已知晓 `OTEL_SEMCONV_STABILITY_OPT_IN` **分域独立**（`http` 管不了 `database`）

### Collector 管道

- [ ] 配置改动先跑 `docker run --rm -v <dir>:/conf <img> validate --config <path>`（无输出即通过）
- [ ] **Processor 顺序已确认**：脱敏排在 transform 迁移**之后**
- [ ] `memory_limiter` 在容器里用**百分比**（写死绝对值读的是宿主机内存）
- [ ] 组件稳定性按「组件 × 信号」逐个查过（`docker run --rm <img> components`），未凭记忆
- [ ] `debug` exporter 的 verbosity 按需要设置（`basic` 只打摘要，看内容须用 `detailed`）
- [ ] `resource` processor 加新属性用 **`insert`** 而非 `upsert`（upsert 只在键存在时生效）

### 定位能力

- [ ] trace 分析默认视图是 **Self Time 聚合**（不是"最慢单个 span"）
- [ ] 三个信号**分别**验证过后端能收（不要因为 trace 通了就认为 log 也通）
- [ ] 团队已知晓「指标全量、trace 采样」的口径差异，不会误判为数据丢失
- [ ] 团队已知晓降采样后 **trace_id 在日志里有效但在后端点不开**
- [ ] 关键请求（如支付）已考虑用头部采样强制保留

### 不该做的

- [ ] **没有**把 Profiles 放进关键定位链路（仍 Alpha）
- [ ] **没有**把 OTel 当后端用（告警与看板是后端产品的职责）
- [ ] **没有**只靠自动插桩（业务语义必须手动补）
