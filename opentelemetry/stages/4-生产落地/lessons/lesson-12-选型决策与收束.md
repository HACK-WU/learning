## 正文

### 第一幕 · 场景引入：链路定位到服务，然后呢

先回到课 1 那次事故。你已经走完了整条链路：

```
下单请求 → 支付服务 → 风控服务 → 用户画像服务 → MySQL 慢查询（全表扫描，4.2 秒）
```

**链路告诉你的最后一件事是：慢在 `user-profile` 调 MySQL。**

然后呢？

你知道这条 SQL 慢，但你不知道它**为什么**慢。是索引缺失？是数据量涨了？是锁等待？还是这个查询本来就该这么慢、只是以前没人注意？

要回答这些，你得做这几件事之一：

- 登机器，`EXPLAIN` 一遍——**但那是事后的现场，已经不是出事时的状态**
- 打开 APM 的代码级剖析——**如果没买商业 APM，这一步就直接断了**
- 让开发加日志、重新部署、等下次复现——**四小时变四天**

**这就是三个信号的共同边界**：它们能定位到"哪个服务、哪次调用、哪条 SQL"，但推不到"哪一行代码在烧 CPU"。

本课的开场问题就是：**这最后一步，OTel 能不能补上？**

### 第二幕 · 认知冲突：是不是该把 Prometheus 和 Jaeger 都换掉

学到这里，一个很自然的念头会冒出来：

> "OTel 这么全，我是不是可以把 Prometheus、Jaeger 都换掉，统一成一套？"

先别急着动手。我们把这个念头拆成两个不同的问题：

**问题 A：采集层能不能统一？**——能，而且应该。这正是 OTel 的价值。

**问题 B：存储分析层能不能统一？**——**不能，也不该。**

混淆这两层，是 OTel 落地最常见的战略错误。往下看第三幕，我们一层一层拆。

### 第三幕 · 层层揭示

#### 11.1 第四信号 Profiles：它补上了什么

##### 一句话定义

**Profiles（剖析）是对运行中的程序按固定频率采样调用栈，回答"哪一行代码在消耗 CPU / 内存"的信号。**

##### 直觉建立：三个信号都是"外部视角"，Profiles 是"内部视角"

把一次故障想象成看病：

| 信号 | 相当于 | 它能告诉你 | 它不能告诉你 |
|------|--------|-----------|-------------|
| Metrics | 体温计 | 发烧了（CPU 90%） | 哪儿发炎 |
| Logs | 病人自述 | 我头疼、我恶心 | 病因是什么 |
| Traces | 检查单流转 | 挂号→内科→验血→CT，哪一步排队久 | 为什么这一步久 |
| **Profiles** | **CT 片** | **哪个器官、哪块组织有病灶** | —— |

前三样都是"从外面看"，Profiles 是"看进去"。

##### 核心原理：采样、eBPF、与 pprof 的关系

**原理一：它是采样的，不是全程记录的**

Profiles 不像 trace 那样记录每一次调用。它按固定频率（典型 **99 Hz**，即每秒 99 次）中断程序，记录"此刻的调用栈是什么"。跑一段时间后聚合，就得到一张火焰图：**某个函数出现的次数越多，说明 CPU 在它身上花的时间越多。**

这个"采样"特性决定了两件事：
- **开销极低**——99 次/秒的中断，对现代 CPU 可以忽略
- **它是统计结果，不是精确计数**——短于采样间隔（约 10 ms）的函数可能采不到

**原理二：eBPF 让它做到"零插桩、全系统"**

传统 profiler 要在应用里装 agent、改代码。eBPF 换了个思路：**在内核里采样**。

程序运行时，它的调用栈信息内核本来就有。eBPF 程序挂在内核的 perf 事件上，按频率读取当前进程的栈——**不需要应用配合，不需要改代码，不需要重启**。

这带来三个独特性质：

| 性质 | 说明 |
|------|------|
| **零插桩** | 应用代码一行不改 |
| **全系统** | 一台机器上一个 agent，剖析上面**所有**进程 |
| **语言无关** | Go / Rust / C++ 这类编译型语言也能剖（传统 agent 做不到） |

**原理三：OTLP Profiles 与 pprof 无损互转**

pprof 是 Go 语言带火起来的剖析格式，已成事实标准。OTLP Profiles **不是**另起炉灶：

- 它在 pprof protobuf 基础上扩展
- 增加了 Resource / Scope 上下文（与 logs、metrics、traces 一致）
- 增加了**字典去重**（不只去重字符串，还去重函数、位置等消息）
- 增加了 **span 引用**（`Link`，可直连 trace_id / span_id）

官方承诺：**原始 pprof 数据与 OTLP Profiles 可以无损来回转换**。

##### 示例演示：实测零插桩采集 + 无损互转

**演示 A：eBPF 真的能采到栈吗（本机 WSL2 实测）**

先确认环境（这是骨架要求实测的一项）：

```
$ uname -r
6.6.87.2-microsoft-standard-WSL2
$ grep CONFIG_BPF_SYSCALL /proc/config.gz
CONFIG_BPF_SYSCALL=y
$ cat /sys/kernel/btf/vmlinux > /dev/null && echo BTF_OK
BTF_OK
```

`BTF_OK` 是关键——BTF（BPF Type Format）是 CO-RE eBPF 的硬前提，没有它现代 eBPF 程序无法移植。

然后挂载一个真实的 eBPF 程序：

```
$ python3 prof.py        # 挂载 perf CPU_CLOCK，99 Hz，全系统采样 6 秒
B: perf CPU_CLOCK attached (system-wide)
SAMPLING 6s ...
[perf CPU_CLOCK] TOTAL_SAMPLES=11877 distinct_stacks=535
    73.6% (8736) ffffffff990001e2 <- ffffffff99086989 <- ffffffff99178931 <- ...
    15.0% (1777)
     4.2% ( 496) ffffffff9b5b7fc9 <- ffffffff9b5b7a12 <- ffffffff9a0807da <- ...
     0.3% (  39) ffffffff9a200134 <- ffffffff9a07858b <- ffffffff9a07e641
     0.2% (  18) ffffffff990001e2 <- ffffffff99086989 <- ffffffff99178931 <- ...
```

**6 秒采到 11,877 个样本、535 个不同的调用栈**——这就是火焰图的原始数据。而**被测进程里一行 OTel 代码都没有**。

> 📌 **一个诚实的对照**：我最初用 kprobe 挂 `__x64_sys_clone` 想抓特定进程的栈，结果 **0 样本**——因为 Python 的 `os.fork()` 在 WSL 下未必走到我挂的那个符号。这说明 eBPF 采样式剖析的**效果高度依赖挂载点选择**，真实 profiler 用 perf 事件正是为了避开这个坑。**实验失败本身也是知识。**

> 📌 那些 `ffffffff...` 是内核地址。真实 profiler 会做**符号化**（symbolization），把地址翻译成函数名。这一步的质量因语言运行时而异，是 alpha 阶段的已知短板。

**演示 B：pprof 与 OTLP 的无损互转（本机 Go 1.26.8 实测）**

先生成一个真实的 CPU profile：

```
$ go run main.go          # 3 秒 CPU 密集计算
GENERATED_BYTES 490
$ go tool pprof -top -nodecount=8 /tmp/l12_real.pprof
Duration: 3.11s, Total samples = 3s (96.54%)
      flat  flat%   sum%        cum   cum%
     2.98s 99.33% 99.33%         3s   100%  main.cpuHog (inline)
     0.02s  0.67%   100%      0.02s  0.67%  runtime.asyncPreempt
         0     0%   100%         3s   100%  main.level1 (inline)
         0     0%   100%         3s   100%  main.level2 (inline)
         0     0%   100%         3s   100%  main.level3 (inline)
```

调用栈 `main → level1 → level2 → level3 → cpuHog` 清晰可见。

再把它解析、重建、逐字段比对（模拟 pprof → OTLP → pprof 的往返）：

```
=== 第一次解析 ===
Samples: 3   Locations: 4   Functions: 7   Mappings: 2
栈签名数: 3
   [runtime.main main.cpuHog runtime.asyncPreempt] [2 20000000]
   [runtime.main main.cpuHog] [245 2450000000]
   [runtime.main main.cpuHog] [53 530000000]

=== 往返后 ===
Samples: 3   Locations: 4   Functions: 7

=== 无损比对 ===
样本数 3 -> 3  true
位置数 4 -> 4  true
函数数 7 -> 7  true
栈签名一致: true (差异 0 条)

原始 490 字节 -> 往返后 481 字节 (比值 0.982)
结论: 往返后调用栈与采样值完全一致 —— 无损
```

**差异 0 条。** 这就是"无损互转"的实证。

字节从 490 变成 481，是因为库重新编码时省掉了原文件里的冗余填充，**不是数据丢失**——栈签名一条不差就是证明。

##### 常见误区

**误区一："Profiles 会取代 Traces。"**
不会。它俩回答不同问题：Trace 说"哪一步慢"，Profile 说"这一步里哪行代码慢"。**没有 trace，profile 就是一堆没有请求上下文的栈；没有 profile，trace 的最后一公里走不完。** 官方设计上就让 sample 携带 `trace_id` / `span_id` 做双向关联，是互补不是替代。

**误区二："eBPF 零插桩，所以什么都能剖。"**
eBPF 需要 Linux 内核能力和 `CAP_BPF` 权限，Windows / macOS 上跑不了；它**剖不到内联函数**；符号化质量因运行时而异（Go 较好，其余仍在补齐）。

**误区三（最危险）："Alpha 只是个标签，用起来没事。"**
Alpha 意味着**格式和 API 可能变**。你现在接入的字段，半年后可能改名。对于"出事时要用的东西"，这个风险不能接受。

##### 一句话记住

> **三个信号告诉你"哪儿慢"，Profiles 告诉你"哪行代码慢"——但它现在还是 Alpha，评估可以，押注不行。**

#### 11.2 横向对比：Prometheus / Jaeger / 商业 APM

##### 一句话定义

**OTel 是"采集与传输层"的标准，Prometheus / Jaeger / 商业 APM 是"存储与分析层"的实现——它们是上下游，不是竞品。**

##### 直觉建立：快递网络 vs 仓库

想象物流：

- **OTel** 是**集装箱标准和运输网络**——统一箱型（OTLP），统一标签（语义约定），谁来运都行
- **Prometheus / Jaeger / 商业 APM** 是**仓库和分拣中心**——东西运到了，怎么存、怎么查、怎么展示

你会问"集装箱标准会不会取代仓库"吗？不会。**标准是让你可以随便换仓库。**

##### 核心原理：三层分层

```
┌─────────────────────────────────────────────────────────┐
│  第 1 层：采集（Instrumentation）                          │
│  OTel SDK / 自动插桩 / eBPF          ← OTel 的领地        │
└─────────────────────┬───────────────────────────────────┘
                      │ OTLP
┌─────────────────────▼───────────────────────────────────┐
│  第 2 层：管道（Pipeline）                                │
│  OTel Collector：接收 / 处理 / 采样 / 路由  ← OTel 的领地  │
└─────────────────────┬───────────────────────────────────┘
                      │ OTLP / 专有协议
┌─────────────────────▼───────────────────────────────────┐
│  第 3 层：存储与分析（Backend）                            │
│  Prometheus │ Jaeger │ 商业 APM │ 自建  ← 选择在这里      │
└─────────────────────────────────────────────────────────┘
```

**OTel 覆盖第 1、2 层，不覆盖第 3 层。**

这就是为什么"用 OTel 替换 Prometheus / Jaeger"这个说法本身是错的——**你替换的是第 1、2 层，第 3 层该用什么还用什么。**

##### 示例演示：三类方案的定位对比

| 维度 | Prometheus | Jaeger | 商业 APM |
|------|-----------|--------|---------|
| **主要信号** | Metrics | Traces | 全信号 + 代码级 |
| **数据模型** | 时间序列 + 标签 | 分布式 trace | 专有模型 |
| **查询语言** | PromQL | 按 trace_id / service 检索 | 厂商自定义 UI |
| **部署形态** | 自托管 / 云托管 | 自托管 / 云托管 | SaaS |
| **成本结构** | 开源免费 + 运维人力 | 开源免费 + 运维人力 | 按数据量/主机收费 |
| **上手速度** | 慢（要建看板、写告警） | 中 | 快（开箱即用） |
| **代码级剖析** | ❌ | ❌ | ✅（部分厂商） |
| **可定制性** | 高 | 中 | 低 |
| **数据主权** | 完全自控 | 完全自控 | 数据在厂商 |

**关键观察：这三样不是三选一，是三种能力。**

一个真实的生产栈往往是：

```
OTel SDK（采集）
    ↓ OTLP
OTel Collector（采样/富化/路由）
    ↓ 分流
    ├── Prometheus Remote Write → Prometheus（指标告警）
    ├── OTLP → Jaeger / Tempo（链路检索）
    └── OTLP → 商业 APM（代码级剖析 + 统一 UI）
```

**注意最后一行的分流能力**——这正是 Collector 的价值：一套插桩，多个后端，**换后端不用改代码**。

##### 常见误区

**误区一："用了 OTel 就不需要 Prometheus 了。"**
需要。OTel 不提供存储、不提供 PromQL、不提供告警规则引擎。你要的是"OTel 采集 + Prometheus 存储告警"。

**误区二："商业 APM 是 OTel 的竞争对手。"**
早期是，现在不是。**主流商业 APM 现在都接受 OTLP 原生接入。** 它们的价值已经从"私有采集"转向"分析体验 + 代码级洞察"。

**误区三："自建一定比买便宜。"**
不一定。省掉的是许可费，增加的是**人力成本**（运维、升级、扩容、故障）和**机会成本**（工程师不做业务去做监控）。**课 1 那四小时里，就有一部分是这样的隐性成本。**

##### 一句话记住

> **OTel 管"怎么把数据运出来"，Prometheus / Jaeger / APM 管"运到哪儿、怎么看"——换后端不改代码，这才是 OTel 的真正价值。**

#### 11.3 迁移路径：存量系统怎么上 OTel

##### 一句话定义

**渐进式迁移：用"新服务直接上 + 老服务桥接 + 关键链路优先"的顺序，在不中断现有可观测能力的前提下，逐步把采集层统一到 OTel。**

##### 直觉建立：换轮子，不是换车

存量系统迁移最大的误区是把它想成"换车"——把 Prometheus 拆了、把 Jaeger 拆了、全部重来。

**正确的心智模型是"换轮子"**：车还在跑，你一个一个轮子换掉，每次换完车都还能开。

##### 核心原理：三种桥接姿势

**姿势一：双发（Dual-export）——最安全**

老链路不动，新链路并行跑一段时间，对比无误再切。

```yaml
# Collector 里同时发给老后端和新后端
exporters:
  prometheusremotewrite:        # 老后端
    endpoint: http://old-prometheus:9090/api/v1/write
  otlp/new-backend:             # 新后端
    endpoint: new-backend:4317

service:
  pipelines:
    metrics:
      receivers: [otlp, prometheus]
      processors: [batch]
      exporters: [prometheusremotewrite, otlp/new-backend]   # 两个都发
```

**适用**：任何你不敢直接切的链路。代价是短期双份存储和双份成本。

**姿势二：接收端桥接（Receiver bridge）——最省力**

老系统不用改，让 Collector 去**适配老协议**：

| 老系统在用 | Collector 用什么接收 |
|-----------|---------------------|
| StatsD | `statsdreceiver` |
| Jaeger 协议 | `jaegerreceiver` |
| Zipkin 协议 | `zipkinreceiver` |
| Prometheus 抓取 | `prometheusreceiver` |
| Fluent Forward | `fluentforwardreceiver` |
| 日志文件 | `filelogreceiver` |

**这是阻力最小的一条路**——老应用一个字不改，只是把原来发给老 agent 的数据改发给 Collector。

**姿势三：发送端桥接（Exporter bridge）——过渡用**

反过来：应用已经上了 OTel SDK，但后端还没换。让 Collector 转成老后端能吃的协议。

```yaml
exporters:
  prometheusremotewrite:        # 老 Prometheus 只认这个
    endpoint: http://prometheus:9090/api/v1/write
  jaeger:                       # 老 Jaeger
    endpoint: jaeger:14250
```

##### 示例演示：一份可落地的四阶段迁移路径

下面这份路径图，你可以直接拿去改成自己系统的版本。

**阶段 0：摸底（1～2 周）**

| 动作 | 产出 |
|------|------|
| 清点现有可观测资产 | 一张表：谁在用 Prometheus / ELK / Jaeger / 商业 agent，覆盖范围多大 |
| 标记"必须保留"的看板与告警 | 迁移中断了这些 = 事故 |
| 选一个**非关键**服务做试点 | 试点服务名 |

> ⚠️ **这一步最容易被跳过，也最容易导致迁移失败。** 你无法迁移你不知道存在的东西。

**阶段 1：旁路验证（2～4 周）**

```
试点服务：装 OTel SDK / 自动插桩
                ↓ OTLP
         OTel Collector ──┬──→ 新后端（开始积累数据）
                          └──→ 老后端（继续承担告警）
```

- **告警仍由老系统负责**——新链路不承载任何 SLA
- 每周比对：新链路的数据完整性 vs 老链路
- **验收标准**：连续两周，新链路的 span / 指标完整率 ≥ 老链路

**阶段 2：灰度切换（4～8 周）**

按服务维度逐步切，每批 10%～20%：

| 批次 | 范围 | 切什么 | 回退条件 |
|------|------|--------|---------|
| 批次 1 | 内部服务（无外部 SLA） | 指标告警切到新后端 | 告警漏报 > 0 |
| 批次 2 | 读多写少的服务 | + 链路检索切到新后端 | 查询失败率 > 1% |
| 批次 3 | 核心读服务 | + 日志关联切到新后端 | 关联失败率 > 5% |
| 批次 4 | 核心写服务 / 支付链路 | 全量切换 | 任何 P0 事故 |

**每批都要留一个"不切"的对照组**，出问题时能立刻对比。

**阶段 3：收敛（8 周后）**

- 下线老 agent，**但保留老后端只读访问 30 天**（历史数据 + 回退保险）
- 统一语义约定，清理重复指标
- 建立"新增服务默认 OTel"的 CI 卡点

**回退方案（每一阶段都要有）**

```
回退触发条件（任一成立即回退）：
  · 新链路数据完整率 < 95%
  · 告警漏报或误报
  · 查询 P99 > 老系统 2 倍
  · 出现任何 P0/P1 事故且怀疑与新链路相关

回退动作：
  1. Collector 配置改回只发老后端（配置回滚，秒级生效）
  2. 保留现场：不要删新链路数据，先导出留证
  3. 复盘：是配置问题、容量问题还是语义问题
```

> 📌 **回退的第一原则：回退的是"数据流向"，不是"代码"。** 因为采集层已经统一，回退只需要改 Collector 配置——这正是 OTel 带来的红利。

##### 常见阻力与应对

| 阻力 | 典型说辞 | 应对 |
|------|---------|------|
| **"现在这套能用，为什么要动"** | 现状偏好 | 不要讲 OTel 的好处，讲**现状的代价**：三个控制台来回切、换后端要改代码、课 1 那四小时 |
| **"改造成本谁来出"** | 优先级之争 | 用**阶段 1 旁路验证**回应：不改告警、不动 SLA，成本只有装一个 SDK |
| **"老系统没人敢碰"** | 技术债恐惧 | 用**接收端桥接**：老应用一个字不改，只改发给谁 |
| **"两套并存期间成本翻倍"** | 预算 | 这是**真实成本，不要回避**。给明确的时间盒（如 8 周）和退出条件 |
| **"出了事算谁的"** | 责任 | 每批次的回退条件写清楚，且**回退不需要改代码**——把风险从"改代码"降为"改配置" |

##### 常见误区

**误区一："一次性把 Prometheus 全替了。"**
这是最常见的失败模式。**渐进式的价值不在于"稳"，而在于"每一步都可回退"。**

**误区二："老系统直接装 OTel SDK 就行。"**
很多老系统用的是 StatsD、自研埋点、甚至日志打点。**先看清它现在发的是什么协议，再决定是桥接还是改造。**

**误区三："迁移完就删老系统。"**
保留**只读**访问 30 天以上。历史数据、审计要求、以及"万一新系统有 bug"的保险。

##### 一句话记住

> **迁移不是换车是换轮子：旁路验证 → 灰度切换 → 收敛下线，每一步都要能在"不改代码"的前提下回退。**

#### 11.4 收束：四小时能缩短到多久

##### 一句话定义

**把课 1 的 164 分钟按"等待信息"和"做决策"两类重新切分，用本课的全套能力重走一遍，给出可量化的耗时对比。**

##### 直觉建立：四小时里，真正干活的有几分钟

课 1 的账是这样的：

| 时间段 | 时长 | 在做什么 | 性质 |
|--------|------|---------|------|
| 21:09 → 21:14 | 5 min | 问题发生 → 告警触发 | 系统 |
| 21:14 → 21:22 | 8 min | 看 Grafana，知道支付服务出问题 | **找信息** |
| 21:22 → 21:38 | 16 min | 翻 Kibana 日志，找到那条 error | **找信息** |
| 21:38 → 21:55 | 17 min | 去 Jaeger 搜 trace，**靠时间戳猜是不是同一次** | **找信息（且猜错风险）** |
| 21:55 → 22:30 | 35 min | 回 Kibana 换姿势搜，做**人工 join** | **找信息** |
| 22:30 → 23:50 | 80 min | 拉人、对齐、翻数据库慢查询 | **找信息** |
| 23:50 → 23:53 | **3 min** | 加索引，修复 | **做决策** |

**总计 164 分钟，其中：**
- **找信息：156 分钟（95.1%）**
- **做决策：3 分钟（1.8%）**

> 📌 **这张表就是整个课程的核心论点**：可观测性的瓶颈从来不是"人不够聪明"，而是**信息散在三个互不连通的控制台里**。

##### 核心原理：OTel 把"找信息"从 O(n) 降到 O(1)

课 1 里最贵的三个动作，本质都是**人工 join**：

| 课 1 的动作 | 为什么慢 | OTel 之后 |
|------------|---------|----------|
| 拿日志去 Jaeger 找对应 trace | 只能靠时间戳猜 | **日志自动带 trace_id，一键跳转** |
| 拿 trace 回 Kibana 找对应日志 | 只能靠时间戳猜 | **同上，双向** |
| 跨服务对齐日志格式 | `duration_ms` vs `cost` | **语义约定统一命名** |
| 1% 采样导致慢请求没抓到 | 采样的偶然性 | **尾部采样，慢请求和错误请求必留**（课 6） |

**每一个"人工 join"消失，对应的那段时间就消失了。**

##### 示例演示：重走一遍，实测计时

我用课 1 完全相同的场景（下单 → 支付 → 风控 → 画像 → MySQL 全表扫描 4.2 秒），构造了完整链路并实测：

**链路落库结果（本机 Collector 0.133.0 实测）：**

```
Parent ID      : 
Name           : checkout
     -> service.name: Str(checkout)
     -> order.id: Str(SO202609022109)

Parent ID      : a4ebd854b4d9a76d
Name           : POST /charge
     -> service.name: Str(payment-service)
     -> http.status_code: Int(502)
     -> order.id: Str(SO202609022109)

Parent ID      : 72562d0ccd0fd73d
Name           : POST /evaluate
     -> service.name: Str(risk-control)
     -> order.id: Str(SO202609022109)

Parent ID      : 4e2b46d1f2a7c92c
Name           : GET /profile
     -> service.name: Str(user-profile)
     -> deployment.version: Str(v2.3.1)

Parent ID      : 29d0370a8a023d03
Name           : SELECT users
     -> service.name: Str(mysql)
     -> db.statement: Str(SELECT * FROM users WHERE phone = ?)
     -> db.rows_scanned: Int(4820000)
     -> db.index_used: Bool(false)
     -> db.query.duration_ms: Int(4200)
```

**注意最后一跳**：`db.index_used=false`、`db.rows_scanned=4820000`——**根因直接挂在 span 上，不需要做任何 join。**

**实测排查耗时（本机 Jaeger，重复查询）：**

```
  按 trace_id 查整条链路                 29.6 ms  OK
  排序找最慢 span                        3.3 ms  OK
  读取根因属性                            1.2 ms  OK
  列出服务清单                            1.0 ms  OK
机器侧查询总耗时: 35.1 ms

最慢 span: [('checkout', 4500000), ...]
根因: {'span': 'SELECT users', 'index_used': False,
       'rows_scanned': 4820000, 'dur_ms': 4200.0}
```

**机器侧 35.1 毫秒**——对比课 1 的 156 分钟人工 join。

> 📌 **实验细节（不必跳过）**：按 `trace_id` 查询时，Jaeger 里已经累积了这个 trace_id 的**多条历史记录**（我在调试时发过几次），所以"最慢 span"排序取到了 `checkout`（4,500,000 μs，是整条链的根 span）而非最深的 `SELECT users`。这不影响结论——**根因属性仍一次性精确命中**。但它提醒了一件事：**真实环境里 trace_id 可能对应多次重试/重发，看 span 不能只看"最慢的那个根"。**

> ⚠️ **必须诚实说明**：这 35 ms 只是**查询耗时**，不是"排查总耗时"。人还要读、要判断、要决定加索引。但课 1 里那 156 分钟的绝大部分（翻日志、猜时间戳、拉人对齐）**是纯粹的机械劳动，现在被压缩到接近零。**

**重算后的一次典型排查：**

| 步骤 | 课 1（三控制台） | OTel 之后 | 说明 |
|------|----------------|----------|------|
| 告警到知道哪个服务 | 8 min | ~0 | 指标已有，且可下钻到 trace |
| 找到出问题的请求 | 16 min | ~1 min | 日志带 trace_id，一键跳转 |
| 定位到慢的那一段 | 17 min | ~1 min | trace 里直接看耗时最长的 span |
| 跨服务对齐 | 35 min | ~0 | 语义约定统一，无需人工 join |
| 找到根因（哪条 SQL） | 80 min | ~2 min | span 上直接带 `db.statement` / `db.index_used` |
| **修复** | **3 min** | **3 min** | **这一步没变** |
| **合计** | **164 min** | **≈ 7 min + 3 min ≈ 10 min** | 排查部分约 16 倍 |

**约 164 分钟 → 约 10 分钟，约 16 倍。**

> 📌 **注意那个"3 分钟没变"**：修复时间不会因为可观测性变好而缩短。**可观测性优化的是"找到根因"，不是"解决问题"。** 把 164 分钟说成"能变成 3 分钟"是不诚实的营销话术。

**再加一句更诚实的**：如果算上"加索引 → 代码评审 → 发布 → 验证"的工程流程，端到端通常是 **30～60 分钟**。但这里面绝大部分是**软件交付流程**的时间，不是排查的时间。

##### 收益结算：除了省时间，还省了什么

| 收益 | 课 1 | OTel 之后 |
|------|------|----------|
| **MTTR（平均修复时间）** | 164 min | ≈ 10 min（排查部分） |
| **需要拉的人数** | 3 个服务的负责人 | 1 人（自己看完） |
| **换后端的成本** | 重写所有插桩代码 | 改 Collector 配置 |
| **认知负担** | 要同时懂 Prometheus + ELK + Jaeger 三套查询 | 一套语义约定 |
| **采样导致的漏检** | 1% 采样，慢请求可能没抓到 | 尾部采样，慢/错请求必留 |

##### 常见误区

**误区一："上了 OTel 就不用值班了。"**
不。OTel 缩短的是**定位**时间，不是**修复**时间，更不替代**容量规划**和**架构治理**。

**误区二："采样率开到 100% 最保险。"**
课 6 已经算过这笔账。**治理比全量更有价值**——尾部采样让"重要的请求" 100% 留下，同时把总量压下去。

**误区三："四小时一次搞定，之后一劳永逸。"**
可观测性**需要持续投入**：语义约定会演进（课 9）、基数会膨胀（课 11）、新服务要接入。**把它当成产品来运营，不是项目来交付。**

##### 一句话记住

> **164 分钟里只有 3 分钟在修问题，其余 156 分钟都在做本该由系统自动完成的 join——OTel 消灭的是这 156 分钟。**

### 第五幕 · 体系收束：下一次 502，还要不要四个小时

回到课程最开始那个问题。

**课 1 的答案是：要。三个控制台、164 分钟、3 分钟修复、拉三个团队。**

**现在的答案是：不需要。**

整条路径现在是这样的：

```
  告警响（Metrics）
      │
      │  点击下钻（exemplar：指标 → trace）
      ▼
  看到整条链路（Traces）
      │
      │  trace_id 自动关联
      ▼
  看到当时的日志（Logs）
      │
      │  span 上直接带 db.statement / db.index_used
      ▼
  看到根因（哪条 SQL、扫了多少行、有没有走索引）
      │
      │  若为 CPU 问题 → Profiles（Alpha，评估环境）
      ▼
  修复
```

**每一个箭头都是"一键跳转"，没有一次人工 join。**

而你为此付出的，是一条 Collector 管道和一套语义约定——**换后端时，改的是配置，不是代码**。

#### 四个信号，四句定位

| 信号 | 回答 | 稳定状态 |
|------|------|---------|
| Metrics | 出问题了吗？多严重？ | **Stable** |
| Logs | 当时发生了什么？ | **Stable** |
| Traces | 卡在哪一步？ | **Stable** |
| Profiles | 哪行代码在烧资源？ | **⚠️ Alpha（2026-09 核查）** |
