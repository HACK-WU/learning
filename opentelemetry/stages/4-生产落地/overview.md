## 一、阶段目标

学完本阶段你应该能够：

1. **搭出**一条 Collector 管道，并能在其中做脱敏、过滤与富化（**这是不改应用代码就能治理数据的关键**）
2. **选择**部署拓扑（Agent / Gateway / 混合），并估算数据量与成本量级
3. **给出**一份可观测体系建设方案：含迁移路径、选型理由、代价与回退方案

## 五、本阶段的高频困惑点（预判）

> 学习时若遇到以下问题属正常，课内会正面回应：

1. **"应用直连后端不就好了，为什么要多一层 Collector？"** → 因为换后端、加采样、做脱敏、加元数据——这些你不会想改几百个服务的代码去做
2. **"core 和 contrib 选哪个？"** → 只跑 OTLP 到 OTLP 原生后端，core 足够且攻击面小；需要云厂商 exporter 或大量集成才用 contrib；受监管环境建议从 core 出发用 ocb 按需构建
3. **"Profiles 要不要上生产？"** → ⚠️ 官方明确**不建议**用于关键生产负载（2026-03 起 public alpha）。先在非关键环境试点，等 GA
4. **"存量 Prometheus 要不要全量迁移？"** → 不必。OTel 可导出 Prometheus 格式，既有 Grafana 看板无需改动；渐进式迁移才是正解

**课 12 核心结论（2026-09-04 实测）**：

- **骨架预判再次被推翻（本课推翻两处）**：①骨架写「Profiles 目标 2026 Q3 GA」——**未兑现**。2026-09-04 复核官方一手页面，规范页与概念页均为 `Status: Alpha`，页脚变更记录停留 2026-03-23（`#9457`），**五个多月未推进到 Beta**；各语言 SDK 页显示 Profiles 列 Go=Beta、Java/Python=Development、其余为 `-`，**无任何语言 Stable**。搜索中出现的「已 Beta」「GA 目标 Q4」等二手说法与官方冲突，讲义以官方为准。②骨架写「WSL 是否支持 eBPF 须实测，不支持则 11.1 降级为认知层讲解」——**实测完全支持，已升级为真机演示**。
- **eBPF 零插桩采集已实证**：WSL2 内核 6.6.87.2、`CONFIG_BPF_SYSCALL=y`、BTF 6 MB 可用；bcc 挂载 `__x64_sys_clone` kprobe 6 秒捕获 **180 次**命中；perf CPU_CLOCK 99 Hz 全系统采样剖析 6 秒得 **11,877 样本 / 535 个不同调用栈**，被测进程零 OTel 代码。
- **pprof ↔ OTLP 无损互转已证实**：Go 1.26.8 生成真实 CPU profile（490 字节），用官方 `google/pprof` 库解析→重建→逐字段比对，样本 3→3、位置 4→4、函数 7→7、**栈签名差异 0 条**；字节 490→481 系重新编码省掉冗余填充，非数据丢失。
- **四信号的边界一句话**：Traces 说"哪一步慢"，Profiles 说"这一步里哪行代码慢"。**没有 trace，profile 是没请求上下文的栈；没有 profile，trace 的最后一公里走不完。**
- **选型的核心判据是分层**：OTel 覆盖**采集层（第 1 层）与管道层（第 2 层）**，不覆盖**存储分析层（第 3 层）**。"用 OTel 替换 Prometheus/Jaeger"这个说法错在混淆了这三层——你替换的是第 1、2 层，第 3 层该用什么还用什么。
- **迁移是换轮子不是换车**：双发（新老并行）、接收端桥接（老协议适配，老应用一字不改）、发送端桥接（转老后端协议）三种姿势；四阶段推进（摸底 → 旁路验证 → 灰度切换 → 收敛下线）。**回退第一原则：回退的是数据流向，不是代码。**
- **收束量化（全课程最重要的一笔账）**：课 1 的 164 分钟里，**找信息 156 分钟（95.1%）、做决策 3 分钟（1.8%）**。实测有了完整链路后，机器侧查询 **35.1 ms** 命中根因。**可观测性优化的是"找到根因"，不是"解决问题"——那 3 分钟修复时间不变**，故 164 分钟应收敛为约 10 分钟（排查部分），端到端含发布流程通常 30–60 分钟。

**课 11 核心结论（2026-09-03 实测）**：

- **骨架预判被推翻**：骨架写「本机无 K8s 集群、10.3 须标注未实测」。实测评估后发现 kind 完全可跑，**10.3 是真测不是概念讲解**——建 kind 集群（K8s v1.34.0）+ cert-manager v1.17.2 + Operator v0.132.0，用零 OTel 代码的 Flask 应用 + 一行注解完成自动注入，产出 **16 条 span 且上下文自动传播**。
- **拓扑分层的判断标准只有一条**：这个动作需要看到全局吗。过滤噪声 / 加 Pod 元数据 / 删 PII 不需要 → Agent；尾部采样 / 按 traceID 路由 / 统调采样率需要 → Gateway。**混合模式是生产默认**，因为只有它能同时满足「PII 不能离网」与「全局决策」两个硬约束。
- **分层治理实证**：三种拓扑发同样 34 条 span，A/B 都落库 34（无差别）；C 落库 14，其中 `/healthz` 从 10 → **0**（Agent 层就过滤掉了），再经 Gateway 50% 采样 24 → 14。
- **成本模型的四个变量已实测校准**：每 span 字节 = 600 B（实测未压缩 959 B，由 191,868 B ÷ 200 条得出）；同样 300 服务规模，**治理 vs 不治理相差 200 倍**。
- **Cardinality 是乘出来的**：同样 150 条 span，dimensions 里多加一个 `user.id`（50 个值），Prometheus 序列数 **5 → 50**、端点体积 **32 KB → 325 KB**。真实系统 user.id 是十万百万级。
- **自动注入的两个静默失效**：① Instrumentation CR 必须早于应用 Pod（webhook 在 Pod **创建时**注入，晚了这个 Pod 就永远不会被注入）；② OTel Python **只覆盖已知库**——`http.server` 的 BaseHTTPRequestHandler 一条 span 都不出，换 Flask 立刻有 16 条。
- **组件名凭记忆必错（课 10 教训重演）**：实际是 `k8s_attributes`（带下划线）、`load_balancing`（exporter）、`span_metrics` / `service_graph`（connector）。

**课 10 核心结论（2026-09-03 实测）**：

- **Collector 是可观测性的 nginx**：换后端只改配置不改代码——实测同一套应用代码，改一行 exporter 配置即从 Jaeger 切到 file，应用侧零改动。
- **课 9 遗留的 `l9-semconv-migrate.yaml` 正式落地**：补齐课 9 只留注释的 **1:N 拆分**，用 OTTL `Split()` 把 `http.target=/users/42?page=1` 拆成 `url.path` + `url.query`，并用 `where` 守卫保证幂等。
- **顺序敏感已实证**：脱敏必须排在 transform 迁移之后，否则迁移新生成的 `url.query` 会躲过脱敏（对照实验 e4a / e4b）。
- **组件稳定性必须逐个查**：`docker run --rm <img> components` 是本机权威来源；0.160.0 上 `filter` processor 仍是 Alpha，与 Collector 本身是否稳定无关。
- **骨架一处事实错误已纠正**：CVE-2026-42602 受影响区间是 v0.124.0–v0.150.0，**v0.151.0 是修复版本**而非受影响版本。
