# 10-场景解法库 · 照着改就能用

> **怎么用**：找到最接近你的场景 → 复制模板 → 改成你的 → 按 [结课实战项目](./07-结课实战项目.md) 的验收清单走一遍。
> **所有模板的 `description` 均按"能被触发"的标准设计**（课 6/7 实测标准）
> **装之前**：见 [08-实战经验](./08-实战经验.md) 的"原则 6：安全"

---

## 使用前必读

### 三个通用改装点

每个模板你都要改这三处：

| 位置 | 改什么 |
|------|--------|
| `name` | 改成你的技能名（小写+连字符，**必须和文件夹名一致**） |
| `description` | 改成你的场景（**最关键**，决定会不会触发） |
| 正文步骤 | 改成你的规矩（编号，别写散文） |

### ⚠️ Windows 用户：必须用无 BOM 写法

```powershell
[System.IO.File]::WriteAllText($path, $content, [System.Text.UTF8Encoding]::new($false))
```

**别用** `Set-Content -Encoding UTF8`——会加 BOM，技能**静默失效**。

### 验收三步（每个模板装完都要做）

```powershell
# 1. 装进去
$dst = "$env:USERPROFILE\.claude\skills\你的技能名"
New-Item -ItemType Directory $dst -Force | Out-Null
Copy-Item "来源路径\*" $dst -Recurse -Force

# 2. 确认在列表里 ★ 不能省 ★
npx skills list -g

# 3. 用日常说法测 3 次（不点名技能）
```

## 场景 1：论文/报告格式检查

**适合**：学生、研究者
**解决的痛**：每次都要重说"引用格式用 APA""字数控制在 800"

```markdown
---
name: paper-format-check
description: "Use when checking a paper or thesis draft for formatting issues before submission. Checks heading levels, figure/table numbering, and reference style. Examples: \"check my paper format\", \"帮我校对论文格式\", \"这篇能交了吗\""
---

# 论文格式检查

## 你要做的事
1. 通读全文，先看整体结构（标题层级是否连续，不跳级）
2. 检查图表编号是否连续、正文是否引用了每个图表
3. 检查参考文献格式是否统一（同一类型用同一种写法）
4. 检查字数是否符合要求

## 输出格式
按「问题 → 位置 → 建议改法」三列输出，最后给一个总数。

## 边界
- 只检查格式，**不改观点、不改论证**
- 信息不足（如不知道要求多少字）时**直接问**，不要猜
- 没问题时明确说"未发现格式问题"，不要硬凑
```

> 💡 **实测**：本模板安装后 `list -g` 正常显示，`description` 含中英双语触发词。

**改装提示**：把"参考文献格式"换成你的学科规范（APA / GB/T 7714 / MLA）。

## 场景 2：周报生成

**适合**：上班族
**解决的痛**：每周从零散要点整理成固定格式，很烦

```markdown
---
name: weekly-report
description: "Use when turning rough bullet notes or a list of completed tasks into a structured weekly report with fixed sections. Examples: \"write my weekly report\", \"帮我把这些要点整理成周报\""
---

# 周报生成

## 你要做的事
1. 把用户给的要点按「本周完成 / 下周计划 / 风险与阻塞」三类归类
2. 每类不超过 5 条，用动词开头
3. 信息不足时直接问，不要编造

## 输出格式
### 本周完成
- ...
### 下周计划
- ...
### 风险与阻塞
- ...（无则写"无"）
```

> 💡 **实测通过**：本模板已装上并成功出现在 `list -g`，BOM 检查 `45 45 45` 正常。

**改装提示**：改成你们公司的模板（比如加"数据指标"段）。

## 场景 3：Git 提交信息规范

**适合**：开发者
**解决的痛**：提交信息写得太随意，review 时看不懂

```markdown
---
name: git-commit-msg
description: "Use when generating a git commit message from staged changes. Follows conventional commits format. Examples: \"write a commit message\", \"帮我写提交信息\""
---

# 提交信息生成

## 格式
`<type>(<scope>): <subject>`

type 只能是：feat / fix / docs / refactor / test / chore

## 你要做的事
1. 先看 `git diff --cached` 了解改了什么
2. 判断 type（新功能=feat，修 bug=fix，只改文档=docs）
3. subject 用**中文祈使句**，不超过 50 字，不加句号
4. 改动超过一处时，正文用列表说明每处改了什么

## 边界
- **不要**为了凑格式而拆分提交
- 一次提交混了多种 type 时，提示用户拆开提交
- 看不出改了什么时**直接问**，不要编
```

**改装提示**：type 列表改成你们团队的约定。

## 场景 4：会议纪要整理

**适合**：常开会的人
**解决的痛**：录音/笔记转成的文字很乱，要整理成固定模板

```markdown
---
name: meeting-notes
description: "Use when turning raw meeting transcripts or scattered notes into structured meeting minutes. Examples: \"整理会议纪要\", \"turn this transcript into minutes\""
---

# 会议纪要整理

## 你要做的事
1. 提取：参会人、时间、议题
2. 按议题归纳**结论**（不是过程）
3. 提取**待办**：每条必须有负责人和截止时间
4. 存疑事项单独列出

## 输出格式
### 基本信息
参会人 / 时间
### 结论
- ...
### 待办
| 事项 | 负责人 | 截止 |
|------|--------|------|
### 存疑
- ...

## 边界
- **不编造**没说过的结论
- 待办没有负责人时，明确标注"待确认"，不要猜
```

## 场景 5：代码审查清单

**适合**：开发者
**解决的痛**：每次 review 关注的点不一样，容易漏

```markdown
---
name: code-review
description: "Use when reviewing a code diff or pull request for bugs, security risks, and style issues. Examples: \"review this PR\", \"帮我看看这段代码\""
---

# 代码审查

## 你要做的事
按这个顺序看，**不要跳**：
1. **整体**：这个改动想解决什么问题？改动范围合理吗？
2. **正确性**：有没有明显 bug、边界情况处理了吗
3. **安全**：有没有 SQL 注入、XSS、硬编码密钥
4. **性能**：有没有 N+1 查询、循环里做 IO
5. **可读性**：命名、注释是否清楚

## 输出格式
按严重程度分级：
- 🔴 必须改：会导致 bug 或安全问题
- 🟡 建议改：影响可维护性
- 🟢 可选：风格建议

每条给「位置 + 问题 + 建议改法」。

## 边界
- **不要**因为风格问题阻塞合并
- 改动太大看不完时，明确说"只看了 XX 文件"
```

## 场景 6：文档润色成固定风格

**适合**：求职者、需要统一文风的人
**解决的痛**：AI 润色出来的风格每次都不一样

```markdown
---
name: doc-polish
description: "Use when polishing a document or resume into a consistent professional style without changing its meaning. Examples: \"润色这段\", \"polish this paragraph\""
---

# 文档润色

## 风格要求
- 书面语，不用口语和网络用语
- 句子控制在 40 字以内，超了就拆
- 用主动语态（"我们完成了 X" 而不是 "X 被完成了"）
- 删掉"非常""很""一些"这类没信息量的词

## 你要做的事
1. 先通读，理解原意
2. 按上面的风格改写
3. 输出时给「原文 → 改后」，并说明改了什么

## 边界
- **绝不改原意**，不确定时保留原文并标注
- 不添加原文没有的信息
- 专业术语保持原样，不要"翻译"成大白话
```

## 找不到你的场景？

**用这个万能骨架**：

```markdown
---
name: 你的技能名
description: "Use when <具体场景>. <做什么>. Examples: \"<用户可能说的话1>\", \"<说法2>\""
---

# 标题

## 你要做的事
1. ...
2. ...
3. ...

## 输出格式
（给一个明确的样子）

## 边界
- 什么情况不做
- 信息不足时怎么办
```

**三段中"边界"最容易被漏，但它最有用**——没有边界说明的技能，AI 会在不该用的时候乱用。

---

## 🐞 改装时的常见错误

| 错误 | 后果 | 正确做法 |
|------|------|---------|
| 只改正文不改 `description` | **不触发**（最致命） | description 和正文一起改 |
| `name` 和文件夹名不一致 | `remove` 删不掉 | 保持一致 |
| 用 `Set-Content` 写文件 | **BOM 导致静默失效** | 用无 BOM 写法 |
| 删掉"边界"段 | AI 在不该用时乱用 | 保留并改写 |
| 装完不测触发 | 不知道能不能用 | 测 3 种说法 |
