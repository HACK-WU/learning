## 反例代码（能跑，且第一个场景的输出"看起来是对的"）

::: code-group

```python [Python]
from typing import Annotated
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.graph import END, START, StateGraph
from operator import add
from typing_extensions import TypedDict


class BadState(TypedDict):
    user_id: str
    message: str
    profile: dict          # ❌ 把用户档案放在 State 里
    trace: Annotated[list, add]


def bad_node(state: BadState) -> dict:
    # ❌ 直接从 state 读档案，读完写回 state
    profile = state.get("profile", {})
    profile["prefers"] = "邮件"
    return {"profile": profile, "trace": ["wrote"]}


b = StateGraph(BadState)
b.add_node("n", bad_node)
b.add_edge(START, "n")
b.add_edge("n", END)
graph = b.compile(checkpointer=InMemorySaver())

# 会话 1：写
r1 = graph.invoke(
    {"user_id": "u1", "message": "我偏好邮件沟通", "profile": {}, "trace": []},
    {"configurable": {"thread_id": "sess-1"}},
)
print("sess-1:", r1["profile"])       # {'prefers': '邮件'}  ← 看着没问题

# 会话 2：换 thread 读
r2 = graph.invoke(
    {"user_id": "u1", "message": "在吗", "profile": {}, "trace": []},
    {"configurable": {"thread_id": "sess-2"}},
)
print("sess-2:", r2["profile"])       # {}  ← 失忆了
```

```typescript [TypeScript]
import { Annotation, StateGraph, START, END, MemorySaver } from "@langchain/langgraph";

const BadState = Annotation.Root({
  user_id: Annotation<string>({ reducer: (_p, n) => n, default: () => "" }),
  message: Annotation<string>({ reducer: (_p, n) => n, default: () => "" }),
  // ❌ 把用户档案放在 State 里
  profile: Annotation<Record<string, any>>({ reducer: (_p, n) => n, default: () => ({}) }),
  trace: Annotation<string[]>({ reducer: (a, b) => a.concat(b), default: () => [] }),
});

function badNode(state: typeof BadState.State) {
  // ❌ 直接从 state 读档案，读完写回 state
  const profile = { ...state.profile };
  profile.prefers = "邮件";
  return { profile, trace: ["wrote"] };
}

const b = new StateGraph(BadState)
  .addNode("n", badNode)
  .addEdge(START, "n")
  .addEdge("n", END);
const graph = b.compile({ checkpointer: new MemorySaver() });

// 会话 1：写
const r1 = await graph.invoke(
  { user_id: "u1", message: "我偏好邮件沟通", profile: {}, trace: [] },
  { configurable: { thread_id: "sess-1" } }
);
console.log("sess-1:", r1.profile);       // { prefers: '邮件' }  ← 看着没问题

// 会话 2：换 thread 读
const r2 = await graph.invoke(
  { user_id: "u1", message: "在吗", profile: {}, trace: [] },
  { configurable: { thread_id: "sess-2" } }
);
console.log("sess-2:", r2.profile);       // {}  ← 失忆了
```

:::


**第一个场景的输出是对的**，所以这个 bug 很容易在自测时溜过去。

> 🇹🇸 **TS 侧差异**：现象**逐字一致**（`sess-1` 有值、`sess-2` 空对象），但有两个写法陷阱：
> ① `Annotation` 的 `profile` 字段 reducer 必须显式给（`reducer: (_p, n) => n`），`default: () => ({})`；Python 的 `profile: dict` 只写类型。
> ② TS 里 `const profile = state.profile; profile.prefers = "邮件"` 会**就地改掉 State 里的对象**（引用共享）；本片段写成 `{ ...state.profile }` 是刻意的——否则连"看起来对"的第一场景都可能因为对象被改而表现异常。这不是 LangGraph 的差异，是 JS 引用语义的差异。

## 逐条对比

| # | 反例 | 正解 | 为什么糟 |
|:--:|------|------|---------|
| 1 | `profile` 存在 `State` 里 | 存在 `Store` 里，按 `user_id` 分格 | State 是 **thread 作用域**。换会话就丢——checkpointer 忠实存了，但那是存给**这个 thread** 的。用户档案需要的是 **user 作用域**，这是两把不同的钥匙 |
| 2 | 抽取与写档在一个节点里 | 拆成 `recall` / `extract` / `confirm` / `write` 四个节点 | 一个节点干完所有事 = 没法在中间插人工确认，也没法单独回放"抽取"这一步。反例连"冲突检测"都没地方放 |
| 3 | 直接 `profile["prefers"] = ...` 覆盖 | `patch_profile` 合并 + 冲突检测 | 静默覆盖。用户上周说"邮件"、这周手滑说"短信"，旧值永久丢失且**没有任何记录**表明它存在过 |
| 4 | 没有风险分级，什么都直接写 | `risk` 标记 + 条件边 → 高风险走 `interrupt` | 联系方式、投诉这类内容未经确认就写档，写错了会影响后续所有回复。反例里连"要不要问一声"的选项都没有 |
| 5 | 命名空间字符串散落各处（本例甚至没有命名空间概念） | `ns_profile()` / `ns_episode()` / `ns_rule()` 收在一处 | 一旦要加"按租户隔离"或改分层方式，就得全局搜索字符串。改一处漏一处 = 数据写进错的格子 |
| 6 | `search` 不传 `limit` | 显式 `limit`（本项目 `episode_limit=20`） | `search` 默认只返回 **10 条且不报错**。经历攒到 11 条时，第 11 条静默消失——不抛异常、不告警，只是慢慢"忘事" |

## 反例 2：把 thread_id 当命名空间第一层

这是**用了 Store 但仍然错**的版本，比上面那个更隐蔽——因为它确实跨了会话写入，只是读的时候对不上。

::: code-group

```python [Python]
def node(state, *, store: BaseStore) -> dict:
    # ❌ 用 thread_id 当第一层
    ns = (state["thread_id"], "preferences")
    store.put(ns, "contact", {"prefers": "邮件"})
    return {}
```

```typescript [TypeScript]
async function node(state: typeof ChatState.State, config: any) {
  const store = config.store;                   // ⚠️ TS 从节点第 2 参取 store
  // ❌ 用 thread_id 当第一层
  const ns = [state.thread_id, "preferences"];
  await store.put(ns, "contact", { prefers: "邮件" });
  return {};
}
```

:::


**后果**：柜子按会话分格。每个会话一个自己的格子，新会话搜自己的格子 → `[]`。**长期记忆退化成短期记忆**，而且比不用 Store 的版本更迷惑——代码里明明"用了 Store"。

**正解**：`ns = (state["user_id"], "preferences")`，第一层永远是 **user 作用域的标识**。
>
> 🇹🇸 **TS 侧差异**：命名空间是**数组** `["u1", "preferences"]`（Python 是元组），四个 store 方法（`put` / `get` / `search` / `delete`）**全部返回 Promise**，漏 `await` 会拿到 `Promise` 当结果。另外节点取 store 的入口是**第 2 参的 `config.store`**（或 `getStore()`），不是关键字参数——从 `config.configurable.store` 取会得到 `undefined`。

## 反例 3：以为 TTL 存在

::: code-group

```python [Python]
store = InMemoryStore()
store.put(("u1", "profile"), "p", {"prefers": "邮件"}, ttl=3600)   # ❌ 直接抛错
```

```typescript [TypeScript]
import { InMemoryStore } from "@langchain/langgraph";

const store = new InMemoryStore();
// ⚠️ TS 侧的坑**不是报错，而是静默无效**——比 Python 更难发现。
//    put 签名是 `put(namespace, key, value, index?)`：**第 4 个参数是 index，不是 ttl**。
//    本机实测：塞 `{ ttl: 0.0001 }`（想让它立即过期）不报错，300ms 后**照样取得到**；
//    塞 `["prefers"]`（正确的 index 形状）也不报错。
//    也就是说 TS 侧根本不存在"TTL 参数"，写进去只是被当成 index 忽略掉。
await store.put(["u1", "profile"], "p", { prefers: "邮件" }, { ttl: 3600 } as any);

// 本机实测：InMemoryStore 上连 `supports_ttl` 属性都没有（undefined），
// 想判断后端能力只能查该后端的文档，没法用一行代码探。
```

:::


实测报错原文：

```
NotImplementedError: TTL is not supported by InMemoryStore.
Use a store implementation that supports TTL or set ttl=None.
```

**为什么容易踩**：`BaseStore.put` 的签名里确实有 `ttl` 参数，类型提示也允许传。**签名存在 ≠ 实现支持**——要查 `store.supports_ttl`（`InMemoryStore` 实测为 `False`）。

**正解**：需要 TTL 就换支持它的后端；`InMemoryStore` 场景下"遗忘"只能靠**不写**（reject / keep 裁决）或**显式 delete**。
>
> 🇹🇸 **TS 侧这个反例"不报错"——比 Python 更危险**（本机实测）：
> ① `put` 签名是 `put(namespace, key, value, index?)`，**第 4 个参数是 `index` 而不是 `ttl`**。硬塞 `{ ttl: 0.0001 }` 不报错，300ms 后照样取得到（既不生效也不提示）。
> ② `InMemoryStore` 上**没有 `supports_ttl` 属性**（实测为 `undefined`），没法像 Python 那样用一行代码探测后端能力——只能查该后端文档。
> ③ 想真用 TTL，TS 侧现成的选择是 `RedisSaver` / `RedisStore`（`fromUrl` 的第 2 参支持 `{ defaultTTL, refreshOnRead }`，单位分钟）。

## TS 写法对照表

| Python | TypeScript | 注意 |
|--------|-----------|------|
| `class BadState(TypedDict): profile: dict` | `Annotation<Record<string, any>>({ reducer, default })` | reducer 必填 |
| `state.get("profile", {})` | `{ ...state.profile }` | JS 对象是引用，浅拷贝防就地改 |
| `ns = (state["user_id"], "preferences")` | `ns = [state.user_id, "preferences"]` | 数组不是元组 |
| `store.put(ns, k, v)` | `await store.put(ns, k, v)` | 四个方法全返回 Promise |
| `def node(state, *, store)` | `node(state, config)` 取 `config.store` | 不在关键字参数里 |
| `put(..., ttl=3600)` 抛 `NotImplementedError` | 第 4 参是 `index`，塞 `{ttl}` **不报错也不生效** | 更隐蔽 |
| `store.supports_ttl` | **不存在**（`undefined`） | 只能查后端文档 |
