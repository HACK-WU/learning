# 设计决策

> 三个"换个人来可能选另一个方案，且也有道理"的决策点，每个写清：候选对比 → 最终选择 → 理由 → 代价 → 什么情况下改选。

---

## 决策 1：抽取事实走规则还是走 LLM？

### 候选方案

| 方案 | 效果 | 代价 |
|------|------|------|
| **A. 正则规则**（本项目） | 可解释、可复现、零延迟、零成本、可单测 | 覆盖率低，换个说法就抽不出来 |
| **B. LLM 抽取** | 覆盖率高，能理解各种变体说法 | 不可复现（同样输入可能不同输出）、有延迟与成本、要处理幻觉 |
| **C. 规则 + LLM 兜底** | 兼顾覆盖与可控 | 两套逻辑要维护，边界难划清 |

### 最终选择：**A. 正则规则**

### 理由

1. **记忆是会被写进档案的东西**，写错了要改，改之前得知道"当初为什么这么记的"。LLM 抽取的结果不可复现，事后无法追溯。
2. 本项目要演示的是**Store 的记忆分层与治理**，不是 NLP。把不确定性引入核心链路会掩盖主题——读者会分不清"这是 Store 的问题还是 LLM 的问题"。
3. 规则可以单测。`test_extract_*` 四个用例直接断言抽取结果，换成 LLM 就得 mock 或打桩，测试的教学价值反而下降。

### 为此付出的代价

- 覆盖率确实低：只认 7 种句式。用户说"我比较喜欢用邮件"抽不出来（因为正则要"偏好…沟通"）。
- 抽取失败（异常）只能兜住返回空候选，不能自我修复。

### 什么情况下该改选 B 或 C

- 真实产品上线，用户说法千变万化 → 选 **B**，但要加**输出校验**（schema 约束）和**抽取日志**（记下原始 message 与抽取结果，便于回溯）。
- 有一定稳定性要求又想提覆盖 → 选 **C**：规则先跑，抽不到再交给 LLM，且 LLM 结果**必须过一轮确认**（本项目已有 confirm 节点，正好复用）。

## 决策 2：冲突了怎么办——静默覆盖 / 拦下裁决 / 双值共存？

### 候选方案

| 方案 | 效果 | 代价 |
|------|------|------|
| **A. 静默覆盖**（新值直接盖旧值） | 实现最简单，用户感觉"助手听懂了" | 旧信息永久丢失；用户改口一次就丢了原意 |
| **B. 拦下等人工裁决**（本项目） | 不丢信息，冲突可见可审计 | 多一次交互；高风险事实才会触发，频率可控 |
| **C. 双值共存 + 时间戳**（都存，用时取最新） | 全自动，保留完整历史 | 档案会无限膨胀；"哪个生效"的逻辑变复杂 |

### 最终选择：**B. 拦下等人工裁决**，且提供三种裁决（confirm 照写 / reject 丢弃 / keep 保留旧值）

### 理由

1. 本项目的主题就是**记忆治理**——"怎么不写脏"。静默覆盖正是"写脏"的典型，选它等于放弃了主题。
2. `interrupt()` 机制在课 8 已经学过，这里正好是它在**记忆场景**的落地（课 8 讲的是审批退款，场景不同但机制相同）。
3. 三种裁决给了完整的语义空间：接受变化（confirm）、否定这次（reject）、否定变化（keep）。只做"是/否"两个选项表达不了"我不要这个新说法但要保留旧的"。

### 为此付出的代价

- 每次冲突都要人工介入。真实场景冲突频繁时会拖慢流程。
- 冲突检测目前只比**同字段不同值**，识别不了语义等价（"邮件" vs "电子邮件"会被判成冲突）。

### 什么情况下该改选 A 或 C

- 冲突极少发生且信息价值低（如"喜欢的颜色"）→ 选 **A**，省掉交互成本。
- 需要完整审计轨迹（金融、医疗）→ 选 **C**，双值共存 + 时间戳，用什么值在**读的时候**决定，写的时候不丢。

## 决策 3：Store 门面（MemStore）要不要抽一层？

### 候选方案

| 方案 | 效果 | 代价 |
|------|------|------|
| **A. 直接调 `store.put(("u1","profile"), ...)`** | 少一层，代码短 | 命名空间字符串散落各节点，改一处要找全部 |
| **B. 抽门面 MemStore**（本项目） | 命名空间约定 SSOT，换后端只改一处 | 多一层间接；过度设计风险 |
| **C. 门面 + 仓储接口（Protocol）** | 最灵活，可替换实现 | 本项目体量下明显过度设计 |

### 最终选择：**B. 抽门面 MemStore**

### 理由

1. **命名空间写错是本课程最实测出来的高频坑**（课 6：用 `thread_id` 当第一层 → 长期记忆退化成短期记忆）。把命名空间收进 `ns_profile()` 这类函数，就把"写错"的可能性从 N 处降到 1 处。
2. `patch_profile`（读改写合并）与 `put`（整体覆盖）的语义差异容易踩——门面里显式分成两个方法，比在各节点裸写更安全。
3. 换 `PostgresStore` 时只改 `MemStore` 内部，节点代码零改动。这是生产落地的真实路径。

### 为此付出的代价

- 多了一层间接，初读代码要多看一个文件。
- `MemStore` 目前只是薄封装，有人会觉得"这层没必要"——这是合理的质疑，见下。

### 什么情况下该改选 A 或 C

- 一次性脚本 / 原型验证，只有一两个地方用 Store → 选 **A**，别为三层抽象买单。
- 需要同时支持多种存储后端并在运行时切换（如灰度迁移）→ 选 **C**，定义 `Protocol` 让两种实现都满足，配合依赖注入切换。

## 📌 三个没做但必须知道的事

> 诚实标注边界，避免读者以为这套能直接上生产。

1. **TTL 没实现**。实测 `InMemoryStore.supports_ttl == False`，`put(ttl=)` 抛 `NotImplementedError`。"遗忘"在本项目里是靠 `reject` / `keep` 裁决**不写**实现的，不是靠时间过期。真实 TTL 要换后端（如带 TTL 的 Redis / Postgres 方案）。
2. **`patch_profile` 是读改写，并发下会丢更新**。两个请求同时改同一用户档案，后写的会盖掉先写的。生产要用带 CAS / 版本号 / 行锁的后端，或者在写档节点加串行化。
3. **抽取规则只有 7 条**，是教学演示级，不是可用的 NLP 方案。
