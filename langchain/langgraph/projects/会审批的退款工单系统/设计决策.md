# 设计决策 · 会审批的退款工单系统

> 每个决策点都**真有争议**——换个人来可能选另一个方案，且也有道理。

---

## 决策 1：审批用 `interrupt()` 卡在节点里，还是拆成"两段图"？

**候选方案**：

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| A · `interrupt()` 卡在节点内 | 一张图，`human_approve` 里 `interrupt()`，外部 `Command(resume=)` 恢复 | 一个图描述完整流程；暂停点就在流程里，Studio 里看得见 | 恢复时该节点**整体重跑**（课 8 实测：执行 2 次）；节点必须无副作用；依赖 checkpointer |
| B · 拆成两张图（"申请图" + "审批后图"） | 第一张跑到"待人工"就结束，人工点击后再起第二张图 | 无状态依赖，节点不重跑；不需要 checkpointer 也能做 | 流程被切成两半，看不到全貌；中间状态要自己落在数据库里；断点续跑、回放全没了 |

**最终选择**：**A · `interrupt()`**

**选择理由**：本项目要的是"一笔工单的完整生命周期可回放"——这要求人工前后是**同一条执行链**。`interrupt()` 把暂停点放回图里，`get_state_history` 能一次列出 8 个存档点（实测），人工前后的状态天然连续。若拆两张图，中间状态落到外部库，就失去了 LangGraph 的存档与 time-trail 能力，等于把最值钱的部分自己实现一遍。

**为此付出的代价**：
1. `human_approve` 节点**必须无副作用**——实测恢复时整个节点会重跑一次，若在里面发短信/写日志/扣库存，就会做两遍。
2. **必须有 checkpointer**——实测无 checkpointer 时 `get_state()` 直接 `ValueError: No checkpointer set`，`approve()` 也没法恢复（能停不能恢复）。
3. 中断载荷只能是**可序列化的值**（dict），不能塞连接对象。

**什么时候该改选另一个**：如果审批可能挂**几天甚至几周**（例如线下合同盖章），用 `interrupt()` 会让存档点长期占用、进程重启即丢失（内存 checkpointer）——这时该改 B：把"待人工"落库，人工完成后以新 thread 起第二段，用业务表而不是 checkpoint 管生命周期。

## 决策 2：风控抖动用"节点级 retry"，还是"整个图重跑"？

**候选方案**：

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| A · 节点级 `RetryPolicy` | `add_node("score_risk", ..., retry_policy=RetryPolicy(max_attempts=3))` | 只重试失败的那一格，前面结果不丢；配置一行 | **只对"可重试异常"生效**——抛 ValueError 完全不重试（实测） |
| B · 外层重试整个图 | 捕获异常后重新 `invoke` 整图 | 不挑异常类型，任何错都能重来 | 前面已成功的节点全部重跑（风控重算、通知重发）；有副作用的节点会重复执行 |
| C · 队列 + 死信（外部重试） | 失败丢回队列，由队列重试 | 与语言无关、可跨进程、有退避与死信 | 要引入 Redis/队列中间件；看不到单节点重试次数；调试链路变长 |

**最终选择**：**A · 节点级 `RetryPolicy`**（配合 C 作为生产补充）

**选择理由**：退款流程里"风控"是只读的，重试它零风险且收益最大；而"退款"有副作用，重试必须靠幂等键兜底。节点级重试的粒度正好——只抖的那一下重来，别的照走。实测风控抖 2 次时，风控被调用 3 次后成功，整单无感知。

**为此付出的代价**：
1. **异常类型成了隐式契约**——实测同样配了 `max_attempts=3`，抛 `TransientUpstreamError` 调 3 次，抛 `ValueError` 只调 1 次直接炸。团队里若有人顺手 `raise ValueError`，重试就静默失效，且不报错、不告警。
2. 节点级重试**没有退避**（连续重试），对下游不友好；生产上仍需要在客户端层做退避。
3. 重试次数计入存档点，会让 `history` 变长（排查时看到重复步骤可能困惑）。

**什么时候该改选另一个**：若下游接口**明确要求退避**（如限流 429 要求等 60s），节点级重试的"立刻重试"会雪上加霜——此时该用 C（队列 + 退避 + 死信），把重试从图里移到基础设施层。

## 决策 3：外部服务怎么注入（依赖注入方式）？

**候选方案**：

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| A · `config["configurable"]` 注入 | 节点签名 `(state, config)`，从 config 取 `Deps` | 官方推荐；不污染 State；存档点里不会混入连接对象 | 签名多一个参数；`config` 类型注解写错会警告 |
| B · 塞进 State 字段 | `state["risk_client"] = ...` | 节点签名最简单，看起来直观 | **实测 `KeyError`**（课 12）；更糟的是连接对象会被序列化进 checkpoint |
| C · 模块级全局单例 | `clients.py` 里 `risk = HttpRiskClient()`，节点直接 import | 最省事，不用传参 | 测试无法替换（要 monkeypatch）；多线程/多租户下互相污染；没法做"每个请求不同配置" |

**最终选择**：**A · `config["configurable"]`**

**选择理由**：课 12 实测过 B 会 `KeyError: 'model'`——State 是**数据契约**，不是依赖容器。更关键的是：State 会被写入 checkpoint，把连接对象塞进去，序列化会炸或存下无用大字段。A 把"运行时依赖"和"业务数据"分开，测试里替换一处即可（`Deps.fake()`）。

**为此付出的代价**：
1. 每个节点都要写 `config` 参数并调 `get_deps(config)`——样板代码。
2. `config` 的类型注解**必须是 `Optional[RunnableConfig]`**：实测写 `config: dict | None` 与 `RunnableConfig | None` 都会触发 `UserWarning`（langgraph 内部只认 `RunnableConfig` / `Optional[RunnableConfig]`，源码 `_runnable.py:168` 的 `KWARGS_CONFIG_KEYS` 不含 `UnionType`）。
3. 新人第一次看会疑惑"为什么节点要两个参数"。

**什么时候该改选另一个**：如果项目**完全没有外部依赖**（纯计算、纯 LLM 调用且模型固定），C 的全局单例更省事——但要预留一个 `Deps` 参数位，等接入第二个环境（测试/预发）时再切到 A，否则届时每个节点都要改签名。

## 📌 三个决策的共性教训

LangGraph 里**"看起来能省的事"往往在运行时才付账**：

| 省掉的东西 | 当时的好处 | 后来付的账 |
|---|---|---|
| 不传 checkpointer | 少一行配置 | 能停不能恢复，回放全无 |
| 顺手 `raise ValueError` | 少定义一个异常类 | 配了重试也不重试，且静默 |
| 依赖塞 State | 节点签名简单 | `KeyError` + 污染存档点 |
