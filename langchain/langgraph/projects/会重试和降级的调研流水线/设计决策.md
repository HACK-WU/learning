# 设计决策

> 三个"换个人可能选另一个方案，且也有道理"的决策点：候选对比 → 最终选择 → 理由 → 代价 → 什么情况下改选。

---

## 决策 1：扇出用 Send 还是 Send + Map-Reduce？

### 候选方案

| 方案 | 效果 | 代价 |
|------|------|------|
| **A. 循环串行**（for 里逐个查） | 最好懂 | N 倍耗时；第 2 个挂了后面就没机会跑 |
| **B. Send 扇出**（本项目） | N 个并行，耗时 = 最慢的那个 | 无法限制并发上限，来源多时会打爆下游 |
| **C. Send + 分批（Map-Reduce 带批次）** | 可控并发 | 多一层批次编排逻辑 |

### 最终选择：**B. Send 扇出**

### 理由

1. 本项目的主题是**容错与子图**，不是并发控制。引入批次编排会盖住主题。
2. `Send` 是课 4 讲过的原语，这里是它在**真实场景**的落地（课 4 只演示了机制）。
3. 实测 3 个来源并行跑通，trace 正确累加，说明扇出的状态归并是可靠的。

### 为此付出的代价

- **没有并发上限**。真实场景有 50 个来源会一次性打出 50 个请求，可能触发下游限流。
- 扇出的子图实例在父图历史里**合成一条**（课 10 实测：子图内部两个节点合成一条），排障时看不出卡在子图第几步。

### 什么情况下该改选 C

- 来源数量 > 10，或对下游有 QPS 承诺 → 必须分批。做法：`fanout` 里按 `batch_size` 切片，用外层循环 + 内层 Send 控制。
- 需要"最快的 N 个结果就够"→ 用 Send 配 `Command` 提前终止其余分支。

## 决策 2：失败要不要重试？重试哪些？

### 候选方案

| 方案 | 效果 | 代价 |
|------|------|------|
| **A. 不重试**（挂了就降级） | 简单，不浪费调用 | 网络抖动这种"再试一次就好"的也被放弃了 |
| **B. 全都重试**（默认策略或 `retry_on=Exception`） | 实现最省事 | 404 / 参数错这类**重试多少次都是一样的结果**，白白浪费 N-1 次调用和时间 |
| **C. 分类重试**（本项目） | 抖动的救回来，永久的立刻降级 | 要预先定义错误分类，且分类错了效果就错 |

### 最终选择：**C. 分类重试** —— `retry_on=TransientError`

### 理由

1. 实测证明**默认 `retry_on` 对 `ValueError` 不重试**（尝试 1 次就抛）。所以"不配 retry_on" ≠ "全都重试"，而是"按框架默认清单重试"——这个清单**不是你业务的清单**。
2. 区分可重试/不可重试是容错设计的核心判断。**把它显式化**，比依赖框架默认更可控、更易审计。
3. 实测效果清晰：抖动来源 3 次调用后成功；永久失败来源重试 0 次直接降级。

### 为此付出的代价

- 依赖**异常分类的正确性**。如果真实 SDK 把 404 包装成通用 `ConnectionError`，分类就错了，会导致白重试。
- 多了一层 `TransientError` / `PermanentError` 的定义，调用方要遵守约定。

### 什么情况下该改选 A 或 B

- 下游调用极便宜且幂等，分类成本高 → 选 **B**，但要设较小的 `max_attempts`（如 2）。
- 有严格超时预算，宁可快速失败 → 选 **A**，配合上游重试。

## 决策 3：降级放在 `error_handler` 还是单独节点？

### 候选方案

| 方案 | 效果 | 代价 |
|------|------|------|
| **A. 单独 degrade 节点 + 条件边** | 逻辑显式，好测试 | **实测走不到**——`error_handler` 会截断流程 |
| **B. `error_handler` 兜底**（本项目） | 确实能兜住，不炸图 | 拿不到异常对象；会截断后续节点 |
| **C. 节点内 try/except 返回失败结论** | 最可控，错误信息完整 | 没有重试（除非手动写循环） |

### 最终选择：**B（`error_handler`）+ C（节点内自存错误）的组合**

### 理由

1. **实测 A 不成立**：`error_handler` 会截断流程，单独特设一个降级节点根本不会被调度。这是课 10「兜底会截断流程」的实战印证。
2. **实测 B 有硬限制**：`error_handler` 只接受 1 个参数且收到的是 state，**拿不到异常对象**。
3. 所以必须**补上 C**：在 `fetch` 内部 try/except 把异常存到函数属性上，让 `degrade` 能读到。这是为了拿到错误信息而付出的工程代价。

### 为此付出的代价

- `fetch.last_error` 这个写法**不优雅**，是个 workaround。有并发时（多个来源并行）它其实是安全的（每个子图实例独立闭包），但读代码的人会疑惑。
- `degrade` 必须**自己把结论写完整**，因为后续节点不跑了。

### 什么情况下该改选纯 C

- 不需要框架重试（自己写重试循环），或错误信息很重要 → 用**纯 C**：节点内 `try/except` 返回 `{ok: False, error: ...}`，完全绕开 `error_handler` 的限制。代码更直白，代价是重试逻辑要自己写。

---

## 📌 三个没做但必须知道的事

1. **没有并发上限**（决策 1 的代价）。来源多了要分批。
2. **`timeout` 未使用**。课 10 提到 `timeout` 只支持 async，本项目是同步节点，所以没用。生产里的 `asyncio` 版本应该配上。
3. **错误分类依赖约定**。真实 SDK 的异常类型未必匹配 `TransientError`/`PermanentError`，接入时要写一层**适配器**把 SDK 异常映射过来——这一步本项目跳过了。
