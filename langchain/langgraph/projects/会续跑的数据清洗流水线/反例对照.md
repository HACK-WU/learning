## 反例 1：重活不标 `@task`

这是**最常见也最隐蔽**的错。代码完全正确，输出也正确——直到流程卡住一次。

::: code-group

```python [Python]
from langgraph.func import entrypoint
from langgraph.types import interrupt

def clean_row(r):          # ❌ 没标 @task，是普通函数
    print(f"   洗第 {r.id} 行（很贵）")
    return do_expensive_work(r)

@entrypoint(checkpointer=InMemorySaver())
def flow(batch):
    rows = [clean_row(r) for r in batch.rows]      # 洗完了
    needs = [r.id for r in rows if r.errors]
    if needs:
        interrupt({"rows": needs})                  # 卡住
    return summarize(rows)
```

```typescript [TypeScript]
import { entrypoint, task, MemorySaver, interrupt } from "@langchain/langgraph";

// ❌ 没标 task，是普通函数
async function cleanRow(r: Row) {
  console.log(`   洗第 ${r.id} 行（很贵）`);
  return doExpensiveWork(r);
}

const flow = entrypoint(
  { name: "flow", checkpointer: new MemorySaver() },
  async (batch: Batch) => {
    const rows = [];
    for (const r of batch.rows) rows.push(await cleanRow(r));   // 洗完了
    const needs = rows.filter((r) => r.errors.length > 0).map((r) => r.id);
    if (needs.length > 0) {
      interrupt<{ rows: number[] }, unknown>({ rows: needs });   // 卡住
    }
    return summarize(rows);
  }
);
```

:::


**实测后果**：

```
第一次 invoke:  [副作用] clean_row 跑了第 1 次
resume:         [副作用] clean_row 跑了第 2 次   ← 白干一遍
```

### 对照正解

::: code-group

```python [Python]
@task                      # ✅ 标了 @task
def clean_row(r):
    return do_expensive_work(r)

@entrypoint(checkpointer=InMemorySaver())
def flow(batch):
    futures = [clean_row(r) for r in batch.rows]   # 先全提交
    rows = [f.result() for f in futures]           # 再统一收
    ...
```

```typescript [TypeScript]
import { entrypoint, task, MemorySaver } from "@langchain/langgraph";

// ✅ 标了 task
const cleanRow = task("clean_row", async (r: Row) => {
  return doExpensiveWork(r);
});

const flow = entrypoint(
  { name: "flow", checkpointer: new MemorySaver() },
  async (batch: Batch) => {
    const futures = batch.rows.map((r) => cleanRow(r));   // 先全提交
    const rows = await Promise.all(futures);              // 再统一收
    // ...
    return summarize(rows);
  }
);
```

:::


```
第一次 invoke:  [副作用] clean_row 跑了第 1 次
resume:         （无输出 —— 复用存档，没重跑）✅
```

**为什么糟**：卡住 10 次，前面的活就干 10 遍。10 万行数据每次卡住就重洗 10 万行。
>
> 🇹🇸 **TS 侧差异**：语义完全一致（`task` 才是"复用存档"的边界，普通函数一律重跑），但写法有三个坑：
> ① `task("名字", fn)` 是**函数式**而不是装饰器（TS 无装饰器支持）——`const cleanRow = task("clean_row", async (r) => ...)`。
> ② 返回值是 **Promise**：`await cleanRow(r)`；Python 侧是 Future，用 `.result()`。
> ③ 因为 JS 没有"先提交后取值"的语法糖，反例 1 的串行版本变成 `for (const r of rows) out.push(await cleanRow(r))`——**看起来和正解差不多**，只差一个 `Promise.all`，所以更容易写错。

## 反例 2：`resume` 用 `dict[int, str]` 传裁决

**照着直觉写**就会犯——"我要告诉它第 1 行 accept、第 2 行 reject"，最自然的写法就是 dict。

::: code-group

```python [Python]
out = pipeline.invoke(batch, cfg)                       # 卡住了
ids = [r["id"] for r in out["__interrupt__"][0].value["rows"]]

# ❌ 看起来最自然
pipeline.invoke(Command(resume={1: "accept", 2: "reject"}), cfg)
```

```typescript [TypeScript]
const out = await pipeline.invoke(batch, cfg);                  // 卡住了
const ids = out.__interrupt__[0].value.rows.map((r: any) => r.id);

// ❌ 看起来最自然——但 TS 侧**不报错**，反而更坑
// 本机实测：这个 dict 会被**原样**当作 interrupt 的返回值传回流程，
// 流程拿到 {"1":"accept","2":"reject"} 去当"裁决列表"用，只会静默判错/漏判。
await pipeline.invoke(new Command({ resume: { 1: "accept", 2: "reject" } }), cfg);
```

:::


**实测报错**：

```
TypeError: expected string or bytes-like object, got 'int'
  langgraph/pregel/_loop.py:912  in <genexpr>
    and all(is_xxh3_128_hexdigest(k) for k in resume)
  langgraph/pregel/_utils.py:291  in is_xxh3_128_hexdigest
    return bool(re.fullmatch(r"[0-9a-f]{32}", value))
```

### 为什么

框架**把 `resume` 的 dict 当成「interrupt id → 该 interrupt 的答案」的映射**，所以会检查每个 key 是不是 32 位十六进制。行 id 是 `1`、`2` 这种 int，直接炸。

### 正解

::: code-group

```python [Python]
# ✅ 用 list[dict]，行 id 放进 value
pipeline.invoke(
    Command(resume=[{"id": 1, "decision": "accept"},
                    {"id": 2, "decision": "reject"}]),
    cfg,
)
```

```typescript [TypeScript]
// ✅ 用数组，行 id 放进元素里
// ⚠️ TS 侧**没有** Python 那条「dict 的 key 必须是 32 位 interrupt-id」的校验
//    （源码里没有 is_xxh3_128_hexdigest 的调用），所以传错 dict 不会抛错，
//    只会把整个对象当成一个 resume 值塞回去 —— 错误暴露得更晚。
//    结论不变：**用数组表达"多条裁决"**。
await pipeline.invoke(
  new Command({
    resume: [
      { id: 1, decision: "accept" },
      { id: 2, decision: "reject" },
    ],
  }),
  cfg
);
```

:::


> 💡 如果真要按 interrupt id 分别答复（一个流程多个 interrupt 时），那 dict 的 key 就该用 `out["__interrupt__"][0].id` 那个 32 位串。
>
> 🇹🇸 **TS 侧这条恰好相反——不报错，所以更危险**（本机实测）：
> ① `new Command({ resume: { 1: "accept" } })` **不会**抛 `TypeError`——TS 源码里没有 `is_xxh3_128_hexdigest` 那道校验，整个对象被**原样**当作 interrupt 的返回值传回流程（实测流程收到 `{"got":{"1":"accept","2":"reject"}}`）。流程若按"裁决列表"解析，会静默判错或漏判。
> ② `resume` 传数组也照收（实测 `[{id:1,decision:"accept"}]` 原样回传），传字符串同样照收。**TS 侧不做类型/形状校验，全靠你自己对齐**。
> ③ 暂停后返回值的形状：`out.__interrupt__[0].value`，与 Python 的下标取值一致；但 TS 的 `out` 上**只有** `__interrupt__` 这一个键（实测 `Object.keys(out) === ["__interrupt__"]`），State 里的字段在中断时不会一起返回。

## 反例 3：不确定就填个默认值

::: code-group

```python [Python]
def coerce_types(row):
    for k, v in row.cleaned.items():
        if k in INT_FIELDS:
            try:
                row.cleaned[k] = int(v)
            except ValueError:
                row.cleaned[k] = 0          # ❌ 猜一个
    return row
```

```typescript [TypeScript]
async function coerceTypes(row: Row) {
  for (const [k, v] of Object.entries(row.cleaned)) {
    if (INT_FIELDS.includes(k)) {
      const n = Number(v);
      if (Number.isNaN(n)) {
        row.cleaned[k] = 0;          // ❌ 猜一个
      } else {
        row.cleaned[k] = n;
      }
    }
  }
  return row;
}
```

:::


**在"所有数据都干净"的测试里，这段代码是满分。**

### 为什么糟

| 问题 | 后果 |
|------|------|
| **无法追溯** | 下游看到 `age=0`，分不清是"真实年龄 0"还是"洗坏了填的" |
| **污染统计** | 平均年龄被一堆 0 拉低，报表错误且没人知道为什么 |
| **掩盖上游问题** | 源头数据格式错了，你静默兜住了，问题永远不会暴露 |

### 正解：不猜，抛出来

::: code-group

```python [Python]
except ValueError:
    raise Unclear(f"第 {row.id} 行字段 {k!r} 的值 {v!r} 不是合法整数")
```

```typescript [TypeScript]
async function coerceTypes(row: Row) {
  for (const [k, v] of Object.entries(row.cleaned)) {
    if (!INT_FIELDS.includes(k)) continue;
    const n = Number(v);
    if (Number.isNaN(n)) {
      throw new Unclear(`第 ${row.id} 行字段 ${JSON.stringify(k)} 的值 ${JSON.stringify(v)} 不是合法整数`);
    }
    row.cleaned[k] = n;
  }
  return row;
}
```

:::


实测效果：`行 1: ["[类型转换] 第 1 行字段 'age' 的值 'abc' 不是合法整数"]`——**错误信息说清了是哪一行、哪个字段、什么值、为什么**，人工一眼能判。
>
> 🇹🇸 **TS 侧有额外的"静默猜值"陷阱**：Python 是 `int(v)` 抛 `ValueError`，不捕获就自然冒泡；TS 的 **`Number("abc")` 不抛错，返回 `NaN`**。若写成 `if (Number.isNaN(n)) row.cleaned[k] = 0`，就是把反例原封不动搬过来；而如果**忘了判 `NaN`**，`NaN` 会一路流到报告里（`JSON.stringify` 时变 `null`），比填 0 更隐蔽。所以 TS 侧必须显式 `Number.isNaN` 检查后抛 `Unclear`。

## 反例 4：串行调用 `.result()`

::: code-group

```python [Python]
@entrypoint(checkpointer=InMemorySaver())
def flow(batch):
    rows = [clean_row(r).result() for r in batch.rows]   # ❌ 立即取 = 串行
    return rows
```

```typescript [TypeScript]
const flow = entrypoint(
  { name: "flow", checkpointer: new MemorySaver() },
  async (batch: Batch) => {
    const rows = [];
    for (const r of batch.rows) rows.push(await cleanRow(r));   // ❌ 逐个 await = 串行
    return rows;
  }
);
```

:::


**实测**：2 个 0.3s 任务 → 耗时 **0.60s**。

### 正解

::: code-group

```python [Python]
futures = [clean_row(r) for r in batch.rows]    # 先全提交
rows = [f.result() for f in futures]            # 再统一收
```

```typescript [TypeScript]
const futures = batch.rows.map((r) => cleanRow(r));   // 先全提交
const rows = await Promise.all(futures);              // 再统一收
```

:::


**实测**：同样 2 个任务 → **0.30s**，快 2 倍。

> 💡 这是 Functional API 版的 `Send` 扇出——**动态扇出就是列表推导**。
>
> 🇹🇸 **TS 侧**：没有 `.result()`，等价物是 `Promise.all`。要点同样是"**先全提交、再统一收**"：
> ```typescript
> const futures = batch.rows.map((r) => cleanRow(r));   // 先全提交
> const rows = await Promise.all(futures);              // 再统一收
> ```
> 反例写法是 `for (const r of rows) out.push(await cleanRow(r))`——**逐个 await 就是串行**，实测耗时同样是 2 倍。

## TS 写法对照表

| Python | TypeScript | 注意 |
|--------|-----------|------|
| `@task` 装饰器 | `const f = task("name", fn)` | 无装饰器，名字必填 |
| `f.result()` | `await f` | 返回 Promise |
| `[clean(r) for r in rows]` + 逐个取 | `rows.map(r => clean(r))` + `Promise.all` | 先提交后收 |
| `for r in rows: clean(r).result()` | `for (const r of rows) await clean(r)` | 串行反例，写法很像正解 |
| `Command(resume={...})` | `new Command({ resume: {...} })` | 必须 `new` |
| dict 形状错误 → `TypeError` | **不报错，原样回传** | TS 无 xxh3 校验，更隐蔽 |
| `except ValueError` | `if (Number.isNaN(n)) throw` | `Number("abc")` 不抛错 |
| `out["__interrupt__"][0].value` | `out.__interrupt__[0].value` | 键只有 `__interrupt__` |
