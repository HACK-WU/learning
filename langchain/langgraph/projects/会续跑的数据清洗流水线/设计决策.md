# 设计决策

> 三个"换个人可能选另一个方案，且也有道理"的决策点：候选对比 → 最终选择 → 理由 → 代价 → 什么情况下改选。

---

## 决策 1：这个需求该用 Functional API 还是 Graph API？

### 候选方案

| 方案 | 效果 | 代价 |
|------|------|------|
| **A. Graph API** | 中间状态具名，可逐格 inspect / 修改；历史 4 条 | 要把 for 循环翻译成节点 + 边 + State schema；样板多 |
| **B. Functional API**（本项目） | 直接把已有脚本改造成 entrypoint，控制流就是 if / while | 中间过程无具名字段；历史只有 2 条；不能逐格改 |
| **C. 混用** | 外层 Functional、内层 Graph | 两套心智模型；存档各管各的 |

### 最终选择：**B. Functional API**

### 理由

1. **需求本身是"改造已有脚本"**——这是课 11 列的 Functional API 首选项信号。原脚本是顺序执行 + 一个判断，翻译成图没有收益。
2. **清洗是流水账**：关心"这批洗出来什么样"，不关心中间第几格。Graph API 的核心优势（逐格 inspect）用不上。
3. 实测并发能力**不打折**：先全提交 `Future` 再统一收，2 个 0.3s 任务从 0.60s 降到 0.30s。

### 为此付出的代价

- **不能逐格改中间状态**。运营想"手动把第 3 行的 city 改成北京"——Functional 做不到（只能整体替换返回值）。
- **历史只有 2 条**，排障时看不到"卡在第几步"的粒度（Graph API 有 4 条）。
- `get_state().values` 是 `3` 这样的整体值，不是 `{'log': [...]}`，可观测性弱。

### 什么情况下该改选 A

- 需求出现"**单独重跑某一行**""**手动改某个字段**""**看每一步的中间结果**" → 立刻换 Graph API。
- 团队要靠图拓扑当文档（多人协作）→ Graph API。

## 决策 2：不确定的数据，猜一个默认值还是问人？

### 候选方案

| 方案 | 效果 | 代价 |
|------|------|------|
| **A. 静默填默认值**（`int(v) or 0`） | 不卡流程，全自动 | **下游埋雷**：age=0 和"不知道 age"是一回事吗？ |
| **B. 整行丢弃** | 简单，不留脏数据 | 数据丢失；一行里 age 坏了把 name 也丢了 |
| **C. 标记 + 交人工**（本项目） | 不猜、不丢，人来定 | 要人介入；量大时人工是瓶颈 |

### 最终选择：**C. 标记 + 交人工**

### 理由

1. **数据清洗的黄金律是"不猜"**。静默填默认值会在下游产生无法追溯的错误——你不知道 `age=0` 是真实数据还是洗坏了。
2. 实测效果清晰：行 1「`age='abc'` 不是合法整数」、行 2「缺少必填字段 name」都被准确标出，交人工裁决。
3. 用 `Unclear` 异常区分"**出错**"和"**要确认**"——这是两种性质不同的事，混在一起会让调用方无法处理。

### 为此付出的代价

- **人工是瓶颈**。10 万行有 1 万行要确认，人工看不过来。
- `interrupt` 会**挂起整条流水线**，没有超时兜底。

### 什么情况下该改选 A 或 B

- 有明确的业务默认值（如"未知年龄统一填 -1"且下游认这个约定）→ 选 **A**，但要记录 `Fix` 便于追溯。
- 数据质量极差且量大 → 选 **B** 先保主流程，坏行走单独的死信队列。
- **折中做法**（生产更常见）：设阈值，少量不确定就 interrupt，超过 N 行就整批挂起等人改规则。

## 决策 3：哪些计算标 `@task`？

### 候选方案

| 方案 | 效果 | 代价 |
|------|------|------|
| **A. 全标** | 最大化复用 | 每个 task 都写存档，checkpoint 膨胀；小函数的序列化开销 > 重跑开销 |
| **B. 全不标** | 最省事 | resume 时**全部重跑**——实测普通函数 resume 跑了 2 次 |
| **C. 按"重跑贵不贵"标**（本项目） | 贵的标，便宜的不标 | 要判断；判断错了要么白存要么白跑 |

### 最终选择：**C. 按成本标** —— `clean_row` 和 `detect_outliers` 标，规则函数不标

### 理由

1. 实测证明**只有 `@task` 的结果会在 resume 时复用**，普通函数一律重跑。所以这个选择直接决定"卡住一次白干多少活"。
2. `clean_row` 是逐行的重活（N 行 = N 次调用），`detect_outliers` 是全量扫描——都值得标。
3. 规则函数（`strip_whitespace` 等）是**纯函数且极快**，标 task 反而增加序列化开销，不标。

### 为此付出的代价

- **判断依赖经验**。"这个函数值不值得标"没有量化标准，边界情况容易判断错。
- 标了 task 的函数**参数必须可序列化**（实测：自定义 dataclass 靠 pickle 兜底，日志警告"未来版本会阻断"）。

### 什么情况下该改选 A

- 流水线里每个步骤都很贵（都要调外部 API）→ **全标**，checkpoint 膨胀的代价远小于重跑。
- 不确定时，**宁可多标**——多存的代价是空间，漏标的代价是重复计算。

## 📌 三个没做但必须知道的事

1. **没有并发上限**。所有行一次性提交 `Future`，10 万行会同时发起。生产要分批。
2. **`interrupt` 无超时**。人一直不答复，流水线就一直挂着。生产要配超时 + 告警。
3. **自定义 dataclass 靠 pickle 兜底**。日志已警告"未来版本会阻断"。生产应让入参/返回值可 JSON 化，或显式注册 `allowed_msgpack_modules`。
