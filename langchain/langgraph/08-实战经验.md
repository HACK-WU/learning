## 一、适用边界与反模式

> **"不该用"比"怎么用"更值钱**——这是从"会用"到"用对"的分界线。

### 1.1 什么时候别用 LangGraph

| 场景 | 为什么别用 | 该用什么 |
|------|-----------|---------|
| **一次 LLM 调用 + 一两个工具** | 图的样板代码比业务还多，节点/边/schema 全是开销 | `ChatOpenAI.bind_tools()` 或 `create_agent` |
| **纯直流程，没有循环** | 控制流就是 `A→B→C`，用图只是把函数调用包一层壳 | 普通函数；要持久化再加 `@entrypoint`（课 11） |
| **流程永不中断、无需回放** | checkpointer、interrupt、time-travel 的复杂度换不来收益 | 普通异步任务队列（Celery / RQ） |
| **要求亚毫秒级延迟** | 每次节点跳转 = 一次 checkpoint 写入往返；6 节点一转实测 3.5–8s | 先问清是否真需要这个延迟量级 |
| **团队没有 Postgres / Redis 运维能力** | 自托管连撞三道门（Redis / Postgres / License，课 13 实测） | LangGraph Platform 托管，或先别上 |
| **合规要求"全链路可解释"且不可回放** | 你需要的恰恰是 LangGraph 的反面 | 传统工作流引擎（Temporal / Airflow） |

> 💡 判断口诀：**有循环、要暂停、要回放、要并行**——占任一条才值得上图。四条全不占，就是在给函数穿铠甲。

### 1.2 六个高频反模式

| # | 反模式 | 为什么会踩 | 正解 |
|---|--------|-----------|------|
| 1 | **State 字段不写 reducer** | 以为"列表会累加"——默认语义是**覆盖**，`log` 从 `['第一版']` 变 `['第二版']`，**不报错**（课 3 实测） | 累加字段一律 `Annotated[list, add]` |
| 2 | **把 `thread_id` 当可选标签** | 看示例里 `thread_id` 像是演示用的，其实它是**主键**（课 5 实测：不传直接 `ValueError`） | 每次 invoke 都显式传 |
| 3 | **把"再跑一次"当重新开始** | 同一 `thread_id` 再 `invoke` 是**接着跑**，字段会叠加（课 5 实测） | 要重开就换 `thread_id` |
| 4 | **`interrupt()` 之前放副作用** | 以为"暂停后从断点续"——实际是**节点整体重跑**（课 8 实测：节点执行 2 次） | 扣款/发短信一律放 `interrupt()` **之后** |
| 5 | **配了 `RetryPolicy` 就算有重试** | 默认 `retry_on` 把 `ValueError`/`TypeError` 当"代码 bug"不重试（课 10 实测：`max_attempts=3` 也只跑 1 次） | 抛自定义异常类型 |
| 6 | **`langgraph build` 过了就觉得能上** | 打包**只校验依赖**，运行时配置一个都不校（课 13 实测：起容器连撞三次） | 构建后必须真起一次容器 |

## 二、高频故障模式（8 条）

> 每条五段式：**症状（可观测）→ 根因 → 排查路径 → 修复 → 预防**
> 全部可溯源：本机实测（`langgraph 1.2.11`）+ 官方文档 + 联网核查。症状均为可观测现象。

### 故障模式 1：并发写同一字段，图直接崩

- **症状**：`langgraph.errors.InvalidUpdateError: At key 'log': Can receive only one value per step.`（课 4 实测）
- **根因**：同一 superstep 内两个节点写同一个 key，而该 key 没声明 reducer。LangGraph 宁可崩也不静默丢数据——这是**设计哲学，不是 bug**。
- **排查**：`stream_mode="updates"` 看这一批里哪几个节点同时返回了同一 key。
- **修复**：

::: code-group

```python [Python]
from typing import Annotated
from operator import add

class State(TypedDict):
    log: Annotated[list[str], add]   # 声明合并方式
    # 两个分支都写 log 也不再冲突
```

```typescript [TypeScript]
import { Annotation } from "@langchain/langgraph";

const State = Annotation.Root({
  // TS 侧 reducer 必填，且要显式写「怎么合并」
  log: Annotation<string[]>({
    reducer: (a, b) => a.concat(b),   // 对应 Annotated[list, add]
    default: () => [],
  }),
  // 两个分支都返回 log 也不再冲突
});
```

:::

> 🇹🇸 **差异**：Python 的 `Annotated[list, add]` 是「类型 + 运算符」，TS 是「函数」——`reducer: (a, b) => a.concat(b)`。而且 TS 的 reducer **必填**：漏掉的结果是编译期 `TS2345`，并非「默认覆盖」。想表达 Python 的「默认覆盖」语义，要写 `reducer: (_p, n) => n`。

- **预防**：所有列表型字段**一律** `Annotated + reducer`，不写裸 `list`。用 `Send` 扇出时尤其要查。
- 📚 来源：本机实测（课 4）+ [LangGraph 错误参考](https://langchain-ai.github.io/langgraph/reference/errors/)

### 故障模式 2：串行不报错，数据却静默丢失

- **症状**：节点 A 返回 `{"history": ["第1版"]}`，节点 B 返回 `{"history": ["第2版"]}`，最终 `history == ["第2版"]`——**第一版没了，不报错、不打招呼**（课 3 实测）。
- **根因**：LangGraph 默认所有字段是**覆盖语义**（LastWriteWins）。你以为"审批意见会累积"，其实一直在被划掉重写。
- **排查**：对比"节点返回值"与"最终 state"——值只剩最后一个时即命中。
- **修复**：同故障模式 1，加 `Annotated[list, add]`。
- **预防**：**这是最阴的一类**——故障模式 1 会崩（好查），这条不会（只能靠代码评审发现）。建议：写节点前先问"这个字段是累加还是覆盖"。
- 📚 来源：本机实测（课 3 验证 A）

### 故障模式 3：图绕圈出不来 / recursion_limit 到了

- **症状**：`langgraph.errors.GraphRecursionError: Recursion limit of 25 reached without hitting a stop condition`
- **根因**：① 条件边某分支**永远到不了 `END`**（最常见）；② 循环是真需求但默认上限太小。**注意 `recursion_limit` 数的是"图跳转次数"，不是你的业务步数**（课 4 实测）。
- **排查**：`graph.get_state(config)` 看 `next` 卡在哪个节点；用 `stream_mode="updates"` 看哪个节点反复出现。
- **修复**：

::: code-group

```python [Python]
# ① 真长任务：调大（留余量）
app.invoke(inp, {"recursion_limit": 100})
# ② 路由 bug：补退出分支（首选，别只调大掩盖问题）
def route(s):
    return END if s["tries"] >= 5 else "retry"
# ③ 用 Literal 约束返回值，让分支穷举
```

```typescript [TypeScript]
// ① 真长任务：调大（留余量）—— 字段名是驼峰 recursionLimit
await app.invoke(inp, { recursionLimit: 100 });
// ② 路由 bug：补退出分支（首选，别只调大掩盖问题）
const route = (s: typeof State.State) => (s.tries >= 5 ? END : "retry");
// ③ 用字面量联合类型约束返回值，让分支穷举
type Next = "retry" | typeof END;
```

:::

> 🇹🇸 **差异有三处**：① 字段名是 `recursionLimit`（驼峰）。本机实测：传 `{ recursionLimit: 7 }` 报 `Recursion limit of 7 reached`，传 `{ recursion_limit: 7 }` 则报 `Recursion limit of 25 reached`——下划线写法**不报错但被忽略**，静默按默认 25 跑；② 默认值同样是 25，超限抛 `GraphRecursionError`；③ TS 没有 `Literal`，用**字面量联合类型** `"retry" | typeof END` 达到同样的穷举效果。

- **预防**：条件边返回类型写 `Literal[...]`；开发期把 `recursion_limit` 调**小**，让死循环早暴露。
- 📚 来源：官方文档错误参考 + [社区排查指南](https://www.buzhou.io/zh/articles/langgraph-graphrecursionerror-invalidupdateerror)
- ⚠️ 版本注意：1.0.6 起官方默认已提到 1000（社区实测 10,006 步不报、10,007 报），但**不要把这个默认值当你的退出策略**。

### 故障模式 4：加了 checkpointer，`update_state` 改了却不生效

- **症状**：改了 state 再 `invoke`，结果还是老样子；或者恢复后从奇怪的位置继续。
- **根因**：checkpoint 记着"图走到哪了"（`next`）。`update_state` 只改值，**不改游标**；老 checkpoint 仍指向旧的待执行节点。
- **排查**：`get_state(config)` 看 `next` 是不是你预期的节点。
- **修复**：确认要改的是**最上游的依据**（如 `amount`）而不是**下游结论**（如 `decision`）——改结论会被重算覆盖（课 9 实测）。要彻底重开就清掉该 `thread_id` 的 checkpoint 或换新 thread。
- **预防**：把 `update_state` 当成"改输入"而非"改结果"。
- 📚 来源：本机实测（课 9）+ [AlterSquare 实践文](https://altersquare.io/blog/langgraph-state-management-undocumented-issues-after-commit)

### 故障模式 5：断点续跑后，副作用执行了两次

- **症状**：审批通过一次，却发了两条短信 / 扣了两笔款。
- **根因**：`interrupt()` **不是"从断点续跑"，是"带着答案把整个节点重跑一遍"**（课 8 实测：节点执行 2 次）。`interrupt()` **之前**的代码每次恢复都会再执行。
- **排查**：在节点首行打日志，看恢复时是否又打了一次。
- **修复**：把所有副作用（扣款 / 发信 / 写库）移到 `interrupt()` **之后**；或给副作用加幂等键。
- **预防**：**`interrupt()` 之前的区域必须是纯计算**（可重复执行无影响）。这是写代码时的硬纪律，不是事后优化。
- 📚 来源：本机实测（课 8）+ 官方文档 Interrupts

### 故障模式 6：配了重试，却一次都没重试

- **症状**：外部接口抛 `ValueError("接口超时了")`，配了 `RetryPolicy(max_attempts=3)`，**日志显示只调用 1 次**直接炸（课 10 实测）。
- **根因**：默认 `retry_on` 把 `ValueError` / `RuntimeError` / `TypeError` 视为**代码 bug**（收件人地址写错了，再送也没用），不重试。只有 `ConnectionError`、HTTP 5xx、不认识的**自定义异常**才重试。
- **排查**：看抛的异常类型是不是这三类。
- **修复**：

::: code-group

```python [Python]
class TransientUpstreamError(Exception):   # 自定义类型 = 可重试
    pass

graph.add_node("risk", risk_node, retry_policy=RetryPolicy(
    max_attempts=3, retry_on=TransientUpstreamError,
))
```

```typescript [TypeScript]
class TransientUpstreamError extends Error {}   // 自定义类型 = 可重试

new StateGraph(State).addNode("risk", riskNode, {
  retryPolicy: {
    maxAttempts: 3,
    // ⚠️ 只收函数：写成 retryOn: TransientUpstreamError 是类型错误
    retryOn: (e: unknown) => e instanceof TransientUpstreamError,
  },
});
```

:::

> 🇹🇸 **三处差异**：① `retry_on` 收**异常类**，`retryOn` 收**函数**（`(e: unknown) => boolean`）；② `retryPolicy` 只能挂在 `addNode` 第三参或 `setNodeDefaults`，挂到 `compile()` 上 `tsc` 报 `TS2353`、`tsx` 静默忽略；③ **不配 `retryPolicy` = 一次都不重试**（源码 `pregel/retry.js` 里 `resolvedRetryPolicy === void 0` 直接 break），实测带 `retryOn` 且 `maxAttempts: 3` 时调 3 次。

- **预防**：**异常类型是隐式契约**——节点文档里写清"本节点抛什么"，团队约定优先于默认行为。
- 📚 来源：本机实测（课 10 验证 + 结课项目反例 1）

### 故障模式 7：同步节点配 timeout，编译期就炸

- **症状**：`ValueError: Node timeouts are only supported for async nodes because ...`（课 10 实测）
- **根因**：Python 掐不干净同步任务，LangGraph **索性在 `compile()` 阶段就拒绝**，而不是运行时给你惊喜。
- **排查**：看报错发生在 compile 还是 run——compile 阶段即为此条。
- **修复**：把节点改成 `async def`，或改用 `asyncio.wait_for` 在节点内部自己控时。
- **预防**：想用节点级 timeout 就**从一开始把节点写成 async**，后期改要动全部签名。
- 📚 来源：本机实测（课 10）

### 故障模式 8：并发上来后 Postgres 连接池耗尽

- **症状**：`psycopg_pool.PoolTimeout: couldn't get a connection after 30.00 sec`；或响应在某个并发点突然悬崖式上涨，**加副本也不缓解**；PG 日志 `FATAL: sorry, too many clients already`。
- **根因**（三个叠加）：① psycopg 池默认 `min_size=4`、`max_size=None`（即封顶 4 条连接）；② 把单个 `AsyncConnection` 而非连接池传给 `AsyncPostgresSaver`，所有 checkpoint 操作在一条连接上串行；③ Web 框架在**整个 run 外面**开了请求级事务——LLM 调用期间一直占着连接。
- **排查**：

::: code-group

```python [Python]
pool.get_stats()   # requests_waiting > 0 且上涨 → 池是瓶颈
```

```typescript [TypeScript]
// pg.Pool 没有 get_stats()，只有三个计数属性
console.log({
  total: pool.totalCount,      // pool_size
  idle: pool.idleCount,        // pool_available
  waiting: pool.waitingCount,  // requests_waiting > 0 且上涨 → 池是瓶颈
});
```

:::

> 🇹🇸 `psycopg_pool` 有 `get_stats()` 一把取全；`pg.Pool` **没有这个方法**，要自己读 `totalCount` / `idleCount` / `waitingCount` 三个属性拼出来。

```sql
SELECT state, count(*) FROM pg_stat_activity GROUP BY 1;
-- idle in transaction 多 → ORM 占连接；idle 多 → 池太小
```

- **修复**：

::: code-group

```python [Python]
# ✅ 传池，并显式给 max_size
pool = AsyncConnectionPool(conninfo=DB_URI, max_size=20)
saver = AsyncPostgresSaver(pool)
# ✅ 绝不让数据库事务跨越 LLM 调用
# ✅ 平台部署：调 LANGGRAPH_POSTGRES_POOL_MAX_SIZE（默认 150/副本，易爆）
```

```typescript [TypeScript]
import pg from "pg";
import { PostgresSaver } from "@langchain/langgraph-checkpoint-postgres";

// ✅ 传池，并显式给 max（node-postgres 默认 10）
const pool = new pg.Pool({ connectionString: DB_URI, max: 20 });
const saver = new PostgresSaver(pool);
await saver.setup();      // 每库跑一次；漏 await 会静默不建表
// ✅ 绝不让数据库事务跨越 LLM 调用
// ✅ 平台部署：各副本的 max 之和不要超过数据库 max_connections
```

:::

> 🇹🇸 **差异**：① 参数名是 `max`（不是 `max_size`）；② `saver.setup()` 在 TS 是 **async**，`await` 不能漏；③ `PostgresSaver` 来自独立包 `@langchain/langgraph-checkpoint-postgres`；④ `LANGGRAPH_POSTGRES_POOL_MAX_SIZE` 是 Python 平**服务端**的开关，TS 自建池时没有对应环境变量，直接按「副本数 x max」算总连接数即可。

- **预防**：副本数 × `max_size` 必须小于 `max_connections`（默认 100）；或直接上 PgBouncer。
- 📚 来源：[Zenthos 生产实践](https://zenthos.in/blogs/langgraph-postgres-checkpointer-production) + [LangChain 官方支持文](https://support.langchain.com/articles/9651943867-how-do-i-resolve-too-many-connections-postgresql-errors-when-scaling-platform-instances) + 社区多篇一致报告
- ⚠️ 本条**非本机实测**（本地无高并发 PG 环境），属联网核查 + 领域公认实践。

## 三、落地 / 上线 Checklist

> 投产前逐项勾。分四组，按"先正确性、后性能、再运维"排。

### A. 正确性（不通过不能上线）

| # | 检查项 | 通过标准 |
|---|--------|---------|
| A1 | 所有列表字段都声明了 reducer | 全仓搜 `Annotated[list`，无裸 `list` 状态字段 |
| A2 | 条件边穷举 | 返回类型用 `Literal[...]`；`add_conditional_edges` 的 mapping 含 `END` 兜底 |
| A3 | `interrupt()` 之前无副作用 | 逐个人工审批节点审一遍 |
| A4 | 重试的异常类型已自定义 | 没有节点靠 `ValueError` 触发重试 |
| A5 | 每次 invoke 都传 `thread_id` | 搜索 `invoke(`，每条都有 configurable |
| A6 | 副作用有幂等键 | 打款/发信类操作键 = 业务标识 + 金额 |

### B. 性能与容量

| # | 检查项 | 通过标准 |
|---|--------|---------|
| B1 | checkpointer 用 Postgres/Redis，不用 MemorySaver | 生产代码无 `InMemorySaver` |
| B2 | 传的是连接池不是单连接 | `AsyncPostgresSaver(pool)` |
| B3 | `副本数 × max_size < max_connections` | 算过，留了 superuser 余量 |
| B4 | 消息历史有裁剪 | 用了 `RemoveMessage` **写回 channel**（只改 prompt 不减 state） |
| B5 | `recursion_limit` 显式设置 | 不依赖默认值当退出策略 |

### C. 可观测与运维

| # | 检查项 | 通过标准 |
|---|--------|---------|
| C1 | LangSmith / Langfuse 已接入 | 每次节点跳转、工具调用都有 trace |
| C2 | checkpoint 有保留策略 | 有定期清理任务（开源 checkpointer **无内置 TTL**） |
| C3 | `/health` 之外有 worker 心跳检查 | 能发现"进程活着但不干活"的僵尸态 |
| C4 | `LANGGRAPH_STRICT_MSGPACK=true` | 防恶意/损坏 checkpoint 反序列化 |
| C5 | 部署后真起过一次容器 | `langgraph build` 通过 ≠ 能跑 |

### D. 安全

| # | 检查项 | 通过标准 |
|---|--------|---------|
| D1 | 密钥走环境变量不入库 | `langgraph.json` 的 `env` 指向 `.env` 文件名 |
| D2 | 自托管 License Key 有效 | 是 JWT 格式，乱填报 `Not enough segments` |
| D3 | 敏感信息不进 state | state 会进 checkpoint 落库 |
