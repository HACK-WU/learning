## 零、先看清四个项目分别回答了什么

四个项目是**刻意按"一条主线一个"来设计的**，不是四个随机的例子：

| 项目 | API | 回答的核心问题 | 关键机制 |
|------|-----|--------------|---------|
| [会审批的退款工单系统](projects/会审批的退款工单系统/README.md) | Graph | **一次任务**怎么跑完、被卡住、再续跑 | `interrupt()` + 条件边 + `RetryPolicy` |
| [会记住和遗忘的客服助手](projects/会记住和遗忘的客服助手/README.md) | Graph | **跨会话的东西**放哪、怎么不写脏 | Store 命名空间 + 冲突检测 |
| [会重试和降级的调研流水线](projects/会重试和降级的调研流水线/README.md) | Graph | **外部依赖不可靠**时怎么不崩、不慢、不白试 | `Send` 扇出 + 子图隔离 + 分类重试 |
| [会续跑的数据清洗流水线](projects/会续跑的数据清洗流水线/README.md) | Functional | **已有脚本**怎么最小成本加暂停和续跑 | `@entrypoint` / `@task` |

> 💡 前三个用 Graph、最后一个用 Functional——**这个分布本身就是结论**：
> 需要"逐格看见、逐格修改"的用 Graph；纯流水账改造用 Functional。

## 一、什么时候用 Graph，什么时候用 Functional

### 判据（一句话）

**中间过程要不要被单独看见和逐格修改？**

### 实测对照表

| 维度 | Graph API | Functional API |
|------|-----------|----------------|
| 状态形态 | 具名字段，`{"log": [...], "amount": 300}` | 整体值，`3`（就一个数） |
| 历史条数 | 2 节点 → **4 条** | 同流程 → **只有 2 条** |
| 逐格修改 | ✅ `update_state` 改单个字段 | ❌ 只能整体替换返回值 |
| config 必填 | ❌ 不传也能跑 | ✅ 不传直接 `ValueError` |
| 并发写法 | `Send` 扇出 | 先全提交 `Future` 再统一收 |
| 暂停续跑 | `interrupt()`，节点**整体重跑** | `interrupt()`，**已完成的 `@task` 不重跑** |
| 改造成本 | 要把 for 循环翻译成节点 + 边 | 原脚本加两个装饰器 |

### 选 Functional 的三个信号（项目 4 实证）

1. **已有脚本要改造**，不是从零设计
2. 控制流**直**（顺序 + 一个 if），没有循环回退
3. 关心"**这批洗出来什么样**"，不关心"第 3 行在第几格"

### 立刻换 Graph 的信号

- 出现"**单独重跑某一行**""**手动改某个字段**""**看每一步中间结果**"
- 团队要靠图拓扑当文档（多人协作）
- 需要 `update_state` 做人工修正

> 📌 **项目 4 的代价实录**：选了 Functional 之后，`get_state().values` 是 `3` 这样的整体值，
> 运营想"手动把第 3 行的 city 改成北京"**做不到**。这不是 bug，是选型的对价。

## 二、什么时候该上 Store（而不是只靠 checkpoint）

**checkpoint 和 Store 不是二选一，是回答两个不同的问题。**

| | checkpoint | Store |
|---|---|---|
| 回答 | "**这次**执行到哪了" | "**这个人**我们认识多少" |
| 生命周期 | 一次执行 / 一个 thread | 跨 thread、跨会话、永久 |
| 寻址 | `thread_id` | `(namespace, key)` |
| 典型内容 | 流转状态、中间结果 | 用户偏好、事实档案 |
| 项目 | 1 / 3 / 4 | **2** |

### 上 Store 的信号

1. 要记住的东西**跨会话**——用户下周来还得认识他
2. 要按**用户/租户**隔离——`("profile", user_id)` 天然隔离
3. 要支持**语义检索**或按 key 精确取

### 只靠 checkpoint 就够的信号

- 只在意"这一笔工单跑到哪了"（项目 1）
- 跑完就不用了（项目 3 的来源结果）

### 🔴 上 Store 必须同时解决的三件事（项目 2 的核心贡献）

Store 是**会被写脏**的——写进去容易，改对难。项目 2 实测出的三个必答题：

| 问题 | 项目 2 的做法 | 不做的后果 |
|------|-------------|-----------|
| **冲突了怎么办** | `interrupt()` 拦下，三种裁决（confirm / reject / keep） | 静默覆盖 = 旧信息永久丢失 |
| **高风险事实能直接写吗** | 风险分级，高风险**必须**过 confirm | 抽错的事实直接进档案 |
| **命名空间怎么管** | `MemStore` 门面 + `ns_*()` 函数收在一处 | 命名空间散落各处，改结构要翻全仓 |

> 📌 **只做"是/否"两个选项是不够的**。项目 2 提供了三种裁决，因为
> "我不要这个新说法，但要保留旧的"（`keep`）表达不了——用 reject 会把两个都丢掉。

## 三、什么时候该重试，什么时候该降级

**这是最容易凭感觉搞错的一块。** 项目 3 的实测结论是：重试和降级不是二选一，
是**按错误分类分流**。

### 第一层判断：这个错，再试一次会不一样吗？

| 错误性质 | 例子 | 该做什么 | 项目 3 实测 |
|---------|------|---------|-----------|
| **瞬时**（抖动、限流、超时） | 网络闪断、503 | **重试** | 抖 2 次 → 调 3 次后成功 |
| **永久**（参数错、404、权限） | 404、KeyError | **立刻降级** | 重试 0 次直接降级 |
| **代码 bug** | `ValueError`、`TypeError` | 都不该——**修代码** | 默认策略**不重试** |

### 🔴 硬事实：默认 `retry_on` 对 `ValueError` 不重试

```
配了 RetryPolicy(max_attempts=3)：
  抛 TransientUpstreamError  → 调用 3 次 ✅
  抛 ValueError              → 调用 1 次直接炸 ❌
```

> **"不配 retry_on" ≠ "全都重试"**，而是"按框架默认清单重试"——
> 那个清单**不是你业务的清单**。团队里有人顺手 `raise ValueError`，
> 重试就**静默失效**：不报错、不告警。

**推论**：异常类型成了**隐式契约**。要在项目里显式定义 `TransientError` / `PermanentError`。

### 第二层判断：重试会带来副作用吗？

| 节点性质 | 能重试吗 | 保护手段 |
|---------|---------|---------|
| **只读**（风控评分、查询） | ✅ 随便重 | 无 |
| **有副作用**（打款、发短信） | ⚠️ 必须幂等 | 幂等键（项目 1：订单号+金额） |

### 第三层：降级放哪

项目 3 实测出的组合方案：

```python
# 子图级兜底：整个子图炸了也不拖垮父图
parent.add_node("source", child, error_handler=degrade)

# 节点级自存：单个来源失败，把错误记进结果里继续走
except Exception as e:
    return {"result": SourceResult(ok=False, error=str(e))}
```

> ⚠️ **`error_handler` 只能接收 1 个参数**，且收到的是 **state 而不是异常对象**（实测）。
> 想在 handler 里知道"为什么失败"，得在节点内部先把错误写进 state。

## 四、什么时候该让人介入（interrupt 的正确用法）

四个项目里有三个用了 `interrupt()`，但**用法和代价完全不同**。

### 🔴 硬事实：interrupt 所在的节点/执行，恢复时会整体重跑

| API | 恢复时会重跑什么 |
|-----|----------------|
| Graph | **整个节点**重跑（项目 1 实测：节点执行 2 次） |
| Functional | 含 interrupt 的那次执行重跑；**已完成的 `@task` 不重跑** |

**推论（四个项目共同的铁律）**：

> **`interrupt()` 之前不要放副作用。** 扣款、发短信、写日志一律放 `interrupt()` **之后**。

### 什么时候该 interrupt

| 场景 | 项目 | 判据 |
|------|------|------|
| 高风险操作要人签字 | 1 | 金额/权限超阈值 |
| 记忆冲突要人裁决 | 2 | 同字段不同值，且是高风险事实 |
| 数据不确定要人定夺 | 4 | 转不了类型、缺必填 |

### 什么时候**别** interrupt

| 情况 | 为什么 | 改用什么 |
|------|-------|---------|
| 等待可能**几天甚至几周** | 内存 checkpointer 进程重启即丢；存档点长期占用 | 落业务表，人工完成后以**新 thread** 起第二段（项目 1 决策 1 的 B 方案） |
| 冲突/异常**频率很高** | 人工是瓶颈，会拖垮流程 | 设阈值：少量才 interrupt，超量整批挂起等人改规则 |
| 有明确业务默认值 | 没必要打扰人 | 填默认值 + 记 `Fix` 便于追溯 |

### ⚠️ 两个 interrupt 的坑（项目 4 实测）

1. **`Command(resume=...)` 传 dict 会被当 interrupt-id 映射校验**
   ```python
   Command(resume={1: "accept"})     # ❌ TypeError: expected string or bytes-like object
   Command(resume=[{"id": 1, "decision": "accept"}])   # ✅ 用 list[dict]
   ```
   框架检查每个 key 是否为 32 位 hex（interrupt id），行 id 是 int 就炸。

2. **Graph API 不传 config 也能跑，Functional API 不行**
   ```python
   flow.invoke(1)                                          # ❌ ValueError
   flow.invoke(1, {"configurable": {"thread_id": "t1"}})   # ✅
   ```

## 六、四个项目共同的反模式（跨项目才看得出来）

这些是**单看一个项目不容易发现、横向对比才浮现**的规律：

| # | 反模式 | 为什么错 | 证据 |
|---|--------|---------|------|
| 1 | **把"再跑一次"当重新开始** | 同 `thread_id` 再 invoke 是**接着跑**，字段会叠加 | 项目 1 实测 |
| 2 | **`interrupt()` 之前放副作用** | 恢复时节点**整体重跑**，副作用做两遍 | 项目 1 实测（节点执行 2 次） |
| 3 | **配了 `RetryPolicy` 就算有重试** | 默认 `retry_on` 不认 `ValueError` | 项目 3 实测（3 次配置只跑 1 次） |
| 4 | **重活不标 `@task`** | resume 时全部重跑，前面的活白干 | 项目 4 实测（普通函数 resume 跑 2 次） |
| 5 | **不确定就填默认值** | 下游分不清"真实值"还是"洗坏了"，污染统计 | 项目 4 `coerce_types` 抛 `Unclear` |
| 6 | **串行调 `.result()`** | 立即取 = 串行，先全提交再收 = 并发 | 项目 4 实测：**0.30s vs 0.60s** |
| 7 | **外部依赖写死在节点里** | 测试无法替换，多租户互相污染 | 项目 1 决策 3（`configurable` 注入） |
| 8 | **命名空间散落各处** | 改结构要翻全仓 | 项目 2 的 `MemStore` 门面 |

## 七、四个项目没覆盖的（诚实清单）

知道边界和知道内容一样重要：

| 没做 | 为什么 | 想做看哪 |
|------|-------|---------|
| **并发上限** | 项目 3/4 都是一次性全发出 | 分批：`fanout` 按 `batch_size` 切片 |
| **`interrupt` 超时** | 人不答复就一直挂着 | 生产配超时 + 告警 |
| **真实 LLM 调用** | 项目 2 刻意用规则保证可复现 | 项目 2 决策 1 给了改 LLM 的路径 |
| **Postgres / Redis 真实后端** | 全部用内存实现保证可跑 | 课 5 / 课 13 |
| **分布式部署** | 单机实测 | 课 13 |
| **自定义类型的序列化** | dataclass 靠 pickle 兜底，官方已警告"未来会阻断" | 生产应改可 JSON 化类型或注册 `allowed_msgpack_modules` |

## 八、带走的三句话

1. **选型看"中间过程要不要被逐格修改"**——要，就 Graph；不要，Functional 能省一大半样板。
2. **重试看"再试一次会不会不一样"**——会，才重试；不会，立刻降级。而且必须**显式分类**，别指望框架默认清单。
3. **`interrupt()` 之前不放副作用**——这一条在 Graph 和 Functional 里都成立，只是重跑的粒度不同。
