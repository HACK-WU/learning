## 1 · 🔴 并发写同一字段，图直接崩

**一眼识别**：`langgraph.errors.InvalidUpdateError: At key 'log': Can receive only one value per step.`

**先止血**：回滚最近一次改动；若在生产，切回上一个镜像版本。

| 若 | 则 |
|---|---|
| 该字段**应该累加**（日志/消息/结果列表） | 加 reducer：`log: Annotated[list[str], add]` |
| 该字段**应该覆盖**，但两个分支都写了 | 改图结构——让两个分支写不同 key，再由一个合并节点处理 |
| 用了 `Send` 扇出 | 被扇出的节点**必须**写带 reducer 的 key |

**修复**：

```python
from typing import Annotated
from operator import add

class State(TypedDict):
    log: Annotated[list[str], add]   # 关键：声明合并方式
```

**成功的标志**：重新运行不再抛 `InvalidUpdateError`，且 `log` 包含所有分支的内容。

**若无效** → 转 `debug` 现场排查；或查故障模式 1 的变体（节点返回值类型与 schema 不符，如该返回列表却返回了字符串）。

**预防**：所有列表型状态字段一律 `Annotated + reducer`，不写裸 `list`。

**原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 1

## 2 · 🔴 数据静默丢失（不报错）

**一眼识别**：不抛异常，但 `state` 里某个字段只剩**最后一次**写入的值；`history` / `log` 长度不增长。

> 这条最危险——**没有报错可搜**。发现方式只能是"结果看起来不对"。

**先止血**：若已影响线上数据，停图 + 从 checkpoint 回放修复（见条目 18）。

| 若 | 则 |
|---|---|
| 字段应该累加 | 加 `Annotated[list, add]` |
| 两个节点**串行**写同一字段 | 同上（串行也覆盖，只是不报错） |
| 已确认是覆盖语义且符合预期 | 无需修复，但**在 State 定义处写注释**说明 |

**修复**：同条目 1。

**成功的标志**：连续运行两次，字段内容**都在**（而不是只剩后者）。

**若无效** → 转 `debug`，用 `stream_mode="updates"` 逐步看每节点返回了什么。

**预防**：写节点前先问"这个字段是累加还是覆盖"，把答案写进字段名或注释。

**原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 2

## 3 · 🔴 图绕圈出不来

**一眼识别**：`langgraph.errors.GraphRecursionError: Recursion limit of 25 reached without hitting a stop condition`

**先止血**：若已上线且大量触发，**先调大 `recursion_limit` 让业务跑通**（临时），同时排查路由 bug。

| 若 | 则 |
|---|---|
| 路由函数某分支**永远到不了** `END` | **首选修这个**——补退出分支，不要只调大 limit 掩盖 |
| 循环是真需求，步数确实多 | `app.invoke(inp, {"recursion_limit": 100})`（留余量） |
| 节点自己跳回自己 | 加计数器退出条件：`return END if s["tries"] >= 5 else "retry"` |

**排查**：

```python
print(graph.get_state(config).next)          # 卡在哪个节点
for ns in graph.stream(inp, config, stream_mode="updates"):
    print(ns)                                 # 哪个节点反复出现
```

**成功的标志**：图能正常走到 `END`；或显式 limit 下不再误报。

**若无效** → 转 `debug`；检查条件边 mapping 是否缺 `END` 兜底项。

**预防**：条件边返回类型写成 `Literal[...]`；开发期把 limit 调**小**，让死循环早暴露。
⚠️ `recursion_limit` 数的是**图跳转次数**，不是你的业务步数。

**原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 3

## 4 · 🟡 忘传 `thread_id`

**一眼识别**：`ValueError: Checkpointer requires one or more of the following 'configurable' keys: thread_id, checkpoint_ns, checkpoint_id`

**先止血**：无（调用即失败，不产生脏数据）。

| 若 | 则 |
|---|---|
| 图 `compile` 时挂了 checkpointer | **每次** `invoke`/`stream` 都必须传 `thread_id` |
| Functional API 挂了 checkpointer | 同上，且 `config` 是必填位置参数 |
| 想重开一次全新对话 | 换一个新的 `thread_id`，**不是**不传 |

**修复**：

```python
config = {"configurable": {"thread_id": "user-123"}}
app.invoke(inp, config)          # Graph API
entrypoint.invoke(inp, config)   # Functional API：必填
```

**成功的标志**：不再抛 `ValueError`。

**若无效** → 检查是否传成了 `{"thread_id": ...}`（漏了 `configurable` 层）。

**预防**：封装一个 `make_config(user_id)` 函数，禁止手写字典。

**原理**：→ [08-实战经验.md](08-实战经验.md) · 反模式 2

## 5 · 🟡 缺 checkpointer

**一眼识别**：
- `ValueError: No checkpointer set`（`get_state` / `get_state_history` / `update_state`）
- `RuntimeError: Cannot use Command(resume=...) without checkpointer`

**先止血**：无（调用即失败）。

| 若 | 则 |
|---|---|
| 只想本地跑通、不要持久化 | 不调这些 API 即可（`interrupt()` **能抛**，只是不能恢复） |
| 要恢复 / 回放 / 审批 | `app = graph.compile(checkpointer=InMemorySaver())`（生产换 Postgres） |

**修复**：

```python
from langgraph.checkpoint.memory import InMemorySaver
app = graph.compile(checkpointer=InMemorySaver())
```

**成功的标志**：`get_state(config)` 能返回快照。

**若无效** → 确认 `compile()` 与 `invoke()` 用的是**同一个** app 对象（常见：compile 了两次，一个挂了一个没挂）。

**预防**：把 `compile(checkpointer=...)` 写进唯一的图构建函数，禁止散落 compile。

**原理**：→ [08-实战经验.md](08-实战经验.md) · 反模式 5 相关（课 8 硬约束 ②）

## 6 · 🔴 副作用执行了两次

**一眼识别**：审批只通过一次，但**扣了两笔款 / 发了两条信 / 写了两条记录**；节点首行日志出现两次。

**先止血**：立即停图；对账，找出重复记录；若涉及资金，走退款/冲正流程。

| 若 | 则 |
|---|---|
| 副作用在 `interrupt()` **之前** | 移到 `interrupt()` **之后**（根因） |
| 副作用本身必须靠前 | 加幂等键：`key = f"{order_id}:{amount}"`，执行前先查 |
| 用了 `@task` 之外的普通函数（Functional API） | 普通函数 resume 时**必然重跑**，改用 `@task` |

**修复**：

```python
def approve(state):
    decision = interrupt({"question": "是否批准？"})   # ← 之前只放纯计算
    do_refund(state["order_id"])                       # ← 副作用放这里
    return {"decision": decision}
```

**成功的标志**：模拟"中断 → 恢复"后，副作用只发生一次。

**若无效** → 转 `debug`；检查是否在子图里（子图中断会被父图捕获，行为不同）。

**预防**：**`interrupt()` 之前必须是纯计算**——写进代码评审清单。

**原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 5

## 7 · 🟡 重试不生效

**一眼识别**：配了 `RetryPolicy(max_attempts=3)`，日志里外部调用**只出现 1 次**就抛了。

**先止血**：无（只是没重试，不产生新问题，但可用性下降）。

| 若抛的异常是 | 则 |
|---|---|
| `ValueError` / `RuntimeError` / `TypeError` | **默认不重试**（被视为代码 bug）→ 改成自定义异常 |
| `ConnectionError` / HTTP 5xx / 自定义异常 | 默认会重试；若不重试，查 `retry_on` 是否被覆盖 |
| 想让所有异常都重试 | `retry_on=lambda e: True` |

**修复**：

```python
class TransientUpstreamError(Exception): pass   # 自定义 = 可重试

graph.add_node("risk", risk_node, retry_policy=RetryPolicy(
    max_attempts=3, retry_on=TransientUpstreamError))
```

**成功的标志**：注入一次失败后，日志出现 3 次调用。

**若无效** → 确认异常是在**节点内抛出**的（try/except 吞掉后 return 不会触发重试）。

**预防**：节点文档写清"本节点抛什么类型"，团队约定优先于默认。

**原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 6

## 8 · 🟡 同步节点配 timeout

**一眼识别**：`ValueError: Node timeouts are only supported for async nodes because ...`（发生在 `compile()` 阶段）

**先止血**：无（编译期就失败）。

| 若 | 则 |
|---|---|
| 节点可以改成 async | `async def node(...)`，然后配 `timeout=` |
| 必须保持同步 | 去掉 `timeout`，在节点内部用 `asyncio.wait_for` 或 requests 的 `timeout=` |

**修复**：

```python
async def node(state):            # 改成 async
    return await asyncio.wait_for(call_api(state), timeout=10)
```

**成功的标志**：`compile()` 通过，超时真的生效。

**若无效** → 确认整个调用链都是 async（中间有同步阻塞调用会卡住事件循环）。

**预防**：想用节点级 timeout，**从一开始就把节点写成 async**。

**原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 7

## 9 · 🟡 `error_handler` 签名写错

**一眼识别**：`TypeError`，发生在兜底函数被调用时（不是 compile 期）。

**先止血**：无。

| 若 | 则 |
|---|---|
| 写成了 `(state, error)` | 改成 `(state)` **单参数** |
| 需要拿到异常对象 | 从 `config` 里翻（handler 只收 state） |

**修复**：

```python
def handler(state):        # 只有一个参数
    return {"status": "fallback"}
```

**成功的标志**：节点失败后走兜底分支，不再抛 `TypeError`。

**若无效** → 转 `debug` 打断点看实际传入参数个数。

**预防**：兜底函数一律按 `(state)` 写。

**原理**：→ [08-实战经验.md](08-实战经验.md) · 课 10 硬约束 ②

## 10 · 🔴 连接池耗尽

**一眼识别**：
- `psycopg_pool.PoolTimeout: couldn't get a connection after 30.00 sec`
- PostgreSQL 日志 `FATAL: sorry, too many clients already`
- 响应在**某个并发点突然悬崖式上涨，加副本也不缓解**

**先止血**：① 扩容 `max_connections`（`ALTER SYSTEM SET max_connections = 200; SELECT pg_reload_conf();`）；② 平台部署下调 `LANGGRAPH_POSTGRES_POOL_MAX_SIZE`（默认 150/副本）；③ 实在不行先限流。

| 若 | 则 |
|---|---|
| 传的是**单连接**给 `AsyncPostgresSaver` | 改成传 `AsyncConnectionPool`，并显式 `max_size` |
| 池用了默认参数 | 默认 `min_size=4`、`max_size=None`（封顶 4 条）——必须显式设 |
| Web 框架在 run 外面开了**请求级事务** | 拆掉——绝不让数据库事务跨越 LLM 调用 |
| 副本数 × `max_size` > `max_connections` | 重算，或上 PgBouncer |

**排查**：

```python
pool.get_stats()      # requests_waiting > 0 且上涨 → 池是瓶颈
```

```sql
SELECT state, count(*) FROM pg_stat_activity GROUP BY 1;
-- idle in transaction 多 → ORM 占连接；idle 多 → 池太小
```

**修复**：

```python
pool = AsyncConnectionPool(conninfo=DB_URI, max_size=20)
saver = AsyncPostgresSaver(pool)
await saver.setup()
```

**成功的标志**：`requests_waiting` 回到 0；并发压测不再悬崖。

**若无效** → 检查该版本 `AsyncPostgresSaver._cursor` 是否带实例级 `asyncio.Lock`（有的话加连接也没用，需升级版本）。

**预防**：副本数 × `max_size` 必须小于 `max_connections` 且留余量；或前置 PgBouncer。

**原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 8
⚠️ 本条非本机实测（本地无高并发 PG 环境），依据联网核查 + 领域公认实践。

## 11 · 🔴 自托管起不来

**一眼识别**（三道门，按出现顺序）：

1. `KeyError: "Config 'REDIS_URI' is missing"`
2. `AttributeError: 'NoneType' object has no attribute 'encode'` ← **实为 POSTGRES_URI 没给**，报错信息有误导性
3. `ValueError: License verification failed`（乱填密钥时报 `Not enough segments`——它是 JWT）

**先止血**：回到上一个可用镜像；若首次部署，先用托管平台顶上。

| 若 | 则 |
|---|---|
| 缺 `REDIS_URI` | 排队用的，必须配 |
| `NoneType ... encode` | 别被报错骗了——补 `POSTGRES_URI` |
| `License verification failed` | 需要有效 License Key；**乱填会报 JWT 格式错** |
| 本地想先跑起来 | 改 `langgraph dev`（不需要 License） |

**成功的标志**：容器能起，`/health` 返回正常，且**有 worker 心跳**（不只是进程活着）。

**若无效** → 检查镜像 Python 版本（默认是 **3.11**，不是你本机的 3.12——装了 3.12-only 依赖会炸）。

**预防**：把三样（Redis / Postgres / License）写进部署清单，**构建后必须真起一次容器**。

**原理**：→ [08-实战经验.md](08-实战经验.md) · 反模式 6

## 12 · 🟡 `langgraph.json` 写错

**一眼识别**：
- `No dependencies found in config`（缺 `dependencies`）
- `Could not find graph 'xxx'`（变量名写错）
- `FileNotFoundError`（`graphs` 路径是**相对 CWD** 解析的，换目录启动就炸）
- `ValueError: Invalid path '{'path': ...}'`（`graphs` 的值**不支持对象形式**）

**先止血**：无（起不来而已）。

| 若 | 则 |
|---|---|
| 缺 `dependencies` | 补上，指向包目录（如 `["."]`） |
| `Could not find graph` | 核对 `graphs` 里的变量名与代码里 `compile()` 赋值的名字一致 |
| `FileNotFoundError` | 在**正确的工作目录**启动；路径是相对 CWD 的 |
| `Invalid path` | 值写成 `"文件:变量名"` 字符串，**不要用对象形式** |

**修复**：

```json
{
  "dependencies": ["."],
  "graphs": { "my_agent": "./src/my_agent/graph.py:graph" },
  "env": ".env"
}
```

**成功的标志**：`langgraph dev` 能起并列出图。

**若无效** → 转 `debug`；确认 `.env` 里密钥已设（`langgraph.json` 的 `env` 指向的是**文件名**）。

**预防**：改完 `langgraph.json` 立刻 `langgraph dev` 验一次。

**原理**：→ [08-实战经验.md](08-实战经验.md) · 反模式 6（课 12 硬约束 ①）

## 13 · 🟡 读 state 报 `KeyError`

**一眼识别**：`KeyError: 'subject'`（读一个你以为存在的字段）


**先止血**：无（不产生脏数据，调用即失败）；按下方分支修复即可。
| 若 | 则 |
|---|---|
| 用 `TypedDict` 且输入没给该字段 | TypedDict **没有默认值**——补默认值或确保输入带上 |
| 从 `TypedDict` 切到了 `dataclass` | 访问方式变了：`state.n` 而非 `state["n"]`；写成下标会报 `TypeError: 'DCState' object is not subscriptable` |
| 想把假模型塞进 State 做测试 | **不能塞**——走 `config["configurable"]` 注入 |

**修复**：

```python
# TypedDict 给默认值 → 换 dataclass 或 Pydantic
@dataclass
class State:
    n: int = 0
    tags: list = field(default_factory=list)
```

**成功的标志**：`invoke({})` 也能跑通。

**若无效** → 转 `debug`；检查是不是子图（子图只收两边 schema 都声明的字段）。

**预防**：状态定义统一一种风格（建议 TypedDict + 显式输入），不要混用。

**原理**：→ [08-实战经验.md](08-实战经验.md) · 课 3 实测撞坑

## 14 · ⚪ 流式无输出

**一眼识别**：调用 `stream` 后**一条都没输出**，或 `messages` 模式一条都不吐，**且不报错**。


**先止血**：无（体验/优化类，不影响业务正确性）。
| 若 | 则 |
|---|---|
| `stream_mode` 名字写错 | **不报错、无输出**——核对拼写（values/updates/messages/custom/debug/events/checks 共 7 种） |
| 用了 `custom` 但没声明 | 数据被**静默丢弃**——`compile` 时声明通道 |
| 用 `messages` 但节点不调大模型 | 一条都不吐（纯计算节点不会"说话"） |
| 想看子图内部 | 加 `subgraphs=True`，返回变成**三元组** |

**修复**：

```python
for chunk in app.stream(inp, config, stream_mode="updates"):
    print(chunk)
```

**成功的标志**：能看到逐节点的进度输出。

**若无效** → 转 `debug`；先换 `stream_mode="debug"` 看每个任务的入参与结果。

**预防**：模式名用常量或枚举，别手打字符串。

**原理**：→ [08-实战经验.md](08-实战经验.md) · 课 7 硬约束

## 15 · ⚪ Store 只回 10 条

**一眼识别**：写入 25 条，`store.search(ns)` **只回来 10 条，且不报错**。

**先止血**：无数据损坏，只是漏读。

| 若 | 则 |
|---|---|
| 用了默认 `search` | `limit` 默认就是 10——显式传 `limit=100` |
| 要遍历全部 | 分页取，别指望一次拿完 |

**修复**：`store.search(ns, limit=100)`

**成功的标志**：返回条数符合预期。

**若无效** → 检查 `namespace` 层级（前缀匹配规则）。

**预防**：所有 `search` 调用**显式带 `limit`**，不依赖默认。

**原理**：→ [08-实战经验.md](08-实战经验.md) · 课 6

## 16 · 🟡 store 是 None

**一眼识别**：`AttributeError: 'NoneType' object has no attribute 'search'`


**先止血**：无（不产生脏数据，调用即失败）；按下方分支修复即可。
| 若 | 则 |
|---|---|
| `compile` 时只挂了 checkpointer | 补 `compile(store=InMemoryStore())` |
| 以为"没挂会降级成空 store" | **不会**——直接拿到 `None` |

**修复**：`app = graph.compile(checkpointer=..., store=InMemoryStore())`

**成功的标志**：节点里 `store` 不是 `None`。

**若无效** → 确认节点签名里声明了 `store` 参数。

**预防**：挂 checkpointer 时**同时**挂 store，养成习惯。

**原理**：→ [08-实战经验.md](08-实战经验.md) · 课 6

## 17 · ⚪ 跨会话记不住

**一眼识别**：换一个 `thread_id`（新会话）后，读不到上个会话存的用户偏好。


**先止血**：无（体验/优化类，不影响业务正确性）。
| 若 | 则 |
|---|---|
| 把偏好存进了 **State** | State 是会话内记忆——换会话必丢 → 改用 **Store** |
| 用了 Store 但 `namespace` 第一层是 `thread_id` | 搜不到（新会话换 thread 就查不到）→ 第一层用**用户 ID** |
| 以为 Store 会自动写 | **不会**——必须显式 `store.put(...)` |

**修复**：

```python
ns = ("users", user_id)              # 第一层是用户，不是 thread
store.put(ns, "pref", {"lang": "zh"})
```

**成功的标志**：新 `thread_id` 下仍能 `search` 到。

**若无效** → 检查 `compile(store=...)` 是否真的传了。

**预防**：短期（会话内）→ State；长期（跨会话）→ Store。**分清楚再写**。

**原理**：→ [08-实战经验.md](08-实战经验.md) · 课 6

## 18 · 通用：从历史回放修复

> 不是具体症状，是**上面多条"若无效"的兜底手段**。

**一眼识别**：需要知道"当时到底发生了什么"。


**先止血**：无（体验/优化类，不影响业务正确性）。
**步骤**：

```python
# ① 拿到历史（须挂了 checkpointer）
for snap in app.get_state_history(config):
    print(snap.next, snap.values, snap.config["configurable"]["checkpoint_id"])

# ② 定位到出事那一步的 checkpoint_id
cfg = {"configurable": {"thread_id": tid, "checkpoint_id": bad_id}}
state = app.get_state(cfg)
print(state.values)

# ③ 改**最上游的依据**（改下游结论会被重算覆盖）
app.update_state(cfg, {"amount": 199})

# ④ 从该点重跑（只重跑它之后的节点）
app.invoke(None, cfg)
```

**成功的标志**：重跑结果与预期一致，且前面的工作没有白费。

**若无效** → 转 `debug` 现场排查。

**预防**：生产环境务必挂 checkpointer——否则**没有历史可翻**。

**原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 4
