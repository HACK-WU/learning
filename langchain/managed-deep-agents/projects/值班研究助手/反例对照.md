# 反例对照

这是一个"看起来能跑"的版本。它 `mda build` 通过、`mda dev` 能起来、在本地聊两句也像那么回事。但它在真实值班场景里会出事。

## 反例版本

```python
# agent.py —— 反例：能跑，但很糟
from dataclasses import dataclass

from langchain_core.tools import tool
from managed_deepagents import define_deep_agent


@dataclass
class Ctx:
    team: str = "platform"
    role: str = "viewer"          # ← 问题 1：角色写在 context 里


@tool
def escalate(summary: str, ctx: Ctx) -> str:
    """升级告警。"""
    if ctx.role != "oncall":       # ← 问题 1：拿 context 当权限依据
        return "你没有权限"
    return f"已升级：{summary}"


agent = define_deep_agent(
    name="duty-assistant",
    model="openai:gpt-5.5",
    tools=[escalate],
    context_schema=Ctx,
    permissions=[{"path": "/workspace/**", "mode": "allow"}],   # ← 问题 2：配了沙箱还写 permissions
    checkpointer=object(),                                        # ← 问题 3：运行时自有，会被拒
)
```

配套的 `sandbox/__init__.py` 里声明了 `define_sandbox(...)`，`memory.py` 里写了 `define_memory(agent=MemoryLayer())` 却没写 user 层，`schedules/morning_digest.py` 里写 `cron="0 8 * * *"` 但没写 timezone。

## 逐条对比

### 差异 1：拿 `context.role` 当权限依据

**反例做法**：`if ctx.role != "oncall": return "你没有权限"`。

**为什么糟**：`context` 是**调用方自己传进来的数据**，平台只按你声明的 schema 校验"形状对不对"，从不校验"值是不是真的"。任何调用方都能传 `{"role": "oncall"}`。这等于把门锁装在门框上、钥匙挂在门把手上。

更隐蔽的一层：这个判断写在工具函数体里，看起来"代码里做了校验"，比写在提示词里更让人放心——**这正是它危险的地方**。

**正确做法**：读 `runtime.server_info.principal`，它是 identity 从已验证 token 解出来的；为 `None` 就拒绝。

**真出事时是什么样**：某个只有只读权限的同事，在请求体里加一行 `"role": "oncall"`，成功升级了一条 P1 告警给错误的团队。事后查日志，工具函数"明明做了权限校验"。

### 差异 2：声明了沙箱还写 `permissions`

**反例做法**：`permissions=[{"path": "/workspace/**", "mode": "allow"}]` 和 `sandbox/` 目录同时存在。

**为什么糟**：不是"配置冲突报错"，是**静默失效**。实测：这份配置 `mda build` 输出 `◇ Managed app compiled`，零警告。源码 `runtime.py` 里：

```python
if sandbox_backend is not None:
    merged["permissions"] = []
```

`build` 不会提示，`dev` 不会提示，agent 照常能跑。你以为 `/workspace/**` 是放行的，实际上根本没有权限层——所有路径都按沙箱默认策略走。

**正确做法**：二选一。要沙箱就删掉 `permissions`，用"只给必要工具"来限制；要路径规则就别声明沙箱。

**真出事时是什么样**：以为 agent 只能写 `/workspace`，结果它在沙箱里能碰的路径比预期宽。排查时会盯着 `permissions` 那行看很久，因为它在代码里明明白白写着。

### 差异 3：`checkpointer=object()` 这类"看起来合理"的残留

**反例做法**：把本地 `create_deep_agent` 的写法直接搬过来，传了 `checkpointer`。

**为什么糟**：这一条反而**最容易发现**——`mda build` 就会报 `Remove 'checkpointer' from define_deep_agent(...). MDA provides the checkpointer automatically.`

把它放进反例，是因为它代表一类思维惯性：**从自托管迁过来时，会本能地想"补齐平台没做的那部分"**，而实际上平台已经做了，你的补齐动作变成了干扰。真正危险的是那些**不报错**的残留（差异 2），但先撞上这个报错的，往往是同一批人。

**正确做法**：删掉。运行时自有线程、run 与持久化。

### 差异 4：记忆只声明 agent 层

**反例做法**：`define_memory(agent=MemoryLayer())`，没有 user 层。

**为什么糟**：两层记忆的语义是**不同的隔离边界**。agent 层全部署共用，user 层按已验证的人隔离。只开 agent 层意味着：值班人 A 说"给我看表格不要看段落"，第二天值班人 B 也会看到表格格式——因为那条偏好写进了共用区。

它不是崩溃，是"慢慢变得不合适"：三个人开始互相覆盖对方的偏好，最后大家都不用这个功能了。

**正确做法**：两层都开，并接受"开 user 层就必须配真实身份"这个连带条件。

**真出事时是什么样**：没人报 bug。只是这个 agent 的"记忆"功能上线三个月后被静默停用。

### 差异 5：cron 没写时区

**反例做法**：`define_schedule(cron="0 8 * * *", prompt=...)`。

**为什么糟**：省略 timezone 后 `ScheduleDefinition.timezone` 是**未设置**状态（实测：该字段根本不存在），cron 交给平台按其默认时区解释。团队在上海，晨报在北京时间下午四点发出——而且**它每天都准点发**，不会报错，只是时间错了。这种错要靠人肉发现："咦，怎么下午才收到早报？"

**正确做法**：显式写 `timezone="Asia/Shanghai"`。

**真出事时是什么样**：上线第一天就有人问"为什么晨报是下午的"，改一行就好——但那一天的值班人错过了早报。

## 差异汇总表

| # | 反例做法 | 后果 | 会不会报错 | 排查难度 |
|---|---|---|---|---|
| 1 | `context.role` 当权限 | 越权升级告警 | 不会 | 高（代码里"有校验"） |
| 2 | 沙箱 + permissions 并存 | 权限层静默消失 | 不会 | 高（配置明写着） |
| 3 | 传 `checkpointer` | 无法构建 | **会** | 低 |
| 4 | 只开 agent 层记忆 | 偏好互相覆盖 | 不会 | 极高（无 bug 可报） |
| 5 | cron 不写时区 | 晨报时间错 | 不会 | 低（人肉发现） |

## 一句话总结

反例版本的五处问题里，只有一处会报错。**其余四处全是"跑得通、看起来对、出事时才知道"**——这正是本课程反复强调的：托管的便利来自"平台替你做决定"，代价是你必须知道那些决定是什么，否则你会在错误的层上做校验、在失效的配置上建信心。
