# 设计决策

四个"不止一个合理答案"的取舍。每个都说清：候选方案对比 → 最终选择 → 选择理由 → 付出的代价 → 什么情况下该改选另一个。

---

## 决策 1：权限判断放哪里

### 候选方案对比

| 方案 | 做法 | 好处 | 坏处 |
|---|---|---|---|
| A 写在提示词里 | 在 `instructions.md` 里写"只有平台组的人才能升级告警" | 一处改完，所有工具生效 | 模型可以不听；context 里的 team 字段谁都能填 |
| B 写在入口的 permissions | `define_deep_agent(permissions=[...])` | 声明式，看起来最"平台化" | **声明沙箱后会被静默清空**（课 6 实测） |
| C 写在工具里 | 工具内读 `runtime.server_info.principal`，为空就拒 | 唯一真正可信的位置；principal 来自已验证 token | 每个写工具都要重复判空逻辑 |

### 最终选择

C。三个工具里只有 `escalate_incident` 是写操作，它在函数体第一段就判 `principal is None`。

### 选择理由

课 7 的核心结论是"三个来源各有信任级别"：`context` 只按 schema 校验形状，**不判权限**；`channel` 只说"从哪来"；只有 `server_info.principal` 经过身份提供方验证。

这个项目又声明了沙箱，所以方案 B 直接失效——不是"不够好"，是"会被静默删掉"。方案 A 表面上最省事，但它把安全边界交给了一个概率模型。

### 付出的代价

- 每个新增写工具都要复制一遍判空模板。三个工具的规模可以接受，三十个工具就该抽公共装饰器。
- 提示词里必须**再写一遍**"不要根据 team 字段判断权限"，因为模型会自然地去用最显眼的字段。这是双保险，也是冗余。

### 什么情况下该改选另一个

- 如果项目**不声明沙箱**，方案 B 重新可用，且比 C 更"声明式"——适合规则简单（只有路径黑名单）的场景。
- 如果写操作多到 10 个以上，应该抽一层 `@requires_principal` 装饰器，但那已经不叫"选 B 或 C"，而是在 C 之上做工程化。

## 决策 2：晨报用临时线程还是持久线程

### 候选方案对比

| 方案 | 做法 | 好处 | 坏处 |
|---|---|---|---|
| A 临时线程（默认） | `define_schedule(cron=..., prompt=...)`，不写 `new_thread` | 零配置；线程列表干净 | 昨天的晨报查不到，跑完即删 |
| B 持久线程 | `new_thread=False` + 预先建好线程并固定 UUID | 晨报可以累积，能对比"昨天 3 个 P1，今天 1 个" | 要手工建线程、把 UUID 写进代码；线程会无限长 |
| C 临时线程 + 贴回 Slack | 方案 A + `deliver_to` 指到固定群 | 线程干净，历史留在群里 | 群消息噪音；跨群汇总做不到 |

### 最终选择

A。晨报只保留"当下快照"的语义。

### 选择理由

晨报的价值在"今天要干什么"，不在"去年今天干了什么"。要追历史，Slack 群本身就是更好的归档——它天然按时间排、能搜索、能被没订阅 agent 的人看到。为了"能对比昨天"而引入一个会无限增长的线程，是拿运维复杂度换一个 Slack 已经免费提供的能力。

### 付出的代价

- 如果哪天产品要"本周 P1 趋势"，agent 自己答不出来——必须去查监控系统，不能查自己的记忆。
- 每次跑都开新线程，线程创建的开销无法避免（单次可忽略，日积月累会在 LangSmith 里留下大量空线程）。

### 什么情况下该改选另一个

- 有人明确要求"每天晨报接着前一天聊"（比如让 agent 自己判断"这个问题昨天提过，今天还没解决"），那就必须方案 B。
- 如果 Slack 群不可用（纯 API 消费方），方案 C 失去落点，只能回退到 B。

## 决策 3：该不该迁到托管

### 候选方案对比

| 方案 | 好处 | 坏处 |
|---|---|---|
| A 迁到 Managed Deep Agents | 沙箱、记忆、通道、调度、部署全由平台管 | 失去自定义 backend、自定义路由、Python 自定义 state_schema |
| B 留在 Deep Agents 自托管 | 完全自由 | 得自己搭服务、管密钥、接 Slack、写定时任务——正是本课程开头那个天花板 |
| C 混用：核心 agent 托管，特殊能力走自建服务 | 两边好处都拿 | 两套运维；跨服务调用要处理身份透传 |

### 最终选择

A。四道门槛逐条对过：没有自定义 BackendProtocol 实现、没有依赖特定 store/checkpointer、没有自定义路由、Python 侧没有用 state_schema。

### 选择理由

这个 agent 的全部复杂度在"业务判断"（谁值班、哪个告警先处理），不在"运行时"。托管接管的恰好是那些跟"让 agent 变聪明"无关、却占八成工作量的部分。

反过来看：如果这个项目有自定义 backend（比如必须接到公司内部的对象存储），那就该选 B 或 C——不是因为托管不好，而是**这个需求本身超出了托管的边界**。

### 付出的代价

- **沙箱只有一种**。想换成 gVisor 或 Firecracker 没门。
- **声明沙箱后 permissions 失效**。文件访问限制只能靠"少给工具"实现，这比路径规则粗暴。
- **memory 是空树起步**。任何历史上下文都得手动搬进 `instructions.md` 或技能文件。
- **评估要自己写判分脚本**。平台给的是跑道，不是标准答案。

### 什么情况下该改选另一个

- 出现"必须在自有 VPC 内跑 shell 命令"的合规要求 → 选 B。
- 需要 WebSocket 长连接或自定义 HTTP 路由 → 选 B（托管只托管 agent，不托管 web 应用）。
- 只是想用一个托管的沙箱、其余全自建 → 选 C，但要想清楚身份怎么跨服务透传。

## 决策 4：要不要加中间件做人工审批

### 候选方案对比

| 方案 | 做法 | 好处 | 坏处 |
|---|---|---|---|
| A 平台自带 interrupt | 在工具里调 `interrupt({...})`，等人回答后继续 | 平台接管暂停/恢复；前端能看到待办 | **续跑会从函数第一行重跑**，副作用要自己防重（课 8 实测） |
| B 作者中间件拦一层 | 写 `AgentMiddleware` 在工具调用前插入审批 | 集中管理，不用改每个工具 | 多一层抽象；审批状态自己要存 |
| C 审批不进 agent | agent 只产出"建议升级"，真正升级由值班人自己点 | 最简单，agent 不碰写操作 | 少了一步自动化；值班人要多点一次 |

### 最终选择

A，且只在 `escalate_incident` 一个工具上用。同时刻意**不**引入人工审批中间件。

### 选择理由

方案 C 最安全但把价值砍掉了一半——"帮我把告警升级了"正是这个 agent 存在的理由。方案 B 在只有一个写工具时属于过度设计：一个中间件要处理"哪些工具需要审批、审批超时怎么办、审批记录存哪"，这些复杂度在单工具场景下全是净负担。

方案 A 的已知坑（续跑重跑函数体）在本项目里是可控的：`escalate_incident` 的副作用是"发一条通知"，重跑两次就是发两条——所以真正上线时要把"发通知"这一步放在 `interrupt` **之后**，并且用幂等键去重。

### 付出的代价

- 审批的待办列表由平台 UI 承载，自己没法定制展示。
- 如果哪天要"两级审批"（组长 + 总监），方案 A 表达不了，必须上 B。

### 什么情况下该改选另一个

- 写工具超过 3 个，且审批规则各不相同时 → 上方案 B 做集中管理。
- 合规要求"所有写操作必须人工确认"→ 方案的边界变成方案 C，agent 只做建议。

## 附：一个被否决的设计（记录理由）

**曾考虑**：把 `query_open_alerts` 做成一个 MCP 连接器，接公司现有的告警平台 MCP 服务。

**否决理由**：MCP 连接器需要工作区密钥托管，而本项目面向的告警平台只有内部 IP 可达，托管侧连不上。这不是"技术上不行"，是"网络拓扑不允许"。改成了在工具里直接调内部 HTTP API（本项目用固定数据模拟）。

这条记录的价值：下次有人问"为什么不用 MCP 连接器"，答案在拓扑，不在能力。
