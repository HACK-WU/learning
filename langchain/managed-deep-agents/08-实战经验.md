## 一、适用边界：什么情况下别用托管

> **"不该用"比"怎么用"更值钱**。这一节是为了让读者在投入两周之前就知道该不该开始。

### 1.1 硬边界：能力上做不到

以下每一条都会直接否掉一类需求。**先拿需求对表，再谈方案。**

| 限制 | 后果 | 遇到时怎么办 |
|------|------|-------------|
| 区域局限于 US LangSmith Cloud | 没有自托管、没有混合部署、没有 EU 区域 | 数据驻留是硬要求 → 退回自建 LangGraph Server |
| CLI 优先，public beta 期无公开管理 API | 没有公开的 create / update / invoke REST 面 | 要程序化编排部署 → 现阶段不可行，只能用 `mda` |
| Slack 是唯一通道 | 没有 Discord / Teams / 邮件 / 短信 | 对接其他 IM → 写自己的 HTTP 通道，或退回自建 |
| 一个项目一个 agent 入口 | 不能在一个项目里放多张图 | 需要多角色 → 用 `subagents=` 委派，不是多入口 |
| 调度声明必须是静态字面量 | 不能读环境变量、不能调函数、不能算 | 要按环境切换时间 → 分开多个项目 / 部署 |
| 构建归档上限 200 MB | 大 fixture 或模型权重进项目就部署失败 | 大数据放对象存储，项目里只留引用 |
| 托管字段不归你设 | `backend` / `store` / `checkpointer` / `memory` / `skills` / system prompt 由运行时注入 | 需要自定义 backend / store / checkpointer → 见 1.3 |
| 沙箱作用域由平台管 | 一个线程一个沙箱，agent 级共享不再支持 | 要跨线程共享工作区 → 用记忆或外部存储，不是沙箱 |

> **这张表的用法**：客户提需求时逐行过。**提前说做不到，比部署时才发现便宜得多**。

### 1.2 软边界：能做到，但四门槛里有一条不过就别迁

迁不迁的判定不是"能不能跑通"，而是四道门槛**逐条**问：

| # | 门槛 | 不过时的信号 |
|---|------|-------------|
| 1 | 自定义 `BackendProtocol` | 你的数据不在文件系统抽象里，得自己实现协议 → **不可迁** |
| 2 | 依赖特定 `store` / `checkpointer` | 检查点要落在自己的库、要能 SQL 查 → **不可迁** |
| 3 | 自定义 HTTP 路由 | 除了 agent 端点，你还需要 `/healthz` `/metrics` 自己的业务路由 → **不可迁** |
| 4 | Python 侧 `state_schema` | 你靠自定义 state 在节点间传结构化数据 → **不可迁** |

四条全否 → 可以迁。**任一条命中，就不是"迁过去再改"，而是"迁过去就变形"**。

### 1.3 三种"看起来适合、实际不适合"的反模式

**反模式 A：把托管当"便宜的 K8s"**
托管接管的是"agent 怎么被造出来、跑在哪、怎么接渠道"，不是通用容器编排。想拿它跑定时脚本、做数据处理管道、当 webhook 接收器 —— 这些它都能勉强做，但每一样都比专用工具贵且脆。

**反模式 B：想要"一点点自定义运行时"**
托管的设计前提是"运行时归平台"。一旦你需要自定义 backend、自定义 checkpointer、或者想在 agent 循环里插自己的调度逻辑，你就在和生产环境的每一次升级对抗。**要么全交出去，要么自己跑，中间态最贵**。

**反模式 C：拿它做多租户 SaaS 的基座**
一个部署的 agent 层记忆对所有调用方共享（见故障模式 5）。要真正的租户隔离，你得一个租户一个部署，或者自己在工具层做过滤。**这不是文档没写清，而是产品边界就是这样**。

## 二、高频故障模式（10 条）

> 按「踩中概率 × 后果严重度」筛过。**1–6 号是静默失效**（不报错、只是你要的效果没发生），**7–10 号会报错但报错位置反直觉**。
> 静默那一组才是真正的成本所在 —— 你有构建绿灯，所以你不会去找它。

### 故障模式 1：工具写好了、文件也在，模型却说"我没有这个工具" {#m1}

**症状（可观测）**
模型在对话里回复"我无法查询订单"或"我没有访问内部系统的权限"，但 `tools/order.py` 明明存在、函数也加了 `@tool`。`mda build` 输出 `◇ Managed app compiled`，exit=0，零警告。

**根因**
`tools/` 目录**不是**"存在即生效"。它只是普通 Python 模块目录，必须两步都做到才算注册：
1. 在 `agent.py` 里 `from tools.order import query_order`
2. 把它放进 `tools=[...]` 参数

漏任一步，config 里**连 `tools` 这个键都不会有**（不是空列表，是压根没设置：`"tools" in config` 为 `False`，硬取抛 `KeyError`，只有 `config.get("tools")` 才得到 `None`），编译阶段不检查、不提示。

**排查路径**
1. 先看编译产物里的 tools 到底是什么：`python -c "from .mda.build... "` 不直观，直接改从源码侧验 —— 在项目根跑 `mda build` 后检查 `.mda/build/langgraph.json` 与产物 `agent.py`，看 `tools` 键是否存在。
2. 更快的判据：把工具数打进日志。`len(agent.tools or [])` 为 0 就是没注册。
3. 区分"漏 import"和"漏传参"：漏 import 报 `NameError`（模块级），漏传参完全静默。

**修复**
补齐两步。若工具很多、不想手抄，用 `from tools import *` 在入口聚合一次再传 —— 但注意这会让静态扫描的可见性变差，团队里要约定。

**预防**
在每个工具模块末尾加一行自检注释（"本模块必须被 agent.py 导入并列入 tools="）；或在 CI 里加一条断言 `assert len(agent.tools) == 预期数量`。

**⚠️ 与之相邻的另一个坑**：`tools/mcp.py` **是**存在即生效的（而且是保留名），`tools/` 下其他文件才需要点名。两类文件的生效机制相反，混在同一个目录里最容易错。

**溯源**：课 4 实验（`k4/d` vs `k4/e`），漏 import 后 config 里没有 `tools` 键（`"tools" in config` 为 `False`）。

### 故障模式 2：技能写得很认真，模型从来不用 {#m2}

**症状（可观测）**
`skills/xxx/SKILL.md` 内容完整，但对话里模型从不按那份流程走。没有任何报错，`mda build` 绿灯。更隐蔽的版本：技能放在 `skills/运维/事故处理/SKILL.md`（两级目录），文件确实被打进产物了，但永远不被发现。

**根因**
两个独立的静默失效叠在一起：
1. **只扫一层**。`skills/` 下只认 `skills/<name>/SKILL.md`，`skills/<分组>/<name>/SKILL.md` 会被静默漏掉。实测 `discovered: ['flat']`，嵌套的 `parent/child` 不在结果里。
2. **frontmatter 是硬门槛**。缺 `name`、缺 `description`、或整个 frontmatter 缺失 —— 该技能卡片被**整张跳过**，构建 exit=0。

**排查路径**
1. 看构建产物里的 `_has_skills` 标志。空目录时它会是 `false`/缺失 —— 这是最快的信号。
2. 直接调解析函数验单个文件：`_parse_skill_metadata(...)`，七种 frontmatter 写法各跑一次，看哪种返回空。
3. 检查目录层级：`skills/` 下**每个直接子目录**里是不是正好一个 `SKILL.md`。

**修复**
- 目录拍平：`skills/事故处理/SKILL.md`，不要分组的上一层。
- frontmatter 补全 `name` + `description`。`description` 是模型判断"要不要用这张卡"的唯一依据，要写成"什么时候用我"，不是"我是什么"。

**预防**
CI 里跑一条 `find skills -name SKILL.md | wc -l` 与 `find skills -mindepth 3` 的对比，深度 >2 就报错。

**溯源**：课 4 实验（`k4/i`，`discovered: ['flat']`）；frontmatter 七态用 `_parse_skill_metadata` 逐个实测。

### 故障模式 3：按官方文档写的 MCP 配置，导入期就崩 {#m3}

**症状（可观测）**
`mda dev` 启动那一刻报 `ValueError: default_tool_timeout was removed in 0.9; use timeout for individual MCP requests`。或者照抄 `prefix_tool_name_with_server_name: true` 得到 `was removed in 0.9; native names are {server}_{tool}`。

**根因**
官方 MCP 配置页仍列着四个 **0.9 已删除**的选项：`prefix_tool_name_with_server_name`、`default_tool_timeout`、`automatic_sse_fallback`、`reconnect`。文档与实现不一致，照抄必崩。

还有个更细的陷阱：MCP 校验分三段，**只在最后一段才真连远端**。
- 段 1 `mda build`：只收文件，**不校验配置**
- 段 2 导入期：pydantic 校验，上面四个选项在这里炸
- 段 3 建图期：才真正连服务器

所以"build 绿灯"完全不代表 MCP 配对了。

**排查路径**
1. 报错里出现 `removed in 0.9` → 直接对照四删表替换，不要怀疑别的地方。
2. 报错在建图期（`RuntimeError`）→ 是远端不可达或 URL 写错，不是配置语法问题。
3. 只想先跑通一部分工具 → 设 `throw_on_load_error=False`，让坏的那个降级而不是整体失败。

**修复**
四个选项的替代方向：前缀开关 → 用原生 `{server}_{tool}` 命名；整体超时 → 用每个请求的 `timeout`；SSE 回退 → 显式选 transport 与端点；自动重连 → 不支持，靠调用方重试。

**预防**
把"版本删了什么"做成团队速查表；升级 CLI 后第一件事是跑一次 MCP 配置的导入期校验，而不是等部署。

**溯源**：课 5 实验（四个选项逐个实测，报错原文见课 5）。

### 故障模式 4：文件权限规则写了，但完全不生效 {#m4}

**症状（可观测）**
`agent.py` 里 `permissions=[...]` 明明禁止写 `/etc`，agent 却写成功了。`mda build` 零警告，运行时零日志。**这是本教程最危险的一处静默行为**。

**根因**
沙箱与文件权限规则在 `execute()` 层面互斥。源码 `runtime.py:1188` 的 `_apply_managed_context` 里：

```
if sandbox_backend is not None:
    merged["permissions"] = []      # 全清，不是部分保留
```

平台的取舍是"保留 shell、丢掉规则"，而且是在运行时静默替换，构建阶段一个字都不提。

反向也成立：**没有**沙箱时，你的规则会保留，并且平台会额外追加一条 `/skills/**` 写保护。

**排查路径**
1. 一句话定位：项目里有没有 `sandbox/`。有 → 你的 `permissions` 一定是空的。
2. 想要证据：在工具里打印 `runtime.server_info` 之外没法直接看到生效的 permissions —— 只能靠"有没有 sandbox 目录"来判断。
3. 别去 `.mda/build` 里找：产物里可能还留着你的 permissions 字面量，但运行时已被覆盖。

**修复**
二选一，不能都要：
- 要文件规则 → 删掉 `sandbox/`，用工具级限制替代 shell
- 要 shell → 接受权限规则失效，把边界收到"只暴露哪几个工具"，并在工具内部自己做路径校验

**预防**
在 `sandbox/__init__.py` 顶部写明"声明本文件会让 permissions 失效"，把这句话放在最显眼的位置 —— 这是本教程反复强调的做法，因为文档不会告诉你。

**溯源**：课 6 实验（沙箱构建 + 权限清空分支），源码 `runtime.py:1188`；Phase 3 项目反例差异 2 复测确认"静默编译通过、零警告"。

### 故障模式 5：用户私有记忆永远是空的 {#m5}

**症状（可观测）**
`memory.py` 里 `agent=` 和 `user=` 两层都声明了，agent 层记忆读写正常，`/memories/user/` 一直是空的。没有任何报错。

**根因**
记忆有三道闸，全过才可用：
1. **声明** —— `MemoryLayer()` 挂上
2. **principal 必须是"人"** —— 默认 LangSmith API key 身份是 `kind=service`，会被判 `not_a_person`
3. **`allow` 策略** —— 只能放宽，不能越权（源码顺序是先 `resolve_user_memory_principal` 判 `None`，才走 `allow`）

第 2 道最常见：用默认 API key 跑，`user` 层就永远挂不上。错误信息是 `not_a_person` 这种需要查源码才懂的值。

还有个相邻的静默坑：**写入路径错了也不报错**。写到**未挂载的层**会报错，但写到 `/memories/` 下的其他路径不报错，运行结束就丢弃。所以官方要求："If the write fails, do not claim that you remembered it."

**排查路径**
1. 先在日志里找 `principal`。为 `None` 或 `kind=service` → 就是这道闸。
2. 检查 `allow` 是不是"恒真"但 principal 仍是 service —— 恒真也救不了服务身份。
3. 写入侧：确认 agent 用的是 `write_file` / `edit_file` / `read_file` 三个工具，不是 shell 重定向。

**修复**
要 user 层真正工作，得换成能识别"人"的身份提供方（Supabase 那条路）。本地只想验证逻辑，可以用 `auth="backend"` 让服务先起来。

**预防**
把"user 层记忆依赖真实身份"写进项目 README 的启动前置条件（Phase 3 项目就是这么做的）。

**溯源**：课 6 实验（默认策略五态 + allow 越权测试）；课 6 第 1010 行答案解析；Phase 3 项目新发现第 2、3 条。

### 故障模式 6：把 `context` 当权限判断依据，越权成功了 {#m6}

**症状（可观测）**
最糟的一种：**没有症状**。调用方在 `context` 里塞 `{"role": "admin", "team": "platform"}`，工具里 `if runtime.context.role == "admin"` 就放行了。日志里一切正常，没有异常，没有告警。

**根因**
`context` 是"访客自己填的登记本"—— 调用方随便写。13 个保留键（含 `user_id`、`mda_groups`、`mda_claims`）会被 `sanitize_configurable` 全剥，但**你自己起的业务字段不会被剥**，而且不校验真假。

唯一可判权限的身份源是 `server_info.principal`。类型层面还有一道保护：工厂的运行时类型里**根本没有** `server_info` 字段，所以你在选配置的时候想判权都判不了。

**排查路径**
1. 全局搜 `runtime.context.` 的每一处使用，逐个问"这处如果调用方撒谎会怎样"。
2. 搜 `if.*role` / `if.*is_admin` / `if.*permission` —— 名字里带权限词的、却从 `context` 取的，全部是嫌疑。
3. 在工具入口打印 `runtime.server_info`，确认它在什么时候是 `None`（注意 `_ManagedReadRuntime` 读 schema 时既没有 `context` 也没有 `server_info`）。

**修复**
判权限只走 `server_info.principal`，且**先判 `None`**：

```python
principal = runtime.server_info.principal if runtime.server_info else None
if principal is None:
    return "拒绝：本次调用没有已验证身份"
```

`context` 只用来"选行为"（用哪份值班表、走快档还是慢档），不参与鉴权。

**预防**
在 `instructions.md` 里写一条硬约束："不要根据上下文里的 team 字段判断你有没有权限" —— 但这只是提示层，真正的防线是代码里根本不从 context 取权限字段。

**溯源**：课 7 知识点 1（三源分离）+ 实验（剥键、`langgraph_auth_user` 污染整段 context）；Phase 3 项目 `tools/duty.py` 的 `escalate_incident` 是正确写法。

### 故障模式 7：按文档注册 Slack 回调地址，得到 404 {#m7}

**症状（可观测）**
Slack 后台填了 `/channels/slack/events`，Slack 侧显示请求失败，服务端日志是 404。或者本地 `mda dev` 起来了，但怎么点都没反应。

**根因**
文档只写了统一形态 `/channels/{name}/events`，但源码 `_identity_http.py:191-193` 按 `transport` 分支：
- `transport == "trigger_server"`（Slack）→ **带 `/v1` 前缀**，真实地址是 `/v1/channels/slack/events`
- HTTP 通道（`transport` 为 `None`）→ **不带前缀**

**排查路径**
1. 不要凭文档猜地址 —— **看 `mda dev` 启动横幅**，它打印的才是真实路由。
2. 用两条 curl 做二分：`/v1/channels/slack/events` 返回 401（路由存在，只是没签名）vs `/channels/slack/events` 返回 404（路由不存在）。**401 = 找对了**。
3. 状态码矩阵：无签名头 → 401 `invalid channel signature`；签名对但没配 `MDA_ASSISTANT_ID` → 500 `channel runtime is not configured`。

**修复**
注册带 `/v1` 的那个地址。另外注意 `verify` 的两种失败语义不同：**返回 `False` = 401（又快又对），抛异常 = 500**。别用抛异常来拒绝。

**预防**
把"Slack 带 `/v1`、HTTP 通道不带"写进部署清单；每次改通道声明后重启 `mda dev` 再看一遍横幅（新增通道文件不会热重载）。

**溯源**：课 8 实验（通道地址二分 + HTTP 七态状态码矩阵）；源码 `_identity_http.py:191-193`；Phase 3 项目实测复现 401 vs 404。

### 故障模式 8：用户收到两张一模一样的审批单 {#m8}

**症状（可观测）**
agent 弹出一个审批表单，用户点完提交，**又收到一张一模一样的**。或者更糟：升级动作被执行了两次。

**根因**
LangGraph 的中断**不是从 `interrupt()` 那行继续**，而是**从函数第一行重跑**。第一次执行时事件是 `message`，续跑时事件类型变成 `user_prompt_response`。如果你的"发表单"逻辑没有挡住第二次，就会再发一张。

**排查路径**
1. 在函数第一行打印 `runtime.channel.event["type"]`，跑一次审批，看它被调用了几次、每次的 type 是什么。
2. 观察顺序：两次调用之间有没有 `interrupt()` 返回 —— 有，就是走了重跑路径。
3. 确认 correlation ID 匹配逻辑：事件先到平台，再按 correlation ID 匹配回来，不是靠 callback 直接续跑。

**修复**
第一道闸就是事件类型判断：

```python
if runtime.channel and runtime.channel.event["type"] != "user_prompt_response":
    ...  # 只有第一次才发表单
```

**预防**
把"续跑 = 重跑"当成写中断逻辑的前提，而不是例外；所有有副作用的动作（发消息、写库、调外部 API）都必须放在闸之后。

**溯源**：课 8 实验（中断续跑重跑 + `channel.event.type` 作为第一道闸）；课 8 第 851 行流程图。

### 故障模式 9：部署预检报 "requires OPENAI_API_KEY in .../.env" {#m9}

**症状（可观测）**
`export OPENAI_API_KEY=sk-...` 明明在 shell 里，`echo $OPENAI_API_KEY` 也有值，`mda deploy` 却报：

```
error: The agent model 'openai:gpt-5.5' requires OPENAI_API_KEY in /path/to/project/.env
```

**根因**
**模型 key 只认 `.env`（或工作区密钥）**。shell 里 `export` 的过不了预检。

这一条特别值得记，因为**官方 deploy 文档写反了** —— 它说 key 可从 `.env`、shell 环境或工作区密钥取得；而 migrate 文档写"shell 里 export 的不会被读取"。实测证明 migrate 文档是对的。

shell 环境变量只在"deploy 时转发成该部署的密钥"这个意义上有用，不能作为预检依据。

**排查路径**
1. 先 `ls -la .env` 确认文件存在（不是 `.env.example`）。
2. 再 `grep OPENAI_API_KEY .env` 确认键名对、值非空。
3. 若写进 `.env` 后仍 403 → 那不是预检问题，是 key 本身无效/撤销/跨 workspace：`403 {"detail":"API key is forbidden"}` 或 `tenant mismatch`。

**修复**
把 key 写进项目根的 `.env`。**注意 `.env` 永远不会被打进构建归档**，所以它是安全的配置位；但也别往里面写真实生产 key 提交到 git。

**预防**
`.gitignore` 里必须有 `.env`；项目里留 `.env.example` 作为键名清单。

**溯源**：课 9 实验一（同 key shell export 失败 vs `.env` 通过）；课 9 第 172–183 行「密钥只走 `.env`（实测修正官方文档）」。

### 故障模式 10：迁移完成了，agent 行为变了，但没有任何报错 {#m10}

**症状（可观测）**
代码一行没改，迁到托管后：文件权限规则不再生效、记忆目录是空的、某些工具调不通。**全都没有报错**。

**根因**
迁移的坑不在"能报错的参数"，而在"不报错但静默改变行为"的部分：
1. `permissions` 仍是参数，但声明 `sandbox/` 时被静默置 `[]`（同故障模式 4）
2. `memory` 会挂上一棵空树 —— 你原来的持久化不在那里
3. `mda build` 对**静态入口**会 import 并逐个断言（`Remove checkpointer from...` 在 build 阶段就报），但**工厂入口**（`agent = 函数`）完全不调用 —— 所以工厂里的问题一个都发现不了

**排查路径**
1. 迁移前先跑四门槛（见 1.2），任一条命中就别迁。
2. 迁移后逐项对照"行为清单"：权限规则生效吗、记忆里有什么、每个工具能调吗。
3. 别信 build 绿灯 —— 特别注意你的入口是静态还是工厂。工厂入口的 build 通过等于零验证。

**修复**
按四门槛逐条改造：自定义 backend → 换成托管提供的；自定义 store/checkpointer → 去掉，用托管的；自定义路由 → 拆成独立服务。

**预防**
迁移前写一份"行为基线"（每个能力一条可观测断言），迁完逐条验 —— 因为平台不会告诉你哪条失效了。

**溯源**：课 9 实验（静态 vs 工厂入口的 build 行为、sandbox 清权限、memory 空树）；课 9 第 454 行迁移对照表。

## 四、真实案例复盘

### 案例：可选功能"没声明"，导致安全检查被整个跳过

**来源**：`managed-deepagents` 官方 CHANGELOG 记录的一处安全修复（报告者 Corridor，issue #229）。**该修复出现在本教程基线之后的版本**，故此处只作教训引用，不用于推导 0.9.5 的具体行为。

**发生了什么**
平台为每个调用方维护两张保留表（`mda_identity_links` 账号关联、`mda_github_credentials` OAuth token）。这两张表的鉴权检查，被排在一个"按调用方记忆"的检查**之后**；而那个记忆检查在**没有声明记忆层**时会提前 `return`。

于是在任何没有声明记忆层的部署上，这两张保留表的检查**从来不执行** —— 一个已认证的调用方可以读取或覆盖其他人的条目。

**根因**
把"可选功能的开关"当成了"安全检查的前置条件"。**逻辑上的顺序错误，编译期完全看不出来。**

**为什么值得记**
这类问题的形状在本教程里反复出现（故障模式 4 的 `permissions = []`、故障模式 5 的三道闸），本质是同一个模式：**平台在你的配置之上做了一层合并，而合并规则不告诉你**。区别只是有的合并让你少了个功能，有的合并让你少了个防线。

**教训**
1. 安全校验**不能**挂在可选功能的条件分支里。
2. "没声明"必须等价于"走最保守路径"，而不是"跳过检查"。
3. 静默失效累积到一定程度就会变成安全漏洞 —— 所以静默本身就该当成缺陷对待。
