## 🔴 1. 症状：`mda build` 报 name 必须是静态字符串 {#s1}

**一眼识别**

```
error: agent `name` in agent.py must be a static string literal (e.g. name="research-assistant").
Dynamic values cannot be used as the LangGraph assistant id.
```

或同类报错指向 `schedules/` 里的某个字段。

| 步骤 | 动作 | 预期 |
|------|------|------|
| 止血 | 把 `name="..."` 里的表达式换成字面量字符串 | build 立刻通过 |
| 定位 1 | 看报错指向哪个文件：`agent.py` 还是 `schedules/*.py` | 指向 schedules 则见下方分支 |
| 定位 2 | 若是工厂入口（`agent = 函数`）：检查函数体有没有 `if` / `try` / `for` / `while` / `with` / `assert` / `del` | 有任一 → 静态扫描判定 name 不是字面量 |
| 修复 | 工厂体只保留 `Assign` / `Return` / 单独表达式语句；分支逻辑挪进工具或中间件 | build 通过且行为不变 |
| 若无效 | → 转「[3. 同步钩子](#s3)」查是否另有运行期错误；仍不过 → 转 `debug` | — |

> **分支**：官方文档给的 `if runtime is None: raise` 守卫写法**本身就会构建失败**。不要照抄，改用返回默认值。

**预防**：入口 `name` 与所有调度字段一律写字面量，环境差异用多个项目而非运行期计算。
**原理**：→ 故障模式 10：[迁移完成了，agent 行为变了，但没有任何报错](08-实战经验.md#m10)

## 🔴 2. 症状：build 报不允许设置托管字段 {#s2}

**一眼识别**

```
error: Remove 'checkpointer' from define_deep_agent(...)
```

同类还有 `store` / `backend` / `state_schema` / `instructions` / `skills` / `mcp` / `sandbox` / `permissions`（静态入口下）。

| 步骤 | 动作 | 预期 |
|------|------|------|
| 止血 | 从 `define_deep_agent(...)` 里删掉报错点名的那个参数 | build 通过 |
| 定位 1 | 判断入口类型：静态（`agent = define_deep_agent(...)`）还是工厂（`agent = 函数`） | **静态入口**会被 import + 逐项断言；**工厂入口完全不检查** |
| 定位 2 | 若确实需要按运行选 `instructions` / `skills` / `mcp` / `sandbox` | 改成工厂入口（返回定义的函数） |
| 修复 | 静态入口只用 `name` / `model` / `tools` / `context_schema` | 通过 |
| 若无效 | → 转「[15. 缺身份声明](#s15)」（若报的是 identity 相关） | — |

> **注意**：`instructions=` 在**静态**入口被拒；而在**工厂**入口里返回 `define_deep_agent(instructions=...)` 是合法的。同一个参数在两处的合法性相反。

**预防**：先定入口形态（要不要按运行变），再决定哪些参数能写。
**原理**：→ 故障模式 10：[迁移完成了，agent 行为变了，但没有任何报错](08-实战经验.md#m10)

## 🔴 3. 症状：`mda dev` 启动就崩，中间件抛 NotImplementedError {#s3}

**一眼识别**

```
NotImplementedError: Asynchronous implementation of awrap_tool_call is not available.
```

（或 `awrap_model_call` / `aafter_model` 等异步钩子名）

| 步骤 | 动作 | 预期 |
|------|------|------|
| 止血 | 给该中间件补上异步版钩子 `awrap_tool_call`（或改用 `async def`） | 服务能起 |
| 定位 1 | 搜中间件文件里所有 `def wrap_` / `def before_` / `def after_` 开头的同步钩子 | 逐个确认是否有对应 `async` 版 |
| 定位 2 | 若该中间件只实现了同步版且逻辑简单 | 直接改成 `async def` 并在内部同步调用 |
| 修复 | 托管层固定走 `ainvoke` / `astream`，同步钩子必然不匹配 | 补异步实现 |
| 若无效 | → 转「[4. MCP 配置已删项](#s4)」（若同时有 MCP）；仍崩 → 转 `debug` | — |

> **关键**：`mda build` **不拦**这条。build 绿灯 + dev 崩溃是这个坑的标准形态。官方中间件文档里给的第三条建议"用同步方式调用"在托管环境不成立。

**预防**：中间件一律只写 `async` 钩子；写完立刻 `mda dev` 起一次，别等部署。
**原理**：→ 故障模式 3 的相邻坑，见课 5 实验

## 🟡 4. 症状：MCP 配置报选项已被删除 {#s4}

**一眼识别**

```
ValueError: default_tool_timeout was removed in 0.9; use timeout for individual MCP requests
```

同类：`prefix_tool_name_with_server_name` / `automatic_sse_fallback` / `reconnect` 都会报 `was removed in 0.9`。

| 步骤 | 动作 | 预期 |
|------|------|------|
| 止血 | 删掉报错点名的那个键 | 导入期不再抛错 |
| 定位 1 | 对着四删表替换：前缀开关 → 用原生 `{server}_{tool}` 命名；整体超时 → 改用每个请求的 `timeout`；SSE 回退 → 显式选 transport；重连 → 不支持，靠调用方重试 | 全部替换完 |
| 定位 2 | 若报错是 `RuntimeError` 而不是 `ValueError` | 已经不是配置问题，是远端不可达 → 查 URL 与网络 |
| 修复 | 只想先跑通部分工具：设 `throw_on_load_error=False` 让坏的降级 | agent 能起，坏的那批工具缺席 |
| 若无效 | → 转 `debug`（MCP 建图期失败需要现场取证） | — |

> **三段校验必须记清**：build 只收文件（不校验配置）→ 导入期 pydantic 校验（这里炸）→ 建图期才真连远端。**build 绿灯完全不代表 MCP 配对了**。

**预防**：升级 CLI 后第一件事是跑一次导入期校验，不是等部署。
**原理**：→ 故障模式 3：[按官方文档写的 MCP 配置，导入期就崩](08-实战经验.md#m3)

## 🟡 5. 症状：`/memories/user/` 永远是空的 {#s5}

**一眼识别**

无报错。日志里可能出现 `not_a_person`。agent 层记忆读写正常，user 层永远空。

| 步骤 | 动作 | 预期 |
|------|------|------|
| 止血 | 先确认这不是"记忆丢了"而是"根本没挂上"：查是否用默认 LangSmith API key 身份跑 | 是 → 就是这道闸 |
| 定位 1 | 在工具里打印 `runtime.server_info.principal` | `None` 或 `kind=service` → 确认 |
| 定位 2 | 检查 `allow` 策略 | 恒真也救不了服务身份；`allow` 只能放宽不能越权 |
| 修复 | 换成能识别"人"的身份提供方（Supabase 那条路）；本地验逻辑可临时 `auth="backend"` | user 层开始有文件 |
| 若无效 | → 转「[6. 权限被静默清空](#s6)」查是否另有覆盖；仍空 → 转 `debug` | — |

> **分支**：如果是"写进去但下次没了"（而不是"从来没挂上"）→ 大概率写到了未挂载的 `/memories/` 路径，**不报错、运行结束即丢弃**。改用 `write_file` / `edit_file`，别用 shell 重定向。

**预防**：把"user 层依赖真实身份"写进项目 README 的启动前置条件。
**原理**：→ 故障模式 5：[用户私有记忆永远是空的](08-实战经验.md#m5)

## 🔴 6. 症状：`permissions` 写了但完全不生效 {#s6}

**一眼识别**

**无报错、无警告、无日志。** 禁止写的路径被写成功了。项目里有 `sandbox/` 目录。

| 步骤 | 动作 | 预期 |
|------|------|------|
| 止血 | 立即二选一：删掉 `sandbox/`（保权限）或接受权限失效、改由工具级限制（保 shell） | 边界变明确 |
| 定位 1 | `ls sandbox/` —— 存在即确诊 | 有 → `permissions = []`（全清） |
| 定位 2 | 确认反向成立：**没有** sandbox 时你的规则会保留，且平台追加 `/skills/**` 写保护 | 用于判断改动方向 |
| 修复 | 保 shell 的方案：把暴露面收到"只给这几个工具"，并在每个工具内部自己做路径校验 | 越权路径被堵 |
| 若无效 | → 转「[5. 用户记忆挂不上](#s5)」（若同时发现记忆异常）；仍越权 → 转 `debug` | — |

> **别去 `.mda/build` 找证据**：产物里可能还留着你的 `permissions` 字面量，运行时已被覆盖，看产物会误判。

**预防**：在 `sandbox/__init__.py` 顶部第一行写"声明本文件会让 permissions 失效"。
**原理**：→ 故障模式 4：[文件权限规则写了，但完全不生效](08-实战经验.md#m4)；源码 `runtime.py:1188`

## 🟡 7. 症状：模型说"我没有这个工具" {#s7}

**一眼识别**

无报错，build 绿灯。模型回复"无法查询""没有权限访问系统"。`tools/xxx.py` 文件确实存在。

| 步骤 | 动作 | 预期 |
|------|------|------|
| 止血 | 打开 `agent.py` 确认两件事同时成立：`from tools.xxx import ...` 有 + `tools=[...]` 里有 | 缺哪个补哪个 |
| 定位 1 | 打印 `len(agent.tools or [])` | 为 0 → 确认没注册 |
| 定位 2 | 区分漏 import（报 `NameError`）vs 漏传参（完全静默） | 无 NameError = 漏传参 |
| 修复 | 补齐两步；工具多时在入口聚合一次再传 | 模型能看到工具 |
| 若无效 | → 转「[8. 技能未被发现](#s8)」（若同时怀疑技能）；仍无 → 转 `debug` | — |

> **相邻坑**：`tools/mcp.py` **是**存在即生效的（保留名），`tools/` 下其他文件才需点名。两类机制相反，别混。

**预防**：CI 加断言 `assert len(agent.tools) == 预期数量`。
**原理**：→ 故障模式 1：[工具写好了、文件也在，模型却说"我没有这个工具"](08-实战经验.md#m1)

## 🟡 8. 症状：技能从来没被用过 {#s8}

**一眼识别**

无报错。`skills/*/SKILL.md` 内容完整，模型从不按流程走。

| 步骤 | 动作 | 预期 |
|------|------|------|
| 止血 | 先看目录层级：`find skills -mindepth 3 -name SKILL.md` | 有输出 → 是嵌套目录，只认一层 |

**预防**：CI 对比 `find skills -name SKILL.md | wc -l` 与 `find skills -mindepth 3`，深度超限即报错。

## 🔴 9. 症状：Slack 回调 404，或本地怎么点都没反应 {#s9}

**一眼识别**

Slack 后台显示请求失败，服务端日志 404。或 `mda dev` 正常但没有任何响应。

| 步骤 | 动作 | 预期 |
|------|------|------|
| 止血 | 看 `mda dev` 启动横幅打印的路由，把 Slack 后台地址改成它 | 通常是 `/v1/channels/slack/events` |
| 定位 1 | 两条 curl 二分：访问 `/v1/channels/slack/events` | 返回 **401** = 路由存在（找对了）；返回 404 = 路径错 |
| 定位 2 | 访问 `/channels/slack/events`（无前缀） | 返回 404 = 证实需要 `/v1` |
| 修复 | Slack 用带 `/v1` 的地址；HTTP 通道**不带**前缀 | 回调变 401 → 签名问题，转下一条 |
| 若无效 | → 转「[10. 签名校验失败](#s10)」 | — |

> **规则**：`transport == "trigger_server"`（Slack）带 `/v1`；HTTP 通道不带。别凭文档猜，看横幅。

**预防**：把这条写进部署清单；新增通道文件后**重启** `mda dev`（不热重载）再核一次。
**原理**：→ 故障模式 7：[按文档注册 Slack 回调地址，得到 404](08-实战经验.md#m7)；源码 `_identity_http.py:191-193`

## 🟡 10. 症状：`401 invalid channel signature` {#s10}

**一眼识别**

```
401 {"error":"invalid channel signature"}
```

| 步骤 | 动作 | 预期 |
|------|------|------|
| 止血 | 核对签名密钥与 Slack 后台 Signing Secret 是否一致 | 一致则进入定位 |
| 定位 1 | 无签名头 vs 签名错 —— 两者都返回 401，看服务端日志区分 | 无头 = 平台没发；错 = 密钥不符 |
| 定位 2 | 检查 `verify` 实现：是返回 `False` 还是抛异常 | 抛异常会变 500，见「[11](#s11)」 |
| 修复 | `verify` 返回 `False`（401，又快又对）；确认密钥从环境变量读 | 401 消失 |
| 若无效 | → 转「[11. 通道运行时缺失](#s11)」（若签名对了但报 500）；仍 401 → 转 `debug` | — |

**预防**：`verify` 一律返回布尔，不用异常做拒绝。
**原理**：→ 故障模式 7：[按文档注册 Slack 回调地址，得到 404](08-实战经验.md#m7)

## 🔴 11. 症状：`500 channel runtime is not configured` {#s11}

**一眼识别**

```
500 {"error":"channel runtime is not configured"}
```

签名验证已通过（否则是 401），但运行时还没挂上。

| 步骤 | 动作 | 预期 |
|------|------|------|
| 止血 | 确认环境变量 `MDA_ASSISTANT_ID` 已设置 | 设置后重启服务 |
| 定位 1 | 检查是本地 `mda dev` 还是已部署环境 | 本地缺变量最典型 |
| 定位 2 | 确认通道文件在 `channels/` 直接子层级（不是嵌套目录） | 嵌套 → 收集时静默跳过 |
| 修复 | 补 `MDA_ASSISTANT_ID`；通道文件拍平到 `channels/xxx.py` | 500 消失，返回正常响应 |
| 若无效 | → 转「[9. 通道地址错误](#s9)」复核路径；仍 500 → 转 `debug` | — |

> **另注意**：缺 `channel` 导出时是 **import 阶段静默跳过**（`collect_channels` 里 `continue`），不报错 —— 表现为"通道整个不存在"，路由直接 404。

**预防**：`channels/` 每个文件都显式导出 `channel`；新增后重启 dev 看横幅是否列出来。
**原理**：→ 故障模式 7 相邻坑（课 8 实验）

## 🔴 12. 症状：用户收到两张一样的审批单 / 动作执行两次 {#s12}

**一眼识别**

同一张表单被提交两次；或升级/下单/发消息被执行两遍。日志里同一函数被调用了两次。

| 步骤 | 动作 | 预期 |
|------|------|------|
| 止血 | 先停掉有副作用的动作（注释掉或用开关），别让它继续重复 | 重复停止 |
| 定位 1 | 打印 `runtime.channel.event["type"]`，跑一次审批 | 出现两次调用、第二次 type 是 `user_prompt_response` → 确诊 |
| 定位 2 | 确认所有副作用动作是否放在事件判断之前 | 在前 → 就是它 |
| 修复 | 加第一道闸：`if runtime.channel and runtime.channel.event["type"] != "user_prompt_response":` 才执行 | 只执行一次 |
| 若无效 | → 转「[11. 通道运行时缺失](#s11)」；仍重复 → 转 `debug` | — |

> **前提认知**：中断续跑是**从函数第一行重跑**，不是从 `interrupt()` 那行继续。所有有副作用的动作都必须在闸之后。

**预防**：把"续跑 = 重跑"写进中断逻辑的注释第一行。
**原理**：→ 故障模式 8：[用户收到两张一模一样的审批单](08-实战经验.md#m8)

## 🔴 13. 症状：部署预检报缺 key，但 shell 里明明有 {#s13}

**一眼识别**

```
error: The agent model 'openai:gpt-5.5' requires OPENAI_API_KEY in /path/to/project/.env
```

`echo $OPENAI_API_KEY` 有值。

| 步骤 | 动作 | 预期 |
|------|------|------|
| 止血 | 把 key 写进项目根的 `.env`（不是 shell export） | 预检通过 |
| 定位 1 | `ls -la .env`（不是 `.env.example`） | 存在 |
| 定位 2 | `grep OPENAI_API_KEY .env` 确认键名与值非空 | 有值 |
| 修复 | 写入 `.env`；shell 变量只在"deploy 转发成部署密钥"意义上有效 | 预检过，进入下一步 |
| 若无效 | → 转「[14. 密钥本身无效](#s14)」（预检过了但 403） | — |

> **官方 deploy 文档说 key 可从 shell 取得，是错的**；migrate 文档才对。实测为准。

**预防**：`.gitignore` 含 `.env`；项目留 `.env.example` 作键名清单。
**原理**：→ 故障模式 9：[部署预检报 "requires OPENAI_API_KEY in .../.env"](08-实战经验.md#m9)

## 🔴 14. 症状：预检过了，但 403 {#s14}

**一眼识别**

```
403 {"detail":"API key is forbidden"}
403 {"detail":"API key tenant mismatch"}
```

| 步骤 | 动作 | 预期 |
|------|------|------|
| 止血 | 换一把有效 key 立刻重试一次 | 能定位是 key 问题还是权限问题 |
| 定位 1 | `forbidden` = key 无效/撤销/过期 | → 换 key |
| 定位 2 | `tenant mismatch` = key 有效但属于别的 workspace | → 换成目标 workspace 的 key |
| 修复 | 按上面两分支换 key；同时确认该 workspace 有 public beta 访问权 | 403 消失 |
| 若无效 | → 转「[18. 归档超限](#s18)」（若换 key 后是构建失败）；仍 403 → 转 `debug` | — |

**预防**：本地 `.env` 用开发 workspace 的 key，别混用生产。
**原理**：→ 故障模式 9 相邻分支（课 9 实验）

## 🔴 15. 症状：`mda dev` 拒绝启动，要求根级 identity {#s15}

**一眼识别**

```
channels/ or connectors/ with an ingress trigger ... require a root identity declaration;
ingress triggers cannot fall back to a deployment service principal
```

| 步骤 | 动作 | 预期 |
|------|------|------|
| 止血 | 在项目根建 `identity.py`（原地建，不要放子目录） | 服务能起 |
| 定位 1 | `ls channels/ connectors/` | 有任一 → 必须有 identity |
| 定位 2 | 看 `identity.py` 的 auth 配法 | 默认 API key 模式无人概念（见 [5](#s5)） |
| 修复 | 加 `identity = define_identity(auth=auth.supabase(project_ref="..."))`；本地验逻辑可临时 `auth="backend"` | 启动成功且 Slack 路由正常注册 |
| 若无效 | → 转「[16. 本地缺 key](#s16)」 | — |

> **不能退回服务身份** —— ingress trigger 不允许 fallback 到 deployment service principal。删掉 `identity.py` 一定起不来。

**预防**：加 Slack 通道的同一次提交里就加 `identity.py`。
**原理**：→ Phase 3 项目新发现第 1 条

## 🔴 16. 症状：`mda dev` 报 user memory 需要 LANGSMITH_API_KEY {#s16}

**一眼识别**

```
user-owned connections, managed tools, and user memory require LANGSMITH_API_KEY under mda dev
```

| 步骤 | 动作 | 预期 |
|------|------|------|
| 止血 | 先判断你是否真需要 user 层记忆 | 不需要 → 删掉 `user=MemoryLayer()` |
| 定位 1 | 若只是本地跑 agent 逻辑、不验身份 | 用 `auth="backend"` 绕过 |
| 定位 2 | 若必须验 user 层 | 需要**真实** key，假 key 会在更靠后的步骤 403 |
| 修复 | 三选一：删 user 层 / `auth="backend"` / 配真实 `LANGSMITH_API_KEY` | 服务能起 |
| 若无效 | → 转「[5. 用户记忆挂不上](#s5)」；仍起不来 → 转 `debug` | — |

> **假 key 会骗过前置检查**：`LANGSMITH_API_KEY=lsv2_fake` 能过启动前置，但随后报 `LangSmith could not identify the API key owner: Forbidden (HTTP 403)`。

**预防**：本地开发默认 `auth="backend"`，只在验收 user 层时才配真 key。
**原理**：→ Phase 3 项目新发现第 2、3 条

## 🟡 17. 症状：部署后 cron 不跑，或跑在错误时区 {#s17}

**一眼识别**

到点了没有任何执行记录；或"早八点晨报"在下午才发。

| 步骤 | 动作 | 预期 |
|------|------|------|
| 止血 | 先确认部署是否真的完成了 cron 同步 | 用了 `--no-wait` → 就是它 |
| 定位 1 | 检查部署命令有没有 `--no-wait` | 有 → 它跳过 cron 同步 |
| 定位 2 | 检查 `schedules/` 里是否显式写了 `timezone` | 没写 → 吃平台默认时区 |
| 修复 | 去掉 `--no-wait` 重新部署；给每个 schedule 显式加 `timezone="Asia/Shanghai"` | cron 到点执行 |
| 若无效 | → 转「[1. 静态字面量被拒](#s1)」（若 build 阶段就报）；仍不跑 → 转 `debug` | — |

> **两个方向相反的默认值**：运行期创建调度时 `cron` 默认 `new_thread=True`，`at` 默认 `False`。线程策略写反会让晨报污染线程列表，或让一次性任务复用到旧上下文。

**预防**：所有 schedule 显式写 `timezone` 与线程策略；部署一律不加 `--no-wait`（有 Slack 通道时更不能加）。
**原理**：→ 故障模式 10 相邻分支（课 8/课 9 实验）

## 🟡 18. 症状：构建归档超 200 MB / 部署失败 {#s18}

**一眼识别**

```
Build over 200 MB
```

或 `BUILD_FAILED` / `DEPLOY_FAILED` 并打印了 revision 日志 URL。

| 步骤 | 动作 | 预期 |
|------|------|------|
| 止血 | `du -sh .` 找最大的目录，先从项目里移出去 | 体积下降 |
| 定位 1 | 检查是否有 `.venv/` / `node_modules/` / 模型权重 / 大数据 fixture 在项目根 | 命中即元凶 |
| 定位 2 | 确认 `.mda/` 构建产物是否被重复计入 | 有 → 清理后重建 |
| 修复 | 大文件移到对象存储，项目里只留引用；`.gitignore` 与项目结构同步清理 | 归档达标 |
| 若无效 | → 打开日志 URL 读 revision 详情；仍失败 → 转 `debug` | — |

> **注意**：`mda build` 会把项目根**整个拷贝**进 `.mda/build`，只排除 `.env` 与 `.env.*`。项目根只放要上线的东西。

**预防**：项目根保持最小；`.env` 之外的本地配置也别放根目录。
**原理**：→ 故障模式 10 相邻分支（课 9 实验）

## ⚪ 19. 症状：环境与脚手架类报错 {#s19}

**一眼识别**

- `cannot find uv`
- `destination ... already exists; remove it or run mda init with another name`
- `npx mda --version` 行为异常 / TS 项目生成不出来

| 步骤 | 动作 | 预期 |
|------|------|------|
| 止血 | 按报错逐条处理（见下方分支） | — |
| 分支 A | `cannot find uv` → 装 `uv`（`mda dev` 靠它拉起本地 dev server，TS 侧同样需要） | 命令可用 |
| 分支 B | `already exists` → 换名字或先删目录（**不要**先 `mkdir`） | init 成功 |
| 分支 C | 想要 `agent.ts` 却只得到 Python 项目 | 用 `npx managed-deepagents init`（渠道决定语言，PyPI 版拒绝 TS） |
| 修复 | 四项验证全绿：`uv --version` → `uv run mda --version` → `uv run mda build` → `ls .mda/build/langgraph.json` | 环境就绪 |
| 若无效 | → 转 `debug` | — |

**预防**：记死"渠道决定语言"这一条；`mda init` 自己建目录，别预建。
**原理**：→ 课 1 环境准备

## ⚪ 20. 症状：沙箱里的文件突然没了 {#s20}

**一眼识别**

上一次会话写的临时文件这次读不到；`ls` 看到的是干净的初始环境。无报错。

| 步骤 | 动作 | 预期 |
|------|------|------|
| 止血 | 确认这是设计行为而非故障：沙箱按会话分配、闲置即回收 | 判断是否需要改设计 |
| 定位 1 | 检查 `sandbox/` 里的 `idle_ttl_seconds` | 900 = 15 分钟闲置回收 |
| 定位 2 | 确认是否跨线程访问 | 一个线程一个沙箱，跨线程看不到 |
| 修复 | 需要跨会话保留的产物 → 写进记忆或外部存储，不要指望沙箱 | 数据持久 |
| 若无效 | → 转 `debug` | — |

**预防**：把"沙箱是临时工作台，不是存储"写进项目说明；TTL 按任务时长调，不按"越大越好"。
**原理**：→ 课 6 知识点 3

## 🔴 21. 症状：零报错，但低权限调用方做成了高权限操作 {#s21}

**一眼识别**

没有异常、没有告警、日志里全是 200。只有事后对账才发现：一个只该看报表的调用方，把工单升级了。

| 步骤 | 动作 | 预期 |
|------|------|------|
| 止血 | 先在**工具内部**加一道 `principal` 判断并立即发布，不等重构 | 越权路径当场断掉 |
| 定位 1 | 全局搜 `runtime.context` 里被当作权限用的字段（`role` / `is_admin` / `team` 之类） | 命中即根因 |
| 定位 2 | 确认写操作的判断依据是不是 `runtime.server_info.principal` | 不是 → 就是它 |
| 定位 3 | 检查是否有人能直调 `backend.read()` / `backend.write()` 绕过中间件 | 有 → 那条路径没有守卫 |
| 修复 | 权限判断一律改读 `principal`；`context` 只用于**选行为**（语言、档位、模板），不用于判权 | 越权不可达 |
| 若无效 | → 转「[6. 权限被静默清空](#s6)」（两件事常同时发生）；仍可疑 → 转 `debug` | — |

> **为什么难发现**：`context` 是调用方自己填的登记本，平台**不校验也不剥离**你自起的业务字段 —— 它会被原样送进工具。写 `context["role"] == "admin"` 就是在信任调用方的自述。
> **一个例外要记清**：13 个平台保留键（如 `thread_id` / `assistant_id`）会被 `sanitize_configurable` 全剥掉，所以保留键读不到不是 bug；但**你自己起的业务字段不会被剥**。

**预防**：把"`context` 选行为、`principal` 判权限"写成团队规约；每个写工具的第一行就是 `principal` 判空。
**原理**：→ 故障模式 6：[把 `context` 当权限判断依据，越权成功了](08-实战经验.md#m6)

## 查不到你当前的症状？

本手册覆盖的是**领域典型**失败模式，不负责定位具体 bug。三种去处：

1. **症状形态相似但报错原文不同** → 先按"最接近的条目"做第一步止血，再转第 2 条
2. **完全没有匹配条目** → `use_skill("debug")` 现场取证（复现 → 假设 → 验证 → 定位）
3. **想知道为什么会这样** → 翻 [08-实战经验.md](08-实战经验.md) 对应编号的故障模式
