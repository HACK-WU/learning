# 设计决策 · 智能客服助手

> 每个决策点都**真有争议**——换个人来可能选另一个方案，且也有道理。
> 论证中的量化依据来自本课程实测（标注了出处）。

## 决策 1：客服 agent 的架构——单 agent + 中间件 vs Router 多专家拆分

**背景**：客服要处理多类诉求（政策咨询 / 订单物流 / 售后处理 / 投诉升级）。可以只用一个 agent 挂全部工具；也可以按"路由 → 分派给专家 → 综合"的模式拆分。

**候选方案**：

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| A · 单 agent + 中间件 | 一个 agent 挂 6 个工具；用中间件（脱敏 / 审批 / 限额）管控行为 | 组装/调试简单；一条对话流；测试成本低（一套管线）；中间件统一生效 | 每次调用携带全部工具 schema（固定税）；提示词承载全部工作准则，变长 |
| B · Router 多专家 | 先分类诉求（政策 / 订单 / 售后），并行分派给 3 个子 agent，再综合回复 | 上下文隔离（每个专家只带自己的工具与知识）；可并行；领域可独立维护（课 12 实测：主代理仅 275 字符 vs 全能 agent 1983 字符） | 调用次数增加（课 12 实测 router 全程 3-7 次调用）；调试链变长；审批/脱敏等护栏要在多处配置；测试面变大 |

**最终选择**：A · 单 agent + 中间件

**选择理由**：本项目的工具规模（6 个）与领域数量（1 条客服线）未达到拆分阈值——课 12 实测结论是「工具在 8 个甚至 16 个时模型仍能选对，退化的信号是**决策质量**而非工具数」；而客服场景的价值点集中在**安全护栏**（审批 / 脱敏 / 限额），单 agent 的中间件管线让护栏"一处配置、全局生效"，拆分反而要在每个子 agent 重复配置。另外，单 agent 一套测试管线即可覆盖，符合"先把简单方案做扎实"的工程原则。

**为此付出的代价**：每次模型调用都携带 6 个工具的完整 schema（约 1.5K 字符的固定税）；工作准则集中在一个提示词里，后续加领域（如发票重开、价格保护）会让提示词持续变长、互相干扰；无法并行处理"同时查订单 + 发票 + 会员"这类多来源问题（单 agent 只能串行）。

**什么时候该改选另一个**：工具数量涨到 10 个以上 / 出现多团队独立维护各自领域 / 需要并行多来源查询时——按课 12 的模式拆分（router 或 subagents），并把护栏中间件迁移到子 agent 组装层。

## 决策 2：退款审批策略——全量审批 vs 金额分级 vs 全自动

**背景**：退款是资金动作（一旦执行不可逆），但客服场景退款高频（小额居多）。审批策略直接影响体验、风险与人工成本。

**候选方案**：

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| A · 全量人工审批 | 每笔退款都中断等人工批准 | 风险最低；资金零误退 | 小额退款也要等人工（人工成本高、用户体验差）；实测中"29 元贴膜"这种退款也要打扰审批人 |
| B · 金额分级 | ≥ 阈值（默认 50 元）中断审批；小额直通 | 小额无感（体验好）；大额有人把关；实现上就是 `when` 谓词一行条件 | 阈值本身是经验值；小额可能被拆单滥用；"直通"部分依赖工单内部校验兜底 |
| C · 全自动 + 事后审计 | 全部退款直接执行，靠审计追溯 | 体验最好、人工零成本 | 错误退款不可逆（钱出去了要人工追回）；无审批的审计只是"事后知道"，防不住损失 |

**最终选择**：B · 金额分级（`when` 条件中断实现）

**选择理由**：实测验证了两条路径的行为差异——399 元退款触发中断、审批请求完整呈现给人工（`{"order_id": "A1001", "amount": 399}`），批准后才执行；29 元退款直通执行、不打扰审批人；再叠加「金额必须与订单实付一致」的工具内校验（防模型幻觉改金额）与「每会话最多 2 次退款」的限额，构成了三层护栏。这与课 10 的护栏思想一致：**闸门装在风险最高的动作上，而不是全部动作上**。

**为此付出的代价**：50 元的阈值是拍脑袋的经验值（缺乏数据支撑，应随真实退款分布调整）；小额直通存在被拆单滥用的理论风险（对策是限额兜底，而非审批）；两条路径意味着两条测试分支（单元测试已分别覆盖）。

**什么时候该改选另一个**：若接入风控模型（可评估账号风险等级）→ 可对低风险账号放宽自动额度，向 C 靠拢；若退款量激增到人工审不过来 → 提高阈值或引入「客服两级审批」（小额客服自审、大额主管审）。

## 决策 3：会话记忆策略——全量历史 vs 摘要压缩 vs 长期档案

**背景**：客服对话要记住上文（订单号、已确认的信息），但历史消息会推高每次调用的 token 成本。

**候选方案**：

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| A · 全量历史 | checkpointer 保存全部消息，原样带进每次调用 | 实现最简；信息零丢失；调试时可见完整上下文 | 长会话 token 线性增长；超长后逼近代价与窗口上限 |
| B · 摘要压缩 | SummarizationMiddleware 超限自动摘要，用摘要替换早期历史 | 压缩后历史封顶（会话可无限长）；关键信息被保留进摘要消息 | 摘要不是"免费优化"：课 7 实测同一对话摘要 303 token vs 全量 135 token——摘要文本有体量，且每次触发多一次模型调用（小对话反而更贵，长对话才回本） |
| C · 长期档案 | 短期用 A/B，另用 InMemoryStore 跨会话记住用户偏好 | 跨会话个性化（"上次你说偏好电话联系"） | 复杂度最高：档案写入/读取/隐私治理都要设计；本课程场景尚未验证跨会话需求 |

**最终选择**：A · 全量历史（checkpointer）+ 明确演进条件

**选择理由**：客服会话的典型长度（本轮 demo 实测 2 轮 ≈7 条消息）远未到需要压缩的量级；课 7 的实测数据（摘要触发后 303 token > 全量 135 token，小对话反而更贵）表明摘要要等长对话才回本——在"信息完整性优先、成本敏感度中等"的客服场景，先用全量历史最合理。此外 A 方案让 demo/测试可完整回放消息序列（本项目的审批流、多轮记忆测试都依赖完整历史），**调试可见性**本身就是本期价值。

**为此付出的代价**：会话超过 ~30 轮后 token 成本明显上升；每个新会话从零开始（用户上次说过的偏好不会记得）；checkpointer 用内存存储，进程重启即失忆（演示级妥协，生产需换持久化存储）。

**什么时候该改选另一个**：会话平均轮次 > 30 → 叠加 B（摘要中间件）；确认需要跨会话记住用户偏好（如联系方式偏好、常用地址）→ 叠加 C（长期 store）；上生产环境 → 先把 checkpointer 换成持久化后端，再启用 B/C。
