## 第一幕：起源与场景引入

> 🏛️ **起源**：HITL（Human-in-the-loop，人在环中）与 guardrails（护栏）并非 LangChain 独创——它们来自 AI 应用落地的真实教训：当 LLM 应用从"说"走向"做"（发邮件、改数据、调用外部系统），**执行权**就成了最危险的资产。业界共识逐步成型：高风险动作应当像财务审批一样"先冻结、后放行"；敏感信息应当像机场安检一样"过闸"。官方文档把 HITL 定性为"为 agent 的工具调用加装人工监督"，把护栏定性为"在关键点位验证与过滤内容"——LangChain 1.x 把它们都落成中间件（核对于 2026-09）。

客服助手第九次进化。它已经能读邮件、查订单、发通知、删记录——**有手有脚**。上线第二个月，麻烦来了。第一次：测试环境的一段提示词被误带到生产，助手主动给 200 个客户群发了"测试"邮件——发出去的那一秒，没有人来得及说"等等"。第二次：用户在对话里贴了身份证号与银行卡号，助手很"配合"地把它复述进了回复和日志——数据泄漏的锅扣在了你的头上。第三次：运营同事发现"清理 90 天前订单"被执行了，翻遍审批记录——**没人批准过**；是助手自己判断"该做"。

> 🎬 **场景**：三次事故的共同点不是模型"说错了话"，而是**模型做了它能做的事，而没有人（或流程）在关键点拥有否决权**。前九课给了它能力（工具、循环、记忆、上下文），这一课补上最后一块拼图：**谁说了算**。

> 📌 **一句话本质**：人机协同 = **把高风险操作的执行权从模型的默认行为里收回来**——工具在执行前被冻结，等人给出决定（approve / edit / reject / respond）后才放行；护栏 = **在输入、输出、工具结果三个点位验证与过滤内容**（PII 脱敏、违规拦截、输出审查）——两者都通过中间件体系挂载（官方定义：HITL 为工具调用加装人工监督；护栏在关键点验证与过滤内容。核对于 2026-09）。
>
> ⚖️ **处境对照**：没有这一课——不可逆动作裸奔（发出去的邮件收不回）、PII 一路畅通（进模型、出回复、落日志）、违规请求照单全收。有了这一课——工具先冻结（实测：审批前执行账本为空）、敏感信息在进入模型视野之前已被脱敏（实测：模型回显的就是脱敏文本）、违规请求在模型被调用之前就被挡下（实测：固定话术 + 跳步收束）。

## 第二幕：认知冲突

到这里你可能有一个自然的冲动：**"简单，我把所有工具的审批都打开，再挂上十个护栏——万事大吉。"**

两个问题会立刻打脸。

**问题一：全开审批 = 审批疲劳。** 当每个动作都停下等点头，人会开始闭眼点"同意"——防线形同虚设，还赔上了流程效率。真正的问题是：**哪些动作值得占用人的注意力？**（官方给出的高危四类：金融交易与转账、删除或修改生产数据、向外部发送通信、任何有重大业务影响的操作。）更进一步：**同一个工具，也不是每次都要停**——给内部同事发邮件和给外部列表群发，风险不同；读数据与删数据，风险不同。这就需要"条件中断"：让判定逻辑按**调用的参数**决定停不停（本课实测了 `when` 谓词方案）。

**问题二：审批不是"同意/拒绝"二选一，而且每种决策都有隐藏代价。** 现实里的审批台至少需要四种按钮：**原样放行**（approve）、**改一改再放行**（edit）、**拒绝并说明理由**（reject）、**我来替它回答**（respond，用于"向用户提问"型工具）。而且每种决策都有代价——特别是 edit：本课实测复现了官方警告的场景——**你改了参数，模型会发现"执行结果和用户原始要求不一致"，然后重新发起原始请求**（第二次中断不请自来）。此外还有一层工程前提：**中断要能"存下来"**——没有检查点（checkpointer），你连恢复都恢复不了（实测：恢复直接报 RuntimeError）。

> ❓ **问题**：什么操作该让人介入（判定标准）？中断如何配置、决策如何落地、又如何恢复执行？护栏挂在哪些点位、用什么策略？

三个追问把这件事拆开：

- 追问一：**哪些操作必须人工把关？**——官方高危清单 + 一个可操作的判定问句（可逆吗？影响钱吗？外面看得见吗？）；决策类型全貌（四种）。
- 追问二：**中断的机制细节？**——按工具配置（三形态）、条件中断（when）、四种决策的落地方式、批量决策的顺序对齐、v1/v2 返回形态、检查点的硬要求、与流式的配合。
- 追问三：**护栏怎么建？**——内置 PII 四策略（redact / mask / hash / block）+ 三个点位（输入/输出/工具结果）+ 自定义护栏两种挂法（before_agent 拦请求 / after_agent 审输出）。

由此得到本课的关键认知：**"能不能自己做主"不是一个开关，而是一套分级设计**——按风险分级设置闸门、按决策类型给出放行方式、按点位布置过滤。和课 9 的分水岭一样，动手之前先问：**这个动作一旦执行，还能撤回吗？**

### 知识点 1：为什么需要人在环中

> 🧭 第 1/3 步｜承接：课 5 的 agent 循环能自己跑、课 8 的中间件能在步骤间插入逻辑——现在把"执行权"从模型手里收回来 → 本步：立高危清单、给决策类型、定判定标准

#### 一句话定义

人在环中（Human-in-the-loop，HITL）= **为 agent 的工具调用加装人工监督**：当模型提议的动作属于需要复核的范围，执行被暂停（工具被冻结），等人给出决定后再放行——官方给出的四种决定方式：approve（原样执行）、edit（改参数执行）、reject（拒绝并反馈）、respond（人工代答，用于"向用户提问"型工具）。

#### 直觉建立（类比）

新员工上岗的"分级授权"。小额报销自己签字就行；超过一万要走主管；对外发合同必须法务会签；转账付款必须双人复核。公司不会让新人"每一步都请示"（那叫没效率），也不会"什么都自己定"（那叫没规矩）——**按风险分级设置审批点**，这才是"人在环中"的真实形态。

> 💡 **类比的边界**：现实审批有"纸质留痕"，agent 的审批靠**检查点（checkpointer）**——中断那一刻，整个对话状态被存进存档点；没有这个存档点，审批流程根本无法开始恢复（本课实测了没有它时的报错）。

#### 核心原理

**① 先立高危清单（官方列举的四类高风险操作）**：

| 场景类别 | 例子 | 为什么危险 |
|---------|------|-----------|
| 金融交易与转账 | 付款、退款、下单 | 钱出去就难回来 |
| 删除或修改生产数据 | 删记录、改配置、清库 | 不可逆或影响面大 |
| 向外部发送通信 | 发邮件、发消息、发公告 | 出了公司大门就收不回 |
| 有重大业务影响的操作 | 变更权限、触发对账 | 连锁反应可能超出预期 |

另有一类特殊的：**"向用户提问"型工具**（如 `ask_user` 澄清需求）——它的"真实实现"其实就是人的回答，对应决策类型里的 `respond`（知识点 2 详解）。

**② 四种决定方式（官方决策类型表 + 直觉）**：

| 决策 | 含义 | 典型场景 |
|------|------|---------|
| `approve` | 原样执行 | 邮件草稿没问题，照发 |
| `edit` | 改参数后执行 | 收件人写错了，改了再发 |
| `reject` | 拒绝执行 + 反馈理由 | 这个文件不能删，告诉它为什么 |
| `respond` | 人工代答（工具不执行） | 模型问"出发日期？"，人来回答 |

**③ 判定标准：一个可操作的问句**。任务到来时问三件事：**① 可逆吗？**（发邮件不可逆、读数据可逆）；**② 影响钱/生产数据吗？**（转账、删库 → 停）；**③ 外面看得见吗？**（发给外部客户 → 停；内部工具调用 → 可放）。三个问题只要命中一个"是"，就该给它挂闸门——官方对 HITL 的定位正是"高风险的决策最有效的护栏之一"。

**④ 实测：审批台上长什么样**。给 `send_email` 挂上闸门（`interrupt_on={"send_email": {...}}`）、`read_inbox` 不上闸门，然后各发一个请求（实测 1a/1b）。邮件请求停在了半路，返回的中断提案（HITLRequest）结构完整：

```text
  返回类型: dict | keys: ['messages', '__interrupt__']
  __interrupt__ 类型: list | 数量: 1
    action_request: name=send_email
      args={'recipient': 'alice@corp.com', 'subject': '周会提醒'}
      description=工具执行待审批 Tool: send_email Args: {'recipient': 'alice@corp.com', 'subject': '周会提醒'}
    review_config: {'action_name': 'send_email', 'allowed_decisions': ['approve', 'edit', 'reject']}
  工具此刻被调用过吗: False （应为 False——等审批）
```

三个看点：① 提案里带着**动作本身**（工具名 + 参数）和**可选项**（`allowed_decisions`，我们配置的 `['approve', 'edit', 'reject']`）；② 描述文本来自 `description_prefix`（"工具执行待审批"）+ 工具名 + 参数——这就是要展示给审批人看的"一句话说明"；③ **工具此刻还没有被执行**（账本为空）——冻结是真的冻结。批准之后（`Command(resume={"decisions": [{"type": "approve"}]})`）：

```text
  approve 后工具执行账本: [('send_email', 'alice@corp.com', '周会提醒')]
```

而 `read_inbox` 的请求从未被中断（`是否被中断: False`，`工具执行账本: [('read_inbox',)]`）——**闸门是按动作配置的，不是全局暂停**。这正是"分级授权"在代码里的样子。

**⑤ 与课 8/课 9 的接口**：HITL 中间件挂在 `after_model` 钩子上——模型生成了工具调用、但**工具还没执行**的那个瞬间（官方执行生命周期描述）。课 8 学的钩子体系是"挂载点"，课 9 学的上下文是"给模型看什么"，本课回答的是"让不让模型做"。

#### 示例演示

见上文实测：中断提案全貌（1a 段）、不设闸门直通对照（1b 段），来源脚本 `playground/lesson-10-hitl-lab.py`。

#### 常见误区

1. **以为 HITL 是"每步都停"**：它是按工具（乃至按参数）配置的闸门——安全操作直通（1b 实测）。
2. **以为审批就是"同意/拒绝"**：四种决策各有分工——特别是 edit（改参数）与 respond（代答）常被忽略。
3. **以为"冻结"是形象说法**：实测确凿——审批前执行账本为空，工具根本没跑（1a）。
4. **以为所有操作都值得挂闸门**：官方明确"一次一个特性"的增量思路（课 9 最佳实践）在这里同样适用——按风险清单逐项加，别全开。

#### 一句话记住

> 高风险动作先冻结、等人点头；四种决定方式（approve / edit / reject / respond）就是审批台上的四个按钮——按钮按风险配置，不必人人都有。

#### 🗣️ 行话对照

- **Human-in-the-loop（HITL）**：为工具调用加装人工监督——在哪遇到：官方 human-in-the-loop 页
- **interrupt_on**：按工具名配置审批策略的映射——在哪遇到：`HumanInTheLoopMiddleware`
- **action_requests / review_configs**：中断提案里的"动作清单"与"可选项清单"——在哪遇到：`__interrupt__` 返回值
- **allowed_decisions**：该动作允许的决策白名单——在哪遇到：`InterruptOnConfig`
- **respond 型工具**：真实实现就是人工回答的"提问"工具——在哪遇到：`ask_user` 模式

### 知识点 2：中断机制

> 🧭 第 2/3 步｜承接：知道"哪些该停"了——现在把它落成机制 → 本步：配置三形态、四种决策的落地细节、批量与条件、恢复与流式、检查点硬要求

#### 一句话定义

中断（interrupt）= 执行到审批点时**冻结运行、把状态存进检查点、把控制权交还调用者**；恢复 = 用 `Command(resume=...)` 把人的决定送回，从存档点继续跑。配置通过 `interrupt_on` 映射（三形态：`True` 全决策、`False` 直通、字典指定白名单），可用 `when` 谓词实现条件中断。

#### 直觉建立（类比）

游戏存档点。你在关卡中途走到"出口"——系统自动存档（冻结状态）、把画面交还给玩家（控制权交还）；玩家决定继续（approve）、换身装备再继续（edit）、或干脆回头（reject）；选择完毕后读取存档（resume），世界从存档点继续运转。而"检查点"就是那个存档文件——没有它，你连"读档"都做不到（实测报错：`Cannot use Command(resume=...) without checkpointer`）。

> 💡 **类比的边界**：游戏存档是你和自己商量；agent 的中断是**把决定权交给流程外的第三方**（审批人、风控系统、另一个服务）——所以中断提案里要携带完整的"审判材料"（动作、参数、说明），供人看懂后用最小的成本做决定。

#### 核心原理

**① 配置三形态（对应官方 `interrupt_on` 说明）**：

```python
interrupt_on={
    "send_email": True,                                        # 全决策都允许（approve/edit/reject/respond）
    "execute_sql": {"allowed_decisions": ["approve", "reject"]},  # 只许放行或拒绝（禁止改参数）
    "read_data": False,                                        # 直通（安全操作）
}
```

`description_prefix` 定制审批说明的前缀（默认 "Tool execution requires approval"）。三形态都在实测代码中出现：白名单字典（1a/2a/2b）、直通 `False`（1b/2e）、`True` 全决策（补充 D 的配置）；2c 还验证了单决策白名单（`["respond"]`）。**配置错误会显式报错**（非空校验：`allowed_decisions` 必须是非空列表——写错 key 或给空列表都会被当场拒绝，避免"闸门静默失效"；两种错误配置的报错原文见补充 H，`True` 形态实测解析为 `['approve', 'edit', 'reject', 'respond']` 全决策）。

**② 四种决策的落地细节（逐个实测）**：

**approve → 原样执行**（1a）：工具被放行、账本记账、流程继续。这是最朴素的一种。

**reject → 错误回执 + 不执行**（2a）。给 `spam-list@corp.com` 群发邮件的请求被拒后，消息链里多了一条 `status=error` 的 ToolMessage：

```text
  reject 后工具被调用过吗: False （应为 False）
    [2] tool(status=error): User rejected the tool call for `send_email` with reason: 公司政策不允许向外部列表群发。
```

注意三点：① 拒绝**不是无声取消**——中间件合成一条错误回执，内容嵌入了我们提供的理由（"公司政策不允许向外部列表群发"）；② 这条回执进入对话，**模型据此改道**（最终回答：邮件未能发送 + 解释原因 + 给出替代建议）；③ 若省略 `message`，中间件会使用默认拒绝消息（官方说明：告诉模型"工具未执行，且除非用户明确要求否则不要重试"）——对副作用型工具，最好给一条领域化的理由，明确告诉它"放弃 / 追问 / 换个更安全的做法"。

**edit → 改参数执行，但有隐藏代价**（2b + 补充 A）。修改收件人后批准，执行的确实是改后的参数：

```text
  编辑执行账本: [('send_email', 'dave@corp.com', '修改后的主题')]
    [1] ai → 调用工具: send_email({'recipient': 'dave@corp.com', 'subject': '修改后的主题'})
    [2] tool(status=success): 邮件已发送至 dave@corp.com，主题：修改后的主题
    [3] ai → 调用工具: send_email({'recipient': 'charlie@corp.com', 'subject': '草稿'})
  ⚠️ 出现第 2 次中断！动作: [('send_email', {'recipient': 'charlie@corp.com', 'subject': '草稿'})]
```

读法：消息 [1] 显示 AI 消息里的工具调用**已被改写为编辑后的参数**；[2] 工具按新参数执行成功；但紧接着 [3]——**模型重新发起了原始请求**（发给 charlie），触发了第二次中断。这不是 bug，是官方警告的现场复现：*"编辑工具参数时要保守修改。对原始参数的重大修改可能让模型重新评估它的方案，进而导致工具被执行多次或采取预期外的行动。"* 根因很直觉：模型看到"结果发给了 dave"，而用户要求的是 charlie——它认为任务没完成，于是补发。**教训：edit 适合"微调"（改个收件人后缀、修个笔误、调个数量），不适合"改需求"**；改了之后要预判模型会不会再次尝试，必要时用第二次拒绝或明确消息收尾（本课实测用"以刚才的发送为准，不需要重发"拒绝第二次，模型最终如实总结了两者的差异）。

**respond → 人工代答，工具不执行**（2c + 补充 B）。`ask_user` 的"真实实现"就是人的回答——三轮回合（订机票场景）：

```text
  第 3 轮问题（ask_user）： {'question': '信息够了大半，但有一件事我必须先说清楚，免得你误会：\n\n**我没有订票能力，也没有实时航班/价格数据。**
  → respond 代答：不需要其他服务，请给出订票方案概要即可。
  ask_user 真实实现被调用吗: False
    [6] tool(status=success): 不需要其他服务，请给出订票方案概要即可。
    [7] ai: 下面是可直接执行的**京沪往返经济舱订票方案概要**。请先看开头两句的限制说明。
```

三个要点：① 人工回答以 `status=success` 的**合成 ToolMessage** 返回——对模型而言这就是工具的成功结果；② `ask_user` 的真实实现**从未被执行**（账本确认）；③ 可以**多轮问答**（本课 3 轮），直到信息足够、模型给出最终方案。官方红线要背下来：**不要用 `respond` 拒绝副作用型工具**——它的消息会被当作"工具成功完成"，等于告诉模型"事情已经办了"。

**③ 批量决策：一次中断里的多个动作，决策与动作顺序对齐**（补充 C）。让模型并行发起两个邮件调用，中断提案里两个动作同台：

```text
  中断中的动作顺序: [('send_email', 'alice@corp.com'), ('send_email', 'bob@corp.com')]
  批量决策（按动作顺序）: ['approve', 'reject']
  执行账本: [('send_email', 'alice@corp.com', '公告')]
  最终回答: 两封邮件已在同一次响应中并行发出，结果如下： - ✅ **alice@corp.com** — 主题「公告」发送成功。 - ❌ **bob@corp.com** — 未发送。工具返回原因：*bob 未订阅公告，本次不发。*
```

一个 approve、一个 reject——两条邮件走了两条路，模型如实汇总了两种结果。规则（官方）：**决策数量必须等于动作数量，顺序必须与动作出现顺序一致**；给错了会报错（实测 2h）：

```text
  报错原文: Number of human decisions (2) does not match number of hanging tool calls (1).
```

顺带一个有趣的观察（主跑 2d）：模型**并不总是并行发起**动作——那次"先删记录再发邮件"的请求里，它先只发了删除动作（一波一个动作，每波独立审批）；被拒绝后它甚至主动判断"清理没发生，此时发'清理完成'邮件会传递错误信息，先暂停"——**拒绝让模型重新评估了整个计划**，这正是 HITL 想要的效果。

**④ 条件中断：`when` 谓词让审批"看参数办事"**（2e）。给内部域名开绿灯（谓词返回 False 时直通）：

```text
  是否被中断: False （应为 False——when 返回 False 直通）
  执行账本: [('send_email', 'teammate@internal.com', '内部同步')]
```

规则：谓词收到 `ToolCallRequest`，返回 `True` 就停、`False` 就放行；未配置 `when` 的工具默认都停（1a 的 alice@corp.com 外部地址停了，2e 的 @internal.com 过了——同一工具两种命运）。官方提示：谓词为 False 的调用**不会进入中断批次**——审批人只看到真正需要决策的动作（不打扰是设计目标）。

**⑤ 返回形态与恢复：v1 / v2 两副面孔 + 检查点硬要求**。默认（v1）返回 dict，中断在 `__interrupt__`（list）；`version="v2"` 返回 `GraphOutput`，用 `.interrupts`（tuple）与 `.value`（状态）：

```text
  【v2】返回类型: GraphOutput | .interrupts 数量: 1
  【v2】.value 的 keys: ['messages']
```

（提示：v2 下若仍用 `result["messages"]` 取值会触发弃用警告——用 `.value["messages"]`。）**检查点是恢复的前提**（补充 D 实测）：

```text
  是否含 __interrupt__: True
  工具执行过吗: False
  恢复调用报错类型: RuntimeError
  恢复调用报错原文: Cannot use Command(resume=...) without checkpointer
```

注意这个行为很"坑"：**没有 checkpointer 时，中断照样返回**（你能看到提案），但一旦想恢复——直接 RuntimeError。属于"看起来能用、实际上不能用"的典型，务必在创建 agent 时就挂上检查点（测试用 `InMemorySaver`，生产用 `AsyncPostgresSaver` / `MongoDBSaver` 等持久化实现——官方建议）。

**⑥ 与流式输出的配合**（2g）。审批和流式并不冲突：`stream_events` 先流出模型的前置说明文字，到审批点停下（`stream.interrupted` 变 True，中断详情在 `stream.interrupts`），决策后**继续流**：

```text
  中断前累计文本: 我打算向 eve@corp.com 发送主题为“流式测试”的邮件。
  stream.interrupted: True
  恢复后 stream.interrupted: False
```

**⑦ 执行生命周期（官方五步 + 实测对应）**：① 模型生成响应 → ② 中间件检查其中的工具调用 → ③ 需要人工的动作被打包成 `HITLRequest`（action_requests + review_configs）并调用 `interrupt` → ④ 等待人类决策 → ⑤ 根据决策执行/改写/回绝，合成 ToolMessage，恢复执行。映射到课 8 的钩子系统：这一切发生在 **`after_model` 钩子**里（模型已出结果、工具未执行的那个缝）。

#### 示例演示

见上文实测：reject（2a 段）、edit 与二次中断（2b/A 段）、respond 多轮（2c/B 段）、批量决策（C 段）、条件中断（2e 段）、v1/v2 与检查点（2f/D 段）、流式（2g 段）、错误复现（2h 段），来源脚本 `playground/lesson-10-hitl-lab.py` 与 `playground/lesson-10-hitl-lab-fix.py`。

#### 常见误区

1. **以为 edit 可以随便改**：重大修改会让模型重评估方案——实测触发二次中断（A 段），官方警告原文可查。
2. **以为 `respond` 能当拒绝用**：它返回的是 `status=success`——等于骗模型"事情办好了"，只能用于"提问型"工具。
3. **以为决策顺序随意**：必须与动作顺序一一对应；数量不匹配直接 ValueError（2h）。
4. **以为没有 checkpointer 也能恢复**：中断照样返回，恢复直接报错（D 段）——测试环境也要 `InMemorySaver`。
5. **以为审批会挡住所有调用**：`False` 直通 + `when` 谓词让大部分调用根本不停（1b/2e）——闸门要精准，不要到处都是。

#### 一句话记住

> 中断 = 存档暂停 + 人工决策 + 读档继续；四种决策按顺序对齐，edit 要保守、respond 只代答、没有检查点就没有恢复。

#### 🗣️ 行话对照

- **interrupt / Command(resume=...)**：冻结与恢复的一对 API——在哪遇到：`langgraph.types`
- **InterruptOnConfig / when 谓词**：按工具（与参数）配置闸门——在哪遇到：`HumanInTheLoopMiddleware`
- **HITLRequest / HITLResponse**：提案与决策载荷——在哪遇到：`__interrupt__` / `Command(resume=...)`
- **GraphOutput（v2）**：`.value` 取状态、`.interrupts` 取中断——在哪遇到：`version="v2"`
- **checkpointer**：中断的"存档文件"——在哪遇到：`InMemorySaver` / `AsyncPostgresSaver`
- **stream.interrupted**：流式下的暂停检测——在哪遇到：`stream_events(version="v3")`

### 知识点 3：护栏体系

> 🧭 第 3/3 步｜承接：执行权管住了——信息流还没管 → 本步：内置 PII 四策略、自定义 before/after 护栏、两条技术路线

#### 一句话定义

护栏（guardrails）= **在关键点位验证与过滤内容的安全网**——官方定位是"在 agent 执行的关键点验证和过滤内容，可以检测敏感信息、执行内容策略、校验输出、阻止不安全行为"。实现载体是中间件：内置护栏（PII 检测、HITL）开箱可用，自定义护栏（`before_agent` / `after_agent` 钩子）按业务规则拦截。技术上有两条路线：**确定性规则**（正则、关键词、显式检查——快、稳、便宜）与**模型审查**（LLM/分类器——能懂语义、但慢且贵）。

#### 直觉建立（类比）

机场安检。进门先过一次安检门（**输入检查**：用户消息里的东西要在进模型之前处理）；登机前再核一遍证件与随身物品（**输出检查**：模型要说出去的话也要过滤）；危险品直接拦下不让进（**block**）；敏感物品做模糊处理再放行（**redact / mask**）。安检规则有硬性的（液体不能超 100ml——确定性规则）也有需要判断的（行为可疑——人工/模型研判）。

> 💡 **类比的边界**：机场安检是"人过机器"；护栏是"内容过代码"——而且它不只是"拦"，还能**改写**：把邮箱换成占位符、把手机号换成掩码、把违规输出替换成固定话术，让流程继续走而不是一刀切失败。

#### 核心原理

**① 官方用例清单（护栏要防的五件事）**：防止 PII 泄漏 / 检测与拦截提示词注入 / 阻断不当或有害内容 / 执行业务规则与合规要求 / 校验输出质量与准确性。本课实测覆盖其中的"PII 防护"与"内容拦截"两个主战场。

**② 内置护栏 A：PII 检测（四策略 × 五类型 × 三点位）**。策略表（官方）：

| 策略 | 处理方式 | 实测输出示例 |
|------|---------|-------------|
| `redact` | 替换为 `[REDACTED_{类型}]` 占位符 | `[REDACTED_EMAIL]` |
| `mask` | 部分遮挡（保留尾部） | `****-****-****-5100` |
| `hash` | 确定性哈希 | `<ip_hash:2a39f1ee>` |
| `block` | 检测到即抛异常 | `PIIDetectionError` |

五种内建类型：`email` / `credit_card`（带 Luhn 校验）/ `ip` / `mac_address` / `url`，也可用 `detector` 自定义（正则字符串 / 编译后的正则 / 函数三种写法——本课用正则字符串实测）。三个点位：`apply_to_input`（默认开，查用户消息）/ `apply_to_output`（默认关，查 AI 消息）/ `apply_to_tool_results`（默认关，查工具结果）。

实测（3a + 回显验证 E2）——同一段输入，三方对照：

```text
  原始输入: 我的邮箱是 john.doe@example.com，卡号 5105-1051-0510-5100，服务器 IP 是 192.168.1.100。
  状态 user 消息: 我的邮箱是 [REDACTED_EMAIL]，卡号 ****-****-****-5100，服务器 IP 是 <ip_hash:2a39f1ee>。
  模型回显输出: 我的邮箱是 [REDACTED_EMAIL]，卡号 ****-****-****-5100，服务器 IP 是 <ip_hash:2a39f1ee>。
```

三个结论：① 三种策略的**实际格式**一目了然（占位符/掩码/哈希）；② 脱敏结果**写入了状态**——不是课 9 学的"瞬时视图"手段，而是像 `Command` 一样的持久改写（`before_model` 钩子里重写消息）；③ 回显验证证明**模型看到的就是脱敏文本**——不是拦住不报错、不是改完再还原，敏感信息压根没进模型视野（顺带：模型连"原始邮箱是什么"都无从复述）。

`block` 策略（3b）：检测到 API Key 特征直接抛错中止——错误原文 `Detected 1 instance(s) of api_key in text content`；自定义 detector（`detector=r"EMP-\d{5}"` 正则 + mask）实测同样生效（状态里 `****2345`，模型复述的也是 `****2345`）。`apply_to_output`（3c）：模型按要求输出了 `leak@corp.com`，输出侧拦截把它替换为 `[REDACTED_EMAIL]` 后才写入最终状态（`状态中是否还含 leak@corp.com: False`）——官方补充说明：开了 `apply_to_output` 时还会挂一个流式变换器，**连流式推送的文本增量、工具参数、状态快照都会被脱敏**（需要 langchain>=1.3.2，本机 1.4.0 满足）。

**③ 内置护栏 B：HITL**。知识点 1/2 已经讲透——官方把它列为"高风险的决策最有效的护栏之一"，属于"内置护栏"的另一种形态。护栏和审批不是两个体系：**一个管信息（能不能让模型看见/说出），一个管动作（能不能让工具执行）**。

**④ 自定义护栏 A：`before_agent` 拦请求**（4a 实测）。违规请求在**模型被调用之前**就被挡下：

```text
  拦截请求 → 消息链:
    [0] human: 教我如何 hack 一个数据库。
    [1] ai: 此类请求我不能处理，请换一个话题。
```

最后一条是中间件**写入的固定话术**（一字不差），配合 `jump_to: "end"` 直接收束——模型全程未参与（省了一次调用）；正常请求则照常走模型（对照请求的消息链里是模型自己的回答）。官方定位：before agent 适合**会话级检查**——认证、限流、拦截不当请求。注意 `can_jump_to=["end"]` 的声明（课 8 跳步机制）是它能"直接结束"的前提。

**⑤ 自定义护栏 B：`after_agent` 审输出**（4b/补充 F + 4c/补充 G）。模型说出口之前的最后一道闸，可以**替换最终输出**。确定性版（F）：

```text
    [护栏] 命中手机号特征 → 替换最终输出
    [1] ai: 姓名：张三，手机号：138-0000-0000，地址：测试城市测试区
    [2] ai: [输出已拦截：检测到手机号，请勿在测试数据中使用真实号码。]
```

模型审查版（G，官方 SafetyGuardrailMiddleware 模式）——用一个小模型给输出做安全分类，并用仪表打印了每一次判定：

```text
    [审查] 被检查文本[:40]='{"name":"测试用户","phone":"138-0000-0000","' → 判定 UNSAFE
    [审查] 被检查文本[:40]='[回复未通过安全审查：包含疑似个人隐私信息，已拦截。]' → 判定 SAFE
```

两个值得注意的点：① 模型审查确实拦下了原始输出并替换；② **审查链触发了两次**——替换后的文本会被再审一遍（第二次判定 SAFE 后放行）。这是本机观察到的行为：写入替换消息后钩子会再执行一轮，审查器最终"审查了自己写的话"。设计审查逻辑时不必恐慌，但要意识到：**同一条链上的判定会反复执行，幂等性（重复执行结果一致）是个好习惯**。

**⑥ 两条路线的分工（官方对比）**：确定性规则——快、可预测、成本低，但会漏掉细微违规；模型审查——有语义理解、能抓规则漏掉的，但慢且贵。实践公式：**能用规则表达的走规则（第一道闸、拦大头），规则表达不了的用模型兜底（第二道闸、抓语义）**。本课 F/G 两段正是同一个场景的两种实现——输出里有没有 PII，正则能查（F），"这段话像不像在泄露隐私"则要模型判断（G）。

**⑦ 组合与顺序**。官方给出多层堆叠的范式（中间件数组按顺序执行，逐层防护：确定性输入过滤 → PII → HITL → 模型审查）；顺序规则沿用课 8 的排序知识——**先便宜的先跑、先确定的先跑**，把贵的模型审查放在最后。

#### 示例演示

见上文实测：PII 三策略与回显（3a/E2 段）、block 与自定义 detector（3b 段）、输出侧脱敏（3c 段）、before_agent 拦截（4a 段）、after_agent 确定性（F 段）与模型审查（G 段），来源脚本 `playground/lesson-10-hitl-lab.py` / `lesson-10-hitl-lab-fix.py` / `lc-l10-echo.py`。

#### 常见误区

1. **以为护栏只有 PII 一种**：护栏是体系——内置（PII/HITL）+ 自定义（before/after）、两条路线、三个点位。
2. **以为 PII 脱敏是"瞬时的"**：实测写入状态（持久改写）——模型看不到原文，后续轮次也看不到。
3. **以为 `block` 只是"过滤掉"**：它是**抛异常中止**（`PIIDetectionError`）——适合"绝对不允许出现"的场景，普通场景用 redact/mask 让流程继续走。
4. **以为 after_agent 只能看看**：它可以替换最终输出——是"最后一道闸"不是"观察哨"。
5. **以为规则过时就该全上模型**：官方两种路线并列，各有所长——规则先行、模型兜底才是工程解。
6. **以为模型审查跑一次就完**：实测触发两轮（对替换文本再审）——设计时要考虑重复执行。

#### 一句话记住

> 护栏 = 安检：进模型前查输入（redact/mask/hash/block），出模型前查输出，动作执行前等审批（HITL）；规则先行、模型兜底，点位齐全才算体系。

#### 🗣️ 行话对照

- **PIIMiddleware / PII 四策略**：内置脱敏件——在哪遇到：`langchain.agents.middleware`
- **apply_to_input / output / tool_results**：三个检查点位——在哪遇到：`PIIMiddleware` 参数
- **detector**：自定义检测规则（正则/函数）——在哪遇到：`PIIMiddleware`
- **PIIDetectionError**：block 策略抛出的异常——在哪遇到：`langchain.agents.middleware`
- **before_agent / after_agent 护栏**：请求与输出两道闸——在哪遇到：`@before_agent` / `@after_agent` 装饰器
- **deterministic vs model-based**：护栏的两条技术路线——在哪遇到：官方 guardrails 页

## 第四幕：实操验证

回到第一幕：三类事故，逐一有了着落。以下覆盖 16 个主实验 + 7 项修正补跑 + 1 项回显验证，全部本机跑通（脚本：`playground/lesson-10-hitl-lab.py`、`lesson-10-hitl-lab-fix.py`；证据合并文件 `lc-l10-lab-output.txt`）：

1. **中断提案与冻结（1a）**：HITLRequest 全貌（动作/参数/说明/可选项），审批前工具未执行，approve 后执行。
2. **对照：不设闸门直通（1b）**：read_inbox 从未中断——闸门按动作配置。
3. **reject（2a）**：status=error 回执嵌入自定义理由，工具不执行，模型据此改道。
4. **edit 与二次中断（2b/A）**：改后参数被执行 + 模型重发原始请求触发第二次中断——官方"编辑要保守"警告的实测复现。
5. **respond（2c/B）**：三轮问答、真实实现从未执行、合成 status=success 回执、最终给出完整方案。
6. **批量决策（C）**：并行双调用一次中断，approve/reject 按顺序对齐，一放一拒各自落地。
7. **条件中断（2e）**：when 谓词放行内部域名，不打扰审批人。
8. **返回形态与检查点（2f/D）**：v1 dict（`__interrupt__`）vs v2 GraphOutput（`.interrupts`/`.value`）；无 checkpointer 恢复报 RuntimeError。
9. **流式配合（2g）**：中断前文本流出、`stream.interrupted` 检测、恢复后继续流。
10. **决策数量不匹配（2h）**：ValueError 错误原文复现。
11. **PII 输入三策略（3a/E2）**：redact/mask/hash 三方对照 + 回显验证（模型看到脱敏文本）。
12. **PII block 与自定义 detector（3b）**：PIIDetectionError + 自定义正则掩码（`****2345`）。
13. **PII 输出侧（3c）**：模型输出被脱敏后写入状态。
14. **before_agent 拦截（4a）**：违规请求模型未参与即被挡下；正常请求放行。
15. **after_agent 确定性审查（F）**：命中手机号 → 替换最终输出。
16. **after_agent 模型审查（G）**：UNSAFE 拦截 → 替换 → 再审 SAFE 放行（两轮判定实测）。

> ✅ **回扣场景**："不可逆动作裸奔"（1a 冻结 + 四种决策）；"不该说的说了"（3a/E2/3c 脱敏进不去出不来）；"该停的没停"（4a/F：请求与输出两道闸）。**HITL 管动作（让不让做）、护栏管信息（能不能见/说）——两条线合起来才是"可控"。**
>
> ⚠️ 数值说明：以上为 2026-09-15 本机实测；模型回答措辞受采样影响（机制性结论——冻结与否、status 值、账本记录、异常类型、判定结果——不受措辞影响）；主跑中 7 项实验经修正补跑完善（2b/2c/2d/2f/3a/4b/4c，详见证据文件来源说明）；`respond` 的多轮问答轮次随模型行为浮动（本课为 3 轮）；生产环境请替换为持久化 checkpointer（未实测生产级实现）。

> 📍 **全局定位**：本课是阶段 3 可控性主线的关键一课，把"信任边界"这块拼图补上：

## 🐞 常见误区

1. **以为审批只有"同意/拒绝"**：四种决策——approve / edit / reject / respond，各有分工与红线（respond 不能当拒绝用）。
2. **以为 edit 是安全的微调**：微调可以，大改会让模型重评估方案——实测二次中断。
3. **以为中断不需要检查点**：没有 checkpointer，中断照返回、恢复直接报错——"看起来能用"的坑。
4. **以为 PII 脱敏后原文还能找回来**：脱敏写入状态，模型全程未见原文；但注意 block 是抛错中止（要评估业务容忍度）。
5. **以为护栏都要用模型**：确定性规则更快更稳，官方建议两者组合——规则拦大头、模型抓语义。
6. **以为审批和护栏是两回事**：都是护栏体系的成员——一个管动作、一个管信息。

### ⏳ 与过时说法对照（写前核对 + 实测发现的差异）

| 旧说法（网上教程 / 直觉） | 现状（官方文档 + 本课实测） | 依据 |
|---|---|---|
| "审批就是同意或拒绝两种按钮" | 四种决策：approve / edit / reject / respond（respond 用于代答型工具） | 官方表 + 2c |
| "改了参数直接执行就行"（直觉） | 重大修改可能引发模型重发原始请求——实测第二次中断 | A |
| "respond 可以用来拒绝"（误用） | 不能——它返回 status=success，等于骗模型"已办成" | 官方 + 2c |
| "没有 checkpointer 也能中断恢复"（直觉） | 中断照返回，但 `Command(resume=...)` 直接 RuntimeError | D |
| "护栏 = PII 脱敏" | 护栏是体系：内置（PII/HITL）+ 自定义（before/after）+ 两条路线 | 全课 |
| "PII 脱敏像课 9 那样是瞬时视图"（知识迁移误用） | 实测写入状态（持久改写）；且 apply_to_output 时连流式增量都脱敏 | 3a/E2/3c |
| "after_agent 只能观察" | 可替换最终输出（本课两种实现均实测） | F/G |
| "模型审查跑一轮就结束"（直觉） | 实测触发两轮（对替换文本再审） | G |
| "所有动作都该挂审批"（过度设计） | 按风险分级 + when 条件放行——不打扰是设计目标 | 1b/2e |

## 课后小测

**Q1**：关于四种审批决策，说法正确的是？
- A. `edit` 修改参数没有副作用，随便改都行
- B. `reject` 是无声取消，模型不会收到任何消息
- C. `respond` 返回 `status=success` 的合成消息，只适合"提问型"工具，不能用来拒绝副作用工具
- D. `approve` 后工具仍会再次请求审批

<details><summary>答案与解析</summary>

**答案：C**。A 错——实测重大修改引发模型重发原始请求（补充 A）；B 错——实测合成 status=error 回执并嵌入理由（2a）；D 错——approve 后工具直接执行（1a 账本记录）。

</details>

**Q2**：关于中断机制的工程细节，说法正确的是？
- A. 没有 checkpointer 也能完整地中断与恢复
- B. 批量决策的决策顺序可以和动作顺序不一致
- C. `when` 谓词返回 False 的调用不会进入中断批次（直通执行）
- D. v2 返回形态是 dict，中断在 `__interrupt__` 键里

<details><summary>答案与解析</summary>

**答案：C**。A 错——无 checkpointer 时恢复报 `Cannot use Command(resume=...) without checkpointer`（补充 D）；B 错——必须顺序对齐，数量不匹配报 ValueError（2h）；D 错——v1 是 dict，v2 是 GraphOutput（`.interrupts`/`.value`）（2f）。

</details>

**Q3**：关于护栏体系，说法正确的是？
- A. PII 脱敏只影响当次模型调用，状态里保留原文
- B. `block` 策略是"过滤掉敏感内容后继续"，不会中断流程
- C. 自定义护栏 `before_agent` 可以在模型被调用之前拦下违规请求并直接结束
- D. 模型审查（model-based）总是优于确定性规则，应该尽量都用模型

<details><summary>答案与解析</summary>

**答案：C**。A 错——脱敏写入状态（持久），模型全程未见原文（3a/E2）；B 错——block 抛 `PIIDetectionError` 中止（3b）；D 错——官方定位两条路线互补：确定性快而稳，模型慢而贵，规则先行、模型兜底（官方 + F/G）。

</details>
