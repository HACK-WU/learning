## 🎯 本课目标

- 理解上下文工程的核心命题：不是"塞得越多越好"，而是"在合适的时机给模型合适的信息"

## 第一幕：起源与场景引入

> 🏛️ **起源**：context engineering（上下文工程）这个词随 LLM 应用实践而流行——社区先有 prompt engineering（怎么写提示词），随后发现：**模型失败的主因往往不是"提示词写得不好"，而是"该给的信息没给、不该给的塞了一堆"**。官方文档把这件事定性为："上下文工程 = 提供正确的信息和工具、以正确的形式，让 LLM 能完成任务——**这是 AI 工程师的第一要务**"。LangChain 1.x 把它落成可操作的三层（模型/工具/生命周期上下文）+ 中间件执行机制（核对于 2026-09）。

客服助手第八次进化。它有了循环（课 5）、流式（课 6）、记忆（课 7）、中间件（课 8）——现在你负责的是整个系统里最容易出问题的一环：**每次模型调用，到底该让它"看到"什么**。

上线第一个月，事故都出在这上面。**资料塞太满**：为了"稳妥"，把产品手册全文塞进 system prompt——账单翻了几倍，模型还经常抓住无关条目答非所问。**"我明明放进去了，怎么没记住"**：你在中间件里拼了一条重要信息进消息列表，下一轮它却像失忆一样。**工具窗口成了杂货铺**：一个只会查看数据的用户，界面里却能"看见"删除按钮（工具清单里躺着 delete_data）。**历史越来越长**：第 30 轮对话时，光上下文就有几万 token，而其中 90% 是早就过期的中间过程。

> 🎬 **场景**：这四类事故指向同一个盲区——**"模型每次调用看到的全部信息"是一个需要设计、可以设计、也必须设计的对象**。它由什么组成？从哪取材？什么时候给？给完算不算数？把这些搞明白，事故就会变成工程。

> 📌 **一句话本质**：上下文工程 = **在合适的时机，把合适的信息和工具、以合适的形式提供给模型**（官方定义：*providing the right information and tools in the right format so the LLM can accomplish a task*）。它的操作对象是"每次模型调用看到的全部信息"（五件套：提示词/消息/工具/模型/格式），信息来源有三个数据源（runtime context / state / store），改动方式分两条路：**瞬时（transient，改视图）与持久（persistent，改账本）**（核对于 2026-09）。
>
> ⚖️ **处境对照**：不这么设计——资料塞满（实测：多 1746 字背景 = 每次多付 964 tokens）、瞬时的改动误当持久（下一轮失忆）、权限之外的工具"在场"（模型可能被诱导调用）、历史无限膨胀（摘要/清理缺位）。这么设计——动态提示词按身份与状态收敛回答边界，消息注入分清"看一眼"与"记下来"，工具按权限过滤（viewer 只见 `read_data`），历史超限时被摘要压缩成一页纸——每一处都有清晰语义。

## 第二幕：认知冲突

到这里你可能已经有一个自然想法：**"那我全量携带不就行了？记忆全带上、工具全给上、历史全保留——宁可多不可漏。"**

两个问题会立刻打脸。

**问题一：塞不下，也塞不起。** 上下文窗口是稀缺资源——不仅是硬上限，更是成本与注意力的双重约束。实测：同一问题，只把 system prompt 从 10 字换成 1755 字，每次调用的 input_tokens 从 70 涨到 1034（多 964 tokens），而"每次调用都要重复付这笔账"；更要命的是无关内容会稀释模型对关键信息的注意力——塞得越满，答偏得越频繁。

**问题二（更隐蔽）："改了视图"不等于"记住了"。** 你在中间件里把一条信息拼进了消息列表——它到底算不算数？下一轮还在吗？换个说法：**哪些改动是"这次给它看一眼"（瞬时），哪些改动是"写进账本、以后一直算数"（持久）？** 这个区分不搞清，你会同时遇到两种方向相反的事故："明明注入过，模型却忘了"和"以为只是临时提示，结果永久收紧了后续对话"。

> ❓ **问题**：信息从哪来（数据源）？在什么时候、以什么形式给模型（组装）？改动落地成"看一眼"还是"记下来"（去留）？

三个追问把这件事拆开：

- 追问一：**上下文到底由什么组成、为什么它是稀缺资源？**——官方把模型调用看到的一切拆成"模型上下文"（指令、消息历史、工具、响应格式），并明确定义三类上下文（model / tool / life-cycle）。先看清"组装现场"，再谈优化。
- 追问二：**五件套怎么动态化？工具怎么读、怎么写？**——提示词可按状态与身份现场生成；消息可"瞬时看一眼"或"持久写账本"；工具可按权限过滤、结果可清理。
- 追问三：**步骤之间的"横切处理"（摘要、审计）如何改变上下文？**——它们通常**持久**改写：摘要把历史揉成一页纸、永久替换原文；审计钩子把用量沉淀进 store。

由此得到本课的第一个关键认知：**处理好上下文的每一步，都要先回答"这是改视图，还是改账本？"**——改视图（瞬时）只影响这一次调用；改账本（持久）从此刻进入历史，未来每一轮都按它办事。本课所有实验都会围绕这条分水岭展开。

### 知识点 1：上下文工程是什么

> 🧭 第 1/3 步｜承接：课 7 存记忆、课 8 装钩子——现在问一个更上位的问题：模型每次调用到底"看到"什么？ → 本步：给上下文下定义、立稀缺性、画三类

#### 一句话定义

上下文工程 = **在合适的时机，把合适的信息和工具、以合适的形式提供给模型**（官方定义：providing the right information and tools in the right format so the LLM can accomplish a task）；它的操作对象是"每次模型调用看到的全部信息"——系统提示词、消息历史、工具、模型、响应格式——这些内容从三个数据源（runtime context / state / store）取材组装。

#### 直觉建立（类比）

给外聘专家做简报。公司资料成千上万，但你不会把档案室搬进会议室——你准备一页简报：专家的角色设定（提示词）、必要背景（消息）、可动用的资源清单（工具），而且随会议推进不断更新。简报做得好，决策就准；简报缺关键信息或塞满无关材料，专家就会答偏或走神。**上下文工程师 = 那个准备简报的人**。

> 💡 **类比的边界**：简报是静态的，模型的"桌面"是动态的——每次调用（甚至循环里的每一圈）都重新组装一遍；而且桌面上的东西分两种去留方式：**看完就撤（瞬时）vs 归档留痕（持久）**——这是本课最重要的分水岭。

#### 核心原理

**① 先立根因**（官方论述整理）："当 agent 失败时，通常是内部那次 LLM 调用采取了错误行动；而 LLM 失败只有两个原因——① 底层模型能力不够；② '对的信息'没有传给 LLM。**更多时候是第二个**。"官方还给了一句定性："缺乏'对的信息'是更可靠 agent 的头号阻塞项"。

**② 上下文是稀缺资源（实测数字）**——同一问题"1+1 等于几"，只换 system prompt（实测 1b）：

```text
  短提示词（10 字）: input_tokens = 70, 总 tokens = 115
  长提示词（共 1755 字）: input_tokens = 1034, 总 tokens = 1091
  差额: 多携带 964 tokens（每次调用都要重复付这笔账）
```

一句话总结：**system prompt 里的每一行字，都会在每一次模型调用中反复付费**——而且还不只是钱：无关内容会稀释模型对关键信息的注意力。课 2 学的"token 预算"概念，在这里升级为"每一次组装都要过的预算审查"。

**③ 三类上下文**（官方分类表）：

| 上下文类型 | 你控制什么 | 瞬时 or 持久 |
|-----------|-----------|-------------|
| 模型上下文 Model Context | 模型调用看到什么（指令、消息历史、工具、响应格式） | 瞬时 Transient |
| 工具上下文 Tool Context | 工具能读什么、能写什么（对 state / store / runtime 的读写） | 持久 Persistent |
| 生命周期上下文 Life-cycle Context | 步骤之间发生什么（摘要、护栏、日志等） | 持久 Persistent |

两个术语先记住：**瞬时（transient）= 只影响这一次调用的"视图"**；**持久（persistent）= 写进状态、后续每轮都算数**。

**④ 三个数据源**（官方数据源表）：

| 数据源 | 别名 | 作用域 | 例子 |
|--------|------|--------|------|
| Runtime Context | 静态配置 | 会话级 | 用户 ID、API key、数据库连接、权限、环境设置 |
| State | 短期记忆 | 会话级 | 当前消息、上传的文件、认证状态、工具结果 |
| Store | 长期记忆 | 跨会话 | 用户偏好、提取的洞察、历史数据 |

（三个数据源正是课 7 已跑通的对象——本课把它们组织进"取材 → 组装"的框架。）

**⑤ 先看一眼"组装现场"**——给模型装个"行车记录仪"，打印一次调用实际收到的全部要素（实测 1a）：

```text
  [组装视图] system prompt: 你是一个天气助手，回答保持简短。
  [组装视图] 消息 1 条: ['human']
  [组装视图] 工具 1 个: ['get_weather']
  [组装视图] 模型: qwen3.8-flash
```

一轮工具调用之后（循环第二圈）再打印：`消息 3 条: ['human', 'ai', 'tool']`——**上下文不是一份静态文档，而是随循环滚动的活件**。这就是本课要"治"的对象。

见上文实测：组装视图（1a 段）、成本对照（1b 段），来源脚本 `playground/lesson-09-context-lab.py`。

#### 常见误区

1. **以为上下文 = system prompt**：提示词只是五件套之一——消息、工具、模型、响应格式同样进入"模型看到什么"。
2. **以为塞得越多越好**：实测多 1746 字背景 = 每次 +964 tokens，且注意力被稀释。
3. **以为上下文工程是某个组件**：它是一层设计策略（给什么、何时给、瞬时还是持久）——课 8 的中间件是执行机制，课 7 的状态/store 是储库，本课是把它们组织起来的"调度学"。

#### 一句话记住

> 上下文工程不是"写提示词"，而是"在合适的时机，给模型合适的信息"——信息分三类、来源分三处、去留分瞬时与持久。

#### 🗣️ 行话对照

- **context engineering（上下文工程）**：为模型每次调用组织"对的信息"——在哪遇到：官方 agents 页
- **model context / tool context / life-cycle context**：三类上下文——在哪遇到：context-engineering 页
- **transient / persistent**：瞬时（单次调用视图）/ 持久（写入状态）——在哪遇到：本课贯穿
- **runtime context / state / store**：三个数据源——在哪遇到：`context=` 参数 / 状态对象 / store 对象
- **组装视图**：一次模型调用实际收到的全部要素——在哪遇到：`ModelRequest`（system_message / messages / tools / model / response_format）

### 知识点 2：模型上下文与工具上下文

> 🧭 第 2/3 步｜承接：知道"模型看到的一切"由什么组成了——现在动手改它 → 本步：五件套逐一动态化 + 工具读写管道 + 瞬时 vs 持久对照表

#### 一句话定义

模型上下文 = 每次模型调用组装给你的**五件套**（系统提示词、消息、工具、模型、响应格式），每一件都可以按 state / runtime / store 动态化；工具上下文 = 工具的**读写管道**——从三个数据源读（决定工具能干什么），往状态与 store 写（把结果带回循环）。

#### 直觉建立（类比）

模型上下文像"每次开会前摊在桌面上的材料"——开会前可以重新摆：换一份简报（动态提示词）、添一页附注（消息注入）、收起无关卷宗（工具过滤）、换一张表格模板（格式收窄）。工具上下文像会桌上的"办事窗口"——窗口收你递的材料（读参数），也能查档案柜（读 state/store），办完盖章归档（写 Command/store）。

> 💡 **类比的边界**：桌面上"添一页附注"分两种写法——贴在本次会议纪要的散页上（瞬时，开完就撤）vs 归入档案室（持久，以后每次都会调出来）——选错写法就会出现"明明给了却像没给"或"只是试放一下却永久生效"。

#### 核心原理

**① 五件套与动态化手法总表**（官方清单 + 本课实测）：

| 件 | 控制什么 | 动态化手法 | 本课实测 |
|----|---------|-----------|---------|
| System Prompt | 指令与人设 | `@dynamic_prompt` 按 state / runtime 现场生成 | 2a、2b |
| Messages | 对话历史 | `override` 注临时消息；`Command` 注持久消息 | 2c、2d |
| Tools | 可用工具集 | 按角色/状态过滤（`override(tools=...)`） | 2e |
| Model | 用哪块模型 | 按场景换模型（`override(model=...)`） | 课 5 已实测 |
| Response Format | 输出结构 | 收窄候选 schema（`override(response_format=...)`） | 2f |

**② 提示词按"谁在问、聊到哪"现场生成**——2a 实测（同一 agent，只换消息数）：

```text
  [探针] 消息 1 条 → system: 你是一个助手。
  [探针] 消息 5 条 → system: 你是一个助手。 这是长对话，请格外简洁。
```

2b 实测（同一 agent，只换运行时身份）：

```text
  [探针·admin] system: 你是一个数据管理助手。 当前用户是管理员，拥有全部操作权限。
  [探针·viewer] system: 你是一个数据管理助手。 当前用户是只读访客，只能执行读取操作，不能修改数据。
```

行为证据：同一个问题"你可以执行哪些操作"，admin 的回答是"查询、新增、修改、删除、导入导出、备份恢复、权限管理……"，viewer 的回答是"可以查询、浏览和解释数据，但不能新增、修改或删除任何数据"——**同一个模型、同一个问题，因为提示词里带了身份，答案自动收敛到权限边界内**。这就是 `@dynamic_prompt` 的价值：把"按人、按场景定制指令"从手工活变成声明式。

**③ 消息的两种加法：瞬时（transient）与持久（persistent）**——本课核心对照实验，务必读懂这两段。

瞬时（2c）：中间件把"[档案注入] 项目代号是 LYRA-9。"拼进本次请求（`override(messages=...)`）：

```text
  回答: LYRA-9
  状态里的消息链:
    [0] human: 项目代号是什么？请直接回答。
    [1] ai: LYRA-9
  状态中包含注入标记『[档案注入]』的消息数: 0（应为 0——瞬时修改不写状态）
```

读法：模型答出了 LYRA-9（它**看到了**注入）；但状态里只有两条原始消息（注入**没有落账**）。改的是"视图"。

持久（2d）：同一个档案，改成"本轮临时注入 + `Command` 持久写入"：

```text
  [档案] 本轮临时注入给模型 + 持久写入状态留给未来轮次
  第一轮回答: LYRA-9
  第一轮后状态中包含注入标记『[档案]』的消息数: 1（应为 1——持久写入）
  状态链:
    [0] human: 项目代号是什么？请直接回答。
    [1] ai: LYRA-9
    [2] human: [档案] 项目代号是 LYRA-9。
  [档案] 已在消息中，本次不再注入
  第二轮回答（无任何注入，直接读状态）: 项目代号是 **LYRA-9**。
  第二轮后『[档案]』消息数: 1（不重复注入，仍为 1）
```

读法四件事：① 本轮靠临时注入用上（回答 LYRA-9）；② 档案**写进状态**（标记数 1）；③ 第二轮不注入任何东西，模型直接读状态照样答对；④ 中间件发现"已在消息中"便跳过注入——一个小幂等技巧，防止同一份档案反复堆积。

一个可以背下来的判据：**`override` 改视图（瞬时）；`Command` 改账本（持久）**。中间件的返回路径上，`ExtendedModelResponse(model_response=..., command=Command(...))` 就是"这次照常回、同时记一笔账"的标准姿势（课 8 的知识点在这里第一次派上大用场）。

**④ 工具按"谁能用"过滤**——2e 实测（同一批 3 个工具，按运行时角色过滤）：

```text
  [过滤·viewer] 模型可见工具: ['read_data']
  回答: 很抱歉，我无法执行这个请求，原因如下： 1. **没有删除权限**：我仅有的工具是 `read_data`（读取业务数据），并不具备任何删除数据的能力。
  [过滤·admin] 模型可见工具: ['read_data', 'write_data', 'delete_data']
```

viewer 提问"请删除所有业务数据"——模型干脆拒绝（它**没有**删除工具，也没有被"诱导"出危险动作）；admin 侧三个工具全在场。与课 8 的 `LLMToolSelectorMiddleware`（用 LLM 智能挑选）对比着记：这里按**权限事实**做确定性过滤，两者解决的是不同问题（精度优化 vs 权限控制），可叠加。

**⑤ 响应格式收窄——注意这是本版本实测踩坑点，官方示例要改造**。官方示例教"在中间件里直接 override 成新 schema"；本机实测**报错**（补充 B）：

```text
  报错类型: ValueError
  报错原文: ToolStrategy specifies tool 'Simple' which wasn't declared in the original response format when creating the agent.
```

正确姿势：**创建时用 `ToolStrategy(Simple | Detailed)` 声明全部候选，中间件只做"收窄"**（收窄到候选子集）——实测通过：

```text
  [格式] 消息 1 条 → 简单格式 Simple
  第一轮 structured_response: answer='你好！👋 有什么我可以帮你的吗？' | type: Simple
  [格式] 消息 5 条 → 详细格式 Detailed
```

（长对话侧返回 `confidence=1.0 | type: Detailed`，字段数按 schema 自动扩充。另一个环境限制：思考模式拒绝结构化输出——报错原文与处置见课 5，本实验用 `extra_body={"enable_thinking": False}` 关掉思考后通过。）

**⑥ 工具结果太长怎么办：两种清理方式都实测了**（2g）。工具返回了 1144 字的报告，直接把全文塞给模型显然浪费。

方案 A：自写瞬时截断（`wrap_model_call` 里替换工具消息内容）：

```text
  [探针] 模型侧 tool 消息: len=127 cleared=None content[:46]='【报告】这是一条很长的报告内容，包含许多细节。这是一条很长的报告内容，包含许多细节。这是一条'
  最终回答: 已阅
  状态侧 tool 消息: len=1144（全量保留）
```

方案 B：官方内置 `ContextEditingMiddleware`（配 `ClearToolUsesEdit(trigger=100, keep=0)`）：

```text
  [探针] 模型侧 tool 消息: len=9 cleared=True content[:46]='[cleared]'
  最终回答: 已阅
  状态侧 tool 消息: len=1144（内置件也是瞬时——状态保留原文）
```

两个关键认知：① **两种方案都是瞬时清理**——模型看短版（内置件替换为 `[cleared]` 占位符、并打上 `cleared=True` 标记），状态留全量原文；② 内置件的触发逻辑（补充 C 标定）：会话 total tokens 超过 `trigger` 时，把**除最近 `keep` 条之外**的工具输出替换为占位符；近似计数对中文的标定实测"1144 字 ≈ 330 tokens"（`token_count_method="approximate"` 是默认；对中文精度敏感时可换 `"model"` 精确计数或自定义 counter——官方参数说明里明确提到了 CJK（中日韩）文本这一场景）。

**⑦ 工具上下文：读写管道**（本知识点下半场）。工具不是"只收参数的哑执行器"——官方文档把它定义为**同时读写上下文的特别角色**。逐个实测：

读运行时上下文（3a）——工具拿 `runtime.context` 完成查询：

```text
    [1] ai → 调用工具: get_my_user_id({})
    [2] tool: 当前用户 ID 是 user_777
  回答: 您的用户 ID 是：**user_777**
```

读 + 写状态（3b）——`login` 工具把结果写回状态（Command），`check_auth` 读状态：

```text
    [1] ai → 调用工具: login({'password': 'correct'})
    [2] tool: 登录成功
    [3] ai → 调用工具: check_auth({})
    [4] tool: 当前登录状态：authenticated = True
  最终状态里的 authenticated = True（工具通过 Command 写入）
```

⚠️ 这里踩到一个"官方示例 vs 本版本"的坑（补充 A）：官方 context-engineering 页写 `Command(update={"authenticated": True})`（纯状态更新），本版本实测**报错**：

```text
  [失败] ValueError: Expected to have a matching ToolMessage in Command.update for tool 'login', got: []. Every tool call (LLM requesting to call a tool) in the message history MUST have a corresponding ToolMessage. You can fix it by modifying the tool to return `Command(update=[ToolMessage("Success", tool_call_id=tool_call_id), ...], ...)`.
```

修正写法：`Command(update={"messages": [ToolMessage("登录成功", tool_call_id=runtime.tool_call_id)], "authenticated": ok})`——**状态更新要搭一条 ToolMessage 一起回去**（工具调用必须在消息流里有回执）。修正后 3b 实测通过（上文输出即修正后结果）。

写 store（3c）——工具把偏好写进跨会话存储，换一个全新会话（新 thread）读回：

```text
  会话 B（thread sess-B，全新对话）：读取偏好
  回答: 已读取你的偏好「语言」：**中文**。 之后我都会用中文与你交流。
  store 直查: {'语言': '中文'}
```

同一份代码、同一把 store、只换 thread——"保存偏好"发生在会话 A，"读取偏好"发生在会话 B，跨会话读回成功。这就是"工具上下文是持久层"的含义：工具对 store 的写入会**一直算数**（课 7 的 store 语义在此升级为"工具侧的读写管道"）。

**⑧ 瞬时还是持久：一张对照表盯全场**（本课核心，全部来自本机实测）：

| 手段 | 改动落地到哪 | 未来轮次是否生效 | 实测 |
|------|-------------|----------------|------|
| `override(messages=...)` 注入 | 只进当次调用视图 | ✗ | 2c |
| `override(tools=...)` / `response_format=...` | 当次调用视图（每轮重新过滤） | ✗ | 2e、2f |
| 自写工具输出截断 | 当次调用视图 | ✗ | 2g-A |
| ContextEditing 清理 | 当次调用视图 | ✗ | 2g-B |
| `Command(update={"messages": [...]})` | 写入 state | ✓ | 2d |
| 工具 `Command` 写状态字段 | 写入 state | ✓ | 3b |
| 工具 `store.put` | 写入 store | ✓（跨会话） | 3c |

（最后一行留给知识点 3 的摘要：它也写状态——且是"替换原文"级别的改写。）

#### 常见误区

1. **以为 `override` 的改动会被记住**：实测不写状态（2c 标记数 0）——要跨轮生效，必须 `Command` 落账。
2. **以为工具只能接收模型给的参数**：还能读 runtime context、state、store 三源（3a 的 `runtime.context` 只是其中一例）。
3. **以为 `Command` 只能更新消息**：还能更新任意状态字段（`authenticated` 实测）；但注意本版本要求 update 里带对应 ToolMessage（补充 A）。
4. **以为清理工具输出会丢数据**：瞬时清理**保留原文**（状态 1144 字不变），省的是模型侧 token；真要"丢原文"的是摘要（知识点 3）。
5. **以为官方示例可以照抄**：本课复现了两处"官方写法在本版本报错"（response_format 候选声明、Command 缺 ToolMessage）——先小脚本验证再抄，是课 4 起就立下的规矩。

#### 一句话记住

> 五件套都能现场动态化；每做一处改动先问一句"改视图还是改账本"——`override` 是看一眼，`Command` / `store` 是记下来。

### 知识点 3：生命周期上下文

> 🧭 第 3/3 步｜承接：五件套与工具都管过了——还有一类"步骤之间"的事没管 → 本步：摘要的持久压缩、自定义审计钩子、最佳实践与反模式

#### 一句话定义

生命周期上下文 = 在模型调用与工具调用**之间**发生的横切处理（压缩、审计、护栏、日志），通过中间件钩子实现；与"每次调用看一眼"的瞬时手段不同，生命周期处理**持久地改写上下文**——摘要替换原文、计数写入状态、洞察沉淀进 store。

#### 直觉建立（类比）

会议之间的"休会整备"：上一场刚散、下一场未开——档案员把记录压缩成一页纪要（摘要）、秘书把用时与开销记进台账（审计）、前台按议程摆好下一场材料（下一轮组装）。休会时做的事，会影响后面**每一场**会——这正是它与"开会中途递纸条"（瞬时手段）的本质区别。

> 💡 **类比的边界**：整备动作要适度——纪要是"折叠信息"，原文细节不可逆丢失；台账是"只加不改"。两者都写进状态，但语义完全不同，别混用。

#### 核心原理

**① 钩子与时机（承接课 8）**：before/after model 之间、模型与工具之间，都是"步骤之间"。官方定位：在核心步骤**之间**拦截数据流，实现横切关注点（summarization、guardrails、logging）。手段官方列了两条路：**① Update context（改状态与 store）；② Jump in the lifecycle（跳步）**——后者课 8 已讲过（jump_to），本课聚焦前者。

**② 摘要：超限时把历史"持久"压缩**——`SummarizationMiddleware`，本机实测（4a，`trigger=("messages", 4)`、`keep=("messages", 2)`）：

```text
  第 1 轮后消息数: 2
  第 2 轮后消息数: 4
  第 3 轮后消息数: 4
  最终状态消息链:
    [0] human: Here is a summary of the conversation to date: ## SESSION INTENT 用户小明（后端工程师）正在系统学习 LangChain，当前希望获得一
    [1] ai: 短期记忆用于维持当前会话/上下文的临时状态，长期记忆则跨会话持久化保存并可被检索或更新的信息。
    [2] human: 我叫什么名字？做什么工作？请简短回答。
    [3] ai: 你叫小明，是后端工程师。
  存在摘要消息: True（应为 True——摘要持久写入状态）
  原始自我介绍消息仍在: False（应为 False——原文已被摘要替换）
```

读法三条：① 消息数涨到 5 条时被压回 4 条（摘要替换了最早的对话，留下 2 条最近的）；② 摘要以 human 消息形态**写入状态**（课 7 的观察在此归位）；③ 第三轮问"我叫什么名字"——**原始自我介绍那条消息已经不在状态里**（False），但模型照样答对"你叫小明，是后端工程师"——答案的来源正是摘要。这就是与瞬时手段的对比：**裁剪/清理是"这次少看几眼"，摘要是"把历史揉进一页纸、永久换掉原文"**。代价也要记住：原文细节不可逆丢失（课 7 的成本对比数字在此仍有参照价值：摘要的 token 账不一定更便宜，但它换来了"历史不再无限膨胀"）。

**③ 自定义生命周期钩子：把"账"沉淀到 store**（4b）——after_model 计数（多少次调用、烧多少 token），after_agent 把整场审计写入 store：

```text
  最终状态: model_calls = 2, total_input_tokens = 696
  store 中的审计记录: {'model_calls': 2, 'total_input_tokens': 696}
```

钩子 `after_model` 逐次累计（状态字段 `model_calls` / `total_input_tokens`），`after_agent` 在执行结束时一次性落进 store——这段直接对应官方最佳实践第 3 条"**监控性能：跟踪模型调用、token 用量与延迟**"。几行钩子就能让每个会话自报账目，跨会话的用量审计也有了基础（配合课 13 的可观测性主题食用更佳）。

**④ 最佳实践（官方 6 条，摘编）**：① **简单起步**——先用静态提示词与工具，有需要再加动态；② **增量测试**——一次只加一个上下文特性（出问题才可归因）；③ **监控性能**——跟踪调用 / token / 延迟（4b 给了可抄的样板）；④ **优先用内置件**（摘要、工具选择器等）；⑤ **把上下文策略写成文档**——让团队知道"什么信息、为什么进上下文"；⑥ **分清瞬时与持久**——本课的对照表就是这一条的注脚。

**⑤ 反模式（对照本课实测）**：把全量资料塞进提示词（1b：+964 tokens/次）；用瞬时手段期待跨轮效果（2c：改视图不落账）；工具输出无限增长不设清理（2g：1144 字常驻，模型侧迟早被撑爆）；摘要阈值照搬默认值不测试（本课用了小阈值以方便教学，生产要按真实 token 预算校准——`trigger` 支持按 messages 或 tokens 两种口径）。

#### 示例演示

见上文实测：摘要持久压缩（4a）、审计钩子（4b），来源脚本 `playground/lesson-09-context-lab.py`。

#### 常见误区

1. **以为摘要是"临时的"**：摘要**持久替换**原文（原文不可逆丢失）；裁剪与清理才是瞬时的——两组手段别记混。
2. **以为瞬时清理能省 state 存储**：不能——省的是模型侧 token；状态仍留全量原文（2g-B 实测）。
3. **以为生命周期钩子"只是日志"**：它可以直接改账本——压缩历史、注入信息、写 store、甚至跳步。
4. **一次加好几个上下文特性**：官方明确"一次一个"——否则出了问题是阈值问题还是注入问题，根本分不清。

#### 一句话记住

> 步骤之间的活儿要"记账"：摘要把历史折算成一页纸（持久替换），审计把用量沉淀进 store（只加不改）；动手前先分清"改视图"还是"改账本"。

- **SummarizationMiddleware / trigger / keep**：摘要中间件与阈值配置——在哪遇到：`langchain.agents.middleware`
- **transient / persistent（在生命周期语境）**：改视图 vs 改账本——在哪遇到：本课对照表

## 第四幕：实操验证

回到第一幕：上线首月四类事故，逐一有了着落。以下覆盖 15 个实验 + 3 组补充证据，全部本机跑通（脚本：`playground/lesson-09-context-lab.py`；补充证据：错误复现与聚焦测试）：

1. **组装视图（1a）**：一次调用的 system / messages / tools / model 全要素打印（含循环第二圈变化）——"上下文是活件"眼见为实。
2. **稀缺性（1b）**：短提示词 70 tokens vs 长提示词 1034（+964）；"每轮重复付费"的意识建立。
3. **动态提示词（2a/2b）**：按状态（1 条 vs 5 条消息）、按身份（admin vs viewer）现场生成——行为差异实测（权限边界自动收敛）。
4. **消息两法（2c/2d）**：瞬时注入=改视图（标记数 0）；持久注入=改账本（标记数 1，第二轮零注入照样答对）。
5. **工具过滤（2e）**：viewer 只见 `read_data`（拒绝删除请求）；admin 见 3 个——权限事实的确定性过滤。
6. **格式收窄（2f）**：Simple → Detailed 现场切换；附带两处本版本差异（候选声明、思考模式）。
7. **结果清理（2g-A/B）**：自写截断与内置 ContextEditing 均为瞬时（模型看 127 字 / `[cleared]`，状态留 1144 字）。
8. **工具读写（3a/3b/3c）**：读 runtime（user_777）；Command 写状态（authenticated=True，含 ToolMessage 修正）；store 跨会话（新线程读回"语言=中文"）。
9. **生命周期（4a/4b）**：摘要持久替换（原文 False、摘要 True、模型照答）；审计钩子（2 次调用 / 696 tokens 沉进 store）。

> ✅ **回扣场景**：四类事故——"资料塞太满"（1b 立成本意识）；"明明放进去了却没记住"（2c/2d 分清视图与账本）；"工具窗口杂货铺"（2e 按权限过滤）；"历史无限膨胀"（2g 清理 + 4a 摘要）。**上下文工程 = 把"给模型看什么"从碰运气变成有账可查的工程。**
>
> ⚠️ 数值说明：以上为 2026-09-15 本机实测；token 数值随文本差异浮动（属正常采样与分词差异）；模型回答措辞受采样影响（机制性结论——0 与 1 的标记数、False/True 判定、工具清单差异——不受措辞影响）；`approximate` 计数对中文场景存在偏差（可用 `"model"` 精确计数替代）；Deep Agents 侧文件系统等重型上下文能力属于本课范围外。

## 🐞 常见误区

1. **以为上下文 = 提示词**：五件套（提示词/消息/工具/模型/格式）都在模型视野里；工具清单与格式也是上下文。
2. **以为"塞得越多越保险"**：实测每多 1746 字背景 = 每次 +964 tokens，且稀释注意力——真正要练的是"取舍"。
3. **以为注入过的消息会一直算数**：`override` 是瞬时（2c）；要持久必须 `Command`（2d）。
4. **以为摘要等于临时裁剪**：摘要持久替换原文（4a）；裁剪/清理是瞬时（2g）——方向相反，别记混。
5. **以为官方示例都能直接抄**：本课复现两处本版本差异（response_format 候选声明、Command 缺 ToolMessage）——先验证再抄（课 4 起的规矩）。

### ⏳ 与过时说法对照（写前核对 + 实测发现的差异）

| 旧说法（网上教程 / 直觉） | 现状（官方文档 + 本课实测） | 依据 |
|---|---|---|
| "给模型的信息越多越好" | 稀缺资源：+1746 字 = 每次 +964 tokens，且注意力被稀释 | 1b |
| "改了 messages 就能一直记住" | `override` 改视图（不写状态）；持久要 `Command` | 2c、2d |
| "工具返回 `Command(update={...})` 即可写状态"（官方示例） | 本版本要求 update 中带 ToolMessage——纯状态更新报 ValueError | 补充 A、3b |
| "中间件里可随需切换 response_format 为任意 schema"（官方示例） | 必须创建时声明候选（`ToolStrategy(A｜B)`），中间件只能收窄 | 补充 B、2f |
| "ContextEditing 清理是裁剪历史、省内存" | 瞬时清理：模型看 `[cleared]`，状态保留原文（省的是模型侧 token） | 2g-B、补充 C |
| "摘要 = 临时压缩，不影响状态" | 摘要持久替换原文（原文不可逆丢失） | 4a |
| "token 计数对中文也很准" | approximate 法 1144 字 ≈ 330 tokens（偏差存在；可换 model / 自定义 counter） | 补充 C |

## 课后小测

**Q1**：关于"瞬时（transient）与持久（persistent）"，说法正确的是？
- A. 中间件里 `override(messages=...)` 注入的消息会写入状态，下一轮仍可见
- B. `Command(update={"messages": [...]})` 注入的消息只在当次调用可见
- C. `override` 改的是"本次调用视图"（不写状态）；`Command` / `store` 写的是"账本"（跨轮生效）
- D. ContextEditing 清理会把状态里的原文删掉以省存储

<details><summary>答案与解析</summary>

**答案：C**。A 错——实测标记数 0（2c）；B 错——实测写入状态、第二轮零注入仍答对（2d）；D 错——瞬时清理，状态保留 1144 字原文（2g-B）。

</details>

**Q2**：关于工具上下文（读写管道），说法正确的是？
- A. 工具只能接收模型给的参数，读不到运行时信息
- B. 工具可以读 runtime context / state / store，可通过 Command 写状态、通过 store.put 写长期记忆
- C. `Command` 更新状态字段时不需要任何消息回执
- D. 工具对 store 的写入只对当前会话有效

<details><summary>答案与解析</summary>

**答案：B**。A 错——3a 实测工具读到 `user_777`；C 错——本版本要求带 ToolMessage（补充 A）；D 错——3c 实测新会话（新 thread）读回"语言=中文"。

</details>

**Q3**：关于生命周期上下文（摘要与钩子），说法正确的是？
- A. 摘要只影响当次调用，状态里的原文保留
- B. 摘要把旧消息持久替换为一条摘要消息；原文不再保留，但模型仍能基于摘要回答
- C. 生命周期钩子只能记日志，不能写入 store
- D. 上下文特性可以一次性全部加上，效率更高

<details><summary>答案与解析</summary>

**答案：B**。A 错——摘要持久替换（4a："原始自我介绍消息仍在: False"）；C 错——4b 实测 after_agent 可写 store；D 错——官方最佳实践"一次加一个"（增量测试）。

</details>
