## 第一幕：起源与场景引入

> 🏛️ **起源**：对话记忆的工程化经历过三个阶段——早期开发者"手工拼历史"（把之前的消息塞回请求）；LangChain 0.x 时代推出一串 Memory 类（缓冲、窗口、摘要等），把常见策略做成开箱组件；1.0 大重构后这批类退出推荐路径，记忆改由底层持久化原语承担：**checkpointer（线程内短期）+ store（跨会话长期）**——与本课程"chains 被砍掉、只留 create_agent"的演化主线一脉相承。2024 年起，主流 AI 产品陆续把"跨会话记忆"做成标配功能，各家机制殊途同归：状态持久化 + 有选择的读写（核对于 2026-09）。

客服助手第六次进化。现在它能跑（课 5）、过程能看（课 6）——但你发现它有个硬伤：**每次都是"新人"**。

用户昨天来问过售后，今天再来，它问："请问您怎么称呼？"用户上周说过"我对花生过敏"，这周再点餐，它又推荐了花生酱。对话一关，全部归零——模型根本不知道"昨天"存在。

更微妙的是：就算你把上次的对话记录复制黏贴回去，聊到第 50 轮时，历史已经长到塞不进窗口——而且越来越慢、越来越贵。

> 🎬 **场景**：给 agent 装上"记忆"——短期记忆让它记得**本次会话**（线程内自动接续），长期记忆让它记得**跨会话的用户信息**（换个会话照样认得你），外加一套管理策略让历史**不失控**。

> 📌 **一句话本质**：记忆不是"把聊天记录都塞回去"——它是 harness 层的**"状态 + 持久化"工程**：短期记忆 = 线程内的状态（checkpointer 持久化），长期记忆 = 跨会话的 store（命名空间 + 键）。模型本身始终是无状态的（核对于 2026-09）。
>
> ⚖️ **处境对照**：不这么写——用户每天重新自我介绍（本课实测：无 checkpointer 的 agent 面对老用户如实回答"我不知道你的名字哦"），历史无限增长拖慢且费钱。这么写——同线程自动接续（实测：第二轮直接答出"你叫小明，最喜欢蓝色"），跨会话召回用户信息（实测：新线程里照样答出"你叫小明"），且历史规模可控（实测：消息数封顶 6 条）。

## 第二幕：认知冲突

第一次听到"给 agent 加记忆"，很容易想到一个简单的做法：**把历史消息拼上去就完了**——每次调用把之前所有对话重新塞进 messages，模型不就有"记忆"了吗？

这个理解只对了一半。历史拼接确实是记忆的**载体**，但三个追问暴露了它包不住的部分。

> ❓ **问题**：如果"拼历史"就够了——为什么每次 invoke 之后历史就没了？历史太长塞不下怎么办？换个会话为什么还能记得我？

三个追问把这件事拆开：

- 追问一：**"这次 invoke"结束，历史去哪了？**——没有持久化就真的没了。每次 invoke 的起点都取决于你递进去的 messages；要在多轮之间"接续"，需要把状态**持久化**——这就是 checkpointer 的职责（线程内短期记忆）。
- 追问二：**历史越聊越长，塞不下怎么办？**——两条路：**裁剪**（扔掉一部分，简单但要接受丢失）或**摘要**（把早期历史压缩成一段摘要，贵一点但保留语义）。管理策略决定"什么能丢、什么必须留"。
- 追问三：**换个会话（新线程）为什么还该记得我？**——线程内的状态是**隔离**的（课 5 已见同线程接续；换一个 thread_id 就是一段全新对话——本课 1c 实测）。要跨会话记住"用户是谁、喜欢什么"，得把信息抽出对话、存到一个**按用户组织**的库里——这就是 store（长期记忆）。

由此得到本课的第一个关键认知：**记忆是分层的**——线程内状态（自动接续）+ 跨会话存储（按用户记）+ 管理策略（控制规模）。三者各管一段，拼历史只是其中最表层的一环。

### 知识点 1：记忆机制总览

> 🧭 第 1/4 步｜承接：第二幕的追问「历史去哪了、太长怎么办、换个会话怎么记得」 → 本步：看清"无状态"的本质与三层记忆版图

#### 一句话定义

记忆是 harness 层的"状态 + 持久化"体系：模型本身**无状态**；短期记忆（线程内）由 **checkpointer** 把 agent 状态持久化，长期记忆（跨会话）由 **store** 以"命名空间 + 键"存储 JSON 文档。

#### 直觉建立（类比）

把模型想成一个**每次开演都失忆的演员**——它只记得"手里这页剧本"（本次调用收到的 messages）。harness 是后台团队：**提词员**（checkpointer）把上一幕的台词接上，**档案室**（store）存着跨场次的用户资料，**场务**（管理策略）决定剧本太长时删哪段。

> 💡 **类比的边界**：演员失忆是"设定"，模型无状态是"架构"——模型不会因为"想记"而记住什么，记忆全靠外部系统在每次调用时**把该给的信息递到它手上**。所以"记忆"改造的从来不是模型，而是调用模型的方式。

#### 核心原理

**① 模型无状态：本次看到什么，只取决于这轮递给它什么**——实测对照（脚本 1a 段）：

```text
-- 1a. 无 checkpointer：两次 invoke 相互独立 --
  [无记忆·第1轮] 你好，小明！很高兴认识你 😊 我是 Qwen3.8。有什么我可以帮你的吗？
  [无记忆·第2轮] 我不知道你的名字哦 😊 我没有关于你的任何个人信息。 如果你愿意告诉我，我可以记住这次对话中你怎么称呼；不过每次新的对话我都是"从零开始"，不会保留之前的记忆。 方便说说你叫什么名字吗？
```

第二轮问"我叫什么名字"——agent 不知道。**这不是模型能力问题，是机制问题**：第二轮 invoke 只递了"我叫什么名字？"这一句，模型确实"没见过"名字。

**② checkpointer：把状态持久化到线程，下一轮自动接续**——实测（脚本 1b 段）：

```text
-- 1b. 有 checkpointer + 同一 thread_id：历史自动接续 --
  [同线程·第1轮] 好的，小明，我记住了：你最喜欢蓝色。
       （消息数: 2）
  状态核验（get_state）——已持久化的消息链:
    [0] human: 我叫小明，最喜欢蓝色。请记住。
    [1] ai: 好的，小明，我记住了：你最喜欢蓝色。
  [同线程·第2轮] 你叫小明，最喜欢蓝色。
       （消息数: 4）
```

给 `create_agent` 配上 `checkpointer=InMemorySaver()`，invoke 时带上同一个 `thread_id`——第一轮结束状态被持久化（`get_state` 可查：2 条消息），第二轮自动载入后变成 4 条，模型直接答出名字和喜好。换个 `thread_id`（脚本 1c 段）则完全隔离：

```text
-- 1c. 换一个 thread_id：记忆相互隔离 --
  [新线程·问名字] 我目前还不知道你叫什么。 如果你愿意，可以告诉我怎么称呼你。
       （消息数: 2）
```

**③ 机制细节（官方口径）**：状态是 agent 运行时的一部分——短期记忆**在 invoke 或某一步（如工具调用）完成时更新，在每一步开始时被读取**；checkpointer 负责把它落到数据库（或内存），这样线程随时可以恢复。官方文档还列了两个配套要点：

- **长期记忆的定位**：需要**跨对话**记住信息时用 store——它不绑定在单个线程里，而是挂在自定义命名空间下，随时、任意线程可召回。
- **生产环境换后端**：`InMemorySaver` / `InMemoryStore` 只适合开发与演示；生产换成数据库后端（checkpointer 有 Postgres、SQLite、Azure Cosmos DB 等，store 有 Postgres、Redis、MongoDB 等）。

**④ 三种载体，一张表看清**（本课全程实测验证）：

| 载体 | 存在哪 | 作用域 | 典型用途 |
|------|--------|--------|----------|
| 消息历史（`messages`） | agent 状态 → checkpointer 持久化 | 单个线程 | 对话接续（默认全量） |
| 自定义 state 字段 | 同上（需 `state_schema` 扩展） | 单个线程 | 结构化会话数据（名字、标记、中间结果） |
| store（命名空间 + 键） | 独立存储（store 后端） | 跨线程、跨会话 | 用户档案、偏好、跨会话事实 |

**⑤ 验证纪律：记忆在不在，看状态不看嘴**——1b 段的 `get_state` 是核验记忆的可靠手法：状态里有几条消息、内容是什么，一查便知。模型"这一轮怎么用记忆"受采样影响（措辞、是否引用都可能波动），不能反过来用单次回答断言"机制坏了/没生效"。

见上文实测：无状态对照（①）、同线程接续（②）、线程隔离（③），以及官方机制口径（④、⑤），来源脚本 `playground/lesson-07-memory-lab.py`（1a-1c 段）。

#### 常见误区

1. **以为"模型会自己记住"**：模型无状态是架构事实——"记得"的前提是 harness 把信息递到它手上（本课全部实验都建立在这一点上）。
2. **以为"窗口够大就不需要记忆机制"**：窗口大只是"塞得下"，但历史越长越慢越贵，且模型会被无关的旧内容"分心"（官方明确列出这两点）——管理策略依然必需。
3. **用单次回答判断"记忆是否生效"**：模型回答有采样随机性；验证记忆靠**状态**（`get_state` / 消息条数），不靠某一句回答的措辞。

#### 一句话记住

> 模型负责"聪明"，harness 负责"记住"——短期记忆在线程里，长期记忆在命名空间里。

#### 🗣️ 行话对照

- **无状态（stateless）**：本次输出只取决于本次输入——在哪遇到：所有 LLM/agent 的底层事实
- **checkpointer**：把 agent 状态持久化、可恢复的组件——在哪遇到：`create_agent(checkpointer=...)`
- **thread（线程）**：一次会话的组织单位（类似一封邮件串）——在哪遇到：`{"configurable": {"thread_id": "..."}}`
- **state / get_state**：agent 的状态快照 / 读取手法——在哪遇到：`agent.get_state(config)`
- **store**：跨会话的 JSON 文档存储——在哪遇到：`create_agent(store=...)`
- **namespace（命名空间）**：store 里类似"文件夹"的组织单位——在哪遇到：`store.put(("users",), key, value)`

### 知识点 2：短期记忆

> 🧭 第 2/4 步｜承接：知道记忆放在哪了——现在处理"聊得太长怎么办" → 本步：全量 / 裁剪 / 摘要 / 自定义 state 四种管法逐一实测

#### 一句话定义

短期记忆 = 线程内的消息历史 + 管理策略。默认全量积累；当历史过大时，用**裁剪**（保留首条 + 最近 N 条）、**摘要**（压缩为一条摘要消息）控制规模，或通过**自定义 state** 把结构化信息从"聊天记录"里提出来。

#### 直觉建立（类比）

会议记录员的三种做法：**全程录音**（全量——最完整，但带子越录越长）；**只留最近几页 + 开头那一页**（裁剪——便宜，但中间内容没了）；**上半场写成一页纸纪要**（摘要——贵一道工序，换"重点还在"）。再加第四种：**贴便签**（自定义 state——把关键信息从记录里"抽出来"贴墙上，随用随取）。

> 💡 **类比的边界**：裁剪和摘要都发生在"送去模型之前"（由中间件/钩子加工状态）；便签（state 字段）则是由工具显式写的结构化数据——载体不同，但都放在同一个线程状态里。

#### 核心原理

**① 默认全量：越聊越长（增长轨迹实测）**——脚本 2a 段（同一线程连续 4 轮 + 检查问题）：

```text
  第 1 轮后消息数: 2
  第 2 轮后消息数: 4
  第 3 轮后消息数: 6
  第 4 轮后消息数: 8
  [全量·检查] 你叫**小明**，喜欢**蓝色**。
       （消息数: 10）
```

每一轮 +2 条（human + ai），第 5 次调用结束时已经 10 条。官方把问题说得很直白：长对话可能超过上下文窗口；即使塞得下，模型也会被过时/离题内容**分心**，同时**响应变慢、成本变高**——所以需要"删或忘"的技术。

**② 裁剪：保留"首条 + 最近 4 条"，封顶 6 条**——用 `@before_model` 中间件在每次模型调用前改写历史（脚本 2b 段，同一段对话）：

```text

  第 2 轮后消息数: 4
  第 3 轮后消息数: 6
  第 4 轮后消息数: 6            ← 触发裁剪：7 条 → 保留 5 条 → +1 回复

    [1] ai: 北京是一座很有魅力的城市呢！如果再加上你喜欢的蓝色，我脑海里会浮现出晴朗日子里的天空蓝，或者颐和园昆明湖的那种蓝。😊 你住在哪个区呀？平时有

    [3] ai: 咪咪听起来好可爱呀！🐱 你是喜欢它毛茸茸的样子，还是它调皮时像小毛球滚来滚去的样子呢？（我总觉得北京人养猫特别有意思，毕竟胡同里猫和现代公寓
    [4] human: 我叫什么名字？我喜欢什么颜色？
    [5] ai: 你叫**小明**，这个你一开始就告诉我啦 😊 至于喜欢的颜色——我得老实承认：**你从来没有告诉过我**。我之前回复里提到的"蓝色"，是我自
```

注意结果里的**关键对照**：消息数被死死封在 6 条，而且"名字"答对了（因为保留策略把**首条**留着）；但"喜欢的颜色"**丢了**（它在第二条 human 消息里，被裁掉了）——模型甚至老实承认"你从来没跟我说过"。

实现方式——`@before_model` 钩子 + `RemoveMessage`：

```python
from langchain.messages import RemoveMessage
from langgraph.graph.message import REMOVE_ALL_MESSAGES
from langchain.agents.middleware import before_model

@before_model
def trim_messages(state, runtime):
    """保留第一条消息与最近 4 条，控制上下文规模。"""
    messages = state["messages"]
    if len(messages) <= 6:
        return None
    first = messages[0]
    recent = messages[-4:]
    return {"messages": [RemoveMessage(id=REMOVE_ALL_MESSAGES), first, *recent]}
```

两个机制细节（官方口径）：`RemoveMessage` 需要消息键带 `add_messages` 归约器才生效——默认 `AgentState` 自带；`REMOVE_ALL_MESSAGES` 表示"清空后重放保留项"。**裁剪的本质是选择**：保留哪些、丢弃哪些，就是你在决定"哪些信息可以丢"——2b 的丢失演示就是这个选择的直接后果。

**③ 摘要：超阈值时把早期历史压缩成一条摘要**——用官方预置的 `SummarizationMiddleware`（脚本 2c 段，同一段对话、同样 4 轮）：

```text
  第 4 轮后消息数: 6            ← 同样触发压缩
  [摘要·检查] 你叫 **小明**。 你喜欢的颜色是 **蓝色**。😊
       （消息数: 6）
  最终保留的消息链:
    [0] human: Here is a summary of the conversation to date: ## SESSION INTENT User (小明) is providing personal background in
    [1] ai: 北京是个很有底蕴的城市呢！既有故宫、胡同这样的老味道，又有非常现代的一面。 你是土生土长的北京人，还是后来才在那边安家呀？😊
    [2] human: 我养了一只猫，叫咪咪。
    [3] ai: 哇，有猫咪陪伴的生活一定特别治愈！在北京住，咪咪平时是不是喜欢趴在窗台上晒太阳、看外面的风景呀？ 咪咪长什么样子呢？有没有像宝石一样蓝色的眼睛？😻
    [4] human: 我叫什么名字？我喜欢什么颜色？
    [5] ai: 你叫 **小明**。 你喜欢的颜色是 **蓝色**。😊
```

和裁剪的对比很清楚：**同样封顶 6 条，但"颜色"也记住了**——因为早期历史不是被扔掉，而是被压缩进了 [0] 那条摘要消息（实测形态：一条 human 消息，内容以 `Here is a summary of the conversation to date:` 开头，摘要里含用户的名字、颜色等关键信息；同配置补证实测：摘要 1212 字符，含"小明""蓝色""北京"）。代价：每次触发摘要要**多跑一次模型调用**（阈值太小会频繁触发——本例小阈值下被多次触发）。

配置方式（官方参数）：

```python
from langchain.agents.middleware import SummarizationMiddleware

SummarizationMiddleware(
    model=model,                  # 用来生成摘要的模型（可与主模型不同）
    trigger=("messages", 6),      # 触发条件：消息数达到 6；也支持 ("tokens", N) / ("fraction", 0.8)
    keep=("messages", 4),         # 压缩后保留：最近 4 条
)
```

补充细节：`fraction` 形式的阈值依赖模型的 profile 数据（课 2 讲过 profile；缺失时需手动指定或用另外两种形式）；摘要面向**文本**压缩——图片/音视频块不会被打小，重要媒体建议存到文件系统/对象存储后在历史里传引用。

**④ 自定义 state：把关键信息从聊天记录里"抽出来"**——扩展 `AgentState` 加字段，工具里读（`runtime.state`）写（`Command(update=...)`）。脚本 2d 段：

```text
  [写状态] 消息链:
    [0] human: 我的名字是小明，请记录下来。
    [1] ai → 调用工具: save_name({'name': '小明'})
    [2] tool: 已记录：小明
    [3] ai: 好的，我已经记录下您的名字：**小明**。
  [读状态] 您之前告诉我的名字是：**小明**。
```

工具实现（写状态用 `Command`，读状态用 `runtime.state`）：

```python
class CustomState(AgentState):
    user_name: str

@tool
def save_name(name: str, runtime: ToolRuntime) -> Command:
    """记录用户的名字到状态。"""
    return Command(update={
        "user_name": name,
        "messages": [ToolMessage(f"已记录：{name}", tool_call_id=runtime.tool_call_id)],
    })

@tool
def get_name(runtime: ToolRuntime) -> str:
    """查询之前记录的用户名字。"""
    name = runtime.state.get("user_name")
    return f"之前记录的用户名是：{name}" if name else "没有记录过。"
```

价值：结构化信息不再依赖"模型从聊天记录里读"——它成了状态里的显式字段，工具随时取用（后续中间件、动态提示词也都能读）。

#### 常见误区

1. **以为裁剪"免费"**：裁剪省条数，但**丢什么由你的保留策略决定**——2b 实测丢了中间信息（颜色答不出）；"首条+最近"只是众多策略中的一种。
2. **以为摘要"一定省钱"**：摘要要额外调模型；摘要文本本身也有体量（成本对比见知识点 4 实测）。它是"保信息"的手段，不是"省 token"的保证。
3. **删消息不看序列合法性**：官方警告——删除后要保证历史对提供方合法（例如带工具调用的 AI 消息必须跟对应的工具结果消息、有些提供方要求历史以 user 开头）。

#### 一句话记住

> 全量最保真、裁剪最省事、摘要最折中、便签（state）最直接——但删之前先想清楚"什么可以丢"。

#### 🗣️ 行话对照

- **trim（裁剪）**：只保留部分消息——在哪遇到：`@before_model` + `RemoveMessage`
- **RemoveMessage / REMOVE_ALL_MESSAGES**：删除消息的指令 / 全量清空标记——在哪遇到：`langchain.messages` / `langgraph.graph.message`
- **摘要中间件（SummarizationMiddleware）**：超阈值自动压缩历史——在哪遇到：`langchain.agents.middleware`
- **trigger / keep**：触发压缩的条件 / 压缩后保留多少——在哪遇到：`SummarizationMiddleware(...)`
- **state_schema**：自定义状态扩展——在哪遇到：`create_agent(state_schema=CustomState)`
- **Command（工具写状态）**：工具返回值里携带状态更新——在哪遇到：`langgraph.types.Command`

### 知识点 3：长期记忆

> 🧭 第 3/4 步｜承接：线程内的账记好了——现在解决"换个会话还认得你" → 本步：store 结构、工具读写、跨线程召回、用户隔离

#### 一句话定义

长期记忆基于 **store**：把数据当成 JSON 文档，按"**命名空间**（类似文件夹）+ **键**（类似文件名）"组织，跨线程、跨会话随时读写。工具里通过 `runtime.store` 操作，配合 `context` 里的 `user_id` 落到对应用户的命名空间。

#### 直觉建立（类比）

医馆的**档案柜**：抽屉按"科室/病人"分层（命名空间），每格档案袋有编号（键），里面是病历（JSON 文档）。医生（工具）根据"现在看的是谁"（`context.user_id`）拉开对应抽屉取档——跟"今天第几次来"（线程）无关。

> 💡 **类比的边界**：档案柜的编号规则纯属人为约定——store 的命名空间设计同样由你决定（`("users",)` 还是 `("users", user_id, "preferences")`），**设计方式直接决定隔离与检索的边界**，这是工程上最容易忽视、也最容易埋雷的一步。

#### 核心原理

**① store 的基本操作：put / get / search**——脚本 3a 段（不经模型，直接操作）：

```text
  get(('users',), 'user_123'): {'name': '小明', 'language': '中文'}
  search(('users',)) 全部: [{'name': '小明', 'language': '中文'}, {'name': '小红', 'language': '英文'}]
  search(filter={'language': '中文'}): [{'name': '小明', 'language': '中文'}]
  search(query='名字')（未配嵌入函数）: [{'name': '小明', 'language': '中文'}, {'name': '小红', 'language': '英文'}]
```

- `put(namespace, key, value)`：写入；`get(namespace, key)`：按名取；`search(namespace, filter=...)`：按内容键值过滤。
- 注意最后一行：**`query` 语义检索需要给 store 配嵌入函数**（`IndexConfig(embed=...)`）；未配置时实测 query 未改变返回结果（仍是全量两条）——语义检索是 RAG 化方向的延伸（课 11 展开）。

**② 工具读写：`runtime.store` + `context` 传用户身份**——3b 段的 agent 配置：

```python
@dataclass
class UserContext:
    user_id: str

@tool
def save_user_name(name: str, runtime: ToolRuntime[UserContext]) -> str:
    """保存用户名字到长期记忆（跨会话）。"""
    runtime.store.put(("users",), runtime.context.user_id, {"name": name})
    return f"已保存：{name}"

@tool
def get_user_name(runtime: ToolRuntime[UserContext]) -> str:
    """从长期记忆读取用户名字（跨会话）。"""
    item = runtime.store.get(("users",), runtime.context.user_id)
    return item.value["name"] if item else "没有找到该用户的记录"

agent = create_agent(model, tools=[save_user_name, get_user_name],
                     store=store, context_schema=UserContext)
```

要点：`runtime` 参数对模型不可见（模型只看到工具的其他参数），但工具能借它拿到 **store**（同一份传给 `create_agent` 的实例）和 **context**（调用时传的 `UserContext(user_id=...)`）。

**③ 跨线程召回：session-1 里教，session-2 里查**——3b 段实测（两个不同 `thread_id`）：

```text
  [session-1·教] 消息链:
    [0] human: 你好，记住：我叫小明。
    [1] ai → 调用工具: save_user_name({'name': '小明'})
    [2] tool: 已保存：小明
    [3] ai: 好的，小明，我已经记住你的名字啦！😊 有什么我可以帮你的吗？
  直连 store 查看: {'name': '小明'}
  [session-2·查] 你叫小明 😊
    [0] human: 我叫什么名字？
    [1] ai → 调用工具: get_user_name({})
    [2] tool: 小明
    [3] ai: 你叫小明 😊
```

注意 session-2 的消息链**只有本轮问答**（新线程没有历史）——"小明"完全来自 store。这就是短期记忆做不到的事：**信息跨过了线程边界**。

**④ 用户隔离与更新**——3c/3d 段实测：

```text
  [session-3·user_456 查] 我这边还没有关于你姓名的记录，所以暂时不知道你的名字 😊 如果你愿意告诉我，我可以帮你记下来，以后就能随时叫出你的名字啦。
  ...
  [session-1·改名] 消息链:
    ...
    [5] ai → 调用工具: save_user_name({'name': '大明'})
    [6] tool: 已保存：大明
    [7] ai: 好的，大明，已经帮你更新啦 ✅ 以后我就这样称呼你。有什么需要尽管说！
  直连 store 查看: {'name': '大明'}
```

- **隔离**：换个 `user_id`（user_456）就查不到——数据按命名空间+键分开存放，不会串号。
- **更新**：`put` 同一个键 = **覆盖**原来的值（改名后 store 里只剩"大明"）——"更新一条记忆"到底是覆盖、合并还是追加，需要显式设计（知识点 4 展开）。

**⑤ 与短期记忆的配合（生产姿势）**：3b 的 agent 同时挂了 checkpointer（线程内接续）和 store（跨会话资料）——"这次聊了什么"归线程，"用户是谁"归 store。生产环境两者都应换成数据库后端；官方还列出了更细的写入策略（热路径 vs 后台）与记忆类型（知识点 4）。

#### 示例演示

见上文实测：store 基本操作（①）、工具读写（②）、跨线程召回（③）、隔离与更新（④），来源脚本 `playground/lesson-07-memory-lab.py`（3a-3d 段）。

#### 常见误区

1. **把 store 当"第二个 checkpointer"**：作用域完全不同——checkpointer 绑定**线程**（这次会话），store 绑定**命名空间**（这个用户/组织）；"跨会话记得"必须走 store。
2. **忘了把 `store` 传给 `create_agent`**：工具里的 `runtime.store` 就是 agent 收到的那个 store 实例——不传就没有（本课 3b 的 agent 显式配置了 `store=store`）。
3. **只 put 不设计更新语义**：同键 `put` 是覆盖——要"累加信息"（比如追加一条偏好）必须自己**读-改-写**（知识点 4 的合并更新实测会展示差别）。

#### 一句话记住

> 短期记忆"属于这次对话"（线程），长期记忆"属于这个人"（命名空间）——跨会话记得你，靠的是 store。

#### 🗣️ 行话对照

- **store**：跨会话 JSON 文档存储——在哪遇到：`create_agent(store=...)`、`runtime.store`
- **namespace / key**：命名空间（文件夹）/ 键（文件名）——在哪遇到：`store.put(("users",), "user_123", {...})`
- **put / get / search**：写 / 读 / 检索——在哪遇到：`runtime.store.*`
- **context_schema / context**：运行上下文类型 / 实例（常用来传 user_id）——在哪遇到：`create_agent(context_schema=...)`、`invoke(..., context=...)`
- **IndexConfig / embed**：为语义检索配置嵌入函数——在哪遇到：`InMemoryStore(index=IndexConfig(...))`

### 知识点 4：记忆工程实践

> 🧭 第 4/4 步｜承接：机制、短期、长期都通了——最后一步是"工程品味"：记什么、怎么更新、花多少钱 → 本步：类型 / 写入时机 / 更新模式 / 成本对比

#### 一句话定义

记忆工程 = 决定"记什么、怎么记、何时写、花多少"：记忆按类型分（语义 / 情景 / 程序），更新按模式分（覆盖 / 合并），写入按时机分（热路径 / 后台），效果与成本按场景**实测**权衡。

#### 直觉建立（类比）

记账的学问：**流水账**（情景——经历过什么）、**客户档案**（语义——这个人是谁）、**内部规章**（程序——我们怎么做事的）。是"当场逐笔记"（热路径——实时，但占用前台精力）还是"打烊后整理"（后台——不占前台，但要定整理频次）？

> 💡 **类比的边界**：记账的"记"字是隐喻——agent 的"程序记忆"现实中不常真的改代码/权重，更常见的是改**提示词**（如反思式改写）；"情景记忆"也常是"存下来的过往案例"，供未来参考。

#### 核心原理

**① 记忆的类型：语义 / 情景 / 程序**（官方概念篇）：

| 类型 | 存什么 | 人类示例 | Agent 示例 |
|------|--------|----------|------------|
| 语义 | 事实 | 学校学到的知识 | 用户的名字、偏好 |
| 情景 | 经历 | 做过的事 | 过往的操作记录 |
| 程序 | 规则 | 本能与技能 | 系统提示词、行为准则 |

注意一个术语陷阱：**"语义记忆"（存事实，心理学概念）≠"语义检索"**（按含义找相似，通常用嵌入向量）——官方专门给了提醒。本课 3a 段未配嵌入时的 query 就是"语义检索"的入口，配好嵌入才能真正生效。

**② 写入时机：热路径 vs 后台**——热路径（对话中由工具/逻辑当场写）：实时、用户可见（"已记住…"），但增加延迟、模型要"多任务"；后台（另起任务整理）：不占前台延迟，但要设计触发时机（定时/事件后/手动）。本课 4a 的工具写入就是典型热路径。

**③ profile vs collection**——单一档案（持续更新一份 JSON：更新要小心别丢字段）vs 文档集合（每条记忆单独存：更不易丢，但"去重/更新/检索"变难）。本课 4a 是 profile 形态的合并更新。

**④ 更新模式：合并 vs 覆盖**——4a 段实测：

```text
  更新前: {'name': '小明', 'city': '北京'}
  [合并更新] 消息链:
    [0] human: 记住：我喜欢喝咖啡。
    [1] ai → 调用工具: remember_preference({'preference': '我喜欢喝咖啡。'})
    [2] tool: 已记住。当前档案: {'name': '小明', 'city': '北京', 'preferences': ['我喜欢喝咖啡。']}
    [3] ai: 好的，已记住你喜欢喝咖啡。以后在推荐或安排相关事项时，我会把这一点考虑进去。
  更新后（合并）: {'name': '小明', 'city': '北京', 'preferences': ['我喜欢喝咖啡。']}
  对照·若直接覆盖写（只写新内容不读旧档案）: {'preferences': ['喜欢喝咖啡']}
```

合并（读 → 改 → 写）：旧字段（name、city）保留，新偏好追加进列表；裸覆盖：名字、城市全丢。工具实现：

```python
@tool
def remember_preference(preference: str, runtime: ToolRuntime[UserContext]) -> str:
    """记住用户的偏好（读取现有档案，追加到 preferences 列表后写回）。"""
    ns = ("users",)
    key = runtime.context.user_id
    item = runtime.store.get(ns, key)
    profile = dict(item.value) if item else {}
    prefs = list(profile.get("preferences", []))
    prefs.append(preference)
    profile["preferences"] = prefs
    runtime.store.put(ns, key, profile)
    return f"已记住。当前档案: {profile}"
```

（档案变大后"更新"会越来越难——官方建议拆分成多文档、或用严格解码保证 schema 有效；集合式的更新/删除是另一类难点。）

**⑤ 成本对比：同一段对话，三种策略**——4b 段实测（4 轮对话 + 1 个检查问题）：

```text
  策略     | 消息数   | token 估算 | 检查问题的回答
  全量     | 10      | 135          | 你叫**小明**，喜欢**蓝色**。
  裁剪     | 6       | 116          | （名字对；颜色丢失——原文见 2b）
  摘要     | 6       | 303          | 你叫 **小明**。 你喜欢的颜色是 **蓝色**。😊
```

三条工程结论（本课最值得记住的部分）：

- **消息数 ≠ token 数**：裁剪把条数从 10 压到 6，token 只降了约 14%（135→116）——留下的消息本身较长；"省成本"要按**内容体量**评估，不能只看条数。
- **摘要不是自动省钱**：本例摘要 303 token，反而**最高**——摘要文本有固定体量，且每次触发多一次模型调用。它解决的是"历史无限增长"（长对话才回本），小对话用它反而亏。
- **取舍对齐目标**：要全保真 → 全量；要省事且能接受丢失 → 裁剪；要压规模但保语义 → 摘要；要"结构化直取" → 把信息抽到 state/store（让未来轮次根本不用背长历史）。

（token 为 `count_tokens_approximately` 估算值，用于横向对比；真实计费以提供方为准。）

见上文实测：合并更新与覆盖对照（④）、三策略成本对比（⑤），来源脚本 `playground/lesson-07-memory-lab.py`（4a-4b 段）。

#### 常见误区

1. **以为"记得越多越好"**：存了不用 = 上下文噪音 + 持续成本；"何时更新记忆""如何避免冗余"是官方单列的问题——记忆需要**管理**，不是囤积。
2. **以为摘要/裁剪是"免费的优化开关"**：两者都有代价（丢失 / 额外调用），要按会话规模与目标实测选择（⑤ 的数据就是反例）。
3. **忘了"谁的数据、存多久、能否删除"**：命名空间只是技术面——真实产品还要考虑隐私与可控性（点到为止，不展开）。

#### 一句话记住

> 记忆工程没有标准答案——只有按"记什么、怎么记、何时写、花多少"做的持续取舍。

#### 🗣️ 行话对照

- **语义记忆 / 情景记忆 / 程序记忆**：事实 / 经历 / 规则——在哪遇到：概念篇 memory
- **热路径（hot path）/ 后台（background）**：写入时机——在哪遇到：概念篇 memory
- **profile / collection**：单一档案 vs 文档集合——在哪遇到：概念篇 memory
- **合并更新（读-改-写）**：更新不丢旧字段的写法——在哪遇到：本课 4a 工具

## 第四幕：实操验证

回到第一幕：客服助手要"记得住"。以下五组验证全部本机跑通（脚本：`playground/lesson-07-memory-lab.py`）：

1. **无状态对照（1a-1c）**：无 checkpointer 两轮互不相识（"我不知道你的名字哦"）；同线程接续（状态核验 2 → 4 条，答出"你叫小明，最喜欢蓝色"）；换线程隔离（"我目前还不知道你叫什么"）。
2. **短期三策略对照（2a-2c）**：全量 10 条（全记得）vs 裁剪封顶 6 条（名字对、颜色丢）vs 摘要封顶 6 条（全记得，摘要以 human 消息形态出现）。
3. **自定义 state（2d）**：工具写状态（`Command`）→ 工具读状态（`runtime.state`），名字跨轮取用成功。
4. **长期记忆链路（3a-3d）**：store 直接读写（put/get/search）；跨线程召回（session-1 教 → session-2 答"你叫小明"）；用户隔离（user_456 查不到）；同键更新（改名后 store 为"大明"）。
5. **工程实践（4a-4b）**：合并更新保住 name/city 并追加偏好（对照覆盖写只剩 preferences）；三策略成本（10 条/135、6 条/116、6 条/303）。

> ✅ **回扣场景**：第一幕的三个尴尬全部有了解法——"每次都问您怎么称呼" = checkpointer 同线程接续（1b）；"历史太长塞不下" = 裁剪/摘要（2b/2c）；"换个会话就失忆" = store 跨会话召回（3b）。
>
> ⚠️ 数值说明：以上为 2026-09-15 本机实测；模型回答措辞与消息条数受采样和对话内容影响（如 2b/2c 的检查回答逐字为当次实测，复跑可能不同）；token 数为估算值；生产使用需替换数据库后端并补充清理/合规策略。

## 🐞 常见误区

1. **以为"模型会自己记住"**：模型无状态是架构事实——"记得"全靠 harness 在调用时把信息递到它手上（本课全部实验的基石）。
2. **以为"窗口够大就不需要记忆机制"**：窗口大只是塞得下——长历史变慢、变贵、让模型分心（官方明确列出）。
3. **以为裁剪/摘要"免费"**：裁剪要接受丢失（2b 实测颜色答不出）；摘要要付额外调用+摘要体量（4b 实测 303 > 135）。
4. **用单次回答判断记忆是否生效**：看状态（`get_state` / 消息条数）——模型措辞受采样影响，不能反推机制。

### ⏳ 与过时说法对照（写前核对 + 实测发现的差异）

| 旧说法（网上教程 / 直觉） | 现状（官方文档 + 本课实测） | 依据 |
|---|---|---|
| "给 agent 加记忆 = 把历史消息拼回去" | 记忆是分层的：线程状态（checkpointer）+ 跨会话存储（store）+ 管理策略——拼历史只是最表层 | 1a-1c、3a-3d |
| "模型有记忆能力" | 模型无状态；记忆是 harness 工程（状态 + 持久化） | 1a、1b |
| "摘要一定省 token" | 同一个对话实测：摘要 303 vs 全量 135——摘要文本有体量、触发有额外调用；长对话才回本 | 4b |
| "存进 store 就完事" | 更新语义（覆盖 vs 合并）与隔离（命名空间/user_id）必须显式设计 | 3d、4a |
| "模型答不出 = 记忆没生效" | 验证看状态（get_state）；回答措辞受采样影响 | 1b 状态核验 |

## 课后小测

**Q1**：关于记忆的载体，说法正确的是？
- A. 模型会自己记住用户，不需要额外机制
- B. 短期记忆存在线程状态里（checkpointer 持久化），长期记忆存在 store 里（跨线程、按命名空间组织）
- C. 只要上下文窗口够大，就不需要任何记忆管理
- D. checkpointer 和 store 是同一种东西的两种叫法

<details><summary>答案与解析</summary>

**答案：B**。A 错——模型无状态（1a 实测"我不知道你的名字哦"）；C 错——窗口大不代表不需要管理（长历史会变慢、变贵、让模型分心）；D 错——checkpointer 绑定线程（短期），store 绑定命名空间（长期），作用域不同（1c 换线程隔离、3b 跨线程召回分别为证）。

</details>

**Q2**：关于短期记忆的三种管理策略，说法正确的是？
- A. 裁剪永远不会丢信息
- B. 摘要一定能降低 token 成本
- C. 裁剪保不保留首条等策略，决定了哪些信息会丢；摘要需要额外模型调用，成本要按会话规模实测
- D. 裁剪和摘要互斥，不能同时出现在一个 agent 里

<details><summary>答案与解析</summary>

**答案：C**。A 错——2b 实测丢了"喜欢的颜色"；B 错——4b 实测摘要 303 token 反而高于全量 135（该对话规模下）；D 错——两者可以组合使用（还可叠加自定义 state）。

</details>

**Q3**：长期记忆的典型用法是？
- A. 在工具里用 `runtime.store` 读写，按 `context` 里的 `user_id` 落到命名空间，实现跨会话召回
- B. 只要把 `store` 传给 `create_agent`，模型就会自动读写记忆
- C. store 只能存字符串
- D. 长期记忆不需要任何隔离设计

<details><summary>答案与解析</summary>

**答案：A**。B 错——需要工具或逻辑显式读写（3b 的 agent 通过 `save_user_name`/`get_user_name` 工具操作）；C 错——存的是 JSON 文档（3a 实测字典写入与读回）；D 错——按 `user_id` 隔离是核心设计点（3c 实测换 user 查不到）。

</details>
