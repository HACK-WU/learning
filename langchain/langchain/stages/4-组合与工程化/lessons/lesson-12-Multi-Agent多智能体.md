## 第一幕：起源与场景引入

> 🏛️ **起源**：多智能体不是某一个发明，而是一组设计模式的集合。其中 **handoffs（交接）这个术语由 OpenAI 在 Agents SDK 中提出**（官方文档明确注明：指用 `transfer_to_sales_agent` 这类工具调用在 agent 之间转移控制权，核对于 2026-09）；**subagents/skills/router** 等模式则在 LangChain 官方文档中被统一整理成五大模式。另有一个概念对照：**skills 模式在概念上等同于 Agent Skills 与 llms.txt**（Jeremy Howard 提出）——都是「用工具调用实现文档/知识的渐进式披露」（progressive disclosure），只不过 skills 披露的是专业提示词与领域知识。

客服助手进入第十二次进化。前十一课它已经是「一个人顶一个团队」：会查资料（课 11）、能守规矩（课 10）、记住上下文（课 9）、流程可控（课 8）。直到业务线从 1 条变成 4 条：**天气、金融、数据库、办公**——每条线都有自己的知识、自己的工具、自己的话术。

你试着把所有东西塞给同一个 agent：系统提示词越写越长，工具从 3 个挂到 8 个、再到 16 个，每条领域知识都挤在同一个提示词里。它开始出现微妙的问题：**回答越来越泛**（被无关领域知识稀释）、**改动越来越难**（四个团队共用一个 prompt，谁都不敢动）、**扩展越来越贵**（每加一个领域，所有调用的上下文都涨一截）。

> 🎬 **场景**：终于有人提出那句经典的话——「让我拆开它。」可拆分不是把一个 agent 抄成四份：拆开之后，**谁调度谁？对话怎么流转？用户的问题谁来接？**——拆开的四个 agent 如何「像一个团队那样协作」，这才是多智能体的真问题。

> 📌 **一句话本质**：多智能体 = **把任务拆给专门的 agent，并设计好它们之间的协作方式**。拆分的三个官方理由：**上下文管理**（让每个 agent 只带自己领域的信息）、**分布式开发**（不同团队独立维护各自的 agent）、**并行化**（多个专项任务同时执行）。而协作方式被官方归纳为五大模式：subagents / handoffs / skills / router / custom workflow（核对于 2026-09）。
>
> ⚖️ **处境对照**：没有这一课——单 agent 的提示词与工具清单随业务线性膨胀，最终「谁都不敢改，越改越糊涂」；有了这一课——**主代理只持有各子代理的一行描述，领域知识按需加载，团队边界清晰可维护**（本课实测：单 agent 每次调用携带 ~1983 字符的全领域上下文 vs 拆分后主代理 ~275 字符，子代理按需 231~907 字符）。

## 第二幕：认知冲突

你可能有一个直觉反应：**「多智能体 = 更高级 = 效果更好。要上了，就直接上多智能体。」**

官方文档在总览页的开头就用一句话拦住了这个冲动：**「不是每个复杂任务都需要多智能体——一个带对工具（有时是动态工具）和提示词的单一 agent 往往就能达到相似效果。」**（核对于 2026-09）

两个更具体的误解会被随后的实测继续打脸：

**误解一：「单 agent 工具一多，就一定选错工具。」**——本课实测：给单 agent 挂上横跨四领域的 **8 个工具**，它依然能精准地并行调用正确的工具；加到 **16 个工具**（含三个近似的天气工具），它依然精确选中了「空气质量」这个正确答案。所以问题**不是「做不到」，而是「代价在涨」**：每次调用都携带全部工具的 schema 与全部领域知识（实测 1983 字符），而且这份代价会随每个新领域的加入而线性增长——**拆分是把「每次调用的固定成本」换成「按需的一次性成本」**。

**误解二：「多智能体就是多开几个 agent 各干各的。」**——拆开之后真正难的不是「多」，而是**协作的流动方式**：对话控制权怎么交给另一个 agent？用户中途插话怎么办？多个 agent 的结果谁来合？这些「流动方式」就是五大模式要回答的问题——它们之间没有优劣，只有**适配**（官方给出四维选择表：分布式开发 / 并行化 / 多跳 / 直接用户交互）。

> ❓ **问题**：那么，**什么时候该拆？拆了之后用哪种模式？**——这正是本课三个知识点要依次回答的：先认清单 agent 的极限（知识点 1），再吃透三种核心协作模式的结构（知识点 2），最后补齐进阶模式并学会做选择（知识点 3）。

### 知识点 1：为什么需要多智能体

> 🧭 第 1/3 步｜承接：课 5 的「Agent = Model + Harness」——单个 harness 的能力边界在哪里 → 本步：看清三重极限与拆分信号

#### 一句话定义

多智能体 = **把任务拆给多个专门化的 agent，并设计它们之间的协作方式**——它要解决的不是「单个 agent 能力不足」，而是三个规模化之后必然到来的压力：**上下文管理**（上下文窗口装不下所有领域知识）、**分布式开发**（多个团队要独立维护各自的能力）、**并行化**（多个子任务要同时执行）。

#### 直觉建立（类比）

一家公司从小作坊到集团公司。十个人的时候，一个全能店长全管了（单 agent 挂满工具）；等到业务线有四个事业部、每个事业部有自己的专业知识与流程时，你需要的不是「一个记性超强的店长」，而是**分工**：专人专岗（每个岗位只需要自己的培训手册）、组织架构（谁向谁汇报、什么任务转给谁）、会议机制（跨部门协作怎么开）。多智能体 = 给 agent 装上「组织架构」。

> 💡 **类比的边界**：公司的组织架构是权力与汇报关系，多智能体的「模式」是**消息与控制权的流动方式**——同样是「专人专岗」，有的架构是「总部统一调度」（subagents），有的是「接力棒传递」（handoffs），有的是「前台先分流」（router）。三类协作的成本结构完全不同（知识点 2、3 实测展开）。

#### 核心原理

**① 官方定义的三个拆分别动机**（核对于 2026-09）：

| 动机 | 官方原文摘要 | 本课实证 |
|------|------------|---------|
| 上下文管理 | 提供专门知识，又不淹没模型的上下文窗口 | 1a：单 agent 1983 字符 vs 拆分后主代理 275 字符 |
| 分布式开发 | 不同团队独立开发维护能力，通过清晰边界组合 | 2a-2f：每个子代理/领域代理独立定义 |
| 并行化 | 为子任务生成专门 worker 并发执行 | 2b：一次 turn 内三个子代理并行（8 次调用） |

**② 官方给的三个拆分信号**（原文摘要：「当单个 agent 有太多工具、决策质量下降时」「当任务需要大量上下文支撑的专门知识（长提示词 + 领域工具）时」「当你需要顺序约束——某些能力必须在前置条件满足后才能解锁时」）。注意第一条的精确含义：**信号是「决策质量下降」而不是「工具数量超过某个数字」**——本课 1b 实测验证了这一点（8 个甚至 16 个工具时模型仍能选对；真正该拆的时刻，是「加进去的领域知识已经让提示词开始互相干扰」或「工具数量还在涨」的趋势上）。

**③ 实测：三重压力的量化（1a + 1b + 补跑 F）**。

静态上下文成本对照（1a）——「全能助手」挂 8 个工具、四个领域知识全写进提示词：

```text
[单 agent 全能架构] system_prompt 247 字符 + 工具 schema 1736 字符 = 共 1983 字符（每次模型调用都携带）
  挂载工具数: 8（四个领域混在一起）

[拆分架构] 每个子代理只带自己领域的工具与知识：
  weather  : 1 个工具 + 领域知识 = 231 字符
  finance  : 2 个工具 + 领域知识 = 566 字符
  database : 1 个工具 + 领域知识 = 242 字符
  office   : 4 个工具 + 领域知识 = 907 字符

[拆分架构 · 主代理] 只带 4 个子代理工具（无领域知识）= 275 字符
[对照] 单 agent 每次调用携带 ~1983 字符；拆分后主代理 ~275 字符，子代理按需 ~231-907 字符
```

看点在两组数字的对比：**单 agent 的 1983 字符是「每次调用都付」的固定税**；拆分后主代理只付 275 字符（四个子代理的一行描述），子代理在自己的那次调用里才付领域成本（231~907 字符）。**这正是「上下文隔离」的经济学含义**。

然后是行为实测——单 agent 真的会「选错工具」吗（1b）？给 8 工具的全能助手一个跨领域任务：

```text
问题: 帮我做两件事：1) 查一下上海现在的天气；2) 给我看看 AAPL 的股价。
模型调用: 2 次
消息路径：
  [ai] ai -> tool: get_weather({'city': '上海'})
  [ai] ai -> tool: get_stock({'symbol': 'AAPL'})
  [tool] tool 返回: 上海：晴，22°C，湿度 40%，东南风 2 级
  [tool] tool 返回: AAPL 当前价格：189.5 美元
  [ai] ai: 两件事都办好了： **1) 上海当前天气** ☀️
```

**如实报告：8 个工具下它一次做对了**（还并行调用了两个工具）。补跑 F 把工具翻倍到 16 个（含三个近似的天气工具 weather / weather_forecast / weather_history / weather_air）：

```text
工具总数: 16（4 真实 + 8 近似领域 + 4 其他领域）
问题（测试近似工具选择）: 帮我看看空气质量怎么样，城市是上海。
模型调用: 2 次
  -> 选中工具: weather_air({'query': '上海'})
  ai: 上海的空气质量指数（AQI）为 **62**，等级为 **良**。
```

**16 个工具下它依然精确选中了 weather_air**——本机模型（qwen3.8-flash）在这个规模上没有出现「选择困难」。所以对第一条拆分信号的正确理解是：**它是「趋势警告」而非「数字红线」**——工具与领域继续增长时（几十个工具、多条业务线各带长文档），退化才会到来；而到那时，你面对的是**已经付了很久的上下文固定税**（每加一个领域，所有调用都涨）。**提前拆的理由是成本结构与可维护性，不只是「防选错」**。

> 🎯 **本节结论**：多智能体的价值主张 = **隔离**（每个 agent 只装自己需要的）+ **可维护**（团队各自迭代）+ **可并行**（专项任务同时跑）。判断「该不该拆」的最实用问句不是「任务复杂吗」，而是：**「这些能力是否由不同知识域组成、且都还在长？」**

#### 常见误区

- **以为「多智能体总是更好」**：官方开篇明确「不是每个复杂任务都需要」——单个带对工具的 agent 往往就够了；拆分有实实在在的协作成本（调用次数、编排复杂度）。
- **以为「工具多了一定选错」**：本课实测 8 个、16 个工具都选对了——退化取决于**模型能力与工具设计的区分度**，不是某个工具数量阈值；但上下文成本从第一刻就在涨。
- **以为「拆分 = 多复制几个 prompt」**：拆分的核心工作量在于**协作设计**（谁调度、谁接话、结果怎么合）——这正是后两个知识点的内容。

### 知识点 2：核心模式（subagents/handoffs/router）

> 🧭 第 2/3 步｜承接：知识点 1 立了「该拆」的判断——本步解决「拆完怎么协作」→ 三种核心模式的机制、实现与实测

#### 一句话定义

三种核心协作模式，按「控制权在哪里」区分：**Subagents**——主代理把子代理当工具调用，**一切路由经过主代理**；**Handoffs**——行为由状态变量动态改变，**控制权在 agent/阶段之间传递**；**Router**——一个分类步骤把输入分派给专职 agent（可并行），**结果汇总成统一回答**（核对于 2026-09，官方总览页定义）。

#### 直觉建立（类比）

三种「部门协作」方式：

- **Subagents = 总部统一调度**：所有对外窗口是总部（主代理），你提出的每件事由总部判断转给哪个部门（子代理），部门干完把结果交回总部，总部再向你汇报。部门之间从不直接对话。
- **Handoffs = 接力棒**：你打着电话，客服发现「这事得技术组」——电话**直接转接**给技术组，后面你就是在和技术组对话（同时后台记录已切换到哪个阶段）。
- **Router = 前台分流**：你的问题在前台被拆解分类，同时发给多个相关部门（并行），各部门把答复交给前台，前台合成一份综合回复给你。

> 💡 **类比的边界**：三种模式的差异不在于「谁更高级」，而在于**用户交互形态与状态管理**——subagents 只有一个对外窗口（便于统一话术）；handoffs 允许直接对话在不同角色间切换（多阶段流程自然，但历史管理要小心）；router 的每次请求独立处理（简单可预期，但无对话记忆）。官方四维选择表（分布式开发/并行化/多跳/直接用户交互）就是对这层差异的量化（见下文）。

#### 核心原理

**① Subagents（子代理模式）**——机制：**把子代理包装为工具**，主代理通过常规的工具调用机制调度它：

```python
subagent = create_agent(model, tools=[...])          # 创建子代理

@tool('weather_expert', description='查询任意城市的天气。输入城市名称。')
def call_weather_agent(query: str) -> str:            # 包装为工具
    result = subagent.invoke({'messages': [{'role': 'user', 'content': query}]})
    return result['messages'][-1].content

main_agent = create_agent(model, tools=[call_weather_agent])  # 主代理持有子代理工具
```

官方总结的四大特征：**集中控制**（所有路由经过主代理）、**无直接用户交互**（子代理结果返回主代理，除非用中断机制）、**子代理即工具**、**可并行执行**（主代理可在一个 turn 内调用多个子代理）。

实测 2a（单体调度）——**恰好 4 次模型调用**，与官方性能表「subagents one-shot = 4 calls」一致：

```text
问题: 杭州今天天气怎么样？
模型调用总数: 4 次（主代理 2 + 子代理内部 2）
主会话消息路径（注意：子代理内部消息不可见）：
  [human]: 杭州今天天气怎么样？
  [ai] ai -> tool: weather_expert({'query': '杭州今天天气'})
  [tool] tool 返回: 杭州今天：**晴** 🌞 - 气温：22°C - 湿度：40% - 风向：东南风 2 级
  [ai] ai: 杭州今天天气：**晴** 🌞 - 气温：22°C - 湿度：40%
```

看点在「**子代理内部消息不可见**」：主会话里只看到 4 条消息（human → 主代理调工具 → 工具返回 → 主代理汇总），子代理内部的两步（调用天气工具、组织答复）被折叠成「一次工具调用」。这就是**上下文隔离的在位证明**——主代理的上下文里永远只有子代理的「一行摘要」，不会混入领域的中间过程。

实测 2b（并行调度）——一个 turn 内三个子代理同行：

```text
模型调用总数: 8 次
  [ai] ai -> tool: weather_expert({'query': '成都'})
  [ai] ai -> tool: finance_expert({'query': 'TSLA 股价'})
  [ai] ai -> tool: database_expert({'query': 'SELECT * FROM orders WHERE user_id = 42'})
  [ai] ai: 三件事已并行处理完毕，汇总如下：
```

8 次 = 主代理 2 + 三个子代理各 2（每次子代理内部「调工具 + 组织答复」）。**并行的代价是固定的**：n 个子代理 = 2n + 2 次调用；换来的是三项任务互不污染上下文。

实测 2c（上下文隔离的对照组）——子代理**不知道**主代理知道的事：

```text
[对照组] 直接把'帮我查一下天气'交给子代理（无任何历史）：
  子代理回复: 请告诉我您想查询哪个城市的天气？

[实验组] 主代理两轮对话（先用 checkpointer 记住城市）：
  [human]: 我在上海工作。
  [human]: 帮我查一下天气。
  [ai] ai -> tool: weather_expert({'query': '上海天气'})
```

**同一个子代理，无人传递时说「请告诉我城市」，被主代理传递后直接查上海**——这组对照把「隔离」的两面性讲透了：隔离保证了上下文纯净，**代价是「把该传的信息显式传对」成了主代理的责任**（官方把这类设计归为「Subagent inputs」决策：isolated 只传任务描述 / forked 传全部历史）。

**② Handoffs（交接模式）**——机制：**工具更新一个跨轮持久的状态变量**（如 `current_step` 或 `active_agent`），系统读取它改变行为——要么换配置（系统提示词、工具集），要么换 agent。官方明确标注：**这个术语由 OpenAI 提出**（用 `transfer_to_sales_agent` 这类工具调用传递控制权）。

两种实现（官方对照，推荐第一种）：

| 实现 | 机制 | 适用 |
|------|------|------|
| **单 agent + 中间件**（推荐大部分场景） | 一个 agent 动态换配置：中间件拦截每次模型调用，按状态换 system_prompt 与工具集 | 常规多阶段流程 |
| **多个 agent 子图** | 多个独立 agent 作为图节点，交接工具用 `Command(goto=..., graph=Command.PARENT)` 导航 | 需要定制化 agent（如子图本身是带反思/检索的复杂图） |

实测 2d（单 agent + 中间件，三阶段流程）——「按需解锁」的顺序约束完美呈现：

```text
[第 1 轮] 用户: 我的手机屏幕碎了想修。
    [中间件] step=triage | 工具集=['record_warranty']
[第 2 轮] 用户: 华为 P60，还在保修期内。
    [中间件] step=triage | 工具集=['record_warranty']
    [中间件] step=diagnose | 工具集=['diagnose_issue']
[第 3 轮] 用户: 就是昨天摔了一下，屏幕左上角裂了。
    [中间件] step=diagnose | 工具集=['diagnose_issue']
    [中间件] step=resolution | 工具集=['provide_solution']

中间件调用轨迹（step 演进）: [('triage', ['record_warranty']), ('triage', ['record_warranty']), ('diagnose', ['diagnose_issue']), ('diagnose', ['diagnose_issue']), ('resolution', ['provide_solution'])]
```

每个阶段**只解锁当前需要的工具**：triage 阶段模型手里只有 record_warranty（想跳步都没工具可用）；记录后 state 迁移，同一轮内模型重新盘点工具集（diagnose），依次推进。这就是官方说的「顺序约束」——**能力按前置条件解锁**。

一个必须知道的实现细节（补跑 D 实测）：**state 类上的默认值不会自动写入运行时 state**：

```text
[turn1]（模型不调工具，直接回复的场景）：
    [中间件] fallback 读取 step=triage | state keys=['messages']
  turn1 r.get('current_step') = None（注意：类默认值未自动写入）
[turn2]（模型调用工具记录后）：
    [中间件] fallback 读取 step=diagnose | state keys=['current_step', 'device', 'messages']
  turn2 r.get('current_step') = 'diagnose'（工具更新后写入）
```

`SupportState` 里写着 `current_step: str = 'triage'`，但运行时 state 里**初始没有这个键**——第一轮中间件读到的是 `.get('current_step', 'triage')` 的兜底值；直到工具用 `Command(update=...)` 写入，键才出现。**结论：中间件里必须用 `.get(key, default)` 模式读状态，别裸读 `state[key]`**。

实测 2e（多 agent 子图）——官方示例场景（销售 ⇄ 客服）本机复现：

```text
问题: 你们这个设备多少钱？另外它连不上网怎么修？
  [ai] ai -> tool: transfer_to_support({})
  [tool] tool 返回: 已转接到技术支持代理
  [ai] ai -> tool: transfer_to_sales({})
  [tool] tool 返回: 已转接到销售代理
  [ai] ai: 您好，我是销售顾问，很高兴为您服务！
最终 active_agent: sales_agent
```

双问题场景触发了**双向 ping-pong**（销售→技术→销售）——这不是 bug，而是 handoffs 结构的固有属性：**同一时刻只有一个 active agent**，两个领域的请求会在交接间来回。对照组（补跑 C 单方向）链路干净利落：

```text
问题: 我的设备连不上网，怎么修？
  [ai] ai -> tool: transfer_to_support({})
  [tool] tool 返回: 已转接到技术支持代理
  [ai] ai: # 设备连不上网 — 排查指南
最终 active_agent: support_agent
```

> ⚠️ 官方在 subgraph handoffs 部分专门警告：**交接时要显式控制上下文**——把 `AIMessage`（触发交接的调用）与配对的 `ToolMessage`（交接回执）一起传过去，**只传这一对，不要传子代理的完整历史**（否则接收方会被无关的中间推理干扰，token 也跟着涨）。本课实测代码严格遵循了这一模式。

**③ Router（路由模式）**——机制：**一个路由步骤分类输入，分派给一个或多个专职 agent（可并行），结果综合为统一回答**。实现上用 `Command(goto=...)`（单 agent 路由）或 `Send(...)`（并行扇出到多个 agent）。

实测 2f（多领域分类 + 并行 + 综合）：

```text
问题: 我们研发同事去上海出差，住宿能报多少？顺便说下我们平台的进展。
[分类] 命中领域: ['finance', 'tech']
模型调用总数: 7 次（分类 1 + 各领域代理 + 综合 1）
并行结果 2 条：
综合回答: 综合多来源信息，关于您询问的两项内容答复如下：
```

一个真实世界的观察：**被分派的两个 agent 里，tech 其实答不了报销问题**（它在自己的知识库里搜索后如实回复「暂无相关信息」），而综合步骤聪明地只采纳了有效信息。这暴露了 router 的依赖：**分类的准确度决定了有多少「无效分派」**——分类错了，agent 空跑，用户还可能收到一份「掺了空结果」的综合。

官方在此有三个关键提醒（核对于 2026-09）：
- **Router vs Subagents 的区别**：router 是「一次分类步骤」（通常单次 LLM 调用或规则，无对话记忆）；subagents 是「一个有记忆的监督者跨轮动态调度」——需要多轮自适应编排时选后者。
- **Stateless vs Stateful**：无状态 router 每次请求独立（简单、可预期）；要支持多轮对话，官方推荐两条路——把 router 包成工具交给一个有状态的对话 agent（tool wrapper），或自己做完整的历史管理（**后者要小心**：官方原文警告多轮下「对话可能感觉不流畅」，并建议多轮场景直接考虑 handoffs 或 subagents）。
- **每次路由都有成本**：router 的「每次请求重新分类」在重复请求场景不省调用（性能对照实测见知识点 3）。

**④ 三模式结构差异对照**（官方四维表 + 本课实测补充）：

| 维度 | Subagents | Handoffs | Router |
|------|-----------|----------|--------|
| 控制流 | 一切经过主代理 | 控制权在状态/agent 间传递 | 分类步骤一次性分派 |
| 用户交互 | 无（只有主代理对外） | 各状态/agent 直接对用户 | 浅（仅最终综合输出） |
| 上下文 | 天然隔离（子代理内部不可见） | 单 agent 型天然连续；子图型需显式设计 | 各 agent 独立，综合层汇总 |
| 并行 | ✅（一次 turn 多子代理） | ❌（顺序流转） | ✅（Send 扇出） |
| 多轮记忆 | 主代理持有 | 状态跨轮持久 | 默认无（可包成工具补救） |
| 本课实测 | 4 calls / 并行 8 calls | 三阶段迁移 + 双向交接 | 7 calls（含分类与综合） |

#### 示例演示

见上文 2a-2f 与补跑 C/D。完整代码：`playground/lesson-12-multi-agent-lab.py`（站二）与 `-fix.py`（补跑 C/D）。

#### 常见误区

- **以为「子代理之间可以互相聊天」**：subagents 模式下子代理只与主代理交互（工具式调用）；agent 之间直接传递控制权是 handoffs 的领域。
- **以为「handoffs 只有子图一种实现」**：官方**推荐单 agent + 中间件**（更简单）；子图实现只用于需要定制化 agent 的场景，而且要自己做上下文设计。
- **以为「state 里声明的默认值拿来就能用」**：实测证明类默认值不写入运行时 state（补跑 D）——中间件必须 `.get(key, default)` 兜底。
- **以为「router 分派出去就没事了」**：分类错了会空跑；多个结果还要综合（多一次调用）——router 的「简单」是有前提的：**领域边界清晰、分类可依赖**。

#### 一句话记住

> 三种核心模式按「控制权」区分：subagents 一切经主代理（隔离+并行）、handoffs 状态驱动接力（顺序+多阶段）、router 一分类二分派三综合（并行+无状态）。

### 知识点 3：进阶模式与选择

> 🧭 第 3/3 步｜承接：三种核心模式解决「怎么协作」——本步解决「还有哪些形态」与「到底选哪个」→ skills / custom workflow + 决策框架

#### 一句话定义

**Skills（技能模式）**——把专业能力打包成「按需加载的技能」，**单个 agent 保持控制权**，用时才把专业提示词与知识装进上下文（渐进式披露）；**Custom workflow（自定义工作流）**——用 LangGraph 自定义执行流，**确定性逻辑与 agentic 行为混合编排**（顺序/分支/循环/并行皆可），每个节点可以是普通函数、一次 LLM 调用或一个完整 agent（核对于 2026-09）。

#### 直觉建立（类比）

- **Skills = 专家带手册上班**：他不把整套手册背在脑子里（不预载全部领域知识），只在接到某类任务时**翻开对应那本**（load_skill）；翻过一次后手册摊在桌上（在对话历史里），同类任务不用再翻。
- **Custom workflow = 工厂流水线**：哪些工位用机器（确定性节点：检索、校验、数据变换——不花 LLM 的钱）、哪些工位用工人（agentic 节点：需要判断与生成的环节），完全由你设计；官方一句妙语：**router 模式本身就是 custom workflow 的一个实例**。

> 💡 **类比的边界**：skills 加载的是「提示词与知识」（不注册新代码能力——除非扩展用动态工具注册）；custom workflow 的确定性节点里**真的没有模型**（本课实测的 retrieve 节点就是一个纯向量检索，零 LLM 调用）——这是它最大的经济性来源。

#### 核心原理

**① Skills 的机制与实测**。最小实现就是一个 `load_skill` 工具 + 系统提示词告知可用技能（官方示例结构）：

```python
@tool
def load_skill(skill_name: str) -> str:
    """加载专业技能包。可用技能：sql_expert / legal_reviewer"""
    return SKILLS[skill_name]   # 技能内容 = 一段专业提示词
```

官方关键特征：**提示词驱动**（技能主要就是专业提示词）、**渐进式披露**（按需才出现）、**团队分发**（各团队独立维护技能）、**轻量组合**（比完整子代理简单）、**引用意识**（技能可引用脚本/模板等资源）。

实测 3a——**「加载技能真的改变了行为」的对照实验**（同一个 SQL 任务）：

````text
[A 有技能] 帮我写一条 SQL：查询用户表里最近 7 天注册的用户。
模型调用: 2 次
  [ai] ai -> tool: load_skill({'skill_name': 'sql_expert'})
  [tool] tool 返回: [技能已加载: sql_expert] 你是 SQL 专家。写查询时必须遵守：
          1) 禁止 SELECT *，必须显式列出字段； 2) 时间过滤用 WHERE，不要全表扫描；
  [ai] ai: 以下按 MySQL 语法给出（表名/字段名请按实际调整）：
          ```sql SELECT id, username, email, created_at FROM users WHERE created_at >= DATE_SUB(CURDATE(), INTERVAL 7 DAY) ORDER BY created_

[B 无技能对照] 帮我写一条 SQL：查询用户表里最近 7 天注册的用户。
模型调用: 1 次
  回答: ```sql SELECT * FROM users WHERE created_at >= CURRENT_DATE - INTERVAL '7 day'; ```
````

对照点：技能里写着「**禁止 SELECT \***」，A 组（加载技能后）显式列出了字段；B 组（无技能）**直接 `SELECT *`**——完全违反。补跑 E 的同任务完整版更清楚：

```text
| SELECT
|     user_id,
|     username,
|     nickname,
|     email,
|     mobile,
|     register_time,
|     source_channel,
|     status
| FROM users
| WHERE register_time >= DATE_SUB(CURDATE(), INTERVAL 7 DAY)
|   AND register_time <  DATE_ADD(CURDATE(), INTERVAL 1 DAY)
| ORDER BY register_time DESC
| LIMIT 1000;
| 性能提示：`register_time` 直接做范围比较（不在列上套 `DATE()`/`YEAR()` 等函数），可命中 `(register_time)` 单列索引或 `(status, register_time)` 复合索引，避免全表扫描
```

8 个显式字段 + 时间范围过滤 + 性能提示——技能里的三条规则条条落实。**同一模型，加载与否 = 两种专业度**。

再看「渐进式披露」的经济学（补跑 B2，这个实验第一次做错了，值得引用其修正过程）：首轮测试忘了开 checkpointer，导致两轮是**两个独立会话**（技能不会留存），turn2 依然 3 次调用；修正为有状态会话后：

```text
turn1 模型调用: 3 次
  -> load_weather_skill
  -> get_weather
turn2 模型调用: 2 次
  [ai] -> tool: get_weather
  [tool]: 南京：晴，22°C，湿度 40%，东南风 2 级
```

**turn1 = 3 次、turn2 = 2 次**：技能装进上下文的「一次性成本」只用付一次，后续同类任务直接复用——这就是渐进披露的账本（与官方性能表「skills 重复请求 3→2 次」一致）。**顺带一条工程教训：测试「上下文复用了没有」之前，先确认会话到底有没有状态（checkpointer）**——否则量到的是两次独立会话。

**② Custom workflow 的机制与实测**。官方核心洞察一句话：**可以在任意 LangGraph 节点里直接调用 LangChain agent**——于是「确定性逻辑」与「agentic 行为」在同一个图里自由混搭。本课实测（3b + 补跑 A）：一个三段式 RAG 流水线——

```text
节点轨迹: rewrite(模型) -> retrieve(确定性) -> agent(agentic)

[rewrite] '年假怎么请' -> '年假 申请 流程 方法'
[retrieve] 命中 3 块: ['01-考勤与休假制度.md', '01-考勤与休假制度.md', '01-考勤与休假制度.md']
回答: 根据《01-考勤与休假制度.md》v3.2，年假申请方式如下：
  1. **提交渠道**：通过 **OA 系统**提交年假申请。
  2. **提前时间**：需**提前 2 个工作日**申请。
  3. **请假单位**：年假最小请假单位为 **0.5 天**。
  4. **可休天数**：按连续服务年限计算： - 入职满 1 年不满 3 年：每年 **5 天**
  5. **有效期**：当年年假可结转至**次年 3 月 31 日**，逾期清零。
```

三个节点三种性质：**rewrite 是模型节点**（花了 1 次 LLM，换来更好的检索词）、**retrieve 是确定性节点**（不花 LLM，直接调课 11 的向量检索）、**agent 是 agentic 节点**（基于资料组织回答，还能调工具）。官方教程里的「WNBA 统计助手」是同一结构（rewrite → retrieve → agent），本课做了同构复现。

> 📌 一个诚实的记录：这个实验的首跑版本**检索质量不佳**（整文档入库、k=2，答案块没被检索到，模型如实回答「无法确认年假请假流程」）；补跑改用课 11 的切分方案（chunk_size=300/overlap=60，k=3）后命中答案并完整作答。**教训与课 11 如出一辙：流水线再好，检索不到位就是白搭**——custom workflow 不会自动修复上游质量问题。

**③ 模式选择：用实测数据说话**。官方性能对比表的核心洞察（调用次数与 token）本课用**同一任务四模式对照**验证（3c + 补跑 B2，任务：「南京今天天气怎么样？」）：

| 模式 | one-shot 调用 | repeat 调用 | 本课实测要点 |
|------|:---:|:---:|------|
| **Subagents** | 4 | 4 | 实测 4/4：无状态设计，每轮重走「主→子→主」全流程 |
| **Handoffs** | — | 2 | 实测 1→3→2（三轮含一次信息补全）：状态保持后重复请求直接执行 |
| **Skills** | 3 | 2 | 实测 3/2（补跑 B2）：首轮加载技能，复用后省 1 次 |
| **Router** | 3 | 3 | 实测 3/3：无状态，每轮重新分类走全流程 |

三个可复用的规律（前两条与官方洞察一致，第三条来自补充观察）：

- **subagents 的中央控制有固定成本**：结果必须流回主代理再汇总，比「直达模式」多一次调用（4 vs 3）——换来的是集中控制与上下文隔离（官方原话意思：这次额外调用提供了 centralized control）。
- **有状态模式（handoffs/skills）在重复请求上省调用**（官方数据为 40~50%；本课实测 3→2）：状态/技能在历史里，第二轮直接开工；**无状态的 subagents 与 router 不省**（4/4、3/3）。
- **多领域任务看并行、单流程任务看状态**：官方多域场景下 subagents 与 router 的 token 效率最高（并行 + 隔离；skills 因为后每次调用都携带全部已加载技能而 token 偏高）；而顺序约束类（如多阶段客服）与重复请求类（如高频 FAQ）是 handoffs/skills 的主场。

**④ 决策速查**（综合官方四维表 + 性能表 + 本课实测）：

| 你的场景特征 | 优先考虑 |
|------------|---------|
| 多领域、结果要统一汇总、需要并行、几乎不直接与子代理对话 | **Subagents** |
| 多阶段流程、每阶段对话对象/话术不同、需要顺序约束 | **Handoffs**（先试单 agent + 中间件） |
| 单 agent 长期在线、技能多但每次只用一两个、追求轻量 | **Skills** |
| 领域边界清晰、每次请求独立、要并行查多个来源再综合 | **Router** |
| 确定性流程为主、只在个别环节需要智能、要把上述模式嵌进更大的编排 | **Custom workflow** |
| 单 agent + 少量工具就能做好的事 | **就先别拆**（官方开篇提醒） |

#### 示例演示

见上文 3a/3b/3c 与补跑 A/B2/E。完整代码：`playground/lesson-12-multi-agent-lab.py`（站三）与两个补跑脚本。

#### 常见误区

- **以为「加载了技能就获得了新能力」**：skills 加载的是**提示词与知识**（行为质量变化，实测 SQL 从 SELECT * 变为显式字段 + 索引建议）；要让技能带来「新的工具」，需要扩展用法（动态工具注册）。
- **以为「custom workflow 里都是 agent」**：恰恰相反——**确定性节点不花 LLM**（实测 retrieve 节点零调用），把钱花在真正需要判断的环节（rewrite/agent）才是工作流的意义。
- **以为「性能对比选模式」能一锤定音**：本课实测与官方数据吻合的部分（subagents 4 calls、skills 3→2、handoffs 状态省调用）都建立在**特定任务形态**上；换任务（例如多域并行）排序会变（官方多域表：subagents/router 9K tokens 最优，skills 15K 偏高）——**先问「我的任务是什么形状」，再看表**。
- **以为「checkpointer 可有可无」**：本课补跑 B2 的翻车实录——没开 checkpointer 时「第二轮复用技能」根本不存在（是两个独立会话）；handoffs 更是必须开（状态跨轮）——**有状态模式的前提是先把状态存好**。

#### 一句话记住

> Skills 是「到用时才翻开的手册」（提示词级、轻量、渐进披露）；custom workflow 是「自己画的流水线」（确定性与 agentic 混编）；选模式的钥匙是你的任务形状——领域多选 subagents、阶段多选 handoffs、技能多选 skills、来源多选 router。

## 第四幕：实操验证

回到第一幕：业务线从 1 条变 4 条，单 agent 提示词与工具清单都在膨胀。以下覆盖 **11 个主实验 + 7 项补跑核查**，全部本机跑通（脚本：`playground/lesson-12-multi-agent-lab.py` 与 `-fix.py` / `-fix2.py` 两个补跑脚本；运行方式：在 `playground/` 内执行 `uv run python lesson-12-multi-agent-lab.py`；证据合并文件 `lc-l12-lab-output.txt`）：

1. **静态上下文成本（1a）**：单 agent 全能架构 1983 字符/每次调用（8 工具 + 四领域知识）vs 拆分后主代理 275 字符、子代理按需 231~907 字符。
2. **单 agent 工具选择（1b）**：8 工具下 2 次调用正确完成跨领域任务（并行调 weather + stock）；**补跑 F**：16 工具下仍精确选中 weather_air——如实记录「未复现选择退化」。
3. **subagents 单体（2a）**：4 次调用（与官方性能表一致）；主会话只见 4 条消息（子代理内部折叠）。
4. **subagents 并行（2b）**：一 turn 三子代理，8 次调用。
5. **subagents 上下文隔离（2c）**：子代理无历史时反问「哪个城市」；主代理从自身历史取出「上海」显式传递后直接查询。
6. **handoffs 单 agent + 中间件（2d）**：三阶段（triage → diagnose → resolution）状态迁移 + 工具集逐阶段解锁；中间件轨迹完整记录。
7. **handoffs 多 agent 子图（2e）**：双问题场景触发销售⇄技术双向交接（ping-pong）；**补跑 C**：单方向问题（纯技术）交接链路干净（销售 → 技术 → 技术作答）。
8. **router（2f）**：模型分类命中 finance + tech 双领域 → Send 并行 → 综合（7 次调用）；观察「无效分派」（tech 答不了报销，综合层只采纳有效信息）。
9. **skills 行为对照（3a）**：加载技能后 SQL 显式列字段（遵守「禁止 SELECT *」）vs 裸 agent 直接 SELECT *；**补跑 E**：完整版 8 显式字段 + 时间范围 + 性能提示。
10. **custom workflow（3b）**：rewrite（模型）→ retrieve（确定性，零 LLM）→ agent（agentic）三段流水线；**补跑 A**：修正检索后完整回答年假问题。
11. **四模式对照（3c）**：同任务（南京天气）调用次数——subagents 4/4、skills 3/3（无状态版）、router 3/3、handoffs 1→3→2；**补跑 B2**：有状态 skills 修正为 3/2（技能复用省调用）。

> **补跑核查**：A（RAG 检索修正——切分 + k=3 后命中答案块）；B/B2（skills 双轮——修正 checkpointer 缺失后验证「复用省调用」）；C（单方向交接）；D（state 观测——类默认值不写入运行时 state，中间件需 `.get` 兜底）；E（技能规则逐条核查）；F（16 工具选择行为）。

> ✅ **回扣场景**：「四条业务线塞不进一个 agent」→ 拆分为四个子代理，主代理只带 275 字符的工具描述（1a）；「拆开之后怎么协作」→ 三种核心模式各自的机制与实测（2a-2f）；「到底选哪个」→ 四模式调用次数对照与决策速查表（3a-3c）。**拆分的收益是隔离与可维护，代价是协作设计——模式选择就是把这份代价花在对的地方。**
>
> ⚠️ 数值说明：以上为 2026-09-16 本机实测；模型回答措辞受采样影响（机制性结论——调用次数、状态迁移、工具选择、消息路径、state 键——不受措辞影响）；单项耗时波动大（同规模 invoke 耗时 3.4s~79.9s 区间，取决于输出长度与网络）；调用计数由回调实测（on_chat_model_start），计数含所有子代理内部调用；本课场景为虚构示例（天气/金融/数据库/办公），生产环境请替换为真实业务域。

## 第五幕：体系收束

> 📍 **全局定位**：本课是阶段 4 的开篇——阶段 3 解决的「单个 agent 如何可控可靠」，本课解决「多个 agent 如何组队」，下一课（课 13）解决「组队之后如何测试与观测」。
> - **与前置课的关系**：课 4 的工具机制是 subagents 的实现载体（**子代理就是工具**）；课 5 的 agent 循环构成主代理的调度循环；课 7 的 checkpointer 是 handoffs 状态跨轮持久化的底座（本课补跑 B2 的反面教材证明了它）；课 8 的中间件是「单 agent 型 handoffs」的实现载体（`wrap_model_call` 动态换配置）；课 9 的上下文工程是全课中心（官方原话：多智能体设计的中心就是上下文工程——「决定每个 agent 看到什么信息」）；课 10 的中断可在子代理内部使用（官方明确支持：子代理需要澄清或审批时可暂停收集输入）；课 11 的检索组件是本课 custom workflow 的节点素材（retrieve 节点）与 router 的知识库变体。
> - **下一步（课 13）**：Testing 与 Observability——多智能体系统的协调链路更长（更多调用、更多分支），「怎么测、怎么看」成为交付前的必修课。
>
> 🔗 **一句话带走**：多智能体是**组织设计**而非数量堆叠——五模式按「控制权在哪」区分，选型看任务形状（领域/阶段/技能/来源四个问句）；而无论选哪种，**上下文工程都是中心**：让每个 agent 只看见它需要的。

## 🐞 常见误区

1. **以为「多智能体一定更强」**：官方开篇即拦截——不是每个复杂任务都需要；本课实测单 agent 在 8 个、16 个工具下均选择正确。「该拆」的真实信号是领域还在增长时上下文成本的固定税与协作可维护性。
2. **以为「拆分会更省钱」**：拆分的总调用数/总 token 可能更高（subagents 4 vs 直达 3；官方多域表中 skills 15K tokens vs subagents 9K）；它省的是**每次调用的上下文税**与**团队可维护性**——要按任务形状算账。
3. **以为「handoffs 就得用多 agent 子图」**：官方推荐单 agent + 中间件（更简单）；子图方式只留给「需要定制化 agent」的场景，且要自己做上下文裁剪。
4. **以为「state 里声明了默认值就能读」**：补跑 D 实测——类默认值不写入运行时 state，第一轮读到的是 `.get` 兜底值；用 `.get(key, default)`，别裸读。
5. **以为「技能加载一次就永久生效」**：前提是会话有状态（checkpointer）；无状态会话每轮都是新会话，技能要重新加载（首跑 B 的翻车与 B2 的修正）。
6. **以为「router 天然支持多轮对话」**：默认无状态、每轮重新分类；官方建议多轮场景考虑 handoffs 或 subagents（或把 router 包成有状态 agent 的工具）。

### ⏳ 与过时说法对照（写前核对 + 实测发现的差异）

| 旧说法（网上教程 / 直觉） | 现状（官方文档 + 本课实测） | 依据 |
|---|---|---|
| 「多智能体 = 让多个 AI 互相聊天」 | 五种模式各有明确的控制流设计；「互相聊天」不是任一模式的形态——子代理只见工具界面、handoffs 是状态迁移、router 是一次分派 | 官方五模式定义 |
| 「多开 agent 分担任务 = 降本」 | 调用与 token 的成本结构因模式而异（实测 4/4、3/2、3/3）；省钱点在「上下文隔离」而非「更多 agent」 | 3c + 官方性能表 |
| 「工具超过 N 个必须拆」 | 实测 8 与 16 个工具均选择正确——退化呈「趋势」而非「红线」；拆的真正理由是可维护性与固定成本 | 1b + 补跑 F |
| 「handoffs 是 LangChain 发明的」 | 术语由 **OpenAI** 提出（工具调用传递控制权）；LangChain 将其整理为可实现的模式 | 官方 handoffs 页注 |
| 「skills 就是加了几段提示词，没什么特别」 | 它是「渐进式披露」机制的载体——概念上与 Agent Skills / llms.txt 同源；实测改变模型行为（SQL 质量对照）且重复请求省调用（3→2） | 3a + 补跑 B2 |
| 「state 声明的默认值可以直接用」 | 类默认值不写入运行时 state（实测 keys=['messages'] → 工具写入后才有 current_step） | 补跑 D |
| 「多智能体系统的核心是调度算法」 | 官方定性：**中心是上下文工程**——决定每个 agent 看到什么；调度只是表象 | 官方总览页 Tip |

## 课后小测

**Q1**：关于「什么时候该拆」，说法正确的是？
- A. 工具数量超过 8 个就必须拆分
- B. 官方的三个拆分别动机是：上下文管理、分布式开发、并行化
- C. 拆分一定比单 agent 省钱
- D. 单 agent 在 16 个工具时必然选错工具

<details><summary>答案与解析</summary>

**答案：B**。A/D 错——本课实测 8 与 16 个工具均选择正确，退化是趋势不是数字红线（1b/补跑 F）；C 错——拆分的总调用/总 token 可能更高（subagents 4 vs 3；多域下 skills 15K vs subagents 9K），省的是「每次调用的上下文固定税」与可维护性。

</details>

**Q2**：关于 handoffs 模式，说法正确的是？
- A. 只有「多个 agent 子图」一种实现方式，官方推荐这种
- B. 状态变量由工具更新（返回 Command），系统据此动态换 prompt/工具集或路由
- C. state 类里声明的默认值会自动写入运行时 state，中间件可直接读取
- D. 双问题场景下 handoffs 能同时激活两个 agent 并行处理

<details><summary>答案与解析</summary>

**答案：B**。A 错——官方推荐「单 agent + 中间件」（更简单），子图方式留给定制化场景；C 错——补跑 D 实测类默认值不写入 state，需 `.get(key, default)` 兜底；D 错——同一时刻只有一个 active agent，双领域请求会 ping-pong（2e 实测），并行是 subagents/router 的能力。

</details>

**Q3**：关于 skills 与 custom workflow，说法正确的是？
- A. skills 加载后一定马上注册新工具，否则没用
- B. custom workflow 的确定性节点（如检索）也需要调用 LLM
- C. 有状态会话下 skills 重复请求省调用（实测 3→2）；custom workflow 的 retrieve 节点零 LLM 调用
- D. custom workflow 只能用确定性逻辑，不能包含 agent

<details><summary>答案与解析</summary>

**答案：C**。A 错——skills 主要是提示词与知识（行为质量变化，3a 实测 SQL 从 SELECT * 到显式字段），「注册新工具」属于扩展用法；B 错——确定性节点不花 LLM（实测 retrieve 零调用）；D 错——恰恰相反，官方的核心洞察是「任意节点都可以调用完整 agent」（rewrite/agent 节点即 agentic 节点）。

</details>
