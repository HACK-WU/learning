# 场景 6：改了一版提示词，"感觉更好"但没有证据（经典设计题）

**场景描述**：为了优化回答质量改了一版系统提示词，团队都觉得"应该更好"；一周后客诉上升，没人说得清是哪次发布引起的。

**🔒 先自己想 30 秒**：怎么把"改了就慌"变成"改完心里有数"？

三层测试各管什么（单元 / 集成 / Evals）？"Evals"和"感觉"差在哪？出了问题，tracing 能回答"这一单为什么这样答"吗？CI 里怎么跑"真链路"又不烧钱？

<details><summary>📖 展开解法</summary>

### 解法一览（效果按"回归覆盖 / 维护成本"对比）

| 解法 | 效果（覆盖 / 成本） | 代价 | 适用边界 |
|------|-------------------|------|---------|
| A · 三层测试（单元 / 集成 / Evals） | 快反馈 + 真验证 + 行为断言 | 编写与维护成本 | 常规开发主线 |
| B · 轨迹断言（Evals 回归集） | "该做的动作有没有做"可回归 | 需要构造参考轨迹 | 每次改提示词 / 工具 |
| C · tracing 接入 | 每次运行可回放（含工具链）；"这一单为什么这样答"可查 | 需要 key / 平台；**启动前配好** | 排障与优化 |
| D · 录制回放（cassette） | 离线复现真实调用（CI 友好，6.66s → 1.85s） | 录制文件要管理 | CI 跑"真链路" |

### 各解法详解（含关键代码）

#### 解法 A（单元层）：剧本模型——把"代码逻辑"与"模型智商"分开测

```python
# 节选自 playground/tests_l13/（import 以测试套件为准）
class ScriptedToolModel(GenericFakeChatModel):
    """剧本模型 + 工具支持：剧本里已预设 tool_calls，绑定时原样返回自身。"""
    def bind_tools(self, tools, *, tool_choice=None, **kwargs):
        return self
```

> 为什么这么写：**所有内置 fake 模型的 `bind_tools` 都未实现**（课 13 实测的官方文档盲区）——挂了工具的 agent 直接传 `GenericFakeChatModel` 会抛 `NotImplementedError`。补 3 行子类即可让"工具调用链"进入秒级单测（本项目单元测试 5 项 0.40s）。

#### 解法 B（Evals 层）：轨迹断言——不比对文本，只核对"该做的动作"

```python
from agentevals.trajectory.match import create_trajectory_match_evaluator

# 参考轨迹（期望行为）：查订单 → 发起退货 → 告知结果
REFERENCE = [ ... ]

evaluator = create_trajectory_match_evaluator(trajectory_match_mode='superset')

# 一次"没办成事"的运行（只查了订单和物流，没有发起退货）
print(evaluator(outputs=missed, reference_outputs=REFERENCE)['score'])
# → False：缺「必须调用的工具」apply_return，当场判失败
```

> 为什么这么写：**回复措辞 100% 在飘，但"该调的工具"不该飘**——把关键行为锁进确定性检查，这是"跑一次看看"永远给不出的保证（课 13 实测：路径分岔 5 次跑出 4 种路径）。

#### 解法 A（工程分流）：pytest marker——默认跑快的、显式跑慢的

```ini
[pytest]
markers =
    integration: tests that call real LLM APIs
addopts = -m "not integration"
```

> 为什么这么写：集成测试真调模型（慢、要 key、有金额成本），日常开发默认跳过；CI / 发布前显式 `-m integration` 跑全量。

#### 解法 D：录制回放——CI 跑"真链路"而不烧钱

```python
# 录制回放（pytest-recording）：首次真调录制，之后离线回放
# 课 13 实测：6.66s → 1.85s；端点不可达时回放照常通过（离线证明）
# 写法见 playground/tests_l13/
```

> 为什么这么写：回放能抓住"真实请求形状"的回归（比 mock 更真），又不依赖网络与额度。**排查陷阱**：cassette 失配时异常被包装成 `Connection error`——别被它带偏（见 08 故障模式 8）。

#### 解法 C：tracing——给每次运行留证

```text
# 环境变量在进程启动前配好（实测「固化」行为：中途改不生效）
LANGSMITH_TRACING=true
LANGSMITH_API_KEY=<YOUR_API_KEY>
```

> 为什么这么写：无 key 时追踪**静默降级**（业务照跑、trace 没了）——配完必须"跑一次、看一眼"确认收到，再宣布接入完成。

### 替代路线（非本课程技术栈）

| 替代方案 | 思路 | 与本课程解法的差异 |
|---------|------|------------------|
| 平台化评测（LangSmith datasets / experiments） | 数据集 + 实验对比 + 趋势追踪 | 规模化、可视、可协作；需要平台接入与 key |
| 网络层 mock（直接拦截 HTTP 层做固定响应） | 不录 LangChain 调用，mock 更底层 | 与控制流解耦；但 mock 贴近实现细节，模型行为变化感知弱 |

### 推荐路径（递进，不是一次全上）

1. 先 A：单元（假模型、秒级）+ 集成（真调用、跑批）+ Evals（轨迹）——本项目三层套件离线 ≈1 秒可回归
2. 关键场景补 B（把"客诉过的问题"转成断言）
3. 线上问题多 → C；CI 要"真"且省钱 → D

### 什么情况下此方案不适用

- 原型阶段：全套测试是负担——但"每次改提示词至少跑一次固定 case 集"是底线
- 别把 Evals 做成"花架子"：没有失败即报警的回归集，等于没有
