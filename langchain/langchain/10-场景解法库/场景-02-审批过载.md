# 场景 2：高风险操作要人把关，但人工审不过来（规模压力题）

**场景描述**：给退款加了全量人工审批后，日均 300 笔退款把审批人淹没——小额退款也要等 4 小时，用户投诉"退款慢"；更糟的是审批人开始不看就点"批准"。

**🔒 先自己想 30 秒**：审批是"越多越安全"吗？怎么把审批量降下来，又不把风险放出去？

<details><summary>📖 展开解法</summary>

### 解法一览（效果按"审批量压降 / 风险漏放"对比）

| 解法 | 效果（审批量压降 / 风险控制） | 代价 | 适用边界 |
|------|---------------------------|------|---------|
| A · 全量人工审批 | 0% / 事前零漏放 | 审批成本爆炸 + "橡皮图章化"（不看就批反而更危险） | 极高风险场景专用 |
| B · 条件中断（`when` 谓词分级） | 小额全直通（量级下降最显著） | 阈值是经验值；小额存在拆单风险 | 退款这类"金额即风险"的动作 |
| C · 批量决策（一批一次处理） | 审批交互次数下降 | 仍需逐条看；决策必须按序对齐 | 同类操作堆积时 |
| D · 自动对账 + 抽样复核 | 事前审批再降 | 错误先发生（前提是"可追回"） | 可追溯、可追回的动作 |

### 各解法详解（含关键代码）

> 图：分级审批决策流见 [assets/scene-02-分级审批流.svg](assets/scene-02-分级审批流.svg)——一眼看清哪些请求根本不会打扰人。

#### 解法 B：条件中断——`when` 谓词让审批"看参数办事"

给 `interrupt_on` 的配置里加 `when` 谓词：**谓词返回 `True` 就停（要审批）、返回 `False` 就放行**。

```python
def only_large_amount(req):
    """金额超过 50 元才进审批；小额直通。"""
    amount = req.tool_call["args"].get("amount", 0)
    return amount > 50

HumanInTheLoopMiddleware(
    interrupt_on={"process_refund": {
        "allowed_decisions": ["approve", "reject"],   # 退款禁止改参数（edit）
        "when": only_large_amount,                    # 条件放行
    }},
)
```

> 为什么这么写：`when` 的语义是"判定是否需要人工决策"——**不打扰是设计目标**（课 10 实测：外部地址停、内部域名直通，同一工具两种命运）。`allowed_decisions` 只开 `["approve", "reject"]` 是刻意的：退款金额不该由审批人手改参数，要改就 reject 走新指令。

#### 解法 A：全量审批——基线形态（对比用）

```python
HumanInTheLoopMiddleware(interrupt_on={"process_refund": True})   # True：全决策都允许（approve/edit/reject/respond）
```

> 为什么给这段：它是**对照组**——不设 `when` 时该工具每次调用都停（课 10 实测：1a 外部地址被拦、2e 加谓词后直通）。先看清"全量停"长什么样，才知道 `when` 替我省掉了什么。

#### 解法 C：批量决策——一批中断一次提交

一个 turn 里模型可能一次发起多个高风险动作，中断会**打包成一批**；恢复时把决策按**提案顺序**逐个对齐提交。

```python
# decisions 与提案顺序一一对应：第一条 approve、第二条 reject（其余类似）
decisions = [{"type": "approve"}, {"type": "reject", "message": "删除操作需要复核，本次先不发。"}]

r2 = agent.invoke(Command(resume={"decisions": decisions}), cfg)
```

> 为什么这么写：**顺序对齐是硬要求**——数量不匹配会报 `ValueError`（课 10 实测 2h）；按序生成决策是"批量审批台"的基本实现。注意：拒绝会生成错误回执进入对话，**模型会据此重新评估计划**（课 10 观察到：被拒后它主动暂停了后续动作）。

#### 解法 D：自动对账 + 抽样复核（流程，无代码）

低风险账号放开自动额度；每日自动对账 + 随机抽样人工复核，把人力留给大额与异常样本。代价是"错误先发生"——仅适用于**可追溯、可追回**的动作。

### 替代路线（非本课程技术栈）

| 替代方案 | 思路 | 与本课程解法的差异 |
|---------|------|------------------|
| 外部审批工作流引擎（BPM / 工单系统） | 把审批搬出 agent，转成工单流转 | 合规模板成熟、多人协作强；但与 agent 上下文断裂，决策要靠回调/轮询送回 |
| 先执行 + 撤销窗口 | 不做事前审批：幂等执行 + 限时撤销（错了回滚） | 体验最快、审批成本为零；只适用于可追回的动作——不可逆动作不能这么干 |

### 推荐路径（递进，不是一次全上）

1. 先上 B（改造最小：一个 `when` 谓词；本项目默认 50 元阈值的做法）
2. 审批排队明显 → 上 C（批量决策接口）
3. 风控成熟后 → 对低风险账号放开自动额度 + 随机抽样（D），把人力留给大额

### 什么情况下此方案不适用

- 监管要求"逐笔人工"的业务不能分级自动化
- 别用"用户等级"直接决定豁免（等级可以刷）——分级依据要用风险信号（金额、行为），不是身份标签
