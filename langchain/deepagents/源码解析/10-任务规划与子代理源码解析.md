# 源码解析 · 子代理上下文创建（isolated vs fork）

> 对应课程：[第 10 课：任务规划与子代理](../stages/4-委派与上线/lessons/10-任务规划与子代理.md) ｜ 模块：`deepagents.middleware.subagents`
> 定位：**配合本课知识点 2 / 知识点 3 使用**——你已经在应用实战里看到现象（isolated 收 2 条、fork 收 5 条），这里解释为什么。
> 版本：`deepagents 0.7.28`（2026-10-21 实测）

## 一句话

子代理的两种上下文模式，本质是 `_validate_and_prepare_state` 里两条完全不同的 `subagent_state` 构造路径：isolated 只塞一条 `HumanMessage(description)`，fork 把父状态全部继承并按 `_FORK_EXCLUDED_STATE_KEYS` 过滤后重放。

## 定位：这段代码在哪

```text
deepagents/middleware/subagents.py
├── _FORK_EXCLUDED_STATE_KEYS（约 50 行）   ← 定义 fork 不能继承的键
├── _FORKED_CONTEXT_KEY   (约 62 行)         ← 标记"我正在 fork 上下文里跑"
├── _validate_and_prepare_state (约 560 行)  ← 两分支的核心
├── task / atask          (约 720 行)         ← 入口
└── _return_command_with_state_update (约 745 行) ← 结果提取
```

## 核心机制：一条函数，两条路径

```python
def _validate_and_prepare_state(subagent_type, description, runtime):
    subagent = subagents_by_name[subagent_type]

    if _is_forked_subagent(subagent) or _is_forked_compiled_subagent(subagent):
        # ========== fork 分支 ==========
        inherited = {key: value for key, value in runtime.state.items()
                     if key not in _FORK_EXCLUDED_STATE_KEYS}
        inherited[_FORKED_CONTEXT_KEY] = True          # 打上"我是子代理"标记
        subagent_state = {
            **inherited,
            "messages": _fork_messages(
                runtime.state.get("messages", []),
                runtime.state.get(SUMMARIZATION_EVENT_KEY),
                description,
            ),
        }
    else:
        # ========== isolated 分支 ==========
        subagent_state = {key: value for key, value in runtime.state.items()
                          if key not in _EXCLUDED_STATE_KEYS | private_state_keys}
        subagent_state["messages"] = [HumanMessage(content=description)]
    return subagent_runnable, subagent_state
```

### isolated：只有一条消息

`messages` 被整个替换成 `[HumanMessage(content=description)]`。父对话里任何内容——包括你刚在自然语言里透露的项目名、密钥——都不会出现在子代理的输入里。

**实测**（探针 2-A）：子代理收到 2 条（system + description），父对话的 "Alpha" / "SECRET_123" 完全不可见。

### fork：继承 + 过滤

`messages` 是 `_fork_messages(...)` 的结果。它会把你给的 `description` 追加成一条**带前缀说明**的消息：

```text
[The messages above are a prior conversation you are continuing as the
 subagent that was just invoked...]
```

**实测**（探针 2-B）：子代理收到 5 条——system、3 条父对话、1 条承重前缀注入消息。

## 那 7 个"fork 不能继承"的键（约 50 行）

```python
_FORK_EXCLUDED_STATE_KEYS = frozenset({...})
```

它比普通 `_EXCLUDED_STATE_KEYS` 多出几类，目的从注释能读出来：

| 键 | 为什么不继承 |
|----|-------------|
| `SUMMARIZATION_EVENT_KEY` | 压缩事件会被折叠进 fork 的 messages；不保留事件本体 |
| `SUMMARIZATION_SESSION_ID_KEY` | 让子代理生成自己的 session ID，避免和父代冲突 |
| 上一轮的 structured_response | 不能把它误当成 fork 的结果 |
| 已披露的技能工具 | 描述的是"父代理上一次模型调用"，fork 有自己的一次 |
| `_RUBRIC_KEY` | 评的是父代理整体目标，不是 fork 的任务 |
| 中间件私有字段 | 输入输出的最小化 |

这几条的设计意图是：**fork 继承的是"对话内容"，不是"这次调用的状态"**。

## 递归保护：`_FORKED_CONTEXT_KEY` 从哪来、用在哪

- **谁写的**：`task` 在 fork 分支里写 `inherited[_FORKED_CONTEXT_KEY] = True`
- **谁读的**：`task` / `atask` 开头的第一行：

```python
if runtime.state.get(_FORKED_CONTEXT_KEY):
    return _FORK_RECURSION_REFUSAL   # "You are a subagent and cannot delegate..."
```

- **为什么是运行时检查而不是编译期移除**：因为 fork 子代理也需要看到 `task` 工具（它可能被要求"再查一下"），但如果真的调用就拒绝。这样既保留了工具的可见性，又防住了无限递归。

**isolated 情况**：它根本不会装配 `_ForkTaskToolMiddleware`，所以 `task` 不在工具列表里，递归无从谈起。

## 与课 9 的衔接

课 9 说过第三段流叫"隔离"——这就是它在代码里的落地：

- isolated 子代理 = 一次 `HumanMessage` 的费用，把重活里所有中间 token 消化在子代理内部
- fork 子代理 = 平时更少用，因为它把父对话整个又带回来，等于"上一课费劲压下去的东西又回来了"

**设计取舍一句话**：`_validate_and_prepare_state` 的两条路径就是"省 token 的默认"与"省事的例外"——默认还是选择前者。
