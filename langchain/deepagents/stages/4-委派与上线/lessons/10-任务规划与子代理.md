## 第一幕：起源与场景引入

课 9 你理解了"上下文最多放多少"这件事。现在的问题是：**真到了要派活的时候，怎么把活分出去？**

> 🎬 **场景**：主角某天早上升级 `deepagents` 到 0.7。他原本的 agent 每次拿到多步任务都会先写一排 `write_todos`，清清楚楚列出 5 个步骤再开始干。可升级完，指令还是那条指令，代码一行没改——`write_todos` 却再也没出现。
>
> 他以为是自己的 agent 代码写错了。查了半天，工具列表里根本没有 `write_todos`。
>
> **没有报错，没有警告，只是工具消失了。**

这是个"静默行为变更"。项目升级后最隐蔽的一种坑：不崩溃、不报红，但行为真的变了。

你之前学的所有机制，在这一课都会被"派活"这件事串起来：

- 课 7 的技能告诉子代理"开工时手里有什么"
- 课 8 的记忆告诉主代理"哪些事每次都记得"
- 课 9 的压缩告诉主代理"跑久了怎么瘦"
- **课 10 的隔离就是第三段流的落地**：把重活外包，只回结论

```mermaid
flowchart LR
    A["主代理：协调"] -->|"task 工具"| B["子代理：干活"]
    B -->|"只回一份最终报告"| A
    A -->|"写报告"| C["另一个子代理"]
    style A fill:#eef6ff,stroke:#7fb2e5
    style B fill:#f0f8f2,stroke:#86bfa0
    style C fill:#f0f8f2,stroke:#86bfa0
```

> 📌 **一句话本质**：任务规划是"怎么把大目标拆成可跟踪的小步"，子代理是"把其中一些步外包给别人干"。两者可以搭，也可以独立用——甚至很多 agent 一辈子不写 `write_todos`，照样靠子代理把活干完。
>
> ⚖️ **处境对照**：掌握子代理，你第一次能"把工作从长上下文里挪出去"——主代理负责协调每轮几十个 token，重活全在子代理里烧。不掌握，你只能用又大又慢的单层 agent 硬扛，还容易上下文腐化。

## 第二幕：认知冲突

**第一处：升级后行为变了，但代码没报错。**

你第一反应是"我哪行代码写错了"。但工具列表里没有 `write_todos`，说明问题不在你的代码，在框架本身的默认装配变了。

官方 0.7 changelog 白纸黑字：

> `create_deep_agent` no longer includes `TodoListMiddleware` by default, so the `write_todos` tool, `todos` state channel, and todo-planning prompt are absent unless restored with `middleware=[TodoListMiddleware()]`. (#4929)

实测也印证：默认 agent 工具数是 8（`ls / read_file / write_file / edit_file / delete / glob / grep / task`），没有 `write_todos`。加回 `TodoListMiddleware` 后变 9，才出现 `write_todos`。

**这叫"opt-in 变更"**：以前默认就带，现在是你要主动要求。

> 🇹🇸 **TS 侧对照**：`deepagents 1.15.1` 从来没默认带过 `write_todos`，也没有 v0.7 那次"静默移除"。实测 `createDeepAgent({ model, tools: [] })` 工具是 **9 个**：`delete / edit_file / execute / glob / grep / ls / read_file / task / write_file`。
>
> 比 Python 的 8 个多一个 `execute`（TS 侧默认就带 shell 执行能力），少了 `write_todos`。加 `todoListMiddleware()` 后变 10 个。所以"升级后工具从 8 变 7"这套口诀**不适用于 TS**——TS 用户要记的是 9 → 10。

**第二处：文档说 `tools` 是"replaces them entirely"，但实测文件工具还在。**

这是本课最反直觉的发现。官方文档（及不少中文搬运）写：自定义子代理的 `tools` 参数"完全替换"主代理的工具。

实测：声明 `tools=[query_db]` 的子代理，可用工具实际是：

```
['ls', 'read_file', 'write_file', 'edit_file', 'delete', 'glob', 'grep', 'query_db']
```

自定义工具确实只有 `query_db`（`send_email` 没进来），但 **7 个文件工具全都在**。

原因：文件工具不是由 `tools` 参数控制，而是由 `FilesystemMiddleware` 单独装配的——每个子代理默认自带一个完整文件系统中间件。要限制它，得显式传 `FilesystemMiddleware(tools=[...])`（源码注释写得很清楚）。实测传入 `tools=['read_file','ls']` 后，子代理工具降为 2 个。

**这也是"理解机制 vs 背文档"的一次分野**：文档说的"replaces"只对自定义工具成立。

**第三处：子代理是不是"mini 主代理"？它能不能再派子代理？**

直觉上，子代理既然也是 agent，那就是个完整的代理，能再派活。但实测在 fork 模式下，`task` 工具被一个特殊中间件替换成"只会拒绝"的版本：

> "You are a subagent and cannot delegate to another subagent. Complete this task yourself instead of calling this tool again."

这个设计是刻意的（防止子代理无限递归把自己烧进去），但它有几个可推导的后果：Fork 子代理不能继续委派；isolated 子代理则根本没有 `task` 工具（因为 `ForkTaskToolMiddleware` 只在 fork 时装配）。

> ❓ **问题**：这四件事——规划、隔离、继承、禁用——到底在代码里是怎么被组织起来的？五特征里哪几条能实测、哪几条是语义？

### 知识点 1：write_todos 与 v0.7 的 opt-in 变更

> 🧭 第 1/4 步｜承接：开场"工具消失但没报错" → 本步：拆开这个静默变更的来龙去脉
> 本知识点关键点：v0.7 的 opt-in、`write_todos` 三态、加回方式、什么时候值得开、怎么发现

#### 一句话定义

v0.7 起，`write_todos` 任务规划工具**不再是默认装配**——它变成 opt-in，要用一行 `middleware=[TodoListMiddleware()]` 显式加回来。这个变更是静默的（不报错、只是工具不在），所以升级后最容易踩空。

> 🇹🇸 TS 侧的 `write_todos` 也是 opt-in，但原因不同：TS 从来没有默认装过，不是"被移除"。加回用的是 `todoListMiddleware()`（小驼峰，从 `langchain` 包导入，`deepagents` 不导出它）。**所以 TS 用户升级不会遇到本课开场那个"工具消失"故事**——它一开始就不在。

#### 直觉建立（类比）

像公司里以前人人桌上都有一块白板写待办，后来发现多数人不写也干得好，就把白板收起来了。想用的人自己去领一块，不用的人省下桌面空间。

> 💡 **类比的边界**：公司收白板是"省桌面"，v0.7 收 `write_todos` 是"省 token"——每轮都要把规划提示和工具 schema 带进上下文，官方实测默认轮次从 ~6000 token 降到 ~2000，降幅 65%。白板不占运行成本，但规划工具每个循环都占。

#### 核心原理

**加回方式（唯一正解）**：

::: code-group

```python [Python]
from langchain.agents.middleware import TodoListMiddleware
from deepagents import create_deep_agent

agent = create_deep_agent(
    model=model, backend=backend,
    middleware=[TodoListMiddleware()],
)
```

```typescript [TypeScript]
import { todoListMiddleware } from "langchain";   // 注意：不是 deepagents 导出
import { createDeepAgent } from "deepagents";

const agent = createDeepAgent({
	model,
	middleware: [todoListMiddleware()],
});
```

:::

> 🇹🇸 TS 侧导入源是 `langchain`（`TodoListMiddleware` 类在那里被包装成 `todoListMiddleware()` 工厂函数）。写 `import { TodoListMiddleware } from "deepagents"` 会拿到 `undefined`，`middleware: [undefined]` 又不会报错——只是静默不生效，是本课第一个坑。

**`write_todos` 的三态与持久化**（官方资料确认）：

- 工具内部维护一个任务列表，每项状态是 `pending` / `in_progress` / `completed`
- 状态持久化在 **agent state** 里（`todos` channel），跨调用可见
- 它是给 agent 的"轻量规划层"，不是中断机制——agent 想写就写

**它值不值得开**（官方 0.7 release notes 原话，三条）：

1. **长多步任务**：需要显式计划跨很多轮保持不跑偏
2. **能力较弱的模型**：需要更多脚手架，避免漏步骤、忘记线程
3. **UI 面向的用例**：可见的计划和进度，和底层执行同样重要

官方自己承认：在三类模型、三类基准上的实测里，关闭 todos 反而奖励略高、成本略低。所以它现在不是默认——**默认值是"省"，按需才开**。

**怎么发现（关键生存技能）**：

::: code-group

```text [Python]
工具列表里没有 write_todos ──┬─ 你从没写，那没事（省 token）
                             └─ 你以前写过现在没了 ──► 先数工具数
                                     │  默认 8 个（无 execute）
                                     └─ 其实提示词里直接写"先列计划"也能让模型规划
```

```text [TypeScript]
工具列表里没有 write_todos ──┬─ 正常，TS 一直默认不带
                             └─ 加了 todoListMiddleware() 还是没有 ──► 查导入源
                                     │  默认 9 个（含 execute），加 todo 后 10 个
                                     └─ 从 langchain 导入；deepagents 没有这个导出
```

:::

**一个更稳的替代**：即使不开 `write_todos`，你仍然可以在系统提示里要求"先列计划"，模型的"通用规划能力"不依赖这个工具。`write_todos` 的价值在于它**结构化 + 持久化 + 可被工具更新**，不是"让模型想做计划"。

#### 235 词内的关键代码路径

默认 agent 的工具数实测：Python 是 **8**，加回后 **9**；TS 是 **9**（多 `execute`），加回后 **10**——多出的都是 `write_todos`。

同时注意：Python v0.7 还顺带把默认系统提示从"带通用指导语"改成"空"，这也是为什么升级后实测系统提示是 0 字符。**升级后行为变化往往不止一处，先数工具、再测系统提示，是排查静默变更的第一步。**

> 🇹🇸 TS 侧同样默认系统提示为空（实测第一段 system 长度 0 字符），但那是设计如此，不是"被移除"。TS 排查静默变更的入口是**数工具 + 看中间件栈名**（默认 5 条：`FilesystemMiddleware → subAgentMiddleware → SummarizationMiddleware → patchToolCallsMiddleware → UnsupportedContentMiddleware`）。

#### 常见误区

- ❌「是我代码写错了」——没报错、工具不在列表，先查版本，再查装配
- ❌「默认就应该带」——v0.7 起默认不带，官方实测关了更好
- ❌「`write_todos` 是唯一做计划的方式」——它有结构化和持久化优势，但通用模型也自带计划能力
- ❌「所有模型都受益于 todos」——官方实测多数模型关闭反而更好，只有弱模型和 UI 场景需要
- 🇹🇸 ❌「从 deepagents 导入 `TodoListMiddleware`」——它从 `langchain` 导出，且是工厂函数 `todoListMiddleware()`
- 🇹🇸 ❌「TS 默认 8 个工具」——是 9 个（多 `execute`）；Python 才是 8 个

#### 一句话记住

> v0.7 把规划从默认收进抽屉：要写待办，主动开 `TodoListMiddleware`；官方实测多数场景关了更好，弱模型和 UI 例外。

### 知识点 2：task 工具与子代理执行五特征

> 🧭 第 2/4 步｜承接：已理解规划 → 本步：拆开子代理这个执行单元，看它到底怎么跑
> 本知识点关键点：内建 task、五特征、默认 general-purpose

#### 一句话定义

主代理通过内建 `task` 工具创建临时子代理；子代理有五条执行特征——**全新上下文（可选）、自主到完成、单份报告、无状态、上下文高效**。这五条决定"什么活该派出去、什么活不该派"。

#### 直觉建立（类比）

子代理是**外包的合同工**：

- 你给他一句活，他干了半天，最后交一份报告（不是一堆过程文件）。
- 你不关心他中途查了多少资料——只要报告符合要求。
- 下次你再找他，他又从零开始，不记得上次说过什么。

> 💡 **类比的边界**：合同工是有记忆的，子代理没有（默认）。这一点是子代理设计里的"信息损失"，也是它省 token 的来源——你为了效率主动接受"丢过程"。

#### 核心原理

**`task` 工具怎么来**（源码确认）：

`create_deep_agent` 里只要 `inline_subagents` 非空，就装配 `SubAgentMiddleware`，主代理就拿到 `task`。参数只有两个：

::: code-group

```python [Python]
task(description="...", subagent_type="...")
```

```typescript [TypeScript]
// 同样是这两个字段，schema 实测 shape = ['description', 'subagent_type']
task({ description: "...", subagent_type: "..." })
```

:::

**一个防呆细节**：`task` 的 schema 专门 `forbid` 未定义键。为什么？模型偶尔会把真正的指令塞进它自己编造的键（比如 `prompt`），只留 `description` 里一个标签——这样派出去的子代理只拿到标签、干了个寂寞，却还"成功"了。所以凡是 `description` 之外出现任何键，直接报错打回。

::: code-group

```text [Python]
# 实测：task 带 prompt 键 → 工具层直接打回，子代理根本没被调用
Error invoking tool 'task' with kwargs {'description': '标签', 'prompt': '真正的指令在这里', ...}
  with error: prompt: Value error, Unexpected argument 'prompt'; put all instructions
  for the subagent in `descrip...
```

```text [TypeScript]
// 实测：带 prompt 键 → 不报错，多余键被静默丢弃
父代理拿到的 tool 结果: "报告"
子代理收到的 description: "标签"     ← prompt 里的"真正的指令"根本没传进去
```

:::

> 🇹🇸 **这是本课第一处"防呆不对称"**：Python 会把多余键打回给模型看（模型下一轮能自我纠正），TS 是 Zod `.strip()` 静默剥掉——**模型永远不知道自己塞错了键，只会一直拿到"标签"级指令，然后干出一个空壳报告**。TS 侧排查"子代理产出很水"时，值得先看主代理的原始 `tool_calls.args` 有没有多余键。

**五特征逐条拆**（带实测证据）：

| # | 特征 | 性质 | 实测/源码证据 |
|---|------|------|--------------|
| 1 | 全新上下文（默认）| 运行形态 | 子代理只收到 2 条消息：system + 你的 `description`；测试父对话里的"小明/Alpha"完全看不到（两侧一致）|
| 2 | 自主执行到完成 | 运行形态 | `subagent.invoke(state, config)` 一直跑到最后一条消息 |
| 3 | 只回一份最终报告 | 交互协议 | Python：工具内部跑 2 轮（含工具调用 + 600 字符噪声），父代理只拿到 14 字符"最终报告：找到 3 条要点。"；TS：子代理跑 3 轮（两轮调工具），父代理只拿到最后那句 |
| 4 | 无状态，不能多次回话 | 交互协议 | 每次 task 都是新实例；`description` 里必须写清"最终要返回什么" |
| 5 | 隔离换高效 | 存在理由 | 重活的所有中间 token 都在子代理内部消耗，压缩成一份报告才回到主上下文 |

**特征 3 的实现细节**（`_return_command_with_state_update`）：子代理返回前，会**从后往前找最后一条有文本的 AIMessage** 作为报告。为什么这么做？因为 Anthropic 偶尔在成功结尾后又发一条空的 `end_turn` 消息——如果直接转发空的，父代理就拿到一条啥也没有的 ToolMessage。

> 🇹🇸 TS 侧实现同名同义，也有这个"从后往前找第一条非空"的逻辑。实测两种边界：子代理最后一条是空 `AIMessage("")` 时，父代理仍拿到前一条"最终报告甲"；子代理中间两轮都在调工具时，父代理只拿到第 3 轮的文本。**所以"子代理报告为空"在两侧都不会发生——它一定会找到点什么，哪怕是很早之前的一句"先查一下"**（这也是为什么 `description` 要写清输出格式）。

- ❌「子代理能记住上次的话」——无状态，每次新实例

### 知识点 3：isolated vs fork

> 🧭 第 3/4 步｜承接：已理解子代理执行形态 → 本步：加一个维度——它要不要继承父对话
> 本知识点关键点：默认 isolated、fork 继承、取舍、何时必须 fork

#### 一句话定义

`mode` 决定子代理能否看到父对话：**isolated**（默认）只看到你给的 `description`；**fork** 继承父代理完整对话历史，像"接着刚才的话继续说"。取舍是：fork 省重复说明，但吃 token，还会把父上下文里的噪声一起带进去。

> 🇹🇸 TS 侧字段名和取值完全一致（`mode?: "isolated" | "fork"`，默认 `isolated`），`"handoff"` 也仍是合法旧别名（实测通过，行为等同 `isolated`：子代理只收到 1 条 human 消息）。但**消息条数不同**——见下面的实测对照。

#### 直觉建立（类比）

- **isolated**：给外包商一张任务单，他只看这张单。
- **fork**：把整个会议室搬给他——所有历史记录、你刚才跟别人说的话、甚至跑题的内容，他全看得见。

> 💡 **类比的边界**：fork 的"继承"不是复制粘贴，而是把父对话注入成一条带前缀说明的消息（`[The messages above are a prior conversation you are continuing as the subagent...]`）。它带着"我知道这是继承上下文"的元信息。

#### 核心原理

**isolated 的实测**（探针 2-A）：

::: code-group

```text [Python]
子代理收到的消息: 2 条
  0. [system] '你是检索专家。'
  1. [human]  '去查一下 deepagents 的 subagents 文档'
父对话里的 "小明" / "Alpha"：完全看不到
```

```text [TypeScript]
子代理收到的消息: 2 条
  0. [system] '你是检索专家。'
  1. [human]  '去查资料'
父对话里的 "小明" / "Alpha"：完全看不到
```

:::

**fork 的实测**（探针 2-B）：

::: code-group

```text [Python]
子代理收到的消息: 5 条
  0. [system] ''                    ← 一条空 system
  1. [human]  '请帮我调研一下子代理机制'
  2. [ai]     '好的，我派个人去查。'
  3. [human]  '顺便说下我叫小明，项目叫 Alpha'
  4. [human]  '[The messages above are a prior conversation you are continuing...'
含 "小明": True；含 "Alpha": True
```

```text [TypeScript]
子代理收到的消息: 4 条              ← 比 Python 少一条
  0. [human]  '请帮我调研一下子代理机制'
  1. [ai]     '好的，我派个人去查。'
  2. [human]  '顺便说下我叫小明，项目叫 Alpha'
  3. [human]  '[The messages above are a prior conversation you are continuing...'（571 字符）
含 "小明": True；含 "Alpha": True
不写 systemPrompt 时：一条 system 都没有
写 systemPrompt 时：变成 5 条，system 排在最前面
```

:::

两者的差别在最后一条：fork 注入了完整的父对话 + 一段"你现在是子代理、接着上面的话说"的前缀（源码注释 `_FORKED_SUBAGENT_TOOL_NOTE` 说这段前缀"承重"——没有它，模型会看到"不可变"字样而拒绝委托给需要继承上下文的子代理）。

> 🇹🇸 **为什么 TS 少一条**：Python 侧不管你有没有写 `system_prompt`，都会塞一条 system（内容可能是空串）；TS 侧只在 `systemPrompt` 非空时才加。这带来一个实际差别：**TS 的 fork 子代理如果不写 `systemPrompt`，它连"你是子代理"这层身份提示都没有**，只能靠最后那条 571 字符的前缀说明知道自己是谁。想让 fork 子代理有稳定的行为基线，TS 侧建议显式给一句 `systemPrompt`。

**取舍表**：

| 维度 | isolated | fork |
|------|----------|------|
| 看到什么 | 只有 `description` | 完整父对话 |
| token | 少 | 多（父对话全部带进去）|
| 噪声 | 无 | 父上下文里的跑题话也进来 |
| 何时用 | 任务自包含 | 任务需要父对话里的具体细节 |
| 能否递归 | 无 task | 有 task 但被拒绝 |

**一个被忽略的交互**：fork 还继承主代理的自定义中间件列表（`middleware` 字段注明：fork 继承父代理中间件，同名替换、异名追加）。所以 fork 不只是"继承对话"，是"继承整个装配"。

> 🇹🇸 TS 侧的注释写得更具体：fork 会"mirror 父代理的 prompt-producing middleware（skills / memory / 自定义）"，从而重建一份**等效**的系统提示；代价是如果子代理自己的 `model` 与父代理不同，缓存前缀会对不上。另外 TS **明确禁止** fork 子代理自己声明 `skills`（实测抛错 `SubAgent 'fk' cannot set skills under mode: "fork"; the parent's skills are inherited instead.`），Python 的报错文案是 `cannot set skills under mode='fork'`——同一个约束，两套文案。

**什么时候必须 fork**：当子代理需要父对话里"只有父代理才知道"的细节时——比如父代理刚跟用户确认过某个偏好，子代理要基于那个偏好写代码。

#### 示例演示

::: code-group

```python [Python]

    model=model, backend=backend,
    subagents=[
        {"name": "writer", "description": "接着用户的偏好写报告",
         "mode": "fork"},   # 继承父对话
    ],
)
```

```typescript [TypeScript]

const agent = createDeepAgent({
	model,
	subagents: [
		{
			name: "writer",
			description: "接着用户的偏好写报告",
			mode: "fork",          // @experimental

```

#### 常见误区

- ❌「fork 不消耗额外 token」——它把父对话整个带进去
- ❌「只用 fork，省得重复说明」——省说明但吃 token，还带噪声
- ❌「fork 是稳定 API」——源码注释明确标注 experimental，可能在未来版本变化
- ❌「子代理能再派子代理」——fork 的 task 被替换成拒绝版本，递归是显式禁止的
- 🇹🇸 ❌「fork 子代理不写 `systemPrompt` 也没事」——TS 侧一条 system 都不带，比 Python 少一层身份提示
- 🇹🇸 ❌「fork 子代理可以自己声明 `skills`」——两侧都抛错，父代理技能自动继承

#### 一句话记住

> isolated 只见任务单、省 token、无噪声；fork 继承整个父对话和中间件，用 token 换省事，还可能带进噪声——只有任务真需要父上下文时才值得。

### 知识点 4：自定义子代理与关掉子代理

> 🧭 第 4/4 步｜承接：已会选模式 → 本步：造专用子代理、以及彻底不要子代理
> 本知识点关键点：声明方式、SubAgentMiddleware 存续条件、关掉 task、递归风险

#### 一句话定义

自定义子代理用声明式字典定义（name / description / prompt / tools 等）；`task` 工具的存在条件是「至少一个同步子代理」。**要彻底去掉** `task`，必须同时做到「profile 关掉默认子代理」加「不传任何同步子代理」，而且不能用 `excluded_middleware`。

> 🇹🇸 **TS 侧结论完全不同，这是本课最大的一处分叉**：TS 没有 `profiles` 模块、没有 `general_purpose_subagent` 开关，`createDeepAgent` 也不接受 `generalPurposeAgent` 参数。实测四种写法（`subagents: []`、`generalPurposeAgent: false`、两者都给）**`task` 都还在**。TS 侧能做到的极限是：把可用子代理类型清空（`task` 的描述里那栏变空），然后让模型调到它时**直接抛异常**而不是返回一句错误文案。<br>换句话说：**Python 能把 `task` 从工具列表里抹掉，TS 不能。**

#### 直觉建立（类比）

像给外包公司列供应商名录：每个供应商（子代理）有名字、擅长的活、给它的工具。你（主代理）照着名录分派。
而"彻底关掉"像把整个外包目录删掉——删掉后你手里就没有 `task` 这个按钮了。

> 💡 **类比的边界**：真实的供应商你能打电话再找回来；关掉后 `task` 工具从工具列表消失，主代理想派也派不了。除非改代码。

#### 核心原理

**声明方式**（核心字段）：

| 字段 | 必填? | 说明 |
|------|------|------|
| `name` | ✅ | 主代理在 `task` 里用的名字 |
| `description` | ✅ | 主代理靠它决定何时派——要具体、动作导向 |
| `system_prompt` | 建议 | **不继承**主代理的；工具用法和输出格式放这里 |
| `tools` | 可选 | 继承主代理工具；设置后**只替换自定义部分**，文件工具仍全量（除非显式传 FilesystemMiddleware 限制）|
| `model` | 可选 | 默认主代理同款；可传更强/更省钱的 |
| `skills` | 可选 | **自定义子代理不继承**主代理技能，要显式传路径 |
| `interrupt_on` | 可选 | 子代理级审批（课 11 展开）|
| `response_format` | 可选 | 结构化输出，父代理直接拿 JSON |

> 🇹🇸 TS 字段名逐个对照（驼峰 + 顺序无关）：`system_prompt → systemPrompt`、`interrupt_on → interruptOn`、`response_format → responseFormat`，其余同名。TS 侧**多两个字段**：`mode`（isolated / fork）与 `permissions`（完整替换父代理权限，不是合并）。TS 侧**少一个**：没有 `description` 的等价"prompt"字段，`systemPrompt` 就是唯一入口。

**一个实测修正文档的点**：`tools` 不是"完全替换"——文件工具由 `FilesystemMiddleware` 单独装配。要限制文件工具，得传 `middleware=[FilesystemMiddleware(backend=..., tools=[...])]`。实测传入 `tools=['read_file','ls']` 后，子代理工具从 8 个降到 2 个。

::: code-group

```text [Python]
A) tools=[query_db]，父有 query_db + send_email
   子代理工具: ['ls','read_file','write_file','edit_file','delete','glob','grep','query_db']  ← 8 个
   含 send_email: False   含任务: False
B) 不声明 tools
   子代理工具: 主代理全部工具（含 query_db，不含 task）
C) tools=[query_db] + FilesystemMiddleware(tools=['read_file','ls'])
   → 文件工具降到 2 个
```

```text [TypeScript]
A) tools=[query_db]，父有 query_db + send_email
   子代理工具: query_db, ls, read_file, write_file, edit_file, delete, glob, grep   ← 8 个
   含 send_email: false
B) 不传 tools
   子代理工具: query_db, send_email, ls, read_file, write_file, edit_file, delete, glob, grep  ← 9 个
C) tools=[query_db] + FilesystemMiddleware({ tools: ["read_file","ls"] })
   子代理工具(3): query_db, ls, read_file
D) 不配任何东西的子代理
   子代理工具(8): send_email, ls, read_file, write_file, edit_file, delete, glob, grep
   → 子代理默认文件工具里没有 execute，也不带 task（isolated）
```

:::

> 🇹🇸 注意两处数字：**TS 子代理的默认文件工具是 7 个（不含 `execute`），主代理是 8 个文件工具 + `task` = 9 个**。所以"tools 设了也没减多少"这个错觉在 TS 侧更明显——你的 1 个自定义工具加上 7 个默认文件工具，正好凑成 8 个。

**`task` 的存续条件**（源码确认）：

```text
if inline_subagents:  → 装配 SubAgentMiddleware → 才有 task
```

所以「只要还有任何一个同步子代理，task 就在」。默认那个 general-purpose「通常」就是它存在的理由——除非 profile 把它禁了。

**彻底关掉 `task` 的官方路径**（源码 graph.py:827 + 文档双重确认）：

::: code-group

```python [Python]
from deepagents.profiles import (
    HarnessProfile, GeneralPurposeSubagentProfile, register_harness_profile,
)
register_harness_profile(
    "openai",
    HarnessProfile(general_purpose_subagent=GeneralPurposeSubagentProfile(enabled=False)),
)
```

```typescript [TypeScript]
// 不存在等价写法：deepagents 1.15.1 没有 profiles 模块
// 也没有 general_purpose_subagent 开关，createDeepAgent 不接受 generalPurposeAgent
// 下面这四种写法实测 task 都还在（工具数 9，含 task: true）
//   createDeepAgent({ model, tools: [] })
//   createDeepAgent({ model, tools: [], subagents: [] })
//   createDeepAgent({ model, tools: [], generalPurposeAgent: false })      ← 参数被忽略
//   createDeepAgent({ model, tools: [], subagents: [], generalPurposeAgent: false })
```

:::

需要**两个条件同时成立**（Python，实测 5e 验证）：
1. profile 里 `general_purpose_subagent.enabled is False`
2. `subagents=` 里没有任何同步子代理

实测效果：工具从 8 → 7，`task` 消失。一旦再传入任何一个同步子代理，`task` 立刻回来。

**TS 侧能做到什么**（实测 5 全部四组 + 6 组）：

| 写法 | 工具数 | 含 task | 调到 `task` 时 |
|------|:---:|:---:|---|
| 默认 | 9 | ✅ | 正常派活 |
| `subagents: []` | 9 | ✅ | 正常派活（派给 general-purpose）|
| `generalPurposeAgent: false`（参数不存在） | 9 | ✅ | 正常派活，参数被静默忽略 |
| 两者都给 | 9 | ✅ | 同上 |
| `createSubAgentMiddleware({ generalPurposeAgent: false, subagents: [] })` 顶掉默认 | 9 | ✅ | **抛异常**：`invoked agent of type general-purpose, the only allowed types are `（后面是空）|
| 拿裸对象顶掉 `subAgentMiddleware` | 8 | ❌ | 没这个工具可调 |

最后一行的"裸对象顶掉"是**非官方 hack**：`middleware: [{ name: "subAgentMiddleware", tools: [] }]` 靠同名原位替换把整个子代理中间件换成一个空壳。它确实能让 `task` 消失，但也一并干掉了子代理能力——不是"关掉委派"，是"拆掉委派机制"。**不要在生产里这么写**，本教程只把它当机制演示。

> 🇹🇸 所以 TS 用户的正确答案是：**你关不掉 `task`，但你可以让它无人可派**。用 `createSubAgentMiddleware({ generalPurposeAgent: false, subagents: [] })` 顶掉默认中间件，`task` 会留着（描述里"Available agent types"那栏变空，描述长度从 1419 → 1054 字符），模型真去调时抛异常。代价是异常会冒到调用方，需要你自己 catch。

**一个必经的坑**：别想用 `excluded_middleware` 移除 `SubAgentMiddleware`——文档明确说这是**故意拒绝**的（它是核心脚手架）。唯一官方路径是上面的 profile 方式。

> 🇹🇸 TS 侧没有 `excluded_middleware` 这个概念，但有等价的"同名原位替换"通道（课 3 讲过）：`middleware` 里给一个 `name === "subAgentMiddleware"` 的条目，就会原位置顶掉默认那一条。这解释了为什么 `createSubAgentMiddleware(...)` 能生效，也解释了为什么裸对象也能生效——**它不校验类型，只认 `name`**。这既是逃生通道，也是踩坑入口。

**递归风险**：isolated 子代理没有 task，fork 子代理有但被拒绝（`_FORK_RECURSION_REFUSAL`）。所以 DAG 式的多层委派，只会发生在你自己声明"子代理的子代理"时——模型天然无法制造无限递归。

> 🇹🇸 两侧的递归防线实测**完全一致**：isolated 子代理工具清单里没有 `task`（7 个文件工具）；fork 子代理清单里有 `task`（8 个），但调用会被替换成拒绝版本，返回同一句文案。

#### 常见误区

- ❌「`tools` 会清掉文件工具」——文件工具独立装配，要看 `FilesystemMiddleware`
- ❌「自定义子代理继承主代理技能」——不继承（general-purpose 才继承）
- ❌「`excluded_middleware` 能去掉 task」——被故意拒绝，只有 profile 方式
- ❌「子代理可以无限嵌套」——模型无法，fork 被拒、isolated 没工具
- 🇹🇸 ❌「`generalPurposeAgent: false` 能关掉 general-purpose」——这个参数只在 `createSubAgentMiddleware` 里，`createDeepAgent` 会静默忽略
- 🇹🇸 ❌「`subagents: []` 就没子代理了」——`task` 还在，general-purpose 还在，照样能派活
- 🇹🇸 ❌「子代理默认文件工具和主代理一样」——子代理 7 个（无 `execute`），主代理 8 个文件工具 + `task`

#### 一句话记住

> 造子代理看字段，关掉子代理看条件：profile 禁默认 + 不传同步，task 就消失；文件工具独立于 tools，要限制得找 FilesystemMiddleware。

## 第五幕：体系收束

四个知识点走完一条完整的"派活"链路：

- **调度**（知识点 1）回答"要不要先做计划"——默认不写，需要才开
- **执行单元**（知识点 2）回答"派出去的活怎么跑"——五特征决定什么适合外包
- **上下文边界**（知识点 3）回答"子代理要不要看父对话"——isolated 换效率，fork 换省事
- **装配**（知识点 4）回答"怎么造和怎么关"——声明式 + 存续条件

> 🇹🇸 **四个知识点里，只有第 2、3 条的"结论"是跨语言通用的，第 1、4 条的执行细节两侧都不一样**。第 1 条两侧都是 opt-in，但成因不同（Python 是 v0.7 主动移除，TS 从来没默认带过）；第 4 条的差异最大——Python 能把 `task` 从工具列表里抹掉，TS 不能。所以本课"体系收束"这一节，你只需要记住那三句跨语言成立的判断（任务要自包含才值得派、过程不回主上下文、子代理默认不能再派），剩下的落地写法按语言分支查前面的知识点即可。

这一课十五条特征和四个开关，串出阶段 4 的完整答案：

| 课 | 问题 | 答案 |
|---|---|---|
| 课 10 | 活怎么分出去 | 计划 + 子代理（隔离）|
| 课 11 | 关键操作要交给人吗 | 审批闸门（interrupt）|
| 课 12 | 活能并行/中途改吗 | 异步 + 动态 |
| 课 13 | 敢上线吗 | 开关清单 + 容错 + 流式 |

一句话收束整课：**任务规划把大目标拆成可跟踪的小步，子代理把其中一些步外包出去——外包的本质，是主动接受"过程不回来"，换来主上下文永远保持小巧干净。**

## 课后小测

**Q1**：你升级 deepagents 到 0.7 后，发现 agent 不再写 `write_todos` 了。最可能的原因是？
- A. 你的代码写错了某个参数
- B. v0.7 把 `TodoListMiddleware` 改成默认关闭（opt-in）
- C. 模型不支持规划工具
- D. 工具的 schema 变了

<details><summary>答案与解析</summary>

**答案：B**。v0.7 changelog #4929：`create_deep_agent` 不再默认包含 `TodoListMiddleware`。这是静默变更——不报错只是工具不在。加回：`middleware=[TodoListMiddleware()]`。

> 🇹🇸 **TS 侧同样选 B，但理由要换**：TS 从来没有默认带过 `write_todos`，不存在"v0.7 移除"这件事。加回的写法也不同——`import { todoListMiddleware } from "langchain"`（小驼峰工厂函数），`deepagents` 包不导出这个符号，写 `import { TodoListMiddleware } from "deepagents"` 会拿到 `undefined`，而 `middleware: [undefined]` 不报错、静默不生效。

</details>

**Q2**：子代理 `tools=[query_db]`，它能用 `read_file` 吗？
- A. 不能，`tools` 完全替换
- B. 能，文件工具由 `FilesystemMiddleware` 单独装配
- C. 取决于模型
- D. 不能，但能读缓存

<details><summary>答案与解析</summary>

**答案：B**。实测 `tools=[query_db]` 后子代理工具是 8 个（7 文件工具 + query_db）。文档说 "replaces them entirely" 只对自定义工具成立。要限制文件工具得传 `FilesystemMiddleware(tools=[...])`。

> 🇹🇸 **TS 侧同样选 B，数字恰好也是 8**：`SubAgent({ tools: [queryDb] })` 后子代理工具是 8 个——1 个自定义 + 7 个文件工具。巧合的是和 Python 总数一样，但构成不同：TS 的 7 个文件工具里**没有 `execute`**（主代理默认 9 个才含 `execute`），所以"子代理能跑 shell"在 TS 侧默认不成立。

</details>

**Q3**：fork 子代理和 isolated 子代理的核心区别是？
- A. fork 更快
- B. fork 继承父对话完整历史，isolated 只有 description
- C. fork 能递归，isolated 不能
- D. fork 不需要 description

<details><summary>答案与解析</summary>

**答案：B**。实测 fork 收到 5 条消息（含父对话全部内容 + 承重前缀），isolated 只有 2 条。两者都不能递归（fork 的 task 被拒，isolated 没 task）。

> 🇹🇸 **TS 侧同样选 B，但数字要改成 4 条**：fork 实测 4 条（3 条父对话 + 1 条 571 字符的承重前缀），isolated 2 条（一条 systemPrompt + 一条 human）。差的正是那条 system——Python 不管你有没有写 `system_prompt` 都会塞一条（内容可能是空串），TS 只在 `systemPrompt` 非空时才加。所以 TS 的 fork 子代理如果不写 `systemPrompt`，**它连"你是子代理"这层身份提示都没有**。

</details>

**Q4**：为什么子代理的中间过程不会污染主上下文？
- A. 它直接不产生中间过程
- B. 只回最后一条有文本的 AIMessage，中间全部丢弃
- C. 中间过程被压缩成摘要
- D. 主代理内存够大

<details><summary>答案与解析</summary>

**答案：B**。`_return_command_with_state_update` 从后往前找最后一条非空 AIMessage 作为报告。Anthropic 尾部偶发空 `end_turn` 消息会被跳过。实测内部 600 字符噪声，父上下文只多一条 14 字符 ToolMessage。

> 🇹🇸 **TS 侧同样选 B，规则一字不差**：从后往前找第一条有文本的 AIMessage。实测两条边界都成立——子代理跑 3 轮（前两轮调工具）时父代理拿到第 3 轮文本；尾部再挂一条空 `AIMessage("")` 会被跳过，仍拿到前一条有文本的。所以"过程不回来"这件事在两侧都是硬的，不依赖模型厂商。

</details>

**Q5**：想彻底去掉 `task` 工具，正确做法是？
- A. `excluded_middleware` 移除 `SubAgentMiddleware`
- B. profile 关掉 general-purpose 且不传任何同步子代理
- C. 只关掉 general-purpose
- D. 不传 `subagents` 参数

<details><summary>答案与解析</summary>

**答案：B**。两个条件同时成立：`GeneralPurposeSubagentProfile(enabled=False)` + `subagents=[]`。A 被文档明确拒绝；C/D 单独都不够（默认 general-purpose 会自动加，除非 profile 禁）。

> 🇹🇸 **TS 侧这题没有正确答案——因为根本关不掉**。实测四种写法（`subagents: []`、`generalPurposeAgent: false`、两者都给、以及只传其一的变体）**`task` 都还在，工具数都是 9**。原因：`generalPurposeAgent` 不是 `createDeepAgent` 的参数（它只存在于 `SubAgentMiddlewareOptions` 里），传了会被静默忽略；而 `subagents: []` 只是"不额外加子代理"，默认那条 general-purpose 依然在。
>
> TS 侧能做到的两件事：① 用 `createSubAgentMiddleware({ generalPurposeAgent: false, subagents: [] })` 顶掉默认中间件——`task` 工具还在，但可用类型栏清空，调到就抛 `invoked agent of type general-purpose, the only allowed types are `（后面是空）；② 拿裸对象 `{ name: "subAgentMiddleware" }` 顶掉——工具数掉到 8，`task` 真没了，但这等于拆掉整个委派机制，**不要在生产里这么写**。
>
> 一句话记：**Python 关得掉，TS 关不掉，只能让它无人可派。**

</details>

## 🇹🇸 本课双语差异速查

| 差异点 | Python | TypeScript |
|---|---|---|
| 默认工具数 | 8 个（无 `execute`）| **9 个（含 `execute`）** |
| 加回 `write_todos` 后 | 9 个 | 10 个 |
| `write_todos` opt-in 成因 | v0.7 主动移除（#4929）| 从来没默认带过 |
| `todoListMiddleware` 导入源 | `deepagents` 包 | **`langchain` 包，小驼峰** |
| `task` 多余键校验 | `forbid`，报错回模型 | **Zod `.strip()`，静默剥离** |
| fork 消息条数 | 5 条（含一条空 system）| **4 条（无 system）** |
| fork 前缀说明长度 | 约 600 字符 | 571 字符 |
| 子代理默认文件工具 | 7 个，不含 `execute` | 7 个，不含 `execute` |
| 子代理默认能否跑 shell | 不能 | 不能 |
| 关掉 `task` | profile 关 GP + `subagents=[]` ✅ | **关不掉**，只能清空可用类型 |
| 未知 `subagent_type` | 返回 `ToolMessage` 错误字符串，模型可自愈 | **直接 `throw`，整轮挂掉** |
| `mode: "handoff"` 别名 | 合法 | 合法 |
| `fork` + `skills` | 报错 | 报错（文案一致）|
| `excluded_middleware` 移除 `SubAgentMiddleware` | 被拒绝 | 同名原位替换可绕过（不校验类型）|

> 那行"子代理默认文件工具"两侧都是 7 个：`ls` / `read_file` / `write_file` / `edit_file` / `delete` / `glob` / `grep`。**注意 `execute` 只在主代理的默认工具里**（Python 主代理默认 8 个也不含它，TS 主代理 9 个含它），所以两侧的子代理默认都不能跑 shell，要给它加得自己传。
