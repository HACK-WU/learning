## 第一幕：起源与场景引入

前 12 课把一个能"想、分、审、并发"的 agent 搭起来了。但有一个残酷现实：**这些能力在本地跑得再顺，上线那一刻会遇到三个完全不讲情面的第一课**：

- **超时**：竞品调研的 agent 一期以上线，主模型调用 3 秒就超时重启
- **限流**：5 个子代理同时扇出，把 API 配额瞬间打满，后面全是 429
- **进程重启**：半夜某个节点崩了，整个线程状态全没了，第二天从零重来

主角需要的不是新能力，而是一张 **清单**：上线前逐项确认——重试开了几层？进程崩了能恢复到哪一步？模型挂了有没有备选？子代理扇出会不会打爆配额？

> 🎬 **场景引入**：交付前夜的最终检查。主角把 agent 的代码和配置摊在桌面，一项一项打勾。这一课不讲怎么造新工具，而是讲**哪些开关该开、开在哪一层、哪些最容易漏**。

```mermaid
flowchart TD
    A["测试通过（本地）"] --> B["上线暴露三类问题"]
    B --> B1["超时 → 需要重试"]
    B --> B2["429 限流 → 需要次数上限"]
    B --> B3["进程重启 → 需要持久化 + 降级"]
    B1 --> C["容错三件套（知识1）"]
    B2 --> C
    B3 --> D["流式观测（知识2）"]
    D --> E["上线清单（知识3）"]
    C --> E
```

> 📌 **一句话本质**：本课是把前面 12 课攒下的"能力开关"收成一张可勾选的清单，并讲清三类开关分别对应哪一类故障。不引入新机制，只做收束。

> ⚖️ **处境对照**：容错和流式是"无感知的高级感"——配好了用户感觉不到，配错了（或没配）要出事故才觉察。所以这一课的语气不是"跟着我造"，而是"逐项自查：你漏了哪个？"

## 第二幕：认知冲突

**第一处：框架里没有"限流"（rate limit）这个能力。** 骨架知识点 1 的关键点 1 写"限流——控制调用频率与并发"。实测 `langchain.agents.middleware` 里带 Limit 的导出只有两个：

```
ModelCallLimitMiddleware   不能控制频率，只能控制"最多调用几次"
ToolCallLimitMiddleware
```

没有任何 "RateLimit" / "Throttle" 中间件。官方的"fault-tolerance"文档把这一列叫 **"Excessive calls (runaway loops)"（防失控循环）**，而不是"限速"。它防的是**模型在一个死循环里反复调同一个工具、几分钟烧光预算**，不是"每秒 N 个请求"。

::: code-group

```python [Python]
from langchain.agents.middleware import ModelCallLimitMiddleware, ToolCallLimitMiddleware

agent = create_deep_agent(
    model=model,
    tools=[search_tool],
    middleware=[
        # 防失控：最多 N 次模型调用 / 工具执行
        ModelCallLimitMiddleware(thread_limit=50, run_limit=50, exit_behavior="end"),
        ToolCallLimitMiddleware(tool_name="search_tool", run_limit=3, exit_behavior="end"),
    ],
)
```

```typescript [TypeScript]
import { createDeepAgent } from "deepagents";
import { modelCallLimitMiddleware, toolCallLimitMiddleware } from "langchain";

const agent = createDeepAgent({
  model,
  tools: [searchTool],
  middleware: [
    // 防失控：最多 N 次模型调用 / 工具执行
    modelCallLimitMiddleware({ threadLimit: 50, runLimit: 50, exitBehavior: "end" }),
    toolCallLimitMiddleware({ toolName: "searchTool", runLimit: 3, exitBehavior: "end" }),
  ],
});
```

:::

**第二处：401/400 到底重不重试？答案在异常家族里，不在错误码里。** 骨架说"哪些错误可重试（网络 / 429 / 5xx），哪些不可（401 / 400）"。实测的真相更精确（探针 1-A / 探针 2-A）：

::: code-group

```python [Python]
default_retry_on(exc):
    if isinstance(exc, ModelError):
        return exc.is_retryable      # 只看这个家族
    return True                       # 其他异常（含模拟 401 的 RuntimeError）一律重试
```

```typescript [TypeScript]
// 默认 retryOn 的全部逻辑就这一句（langchain 包 constants.js 的 RetrySchema）
retryOn: (e) => getRetryable(e) ?? true;
// getRetryable 只读 Symbol 标记，不看异常类型、也不看 status 字段
```

:::

实测结果：

| 异常 | is_retryable | 默认重试? |
|------|:---:|:---:|
| `ModelAuthenticationError`（HTTP 401）| False | ❌ |
| `ModelInvalidRequestError`（HTTP 400）| False | ❌ |
| `ModelPermissionDeniedError`（HTTP 403）| False | ❌ |
| `ModelNotFoundError`（HTTP 404）| False | ❌ |
| `ModelRateLimitError`（HTTP 429）| True | ✅ |
| `ModelAPIError`（HTTP 5xx）| True | ✅ |
| 任意普通异常（含 RuntimeError("unauthorized")）| — | ✅ |

所以"401/400 不可重试"**只在异常是 ModelError 子类时才成立**。如果一个 provider 用普通异常（如 `requests.HTTPError`）报 401，`default_retry_on` 会**返回 True 去重试它**——这恰恰是你最不想重试的（重试是浪费、还可能触发更多风控）。这也是为什么官方建议 `retry_on` 要么传具体异常元组、要么传自定义 callable，而不是用默认。

🇹🇸 **TS 侧这一处的结论是"同一个陷阱，两套机制"**。TS 没有 `ModelError` 家族，`getRetryable` 只认 `Symbol.for("langchain.errors.retryable")` 这个标记，**完全不看 `status` 字段**。实测（探针 1-A）用 `createDeepAgent` 装配，八个用例**全部重试 3 次**：

```text [TypeScript]
Error.status=401               调用 3 次｜重试了
Error.status=403               调用 3 次｜重试了
Error.status=429               调用 3 次｜重试了
Error.status=500               调用 3 次｜重试了
裸 Error('unauthorized')        调用 3 次｜重试了
401 打标 false                  调用 3 次｜重试了    ← 打了标照样重试
500 打标 false                  调用 3 次｜重试了    ← 打了标照样重试
500 打标 true                   调用 3 次｜重试了
```

注意最后三行：**明明打了 `stampRetryable(err, false)`，还是重试了**。这不是打标本身失效，而是 `createDeepAgent` 的中间件链会把模型的原始异常包一层 `MiddlewareError`，标记留在 `.cause` 上，而默认 `retryOn` 的 `getRetryable(e) ?? true` 只读最外层：

```text [TypeScript]
retryOn 收到的链: MiddlewareError(marked=undefined) -> Error(marked=false)
```

对照组说明了问题边界（探针 1-B / 1-C）：同样是打标 `false` 的错误，换成 `createAgent` 装配就**只调 1 次**；而在 `createDeepAgent` 下自己写一个沿 `cause` 链找标记的 `retryOn`，也能压回 1 次：

```text [TypeScript]
-- B) 换 createAgent（无 deepagents 中间件链）--
401 打标 false   调用 1 次｜不重试
500 打标 true    调用 3 次｜重试了

-- C) createDeepAgent + 自定义 retryOn 沿 cause 链找标记 --
401 打标 false   调用 1 次｜不重试｜标记=false
500 打标 true    调用 3 次｜重试了｜标记=true
不打标           调用 3 次｜重试了｜标记="unmarked"
```

这条差异的实际后果是：**如果你在 TS 侧依赖 `stampRetryable` 做"这个错误别重试"的精细控制，在 `createDeepAgent` 里必须自己解包 `cause`，否则精细控制静默失效**。Python 侧不存在这个问题（`ModelError.is_retryable` 就在异常自身上，中间件不改写它）。


**第三处：`stream.subagents` 不在 `agent.stream()` 上，在 `stream_events(version="v3")` 上。** 骨架知识点 2 的关键点 2 直接说"用 `stream.subagents`"，但我实测 `agent.stream` / `agent.astream` 上**都没有** `subagents` 属性（探针 5-C），只有 `stream_events(version="v3")` 返回的 `GraphRunStream` 上才有（探针 6-A）。而且同步/异步版本的形态还不同：

```
同步 agent.stream_events(..., version="v3")
  stream.subagents  → 可迭代的子代理句柄
  sub.output        → 普通 dict（值，直接读）
  句柄.messages     → 可迭代

异步 agent.astream_events(..., version="v3")
  先 await 拿 run
  run.subagents     → 也是句柄
  sub.output        → 是 方法，要 sub.output() 才能拿到
  可能是 AsyncIterator
```

**还有一个隐藏得很深的坑**：`stream.subagents` 返回的 StreamChannel **只能订阅一次**（探针 6-B）。两次 `for sub in stream.subagents` 会抛：

```
RuntimeError: StreamChannel already has a subscriber; use .atee(n) for fan-out.
```

需要多个消费者时必须先 `.atee(n)` 分叉。官方文档没提这个，是踩出来的。

🇹🇸 **TS 侧把握手方式全换了，但坑的位置不一样**（探针 8）：

```text [TypeScript]
agent.stream 上有没有 subagents: false        ← 跟 Python 一样，入口不在 stream 上
streamEvents 返回的是 Promise: true（要 await）
await 后是 GraphRunStream
投影：subgraphs=object｜subagents=object｜messages=object｜values=object｜output=object
subagents 是 StreamChannel: true
句柄 name="worker"
  字段类型：output=object（Promise）｜messages=object｜toolCalls=object｜subagents=object
  有没有 status: 没有｜有没有 path: 没有
第二次遍历 → ["worker"]（TS 侧没抛）
有没有 atee: undefined｜有没有 iterate: function
```

三处必须改写认知的地方：

- **`streamEvents` 返回 Promise，不是同步句柄**。Python 的同步版 `stream_events` 直接给你可迭代的 `stream.subagents`；TS 必须先 `await`，否则你在 Promise 上查任何属性都是 `undefined`——我第一次就栽在这里，误判「TS 没有 subagents 投影」。
- **句柄字段少两个，形态全变**。TS 句柄自有属性是 `name / cause / output / messages / toolCalls / subagents`，**没有 `status`、没有 `path`**（Python 两个都有）。`output` 是 **Promise**（Python 同步版是普通 dict、异步版是方法），`messages` / `toolCalls` / `subagents` 都是 `StreamChannel`，不是数组也不是迭代器。
- **单订阅限制在 TS 侧不存在**。`StreamChannel` 没有 `atee` 方法，但**可以多次遍历**（实测第二次遍历仍返回 `["worker"]`，没抛错）。源码注释写的是「Each call returns an independent cursor so multiple consumers can iterate the same channel concurrently.」——所以 Python 那句「必须 `atee` 分叉」在 TS 侧是**用不上的建议**，两边方向相反。

### 知识点 1：容错三件套

> 🧭 第 1/3 步｜承接：开场三类故障（超时/限流/崩溃） → 本步：每类对应一个开关，且说清"开在哪一层"
> 本知识点关键点：重试判定、次数上限（非限速）、降级链路、中间件落点、子代理容错放大

#### 一句话定义

容错三件套是三个"故障→恢复"开关：**重试**（瞬时故障自动再试）、**次数上限**（防失控烧预算）、**降级**（主模型挂了换备选）。配上**持久化**，进程崩了能从最近一步恢复。

#### 直觉建立（类比）

- **重试** = 打电话占线自动重拨（只对占线重拨，不接的号码拨一万遍也没用）
- **次数上限** = 给电话设个"最多打 3 分钟"的闹钟，防止漫无边际聊下去
- **降级** = 打不通主叫号码就自动转语音信箱，至少有个回复
- **持久化** = 记笔记，聊到一半挂了，从笔记恢复接着聊

> 💡 **类比的边界**：电话占线重拨是"所有占线都重拨"，但框架默认对**非 ModelError 的所有异常都重试**——所以要区分"哪种占线该重拨、哪种不该"。

#### 核心原理

**官方把"故障→策略"列成了 6 行**（fault-tolerance 文档）：

| 故障类型 | 谁修 | 策略 | 中间件 |
|---------|------|------|--------|
| 瞬时（网络/限流）| 系统自动 | 指数退避重试 | `ModelRetryMiddleware` / `ToolRetryMiddleware` |
| 模型能恢复（工具输出烂/解析失败）| 模型 | 转成错误 ToolMessage 喂回去 | `ToolErrorMiddleware` |
| 用户能补（缺信息/指令不清）| 人 | 用 `interrupt()` 暂停 | Human-in-the-loop（课 11）|
| 供应商挂 | 系统自动 | 换备选模型 | `ModelFallbackMiddleware` |
| 调用过多（失控循环）| 系统自动 | 每次 run 封顶 | `ModelCallLimitMiddleware` / `ToolCallLimitMiddleware` |
| 意外错误 | 开发者 | 让它炸出来 | 不配中间件 |

**第一层：重试。** 模型调用和工具调用各有一个重试中间件，但语义分开：

::: code-group

```python [Python]
# 模型级：网络超时 / 限流 / 5xx 这类瞬时错误
ModelRetryMiddleware(max_retries=3, backoff_factor=2.0, initial_delay=1.0)

# 工具级：只对会打外网的特定工具重试，别对文件工具重试
ToolRetryMiddleware(max_retries=2, tools=["search", "fetch_url"],
                    retry_on=(TimeoutError, ConnectionError))
```

```typescript [TypeScript]
import { modelRetryMiddleware, toolRetryMiddleware } from "langchain";

// 模型级：网络超时 / 限流 / 5xx 这类瞬时错误
modelRetryMiddleware({ maxRetries: 3, backoffFactor: 2, initialDelayMs: 1000 });

// 工具级：只对会打外网的特定工具重试，别对文件工具重试
toolRetryMiddleware({
  maxRetries: 2,
  tools: ["search", "fetch_url"],
  retryOn: (e) => e instanceof Error && /timeout|ECONNRESET/.test(e.message),
});
```

:::

🇹🇸 **TS 侧选项名与默认值**（源码 `RetrySchema`）：`maxRetries`(默认 2) / `retryOn`(默认 `(e) => getRetryable(e) ?? true`) / `backoffFactor`(默认 2) / `initialDelayMs`(默认 1000) / `maxDelayMs`(默认 60000) / `jitter`(默认 true) / `onFailure`(默认 `"continue"`)。跟 Python 的 `max_retries` / `backoff_factor` / `initial_delay` / `max_delay` / `on_failure` 一一对应，只是驼峰。

退化计算实测（探针 1-C，`initial_delay=0.5, backoff_factor=2.0, max_delay=8.0`）：

```
第 0 次重试前等 0.5s
第 1 次重试前等 1.0s
第 2 次重试前等 2.0s
第 3 次重试前等 4.0s
第 4 次重试前等 8.0s   ← 被 max_delay 封顶
第 5 次仍 8.0s
backoff_factor=0.0 → 恒定间隔（如每次等 2.0s）
```

**第二层：次数上限（不是限速）。** 两件事必须分清：

- `ModelCallLimitMiddleware` 默认 `exit_behavior="end"`——超限后**正常结束**本轮，消息内容是 `Model call limits exceeded: thread limit (3/3), run limit (3/3)`，不会炸
- `ToolCallLimitMiddleware` 默认 `exit_behavior="continue"`——超限后**继续**让模型跑下一轮，它还能尝试别的工具。探针 8-D 实测：限 1 次、模型想调 3 轮，工具实际只执行 1 次，但流程继续

拦截层不同会影响你观测到"上限撞没撞到"：Model 层默认 end（会结束），Tool 层默认 continue（不结束）。**上线前要按"是防失控还是防爆预算"决定要不要改成 end**。

🇹🇸 **TS 侧默认值一致，但 Tool 层多一档**（探针 5）：

```text [TypeScript]
modelCallLimit runLimit=1（想跑 4 轮）→ 实际 1 轮
  末条="Model call limits exceeded: run level call limit reached with 1 model calls"
exitBehavior='error' → 抛出 ModelCallLimitMiddlewareError
toolCallLimit 默认 → 模型 2 轮、tool 消息 2 条
  被拦的那条="Tool call limit exceeded. Do not call 'echo' again."
toolCallLimit exitBehavior='end' → 模型 2 轮｜末条="'echo' tool call limit reached: run limit exceeded (2/1 calls)."
```

两侧默认值一致（Model 层 `"end"` / Tool 层 `"continue"`），但 **TS 的 Tool 层多一档 `"end"`**——Python 只有 `continue` / `error` 两档。这个多出来的档位在"工具撞上限就该整轮收工"的场景下很有用，反过来说，从 Python 迁到 TS 时别以为档位集合一样。


**第三层：降级。** 中间件顺序决定降级是否真正兜底（探针 4）：

```
重试在前、降级在后：  primary → backup1
  primary 只被调 1 次（重试没料可试）就降级
降级在前、重试在后：  primary → primary → primary
  三连重试，最后报错，backup1 根本没被调用
```

::: code-group

```python [Python]
# 推荐：重试在外层（对主模型先重试），降级在内层（重试无效才换模型）
ModelRetryMiddleware(max_retries=2),
ModelFallbackMiddleware("gpt-5.5"),
```

```typescript [TypeScript]
import { modelRetryMiddleware, modelFallbackMiddleware } from "langchain";

// 推荐：重试在外层（数组靠前 = 外层），降级在内层
modelRetryMiddleware({ maxRetries: 2 }),
modelFallbackMiddleware("gpt-5.5"),
```

:::

🇹🇸 两个容易写错的签名差异：`modelFallbackMiddleware(...models)` 是**可变参数**，不是数组——`modelFallbackMiddleware(["a","b"])` 会把数组当成一个模型传进去；要传多个就 `modelFallbackMiddleware("a", "b")`。Python 的 `ModelFallbackMiddleware("gpt-5.5")` 单参数形式两侧同构，但多模型时 Python 收的是位置参数序列、TS 收的是 rest，写起来看起来一样、类型上不一样。

🇹🇸 **重试耗尽后会不会抛，两侧默认行为也不同**（探针 2）：

```text [TypeScript]
onFailure 默认     → 没抛，末条是 AIMessage=true｜文案="Model call failed after 2 attempts with MiddlewareError: http 500"
onFailure='error'  → 抛出 MiddlewareError
```

默认 `onFailure: "continue"` 会把失败**写成一条 AIMessage 塞回对话**，然后流程继续跑。也就是说：**模型全挂了，你的 agent 不会崩，而是拿着一句"调用失败"的假回答往下走**——这在生产里比直接报错更危险，因为它会静默产出错误结论。要它抛必须显式 `onFailure: "error"`。Python 侧同名参数叫 `on_failure`，取值语义同构，但默认值未在本轮实测对比，切换语言时请自己验一遍。

**中间件栈内的落点**（源码 `graph.py` 装配顺序）：
`Filesystem` → `SubAgent` → `_ParentNotifier` → `summarization` → `PatchToolCalls` → `AsyncSubAgent`(若配) → `interrupt` → `UnsupportedContent` → `_ToolExclusion`(若配)，然后才是你传的 middleware 与默认栈：

- **你的中间件名与栈中已有重名（如 `ModelFallbackMiddleware`）** → 按名字**原位替换**，不新增
- **别的新名字** → 插在最后一个 core 之后、profile/缓存/记忆尾之前

**子代理容错：子代理模型不继承主代理的容错中间件**（探针 4-D）。实测：主模型配了 `ModelRetryMiddleware(max_retries=2)`，子代理模型内部抛 `ModelAPIError` 时——**直接被调了 1 次就抛穿**，没有重试，`task` 工具也没兜住（异常变成 ToolMessage 返回，但子代理那次调用已失败）。所以"给子代理加容错"必须显式放进子代理自己的 `model` 里，或者靠顶层的降级/重试覆盖整个扇出路径。这正是关键点 5 说的"容错放大效应"：**一个子代理失败不应让其他几百个白跑**，但也别指望主代理的中间件自动保护子代理。

🇹🇸 **TS 侧"不继承"这条一样成立，但失败形态更硬**（探针 9）：

```text [TypeScript]
主代理配了 retry → 整体仍抛 MiddlewareError
  主模型调用 1 次｜子代理模型调用 1 次（没有重试）
给子代理自己配 retry → 子代理 3 次，末条 "done"
```

差别在**异常往哪走**：Python 至少把异常包成一条 ToolMessage 还给模型，模型还能读到错误、决定下一步；TS 是直接 `MiddlewareError` **抛穿整个 `invoke`**，你在调用方 catch 得到的是一个包装错误，主图状态也就停在那儿了。所以 TS 侧更要在子代理自己的 `model` 上配好容错——指望"顶层兜一下"在这里兜不住。


#### 常见误区

- ❌「有 QPS 限流中间件」——只有调用次数上限，限速要自己在外部网关做
- ❌「401/400 一律不重试」——只有 ModelError 家族按 is_retryable 分支；普通异常默认全重试
- ❌「重试 + 降级随便排」——顺序错了降级根本不会触发（探针 4-C）
- ❌「子代理继承主代理容错」——实测不继承
- ❌「超上限会报错」——Model 层默认 end（结束），Tool 层默认 continue（继续）
- 🇹🇸「在 TS 里 `stampRetryable` 打了标就一定不重试」——`createDeepAgent` 下标记被 `MiddlewareError` 包在 `.cause` 上，默认 `retryOn` 看不到，要自己解包
- 🇹🇸「重试耗尽会抛错」——默认 `onFailure: "continue"` 把失败写成 AIMessage 继续跑，静默产出错误结论
- 🇹🇸「`modelFallbackMiddleware` 收数组」——是可变参数 `(...models)`，传数组会把整个数组当单个模型


#### 一句话记住

> 重试治瞬时，上限防失控（不是限速），降级保最后兜底，持久化保崩溃恢复——子代理要单独配容错，中间件顺序错了降级不触发。

#### 🗣️ 行话对照

| 说你听到的 | 意思 |
|-----------|------|
| "rate limiting" | 框架里没有；只有调用次数上限（budget）|
| "transient errors" | 瞬时错误（网络抖动/429/5xx），值得重试 |
| "excessive calls" | 失控循环，官方把它单列为"A 类故障"防烧预算 |

### 知识点 2：流式与事件流

> 🧭 第 2/3 步｜承接：容错配好了 → 本步：上线后怎么看见子代理在干嘛，以及主流怎么"失真"
> 本知识点关键点：入口是 `stream_events` v3、`subagents` 句柄、单订阅限制、主流拍平失真

#### 一句话定义

事件流（`stream_events` v3）给每个委派的子代理一个**独立句柄**（`stream.subagents`），每个句柄能单独看它自己的消息、工具调用、嵌套子代理和最终输出。主代理的 `stream.messages` 只看得到协调器自己讲的，子代理的细节得从句柄里看。

#### 直觉建立（类比）

- **main stream** = 会议室播报的"主持人总结"，一句话概览，不逐字转述
- **stream.subagents** = 每个分会场的**独立麦克风**：只有你想听某个分会场时，才把它的麦接进来

> 💡 **类比的边界**：分会场麦克风是"接入才出声"（lazy 打开流），不是所有分会场全程录音给你转播——这正是"轻量投影"的含义。

#### 核心原理

**入口不是 `agent.stream()`，是 `agent.stream_events(..., version="v3")`**（探针 6-A）：

::: code-group

```python [Python]
sync_run = agent.stream_events({...}, config=cfg, version="v3")
for subagent in sync_run.subagents:
    print(subagent.name, subagent.status, subagent.path)
    for msg in subagent.messages:
        print(msg.text)
```

```typescript [TypeScript]
const run = await agent.streamEvents(input, { ...config, version: "v3" });
for await (const subagent of run.subagents) {
  console.log(subagent.name, subagent.output);   // TS 侧没有 status / path
  for await (const msg of subagent.messages) {
    console.log(msg.text);
  }
}
```

:::

子代理句柄暴露的字段（官方表格）：

| 字段 | 说明 |
|------|------|
| `name` | 协调器调 `task` 时传的 `subagent_type`（你配置的名字）|
| `messages` | 该子代理自己发的消息（不是主流的）|
| `tool_calls` | 该子代理自己的工具调用 |
| `subagents` | 该子代理再嵌套的子代理 |
| `output` | 该子代理最终状态 |
| `path` | 命名空间路径 |
| `status` | `started` / `completed` / `failed` / `interrupted` |

🇹🇸 **TS 侧句柄少了两个字段，其余全是 `StreamChannel`**（探针 8）：

| 字段 | Python | TypeScript |
|------|--------|-----------|
| `name` | 有 | 有（自有属性）|
| `messages` | 可迭代 | `StreamChannel` |
| `tool_calls` / `toolCalls` | 有 | `StreamChannel` |
| `subagents` | 有 | `StreamChannel` |
| `output` | 同步版是 dict、异步版是方法 | **Promise**（直接 `await`）|
| `path` | 有 | **没有** |
| `status` | 有 | **没有** |

也就是说：Python 里 `subagent.status == "failed"` 这种判断，TS 侧**根本没有对应字段**，你得从 `subagent.output` 这个 Promise 的 resolve / reject 去推断成败。迁代码时这一句最容易被漏，因为 TS 不会报"属性不存在"（`as never` 一写就绕过去了），而是静默给你 `undefined`。


**同步 vs 异步形态不同**（实测，官方没强调）：

```
同步 agent.stream_events(version="v3")
  stream.subagents   可迭代
  sub.output         普通 dict（直接读）
  sub.messages       可迭代

异步 agent.astream_events(version="v3")
  先 await 得到 run
  run.subagents       可迭代
  sub.output          是方法，要 sub.output()
  sub.messages        可能是 AsyncIterator
```

**主流视角为什么"失真"**：主流的 `stream.messages` 只包含协调器自己发的那几句（用户问题、模型回答、工具结果摘要）。子代理内部的推理过程、中间工具调用、再到协调器的对话，**不会逐字进入主流**。如果只挂一个 `stream.messages`，你看到的是"子代理干活 → 返回一行报告"，完全看不见它中间干了什么。要用子代理进度面板，就得连 `stream.subagents` 的句柄。

**单订阅限制**（探针 6-B，文档没提，最容易踩）：`stream.subagents` 的 StreamChannel **只能被遍历一次**。要多个消费者（一个画卡片、一个存日志），必须先分叉：

::: code-group

```python [Python]
# ❌ 会抛 RuntimeError
a = list(run.subagents)
b = [s.name for s in run.subagents]   # 第二次遍历 → RuntimeError

# ✅ 用 atee(n) 分叉
fork_a, fork_b = run.subagents.atee(2)
```

```typescript [TypeScript]
// TS 侧没有 atee，也不需要：同一个 channel 可以多次独立遍历
for await (const s of run.subagents) console.log(s.name);   // 第一次
for await (const s of run.subagents) console.log(s.name);   // 第二次仍返回 ["worker"]，不抛
```

:::

🇹🇸 这条要特别标出来：**Python 的"必须 atee"在 TS 侧是用不上的建议**。TS `StreamChannel` 没有 `atee` 方法（实测 `typeof run.subagents.atee === "undefined"`），但有 `iterate(startAt?)`，源码注释明确写「Each call returns an independent cursor so multiple consumers can iterate the same channel concurrently」。所以两侧在"多消费者"这件事上方向完全相反——把 Python 的 atee 写法照搬到 TS 会直接崩在"方法不存在"，反过来把 TS 的多重遍历写法搬到 Python 会崩在"already has a subscriber"。

**只做"知道有这条路"，不上手造**（关键点 4 的定位）：子代理卡片、待办列表、沙箱 IDE 这些前端页面的具体实现，以及 ACP（Agent Client Protocol，接 IDE）和 AG-UI（给前端交互的协议）两页，本课只告诉你它们是存在的、各解决"谁能看见 agent"的哪个侧面。真做前端归 Phase 3 结课项目。

#### 常见误区

- ❌「`agent.stream().subagents` 能用」——没有，入口是 `stream_events(version="v3")`
- ❌「主流能拍平成子代理全流程」——主流只有协调器视角，子代理细节在句柄里
- ❌「subagents 能遍历多次」——StreamChannel 单订阅，要 atee 分叉
- ❌「同步异步形态一样」——output 一个是值一个是方法
- 🇹🇸「TS 的 `streamEvents` 直接返回句柄」——返回的是 Promise，必须先 `await`，否则查什么都是 `undefined`
- 🇹🇸「TS 侧单订阅也要 atee」——恰恰相反，TS 可多次遍历且没有 `atee` 方法
- 🇹🇸「TS 句柄也有 status / path」——两个都没有，成败要从 `output` 这个 Promise 推断

#### 一句话记住

> 事件流 v3 给每个子代理一个独立麦克风（`stream.subagents`），主流只有一个主持人口径；这个麦克风只能接一次，要多路需 `atee`。

#### 🗣️ 行话对照

| 说你听到的 | 意思 |
|-----------|------|
| "event streaming" | `stream_events(version="v3")`，类型化投影 API |
| "typed projections" | 每个投影（subagents/messages/tool_calls/values）独立迭代器 |
| "subagent handle" | 单个子代理的运行句柄，`.messages` `.tool_calls` `.subagents` `.output` |
| "namespace path" | `path`，标记该事件来自哪个子图 |
| "stream.subagents" | 轻量投影：只在你访问句柄时才开对应流 |

#### 官方文档

- [Event streaming](https://docs.langchain.com/oss/python/deepagents/event-streaming) —— `stream.subagents` 权威用法
- [Streaming](https://docs.langchain.com/oss/python/deepagents/streaming) —— 传统 `stream(subgraphs=True)` 的命名空间方式

### 知识点 3：上线清单与部署选项

> 🧭 第 3/3 步｜承接：容错与流式都懂 → 本步：交付前逐项打勾，指出最容易漏的三项
> 本知识点关键点：checkpointer 缺失的恢复、durability 三模式、沙箱最小权限、版本锁定、八项清单

#### 一句话定义

上线清单是八项可在代码里逐条确认的能力开关，配上前四课学过的机制（memory、subagents、interrupt、async）做定位级提示。最常漏的三项都是"平时测试暴露不出来"的。

#### 直觉建立（类比）

像发车前检查单（pre-flight checklist）：不是每个开关都在每一架飞机上都重要，但漏了某个，出事时才后悔。最容易漏的往往不是"麻烦的"，而是"测试环境里根本触发不了的"。

> 💡 **类比的边界**：发车检查是飞机起飞前一次性确认；线上清单是每次发布前确认一次，不是每次请求都跑。

#### 核心原理

**最容易漏的三项（按踩坑优先级）**：

**① 不配 checkpointer，`interrupt` 就不恢复（最阴）。** 实测（探针 7）：不传 checkpoint 时配 `interrupt_on`，`invoke` **不报错、能正常触发中断**，`out["__interrupt__"]` 有值。但你要用 `Command(resume=...)` 恢复时，直接炸：

```
RuntimeError: Cannot use Command(resume=...) without checkpointer
```

也就是说——**测试时 human-in-loop 看起来"能暂停"，一到真要恢复就挂**。这是测试与上线行为差异最大的一个：本地不配 checkpoint 时模拟审批能走通（因为根本没人真去恢复），上线配了恢复才暴露。这是重复课 11 的结论，但在这里作为"上线检查项"再次强调。

🇹🇸 **TS 侧这条方向完全相反，是本课最危险的一条差异**（探针 7）：

```text [TypeScript]
不配 checkpointer + interruptOn → invoke 直接抛 GraphValueError
  文案="No checkpointer set"
  排障链接=https://docs.langchain.com/oss/javascript/langgraph/MISSING_CHECKPOINTER/
配了 checkpointer → 中断条数 1
  恢复后 tool 消息=["executed"]
```

对比两侧的行为顺序：

| 阶段 | Python | TypeScript |
|------|--------|-----------|
| 第一次 `invoke` | 正常触发中断（`__interrupt__` 有值）| **直接抛 `GraphValueError: No checkpointer set`** |
| `Command(resume=...)` | 此时才抛 `RuntimeError` | 走不到这一步 |

这意味着 **Python 的开发习惯会把你坑在 TS 上**：在 Python 里"不配 checkpoint 也能演示审批流程"，换成 TS 后**连第一次演示都跑不起来**，而且报错发生在 `invoke`，不是在 resume。反过来说，TS 这条更"早失败早发现"——它不会让你带着一个"只能演示不能恢复"的配置上线。但如果你从 Python 迁过来，把 `interruptOn` 配上却忘了 `checkpointer`，本地第一跑就崩，别以为是中断功能坏了。


**② 持久化三模式要按业务选**（going-to-production 文档）：

```
durability="exit"   只在图结束/中断时落盘 → 最快，崩溃丢中间步
durability="async"  异步落盘（默认）       → 崩溃可能丢最后一步
durability="sync"   每步同步落盘           → 最慢，最安全
```

🇹🇸 TS 侧三档取值**字符串完全一样**（`"exit" | "async" | "sync"`，定义在 `@langchain/langgraph` 的 `PregelOptions` 里），默认也是 `"async"`。两处写法差异：一是它不在 `createDeepAgent` 的构造参数里，而是**调用时传**（`invoke(input, { durability: "sync" })`）；二是旧的 `checkpointDuring` 已标记 **deprecated**，别再写。TS 侧的注释原文：「`async`: Save checkpoint asynchronously while the next step executes (default). `sync`: Save checkpoint synchronously before the next step starts. `exit`: Save checkpoint only when the graph exits.」

关键点 1（持久记忆落点）重复课 8：`MemorySaver` 是内存实现，**进程重启全丢**，生产要么换持久化 checkpoint，要么接受"thread 内消息丢失"。关键点 2（沙箱最小权限）重复课 6：`permissions` 只给最小路径，别图省事给根目录。

**③ 版本锁定——v0.7 的静默行为差异必须写进约束。** 课 10 讲过：`write_todos` 从默认带变成 opt-in，升级后**直接消失、不报错**。这是最容易在生产出怪现象的：本地 0.6 开发的 agent，部署到一个 0.7 环境，待办工具没了但日志不报错。当前基线（探针 7-E）：

```
deepagents 0.7.28
依赖约束：langchain>=1.4.6,<2.0.0；langchain-core>=1.6.11,<2.0.0
extras：quickjs(>=0.3.9) / aws / video
```

写进 `pyproject.toml` / `requirements.txt` 的关键是把 `write_todos` 从"环境里有没有"收敛成代码里的显式步骤，或者锁版本到 0.6 行为。

🇹🇸 **TS 侧的版本锁定看的地方不一样**（探针 10）：`deepagents 1.15.1` 自己的 `dependencies` 只有 4 个工具库（`fast-glob` / `micromatch` / `yaml` / `zod`），真正约束你的是 8 个 `peerDependencies`：

```text [TypeScript]
deepagents 1.15.1
peerDependencies:
  @langchain/anthropic: ^1.5.12
  @langchain/core: ^1.2.14
  @langchain/langgraph: ^1.4.10
  @langchain/langgraph-checkpoint: ^1.1.5
  @langchain/langgraph-sdk: ^1.9.23
  @langchain/openai: ^1.6.2
  langchain: ^1.5.10
  langsmith: >=0.7.1 <0.10.0
```

Peer 依赖不满足时 npm 会警告而不是硬失败（pnpm 更严格），所以**锁版本要把这 8 个一起锁**，只锁 `deepagents` 会在某天 `langchain` 小版本漂移后出现"中间件签名不匹配"这类难查的问题。好消息是 TS 侧没有 Python 那种「v0.7 静默移除 `write_todos`」的对应事件——TS 的工具集变更走的是 minor 版本 + changelog，不会静默消失。


**部署选项全景（定位级）**：

- **Managed Deep Agents**（推荐）：LangSmith 托管运行时，author 成项目文件，自带 threads/checkpointer/store，public beta
- **LangSmith Deployment**：需要自定义应用代码/路由/鉴权时直接配
- **自托管 LangGraph**：自定义 Docker、要完全掌控时，用 `langgraph.json` + `langgraph dev` 本地开发
- **前端/协议**：ACP（IDE 对接）、AG-UI（前端交互），本课只到"知道有这条路"

**上线前八项必查清单**（每项都能在代码/配置里勾）：

| # | 检查 | 对应前面哪课 | 漏了会怎样 |
|---|------|:---:|----------|
| 1 | `thread_id` 稳定 + `context` 传用户元数据 | — | 会话串扰 |
| 2 | 持久化 checkpoint（不是 MemorySaver，除非可接受重启丢）| 课 11 | 恢复失败 |
| 3 | `durability` 按业务选 exit/async/sync | 课 13 | 崩溃丢步 |
| 4 | `permissions` 最小路径 | 课 6 | 越权写文件 |
| 5 | 沙箱只装必要依赖 | 课 6 | 暴露面过大 |
| 6 | 版本约束锁 v0.7（含 write_todos opt-in）| 课 10 | 静默丢工具 |
| 7 | 外部做 QPS 限流（框架没有）+ 内部次数上限 | 课 13 | 撞 429 / 烧预算 |
| 8 | 子代理单独配容错（不继承主代理）| 课 13 | 一个子代理带崩整体 |

🇹🇸 这八项 TS 侧**全部适用**，只有第 6 项和第 7 项要改说法：第 6 项不是锁 `write_todos`（TS 没这个静默变更），而是锁那 8 个 peerDeps；第 7 项同理——TS 侧也没有任何 Rate/Throttle 中间件（探针 3 实测 `带 Rate/Throttle 的中间件：(没有)`），QPS 限流一样要在外部网关做。

#### 常见误区

- ❌「MemorySaver 能用于生产」——进程重启全丢
- ❌「配了 interrupt_on 就一定能恢复」——没 checkpointer 恢复时炸（实测）
- ❌「框架自带 429 限流」——没有，QPS 限流要在网关做
- ❌「子代理容错靠主代理」——不继承，要单独配
- ❌「版本随便升」——v0.7 静默移除 write_todos
- 🇹🇸「不配 checkpointer 也能先演示中断」——TS 侧第一次 `invoke` 就抛 `GraphValueError`，跟 Python 相反
- 🇹🇸「锁 `deepagents` 一个包就够」——真正约束在 8 个 peerDeps，peer 不满足只警告不报错
- 🇹🇸「TS 侧工具集也会静默变更」——没有对应事件，变更走 minor + changelog

#### 一句话记住

> 上线八项开关里最容易漏三项：checkpointer（不配则中断不可恢复）、持久化 durable 模式、版本锁定（v0.7 静默丢工具）；QPS 限流框架没有要自己做。

## 第四幕：实操验证（复现与验证）

### 4.1 机制验证：探针带你亲手走一遍

**探针 1：重试真的会重试 401 吗**

```
ModelAuthenticationError(401) → 重试 False   ← 只有 ModelError 家族按 is_retryable 分支
RuntimeError("unauthorized")  → 重试 True    ← 普通异常默认全重试
ModelRateLimitError(429)      → 重试 True
ModelAPIError(5xx)            → 重试 True
```

🇹🇸 TS 侧同一组问题的答案（`l13-production.ts` 探针 1）：

```text [TypeScript]
-- A) 默认 retryOn（只看最外层错误）--
Error.status=401        调用 3 次｜重试了
Error.status=403        调用 3 次｜重试了
Error.status=429        调用 3 次｜重试了
Error.status=500        调用 3 次｜重试了
裸 Error('unauthorized') 调用 3 次｜重试了
401 打标 false           调用 3 次｜重试了    ← 打了标也重试
500 打标 false           调用 3 次｜重试了    ← 打了标也重试
500 打标 true            调用 3 次｜重试了

-- B) 换 createAgent（没有 deepagents 中间件链）--
401 打标 false           调用 1 次｜不重试     ← 标记生效了

-- C) createDeepAgent + retryOn 沿 cause 链找标记 --
401 打标 false           调用 1 次｜不重试｜标记=false
不打标                   调用 3 次｜重试了｜标记="unmarked"
```

TS 侧没有 `ModelAuthenticationError` 这种家族，`getRetryable` 只读 `Symbol.for("langchain.errors.retryable")` **且只看最外层对象**。而 `createDeepAgent` 的中间件链会把模型异常包一层 `MiddlewareError`：

```text [TypeScript]
retryOn 收到的链: MiddlewareError(marked=undefined) -> Error(marked=false)
```

于是 `stampRetryable(err, false)` 打的标记留在 `.cause` 上，默认 `retryOn` 看不到——**这是 TS 侧独有的"精细控制静默失效"**。A 组与 B/C 组的对比就是证据：同一个错误、同一个中间件，只因为装配入口不同，重试次数从 1 变成 3。

**探针 2：中间件里数调用次数**

```
失败 2 次后成功：ModelAPIError 调 3 次、ModelRateLimitError 调 3 次 → 都成功
失败 2 次：ModelAuthenticationError 只调 1 次（不重试）
一直失败：RuntimeError 调 3 次后放弃（max_retries=2）
max_retries=0：只调 1 次（完全不重试）
```

🇹🇸 TS 侧（探针 2）：

```text [TypeScript]
maxRetries=0       → 调用 1 次｜末条="Model call failed after 1 attempt with MiddlewareError: "
失败 2 次后成功     → 调用 3 次｜末条="ok"
onFailure 默认     → 没抛，末条是 AIMessage=true｜文案="Model call failed after 2 attempts with MiddlewareError: http 500"
onFailure='error'  → 抛出 MiddlewareError
```

次数语义两侧一致，但**失败后的去向不同**：Python 那行"放弃"意味着异常往上走；TS 默认 `onFailure: "continue"` 是**把失败写成一条 AIMessage 塞回对话**，`invoke` 正常返回。这一点在观测上很坑——你的日志里看不到异常，只看到模型说了一句"调用失败"。

**探针 3：没有 rate limit 中间件**

```
带 Limit/Rate/Throttle 的导出：只有 ModelCallLimitMiddleware、ToolCallLimitMiddleware
→ 是"调用次数上限"，不是 QPS 限流
```

🇹🇸 TS 侧（探针 3）：

```text [TypeScript]
带 Limit 的导出：ToolCallLimitExceededError, modelCallLimitMiddleware, toolCallLimitMiddleware
带 Rate/Throttle 的中间件：(没有)
```

两侧都是"没有速率限制"。另外 TS 侧的 `deepagents` 包 56 个导出里**一个容错中间件都没有**——`modelRetryMiddleware` / `modelFallbackMiddleware` / `modelCallLimitMiddleware` / `toolCallLimitMiddleware` / `toolRetryMiddleware` 全在 `langchain` 包。所以从 Python 的 `from langchain.agents.middleware import ...` 迁过来时，import 路径要改成 `from "langchain"`，而不是 `from "deepagents"`。

**探针 4：重试与降级的顺序问题**

```
重试在前、降级在后：primary → backup1        ← 降级触发
降级在前、重试在后：primary → primary → primary ← 三连重试，backup1 没被调
子代理模型失败：调 1 次就抛穿主代理（不继承重试，task 也没兜住）
```

🇹🇸 TS 侧（探针 4）：

```text [TypeScript]
重试(外) + 降级(内) → {"primary":1,"backup":1}
降级(外) + 重试(内) → {"primary":3}
```

顺序结论两侧完全一致：**降级必须放在数组靠后（里层）**，放外层时重试把 primary 打满就直接失败，backup 一次没被调。这条可以放心跨语言复用——"重试包降级"是对的，"降级包重试"是白配。

子代理那条 TS 侧失败形态更硬（探针 9）：Python 把异常包成 ToolMessage 还给模型，TS 直接 `MiddlewareError` 抛穿整个 `invoke`。

**探针 5：`stream.subagents` 入口**

```
agent.stream / agent.astream → 没有 subagents 属性
agent.stream_events(version="v3") → 有 subagents（返回 GraphRunStream 投影）
```

🇹🇸 TS 侧（探针 8 前半段）：

```text [TypeScript]
agent.stream 上有没有 subagents: false
streamEvents 返回的是 Promise: true（要 await）
await 后是 GraphRunStream
投影：subgraphs=object｜subagents=object｜messages=object｜values=object｜output=object
subagents 是 StreamChannel: true
```

结论同构：入口都不在 `stream` 上，都在 v3 事件流上。差别是 TS 要先 `await`——**`streamEvents` 返回 Promise，不是句柄**。这一条我在实测中先踩了一遍：直接在 Promise 上查 `"subagents" in run` 得到 `false`，差点得出"TS 没有这个投影"的错误结论。

**探针 6：同步 vs 异步形态 + 单订阅**

```
同步 stream_events v3：
  stream.subagents 可迭代   sub.output 是 dict（直接读）   sub.messages 可迭代
异步 astream_events v3：
  先 await 拿 run           sub.output 是方法（要 call）   sub.messages 可异步迭代

StreamChannel 只能订阅一次：
  第二次 for → RuntimeError: already has a subscriber; use .atee(n) for fan-out.
  run.subagents.atee(2) → 两个独立分支都能看到完整的子代理列表
```

🇹🇸 TS 侧（探针 8 后半段）：

```text [TypeScript]
句柄 name="worker"
  字段类型：output=object（Promise）｜messages=object｜toolCalls=object｜subagents=object
  output 里 messages 条数=2
收到的子代理：["worker"]
第二次遍历 → ["worker"]（TS 侧没抛，跟 Python 的单订阅限制不同）
有没有 atee: undefined｜有没有 iterate: function
```

三条要改写的认知：`output` 是 Promise（不是 dict、也不是方法）；句柄**没有 `status` / `path`**；**可以多次遍历、没有 `atee`**。所以"Python 单订阅要 atee"这条经验在 TS 侧完全反向。

**探针 7：checkpointer 缺失的真实行为**

```
不配 checkpointer + interrupt_on：
  invoke 正常触发中断（__interrupt__ 有值）——测试看起来"能暂停"
  用 Command(resume=...) 恢复 → RuntimeError: Cannot use Command(resume=...) without checkpointer
  → 不配 checkpoint 时，中断只能演示，不能真正恢复
```

🇹🇸 TS 侧（探针 7）——**方向完全相反**：

```text [TypeScript]
不配 checkpointer + interruptOn → invoke 直接抛 GraphValueError
  文案="No checkpointer set"
  排障链接=https://docs.langchain.com/oss/javascript/langgraph/MISSING_CHECKPOINTER/
配了 checkpointer → 中断条数 1
  恢复后 tool 消息=["executed"]
```

TS 连第一次 `invoke` 都不给过，走不到 `resume` 那一步。所以 Python 那套"先演示、后配持久化"的开发节奏在 TS 侧行不通。

顺带记一个写探针时的坑：这个探针第一版我用了一个"永远抛错"的模型桩，结果模型异常先炸、把 `GraphValueError` 盖掉，输出成了"文案=never"。**测某个机制时要保证别的层不抢先报错**——换成能正常发 tool_call 的桩模型才拿到真实结果。

**探针 8：工具级重试与失败策略**

```
不配 ToolRetry：工具失败 1 次,返回 RuntimeError 错误给模型
ToolRetry(max_retries=2)：工具执行 3 次,返回 "failed after 3 attempts"
on_failure="error"：异常直接传播
on_failure="continue"：错误转成 ToolMessage 给模型继续
ToolCallLimitMiddleware 默认 continue：工具被压到 1 次执行，但流程继续跑
```

🇹🇸 TS 侧（探针 6）：

```text [TypeScript]
失败 2 次后成功 → 工具执行 3 次｜tool 消息=["ok"]
一直失败(默认) → 工具执行 3 次｜tool 消息="Tool 'always' failed after 3 attempts with Error"
onFailure='error' → 工具执行 3 次，抛出 Error
```

次数与策略两侧同构。`toolRetryMiddleware` 的 `onFailure` TS 侧取值比 Python 多（含两个 deprecated 别名），日常只用 `"continue"` / `"error"` 两个就够，跟 Python 对齐。

### 4.2 综合自检：我能不能把这个 agent 交付

真要被问"你这 agent 能上线吗"，按这份五步自检走：

```
① 故障枚举：会不会超时 / 429 / 崩溃 / 模型挂 / 失控循环？   → 没枚举全先别谈上线
② 恢复开关：瞬时错误重试了吗？     —— ModelRetry / ToolRetry
③ 防烧预算：上限开了吗？          —— ModelCallLimit / ToolCallLimit
④ 最后兜底：主模型挂了换谁？       —— ModelFallback + 顺序对不对
⑤ 崩溃恢复：checkpoint 配了吗？   —— 配的是持久化，不是 MemorySaver
```

再对五项每类点一个"最容易踩的坑"：重试默认会重试 401（除非用 ModelError）、上限 Model 层默认 end 而 Tool 层默认 continue、降级顺序错了不触发、子代理不继承容错、MemorySaver 重启丢。

## 第五幕：体系收束

三个知识点回答三个递进的问题：

- **故障来了能恢复吗**（知识点 1）：重试治瞬时、上限防失控、降级保兜底、checkpoint 保崩溃
- **上线后能看见吗**（知识点 2）：`stream_events` v3 给每个子代理独立句柄
- **能交付吗**（知识点 3）：八项清单逐条勾，最容易漏 checkpointer / durable / 版本锁

放在阶段 4 的整体里看：

| 课 | 问题 | 答案 | 本课新增的约束 |
|---|---|---|---|
| 课 10 | 活怎么分出去 | 计划 + 子代理隔离 | 子代理要单独配容错 |
| 课 11 | 关键操作要交给人吗 | 审批闸门 + 权限红线 | 审批要能恢复必须有 checkpointer |
| 课 12 | 能并发 / 能海量吗 | 异步五工具 + 动态代码派发 | 融进容错顺序与流式句柄 |
| 课 13 | 敢上线吗 | 开关清单 + 容错 + 流式 | 交付前逐项勾 |

🇹🇸 **换成 TypeScript，这张表要改两格**：课 11 那格的"审批要能恢复必须有 checkpointer"在 TS 侧要加重——不是"恢复时才有问题"，而是"没有 checkpointer 第一次 invoke 就抛"；课 12 那格的"融进流式句柄"要改说法——TS 的句柄没有 `status`/`path`，靠 `output` 这个 Promise 判成败。其余四格（拆分、隔离、异步五工具、逐项勾）两语言同构。


放在整个教程里看（五阶段）：

- **阶段 1**：故事线（规划 → 执行 → 反思）——agent 单脑
- **阶段 2**：记忆（短期/长期/工作区）——agent 有记忆
- **阶段 3**：上下文管理（精简/回溯/沙箱/解释器）——agent 脑子不爆
- **阶段 4**：委派（计划/审批/并发/上线）——agent 会分活、敢交付
- **阶段 5**：回顾与展望 —— 反思沉淀

一句话收束整课、也收束整个阶段：**“能跑起来”和“能交付”之间，隔着一张开关清单——法律上的授权、预算上的上限、故障上的兜底，哪一个漏了，线上都会替你说出来。**

## 🐞 常见误区（本课专属）

| 误以为 | 实际 | 怎么排查 |
|--------|------|---------|
| "框架有 QPS 限流" | 只有调用次数上限 | 搜 `RateLimit` 找不到 |
| "401/400 一律不重试" | 只对 ModelError 家族成立 | 用普通异常模拟 401 看会不会重试 |
| "重试+降级随便排" | 顺序错了降级不触发 | 数 primary 被调几次 |
| "子代理继承主代理容错" | 不继承 | 给子代理模型抛错看被调几次 |
| "配了 interrupt_on 就能恢复" | 没 checkpointer 恢复时炸 | 用 Command(resume=...) 实测 |
| "MemorySaver 能生产" | 进程重启全丢 | 重启进程看状态 |
| "stream().subagents 能用" | 入口是 stream_events v3 | 打印 dir 看属性 |

| 🇹🇸 "打了 stampRetryable 标就一定不重试" | `createDeepAgent` 下标记被 `MiddlewareError` 包在 `.cause` 上，默认 `retryOn` 看不见 | 用自定义 `retryOn` 打印 `.cause` 链对比 |

## 课后小测

**Q1**：`ModelRetryMiddleware(default_retry_on)` 对一个 `RuntimeError("unauthorized")`（普通异常）会怎么处理？
- A. 不重试
- B. 重试
- C. 报配置错误
- D. 视 status_code 而定

<details><summary>答案与解析</summary>

**答案：B**。`default_retry_on` 只有对 `ModelError` 家族才查 `is_retryable`，其他异常返回 `True`。所以模拟 401 的普通异常会被重试。要让 401 真不重试，要么用能抛 `ModelAuthenticationError` 的官方 SDK，要么给 `retry_on` 传自定义 callable。

🇹🇸 **TS 侧这题答案也是 B，但理由完全不同**。TS 没有 `ModelError` 家族，判定只看 `Symbol` 标记：`getRetryable(e) ?? true`。普通 `Error` 没有标记 → 返回 `undefined` → 落到 `?? true` → 重试。所以"裸 Error 会被重试"两侧同结论，但**TS 侧更彻底**：连 `status: 401` 都不看（实测 `Error.status=401` 照样重试 3 次）。

更值得记的是 TS 的加试题：**打了 `stampRetryable(err, false)` 标记，在 `createDeepAgent` 下依然会被重试**——因为标记被 `MiddlewareError` 包进 `.cause`，而默认 `retryOn` 只读最外层。同样是这个错误，换 `createAgent` 装配就只调 1 次。所以 TS 侧要真控制重试，必须自己写 `retryOn` 沿 `cause` 链找标记。

</details>

**Q2**：以下哪个是框架自带的能力？
- A. QPS 限速
- B. 调用次数上限
- C. 429 自动等待重试
- D. 节流

<details><summary>答案与解析</summary>

**答案：B**。`ModelCallLimitMiddleware` / `ToolCallLimitMiddleware` 控制每次 run 的调用次数上限。框架没有 QPS 限速、也没有"429 自动等待"类中间件——429 要自己用 `retry_on=(RateLimitError,)` 配退化重试，或外部网关处理。

🇹🇸 TS 侧同样选 B。探针 3 的导出扫描结果：`带 Rate/Throttle 的中间件：(没有)`。一个额外的坑是 **import 路径**——这些中间件全在 `langchain` 包，不在 `deepagents`；从 Python 的 `langchain.agents.middleware` 迁过来时 if 路径写错，TS 会报"导出不存在"，比 Python 的 `ImportError` 更早暴露，倒是好事。

</details>

**Q3**：`stream.subagents` 的正确入口是什么？
- A. `agent.stream()` 的返回值
- B. `agent.stream_events(..., version="v3")` 的返回值
- C. `agent.astream(subgraphs=True)` 的命名空间
- D. A 和 C

<details><summary>答案与解析</summary>

**答案：B**。实测 `agent.stream()` 没有 `subagents` 属性（探针 5-C），入口是 `stream_events(version="v3")` 返回的 `GraphRunStream`（探针 6-A）。注意 C 的 `astream(subgraphs=True)` 是老路，给出的是 `(namespace, chunk)` 元组，不是独立句柄。

🇹🇸 TS 侧答案同样是 B（`streamEvents` + `version: "v3"`），但写法上多一步：**它是 async，必须 `await`**。直接在返回值上查属性会得到 `undefined`——`await` 之后才是 `GraphRunStream`。

</details>

**Q4**：不配 checkpointer 时配 `interrupt_on`，会发生什么？
- A. 触发中断会报错
- B. 正常触发中断，但恢复时炸
- C. 完全不触发中断
- D. 配置无法启动

<details><summary>答案与解析</summary>

**答案：B**（实测探针 7）。`invoke` 能正常触发中断、`__interrupt__` 有值——所以测试看起来"审批能暂停"。但用 `Command(resume=...)` 恢复时炸：`RuntimeError: Cannot use Command(resume=...) without checkpointer`。这是"测试通过、上线才暴露"的一类。

🇹🇸 **TS 侧这题答案变了，选 A**。探针 7 实测：不配 checkpointer 时第一次 `invoke` 就抛 `GraphValueError: No checkpointer set`，并给出 `https://docs.langchain.com/oss/javascript/langgraph/MISSING_CHECKPOINTER/` 排障链接。所以 TS 侧不存在"先演示、后配持久化"这条路径——它把错误提前到了最早的时刻。

这道题真正该记住的不是 A 还是 B，而是：**同一个配置缺陷，两侧暴露的时机相反**。从 Python 迁到 TS 时，"本地能跑通审批演示"不再是"配置没问题"的证据。

</details>

**Q5**：子代理模型内部抛异常，且主模型配了 `ModelRetryMiddleware(max_retries=2)`，子代理会被重试几次？
- A. 2 次
- B. 1 次（不重试）
- C. 3 次
- D. 无限重试

<details><summary>答案与解析</summary>

**答案：B**（实测探针 4-D）。子代理模型被调 1 次就抛穿主代理，主代理的 retry 中间件**不覆盖子代理**，`task` 工具也没兜住（异常变成 ToolMessage 但那次调用已失败）。要保护子代理必须显式给它自己的模型配容错。

🇹🇸 TS 侧答案同样是 B（探针 9：`主模型调用 1 次｜子代理模型调用 1 次`），但后果更重：TS 不是把异常包成 ToolMessage，而是直接 `MiddlewareError` **抛穿整个 `invoke`**。所以"一个子代理炸掉不会带崩整体"这句话在 TS 侧**不成立**——除非你显式给子代理配了容错。

</details>

## 🇹🇸 本课双语差异速查

配容错时最容易踩的十几个点，一次对齐（TS 侧全部有 `l13-production.ts` 实测输出支撑）：

| 维度 | Python | TypeScript |
|------|--------|-----------|
| 重试判定依据 | `ModelError.is_retryable`（异常家族）| **`Symbol` 标记**，不看 `status` 字段 |
| 401 是否默认重试 | 不重试（若是 ModelError 子类）| **重试**（无标记 → `?? true`）|
| `stampRetryable` 打标效果 | — | **`createDeepAgent` 下失效**，标记被 `MiddlewareError` 包进 `.cause` |
| 要打标生效怎么办 | — | 自定义 `retryOn` 沿 `cause` 链查 `getRetryable` |
| 重试耗尽默认行为 | 异常往上抛 | **`onFailure: "continue"` 写 AIMessage 继续跑** |
| 要它抛错 | 默认就是 | 显式 `onFailure: "error"` |
| `ModelCallLimit` 默认档 | `exit_behavior="end"` | `exitBehavior: "end"`（一致）|
| `ToolCallLimit` 默认档 | `exit_behavior="continue"` | `exitBehavior: "continue"`（一致）|
| `ToolCallLimit` 可选档 | `continue` / `error` | `continue` / `error` / **`"end"`（独有）** |
| 降级中间件签名 | `ModelFallbackMiddleware("a","b")` | **`modelFallbackMiddleware(...models)`**，不是数组 |
| 容错中间件从哪导入 | `langchain.agents.middleware` | **`langchain`**（`deepagents` 56 个导出里没有）|
| checkpointer 缺失时机 | 第一次 `invoke` 正常中断，`resume` 时才炸 | **第一次 `invoke` 就抛 `GraphValueError`** |
| 缺 checkpointer 报错文案 | `Cannot use Command(resume=...) without checkpointer` | `No checkpointer set` + MISSING_CHECKPOINTER 链接 |
| `durability` 三档 | `exit`/`async`/`sync` | 同名同默认，但在调用时传；`checkpointDuring` 已 deprecated |
| 流式入口 | `stream_events(version="v3")` 同步返回 | **`streamEvents` 返回 Promise，要 `await`** |
| 子代理句柄字段 | `name`/`messages`/`tool_calls`/`subagents`/`output`/`path`/`status` | 有 `name`/`messages`/`toolCalls`/`subagents`/`output`，**无 `path`/`status`** |
| 句柄 `output` 形态 | 同步版 dict、异步版方法 | **Promise** |
| 多消费者遍历 | 单订阅，要 `atee(n)` 分叉 | **可多次遍历，无 `atee`** |
| 子代理失败传播 | 包成 ToolMessage 还给模型 | **`MiddlewareError` 抛穿整个 `invoke`** |
| 版本约束看哪里 | `dependencies`（`langchain>=1.4.6`）| **`peerDependencies`（8 个）** |
| 静默工具变更 | v0.7 移除 `write_todos` | 无对应事件，走 minor + changelog |

三条最该记住的、会"静默失效"的差异：

1. **`stampRetryable` 在 `createDeepAgent` 下不生效**——不报错、不警告，就是照旧重试。你的"401 不重试"策略会静默落空。
2. **`onFailure` 默认 `"continue"`**——模型全挂了也不抛，写成一条 AIMessage 让流程继续，产出错误结论。这在生产里比崩溃更难查。
3. **TS 句柄没有 `status` / `path`**——`as never` 一写就绕过了类型检查，运行时静默 `undefined`，你的状态面板会永远是空的。
