## 第一幕：起源与场景引入

课 10 学会了派活，课 11 学会了装闸。但这两课都有一个隐含前提：**活是一件一件派的，而且派出去就等着**。

> 🎬 **场景**：主角要同时调研 5 个竞品。他让 agent 去查，结果 agent 规规矩矩地：查完 A 等回来，再查 B，再等……5 个竞品耗了 15 分钟，其中 12 分钟在等。
>
> 更糟的是第二个问题：查到第 4 个时，主角发现方向搞错了——这 5 个根本不是同一类产品。他想喊停，但 agent 已经把第 5 个也查完了。

两件事要解决：

- **同时派**：5 个竞品应该一起查，不是排队
- **中途改**：查到一半能喊停、能改指令

这一课就是这两件事，加上一个更隐蔽的第三件事：**当活有 300 件时，"一件一件派"这个模式本身会崩**。

> 📌 **一句话本质**：异步子代理把"派活"从**函数调用**变成**提交任务**（拿到 task_id 就走）；动态子代理把"派活"从**模型逐个决策**变成**代码批量循环**。两者解决的是不同的瓶颈——前者解决"等"，后者解决"数量和覆盖"。

> ⚖️ **处境对照**：装上这两种能力，你能处理"5 个竞品同时查"和"300 个文件全审"。但代价是：异步需要一套远程服务，动态需要解释器，两者都比写一个 `task` 复杂得多。所以本课最后一定讲"什么时候不该用"。

## 第二幕：认知冲突

**第一处：异步子代理不是"进程内并发"，它压根不在你的进程里。**

很多人以为异步子代理就是把同步子代理放到 `asyncio.gather` 里：

::: code-group
```python [Python]
# ❌ 这是想当然
await asyncio.gather(*[task(desc) for desc in tasks])
```
```typescript [TypeScript]
// ❌ 同样是想想当然
await Promise.all(tasks.map((desc) => task(desc)))
```
:::

实测真相：异步子代理必须配 `graph_id` / `graphId`，而且它是**通过 LangGraph SDK 在远程 Agent Protocol 服务器上创建 thread + 启动 run**：

::: code-group
```python [Python]
subagents=[{
    "name": "researcher",
    "description": "远程研究",
    "graph_id": "research_agent",        # ← 远程图的名字
    "url": "https://my-deployment.langsmith.dev",   # ← 远程服务地址
}]
```
```typescript [TypeScript]
subagents: [{
  name: "researcher",
  description: "远程研究",
  graphId: "research_agent",              // ← 远程图的名字（驼峰）
  url: "https://my-deployment.langsmith.dev",  // ← 远程服务地址
}]
```
:::

`graph_id` 是**唯一的分流判据**（源码 `graph.py:691-694`）：

::: code-group
```python [Python]
for spec in subagents or []:
    if "graph_id" in spec:
        async_subagents.append(cast("AsyncSubAgent", spec))
        continue
```
```typescript [TypeScript]
// langsmith-*.js:7921 —— 用类型守卫，判据同样是"有没有那个字段"
const asyncSubAgents = allSubagents.filter((item) => isAsyncSubAgent(item));
// graphId 是运行时判据（源码原话：presence of the `graphId` field）
function isAsyncSubAgent(subAgent) {
	return "graphId" in subAgent;
}
```
:::

实测验证（TS 侧探针 1 把这四种规格全跑了一遍）：

| 规格 | 走异步？ |
|------|---------|
| `{"name":"a", "graph_id":"g"}` | ✅ 是 |
| `{"name":"b", "url":"http://x"}` | ❌ 否（只写 url 不算） |
| `{"name":"c"}` | ❌ 否（普通同步子代理） |
| `{"graphId": ""}`（TS 空串） | ✅ 是（`"graphId" in spec`，不做非空校验） |

两侧一致的地方：都只认那个字段，`url` 本身不是开关。TS 侧多一个坑——`graphId` 写空串**照样被当成异步**，然后启动时拿空 `assistant_id` 去请求远程，报的是服务端错误而不是配置错误。另外 TS 侧如果两个异步子代理**重名**，`createDeepAgent` 直接抛 `Duplicate async subagent names: dup`。

所以"异步"在这里的含义是：**提交到远端后台跑，主代理拿到 task_id 立刻继续**。跨进程、跨机器、跨部署。

**第二处：不是四个工具，是五个。**

骨架知识点 1 的关键点 2 写：`launch` / `check` / `update` / `cancel`。

实测模型看到的工具清单（Python 探针 4-B、TS 侧探针 2）是五个，而且名字也不是 `launch`，两侧一字不差：

```text
start_async_task     ← 骨架叫 "launch"
check_async_task
update_async_task
cancel_async_task
list_async_tasks     ← 骨架漏了这个
```

`list_async_tasks` 不是可有可无的辅助工具。当主代理忘了自己派过几个、或者需要按状态筛"还在跑的"时，它是唯一入口——而且它还能顺便刷新所有任务的实时状态。

**第三处：动态子代理的收益不是"更快"，而是"上下文小两个数量级"。**

这是本课最反直觉的一点。实测（Python 探针 7，N=8，每个子代理返回约 600 字）：

| 方式 | 主模型调用 | 主上下文消息数 | 主上下文总字符 |
|------|-----------|--------------|--------------|
| 并行 `task` tool_calls | 2 次 | 11 条 | 3526 字符 |
| 动态 `eval` 循环 | 2 次 | 4 条 | **38 字符** |

TS 侧同构复现（探针 7，同样是 8 个子代理、每个返回 600 字），结论同向但没有 Python 那么极端：

```text [TypeScript]
并行 task × 8：消息 11 条，tool 结果 8 条，总字符 4809
动态 eval × 8：消息 4 条，tool 结果 1 条，总字符 12
字符比 401:1
```

消息条数两侧完全一样（11 vs 4），字符比更高是因为 TS 的 ToolMessage 包裹了更多元数据。**关键结论跨语言成立：并行模式下 8 份报告全进主上下文，动态模式下它们留在解释器变量里。**

速度上两侧都**没有**"动态更快"这回事，但成因不同：

```text [Python]
N=4    并行 0.087s  vs  动态 0.329s     ← 动态慢 3.8 倍
N=12   并行 0.111s  vs  动态 0.225s     ← 动态慢 2 倍
N=30   并行 0.196s  vs  动态 0.317s     ← 动态慢 1.6 倍
```

```text [TypeScript]
N= 4   并行 0.038s  vs  动态 0.042s     → 动态慢 1.11x
N=12   并行 0.052s  vs  动态 0.049s     → 动态快 1.06x
N=30   并行 0.088s  vs  动态 0.080s     → 动态快 1.10x
```

Python 侧的固定开销主要在解释器冷启动和序列化往返，N 小时占大头。TS 侧用 WASM QuickJS，冷启动便宜得多，所以三条曲线基本贴在一起——**"动态更慢"这个结论在 TS 侧站不住**，只能说"两侧都快到没有区别"。

那它的价值在哪？**每个子代理的返回结果留在解释器变量里，不进主上下文**。主代理只看到最后一行代码的值（`38 / 12 字符`），而不是 8 份完整报告（`3526 / 4809 字符`）。

> ❓ **问题**：既然异步要远程服务、动态要解释器且小规模没优势，那到底什么时候该用哪个？三种模式的边界在哪？

### 知识点 1：异步子代理的控制工具

> 🧭 第 1/3 步｜承接：开场"5 个竞品排队查太慢" → 本步：把"派活"变成"提交任务"，并且能查、能改、能停
> 本知识点关键点：五个工具、状态机、装配位置、审批的处理方式、并发与成本

#### 一句话定义

异步子代理是"把任务提交到远程 Agent Protocol 服务器，立刻拿回 task_id"的模式。主代理不等待，用五个工具管理这批后台任务的整个生命周期。

#### 直觉建立（类比）

像点外卖而不是自己做饭：

- **同步子代理** = 自己做饭：动手、等着、做好了吃
- **异步子代理** = 点外卖：下单拿到订单号就走，回头用订单号查进度、改地址、取消

> 💡 **类比的边界**：外卖你只能"取消"或"改地址"，不能改菜谱；而异步子代理的 `update_async_task` 会**中断当前 run 并在同一 thread 上开新 run**，子代理能看到完整历史加上你的新指令。它比改地址强，相当于"让厨师按新要求重做，但他还记得前面做到哪了"。

#### 核心原理

**五个工具各自的真实行为**（源码 `async_subagents.py` + 探针 4-B；TS 侧 `langsmith-*.js` + 探针 4）：

| 工具 | 做什么 | 关键实现细节 |
|------|--------|-------------|
| `start_async_task` | 建 thread + 起 run，返回 task_id | task_id **就是** thread_id |
| `check_async_task` | 查状态，完成则带回结果 | 状态可能是 `running`/`success`/`error`/`waiting`/`cancelled`（TS 无 `waiting`） |
| `update_async_task` | 中途改指令 | `multitask_strategy="interrupt"`：中断旧 run、同 thread 开新 run，**task_id 不变** |
| `cancel_async_task` | 取消 | 若任务在 `waiting` 状态**不会**调远程 cancel（没有活跃 run 可取消），只标本地状态 |
| `list_async_tasks` | 列出所有任务 + 实时状态 | 先按**缓存状态**筛选，再对筛出的拉实时状态 |

两侧工具名和参数名完全一致（`taskId` 驼峰在两侧都是驼峰，因为 Python 侧的 `task_id` 是函数参数、暴露给模型的 schema 也是 `task_id`——注意这里 TS 是 `taskId`）。实测 TS 侧的一次完整往返（探针 4）：

```text [TypeScript]
4-A start          tool = "Launched async subagent. taskId: t-1"
    taskId = threadId? true｜状态=running｜agent=researcher
    假服务收到的 run 请求: graphId=research_agent multitask=(默认)
4-C check(success) tool = {"status":"success","threadId":"t-1","result":"远程图 research_agent 完成，收到任务：查竞品 A"}
4-D update         tool = Updated async subagent. taskId: t-1
    taskId 是否不变: true｜runId 是否变了: true（r-1 → r-2）
    假服务收到的 multitask 策略 = interrupt
4-E list           tool = 1 tracked task(s): - taskId: t-1 agent: researcher status: pending
```

注意 `check_async_task` 的返回值形态：Python 返回的是给人看的一句话 + 结构化字段，TS 返回的是**纯 JSON 字符串**（`{"status": ..., "threadId": ..., "result": ...}`）。这意味着 TS 侧的模型更容易"读漏"状态——它得自己解析 JSON。

**`waiting` 是个容易被忽略的状态**：子代理自己也能配 `interrupt_on` / `interruptOn`。它暂停等人审批时，任务状态是 `waiting` 而不是 `running` 或 `success`。源码注释写得很清楚：

```text [Python]
A run that hits `interrupt()` ends as `success`; only its thread shows the pause.
```

也就是说，光看 run 状态会误判"成功了"，必须再查 thread 才知道它在等人。Python 侧靠这张映射表补上这个语义（`async_subagents.py:138`）：

```python [Python]
_THREAD_TO_TASK_STATUS = {"interrupted": _WAITING, "busy": "running", "error": "error"}
```

而且**这个审批只能由用户在那个子代理自己的 thread 上回答，主代理不能代批**（`_WAITING_NOTE`）。这正好接上课 11 的结论：审批是图级的，异步子代理在另一张图里，所以只能人自己过去点。

> 🇹🇸 **TS 侧没有这套东西**。`AsyncTaskStatus` 的联合类型里确实列了 `"interrupted"`，但整份 bundle 里 `waiting` 只出现在三处跟异步无关的散文里，`_THREAD_TO_TASK_STATUS` 这张表**根本不存在**。实测（TS 探针 4-C）`check_async_task` 直接返回 `{"status":"success", ...}`，`AsyncTask.status` 也只可能是 `pending`/`running`/`success`/`error`/`cancelled`/`timeout`/`interrupted` 七个之一。
>
> 后果很实际：**一个正在等人审批的远程子代理，在 TS 侧的异步任务视图里显示为 `success`**。主代理会以为活干完了，把"完成但没有结果"当成最终结论交给用户。这不是"少一个状态"，是**一个静默的错误结论**。
>
> 规避办法只有一条：异步子代理的远程图**不要配 HITL**。要审批就把它做成同步子代理（课 11 的路子），审批链留在同一个进程里。

Python 侧不写 `url` 时可以走**进程内 ASGI 传输**，但**只能用 `ainvoke`**。

这里有个比"报错"更阴的地方：实测用同步 `invoke` 调 `start_async_task` 时，这个 `ValueError` **被 `start_async_task` 自己 catch 住了**，变成一条普通的工具返回值（探针 8-B）：

```text [Python]

configured. ASGI transport (url=None) requires async invocation.
```

也就是**流程不中断**，报错字符串作为工具结果交给模型。模型很可能把它当成"启动失败但可以重试"，然后反复重试或编一个合理化的解释。排查时得去翻 ToolMessage，光看有没有异常是发现不了的。

> 🇹🇸 **TS 侧的行为完全不同，而且更糟**：没有 ASGI 那条路，也没有那句可诊断的报错。`url` 不写时 SDK 回落到 `http://localhost:8123`，于是报的是**连接失败**（TS 探针 5）：
>
> ```text [TypeScript]
> tool = Failed to launch async subagent 'r': ConnectionError: Unable to connect to
>        LangGraph server. Please ensure the server is running and accessible.
> 有没有 "requires async invocation" 提示: false
> ```
>
> 开发机上恰好有个服务跑在 8123，这个错误就会变成"连上了但 assistant 不存在"，排查方向彻底跑偏。**TS 侧请把 `url` 当必填项写**，别依赖默认值。

**主代理怎么知道任务完成了**（这是异步设计里最精妙的部分，也是两侧分叉最大的地方）：

::: code-group
```python [Python]
# 源码在三个时机主动检查（async_subagents.py:1450-1490）
def before_agent(self, state, runtime):  ...   # 每次 agent 启动前
async def abefore_model(self, state, runtime): ...  # 每次模型调用前
@hook_config(can_jump_to=["model"])
async def aafter_model(self, state, runtime): ...
# 给了最终答案之后再查一次；有新状态就 jump_to: "model" 让模型多说一轮
```
```typescript [TypeScript]
// 整个 createAsyncSubAgentMiddleware 只有两个字段：
return createMiddleware({
  name: "asyncSubAgentMiddleware",
  stateSchema: AsyncTaskStateSchema,
  tools,                                   // ← 只有工具
  wrapModelCall: async (request, handler) => { ... }   // ← 只拼系统提示
});
// 没有 beforeAgent、没有 beforeModel、没有 afterModel
```
:::

Python 侧不需要主代理轮询，中间件自己会在三个时机主动检查。TS 侧**一次都不查**——`AsyncTask` 只会因为主代理显式调用 `check_async_task` / `list_async_tasks` 而更新。

这条差异的实际后果：

- Python：任务在后台完成 → 下一轮模型调用前，中间件已经把它写进 messages → 模型自然知道
- TS：任务在后台完成 → **谁都不知道**，直到用户问"好了吗"、主代理才去 check

也就是说 TS 侧必须靠**系统提示**来约束行为。它确实带了一段（`ASYNC_TASK_SYSTEM_PROMPT`，包含 "Never auto-check after launching"、"NEVER report a status from a previous tool result" 等硬规则），但这段只在你自己传 `systemPrompt` 时才会生效：

```typescript [TypeScript]
// createAsyncSubAgentMiddleware: const fullSystemPrompt = systemPrompt ? ... : null
// createDeepAgent 装配时没有传 systemPrompt → 这段提示根本不会进上下文
...asyncSubAgents.length > 0 ? [createAsyncSubAgentMiddleware({ asyncSubAgents })] : []
```

> ⚠️ 这是个实打实的缺口：TS 侧自动装配的异步中间件**既没有系统提示、也没有自动轮询**。五个工具的 description 里带了工作流说明（"Report the task ID to the user and stop"、"Statuses shown earlier are always stale"），所以模型能凑合工作，但少了 Python 那层"主动提醒"。如果你要上生产，建议自己包一层 `createAsyncSubAgentMiddleware({ asyncSubAgents, systemPrompt: ASYNC_TASK_SYSTEM_PROMPT })` 挂进 `middleware`，把这段提示补上。

Python 侧还有一层远程配合：子代理结束时，如果父 thread 空闲（`idle` 或 `error`），会主动起一个 run 唤醒父代理（`_awake_parent`）。源码注释解释了为什么只在这两种状态派：

```text [Python]
A new run on a thread waiting for a human would cancel that approval;
`reject` covers a thread that just became busy.
```

如果父代理正等着人批审批，这时候插一条通知 run 会把审批冲掉。所以这种情况下不推，等父代理自己下次检查时捞到。

**通知消息不是用户消息**。它带一个明确的头：

```text [Python]
[SYSTEM NOTIFICATION - NOT USER INPUT]
An async subagent task you started has an update. This is not a message from the user:
don't treat it as their answer to any question.
```

这是必要的防御。否则模型可能把"子代理任务完成了"误当成"用户回答了我刚才问的问题"。

> 🇹🇸 TS 侧另有 `createCompletionCallbackMiddleware` 做类似的事，但它是**给远程子代理自己挂的**（子代理结束时回调父 thread），不是父代理侧的自动轮询。要启用得在远程那侧配置 `callbackGraphId`，父代理这边的 `callbackThreadId` 由 `start_async_task` 自动写进 state。两侧都叫 `CompletionCallbackMiddleware`，但**默认都不启用**。

**并发上限**：异步子代理没有 `max_subagent_concurrency` 这类参数（那是动态子代理的）。它的并发上限取决于远程服务的承载能力和你的 API 配额——因为**每个子代理都是一条独立的调用链**，都在烧 token。

#### 常见误区

- ❌「异步子代理是进程内 `asyncio` 并发」——它是远程 thread + run，跨进程
- ❌「四个工具」——是五个，漏了 `list_async_tasks`
- ❌「不配 url 就能用 `invoke`」——ASGI 传输只支持 `ainvoke`（仅 Python；TS 侧压根没这条路）
- ❌「`update` 会保留旧 run」——它会 `interrupt` 旧 run 并开新的，`task_id` 不变但 `run_id` 变了
- ❌「主代理能替子代理批审批」——`waiting` 状态必须用户自己在子代理 thread 上回答
- ❌「`waiting` 两侧都有」——🇹🇸 TS 侧没有，等人审批的远程任务在异步视图里显示为 `success`
- ❌「主代理会自动发现任务完成」——🇹🇸 TS 侧不自动轮询，得主代理主动 `check_async_task`
- ❌「TS 侧会自动带上异步工具的使用说明」——🇹🇸 不传 `systemPrompt` 就没有那段提示

#### 一句话记住

> 异步子代理 = 提交到远程服务器拿 task_id；五个工具管理生命周期；`graph_id` / `graphId` 是唯一开关；不写 url 就只能用 `ainvoke`（TS 则是直接连不上）。

| "Agent Protocol" | 远程服务的接口规范，LangGraph Platform 实现了它 |
| "ASGI transport" | 进程内直连，不写 url 时用，只支持异步 |

### 知识点 2：动态子代理

> 🧭 第 2/3 步｜承接：5 个能并发了 → 本步：300 个怎么办，以及为什么"派 300 次"这个模式本身会崩
> 本知识点关键点：机制、解释器边界、真实收益、并发控制、失败传播

#### 一句话定义

动态子代理是"让模型写一段 JS 脚本，脚本里用 `task()` 循环派发子代理，脚本在 QuickJS 解释器里执行"的模式。编排逻辑从模型的逐步决策变成代码的结构。

> 🇹🇸 **TS 侧的动态子代理不在 `deepagents` 包里**。它来自一个独立包 `@langchain/quickjs`（当前 `0.6.5`，peer 依赖 `deepagents >= 1.13.4-rc.0`），而且导出的是**工厂函数**：
>
> ```typescript [TypeScript]
> import { createCodeInterpreterMiddleware } from "@langchain/quickjs";
>
> const agent = createDeepAgent({
>   middleware: [createCodeInterpreterMiddleware({ maxSubagentConcurrency: 8 })],
> });
> ```
>
> 对照 Python 的 `from langchain_quickjs import CodeInterpreterMiddleware` + `CodeInterpreterMiddleware(...)`，两边一字母一括号都不一样。写错了不会报"模块不存在"，而是 `createDeepAgent` 收到一个奇怪对象后在运行时炸。

#### 直觉建立（类比）

像**发快递 vs 自己一趟趟送**：

- 逐轮 `task` = 你自己开车，送一件回来再取下一件。送 300 件要跑 300 趟，而且你得记住哪些送过了
- 动态派发 = 你写一张配送单交给调度系统，系统按单子一次性派完

> 💡 **类比的边界**：配送单是死的，遇错就卡；而脚本可以写 `try/catch`、可以按结果分支、可以第二遍只重跑失败的。它是**程序**，不是清单。

#### 核心原理

**机制**：装解释器中间件后，解释器里多一个全局函数 `task()`。实测解释器的全局对象（Python 探针 3-A）：

```text [Python]
__console_error, __console_log, __console_warn, console, performance, task
```

TS 侧（探针 6-A）更干净，还多一个会话标识：

```text [TypeScript]
__sessionId__,console,performance,task
→ undefined | undefined | undefined | undefined   ← require / process / fetch / Deno 全是 undefined
```

就这么几个。`task` 是唯一能派活的入口。

**它怎么接到子代理的**？关键发现是：`task()` **不是重新实现**，而是桥接到外层已有的 `task` 工具。Python 侧（源码 `_repl.py:536-560`）：

```python [Python]
task_tool = find_subagent_task_tool(getattr(runtime, "tools", ()) or ())
if task_tool is None:
    raise RuntimeError("task tool not configured for this eval")
```

TS 侧同样的思路（`@langchain/quickjs` 的 `createCodeInterpreterMiddleware`）：

```typescript [TypeScript]
// 中间件每次 wrapModelCall 时都重新找一遍 task 工具
if (!taskTool && subagents) taskTool = findTaskTool(agentTools);
// 找到才装桥接，装的时候带上并发队列
subagentBridge: taskTool && subagents ? {
  dispatch: createBridgeDispatch(taskTool, config),
  maxConcurrency: maxSubagentConcurrency
} : void 0
```

这意味着：动态子代理用的是**同一套子代理定义**，`task()` 只是换了个调用入口。所以你会看到：即使只配同步子代理，`task` 工具依然在清单里（探针 4），动态派发也能用。

> ⚠️ 但 TS 侧有个反直觉的实测结果（探针 6 补测）：**完全不配 `subagents` 时，`typeof task` 仍然是 `"function"`**。原因是 `subagents` 选项默认 `true`，而 `createDeepAgent` 总会自动补一个 `general-purpose` 子代理，所以 `taskTool && subagents` 恒为真。要在 TS 侧关掉，只能显式传 `subagents: false`，此时 `typeof task` 变成 `"undefined"`。

**调用形式**（两侧写在 JS 里都一样，键名用驼峰）：

```javascript
const result = await task({
  description: "审查 src/auth/login.ts 的注入风险",
  subagentType: "reviewer",
  responseSchema: {          // 可选，给了就返回结构化对象
    type: "object",
    properties: {
      severity: { type: "string", enum: ["high", "medium", "low"] },
      issues: { type: "array", items: { type: "string" } },
    },
  },
});
result.severity;   // 模型看到最后一行
```

TS 侧的键名宽容度实测（探针 3 的 6-E）：

```text [TypeScript]
subagent_type 可用: worker 完成: snake 写法     ← 自动改名成 subagentType
未知键: task: unknown keys: bogus. Allowed: description, subagentType, responseSchema
```

两侧都是 JS 里写驼峰。TS 侧额外做了兼容（`subagent_type` → `subagentType`、`response_schema` → `responseSchema` 自动改名），未知键会**抛错**并列出允许的三个键——这个设计比静默丢弃好，模型能立刻看到自己的错误。Python 侧走的是 Pydantic 的 `_reject_unknown_keys` 校验器（`subagents.py:470-492`），同样抛校验错误，但文案不同：`Unexpected argument 'bogus'; put all instructions for the subagent in `description`.`——所以两侧都是"报错不静默"，只是提示语不一样，别拿同一段文案去做断言。

**解释器的能力边界**（探针 3-B，这是安全设计的核心）：

| 探测项 | Python 侧 | TypeScript 侧 |
|--------|----------|--------------|
| `typeof require` | `undefined` | `undefined` |
| `typeof process` | `undefined` | `undefined` |
| `typeof fetch` | `undefined` | `undefined` |
| `typeof Deno.readTextFile` | `ReferenceError: Deno is not defined` | （`typeof Deno` 本身即 `undefined`） |

**没有文件系统、没有 shell、没有网络**。这印证了骨架知识点 2 的关键点 3。它不是"配了权限才不能读"，是**压根没有那些对象**。这是 QuickJS 沙箱的性质，不是靠 `permissions` 拦的。

**真实收益：主上下文不变大**（探针 7）。8 个子代理各返回 600 字：

```text [Python]
并行 task tool_calls：主上下文 3526 字符，8 条 tool 结果
动态 eval + 循环：    主上下文   38 字符，1 条 tool 结果
```

```text [TypeScript]
并行 task × 8：消息 11 条，tool 结果 8 条，总字符 4809
动态 eval × 8：消息 4 条，tool 结果 1 条，总字符 12
```

差异来自哪里一目了然：并行模式下，8 份子代理报告**全都进了主代理的 messages**；动态模式下，它们留在解释器的 JS 变量里，只有最后一行表达式的值回到主上下文。

这才是"规模化"的真实含义——不是快，是**主上下文不会被 N 个子代理的结果撑爆**。

**并发控制**：`max_subagent_concurrency`（TS 同名驼峰 `maxSubagentConcurrency`）默认 **32**。Python 源码是 `_DEFAULT_MAX_SUBAGENT_CONCURRENCY = 32`，TS 是 `DEFAULT_MAX_SUBAGENT_CONCURRENCY`（同值）。实测（Python 探针 2）：

```text [Python]
默认：派 8 个，峰值并发 8，耗时 0.57s
设为 2：派 8 个，峰值并发 2，耗时 1.17s
```

TS 侧（探针 6-C，派 40 个并统计峰值）：

```text [TypeScript]
默认派 40 个，峰值并发 = 32        ← 确认默认值真的是 32，不是"无限"
显式设 5 派 20 个，峰值并发 = 5
maxSubagentConcurrency=2 派 8 个（每个 60ms）：峰值 2，耗时 0.28s（默认是 0.10s）
```

信号量真的压住了并发，代价是耗时翻倍。非法值两侧都直接拒绝：

```text [Python]
0    → ValueError: must be a positive integer
-1   → ValueError: must be a positive integer
1.5  → ValueError: must be a positive integer     ← 检查的是 type(x) is not int
```

```text [TypeScript]
0    → 抛错: `maxSubagentConcurrency` must be a positive integer
-1   → 抛错: `maxSubagentConcurrency` must be a positive integer
1.5  → 抛错: `maxSubagentConcurrency` must be a positive integer
```

两侧连拒绝 `1.5` 都一致，但**抛错的时机不同**：Python 在构造 `CodeInterpreterMiddleware(...)` 时抛，TS 在 `createCodeInterpreterMiddleware(...)` 时也抛——这点反而一致，都是**创建期**而不是运行时。

**失败传播**：Python 侧子代理内部抛异常时，`task()` **不会让整个 eval 失败**，而是返回一个错误对象（探针 3-C）：

```text [Python]
<error type="RuntimeError">worker 内部炸了</error>
```

TS 侧**完全相反**（探针 6-D）：桥接层在 `catch` 里 `promise.reject(context.newError(msg))`，所以异常直接抛到 JS 侧：

```text [TypeScript]
6-D 子代理抛异常:
  抛到 JS 侧了: worker 内部炸了
  → caught          ← 我用 try/catch 接住了
```

这个差异很关键：

- **Python**：`task()` 永远返回一个值，你得**自己判断**它是不是 `<error>`。忘了判，错误字符串会当正常结果往下传
- **TS**：`task()` 会抛，你不 `try/catch` 就会让整个 `eval` 失败，**剩下的 299 个也不再派**

一个是"静默污染"，一个是"全盘中断"，两种都不是好默认。同一条脚本写两遍时，这里的写法必须分开：

::: code-group
```javascript [Python 侧写法]
const r = await task({ description: "...", subagentType: "reviewer" });
if (String(r).startsWith("<error")) { /* 单独处理 */ }
```
```javascript [TypeScript 侧写法]
let r;
try {
  r = await task({ description: "...", subagentType: "reviewer" });
} catch (e) {
  // 一个失败，不影响其它
  r = { failed: true, reason: String(e.message) };
}
```
:::

> ⚠️ TS 侧还有一处两侧不一致：**未知 `subagentType` 直接抛错**（补测）——
> ```text [TypeScript]
> task() 未知类型 → 抛错: Error: invoked agent of type nobody, the only allowed types are `general-purpose`, `w`
> ```
> Python 侧返回的是字符串 `We cannot invoke subagent nobody because it does not exist...`（`subagents.py:847`），模型能自己看懂并改。TS 侧一抛，整个 `eval` 就挂了——这跟课 10 里"未知 subagent_type"的差异是同一个根因。

**触发方式**：官方文档给了个实用技巧——提示词里带上 "workflow" 这个词，解释器系统提示会把它当作"走代码编排"的信号。想要单次直接委派时就别用这个词。

#### 常见误区

- ❌「动态子代理能读文件」——解释器里没有 `fs`/`require`/`process`，要读文件得派个子代理去做
- ❌「动态派发比并行 `task` 快」——Python 实测更慢（固定开销），TS 实测基本持平，快从来不是它的卖点
- ❌「`task()` 是独立实现」——它桥接到外层 `task` 工具，用同一套子代理定义
- ❌「子代理失败会让 eval 抛异常」——🇵🇾 Python 返回 `<error>` 对象，脚本要自己判
- ❌「子代理失败不会让 eval 抛异常」——🇹🇸 TS 侧**恰恰会抛**，不 `try/catch` 就整轮挂掉
- ❌「并发越大越好」——默认 32，调大要考虑下游 API 限流
- ❌「解释器中间件是 `CodeInterpreterMiddleware`」——🇹🇸 TS 侧是 `createCodeInterpreterMiddleware()` 工厂函数，且来自独立包 `@langchain/quickjs`
- ❌「不配 subagents 就没有 `task()`」——🇹🇸 TS 侧默认仍有（内置 general-purpose），要关得显式 `subagents: false`

#### 一句话记住

> 动态子代理 = 模型写 JS 循环，`task()` 在 QuickJS 里批量派活；收益是主上下文不被 N 份结果撑爆，代价是多一层解释器和固定开销。

| 说你听到的 | 意思 |
|-----------|------|
| "programmatic subagents" | 动态子代理的官方名 |
| "QuickJS" | 轻量 JS 引擎，解释器就跑在里面 |
| "eval 工具" | 模型写代码的工具，默认名就叫 `eval`（TS 同样是 `eval`，可用 `toolName` 改） |
| "fan-out" | 扇出：一个循环派出 N 个 |

### 知识点 3：选型（同步 / 异步 / 动态）

> 🧭 第 3/3 步｜承接：三种都能用了 → 本步：判断该用哪个，以及什么时候一个都别用
> 本知识点关键点：三条判据、混合策略、上下文成本对照、常见误用

#### 一句话定义

选型看三件事：**要不要等结果**（不等就同步够）、**要不要并发且能中途干预**（要就异步）、**编排逻辑能不能事先写成代码**（能就动态）。

#### 直觉建立（类比）

- **同步** = 打电话问同事，等他答完你才继续
- **异步** = 发微信问同事，发完干别的，想起来再看
- **动态** = 给 300 个同事群发模板消息，用脚本汇总回执

> 💡 **类比的边界**：群发模板消息不需要每个人有独立判断；而动态子代理派出的每个子代理都有完整推理能力，能处理开放式任务。所以它比"群发模板"灵活得多，但也贵得多。

#### 核心原理

**三条判据（按顺序问）**：

```
① 派出去之后，主代理能不能干别的？
   ├─ 不能 → 同步子代理（最简单，别加复杂度）
   └─ 能 → ② 需要在跑的过程中改指令/喊停吗？
            ├─ 需要 → 异步子代理（远程 + 五个工具）
            └─ 不需要 → ③ 数量大吗？编排逻辑能写成代码吗？
                         ├─ 能 → 动态子代理
                         └─ 不能 → 同步子代理 + 并行 tool_calls
```

**关键：判据 ③ 之前还有一道"数量"门**。实测数据说明为什么：

```text [Python]
N=4    并行 tool_calls 0.087s  vs  动态 0.329s     ← 动态慢 3.8 倍
N=12   并行 0.111s             vs  动态 0.225s     ← 动态慢 2 倍
N=30   并行 0.196s             vs  动态 0.317s     ← 动态慢 1.6 倍
```

```text [TypeScript]
N= 4   并行 0.038s  vs  动态 0.042s     → 动态慢 1.11x
N=12   并行 0.052s  vs  动态 0.049s     → 动态快 1.06x
N=30   并行 0.088s  vs  动态 0.080s     → 动态快 1.10x
（各跑 3 次取中位数，子代理带 20ms 模拟延迟）
```

Python 侧 N 小的时候动态完全是净亏。TS 侧三条曲线基本贴平——**在 TS 里"动态更慢"不是个理由**，你该拿它当"速度上没差别"来看。两侧共通的只有一点：**动态派发不会更快**，最多持平。

但上下文开销反过来（N=8 时 3526 vs 38 字符 / 4809 vs 12 字符）。所以真正的判据是：

- **N 小（几个）+ 结果要看** → 并行 `task` tool_calls，简单直接
- **N 大（几十上百）+ 只要汇总** → 动态，主上下文省下的是数量级

**三种模式的上下文成本对照**（实测 + 源码推断）：

| 模式 | 子代理结果去哪 | 主上下文增长 | 需要什么额外设施 |
|------|--------------|-------------|----------------|
| 同步 `task` | 全部进 messages | 线性（每个一份） | 无 |
| 并行 `task` × N | 全部进 messages | 线性 × N | 无（模型一轮多发几个） |
| 异步 | 不进 messages，进 `async_tasks` / `asyncTasks` 状态 | 只有你 check 的那份 | 远程 Agent Protocol 服务 |
| 动态 | 留在解释器变量 | 只有最后一行 | QuickJS 解释器 |

异步那个要特别说明：子代理结果**不自动进主上下文**，得主代理主动 `check_async_task` 才拿回来。所以它是"按需取"，不是"自动汇总"。这也是为什么 `list_async_tasks` 有用——先看谁完成了，再决定 check 哪个。

> 🇹🇸 但请注意：Python 侧靠 `before_agent`/`before_model`/`after_model` 三个钩子**主动把状态变化推进 messages**，所以"不自动进主上下文"这个说法对 Python 是打折扣的（结果本身要 check 才拿，但"任务状态变了"这件事会自动告诉你）。TS 侧没有这些钩子，所以对 TS 来说这句话是**字面意义**的：不 check 就什么都不知道。

**混合策略**（实际项目里最常见）：

这一个 agent 同时具备三种能力。但要小心：**工具清单会膨胀**。实测对照（Python 探针 8-A）：

```text [Python]
同步子代理或无子代理：8 个工具
   delete, edit_file, glob, grep, ls, read_file, task, write_file

配了异步子代理：13 个工具
   上面 8 个 + start_async_task, check_async_task,
   update_async_task, cancel_async_task, list_async_tasks
```

TS 侧（探针 2）基线不同，差额一样：

```text [TypeScript]
无子代理      9 个: delete, edit_file, execute, glob, grep, ls, read_file, task, write_file
异步子代理   14 个，比基线多: cancel_async_task, check_async_task, list_async_tasks, start_async_task, update_async_task
（TS 基线多一个 execute——课 2 已讲过，TS 默认带 shell 执行能力）
```

工具越多，模型选错的概率越高。所以：

- 不需要异步，就别配带 `graph_id` / `graphId` 的子代理（`start_async_task` 等 5 个工具不会出现）
- 不需要动态，就别加解释器中间件（`eval` 不会出现）

**常见误用：为了"看起来高级"上异步**。

异步的隐性成本很高：

- 需要一套远程服务（LangGraph Platform 或自建的 Agent Protocol 服务）
- 需要处理 `waiting` 状态（子代理的审批要人自己去那个 thread 答）
- 需要处理通知与用户消息的混淆（虽然有 `[SYSTEM NOTIFICATION]` 头）
- 调试链路跨进程，出问题要看两个服务的日志

如果一个任务的子代理只要 3 秒，上异步是纯亏 —— 同步阻塞 3 秒，比配一套远程服务划算得多。

模型会写出类似这样的脚本：

```javascript
const files = ["a.ts", "b.ts", /* ... 40 个 */];
const results = await Promise.all(files.map(f =>
  task({
    description: `审查 ${f} 的安全问题`,
    subagentType: "reviewer",
    responseSchema: { type: "object", properties: {
      severity: { type: "string", enum: ["high","medium","low"] },
      issues: { type: "array", items: { type: "string" } } } },
  })
));
// 只把高严重级的带回主上下文
results.filter(r => r.severity === "high");
```

最后一行是关键：如果最后一行是 `results`，40 份结果全进主上下文；如果是 `results.filter(...)`，只有高严重级的那几条进来。

> ⚠️ 但上面这段脚本在 TS 侧有个前提：**`task()` 会抛**，40 个里只要有 1 个失败（模型输出不合法、子代理超时、`subagentType` 打错），整个 `Promise.all` 就 reject，剩下的全部白跑。TS 侧要写成这样才安全：
>
> ```javascript [TypeScript]
> const results = await Promise.allSettled(files.map(f =>
>   task({ description: `审查 ${f} 的安全问题`, subagentType: "reviewer", responseSchema: {...} })
> ));
> results.filter(r => r.status === "fulfilled" && r.value.severity === "high");
> ```
>
> `allSettled` 而不是 `all`，这一个小改动就是 TS 侧"一个失败别拖垮 39 个"的全部代价。Python 侧不需要——它天然不抛。

#### 常见误区

- ❌「异步一定比同步好」——3 秒的任务上异步是纯亏
- ❌「动态一定比并行 `task` 好」——Python 侧 N 小时慢 3.8 倍；TS 侧速度持平，但上下文收益照旧
- ❌「三种都配上最灵活」——Python 工具从 8 涨到 13、TS 从 9 涨到 14，模型选错概率上升
- ❌「异步结果会自动汇总」——要主动 `check_async_task`
- ❌「动态脚本最后一行随便写」——最后一行决定多少内容回主上下文
- ❌「`Promise.all` 就够了」——🇹🇸 TS 侧一个失败全崩，要用 `allSettled`

#### 一句话记住

> 先问"要不要等"（不等才同步），再问"要不要中途改"（要才异步），再问"量大不大、能不能写成循环"（量大才动态）；三种都配会撑爆工具清单。

#### 🗣️ 行话对照

| 说你听到的 | 意思 |
|-----------|------|
| "blocking subagent" | 同步子代理，`task` 会等 |
| "fire and forget" | 异步：发起就不等 |
| "steering" | 中途干预（`update`/`cancel` 属这类） |
| "context amplification" | 子代理结果把主上下文撑大 |

## 第五幕：体系收束

三个知识点回答三个递进的问题：

- **能并发吗**（知识点 1）：异步把"派活"变成"提交任务"，五个工具管生命周期，`graph_id` 是开关
- **能海量吗**（知识点 2）：动态把"派活"变成"代码循环"，收益是主上下文不被撑爆，不是速度
- **该用哪个**（知识点 3）：三条判据顺序问下来，多数场景答案是"同步就够"

放在阶段 4 的整体里看：

| 课 | 问题 | 答案 | 本课新增的约束 |
|---|---|---|---|
| 课 10 | 活怎么分出去 | 计划 + 子代理隔离 | 子代理定义可被三种模式复用 |
| 课 11 | 关键操作要交给人吗 | 审批闸门 + 权限红线 | 异步子代理的审批是 `waiting`，人得自己去那个 thread |
| 课 12 | 能并发 / 能海量吗 | 异步五工具 + 动态代码派发 | 工具清单会膨胀，别三种都配 |
| 课 13 | 敢上线吗 | 开关清单 + 容错 + 流式 | 异步任务的监控与容错是上线必备 |

一句话收束整课：**并发不是免费的速度，海量不是免费的能力——异步买到的是"等待期间能干活"，动态买到的是"主上下文不被撑爆"，两者都要付出基础设施和复杂度的代价。**

🇹🇸 **换成 TypeScript，这句话要加一个限定**：TS 侧异步买到的东西比 Python 少一样。Python 的异步中间件会替你在 `before_agent` / `before_model` / `after_model` 三个钩子上自动刷新任务状态，主代理"不用问也知道进展"；TS 的 `createAsyncSubAgentMiddleware` 只返回 `tools` + `wrapModelCall`，**没有任何钩子**，状态得靠模型自己想起来调 `check_async_task`。所以 TS 侧更准确的说法是：异步买到的是"等待期间能干活"，但"自动知道进展"这件事要你自己补系统提示或自己写包装层。

## 🐞 常见误区（本课专属）

| 误以为 | 实际 | 怎么排查 |
|--------|------|---------|
| "异步是进程内并发" | 远程 thread + run，跨进程 | 看子代理规格里有没有 `graph_id` |
| "四个异步工具" | 五个，漏了 `list_async_tasks` | 打印模型看到的工具清单 |
| "写了 url 就是异步" | 必须是 `graph_id` | 用 `"graph_id" in spec` 判 |
| "不配 url 也能 invoke" | 报错被吞成工具返回值，流程不中断 | 翻 ToolMessage 找 "requires async invocation" |
| "动态比并行快" | 实测更慢，固定开销 | 量 N=4 和 N=30 的耗时 |
| "动态能读文件" | 解释器无 fs/shell/网络 | `typeof require` → `undefined` |
| "子代理失败会中断 eval" | 返回 `<error>` 对象 | 脚本里要自己判 `result` 类型 |
| "异步结果自动汇总" | 要主动 `check_async_task` | 看主上下文有没有那份结果 |
| 🇹🇸 "TS 侧也有 `waiting` 状态" | **没有**，`AsyncTaskStatus` 只有 7 个值 | 打印 `Object.keys` 或看 d.ts；等人审批的远程任务在 TS 里显示 `success` |
| 🇹🇸 "TS 也会自动轮询状态" | **不会**，异步中间件只有 tools + wrapModelCall | 看中间件栈里有没有 before/after 钩子 |
| 🇹🇸 "动态子代理是 deepagents 提供的" | 在独立包 `@langchain/quickjs` | `npm ls @langchain/quickjs`；`import` 失败会运行时炸 |
| 🇹🇸 "子代理抛异常会变成错误字符串" | **直接 reject 到 JS 侧** | 不 try/catch 就整个 `eval` 崩 |
| 🇹🇸 "不写 url 会提示 requires async invocation" | 报 `ConnectionError`，回落 localhost:8123 | 看错误文案里有没有 `localhost:8123` |

### ⏳ 与过时说法对照

| 过时的说法 | 现在该怎么说 |
|-----------|-------------|
| "异步子代理用 `launch` 启动" | 工具名是 `start_async_task`（五个之一）|
| "异步只需配 `url`" | 必须配 `graph_id`，`url` 只决定走远程还是进程内 ASGI |
| "动态子代理是让模型自己调 `task`" | 是让模型**写代码**，代码里调 `task()` |
| "上异步能提速" | 提速来自"不阻塞"，不是"跑得快"；反而多一层远程调用开销 |
| 🇹🇸 "TS 里叫 `graph_id`" | 叫 `graphId`；而且空串也算异步（不做非空校验）|
| 🇹🇸 "TS 也走 `CodeInterpreterMiddleware` 这个类" | 是工厂函数 `createCodeInterpreterMiddleware()`，且在 `@langchain/quickjs` 包里 |
| 🇹🇸 "TS 侧不用管并发上限，默认给足" | 默认 32，够但会静默截断；显式设 0 / 负数 / 小数会在创建期抛错 |

```mermaid
flowchart TD
    Q["要派活"] --> A{"派完能<br/>干别的吗?"}

    B -->|"不要"| C{"N 大吗?<br/>能写循环吗?"}
    C -->|"不大 / 要逐份看结果"| PAR["同步 + 并行 tool_calls"]
    C -->|"大 / 只要汇总"| DYN["动态子代理<br/>eval + task() 循环"]

    ASYNC --> A5["五个工具:<br/>start / check / update<br/>cancel / list"]
    DYN --> D1["收益: 主上下文<br/>Py 3526→38<br/>TS 4809→12"]
    DYN --> D2["代价: 固定开销<br/>N=4 Py 慢 3.8x<br/>TS 慢 1.1x"]

    style SYNC fill:#f0f8f2,stroke:#86bfa0
    style ASYNC fill:#eef6ff,stroke:#7fb2e5
    style DYN fill:#fff8ec,stroke:#e0b877
    style PAR fill:#f0f8f2,stroke:#86bfa0
```

> 读图指引：从上往下是一道决策树，不是能力阶梯——**越往下不代表越好**。左边那条"不能等 → 同步"是最常走的路，也是多数项目该走的路。右边两个分支各自挂了代价标签：异步的五工具复杂度、动态的固定开销。看到这两个代价还觉得划算，才是该用的场景。

🇹🇸 **TS 读者额外注意两条**：

- 走右边的 ASYNC 分支时，图里那个"五个工具"在 TS 侧是**只给了工具、没给自动轮询**，你得自己在系统提示里写清"何时该 check"，否则模型派完活就忘了
- 走 DYN 分支时，"固定开销"在 TS 侧被摊薄了（N=4 只慢 1.11 倍，N≥12 反超），因为 TS 的解释器起停比 Python 的 QuickJS 桥接轻。但"收益"这一栏 TS 更夸张（401:1），所以 TS 侧结论更干脆：**只要 N 大且你只要汇总，动态就是明显更优；N 小就无所谓，选你更熟的那个**

## 课后小测

**Q1**：子代理规格里只有 `url` 没有 `graph_id`，会发生什么？
- A. 正常走异步
- B. 被当成普通同步子代理
- C. 报配置错误
- D. 走 ASGI 进程内传输

<details><summary>答案与解析</summary>

**答案：B**。源码 `graph.py` 用 `if "graph_id" in spec` 分流，实测 `{"url":"http://x"}` → 走异步 False。`url` 只决定异步子代理走远程还是进程内 ASGI，它本身不是异步开关。

🇹🇸 **TS 侧答案一样是 B，但判定细节有两处不同**：键名是 `graphId`；而且判据是 `"graphId" in subAgent`，**不做非空校验**——`{"graphId": ""}` 实测仍返回 `isAsyncSubAgent = true`，会在真正 start 的时候才炸。所以 TS 侧排查时不能只看"有没有这个键"，要看值是不是空串。

</details>

**Q2**：`update_async_task` 对正在跑的任务做了什么？
- A. 排队等当前 run 结束后追加
- B. 中断当前 run，同 thread 开新 run
- C. 直接取消，不执行新指令
- D. 修改当前 run 的参数

<details><summary>答案与解析</summary>

**答案：B**。源码用 `multitask_strategy="interrupt"`，中断旧 run 并在同一 thread 上开新 run。`task_id` 不变（它等于 thread_id），但 `run_id` 会更新。子代理能看到完整历史加上新指令。

🇹🇸 TS 侧实测完全一致：`taskId` 不变、`runId` 从 `r-1` 变 `r-2`、假服务收到的 `multitask` 策略就是 `interrupt`。区别只在字段名——TS 的 `AsyncTask` 里是 `taskId` / `agentName` / `threadId` / `runId`，全驼峰。

</details>

**Q3**：动态子代理 `Promise.all` 派 12 个子代理 vs 并行 `task` tool_calls 派 12 个，哪个更快？
- A. 动态更快
- B. 并行 tool_calls 更快
- C. 一样快
- D. 取决于模型

<details><summary>答案与解析</summary>

**答案：B（Python 侧）**。实测 N=12：并行 0.111s，动态 0.225s。动态多了解释器启动 + 序列化往返的固定开销。动态的价值不在速度，在主上下文体积（N=8 时 3526 → 38 字符）。

🇹🇸 **TS 侧这题答案变了，选 A**：实测 N=12 并行 0.052s、动态 0.049s，动态反而快 1.06 倍；N=30 也是动态快 1.10 倍。只有 N=4 这一档动态慢 1.11 倍。原因是 TS 的 QuickJS 起停比 Python 的桥接轻、固定开销被摊薄。

**所以这道题真正该记住的不是 A 还是 B，而是"速度不是选型判据"**：两侧速度差都在 1 倍上下浮动，属于噪声量级；而上下文差异是 401 倍和 93 倍，差两个数量级。用速度选型会选错，用上下文体积选型才稳。

</details>

**Q4**：异步子代理任务状态是 `waiting`，说明什么？
- A. 正在排队等资源
- B. 子代理在等人审批或回答
- C. 已经成功但结果没取
- D. 网络超时

<details><summary>答案与解析</summary>

**答案：B（Python 侧）**。源码注释：run 碰到 `interrupt()` 时状态是 `success`，只有 thread 才显示暂停。所以 `waiting` 是靠查 thread 判断出来的。而且这个审批必须用户在那个子代理自己的 thread 上回答，主代理不能代批。

🇹🇸 **TS 侧这题不成立——TS 根本没有 `waiting`**。`AsyncTaskStatus` 只有 7 个值：`pending` / `running` / `success` / `error` / `cancelled` / `timeout` / `interrupted`。Python 那个"thread 暂停 → waiting"的映射（`_THREAD_TO_TASK_STATUS`）在 TS 侧不存在。

危险后果：**一个正在等人审批的远程子代理，在 TS 的异步视图里会显示成 `success`**。主代理看到 `success` 就去取结果，取到的是半截。规避办法是异步子代理的远程图不要配 HITL——需要人审批的活儿留在同步子代理或主代理上做。

</details>

**Q5**：解释器里 `typeof require` 返回什么？
- A. `"function"`
- B. `"object"`
- C. `"undefined"`
- D. 抛 ReferenceError

<details><summary>答案与解析</summary>

**答案：C**。实测返回 `undefined`。解释器全局只有 `console`、`performance`、`task` 等少数对象。注意 `typeof Deno.readTextFile` 会抛 ReferenceError（因为访问 `Deno` 这个未声明标识符的属性），这是两者的区别——`require` 是声明过的但值为 undefined。

🇹🇸 TS 侧答案同样是 C，而且更彻底：`require` / `process` / `fetch` / `Deno` 四个探针全是 `undefined`。全局对象实测为 `__sessionId__,console,performance,task`。

另外 TS 侧有个 Python 没有的坑：**完全不配 `subagents` 时，`typeof task` 仍然是 `"function"`**——`task` 是桥接层注入的，不看有没有子代理。要真关掉得显式写 `subagents: false`，那时 `eval` 返回才变 `undefined`。所以"用 `typeof task` 判断动态派发是否可用"这个写法在 TS 侧无效。

</details>

## 🇹🇸 本课双语差异速查

| 差异点 | Python | TypeScript |
|---|---|---|
| 分流键名 | `graph_id` | `graphId` |
| 分流判据强度 | `"graph_id" in spec` | `"graphId" in subAgent`，**空串也算异步** |
| 重名检查 | 抛 `Duplicate async subagent names` | 同，抛 `Duplicate async subagent names: dup` |
| 任务状态集 | 8 个，含 **`waiting`** | 7 个，**无 `waiting`** |
| thread 暂停的映射 | `{"interrupted": waiting, "busy": running}` | **无此映射**，暂停的 thread 表现为 `success` |
| 自动轮询 | `before_agent` / `before_model` / `after_model` 三钩子 | **无钩子**，只有 `tools` + `wrapModelCall` |
| 中间件自动给的 systemPrompt | 有（含"别自动 check""别照抄旧状态"硬规则） | **不传**，只在你显式传 `systemPrompt` 时才有 |
| 动态子代理归属 | `deepagents` 包内 | 独立包 `@langchain/quickjs` |
| 动态子代理构造 | 类 `CodeInterpreterMiddleware()` | **工厂** `createCodeInterpreterMiddleware()` |
| 依赖声明 | 装在 deepagents 里 | `peer: deepagents >= 1.13.4-rc.0` |
| 并发上限字段 | `max_subagent_concurrency`（默认 32）| `maxSubagentConcurrency`（默认 32）|
| 非法并发值 | 未实测 | **创建期抛错** `must be a positive integer` |
| 子代理抛异常 | 返回 `<error type="RuntimeError">` 字符串 | **`promise.reject`**，直接抛到 JS 侧 |
| 未知 `subagentType` | 返回字符串说明 | **抛错** `invoked agent of type X` |
| 未知工具键 | 未实测 | **抛错** 并列出允许键 |
| 蛇形键兼容 | 不适用 | `subagent_type` 自动改名成 `subagentType` |
| 不写 url | 报 `ASGI transport (url=None) requires async invocation` | 报 `ConnectionError`，回落 **localhost:8123** |
| `check_async_task` 返回 | 人话 + 字段 | **纯 JSON 字符串** |
| `statusFilter` 筛什么 | 缓存状态 | 缓存状态（同）|
| 终态任务再 cancel | 再发一次远程 cancel | 同（两侧都宽松）|
| 工具基线数 | 8（无 `execute`）| 9（多 `execute`）|
| 异步子代理工具数 | 13 | 14 |
| 中间件栈长度 | 有异步时多 1 条 | 有异步时 5 → 6 条 |
| `task()` 不配 subagents | 不可用 | **`typeof task` 仍是 function**，需 `subagents: false` |
| 不在系统提示时谁能提醒 | 钩子会推 | **没人**，只能靠模型自己想起来 |
| `Promise.all` 一失败 | 不适用 | **全崩**，要 `Promise.allSettled` |

> 这张表里最该记住的是三行：**TS 没有 `waiting`**（等人审批显示成 `success`，主代理会去取半截结果）、**TS 没有自动轮询**（模型不问就永远不知道进展）、**TS 的动态子代理在独立包里且是工厂函数**（写错不报模块不存在，运行时炸）。这三条都不是"写法差异"，是会让你的异步流程静默失效的差异。
