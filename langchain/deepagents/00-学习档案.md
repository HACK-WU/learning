### 课 6 复盘（沙箱与解释器）

- 核心洞见：
  - 沙箱不是新工具，是一种"让 `execute` 留下来的资格"——由 `isinstance` 判定，`Composite` 只看 `default`。
  - `BaseSandbox` 的真实门槛是三个方法（`execute` / `upload_files` / `download_files`），不是文档说的"只需 execute"。
  - 两个平面：`write` 走 `upload_files`、`read` 走 `execute`，同一个路径在两条路上指向不同存储。
  - 解释器是"只算不碰的纸"：默认够不着文件 / 网络 / shell；两座桥（PTC 白名单、`task()`）都要显式搭。
  - "权限 + 执行能力"是不安全组合：配错（非 Composite / 路径越界）直接构造期 `NotImplementedError`。
- 配套：应用实战 `应用实战/06-沙箱与解释器分工.md`、源码解析 `源码解析/06-沙箱协议与execute派生.md`。

### 课 7 复盘（Skills 技能）

- 核心洞见：
  - 渐进式披露的"省"是数量问题不是二值——固定说明约 1.9k 字符不随 skill 数变，单个小技能反而更贵（1 个 500 字符 = 388%）。
  - `/skills/` 里的路径是给后端解析的键，不是 OS 路径；默认 `StateBackend` 下 `./skills` 会 `path_not_found` 且静默。
  - `read_file` 返回完整 frontmatter；`pinned_skills` 返回剥掉 frontmatter 的正文，两条路径行为不同。
  - `include_tools` 是"读到才披露"：实测首轮 8 个工具，读过 skill 后 9 个。
  - 顺序即收益：skills 在压缩/fallback 之后、prompt caching 之前；Memory 在缓存后，刻意对立。
- 配套：应用实战 `应用实战/07-Skills技能.md`、源码解析 `源码解析/07-SkillsMiddleware与披露链路.md`。源码锚点：`graph.py:683` 的 `_passed_skills_sources`（同名实例替换默认槽位）；`skills.py` 的 `before_agent` / `modify_request`；`_skill_tools.py` 的 `_disclose_skill_tools`。

### 课 9 复盘（上下文工程）

- 核心洞见：
  - 压缩不是一个动作，是四个：卸载（20k token，每次工具调用都查）、裁剪参数（约 85%，老的 write/edit 参数截成指针）、摘要（约 85% 且无可卸载时）、修补悬空调用（不压缩但必需）。
  - `TOOLS_EXCLUDED_FROM_EVICTION` 排除了全部 7 个文件工具——因为 `read_file` 有 offset/limit 分页，从一开始就不给自己变大的机会（实测 600KB → 455 字符）。
  - 摘要不动 `state["messages"]`：实测输入 16 条、送模型 4 条、state 仍 17 条，压缩发生在 `wrap_model_call`，原文可回放可评测。
  - 默认阈值随模型 profile 变：有 profile 走 `("fraction", 0.85)` / `("fraction", 0.10)`，无 profile 退回 `("tokens", 170000)` / `("messages", 6)`；200k 窗口恰好算出 170k，与固定值撞上。
  - 缓存实际注册三家（Anthropic / Bedrock / Fireworks，后两者装包才注册），官方文档只写两家；非 Anthropic 上中间件存在但 no-op（无 `cache_control` 键）。
  - `PatchToolCallsMiddleware` 区分"未完成"与"参数畸形"，都补 `status="error"`，这是中断后可恢复的基础。

### 课 10 复盘（任务规划与子代理）

- 核心洞见：
  - `write_todos` 的消失是 v0.7 静默变更（#4929）：`create_deep_agent` 不再默认包含 `TodoListMiddleware`，升级后工具消失且不报错；加回 `middleware=[TodoListMiddleware()]`。官方实测三类模型关闭 todos 反而奖励略高、成本略低，所以默认是"省"。

### 课 11 复盘（人在环中）

- 核心洞见：
  - `interrupt_on` 三种形态（`True` / `False` / `{allowed_decisions, when}`），四种决策全部实测：`approve` 原样执行、`edit` 改参数（`/a.txt` 不写、`/safe.txt` 写 `'改过的内容'`）、`reject` 回传原因、`respond` **不执行**而是把人的话当 ToolMessage。
  - **骨架"不能按参数条件触发"是错的**：`InterruptOnConfig` 有 `when: Callable[[ToolCallRequest], bool]`，实测 `only_bulk` 谓词让群发 `all@` 中断、单发 `one@` 不中断。`permissions` 的 `mode="interrupt"` 更内建按路径谓词（写 `/secrets/key.txt` 中断、写 `/public/ok.txt` 不中断）。谓词抛异常会直接把 run 炸掉，需防御性写法。
  - checkpointer 是硬前置：无 saver 时 `__interrupt__` 照样产生但 `Command(resume=...)` 报 `RuntimeError: Cannot use Command(resume=...) without checkpointer`。恢复必须同一 `thread_id`，且 resume 结构是 `{"decisions": [...]}`（传裸 list 会 `TypeError: list indices must be integers`）。
  - 中断信息在 `__interrupt__` 键，不在 `messages`（中断态只有 human + ai 两条，ai 带 1 个 tool_call 无对应 ToolMessage = 悬空调用）。
  - `PatchToolCallsMiddleware` 在 `before_agent` 修补悬空调用：实测中断后不批准直接问别的事，自动补 `status="error"` 的 ToolMessage（"did not complete - no result was recorded"）再继续，模型不会看到畸形对话。
  - 装配位置：`HumanInTheLoopMiddleware` 只在 `main_interrupt_on is not None` 时入栈，位置在 `MemoryMiddleware` 之后、`UnsupportedContentMiddleware` 之前；`permissions` 的 interrupt 规则先转 `interrupt_on` 再与用户配置合并（用户项优先）。
  - `deny` 优先于 `interrupt`：同路径两者都配，实测不中断、直接 `Error: permission denied`（不浪费人点注定被拒的事）。
  - 子代理的 `interrupt_on` 能让**父图**暂停（实测待批动作 `['write_file']` 冒到最外层）——审批是图级而非工具级，这解释了课 12 异步子代理为何要另作处理。
  - `allowed_decisions` 是硬校验不是 UI 提示：只允许 `["approve","reject"]` 时传 `edit` → `ValueError: Unexpected human decision`。
- 配套：应用实战 `应用实战/11-人在环中.md`。源码锚点：`graph.py:955-961`（permissions→interrupt 转换 + HITL 入栈条件 + 位置）；`_fs_interrupt.py:20-45`（文件工具路径/作用域映射表）、`:157-203`（从 permissions 生成 InterruptOnConfig）；`human_in_the_loop.py:815`（`interrupt(hitl_request)["decisions"]`）、`:818-825`（决策数量校验）；`patch_tool_calls.py:14-56`（`before_agent` 修补悬空调用）。


### 课 12 复盘（异步与动态子代理）

- 核心洞见：
  - 异步子代理不是进程内并发，而是**通过 LangGraph SDK 在远程 Agent Protocol 服务器上建 thread + 起 run**。分流判据是 `"graph_id" in spec`（`graph.py:691-694`），实测 `{"url":"http://x"}` 只写 url **不走异步**。
  - 工具是**五个**不是四个：`start_async_task` / `check_async_task` / `update_async_task` / `cancel_async_task` / `list_async_tasks`（骨架叫 "launch" 且漏了 list）。实测工具计数：同步或无子代理 8 个，配异步后 13 个。
  - 不配 `url` 走进程内 ASGI，只支持 `ainvoke`。但**报错被 `start_async_task` catch 成普通工具返回值**，流程不中断（实测 ToolMessage 含 "ASGI transport (url=None) requires async invocation"），比抛异常更隐蔽。
  - `update_async_task` 用 `multitask_strategy="interrupt"`：中断旧 run、同 thread 开新 run，`task_id` 不变（task_id 就是 thread_id），`run_id` 变。
  - `waiting` 状态只能靠查 thread 得出：run 碰到 `interrupt()` 会显示 `success`，只有 thread 显示暂停（`_task_status`）。这类审批**主代理不能代批**，用户得去子代理自己的 thread 回答。
  - `cancel` 在 `waiting` 状态不调远程 cancel（没有活跃 run），只标本地 cancelled。
  - 动态子代理的 `task()` **不是独立实现，而是桥接外层 `task` 工具**（`_repl.py:536-560` 的 `find_subagent_task_tool`），所以即使只配同步子代理也能动态派发。
  - **动态的真实收益是上下文，不是速度**。实测 N=8（每份约 600 字）：并行 task tool_calls 主上下文 3526 字符 / 8 条 tool 结果 / 11 条消息；动态 eval 只有 **38 字符 / 1 条 / 4 条消息**（省 93 倍）。但耗时动态更慢：N=4 0.087 vs 0.329（慢 3.8 倍）、N=12 0.111 vs 0.225、N=30 0.196 vs 0.317——解释器启动+序列化是固定开销，不随 N 摊薄。
  - 解释器边界实测（`Object.keys(globalThis)`）：只有 `console, performance, task` 等；`require`/`process`/`fetch` 都是 `undefined`，`Deno` 直接 ReferenceError。无文件、无 shell、无网络，是沙箱性质而非 permissions 拦的。
  - 子代理失败不中断 eval，返回 `<error type="RuntimeError">...`，脚本必须自己判。
  - `max_subagent_concurrency` 默认 **32**，实测设为 2 时峰值并发真的压到 2（耗时 0.57s→1.17s）。非法值（0/-1/**1.5**）全拒，因为检查是 `type(x) is not int`。
  - `AsyncSubAgentMiddleware` 只在 `if async_subagents` 时入栈，位置在 `PatchToolCallsMiddleware` 之后（与骨架一致）。
- 配套：应用实战 `应用实战/12-异步与动态子代理.md`。源码锚点：`graph.py:691-694`（graph_id 分流）、`:923-926`（异步中间件入栈）；`async_subagents.py` 的 `_ClientCache.get_sync`（ASGI 限制）、`_task_status`/`_THREAD_TO_TASK_STATUS`（waiting 判定）、`_build_update_tool`（interrupt 策略）、`_awake_parent`（空闲才推送通知）、`_build_async_subagent_tools`（五个工具）；`langchain_quickjs/_repl.py:63`（并发默认 32）、`:536-560`（task 桥接）、`:502-533`（payload 校验）。


### 课 13 复盘（生产化：容错、流式与上线）

- 核心洞见：
  - **"限流"在框架里不存在**：`langchain.agents.middleware` 带 Limit 的只有 `ModelCallLimitMiddleware` / `ToolCallLimitMiddleware`，是**调用次数上限（budget）**，不是 QPS 限速。官方 fault-tolerance 文档把这一列叫 "excessive calls (runaway loops)"（防失控循环），429 的 QPS 限流要在外部网关做。
  - **重试判定在异常家族，不在错误码**：`default_retry_on(exc)` 对 `isinstance(exc, ModelError)` 才看 `exc.is_retryable`，其他异常一律返回 True。实测：`ModelAuthenticationError`(401)/`ModelPermissionDeniedError`(403)/`ModelInvalidRequestError`(400)/`ModelNotFoundError`(404) 的 `is_retryable=False`（不重试）；`ModelRateLimitError`(429)/`ModelAPIError`(5xx)=True（重试）；**普通异常（含模拟 401 的 RuntimeError）→ 重试 True**。所以"401/400 不可重试"只在异常是 ModelError 子类时成立。`is_retryable` 是**类属性**，不是构造参数。
  - **重试与降级的顺序决定降级是否触发**（实测）：重试在前、降级在后 → primary 只调 1 次就降级到 backup1；降级在前、重试在后 → primary 连调 3 次报错，backup1 从未被调。正确姿势：`ModelRetryMiddleware` 在外，`ModelFallbackMiddleware` 在内。
  - **子代理不继承主代理的容错中间件**（实测）：主模型配 `ModelRetryMiddleware(max_retries=2)`，子代理模型抛 `ModelAPIError` 时只调 1 次就抛穿主代理（task 变 ToolMessage），未被重试。子代理容错要显式配进子代理的模型或靠顶层覆盖。
  - **`stream.subagents` 的正确入口是 `agent.stream_events(..., version="v3")`**，不是 `agent.stream()`（实测 `agent.stream` / `astream` 无 `subagents` 属性；`stream_events` 返回 `GraphRunStream`，投影含 subagents/messages/tool_calls/values/output）。同步 v3：`sub.output` 是普通 dict（直接读）；异步 `astream_events` 先 await 拿 run、`sub.output` 是方法（要 call）。
  - **StreamChannel 单订阅限制**（实测，文档没提）：`stream.subagents` 只能被遍历一次，第二次 `for` 抛 `RuntimeError: StreamChannel already has a subscriber; use .atee(n) for fan-out`。多消费者要 `run.subagents.atee(n)` 分叉。
  - **不配 checkpointer + interrupt_on 的行为**（实测）：invoke 正常触发中断（`__interrupt__` 有值）——测试看着"能暂停"；但 `Command(resume=...)` 恢复时炸 `RuntimeError: Cannot use Command(resume=...) without checkpointer`。这是"测试通过、上线暴露"的第一坑。
  - 持久化三模式：`durability="exit"`（图结束才落盘，最快）、`"async"`（默认，可能丢最后一步）、`"sync"`（每步同步，最慢最安全）。`MemorySaver` 是内存实现，进程重启全丢。
  - 版本锁定：当前基线 `deepagents 0.7.28`，要求 `langchain>=1.4.6,<2.0.0`、`langchain-core>=1.6.11,<2.0.0`、Python `>=3.11,<4.0`；extras `quickjs(>=0.3.9)` 等。v0.7 的 `write_todos` 静默 opt-in 是上线最容易忽略的差异。
  - 工具级重试与失败策略（实测）：`ToolRetryMiddleware(max_retries=2)` 让工具实调 3 次；`on_failure="error"` 异常直接传播、`"continue"` 转成错误 ToolMessage；`ToolCallLimitMiddleware` 默认 `exit_behavior="continue"`（限 1 次调 3 轮 → 工具实际只执行 1 次但流程继续），`ModelCallLimitMiddleware` 默认 `"end"`（超限正常收束，消息含 "Model call limits exceeded: thread limit (3/3), run limit (3/3)"）。
  - 栈内装配顺序（源码 graph.py）：`Filesystem → SubAgent → _ParentNotifier → summarization → PatchToolCalls → AsyncSubAgent(若配) → interrupt → UnsupportedContent → _ToolExclusion(若配)`；用户 middleware 中名字与栈内重名者**原位替换**，新名字插在最后一个 core 之后、profile/缓存/记忆尾之前（`_apply_custom_middleware:211-245`）。
- 配套：无应用实战（本课为清单检查，工程落地归 Phase 3 结课项目）。源码锚点：`graph.py`（装配顺序）；`langchain/agents/middleware/_retry.py`（default_retry_on / calculate_delay / validate_retry_params）、`model_retry.py`、`model_fallback.py`、`model_call_limit.py`、`tool_call_limit.py`、`tool_retry.py`；`langchain_core/exceptions.py:68-108`（ModelError 家族与 is_retryable 类属性）；`stream_events`/`astream_events` v3 的 subagents 投影与 StreamChannel（langgraph/stream/stream_channel.py）。
