## 🔴 症状 1：长周期查询直接报错

**一眼识别**：HTTP 500，响应体含
`Query would scan 432 Parquet files, exceeding the file limit`
**不是超时、不是变慢，是查询根本没执行。**

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 把查询窗口收窄到 3 天内；或临时把面板的时间范围改小 | 查询恢复正常返回 |
| 定位 1 | `SELECT count(*) FROM system.parquet_files` | 看当前文件总数；接近或远超 432 即确认是文件数问题 |
| 定位 2 | 重放同样的查询，但窗口换成 2 小时 | 若 2 小时能过、30 天报错 → 确认是文件数上限，不是数据或语法问题 |
| 定位 3 | 算窗口：`可查天数 ≈ query_file_limit × gen1_duration(分钟) ÷ 1440` | 默认 `432 × 10 ÷ 1440 = 3 天` |
| 修复 | 三选一：① 收窄窗口（官方推荐）② 建降采样层查聚合表 ③ 换 Enterprise / 调大 `--query-file-limit` | 长周期查询可用 |
| 若无效 | 若刚装完能查、过几天就不能查 → 数据在 WAL 里时不受限，落 Parquet 后才触发。这是**延迟引爆**，不是配置没生效。仍无法定位 → 转 `debug` | — |

> ⚠️ **调大 `--query-file-limit` 前先读代价**：查询变慢、内存飙升、进程可能被 OOM 杀掉、对象存储上每个文件最多 2 次 GET。官方建议保持默认值。
>
> **预防**：建降采样层，长周期只查聚合表。
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 1

## 🔴 症状 2：数据静默消失（写入全 204，查不到）

**一眼识别**：写入持续返回 HTTP 204，但 `SELECT count(*)` 为 0 或远少于预期；日志无任何报错；磁盘占用却在涨。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 立即查保留期：`influxdb3 show databases`，看 `retention_period` 列 | 若显示 `0d` → 根因确认 |
| 定位 1 | 确认语义：3.x 里 `0d` = **查询时立即标记全部删除**；1.x/2.x 里 `0d` = 永久 | 从旧版运维脚本复制过来的 `0d` 是典型来源 |
| 定位 2 | 检查其他反转/漂移写法：`mo` = 30 天（三个自然月是 91.3 天）、`y` = 365 天 | 保留期与合规要求是否对得上 |
| 修复 | Core 的保留期**创建后不可改** → 只能用正确保留期建新库并迁移数据 | 新库数据可见 |
| 若无效 | 数据在物理删除前可能仍在存储上，动作要快；仍不可见 → 转 `debug` | — |

> ⚠️ **抢时间**：保留期是查询时过滤，物理删除由保留强制执行服务**异步**完成，跑完就真没了。发现 `0d` 后第一件事是止血，第二件事才是查根因。
>
> **预防**：永久保留写 `none`，绝不写 `0d`；建库脚本纳入版本管理。
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 2

## 🔴 症状 3：写入返回 400，部分数据进去了

**一眼识别**：HTTP 400，响应体含
`{"error":"partial write of line protocol occurred","data":[{"line_number":2,"error_message":"invalid column type for column 'temp', expected iox::column_type::field::float, got iox::column_type::field::string"}]}`
或 `{"error_message":"No fields were provided"}`

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 判断业务能否接受部分写入：不能接受 → 请求加 `accept_partial=false` 让整批拒绝，避免脏数据 | 要么全成、要么全败，状态清晰 |
| 定位 1 | 读响应体 `error_message`，记下 `expected` 与 `got` 的类型 | 明确冲突的具体列 |
| 定位 2 | `SELECT column_name, data_type FROM information_schema.columns WHERE table_name = '<表名>'` | 看到该列当前已定型为什么 |
| 定位 3 | 查是哪一个采集端在写错类型（新设备 / 新版本 SDK） | 定位到具体写入方 |
| 修复 | 修采集端类型：字符串加双引号、整数加 `i` 后缀、浮点与布尔**不加引号**；两种类型都要存 → 换 field 名或全转字符串 | 写入返回 204 |
| 若无效 | 若列类型已被污染且无法改 → 只能新建表（改名）；仍报 400 → 转 `debug` | — |

> 💡 **第一次成功的写入给列定型**，后续类型不同不会被转换，只会被拒绝。
>
> **预防**：客户端解析 400 的响应体而非只看状态码；给采集端字段类型定契约并加 lint。
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 3

## 🔴 症状 4：进程被 OOM 杀掉 / 内存预算耗尽

**一眼识别**：进程突然消失且日志无优雅退出记录；`dmesg \| grep -i oom` 有命中；或 DataFusion 报内存预算耗尽。监控上 **CPU 不到 50%，内存已顶满**。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 收窄查询窗口（与症状 1 同源，文件数是万恶之首）；必要时临时限流大窗口查询 | 内存回落，进程稳定 |
| 定位 1 | 确认是 OOM kill 还是主动退出：`dmesg \| grep -i oom` | 有命中 → OOM；无 → 查其他退出原因 |
| 定位 2 | 核对三项内存默认：**快照阈值 50% + DataFusion 执行池 20% + Parquet 缓存 20% = 90%** | 留给 OS / WAL / 网络缓冲的只剩 10% |
| 定位 3 | 看是否在大窗口查询后才开始崩 | 文件数一多，每个文件都要读元数据与行组，内存线性涨 |
| 修复 | ① 收窄窗口 ② 显式调小 `--parquet-mem-cache-size`（如 10%）让给执行池 ③ 需大窗口 → 降采样或换 Enterprise | 进程稳定，无 OOM |
| 若无效 | 不要靠调大 `--query-file-limit` 硬扛，那会加剧内存问题；仍 OOM → 转 `debug` | — |

> ⚠️ **容器场景**：设 memory limit 时必须把这 90% 算进去，否则等于让 InfluxDB 在沙箱里跑马拉松。
>
> **预防**：容量规划按内存算不按 CPU 算。
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 4

## 🟡 症状 5：保留期改不了

**一眼识别**：更新保留期的命令失败或选项不存在；Enterprise 文档里的"修改保留期""表级保留期"在 Core 上都没有。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 确认当前库的实际保留期：`influxdb3 show databases` | 明确现状，评估数据风险 |
| 定位 1 | 确认运行的是 Core 还是 Enterprise | Core 上"改保留期"是**功能差异**，不是 bug |
| 定位 2 | 若当前保留期有风险（如 `0d`）→ 立即按症状 2 处理 | 优先止血 |
| 修复 | 建新库（正确保留期）+ 迁移数据 | 新库保留期正确 |
| 若无效 | 迁移窗口注意：Core 双写窗口只有 1–3 天，写太久最早的数据反而查不到；仍失败 → 转 `debug` | — |

> **预防**：建库那一刻就把保留期定对，字面值逐字核对。
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 5

## 🟡 症状 6：写入报错，撞上硬限制

**一眼识别**：写入失败并报错，此前一直正常；库数 / 表数 / 列数刚突破阈值。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 若刚新增的采集端在自动建表 → 先停掉该采集端 | 停止阈值继续恶化 |
| 定位 1 | 数库与表：`influxdb3 show databases` + 各库表数量。**Core：库 5 / 所有库的表总计 2000 / 单表 500 列** | 明确撞的是哪一项 |
| 定位 2 | `SELECT count(*) FROM information_schema.columns WHERE table_name = '<表名>'` | 看列数是否超限 |
| 定位 3 | 检查 tag 里有没有"每个点都不同"的字段（`order_id`、`trace_id`）或随时间单调增长的表名（表名带日期/设备 ID） | 定位到具体设计缺陷 |
| 修复 | 高基数字段从 tag 降级为 field；按日期建表的改为 tag 区分；表数真需要更多 → 评估 Enterprise | 写入恢复 |
| 若无效 | Enterprise 的表上限各版本文档口径不一，请查当期官方文档确认；仍失败 → 转 `debug` | — |

> **预防**：schema 评审时对每个 tag 问"取值多少种、会不会随时间单调增长"；给表数量设监控告警。
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 6

## ⚪ 症状 7：压缩率极差，磁盘涨得比数据量快

**一眼识别**：同样数据量，磁盘占用是预期数倍；Parquet 文件数量正常但单文件体积异常；**查询没有明显变慢**，只是存储成本失控。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 一般无需紧急止血（不影响可用性）；若磁盘将满 → 先缩保留期或归档冷数据 | 磁盘不再上涨 |
| 定位 1 | 算点密度：`该表点数 ÷ (series 数 × 时间块数)` | 接近 1 健康；远小于 1 说明 series 太碎 |
| 定位 2 | 对比 tag 组合数与实际点数 | 每个 series 只贡献极少的点 → 压缩失效 |
| 定位 3 | 查 Parquet 压缩前后大小 | 量化压缩率缺口 |
| 修复 | 高频变化、取值极多的维度从 tag 挪到 field；去掉不必要的维度；长周期数据改用降采样层承载 | 压缩率回升 |
| 若无效 | 仍无改善 → 转 `debug` 分析具体 schema | — |

> 💡 **易混点**：官方说"高基数不影响整体性能"讲的是 1.x/2.x 的历史痛点（TSM 索引爆炸），3.x 确实解决了；但**点密度影响的是压缩率**，是另一回事。基数高不慢，但基数高**占地方**。
>
> **预防**：schema 设计阶段算一遍基数乘法（`基数 = tag1 取值数 × tag2 取值数 × ...`），这是乘法不是加法。
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 7

## 🟡 症状 8：崩溃重启后丢失最后几秒写入

**一眼识别**：强杀进程后重启，最后几秒到几十秒的写入丢失；或重启后 WAL 重放耗时很长，服务迟迟不可用。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 确认丢失的数据能否从上游重放（Telegraf buffer / Kafka / 采集端本地缓存） | 能重放则先补数据 |
| 定位 1 | 检查写入请求是否带 `no_sync=true` | 带了 = 崩溃时**允许丢数据**，符合预期 |
| 定位 2 | 查上次停机方式：`kill -9` / `docker kill` / OOM kill 都是强杀，会绕过 WAL 刷写 | 确认是不是强杀导致 |
| 定位 3 | 查 WAL 配置：`--wal-max-write-buffer-size`、`--wal-replay-concurrency-limit` | 并发设太高会在重放时 OOM |
| 修复 | 需要持久性 → `no_sync` 保持默认 `false`；停机脚本统一改 SIGTERM 并等待退出；容器 `terminationGracePeriodSeconds` 设够 | 重启不再丢数据 |
| 若无效 | 重放仍然极慢或 OOM → 调低 `--wal-replay-concurrency-limit`；仍失败 → 转 `debug` | — |

> **预防**：把"用什么信号停机"写进运维手册；对 `no_sync=true` 的写入路径单独标注，让下游知道这批数据允许丢。
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 8

## 🟡 症状 9：认证与端点不通

**一眼识别**：HTTP 401（认证）或 HTTP 404（资源不存在）。这条是**分流入口**，先排除它再查别的。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 确认 token 是否还有效、是否被轮换 | 排除最常见的认证失效 |
| 定位 1 | **401** → `Authorization` 头缺失/格式错误，或 token 无该库的写权限 | 补 `Authorization: Bearer <TOKEN>` |
| 定位 2 | **404** → 库名不存在，或端点路径写错 | 写入原生端点是 `/api/v3/write_lp`，不是 `/write` |
| 定位 3 | 核对 host 是否带 scheme（`http://` 不能省） | 客户端默认写 V2 端点，注意区分 |
| 修复 | 按上面三条分别修正 | 请求返回 204 |
| 若无效 | 仍不通 → 转 `debug` 抓完整请求与响应 | — |

> **预防**：token 轮换纳入变更管理；客户端配置里的 host 统一带 scheme。
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 9

## 🚑 通用止血动作（不确定是哪类问题时，先把损失停下）

| 场景 | 止血动作 | 代价 |
|------|----------|------|
| 查询报文件数超限 | 收窄查询窗口到 3 天内 | 暂时查不到长周期数据 |
| 怀疑保留期写错（`0d`） | 立即建正确保留期的新库，把新写入切过去 | 需要迁移历史数据 |
| 写入部分失败且业务不接受 | 加 `accept_partial=false` 让整批拒绝 | 批次整体失败，需重投 |
| 内存濒临 OOM | 限流大窗口查询；必要时重启并调小 Parquet 缓存 | 部分查询被拒 |
| 刚变更就出问题 | 回滚变更（配置 / 版本 / schema） | 丢失新功能 |
| 采集端在疯狂自动建表 | 停掉该采集端 | 该来源数据中断 |
