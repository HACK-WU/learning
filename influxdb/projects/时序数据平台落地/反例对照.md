# 反例对照 · 时序数据平台落地

> 不是"错误示例"，而是**看起来能跑、实际很糟**的版本 —— 只有这样才能教会"为什么最佳实践是最佳实践"。

## ❌ 反例：单文件硬编码版（`实现/bad_example.py`）

```python
def check(name, pps, days, tags, fields, want_managed, need_v3,
          need_pe, need_ha, telegraf_urls, db_tag_card, org, panels, refresh):
    problems = []

    # 硬限制（写死在这里，别的模块拿不到）
    if len(tags) + len(fields) + 1 > 500:
        problems.append("列数超限")

    # 基数
    series = 1
    for v in tags.values():
        series *= v
    if pps / series < 0.01:
        problems.append("点密度太低")

    # ⚠️ 致命：把 432 无条件套用到所有形态，不管选的是哪个 SKU
    files = FILES_PER_DAY * days
    if files > QUERY_FILE_LIMIT:
        problems.append(f"文件数 {files:.0f} 超限")

    # 降采样：只按默认 10 分钟算，从不读用户配置的调度周期
    if days * 24 * 6 > QUERY_FILE_LIMIT:
        problems.append("降采样层超限")

    # 保留期：只检查了一个坑
    if days <= 0:
        problems.append("保留期必须为正")

    # Telegraf：只看了 URL 数量，语义理解成负载均衡
    if len(telegraf_urls) > 1:
        problems.append("多 URL 有负载均衡风险")
    if db_tag_card > 5:
        problems.append("database_tag 库数超限")
    if org:
        problems.append("organization 非空")

    # SKU 排雷：只排了一个，而且没区分「不满足」与「约束打架」
    if want_managed and need_v3 and need_pe:
        problems.append("Serverless 不满足")

    # 成本：只算机器钱，人力按 0 处理
    cost = 240
    if panels and refresh:
        cost += panels * (60 / refresh) * 60 * 730 / 100 * 0.012

    return problems, cost
```

> 它**能跑通**（`rc=0`），输出看着也挺像回事：
> ```
> 问题： ['文件数 12960 超限', '降采样层超限', '多 URL 有负载均衡风险',
>        'database_tag 库数超限', 'organization 非空']
> 月成本：$366.14
> ```
> 问题在下面。

## 🔍 逐条对比

| # | 维度 | ❌ 反例 | ✅ 正确做法 | 为什么糟 |
|---|------|---------|------------|----------|
| 1 | **约束归属** | `432` 无条件套用到所有形态 | `SKU_FILE_LIMIT` 按 SKU 分列：Core 是硬约束（报错），其他有 compactor 免检 | 这是 L19 修过的 **P0-1**。正确版算出 IoT 场景幸存 `enterprise / serverless / dedicated`，而反例还在报"文件数超限"—— **它警告的那个 SKU 根本不在候选集里**，把人引向"缩短查询窗口"这个根本不需要的妥协 |
| 2 | **降采样口径** | 硬编码 `days * 24 * 6`（写死 10 分钟），从不读用户配置的 `downsample_interval_min` | `files = 窗口天数 × 24 × 60 ÷ 调度周期(分钟)`，并反解出最小可行周期 | ⭐ L14 核心结论：**降采样层能否查到取决于调度周期，不是精度**。反例把最重要的那个变量写死成常量，等于这条规则对真实配置永远无效 |
| 3 | **Telegraf 语义** | "多 URL 有负载均衡**风险**" | "多 URL = **故障转移**，每次 flush 随机挑一个，另一个不会有副本" | 语义完全理解反了。按"风险"理解会以为数据被均衡写到了两边，**而实际是另一个实例一条数据都没有** —— 故障时你以为有备份，其实没有 |
| 4 | **保留期检查** | 只查 `days <= 0` | 解析实际写法，分两类命中检测：`0d` 语义反转（**reverse**，灾难级，P0）+ `mo`/`y` 非日历（**drift**，合规级，P1）；未命中的降 INFO 保留作检查项 | ⭐ L18 核心结论。反例完全没覆盖 `0d` 反转 —— 而这是**唯一一条会让你静默丢光数据**的差异。它拦住了"保留期为 0 天"（会立刻报错，有声音），却放过了"从 1.x 迁移过来的 `0d` 表示永久"（静默删库） |
| 5 | **成本口径** | 只算机器钱 $240 + 面板查询费，运维人力按 0 | 显式列出主机 / 存储 / **运维人力**，并提示 Enterprise 授权费未知 | 反例算出 **$366/月**，正确版算出 IoT 场景 Core 自托管 **$7,780/月** —— 差 **21 倍**，因为漏算了占 96% 的运维人力。按反例的数字做预算会上演"省了托管费、赔了两个人" |
| 6 | **输出可追溯** | 只有一句话字符串（`"列数超限"`） | `Finding` 带 `stage`（阶段·课时）、`detail`（依据）、`action`（建议），并标 ⭐/⚠️/📌 | 看到"列数超限"你不知道是 Core 的哪个限制、要不要改、改成多少。正确版写明"Core 上限 500 列，当前 X 列，建议拆表"—— **能直接照着做** |
| 7 | **退出码** | 永远 `rc=0` | `0` 通过 / `1` 有 P0 / `2` 只有 P1 / `3` 参数错 | 反例**看着跑得很成功**（rc=0），实际上它同时漏掉了 3 个 P0。进 CI 时这个脚本永远绿灯，等于没有门禁 |
| 8 | **可维护性** | 一个函数 15 个参数、8 段 if | 5 个模块各管一段，新增规则不改主程序 | 加一条规则就要改这个巨型函数并加一个参数。参数到 20 个时没人敢动它 |
| 9 | **信号强度** | 5 条问题全是平级字符串，看不出哪条致命 | 按 reverse=P0 / drift=P1 / 未命中=INFO 分级，且只对本场景命中的项升级 | 反例的 5 条里真正致命的（`0d` 反转）**一条都没有**，反而列了 3 条"写进去就会报错、自己能发现"的。它把注意力引向了错误的地方 —— 这比漏检更隐蔽，因为**看起来确实查出了 5 个问题** |

## 💡 一句话教训

> **能跑通 ≠ 检查到位。反例退出码是 0，正确版是 1 —— 一个"成功"的脚本可能什么都没查出来。**

更精确地说，反例犯的错分三类，正好对应课程里三条方法论：

1. **约束归属错误**（第 1、2 条）—— 把 A 的约束套到 B 上。L19 的 P0-1。
2. **静默项漏检**（第 4、5 条）—— 拦住了会报错的，放过了会静默的。L18 的核心结论：
   *风险要按「失败时有没有声音」排序，不是按「会不会发生」排序。*
3. **信号强度缺失**（第 6、9 条）—— 查出来的项不分轻重。L18 的另一半：
   *reverse（方向反了）与 drift（幅度偏了）后果差一个量级，混为一谈会让合规问题挤占对灾难问题的注意力。*

反例拦住的 5 条里，有 3 条属于"报错型"（列数超限、库数超限、organization 非空，
这些写进去就会失败、很容易自己发现）；
它漏掉的恰恰是那些**跑得顺顺当当、但结果是错的**项。

> 📌 **最隐蔽的一点是它没有漏得"很明显"** —— 它确实输出了 5 个问题、退出码 0 看着很成功。
> 判断一个检查器好不好，不看它报了多少条，看**它报的是不是你真正需要处理的那几条**。
