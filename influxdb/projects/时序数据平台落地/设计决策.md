# 设计决策 · 时序数据平台落地

> 每个决策点必须**真有争议** —— 换个人来可能选另一个方案，且也有道理。唯一正确答案不算决策点。

## 决策 1：规则该按「阶段」分模块，还是按「检查类型」分模块？

**候选方案**

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| A · 按阶段分模块 | `schema_design` / `engine` / `ops` / `decision`，一个模块对应课程一个阶段 | 每条结论天然带阶段归属，能直接回指讲义；新增规则时知道该放哪 | 同一类检查（比如"限流类"）会散在不同模块，横向复用时要跨文件找 |
| B · 按检查类型分模块 | `limits.py`（所有上限类）/ `cost.py`（所有成本类）/ `config_check.py`（所有配置类） | 同类检查集中，改一个阈值只动一处 | 阶段归属丢失，输出要额外维护一张"规则→课时"映射表；课程复盘时找不到对应关系 |
| C · 单文件全塞进去 | 一个 `check.py` 搞定 | 代码最短，初看最简洁 | 每加一条规则改同一个函数；无法定位归属 —— 这正是 [反例对照](反例对照.md) 的做法 |

**最终选择**：**A · 按阶段分模块**

**选择理由**：这个项目的**首要产出不是代码，是可追溯的判断**。
每条结论都要能回到讲义核对（本课程的评审清单把"可回指"列为强制项），
按阶段分模块让"这条规则属于 L14"这件事**从目录结构里直接读出来**，不需要额外维护映射表。
代价（同类检查分散）在本项目里不严重 —— 检查规则之间很少需要横向复用逻辑。

**为此付出的代价**：想找"所有跟文件数有关的检查"时，要去 `engine.py` 和 `ops.py` 各找一处
（432 上限与降采样调度周期是同一个公式的两个用法）。

**什么时候该改选另一个**：若项目演进成一个通用体检平台、规则涨到几百条且需要按类型批量开关
（比如"只跑成本类检查"），就该改 B，并补一张规则元数据表。当前 16 条规则，A 更简单。

## 决策 2：结论该「打印给人看」还是「用退出码表达」？

**候选方案**

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| A · 只打印报告 | 输出分级的文字报告，永远 `exit 0` | 简单；不会因为"有风险"导致脚本链断掉 | 无法挂进 CI；跑完还得人肉看有没有 P0 |
| B · 只给退出码 | 出问题就非 0 退出，细节靠日志 | CI 友好 | 人的可读性差，不适合作为汇报材料 |
| C · 两者都要 | 打印完整报告 **且** 用退出码表达结论 | 既能汇报又能进 CI | 需要明确退出码语义，否则调用方会误判 |

**最终选择**：**C · 两者都要**

**选择理由**：本项目的两个使用场景对输出形态要求相反 ——
**汇报场景**要一份能贴在文档里的完整报告（每条含归属、依据、建议），
**回归场景**要在改配置后自动判断"有没有踩回旧坑"。
这两件事不冲突，只要把退出码语义写清楚就行。

**为此付出的代价**：必须维护一张退出码表（`0` 通过 / `1` 有 P0 / `2` 只有 P1 / `3` 参数错），
且调用方要理解 `2` 不算失败 —— 否则会把"有风险但可推进"误当成"构建失败"。

**什么时候该改选另一个**：若只用于一次性评估（不进 CI），A 足够，退出码反而是负担。
若只做门禁，B 更合适，完整报告可以拆到另一个子命令里。

## 决策 3：常量该「各模块自己定义」还是「集中在 config.py」？

**候选方案**

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| A · 集中在 `config.py` | 所有官方常量 + 负载定义放一个文件，其他模块 import | 单一数据源，改一处全项目生效；常量旁边能写清出处与课时 | 模块间通过 config 产生耦合；config 会变长 |
| B · 各模块自己定义 | 谁用谁定义，`engine.py` 里写 432，`ops.py` 里再写一遍 | 模块独立，删掉一个模块不影响别人 | 同一个数字散落多处，改一处漏一处 —— **本课程 L15/L16 都栽在这上面**（讲义与实跑不同步） |
| C · 从外部文件读 | 常量放 YAML / JSON，运行时加载 | 非程序员也能改 | 多一层解析与校验；本项目没有"非程序员改配置"的需求 |

**最终选择**：**A · 集中在 `config.py`**

**选择理由**：这是被本课程的历史教训直接逼出来的选择。
L15 的 5 个 P0 和 L16 的 2 个 P0，根因都是**同一个数字在两个地方不一致**。
`config.py` 让"432"只出现一次，且能在旁边写明它属于哪个 SKU、出自哪一课。

**为此付出的代价**：模块间通过 config 耦合 —— 改 `Workload` 数据类会影响全部五个模块。
对本项目可接受（规则数量有限、都在一个仓库里）。

> 📌 **落地时被校验器抓到的一次自相矛盾**（值得记下来）：
> `engine.py` 在打印"⭐ 432 是 query-file-limit 的默认值，3 天是它的派生值"这句话时，
> 前半句是常量化的，但**计算派生天数的表达式里写死了 `432` 和 `10`** ——
> 一个正在讲"约束要集中管理"的模块，自己却在硬编码。
> 用 AST 遍历 `BinOp` 子节点才抓到它（正则会把 docstring 里的说明文字一起误报）。
> **教训：文档里的原则不会自动变成代码，得有校验器盯着。**

**什么时候该改选另一个**：若规则拆成可插拔的第三方插件、各自独立发布，就该改 B + 版本协商，
否则 config 会成为跨团队的改动瓶颈。

## 决策 4（附加）：`main.py` 为什么要「先排雷，再体检」？

这不是可选项而是**正确性要求**，单列出来是因为它最容易被当成"顺序无关"而颠倒。

**问题**：`decision.py` 会排除不满足硬约束的 SKU（比如业务要求托管 → Core 被排除）。
如果 `engine.py` / `ops.py` 仍按"默认选 Core"去报它的 432 约束，
输出就会自相矛盾：**一边告诉你 Core 不能用，一边告诉你 Core 查不到数据**。

**解决**：`main.py` 分两阶段 —— 先跑 `decision.run()` 拿到幸存 SKU 列表，
再把列表传给下游模块；下游遇到 Core 专属规则时，Core 已不在候选集就跳过或降级。

> 📌 这正是 L19 的**约束归属**原则落地：**把 A 的约束套到 B 上，和把 A 的优点算到 B 头上，是同一类错误**。
> 本项目把这个判断写进了代码结构，而不只是写在文档里 —— 因为写在文档里的原则，
> 下一次改代码时很可能会被忘掉（L17 的"标注慎引却打满分"就是这么发生的）。

**代价**：`engine.run()` / `ops.run()` 多了个 `allowed_skus` 参数，
`main.py` 要用 `try / except TypeError` 兼容不需要该参数的模块（`schema_design` / `tco`）。

**什么时候该简化**：若所有模块都统一接受上下文参数（传一个 `Context` 对象而非裸 list），
就能去掉 `try / except`。当前为保持模块签名简单，容忍了这点不优雅。

## 决策 5：已知陷阱该「无条件全部告警」还是「只报本场景命中的」？

**候选方案**

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| A · 无条件全部告警 | 每条已知陷阱都按最严重级别报出来（`0d` 反转永远 P0） | 实现最简单；不会漏；形式上"覆盖全面" | 读者看到 4 条 P0 但只有 1 条跟他有关，**剩下的会稀释注意力** —— 告警疲劳 |
| B · 只报命中的 | 未命中的陷阱不报 | 输出干净 | 失去了教学价值：读者不知道还存在哪些坑；改了配置后新踩的坑不会被提示 |
| C · 命中检测 + 未命中降级为 INFO | 命中按 reverse=P0 / drift=P1；未命中降 INFO 并注明"什么情况下会命中" | 既有信号强度又有覆盖面 | 每条陷阱要额外写一个命中判断函数，实现成本更高 |

**最终选择**：**C · 命中检测 + 未命中降级为 INFO**

**选择理由**：本项目初版用的是 A —— 迁移检查无条件输出 4 条（2 条 P0 + 2 条 P1），
保留期检查无条件输出 2 条（1 条 P0 + 1 条 P1），**不管实际配置写的是 `90d` 还是 `0d`**。
这造成了两个具体缺陷：

1. **信号被稀释**：`业务指标分析` 场景写的是 `1y`，却被告知"保留期 0d 会删光数据"（它根本没写 0d）；
   真正命中的"默认精度反转"混在两条无关告警里。
2. **自相矛盾**：一个用来**教 reverse / drift 分类**的模块，自己却不对输入做分类判断 ——
   **嘴上讲分类、手上无差别告警**。这与 L17 的"标注慎引却打满分"、L19 的"批评想托管却推荐自托管"
   是同一类错误的第三次出现。

**为此付出的代价**：`MIGRATION_TRAPS` 从 4 元组变成 5 元组（多一个命中判断 lambda），
可读性下降；`check_retention` 要先解析保留期字符串再分支，比无条件告警复杂得多。

**什么时候该改选另一个**：若把它做成 CI 门禁且只看退出码（人不读报告），
A 的告警疲劳不影响结论（退出码只看有没有 P0），此时 A 的简单更划算。
但只要有人读报告，就该用 C。

> 📌 **附带的阈值教训**：drift 的严重度最初用**绝对天数**判（`diff >= 1` 天就判 P0），
> 结果 `1y` 差 0.2 天（相对 0.07%）在有合规要求时被判 P0，而 `3mo` 差 1.3 天（相对 1.45%）反而是 P1 ——
> **严重的排在轻微的后面**。改为按**相对偏差 ≥ 0.3%** 判才自洽。
> 判据选绝对量还是相对量，要在写第一条规则时就想清楚。
