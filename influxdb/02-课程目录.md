> 🎯 **本阶段核心结论**：主键 = **timestamp + tag set**（null tag 不进主键）；Core 硬限制 **库 5 / 表 2000 / 列 500**；**基数是乘法**（点密度趋近 0 则压缩失效）；**需要按某字段查 ≠ 它必须是 tag**；**UTC+8 按天分桶默认错位 8 小时**（origin 默认 epoch）；**`LAG` 是前一行不是前一小时**；**3.x 只有 SQL 与 InfluxQL 两种语言，Flux 已移出清单**；**`NON_NEGATIVE_DIFFERENCE()` SQL 无但 InfluxQL 有**

## 阶段 4 · 存储引擎与性能（凭什么快、慢在哪）✅ 已完成

> 阶段导览：[overview](stages/4-存储引擎与性能/overview.md) ｜ 路径图：[stage-04-path.svg](stages/4-存储引擎与性能/assets/stage-04-path.svg)
> ⚡ L11《向量化执行》回扣开课时的概念澄清：「向量化执行」≠ 向量数据库
> 🎯 **本阶段核心结论**（9 / 9）：**Core 没有 compactor** —— gen1 Parquet 文件永不合并，90 天累积约 **12,960 个**，长周期查询慢的根因是**要打开的文件多**而非数据量大（**架构天花板，调参无效**）；**「刚写就能查」的上界是 15 分钟**（可查缓冲最多 900 个 WAL 文件）；**`no_sync=false` 是默认值**，改 true 即拿持久性换延迟；**停机要用 SIGTERM** 否则绕过刷 WAL；**「72 小时限制」实为 432 个文件限制**（72h = 432×10min 的派生值，代码无时间判断）→ **Core 查不了 1 周以上的数据且是直接报错**；**列存省 I/O、SIMD 省 CPU，列存是 SIMD 的前提**；**<10ms 来自 LVC，需主动创建、InfluxQL 不可用、重启即清空**；**「改掉 `SELECT *`」在 Core 上基本不成立**（官方说 1000 列才明显变慢，而 Core 每表上限 500 列）

## 阶段 5 · 生产落地（部署、成本、生态）✅ 已收官

> 阶段导览：[overview](stages/5-生产落地/overview.md) ｜ 路径图：[stage-05-path.svg](stages/5-生产落地/assets/stage-05-path.svg)
> 🎯 **本阶段核心结论**（12 / 12）：**选型第一判据是「要查多久」不是「要多少钱」** —— 432 文件 × 10min = **72 小时 ≈ 3 天**，超限是**报错**不是变慢；**「能存」与「能查」在 Core 上分家**（90 天 = 3.4 TB 存得下，但 12,960 文件查不了）→ 超过 3 天的部分本质只是冷备份；**内存三默认相加 = 90%**，这是「内存比 CPU 先到瓶颈」的根因；**Core 是「数据不丢、服务会断」**，秒级切换必须 Enterprise；**升级 3.10+ 前必须备份 catalog**（v2→v3 单向不可逆）；**自监控数据自己也只受 3 天可查窗口**，且文件数只跟墙钟有关、跟数据量无关

> **L17 核心结论**：① **InfluxDB 是存储引擎（发动机），Prometheus 是完整监控方案（整车）**——拿组件比整体是最常见的不公平对照；② **没有一款赢下全部场景**（实验 A 四个场景四个不同冠军），且**先排雷再打分**比打分重要；③ 四个反直觉事实全部是官方自己说的（拉模式只是 "slightly better" / 本地存储 "not meant as durable long-term storage" / VM 的 20x·70x·7x 全是 `up to` 厂商自述 / "Partitioning does not speed up queries"）。

> **L18 核心结论**：① **迁移风险要按「失败时有没有声音」排，不是按「会失败的概率」排**——报错型最坏是延期，静默反转最坏是丢数据且无人知晓；② **「静默」必须再分两类**：`reverse`（方向反了，`0d` 想永久结果立刻全删）灾难级 vs `drift`（幅度偏了，`3mo` = 90 天 vs 三个自然月 91.3 天）合规级；③ **不可逆点不止一个，版本升级的不可逆点比数据迁移靠前得多**（3.9.x → 3.10+ 在启动 3.10 那一步就已不可逆）；④ **双写窗口可以算出来**：Core 上只有 1-3 天（上限 = 可查窗口 = 3 天），写太久最早的数据反而查不到。

> **L19 核心结论**：① **约束是有归属的** —— 432 文件上限是 **Core 的属性**，不是 InfluxDB 的属性（实验 B 初版套用到全部 SKU，得出「降采样必须每 20 小时跑一次」的荒谬结论）；② **选型是两次决策不是一次** ——「我们选了 InfluxDB」没有信息量，五个 SKU 硬约束差异极大，**Serverless 不是 Core 的托管版**（无原生 v3 API、无处理引擎）；③ **打分器会输出冠军，但不会告诉你约束本身有问题** —— 新增约束冲突检测，区分「某 SKU 不满足约束」与「约束之间打架」；④ **成本排序会被授权费翻转** —— Enterprise 授权费不公开（❓ 不估算），IoT 场景运维人力是主机费的 **31 倍**。
