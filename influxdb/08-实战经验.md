## 🚫 适用边界与反模式

### 什么时候不该用它

> "不该用"比"怎么用"更值钱——这是从"会用"到"用对"的分界线。

| 场景 | 为什么不适合 | 该用什么替代 |
|------|-------------|-------------|
| **要按主键查单条记录**（订单详情、用户资料） | 时序库的主键是 `时间戳 + tag set`，按业务 ID 取单条是它的盲区 | PostgreSQL / MySQL |
| **强事务、多行一致性更新** | 写入是追加语义，没有跨行事务 | 关系型数据库 |
| **Core 上想查 1 个月以上的原始精度数据** | 无 compactor，gen1 文件永不合并，432 文件上限是**架构天花板** | Enterprise（有压实）/ 降采样后查聚合层 |
| **Core 上要求秒级故障切换** | Core 是**数据不丢、服务会断**，恢复靠 WAL 重放 | Enterprise（HA + 读副本） |
| **要跑复杂 JOIN / 多维即席分析** | 3.x 的 SQL 走 DataFusion，JOIN 支持有限 | ClickHouse / Doris |
| **只存几百 MB、几天就扔** | 杀鸡用牛刀，运维成本高于收益 | 文件 + 定时清理脚本 |
| **需要 Flux** | 3.x 只有 SQL 与 InfluxQL 两种语言，Flux 已移出清单 | 用 Python 处理引擎重写 |

### 高频反模式（能跑，但迟早出事）

1. **把 Core 的约束当成 InfluxDB 的约束**：432 文件上限、库 5 / 表 2000 / 列 500 全是 **Core 的属性**。套到 Enterprise 或 Serverless 上会得出"降采样必须每 20 小时跑一次"这类荒谬结论。
   → 后果：选型阶段就排除掉正确答案。
   → 正确做法：先问"这是哪个 SKU 的约束"，再算数。

2. **保留期写 `0d` 表示"永久保存"**：1.x / 2.x 里 `0d` = 永久，3.x 里 `0d` = **查询时立即标记全部删除**。官方原文："This differs from InfluxDB 1.x and 2.x where 0d meant infinite retention."
   → 后果：数据静默消失，没有报错，没有人知道。
   → 正确做法：永久保留写 `none`。

3. **降采样层数按 `天数 × 24 × 6` 硬算**：文件数取决于**调度周期**而非精度。公式是 `文件数 = 窗口天数 × 24 × 60 ÷ 调度周期(分钟)`，默认 gen1 = 10 分钟 → 每天 144 个文件。
   → 后果：算出来的降采样层自己就超限。
   → 正确做法：从 `downsample_interval_min` 反推，别从精度反推。

4. **用 `SELECT *` 当性能问题 blamed**：官方说要到 1000 列才明显变慢，而 Core 每表上限 500 列——**在 Core 上这个优化建议基本不成立**。
   → 后果：优化了半天，P99 一动不动。
   → 正确做法：先查文件数与时间窗口。

5. **TCO 只算机器钱**：自托管省下的是授权费，付出的是运维人力。本项目实战项目的 IoT 场景里，运维人力是主机费的 **31 倍**。
   → 后果：选型时觉得自托管便宜，上线一年后发现更贵。
   → 正确做法：把 FTE 折算进去再比。

## 🔥 高频故障模式

> 每条固定**五段式**：症状 → 根因 → 排查路径 → 修复 → 预防。
> 已收录 **9 条**。排序按「踩中概率 × 后果严重度」。

### 故障模式 1：长周期查询直接报错，不是变慢

- **症状（可观测）**：HTTP 500，响应体原文为
  `External error: Query would scan 432 Parquet files, exceeding the file limit. InfluxDB 3 Core caps file access to prevent performance degradation and memory issues. Use a narrower time range, or increase the limit with --query-file-limit (this may cause slower queries or instability).`
  注意是**报错**不是超时——查询根本没执行。
- **根因**：Core 没有 compactor（压实器是 Enterprise 的功能）。gen1 的 10 分钟 Parquet 块**永不合并**，一天 144 个文件、一个月约 4,300 个、一年超 52,000 个。而单查询默认只允许扫 432 个文件。
  72 小时这个数字是**派生值**不是限制本身：`432 文件 × 10 分钟 = 4,320 分钟 = 72 小时`。代码里没有任何"判断时间范围"的逻辑，只有文件计数。
- **排查路径**：
  1. 先看是不是刚写完就能查、过一会儿才报错——刚写入时数据在 WAL 里而非 Parquet，`system.parquet_files` 为 0，此时同样的查询能过。**这个坑是延迟引爆的：新装环境一切正常，直到你想分析长周期数据时才炸**。
  2. 查当前文件数：`SELECT count(*) FROM system.parquet_files`。
  3. 算窗口：`可查天数 ≈ query_file_limit × gen1_duration(分钟) ÷ 1440`。默认 `432 × 10 ÷ 1440 = 3 天`。
- **修复**（三选一，代价递增）：
  1. 收窄查询窗口到 3 天内——**官方推荐**。
  2. 建降采样层（把 1 分钟原始值聚合成 1 小时均值），长周期查聚合表。注意聚合表本身也按 gen1 出文件，一样要算窗口。
  3. 换 Enterprise（有压实）或调大 `--query-file-limit`。官方对调大这个值的警告很直白：查询变慢、内存飙升、**进程可能被 OOM 杀掉**、对象存储上每个文件最多 2 次 GET 请求。
- **预防**：选型阶段就把"最长要查多久"当成第一判据，而不是"要花多少钱"。**Core 上 90 天的数据存得下但查不了**，超出的部分本质只是冷备份。

> 对应速查条目：[09-排障速查手册.md](09-排障速查手册.md) · 症状 1
> 溯源：InfluxData 官方配置文档 `query-file-limit` 条目（核查于 2026-09）；报错原文引自 raspberry.tips 对 Core 3.11.0 的实测复现（核查于 2026-09）

### 故障模式 2：数据静默消失，写入全部返回 204

- **症状（可观测）**：写入持续返回 HTTP 204（成功），`SELECT count(*)` 返回 0 或远少于预期，日志无任何报错，磁盘占用却在涨。
- **根因**：保留期 `0d` 的**语义反转**。`0d` 在 1.x / 2.x 里表示永久保留，在 3.x 里表示"查询时立即标记全部删除"。这是 reverse 型静默——不是幅度偏了，是**方向反了**。
  同类反转还有：`mo` = 30 天、`y` = 365 天，而"三个自然月"是 91.3 天、"一个自然年"是 365.25 天——这是 drift 型（幅度偏），危害等级低一档。
- **排查路径**：
  1. 查库的实际保留期：`influxdb3 show databases`（看 retention_period 列）。
  2. 检查是不是从 1.x / 2.x 的运维脚本里直接复制过来的 `0d`。
  3. 确认数据是否还在存储里：保留期是**查询时过滤**，不是立刻物理删除——数据可能仍在对象存储上，改回 `none` 有可能救回来。
- **修复**：Core 的保留期**创建后不可改**（见故障模式 5），只能建新库 + 迁移数据。所以这一步要快——物理删除由保留强制执行服务异步完成，跑完就真没了。
- **预防**：迁移检查表里，`0d` 必须是**显式高优先级检查项**。风险排序要按「失败时有没有声音」排，不按「会不会失败」排——报错型最坏是延期，静默反转最坏是丢数据且无人知晓。

> 对应速查条目：[09-排障速查手册.md](09-排障速查手册.md) · 症状 2
> 溯源：InfluxData 官方《Data retention in InfluxDB 3 Core》原文（核查于 2026-09）

### 故障模式 3：写入返回 400，但数据确实写进去了一部分

- **症状（可观测）**：HTTP 400，响应体为
  `{"error":"partial write of line protocol occurred","data":[{"original_line":"...","line_number":2,"error_message":"invalid column type for column 'temp', expected iox::column_type::field::float, got iox::column_type::field::string"}]}`
  同时另一部分数据已成功落库。
- **根因**：**第一次成功的写入给列定型**。同一张表的同一个 field，后续写入若类型不同，不会被转换，而是被拒绝。默认 `accept_partial=true` → 好的那部分照写、坏的那部分丢弃，并返回一个 400。
  这意味着：**客户端如果只看 HTTP 状态码是不是 2xx，就会漏掉部分失败；如果只看有没有报错，又会误以为整批都失败了。**
- **排查路径**：
  1. 看响应体里的 `error_message`，确认 `expected` 与 `got` 分别是什么类型。
  2. 查当前列类型：`SELECT column_name, data_type FROM information_schema.columns WHERE table_name = '<表名>'`。
  3. 找出是哪个采集端在写错类型——往往是某个新增设备或新版本 SDK 把数值写成了字符串（比如 `temp="24.6"` 多了引号）。
- **修复**：
  - 短期：修采集端，统一类型。字符串字段值用双引号，整数加 `i` 后缀，浮点数与布尔值**不要**加引号。
  - 若业务上确实两种类型都要存：换 field 名（如 `temp_f` 与 `temp_s`），或全部改成字符串再在查询侧转换。
  - 若要求严格全成功或全失败：请求带 `accept_partial=false`，此时一批里有一行坏就整批拒绝。
- **预防**：写入端对 400 做**响应体解析**而不是只看状态码；关键的批写入用 `accept_partial=false`；给采集端的字段类型定死契约并加 lint。

> 对应速查条目：[09-排障速查手册.md](09-排障速查手册.md) · 症状 3
> 溯源：InfluxData 官方《Use the v3 write_lp API to write data》Partial writes 章节（核查于 2026-09）

### 故障模式 4：内存先崩，CPU 还很闲

- **症状（可观测）**：进程被 OOM killer 杀掉，或 DataFusion 报内存预算耗尽；监控上 CPU 使用率不到 50%，内存却顶到上限。
- **根因**：**三个内存默认值相加 = 90%**。
  - `force snapshot memory threshold` 默认 = 可用内存的 50%
  - `DataFusion execution memory pool` 默认 = 可用内存的 20%
  - `parquet-mem-cache-size` 默认 = 可用内存的 20%
  三者相加 90%，留给操作系统、WAL 缓冲、网络缓冲的只有 10%。而"内存比 CPU 先到瓶颈"是时序库的常态，不是异常。
- **排查路径**：
  1. 先确认是 OOM kill 还是主动退出：`dmesg | grep -i oom`。
  2. 查当前三项配置：`--force-snapshot-mem-threshold`、`--exec-mem-pool-bytes`、`--parquet-mem-cache-size`。
  3. 看是不是查询窗口变大后突然开始崩——文件数一多，DataFusion 要给每个文件读元数据与行组，内存随之线性涨。
- **修复**：
  1. 先收窄查询窗口（与故障模式 1 同源：文件数是万恶之首）。
  2. 显式设小 `parquet-mem-cache-size`（如 10%），把内存让给执行池。
  3. 真的需要大窗口查询 → 走降采样或换 Enterprise，**不要靠调大 `query-file-limit` 硬扛**。
- **预防**：容量规划时按内存算不按 CPU 算；给容器设的 memory limit 必须把这 90% 算进去，否则等于让 InfluxDB 在沙箱里跑马拉松。

> 对应速查条目：[09-排障速查手册.md](09-排障速查手册.md) · 症状 4
> 溯源：InfluxDB 3 Core release notes v3.0.0「Memory settings updates」与 `parquet-mem-cache-size` 条目（核查于 2026-09）

### 故障模式 5：想改保留期，发现改不了

- **症状（可观测）**：执行更新保留期的命令返回错误或选项不存在；官方文档里 Enterprise 有的"修改保留期"与"表级保留期"，在 Core 上都没有。
- **根因**：Core 的保留期**只能在创建数据库时设置，之后不可更改**。这是 Core 与 Enterprise 的功能差异，不是 bug。
- **排查路径**：
  1. 确认当前库保留期：`influxdb3 show databases`。
  2. 确认这是 Core 还是 Enterprise——很多人是在 Core 上照着 Enterprise 文档操作。
- **修复**：**建一个新库 + 迁移数据**。而 Core 上双写窗口只有 1–3 天（上限 = 可查窗口 = 3 天），所以迁移必须快，写太久最早的数据反而查不到。
- **预防**：建库那一刻就要把保留期定对。建库脚本纳入版本管理，并在 checklist 里显式确认 `retention_period` 的**字面值与语义**（不要写 `0d`）。

> 对应速查条目：[09-排障速查手册.md](09-排障速查手册.md) · 症状 5
> 溯源：InfluxData 官方《Create a database》：「Retention periods are immutable in Core」（核查于 2026-09）

### 故障模式 6：写入突然开始失败，报"超限"

- **症状（可观测）**：写入请求失败并报错；此前一直正常，某天突然开始。
- **根因**：撞上 Core 的三项硬限制——**库 5 个 / 所有库的表总计 2000 张 / 单表 500 列**（1 个时间列 + 499 个 tag+field 列）。超过列限制时写入请求直接失败并报错。
  最常见的触发方式：把高基数字段（如 `order_id`、`trace_id`）误设为 **tag**，每个新值都撑开主键；或者采集端自动建表，表名里带了日期或设备 ID，表数随时间线性增长。
- **排查路径**：
  1. 查库与表数量：`influxdb3 show databases`，再数各库的表。
  2. 查列数：`SELECT count(*) FROM information_schema.columns WHERE table_name = '<表名>'`。
  3. 看 tag 里有没有"每个点都不同"的字段——如果有，它应该是 field 或者根本不该进时序库。
- **修复**：
  - 高基数字段从 tag 降级为 field（`WHERE order_id = 'x'` 会变慢，但这比写不进去强）。
  - 按日期建表的改成按日期分库或用 tag 区分。
  - 表数量真的需要更多 → Enterprise 的表上限更高（⏳ 具体数值各版本文档口径不一，Core 的 2000 以官方《Manage databases》为准，Enterprise 数值请查当期文档）。
- **预防**：schema 评审时对每个 tag 问一句"这个字段的取值有多少种？会不会随时间单调增长？"；给表数量设监控告警，别等写不进去才发现。

> 对应速查条目：[09-排障速查手册.md](09-排障速查手册.md) · 症状 6
> 溯源：InfluxData 官方《Manage databases》Database, table, and column limits（核查于 2026-09）

### 故障模式 7：压缩率极差，磁盘涨得比数据量快

- **症状（可观测）**：同样的数据量，磁盘占用是预期的数倍；Parquet 文件数量正常但单个文件体积异常；查询没有明显变慢，但存储成本失控。
- **根因**：**点密度趋近 0 时列存压缩失效**。列存的压缩收益来自"同一列里相邻值相似"，而如果 tag 组合（series 数）过多，每个 series 在单个时间块里只有一两个点，列就变成大量碎片，字典编码与 RLE 都压不动。
- **排查路径**：
  1. 算点密度：`该表的点数 ÷ (series 数 × 时间块数)`。接近 1 是健康的，远小于 1 说明 series 太碎。
  2. 对比 tag 组合数与实际点数，看是不是每个 series 只贡献了极少的点。
  3. 查 Parquet 文件的压缩前后大小。
- **修复**：把高频变化、取值极多的维度从 tag 挪到 field；把不必要的维度干脆去掉；对确实需要高维度的场景，改用降采样层承载长周期数据。
- **预防**：schema 设计阶段就算一遍基数乘法——`基数 = tag1 取值数 × tag2 取值数 × ...`，这是**乘法**不是加法。

> ⚠️ **易混点，务必读**：官方《InfluxDB 模式设计建议》确实写着"存储引擎支持无限的标签值和序列基数，标签值基数不会影响数据库的整体性能"。**这句话与上面的根因不矛盾，但极易被误读成"基数完全无害"**：
> - 官方讲的是 **1.x / 2.x 的历史痛点**——那时高基数会让 TSM 的倒排索引爆炸，导致查询与内存直接崩掉。3.x 换了存储引擎，这个"索引爆炸"问题确实解决了。
> - 但**点密度影响的是压缩率**，是另一条链路。基数高不会让查询变慢，但会让每个 series 的点变稀，列存压不动，**磁盘占用随之上涨**。
> - 一句话：**3.x 上基数高不慢，但基数高占地方。** 本故障模式的"磁盘爆炸"正是后者。

> 对应速查条目：[09-排障速查手册.md](09-排障速查手册.md) · 症状 7
> 溯源：官方《InfluxDB 模式设计建议》（基数与主键定义，核查于 2026-09）。⚠️ 该页"高基数不影响性能"的表述针对的是 1.x/2.x 的索引爆炸痛点，**不可外推为"基数对存储无影响"**；点密度与压缩率的关系属课程[阶段 3 · L7](stages/3-数据模型与查询/lessons/lesson-07-Schema设计与基数陷阱.md)结论。

### 故障模式 8：崩溃重启后丢数据 / 服务恢复慢

- **症状（可观测）**：进程被强杀后重启，最后几秒到几十秒的写入丢失；或重启后 WAL 重放耗时很长，服务迟迟不可用。
- **根因**：两个开关都指向同一个取舍——
  - `no_sync`：默认 `false`，即**等 WAL 刷到对象存储后才返回 204**。改成 `true` 可以显著降低写入延迟，代价是崩溃时可能丢数据。
  - 停机信号：必须用 **SIGTERM** 走优雅关闭把 WAL 刷下去；SIGKILL 会绕过这一步。
  另需注意 WAL 重放本身有并发参数，设太高会 OOM。
- **排查路径**：
  1. 确认写入请求有没有带 `no_sync=true`。
  2. 确认上一次停机是怎么停的（`kill -9` / 容器 `docker kill` / OOM kill 都是强杀）。
  3. 查 WAL 相关配置：`--wal-max-write-buffer-size`、`--wal-replay-concurrency-limit`。
- **修复**：需要持久性的场景把 `no_sync` 保持默认 `false`；停机脚本统一改成 SIGTERM 并等待退出；容器编排里把 `terminationGracePeriodSeconds` 设够。
- **预防**：把"用什么信号停机"写进运维手册；对 `no_sync=true` 的写入路径做单独标注，让下游知道这批数据允许丢。

> 对应速查条目：[09-排障速查手册.md](09-排障速查手册.md) · 症状 8
> 溯源：InfluxData 官方《Use the v3 write_lp API to write data》no_sync 章节（核查于 2026-09）；优雅关闭见 Core release notes（核查于 2026-09）

### 故障模式 9：认证与端点不通（401 / 404）

- **症状（可观测）**：HTTP **401**（认证失败）或 HTTP **404**（资源不存在）。写入和查询都不通，且往往是在"服务明明起来了"的情况下。
- **根因**：三类原因混在同一个现象下——
  1. **401**：`Authorization` 请求头缺失或格式错误，或 token 没有目标库的写权限。
  2. **404**：库名不存在，或**端点路径写错**。
  3. 本课程[阶段 2 · L3](stages/2-上手篇/lessons/lesson-03-环境搭建与第一次写入.md) 的两条实操结论也归在这里：写入的原生端点是 `/api/v3/write_lp`，而**客户端默认写的是 V2 端点**；`host` 必须带 scheme（`http://` 不能省）。
- **排查路径**：
  1. 先分 401 还是 404——这两类的处置完全不同，不要一起查。
  2. 401 → 检查 `Authorization: Bearer <TOKEN>` 是否存在、token 是否被轮换、是否对该库有写权限。
  3. 404 → 检查库名是否存在（`influxdb3 show databases`），再检查端点路径是不是写成了 `/write` 或 `/api/v2/write` 而你期望的是 v3 语义。
  4. 两者都不是 → 核对 host 是否带 scheme。
- **修复**：按上面三条分别修正。token 轮换后需同步更新所有客户端配置。
- **预防**：token 轮换纳入变更管理；客户端配置里的 host 统一带 scheme；写入端点在配置里显式写全，不依赖客户端默认值。

> 对应速查条目：[09-排障速查手册.md](09-排障速查手册.md) · 症状 9
> 溯源：HTTP 401/404 语义为通用标准；v3 原生写入端点与 host scheme 要求见 InfluxData 官方《Use the v3 write_lp API to write data》（核查于 2026-09）与本课程 [阶段 2 · L3](stages/2-上手篇/lessons/lesson-03-环境搭建与第一次写入.md)

## ✅ 落地 Checklist

> 投产 / 上线前逐项打勾。**前 5 项是"错了会丢数据或选错产品"的项，优先于所有性能调优。**

**选型与设计（上线前）**

- [ ] 已明确"最长要查多久"，并据此选 SKU——不是先选产品再想办法
- [ ] 已确认每条硬限制属于哪个 SKU，没有把 Core 的约束套到别的 SKU 上
- [ ] 保留期字面值已逐字核对：永久写 `none`，**绝不写 `0d`**
- [ ] 每个 tag 都回答过"取值有多少种、会不会随时间单调增长"
- [ ] 基数按乘法算过，点密度估算过（`点数 ÷ (series 数 × 时间块数)`）

**写入侧**

- [ ] 采集端字段类型有明确契约，且加了 lint 校验
- [ ] 客户端会解析 400 的**响应体**，不是只看状态码
- [ ] 关键路径用 `accept_partial=false`，或明确接受部分失败并有补偿
- [ ] `no_sync` 的取值与业务的数据丢失容忍度匹配

**容量与运维**

- [ ] 内存预算按 **90% 三默认之和**算过，容器 memory limit 覆盖得上
- [ ] 有文件数 / 表数 / 库数的监控与告警（不只是磁盘和 CPU）
- [ ] 停机脚本用 SIGTERM，且有足够的优雅退出等待时间
- [ ] 自监控数据本身也在可查窗口内（Core 上自监控数据自己也只受 3 天窗口约束）
- [ ] 回滚预案已就绪：降级方案（收窄窗口 / 切降采样层）是写下来的，不是临场想的
- [ ] 升级前 catalog 已备份（跨大版本升级存在不可逆点）
