## 1. 消费者积压

**一眼识别**：`kafka-consumer-groups.sh --describe` 隔 60 秒跑两次，**LAG 列在涨**；监控上 `records-lag-max` 持续攀升。

| 步骤 | 动作 | 预期 |
|------|------|------|
| 止血 | 若下游已受影响：先**降级消费逻辑**（跳过非关键步骤）或**限流生产者** | LAG 停止上涨 |
| 定位 1 | 连跑两次 `--describe`，确认「在涨」还是「高位横盘」 | 高位横盘 = 正常追赶，不是事故，转监控观察 |
| 定位 2 | 看 LAG 分布：**均匀上涨** → 全局性能力不足；**只 1-2 个分区远高于均值** → 热分区 | 确定分支 |
| 定位 3 | `--describe --group X --members` 看组内消费者数 | 消费者数 ≥ 分区数时，再加实例也无效 |
| 修复（全局性） | 优先优化消费逻辑（批量写库、异步 IO）；再扩实例至**分区数**为止 | LAG 转为下降 |
| 修复（热分区） | 改 key 提高基数（加后缀 / 换更细粒度字段）；保序允许时改轮询 | LAG 分布趋于均匀 |
| 若无效 | → 转 [7. 再均衡风暴](#7-再均衡风暴)（LAG 反复涨落很可能是再均衡）；或转 `debug` | — |

**预防**：分区数按预期消费者数 × 2-3 起建；LAG 告警盯**增长率**而非绝对值。
**原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 1

## 2. 毒药消息阻塞分区

**一眼识别**：某分区 LAG **卡在固定值不动**；消费者日志里**同一条消息**反复报同一个异常；严重时整个组的 LAG 都在涨。

| 步骤 | 动作 | 预期 |
|------|------|------|
| 止血 | 立即把该消息**投 DLQ 并跳过**（手动 seek 到 offset+1，或用已埋的 DLQ 逻辑） | 分区恢复流动，LAG 开始下降 |
| 定位 1 | `--describe` 找到 LAG 卡住的分区与 offset | 拿到具体 partition / offset |
| 定位 2 | `kafka-console-consumer.sh --topic T --partition N --offset M --max-messages 1` 读出那条消息 | 确认是格式错误 / 超大消息 / 引用了不存在的实体 |
| 修复 | 修正数据或消费者代码后**重放** DLQ；为消费端加**毒药消息检测**（失败 N 次进 DLQ 并提交位移） | 同类坏消息不再阻塞 |
| 若无效 | → 转 `debug` 现场排查（若跳过位移后又在**下一个** offset 卡住，说明是一批坏数据而非单条） | — |

**预防**：消费端异常路径必须有出口（DLQ / 跳过），**绝不允许"抛异常且不提交位移"**；DLQ 要有监控。
**原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 2

## 3. 生产者批次过期

**一眼识别**：`TimeoutException: Expiring N record(s) for topic-X-Y: 120000 ms has passed since batch creation`。

> ⚠️ **这条报错意味着数据没写进去，且不会重传**。先确认有没有丢数据。

| 步骤 | 动作 | 预期 |
|------|------|------|
| 止血 | 确认发送端有回调/Future 检查：把失败记录**落盘或写入 outbox**（不要只打日志） | 失败消息可重发，不静默丢失 |
| 定位 1 | `kafka-topics.sh --describe --topic T`：看 `Leader` 是否为 `-1`、ISR 是否收缩 | Leader=-1 或 ISR 收缩 → 转 [8. 分区不可用](#8-分区不可用) |
| 定位 2 | 若 leader 正常：查生产者指标 `record-error-rate` / `request-latency-avg` / `buffer-available-bytes` | 缓冲区持续满 = 生产者过载 |
| 修复（broker 侧慢） | 先恢复 broker 可用性；`delivery.timeout.ms` 调大仅用于**扛过滚动重启**这类可预期中断 | 超时消失 |
| 修复（生产端过载） | 调大 `batch.size`、加适度 `linger.ms`、开 `compression.type=lz4`；仍不够则扩分区或加生产者实例 | 单请求承载更多数据，吞吐上升 |
| 若无效 | → 转 `debug` 现场排查 | — |

**预防**：**禁用 fire-and-forget**；满足 `delivery.timeout.ms >= linger.ms + request.timeout.ms`。
**原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 3

## 4. 连不上或拿不到元数据

**一眼识别**：`TimeoutException: Failed to update metadata after 60000 ms`；前置日志 `Connection to node -1 could not be established. Broker may not be available.`；变体 `Topic X not present in metadata after 60000 ms`。

| 步骤 | 动作 | 预期 |
|------|------|------|
| 止血 | 确认是**新上线/变更触发**还是**运行中的突发**：前者优先回滚变更 | 恢复通信 |
| 定位 1 | `nc -zv broker-host 9092` 测端口；`nslookup broker-host` 测 DNS | 定位是网络层还是解析层 |
| 定位 2 | 查 broker 的 `advertised.listeners`：**这个地址客户端能否解析并访问？**（Docker/K8s 头号坑） | bootstrap 通但 advertised 地址不可达 → 就是它 |
| 定位 3 | `kafka-broker-api-versions.sh --bootstrap-server ...` 验证 API 握手 | 能返回版本列表 = 基础连通正常 |
| 定位 4 | 若报 `not present` 变体：`kafka-topics.sh --list` 确认 topic 是否存在 | `auto.create.topics.enable=false` 时需先建 topic |
| 修复 | 修正 `bootstrap.servers`（至少填 3 个）/ `advertised.listeners` / 防火墙 / 安全协议；缺 topic 就建 | 客户端拿到元数据 |
| 若无效 | → 转 `debug` 现场排查 | — |

**预防**：`bootstrap.servers` 至少 3 个 broker；容器环境每个 broker 广播**唯一且客户端可达**的地址。
**反面教训**：**不要**靠调大 `request.timeout.ms` 掩盖——broker 不可达时等更久只是延迟发现。
**原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 4

## 5. NOT_LEADER_OR_FOLLOWER

**一眼识别**：`NotLeaderOrFollowerException: For requests intended only for the leader...`；或 `Error while fetching metadata ... {orders=NOT_LEADER_OR_FOLLOWER}`。

> 这是**可重试异常，设计如此**。先判断是短暂突发还是持续刷屏。

| 步骤 | 动作 | 预期 |
|------|------|------|
| 止血 | **不需要止血**。确认客户端开了重试 + 幂等（开启后整个切换对应用透明） | 应用无感 |
| 定位 1 | 是否发生在滚动重启 / 分区重分配 / 优选 leader 选举窗口内？ | 是 → **正常现象，无需处理，也不应告警** |
| 定位 2 | 若**持续刷屏**：`--describe --under-replicated-partitions` 找异常分区；查 broker 日志找反复进出 ISR 的节点 | 定位到不健康的 broker |
| 定位 3 | `kafka-metadata-quorum.sh --bootstrap-server ... describe --status` 看 controller 是否健康 | controller 异常会拖慢元数据传播 |
| 定位 4 | 容器环境：`kafka-broker-api-versions.sh` 验证每个 broker 广播的是**不同**地址 | 三个 broker 广播同一地址 = 配置错误 |
| 修复 | 修 broker 健康 / 修 advertised 地址 / 稳住 controller；**不要**对它 fail-fast | 告警停止 |
| 若无效 | → 转 [8. 分区不可用](#8-分区不可用) | — |

**预防**：**不要对瞬时 network/not_leader 异常告警**（broker 离线期间属正常且无影响）；滚动重启一次一个、等 `UnderReplicatedPartitions` 归零再继续。
**原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 5

## 6. 重复消费或消息丢失

**一眼识别**：消费者重启后大量重复处理；或崩溃后一批消息再也没被处理。

| 步骤 | 动作 | 预期 |
|------|------|------|
| 止血 | 丢失场景：从 DLQ / 备份重放补数；重复场景：确认下游有幂等（无则暂停消费，先补幂等） | 数据回到正确状态 |
| 定位 1 | 查 `enable_auto_commit`：为 `true` 时按时间提交，**可能在处理完成前就推进了位移** | 定位到提交时机问题 |
| 定位 2 | 查 `commit()` 位置：是否在业务处理**成功之后** | 先提交后处理 = 崩溃必丢 |
| 修复 | 关自动提交，处理成功后手动提交；消费端加**业务主键幂等去重** | 不丢；重复也无害 |
| 若无效 | → 转 `debug` 现场排查 | — |

**预防**：口诀 **先处理后提交**；"至少一次"下重复投递是**必然**，幂等是必需项而非可选项。
**原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 6

## 7. 再均衡风暴

**一眼识别**：日志反复刷 `Revoking previously assigned partitions` / `(Re-)joining group`；`--describe --group X --state` 在 `PreparingRebalance` ↔ `CompletingRebalance` 间反复横跳；LAG 反复涨落。

| 步骤 | 动作 | 预期 |
|------|------|------|
| 止血 | 先确认**是不是 Pod 在反复重启**（K8s OOM / 存活探针）：是则先修 K8s 侧，Kafka 配置怎么调都没用 | 停止无谓重启 |
| 定位 1 | 算「单批记录数 × 单条处理时间」是否 > `max.poll.interval.ms`（默认 300s） | 超过 = 处理超时被踢 |
| 定位 2 | 查 GC 停顿是否超过 `session.timeout.ms` | 长 GC 会被误判为失联 |
| 修复 | 调大 `max.poll.interval.ms` **或**调小 `max.poll.records`；改用 `CooperativeStickyAssignor`；启用静态组成员身份 | 组状态稳定在 `Stable` |
| 若无效 | → 转 [1. 消费者积压](#1-消费者积压)（积压与再均衡互为因果）；或转 `debug` | — |

**预防**：单批处理时间必须显著小于 `max.poll.interval.ms`；滚动发布用静态成员身份避免全组再均衡。
**原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 7

## 8. 分区不可用

**一眼识别**：`kafka-topics.sh --describe` 显示 `Leader: -1`，或 `--unavailable-partitions` / `--under-replicated-partitions` 列出分区；生产报 `NotEnoughReplicas`。

| 步骤 | 动作 | 预期 |
|------|------|------|
| 止血 | 确认副本因子与 `min.insync.replicas`：RF=1 的单点分区只能等 broker 恢复 | 明确恢复路径 |
| 定位 1 | `--describe` 看 ISR 里还剩谁；查对应 broker 进程与磁盘（`kafka-log-dirs.sh --describe`） | 定位是进程挂了还是磁盘满了/坏了 |
| 定位 2 | 查 controller 状态：`kafka-metadata-quorum.sh describe --status` | controller 不健康会拖慢 leader 选举 |
| 修复 | 恢复 broker（进程 / 磁盘 / 网络）；确认 `controlled.shutdown.enable=true` 以便优雅移交 leader | 分区重新选出 leader，ISR 恢复完整 |
| 若无效 | → 转 `debug` 现场排查 | — |

**预防**：生产环境 RF ≥ 3、`min.insync.replicas` ≥ 2；`unclean.leader.election.enable=false`（宁可短暂不可用，不要数据不一致）。
**原理**：→ 见 [课 7 副本机制与故障转移](stages/3-可靠性与高可用/lessons/lesson-07-副本机制与故障转移.md)

## 通用：命令速查

```powershell
docker exec kafka /opt/kafka/bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --group <组名>
```

```powershell
docker exec kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 --describe --topic <topic>
```

```powershell
docker exec kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 --describe --under-replicated-partitions
```

```powershell
docker exec kafka /opt/kafka/bin/kafka-metadata-quorum.sh --bootstrap-server localhost:9092 describe --status
```

> 单机 Docker 环境（本课 3 搭的）只有 1 个 broker，**副本与 controller 相关条目无法真实复现**，仅作生产参考。
