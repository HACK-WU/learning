# Kafka 实战经验

> 定位：**学习态**——坐着读，搞懂"为什么会出问题"。真出事了直接翻 [排障速查手册](09-排障速查手册.md)。
> 证据纪律：以下每条故障模式均可溯源（官方文档 / 联网核查 / 领域公认实践），核查于 2026-08。

## 一、适用边界与反模式：什么时候别用 Kafka

> **"不该用"比"怎么用"更值钱**——这是从"会用"到"用对"的分界线。

### 明确别用的场景

| 场景 | 为什么 Kafka 不合适 | 该用什么 |
|------|-------------------|---------|
| **低延迟请求-响应** | 用户点"下单"要同步等到结果。Kafka 是异步管道，硬套会引入不必要的延迟与复杂度 | HTTP / gRPC |
| **小流量 + 复杂路由** | 每天几百条消息、要按规则路由到不同队列并流转。Kafka 的分区模型对"按规则分发"支持很弱 | RabbitMQ（交换机/路由模型正对口） |
| **强一致跨系统事务** | Kafka 事务**只覆盖 Kafka 内部** topic 与 `__consumer_offsets`（课 8）。跨数据库的原子性它保证不了 | 同步事务 + 最终一致（对账兜底） |
| **纯任务队列**（传统短板） | 消费者数曾不能超过分区数、无法单条确认。**注**：KIP-932 share groups 已于 **4.2 GA**（4.0 EA → 4.1 Preview → 4.2 GA，核查于 2026-08），补上了消费者数可超分区数与单条确认——但生产案例仍在积累 | 传统 MQ 仍更稳妥；新场景可评估 share groups |
| **3 人小团队 + 单体应用** | 运维一套 Kafka 集群（容量规划、监控、升级）的复杂度远超收益 | 云托管服务或轻量 MQ |

### 三个高频反模式（用了 Kafka 但用错了）

1. **把命令当事件发**：发 `SendEmail` / `UpdatePoints` 这类祈使句指令，等于把同步调用的耦合包了层异步的皮。正确做法是发 `UserRegistered` 这类**过去式事实**（课 10）。
2. **按消费方建 topic**：`to-points-service`、`to-risk-service`——每加一个下游都要生产者写双份代码，耦合从代码搬进了管道。应按业务事件建 `orders`。
3. **拿 Kafka 当数据库**：靠反复重放 topic 来查询当前状态，性能与语义都会崩。需要状态查询就配读模型（CQRS）或压实 topic。

## 二、高频故障模式

> 五段式：`症状（可观测）→ 根因 → 排查路径 → 修复 → 预防`。症状必须可观测——"服务很慢"不算，"LAG 从 1 万涨到 50 万且只集中在 1 个分区"才算。

### 故障模式 1：消费者积压（Lag）持续上涨

- **症状**：监控上 `records-lag-max` 持续攀升；下游数据延迟；`kafka-consumer-groups.sh --describe` 隔一分钟跑两次，LAG 列在涨。
- **根因**（三类，处置完全不同）：
  1. **全局性积压**（所有分区 LAG 均匀上涨）= 消费能力不足，生产速率 > 消费速率。
  2. **热分区**（只有 1-2 个分区 LAG 远高于平均）= 分区 key 基数太低导致数据倾斜，比如用 `user_id` 时某个大客户刷量，或用常量/null 当 key 把所有消息塞进一个分区。**加消费者没用**——组内一个分区只能被一个消费者消费。
  3. **再均衡风暴**（LAG 反复涨落、日志里刷 `Revoking previously assigned partitions`）= 消费者被反复踢出组。
- **排查路径**：
  1. `--describe --group` 连跑两次确认"在涨"还是"高位横盘"（高位横盘是正常追赶，不是事故）。
  2. 看 LAG 分布：均匀 → 全局性问题；集中 → 热分区。
  3. `--members` 确认组内消费者数量是否符合预期。
  4. 查消费者日志有无 revoke/join 循环；查 GC 停顿是否超过 `session.timeout.ms`。
- **修复**：全局性 → 优化消费逻辑（批量写库、异步 IO）优先于加实例；加实例最多加到**分区数**（超出的闲置）。热分区 → 改 key 提高基数（加后缀/换更细粒度字段），或在保序允许时改轮询。再均衡 → 调大 `max.poll.interval.ms` 使其大于最坏情况处理时间，或用静态组成员身份。
- **预防**：分区数按"预期消费者数 2-3 倍"起建；LAG 告警盯**增长率**而非绝对值；按分区粒度监控。

### 故障模式 2：毒药消息（Poison Pill）阻塞整个分区

- **症状**：某个分区的 LAG 卡在固定值不动，消费者反复重启；日志里同一条消息反复报错；严重时**整个消费者组**的 LAG 都在涨（因为再均衡把暂停扩散到了全部分区）。
- **根因**：一条消息本身有问题（JSON 格式错误、schema 不兼容、引用了已删除的实体、单条消息超过 `max.partition.fetch.bytes`），导致消费者处理它必然抛异常。而处理异常 → 不提交位移 → 反复重试同一条 → 超过 `max.poll.interval.ms` 被踢出组 → 再均衡 → 坏消息被分给下一个消费者 → 再次卡死。**这是一个正反馈死循环**。
- **排查路径**：
  1. `--describe` 找到 LAG 卡住的分区与对应 offset。
  2. 用 `kafka-console-consumer.sh --partition N --offset M --max-messages 1` 把那条消息读出来看。
  3. 看消费者日志里反复出现的同一个异常。
- **修复**：短期——把位移跳过这条消息（手动 seek 或用 DLQ 逻辑）；长期——加**毒药消息检测**：失败 N 次后投 DLQ 并提交位移，主分区继续前进。
- **预防**：消费端必须有失败出口（DLQ / 退避重试 / 跳过），**永远不要让异常路径不提交位移**。DLQ 本身要有监控（否则沦为没人管的垃圾场）。

### 故障模式 3：生产者 Expiring records（批次过期）

- **症状**：`org.apache.kafka.common.errors.TimeoutException: Expiring N record(s) for topic-X-Y: 120000 ms has passed since batch creation`。
- **根因**：消息在生产者**客户端缓冲区**里等待发送的时间超过了 `delivery.timeout.ms`（默认 120000ms），生产者放弃这批消息。两种截然不同的病：
  - **Broker 侧不可用/慢**：分区 leader 挂了或正在选举、broker 负载高、磁盘慢 → 批次根本发不出去。
  - **生产者侧过载**：生产速率 > 单条连接的排出速率，缓冲区积压。
- **排查路径**：先 `kafka-topics.sh --describe` 看目标分区 `Leader` 是否为 `-1`、ISR 是否收缩（是 → broker 侧问题）；再看生产者指标 `record-error-rate`、`request-latency-avg`、`buffer-available-bytes`；看 broker 日志有无慢请求/leader 选举。
- **修复**：broker 侧问题 → 先恢复可用性（**没有任何生产者配置能让不可达的 leader 变可达**），调大 `delivery.timeout.ms` 只是为了"扛过滚动重启"这类可预期的短暂中断。生产者过载 → 调大 `batch.size`、加适度 `linger.ms`、开压缩（`lz4`），让每个请求装更多数据；仍不够则扩分区或加生产者实例（**一个 KafkaProducer 只有一个 Sender 线程**）。
- **预防**：**永远不要 fire-and-forget**——`send()` 后必须检查回调/Future，过期批次意味着数据根本没写进去。配置约束：`delivery.timeout.ms >= linger.ms + request.timeout.ms`。
- **关键认知**：**批次过期的记录不会重传**，生产者不复活过期批次。不检查回调 = 静默丢数据。

### 故障模式 4：连不上 / 元数据拿不到（Failed to update metadata）

- **症状**：`TimeoutException: Failed to update metadata after 60000 ms`；或 `Topic X not present in metadata after 60000 ms`；日志前置 `Connection to node -1 could not be established. Broker may not be available.`
- **根因**：客户端拿不到集群元数据。**最容易踩的是双地址陷阱**——客户端先用 `bootstrap.servers` 连上一个 broker，但后续真实连接用的是 broker 返回的 `advertised.listeners` 地址。所以有两类失败：压根没连上任何 bootstrap broker；或 bootstrap 通了但 advertised 地址客户端不可达（Docker/K8s 里最常见：broker 广播了容器名或 localhost）。
- **排查路径**：
  1. `nc -zv broker-host 9092` 测端口，`nslookup` 测 DNS。
  2. 查 broker 的 `advertised.listeners` 配置：广播的地址，**客户端能否解析并路由**？
  3. `kafka-broker-api-versions.sh --bootstrap-server ...` 验证能否完成 API 握手。
  4. 确认 topic 是否存在（`auto.create.topics.enable=false` 时向不存在的 topic 发送会报 not present 变体）。
  5. 安全协议是否匹配（客户端 PLAINTEXT 连 broker 的 SSL 监听器）。
- **修复**：修正 `bootstrap.servers`（至少写 3 个 broker）/ `advertised.listeners` / 防火墙 / 安全协议；topic 不存在就先建。
- **预防**：`bootstrap.servers` 至少填 3 个 broker 避免单点发现失败；Docker/K8s 里**每个 broker 必须广播自己唯一的、客户端可达的地址**。
- **反面教训**：单纯调大 `request.timeout.ms` 无效（这是最常见的错误处置）——broker 不可达时，等更久只是延迟发现，不解决任何问题。

### 故障模式 5：NOT_LEADER_OR_FOLLOWER 刷屏

- **症状**：日志里大量 `NotLeaderOrFollowerException: For requests intended only for the leader...`；或 `Error while fetching metadata ... {orders=NOT_LEADER_OR_FOLLOWER}`。
- **根因**：客户端缓存的元数据过期——leader 已经换了（broker 重启、优选 leader 选举、分区重分配），客户端还在往旧 leader 发。**这是可重试异常，设计如此**（broker 返回该错误就是为了让客户端刷新元数据）。
  分两种：**短暂突发**（滚动重启期间正常现象，客户端 1-3 秒内自愈，**不需要告警**）；**持续刷屏**（某个 broker 反复丢失/重获 leadership，或 Docker/K8s 里多个 broker 广播了同一个地址）。
- **排查路径**：`--describe` 看 leader 是否稳定、有无 `--under-replicated-partitions`；`kafka-metadata-quorum.sh describe --status` 看 controller 健康；日志里 grep leader/election/isr 找反复进出 ISR 的 broker；K8s/Docker 用 `kafka-broker-api-versions.sh` 验证每个 broker 广播的是**不同**地址。
- **修复**：短暂的无需处理，确保客户端开了重试即可（幂等开启时整个切换对应用透明）。持续的 → 修 broker 健康 / 修 advertised 地址 / 稳住 controller。**不要**对它 fail-fast。
- **预防**：**不要对这类瞬时异常告警**（AWS 官方文档明确：broker 离线期间的 network/not_leader 异常是正常且无影响的）；滚动重启一次一个、等 `UnderReplicatedPartitions` 归零再继续；监控 leader 变更频率与 ISR 收缩率。

### 故障模式 6：位移提交时机导致的重复/丢失

- **症状**：消费者重启后大量重复处理（重复消费）；或崩溃后一批消息再也没被处理（丢失）。
- **根因**：自动提交（`enable_auto_commit=true`，默认 5 秒一次）与业务处理的边界不一致——**自动提交按时间触发，可能在消息处理完成前就把位移推进了**。此时崩溃 = 永久丢失。反之手动提交但"先提交后处理"同样丢；"处理前提交 + 处理失败"也丢。
- **排查路径**：确认 `enable_auto_commit` 值；确认 `commit()` 调用位置在业务处理**成功之后**；确认幂等去重是否真的生效。
- **修复**：关自动提交，处理成功后再手动提交；消费端加幂等（业务主键去重），因为"至少一次"语义下重复投递是**必然**而非异常。
- **预防**：记住课 6 的口诀——**先处理后提交**。需要更强保证时用事务把位移和产出绑在一起（设计决策 1）。

### 故障模式 7：再均衡（Rebalance）风暴

- **症状**：LAG 反复涨落；日志刷 `Revoking previously assigned partitions` / `(Re-)joining group`；`--describe --state` 的状态在 `PreparingRebalance` 与 `CompletingRebalance` 之间反复横跳。
- **根因**：消费者处理一批消息的时间超过了 `max.poll.interval.ms`（默认 300s），被协调者踢出组 → 再均衡 → 新的一批又要处理超时 → 循环。也可能是 K8s 的 OOM kill / 存活探针失败导致 Pod 反复重启（从 Kafka 侧看长得一模一样，但**根因在 K8s 不在 Kafka**）。
- **排查路径**：看消费组状态是否稳定（健康应恒为 `Stable`）；算最坏情况处理时间是否 < `max.poll.interval.ms`；看 K8s 事件有无重启/OOM。
- **修复**：调大 `max.poll.interval.ms` 或调小 `max.poll.records`；用 `CooperativeStickyAssignor`（增量协作再均衡，只有被迁移的分区暂停）；用静态组成员身份避免滚动发布触发全组再均衡。
- **预防**：单批数据量 × 单条处理时间必须显著小于 `max.poll.interval.ms`。

## 三、落地 / 上线 Checklist

### 生产者（投产前必查）

- [ ] `acks='all'` **显式**写出（不依赖默认值——kafka-python 2.x 默认 `acks=1`，3.0 起才对齐 `all`）
- [ ] `enable_idempotence=True` 显式开启
- [ ] 每条消息有**业务含义的 key**（保序 + 均匀分布），不是 `None` 或常量
- [ ] `send()` 结果**被检查**（回调或 Future），异常有落盘/outbox 兜底
- [ ] `delivery.timeout.ms >= linger.ms + request.timeout.ms`
- [ ] 退出前 `flush()` + `close()`

### 消费者（投产前必查）

- [ ] `enable_auto_commit=False`，`commit()` 在业务处理**成功之后**
- [ ] 消费端有**幂等去重**（业务主键），接受"至少一次"下重复必然发生
- [ ] 处理异常有**出口**：退避重试 → 超次数进 DLQ → 提交位移继续
- [ ] 单批处理时间 << `max.poll.interval.ms`
- [ ] DLQ 有**监控与告警**（否则等于换个地方静默丢弃）

### Topic 与集群

- [ ] 按**业务事件**命名 topic，不按消费方命名
- [ ] 分区数按"预期消费者数 × 2-3"起建（**只能加不能减**）
- [ ] 生产环境副本因子 ≥ 3，`min.insync.replicas` ≥ 2
- [ ] `unclean.leader.election.enable=false`（宁可不可用，不要数据不一致）
- [ ] 保留策略按业务与磁盘容量设定，不是无限

### 可观测性

- [ ] LAG 监控按**分区粒度** + 盯**增长率**（不只是绝对值）
- [ ] 告警不覆盖瞬时异常（network / not_leader 属正常）
- [ ] 有 `__consumer_offsets` / `UnderReplicatedPartitions` 的基础告警
