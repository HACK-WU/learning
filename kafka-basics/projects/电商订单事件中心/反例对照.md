# 反例对照：能跑，但很糟

> 下面的「反面版本」**在你的机器上完全能跑通**，输出看起来和正确版本一模一样——这正是它危险的原因。它把课 1 到课 10 讲过的坑**全踩了一遍**，却不会报任何错。

---

## 反面版本（不要抄）

```python
from kafka import KafkaProducer, KafkaConsumer

# ❌ 反面教材：每一行都有问题，注释标出踩了哪个坑
producer = KafkaProducer(
    bootstrap_servers='localhost:9092',
    # 坑1：不写 acks，依赖默认值（2.x 是 1，3.x 才是 all）——跨版本行为不一致
    # 坑2：不写 key，所有消息轮询分布 → 同一用户的订单乱序
    # 坑3：幂等没显式开启，重试时可能产生重复消息
)

# 坑4：fire-and-forget，send 完不检查回调 → 发送失败静默丢消息
for i in range(100):
    producer.send('to-points-service', f'order-{i}'.encode())  # 坑5：按消费方命名 topic

# 坑6：不 flush 不 close，进程退出时缓冲区里的消息可能直接丢失
```

```python
consumer = KafkaConsumer(
    'to-points-service',
    bootstrap_servers='localhost:9092',
    group_id='points-service',
    enable_auto_commit=True,   # 坑7：自动提交，处理前就提交了 → 处理失败消息永久丢失
)

for msg in consumer:
    try:
        points = int(msg.value)          # 坑8：不做反序列化校验，坏消息直接抛异常
        save_to_db(points)               # 坑9：无幂等，重复消费就重复加分
    except Exception as e:
        print(e)                          # 坑10：捕获后不处理，坏消息无限阻塞该分区
        # 不进 DLQ、不跳过、不告警 → 分区卡死
```

## 逐条对照（8 条差异，每条说清"为什么糟"）

| # | 反面做法 | 正确做法 | 为什么糟 |
|---|---------|---------|---------|
| 1 | 依赖 `acks` 默认值 | 显式写 `acks='all'` | **跨版本行为不一致**：kafka-python 2.x 默认 `acks=1`（leader 写入即确认，leader 挂了就丢），3.0 起才对齐为 `all`。不显式写，换台机器装个旧版本，可靠性凭运气 |
| 2 | 不指定 key | `key=user_id` | 同一用户的订单散落在不同分区 → **乱序**。先"取消"后"创建"的下游会算出错误状态；且无法做按用户聚合 |
| 3 | 不显式开启幂等 | `enable_idempotence=True` | 网络抖动触发内部重试时，broker 可能已写入两次 → **重复消息**。课 8：幂等消除的正是这一类重复 |
| 4 | `send()` 后不检查回调 | 用回调/`future.get()` 检查异常 | `send()` 是**异步**的（课 9 的核心），返回不代表成功。发送失败只写一行日志，业务侧以为成功了 → **静默丢消息**，且无任何补救痕迹 |
| 5 | 按消费方命名 `to-points-service` | 按业务事件命名 `orders` | 每加一个下游就要生产者多写一份（课 10 主题三原则）。今天 3 个下游写 3 份，明天第 4 个来，生产者要改代码上线——**耦合从代码搬进了管道** |
| 6 | 不 `flush()` / `close()` | 退出前 `flush()` + `close()` | 消息还在客户端缓冲区里没发出去，进程一退就没了。开发环境消息少不易复现，生产上批量退出时集中爆发 |
| 7 | `enable_auto_commit=True` | 手动提交，处理成功后才提交 | 自动提交按时间触发（默认 5 秒），**消息可能在处理完成前就被标记为已消费**。此时消费者崩溃 → 这批消息**永久丢失**（课 6 的核心考点） |
| 8 | 坏消息只 `print` 异常 | 重试 N 次后进 DLQ | 一条毒药消息会**永久阻塞整个分区**，进而触发再均衡把积压扩散到全组（课 6 + 设计决策 2）。且积压会一直涨到触发告警，值班同学看到的是"全线积压"，很难定位到源头是一条坏 JSON |

## 一眼看出坏味道的检查清单

读自己的 Kafka 代码时，问这 5 个问题，任何一个答"没有/不确定"就是坏味道：

1. `acks` 和幂等是**显式写**的吗，还是靠默认值？
2. 每条消息**有业务含义的 key** 吗，还是 `None`？
3. `send()` 的结果**被检查**了吗，还是发完就不管？
4. 位移是在**业务处理成功之后**提交的吗？
5. 处理抛异常时，有**出口**（DLQ / 跳过 / 退避重试）吗，还是让分区卡住？
