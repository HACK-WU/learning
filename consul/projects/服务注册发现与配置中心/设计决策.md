# 设计决策 · 服务注册发现与配置中心

> 每个决策点都**真有争议**——换个架构师来可能选另一个方案，且也有道理。

## 决策 1：健康检查用 TTL（应用上报）还是 HTTP 探测（agent 拉取）

**候选方案**

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| A · TTL 检查 | 应用自己定时调 `/v1/agent/check/pass`，超时未上报则判 critical | 能反映**应用内部状态**（如线程池耗尽、依赖的 DB 连不上，虽然端口还通）；无需暴露健康检查端点 | 应用必须集成心跳逻辑；心跳线程挂了会被误判死亡；网络抖动可能导致误摘 |
| B · HTTP 检查 | agent 定期 GET 应用的 `/health`，按状态码判定 | 应用零侵入（不必改代码上报）；agent 统一管控 | 只能反映"端口通不通"，无法感知应用内部假死；每个服务都要暴露一个端点 |

**最终选择**：**A · TTL 检查**

**选择理由**：本项目要演示的是"完整生命周期"——注册、心跳、注销都由应用掌控，TTL 能把这条链路显式暴露出来（教学价值）。更重要的是，TTL 能表达"进程活着但已经不能干活"这种 HTTP 检查抓不到的状态，这对配置中心这类基础组件更重要。

**为此付出的代价**：

1. 应用必须常驻一个心跳线程，且这个线程本身可能出 bug（本项目实测：心跳线程被 `stop_event` 停掉后，实例在约 8 秒内被摘除——这是预期行为，但代码 bug 导致心跳漏报时也会同样被摘，且难以区分）
2. 心跳周期必须小于 TTL 且留足余量（本项目取 TTL 的一半），网络抖动时有一两次失败容错
3. 客户端库要处理上报失败的重试，复杂度高于 HTTP 检查

**什么时候该改选另一个**：若你的服务是**无法修改代码的第三方应用**（如买来的商业软件、闭源组件），或者团队没有统一的 SDK 可嵌入，HTTP 检查是唯一可行解；另外，若团队运维能力强、倾向于"健康检查逻辑集中在 agent 而非散落在各应用"，HTTP 检查更可控。

## 决策 2：配置更新用阻塞查询（长轮询）还是定时轮询

**候选方案**

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| A · 阻塞查询 | 带 `index` + `wait` 参数发起请求，服务端挂起直到配置变更或超时 | 变更**秒级**生效（本项目实测 1023ms）；无变更时几乎零请求开销；单向 HTTP 即可，无需额外基础设施 | 长连接占用服务端资源；**客户端超时必须大于 wait**（本项目踩坑点）；需要处理超时重试 |
| B · 定时轮询 | 每 N 秒拉一次全量配置 | 实现最简单；无长连接；对服务端无特殊要求 | 实时性与请求量二选一（1 秒轮询 = 每实例每分钟 60 次请求，实例多了 Consul 压力大）；且轮询间隔内的变更有延迟 |
| C · consul-template | 官方工具监听变更并渲染配置文件、触发命令重启 | 零编码；成熟稳定；支持多后端 | 靠"重写文件 + 执行命令"生效，本质是**重启或信号通知**，不是进程内热更新；容器环境里子进程管理复杂（课 6 实测踩过） |

**最终选择**：**A · 阻塞查询**

**选择理由**：本项目要的是"进程内热更新"——配置变了立刻在内存生效，不重启、不重载进程。阻塞查询是 Consul 原生的推送式能力，延迟和开销都远优于轮询（实测 1023ms 内唤醒）。consul-template 虽然成熟，但它是"渲染文件 + 触发命令"模型，跟"进程内变量热更新"不是一回事。

**为此付出的代价**：

1. **客户端超时必须单独调大**——`urllib` 的 `timeout` 是**整个请求的总耗时上限**而非连接超时，沿用默认 5 秒会在 wait=60s 的阻塞查询上必然 `TimeoutError`。本项目实测踩到并修复（见[反例对照.md](./反例对照.md) 差异 1）
2. **同值重写不会唤醒阻塞查询**——实测确认：对同一 key 写入相同值，前缀查询的 index 不推进（136 → 136），阻塞查询永远挂起到超时。所以"配置没变"和"配置变了但值相同"在语义上要区分开
3. 每个 watch 循环占一个长连接，实例数 × watch 数增长时需在架构上收敛（如每节点一个 watcher 再内部分发）

**什么时候该改选另一个**：若你的应用是**无法改代码**的现成程序（只能通过配置文件 + 重启生效），选 consul-template；若实例规模极大（数千实例同时 watch 同一前缀）且对秒级不敏感，定时轮询 + 本地缓存的服务端压力更可预测。

## 决策 3：选主用 Consul 会话锁还是外部协调服务

**候选方案**

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| A · Consul 会话锁 | 用 session + KV acquire 抢锁，靠 TTL 续约维持 | **不引入新组件**——已经在用 Consul 了，复用即可；崩溃后 TTL 到期自动释放，无需人工干预 | 是**建议性锁**，不遵守规则的应用可直接改 KV 绕过；依赖 Consul 可用性（Consul 挂 = 选主挂）；抢锁有 LockDelay 等待（实测约 15 秒） |
| B · 外部协调（etcd / ZooKeeper / K8s Lease） | 用专门的一致性组件选主 | 语义更强（etcd 有租约 + 事务）；与 Consul 解耦，Consul 故障不影响选主 | 多一套组件要运维；若主业务已依赖 Consul，等于双份运维成本 |
| C · 数据库悲观锁 / 唯一索引 | 用 DB 的一行记录当锁 | 零新组件（DB 已有）；DBA 熟悉 | 性能差、无 TTL 自动释放（进程崩溃需人工清理）；强依赖 DB 可用性；轮询检测延迟高 |

**最终选择**：**A · Consul 会话锁**

**选择理由**：本项目的前提就是"已经在用 Consul 做服务发现与配置"，此时为选主再引入一套协调组件，运维成本不划算。会话锁的 TTL 自动释放机制正好覆盖"leader 进程崩溃"这个最核心的场景（实测：直接销毁会话模拟崩溃，锁的 Session 字段变空，另一个候选者随后可抢到）。

**为此付出的代价**：

1. **它是建议性锁**——锁只能约束"愿意遵守规则"的参与者。任何能访问 Consul 的代码都可以无视锁直接改那个 KV 键。生产环境必须靠 ACL 限制写权限来兜底
2. **LockDelay 会导致"锁明明释放了却抢不到"**——这是本项目实测最反直觉的一点：会话销毁后锁立即自动释放，但新候选者在约 15 秒内抢锁**全部返回 False**，直到 17 秒才成功。这是 Consul 为防止脑裂设计的等待期（课 6 已实测）。若你的业务要求 leader 故障后 1 秒内完成交接，Consul 锁不是好选择
3. 选主与该 Consul 集群的可用性绑定——Consul quorum 丢失期间无法续约，可能触发 leader 反复切换

**什么时候该改选另一个**：若选主是**核心业务强依赖**且要求亚秒级交接（如金融交易的主备切换），应选 etcd 租约或 Raft 库内建选主；若已经在 K8s 上且只需单实例语义，直接用 K8s 的 Lease 或 StatefulSet 更省事。

---

## 📊 三个决策的一句话总结

| 决策 | 选择 | 核心理由 | 最大代价 |
|------|------|---------|---------|
| 健康检查模型 | TTL（应用上报） | 能表达"进程活着但不能干活" | 心跳线程本身成了新的故障点 |
| 配置更新方式 | 阻塞查询 | 秒级生效 + 零额外组件 | 客户端超时、同值重写两个坑 |
| 选主机制 | Consul 会话锁 | 复用已有组件，崩溃自动释放 | 建议性锁 + LockDelay 15 秒交接延迟 |
