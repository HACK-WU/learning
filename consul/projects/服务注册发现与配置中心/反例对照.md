# 反例对照 · 服务注册发现与配置中心

> 不是"错误示例"，而是**看起来能跑、实际很糟**的版本——只有这样才能教会"为什么最佳实践是最佳实践"。

## ❌ 反例：一个"能跑通"的简化版配置监听

下面这段代码**能正常启动、能读到配置、演示时看起来完全正常**——这是它危险的原因：

```python
# ❌ 反例：直接轮询版配置监听（能跑，但暗藏四个坑）
import time, base64, urllib.request, json

CONSUL = 'http://127.0.0.1:8500'

def load_config():
    """每 2 秒拉一次配置"""
    with urllib.request.urlopen(f'{CONSUL}/v1/kv/demo?recurse=true',
                                timeout=5) as resp:
        items = json.loads(resp.read().decode())
    return {i['Key'].split('/')[-1]: base64.b64decode(i['Value']).decode()
            for i in items}

config = load_config()
while True:
    time.sleep(2)                      # ① 轮询间隔
    new_config = load_config()         # ② 无超时保护、无异常处理
    if new_config != config:
        config = new_config
        print('配置已更新')
```

> 它**能跑通**：配置确实会更新，控制台确实会打印。初看还比正确版本**更简洁**（没有 index 游标、没有快照、没有线程）。问题在下面。

## 🔍 逐条对比

| # | 维度 | ❌ 反例 | ✅ 正确做法 | 为什么糟 |
|---|------|---------|------------|----------|
| 1 | **实时性 vs 开销** | 每 2 秒全量拉一次 | 阻塞查询（index + wait），无变更时挂起 | 延迟固定 2 秒（最多），且**请求量与实例数成正比**：100 个实例 = 每分钟 3000 次请求打在 Consul 上，纯属浪费。阻塞查询在无变更时几乎零开销，且变更毫秒级唤醒（本项目实测 1023ms） |
| 2 | **Consul 不可用时的表现** | 异常直接抛出，进程崩溃 | `try/except` 捕获后回落本地快照，服务继续用旧配置运行 | **一个配置中心的抖动导致所有业务实例崩溃**——这是把"配置中心"变成"单点故障"的典型方式。正确做法是 Consul 挂了服务照跑（能力降级而非整体崩溃） |
| 3 | **KV 无版本历史** | 配置只在内存里，无留档 | 落盘快照 + `export()` 导出 | Consul KV **没有版本历史、没有审计**（课 6 实测：改了就查不回旧值）。出事后无法回答"昨晚 8 点这个值是多少"，排查只能靠猜 |
| 4 | **同值重写的认知盲区** | 靠 `new_config != config` 比较判断变更 | 用响应头 `X-Consul-Index` 判断 | 反例靠值比较，看似等价，实则埋雷：某次写入**值恰好相同**时（如灰度回滚到上一个配置），值比较判不出变更，而 index 能正确推进语义。反过来，本项目实测发现**同值重写连 index 都不推进**（136 → 136），所以"值相同"场景下无论哪种方式都不会唤醒——必须意识到这个边界 |

## 💡 一句话教训

> **能跑通 ≠ 能扛住；差别在于失败时怎么表现。**
>
> 反例在正常路径下与正确版本输出完全一致，只有当 Consul 抖动、实例规模上量、需要追溯历史配置时，四个坑才会同时爆发——而那时通常已经是生产事故了。

想亲眼看到差异，可以在[实现/](./实现/)目录跑：

```powershell
# 正确版本：改 KV 后毫秒级唤醒，且 Consul 断开时用快照兜底

```

然后停掉 Consul agent（`consul leave`），观察：

- ✅ 正确版本：服务仍在响应（用快照中的旧值），Consul 恢复后自动重新同步
- ❌ 反例版本：抛异常后进程直接退出
