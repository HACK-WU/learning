## 🚫 适用边界与反模式

### 什么时候不该用 Consul

> "不该用"比"怎么用"更值钱——这是从"会用"到"用对"的分界线。

| 场景 | 为什么不适合 | 该用什么替代 |
|------|-------------|-------------|
| **KV 当主配置中心（有审计/灰度/版本需求）** | 本机实测：KV **没有版本历史**（改了查不回旧值）、**没有审计日志**（企业版才有）、单值 512KB 上限（实测 600KB 写返回 413） | 专业配置中心（Nacos / Apollo），或用 Git 做源 + Consul 只做分发 |
| **需要跨数据中心同步数据** | 本机实测：KV 与目录**都不跨 DC 复制**（dc2 本地读同 key 返回 404，同 key 两 DC 可存不同值）。联邦连的是查询通道，不是数据副本 | 数据库自带复制、消息队列，或应用层同步 |
| **只需单 K8s 集群内的服务发现** | Consul 的价值在异构环境（VM+容器）与多 DC；纯 K8s 场景 Service/Endpoints 已够，Consul 是纯增重 | Kubernetes Service（课 7 决策卡片） |
| **需要亚秒级故障交接的选主** | 本机实测：会话锁在 holder 崩溃后受 **LockDelay** 约束，约 15 秒内新候选抢锁全部失败（17 秒才成功） | etcd 租约、K8s Lease、或 Raft 库内建选主 |
| **把 Consul 当数据库存业务数据** | KV 设计目标是配置与协调元数据，非业务存储；无索引、无查询能力、无事务跨键一致性（事务上限 64 操作且限单 DC） | 数据库 |
| **dev 模式上生产** | `-dev` 用内存存储、无 Raft 持久化，重启即全丢（官方文档与多份运维指南一致强调） | 正式集群（3/5 奇数 server，持久化 data_dir） |

> **一句话**：Consul 的主场是**异构环境的服务注册发现 + 健康检查**；把 KV 当配置源可以，但别指望它承担配置中心的管理职责（版本、审计、灰度）。

### 高频反模式（能跑，但迟早出事）

1. **用短超时客户端发阻塞查询**
   实测踩坑：`urllib` 的 `timeout` 是**整个请求的总耗时上限**而非连接超时。对 `wait=60s` 的阻塞查询沿用默认 5 秒超时，必然在变更到达前 `TimeoutError`，表现为"配置热更新永远不生效"。
   → **正确做法**：阻塞查询的客户端超时必须 **大于** `wait` 参数。

2. **以为"改了配置就会触发更新"**
   实测确认：对同一 key **写入相同的值**，前缀查询的 `index` 不推进（136 → 136），阻塞查询永远挂起到超时。
   → **正确做法**：理解"值相同 = 无变更"语义，需要强制触发时写入不同的值（如带时间戳）。

3. **TTL 检查 + DCSA 的隐式注销**
   实测踩坑：注册带 TTL 检查且设了 `DeregisterCriticalServiceAfter`，心跳一断服务连同 sidecar 注册一起被自动注销，sidecar 的 watch 报 404 后进入指数退避（日志 `retry=5s/20s/45s`）。
   → **正确做法**：明确 DCSA 是"故障即销毁"语义，需要保留实例做排查时不要设。

4. **把 Consul 锁当互斥原语强依赖**
   它是**建议性锁**（Advisory lock）——只能约束愿意遵守规则的参与者，任何能访问 Consul 的代码都能直接改那个 KV 键绕过锁。
   → **正确做法**：用 ACL 限制写权限兜底；核心互斥场景用更强的原语。

5. **开了 Connect 就当零信任**
   实测：默认意图策略是 **allow**（无 ACL 时任何人都能给自己的服务领一张合法证书）。
   → **正确做法**：ACL 默认拒绝 + default deny intention + 显式 allow 清单，三件套缺一不可。

## 🔥 高频故障模式

> 每条固定五段式：症状 → 根因 → 排查路径 → 修复 → 预防。症状均为可观测现象。

### 故障模式 1：配置热更新永远不生效（阻塞查询超时）

- **症状（可观测）**：应用日志里配置更新时间间隔恰好等于客户端超时值；或直接抛 `TimeoutError: timed out`；改了 KV 但接口返回的还是旧值
- **根因**：客户端 HTTP 超时小于 Consul 的 `wait` 参数。`urllib`/requests 的 timeout 是**总耗时上限**，阻塞查询会挂起等待变更，客户端先超时断开
- **排查路径**：
  1. 对比客户端 timeout 与阻塞查询的 `wait` 值 → 前者 < 后者即命中
  2. 单独用 curl 验证：`curl "http://127.0.0.1:8500/v1/kv/demo?recurse&index=<idx>&wait=30s" -m 40`，能返回说明服务端正常，问题在客户端
- **修复**：把阻塞查询的超时设为 `wait + 15s` 以上
- **预防**：客户端库里把"普通请求"与"阻塞查询"分成两套超时配置，并在代码注释里写明原因
- **来源**：本机实测（2026-08-28，Consul 2.0.2 + Python 3.11）

> 对应速查条目：[09-排障速查手册.md](09-排障速查手册.md) · 症状 4

### 故障模式 2：改了 KV 但阻塞查询不返回

- **症状（可观测）**：写入成功（HTTP 200），但所有 watch 该前缀的客户端都无反应，直到 wait 超时
- **根因**：**同值重写不推进 index**。本机实测：写入 `samekey=v1`（新值）时前缀 index 从 134 → 136；再次写入 `samekey=v1`（相同值）时 index 保持 136 不变
- **排查路径**：
  1. 手动对比写入前后的 index：`curl -v ".../v1/kv/demo?recurse=true"` 看 `X-Consul-Index` 响应头
  2. 若两次 index 相同，说明写入未产生状态变更
- **修复**：写入不同值（如附加时间戳）；或接受"值相同即无变更"的语义
- **预防**：配置发布流程中，若需要"强制推送"（如回滚到历史值），显式写入一个版本号键来推进 index
- **来源**：本机实测（2026-08-28）

> 对应速查条目：[09-排障速查手册.md](09-排障速查手册.md) · 症状 5

### 故障模式 3：锁明明释放了，新候选却抢不到

- **症状（可观测）**：会话销毁后查询锁键，其 `Session` 字段已变为空（确认已释放），但新候选者 `acquire` 持续返回 `false`；约 15 秒后突然成功
- **根因**：**LockDelay**。Consul 在锁被释放后强制等待一段时间（默认 15 秒）才允许再次获取，目的是防止原持有者因网络分区"假死"时新持有者同时进场造成脑裂
- **排查路径**：
  1. 确认锁确实释放：`curl ".../v1/kv/<lock-key>"` 看 `Session` 字段是否为空
  2. 若为空但仍抢不到 → 是 LockDelay 在起作用，属预期行为
  3. 本机实测时间线：t=0/5/11 秒抢锁均 False，t=17 秒 True
- **修复**：这是设计行为，不是 bug。若业务不能接受 15 秒交接延迟，换选主机制（etcd 租约 / K8s Lease）
- **预防**：把"锁交接延迟 = LockDelay + 检测时间"写进容量与 SLA 评估
- **来源**：本机实测（2026-08-28）+ 课 6 讲义实测一致

> 对应速查条目：[09-排障速查手册.md](09-排障速查手册.md) · 症状 6

### 故障模式 4：服务注册成功但很快消失

- **症状（可观测）**：服务注册返回 200，几秒到一分钟后从服务列表消失；`consul monitor` 里能看到 deregister 相关日志
- **根因**：两类最常见——① 健康检查失败导致被标记 critical，配合 `DeregisterCriticalServiceAfter` 触发自动注销；② TTL 心跳线程未启动或异常退出，TTL 到期后判死
- **排查路径**：
  1. 查当前检查状态：`curl "http://127.0.0.1:8500/v1/agent/checks"`
  2. 查健康视图：`curl "http://127.0.0.1:8500/v1/health/service/<name>"`（注意用 health 接口而非 catalog）
  3. 看 agent 日志：`consul monitor -log-level=debug | grep health`
  4. 确认心跳线程是否真的在跑（本机实测：心跳线程被停掉后约 8 秒内实例从健康列表消失）
- **修复**：修正健康检查端点 / 恢复心跳上报；排查期可先移除 DCSA 避免实例被销毁
- **预防**：TTL 心跳周期设为 TTL 的一半以下；健康检查端点要能真实反映"能不能干活"
- **来源**：本机实测（2026-08-28）+ HashiCorp 官方排错文档思路（[Consul Errors And Warnings](https://support.hashicorp.com/hc/en-us/articles/115015603408)）

> 对应速查条目：[09-排障速查手册.md](09-排障速查手册.md) · 症状 2

### 故障模式 5：No known Consul servers（agent 找不到 server）

- **症状（可观测）**：日志出现 `[ERR] agent: failed to sync remote state: No known Consul servers`、`[WARN] agent.router.manager: No servers available`；HTTP 请求返回 `500 No known Consul servers`；`consul info` 显示 `known_servers: 0`
- **根因**：agent 的 server 地址列表失效或未配置。常见触发：server 全部被替换成新 IP（ASG 重建、子网变更）、`retry_join` 未配置或指向旧地址、8300/8301 端口被防火墙阻断
- **排查路径**：
  1. 确认 agent 视角的 server 列表：`consul info | grep known_servers`
  2. 测连通性：`nc -zv <server> 8300`（server RPC）与 `8301`（LAN gossip，TCP+UDP 都要通）
  3. 查 server 侧是否健康：`curl http://<server>:8500/v1/status/leader`
- **修复**：补充/更新 `retry_join` 指向新 server 地址后重启 agent；或先恢复网络与端口
- **预防**：8300 与 8301 当成一对来管理（防火墙策略同时评审）；对 `consul.client.rpc.failed` 持续非零告警（该指标只存在于 agent 侧，server 仪表盘看不到）
- **来源**：HashiCorp 官方错误清单（[Consul Errors And Warnings](https://support.hashicorp.com/hc/en-us/articles/115015603408)）+ Netdata Consul 排障指南（[链接](https://www.netdata.cloud/guides/consul/consul-client-rpc-failed)，核查于 2026-08）

> 对应速查条目：[09-排障速查手册.md](09-排障速查手册.md) · 症状 1

### 故障模式 6：leader 频繁切换（选举震荡）

- **症状（可观测）**：日志反复出现 `New leader elected`、`Election timeout reached, restarting election`；写入间歇性失败；Raft commit 延迟飙升
- **根因**：典型三因——① 网络不稳定/分区；② **磁盘 I/O 慢**（Raft 每次 append 都要 sync 到盘，慢盘会触发超时误判）；③ 集群规模或 `raft_multiplier` 配置不当
- **排查路径**：
  1. 看选举日志：`consul monitor | grep -i "leader elected"`
  2. 看当前 peers：`consul operator raft list-peers`
  3. 查磁盘 I/O 与 commit 延迟指标
- **修复**：先恢复网络与磁盘性能；跨 DC/高延迟环境调大 `raft_multiplier`
- **预防**：server 用奇数（3/5/7）且分布在稳定低延迟网络段；监控 Raft 内部指标（commit 时间、snapshot 延迟）而不只是服务发现指标
- **来源**：HashiCorp 官方参考架构（[Consul reference architecture](https://www.consul.io/docs/guides/deployment.html)，核查于 2026-08）+ Azimuth 排障文档（[Debugging Consul](https://azimuth-cloud.github.io/azimuth-config/debugging/consul)）

> 对应速查条目：[09-排障速查手册.md](09-排障速查手册.md) · 症状 3

### 故障模式 7：Connect 意图改了不生效（内置代理）

- **症状（可观测）**：意图已删除（`/v1/connect/intentions` 返回 `[]`），但连接仍被拒，且 `/v1/agent/connect/authorize` 仍返回已删除的意图 ID；新创建的意图在观察窗内也不生效
- **根因**：内置代理（`consul connect proxy`）的意图视图不随变更刷新。本机实测：意图删除后 11 分钟内持续匹配"幽灵意图"，sidecar 进程重启也不恢复，新意图 60 秒观察窗内不生效。与官方文档一致——内置代理"not supported for production...not under active development"
- **排查路径**：
  1. 对比两个视图：`GET /v1/connect/intentions`（集群真实状态）vs `POST /v1/agent/connect/authorize`（agent 授权视图）
  2. 两者不一致 = agent 侧缓存陈旧
- **修复**：生产环境换用 Envoy 数据面（走 xDS 增量流）；内置代理仅用于本地功能验证
- **预防**：不要把内置代理用于任何"意图行为"的验证；功能验证与生产部署使用同一套数据面
- **来源**：本机实测（2026-08-28，Consul 2.0.2 dev 模式）+ 官方文档内置代理定位说明

> 对应速查条目：[09-排障速查手册.md](09-排障速查手册.md) · 症状 7

## ✅ 落地 Checklist

> 投产 / 正式启用前逐项打勾。

**集群与部署**

- [ ] server 数量为奇数（3 或 5），且分布在稳定的低延迟网络段
- [ ] **未使用 `-dev` 模式**（dev 无 Raft 持久化，重启全丢）
- [ ] `data_dir` 有持久化且 Consul 进程有读写权限
- [ ] 8300（server RPC）与 8301（LAN gossip，TCP+UDP）成对开放；跨 DC 另需 8302
- [ ] `retry_join` 已配置且指向稳定的 server 地址
- [ ] 快照与备份策略就绪（Consul 官方建议 `raft_snapshot_interval` 等关键默认值需按规模审视）

**服务与健康检查**

- [ ] 健康检查端点能真实反映"能不能干活"（不只是端口通）
- [ ] TTL 检查的心跳周期 ≤ TTL 的一半
- [ ] 明确 `DeregisterCriticalServiceAfter` 的语义（设了 = 故障即销毁，影响排查）
- [ ] 消费方用 `/v1/health/service` 而非 `/v1/catalog/service`（后者不过滤健康状态）

**KV 与配置**

- [ ] 重要配置有**外部留档**（KV 无版本历史，本机实测）
- [ ] 单值大小远低于 512KB 上限（实测 600KB 返回 413）
- [ ] 客户端阻塞查询超时 > `wait` 参数
- [ ] 应用有 Consul 不可用时的降级路径（本地快照 / 缓存）

**安全**

- [ ] ACL 已启用且默认策略为拒绝
- [ ] 若启用 Connect：默认意图策略已设为 deny，且配了显式 allow 清单
- [ ] 生产未使用内置代理作为数据面

**可观测性**

- [ ] 告警覆盖 `consul.client.rpc.failed`（每个 agent，非仅 server）
- [ ] 监控 Raft 内部指标（leader 稳定性、commit 时间）
- [ ] 定期比对 agent 本地服务列表与 catalog 的差异

## 📰 真实事故案例复盘

### 案例 1：Roblox 2021 年 10 月大规模宕机（Consul 作为单点故障）

- **经过**：2021-10-28 起 Roblox 全站中断约 73 小时。起初表现为 KV 写延迟从常态 <300ms 劣化到约 2 秒，随后服务发现失效、容器调度（Nomad）与密钥获取（Vault）全部瘫痪
- **根因**：Consul 集群在负载下不稳定。团队先后排除硬件故障（换新机无效）、重置集群状态（用 iptables 屏蔽流量后恢复、放开流量再次劣化），最终定位为**集群承载的负载模式**（海量服务注册 + 健康检查 + watch）超出承载能力。恢复手段是系统性削减 Consul 使用量：非必要调用全禁、服务实例从数百缩到个位数、健康检查频率从 60 秒放宽到 10 分钟
- **损失**：全站不可用约 73 小时
- **教训**：**Consul 会变成单点故障**——当服务发现、调度、密钥全挂在它上面时，它不健康的代价是全站。两 defence：① 关键依赖要有 fallback（Roblox 事后正是靠降级与限流恢复）；② 控制 Consul 的负载规模——健康检查频率、watch 数量、实例规模都是可调的容量参数
- **来源**：[Roblox Return to Service（官方博客）](https://about.roblox.com/bn-in/newsroom/2022/01/roblox-return-to-service-10-28-10-31-2021)（核查于 2026-08）

### 案例 2：Stripe 早期 Consul 落地踩坑（磁盘 I/O 引发 Raft 震荡）

- **经过**：Stripe 在 2016 年前后引入 Consul 时遭遇一系列问题：Raft 频繁故障转移、某版本 TLS 功能损坏、leader election 相关的 goroutine 泄漏导致内存吃满
- **根因**：Raft 频繁 failover 的直接原因是**主节点磁盘 I/O 太慢**——磁盘跟不上 Consul 的读需求，节点卡住被误判为下线，触发重新选举，循环往复。Consul 强一致（默认 consistent 读）意味着选举期间读写均不可用
- **损失**：服务发现间歇性不可用，依赖 fallback（硬编码 DNS 名）维持
- **教训**：① **磁盘 I/O 是 Consul 的生命线**（Raft 每次 append 都 sync 到盘），慢盘会直接引发选举震荡；② 引入期要"小范围 + 保留 fallback"双保险；③ 他们最终用 consul-template 生成 DNS 记录替代直接 API 查询（并踩到 watch 模式把 server 打挂的坑，改用 60 秒 cron）
- **来源**：[Service discovery at Stripe（官方博客）](https://stripe.com/en-GB/blog/service-discovery-at-stripe)（核查于 2026-08）

### 案例 3：爱奇艺 Consul 多 DC 故障（网络抖动触发 OOM）

- **经过**：多个 DC 的 Consul Server 不响应请求，大量 agent 连不上 server 且无法自动恢复；表现为 Raft 选举失败、HTTP/DNS 查询超时（部分耗时数十秒）、goroutine 与内存快速增长直至系统 OOM
- **根因**：DC 间网络抖动（RTT 从 2ms 涨到 800ms、伴随丢包，持续约 1 分钟）→ 低版本 `armon/go-metrics` 的 Prometheus 实现使用全局锁 `sync.Mutex`，高并发下性能急剧下降 → 资源耗尽。网络恢复瞬间反而丢失 leader、Raft 持续选举失败
- **损失**：多 DC 服务注册中心不可用
- **教训**：① **跨 DC 网络抖动是 Consul 多 DC 部署的头号风险**（本课实测也显示 WAN 成员状态翻转滞后于 RPC 失败）；② 依赖库的全局锁在高并发下会成为放大器；③ 版本升级与依赖治理同样属于可用性工程
- **来源**：[爱奇艺微服务平台 Consul 故障复盘](https://ecweb.ecer.com/topic/en/detail-728137-iqiyis_microservice_evolution_after_consul_failure.html)（核查于 2026-08；该页面为第三方转载，原始出处为爱奇艺技术团队分享，细节以转载内容为准）
