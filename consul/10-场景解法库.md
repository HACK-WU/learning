## 场景 1：小团队微服务，要做服务寻址

**场景描述**：十几个服务，部署在几台 VM 或容器上，服务之间靠 IP 硬编码调用，加机器就要改配置。

### 推荐解法

用 Consul 做**服务注册 + 健康实例发现**，消费方按服务名发现，直连调用（客户端发现模式）。

```bash
# 1. 每个节点跑一个 agent（生产用 client，非 dev）
consul agent -config-dir=/etc/consul.d/

# 2. 服务注册（带健康检查）
curl -X PUT --data-binary @web.json http://127.0.0.1:8500/v1/agent/service/register

# 3. 消费方按服务名发现健康实例
curl "http://127.0.0.1:8500/v1/health/service/web?passing=true"
```

**为什么这么配**：
- **用 `/v1/health/service` 而不是 `/v1/catalog/service`**——前者带健康过滤，后者返回的是注册表而非可用实例（课 4）。这个区别在生产上直接决定"会不会调到已经挂掉的实例"。
- 应用只与**本机 agent（:8500）**通信，代码里不出现任何 Server 地址。Server 地址只对 agent 可见，集群拓扑变化对应用透明。

### 这个解法的边界

- **别用 `consul agent -dev` 上生产**：dev 用内存存储、无 Raft 持久化，重启即全丢。
- 生产最小拓扑是 **3 或 5 个 server**（奇数，满足 quorum）+ 每节点 client agent。
- 如果你的服务全在同一个 K8s 集群里 → 转 [场景 4](#场景-4纯-k8s-单集群服务发现)，大概率不需要 Consul。

## 场景 2：想用 KV 当配置中心

**场景描述**：配置散落在各服务的配置文件里，改一次要重启一批服务，想集中管理并支持热更新。

### 推荐解法

**Consul 做分发，Git 做源。** KV 存配置、用阻塞查询推给应用；但配置的**版本历史、审计、灰度**交给 Git + 外部流程。

```python
# 阻塞查询：index 变化才返回，实现秒级热更新
def wait_update(key, index, timeout="60s"):
    r = requests.get(
        f"http://127.0.0.1:8500/v1/kv/{key}?recurse=true&index={index}&wait={timeout}",
        timeout=90,  # 必须大于 wait，否则永远超时
    )
    return r.headers.get("X-Consul-Index"), r.json()
```

**为什么这么配**（本机实测依据）：
- KV **没有版本历史**——改了查不回旧值，所以版本管理必须外置到 Git。
- KV **没有审计日志**（企业版才有），所以"谁在什么时候改了什么"要靠外部留痕。
- 单值上限 **512KB**，实测写 600KB 返回 **413**。
- 事务上限 **64 个操作且限单 DC**。

### 这个解法的边界

> ⚠️ 这是全课程**最容易被高估**的能力。

- **有审计 / 灰度 / 版本需求 → 别用 KV 当主配置中心**，用 Nacos / Apollo 等专业配置中心。
- **写入相同的值不会触发更新**：实测对同一 key 写同值，`index` 不推进（136 → 136），阻塞查询永远挂起。需要强制触发时写不同的值（如带时间戳）。
- **本地快照兜底**：Consul 不可达时应用应能凭本地快照启动。做法：原子写（先写 `.tmp` 再 `os.replace`）+ 启动时回落。

## 场景 3：多实例部署，要选主 / 防重跑

**场景描述**：定时任务或后台 worker 部署了多个实例，只想让其中一个干活，且它挂了要有别人接上。

### 推荐解法

用 **session + KV 锁**做领导者选举。

```python
# 建 session（绑定健康检查，实例挂了 session 自动失效）
session = consul.session.create(ttl="15s", behavior="release")
# 抢锁
locked = consul.kv.put("service/leader", my_id, acquire=session)
```

**为什么这么配**：
- session 绑定健康检查，holder 崩溃后锁自动释放，无需人工介入。
- `behavior="release"` 表示 session 失效时释放（而非删除）键值。

### 这个解法的边界

> ⚠️ **亚秒级交接做不到**——这是实测结论，不是保守估计。

- 本机实测：holder 崩溃后受 **LockDelay** 约束，约 **15 秒内新候选抢锁全部失败**（17 秒才成功）。
- **需要亚秒级故障交接的选主 → 用 etcd 租约、K8s Lease 或 Raft 库内建选主。**
- 它是**建议性锁（Advisory lock）**——只能约束愿意遵守规则的参与者，任何能访问 Consul 的代码都能直接改那个 KV 键绕过锁。核心互斥场景要用更强的原语，或用 ACL 限制写权限兜底。

## 场景 4：纯 K8s 单集群服务发现

**场景描述**：服务全跑在一个 Kubernetes 集群里，想引入 Consul 做服务发现。

### 推荐解法

**别用。** 用 Kubernetes 原生 Service / Endpoints。

**为什么**：Consul 的价值在**异构环境（VM + 容器）与多 DC**。纯 K8s 场景下 Service 已经提供了稳定的 DNS 名与负载均衡，引入 Consul 是**纯增重**——多一套控制面要运维，多一层故障域。

### 这个解法的边界

- **反例**：如果你的 K8s 集群**不止一个**，或者有 **VM 上的遗留服务**要跟 K8s 里的服务互相调用 → 转 [场景 5](#场景-5异构环境vm--容器统一寻址)，这时 Consul 的价值才成立。
- 注：K8s 落地细节（Helm / consul-k8s / CRD）已登记为缺口 #6，并入课 12 骨架，**待阶段 4 补充**。

## 场景 5：异构环境（VM + 容器）统一寻址

**场景描述**：一部分服务在 VM 上（遗留系统），一部分在 K8s 里，两边要互相调用，且不想维护两套服务发现体系。

### 推荐解法

**这是 Consul 的最大价值场景。** 在所有环境里都跑 Consul agent，用同一套服务名寻址。

**为什么这么配**：
- Consul 与运行环境解耦——VM 和容器里的 agent 是同一个二进制，服务注册与健康检查语义完全一致。
- 消费方不需要知道目标实例在 VM 还是容器里，`/v1/health/service/<name>?passing=true` 一视同仁。

### 这个解法的边界

- K8s 侧的具体落地（Helm chart、consul-k8s、CRD、sidecar 注入）属**待补充内容**，已登记为缺口 #6。
- 跨环境调用意味着网络要打通，Consul 只解决"寻址"，不解决"网络可达"。

## 场景 6：多机房 / 多地域部署

**场景描述**：服务分布在多个机房或地域，希望一个机房的服务能调用另一个机房的。

### 推荐解法

用**多数据中心联邦**打通查询通道，让 dc1 能查到 dc2 的服务。

**为什么这么配**：联邦连的是**查询通道**，让一个 DC 能查询另一个 DC 的服务目录。

### 这个解法的边界

> ⚠️ **联邦不是数据复制**——这是最容易搞错的一点。

- 本机实测：KV 与目录**都不跨 DC 复制**——dc2 本地读同 key 返回 **404**，同 key 两个 DC 可以存**不同的值**。
- **想跨机房同步数据/配置 → 做不到**，转 [场景 10](#场景-10想跨机房同步配置数据)。
- 需要主备切换时，注意各 DC 数据独立，一致性要由应用层保证。

## 场景 7：要做服务间 mTLS 与授权

**场景描述**：想让服务之间的调用走加密通道，并且能控制"谁可以调谁"。

### 推荐解法

用 **Connect** 做 mTLS + **intentions** 做授权，配合内置 CA 或外部 CA 签发证书。

```bash
# 服务以 Connect 方式注册（带 sidecar）
curl -X PUT --data-binary @web-connect.json http://127.0.0.1:8500/v1/agent/service/register

# 建 intention：允许 web 调 api
curl -X POST --data-binary @acl-intention.json http://127.0.0.1:8500/v1/connect/intentions
```

**为什么这么配**：
- 内置 CA 开箱即用，实测默认有效期 **10 年**（读 `NotAfter` 字段：2026 → 2036）。
- 证书由 CA 签发，服务间自动 mTLS，应用代码无感知。

### 这个解法的边界

> ⚠️ **默认策略是最大的坑**——这部分确定性标注为「中」，因数据面未在本机完整实测。

- 实测：**默认意图策略是 allow**（无 ACL 时任何人都能给自己的服务领一张合法证书）。**"开了 Connect 就当零信任"是错的。**
- 正确做法三件套，缺一不可：**ACL 默认拒绝 + default deny intention + 显式 allow 清单**。
- **待验证**：本机 Connect 数据面（Envoy sidecar 实际转发）未完整跑通，课 7 曾记录受限于缺 Envoy 二进制。**本场景的 mTLS 数据面行为标注为「配置层已验证、数据面未实测」**。
- 网格能力的成色评估见课 7 知识点 3。

## 场景 8：要上生产，权限怎么收口

**场景描述**：Consul 要上生产了，需要控制"谁能读什么、谁能改什么"，避免所有人共用一个 token。

### 推荐解法

用 **ACL 三层模型**：token → policy → rule，配合**默认拒绝**。

```hcl
# 1. 开启 ACL（默认拒绝）
acl {
  enabled        = true
  default_policy = "deny"
}

# 2. 建只读策略
key_prefix "app/" {
  policy = "read"
}

# 3. bootstrap 拿管理 token（只能执行一次）
consul acl bootstrap
```

**为什么这么配**（课 8 全链路实测）：
- **最小权限**：按 `key_prefix` / `service_prefix` / `node_prefix` 分别授权，而不是给一个万能 token。
- **默认拒绝**：`default_policy = "deny"`，让"忘了授权"表现为被拒绝，而不是默认放行。

### 这个解法的边界

> ⚠️ **ACL 有三条静默失败，会让你以为"配对了"——这是本课最反直觉的部分。**

1. **无权限读单个 key → 403**（明确报错，好发现）
2. **无权限列服务 → `200 {}`**（返回 200 + 空对象，**看起来像"没有服务"**）
3. **无权限列 keys → `200 []`**（返回 200 + 空数组，**看起来像"没有配置"**）

第 2、3 条最危险：排查时你会以为"服务没注册上""配置没写进去"，实际是**权限不足的静默降级**。

其他要点：
- **匿名 token 的 SecretID 字面量就是 `anonymous`**，默认策略下它能读到的内容要专门检查。
- **bootstrap 只能执行一次**，第二次报 `ACL bootstrap no longer allowed`。
- **ACL、gossip 加密、TLS 是三件独立的事**，开了 ACL 不等于通信加密。
- 完整权限矩阵实测见课 8 知识点 3。

## 场景 9：配置热更新要秒级生效

**场景描述**：改了配置希望几秒内推到所有实例，不要重启服务。

### 推荐解法

用**阻塞查询（长轮询）**：带 `X-Consul-Index` + `wait` 参数，index 不变时服务端挂起请求，变更到达立刻返回。

```python
index = None
while True:
    index, data = wait_update("app/", index, timeout="60s")
    apply_config(data)  # 秒级生效
```

### 这个解法的边界

> ⚠️ **客户端超时必须大于 `wait`，否则这条解法 100% 失效。**

- 实测踩坑：`urllib` / `requests` 的 `timeout` 是**整个请求的总耗时上限**而非连接超时。对 `wait=60s` 沿用默认 5 秒超时，必然在变更到达前超时，表现为"配置热更新永远不生效"。
- 替代方案：**Consul Template** 渲染配置文件 + 触发 reload。**注意：Consul Template 在本课程尚未实测**（现有实战项目内 0 次出现），已登记进应用实战篇判定。

## 场景 10：想跨机房同步配置数据

**场景描述**：希望写在 dc1 的配置，dc2 也能读到，保持一份数据两地可用。

### 推荐解法

**做不到。** Consul 不支持跨 DC 数据复制，请改变设计。

**替代方案**：
- 数据库自带复制
- 消息队列同步
- 应用层双写

**为什么**（本机实测）：
- KV 与目录**都不跨 DC 复制**：dc2 本地读同 key 返回 **404**；同 key 两个 DC 可以存**不同的值**。
- 联邦打通的是**查询通道**，不是数据副本。dc1 可以查询 dc2 的服务目录，但两边的数据各自独立存储。
