## 一、判定标准

不是每课都必须配实战篇。判定采用两条硬标准：

1. **可实操性**：该课知识点能否在单机（Windows + Consul dev/单机多实例）上跑出可观测结果。纯认知型、纯决策型的课不配。
2. **未被现有项目覆盖**：已被现有实战项目焊进去的知识点，不再重复配套。

按这两条，出现三种结论：

- **配套实战篇**：知识点可实操 + 现有项目未覆盖 → 需要写
- **并入现有项目**：知识点可实操 + 现有项目已覆盖 → 不另写，回指项目
- **不配**：决策/认知型，或受环境限制无法单机实测 → 说明原因

## 四、三份待写实战篇的立项说明

### 实战篇 A：一致性读模式实测（配课 5）✅ **2026-09-17 已完成**

- **干了什么**：起三节点集群，对同一 KV 键分别用三种模式读，并强杀 leader 观测无 leader 窗口内三者表现。
- **实测结论**：
  - 写后立即读，`stale` **10/10 次稳定落后一个版本**（不是偶发）
  - `X-Consul-LastContact` 可量化新旧：default/consistent 恒为 0，stale 为 15/30/45ms
  - **强杀 leader 后约 9.5 秒窗口内，`default` 与 `consistent` 全部返回 500，只有 `stale` 持续返回旧值**
  - **quorum 丢失时（三节点挂两个）stale 也不可用**（返回 404）——stale 换的是"选举期间可用"，不是灾备能力
- **过程中的自我纠错**：初版脚本一直访问 8500，而被杀的正是 node1（8500），导致三种模式全失败——那是"连不上 agent"而非读模式差异。修正为从存活节点读后才得到上面这组数据，该教训已写入正文 4.5 节。

### 实战篇 B：Connect 服务网格最小闭环（配课 7）✅ **2026-09-17 已完成，风险已解除**

- **环境可行性结论（重要）**：原判定为「⚠️ 中低，需先验证 Envoy」。实测确认本机**无 Envoy、无 consul-dataplane**，但 **Consul 2.0.2 自带内置代理 `consul connect proxy`，可跑通完整 mTLS 数据面**——**不需要 Envoy**。降级预案未启用。
- **干了什么**：注册两个带 sidecar 的服务，用内置代理跑通 mTLS 调用，用 intention 控制放行/拒绝，并读取证书与 SPIFFE 身份。
- **实测结论**：
  - 通过 upstream 端口访问 → HTTP 200，mTLS 数据面打通
  - 不带客户端证书连 sidecar → TLS 握手即失败（`TLSV13_ALERT_CERTIFICATE_REQUIRED`）
  - **绕过 sidecar 直连应用端口 → 明文 200**（sidecar 与应用之间是 localhost 明文，应用监听 `0.0.0.0` 时网格可被绕过）
  - intention deny 立即生效，日志含 `Matched L4 intention ... Action: DENY`；改回 allow 后 **82ms 恢复**
  - 证书：根证书 10 年、叶子证书 3 天；身份为 SPIFFE ID
- **与课 7 记录的差异**：课 7 曾记录"删除 intention 后长时间仍生效"，本次**未复现**（2.0.2 + `consul config write` 配置条目方式下秒级生效）。已在正文显式说明差异来源，未重复断言。
- **未覆盖**：七层能力（路径级授权、灰度、流量拆分）需 Envoy，本次未实测。

### 实战篇 C：ACL 生产权限模型落地（配课 8）✅ **2026-09-17 已完成**

- **干了什么**：起 `default_policy = deny` 的 agent，为 web/api/ops 三个角色设计最小权限策略，用 21 项权限矩阵逐条验证越权确实被拒。
- **实测结论**：
  - web 写 `api/` → 403；ops 写 `web/` → 403；web 注册名为 api 的服务 → 403 —— 最小权限生效
  - **递归读（`?recurse=true`）越权返回 404，不是 403** —— 客户端会当成"配置不存在"，导致配置热更新静默失效
  - 匿名列目录/列 keys/查健康实例均返回 **200 空结果**（`{}` / `[]`），看起来像"没数据"实为"没权限"
  - **`operator` 资源不带 label**，正确写法是 `operator = "read"`；写成 `operator_prefix "" { policy = "read" }` 不报错但**权限静默不生效**
  - 策略缺 `session_prefix` 时建 session 直接 403 —— 分布式锁用不了，是 ACL 上线最易漏的一项

## 五、推进结果

按**确定性从高到低**执行，三份全部完成，其中风险最高的 B 篇意外跑通：

1. **实战篇 C（课 8 ACL）** ✅ —— 21 项权限矩阵全实测，抓出 `operator` 语法静默失效与递归读 404 两个坑
2. **实战篇 A（课 5 读模式）** ✅ —— 三节点集群 + 强杀 leader，量化出 9.5 秒不可用窗口
3. **实战篇 B（课 7 Connect）** ✅ —— 原判定「需先验证 Envoy，风险中低」，实测发现内置代理即可跑通 mTLS，**风险解除**
4. **实战篇 D（课 7 灰度切分）** ✅ —— 17 项控制面实测，抓出"子集不存在也写入成功"与"配置条目 ≠ 网关进程"两个坑
5. **实战篇 E（课 7 真实数据面）** ✅ —— Docker 起 Envoy，**兑现 D 篇边界**：实测 50/50 → 16/14、90/10 → 22/8，证明数据面真的按权重分发

> **D → E 是本次最有价值的推进结构**：D 篇明确写下"我只能证明控制面算得对，不能证明流量真按规则走"，E 篇接着把 Envoy 跑起来把这条边界兑现。**前一篇主动标注边界、后一篇定向兑现**，比各自独立成篇更有教学价值。

### 实战篇 D：灰度发布与流量切分（配课 7）✅ **2026-09-21 已完成，边界已由 E 篇兑现**

- **为什么补这篇**：缺口台账 #8「灰度发布」。原判定未单列，实测发现它是 discovery chain 的**最典型应用**，且踩坑点密集（协议声明、权重和、子集校验），值得独立成篇。
- **干了什么**：注册 v1/v2 两个实例，写 `service-splitter` 做灰度，演进权重并观察 discovery chain 变化，最后写 `ingress-gateway` 验证网关配置。
- **实测结论（17 项，见正文「实测证据」表）**：
  - 未声明 `Protocol = "http"` 时写 splitter → 500 `protocol "tcp" that does not permit advanced routing`
  - 权重和 = 90 → 500 `the sum of all split weights must be 100, not 90.000000`（**不是格式错，是权重算错**）
  - 权重演进 100/0 → 50/50 → 0/100 全部即时生效，`StartNode` 恒为 `splitter:web`
  - **切到不存在的子集 `v9` 写入成功**，chain 里照样出现 `v9.web` Target —— **不校验子集非空**，是最危险的一条（配错了不告诉你）
  - **写 `ingress-gateway` 成功，但 `ss -tln | grep :8080` 无输出** —— 配置条目 ≠ 进程
- **本篇边界（明确的）**：只证明"控制面算得对"，**不证明"流量真按规则走"**——后者需 Envoy，已由 E 篇兑现。未测：TLS 终止、超时重试、跨 DC 灰度、Envoy 版本兼容矩阵。

### 实战篇 E：北向网关与真实数据面（配课 7）✅ **2026-09-21 已完成，兑现 D 篇边界**

- **为什么补这篇**：B 篇用内置代理跑通 mTLS，但七层能力（真实流量切分、网关路由）必须上 Envoy。本篇**用 Docker 起 Envoy 1.37.6**，把 D 篇"算得对"升级为"真的按规则走"。
- **干了什么**：Docker 起 Envoy 做真实数据面，bootstrap 生成网关配置，注册带 `Kind: "ingress-gateway"` 的网关服务，实测流量分发比例与 intention 拦截。
- **实测结论**：
  - **50/50 配置 → V1=16 / V2=14；90/10 配置 → V1=22 / V2=8**（30 次采样）—— **数据面真的按权重分发**，这是 D 篇未能证明的部分
  - **权重不是精确的**：90/10 下实测 22/8（约 73/27）是 Envoy 加权轮询的小样本统计波动，**不要拿单次小样本校准权重**
  - **直连 sidecar 端口 `code=000` 连不上，经网关却正常** —— 反证 sidecar 只接受 mTLS，网格加密在生效
  - **intention deny 写入 200，但 24 次请求 V2 命中 11 次、拦截 0 次**；Envoy 有 RBAC 过滤器但**无 DENY 策略** → 规则未下发
- **未确认部分（如实记录，不编结论）**：deny 未生效的根因**未能查实**。疑点是网关转发时使用的身份可能不是 `ingress-gw`，导致 source 匹配不上。曾用 `openssl s_client` 抓证书验证身份，但抓到的是 **sidecar 自己的服务端证书**（SAN 为目标服务自身），**拿不到网关的客户端身份**——**该探测方法本身是错的**，已如实撤回。
- **反哺排障手册**（本次新增）：E 篇的 5 个卡点已沉淀为排障手册症状 16–20，其中两条是最高频误诊项：
  - **症状 16**：网关 404 但配置正常 → 用"404 响应头有无 `server: envoy`"区分"网关没起" vs "路由没匹配"
  - **症状 17**：网关 503 但服务 passing → sidecar 进程已消失而注册还在，用"passing 但端口无监听"暴露两个视图打架
  - 另三条：**症状 18**（TLS/CA 报错不是网络问题）、**症状 19**（`No ingress-gateway services registered`）、**症状 20**（intention deny 未拦截，根因未确认）

> 五篇均遵守课程铁律：结论必须实测，不能编造。未实测的部分（Envoy 七层能力、证书轮转、WAN gossip 池、参数敏感性）已在各自正文的「仍存在的已知边界」中显式标注。
