| 改了 KV 配置但应用不更新 / `TimeoutError: timed out` | 🟡 | **症状 4**：配置热更新不生效 |
| 应用**刚启动那段时间**改 KV 完全没反应，跑久了又正常 | 🟡 | **症状 15**：空前缀导致阻塞查询秒回（index 游标为 None） |
| 写 KV 返回 200 但阻塞查询不返回 | 🟡 | **症状 5**：同值重写不触发更新 |
| 锁的 Session 已空但新候选抢不到（约 15 秒内） | 🟡 | **症状 6**：LockDelay 抢锁失败 |

| `413 Request Entity Too Large` | ⚪ | **症状 8**：KV 值超限 |

## 🔴 症状 1：agent 找不到 server

**一眼识别**：`[ERR] agent: failed to sync remote state: No known Consul servers`；`[WARN] agent.router.manager: No servers available`；HTTP 返回 `500 No known Consul servers`

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 若 agent 仍能响应本地查询，先**不要重启**（重启会丢本地服务注册）；若已不可用，重启 agent 并带上正确的 `retry_join` | 本地服务暂时可查 / agent 重新入集群 |
| 定位 1 | `consul info \| grep known_servers` | `0` = 确认命中本症状；短暂抖动正常，**持续为 0** 才是故障 |
| 定位 2 | `nc -zv <server-ip> 8300` 与 `nc -zv <server-ip> 8301` | 8300（server RPC）与 8301（LAN gossip，TCP+UDP）都要通 |
| 定位 3 | `curl http://<server>:8500/v1/status/leader` | 返回空字符串 = server 侧自身丢失 leader，转「症状 3」 |
| 修复 | 更新 `retry_join` 指向当前有效的 server 地址后重启 agent（常见于 server 被 ASG/重建换了 IP） | `known_servers` 恢复非零，日志不再报错 |
| 若无效 | → 转「症状 3」（server 侧无 leader）；或转 `debug` 现场取证 | — |

> **预防**：把 8300 与 8301 当成一对来管理，防火墙策略改动时同时评审；对 `consul.client.rpc.failed` 持续非零告警（该指标只在 agent 侧产生，server 仪表盘看不到）
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 5

## 🔴 症状 2：服务注册后消失 / 健康检查 critical

**一眼识别**：注册返回 200，几秒到一分钟后服务从列表消失；`consul monitor` 有 deregister 相关日志；UI 中检查项标红

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 若设了 `DeregisterCriticalServiceAfter` 且实例还需保留排查，先移除该配置再重新注册 | 实例不再被自动销毁 |
| 定位 1 | `curl "http://127.0.0.1:8500/v1/agent/checks"` | 看到检查状态与输出；`critical` = 检查未通过 |
| 定位 2 | `curl "http://127.0.0.1:8500/v1/health/service/<name>"` | 空的 health 视图 = 无健康实例（**注意用 health 接口，不要用 catalog**） |
| 定位 3 | 若是 TTL 检查：确认应用的心跳线程是否在跑 | 本机实测：心跳停止后约 **8 秒**内实例从健康列表消失 |
| 修复 | 修正健康检查端点（返回 2xx）/ 恢复 TTL 心跳上报；TTL 心跳周期设为 TTL 的一半以下 | 检查转 `passing`，服务重新出现在 health 视图 |
| 若无效 | → 检查 ACL 是否拒绝了 `service:write`；或转 `debug` | — |

> **预防**：TTL 心跳周期 ≤ TTL/2；健康检查端点要能反映"能不能干活"而不只是"端口通不通"
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 4

## 🔴 症状 3：leader 频繁切换（选举震荡）

**一眼识别**：日志反复出现 `New leader elected`、`Election timeout reached, restarting election`；写入间歇性 500；Raft commit 延迟飙升

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 优先恢复**网络连通性**与**磁盘 I/O**——这两项是选举震荡最常见根因，先止血再深挖 | 选举停止震荡 |
| 定位 1 | `curl http://127.0.0.1:8500/v1/status/leader` | 空字符串 = 当前无 leader；地址频繁变化 = 正在震荡 |
| 定位 2 | `consul operator raft list-peers` | 看各节点状态与 `Voter` 标记 |
| 定位 3 | 查 server 的磁盘 I/O 与 Raft commit 延迟指标 | 磁盘慢是经典根因（Raft 每次 append 都 sync 到盘） |
| 修复 | 恢复网络/换更快的盘；跨 DC 或高延迟环境调大 `raft_multiplier` | leader 稳定，写入恢复正常 |
| 若无效 | → 转 `debug`；必要时按官方灾难恢复流程处理 | — |

> **预防**：server 用奇数（3/5/7）且放在稳定低延迟网段；监控 Raft 内部指标（leader 稳定性、commit 时间、snapshot 延迟），而不只是服务发现指标
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 6

## 🟡 症状 4：配置热更新不生效（客户端超时）

**一眼识别**：改了 KV 但应用读到的还是旧值；应用日志抛 `TimeoutError: timed out`；或配置"更新"的时间间隔恰好等于客户端超时值

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 重启应用强制重新全量拉取配置（临时恢复正确性，不解决根因） | 应用读到最新配置 |
| 定位 1 | 对比客户端 timeout 与阻塞查询的 `wait` 参数 | **timeout < wait** = 命中本症状 |
| 定位 2 | `curl -m 40 "http://127.0.0.1:8500/v1/kv/<prefix>?recurse=true&index=<idx>&wait=30s"` | 能正常返回 = 服务端无问题，问题在客户端配置 |
| 修复 | 把阻塞查询的超时设为 `wait + 15s` 以上（如 wait=30s → timeout=45s） | 变更后毫秒级返回（本机实测约 1 秒） |
| 若无效 | → 转「症状 5」（可能是同值重写）；若只在**应用刚启动**时失效 → 转「症状 15」（空前缀导致阻塞查询秒回） | — |

> **预防**：客户端库把"普通请求"与"阻塞查询"分成两套超时配置，并在代码注释写明原因；阻塞查询的调用方一律用**循环重试**包住，不要只等一次（见「症状 15」）
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 1

## 🟡 症状 5：写 KV 返回 200 但阻塞查询不返回

**一眼识别**：写入成功，所有 watch 该前缀的客户端都无反应，直到 wait 超时

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 若需立即生效，写入一个**不同的值**（如附加时间戳）强制推进 index | 阻塞查询立刻返回 |
| 定位 1 | 记录写入前的 index：`curl -D- "http://127.0.0.1:8500/v1/kv/demo?recurse=true"` 看响应头 `X-Consul-Index` | 拿到当前 index |
| 定位 2 | 写入后再查一次 index | **两次相同** = 同值重写未推进 index（本机实测：136 → 136） |
| 修复 | 需要触发更新时写入不同值；或在配置发布流程中用独立的"版本号键"推进 index | 阻塞查询正常唤醒 |
| 若无效 | → 转「症状 4」（确认客户端超时够大） | — |

> **预防**：理解"值相同 = 无变更"是 Consul 的语义；需要"强制推送"的场景（如回滚到历史值）用版本号键驱动
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 2

## 🟡 症状 6：锁已释放但新候选抢不到

**一眼识别**：查锁键的 `Session` 字段已为空（确认释放），但新候选 `acquire` 持续返回 `false`；约 15 秒后突然成功

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | **不需要止血**——这是预期行为。若业务允许等待，静待 LockDelay 结束即可 | 约 15 秒后自动抢到 |
| 定位 1 | `curl "http://127.0.0.1:8500/v1/kv/<lock-key>"` 看 `Session` 字段 | 为空 = 锁确实已释放 |
| 定位 2 | 若为**空却仍抢不到** → 是 LockDelay 在起作用（设计如此，防脑裂） | 本机实测时间线：t=0/5/11 秒 False，t=17 秒 True |
| 修复 | 接受该延迟；若业务不能容忍 15 秒交接，换选主机制（etcd 租约 / K8s Lease） | — |
| 若无效 | `Session` **不为空**却抢不到 = 锁仍被他人持有，排查原持有者的会话与心跳 | — |

> **预防**：把"锁交接延迟 = 故障检测时间 + LockDelay"写进容量与 SLA 评估
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 3

## 🟡 症状 7：Connect 意图改了不生效

**一眼识别**：`GET /v1/connect/intentions` 返回 `[]`（意图已删），但 `POST /v1/agent/connect/authorize` 仍返回已删除的意图 ID；或新创建的意图长期不生效

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 若因幽灵 deny 导致业务被误拦：临时改为**创建 allow 意图**覆盖（注意：新建也可能不生效，取决于数据面） | 连接恢复（内置代理下不确定，见下） |
| 定位 1 | 对比两个视图：`GET /v1/connect/intentions`（集群真实状态）vs `POST /v1/agent/connect/authorize`（agent 授权视图） | 两者不一致 = agent 侧视图陈旧 |
| 定位 2 | 确认数据面：`consul connect proxy`（内置代理）还是 Envoy | **内置代理 = 命中本症状**（官方明确定位为仅测试用） |
| 修复 | 生产换用 Envoy 数据面（走 xDS 增量流）；内置代理仅用于本地功能验证 | 意图变更正常传播 |
| 若无效 | 内置代理下本机实测：意图删除后 11 分钟内持续匹配幽灵意图，**重启 sidecar 也不恢复** → 只能换数据面 | — |

> **预防**：不要用内置代理验证任何"意图行为"；功能验证与生产部署使用同一套数据面
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 7

## ⚪ 症状 8：KV 写入返回 413

**一眼识别**：`413 Request Entity Too Large`（本机实测写入约 600KB 值时返回）

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 停止写入，改用小值 | 写入成功 |
| 定位 1 | 确认值大小 | 超过官方 512KB 上限即会 413（本机实测 600KB 触发） |
| 修复 | 拆分到多个键，或改存对象存储的引用（KV 只放指针） | 写入成功 |
| 若无效 | → 转 `debug` | — |

> **预防**：把上限校验放在写入侧；KV 定位是配置与协调元数据，不是文件存储
> **原理**：→ [08-实战经验.md](08-实战经验.md)「适用边界」第 1 条

## 🟡 症状 9：跨 DC 查询返回 500

**一眼识别**：带 `?dc=<其他DC>` 的查询返回 HTTP 500；不带 `?dc=` 的本 DC 查询正常

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 把依赖跨 DC 查询的调用**切回本 DC**，或在本 DC 补一份数据 | 业务恢复（本 DC 读写始终可用） |
| 定位 1 | `curl "http://127.0.0.1:8500/v1/agent/members?wan=1"` | 目标 DC 成员是否 alive；**注意：WAN 状态翻转滞后于 RPC 失败**（本机实测：RPC 已 500，成员仍显示 alive） |
| 定位 2 | 本 DC 本地读写是否正常 | 正常 = 本 DC Raft 独立健康（远端失联不影响本地） |
| 修复 | 恢复目标 DC 的 server 或 DC 间网络；恢复后跨 DC 查询自动可用（本机实测：dc2 重启后查询立即恢复） | 跨 DC 查询返回数据 |
| 若无效 | → 转「症状 1」排查 agent 与 server 的连通性 | — |

> **预防**：不要设计"必须依赖跨 DC 查询"的关键链路——远端 DC 失联时它一定断（本机实测 9ms 内失败）
> **原理**：→ [08-实战经验.md](08-实战经验.md)「适用边界」第 2 条

## 🔴 症状 10：接口返回 200 但数据是空的（ACL 静默失败）

> **2026-09-17 新增**｜证据：**本机实测**（课 8 权限矩阵）
> ⚠️ **最容易被误诊的一条**——你以为"没数据"，实际是"没权限"。

**一眼看到的现象**

```text
查服务列表  → 200，返回 {} （空对象）
查 KV 键列表 → 200，返回 [] （空数组）
查单个 KV 键 → 403 （明确报错）
```

**为什么会这样**：Consul ACL 对"无权限"的响应**不一致**。列表类操作返回 **200 + 空结果**（因为"你无权看到任何一项"和"确实没有"在 API 层表达相同），而读单个键返回 403。

**30 秒判断法**

```bash
# 用管理 token 查同一接口，对比结果
consul catalog services -token=<管理token>

# 管理 token 能看到、业务 token 看到空 → 就是权限问题，不是数据问题
```

**止血**：给业务 token 补 `service:read` / `node:read` / `key_prefix:read` 权限。

**原理**：课 8 知识点 3「权限矩阵实测」。

> ⚠️ **特别注意**：如果这是**监控账号**，它会一直"正常返回空"，**你永远收不到告警**。监控 token 必须权限充足。

## 🟡 症状 11：快照恢复后，快照之后的数据全没了

> **2026-09-17 新增**｜证据：官方文档（`manage/disaster-recovery`）+ 课 11 验证 3 命令

**一眼看到的现象**：执行 `consul snapshot restore` 后，某些最近写入的 KV、最近注册的服务**不见了**。

**为什么会这样**：**恢复是"全量覆盖"而非"增量合并"**——它把集群状态**回滚到快照时刻**。快照之后的所有变更都会丢失。很多人误以为它是"把缺的补上"。

**30 秒确认**

```bash
# 恢复前先确认快照时刻
consul snapshot inspect backup.snap

# 恢复后对比：快照之后写入的数据应已丢失（这是预期行为，不是 bug）
consul kv get app/config/demo
```

**止血**：**已经发生的倒退无法用 Consul 自身撤销**。只能：
1. 若有更新的快照 → 恢复那一份
2. 若没有 → 从外部源（Git 配置仓库等）重新写入

**预防**（这才是重点）：
- ✅ **定期备份，并明确记录每个快照的时间点**
- ✅ **恢复前先 `snapshot inspect` 确认时刻**，评估会丢多少

## ⚪ 症状 12：K8s 上不同 namespace 的同名服务只有一个生效

## 🔴 症状 13：前缀递归读返回 404（无权限伪装成"空配置"）

> **2026-09-17 新增**｜证据：**本机实测**（实战篇 C，21 项权限矩阵）｜这是症状 10 的**递归读变体**，比它更隐蔽

**一眼识别**：读 KV 前缀 `GET /v1/kv/<prefix>?recurse=true` 返回 **404**，代码按"键不存在"处理 → 配置中心返回空配置 → 此后配置热更新**完全静默失效**，日志里没有任何错误。

**为什么会这样**：无权限时递归读返回的是 **404，不是 403**。而"前缀真的还没建"也是 404——两者在 API 层**无法区分**。于是 ACL 配置错误被伪装成了业务上的"空配置"。

**30 秒判断法**（关键：归因探针必须走**裸路径**）

```bash
# 1) 先按你原来的方式读（会拿到 404）
curl -o /dev/null -w "%{http_code}\n" \
  "http://127.0.0.1:8500/v1/kv/app/config?recurse=true" -H "X-Consul-Token: <业务token>"
# 404

# 2) 补一次裸路径单键读 —— 不带任何查询参数！
curl -o /dev/null -w "%{http_code}\n" \
  "http://127.0.0.1:8500/v1/kv/app/config/__probe__" -H "X-Consul-Token: <业务token>"
# 403 = 无权限（与键是否存在无关）
# 404 = 有权限，只是键不存在
```

> ⚠️ **探针别写错**：无权限时 `/v1/kv/x` 裸路径 → **403**；但 `/v1/kv/x?recurse=false` → **404**。
> 只要带了 query string，403 语义就丢了，探针会永远返回 404、归因逻辑形同虚设。**必须手工构造不带参数的请求**，不能复用 `kv_get()` 再传 `recurse=False`。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 给业务 token 补 `key_prefix "<prefix>" { policy = "read" }` | 递归读返回数据 |
| 定位 1 | 按上方 30 秒判断法做裸路径复核 | 403 = 确认是权限问题 |
| 定位 2 | 用管理 token 读同一前缀 | 能看到数据 = 数据没问题，纯权限问题 |
| 修复 | 客户端把 404 分支改成：先裸路径复核，拿到 403 就抛 `PermissionError`，**不要静默当成空配置** | 权限问题从"静默失效"变成"启动即报错" |
| 若无效 | → 转「症状 14」（确认 policy 里的资源名写法对不对） | — |

> **预防**：任何"把 404 当正常分支"的配置加载代码，都要追问一句"这个 404 会不会其实是 403"
> **原理**：实战篇 C · 权限矩阵实测；与「症状 10」同源（无权限响应不一致）

## 🟡 症状 14：policy / token 创建都返回 200，但调用仍 403

> **2026-09-17 新增**｜证据：**本机实测**（实战篇 C 权限矩阵）｜**配错了完全不告诉你**

**一眼识别**：创建 policy 返回 200、创建 token 返回 200，全程无报错、无警告；但某天用这个 token 调 `/v1/operator/raft/configuration` 才第一次发现 403。

**为什么会这样**：`operator` / `acl` / `keyring` / `mesh` / `peering` 这几类资源**不带 label**（没有子路径），必须写成**赋值形式**；写成 `_prefix` 形式时 Consul **不报错，直接忽略**。

```hcl
# ❌ 错：创建返回 200，但权限不生效
operator_prefix "" { policy = "read" }

# ✅ 对：不带 label 的资源用赋值形式
operator = "read"
```

对照——**带 label** 的资源必须用 `_prefix` 块（`key` / `node` / `service` / `session` / `agent` / `event` / `query`）：

```hcl
key_prefix "app/config" { policy = "read" }
service_prefix "web"    { policy = "write" }
```

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 把 `operator_prefix "" {}` 改成 `operator = "read"` 并更新 policy | 调用不再 403 |
| 定位 1 | 扫描规则文本，正则查 `\b(operator|acl|keyring|mesh|peering)_prefix\s` | 命中 = 确认写错 |
| 定位 2 | 用该 token 实际调用一次目标接口（不要只看创建返回 200） | 403 = 权限确实没生效 |
| 修复 | 改用赋值形式；并在代码里加 `validate_acl_rules()` 扫描函数，创建 policy 前拦截 | 错误写法在创建阶段就被拦下 |
| 若无效 | → 转「症状 13」/「症状 10」继续查权限链路 | — |

> **预防**：**判定权限是否生效必须实测调用一次**，不能只看配置接口返回 200——这是"配错了不告诉你"类故障的统一判据
> **原理**：实战篇 C · 权限矩阵实测

## 🟡 症状 15：应用刚启动时改 KV 完全没反应（空前缀 → 阻塞查询秒回）

> **2026-09-17 新增**｜证据：**本机实测**（综合实战项目第 4 步修复前后对比）｜**只在启动窗口出现，极易被当成偶发**

**一眼识别**：应用刚起来时改动 KV，配置**完全不更新**；跑一段时间后再改却正常。没有任何报错，"像偶发"。

**为什么会这样**：空前缀（还没写入过任何配置）拿不到起始 index → 阻塞查询**不带 `?index` 参数** → Consul 把这当成普通查询**立即返回**（实测 **2ms**，而不是挂起到 wait 超时）。

如果调用方只等**这一次**，这次机会 2ms 就用完了，之后写入的变更**再没人接收**——表现为"启动那段时间热更新完全失效"。空前缀是首次启动的**常态**，不是边界情况。

**30 秒判断法**

```bash
# 用空前缀发一次阻塞查询，看它是不是"秒回"
time curl "http://127.0.0.1:8500/v1/kv/app/config?recurse=true&wait=5s"
# 若耗时 ~0.002s 而非 ~5s → index 游标为 None，命中本症状
```

> **通用判据**：阻塞查询若**秒回**而不是挂起，先怀疑 `index` 游标是不是 None。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 重启应用（进入下一轮循环重试窗口），或先手动写入一个配置键让前缀非空 | 热更新恢复 |
| 定位 1 | 打印 `wait_update()` 的实际耗时 | 2ms 级 = 命中本症状 |
| 定位 2 | 确认前缀是否为空：`curl "http://127.0.0.1:8500/v1/kv/<prefix>?recurse=true"` | 404 = 空前缀 |
| 修复 | 调用方改成**循环重试**：`while time.time() < deadline: wait_update(wait="5s")`，而不是只调一次 | 修复后实测约 **1000ms** 检测到变更 |
| 若无效 | → 转「症状 4」（超时是否小于 wait）；→ 转「症状 5」（是否同值重写） | — |

> **已知限制（诚实记录）**：曾尝试用 `_fetch_current_index()` 从空前缀查询的响应头里取 `X-Consul-Index` 作为起始游标，**实测无效**——空前缀查询本身返回 404，而 404 响应头在客户端的 `_request()` 中被丢弃（`ConsulError` 只保留 status + body），拿不到值。该方案已**撤回**（未留着假装修好），正确解法是调用方循环重试。
> **预防**：阻塞查询一律包在循环里；不要假设"第一次 wait 一定在监听"
> **原理**：综合实战项目 `实现/main.py` 第 4 步 + `实现/config_center.py` 的 404 分支注释

## 🔴 症状 16：网关返回 404，但配置明明写好了

> **2026-09-21 新增**｜证据：**本机实测**（实战篇 E，Envoy 1.37.6 真实数据面）

**一眼识别**：`curl` 网关端口返回 **404**，响应头带 `server: envoy`；而 `consul config read -kind ingress-gateway` 能正常读到配置，网关进程也在跑。

**为什么会这样**：Consul 给网关生成的路由，**按 Host 头做域名匹配**——`virtual_hosts.domains` 是 `web.ingress.*`。不带 Host 头（或用 IP 当 Host）时，没有 virtual host 能匹配上，Envoy 直接回 404。

**这条的关键判据**（先看它，能省半小时）：

| 404 的响应头 | 含义 | 去向 |
|---|---|---|
| `server: envoy` | **网关活着**，是路由层没匹配上 | 留在本文（Host 头问题） |
| 连接被拒 / 无响应 | 网关进程根本没起 | → 转「症状 18」「症状 19」 |

**30 秒判断法**

```bash
# 1) 不带 Host —— 复现 404
curl -o /dev/null -w "%{http_code}\n" http://127.0.0.1:19180/
# 404

# 2) 带正确 Host —— 命中路由
curl -o /dev/null -w "%{http_code}\n" -H "Host: web.ingress.consul" http://127.0.0.1:19180/
# 200

# 3) 权威答案：看 Envoy 到底要求什么域名
curl -s http://127.0.0.1:19000/config_dump | grep -o '"domains":\[[^]]*\]' | head -3
# "domains":["web.ingress.*","web.ingress.*:19180"]
```

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 调用方补上 Host 头（值需匹配 `web.ingress.*`）；上游是 Nginx 时配 `proxy_set_header Host web.ingress.consul` | 立即 200 |
| 定位 1 | 看 404 响应头有没有 `server: envoy` | 有 = 网关活着，问题在路由匹配，别去查网关进程 |
| 定位 2 | 按上方第 3 步查 `domains` | 拿到 Envoy 实际接受的域名模式 |
| 修复 | 统一 Host 头；或在 ingress 配置里显式指定 `Hosts` 字段覆盖默认域名 | 请求命中路由 |
| 若无效 | 响应头无 `server: envoy` → 转「症状 18/19」查网关进程是否真的起来了 | — |

> **预防**：**验收网关不能只 `curl` 端口通不通**——不带 Host 的探测永远拿到 404，会让你误判成"网关坏了"。把 Host 头写进验收脚本和上游配置模板。

## 🔴 症状 17：网关 503，但 Consul 说服务 passing

> **2026-09-21 新增**｜证据：**本机实测**（实战篇 E）｜**两个视图互相矛盾，极易误诊**

**一眼识别**：经网关请求返回 **503**（路由命中了，后端不可达），但查健康接口显示服务 **passing**，实例数正常。

**为什么会这样**：**sidecar 代理进程已经没了，但服务注册还在**。Consul 的 health 视图反映的是"注册条目与健康检查"，**不反映 sidecar 进程是否存活**——注册条目不会因为代理进程退出而自动消失。

本机实测触发方式：用普通 `&` 后台启动 sidecar，脚本执行结束后进程被回收，端口随之消失，而 Consul 仍报 `passing`。

**30 秒判断法**（关键：两个视图都查，看它们是否打架）

```bash
# 1) Consul 视角 —— 说它很健康
curl -s "http://127.0.0.1:8500/v1/health/service/web-v1?passing" \
  | python3 -c "import sys,json;print(len(json.load(sys.stdin)),'个 passing 实例')"
# 1 个 passing 实例   ← 看起来完全正常

# 2) 但端口根本没人听
ss -tln | grep :21000
# 无输出              ← 真相在这里

# 3) 确认进程
pgrep -af "consul connect proxy"
# 无输出 = 代理进程已消失
```

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 重启 sidecar，并改用脱离会话的方式启动（见下） | 端口恢复监听 |
| 定位 1 | 同时查 health 视图与实际端口监听 | **passing 但端口无监听** = 确认命中本症状 |
| 定位 2 | `pgrep -af "consul connect proxy"` | 无输出 = 进程被回收（常见于脚本/终端退出） |
| 修复 | 用 `setsid nohup <cmd> > /tmp/x.log 2>&1 < /dev/null &` 启动，而不是裸 `&` | 进程不再随脚本退出被回收 |
| 若无效 | 端口在听但仍 503 → 检查 intention 是否拦截（→「症状 20」）；或查后端进程本身 | — |

> **预防**：**别把 Consul 的 passing 当成"代理在跑"**。需要对 sidecar 进程做独立的存活监控（进程级 + 端口级），两者都要有。
> **原理**：→ [实战E-北向网关与真实数据面](./practices/实战E-北向网关与真实数据面/README.md) · 场景 2「⚠️ 必须用 setsid」

## 🟡 症状 18：bootstrap 报 TLS/CA 错误（不是网络问题）

| 步骤 | 动作 | 预期 |

| **止血** | 导出 Consul 的 Connect CA 根证书，用 `-grpc-ca-file` 传给命令 | 见下方命令 |
| 定位 1 | 按上方第 1 步查 `Roots` 数量 | `0` = 先等 CA 初始化；`≥1` = 确认是缺 CA 参数 |
| 定位 2 | `nc -zv <ip> 8502` | 通 = **排除网络问题**，不要在防火墙上浪费时间 |
| 修复 | 见下方命令 | bootstrap 生成成功（本机实测 11838 字节） |

consul connect envoy -gateway=ingress -bootstrap -grpc-ca-file=/tmp/ca.pem > boot.json

## 🟡 症状 19：报 No ingress-gateway services registered（配置写了却说没有）

> **2026-09-21 新增**｜证据：**本机实测**（实战篇 E）｜**配置条目 ≠ 服务注册**

**一眼识别**：明明刚 `consul config write` 过 `ingress-gateway`，`consul config read` 也读得到，但 bootstrap 报 `No ingress-gateway services registered with this agent`。

**为什么会这样**：**config entry 不等于服务注册**。写 `ingress-gateway` 配置条目只是声明"应当有这样一个网关"；Consul 还要在 agent 上看到一个 `Kind` 为 `ingress-gateway` 的**服务实例**，才认为网关存在。两者缺一不可。

**30 秒判断法**

```bash
# 1) 配置条目存在（这说明不了什么）
consul config read -kind ingress-gateway -name ingress-gw
# 能读到

# 2) 关键：agent 上有没有带 Kind 的服务实例
curl -s http://127.0.0.1:8500/v1/agent/services \
  | python3 -c "import sys,json;d=json.load(sys.stdin);print([(k,v.get('Kind')) for k,v in d.items() if 'gw' in k])"
# [] 或 Kind 为 None = 命中本症状
```

**修复**（关键是 `Kind` 字段，漏了它 Consul 认不出这是网关）：

```bash
curl -s -X PUT http://127.0.0.1:8500/v1/agent/service/register -d '{
  "Name": "ingress-gw", "ID": "ingress-gw", "Port": 19180,
  "Kind": "ingress-gateway" }'
```

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 按上方命令注册，补齐 `Kind` 字段 | — |
| 定位 1 | 查 agent 服务列表里该服务的 `Kind` | 为空 = 注册时漏了 `Kind` |
| 定位 2 | 重新执行 bootstrap，**看报错有没有变** | 见下「诊断信号」 |
| 修复 | 带 `Kind` 重新注册 | 报错进展到下一阶段 |
| 若无效 | → 转「症状 18」 | — |

> 💡 **诊断信号（很有用）**：带 `Kind` 注册后，如果报错**从 `No ingress-gateway services registered` 变成了 TLS/CA 错误**，这**不是新问题，而是进展**——说明 Consul 已经认出它是网关，卡点前移了。**报错内容变化本身就是定位线索**，不要因为"又报错了"就回退刚才正确的改动。
> **预防**：把网关的配置条目与 agent 服务注册当成**一对**来管理，缺任何一个网关都不会工作。

## 🔴 症状 20：intention deny 写入 200，但流量一次都没拦住

> **2026-09-21 新增**｜证据：**本机实测**（实战篇 E）
> ⚠️ **安全类静默失效**——与「症状 10」「症状 14」同源：配置接口说成功，实际未生效。
> ⚠️ **根因尚未确认**，本条只陈述实测事实，不给出未经证实的结论。

**一眼识别**：`PUT /v1/config` 写 `service-intentions` 返回 **200**、ID 已生成，`GET /v1/connect/intentions` 也查得到这条 deny；但流量照常打到被 deny 的服务，一次都没被拒。

**为什么会这样（已确认的部分）**：Consul **接受并存储**了 intention，但没有把它翻译成 Envoy 的 RBAC **DENY 策略**。实测证据：

```bash
curl -s http://127.0.0.1:19000/config_dump | python3 -c "
import sys,json,re
s=json.dumps(json.load(sys.stdin))
print('RBAC 过滤器存在:', 'envoy.filters.network.rbac' in s)
print('含 DENY 策略   :', bool(re.search(r'\"policies\":\s*\{\s*\"[^\"]*\":\s*\{[^}]*\"permissions\":\s*\[\s*\{\s*\"action\":\s*\"DENY\"', s)))
"
# RBAC 过滤器存在: True
# 含 DENY 策略   : False      ← 规则没下发，所以拦不住
```

**实测数据**：配置 deny 后发 24 次请求，目标服务命中 **11 次，拦截 0 次**。

**30 秒判断法**

```bash
# 1) Consul 说配好了
curl -s http://127.0.0.1:8500/v1/connect/intentions
# 能看到 deny 条目

# 2) 但 Envoy 里没有 DENY 策略（按上方 python 片段查 config_dump）
# 含 DENY 策略: False  = 确认未下发

# 3) 决定性判据：实际发流量，看有没有被拒
#    被拦会有 403；一次都没出现 403 = 未生效
```

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | **不要依赖这条 deny 做安全边界**。需要立即阻断时，改用网络层手段（摘除服务实例 / 上游 Nginx 拒绝 / 安全组） | 流量被真正切断 |
| 定位 1 | 查 Consul intentions 清单 | 条目存在（这只证明"存进去了"） |
| 定位 2 | 按上方查 Envoy `config_dump` 有无 DENY 策略 | `False` = 规则未下发到数据面 |
| 定位 3 | 实际发请求统计拦截次数 | 0 次拦截 = 确认未生效 |
| 修复 | **暂无已验证的修复方案**（见下「未确认部分」） | — |

**未确认部分（诚实记录）**：
- **疑点**：网关转发时使用的身份可能不是 `ingress-gw`，导致 intention 的 `Source` 匹配不上，规则无从生成。
- **本轮未能证实**：曾尝试用 `openssl s_client` 抓证书来验证身份，但抓到的是 **sidecar 自己的服务端证书**（SAN 为目标服务自身），**拿不到网关的客户端身份**——**这个探测方法本身是错的**，不能据此下结论。需要抓网关侧证书或开 Envoy debug 日志才能定论。

> **预防**：与「症状 14」同一判据——**判定安全策略是否生效，必须实测一次流量**，不能只看配置接口返回 200。网关场景下的 intention 尤其要自己先验证。
> **原理**：→ [实战E-北向网关与真实数据面](./practices/实战E-北向网关与真实数据面/README.md) · 场景 3；与「症状 7」（内置代理下意图不生效）是不同数据面上的同类问题

## 🚑 通用止血动作（不确定是哪类问题时，先把损失停下）

| 场景 | 止血动作 | 代价 |
|------|----------|------|
| 刚变更 Consul 配置/版本就出问题 | 回滚配置或版本 | 丢失新特性 |
| 单个 agent 异常 | 摘除该 agent 上的服务（或用 maintenance 模式） | 该节点容量下线 |
| Consul 整体不可用 | 应用回落到本地快照/缓存（前提：已实现降级路径） | 配置不再是最新 |
| 集群状态彻底损坏 | 按官方灾难恢复流程从快照恢复 | 可能丢失快照之后的数据 |
