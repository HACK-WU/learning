# Consul 排障速查手册

> **怎么用**：出事了别从头读。按下面索引表找**症状**，翻到对应条目照做。
> **想懂为什么**：每个条目末尾有原理链接，事后再看 [08-实战经验.md](08-实战经验.md)。
> **查不到**：→ 转 `debug` skill 现场取证。
> 适用版本：Consul 2.0.2（本机实测环境）；命令以 HTTP API 与 CLI 为主，跨 1.x/2.x 通用。

## 🔎 症状倒查索引

| 一眼看到的现象 / 报错关键字 | 紧急度 | 翻到 |
|--------------------------|:------:|------|
| `No known Consul servers` / `No servers available` / `500` | 🔴 | **症状 1**：agent 找不到 server |
| 服务注册成功但很快消失 / 健康检查 critical | 🔴 | **症状 2**：服务注册后消失 |
| 日志反复 `New leader elected` / 写入间歇失败 | 🔴 | **症状 3**：leader 频繁切换 |
| 改了 KV 配置但应用不更新 / `TimeoutError: timed out` | 🟡 | **症状 4**：配置热更新不生效 |
| 写 KV 返回 200 但阻塞查询不返回 | 🟡 | **症状 5**：同值重写不触发更新 |
| 锁的 Session 已空但新候选抢不到（约 15 秒内） | 🟡 | **症状 6**：LockDelay 抢锁失败 |
| 意图已删但连接仍被拒 / 新意图不生效 | 🟡 | **症状 7**：意图视图不刷新 |
| `413 Request Entity Too Large` | ⚪ | **症状 8**：KV 值超限 |
| 跨 DC 查询 `?dc=` 返回 500 | 🟡 | **症状 9**：跨 DC 查询失败 |

**紧急度**：🔴 立即处理（业务已受损）｜ 🟡 尽快处理（有风险未爆发）｜ ⚪ 有时间再看（体验 / 优化）

## 🔴 症状 1：agent 找不到 server

**一眼识别**：`[ERR] agent: failed to sync remote state: No known Consul servers`；`[WARN] agent.router.manager: No servers available`；HTTP 返回 `500 No known Consul servers`

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 若 agent 仍能响应本地查询，先**不要重启**（重启会丢本地服务注册）；若已不可用，重启 agent 并带上正确的 `retry_join` | 本地服务暂时可查 / agent 重新入集群 |
| 定位 1 | `consul info \| grep known_servers` | `0` = 确认命中本症状；短暂抖动正常，**持续为 0** 才是故障 |
| 定位 2 | `nc -zv <server-ip> 8300` 与 `nc -zv <server-ip> 8301` | 8300（server RPC）与 8301（LAN gossip，TCP+UDP）都要通 |
| 定位 3 | `curl http://<server>:8500/v1/status/leader` | 返回空字符串 = server 侧自身丢失 leader，转「症状 3」 |
| 修复 | 更新 `retry_join` 指向当前有效的 server 地址后重启 agent（常见于 server 被 ASG/重建换了 IP） | `known_servers` 恢复非零，日志不再报错 |
| 若无效 | → 转「症状 3」（server 侧无 leader）；或转 `debug` 现场取证 | — |

> **预防**：把 8300 与 8301 当成一对来管理，防火墙策略改动时同时评审；对 `consul.client.rpc.failed` 持续非零告警（该指标只在 agent 侧产生，server 仪表盘看不到）
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 5

## 🔴 症状 2：服务注册后消失 / 健康检查 critical

**一眼识别**：注册返回 200，几秒到一分钟后服务从列表消失；`consul monitor` 有 deregister 相关日志；UI 中检查项标红

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 若设了 `DeregisterCriticalServiceAfter` 且实例还需保留排查，先移除该配置再重新注册 | 实例不再被自动销毁 |
| 定位 1 | `curl "http://127.0.0.1:8500/v1/agent/checks"` | 看到检查状态与输出；`critical` = 检查未通过 |
| 定位 2 | `curl "http://127.0.0.1:8500/v1/health/service/<name>"` | 空的 health 视图 = 无健康实例（**注意用 health 接口，不要用 catalog**） |
| 定位 3 | 若是 TTL 检查：确认应用的心跳线程是否在跑 | 本机实测：心跳停止后约 **8 秒**内实例从健康列表消失 |
| 修复 | 修正健康检查端点（返回 2xx）/ 恢复 TTL 心跳上报；TTL 心跳周期设为 TTL 的一半以下 | 检查转 `passing`，服务重新出现在 health 视图 |
| 若无效 | → 检查 ACL 是否拒绝了 `service:write`；或转 `debug` | — |

> **预防**：TTL 心跳周期 ≤ TTL/2；健康检查端点要能反映"能不能干活"而不只是"端口通不通"
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 4

## 🔴 症状 3：leader 频繁切换（选举震荡）

**一眼识别**：日志反复出现 `New leader elected`、`Election timeout reached, restarting election`；写入间歇性 500；Raft commit 延迟飙升

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 优先恢复**网络连通性**与**磁盘 I/O**——这两项是选举震荡最常见根因，先止血再深挖 | 选举停止震荡 |
| 定位 1 | `curl http://127.0.0.1:8500/v1/status/leader` | 空字符串 = 当前无 leader；地址频繁变化 = 正在震荡 |
| 定位 2 | `consul operator raft list-peers` | 看各节点状态与 `Voter` 标记 |
| 定位 3 | 查 server 的磁盘 I/O 与 Raft commit 延迟指标 | 磁盘慢是经典根因（Raft 每次 append 都 sync 到盘） |
| 修复 | 恢复网络/换更快的盘；跨 DC 或高延迟环境调大 `raft_multiplier` | leader 稳定，写入恢复正常 |
| 若无效 | → 转 `debug`；必要时按官方灾难恢复流程处理 | — |

> **预防**：server 用奇数（3/5/7）且放在稳定低延迟网段；监控 Raft 内部指标（leader 稳定性、commit 时间、snapshot 延迟），而不只是服务发现指标
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 6

## 🟡 症状 4：配置热更新不生效（客户端超时）

**一眼识别**：改了 KV 但应用读到的还是旧值；应用日志抛 `TimeoutError: timed out`；或配置"更新"的时间间隔恰好等于客户端超时值

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 重启应用强制重新全量拉取配置（临时恢复正确性，不解决根因） | 应用读到最新配置 |
| 定位 1 | 对比客户端 timeout 与阻塞查询的 `wait` 参数 | **timeout < wait** = 命中本症状 |
| 定位 2 | `curl -m 40 "http://127.0.0.1:8500/v1/kv/<prefix>?recurse=true&index=<idx>&wait=30s"` | 能正常返回 = 服务端无问题，问题在客户端配置 |
| 修复 | 把阻塞查询的超时设为 `wait + 15s` 以上（如 wait=30s → timeout=45s） | 变更后毫秒级返回（本机实测约 1 秒） |
| 若无效 | → 转「症状 5」（可能是同值重写） | — |

> **预防**：客户端库把"普通请求"与"阻塞查询"分成两套超时配置，并在代码注释写明原因
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 1

## 🟡 症状 5：写 KV 返回 200 但阻塞查询不返回

**一眼识别**：写入成功，所有 watch 该前缀的客户端都无反应，直到 wait 超时

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 若需立即生效，写入一个**不同的值**（如附加时间戳）强制推进 index | 阻塞查询立刻返回 |
| 定位 1 | 记录写入前的 index：`curl -D- "http://127.0.0.1:8500/v1/kv/demo?recurse=true"` 看响应头 `X-Consul-Index` | 拿到当前 index |
| 定位 2 | 写入后再查一次 index | **两次相同** = 同值重写未推进 index（本机实测：136 → 136） |
| 修复 | 需要触发更新时写入不同值；或在配置发布流程中用独立的"版本号键"推进 index | 阻塞查询正常唤醒 |
| 若无效 | → 转「症状 4」（确认客户端超时够大） | — |

> **预防**：理解"值相同 = 无变更"是 Consul 的语义；需要"强制推送"的场景（如回滚到历史值）用版本号键驱动
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 2

## 🟡 症状 6：锁已释放但新候选抢不到

**一眼识别**：查锁键的 `Session` 字段已为空（确认释放），但新候选 `acquire` 持续返回 `false`；约 15 秒后突然成功

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | **不需要止血**——这是预期行为。若业务允许等待，静待 LockDelay 结束即可 | 约 15 秒后自动抢到 |
| 定位 1 | `curl "http://127.0.0.1:8500/v1/kv/<lock-key>"` 看 `Session` 字段 | 为空 = 锁确实已释放 |
| 定位 2 | 若为**空却仍抢不到** → 是 LockDelay 在起作用（设计如此，防脑裂） | 本机实测时间线：t=0/5/11 秒 False，t=17 秒 True |
| 修复 | 接受该延迟；若业务不能容忍 15 秒交接，换选主机制（etcd 租约 / K8s Lease） | — |
| 若无效 | `Session` **不为空**却抢不到 = 锁仍被他人持有，排查原持有者的会话与心跳 | — |

> **预防**：把"锁交接延迟 = 故障检测时间 + LockDelay"写进容量与 SLA 评估
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 3

## 🟡 症状 7：Connect 意图改了不生效

**一眼识别**：`GET /v1/connect/intentions` 返回 `[]`（意图已删），但 `POST /v1/agent/connect/authorize` 仍返回已删除的意图 ID；或新创建的意图长期不生效

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 若因幽灵 deny 导致业务被误拦：临时改为**创建 allow 意图**覆盖（注意：新建也可能不生效，取决于数据面） | 连接恢复（内置代理下不确定，见下） |
| 定位 1 | 对比两个视图：`GET /v1/connect/intentions`（集群真实状态）vs `POST /v1/agent/connect/authorize`（agent 授权视图） | 两者不一致 = agent 侧视图陈旧 |
| 定位 2 | 确认数据面：`consul connect proxy`（内置代理）还是 Envoy | **内置代理 = 命中本症状**（官方明确定位为仅测试用） |
| 修复 | 生产换用 Envoy 数据面（走 xDS 增量流）；内置代理仅用于本地功能验证 | 意图变更正常传播 |
| 若无效 | 内置代理下本机实测：意图删除后 11 分钟内持续匹配幽灵意图，**重启 sidecar 也不恢复** → 只能换数据面 | — |

> **预防**：不要用内置代理验证任何"意图行为"；功能验证与生产部署使用同一套数据面
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 7

## ⚪ 症状 8：KV 写入返回 413

**一眼识别**：`413 Request Entity Too Large`（本机实测写入约 600KB 值时返回）

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 停止写入，改用小值 | 写入成功 |
| 定位 1 | 确认值大小 | 超过官方 512KB 上限即会 413（本机实测 600KB 触发） |
| 修复 | 拆分到多个键，或改存对象存储的引用（KV 只放指针） | 写入成功 |
| 若无效 | → 转 `debug` | — |

> **预防**：把上限校验放在写入侧；KV 定位是配置与协调元数据，不是文件存储
> **原理**：→ [08-实战经验.md](08-实战经验.md)「适用边界」第 1 条

## 🟡 症状 9：跨 DC 查询返回 500

**一眼识别**：带 `?dc=<其他DC>` 的查询返回 HTTP 500；不带 `?dc=` 的本 DC 查询正常

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 把依赖跨 DC 查询的调用**切回本 DC**，或在本 DC 补一份数据 | 业务恢复（本 DC 读写始终可用） |
| 定位 1 | `curl "http://127.0.0.1:8500/v1/agent/members?wan=1"` | 目标 DC 成员是否 alive；**注意：WAN 状态翻转滞后于 RPC 失败**（本机实测：RPC 已 500，成员仍显示 alive） |
| 定位 2 | 本 DC 本地读写是否正常 | 正常 = 本 DC Raft 独立健康（远端失联不影响本地） |
| 修复 | 恢复目标 DC 的 server 或 DC 间网络；恢复后跨 DC 查询自动可用（本机实测：dc2 重启后查询立即恢复） | 跨 DC 查询返回数据 |
| 若无效 | → 转「症状 1」排查 agent 与 server 的连通性 | — |

> **预防**：不要设计"必须依赖跨 DC 查询"的关键链路——远端 DC 失联时它一定断（本机实测 9ms 内失败）
> **原理**：→ [08-实战经验.md](08-实战经验.md)「适用边界」第 2 条

## 🚑 通用止血动作（不确定是哪类问题时，先把损失停下）

| 场景 | 止血动作 | 代价 |
|------|----------|------|
| 刚变更 Consul 配置/版本就出问题 | 回滚配置或版本 | 丢失新特性 |
| 单个 agent 异常 | 摘除该 agent 上的服务（或用 maintenance 模式） | 该节点容量下线 |
| Consul 整体不可用 | 应用回落到本地快照/缓存（前提：已实现降级路径） | 配置不再是最新 |
| 集群状态彻底损坏 | 按官方灾难恢复流程从快照恢复 | 可能丢失快照之后的数据 |
