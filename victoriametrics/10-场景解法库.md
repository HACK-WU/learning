## 场景 1：加了一个标签，序列数从 800 涨到 80 万

**场景描述**：线上服务为了「能按用户排查问题」，给请求计数指标加了 `user_id` 标签。上线后内存持续上涨，抓取耗时从 200ms 涨到 3s，任何面板都要等十几秒。基数审计显示序列数从几百条涨到几十万条。

> 📐 **数字怎么来的（推演，非实测）**：请求计数指标的序列数 = `method × path × status` 的组合数（本仓库 promql 课程实测 27 条），乘以 1 万活跃用户 ≈ **27 万条**。基数爆炸的公式永远是 `序列数 × 新标签取值数`。

**🔒 先自己想 30 秒**：第一反应是加内存？加机器？还是删数据？如果让你来救火，**第一步**做什么？

<details><summary>💡 提示（分四层想）</summary>

- **数据模型层**：这个标签**真的该加**吗？取值有多少？会不会无限增长？
- **采集层**：能不能在**进存储之前**就把它拦下来？注意 relabel 有两个作用段
- **存储/查询层**：保留细粒度但缩短保留期？还是预聚合成少量序列长期保存？
- **护栏层**：下次有人再加一个高基数标签，怎么提前发现？

</details>

<details><summary>📖 展开解法</summary>

### 解法一览（5 个，含代价与边界）

| 解法 | 能解决到 | 代价 | 适用边界 |
|------|---------|------|---------|
| **A · 标签降维**：不加 `user_id`，改用有限取值维度（`user_tier=gold/silver`、`region`），用户级明细交给日志/链路追踪 | 治本，序列数不增长 | 失去「按单个用户下钻」；需与日志系统打通才有替代 | 只要「分群看」就够的场景（绝大多数） |
| **B · 采集侧拦截**：`metric_relabel_configs` + `labeldrop` 丢弃高基数标签；或 hash 分桶把值收敛到有限集合 | 不用改代码，当天生效 | 需维护 relabel 规则；信息有损；**写错配置段会静默失效** | 埋点已上线、来不及发版的救火场景 |
| **C · 预聚合 + 分层保留**：细粒度序列短保留（如 2 天），用 recording rules 预聚合成服务级序列长期保留 | 保留近期明细，长期成本可控 | 失去历史明细；多一层规则要维护 | 既要看近期明细、又要看长期趋势 |
| **D · 扩容 / 上集群**：拆服务 + 多个实例，或上 VictoriaMetrics 集群横向扩展 | 扛住更高基数 | 运维复杂度显著上升；**基数本身没减少，只是分散了** | 基数**确实**业务必要（已确认合理性） |
| **E · 元告警（护栏）**：对「序列数增长率」设告警，配 `topk` 做基数审计 | 不解决问题，但能**在下一次上线时被打回** | 需定期维护阈值 | 任何规模都必须配（它不是解法，是保险丝） |

### 推荐路径（递进，不是一次全上）

1. **先上 E**（当天）：没有护栏，任何治理都会被下一次上线打回。至少配一条「序列数 1 小时涨 50%」的告警。
2. **紧急止血用 B**（当天）：先降内存水位。**注意配置段**——见下方代码块。
3. **治本用 A**（下一个发版窗口）：把用户级维度挪到日志/追踪，指标只保留分群维度。
4. **仍要看近期明细才上 C**（一周内）：细粒度短保留 + 服务级预聚合长保留。
5. **最后才考虑 D**：先证明「这个基数业务上真的必要」，再谈扩容。否则只是用钱买时间。

```yaml
# B 的正确写法 —— 注意是 metric_relabel_configs，不是 relabel_configs
scrape_configs:
  - job_name: demo
    metric_relabel_configs:          # ← 写错成 relabel_configs 会静默失效
      - action: labeldrop
        regex: (user_id|session_id)  # ← regex 需写成分组形式
```

```promql
# E 的写法：基数审计三连（本仓库 promql 课程实测基线 837 条序列）
count({__name__=~"demo.+"})                          # 总量
topk(5, count by (__name__) ({__name__=~"demo.+"}))  # 谁最占地方
count by (path, method, status) (demo_api_request_duration_seconds_count)  # 单指标标签构成
```

### 知识点挂钩

- 基数三层治理（写入前根治 / 查询时治标 / 限流兜底）→ **课 4**
- `relabel_configs` vs `metric_relabel_configs` 的作用点差异 → **课 4**（实战项目实测序列数 1 vs 50）
- 高基数是空间与查询耗时的共同主变量（序列翻一倍耗时涨 3.5 倍）→ **课 7**
- 索引比数据还占地方（`items.bin` 806 KB > `values.bin` 285 KB）→ **课 5**

### 什么情况下此方案不适用

- **真的需要按用户维度做分析**（如「某 VIP 用户的所有请求耗时分布」）——VM **不是**正确的工具，指标天生是聚合视角。这类需求应交给 VictoriaLogs / ELK 或数仓。
- **基数来自不可避免的维度增长**（如每个租户一条序列，而租户在增长）——这时 B/C 都只是拖延，应直接评估 D。

### 做错会踩的坑

→ [08-实战经验.md](08-实战经验.md) · **故障模式 2**（`labeldrop` 写了却不生效）：本场景最常见的失败不是选错解法，而是 B 写在了错误的配置段，静默失效。
→ 反直觉点：**`sum` 聚合救不了已经爆掉的基数**——聚合只减少返回行数，服务端照样要把几十万条序列读进来。

</details>

## 场景 2：单机快到天花板了，要不要上集群

**场景描述**：单机 VM 已经装了 800 万活跃序列，内存占用接近 19 GB（本机 31.8 GB 的 60% 水位），磁盘 82%。团队在犹豫：是继续加内存，还是拆成集群？

> 📐 实测基准（本机）：`-memory.allowedPercent` 默认 **60%**，31.8 GB → VM 额度 **19.1 GB**；官方经验值 **1GB / 百万序列**；单节点建议上限约 **1000 万**活跃序列。

**🔒 先自己想 30 秒**：上集群之前，有没有更便宜的选项？如果上了集群，哪些事情会变复杂？

<details><summary>💡 提示（分三层想）</summary>

- **能不能先减**：基数能不能降下来？降 30% 的基数和加 50% 的内存，哪个便宜？
- **上集群的隐性成本**：运维组件从 1 个变 3 类；扩容**不迁移旧数据**；调试路径变长
- **有没有中间态**：能不能按业务拆成多个单机实例 + vmauth 路由？

</details>

<details><summary>📖 展开解法</summary>

### 解法一览（4 个，含代价与边界）

| 解法 | 能解决到 | 代价 | 适用边界 |
|------|---------|------|---------|
| **A · 垂直扩容 + 降基数**：加内存到 64 GB，同时用 relabel / 流式聚合降基数 | 最省事，架构不变 | 有物理上限（单机约 1000 万序列）；**加内存还会拉长重启恢复时间** | 序列数 < 1000 万且增长平缓 |
| **B · 按业务拆分多单机实例**：不同业务线各自一个单机 VM，前面 vmauth 路由 | 架构简单，故障域隔离，各业务互不影响 | 失去全局视图（跨业务查询要自己拼）；实例数量多了运维也烦 | 业务线边界清晰、不需要全局聚合查询 |
| **C · 上集群（三件套）**：vminsert / vmselect / vmstorage | 真正水平扩展，支持多租户 | **运维复杂度显著上升**；扩容**不迁移旧数据**（需重启 vminsert/vmselect）；无副本时节点故障会**静默少数据** | 序列数 > 1000 万，或需要多租户 |
| **D · 分层：近期热数据单机 + 历史长期存储** | 降低单机压力又不引入集群复杂度 | 需要维护两套存储与查询路由 | 查询负载明显集中在近期数据 |

### 推荐路径（递进）

1. **先做 A 的一半——降基数**（零成本）：在决定花钱之前先确认「这 800 万序列都是必要的吗」。课 5 的实测结论是**索引比数据还占地方**，减序列数是收益最大的动作。
2. **仍不够 → 评估 B**（架构简单优先）：如果业务线边界清晰、不需要全局查询，**多单机 + vmauth 比集群划算得多**。
3. **确认需要水平扩展或多租户 → C**：上集群时**从一开始就配 RF=2**（别等出事再补），并接受「扩容不迁移旧数据」这个约束。
4. **D 作为特殊形态**：只在查询负载明显冷热分明时考虑。

```bash
# 上集群前必做的容量核算（本机实测参数）
# 1. 内存额度 = 总内存 × allowedPercent(默认 60%)
# 2. 官方经验值：1GB / 百万活跃序列
# 3. 查当前真实序列数（注意：hour_metric_ids 有 15 秒延迟，要用 tsdb 端点）
curl -s 'http://localhost:8428/api/v1/status/tsdb' | python3 -c "import sys,json;d=json.load(sys.stdin)['data'];print(d['totalSeries'])"
```

### 知识点挂钩

- 内存水位规则与虚拟/物理内存的区别 → **课 7**
- 集群三件套分工与 shared-nothing 架构 → **课 8**
- 扩容不迁移旧数据、无副本静默降级 → **课 8**（实测 1000 → 509）
- 复制因子代价与最小推荐配置 → **课 9**

### 什么情况下此方案不适用

- **增长来自基数失控而非业务增长**：这时上集群只是把问题分散，降基数才是正解。
- **团队没有运维分布式系统的能力**：三件套 + 复制 + vmauth 的运维成本是实打实的，B 方案（多单机）对小团队更友好。

### 做错会踩的坑

→ [08-实战经验.md](08-实战经验.md) · **故障模式 6**（无副本节点故障静默降级）：上集群后如果只配一个 vmstorage 或忘了 RF=2，故障时会**静默少数据**且查询不报错——比单机宕机更难发现。

</details>

## 场景 3：五个团队要共用一套监控，怎么隔离

**场景描述**：公司有 5 个业务团队，都想把指标存到一个 VM 集群里。要求是「各看各的，互不干扰」。你负责设计这套方案。

> 📐 实测基准（课 10）：租户 ID 边界 `2^32-1` 可用、`2^32` 报 400、**空 ID 静默进 tenant 0**；数据隔离 ✅ 但资源隔离 ❌（大租户让他人查询慢 **7.4 倍**）。

**🔒 先自己想 30 秒**：「各看各的」这句话，其实包含了几个不同层次的要求？全都满足吗？

<details><summary>💡 提示（分四层想）</summary>

- **数据隔离**：A 团队能不能看到 B 团队的数据？（这个是硬边界）
- **资源隔离**：A 团队跑一个超大查询，会不会拖慢 B 团队？（这个社区版做不到）
- **认证授权**：谁来决定「你是 A 团队的」？客户端能不能自己选？
- **故障域**：一个团队把集群搞垮了，其他团队陪葬吗？

</details>

<details><summary>📖 展开解法</summary>

### 解法一览（4 个，含代价与边界）

| 解法 | 能解决到 | 代价 | 适用边界 |
|------|---------|------|---------|
| **A · vmauth 静态绑定租户**：每个团队一个 Basic Auth 账号，租户号**写死在服务端**，`src_paths` 控读写 | 数据隔离 ✅ + 认证 ✅ + 读写分离 ✅ | 客户端无法自选租户（这是**特性**不是限制）；路径拼接要自己拼对（连踩两次 400） | 团队数量固定、租户关系稳定（最常见） |
| **B · 每团队独立 vmagent + 独立 vmalert**：采集与告警也按租户拆开 | 故障域隔离 ✅ + 告警不再双向失效 | 组件数量 × 团队数；运维成本上升 | 租户数量不多（≤10），且告警必须准确 |
| **C · 前置治理（采集端降基数）**：在 vmagent 用 relabel 卡住每个租户的基数上限 | 缓解坏邻居（社区版唯一可行的资源治理） | 只能缓解，不是硬配额；靠配置纪律维持 | 社区版下**必须做**，否则坏邻居无解 |
| **D · 超大租户拆独立集群** | 彻底隔离故障域与资源 | 运维 N 套集群；失去统一视图 | 某个租户的量级远超其他所有租户 |

### 推荐路径（递进）

1. **先上 A**（基础，不可省）：vmauth 是唯一能在社区版提供**认证 + 租户绑定 + 读写分离**的组件。注意三点——① **务必处理空租户 ID**（不设防会静默进 tenant 0）；② 路径拼接规则 `url_prefix + 原始路径`；③ **不要配 `unauthorized_user`**（会把 401 变成 200+空结果，带偏排查）。
2. **紧接着上 C**（社区版必做）：既然社区版没有硬配额，坏邻居只能靠**源头治理**。在 vmagent 给每个租户配 relabel 卡基数。
3. **告警必须上 B**：多租户场景下**每租户一个独立 vmalert**。否则会出现「假告警恒真 + 真告警永不响」的双向失效——这是实战项目里最危险的一个坑。
4. **D 只在量级失衡时考虑**：某个租户吃掉大部分资源时，拆出去比在集群内治理更划算。

```yaml
# A 的正确写法（注意 url_prefix 必须带协议段）
users:
  - username: "team-a"
    password: "xxx"
    url_map:
      - src_paths: ["/api/v1/write", "/api/v1/import.*"]
        url_prefix: "http://vminsert:8480/insert/100/prometheus"   # ← 漏了 prometheus 段会 400
      - src_paths: ["/api/v1/query.*", "/api/v1/export.*"]
        url_prefix: "http://vmselect:8481/select/100/prometheus"
```

### 知识点挂钩

- 租户模型（`accountID[:projectID]`、projectID 是平级标识）→ **课 8 / 课 10**
- vmauth 认证与路由、路径拼接坑 → **课 10**
- 数据隔离 ✅ / 资源隔离 ❌ 的实测边界 → **课 10**（慢 7.4 倍）
- 多租户告警必须独立 vmalert → **实战项目**（双向失效）

### 什么情况下此方案不适用

- **需要硬性资源配额**（每租户序列数上限、查询内存上限）——社区版**做不到**，这是企业版功能（`-tenant.*` 系列参数，核查于 2026-09）。要么上企业版，要么走 D 拆集群。
- **租户数量非常多且动态增减**（如 SaaS 给 100 个客户）——vmauth 静态绑定的运维成本会失控，应评估企业版或 D。

### 做错会踩的坑

→ [08-实战经验.md](08-实战经验.md) · **故障模式 3**（单 vmalert 服务多租户）：这是本场景**最容易踩且后果最严重**的坑——不是「泄露」，而是**告警系统整体失真**。
→ [09-排障速查手册.md](09-排障速查手册.md) · **症状 6**（`count()` 掉一半）：多租户叠加无副本时，故障表现会更加隐蔽。

</details>

## 场景 4：数据要保留一年，磁盘扛不住

**场景描述**：合规要求指标保留 1 年。按当前 15 秒采集间隔、500 万序列计算，一年大约需要 **17.5 万亿个样本**。按每样本 2~4 字节估算，磁盘需求依然惊人。老板不同意加盘，怎么办？

> 📐 数字推算：500 万序列 × (365×24×3600/15) = 500 万 × 2,102,400 ≈ **1.05 × 10^13** 样本/序列合计。实际总量取决于序列数，量级足以压垮常规单机。

**🔒 先自己想 30 秒**：保留一年是硬要求，但「每个数据点都保留原始精度」也是硬要求吗？这两个要求是一回事吗？

<details><summary>💡 提示（分三层想）</summary>

- **精度换时间**：一年前的 15 秒精度，真的有人看吗？老数据能不能降到 5 分钟精度？
- **分层保留**：核心指标保留长、调试指标保留短，能不能分开？
- **预聚合**：历史趋势看聚合值就够，原始明细只保留近期——这个思路可行吗？

</details>

<details><summary>📖 展开解法</summary>

### 解法一览（4 个，含代价与边界）

| 解法 | 能解决到 | 代价 | 适用边界 |
|------|---------|------|---------|
| **A · 降采样**（企业版 `-downsampling.period=30d:5m`） | 官方支持的多级降采样，查询自动适配 | **企业版功能**；降采样不减少序列数，对高 churn 场景无效 | 需要长期保留 + 能接受付费（核查于 2026-09） |
| **B · 多保留期**（企业版 `-retentionFilter`） | 按标签给不同数据集设不同保留期（如 `{env="dev"}:7d`） | **企业版功能** | 数据重要性差异明显 |
| **C · 社区版自建分层**：原实例短期保留（如 14 天）+ recording rules 预聚合成服务级指标写入第二个长保留实例（1 年） | **社区版可行**，成本可控 | 需自己维护两套实例与规则；失去历史明细 | 历史只需看趋势、不需看明细 |
| **D · 缩短保留期 + 提升压缩**：砍到 3 个月，同时治理基数与数据形态 | 零成本 | **不满足合规要求**，只在合规可谈判时才成立 | 合规要求可调整 |

### 推荐路径（递进）

1. **先算清楚真实需求**：一年前的数据，谁在看？看什么粒度？**如果答案是「看趋势」，C 就够了，不必买企业版。**
2. **社区版走 C**：原实例 14 天保留 + vmalert recording rules 预聚合（`sum by`、`avg by`）写入长保留实例。**注意预聚合要用 recording rules，不是查询时聚合**——后者不减少存储。
3. **确认必须保留明细 → 评估 A**：企业版降采样是唯一官方支持的「保留长期 + 省空间」方案（核查于 2026-09）。评估前先确认预算。
4. **D 作为谈判筹码**：把「保留 1 年原始精度」的真实成本摆给合规方看，很多时候 3 个月足够。

```yaml
# C 的写法示例：vmalert recording rules 做预聚合降维
groups:
  - name: long-term-rollup
    interval: 5m
    rules:
      # 把 path 维度聚合掉，只保留服务级指标（序列数大幅下降）
      - record: service:http_requests:rate5m
        expr: sum by (service, status) (rate(http_requests_total[5m]))
      - record: service:http_request_duration:p95_5m
        expr: histogram_quantile(0.95, sum by (service, le) (rate(http_request_duration_seconds_bucket[5m])))
```

### 知识点挂钩

- 每样本字节与三层压缩（列式 → 值编码 → ZSTD 5.58 倍）→ **课 6**
- 降采样与多保留期（企业版边界）→ **课 6**（课中已标注这是企业版功能）
- recording rules 与预聚合 → **课 11**
- 基数才是空间主变量（索引比数据大）→ **课 5**

### 什么情况下此方案不适用

- **合规要求必须保留原始明细且可回溯**：C 会丢失历史明细，只能靠 A（企业版）。
- **高 churn 场景**（序列频繁生灭，如 K8s Pod 指标）：官方明确指出**降采样不减少序列数**，对这类场景无效（核查于 2026-09）。这时正解是 recording rules 减少序列数，而不是降采样。

### 做错会踩的坑

→ [08-实战经验.md](08-实战经验.md) · 反模式 **第 8 条**（用平均值法做容量规划）：估算磁盘时若用实测的平均值（6234.7 字节/序列）而非边际成本（65.5 字节/序列），会得出荒谬的结论，**差 95 倍**（课 7 实测）。

</details>

## 场景 5：节点挂了，数据会不会丢

**场景描述**：VM 集群跑了 3 个 vmstorage。某个节点宕机 2 小时。运维问你：这 2 小时的数据丢了吗？恢复后能自动补上吗？需不需要人工介入？

> 📐 实测基准（课 9）：RF=2 配 dedup 后查询保持 **300 不变**；**副本缺口不自动补齐**（故障期 100 条，恢复后仍 100 / 0）；副本失败的唯一可靠证据是 vminsert 日志 `cannot make a copy`。

**🔒 先自己想 30 秒**：「配了复制因子」和「数据不会丢」是一回事吗？恢复之后呢？

<details><summary>💡 提示（分三层想）</summary>

- **写入期**：RF=2 时一个节点挂了，写入还会成功吗？数据写到哪了？
- **恢复后**：缺的副本会不会自动补上？如果不补，怎么发现、怎么修？
- **检测**：你靠什么知道「刚才有副本失败了」？有没有能观测的信号？

</details>

<details><summary>📖 展开解法</summary>

### 解法一览（4 个，含代价与边界）

| 解法 | 能解决到 | 代价 | 适用边界 |
|------|---------|------|---------|
| **A · RF=2 + dedup（最小高可用）** | 单节点故障时**查询不受影响**；数据不丢 | 存储成本翻倍；**必须配 dedup** 否则查询翻倍；RF>1 时**禁用慢节点重路由** | 绝大多数生产场景的基线 |
| **B · 3 节点配 RF=2（推荐最小配置）** | 故障期写入**仍是双副本**（2 节点配 RF=2 时会退化成单副本） | 多一个节点的成本 | **生产推荐**，比 A 更稳 |
| **C · 副本缺口人工修复**：用 `/api/v1/export` 导出故障期数据重新写入 | 补齐缺口 | 人工操作；会重写数据；需要知道故障窗口 | 故障已发生且数据重要时 |
| **D · 前置 vmagent 持久化队列** | 后端整体不可用时**零丢失**（实测停机 150 秒零丢弃） | 只保护「后端不可达」，**不保护 vmagent 自身崩溃**（前 60 秒在内存） | 采集端到存储的链路保护 |

### 推荐路径（递进）

1. **基线必上 B**：**3 个 vmstorage 配 RF=2**。这不是「高级配置」而是生产底线——2 节点配 RF=2 时，故障期写入的数据实际是单副本。
2. **必须监控副本失败**：查 vminsert 日志 `cannot make a copy`。⚠️ **指标 `vm_rpc_rows_incompletely_replicated_total` 实测在 5 次失败后仍为 0，不可靠**（课 9 实测），别只信它。
3. **D 作为链路保护**：vmagent 的持久化队列能扛后端整体不可用，但**不保护 vmagent 自己崩溃**（前 60 秒在内存缓冲）。
4. **C 作为事后补救**：知道副本有缺口时，用 export 导出故障窗口的数据重新写入，会重新走复制流程。

```bash
# 1. 确认副本是否真的在起作用（给每个节点单独接 vmselect 验证）
# 2. 副本失败的唯一可靠证据
docker logs vminsert 2>&1 | grep -i "cannot make a copy"
# 3. 缺口修复：导出故障窗口数据重灌
curl 'http://vmselect:8481/select/0/prometheus/api/v1/export' \
  --data-urlencode 'match[]={__name__=~".+"}' \
  --data-urlencode 'start=<故障开始>' --data-urlencode 'end=<故障结束>' > recovery.jsonl
```

### 知识点挂钩

- 复制因子与 dedup 的配套关系 → **课 9**（实测无 dedup 600 / 有 dedup 300）
- 副本缺口不补齐（本课最重要警告）→ **课 9**
- 静默降级（无副本时 1000 → 509 不报错）→ **课 8**
- vmagent 持久化队列的能力与边界 → **课 11**（150 秒零丢弃 / 前 60 秒在内存）

### 什么情况下此方案不适用

- **需要强一致、自动补副本**：VM 的复制是**写入时尽力而为**，不用 Raft 这类共识协议（课 9）。这是设计取舍（换取低资源占用与运维简单），不是缺陷。若业务无法接受，需要重新评估选型。
- **故障时间极长且无监控**：副本缺口会持续累积且无人知晓。**监控副本失败是这套方案成立的前提**。

### 做错会踩的坑

→ [08-实战经验.md](08-实战经验.md) · **故障模式 6**（静默降级）与 **故障模式 7**（dedup 误删）：这两条是同一个配置域的两个极端——**忘了配副本**会静默少数据，**dedup 设太大**会误删数据。

</details>

## 场景 6：要从 Prometheus 迁过来（或 VM 之间迁移）

**场景描述**：现有一套 Prometheus 存了 2 年数据、约 1000 万序列。要迁到 VictoriaMetrics。业务方要求「尽量不停机，不要丢数据」。

> 📐 实测基准（课 12）：vmctl remote-read 迁移 **1058 万样本 / 195.4 MB / 5.76 秒**；样本层面**幂等**（同窗口重跑样本数完全一致 10,580,035）；VM 间跨租户迁移 240 序列 / 30 ms。

**🔒 先自己想 30 秒**：「迁移」这个词下面其实藏着三件不同的事——历史数据、实时链路、查询入口。它们能同时切吗？

<details><summary>💡 提示（分三层想）</summary>

- **历史数据**：2 年的老数据怎么搬？搬的过程中服务要不要停？
- **实时链路**：什么时候开始双写？双写期间查哪边？
- **查询入口**：Grafana 数据源什么时候切？切错了能回滚吗？

</details>

<details><summary>📖 展开解法</summary>

### 解法一览（4 个，含代价与边界）

| 解法 | 能解决到 | 代价 | 适用边界 |
|------|---------|------|---------|
| **A · 三阶段渐进（推荐）**：① Prometheus 加 `remote_write` 双写 → ② 查询切到 VM（Grafana 加数据源）→ ③ vmagent 接管抓取，Prometheus 退场 | **全程不停机**，随时可回滚 | 需要跑一段时间双写；PromQL 与面板不用改 | 绝大多数场景（课 1 已给出这条路径） |
| **B · vmctl 一次性迁移**：`remote-read`（源存活）/ `prometheus`（停机窗口）/ `vm-native`（VM 间） | 快速搬完历史数据 | 源端需要能承受读取压力；参数有三个坑（见下） | 有明确停机窗口，或源端可承受读取 |
| **C · 只切增量，不要历史**：不迁历史数据，新旧系统并行到老数据自然过期 | 最省事，风险最低 | 一段时间内要查两个地方 | 历史数据价值低，或保留期短 |
| **D · 原地切换**：直接把 Prometheus 换成 VM，重新采集 | 最快 | **丢失全部历史数据** | 只在历史数据完全无价值时 |

### 推荐路径（递进）

1. **先走 A 的第 ① 步**（零风险）：Prometheus 加一行 `remote_write`，数据开始双写。**这一步不改任何查询，可随时撤销。**
2. **历史数据用 B 补**：在双写期间用 `vmctl remote-read` 搬历史。实测 1058 万样本只要 5.76 秒且**幂等**，中断可安全重跑。
3. **验证后再切查询（A 的第 ② 步）**：在 Grafana 加 VM 数据源，逐面板对比。**注意 MetricsQL 与 PromQL 有六类有意差异**（窗口前采样点、不外推等），迁移后**必须重新校准告警阈值**，尤其是用 `increase` 的规则。
4. **最后才让 vmagent 接管抓取（A 的第 ③ 步）**。

```bash
# vmctl remote-read 迁移（三个参数坑已规避）
vmctl remote-read \
  --remote-read-src-addr=http://prometheus:9090 \
  --remote-read-step-interval=hour \        # ← 值是 month/week/day/hour/minute，不是秒数
  --vm-addr=http://vmselect:8481 \          # ← 集群必须指 vmselect，指 vminsert 返 400
  --vm-account-id=0 \
  -s --disable-progress-bar                 # ← 不加会在无 TTY 环境报 inappropriate ioctl
```

```promql
# 迁移后必须重新校准的告警阈值（MetricsQL 不做外推、窗口前采样点不同）
increase(http_requests_total[5m])   # 迁移后数值可能与 Prometheus 不同
```

### 知识点挂钩

- 渐进共存三阶段路径 → **课 1**
- remote write 配置与 `external_labels` → **课 4**
- MetricsQL 与 PromQL 的六类有意差异 → **课 3**
- vmctl 三种模式与参数坑 → **课 12**

### 什么情况下此方案不适用

- **源端 Prometheus 已无历史数据价值**：不必走 B，直接 C 或 D。
- **需要 100% 精确的数据对齐**：迁移后数值可能因 MetricsQL 差异而不同，**这不是 bug**（课 3：官方从未承诺 100% 兼容）。

### 做错会踩的坑

→ [08-实战经验.md](08-实战经验.md) · 反模式 **第 1 条**（用 HTTP 状态码判断写入成功）：迁移后验证数据是否搬完，**必须用 `/api/v1/export`**，不能看 vmctl 的退出码或 HTTP 204。
→ [09-排障速查手册.md](09-排障速查手册.md) · **症状 13**（时间戳秒/毫秒）：迁移中若手写导入脚本，传秒级时间戳会得到 **1970-01-22** 的数据。

</details>

## 场景 7：告警要么不响，要么吵到没人看

**场景描述**：团队配了一堆告警，结果两极分化——有些故障发生了告警不响，有些告警天天响但都是毛刺，最后大家把告警群静音了。

> 📐 实测基准：告警用全站口径时，全站 2.25% vs 按接口 4.37%（**稀释近一半**，实战项目实测）；`absent(up)` 在采集中断时**无结果**（停 140 秒实测，实战项目）；reload 返 200 但 `config_last_reload_successful=0` 是假成功（课 11）。

**🔒 先自己想 30 秒**：「告警不响」和「告警太吵」，看起来是两个相反的问题。它们会不会有同一个根因？

<details><summary>💡 提示（分四层想）</summary>

- **口径层**：告警看的是全局还是分路径？阈值定的依据是什么？
- **存在性层**：服务整个消失时，你的表达式还成立吗？
- **灵敏度层**：`for` 和窗口怎么配？阈值贴着日常水位会怎样？
- **验证层**：你怎么确认一条告警规则**真的会响**？有没有演练过？

</details>

<details><summary>📖 展开解法</summary>

### 解法一览（5 个，含代价与边界）

| 解法 | 能解决到 | 代价 | 适用边界 |
|------|---------|------|---------|
| **A · 分路径口径 + 最小流量过滤**：告警用 `by (path)`；低流量接口加 `请求数 > N` 的前置条件 | 解决「该响不响」 | 告警数量随路径数增长 | 所有比率类告警 |
| **B · 可用性三层防线**：`up == 0` / `absent(last_over_time(up[2m]))` / `time()-max(timestamp(up)) > 120` | 解决「服务消失时告警哑火」 | 每个服务都要配三条 | **所有服务，无例外** |
| **C · `for` + 合适窗口**：`for` 至少覆盖 2 个求值周期；窗口至少 4 倍抓取间隔 | 解决「毛刺乱响」 | 告警响应变慢（这是**必要的代价**） | 所有告警 |
| **D · 阈值基于历史水位定**：用 P95/P99 历史分布定阈值，而非拍脑袋 | 解决「永久 firing 的狼来了」 | 需要历史数据积累 | 所有阈值型告警 |
| **E · 定期故障演练**：主动停 vmagent / 停节点，验证告警真的会响 | 解决「配了但从没验证过」 | 需要演练窗口 | **每季度至少一次** |

### 推荐路径（递进）

1. **先补 B**（最重要，立即做）：**服务消失时告警哑火**是最危险的失效——最严重的故障反而最安静（课 4 / 课 11）。三条防线缺一不可，注意**第二条必须用 `absent(last_over_time(...))` 而非 `absent()`**。
2. **再修 A**：把比率类告警改成分路径口径，低流量接口加最小流量过滤。
3. **然后调 C 和 D**：窗口至少 4 倍抓取间隔；`for` 覆盖 2 个求值周期；阈值基于历史水位（别贴着日常水位）。
4. **最后把 E 变成制度**：没有演练过的告警等于没有告警。

```promql
# B 的三层防线（缺一不可）
up{job="api"} == 0                                        # 单实例失联
absent(last_over_time(up{job="api"}[2m]))                 # 序列消失（注意不能用 absent(up)）
time() - max by (job) (timestamp(up{job="api"})) > 120    # 滞后量化

# A 的分路径 + 最小流量过滤
(
  sum by (path) (rate(http_requests_total{status=~"5.."}[2m]))
    / sum by (path) (rate(http_requests_total[2m]))
) > 0.05
and
sum by (path) (rate(http_requests_total[2m])) > 1          # ← 最小流量过滤
```

### 知识点挂钩

- 聚合过度稀释短板 → **实战项目**（2.25% vs 4.37%）
- `absent()` 的失效与正确写法 → **实战项目**（停 140 秒的三种表达式对照）
- `for` 与窗口配置、告警状态迁移 → **课 11**
- 阈值贴着水位的狼来了效应 → 本仓库 `promql/` 课程 L11

### 什么情况下此方案不适用

- **需要亚秒级故障发现**：抓取间隔 + 评估间隔 + `for` 的叠加决定了最快也是十几秒级。这类需求应走客户端埋点直报或流式计算，不是 VM 告警的适用场景。
- **告警数量已经爆炸**：这时问题不在规则写法，而在**告警体系设计**（分级、路由、抑制），需要 Alertmanager 层面的治理，超出本场景范围。

### 做错会踩的坑

→ [08-实战经验.md](08-实战经验.md) · **故障模式 9**（`for` 计时被重启清零）：配完告警后**反复重启 vmalert 排查「为什么不响」**，恰恰是让它永远不响的原因。
→ [09-排障速查手册.md](09-排障速查手册.md) · **症状 9** 与 **症状 15**：验证告警时**先等够 `for` 的完整时长，期间绝不重启**；reload 后必查 `config_last_reload_successful`。

</details>
