## 🔴 症状 1：写入返 204，但查询 0 条、序列数不涨

**一眼识别**：`/api/v1/import/prometheus` 返回 **HTTP 204**；查同一指标 **0 条**；`/api/v1/series/count` **不增长**。**全程不报错。**

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 若下游依赖该数据做决策，先撤下相关面板并标注「数据异常」 | 不再有人依据错误数字决策 |
| 定位 1 | 查 `/api/v1/series/count` | 涨了 → 数据已进来，问题在**可见性**；没涨 → 问题在**写入** |
| 定位 2 | 没涨 → 查 `vm_rows_inserted_total{type="..."}` | CSV import 实测为 **0**（返 204 但一行没写） |
| 定位 3 | 确认端点与格式匹配 | 行协议端点 `/api/v1/import/prometheus` **只吃纯文本行**；JSON 必须走 `/api/v1/import` |
| 定位 4 | 涨了 → 加 `nocache=1` 再查 | 查得到 → 挡路的是**结果缓存** |
| 定位 5 | 检查时间戳单位 | import 用**毫秒**；传秒级 `1788355138` 被解析成 **1970-01-22** |
| 修复 | 回填期间加 `-search.disableCache`；验证改用 `/api/v1/export` | 数据可见 |
| 若无效 | → 转「症状 10」（可能一直在用旧数据验证新配置） | — |

```bash
# 验证写入的正确姿势（不看 HTTP 状态码）
curl -s 'http://localhost:8428/api/v1/export?match={__name__="你的指标"}' | head
curl -s 'http://localhost:8428/metrics' | grep vm_rows_inserted_total
```

> **预防**：把「验证写入用 `/api/v1/export`，不看 204」定为团队约定。
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 1

## 🟡 症状 2：`labeldrop` 写了却不生效，序列数持续暴涨

**一眼识别**：配置里 `labeldrop` 明明白白写着；目标序列**仍带着**该标签；`totalSeries` 持续上涨。**不报任何错。**

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 若内存/磁盘吃紧，先用 vmauth 限流或临时缩短 retention | 止血不依赖改配置 |
| 定位 1 | 数一下目标序列里**带该标签**的有多少条（**只看近 90 秒新增样本**） | 有值 → 确认未生效 |
| 定位 2 | 检查 `labeldrop` 在哪个配置段 | 对指标自带标签操作 → **必须是 `metric_relabel_configs`**；写在 `relabel_configs` 永不匹配 |
| 定位 3 | 检查 `regex` 是否写成分组形式 | 应为 `(user_id\|session_id)`，不是 `user_id` |
| 修复 | 移到 `metric_relabel_configs` 段并修正 regex | 新增样本中该标签消失 |
| 若无效 | → 转「症状 10」（改了配置但行为不变，多半一直在拿旧数据验证新配置） | — |

```yaml
# ❌ 写错段：relabel_configs 只作用于抓取目标标签
scrape_configs:
  - job_name: demo
    relabel_configs:
      - action: labeldrop
        regex: user_id

# ✅ 正确：metric_relabel_configs 才作用于指标自带标签
scrape_configs:
  - job_name: demo
    metric_relabel_configs:
      - action: labeldrop
        regex: (user_id|session_id)
```

**决定性对照（实战项目实测）**：两个并行 vmagent 写不同 accountID，其他配置相同

| 组 | 序列数 | 带 user_id |
|---|---|---|
| 有 `metric_relabel_configs` + `labeldrop` | **1** | **0** |
| 无任何 relabel | **50** | **50** |

> **预防**：验证时序数据的「改写」是否生效，**判定只看近 90 秒新增样本**——历史序列不会消失，查全量会永远 FAIL。
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 2

## 🔴 症状 3：告警恒 firing 不消失，同时真故障不响

**一眼识别**：A 租户明明正常，告警**恒为 firing 且永不消失**；B 租户真出问题，**一条都不响**。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 暂停信任该组告警，改人工巡检；对恒 firing 的告警先静默避免狼来了 | 决策不再依赖失真告警 |
| 定位 1 | 查 `/api/v1/rules`（**不是** `/api/v1/alerts`） | 看到各规则的真实状态与 `lastError` |
| 定位 2 | 检查各租户规则命中的样本是否越到了别的租户 | 越界 → 确认根因 |
| 定位 3 | 查 vmalert 启动参数 `-datasource.url` | 只有**一个** → 所有租户规则都在查同一数据源 |
| 修复 | **每租户一个独立 vmalert 实例**，各自 `-datasource.url` 指向自己的 accountID | 各租户规则只查自己的数据 |
| 若无效 | → 转「症状 9」（可能是 `for` 计时被重启清零） | — |

```bash
# 查规则真实状态（权威端点）
curl -s 'http://localhost:8880/api/v1/rules' | python3 -m json.tool
```

> **预防**：多租户隔离四层逐层检查——采集（独立 vmagent）/ 存储（URL 路径 accountID）/ 查询（vmauth 路由）/ **告警（独立 vmalert）**。漏任意一层即击穿。
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 3

## 🔴 症状 4：服务挂了，告警却集体沉默

**一眼识别**：服务完全不可用，所有业务告警（错误率、延迟）**一条都没响**；面板曲线**断掉**而非掉到 0。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 立即人工确认服务状态并启动应急预案（**别等告警**） | 止损动作不依赖监控系统 |
| 定位 1 | 查 `up{job="..."}` | 0 行或值全为 0 → 实例级失联 |
| 定位 2 | 查 `absent(up{...})` | **无结果不等于健康**——历史序列还在，`absent()` 恒为 0 |
| 定位 3 | 查 `absent(last_over_time(up{...}[2m]))` | 返回 **1** → 确认序列已消失 |
| 定位 4 | 查 `time() - max by (tenant) (timestamp(up{...}))` | 得到滞后秒数（实测 139.8 / 244 秒） |
| 修复 | 补齐三层防线：`up == 0` / `absent(last_over_time(up[2m]))` / `time()-max(timestamp(up)) > 120` | 任一死法都有对应告警 |
| 若无效 | → 检查 Alertmanager 是否正常（告警产生了但没发出去） | — |

**决定性对照（实战项目：停 vmagent 140 秒后逐一求值）**

| 表达式 | 结果 |
|---|---|
| `absent(up{tenant="tenant-a"})` | **无结果**（恒 false）❌ |
| `absent(last_over_time(up{tenant="tenant-a"}[2m]))` | **1** ✅ |
| `time() - max(timestamp(up{tenant="tenant-a"}))` | **139.8 秒** ✅ |

> **预防**：任何服务上线必须同时配这三条；定期演练「停掉 vmagent」验证告警真的会响。
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 4

## 🟡 症状 5：错误率已经很高，告警阈值却没触发

**一眼识别**：某接口错误率明显偏高，但告警从未 firing；全站错误率面板显示「一切正常」。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 立刻按路径下钻，确认受影响范围 | 定位到具体接口 |
| 定位 1 | 把查询加 `by (path)` 或 `by (method, path)` 重跑 | 各路径数值分开 |
| 定位 2 | 按数值**降序**看第一条 | 实测：全站 **2.25%** vs 按接口 **4.37%** |
| 定位 3 | 对比两侧差值 | 差值大 → 确认被稀释 |
| 修复 | 告警一律改为**分路径**粒度；全站口径只作总览速读 | 短板路径暴露出来 |
| 若无效 | → 转「症状 9」（可能是 `for` 计时问题而非口径问题） | — |

```promql
# ❌ 全站口径（健康流量会稀释问题接口）
sum(rate(http_requests_total{status=~"5.."}[2m])) / sum(rate(http_requests_total[2m]))

# ✅ 分路径口径（告警必须用这个）
sum by (path) (rate(http_requests_total{status=~"5.."}[2m]))
  / sum by (path) (rate(http_requests_total[2m]))
```

> **预防**：比率类指标默认准备「全站 + 分路径」两个版本，告警只用后者；**低流量接口要加最小流量过滤**（否则 1 个请求失败 1 次就是 100%）。
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 5

## 🔴 症状 6：`count()` 突然掉一半，但查询成功不报错

**一眼识别**：`count(...)` 从 **1000 掉到 509**；查询**成功**（HTTP 200）、**不报错**；没有任何告警触发。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 立即确认是否有 vmstorage 节点宕机；若有，先恢复节点 | 恢复后数据自动回来 |
| 定位 1 | 用 `up` 或健康检查确认所有 vmstorage 存活 | 有节点挂 → 确认根因 |
| 定位 2 | 对比故障前后的 `count()` 绝对值 | 掉了约 1/N（N = 节点数）→ 静默降级 |
| 定位 3 | 查 vminsert 日志是否有 `cannot make a copy` | 这是**副本失败的唯一可靠证据**（HTTP 仍返 204） |
| 定位 4 | 查 `vm_rpc_rows_incompletely_replicated_total` | ⚠️ 实测 5 次失败后**仍为 0**，不可靠，别只信它 |
| 修复 | vminsert 配 `-replicationFactor=2`；vmselect 配 `-dedup.minScrapeInterval` | 故障期查询不再掉数据 |
| 若无效 | → 转「症状 7」（若已配 dedup，可能是间隔设错） | — |

```bash
# 副本失败的唯一可靠证据在日志里
docker logs vminsert 2>&1 | grep -i "cannot make a copy"
```

> **预防**：**最小 3 个 vmstorage 配 RF=2**；告警规则里加数据完整性检查（如 `vm_new_timeseries_created_total` 异常跌落）。
> ⚠️ **副本缺口不自动补齐**：故障期写入 100 条，节点恢复后仍 100 / **0**，社区版无修复机制，需人工导出重灌。
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 6

## 🟡 症状 7：开 dedup 后样本数变少（如 12 → 3）

**一眼识别**：配了 `-dedup.minScrapeInterval` 后，某些序列样本数**明显少于实际写入数**；曲线出现不应有的稀疏。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 若已影响告警判断，先临时下调 dedup 间隔或关闭 dedup | 恢复数据完整性优先 |
| 定位 1 | 确认真实采集间隔（`scrape_interval`） | 例如 5s |
| 定位 2 | 对比 vmselect 的 `-dedup.minScrapeInterval` 值 | **必须相等**，设大就会误删 |
| 定位 3 | 用已知样本数的测试序列验证 | 实测：12 个样本（间隔 5s）用 30s → 剩 **3 个**（丢 75%） |
| 修复 | 把 `-dedup.minScrapeInterval` 设为**等于**真实采集间隔 | 恢复 12 个 |
| 若无效 | → 转「症状 6」（可能是副本本身就有缺口） | — |

> **预防**：改采集间隔时同步改 dedup 间隔，两者写进同一份配置注释。
> ⚠️ **关键认知**：设大**不会漏掉副本，只会误删数据**。
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 7

## 🟡 症状 8：`delete_series` 返 204，但磁盘反增、序列数不降

**一眼识别**：删除接口返 **204** 且日志确认 `Deleted 20000 series`；但磁盘占用**反增 2,348 KB**、`/api/v1/series/count` **不降**（142,394 → 142,396）。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | **立即停止后续删除操作**——删除不可逆、无回收站 | 防止损失扩大 |
| 定位 1 | 查**具体指标**（不是 `/series/count`，它含已删未回收的序列） | 确认删除确实生效 |
| 定位 2 | 查 `/snapshot/list` 是否有快照 | 有快照 → 被冻结的数据块无法在合并中丢弃 |
| 定位 3 | 需要立即回收 → `POST /internal/force_merge` | **1 秒内**回收（实测 1,068 KB） |
| 修复 | 按「删快照 → force_merge」顺序操作 | 磁盘占用下降 |
| 若无效 | → 确认端点打的是 **vmstorage**（vmselect/vminsert 返 400） | — |

```bash
# 空间回收（只有 vmstorage 有此端点）
curl -X POST 'http://vmstorage:8482/internal/force_merge'
```

> **预防**：**删除前的前置检查——备份存在、且备份时间早于删除时刻**（本课误删 20,000 条因备份晚于删除而无法找回）。快照保留短期（小时级）。
> ⚠️ **v1.149.0 起 `delete_series` 仅接受 POST**（核查于 2026-09），升级后脚本要改。
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 8

## 🟡 症状 9：告警规则写了却永远 inactive

**一眼识别**：规则语法正确、数据源可达，但状态**永远停在 inactive**；反复重启排查后依然如此。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 若该告警覆盖关键路径，先转人工巡检 | 关键路径不失守 |
| 定位 1 | **先等够 `for` 的完整时长，期间绝不重启/重载 vmalert** | 重启会把 `for` 计时清零 |
| 定位 2 | 查 `/api/v1/rules` 看真实状态与 `lastError` | 看到 pending / firing / 具体错误 |
| 定位 3 | 若刚 reload 过，查 `vmalert_config_last_reload_successful` | **不要信 HTTP 200**——返 200 但该指标为 0 是假成功 |
| 定位 4 | 检查 MetricsQL 语法（如 label matcher 是否误写进方括号 `lag(up[job="x"])`） | 语法错会导致 reload 假成功 + 重启 fatal |
| 修复 | 修正语法后重新 reload，**等待完整的一个 `for` 周期** | 观察到 pending → firing |
| 若无效 | → 转「症状 3」（多租户场景可能是数据源指错） | — |

```bash
# 查 reload 是否真的成功（不能只看 HTTP 状态码）
curl -s 'http://localhost:8880/metrics' | grep vmalert_config_last_reload_successful
# 查规则真实状态（权威端点是 /api/v1/rules，不是 /api/v1/alerts）
curl -s 'http://localhost:8880/api/v1/rules' | python3 -m json.tool
```

> **预防**：把「观察告警状态迁移时不重启观察对象」写进排障纪律；reload 后必查 `config_last_reload_successful`。
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 9

## 🟡 症状 10：反复改配置，行为始终不变

**一眼识别**：反复修改 relabel / 告警规则，**行为始终不变**；对照实验的两组结果**一模一样**；排查多轮毫无进展。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 暂停继续改配置（改了也不会生效），先确认清理是否真的生效 | 停止无效排查 |
| 定位 1 | `docker inspect <容器>` 看 `Mounts` | 确认是 **volume** 还是 **bind mount** |
| 定位 2 | 按实际类型清理：bind mount → 删**宿主机目录**；volume → `docker volume rm` | ⚠️ 用清 volume 的方式清 bind mount 数据 = 清了个寂寞 |
| 定位 3 | `docker ps -a` 确认没有旧名容器残留 | 旧容器会继续占端口，新配置根本没生效 |
| 修复 | 按实际挂载类型清理；确认目录真的空了再重启 | 新配置生效 |
| 若无效 | → 转 `debug` skill 现场取证 | — |

```bash
# 确认数据到底挂在哪
docker inspect vmstorage-1 --format '{{json .Mounts}}' | python3 -m json.tool
# 确认无残留容器占端口
docker ps -a --filter "name=capstone" --format '{{.Names}}\t{{.Status}}'
```

> **预防**：**为每个关键假设找一个能回显真实状态的观测点**，不靠「没报错」推断。实验脚本的 reset 段要同时处理 bind mount 目录与旧名容器。
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 10

## 🟡 症状 11：报错 `unsupported path requested`

**一眼识别**：日志或响应中出现 `unsupported path requested: /select/100/...` 或 `/insert/0/prometheus/api/v1/write/api/v1/write`。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 若影响写入，先确认数据是否有备份/队列兜底（vmagent 持久化队列可缓冲） | 数据不丢 |
| 定位 1 | 看报错路径里**是否缺 `prometheus` 协议段** | vmauth 拼接规则是 `url_prefix + 原始路径`，漏段就 400 |
| 定位 2 | 看路径里**是否出现了重复的 `/api/v1/write`** | vmalert 的 `-remoteWrite.url` 会**自动追加**，手写就重复 |
| 定位 3 | 确认协议风格匹配（Prometheus 风格的 `/api/v1/write` 不能拼到 influx 后端） | 拼错会报 `/insert/100/influx/api/v1/write` |
| 修复 | vmauth 的 `url_prefix` 补上协议段；vmalert 的 `-remoteWrite.url` **去掉**手写的 `/api/v1/write` | 请求正常 |
| 若无效 | → 转 `debug` skill 现场取证 | — |

```yaml
# ❌ vmauth：漏了 prometheus 协议段
url_prefix: "http://vmselect:8481/select/100"
# ✅ 正确
url_prefix: "http://vmselect:8481/select/100/prometheus"

# ❌ vmalert：多写了 /api/v1/write（会自动补）
-remoteWrite.url=http://vminsert:8480/insert/0/prometheus/api/v1/write
# ✅ 正确
-remoteWrite.url=http://vminsert:8480/insert/0/prometheus
```

> **预防**：这两处坑**同源**（路径拼接），团队内统一收录成一个 snippet。
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 3

## 🟡 症状 12：报错 `cannot fallocate ... operation not supported`

**一眼识别**：执行 vmrestore 时报 `cannot fallocate 210 bytes: operation not supported`。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 停止恢复操作，确认目标目录未被写坏 | 不制造次生损伤 |
| 定位 1 | 确认恢复目标目录所在的文件系统 | Windows + WSL 下 `D:\` 挂载目录是 **9p** |
| 定位 2 | 9p **不支持 fallocate**，VM 预分配文件会失败 | 确认根因 |
| 修复 | 改用 **docker 命名卷**（overlay 文件系统）作为恢复目标 | 恢复正常 |
| 若无效 | → 转 `debug` skill 现场取证 | — |

```bash
# ❌ 在 9p 挂载目录恢复
docker run --rm -v /mnt/d/vm-data:/vmdata ... vmrestore ...
# ✅ 用 docker 命名卷
docker volume create vm-restore-data
docker run --rm -v vm-restore-data:/vmdata ... vmrestore ...
```

> **预防**：Windows + WSL 环境下，VM 的数据目录一律用 docker 命名卷，不要用 `/mnt/d/...` 挂载目录。
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 8

## 🟡 症状 13：数据时间戳显示 1970-01-22

**一眼识别**：写入的数据查不到，或 `export` 出来时间戳是 **1970-01-22**；极端情况报 `year XXXXX is out of range`。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 停止当前批量写入，避免产生大量脏数据 | 不再制造垃圾数据 |
| 定位 1 | 检查写入用的时间戳单位 | **import API 用毫秒**；传秒级 `1788355138` → 1970-01-22 |
| 定位 2 | 检查 `/api/v1/export` 读回的时间戳单位 | **是毫秒**，当秒用会得到荒谬年份 |
| 修复 | 写入时间戳统一乘 1000（秒 → 毫秒） | 数据落在正确时间点 |
| 若无效 | → 转「症状 1」（可能是缓存或端点问题） | — |

> **预防**：时间戳单位在封装层统一处理，不在业务代码里各自转换。
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 1

## ⚪ 症状 14：查询返 422 或报 `exceeded maximum resolution`

**一眼识别**：长跨度查询返 **HTTP 422**；或报 `exceeded maximum resolution of 11,000 points per timeseries`。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 若是面板，先调大 step 或缩短时间范围让面板能出图 | 恢复可见性 |
| 定位 1 | 算一下：跨度 ÷ step 是否超过 **30000** | `-search.maxPointsPerTimeseries` 默认 30000 |
| 定位 2 | 7 天 × step=10s = **60481 点** → 超限被拒 | 确认根因 |
| 修复 | 调大 step、缩短跨度，或调高 `-search.maxPointsPerTimeseries` | 查询成功 |
| 若无效 | → 转「症状 6」（可能是节点故障导致结果异常） | — |

> **预防**：长跨度面板用 **recording rules 预聚合**，别让面板直接扫原始数据。
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 6

## 🟡 症状 15：vmalert `/-/reload` 返 200 但配置没生效

**一眼识别**：reload 接口返回 **HTTP 200**，但新规则没生效；或重启 vmalert 直接 fatal。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 若旧规则仍在工作，先维持现状不要反复重启 | 避免服务中断 |
| 定位 1 | 查 `vmalert_config_last_reload_successful` | **0** → 假成功（HTTP 200 不代表配置有效） |
| 定位 2 | 检查 MetricsQL 语法，特别是 label matcher 是否误写进方括号 | `lag(up[job="x"])` 是错的，`lag(up{job="x"})` 才对 |
| 定位 3 | 查日志确认是否有 fatal 原因 | 语法错会导致重启直接 fatal |
| 修复 | 修正语法后重新 reload，并确认指标变为 **1** | 配置生效 |
| 若无效 | → 转「症状 9」（可能是 `for` 计时问题） | — |

```bash
curl -s 'http://localhost:8880/metrics' | grep vmalert_config_last_reload_successful
# 期望：vmalert_config_last_reload_successful 1
```

> **预防**：reload 是**异步**的，必须查指标确认，不能只看 HTTP 状态码。这与「写入返 204 不等于写进去」是同一条纪律。
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 9
