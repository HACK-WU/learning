## 🚫 适用边界与反模式

### 什么时候不该用 VictoriaMetrics

> "不该用"比"怎么用"更值钱——这是从"会用"到"用对"的分界线。

| 场景 | 为什么不适合 | 该用什么替代 | 依据 |
|------|-------------|-------------|------|
| **数据量极小（< 100 万序列）、单机 Prometheus 跑得好好的** | 小数据集上 Prometheus 反而**快 3~35 倍**。VM 的优势在规模，小规模是反优势 | 继续用 Prometheus | 课 12 实测 |
| **需要频繁删除/更新数据** | 删除是**墓碑机制**：返 204、日志确认删除，但磁盘**反增 2,348 KB**、`/series/count` 不降；**不可逆无回收站** | 需要频繁变更的数据放业务库 | 课 12 实测 |
| **需要事务保证** | VM 不是 OLTP 数据库，无事务 | PostgreSQL / MySQL | 课 12 |
| **要存字符串值或日志** | VM **只存数值型指标**，不支持字符串值 | VictoriaLogs / Loki / ELK | 课 1 |
| **超高基数 + 需要精确单点查询** | 压缩与缓存都只在基数可控时才有效；高基数是空间与查询耗时的共同主变量 | 日志 / 数仓 | 课 5 / 课 7 实测 |
| **需要亚秒级精度的告警** | 抓取间隔 + 评估间隔 + `for` 叠加，最快十几秒级 | 客户端埋点直报 / 流式计算 | 课 11 |
| **需要原生多租户硬配额** | 社区版**只有数据隔离，没有资源隔离**（实测大租户让他人慢 7.4 倍）；租户级硬限额是企业版功能 | 企业版 / 架构拆分 | 课 10 实测 + 官方 enterprise.md |

### 高频反模式（能跑，但迟早出事）

1. **用 HTTP 状态码判断写入是否成功** —— CSV import 四种写法全返 204 但 `vm_rows_inserted_total=0`；JSON 喂给行协议端点同样 204 且全丢。**验证写入必须用 VM 自身统计或 `/api/v1/export`**（课 4 / 课 12 实测）
2. **把 `labeldrop` 写在 `relabel_configs`** —— 它作用于抓取目标标签，不作用于指标自带标签。写错位置**不报错、永不匹配**，是典型的静默失败（课 4 + 实战项目实测：序列数 50 vs 1）
3. **`dedup.minScrapeInterval` 设成「保险起见大一点」** —— 12 个样本（间隔 5s）用 30s 窗口只剩 3 个（丢 75%）。**必须等于真实采集间隔**（课 9 实测）
4. **空租户 ID 不设防** —— 写入返 204、不报错，数据静默进 tenant 0（课 10 实测）
5. **用 `du` 判断快照占用** —— 硬链接被重复计数，快照看起来很大其实只占 68 KB。**必须用 `df`**（课 12 实测）
6. **告警用全站聚合口径** —— 实测全站 2.25% vs 按接口 4.37%，**稀释近一半**，配 5% 阈值则故障已到 5% 仍不响（实战项目实测）
7. **用 `absent(up)` 检测采集中断** —— 历史序列仍在，`absent()` 恒为 0。必须用 `absent(last_over_time(up[2m]))`（实战项目实测：停 140 秒，`absent(up)` 无结果）
8. **拿平均值法做容量规划** —— 边际成本 65.5 字节/序列 vs 平均值 6234.7，**差 95 倍**（课 7 实测）
9. **以为重启会清空缓存** —— fastcache 落盘于 `data/cache/`，重启后缓存条目几乎不变（297415 → 337608），命中率 99.94%（课 7 实测）
10. **以为快照留着没关系** —— 快照自身 68 KB，却阻止 **1,128 KB** 被回收（**16 倍**）（课 12 实测）

## 🔥 高频故障模式

> 每条固定**五段式**：症状 → 根因 → 排查路径 → 修复 → 预防。
> 全部症状均为**可观测**的具体现象，实测依据标注在数据里。

### 故障模式 1：写入返回 204，但数据就是查不到

- **症状（可观测）**：`/api/v1/import/prometheus` 返回 **HTTP 204**；`/api/v1/query` 查同一指标返回 **0 条**；`/api/v1/series/count` 数字**不增长**
- **根因**：两处可能，都来自「写入成功」与「数据可见」是两件事：
  - **写入侧**：数据在内存缓冲里（默认 1 秒刷盘），未落盘时连 `nocache=1` 都查不到
  - **查询侧**：命中了结果缓存。缓存重置依赖新样本时间戳是否落在 `-search.cacheTimestampOffset`（默认 **5m**）窗口内，单纯等待不保证刷新
  - **最隐蔽的一种**：CSV import / JSON 喂错端点，返 204 但**一行都没写**，`vm_rows_inserted_total{type="csvimport"}=0`

  实测对照（课 2）：
  ```bash
  # 1. 不刷盘时，连 nocache=1 都查不到 → 数据确实还在内存
  # 2. 刷盘后 nocache=1 查得到，普通查询仍为 0 → 挡路的是缓存
  # 3. 3 秒后普通查询仍是 0 → 缓存不会在几秒内自动恢复
  ```

- **排查路径**：
  1. 先查 `/api/v1/series/count`——**序列数涨了说明数据进来了**，问题在可见性；没涨才是写入问题
  2. 序列数没涨 → 查 `vm_rows_inserted_total{type="..."}` 确认协议是否真的被解析（CSV import 是经典反例）
  3. 确认端点与数据格式匹配：行协议端点 `/api/v1/import/prometheus` 只吃纯文本行；JSON 必须走 `/api/v1/import`
  4. 加 `nocache=1` 再查，排除结果缓存
  5. 时间戳单位：**import 用毫秒**，传秒级 `1788355138` 会被解析成 **1970-01-22**，永远查不到
- **修复**：回填历史数据期间加 `-search.disableCache`；写入验证改用 `/api/v1/export`（不受缓存与秒级延迟影响）
- **预防**：把「验证写入用 `/api/v1/export`，不看 HTTP 状态码」定为团队约定。这是本课**贯穿 4 课**（L2 / L4 / L11 / L12）的第一方法论

> 对应速查条目：[09-排障速查手册.md](09-排障速查手册.md) · 症状 1

### 故障模式 2：高基数标签没被 drop 掉，序列数持续暴涨

- **症状（可观测）**：`/api/v1/status/tsdb` 的 `totalSeries` 持续上涨；内存与查询耗时同步上涨；打开面板要等十几秒。**配置里的 `labeldrop` 明明白白写着，就是不生效**
- **根因**：`labeldrop` 写在了 `relabel_configs` 而不是 `metric_relabel_configs`。前者作用于**抓取目标**（target 标签），后者才作用于**指标自带标签**。写错位置**不报错、永不匹配**——这是静默失败

  决定性对照实验（实战项目 `p10-final-ab.sh`）：两个并行 vmagent 写入不同 accountID，其他配置完全相同

  | 组 | 序列数 | 带 user_id 的序列 |
  |---|---|---|
  | 实验组（`metric_relabel_configs` + `labeldrop`） | **1** | **0** |
  | 对照组（无任何 relabel） | **50** | **50** |

  另一个隐蔽变体：**regex 隐式全匹配**——写 `regex: user_id` 期望匹配单个标签，实际必须写成 `(user_id|session_id)` 这样的分组形式

- **排查路径**：
  1. 别信「配置写了就该生效」——**查数据**。数一下目标序列里带该标签的有多少条
  2. 确认 relabel 的**作用段**：对指标自带标签做操作 → 必须是 `metric_relabel_configs`
  3. 确认 `regex` 写成了分组形式
  4. 验证时序数据上的「改写」是否生效时，**判定只看近 90 秒新增样本**——历史序列不会消失，查全量会永远 FAIL
- **修复**：把 `labeldrop` 移到 `metric_relabel_configs` 段
- **预防**：任何 relabel 规则上线后，用「近 90 秒新增样本」的口径数一次序列数；把基数审计做成告警（序列数 1 小时涨 50% 就报警）

> 对应速查条目：[09-排障速查手册.md](09-排障速查手册.md) · 症状 2

### 故障模式 3：多租户告警「假警报不停 + 真故障不响」的双向失效

- **症状（可观测）**：A 租户一切正常，告警却**恒为 firing 且不消失**；B 租户真的出问题了，告警**一条都不响**
- **根因**：**单个 vmalert 实例服务多个租户**。vmalert 只有一个 `-datasource.url`，所有租户的规则都去查同一个数据源——B 租户的规则实际在查 A 租户的数据
- **排查路径**：
  1. 查 `/api/v1/rules`（不是 `/api/v1/alerts`——后者不能反映规则是否真的被加载与求值）
  2. 对比各租户规则命中的样本，看是否越到了别的租户
  3. 确认 vmalert 启动参数里 `-datasource.url` 指向哪个 accountID
- **修复**：**每租户一个独立 vmalert 实例**，各自 `-datasource.url` 指向自己的 accountID（集群 URL 路径里写死租户号）
- **预防**：多租户告警的四层隔离必须逐层检查——采集（独立 vmagent）/ 存储（URL 路径 accountID）/ 查询（vmauth 路由）/ 告警（**独立 vmalert**）。**漏任意一层即击穿**

> 对应速查条目：[09-排障速查手册.md](09-排障速查手册.md) · 症状 3

### 故障模式 4：服务已经挂了，告警却集体沉默

- **症状（可观测）**：服务完全不可用，所有业务告警（错误率、延迟）**一条都没响**；面板曲线**断掉**而不是掉到 0
- **根因**：**序列消失了**。抓不到样本 → 没有序列满足 `错误率 > 5%` 这类条件 → 表达式返回空表 → 空表不触发告警。**最严重的故障，告警反而最安静**
- **排查路径**：
  1. 查 `up{job="..."}`：返回 0 行或值全为 0 → 实例级失联
  2. 查 `absent(up{tenant="..."})`：**如果无结果，不代表健康**——历史序列还在，`absent()` 恒为 0
  3. 正确的检测是 `absent(last_over_time(up{tenant="..."}[2m]))`

  决定性对照（实战项目：停 vmagent 140 秒后逐一求值）：

  | 表达式 | 结果 |
  |---|---|
  | `absent(up{tenant="tenant-a"})` | **无结果**（恒 false）❌ |
  | `absent(last_over_time(up{tenant="tenant-a"}[2m]))` | **1** ✅ |
  | `time() - max(timestamp(up{tenant="tenant-a"}))` | **139.8 秒** ✅ |

- **修复**：建立三层防线——`up == 0`（单实例）→ `absent(last_over_time(up[2m]))`（序列消失）→ `time() - max(timestamp(up)) > 120`（滞后量化）
- **预防**：任何服务上线必须同时配这三条；**定期演练「停掉 vmagent」验证告警是否真的响**。注意：演练中会踩到的坑见故障模式 9

> 对应速查条目：[09-排障速查手册.md](09-排障速查手册.md) · 症状 4

### 故障模式 5：错误率告警该响不响（阈值被聚合稀释）

- **症状（可观测）**：某个接口错误率已经很高，但告警从未触发；全站错误率面板显示「一切正常」
- **根因**：**错误率用了全站聚合口径**。健康接口的流量把问题接口稀释掉了

  实测（实战项目）：同一个数据集，**全站口径 2.25%，按接口口径 4.37%**——稀释了近一半。若阈值配 5%，则故障已经到 5% 仍不响

- **排查路径**：
  1. 把查询加 `by (path)`（或 `by (method, path)`）重跑，看各接口分开的数值
  2. 按数值**降序**看第一条
  3. 对比「全站 vs 分路径」的差值——差值大就是被稀释了
- **修复**：告警一律用**分路径**粒度；全站口径只作总览速读
- **预防**：比率类指标默认准备「全站 + 分路径」两个版本；告警只用后者。另注意给低流量接口加**最小流量过滤**（否则 1 个请求失败 1 次就是 100%）

> 对应速查条目：[09-排障速查手册.md](09-排障速查手册.md) · 症状 5

### 故障模式 6：停掉一个存储节点，查询悄悄少了一半数据

- **症状（可观测）**：`count(...)` 从 **1000 掉到 509**；查询本身**成功**（HTTP 200），不报任何错；没有任何告警
- **根因**：**集群无副本时的静默降级**。一致性哈希把数据分散在各 vmstorage，节点挂了，它那部分数据就查不到了。**vmselect 返回的是「能查到的数据」，不是「应该有的数据」**——它不知道有 491 条在不存在的节点上
- **排查路径**：
  1. 用 `up` 或健康检查确认所有 vmstorage 节点存活
  2. 对比故障前后的 `count()` 绝对值
  3. 查 vminsert 日志是否有 `cannot make a copy`——这是**副本失败的唯一可靠证据**（HTTP 仍返 204）
- **修复**：配 `-replicationFactor=2`（在 vminsert 上）+ vmselect 配 `-dedup.minScrapeInterval`
- **预防**：
  - **最小推荐 3 个 vmstorage 配 RF=2**（2 节点配 RF=2 时故障期数据会退化成单副本）
  - 告警规则里加「数据完整性」检查（如监控 `vm_new_timeseries_created_total` 的异常跌落）
  - ⚠️ **副本缺口不会自动补齐**：故障期写入 100 条，节点恢复后仍 100 / **0**，社区版无修复机制

> 对应速查条目：[09-排障速查手册.md](09-排障速查手册.md) · 症状 6

### 故障模式 7：配了副本和 dedup，数据反而被误删

- **症状（可观测）**：开启 dedup 后，某些序列的样本数**明显少于实际写入数**；曲线出现不应有的稀疏
- **根因**：`-dedup.minScrapeInterval` 设得**大于**真实采集间隔。VM 会把间隔内的多个样本当成重复副本去重掉

  实测（课 9）：12 个样本（间隔 5s）用 `dedup=30s` 只剩 **3 个**（丢 75%）；改用 `dedup=5s` 恢复 12 个

- **排查路径**：
  1. 确认真实采集间隔（`scrape_interval`）
  2. 对比 vmselect 的 `-dedup.minScrapeInterval` 值——**必须相等**
  3. 用一个已知样本数的测试序列验证（如上面 12 → 3 的对照）
- **修复**：把 `-dedup.minScrapeInterval` 设为**等于**真实采集间隔
- **预防**：改采集间隔时同步改 dedup 间隔，并把两者写进同一份配置注释里。**设大不会漏掉副本，只会误删数据**——这是最反直觉的一点

> 对应速查条目：[09-排障速查手册.md](09-排障速查手册.md) · 症状 7

### 故障模式 8：删除数据后磁盘空间反增，且不可逆

- **症状（可观测）**：`/api/v1/admin/tsdb/delete_series` 返回 **204**，日志确认 `Deleted 20000 series`；但磁盘占用**反增 2,348 KB**，`/api/v1/series/count` **不降**（142,394 → 142,396）
- **根因**：**删除是墓碑机制而非空间回收**。删除只写墓碑标记，真正释放空间要等后台合并；而合并**不会自动触发**——自动等待 120 秒纹丝不动，需手动 `POST /internal/force_merge`（1 秒内回收 1,068 KB）。且**不可逆、无回收站**

  更隐蔽的叠加因素：若存在快照，被快照冻结的数据块无法在合并中丢弃，VM 只能把「未删除的数据」重写一份，导致**总占用上升**（实测带快照时删除 + 合并反增 628 KB；删快照瞬间释放 1,128 KB）

- **排查路径**：
  1. 确认是真的删了：查**具体指标**（不是 `/series/count`，它含已删未回收的序列）
  2. 确认无快照：`/snapshot/list`
  3. 需要立即回收 → `POST /internal/force_merge`（**只有 vmstorage 有此端点**，vmselect/vminsert 返 400）
- **修复**：按「删快照 → force_merge」顺序操作
- **预防**：
  - **删除前的前置检查：备份存在、且备份时间早于删除时间**（本课误删 20,000 条因备份晚于删除而**无法找回**）
  - 快照保留**短期（小时级）**
  - ⚠️ **v1.149.0 起 `delete_series` 仅接受 POST**（此前 GET 也可，存在 SSRF 删除风险）——升级后脚本要改（核查于 2026-09）

> 对应速查条目：[09-排障速查手册.md](09-排障速查手册.md) · 症状 8

---

### 故障模式 9：告警规则明明写了，就是不响（排查时被自己干扰）

- **症状（可观测）**：规则语法正确、数据源可达，但告警状态**永远停在 inactive**；反复排查重启后依然如此
- **根因**：**排查动作本身在干扰观察对象**。`for: 1m` 的计时会在 vmalert 重启/重载时**清零**。连续三轮因重启 vmalert 而误判「规则写了却不响」，纯等待（不重启）后才观察到 pending → firing

  第二个变体：**reload 是假成功**——`/-/reload` 返回 HTTP 200，但 `vmalert_config_last_reload_successful=0`。根因是 MetricsQL 语法错误（如把 label matcher 误写进方括号 `lag(up[job="x"])`），且会导致 vmalert 重启直接 fatal

- **排查路径**：
  1. **先等够 `for` 的时长，期间绝不重启/重载 vmalert**
  2. 查 `/api/v1/rules` 看规则的真实状态（inactive / pending / firing）与 `lastError`
  3. 若刚 reload 过，查 `vmalert_config_last_reload_successful`——**不要信 HTTP 200**
  4. 用 `/api/v1/rules` 而非 `/api/v1/alerts` 判断规则是否被加载
- **修复**：修正语法错误后重新 reload；改完配置**等待完整的一个 `for` 周期**
- **预防**：把「观察告警状态迁移时不重启观察对象」写进排障纪律；reload 后必查 `config_last_reload_successful`

> 对应速查条目：[09-排障速查手册.md](09-排障速查手册.md) · 症状 9

---

### 故障模式 10：改了配置却一直在用旧数据验证（环境层面的静默失败）

- **症状（可观测）**：反复修改 relabel / 告警规则，**行为始终不变**；对照实验的两组结果**一模一样**；排查三轮毫无进展
- **根因**：**清理动作没真的清掉数据**。实战项目中 `reset` 一直在执行 `docker volume rm`，但实际数据写在 **bind mount 的宿主机目录**里——volume 是空的，清了个寂寞，于是一直在用旧数据验证新配置

  同类问题：容器改名后旧容器仍在运行并占用端口，导致新配置根本没生效

- **排查路径**：
  1. 先确认数据到底在哪：`docker inspect <容器>` 看 `Mounts` 是 **volume 还是 bind**
  2. 清数据要清**实际路径**（bind mount → 删宿主机目录；volume → `docker volume rm`）
  3. 用 `docker ps -a` 确认没有同名/旧名容器残留占着端口
- **修复**：按实际挂载类型清理；清理后确认目录真的空了再重启
- **预防**：
  - **为每个关键假设找一个能回显真实状态的观测点**，不靠「没报错」推断
  - 实验脚本的 reset 段要同时处理 bind mount 目录与旧名容器

> 对应速查条目：[09-排障速查手册.md](09-排障速查手册.md) · 症状 10
