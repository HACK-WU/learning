# 实战项目：多租户监控平台（从采集到告警的完整链路）

> 所属课程：VictoriaMetrics 系统学习 ｜ 学习目标：动手实操 ｜ 预计耗时：4–5 小时
> 项目性质：**技术域（可运行的多文件工程）** —— 全部结论均在本机 Docker 环境实测

## 🎯 一句话需求

给两个业务团队（backend / frontend）建一套**共享一套存储、但彼此看不见对方数据**的监控平台：各自采集、各自告警，一个团队出事不能影响另一个，运维还要能在一个入口统一管理。

## ✅ 目标与非功能约束

**功能目标**

1. 两个租户的指标采集进各自的 `accountID`，跨租户查询**查不到**对方数据
2. 统一入口（vmauth）按身份路由，只读身份**写不进去**
3. 每个租户有独立的告警规则，降级租户告警、健康租户安静
4. 高基数标签（`user_id`）在写入前被剔除
5. 单存储节点宕机不影响读写，单采集节点宕机只影响自己租户

**非功能约束**（本项目 5 项）

| 约束 | 具体要求 | 实测结果 |
|------|----------|---------|
| **租户隔离** | 跨租户查询返回 0 行 | ✅ 100 查 tenant-b = 0 行，200 查 tenant-a = 0 行 |
| **权限最小化** | 只读身份写入被拒 | ✅ HTTP 400；错误密码 HTTP 401 |
| **高可用** | 单 vmstorage 宕机可读写 | ✅ 查询 1918→2314 持续增长，写入 204 |
| **故障域隔离** | 一个租户挂了不影响另一个 | ✅ 停 vmagent-a 后 tenant-b 数据持续增长 |
| **基数可控** | 高基数标签不进存储 | ✅ 50 条序列塌缩为 1 条 |

## 🏗️ 架构拓扑

```text
                         ┌──────────────────────────────────────┐
                         │            vmauth :8506              │
                         │   按 Basic Auth 身份 → accountID     │
                         └───────────────┬──────────────────────┘
                                         │
              ┌──────────────────────────┼──────────────────────────┐
              │ backend  → 100           │        frontend  → 200   │
              │ viewer   → 100 (只读)    │                          │
              ▼                          ▼                          ▼
    ┌──────────────────┐      ┌────────────────────┐     ┌──────────────────┐
    │  vmagent-a :8502 │      │   vminsert :8500   │     │  vmagent-b :8503 │
    │  抓 tenant-a     │─────▶│  (一致性哈希分片)   │◀────│  抓 tenant-b     │
    └──────────────────┘      └─────────┬──────────┘     └──────────────────┘
                                        │
                        ┌───────────────┴───────────────┐
                        ▼                               ▼
              ┌──────────────────┐            ┌──────────────────┐
              │ vmstorage-1      │            │ vmstorage-2      │
              │ (复制因子 2)      │◀──────────▶│ (复制因子 2)      │
              └──────────────────┘            └──────────────────┘
                        │                               │
                        └───────────────┬───────────────┘
                                        ▼
                              ┌──────────────────┐
                              │  vmselect :8501  │
                              │   (查询聚合去重)   │
                              └──────────────────┘
                                        │
                    ┌───────────────────┼───────────────────┐
                    ▼                                       ▼
          ┌──────────────────┐                   ┌──────────────────┐
          │ vmalert-a :8505  │                   │ vmalert-b :8507  │
          │ 查 accountID 100 │                   │ 查 accountID 200 │
          └────────┬─────────┘                   └────────┬─────────┘
                   └──────────────┬───────────────────────┘
                                  ▼
                        ┌──────────────────┐
                        │ alertmanager:8504│
                        └──────────────────┘
```

**关键设计**：租户隔离贯穿**四层**——采集（独立 vmagent）、存储（accountID）、查询（vmauth 路由）、告警（独立 vmalert）。任何一层漏掉，隔离都会被击穿。

## 🚀 运行方式

### 前置条件

- WSL Ubuntu + Docker（本项目实测：Docker 29.4.1，20 核 / 31 GB）
- 镜像：`victoriametrics/{vmagent,vminsert,vmselect,vmstorage,vmauth,vmalert}:v1.151.0`
- 端口段 **8500–8507** 需空闲（避开本课程前面 12 课的实验容器）

### 三步跑起来

```bash
cd victoriametrics/projects/多租户监控平台/实现

bash p00-render.sh      # 1. 渲染两个租户各自的抓取配置与告警规则
bash p01-up.sh --reset  # 2. 拉起 11 个容器（--reset 清空数据，可重复实验）
bash p02-verify.sh      # 3. 端到端验证（14 项，全绿才算过）
```

### 跑第二遍之前（重要）

```bash
bash p21-cleanup.sh     # 停掉 11 个容器 + 清空 data（否则 p01-up.sh 会报端口被占用）
```

> ⚠ 容器占用的是**固定端口** 8500–8507。上一轮的容器还在跑就直接 `p01-up.sh`，
> 会撞 `port is already allocated`。重跑前务必先清理。

### 故障演练（第四步，建议做）

```bash
bash p14-failover.sh    # 6 项：存储宕机、采集宕机、故障域隔离、自动恢复
```

> ⚠ **故障演练总耗时约 8 分钟**，其中大部分是等待 `for: 1m` 与 `last_over_time[2m]` 窗口。
> 这不是脚本慢，是告警防抖机制本身就要求这个时间。

## 📊 实测结果速览

| 验证项 | 结果 |
|--------|------|
| 端到端验证 | **14/14 PASS** |
| 故障演练 | **6/6 PASS** |
| 租户隔离 | 100 查 tenant-b = **0 行**；200 查 tenant-a = **0 行** |
| 权限控制 | 只读写入 **400**；错误密码 **401** |
| 告警准确性 | tenant-a（5% 错误）**firing**；tenant-b（健康）**0 条** |
| 错误率口径 | 全站 **2.3%** vs 按接口 **4.7%**（稀释近一半） |
| 基数治理 | **50 条** 高基数序列 → **1 条** 聚合序列 |
| 高可用 | 单存储节点宕机，查询/写入**均正常** |
| 故障域隔离 | 停 vmagent-a，tenant-b 数据**持续增长** |

## 💡 为什么这个项目不是玩具

1. **它验证的是「坏了怎么办」，不只是「跑起来了吗」** —— 故障演练会真的杀掉存储节点和采集节点，看数据是否还活着、告警是否响。
2. **每个结论都有对照实验** —— 「labeldrop 生效了吗」不是靠看配置，而是靠两个并行 vmagent 写入不同 accountID，对比 50 条 vs 1 条序列。
3. **踩到的坑都是真的** —— 项目开发过程中踩到 6 个坑（详见[反例对照.md](反例对照.md)），其中 4 个是**静默失败**：不报错、数字看起来正常，但结论是错的。
4. **它暴露了文档不会告诉你的东西** —— 比如「单个 vmalert 无法同时服务两个租户」这个结构性约束，官方文档不会写，但它直接决定了多租户告警的架构。
