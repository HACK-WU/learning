# 阶段 2：数据怎么进来、怎么查

> 故事章节：**把老链路接进来**
> 返回：[课程目录](../../02-课程目录.md) ｜ [学习路径总览](../../01-学习路径总览.md)

## 阶段目标

- **目标**：搞清数据从哪儿进来、怎么查出去，以及为什么查询语义和 Prometheus 不完全一样
- **学习重点**：MetricsQL 与 PromQL 的差异 / 写入协议全家桶 / 基数治理
- **必须掌握**：
  - 能说清 MetricsQL 与 PromQL 的关键差异，并知道哪些会影响告警阈值
  - 能配置 Prometheus remote write 把数据接入 VictoriaMetrics
  - 能识别基数爆炸的征兆，并用 relabel 或流式聚合治理它

## 为什么这个阶段重要

阶段 1 你已经把 VictoriaMetrics 跑起来了，能用它存数据、查数据。
但要真正把生产链路迁过来，还有三件事没解决：

1. **查询语义**：我的 PromQL 迁移过去，数字会不会变？（课 3）
2. **数据入口**：生产环境的 Prometheus 怎么把数据送过来？（课 4）
3. **成本控制**：什么会让这套系统崩溃，怎么防？（课 4）

## 阶段核心结论

- **课 3**：MetricsQL 是 PromQL 的超集，官方自测兼容性 72.78%。
  迁移后**必须重校告警阈值**，尤其是用 `increase` 的规则。
  MetricsQL 扩展是**单向门**，用了就回不去 Prometheus。
- **课 4**：数据进来的方式决定了它的形态，形态决定了存储成本。
  **基数治理只有写入前两条路能根治**：relabel 丢弃、流式聚合；
  查询时 `sum by` 只是障眼法。
