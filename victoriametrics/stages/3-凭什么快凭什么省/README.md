## 阶段目标

前两个阶段回答了「为什么需要 VM」和「数据怎么进来、怎么查」。
到这一步，你已经能把 VM 用起来了。

但还差一个关键问题没回答：**凭什么？**

- 凭什么官方敢说比 Prometheus **省 7 倍存储**？
- 凭什么处理百万级序列时**省 7 倍内存**？
- 凭什么查询比 Prometheus **更快**？

这个阶段就拆开引擎盖，把这三个「凭什么」讲清楚。

## 阶段核心结论（随课程推进更新）

### 课 5 已验证

- **存储三层**：`data/`（按 TSID 排的样本）+ `indexdb/`（标签→TSID 倒排索引）+ `cache/`（热数据）
- **无 WAL**：靠 `parts.json` 原子注册保证已落盘数据一致性，
  代价是**未 flush 的内存数据（最后几秒）会丢**
- **索引可能比数据大**：实测 `items.bin` 806 KB > `values.bin` 285 KB
  → **基数控制才是省存储的真正杠杆**
- **合并是台阶式**的：实测 25→13、17→1，原子安全，
  顺带做**去重、降采样、空间回收**
- **磁盘必须留 20% 空闲**，否则合并停摆

## 阶段 3 收官：「凭什么快、凭什么省」总答案

**凭什么省（课 6）**
- 列式布局 → delta-of-delta / Gorilla XOR → ZSTD（实测 5.583 倍）
- 每样本字节：恒定 1.02 / 缓变 3.97 / 随机 6.12

**凭什么快（课 5 + 课 7）**
- MergeSet 分层 part、TSID + 倒排索引（课 5）
- hour_metric_ids 按小时分桶，**跳过 97.5% 数据不读**（scanned/read = 40.08）
- fastcache 分层：tsid 命中率 99%
- fastcache 落盘，**重启几乎不冷**

**共同前提（课 4）**
- **基数控制**。序列数翻 2 倍 → 查询耗时涨 3.5 倍；时间窗口翻 12 倍 → 耗时仅涨 1.3 倍

## 核心结论（课 6 补充）

- **课 6 压缩**：三层流水线 = 列式布局 + 值编码（delta-of-delta / Gorilla XOR）+ ZSTD（实测 5.583 倍）
- 实测每样本字节：恒定 1.02 / 缓变 3.97 / 随机 6.12
- 降采样是企业版功能，适合趋势分析，不适合 SLO 计算
- 测量方法论：验证写入用 `vm_rows_inserted_total`，测压缩用 `vm_zstd_block_*`，算存量用 `count_over_time()`
