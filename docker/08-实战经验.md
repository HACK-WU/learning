## 一、适用边界与反模式

> **"不该用"比"怎么用"更值钱。** 这是从"会用"到"用对"的分界线。

### 六个反模式（别在这些场景用容器）

| # | 反模式 | 依据 | 该用什么 |
|---|--------|------|---------|
| 1 | **需要强隔离**：多租户平台、要跑用户提交的不可信代码 | 🔵 容器**共享宿主机内核**，隔离边界弱于虚拟机（课 12、课 14） | 虚拟机，或 gVisor / Kata Containers 这类安全容器运行时 |
| 2 | **需要不同的内核 / 操作系统** | 🔵 容器共享宿主机内核——Linux 主机上跑不了 Windows 容器（课 14） | 虚拟机 |
| 3 | **一次性脚本、纯本地小工具** | ⚪ 镜像构建 + 运行链路是纯粹的额外负担，换不来"环境可复现"这个收益 | 直接跑 |
| 4 | **把容器当虚拟机用**：一个容器塞一堆服务、SSH 进去改配置 | ⚪ 违背"一个容器一个主进程"；可写层不持久，改的东西重启就没（课 3、课 10） | 拆分服务；配置走环境变量 / 卷 |
| 5 | **规模没到就上编排** | 🔵 官方对容器的定位是"high density environments 与 **small and medium deployments**"（课 14） | compose + 重启策略 + 健康检查 |
| 6 | **有状态服务却没准备好做卷与备份** | 🔵 可写层不持久，容器删除即丢（课 3、课 7） | 先解决卷 / 备份 / 恢复，或改用托管服务 |

**正面判断条件**（同时满足才值得容器化）：
- 需要**跨机器 / 跨人**复现同一个环境
- 服务之间**依赖明确**，能用一份声明描述清楚
- 团队**具备**课 15 那八条能力前提（会写 Dockerfile、会做卷备份、会配日志与监控……）

### 三条容易被忽略的边界

**其一，"环境一致"指的是应用层，不是内核层。**
镜像把 glibc、依赖、配置都固化了，但**内核是宿主机的**。所以同一个镜像在 Ubuntu 22.04 和 Debian 12 上可能表现不同——如果它碰到了内核特性差异。课 14 那句"容器共享内核"在这里从抽象概念变成了具体风险。

**其二，容器化的成本是"替换"，不是"消除"。**
课 15 那张八项清单（镜像维护 / 日志 / 监控 / 存储 / 网络 / 安全 / 交付链路 / 磁盘）不是危言耸听。最常见的失败模式是**"只做了一半"**：应用容器化了，日志和监控没跟上，于是一出问题就两眼一抹黑——偏偏容器里出问题又特别"静默"。

**其三，静默失败是容器时代的常态故障。**
课 10 的 OOM 就是典型：进程被 SIGKILL，**应用根本没机会写日志**。`docker ps` 里状态变成了 `Exited (137)`，日志里空空如也。这类故障只能靠**容器外部的观测**（`State.OOMKilled`、`docker stats`、`docker events`）发现。

## 二、高频故障模式（10 条）

> 每条五段式：**症状（可观测）→ 根因 → 排查路径 → 修复 → 预防**。
> 症状全部可观测——写"服务很慢"无效，要写"退出码 137 且日志里没有任何异常"这种。

### 故障模式 1 · 日志撑爆磁盘（默认驱动**不轮转**）

**症状**：宿主机磁盘告警，查下来 `/var/lib/docker/containers/<id>/<id>-json.log` 占了几十 GB。服务可能仍在正常运行。

**根因**：默认日志驱动是 `json-file`，而它**默认不做轮转**。这是官方明确警告过的：

> 🔵 "By default, **no log-rotation is performed**. As a result, log-files stored by the default `json-file` logging driver can cause a significant amount of disk space to be used for containers that generate much output, **which can lead to disk space exhaustion**."（课 11）

官方保留 `json-file` 为默认只为向后兼容，并明确推荐改用 `local` 驱动。

**排查路径**：
1. `docker info --format '{{.LoggingDriver}}'` —— 确认当前默认驱动
2. `docker inspect <容器> --format '{{.LogPath}}'` —— 找到日志文件在宿主机的真实位置（**不在容器里**）
3. 在宿主机上 `du -sh` 那个路径看大小

**修复**：日志驱动换成 `local`，且 `max-size` 与 `max-file` **必须成对设置**：

```bash
docker run --log-driver local --log-opt max-size=10m --log-opt max-file=3 ...
```

> ⚠️ 官方原话：`max-file` "**Only effective when `max-size` is also set**"——只写 `max-file` 轮转根本不生效，这是最常见的配置错误。

**预防**：`local` 驱动默认就有保障（20m × 5 文件 = 100MB，且默认压缩）。但仍要注意：**改 daemon 配置只影响之后创建的容器，已有的必须重建**（课 11）——这条也是故障模式 10 的成因。

### 故障模式 2 · 静默 OOM：退出码 137，日志里什么都没有

**症状**：容器半夜挂了，`docker ps` 显示 `Exited (137)`。查应用日志——**干干净净，没有任何异常堆栈**。

**根因**：`137 = 128 + 9`，即进程死于 **SIGKILL**。内核 OOM killer 杀进程时不会给应用写日志的机会。

**⚠️ 关键判定**：**137 不等于 OOM**。停止超时后的强制杀死也会产生 137。真正的判定依据是：

```bash
docker inspect <容器> --format '{{.State.OOMKilled}}'
```

只有返回 `true` 才是 OOM。

**排查路径**：
1. `docker inspect <容器> --format 'OOMKilled={{.State.OOMKilled}}  ExitCode={{.State.ExitCode}}'`
2. 若为 OOM → 看 `docker stats` 的历史峰值，对比设的 `-m`
3. 若不是 OOM → 去查停止流程（转故障模式 4）

**修复**：
- 短期：调大 `-m`，但**先测峰值**——官方原话："Perform tests to understand the memory requirements of your application before placing it into production."
- ⚠️ **JVM 类运行时特别注意**：`-Xmx` 只是总占用的一部分，还要算堆外内存、线程栈、JIT 代码缓存、GC 开销。把 `--memory` 设成刚好等于 `Xmx`，几乎必然被 OOM。
- 别走捷径：🔵 `--oom-kill-disable` 在 **cgroup v2 上会被直接丢弃**（官方原话 "is discarded on v2"）

**预防**：给所有生产容器设 `-m` / `--cpus`；用 `docker stats` 观察**峰值**（不是平均值）并留 20%–50% 余量。

### 故障模式 3 · "启动了"≠"就绪了"：偶发的 connection refused

**症状**：整套环境 `docker compose up -d` 起来，**有时**应用启动失败报 `connection refused`，手动重启一次就好。本地开发时几乎不出现，CI 里三天两头出现。

**根因**：这是 `depends_on` 短语法的经典坑。官方原话：

> 🔵 "With short syntax, Compose **does not wait for dependency services to be 'healthy'** before starting a dependent service."（课 9）

数据库"进程起来了"和"能接受连接"之间有一段初始化时间。这段窗口期里应用去连，必吃 connection refused。本地不常出现是因为开发机上数据卷是热的、初始化快。

**排查路径**：
1. 看 db 的启动时间与应用崩溃时间是否几乎重合
2. 确认 compose 里用的是不是 `depends_on: [db]` 这种短语法
3. 确认 db 服务**有没有声明 `healthcheck`**

**修复**：

```yaml
services:
  app:
    depends_on:
      db:
        condition: service_healthy      # ← 等"能连"，不是等"启动"
  db:
    image: postgres:16
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres -d orders"]
      interval: 3s
      timeout: 3s
      retries: 5
      start_period: 10s
```

> ⚠️ **这两件事必须成对出现**：`condition: service_healthy` 依赖被依赖方**确实声明了 `healthcheck`**。只写前者而后者缺失，条件永远不满足，Compose 会一直等到超时。

**预防**：任何"依赖另一个服务才能工作"的服务，都要问一句："等的是启动，还是就绪？"

### 故障模式 4 · `docker stop` 每次都等满 10 秒

**症状**：发布时 `docker stop` 卡住约 10 秒才返回。日志里应用没有收到任何关闭信号，正在处理的请求被硬打断。

**根因**：两个成因，常同时存在：

1. **`ENTRYPOINT` 用了 shell 形式**。`CMD app` 或 `ENTRYPOINT python app.py` 会让 `/bin/sh -c` 成为 PID 1，而它**不转发信号**给子进程（课 5、课 10）
2. **应用没注册信号处理器**。🔵 官方原话：

> "A process running as **PID 1** inside a container is treated specially by Linux: it **ignores any signal with the default action**. So, the process doesn't terminate on `SIGINT` or `SIGTERM` **unless it's coded to do so**."

**排查路径**：
1. `time docker stop <容器>` —— 确认是否真的是 10 秒（Linux 默认宽限期；Windows 是 30 秒）
2. `docker inspect <容器> --format '{{json .Config.Entrypoint}}'` —— 是数组（exec 形式）还是字符串（shell 形式）
3. 进容器 `cat /proc/1/cmdline` —— 看 PID 1 到底是谁

**修复**：
- Dockerfile 改用 exec 形式：`ENTRYPOINT ["python", "app.py"]`
- 应用里注册 SIGTERM 处理器，做清理后主动退出
- 兜底可加 `--init`（用 tini 当 PID 1，转发信号 + 回收僵尸进程）

**预防**：把"能在 10 秒内优雅退出"写进发布检查清单。

### 故障模式 5 · 数据随容器一起没了

**症状**：两种情况，都很痛：
- **A**：更新镜像后 `docker rm` + `docker run`，之前产生的数据全没了
- **B**：执行了 `docker compose down -v`，数据库数据全没了

**根因**：
- A：数据写在容器的**可写层**。🔵 官方原话（课 3、课 7）：可写层与容器同生命周期，容器删除时其上未存于持久存储的所有改动一并消失
- B：🔵 `-v` 会删除 compose 文件 `volumes` 段声明的**具名卷**（课 9）。而 `down` **不加 `-v`** 时具名卷是保留的

**排查路径**：
1. `docker inspect <容器> --format '{{json .Mounts}}'` —— 看数据目录到底挂没挂卷
2. `docker volume ls` —— 卷还在不在
3. 如果卷在但容器是新的，检查是不是**匿名卷**：🔵 官方原话——匿名卷"don't have a stable name, they are **not automatically mounted by a subsequent `up`**"

**修复**：
- 所有需要持久化的目录挂**具名卷**或 bind mount
- `down` 与 `down -v` 的区别写进团队规范：`down` 是"收工"，`down -v` 是"拆家"
- 定期备份（课 7 的 `--volumes-from` + `tar` 套路；生产用数据库自带工具）

**预防**：`docker inspect` 确认挂载，是上线前的必查项。

### 故障模式 6 · 服务名 ping 不通（`bad address`）

**症状**：`docker exec app ping postgres` 报 `ping: bad address 'postgres'`。改成 IP 能通，但重启后 IP 会变。

**根因**：两个可能，按概率排序：
1. **不在同一个自定义 bridge 网络**。🔵 官方原话：服务发现只解析**自定义容器名**；默认 bridge 网络上只能靠 IP 或 legacy `--link`
2. **对方容器没有 `--name`**（或 compose 服务名写错）

**排查路径**（课 8 的"网络排障三步"）：
1. `docker network inspect <网络> --format '{{range .Containers}}{{.Name}} {{end}}'` —— 双方都在吗
2. `docker exec <容器> cat /etc/resolv.conf` —— **看到 `127.0.0.11` 才说明用的是内嵌 DNS**（即它挂在自定义网络上）；若是宿主机 resolv.conf 的副本，说明挂在默认 bridge 上
3. `docker exec <容器> ping -c 2 <对方名>`

**修复**：两个容器都挂到同一个用户自定义 bridge 网络，并都用 `--name`（或 compose 服务名）。

> 🔵 官方定论："**User-defined bridge networks are superior to the default `bridge` network.**" 且默认 bridge "is **considered a legacy detail of Docker** and is **not recommended for production use**"。

**预防**：compose 会自动创建项目网络，所以**用 compose 就自动解决了**（课 9 的隐式 default 网络）。

### 故障模式 7 · 镜像又大、构建又慢

**症状**：镜像几百 MB 甚至 GB 级；改一行代码，构建要跑好几分钟——明明只改了一行。

**根因**（三者常叠加）：
1. **`COPY` 顺序不对**：`COPY . .` 写在安装依赖之前，导致改任何文件都重装依赖（课 4）
2. **没用多阶段构建**：编译工具链、SDK、pip 缓存全进了最终镜像（课 6）
3. **没有 `.dockerignore`**：`.git`、本地依赖目录、甚至 `.env` 全被塞进构建上下文（课 4、课 12）

**排查路径**：
1. `docker history <镜像>` —— 逐层看体积，找大头
2. `docker build --progress=plain` —— 看哪些层显示 `CACHED`、哪些被重跑
3. 检查 `.dockerignore` 存不存在

**修复**：
- 依赖清单单独一层、放在代码之前
- 上多阶段构建，只把构建产物拷进运行时镜像
- 补 `.dockerignore`

**预防**：把镜像体积设为**非功能约束**（比如 < 150MB）并在 CI 里核——这正是结课项目采用的办法。

### 故障模式 8 · 密钥烤进了镜像层，删不掉

**症状**：安全扫描报告镜像里疑似有凭据；或者更隐蔽——一切正常，直到有人把镜像推到了公开仓库。

**根因**：两种写法都会留下痕迹：
- **`ARG`**：🔵 `docker history` 里能看到明文（课 6、课 12）
- **`COPY` 密钥文件**：即使后面一层 `rm` 掉，🔵 数据仍在下层——这正是课 3 讲的"在容器里 `rm` 删不掉体积"的同一套机制

**排查路径**：

```bash
docker history <镜像> --no-trunc | grep -iE 'password|secret|token|api[_-]?key'
```

**修复**：
- 构建期密钥改用 `RUN --mount=type=secret`（课 5、课 12）
- ⚠️ **重建镜像并不能救回已泄露的密钥——必须轮换**
- 官方在缓存后端文档里也强调了同一条：构建里的凭据"ensure you manipulate them using the dedicated **`--secret`** option... `COPY` or `ARG` **could result in leaked credentials**"

**预防**：把上面那条 `docker history | grep` 做成 CI 的**发布闸门**（课 13）。

### 故障模式 9 · 以 root 运行 + 挂载 docker.sock

**症状**：安全团队开出的高危项；或者在共享环境里，A 同事的容器能影响 B 同事的容器。

**根因**：三个叠加的错误认知：
1. 以为"容器里的 root 是假的"——🔵 官方原话："The default user within a container is **`root` (uid = 0)**"（课 12）
2. 用了 `--privileged`——🔵 官方警告："A container with `--privileged` is **not a securely sandboxed process**. Containers in this mode can **get a root shell on the host**."
3. 挂载了 `/var/run/docker.sock`——🔵 官方原话：这会给容器 "**full access to create and manipulate the host's Docker daemon**"

**排查路径**：
1. `docker inspect <容器> --format 'Privileged={{.HostConfig.Privileged}}'` —— 应为 false
2. `docker inspect <容器> --format '{{.Config.User}}'` —— **为空即仍是 root**
3. `docker inspect <容器> --format '{{json .Mounts}}'` —— 有没有挂 docker.sock 或 `/:/host`

**修复**：
- Dockerfile 加 `USER`（🔵 官方称为防止提权攻击的 **"best way"**）
- 用 `--cap-drop=ALL` 再按需 `--cap-add`
- 加 `--read-only`、`no-new-privileges`
- **绝不挂载 docker.sock 与宿主机根目录**

**预防**：写进团队规范（结课项目 README 里那份 11 条必做 + 5 条禁止可以直接抄）。

### 故障模式 10 · 改了 daemon 配置，容器毫无反应

**症状**：改了 `/etc/docker/daemon.json` 的日志配置（或 resource 相关配置），重启 Docker 后——已有容器的行为**完全没变**。

**根因**：🔵 官方原话（课 11）：

> "Existing containers **don't use the new logging configuration automatically**. To update the logging driver for a container, the container has to be **re-created** with the desired options."

容器在创建时就把配置快照进了自己的 `HostConfig`，之后 daemon 怎么改都与它无关。

**排查路径**：

```bash
docker inspect <容器> --format '{{.HostConfig.LogConfig.Type}}'
```

看它实际用的是什么——多半还是创建时的旧值。

**修复**：**重建容器**（`docker rm` + `docker run`，或 compose 的 `up -d --force-recreate`）。

**预防**：把 daemon 级配置变更纳入变更管理：改完需要滚动重建所有存量容器才真正生效。

## 三、落地 Checklist

> 抄进你的项目 README，作为"容器化上岗清单"。**八条正好对应课 4–13 的主线。**

- [ ] 会写并维护 **Dockerfile**：依赖层前置、多阶段、`.dockerignore`（课 4–6）
- [ ] 理解**数据不能放容器层**，卷的备份与恢复跑通过一次（课 7）
- [ ] 会配**自定义网络**与端口发布，且知道 `-p` 默认绑 `0.0.0.0`（课 8）

- [ ] 会设**资源限制**与**重启策略**（课 10）

**再加三条"红线"自查**：

```bash
# 有没有 privileged
docker ps --format '{{.Names}}' | while read c; do
  [ "$(docker inspect "$c" --format '{{.HostConfig.Privileged}}')" = "true" ] && echo "⛔ $c"
done

# 有没有仍以 root 运行
docker ps --format '{{.Names}}' | while read c; do
  [ -z "$(docker inspect "$c" --format '{{.Config.User}}')" ] && echo "⚠️ $c 未指定 USER"
done

# 有没有用 latest（生产不该用）
docker images --format '{{.Repository}}:{{.Tag}}' | grep ':latest'
```

## 四、事故案例（如实留空）

> **本节不填。**

其他课程的这一章会放真实事故复盘（时间线、损失、根因、改进项）。本课程**不提供**，原因如实说明：

1. **本机 Docker 守护进程未运行**，无法产出 🟢 实测数据
2. 凭记忆或想象写"某次事故"会**违反证据纪律**——那些数字、报错、时间线都不可溯源
3. 二手案例同样不收：zookeeper 课程在评审时就把 Pinterest 这类二手案例**排除**出了事故章节，理由是"不可虚构"

**如果你想要这一章**：最好的来源是你自己的生产环境。建议的采集格式：

```
## 事故：<一句话现象>
- 时间：<发生时间>  影响：<范围与时长>
- 现象（可观测）：<报错原文 / 指标数值>
- 根因：<对应本文档的故障模式 N>
- 修复：<做了什么>
- 改进项：<为了防止复发，改了什么>
```

把它填进本节，这份文档才真正属于你的团队——**别人的事故只能让你"读过"，你自己的事故才能让你"记住"**。
