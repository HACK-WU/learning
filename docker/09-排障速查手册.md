## 🔴 条目 1 · 日志撑爆磁盘（默认不轮转）

**一眼识别**：宿主机磁盘告警；`/var/lib/docker/containers/<id>/<id>-json.log` 体积异常。服务本身可能仍在正常运行。

**关键特征：这是"慢性失血"——服务一直通，磁盘一天天涨满。**

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 清空该容器的日志（先确认服务允许），或临时停掉高频输出 | 磁盘不再上涨 |
| 定位 1 | `docker info --format '{{.LoggingDriver}}'` | 若是 `json-file` 且未配轮转 → 命中 |
| 定位 2 | `docker inspect <容器> --format '{{.LogPath}}'` | 拿到日志在**宿主机**上的真实路径（不在容器里） |
| 定位 3 | 在宿主机上 `sudo du -sh <上一步的路径>` | 确认是不是它占的 |
| 修复 | 日志驱动换 `local`，且 **`max-size` 与 `max-file` 成对设置**：<br>`docker run --log-driver local --log-opt max-size=10m --log-opt max-file=3 ...` | 开始轮转，占用封顶 |
| 若无效 | → 检查是不是别的东西在涨：`docker system df` 看四类分项 | — |

**⚠️ 两个必踩的坑**：
- **只写 `max-file` 不生效**。🔵 官方原话："Only effective when `max-size` is also set."
- **改 daemon 配置对已有容器无效**，必须重建 → 转[条目 10](#-条目-10--改了-daemon-配置不生效)

**预防**：统一用 `local` 驱动（🔵 默认就轮转：20m × 5 文件 = 100MB，且默认压缩）。

**原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 1

## 🔴 条目 2 · 静默 OOM（退出码 137）

**一眼识别**：`Exited (137)`，且**应用日志里没有任何异常**。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 先确认业务是否可重启；重建容器并临时放宽 `-m` | 服务恢复 |
| 定位 1 | `docker inspect <容器> --format 'OOMKilled={{.State.OOMKilled}}'` | **`true` 才是 OOM** |
| 定位 2 | 若 `OOMKilled=false` → 不是 OOM，137 也可能是停止超时被强杀 → 转[条目 4](#-条目-4--docker-stop-每次等满-10-秒) | — |
| 定位 3 | 确认 OOM 后：回顾 `docker stats` 的**峰值**，对比设的 `-m` | 峰值接近上限即确认 |
| 修复 | 按**峰值**调大 `--memory`，留 20%–50% 余量 | 不再触发 |
| 若无效 | ⚠️ 若是 JVM：`-Xmx` 只是总占用的一部分，还要算堆外内存 / 线程栈 / JIT 代码缓存 / GC 开销 | — |

**⚠️ 不要走的两条捷径**：
- `--oom-kill-disable`：🔵 在 **cgroup v2 上会被直接丢弃**（官方原话 "is discarded on v2"）
- `--oom-score-adj` 极端值：官方不建议用它绕过保护

**预防**：所有生产容器设 `-m` / `--cpus`；🔵 官方原话——"Perform tests to understand the memory requirements of your application before placing it into production."

**原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 2

## 🟡 条目 3 · 依赖未就绪（connection refused 玄学故障）

**一眼识别**：应用启动时报 `connection refused`；**手动重启一次就好**；本地少见、CI 里常见。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 重启应用服务：`docker compose restart app` | 通常立刻恢复（db 此时已就绪） |
| 定位 1 | 看 db 的启动时间与应用崩溃时间是否几乎重合 | 重合 → 命中 |
| 定位 2 | 检查 compose 里是不是 `depends_on: [db]` **短语法** | 🔵 短语法**不等就绪** |
| 定位 3 | 检查 db 服务**有没有 `healthcheck`** | 没有 → 即使写了 `service_healthy` 也永远等不到 |
| 修复 | 改成 `condition: service_healthy`，**并给 db 补 `healthcheck`**：<br>`test: ["CMD-SHELL", "pg_isready -U postgres -d orders"]` | 应用等 db 真正能连了才起 |
| 若无效 | → 检查双方是否在同一网络 → 转[条目 6](#-条目-6--服务名-ping-不通) | — |

**⚠️ 这两件事必须成对出现**：`condition: service_healthy` + 被依赖方声明 `healthcheck`。缺后者，Compose 会一直等到超时。

**预防**：任何"依赖别的服务才能工作"的服务，都要问："等的是启动，还是就绪？"

**原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 3

## 🟡 条目 4 · `docker stop` 每次等满 10 秒

**一眼识别**：`docker stop` 卡住约 **10 秒**（Linux 默认宽限期；Windows 是 30 秒）才返回；应用没收到关闭信号，正在处理的请求被硬打断。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 暂无（这是发布期体验问题，不是故障）；可临时用 `docker stop -t <秒数>` 缩短等待 | 更快返回，但应用仍不优雅 |
| 定位 1 | `docker inspect <容器> --format '{{json .Config.Entrypoint}}'` | **数组** = exec 形式（对）；**字符串** = shell 形式（错） |
| 定位 2 | `docker exec <容器> cat /proc/1/cmdline` | 看 PID 1 是谁。若是 `sh -c`，信号不会转发 |
| 定位 3 | 确认应用有没有注册 SIGTERM 处理器 | 🔵 PID 1 会**忽略默认动作的信号**，不注册就收不到 |
| 修复 | ①Dockerfile 改 exec 形式：`ENTRYPOINT ["python","app.py"]`<br>②应用注册 SIGTERM 处理器做清理后退出<br>③兜底：`--init`（tini 转发信号 + 回收僵尸） | 秒退 |
| 若无效 | → 用 `docker logs` 确认应用是否真的收到了 SIGTERM | — |

**预防**：把"能在 10 秒内优雅退出"写进发布检查清单。

**原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 4

## 🔴 条目 5 · 数据随容器一起没了

**一眼识别**（两种）：**A** 更新镜像后 `rm` + `run`，数据没了；**B** 执行了 `docker compose down -v`，数据库数据没了。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 立刻停止对该环境的一切写操作；若有备份，先复制一份当前卷目录留证 | 避免二次破坏 |
| 定位 1 | `docker inspect <容器> --format '{{json .Mounts}}'` | 看数据目录**到底挂没挂卷** |
| 定位 2 | `docker volume ls` | B 情况：卷是否已被删 |
| 定位 3 | 若卷在但换了新容器：检查是不是**匿名卷** | 🔵 匿名卷没有稳定名字，**不会被后续 `up` 自动挂回** |
| 修复 | A：改用**具名卷**（或 bind mount）重建<br>B：从备份恢复；无备份则数据不可恢复 | — |
| 若无效 | → 检查 `docker system prune --volumes` 是否被误执行过 | — |

**⚠️ 最关键的一条**：`down` 是"收工"，`down -v` 是"拆家"。🔵 `-v` 会删除 compose 文件 `volumes` 段声明的**具名卷**。

**预防**：卷的备份用课 7 的套路跑通一次（临时容器 + `--volumes-from` + `tar`）；生产用数据库自带工具（`pg_dump` 等），别直接 tar 正在被写入的目录。

**原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 5

## 🟡 条目 6 · 服务名 ping 不通

**一眼识别**：`docker exec app ping postgres` → `ping: bad address 'postgres'`。改成 IP 能通，但重启后 IP 会变。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 临时写死 IP 应急（不推荐长期使用） | 连通恢复 |
| 定位 1 | `docker network inspect <网络> --format '{{range .Containers}}{{.Name}} {{end}}'` | 双方容器名**都在**列表里吗 |
| 定位 2 | `docker exec <容器> cat /etc/resolv.conf` | **看到 `127.0.0.11` 才说明用的是内嵌 DNS**（挂在自定义网络上）；若像宿主机 resolv.conf 的副本 → 挂在默认 bridge 上 |
| 定位 3 | 确认对方有没有 `--name` | 🔵 服务发现只解析**自定义容器名**，不解析自动生成的名字 |
| 修复 | 两容器挂到同一个**用户自定义 bridge 网络**，并都指定 `--name`：<br>`docker network create app-net` → `docker run --network app-net --name db ...` | 按名可 ping 通 |
| 若无效 | → 检查是否跨网络（不同 bridge 之间只能经已发布端口通信） | — |

**⚠️ 端口相关**：同一自定义网络内互访**不需要 `-p` 也不需要 `EXPOSE`**——🔵 官方原话：同一自定义 bridge 上的容器"effectively expose **all ports** to each other"。

**预防**：用 compose 就自动解决了（compose 会为每个项目创建网络）。

**原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 6

## ⚪ 条目 7 · 镜像大 / 构建慢

**一眼识别**：镜像几百 MB 甚至 GB；改一行代码却触发了依赖重装。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 无（不影响正确性，跳过也可） | — |
| 定位 1 | `docker history <镜像>` | 逐层看体积，找出大头 |
| 定位 2 | `docker build --progress=plain . 2>&1 \| grep -E 'CACHED\|RUN\|COPY'` | 看哪些层命中缓存、哪些被重跑 |
| 定位 3 | 检查有没有 `.dockerignore` | 缺了会把 `.git` / 本地依赖目录全塞进上下文 |
| 修复 | ①依赖清单 `COPY` 放在代码**之前**<br>②上多阶段构建，只拷贝构建产物<br>③补 `.dockerignore` | 体积下降、改代码不再重装依赖 |
| 若无效 | → `docker system df` 检查是不是构建缓存在堆积（`docker builder prune` 清理） | — |

**预防**：把镜像体积设为**非功能约束**并在 CI 里核对。

**原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 7

## 🔴 条目 8 · 密钥烤进镜像层

**一眼识别**：`docker history` 里能看到明文凭据；或安全扫描报镜像含 secrets。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | **立刻轮换该凭据**。重建镜像**不能**救回已泄露的密钥 | 泄露失效 |
| 定位 | `docker history <镜像> --no-trunc \| grep -iE 'password\|secret\|token\|api[_-]?key'` | 命中即有明文 |
| 修复 | 构建期密钥改用 `--mount=type=secret`：<br>`RUN --mount=type=secret,id=mytoken ...`<br>`docker buildx build --secret id=mytoken,src=./token.txt .` | history 里不再有明文 |
| 若无效 | → 检查 compose / 环境变量里是不是还有明文 | — |

**⚠️ 为什么删不掉**：`COPY` 了再 `rm`、或用 `ARG` 传——数据仍在**下层**。这与课 3 讲的"在容器里 `rm` 删不掉体积"是同一套机制。

🔵 官方警告：构建里的凭据必须用 `--secret`，"Manually managing secrets using `COPY` or `ARG` **could result in leaked credentials**"。

**预防**：把上面那条 `docker history | grep` 做成 CI 的**发布闸门**。

**原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 8

## 🔴 条目 9 · 权限过大（root / `--privileged` / docker.sock）

**一眼识别**：容器里 `id` 是 `uid=0(root)`；或启动参数里有 `--privileged`；或挂载了 `/var/run/docker.sock`、`-v /:/host`。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 立刻重建容器，去掉 `--privileged`、docker.sock、`-v /:/host` | 暴露面收回 |
| 定位 1 | `docker inspect <容器> --format 'Privileged={{.HostConfig.Privileged}}'` | 应为 **false** |
| 定位 2 | `docker inspect <容器> --format '{{.Config.User}}'` | **为空 = 仍是 root** |
| 定位 3 | `docker inspect <容器> --format '{{json .Mounts}}'` | 有没有挂 docker.sock 或 `/:/host` |
| 修复 | ①Dockerfile 加 `USER`（🔵 官方称为防提权的 **best way**）<br>②`--cap-drop=ALL` 再按需 `--cap-add`<br>③`--read-only` + `no-new-privileges` | 三重收敛 |
| 若无效 | → 检查基础镜像是不是自带 root 默认用户 | — |

**三条绝对不要做**（官方依据）：
- `--privileged`：🔵 "**not a securely sandboxed process**"，容器可"get a root shell on the host"
- 挂载 `/var/run/docker.sock`：🔵 等于交出"full access to create and manipulate the host's Docker daemon"
- `-v /:/host`：容器里的 root 能直接读写宿主机任意文件

**预防**：用结课项目 README 里那份"11 条必做 + 5 条禁止"直接抄进团队规范。

**原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 9

## ⚪ 条目 10 · 改了 daemon 配置不生效

**一眼识别**：改了 `/etc/docker/daemon.json`（日志驱动、资源相关等）并重启 Docker，但**已有容器行为没变**。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 无（配置变更类问题） | — |
| 定位 | `docker inspect <容器> --format '{{.HostConfig.LogConfig.Type}}'` | 多半仍是**创建时**的旧值 |
| 修复 | **重建容器**：`docker rm` + `docker run`；compose 用 `up -d --force-recreate` | 新配置生效 |
| 若无效 | → 确认 Docker 是否真的重启了；`docker info` 看当前生效配置 | — |

🔵 官方原话："Existing containers **don't use the new logging configuration automatically**. To update the logging driver for a container, the container has to be **re-created**."

**预防**：把 daemon 级配置变更纳入变更管理——改完需要**滚动重建所有存量容器**才真正生效。

**原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 10
