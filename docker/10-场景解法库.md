## 场景 1：新人入职，要一键跑起整套环境

**场景描述**：新人第一天，照着 Wiki 上的四条长命令敲，漏了一个 `--network` 排查一下午。你想做成"克隆仓库 + 一条命令"就能跑起来——包括数据库、缓存、应用和入口代理，并且**要能反复重建而不丢演示数据**。

**🔒 先自己想 30 秒**：你的第一反应是不是"把所有服务写进 `compose.yaml`，然后 `docker compose up -d` 就完了"？那如果要跑第二套互不干扰的副本呢？如果想保留演示数据呢？

<details><summary>💡 提示（分层想）</summary>

分三层问自己：

1. **描述层**：这套环境有哪些"东西"需要被记住？服务、数据、网络——分别对应 compose 的哪些顶层段？
2. **隔离层**：两套副本同时跑会不会撞名？项目名在这件事里扮演什么角色？
3. **持久层**：`up -d` / `down` / `down -v` 三者的差别，哪一个是"收工"、哪一个是"拆家"？

</details>

<details><summary>📖 展开解法</summary>

### 解法一览

| 解法 | 能解决到 | 代价 | 适用边界 |
|---|---|---|---|
| **A · 一份 compose.yaml + 具名卷 + 顶层 networks** | 一键起停；数据在卷里不随容器消失；服务名即 DNS 名 | 需要维护一份 YAML；团队要接受 compose 语法 | 单机 / 小团队（**绝大多数情况**） |
| **B · 顶层 `name` 或 `-p` 区分多套副本** | 同一份文件不改一字部署多套，资源互不干扰 | 卷 / 网络名都带前缀，运维时要认得清 | 需要并行多环境（如每人一套） |
| **C · 直接上编排平台** | 跨机调度、自愈 | 学习曲线与运维成本**本身就要立项**（课 14、15） | 真的需要多机调度与自愈时 |

### 推荐路径

**A → B**（先做 A，需要多套时再加 B）。C 在这个场景**不要做**——单机遇不到它的收益。

关键的三条官方依据：
- **隐式 default 网络**：🔵 "If `networks` is empty or absent from the Compose file, Compose considers an implicit definition for the service to be connected to the `default` network."——所以你**不用手写 `--network`**，服务名就能当 DNS 用
- **服务间通信不需要 `links`**：🔵 "**Links are not required to enable services to communicate.**"
- **具名卷独立于容器**：`down` 不删具名卷；`down -v` 才删

### 知识点挂钩

课 7（卷）· 课 8（网络 / 服务名 DNS）· 课 9（compose / 项目名 / down 语义）

### 不适用

- 需要跨机调度与自愈 → 转场景 8
- 环境里包含必须跑在宿主机上的东西（如特定内核模块）→ 容器化不了

### 做错会踩的坑

- 用**匿名卷**：🔵 官方原话——匿名卷"don't have a stable name, they are **not automatically mounted by a subsequent `up`**"。重建后数据"看起来没了"
- `down -v` 当成常规收工命令：🔵 它会删除 compose 文件 `volumes` 段声明的**具名卷**
- 服务没写 `healthcheck` 却指望 `depends_on` 等就绪 → 转场景 4

</details>

## 场景 2：镜像 800MB，构建 10 分钟

**场景描述**：镜像 800MB，改一行代码要等 10 分钟构建，其中 8 分钟在重装依赖。你想让它小一点、快一点。

**🔒 先自己想 30 秒**：第一反应是不是"换个更小的基础镜像"？换成 alpine 之后，体积能降多少、会带来什么新麻烦？

<details><summary>💡 提示（分层想）</summary>

1. **顺序**：改代码为什么会重装依赖？触发缓存失效的是哪一条指令？
2. **产物**：最终镜像里，哪些东西**只有构建时需要**？（编译器、SDK、包管理器缓存……）
3. **地基**：换基础镜像省的是哪部分体积？如果换来的代价是"每次装依赖都要从源码编译"，这个交换划算吗？

</details>

<details><summary>📖 展开解法</summary>

### 解法一览

| 解法 | 能解决到 | 代价 | 适用边界 |
|---|---|---|---|
| **A · 依赖清单单独一层，放在 `COPY` 代码之前** | 改代码不再重装依赖 | 几乎为零 | **必做**，与后面几条不冲突 |
| **B · 多阶段构建** | 构建工具链不进最终镜像，常是**最大的一块**收益 | Dockerfile 稍复杂 | 有编译 / 构建步骤的语言 |
| **C · 补 `.dockerignore`** | 构建上下文瘦身；顺带挡住 `.env` / `.git` 进镜像 | 几乎为零 | **必做**（课 4、课 12） |
| **D · 换更小的基础镜像**（slim / alpine / distroless） | 进一步压体积 | ⚠️ **musl 兼容性风险**；distroless 无 shell 难排障 | 见下方"不适用" |

### 推荐路径

**A → C → B → D**（按"代价递增、收益递减"排序）。**D 放最后**——它最省体积，也最容易引入新问题。

关于 D 的权衡表（课 6 已标注 ⏳ 置信度）：

| 候选 | 优点 | 代价 |
|---|---|---|
| `python:3.12-slim` 一类（glibc 系 slim） | wheel 生态无障碍，体积可接受 | 比 alpine 大几十 MB |
| `alpine`（musl） | 最小 | 🔵 官方明确警示 musl 兼容性风险；⏳ 领域认知：部分 wheel 装不上，需现场编译 |
| `distroless` | 攻击面最小 | 无 shell，**排障极其难受** |

### 知识点挂钩

课 4（分层与缓存失效）· 课 6（多阶段 / 基础镜像选型）· 课 12（`.dockerignore` 挡密钥）

### 不适用

- 有强合规要求且不需要进容器调试 → distroless 反而合适
- 改代码频繁但依赖极稳定 → A 的收益最大，B 收益有限

### 做错会踩的坑

- 先 `COPY . .` 再装依赖：**任何**文件改动都会让依赖层缓存失效
- 只做 D 不做 A/B/C：换了个小地基，上面仍堆着编译器和缓存
- 忽视 `.dockerignore`：`.git` 和本地依赖目录悄悄进了上下文，甚至把 `.env` 带进去 → 转场景 7

</details>

## 场景 3：服务要上生产，怎么加固

**场景描述**：安全扫描报告第一条就是"容器以 root 运行"。你想在不影响功能的前提下把攻击面收下来。

**🔒 先自己想 30 秒**：第一反应是不是"加 `--privileged` 让它先跑起来"？或者"全 `cap_drop` 了要是某个功能需要权限怎么办"？

<details><summary>💡 提示（分层想）</summary>

1. **身份层**：容器里跑的进程是 root 吗？官方说防止提权攻击的"best way"是什么？
2. **能力层**：root 的权力能不能被切成小块、按需发放？
3. **文件系统层**：应用真的需要写根文件系统吗？
4. **边界层**：如果加了 `--privileged`，容器还能算"沙箱"吗？

</details>

<details><summary>📖 展开解法</summary>

### 解法一览

| 解法 | 能解决到 | 代价 | 适用边界 |
|---|---|---|---|
| **A · Dockerfile 加 `USER`**（非 root） | 消除"容器内是 root"这一最大面 | 需处理文件属主；绑特权端口要额外能力 | 🔵 官方称为防提权的 **best way**，**应默认做** |
| **B · `--cap-drop=ALL` 再按需 `--cap-add`** | 能力最小化 | 需要搞清楚应用到底要哪些能力 | 所有生产容器 |
| **C · `--read-only` + `tmpfs`** | 根文件系统不可写 | 需要写的地方要显式挂 tmpfs / 卷 | 无状态服务最合适 |
| **D · `no-new-privileges`** | 让 `su` / `sudo` 类提权失效 | 几乎为零 | 所有生产容器 |
| ⛔ **`--privileged`** | — | 🔵 官方："**not a securely sandboxed process**"，可"get a root shell on the host" | **永远不要作为"先跑起来"的手段** |

### 推荐路径

**A → B → D → C**（C 视应用是否真的需要写盘而定）。**永远不要选 `--privileged`。**

配套两条：
- **资源限制** `-m` / `--cpus`（课 10）——防的是"拖垮邻居"
- **镜像扫描进 CI**（课 13）——防的是漏洞堆积

### 知识点挂钩

课 12（降权 / 能力收敛 / 只读根）· 课 10（资源限制）· 课 11（健康检查）

### 不适用

- 需要加载内核模块、操作宿主机设备 → 容器做不到，用虚拟机（课 14）
- 应用确实要绑 80/443 → 加 `--cap-add=NET_BIND_SERVICE`，而不是全放开；或改监听高位端口由反代转发

### 做错会踩的坑

- 用 `--privileged` "先跑起来再说"：官方警告它能拿宿主机 root shell
- 挂载 `/var/run/docker.sock`：🔵 等于交出"full access to create and manipulate the host's Docker daemon"
- `-v /:/host`：容器里的 root 能读写宿主机任意文件
- 只加 `USER` 不处理属主：应用启动报权限错误，然后有人"临时"改回 root

</details>

## 场景 4：多服务依赖，启动顺序怎么排

**场景描述**：应用依赖数据库和缓存。`docker compose up -d` 后**有时**应用启动失败报 `connection refused`，手动 `restart` 一次就好。本地很少见，CI 里三天两头发生。

**🔒 先自己想 30 秒**：第一反应是不是"在应用里加重试逻辑"？加了重试之后，这个偶发故障就真的消失了吗？如果数据库永远起不来呢？

<details><summary>💡 提示（分层想）</summary>

1. **语义层**：`depends_on` 保证的是"启动"还是"就绪"？官方原话怎么说？
2. **成对性**：要让 Compose 等到"就绪"，需要几个东西同时存在？少一个会怎样？
3. **兜底层**：就算顺序对了，长跑过程中数据库重启了怎么办——启动顺序解决不了这一类问题

</details>

<details><summary>📖 展开解法</summary>

### 解法一览

| 解法 | 能解决到 | 代价 | 适用边界 |
|---|---|---|---|
| **A · `depends_on` + `condition: service_healthy`，并给被依赖方写 `healthcheck`** | 启动期不再抢跑 | 需要为被依赖方写健康检查命令 | **首选** |
| **B · 应用内连接重试 + 退避** | 覆盖**运行期**的依赖闪断 | 要写重试逻辑，且要设上限 | 生产必备（A 解决不了运行期） |
| **C · 启动脚本 sleep 若干秒** | 掩盖问题，碰运气 | 慢机器上仍失败；快机器上白等 | ❌ 不推荐 |
| **D · `service_completed_successfully`** | 等一次性任务（迁移 / 初始化）跑完 | 仅适用于会退出的服务 | 迁移场景 |

### 推荐路径

**A + B 一起做**。它们解决的是两个不同的时间窗：

- **A 管启动期**：Compose 等 db 的 `healthcheck` 通过后才启动 app
- **B 管运行期**：db 运行中重启、网络闪断，应用自己能重连

⚠️ **A 必须成对**：`condition: service_healthy` **依赖被依赖方确实声明了 `healthcheck`**。只写前者而后者缺失，条件永远不满足，Compose 会一直等到超时——这是最常见的失败用法。

### 知识点挂钩

课 9（`depends_on` 三种 condition / healthcheck）· 课 11（健康检查三态）

### 不适用

- 依赖根本不会"就绪"的服务（如纯静态资源）→ 用 `service_started` 即可
- 需要跨机等待 → 超出 compose 能力，转场景 8

### 做错会踩的坑

- 只写 `condition: service_healthy` 不给 db 加 `healthcheck`
- 用 `sleep 30` 代替健康检查：慢机器上照样失败
- 以为 A 能替代 B：启动顺序**管不了**运行期的依赖重启

</details>

## 场景 5：数据库放不放进容器

**场景描述**：本地和 CI 都用容器跑 Postgres，很方便。要上生产了，有人问："生产你也敢把数据库放容器里？"

**🔒 先自己想 30 秒**：这个问题真正问的是什么？是"容器能不能跑数据库"，还是"**谁负责备份与恢复**"？

<details><summary>💡 提示（分层想）</summary>

1. **能力层**：容器跑数据库有没有技术障碍？（想想卷和备份）
2. **责任层**：备份、恢复、升级、故障切换——这些活儿谁干？
3. **一致性层**：如果本地用容器、生产用托管，"环境一致"这个最大收益还剩多少？

</details>

<details><summary>📖 展开解法</summary>

### 解法一览

| 解法 | 能解决到 | 代价 | 适用边界 |
|---|---|---|---|
| **A · 全环境容器化 + 具名卷** | 环境完全一致；新人零配置 | 备份 / 恢复 / 升级的责任在你 | 小团队、能自己管住备份 |
| **B · 生产用托管，本地 + CI 用容器** | 生产省运维；开发体验不变 | 需要保证两边版本与配置一致 | 团队无 DBA 能力，**最常见的折中** |
| **C · 全托管** | 最省运维 | 开发与生产有差异（版本、扩展、参数） | 团队小、对一致性要求不高 |
| **D · 容器化但不做备份** | — | ❌ 数据随卷一起丢 | **永远不要** |

### 推荐路径

**B**（生产托管 + 本地/CI 容器化），除非你的团队明确具备自管数据库的能力，才走 A。

无论选哪个，**这三条不能省**：
- 数据在**具名卷**里，不在容器层（课 7）
- 备份**演练过恢复**——没恢复过的备份等于没有备份
- 生产用数据库自带工具（`pg_dump` 等），别直接 tar 正在被写入的目录

### 知识点挂钩

课 7（卷 / 备份恢复）· 课 9（`down -v` 的风险）· 课 15（成本与风险清单）

### 不适用

- 选了 A 却没人负责备份 → 迟早出事（对应[故障模式 5](08-实战经验.md)）
- 数据库需要特殊内核调优 / 特定内核模块 → 容器的局限性（课 14）

### 做错会踩的坑

- 用**匿名卷**：重建后不自动挂回，数据"看起来没了"
- `docker compose down -v` 当常规收工：🔵 会删掉 compose 声明的具名卷
- 备份了但从没恢复演练过：真正出事时才发现备份不可用

</details>

## 场景 6：日志和监控怎么建

**场景描述**：服务半夜挂了，`Exited (137)`，日志里**什么都没有**。你想建一套能真正发现问题的可观测性。

**🔒 先自己想 30 秒**：第一反应是不是"把日志采集 agent 装进每个容器"？那 OOM 这种"应用没机会写日志"的情况，容器内部的 agent 能发现吗？

<details><summary>💡 提示（分层想）</summary>

1. **日志层**：日志默认写到哪？会不会撑爆磁盘？轮转怎么配？
2. **指标层**：容器里 `free` / `top` 看到的数字可信吗？真实数据在哪？
3. **状态层**：`docker ps` 显示 `Up` 能说明服务可用吗？
4. **外部视角**：哪些信息是**必须**从容器外才能观测到的？

</details>

<details><summary>📖 展开解法</summary>

### 解法一览

| 解法 | 能解决到 | 代价 | 适用边界 |
|---|---|---|---|
| **A · 日志驱动换 `local` + 配轮转** | 磁盘不撑爆 | 需要重建已有容器才能生效（条目 10） | **必做** |
| **B · 加 `healthcheck`** | 让 `Up` 之外的"能不能用"被表达出来 | 要写一个有意义的检查命令 | **必做**，且是发布闸门的前提 |
| **C · `docker stats` / `docker events` / `inspect` 关键字段** | 单机排障够用 | 不留存历史 | 小规模起步 |
| **D · 集中式指标**（⏳ cAdvisor → Prometheus → Grafana） | 历史趋势、告警 | 要建一套组件 | 多机 / 生产 |

### 推荐路径

**A → B → C → D**。前三条代价极低且立刻见效；D 等真的需要历史与告警时再做。

三条关键依据：
- 🔵 默认 `json-file` **不轮转**，能撑爆磁盘；官方推荐 `local`（默认 20m × 5 文件 = 100MB 且默认压缩）
- 🔵 指标的真实来源是 **cgroups**，`docker stats` 读的就是它；容器里 `free` 报告的 swap 是**宿主机**的（官方原话 "Don't rely on the output of `free`"）
- 🔵 **网络指标 cgroup 不记账**（官方解释了原因：网络接口属于 network namespace 而非 cgroup）

**OOM 这类静默死亡只能靠容器外观测发现**：

```bash
docker inspect <容器> --format 'OOMKilled={{.State.OOMKilled}}  ExitCode={{.State.ExitCode}}  Restarts={{.RestartCount}}'
docker events --filter 'type=container' --since 10m
docker stats --no-stream
```

### 知识点挂钩

课 11（日志驱动 / 健康检查 / cgroup 指标）· 课 10（OOMKilled / 重启策略）· 课 12（安全边界）

### 不适用

- 单机、服务极少 → 做到 C 就够，不必上 D
- 需要跨机聚合 → D，或转场景 8

### 做错会踩的坑

- 只写 `max-file` 不写 `max-size`：🔵 官方原话"Only effective when `max-size` is also set"，轮转根本不生效
- 以为 `Up` 等于健康：进程活着但服务不可用，只有 `healthcheck` 能发现
- 在容器里跑 `free` / `top` 判断用量：数字不可信

</details>

## 场景 7：CI 里怎么构建与交付

**场景描述**：本地构建 1 分钟，CI 里要 20 分钟。而且你担心：万一有人不小心把密钥打进镜像并推到仓库怎么办？

**🔒 先自己想 30 秒**：第一反应是不是"把 `node_modules` 缓存起来"？CI 环境与本地最大的差别是什么，决定了缓存在哪一层失效？

<details><summary>💡 提示（分层想）</summary>

1. **环境层**：CI 每次构建面对的是什么？（几乎无状态的新机器）——本地 BuildKit 缓存还在吗？
2. **缓存层**：外部缓存要怎么用？（导出 / 导入两个动作）
3. **闸门层**：什么东西**绝对不能**进仓库？应该在流程的哪一步被拦下？

</details>

<details><summary>📖 展开解法</summary>

### 解法一览

| 解法 | 能解决到 | 代价 | 适用边界 |
|---|---|---|---|
| **A · 外部缓存 `--cache-to` / `--cache-from`** | 跨构建复用层 | 需要一个缓存位置 | 🔵 官方：CI 环境"almost essential" |
| **B · 缓存模式 `max`** | 命中率更高（连中间层也缓存） | 缓存更大 | 🔵 官方："`max` is **more likely to get more cache hits**" |
| **C · 按分支用不同缓存 ref** | 避免互相覆盖 | 引用稍复杂 | 🔵 官方警告：同一位置写两次会覆盖 |
| **D · 发布前三道闸门**（查密钥 / 集成测试 / 漏洞扫描） | 脏镜像进不了仓库 | 流水线步骤变多 | **必做** |
| **E · tag 带 git sha，永不覆盖** | 产物可追溯、可回滚 | 仓库会积累历史镜像（需清理策略） | **必做** |

### 推荐路径

**A + B → C（多分支时）→ D + E**。

三道闸门的具体形态（课 13）：

```yaml
# 闸门①：镜像里有没有密钥
docker history <镜像> --no-trunc | grep -iE 'password|secret|token|api[_-]?key' && exit 1

# 闸门②：用 compose 跑集成测试
docker compose -f compose.yaml -f compose.test.yaml up \
  --abort-on-container-exit --exit-code-from tests

# 闸门③：漏洞扫描
docker scout cves <镜像>
```

**⚠️ 三条官方提醒**（课 13）：
- 构建里的凭据必须用 `--secret`；🔵 `COPY` / `ARG` "could result in **leaked credentials**"
- `gha` 缓存后端是 Experimental，**只能在 workflow 内使用**；GitHub Cache API v1 已于 **2025-04-15** 停用
- **`cache mounts` 默认不会被 gha 缓存保留**

**一条最重要的流程约束**：**PR 只构建、不推送**——PR 的代码不可信，不该拿到写 registry 的凭据。

### 知识点挂钩

课 13（缓存后端 / 闸门 / tag 策略 / 回滚）· 课 12（密钥不进层）· 课 9（compose 复用）

### 不适用

- 构建极快、无外部依赖 → A 收益有限
- 自托管 runner → 需自行确认 Buildx / BuildKit 版本满足 gha 缓存要求

### 做错会踩的坑

- 只加 `--cache-from` 忘了 `--cache-to`：🔵 外部缓存**必须显式导出再显式导入**，两个动作缺一不可
- 多分支共用一个缓存 ref：🔵 官方警告会**覆盖**之前的数据
- 用 `latest` 部署：无法追溯，也无法可靠回滚

</details>

## 场景 8：要不要上 Kubernetes

**场景描述**：别人都在用 K8s，有人担心我们落后了。同时你又听说"K8s 从 1.24 起不用 Docker 了"——那我们学的 Docker 是不是白学了？

**🔒 先自己想 30 秒**："别人都在用"是不是一个技术决策？如果不是，该用什么来判断？另外——"K8s 不用 Docker"到底抛弃的是哪一层？

<details><summary>💡 提示（分层想）</summary>

1. **澄清层**：官方对"用 Docker 构建"这件事是怎么说的？它算不算"依赖 Docker 作为运行时"？
2. **规模层**：几台机器？几个服务？能接受多长停机？有没有专职运维？
3. **成本层**：编排平台带来的是能力，还是**能力 + 一整套运维负担**？

</details>

<details><summary>📖 展开解法</summary>

### 解法一览

| 解法 | 能解决到 | 代价 | 适用边界 |
|---|---|---|---|
| **A · compose + 重启策略 + 健康检查** | 单机 / 少量机器的调度与自愈需求 | 无跨机调度 | 1–3 台、服务个位数、能接受分钟级停机 |
| **B · Swarm** | Docker 内置的多机编排 | 生态与社区小于 K8s | 想要"最省事的多机"，且清楚生态取舍 |
| **C · Kubernetes** | 跨机调度、自愈、滚动发布 | 学习曲线与运维成本**本身就要立项** | 真的需要这些能力**且**有专职投入 |
| **D · 什么编排都不上** | — | 无调度能力 | 单机 / 单一服务 |

### 推荐路径

**先做 A**。升级的触发条件是**"出现了新需求"，不是"想升级"**：

- A → C 的信号：真的需要**多机调度 / 自愈 / 滚动发布**，**且**有专职运维投入

### ⭐ 先破除那个流传最广的误读

🔵 Kubernetes 官方原话：

> "If you are using Docker for **building** your application containers, **you can still run these containers on any container runtime. This use of Docker does not count as a dependency on Docker as a container runtime.**"

也就是说：

| 用途 | 是否受影响 |
|---|---|
| **用 Docker 构建镜像** | ❌ **不受影响**——产物是标准 OCI 镜像 |
| **用 Docker 当 K8s 的节点运行时** | ✅ 受影响——这条路由 `dockershim` 提供，**v1.24 已移除** |

`dockershim` 之所以存在，是因为 **Docker 早于 CRI 规范出现**，当年需要一个适配器。现在 kubelet 通过 CRI 直连 containerd/CRI-O，**中间那层 dockerd 被绕开**——仅此而已。

### 知识点挂钩

课 14（运行时栈 / CRI / dockershim / 容器 vs VM）· 课 15（引入决策树 / 成本清单）

### 不适用

- 只有一两台机器 → C 是过度设计
- 需要强隔离、多租户 → 先解决隔离（虚拟机 / 安全容器运行时），编排不是这个问题的解

### 做错会踩的坑

- 为了"不落后"上 K8s：成本陡增，收益为零
- 以为"K8s 不用 Docker"意味着要重写 Dockerfile：不需要（见上文）
- 把有状态服务硬塞进编排：数据库这类要在存储上额外下功夫

</details>
