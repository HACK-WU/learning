# 09 · 排障速查手册（使用态 · 按症状倒查）

> **怎么用**：出事了别从头读。按下面索引表找**症状**，翻到对应条目照做。
> **想懂为什么**：每个条目末尾有原理回指，事后再看 [08-实战经验.md](08-实战经验.md)。
> **都查不到**：→ 转 `debug` skill 现场取证。
>
> **先止血，后定位。** 线上没时间让你先搞清楚再动手。
> **但请记住**：SurrealDB 里"没报错"**不等于**"成功了"——判断成功与否要看副作用。
>
> 适用版本：SurrealDB 3.2.4（本机实测环境），核查于 2026-09。

## 🔎 症状倒查索引

| 一眼看到的现象 / 报错关键字 | 紧急度 | 翻到 |
|--------------------------|:------:|------|
| 脚本全绿但数据没写进去 / 行数对不上 | 🔴 | **症状 1**：HTTP 200 但数据是错的 |
| 多字查询返回 0 条，单字正常 | 🔴 | **症状 2**：库内检索多字零召回 |
| 查询返回空 `[]`，以为没数据 | 🔴 | **症状 3**：权限被静默拒绝 |
| `GET /xxx` 返回 404 / 500 Invalid JSON | 🔴 | **症状 4**：端点被覆盖或空 body |
| 多条件检索排序不对 / 分数恒为 0 | 🟡 | **症状 5**：score 编号没对应 |
| 无意义查询的分数反超有效查询 | 🟡 | **症状 6**：停用词噪声 |
| `Parse error` / `function not found` | 🟡 | **症状 7**：语法版本不符 |
| 向量查询慢 / 结果不对 / 不走索引 | 🟡 | **症状 8**：KNN 算子写错 |
| 灌数极慢 / 行数永远是 0 | 🟡 | **症状 9**：逐条写入或语法错 |
| 图扩展报"无邻居"但数据有 | ⚪ | **症状 10**：只取到最后一条语句 |

**紧急度**：🔴 立即处理（业务已受损）｜ 🟡 尽快处理（有风险未爆发）｜ ⚪ 有时间再看（体验 / 优化）

## 🔴 症状 1：脚本全绿但数据没写进去

**一眼识别**：HTTP 状态码 200；脚本不报错；后续查询全部返回空；**行数对不上**（如 chunk 表 0 条但 insert 全部"成功"）。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 若已有服务在跑且读到脏数据：先停写，别让错误数据继续扩散 | 不再产生新错误数据 |
| 定位 1 | 打印**原始响应体**，不要只看 `status_code` | 看到 `"status":"ERR"` = 命中本症状 |
| 定位 2 | 批量请求时**逐条**查 status（一次发 50 条，只有一条失败也会返回 200） | 找到失败的那一条 |
| 定位 3 | 往前追：查问题表的**上一步写入**是否真的成功 | 定位到首次出错的位置 |
| 修复 | 解出响应体逐条查 status（代码见 [08 模式 1](08-实战经验.md)） | 错误立刻暴露而非静默 |
| 若无效 | → 转「症状 9」（可能压根没写进去，是语法错导致 0 行）；或转 `debug` | — |

> **预防**：在公共层统一做 status 检查（`common.py::Conn.sql()`），业务代码永远不直接摸响应体。
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 1

## 🔴 症状 2：多字查询返回 0 条，单字正常

**一眼识别**：`fn::qa_kw('索引', 3)` 正常出结果，`fn::qa_kw('索引怎么加速查询', 3)` 返回 **0 条**。**验收可能仍是绿的**——如果验收只测了单字。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 若端点已上线：临时改用应用层检索（把 terms 拆好在应用侧查），先恢复功能 | 查询结果恢复正常 |
| 定位 1 | 验证 AND 语义：`SELECT * FROM chunk WHERE grams @@ '索引 zzzzz';` | **0 条** = 坐实 `@@` 是 AND 语义 |
| 定位 2 | 检查函数是否用了 `FOR` + `LET` 累积 | 若是 → 返回必为 `[]`，FOR 内 LET 不写回外层 |
| 定位 3 | 检查是否用了闭包 `array::any($terms, \|\|$t\|\| grams @@ $t)` | 若是 → 配 score 时报 `no MATCHES clause found` |
| 修复 | 改为**每个 term 一条子查询**，各自带 score，外层 `GROUP BY` 归并取 `math::max(s)`（完整代码见 [08 模式 4](08-实战经验.md)） | 5 个查询 Top1 与应用层完全一致 |
| 若无效 | → 转「症状 5」（可能是 score 编号问题）；或转 `debug` | — |

> **预防**：① 验收输入**刻意包含复杂输入**（多字、含停用词、边界字符）；② 补一条**跨层对照断言**——库内 Top1 必须等于应用层 Top1。**"最小可过输入"是 bug 的天然庇护所。**
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 4

## 🔴 症状 3：查询返回空，以为没数据（实为权限拒绝）

**一眼识别**：查询返回空数组 `[]`，**没有一条报错**。用 root 跑同一条 SQL 却能看到数据。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 若是**误收紧**导致业务不可用：先用 root 确认数据完好，再回滚权限定义 | 业务恢复读取 |
| 定位 1 | 用 **root** 跑同一条 SQL，对比结果集大小 | root 有数据、普通用户没数据 = 命中本症状 |
| 定位 2 | **副作用检查**：低权限用户执行 CREATE，再用 root 查记录是否真的产生 | 记录未产生 = 权限确实生效（这是对的） |
| 定位 3 | **阳性对照**：测"错误密码被拒"的同时，必须测"正确密码能通过" | 只测拒绝会漏掉配置错误 |
| 定位 4 | 检查鉴权头：root 用 `Basic`，记录用户用 `Bearer` | 用反了会 40+ 次 401，且错误信息不提示是头的问题 |
| 修复 | 权限没问题 → 问题在别处（数据/语法/租户字段）；权限误收紧 → 修正 PERMISSIONS 表达式 | 结果集符合预期 |
| 若无效 | → 转「症状 1」（可能压根没数据）；或转 `debug` | — |

> **预防**：验证"某事没发生"**不能依赖"没报错"**。要么查副作用，要么配阳性对照。
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 8

## 🔴 症状 4：`GET /xxx` 返回 404 或 500

**一眼识别**：`GET /qa` 返回 **404**（定义时完全不报错）；或返回 **500 `Invalid JSON`**。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 若是 404：临时让客户端改用 POST（若 POST 分支还在）；若是 500：GET 端点暂时下线 | 客户端不再撞错 |
| 定位 1 | `INFO FOR DB;` 看 `apis` 里剩几条、各自是什么 method | 只剩一条 = 被覆盖，命中本症状 |
| 定位 2 | 检查是否分了两条 `DEFINE API`（`FOR GET` 一条、`FOR POST` 一条） | 是 → **后定义的覆盖先定义的** |
| 定位 3 | 若 500：检查 IF 块里是否用了 `RETURN` 想终止端点 | **IF 里的 RETURN 不终止执行**，代码继续往下走 |
| 定位 4 | dump `$request` 结构，确认 `method` 是**小写** `get`/`post`、`body` 是**字节数组** | 与 `'GET'` 比较永远为假 |
| 修复 | ① 合并成一条 `FOR GET, POST`；② 用 `IF/ELSE` 分开两条路；③ 空 body 兜底（代码见 [08 模式 5](08-实战经验.md)） | GET/POST 均正常 |
| 若无效 | → 转「症状 7」（可能是其他语法错）；或转 `debug` | — |

> **预防**：① 同一路径的 GET/POST 必须合并成一条 `DEFINE`；② 部署后立刻 `INFO FOR DB` 核对 apis 列表；③ 保留 GET 不是为了功能，是为了**可验证性**——浏览器直接访问就能确认端点活着，排障时这个价值远大于省下的几行代码。
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 5

## 🟡 症状 5：多条件检索排序不对 / 分数恒为 0

**一眼识别**：命中第二个条件的记录分数**恒为 0**，排序退化成任意顺序。不报错。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 若排序错乱影响线上结果：临时改为单条件查询，先保正确性 | 结果正确（召回可能下降） |
| 定位 1 | 把命中第二个条件的记录单独拎出来，看它的 score 是不是恒为 0 | 恒为 0 = 命中本症状 |
| 定位 2 | 检查是否多个 `@@` 条件共用了同一个 `search::score(0)` | 是 → `score(0)` 只对应**第一个**匹配表达式 |
| 修复 | 用 `@N@` 编号绑定 + 加权求和：`grams @0@ 'x' OR grams @1@ 'y'` 配 `1.0*search::score(0) + 0.3*search::score(1)` | 各分支得分正常 |
| 若无效 | → 转「症状 6」（可能是停用词噪声掩盖了排序）；或转 `debug` | — |

> **预防**：权重按**文档频率**定，不要拍脑袋。本项目 bigram 权重 1.0、单字 0.3，依据是单字在 48 块语料里出现在 31 块（65%）。
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 2

## 🟡 症状 6：无意义查询的分数反超有效查询

**一眼识别**：junk 查询（如"紫色大象在跳舞"）的 Top1 分数**高于**有效查询。本项目实测：噪声 5.59 > 有效 5.35。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 若线上出现"答非所问"：临时提高分数阈值，过滤低分结果 | 减少明显错误的返回 |
| 定位 1 | 统计查询里每个 term 的**文档频率（DF）** | 某 term 的 DF > 30% = 噪声源（如「不」在 24/48 块 = 50%） |
| 定位 2 | 对比噪声查询与有效查询的**分项得分构成** | 看出是哪些 term 在贡献噪声分 |
| 定位 3 | 先确认**判据没选错**：junk 查询本身必须挑语料里真正不存在的词（"这个术语肯定不存在zzz"含「存在」，语料里真有这句话，拿它当基线是**判据错了**） | 基线有效 |
| 修复 | 加停用词过滤，**顺序是"先过滤 → 再排序 → 再截断"**；过滤后为空要降级退回未过滤版本 | 噪声 Top1 从 5.59 降到 **1.04**，有效查询 Top1 全部不变 |
| 若无效 | → 转「症状 5」（可能是 score 编号错导致加权没生效）；或转 `debug` | — |

> **预防**：停用词表是手工维护的，**语料变了要重新统计词频**。换语料时先跑词频统计脚本。
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 3

## 🟡 症状 7：`Parse error` 或 `function not found`

**一眼识别**：执行报 `Parse error`、`function not found`、`Invalid function/constant path`。错误信息通常**不告诉你该怎么改**。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 若是部署脚本中途失败：先确认已执行到哪一步（重跑可能重复定义） | 明确当前状态 |
| 定位 1 | 对照下表看是不是撞了版本变更 | 命中即知正解 |
| 定位 2 | `INFO FOR DB;` 看定义是否真的建上 | 没建上 = 语句没执行成功 |
| 定位 3 | 按分号切分语句时，**DEFINE FUNCTION / DEFINE API 不能切**（函数体内含分号） | 切碎了会报 `Unexpected end of file` |
| 修复 | 见下表正解列 | 语句正常执行 |
| 若无效 | → 转 `debug`；或查对应版本的官方 changelog | — |

**3.2.4 语法变更对照表**：

| 老写法 | 报错 | 正解 |
|---|---|---|
| `SEARCH ANALYZER` | Parse error | `FULLTEXT ANALYZER az BM25 HIGHLIGHTS` |
| `vector::distance::cosine` | function not found | 全表精算 `vector::similarity::cosine`；走索引 `vector::distance::knn()` |
| `REMOVE ANALYZER x ON DATABASE` | Parse error | `REMOVE ANALYZER x;` |
| `INSERT ... VALUES (...)` | 语法不存在 | `INSERT INTO t [{...},{...}]` |
| `type::is::string` | Invalid function path | `type::is_string` |
| `RETURN version()` | Parse error | 用 `GET /version` 端点 |

> **预防**：跨版本升级时把上表当 checklist 跑一遍。**特别注意第 4 行** —— 它不报错，只是行数永远是 0。
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 6

## 🟡 症状 8：向量查询慢 / 结果不对 / 不走索引

**一眼识别**：查询能跑、结果"看起来对"，但 `EXPLAIN` 里**没有 `KnnScan` 算子**；数据量大时慢得离谱。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 若线上超时：临时改用关键词检索兜底，或减少返回条数 | 响应恢复 |
| 定位 1 | `EXPLAIN` 看有没有 `KnnScan` 算子 | 没有 = 没走索引，命中本症状 |
| 定位 2 | 检查 KNN 算子是否漏了开头的 `<` | 正解是 `emb <\|k,ef\|> $qv`，**`<` 极易漏** |
| 定位 3 | 检查 `DIST`：默认是**欧氏距离不是余弦** | 若 embedding 是归一化的余弦向量，默认 DIST 会给出错误最近邻 |
| 定位 4 | 检查 `DIMENSION` 是否与模型输出维度对齐 | 不对齐会建索引失败或结果错 |
| 修复 | 补全算子；显式声明 `DIST COSINE`；对齐 `DIMENSION` | `EXPLAIN` 出现 `KnnScan`，延迟下降 |
| 若无效 | → 转「症状 7」（可能是函数名错）；或转 `debug` | — |

> **预防**：把 KNN 查询模板固化成常量，别每次手拼。K 管回几条（**硬上限，LIMIT 管不了**），EF 管找多仔细（太小会真漏）。
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 7

## 🟡 症状 9：灌数极慢 / 行数永远是 0

**一眼识别**：灌数耗时远超预期；或**行数断言显示 0 行**而脚本不报错。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 若是全量重建：先确认旧库还在（别先删），慢就慢点，别中断 | 数据不丢 |
| 定位 1 | **先断言行数**——这是第一步，不是最后一步 | 0 行 = 写入语法错，不是性能问题 |
| 定位 2 | 检查是否用了 `INSERT ... VALUES`（3.2.4 语法不存在） | 是 → 改 `INSERT INTO t [{...},{...}]` |
| 定位 3 | 检查是否逐条 HTTP 写入 | 是 → **22 倍差距**（5045 条：逐条 153 s / 批量 50 每批 6.7 s） |
| 定位 4 | 检查 JSON 里 `id` 是否传了字符串 | 是 → 生成嵌套 id `chunk:chunk:l01_0`，**不报错但按原 id 查不到** |
| 修复 | 批量发送（50/批）+ 改用 CREATE 记录字面量 + 内置行数断言 | 6.7 s 完成，行数正确 |
| 若无效 | → 转「症状 1」（可能响应体里是 ERR）；或转 `debug` | — |

> **预防**：**性能测量前必须断言行数**。本项目曾因语法不存在导致三档全 0 行，而"耗时不变"看起来像是性能好——测的是"没写进去"的速度。
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 9

## ⚪ 症状 10：图扩展报"无邻居"，但数据明明有

**一眼识别**：图遍历返回空；拆开单条语句跑却有数据。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 若依赖图扩展做推荐/上下文：临时关掉该路召回，先保主检索 | 主功能可用 |
| 定位 1 | 把两条语句**拆开各跑一次**，对比结果 | 单跑有数据 = 命中本症状 |
| 定位 2 | 检查是否只取了 `payload[-1]["result"]` | 是 → SDK 的 `result()` **只返回最后一条语句** |
| 修复 | 遍历所有语句响应，不要只取 `[-1]` | 出边入边都能拿到 |
| 若无效 | → 检查关系边是否真的建上（`INSERT INTO edge` 建边在本版本**静默不写入**）；或转 `debug` | — |

**同类坑：时间单位解析**。

```python
# ✗ 错
float(t.rstrip("µsns"))       # "500µs" 里的 s 会被误删，且 µ 是多字节

# ✓ 对：按后缀匹配换算，不做字符删除
for suf, factor in [("ns", 1e-6), ("µs", 1e-3), ("us", 1e-3),
                    ("ms", 1.0), ("s", 1000.0)]:
    if t.endswith(suf):
        return float(t[:-len(suf)]) * factor
```

> **预防**：封装一个"执行多条语句并返回全部结果"的工具函数，别在业务代码里直接取 `[-1]`。
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 10

## ⛔ 三个"看似止血、实则毁现场"的动作

> 排障时最容易犯的错：**急着恢复，结果把证据毁了**。

| 动作 | 毁掉了什么 | 该先做什么 |
|---|---|---|
| 直接重启服务 | 内存中的错误现场、未落盘的审计 | 先 dump 当前响应体与 `INFO FOR DB` |
| 删库重灌 | 触发问题的脏数据 | 先 export 一份现状再动手 |
| 撤权限定义来验证是不是权限问题 | 权限配置的当前状态 | 先 `INFO FOR DB` 存一份权限定义快照 |

**顺序原则**：**先存证，再动手；先降级，再修复；先止血，再定位。**

## 附：SurrealDB 排障的三条通用纪律

> 这三条比上面任何一条具体症状都重要。

### 纪律一：不信任"没报错"

SurrealDB 里**静默失败是常态而非例外**。本项目踩到 11 条（详见 [08 附三](08-实战经验.md)）：

- 权限拒绝 → `status=OK` + `result=[]`
- HTTP 200 → 响应体里可能是 `status=ERR`
- 写入语法错 → 不报错，行数永远是 0

**判断成功与否的唯一可信依据是副作用，不是程序有没有报错。**

### 纪律二：断言副作用，配阳性对照

| 要验证的事 | 错误做法 | 正确做法 |
|---|---|---|
| 权限生效 | 看 CREATE 是否报错 | 低权限 CREATE 后，用 root 查记录是否产生 |
| 拒绝无效密码 | 只测错误密码被拒 | 同时测正确密码能通过 |
| 走索引 | 看是否报错 | `EXPLAIN` 查具体扫描算子名 |
| 写入成功 | 看 HTTP 状态码 | 逐条查响应体 status + 行数断言 |

### 纪律三：先怀疑判据，再怀疑代码

验收失败时按顺序问三个问题：

1. 这个断言**期望的结果**（空 / 非空 / 数值大小）在原理上成立吗？
2. 我选的**测试输入**是不是恰好避开了缺陷？（单字 vs 多字）
3. 有没有**阳性对照**证明测试本身有效？

本项目 B7 验收改了三次才改对：前两次是**判据错**，第三次才发现**代码真有缺陷**。所以 —— 先怀疑判据，但**别一直怀疑判据**。

### 纪律四：先怀疑实验，再相信结论

纪律三查的是**判据**（断言写得对不对）。课 8 复核暴露了更靠前的一层：**判据没错，是实验设计错了**。当时评审逐字执行了每条命令，结论照样错。

跑对照实验前，先过三关：

1. **每个变体独立初始化** —— 建表/清表写在变体循环**内**。判定只看这个变体自己写入的行，不能"结果表里有一行满足就算本变体成功"
2. **贴出来的输出能重跑复现** —— 写下脚本名不等于验证过。按脚本当前状态重跑一次、逐字段比对
3. **所有变体都成功 = 先怀疑探针** —— 一个"找出哪种写法可行"的实验若全部成功，几乎必然是探针缺陷。强制加一个**已知必失败**的对照组（字面量、明显非法写法），验证探针有鉴别力

**这三关来自哪次事故**：课 8 跑六种写法对照，确定 EVENT 的 THEN 里怎么写能拿到记录 ID。原探针结果表在五个变体间**从不清空**，判定又是"表里任意一行有 `pid` 就算成功"——第一个成功变体（`$after.id`）写的行被后面所有变体复用，六个变体全判成功，`$this.id` 因此被误判为可用。真实结论：`$this` 在 THEN 值位恒为 `NONE`，`$this.id` 静默丢字段。

第二层更值得记：讲义 8.2 那段"实测输出"里的 `"rid": "order:o1"`，**重跑脚本根本没这个字段** —— 那段输出从来没被复现过，是照预期写出来的。第一关查出的是"看错了"，第二关查出的是"写了没跑"。

> **一句话记住**：逐字执行命令只能证明你没偷懒，证明不了实验没写错。跑之前先问"如果结论是错的，这个实验能显示出来吗"。
