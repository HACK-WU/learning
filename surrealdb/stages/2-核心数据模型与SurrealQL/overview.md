## 五、本阶段的高频困惑点（预判）

> 学习时若遇到以下问题属正常，课内会正面回应：

1. **"没有 JOIN，我要怎么关联两张表？"** → 三条路：记录链接（record link）、RELATE 图边、子查询
2. **"记录 ID 里能放数组？这不是反范式吗？"** → 是刻意的，时序与分桶场景靠这个
3. **"UPDATE 为什么现在不自动创建了？"** → 2.0 起的行为变更，需要 UPSERT
4. **"SCHEMAFULL 会不会让迁移很痛苦？"** → 支持 `ALTER TABLE` 收紧，不必重写数据

**课 3 已沉淀结论**：

1. 记录 ID 既是主键也是**地址**；数组/对象 ID 天然有序，区间查询是不建索引的顺序 I/O
2. **数组 ID 顺序敏感，对象 ID 键序不敏感**（四组对照实验坐实）
3. 类型系统比 JSON 厚：金额用 `decimal`（实测 `0.1+0.2 = 0.30000000000000004`）
4. **REFERENCE ≠ 外键**：不校验目标存在性，只做「反向可见 + ON DELETE 策略」；要删除保护用 `REJECT`
5. **SCHEMAFULL 报错而非静默丢弃**未定义字段（3.2.4 实测）
6. 模式演进先松后紧：`ALTER TABLE ... SCHEMAFULL` 收紧但不重写老数据

**课 4 已沉淀结论**：

7. **UPDATE 不存在时静默无操作**（返回 `[]`，不报错）；改字段用 `SET`/`MERGE`，整体替换才用 `CONTENT`（会删掉未提及字段）
8. **事务必须打包进同一次请求**——CLI 逐行敲的 `BEGIN` 不会开启事务，改动已直接落库；条件中止用 `THROW`
9. 事务里 UPDATE 不存在记录**不会回滚**（因为它不报错）；这与结论 7 构成一条静默失败链
10. SPLIT / GROUP BY 的字段**必须出现在 SELECT 列表**；两者 3.0 起互斥

**课 5 已沉淀结论**：

11. **边即记录**：有 ID、能挂属性、能被 UPDATE；推荐显式指定边 ID（如 `knows:b2c`），否则随机 ID 难以精确更新
12. **`in` = 起点、`out` = 终点**（反直觉）；写反不报错、只返回 `[]`——**静默失败链的第三次出现**，对策是检查返回数组长度
13. **通配符是 `?` 不是裸 `->`**；`->edge` 到边、`->edge->table` 到节点；`<->` 不剔除起点；遍历不跨边表去重；**FETCH 只展开记录链接，不走路**
14. **`.{N}()` 是"恰好第 N 跳"**（跳不到返回 `[]`），树形用 `.{1..N}.{字段, then: 路径.@}`；**骨架的 `@{depth}` 在 3.2.4 已报 Parse error**
15. **递归不自动去重、环上会重复计数**，但深度上限保护有效不会爆栈；成本 ≈ 扇出 ^ 深度，"图数据库"不等于多跳一定快
