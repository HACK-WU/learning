## 一、阶段目标

学完本阶段你应该能够：

1. 用自己的话说清**一个现代应用为什么会被迫拆成多个数据库**，以及这种拆法的具体代价（不是抽象的"复杂度高"，而是"改一次商品价格要跨五个系统同步"）
2. 说清 SurrealDB 的**一句话定义与核心定位**（多模型 ≠ 什么都能干，而是"一个引擎装下所有形状"）
3. 在本机**跑起 SurrealDB**，并用 CLI / HTTP / GUI / SDK 四种方式连上它
4. 理解 SurrealDB 的**四级层级结构**（Namespace / Database / Table / Record），知道每一层管什么

## 五、阶段核心结论速览

> 学完后回看，本阶段应沉淀出这几条：

1. **多模型的敌人不是某个数据库，是"按形状拆库"这件事本身**
2. SurrealDB 的核心承诺：**一个事务里跨文档、图、向量、全文**，不是"五个引擎拼一拼"
3. 单二进制是它最大的部署优势，也是理解它所有设计选择的起点
4. 四级层级（NS/DB/Table/Record）里，**Namespace 和 Database 是多租户的物理边界**，不是逻辑分组

**阶段核心结论**：

1. 多模型的敌人不是某个数据库，是**"按形状拆库"这件事本身**——它把一致性责任从数据库转移到了应用代码
2. SurrealDB 的核心承诺：**一个事务里跨文档、图、向量、全文**，不是"五个引擎拼一拼"
3. 统一 KV 底座（`*` 文档 / `~` 图边 / `+` 索引）是"一条查询跨形状"能成立的技术原因；键前缀 `*·NS·DB·Table·RecordID` 印证了四级层级是物理编码的
4. 成熟度坐标：DB-Engines 综合榜第 155 位但同比在涨；3.0 的破坏性变更清单本身就是"仍在快速演进"的信号
5. 上手三坑（本机实测）：相对路径落 CWD / 裸 `SELECT 1;` 报 expected FROM / WS 新会话需重新 signin

**课程实操环境**（后续课程沿用）：

- WSL Ubuntu 24.04，SurrealDB `3.2.4+20260803.93ab219`，二进制在 `/usr/local/bin/surreal`
- 实例：`--bind 127.0.0.1:8000`，后端 `rocksdb:/mnt/d/projects/learning/surrealdb/playground/data/mydb`
- 凭据 `root/root`；库 `learn` / `shop`；样例数据 `product:sku_8848`
- Python SDK 2.0.0（装在 `playground/.venv`，因 Ubuntu 24.04 的 PEP 668 限制）
