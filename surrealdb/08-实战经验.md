## 怎么用这份文档

每条故障模式按**五段式**组织：症状（可观测）→ 根因 → 排查路径 → 修复 → 预防。

**10 条故障模式按"炸的方式"分组**，不是按知识点分组 —— 因为排查时你先看到的是"怎么炸的"：

| 组 | 条数 | 特征 |
|---|---|---|
| A · 静默失败 | 5 条（模式 1-5） | 状态码/返回体告诉一切正常，数据在悄悄出错 |
| B · 语法与版本 | 2 条（模式 6-7） | 直接报错，但提示词指错方向 |
| C · 权限与鉴权 | 1 条（模式 8） | 被拒的表现与"没数据"无法区分 |
| D · 性能与工程 | 2 条（模式 9-10） | 能跑，但慢或错得隐蔽 |

## A 组 · 静默失败（最危险）

> 这组的共同点：**全都返回"看起来正常"的状态**。对付它们只有一招 —— **断言副作用，不依赖报错**。

### 故障模式 1：HTTP 200 但数据是错的

**症状（可观测）**：HTTP 状态码 200；脚本不报错；后续查询全部返回空；查表行数对不上（如 chunk 表 0 条但 insert 全部"成功"）。

**根因**：SurrealDB 把错误放在**响应体**里，不放状态码里。HTTP 200 的响应体可能是：

```json
[{"time":"...","status":"ERR","result":"..."}]
```

本项目第二十次踩到：期望 `record<doc>` 却收到字符串 `'doc:l01'`，服务端愉快地返回 200 + ERR。【实测】

**排查路径**：

1. 打印原始响应体，别只看 `status_code`
2. 批量请求时要**逐条**查 status（一次发 50 条语句时，只有其中一条失败也会返回 200）
3. 往前追：发现问题表的上一步写入是否"真的成功"

**修复**：

```python
# ✗ 错
r = requests.post(url, ...)
if r.status_code == 200:
    return parse(r.json())       # 以为成功了

# ✓ 对
if isinstance(payload, list):
    for item in payload:
        if item.get("status") == "ERR":
            return False, item, item.get("result") or item.get("kind")
return True, payload, None
```

**预防**：在公共层（`common.py::Conn.sql()`）统一做 status 检查，业务代码永远不要直接摸响应体。

> 对应速查条目：→ [09 症状 1](09-排障速查手册.md)

### 故障模式 2：多条件全文检索，排序悄悄退化

**症状（可观测）**：命中第二个条件的记录分数**恒为 0**，排序退化成任意顺序。不报错。

**根因**：`search::score(0)` 只对应**第一个**匹配表达式。【实测】

```sql
-- ✗ 错：两个条件共用一个 score 索引
SELECT id, search::score(0) AS s FROM chunk
WHERE grams @@ 'x' OR grams @@ 'y'
ORDER BY s DESC;
```

**排查路径**：把命中第二个条件的记录单独拎出来，看它的 score 是不是恒为 0。

**修复**：`@N@` 编号绑定 + 加权求和。

```sql
-- ✓ 对
SELECT id, (1.0*search::score(0) + 0.3*search::score(1)) AS s
FROM chunk WHERE grams @0@ 'x' OR grams @1@ 'y'
ORDER BY s DESC;
```

**权重怎么定**：本项目 bigram 权重 1.0、单字权重 0.3。理由是单字（如「的」）在 48 块语料里出现在 31 块（65%），等权会把噪声块拉进前列。【实测】

**预防**：① 只要写多个 `@@` 条件，就**必须**同时写 `@N@` 编号，把它变成编码习惯而非优化项；② 权重按**文档频率**定，不要拍脑袋 —— 换语料时重跑词频统计；③ 在检索层加一条自检：随机抽 20 条命中第二个条件的记录，若 score 全为 0 立即告警。

> 对应速查条目：→ [09 症状 5](09-排障速查手册.md)

### 故障模式 3：停用词把噪声抬得比信号还高

**症状（可观测）**：无意义查询的 Top1 分数**反超**有效查询。本项目实测：噪声 5.59 vs 有效 5.35。【实测】

**根因**：中文单字在语料里普遍存在。`不` 出现在 24/48 块（50%）、`在` 16/48（33%），多个高频单字累加后反超真实信号。

**排查路径**（`diag_noise.py`）：

1. 统计查询里每个 term 的文档频率（DF）
2. 若某 term 的 DF > 30%，它就是噪声源
3. 对比噪声查询与有效查询的**分项得分构成**

**修复**：加停用词过滤，且**顺序是"先过滤 → 再排序 → 再截断"**。

两个容易做错的顺序问题：

1. **先过滤后截断**，不能反。若先截断，停用词会先占掉 `max_terms` 的名额，长查询里真正有区分度的 bigram 反而被挤掉
2. **过滤后为空要降级**，退回未过滤版本。若整个查询被滤成空（如"的的的"），宁可返回噪声也不能让查询变 0 条 —— 后者在端点上表现为 `count=0`，看起来像服务故障

**效果验证**（`diag_noise2.py`）：加过滤后中文噪声 Top1 从 5.59 降到 **1.04**，四个有效查询的 Top1 全部保持正确。

**副作用要盯**：停用词表是手工维护的，**语料变了要重新统计词频**。换语料时先跑 `diag_noise.py`。

**预防**：① 停用词表纳入版本管理，语料变更时**先跑词频统计再上线**（`diag_noise.py` 保留了这个能力）；② 线上保留一组"已知 junk 查询"作为常态巡检，分数异常抬升即告警；③ 注意**判据本身也会错** —— 选 junk 基线时要确认该词在语料里真的不存在。

> 对应速查条目：→ [09 症状 6](09-排障速查手册.md)

### 故障模式 4：库内检索函数多字查询零召回（验收全绿但功能是坏的）

**症状（可观测）**：单字查询正常出结果，**多字查询全部返回 0 条**。更危险的是验收是绿的 —— 因为验收只测了单字。

本项目实测对照：

| 查询 | 库内函数（老写法） | 应用层 |
|---|---|---|
| 索引怎么加速查询 | **0 条** | 3 条 |
| 权限隔离怎么做 | **0 条** | 3 条 |
| 图关系怎么建 | **0 条** | 3 条 |
| 向量检索用什么距离函数 | **0 条** | 3 条 |
| 端点怎么定义 | **0 条** | 3 条 |

**根因**：把整个查询串当成一个匹配表达式传给 `@@`，而 `@@` 是 **AND** 语义——tokenize 后要求同一块里同时含全部 gram，多字查询几乎不可能满足。

**根因链**（四条，逐条实测排除）：

1. `grams @@ 'a b'` 是 **AND** 语义。测「索引 zzzzz」→ 0 条，坐实。整个查询串 tokenize 后要求一块里同时含全部 gram，几乎不可能
2. `FOR` 循环 + `LET` 累积 → 0 条，**FOR 块内的 LET 不写回外层变量**
3. 闭包 `array::any($terms, |$t| grams @@ $t)` → 0 条；配 score 时报 `no MATCHES clause found in WHERE condition` —— `search::score()` 只在**顶层 MATCHES 语法**下可用
4. 唯一可行解：**每个 term 一条子查询，各自带 score，外层 GROUP BY 归并取最高分**

**排查路径**（`diag_matchop.py` → `diag_fnloop4.py`，五个诊断脚本）：

| 脚本 | 验证的假设 | 结果 |
|---|---|---|
| `diag_matchop.py` | `@@` 是不是 AND 语义 | 是，测「索引 zzzzz」→ 0 条 |
| `diag_fnloop.py` | FOR + LET 能否累积 | 否，返回 `[]` |
| `diag_fnloop2.py` | 闭包 + `@@` 能否工作 | 否，配 score 时报错 |
| `diag_fnloop4.py` | 多子查询归并是否可行 | **是，排序与应用层一致** |

**修复**：

```sql
DEFINE FUNCTION fn::qa_kw($t1: string, $t2: string, $t3: string, $k: number) {
  LET $a = (SELECT id, text, search::score(0) AS s FROM chunk
            WHERE grams @@ $t1 ORDER BY s DESC LIMIT $k);
  LET $b = (SELECT id, text, search::score(0) AS s FROM chunk
            WHERE grams @@ $t2 ORDER BY s DESC LIMIT $k);
  LET $c = (SELECT id, text, search::score(0) AS s FROM chunk
            WHERE grams @@ $t3 ORDER BY s DESC LIMIT $k);
  RETURN (SELECT id, text, math::max(s) AS s
          FROM array::concat($a, $b, $c)
          GROUP BY id, text ORDER BY s DESC LIMIT $k);
};
```

修后实测：5 个查询的 Top1 与应用层**完全一致**。

**遗留代价**：函数签名固定 3 个 term，不是可变数组。这是 3.2.4 上唯一能同时保住"召回"与"排序"的写法。

**预防（本条最重要的方法论）**：

> **验收项的"最小可过输入"是 bug 的天然庇护所。**

两条硬要求：
1. 验收输入要**刻意包含复杂输入**（多字、含停用词、含边界字符）
2. 补一条**跨层对照断言**：库内结果必须等于应用层结果（本项目 D1b）

本条是本项目**唯一一个"验收全绿但功能是坏的"的缺陷**。前 21 条坑至少还有症状，这条连症状都没有。

> 对应速查条目：→ [09 症状 2](09-排障速查手册.md)

### 故障模式 5：端点定义被静默覆盖

**症状（可观测）**：`GET /qa` 返回 404，且**定义时完全不报错**。

**根因**：同一路径的 GET 与 POST 若分两条 `DEFINE API`，**后定义的覆盖先定义的**，`INFO FOR DB` 里只剩后者。【实测】

```sql
-- ✗ 错
DEFINE API OVERWRITE "/qa" FOR GET THEN { ... };
DEFINE API OVERWRITE "/qa" FOR POST THEN { ... };   -- 覆盖了上一条
```

**排查路径**：`INFO FOR DB;` 看 `apis` 里到底剩几条、各自是什么 method。

**修复**：合并成一条。

```sql
-- ✓ 对
DEFINE API OVERWRITE "/qa" FOR GET, POST THEN { ... };
```

**顺带解决第二个坑**：IF 块里的 `RETURN` **不终止**端点执行。

```sql
-- ✗ 错：GET 时空 body 会继续走到 decode，报 500 Invalid JSON
IF $method = 'get' { RETURN { body: 'hint' }; };
LET $body = encoding::json::decode(type::string($request.body));
```

要用 `IF / ELSE` 把两条路分开，并对空 body 兜底：

```sql
LET $raw = type::string($request.body);
LET $body = IF $raw = '' THEN {} ELSE encoding::json::decode($raw) END;
```

**预防**：① 同一路径的 GET/POST **必须合并成一条** `DEFINE API`；② 部署后立刻 `INFO FOR DB` 核对 apis 列表，把"端点数量与方法"纳入部署后的自检项；③ 端点内所有分支用 `IF/ELSE` 显式分开，不要依赖 `RETURN` 提前终止；④ 对空 body 一律兜底 `IF $raw = '' THEN {} ELSE ... END`。

> 对应速查条目：→ [09 症状 4](09-排障速查手册.md)

## B 组 · 语法与版本（报错但指错方向）

### 故障模式 6：3.x 的语法变更集中爆发

**症状（可观测）**：`Parse error` 或 `function not found`，错误信息通常不告诉你该怎么改。

**根因**：3.0 起一批语法变更，老教程/老代码照抄必崩。

| 老写法 | 报错 | 3.2.4 正解 | 来源 |
|---|---|---|---|
| `SEARCH ANALYZER` | Parse error | `FULLTEXT ANALYZER az BM25 HIGHLIGHTS` | 【实测】 |
| `vector::distance::cosine` | function not found | 全表精算 `vector::similarity::cosine`；走索引 `vector::distance::knn()` | 【实测】 |
| `REMOVE ANALYZER x ON DATABASE` | Parse error | `REMOVE ANALYZER x;` | 【实测】 |
| `INSERT ... VALUES (...)` | 语法不存在 | `INSERT INTO t [{...},{...}]` | 【实测】 |
| `type::is::string` | Invalid function path | `type::is_string`（报错信息会提示） | 【实测】 |
| `RETURN version()` | Parse error | 用 `GET /version` 端点 | 【实测】 |

**排查路径**：报错后先查 `INFO FOR DB` 看定义是否真的建上；再对照上表看是不是撞了版本变更。

**修复**：见上表正解列。

**预防**：跨版本升级时，把上表当 checklist 跑一遍。**特别注意第 4 行** —— 它不报错，只是行数永远是 0。

> 对应速查条目：→ [09 症状 7](09-排障速查手册.md)

### 故障模式 7：KNN 算子写错，静默不走索引

**症状（可观测）**：查询能跑、结果"看起来对"，但**不走 HNSW 索引**；数据量大时慢得离谱。

**根因**：KNN 算子是 `emb <|k,ef|> $qv`，**开头的 `<` 极易漏**。本项目在三处犯过同样的错。

```sql
-- ✗ 错
WHERE emb <%d,80|> $q      -- 漏了 < 开头；且 Python 里 %d 还被当成占位符
-- ✓ 对
WHERE emb <|%d,80|> $q
```

**另一个坑**：`DIST` 默认是**欧氏距离不是余弦**。若你的 embedding 模型输出是归一化的余弦向量，默认 DIST 会给出错误的最近邻。【实测】

**排查路径**：`EXPLAIN` 看有没有 `KnnScan` 算子。没有 `KnnScan` = 没走索引。

**修复**：算子补全；显式声明 `DIST COSINE`。

**预防**：把 KNN 查询模板固化成常量，别每次手拼。

> 对应速查条目：→ [09 症状 8](09-排障速查手册.md)

## C 组 · 权限与鉴权

### 故障模式 8：权限拒绝与"没数据"无法区分

**症状（可观测）**：查询返回空数组 `[]`，**没有一条报错**。你会以为是没有数据，实际是权限拒绝了。

**根因**：SurrealDB 权限拒绝时的行为是返回 `status=OK` + `result=[]`，**不返回错误**。【实测】

**排查路径**：

> 关键：不能靠"是否报错"来判断。

1. **副作用检查**：用低权限用户执行 CREATE，然后用 **root** 检查记录是否真的产生
2. **阳性对照**：测"错误密码被拒"的同时，必须测"正确密码能通过" —— 只测拒绝会漏掉配置错误
3. 用 root 跑同一条 SQL，对比结果集大小

```python
# ✓ 对：查副作用而非查报错
uc.sql("CREATE chunk:hack SET ...;")
ok, payload, _ = conn.sql("SELECT id FROM chunk WHERE id = chunk:hack;")
created = len(payload[-1].get("result") or []) > 0
return not created, "越权写入 %s" % ("被拒绝（正确）" if not created else "成功（危险）")
```

**修复**：权限没问题的话，问题在别处（数据、语法、租户字段）。

**预防**：

> **验证"某事没发生"，不能依赖"没报错"。**

**鉴权头也别用错**（本项目踩过 40+ 次 401）：

| 身份 | 该用的头 |
|---|---|
| 系统用户（root） | `Authorization: Basic ...` |
| 记录用户（ACCESS token） | `Authorization: Bearer ...` |

用反了就 401，且**错误信息不提示是头的问题**。

> 对应速查条目：→ [09 症状 3](09-排障速查手册.md)

## D 组 · 性能与工程

### 故障模式 9：逐条写入，慢 22 倍

**症状（可观测）**：灌数极慢，但每步都"成功"。

**根因**：每条 HTTP 请求的固定开销（连接、鉴权、序列化）远大于数据本身。

| 方式 | 5045 条耗时 | 来源 |
|---|---|---|
| 逐条 | 153 s | 【实测】 |
| 批量（50/批） | 6.7 s | 【实测】 |

**22 倍差距**，且数据量越大差距越大。课 12 的更极端场景实测是 **940 倍**差距。【实测】

**排查路径**：计时 + **断言行数**。

> ⚠️ **性能测量前必须断言行数**。本项目曾因 `INSERT ... VALUES` 语法不存在导致三档全 0 行，而"耗时不变"看起来像是性能好 —— 测的是"没写进去"的速度。

**修复**：按批发送（本项目 50/批）。另外 JSON 里给 `id` 传字符串会生成嵌套 id（`chunk:chunk:l01_0`），**不报错但按原 id 查不到**，改用 CREATE 记录字面量。

**预防**：批量写入函数里内置行数断言，写不进去立刻炸，不要等到下游才发现。

> 对应速查条目：→ [09 症状 9](09-排障速查手册.md)

### 故障模式 10：客户端只取到最后一条语句的结果

**症状（可观测）**：图扩展报"无邻居"，但数据明明有。

**根因**：一次发两条语句时，SDK 的 `result()` 只返回**最后一条**，前面的被覆盖。【实测】

```python
# ✗ 错
ok, payload, err = conn.sql("SELECT ->refs->doc FROM doc; SELECT <-refs<-doc FROM doc;")
out = payload[-1]["result"]        # 只有入边，出边被覆盖
```

**排查路径**：把两条语句拆开各跑一次，对比结果。

**修复**：遍历所有语句响应，不要只取 `[-1]`。

**同类坑**：`rstrip` 解析时间单位。

```python
# ✗ 错
float(t.rstrip("µsns"))       # "500µs" 里的 s 会被误删，且 µ 是多字节

# ✓ 对：按后缀匹配换算，不做字符删除
for suf, factor in [("ns", 1e-6), ("µs", 1e-3), ("us", 1e-3),
                    ("ms", 1.0), ("s", 1000.0)]:
    if t.endswith(suf):
        return float(t[:-len(suf)]) * factor
```

**预防**：① 封装一个"执行多条语句并返回**全部**结果"的工具函数，业务代码永远不要直接取 `[-1]`；② 时间单位一律用**后缀匹配换算**，禁止 `rstrip` 删字符；③ 关系边建完后用 `SELECT * FROM edge` 断言行数 —— 本版本 `INSERT INTO edge` 建边可能**静默不写入**。

> 对应速查条目：→ [09 症状 10](09-排障速查手册.md)

## 附一：适用边界与反模式（不该用 / 不该这么用）

### 不该用 SurrealDB 的场景

| 场景 | 崩点数字 | 替代方案 |
|---|---|---|
| 深图遍历做核心链路 | 扇出 5 时**第 5 跳 3125 条 / 23.68 ms**，耗时陡增 5.7 倍；扇出 10 时第 5 跳 = 10 万条【实测】 | 专用图库（Neo4j）；或物化祖先链 + 深度 ≤ 3 + 强制 LIMIT |
| 8 万行以上重聚合 | 60.2 ms vs Postgres 7.27 ms，**8.3x** 且近线性劣化【实测】 | 分析型库（ClickHouse / Doris） |
| 中文全文检索（强需求） | 内置分析器**开箱不可用**，查中文 0 条【实测】 | Elasticsearch，或自建 bigram（本项目方案） |
| 复杂搜索（高亮/聚合/分词） | 课 6 原文结论：**请留给 ES**【实测】 | Elasticsearch |
| 需要成熟度保障的核心交易 | 2021 年创立，生态成熟度落后于理念【官方】 | Postgres |

### 高频反模式

| 反模式 | 后果 | 正解 |
|---|---|---|
| 用"是否报错"验证权限 | 误判（拒绝不报错） | 副作用检查 + 阳性对照 |
| 用"是否报错"验证写入 | 误判（HTTP 200 可能 ERR） | 逐条查响应体 status |
| 验收只测最简单输入 | 放过缺陷（模式 4） | 刻意复杂输入 + 跨层对照 |
| 多条件共用一个 `score(N)` | 排序退化 | `@N@` 编号绑定 |
| 逐条 HTTP 写入 | 慢 22–940 倍 | 批量 + 行数断言 |
| 性能测量不断言行数 | 测的是"没写进去"的速度 | 内置行数断言 |
| 照抄老版本语法 | Parse error / 静默 0 行 | 见模式 6 对照表 |
| 把 LIVE 当消息队列用 | 断连即亡、不补历史 | 要可靠用消息队列 |
| EVENT 的 THEN 里改自己 | 递归 / 主写入回滚 | 改别的记录，或改用 LIVE |
| `DEFINE API` 裸奔上公网 | 默认匿名可调 + 系统权限运行 | 显式收紧权限 |

## 附二：上线前后 Checklist

> 打勾项均可在 [09-排障速查手册.md](09-排障速查手册.md) 找到对应症状。

### 上线前

- [ ] **状态码检查**统一在公共层做，业务代码不直接摸响应体
- [ ] **批量写入**带行数断言，跑一次空库到满数据的灌数计时
- [ ] **EXPLAIN 验证**：核心查询路径都有 `IndexScan` / `KnnScan`，无 `TableScan`
- [ ] **权限副作用验证**：低权限用户 CREATE 后用 root 查记录是否产生
- [ ] **阳性对照**：错误密码被拒 + 正确密码能通过，两条都测
- [ ] **验收输入复杂度**：至少一条多字查询、一条含停用词、一条边界字符
- [ ] **跨层对照**：库内函数结果 == 应用层结果
- [ ] **端点合并检查**：`INFO FOR DB` 确认同一路径的 GET/POST 都在
- [ ] **鉴权头**：root 用 Basic、记录用户用 Bearer
- [ ] **备份含 JWT 密钥** → 按凭证级别保管
- [ ] **存储后端确认**：要时间旅行看日志那行 `Versioning enabled`，别信"没报错"
- [ ] **端点收权限**：`DEFINE API` 不要裸奔上公网

### 上线后

- [ ] 监控**进程级 5 个指标**（只有这些，别指望做容量规划）
- [ ] 定期 export（**import 必须恢复到空库** —— 非空库必整批回滚）
- [ ] 语料变更时**重跑词频统计**，更新停用词表
- [ ] 版本升级时跑一遍模式 6 的语法变更 checklist

## 附三：静默失败全清单（11 条）

> 这 11 条是本项目**实际踩过**的，按危险度排序。共同点：**全都返回"看起来正常"的状态**。

| # | 坑 | 表面征兆 | 详见 |
|---|---|---|---|
| 1 | 只看 HTTP 状态码 | 数据没写进去，脚本全绿 | 模式 1 |
| 2 | 库内函数传整个查询串 | 多字 0 条，单字正常，**验收仍绿** | 模式 4 |
| 3 | `$request.body` 是字节数组 | 端点 200，`count=0` | 模式 5 |
| 4 | `$request.method` 是**小写** | GET 走 POST 分支，200 但空结果 | 模式 5 |
| 5 | 权限拒绝不报错 | 断言失败但权限其实是好的 | 模式 8 |
| 6 | GET/POST 分两条定义 | GET 404，定义时无提示 | 模式 5 |
| 7 | 多条件共用一个 score | 排序乱了，分不出对错 | 模式 2 |
| 8 | IF 里 RETURN 不终止 | GET 报 500 Invalid JSON | 模式 5 |
| 9 | `id` 传字符串 | 行数对，按 id 查不到 | 模式 9 |
| 10 | FOR 循环里 LET 累积 | 返回 0 条，不报错 | 模式 4 |
| 11 | 闭包里用全文匹配符 | 返回 0 条；配 score 时才报错 | 模式 4 |

**对付它们只有一招**：

> **断言副作用，不依赖报错。**

其中第 2 条最值得记住：**它是唯一一个"验收全绿但功能是坏的"的缺陷**。前 21 条坑至少还有症状，第 2 条连症状都没有 —— 因为验收只测了单字输入。
