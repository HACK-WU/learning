# 设计决策

> 记录"为什么这么做"，以及**被否决的备选方案为什么不行**。
> 每条决策都带实测证据，不是事后追认的理由。

判断标准：只有"我在两个都能用的方案之间犹豫过"才算决策；
一开始就唯一可行的不写。

---

## 决策 1：中文全文检索用应用层 bigram，不用内置分析器

**选择**：在 `chunk` 表加冗余字段 `grams`，应用层把中文切成 bigram 后写进去，
对 `grams` 建 `FULLTEXT` 索引。

**否决的备选**：

| 备选 | 实测结果 |
|---|---|
| `FULLTEXT ANALYZER blank` | 查中文 0 条；英文阳性对照正常 |
| `FULLTEXT ANALYZER class` | 查中文 0 条 |
| `SEARCH ANALYZER` 老语法 | Parse error（3.0 起改语法） |
| `ngram()` tokenizer | Parse error，3.2.4 不支持 |
| 对 `text` 直接建索引 | 查中文 0 条，EXPLAIN 也不走索引 |

证据：`playground/cap-probe5-zh2.py`。关键设计是**配了英文阳性对照** ——
同一个索引查英文正常、查中文 0 条，才能排除"索引没建好"，锁定问题在分析器。

**代价**：存储膨胀。`grams` 字段约为原文的 2-3 倍。
这是 3.2.4 上唯一可行的路，没有更优解可选，所以不算真权衡 —— 但值得单列，
因为这是整个项目最大的环境约束。

## 决策 2：向量维度定 12 维，配合确定性主题直方图

**选择**：`emb` 用 12 维，由 `common.py::embed()` 按主题关键词命中次数生成并归一化。

**否决的备选**：

| 备选 | 为什么不行 |
|---|---|
| 接真 embedding 模型 | 本机无模型、无外网下载权限 |
| 随机向量 | 检索结果无意义，无法验证"向量路是否真的贡献了召回" |
| 更高维度（如 384） | 维度与主题数不匹配，HNSW 在极小数据上反而退化 |

**真权衡点在于**：维度越高越"像真的"，但 12 个主题里塞进 384 维，
大量维度恒为 0，HNSW 的距离计算被噪声主导。

选 12 维是**让维度与数据的真实自由度匹配**。代价是语义泛化能力弱：
"索引"与"加速"若不在同一主题词表里，向量路就分不出相关性。

**这个决策的可验证收益**：正因为向量路弱、关键词路强，两者的互补性才看得清清楚楚。
`demo.py` 第二幕显示 kw 独有 1 条、vec 独有 1 条 —— 若用真 embedding，
两路可能高度重合，反而演示不出"为什么必须混合"。

## 决策 3：混合检索用 `search::rrf` 服务端融合，不用应用层重排

**选择**：`search::rrf([$kw, $vec], limit, k)`，一次查询在服务端完成融合。

**否决的备选**：应用层分别取回两路结果，Python 里算 RRF 再排序。

**为什么不选**：

1. 往返次数从 1 变 3，本机实测每次往返约 50ms 网络开销
2. 应用层要自己实现 RRF，换语言要重写
3. 两路各取 Top-K 再截断，会丢掉"各自排名靠后但融合后靠前"的结果

**踩到的坑**：`search::rrf` 的第二个参数是 **limit**，不是常见的 k 常数。
按 RRF 论文的习惯把 k=60 传进去会得到完全错误的结果，且不报错。

**代价**：融合算法固定，无法自定义权重。若业务需要"关键词权重 0.7、向量 0.3"，
`search::rrf` 做不到，只能退回应用层。

## 决策 4：租户隔离用同库行级 PERMISSIONS，不用独立命名空间

**选择**：所有租户的 chunk 存在同一张表里，靠表级
`PERMISSIONS FOR select WHERE tenant = $auth.tenant` 隔离。

**否决的备选**：每个租户一个 namespace/database（`USE NS tenant_a DB docs`）。

| 维度 | 独立命名空间 | 同库行级过滤 |
|---|---|---|
| 隔离强度 | 强，物理隔离 | 弱，依赖权限表达式正确 |
| 跨租户查询 | 需多次连接 | 一次查询（root 视角） |
| 资源开销 | 每租户一套索引与元数据 | 共享 |
| 运维复杂度 | 租户多时爆炸 | 低 |
| 漏写过滤的后果 | 不可能发生 | 有 PERMISSIONS 兜底 |

**当选理由**：本项目的租户是"同一产品的不同客户"，数据量小、租户数可控，
且需要 root 视角的全局审计（验收 C6 正是验证这点）。

**什么时候该改选命名空间**：租户间有合规要求（如金融、医疗数据不得同库）、
单租户数据量达到需要独立扩缩容的规模。这是适用边界问题，不是优劣问题。

**本决策的关键细节**：权限过滤写在服务端，应用层**不需要**写 `WHERE tenant = ...`，
也**无法**绕过它。验收 C5 用副作用检查验证：alice 执行 CREATE 后，
用 root 检查记录是否真的产生 —— 结果是被拒绝。

## 决策 5：检索逻辑下推到 `DEFINE FUNCTION` + `DEFINE API`

**选择**：库内定义 `fn::qa_kw` / `fn::qa_scoped`，并对外暴露 `/qa` 与 `/ask` 端点。

**否决的备选**：应用层拼 SQL 发过去。

**当选理由**：

1. 客户端不需要知道 bigram 的存在，换语言不用重写
2. 权限在服务端求值，客户端拿不到越权数据的机会都没有
3. 审计的 `tenant` 取自 `$auth` 而非客户端传参 —— 防伪造，这在应用层做不到同等强度

**真权衡点（本决策的诚实标注）**：

下推后，**函数内无法调用应用层的 bigram 生成器**。第一版写成
`WHERE grams @@ $q`（`$q` 是整个查询串），测下来**多字查询全部返回 0 条**：

| 查询 | 库内函数（老写法） | 应用层 |
|---|---|---|
| 索引怎么加速查询 | **0 条** | 3 条 |
| 权限隔离怎么做 | **0 条** | 3 条 |
| 图关系怎么建 | **0 条** | 3 条 |
| 向量检索用什么距离函数 | **0 条** | 3 条 |
| 端点怎么定义 | **0 条** | 3 条 |

而这个 bug 被验收放过了 —— D1 只测 `fn::qa_kw('索引', 3)` 这种**单字**调用，
恰好是唯一能work的情况。是评审时逐条核实断言才挖出来的。

根因链（四条，逐条实测排除，`diag_matchop.py` ~ `diag_fnloop4.py`）：

1. `grams @@ 'a b'` 是 **AND** 语义（测「索引 zzzzz」→ 0 条），
   整个查询串 tokenize 后要求一块里同时含全部 gram，几乎不可能
2. `FOR` 循环 + `LET` 累积 → 0 条，**FOR 块内的 LET 不写回外层变量**
3. 闭包 `array::any($terms, |$t| grams @@ $t)` → 0 条，配 score 时报
   `no MATCHES clause found` —— `search::score()` 只在**顶层 MATCHES 语法**下可用
4. 只剩可行解：**每个 term 一条子查询，各自带 score，外层 GROUP BY 归并取最高分**

**修后的方案**：函数签名改为 `fn::qa_kw($t1, $t2, $t3, $k)`，
由应用层把问题切成 term 再传进去。实测 5 个查询的 Top1 与应用层**完全一致**。

**遗留代价**：函数签名固定 3 个 term，不是可变数组。这是 3.2.4 上唯一能
同时保住"召回"与"排序"的写法。查询超过 3 个 term 时会被截断，
应用层 `_kw_terms()` 的 `max_terms` 参数需与此对齐。

**分工结论**：应用层负责"把问题变成 terms"（需要分词的那一步），
库内函数负责"拿 terms 检索 + 权限过滤 + 审计"（需要可信执行环境的那一步）。
两者按能力边界分工，不是谁取代谁。

## 决策 6：`/qa` 的 GET 与 POST 合并成一条 `DEFINE`

**选择**：`DEFINE API OVERWRITE "/qa" FOR GET, POST THEN { ... }` 一条语句。

**否决的备选**：分两条写，`FOR GET` 一条、`FOR POST` 一条。

**实测后果**：后定义的覆盖先定义的，且**不报错**。
`deploy_logic.py` 验证 1.5 复现：只定义 `FOR POST` 后，`GET /qa` 直接 404。

这是典型的"静默失败"：定义语句返回 OK，你以为两个方法都注册了，
直到某个客户端发 GET 才暴露。

**为什么还要保留 GET**：不是为了功能，是为了**可验证性**。
浏览器直接访问 `http://127.0.0.1:8000/qa` 就能确认端点活着 ——
排障时这个价值远大于它省下的几行代码。

## 决策 7：灌数用批量 `INSERT`，不用逐条 `CREATE`

**选择**：`init_db.py` 按每批 50 条批量发送。

**否决的备选**：逐条 HTTP 请求写。

| 方式 | 5045 条耗时 |
|---|---|
| 逐条 | 153 s |
| 批量（50/批） | 6.7 s |

**22 倍差距**。根因是每条 HTTP 请求的固定开销（连接、鉴权、序列化）远大于数据本身。

**踩到的坑**：JSON 里给 `id` 传字符串会生成嵌套 id（`chunk:chunk:l01_0`），
不报错但按原 id 查不到。改用 CREATE 记录字面量解决。
另外 `INSERT ... VALUES` 语法在 3.2.4 上不存在，要用对象数组
`INSERT INTO t [{...},{...}]` —— 用错时行数断言能立刻抓出来。

## 决策 8：BM25 打分用 `@N@` 编号绑定加权，不用等权多条件

**选择**：`grams @0@ 'x' OR grams @1@ 'y'` 配 `1.0*search::score(0) + 0.3*search::score(1)`。

**否决的备选**：写成 `grams @@ 'x' OR grams @@ 'y'`，然后 `search::score(0)`。

**实测后果**：`search::score(0)` 只对应**第一个**匹配表达式。
命中第二个分支的记录分数恒为 0，`ORDER BY score DESC` 退化成任意顺序。

**加权理由**：bigram 权重 1.0、单字权重 0.3。单字（如「的」）在 48 块语料里
出现在 31 块（65%），等权会把噪声块拉进前列。

**加权之后还需要停用词过滤**：这是个独立发现的缺陷。仅靠 0.3 的低权重，
无意义查询仍能累加出比有效查询更高的分 —— 见下一条。

## 决策 9：加停用词过滤，且顺序是"先过滤后截断"

**选择**：`_kw_terms()` 里先去掉停用词，再排列优先级，最后截断到 `max_terms`。

**触发这个决策的实测**：验收 B7 失败，无意义查询 Top1=5.59 反而高于有效查询 5.35。

根因（`diag_noise.py`）：`不` 出现在 24/48 块（50%）、`在` 16/48（33%），
噪声单字累加后反超真实信号。

**两个容易做错的顺序问题**：

1. **先过滤后截断**，而非先截断后过滤。若先截断，停用词会先占掉 `max_terms` 的名额，
   长查询里真正有区分度的 bigram 反而被挤掉。
2. **过滤后为空要降级**，退回未过滤版本。若整个查询被滤成空（如"的的的"），
   宁可返回噪声，也不能让查询直接变 0 条 —— 后者在端点上表现为 `count=0`，
   看起来像服务故障。

**效果验证**（`diag_noise2.py`）：加过滤后中文噪声查询 Top1 从 5.59 降到 1.04，
而四个有效查询的 Top1 全部保持正确（索引→l06_0、权限→l10_4、图→l12_4、向量→l07_3）。

**副作用要盯**：停用词表是手工维护的，语料变了要重新统计词频。
`diag_noise.py` Q3 保留了这个统计能力，换语料时先跑它。

## 决策 10：验收用"副作用检查"，不用"是否报错"

**选择**：验证权限是否生效时，不检查 CREATE 是否被拒绝，而是**检查记录是否真的产生**。

**触发原因**：验收 C5 的初版断言失败，但排查发现**权限其实是生效的** ——
是断言写错了。SurrealDB 在权限拒绝时的行为是返回 `status=OK` + `result=[]`，
**不返回错误**。

**通用教训**：验证"某事没发生"时，不能依赖"没报错"。
要么查副作用（记录是否存在），要么配阳性对照（用 root 跑同一个操作应当成功）。

这个原则在本项目用了三次：

- C5 越权写入：查记录是否产生
- C7 错误密码：配正确密码的阳性对照
- B5/B6 走索引：EXPLAIN 输出里查具体的扫描算子名

## 决策汇总：哪些是真权衡，哪些是环境所迫

| 决策 | 性质 |
|---|---|
| 1. bigram 分词 | 环境所迫（3.2.4 无中文分析器） |
| 2. 12 维向量 | 环境所迫（无 embedding 模型），但维度选择是真权衡 |
| 3. 服务端 RRF | 真权衡（往返 vs 灵活性） |
| 4. 行级权限 | 真权衡（隔离强度 vs 成本） |
| 5. 逻辑下推 | 真权衡（精度 vs 可信执行） |
| 6. GET/POST 合并 | 环境所迫（语言行为如此） |
| 7. 批量写入 | 真权衡（实现复杂度 vs 22 倍性能） |
| 8. @N@ 加权 | 环境所迫（语言行为如此） |
| 9. 停用词过滤 | 真权衡（召回 vs 精度） |
| 10. 副作用检查 | 方法论，非权衡 |

**这份表里"环境所迫"占了 4 条** —— 这本身是个值得记住的结论：
在 SurrealDB 3.2.4 上做中文检索，相当大的精力会花在绕开版本限制上，
而不是花在算法选择上。选型时要把这部分成本算进去。
