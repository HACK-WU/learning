## 一、静默失败：HTTP 200 但结果是错的

这类最危险。状态码告诉一切正常，数据在悄悄出错。

### 1. 只检查 HTTP 状态码，不看响应体里的 status

```python
# ✗ 错
r = requests.post(url, ...)
if r.status_code == 200:
    return parse(r.json())       # 以为成功了
```

**现象**：chunk 表灌完 0 条，脚本不报错，后续全部查询返回空。

**根因**：SurrealDB 在 HTTP 200 的响应体里返回 `{"status": "ERR", ...}`。
本项目第二十次踩到：期望 `record<doc>` 却收到字符串 `'doc:l01'`，
服务端愉快地返回 200 + ERR。

**正解**：解出响应体逐条查 status。

```python
# ✓ 对
if isinstance(payload, list):
    for item in payload:
        if item.get("status") == "ERR":
            return False, item, item.get("result") or item.get("kind")
return True, payload, None
```

**怎么发现的**：chunk 表 0 条，往前追发现 insert 全部"成功"。

### 2. 给 `id` 传字符串，生成嵌套 id

```python
# ✗ 错
{"id": "chunk:l01_0", "text": "..."}
```

**现象**：记录写进去了，但按 `chunk:l01_0` 查不到。

**根因**：SurrealDB 把字符串当成 id 的一部分，生成 ``chunk:`chunk:l01_0` ``。
**不报错**。

**正解**：改用 CREATE 记录字面量，让服务端解析。

**怎么发现的**：灌数后行数对但查询全空，打印 id 看到双层前缀。

### 3. `$request.body` 当对象用

```sql
-- ✗ 错
LET $b = $request.body;
LET $q = $b.q OR '';
```

**现象**：端点返回 HTTP 200，`count=0`，永远查不到东西。

**根因**：3.2.4 上 `$request.body` 是**字节数组**（`[123,34,113,...]`），
`$b.q` 恒为 null，`OR ''` 兜底成空串。本项目第二十一次踩到。

**正解**：先转字符串再解 JSON，并对空 body 兜底。

```sql
-- ✓ 对
LET $raw = type::string($request.body);
LET $body = IF $raw = '' THEN {} ELSE encoding::json::decode($raw) END;
LET $q = $body.q OR '';
```

**怎么发现的**：diag_body.py 把 `$request` 原样 dump 出来才看清是数组。

---

### 4. `$request.method` 是大写

```sql
-- ✗ 错
IF $request.method = 'GET' { ... }
```

**现象**：GET 请求走进 POST 分支，返回 `count=0` 的空结果，状态码还是 200。

**根因**：`$request.method` 是**小写** `get`/`post`。
跟 `'GET'` 比较永远为假。本项目第二十二次踩到。

**正解**：`IF $request.method = 'get'`。

**怎么发现的**：diag_method.py dump 出 `method: get`。

### 5. 权限拒绝时指望它报错

```python
# ✗ 错
ok, payload, err = uc.sql("CREATE chunk:hack SET ...;")
assert not ok          # 会失败：ok 是 True
```

**现象**：断言失败，但权限其实是生效的。

**根因**：SurrealDB 权限拒绝时返回 `status=OK` + `result=[]`，**不报错**。

**正解**：查副作用 —— 用 root 检查记录是否真的产生。

```python
# ✓ 对
uc.sql("CREATE chunk:hack SET ...;")
ok, payload, _ = conn.sql("SELECT id FROM chunk WHERE id = chunk:hack;")
created = len(payload[-1].get("result") or []) > 0
return not created, "越权写入 %s" % ("被拒绝（正确）" if not created else "成功（危险）")
```

**通用规则**：验证"某事没发生"不能依赖"没报错"。

### 6. 同一路径的 GET 与 POST 分两条 DEFINE

```sql
-- ✗ 错
DEFINE API OVERWRITE "/qa" FOR GET THEN { ... };
DEFINE API OVERWRITE "/qa" FOR POST THEN { ... };
```

**现象**：`GET /qa` 返回 404，且定义时**不报错**。

**根因**：后定义的覆盖先定义的，`INFO FOR DB` 里只剩后者。

**正解**：合并成一条 `FOR GET, POST`。

**怎么发现的**：deploy_logic.py 验证 1.5 特意保留了这个反例复现。

### 7. 多条件全文检索用同一个 score 索引

```sql
-- ✗ 错
SELECT id, search::score(0) AS s FROM chunk
WHERE grams @@ 'x' OR grams @@ 'y'
ORDER BY s DESC;
```

**现象**：命中第二个条件的记录分数恒为 0，排序退化成任意顺序。

**根因**：`search::score(0)` 只对应**第一个**匹配表达式。

**正解**：`@N@` 编号绑定 + 加权求和。

```sql
-- ✓ 对
SELECT id, (1.0*search::score(0) + 0.3*search::score(1)) AS s
FROM chunk WHERE grams @0@ 'x' OR grams @1@ 'y'
ORDER BY s DESC;
```

### 8. IF 块里的 RETURN 不会终止端点执行

```sql
-- ✗ 错
IF $method = 'get' { RETURN { body: 'hint' }; };
LET $body = encoding::json::decode(type::string($request.body));  -- 空串，报 500
```

**现象**：`GET /qa` 返回 HTTP 500，`Invalid JSON`。

**根因**：IF 块里的 RETURN **不终止**端点，代码继续往下走，
对 GET 的空 body 执行 decode。

**正解**：用 `IF / ELSE` 把两条路分开。

```sql

            FOR create NONE, FOR update NONE, FOR delete NONE;
```

## 三、鉴权类

### 18. 记录用户 token 用 Basic 头

**现象**：40+ 条请求全部 401 InvalidToken。

**根因**：

| 身份 | 该用的头 |

**怎么发现的**：cap-auth.sh 穷举四种组合逐一试出来的。

## 四、客户端与工程类

### 19. `conn.result()` 只返回最后一条语句的结果

```python
# ✗ 错
ok, payload, err = conn.sql("SELECT ->refs->doc FROM doc; SELECT <-refs<-doc FROM doc;")
out = payload[-1]["result"]        # 只有入边
```

**现象**：图扩展报"无邻居"，但数据明明有。

**根因**：一次发两条语句时，`result()` 只给最后一条，入边结果覆盖了出边。

**正解**：用 `conn.sql()` 遍历所有语句响应。

### 21. `rstrip` 解析时间单位

```python
# ✗ 错
float(t.rstrip("µsns"))       # "500µs" 里的 s 会被误删，且 µ 是多字节
```

**正解**：按后缀匹配换算，不做字符删除。

```python
# ✓ 对
for suf, factor in [("ns", 1e-6), ("µs", 1e-3), ("us", 1e-3),
                    ("ms", 1.0), ("s", 1000.0)]:
    if t.endswith(suf):
        return float(t[:-len(suf)]) * factor
```

### 22. 库内全文函数传整个查询串

```sql
-- ✗ 错
DEFINE FUNCTION fn::qa_kw($q: string, $k: number) {
  RETURN (SELECT id FROM chunk WHERE grams @@ $q LIMIT $k);
};
-- 调用 fn::qa_kw('索引怎么加速查询', 3) → 0 条
```

**现象**：单字查询能出结果，多字查询全部 0 条。更危险的是**验收是绿的** ——
D1 只测 `fn::qa_kw('索引', 3)`，恰好是唯一能work的情况。

**根因**：`grams @@ 'a b'` 是 **AND** 语义。整个查询串 tokenize 后要求
一块里同时含全部 gram。实测「索引 zzzzz」→ 0 条，坐实 AND。

**正解**：每个 term 一条子查询，各自带 score，外层归并取最高分。

```sql
-- ✓ 对
DEFINE FUNCTION fn::qa_kw($t1: string, $t2: string, $t3: string, $k: number) {
  LET $a = (SELECT id, text, search::score(0) AS s FROM chunk
            WHERE grams @@ $t1 ORDER BY s DESC LIMIT $k);
  LET $b = (SELECT id, text, search::score(0) AS s FROM chunk
            WHERE grams @@ $t2 ORDER BY s DESC LIMIT $k);
  LET $c = (SELECT id, text, search::score(0) AS s FROM chunk
            WHERE grams @@ $t3 ORDER BY s DESC LIMIT $k);
  RETURN (SELECT id, text, math::max(s) AS s
          FROM array::concat($a, $b, $c)
          GROUP BY id, text ORDER BY s DESC LIMIT $k);
};
```

**怎么发现的**：评审时逐条核实设计决策里的断言，补做 `diag_downpush.py`
发现 5/5 查询零召回。这是本项目唯一一个"验收全绿但功能是坏的"的缺陷。

### 23. FOR 循环里用 LET 累积结果

```sql
-- ✗ 错
LET $out = [];
FOR $t IN $terms {
  LET $hit = (SELECT id FROM chunk WHERE grams @@ $t LIMIT $k);
  LET $out = array::concat($out, $hit);   -- 不写回外层
};
RETURN $out;                               -- 仍是 []
```

**现象**：返回 0 条，不报错。

**根因**：FOR 块内的 `LET` 不写回外层变量，每次迭代的赋值都丢掉。

**正解**：显式写多条子查询（见第 22 条），别指望循环累积。

---

### 24. 闭包里用全文匹配符

```sql
-- ✗ 错
WHERE array::any($terms, |$t| grams @@ $t)
```

**现象**：返回 0 条；若同时用 `search::score()` 则报
`no MATCHES clause found in WHERE condition`。

**根因**：`search::score()` 只在**顶层 MATCHES 语法**下可用，
闭包里的 `@@` 引擎不认作 MATCHES 子句。

**正解**：同第 22 条，展开成多条顶层子查询。

---

### 25. 验收只测最简单的输入

```python
# ✗ 错
def d1():
    ok, payload, err = conn.sql("RETURN fn::qa_kw('索引', 3);")
    return len(rows) > 0
```

**现象**：函数对多字查询完全失效，验收却常年全绿。

**根因**：单字输入恰好绕过了 AND 语义的缺陷。

**正解**：
- 验收输入要**刻意包含复杂输入**（多字、含停用词、含边界字符）
- 再补一条**与应用层结果对照**的断言（D1b）：库内 Top1 必须等于应用层 Top1

**通用教训**：验收项的"最小可过输入"是 bug 的天然庇护所。

---

```python
# ✗ 错
junk = kw_search("这个术语肯定不存在zzz")
assert len(junk) == 0
```

**两层错误**：

1. 中文单字在语料里普遍存在，bigram 必然召回噪声，不该期望为空
2. 更隐蔽：**这个 junk 查询本身选错了**。它含「存在」二字，
   而 `chunk:l11_3` 原文就是「health 端点对不存在的服务也返回 200」——
   它得分 5.59 属于**正确命中**，拿它当噪声基线是判据本身错了

**正解**：
- junk 查询必须挑语料里真正不存在的词（如"紫色大象在跳舞"）
- 判据用"分数显著低于有效查询"，而非"结果为空"
- 且在检索层加停用词过滤，从源头压低噪声
