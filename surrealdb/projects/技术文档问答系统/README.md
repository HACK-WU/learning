# 技术文档问答系统

> SurrealDB 结课综合项目 —— 用一个"能问能答"的检索系统，把四个阶段的所学串成一条线。

语料就是本课程 12 篇讲义本身。你问"索引怎么加速查询"，它从讲义里找出真正讲索引的那一段。
**系统的检索对象就是关于检索的课程** —— 自指的设计让每一步对错都能立刻被验证：你一眼就能看出
召回的那段话到底对不对题，不需要额外领域知识。

---

## 1. 它解决了什么问题

技术文档检索有三个绕不开的痛点，本项目逐一对应：

| 痛点 | 本项目怎么处理 | 对应阶段 |
|---|---|---|
| 关键词检索只会字面匹配，"加速查询"找不到讲"索引"的段落 | 关键词路 + 向量路 + `search::rrf` 融合 | 阶段 3 |
| 中文全文检索直接建索引等于没建 | 应用层预切 bigram 存冗余字段 | 阶段 2 |
| 多租户文档混在一张表里，应用层漏写 `WHERE tenant=` 就串数据 | 表级 PERMISSIONS 在服务端兜底 | 阶段 4 |
| 检索逻辑散落在应用里，换语言要重写 | `DEFINE FUNCTION` + `DEFINE API` 下推到库内 | 阶段 3 |

## 2. 三分钟跑起来

前置条件：SurrealDB 3.2.4 已在 `127.0.0.1:8000` 以 root/root 启动。

```bash
# 1. 建库 + 灌数 + 体检（幂等，可反复跑）
python3 init_db.py

# 2. 部署函数与 HTTP 端点
python3 deploy_logic.py

# 3. 端到端演示（五幕，看完就知道它干了什么）
python3 demo.py

# 4. 验收 38 项
python3 verify.py
```

单独提问：

```bash
python3 query.py "索引怎么加速查询"
python3 query.py "权限隔离怎么做" --mode hybrid --user alice@acme.io
python3 query.py "图关系怎么建" --compare        # 并排对比四种模式
```

性能与规模测量：

```bash
python3 bench.py
```

## 3. 能力覆盖地图

本项目刻意跨越全部四个阶段，不是拿学得最熟的部分凑数。

| 阶段 | 能力 | 落在哪个文件 | 怎么验证 |
|---|---|---|---|
| 阶段 1 | 环境、鉴权、多模型心智 | `common.py` | `init_db.py` 六项体检 |
| 阶段 2 | SCHEMAFULL 建模、图关系、索引 | `schema.py` `seed.py` | 验收 A 组（A1-A6）+ EXPLAIN |
| 阶段 3 | 全文 / 向量 / 混合检索、图遍历、逻辑下推 | `retrieve.py` `pushdown.py` | 验收 B1-B8、D1-D7 |
| 阶段 4 | 行级权限、多租户、可观测、规模决策 | `schema.py` `bench.py` | 验收 C1-C7、E1-E4 |

跨阶段整合的关键在于**它们互相依赖，不是并列罗列**：

- 权限约束检索（阶段 4 × 阶段 3）：`fn::qa_scoped` 在库内做租户过滤，客户端无法绕过
- 索引支撑检索（阶段 2 × 阶段 3）：没有 bigram 字段，混合检索的关键词路就是空转
- 可观测验证前两者（阶段 4）：EXPLAIN 证明走索引，服务端 `time` 证明不是网络慢
- 逻辑下推收束全部（阶段 3）：把上述三条封装成一个 HTTP 端点对外

## 4. 数据模型

五张表、两张关系表：

```
doc    ──refs──> doc       文档间的引用关系（RELATE，TYPE RELATION）
doc    ──包含──> chunk     文档切成块，检索的最小单位
chunk  ──hit───> term      倒排索引（term→chunk），图的方式建倒排
user                       登录用户，带 tenant 属性
qlog / ask_audit           提问审计
```

`chunk` 是核心表，每行存三份"同一内容的不同表示"：

| 字段 | 内容 | 服务于 |
|---|---|---|
| `text` | 原文 | 展示 |
| `grams` | 中文 bigram（索引化） | 全文检索 |
| `emb` | 12 维主题向量（HNSW 索引） | 向量检索 |

## 5. 四种检索模式，不是摆设

同一个问题跑四种模式，结果真的不同（`demo.py` 第二幕）：

```
问题：索引怎么加速查询

kw      chunk:l06_0  5.35    kw 独有：chunk:l07_0
vec     chunk:l06_1  1.00    vec 独有：chunk:l07_2
hybrid  chunk:l06_0  0.58    两路融合
graph   chunk:l06_0  0.58    + 沿 refs 边带出邻居文档背景
```

**kw 独有 1 条、vec 独有 1 条** —— 这是混合检索存在理由的实证：两路召回的
不是同一批结果，融合才有增益。若两路结果完全重合，混合就是纯粹的开销。

## 6. 实测结论（都能在本机复现）

| 结论 | 数据 | 出处 |
|---|---|---|
| 内置分析器切不开中文 | 三种分析器查中文全部 0 条，英文阳性对照正常 | `playground/cap-probe5-zh2.py` |
| 自建 bigram 后命中并走索引 | EXPLAIN 显示 FullTextScan | 验收 B5 |
| 批量写入 vs 逐条 | 153s → 6.7s（22 倍），5045 条（本项目 `init_db.py` 复现值） | `init_db.py` |
| 索引让规模增长近线性 | 16 倍数据 → 12.4 倍耗时（1.43→17.73ms） | `bench.py` |
| 墙钟 ≠ 服务端耗时 | 50.4ms vs 0.395ms，99% 是网络 | `bench.py` / 验收 E4 |
| 权限在服务端生效 | 同一条 SQL，alice 见 33 块、bob 见 15 块、root 见 48 块 | 验收 C2-C4 |

## 8. 诚实标注：本项目的边界

不吹嘘，说清哪些是妥协：

1. **向量不是真 embedding**。本机无 embedding 模型与外网下载，用「12 维主题直方图」代替。
   它能证明"向量路可用、HNSW 索引生效、两路互补"，但语义泛化能力远不及真模型。
   换真模型只需改 `common.py` 的 `embed()` 与 `schema.py` 的 `DIMENSION`，其余不动。

2. **语料只有 48 块**。规模测试用的是复制放大的合成数据，能反映索引的规模敏感性，
   不反映真实语料的分布特征。

3. **租户隔离用同库行级过滤，不是独立命名空间**。资源更省，但隔离强度弱于命名空间方案。
   选型理由见 `设计决策.md` 决策 4。

4. **本项目跑在 root 下做初始化**。生产必须用 `DEFINE ACCESS` 创建的记录用户，
   系统用户不受 PERMISSIONS 约束这一点在验收 C4 里作为对照项显式验证过。
