> 出事了要快查 → 去 [09-排障速查手册.md](09-排障速查手册.md)；要主动设计一个方案 → 去 [10-场景解法库.md](10-场景解法库.md)。

## 一、适用边界与反模式

### 1.1 模式的敌人不是面条，是过度设计

**最常见的反模式：拿着锤子找钉子。** 学完一个模式，看什么都像它的应用场景，套完一层再套一层。

```python
# ❌ 过度设计：两个分支、半年没变过的逻辑，套了三层抽象
class PaymentStrategyFactoryProvider: ...
class AbstractPaymentStrategy(ABC): ...
class AlipayPaymentStrategy(AbstractPaymentStrategy): ...

# ✅ 正解：两三个分支且不常变，if-else 就是最好的写法
def pay(method: str, amount: float) -> str:
    if method == "alipay":
        return f"支付宝支付 {amount:.2f} 元"
    if method == "wechat":
        return f"微信支付 {amount:.2f} 元"
    raise ValueError(f"不支持的支付方式: {method}")
```

**判据（课 1 的 YAGNI + 课 12 的三问之一）**：这个变化**真的会来吗**？
答不上来就别上模式。模式治的是"变化"，不是"代码洁癖"。

> 📌 一个可操作的信号：当你在**同一处**加第 3 个 `elif` 时，才值得考虑抽策略。前两次就当它是正常的。

### 1.2 抽象不是免费的

课 12 的诚实账本：订单处理系统重构后，代码量从**约 45 行涨到约 100 行（翻倍）**。

这笔钱花在哪：

| 成本项 | 说明 |
|---|---|
| 多出来的类/函数 | 每种变化点一个实现 + 一个注册入口 |
| 间接层 | 调用方不再直接看到实现，多一次跳转 |
| 认知负担 | 新人要理解"为什么这里有个工厂" |
| 调试难度 | 栈变深，错误发生在"注册表的哪个实现里"不直观 |

**什么时候这笔钱值得花**：变化点确实存在、且**变化频率 > 理解成本**。
**什么时候不值得**：一次性脚本、生命周期三个月的活动页、只有你一个人看的内部工具。

### 1.3 五种"看着像模式其实不是"的写法

| 写法 | 看着像 | 实际是 | 问题 |
|---|---|---|---|
| 全局配置类 + `get_instance()` | 单例 | **模块级变量就该干的事** | 引入了不必要的类和锁 |
| `@decorator` 包业务规则 | GoF 装饰器 | 语法糖 | 定义时永久生效，**运行时装卸不了** |
| 万能 `Manager` 类 | 外观 | 上帝类 | 一个 `XxxAndYyy`/`XxxManager` 类名就是坏味道信号 |
| 继承 + `super()` 链 5 层 | 模板方法 | 继承滥用 | 骨架漂移、改一处崩一片 |
| 字典塞一百个 key 当"配置" | 策略注册表 | 硬编码字典 | 没有隔离变化点，只是把 `if-else` 换了个地方 |

## 二、高频故障模式（9 条）

### 故障 1 · `@decorator` 当成 GoF 装饰器，运行时卸不掉

**现象**：想"动态地"给对象加一个折扣，加了之后发现卸不掉，或者所有实例都被影响了。

```python
# ❌ 错：@ 语法糖在定义时永久包装，这不是 GoF 装饰器
@discount(0.9)
def price(order): ...
# 运行时想卸掉？卸不掉。想只对一个订单生效？做不到（它作用于函数本身）

# ✅ 正解：GoF 装饰器是对象运行时的组合，不想要就不套
base = OrderPrice(order)
wrapped = MemberDiscount(GiftWrap(base))   # 想卸？这行不写就行
```

**分界**：横切关注点（日志/计时/缓存）用 `@`；业务职责的动态叠加用 GoF 装饰器。

---

### 故障 2 · 浅拷贝导致"改一个订单，另一个也变了"

**现象**：用模板订单批量生成，`copy.copy` 之后给第一个订单加商品，结果第二个订单也多了这个商品。

```python
import copy
tpl = Order(items=["A"])
o1, o2 = copy.copy(tpl), copy.copy(tpl)
o1.items.append("B")
print(o2.items)   # ['A', 'B'] ← 踩了：items 是共享引用
```

**根因**：浅复制只复制外层容器，嵌套的可变对象仍是共享引用。

**修法**：嵌套结构一律 `copy.deepcopy`。

> ⚠️ **连 `dataclasses.replace` 也是浅复制**（课 4 的边界提醒）——它只替换你点名的字段，没点名的可变字段仍共享。
> 所以 `replace` 适合改字符串、数字这类**不可变顶层字段**；涉及嵌套列表/字典用 `deepcopy`。

---

### 故障 3 · 装饰器套娃顺序搞反，算出来的钱不对

**现象**：礼品包装 + 运费险 + 会员折扣，套出来的价格和手算对不上。

**根因**：**外层最后执行**，套娃顺序 = 计算优先级。实测（课 6）：顺序不同结果不同（讲义实测值 81.81）。

```python
# 折扣要最后套（套在最外层），否则它先折后加运费
price = MemberDiscount(GiftWrap(ShippingInsurance(base)))
```

**对策**：把"谁在最外层"写进注释或测试；组合顺序本身就是业务规则，值得一条单测锁死。

---

### 故障 4 · 观察者循环通知，栈溢出或死循环

**现象**：订单状态一变就发通知，通知里又去改订单状态，然后无限递归。

```python
# ❌ 危险：回调里反手触发同一条事件链
def on_paid(order):
    order.state = "shipping"   # 又触发一次状态变更 → on_paid 又被调用
```

**对策（课 9 的规矩）**：**回调只响应，不反手**。观察者里不做会回触事件源的操作；确实要改状态，改为显式调用一个独立的流程函数。

---

### 故障 5 · 观察者导致内存泄漏

**现象**：长生命周期的事件源（如全局订单中心）+ 大对象观察者（如带缓存的报表组件），报表组件早该回收了却一直活着。

**根因**：事件源一直攥着观察者的强引用。

```python
# ✅ 用弱引用集合当名单：观察者被 GC 时自动除名
import weakref
self._subscribers: "weakref.WeakSet" = weakref.WeakSet()
```

**代价**：`WeakSet` **无序**——如果订阅方之间有顺序依赖，本来就不该用观察者（写显式流程）。

---

### 故障 6 · 状态名拼错，转移静默失效

**现象**：`o.state = "shippde"`（拼错）不报错，但这个状态永远匹配不上任何规则，订单卡死。

```python
# ✅ 把取值约束在定义处，拼错当场报错
from enum import StrEnum
class State(StrEnum):
    PENDING = "pending"
    PAID    = "paid"
    SHIPPED = "shipped"
```

**附带收益（课 9）**：转移表**漏配即拒绝**——表里没有的（状态, 动作）组合自动拒绝，合法性由表结构保证，不用写 `if`。

---

### 故障 7 · 生成器用完了才发现是空的

**现象**：分页遍历时，第一次遍历有数据，第二次遍历空列表。

```python
gen = (o for o in orders if o.paid)
list(gen)     # 有数据
list(gen)     # [] ← 生成器是一次性的，走完即空
```

**根因**：**可迭代 ≠ 迭代器**。`list` 可反复 `for`；`iter(list)` 是消耗品。

**对策**：要复用就先 `list()` 固化，或每次重新构造生成器。

---

### 故障 8 · 代理和装饰器混用，缓存了不该缓存的东西

**现象**：用 `@lru_cache` 缓存了依赖外部状态的函数，数据更新了还拿旧值。

```python
# ❌ 错：结果依赖数据库当前状态，缓存后不失效
@lru_cache
def get_user_level(uid: int) -> str: ...

# ✅ 正解：纯函数（同参数必同结果）才用 lru_cache；
#          有失效需求就用带 TTL 的缓存，或手写缓存代理显式管理失效
```

**判据**：`@lru_cache` 只适用于**纯函数**——同样的参数永远得到同样的结果。
**`@cached_property`** 同理：适用于实例生命周期内不变的昂贵属性。

---

### 故障 9 · 责任链忘了"拦截即停"，或链条断了没人兜底

**现象**：风控拦截了，但订单还是继续往下走了。

```python
# ❌ 错：拦截了却继续调用 next_
def risk_check(order, next_):
    if order.amount > 10000:
        return "风控拦截"      # 忘了 return 之前该阻止后续
    return next_(order)        # 其实这条没错，错在下面那种

def risk_check_bad(order, next_):
    blocked = "风控拦截" if order.amount > 10000 else None
    next_(order)               # ❌ 无论拦没拦截都往下走
    return blocked
```

**对策**：拦截分支**直接 return，不调 `next_`**；给链条末端加一个默认处理者兜底（否则请求可能无人处理）。

## 三、模式的组合规律

单看一个模式容易，难的是组合。12 课里反复出现的四种组合套路：

| 组合 | 场景 | 为什么这么搭 |
|---|---|---|
| **工厂 + 策略** | 支付渠道（造哪种 + 怎么算） | 工厂管"造哪个实现"，策略管"这个实现怎么算"，注册表把两者合一 |
| **观察者 + 状态** | 订单流转（状态一变，多方通知） | 状态机负责"能不能转"，观察者负责"转了告诉谁"，两者正交 |
| **责任链 + 命令** | 下单请求（先层层校验，再入队执行） | 责任链决定"放不放行"，命令让通过的请求可排队/撤销 |
| **命令 + 备忘录** | 撤销（反动作写不出来时） | 命令管"做什么/反做什么"，备忘录管"做之前的样子"，读档式回滚 |

> 💡 课 12 的订单系统是这四组的一起落地：工厂+策略（支付/计价）、观察者（通知）、责任链（校验）、状态（流转）、命令+备忘录（撤销）。

## 四、Python 特有的三条经验

1. **一等函数优先于类**。策略、命令、观察者、状态——这四种在 Python 里都能用**函数 + 字典/列表**实现，比建类层次轻得多。只有"有状态"或"一套多方法"时才值得上类。
2. **`Protocol` 优先于 `ABC`**。`Protocol` 是结构化子类型（鸭子类型的静态表达），外部 SDK 不继承也能适配；`ABC` 要求显式继承，对接第三方时很别扭。
3. **`__init_subclass__` 是注册表的利器**。定义子类即注册，加新产品时"定义一个新类 + 给个参数"，创建逻辑零改动——这是课 3 最 Pythonic 的一招，课 12 的终章重构也靠它。
