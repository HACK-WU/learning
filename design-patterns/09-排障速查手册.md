## 1 · 加个新分支，要改好几个地方（散弹式修改）

**症状**：老板说"加个货到付款"，你改了支付的 `elif`、计价的 `elif`、通知的列表 —— 三处全在**已上线、已测过、正在跑**的代码上。

**判据**：同一个需求要改 ≥ 2 处 → 变化点没被隔离。课 1 给这个病起过名字：**散弹式修改**。

**动作**：
1. 把每个"会变的东西"各自抽成一组实现（函数/类都行）
2. 用**注册表**（字典或列表）代替 `if-elif`，主流程只查表
3. 新增需求 = 新增一个实现 + 注册一行

```python
# 之前：if-elif 堆在业务里
def price(kind, o):
    if kind == "normal": ...
    elif kind == "vip": ...

# 之后：注册表
PRICING: dict[str, Callable[[Order], float]] = {}
def register(kind):
    def deco(fn):
        PRICING[kind] = fn
        return fn
    return deco

@register("vip")
def _vip(o): ...
# 加新档位 = 新增一个函数，PRICING 零改动
```

**验收**：新增需求时 `process_order`（主流程）**一行未改**。这是课 12 的验收标准。

**出处**：课 1（坏味道）· 课 8（策略）· 课 12（四步重构法）

## 2 · 想给对象加功能，但不敢改原类

**症状**：要给订单加"礼品包装""运费险""会员折扣"，但改 `Order` 类风险太大。

**判据**：先问一句 —— **这些功能是"横切关注点"还是"业务职责"？**

| 如果是 | 用 |
|---|---|
| 日志 / 计时 / 缓存 / 权限校验（横切，对所有实例一致） | Python `@decorator` 语法糖 |
| 定价花头等业务职责（**每个对象可能不同**） | GoF 装饰器模式（运行时组合） |

**动作（GoF 装饰器）**：

```python
class PriceComponent(Protocol):
    def total(self) -> float: ...

class MemberDiscount:
    def __init__(self, inner: PriceComponent): self._inner = inner
    def total(self): return self._inner.total() * 0.9

# 想卸掉折扣？这行不写就行
price = MemberDiscount(GiftWrap(base))
```

⚠️ **两个坑**
1. **`@` 语法糖是运行时卸不掉的**（定义时永久生效）。要动态装卸 → 用 GoF 装饰器。
2. **套娃顺序影响结果**（外层最后执行）。讲义实测：顺序不同结果不同（81.81）。把顺序写进测试锁死。

**出处**：课 6 · 故障见 [08 · 故障 1 / 故障 3](08-实战经验.md)

## 3 · 第三方 SDK 接口跟我们要的不一样

**症状**：物流、发票、风控三家 SDK 各自为政，方法名、参数、返回格式全不一样，调用方写得一团乱。

**判据**：只差**格式转换**（无状态、逻辑简单）→ 函数适配器；转换逻辑复杂或**有状态** → 类适配器；要**统一多个子系统的编排** → 外观。

**动作（由轻到重）**：

```python
# ① 函数适配器：最轻，闭包返回鸭子类型对象
def adapt(sdk):
    class _A:
        def ship(self, order): return sdk.pushOrder(order.no, order.addr)
    return _A()

# ② 类适配器：转换复杂 / 需要持有状态
class LogisticsAdapter:
    def __init__(self, sdk): self._sdk = sdk
    def ship(self, order) -> str: ...

# ③ 外观：一个入口编排多个子系统
class OrderFacade:
    def __init__(self, logistics, invoice, risk): ...
    def place(self, order):      # 一句话搞定下单全流程
        ...
```

⚠️ **别过度**：子系统只有一两个组件、不复杂 → **直接调，不需要外观**。
用 `Protocol` 描述目标接口（而非 `ABC`），外部 SDK 不继承也能适配。

**出处**：课 5

## 4 · `if-elif` 已经排到十几层

**症状**：一个函数里十几层 `if-elif`，每加一档都要改这个函数。

**判据**：先分清是**"整段算法要换"**还是**"骨架固定、个别步骤变"**。

| 情况 | 用 |
|---|---|
| 整段算法可替换、无状态 | **策略**（一等函数 + 字典分发，首选） |
| 算法有状态 / 是"一套多方法"（计价+退款+积分） | 类策略（`Protocol` + 注入） |
| 骨架固定、个别步骤变、子类体系自然存在 | **模板方法**（`ABC` + 钩子） |
| 不想引入继承，只是个别步骤要定制 | 函数注入 / 回调参数 |

**动作（策略，最 Pythonic 的写法）**：

```python
PRICING = {"normal": _normal, "gold": _gold, "platinum": _platinum}
# 加钻石会员：注册一行，checkout 与既有规则零修改
PRICING["diamond"] = _diamond
```

⚠️ **别硬用模板**：变化的是"整个流程"而非"个别步骤" → 回到策略。
⚠️ **模板方法别重写骨架**：子类只填空，重写整个骨架方法 = 骨架漂移。

**出处**：课 8 · 辨析见 [final 手册 · 全局速查](final-课程手册.md)

## 5 · 状态一变要通知一堆地方，订阅方还在加

**症状**：订单支付成功，要通知用户短信、库存系统、数据报表……每加一个订阅方就改一次流转代码。

**动作（观察者）**：

```python
self._subs: list[Callable[[Order], None]] = []
def subscribe(self, fn): self._subs.append(fn)
def _emit(self, order):
    for fn in self._subs: fn(order)
```

⚠️ **三个坑**
1. **循环通知**：回调里反触同一事件链 → 栈溢出。**规矩：回调只响应，不反手。**
2. **顺序依赖**：订阅方之间有顺序/依赖 → **别用观察者，写显式流程**。
3. **内存泄漏**：长生命周期事件源 + 大对象观察者 → 用 `weakref.WeakSet`（代价：失去顺序）。

📌 **跨系统/跨进程广播** → 那是消息队列（发布订阅的分布式版），不是进程内观察者。

**出处**：课 9 · 故障见 [08 · 故障 4 / 故障 5](08-实战经验.md)

## 6 · 出现非法状态，订单跳到了不该到的状态

**症状**：`o.state = "cancelled"` 谁都拦不住，脏数据要半夜才炸。

**动作（状态模式 · 转移表）**：

```python
TRANSITIONS: dict[str, dict[str, Callable]] = {
    "created":  {"pay": to_paid, "cancel": to_cancelled},
    "paid":     {"ship": to_shipped, "refund": refund_and_close},
    # 表里没有的组合 = 自动拒绝，不用写 if
}

def transition(order, action):
    allowed = TRANSITIONS.get(order.state, {})
    if action not in allowed:
        raise IllegalTransition(f"{order.state} 不能执行 {action}")
    return allowed[action](order)
```

**两个加固动作**
1. **漏配即拒绝**：合法性由表结构保证，不写 `if`。
2. **状态名用 `StrEnum` 防拼错**：`"shippde"` 悄悄混进去是最难查的 bug 之一。

**出处**：课 9 · 课 12（撤销守卫）· 故障见 [08 · 故障 6](08-实战经验.md)

## 7 · 要做撤销，但反动作写不出来

**症状**：想做"撤销发货"，但发货已经调了第三方物流，反着做做不回来。

**判据（两种撤销哲学，课 11）**：

| 方案 | 做法 | 适用 | 代价 |
|---|---|---|---|
| **命令（反着做）** | 每个命令实现 `undo()` | 反动作能写出来 | 省内存（只存 delta） |
| **备忘录（读档）** | 动手前拍快照，撤销时恢复 | **反动作写不出来** | 占内存（存全量） |
| **补偿动作** | 不回滚，做一笔反向业务（补发更正短信） | 已产生外部副作用 | 业务逻辑复杂 |

**动作**：

```python
# 备忘录式（课 12 取消订单用的就是它，反动作一行没写）
snapshot = copy.deepcopy(order)      # 动手前先拍
# ... 执行操作 ...
order = snapshot                      # 撤销 = 读档恢复
```

💡 **可以混用**：命令对象揣着一份快照，既要留痕又要能回滚。
💡 **快照工具箱**：`copy.deepcopy`（嵌套结构）/ `dataclasses.replace`（只改顶层不可变字段）。

**出处**：课 10（命令）· 课 11（备忘录）· 课 12

## 8 · 校验层层把关，顺序还经常变

**症状**：下单请求要过"风控 → 限购 → 库存"，大促时想把风控前置；每次调顺序都要改主流程。

**判据**：请求要**层层把关、任一环可拦截、顺序还想能调** → **责任链**。
（对比：一个变化要通知**所有**订阅方 → 那是**观察者**，不是责任链。）

**动作（中间件式）**：

```python
def build_chain(*middlewares):
    def run(order):
        def dispatch(i):
            if i == len(middlewares): return None      # 末端兜底：放行
            return middlewares[i](order, lambda: dispatch(i + 1))
        return dispatch(0)
    return run

# 大促风控前置 —— 校验函数零改动，一行重组装
check = build_chain(risk, limit, stock)     # 平时
check = build_chain(risk, stock, limit)     # 大促
```

⚠️ **两个坑**
1. **忘了"拦截即停"**：拦截分支直接 `return`，**不调 `next_`**，否则后面的环节照样执行。
2. **链条断了没人兜底**：末端加一个默认处理者，否则请求可能无人处理。

**出处**：课 10

## 9 · 改了一个对象，另一个也跟着变了

**症状**：用模板订单批量生成，给第一个订单加个商品，第二个订单也多了这个商品。

**根因**：用了浅复制，嵌套的可变对象仍是共享引用。

**动作**：

```python
import copy
o1 = copy.deepcopy(tpl)      # ✅ 嵌套结构一律 deepcopy
o2 = copy.deepcopy(tpl)
```

⚠️ **`dataclasses.replace` 也是浅复制** —— 它只替换你点名的字段，**没点名的可变字段（如 `items`）仍是共享引用**。
`replace` 适合改字符串、数字这类**不可变顶层字段**；涉及嵌套列表/字典 → `deepcopy`。

**出处**：课 4 · 故障见 [08 · 故障 2](08-实战经验.md)

## 10 · 加一个功能要动已上线代码，回归范围巨大

**症状**：改一个函数，整个模块都要全量回归。

**动作：四步重构法（课 12）** —— **第 0 步不能省**：

| 步 | 动作 |
|---|---|
| **0** | **先织测试网**：挑几笔固定订单（**成功路径 + 拒绝路径都要有**），把重构前输出原样锁死 = 行为基准 |
| 1 | 闻坏味道（长 `if-else` / 上帝类 / 散弹式修改 / `XxxAndYyy` 类名） |
| 2 | 问变化点（三问：变化真会来吗 / 变化点在哪 / 团队看得懂吗） |
| 3 | 查药方（变化点 → 模式，见 [10 · 场景解法库](10-场景解法库.md)） |
| 4 | **小步替换**：一步只换一个零件，每步回来对行为基准，**逐字一致才许继续** |

🎯 **验收标准**：新增需求 = 新增实现 + 注册一行，主流程**一行未改**。
课 12 实测：三个新需求 = 三个新函数 + 三行注册，回归范围从"整个函数全量"缩到"新函数单测 + 一次冒烟"。

⚠️ **两个坑**
1. **推倒重写**：重写没有行为基准，新 bug 和旧行为混在一起无从分辨。**没有行为保持验证的重构 = 赌博。**
2. **拒绝路径没纳入测试网**：拒绝输出同样是可观察行为，改丢了就是线上事故。

**出处**：课 12

## 11 · 不知道该不该上模式

**动作：课 12 的三问，按顺序问**。

1. **变化真的会来吗？** —— YAGNI。为想象中的需求上模式，是过度设计的起点。**课 1 原话：没病别吃药。**
2. **变化点在哪？** —— 找出"会变的那一处"，隔离它；稳定部分不许被迫修改。
3. **团队看得懂吗？** —— 模式是团队词汇：一句"这里加个策略"胜过十行注释；没人认识的模式等于没写文档的炫技。

📌 **可操作的时机信号**：当你在**同一处**加第 3 个 `elif` 时，才值得考虑抽策略。前两次就当它是正常的。

📌 **成本的诚实账**：课 12 重构后代码量**从约 45 行涨到约 100 行（翻倍）**。这笔钱在"变化确实会来"时才值得花。

## 12 · 遍历百万数据，内存爆了

**症状**：`for o in all_orders` 一次性把百万订单装进内存。

**动作（迭代器 + 生成器，Python 已语言内化）**：

```python
paid = (o for o in all_orders if o.paid)        # 生成器：数据在流里，不在内存里
page = list(itertools.islice(paid, 100))        # 惰性分页，内存占用常数
```

⚠️ **两个坑**
1. **生成器是一次性的**（用尽即止）：第二次遍历是空的。要复用先 `list()` 固化或重新构造。
2. **可迭代 ≠ 迭代器**：`list` 可反复 `for`；`iter(list)` 是消耗品。

**出处**：课 11 · 故障见 [08 · 故障 7](08-实战经验.md)

## 通用三板斧（不知道从哪开始时用）

1. **先问变化点在哪** —— 所有模式都是"隔离某一类变化点"的药方。说不出变化点，就别上模式（课 1）。
2. **先织测试网再动手** —— 没有行为基准的改动都是赌博，尤其是重构（课 12 第 0 步）。
3. **先试最轻的方案** —— 一等函数 + 字典，通常比建类层次更 Pythonic、更好懂（课 8 / 课 10）。
