# 10 · 场景解法库（设计态）

> **定位：设计态。** 面对一个**还没写**的功能，怎么选模式、怎么搭结构 —— 看这里。
> 出事了要快查 → [09-排障速查手册.md](09-排障速查手册.md)；想搞懂原理 → [08-实战经验.md](08-实战经验.md)。
>
> 体例：每个场景 = **需求 → 候选方案对比 → 推荐 → 代码骨架 → 翻转条件**。
> **翻转条件**是重点：方案不是永远对的，条件变了要换药。

## 场景 1 · 支付方式会一直加（支付宝 / 微信 / 银行卡 / 货到付款…）

**需求**：订单要支持多种支付方式，渠道还在持续增加，每次加渠道不想改主流程。

**候选方案**

| 方案 | 加新渠道的代价 | 适用 |
|---|---|---|
| `if-elif` 链 | 改主流程（+1 分支） | 2-3 种且基本不变 |
| **工厂函数 + 字典注册表** | **新增函数 + 注册一行** | ✅ 推荐 |
| 工厂方法（`ABC` + 子类） | 加一个子类 | 需要继承体系、子类有差异行为 |
| 抽象工厂 | 加一整套子类 | 一族对象成套创建（不只是支付一种） |

**推荐：工厂函数 + 字典 + `__init_subclass__` 自动注册**

```python
PAYMENTS: dict[str, Callable[[Order], str]] = {}

class Payment(ABC):
    channel: str = ""
    def __init_subclass__(cls, channel: str = "", **kw):
        super().__init_subclass__(**kw)
        if channel:
            PAYMENTS[channel] = cls()

class Alipay(Payment, channel="alipay"):
    def pay(self, o): return f"支付宝支付 {o.total:.2f} 元"

# 加货到付款 = 定义一个新类 + 给个参数，注册表自动更新
class CashOnDelivery(Payment, channel="cod"):
    def pay(self, o): return "货到付款，签收时收款"
```

**翻转条件**
- 渠道只有 2-3 种且半年内不会加 → **别上工厂**，`if-elif` 就行（课 3）
- 每种支付还要配套"退款方式 + 对账格式"（一族对象） → 升级为**抽象工厂**
- 支付之外还涉及"计价规则也随渠道变" → 工厂 + **策略**组合

## 场景 2 · 计价规则复杂且会变（会员折扣 / 满减 / 大客户）

**需求**：不同会员等级不同折扣，还要支持满减、大客户优惠，规则在持续加。

**候选方案**

| 方案 | 适用 |
|---|---|
| `if-elif` 判断等级 | 2-3 档且不变 |
| **一等函数 + 字典分发** | ✅ 推荐：算法无状态、可整体替换 |
| 类策略（`Protocol` + 注入） | 算法**有状态**，或是"一套多方法"（计价+退款+积分） |
| GoF 装饰器叠加 | 各种优惠可**自由组合**（满减 + 会员折 + 运费险） |

**推荐：优先字典分发；需要叠加时换装饰器**

```python
# ① 单一规则：字典分发
PRICING = {"normal": _normal, "gold": _gold, "big_client": _big_client}
total = PRICING[o.level](o)

# ② 规则要叠加：装饰器（注意顺序——外层最后执行）
price = MemberDiscount(FullReduction(ShippingInsurance(base)))
```

**翻转条件**
- 只有 2-3 个可选功能且不常变 → `if-else` 就行，**别过度设计**（课 6）
- 变化的是"整个流程"而不是"某一步算法" → 不是策略，重新识别变化点
- 规则可以由运营配置（不用发版） → 考虑**规则引擎**或配置化，模式解决不了发版问题

## 场景 3 · 要接三家外部系统，接口五花八门

**需求**：物流、发票、风控三家 SDK 各自为政，方法名/参数/返回格式全不一样。

**候选方案**

| 方案 | 适用 |
|---|---|
| 在调用方写转换 | ❌ 转换散落各处，散弹式修改 |
| **函数适配器**（闭包） | ✅ 只差格式转换、无状态 |
| 类适配器 | 转换逻辑复杂、有状态 |
| **外观** | 要统一**多个子系统**的编排（下单要连调三家） |

**推荐：函数适配器起步，需要编排时加外观**

```python
# 目标接口用 Protocol 描述（外部 SDK 不继承也能适配）
class Shipper(Protocol):
    def ship(self, o: Order) -> str: ...

def adapt_logistics(sdk) -> Shipper:
    class _A:
        def ship(self, o): return sdk.pushOrder(o.no, o.addr)
    return _A()

# 多个子系统要统一入口 → 外观
class OrderFacade:
    def __init__(self, logistics: Shipper, invoice, risk): ...
    def place(self, o: Order): ...
```

**翻转条件**
- 子系统只有一两个组件、不复杂 → **直接调，不需要外观**（课 5）
- 两个**已有**系统接口不兼容 → 适配器（**事后补救**），不是桥接（事前设计）

## 场景 4 · 两个维度都会独立增加（通知渠道 × 紧急度）

**需求**：通知要支持短信/邮件/钉钉/企微，同时分普通/加急，**两个维度都在加**。

**候选方案**

| 方案 | 类数量 | 问题 |
|---|---|---|
| 继承排列组合 | M × N | 4 渠道 × 2 紧急度 = 8 个类；加一个维度成员要加 N 个类 |
| **桥接** | **M + N** | ✅ 推荐：两个维度各自成轴，组合连接 |

**推荐：桥接（`Protocol` + 构造注入，乘法变加法）**

```python
class Channel(Protocol):
    def send(self, msg: str) -> None: ...

class Notifier:                      # 抽象轴
    def __init__(self, channel: Channel): self._ch = channel
    def notify(self, msg): self._ch.send(msg)

class UrgentNotifier(Notifier):      # 抽象轴的扩展（重试/升级）
    def notify(self, msg): 
        for _ in range(3): self._ch.send(msg)

# 4 渠道 + 2 紧急度 = 4 + 2 = 6 个类，不是 8 个；再加一维也不炸
```

**翻转条件**
- **只有一个维度会变**（比如只有格式变） → 不用桥接，单条继承或参数化就够（课 7）
- 两个维度是**事后**发现不兼容 → 那是适配器，不是桥接

## 场景 5 · 订单状态流转，还要通知一堆系统

**需求**：待支付 → 已支付 → 已发货，状态一变要通知用户、库存、报表，订阅方还在增加。

**推荐：状态（转移表）+ 观察者（订阅列表）组合 —— 两个正交的问题分开解**

```python
# ① 状态机：负责"能不能转"（合法性由表结构保证，漏配即拒绝）
TRANSITIONS = {
    ("created", "pay"):    to_paid,
    ("created", "cancel"): to_cancelled,
    ("paid",    "ship"):   to_shipped,
}

# ② 观察者：负责"转了告诉谁"（事件源不知道观察者是谁）
order.subscribe(send_sms)
order.subscribe(update_stock)
order.subscribe(append_report)
```

**翻转条件**
- 订阅方之间有**顺序/依赖** → **别用观察者，写显式流程**（课 9）
- **跨系统/跨进程**广播 → 消息队列（发布订阅的分布式版），不是进程内观察者
- 每个状态的行为很重（一堆方法） → **类版状态模式**，别硬塞进转移表
- 订阅方是大对象 + 事件源长生命周期 → 名单用 `weakref.WeakSet` 防内存泄漏

## 场景 6 · 下单请求要层层校验，顺序还想能调

**需求**：下单要过"风控 → 限购 → 库存"，大促时想把风控前置，顺序经常变。

**推荐：责任链（中间件式，拦截即停 + 链序可配置）**

```python
def risk(order, next_):
    return "风控拦截" if order.amount > 10000 else next_()   # 拦截：不调 next_

def build_chain(*mws):
    def run(order):
        def dispatch(i):
            return None if i == len(mws) else mws[i](order, lambda: dispatch(i + 1))
        return dispatch(0)
    return run

check = build_chain(risk, limit, stock)   # 平时
check = build_chain(risk, stock, limit)   # 大促：一行重组装，校验函数零改动
```

**翻转条件**
- 请求要通知**所有**处理者（不是一环拦截） → 那是**观察者**（群发 vs 接力）
- 校验之间**有强依赖**（B 必须用 A 的结果） → 链不合适，写显式流程
- 末端别忘加兜底处理者，否则请求可能无人处理

## 场景 7 · 要支持撤销 / 重做

**需求**：用户手滑点了"发货"想撤回；或者取消订单要能恢复。

**候选方案**

| 方案 | 做法 | 适用 |
|---|---|---|
| **命令（反着做）** | 每个命令实现 `undo()` | 反动作**能**写出来（省内存） |
| **备忘录（读档）** | 动手前拍快照，撤销时恢复 | ✅ 反动作**写不出来**（已调外部物流） |
| 补偿动作 | 不回滚，做一笔反向业务 | 已产生外部副作用（补发更正短信） |

**推荐：反动作写得出用命令，写不出用备忘录；两者可混用（命令揣快照）**

```python
# 备忘录式（课 12 取消订单用的就是它，反动作一行没写）
snapshot = copy.deepcopy(order)     # 动手前先拍
...                                  # 执行操作
order = snapshot                     # 撤销 = 读档恢复
```

**翻转条件**
- 对象很大 + 撤销频繁 → 快照太占内存，改用**命令式 delta**
- 已经调了第三方（发了短信、扣了款） → 回滚不了，只能**补偿**
- 只是替换算法、不需要留痕 → 用**策略**，别上命令（命令是"记账本"）

## 场景 8 · 要处理百万级数据，不能全装内存

**推荐：迭代器 + 生成器（Python 已语言内化，GoF 23 种里唯一）**

```python
paid  = (o for o in all_orders if o.paid)     # 生成器：数据在流里，不在内存里
page1 = list(itertools.islice(paid, 100))     # 惰性分页，内存占用常数
```

**翻转条件**
- 需要**反复**遍历同一批数据 → 先 `list()` 固化（生成器是一次性的，走完即空）
- 需要**随机访问 / 知道总数** → 生成器不合适（它不提供 `len()`）
- 数据源本身就是分页 API → 直接在生成器里包分页请求，调用方无感

## 场景 9 · 重构一段"跑得动但改不动"的老代码

**推荐：四步重构法（课 12）—— 第 0 步不能省**

| 步 | 动作 | 产出 |
|---|---|---|
| **0** | **先织测试网**：挑固定订单（成功 + **拒绝**路径都要有），锁死重构前输出 | 行为基准 |
| 1 | 闻坏味道 | 长 `if-else` / 上帝类 / 散弹式修改 / `XxxAndYyy` 类名 |
| 2 | 问变化点（三问） | 变化真会来吗 / 在哪 / 团队看得懂吗 |
| 3 | 查药方 | 见本文各场景 |
| 4 | **小步替换**，每步对基准，逐字一致才继续 | 可验证的重构 |

🎯 **验收**：新增需求 = 新增实现 + 注册一行，主流程**一行未改**。
课 12 实测：三个新需求 = 三个新函数 + 三行注册；代价是代码量**约 45 行 → 约 100 行（翻倍）**。

**翻转条件**
- 这段代码三个月后就要下线 → **别重构**，成本收不回来
- 没有测试、也没法补 → 风险极高，先补测试网再谈重构（重写 ≠ 重构）
- 变化点问不出来 → 说明还没理解这个模块，先读代码，别急着改

---

## 收尾 · 九个场景的共同规律

1. **先找变化点，再选模式**。九个场景的第一步都不是"用哪个模式"，而是"什么在变"。模式是药方，变化点是病。
2. **优先最轻的方案**。一等函数 + 字典，通常比建类层次更 Pythonic、更好懂。类只在"有状态"或"一套多方法"时才值得。
3. **每个推荐方案都有翻转条件**。模式不是身份象征，条件变了就换药 —— 课 12 的原话：**词汇不是法律**。
4. **模式的成本是真实的**。抽象要钱：多出来的类、更深的栈、新人的认知负担。课 12 那笔账是从 45 行到 100 行。
5. **组合才是常态**。真实场景几乎都是组合：工厂+策略、观察者+状态、责任链+命令、命令+备忘录。
