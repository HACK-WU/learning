# 设计决策

> 每个决策点都是**换个人来可能选另一个方案，且也有道理**的那种。
> 格式：候选方案 → 最终选择 → 理由 → 付出的代价 → 什么情况下该改选另一个。

## 决策 1：日志怎么进 Loki？—— Promtail 文件采集 vs 应用直推

### 候选方案

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. Promtail 采文件**（业界标准） | 应用写日志文件，Promtail 用 inotify 监听并推送 | 应用零耦合；有 `positions.yaml` 断点续传；应用挂了日志不丢 | 需要文件采集器；依赖 inotify |
| **B. 应用直推 Loki** | 应用内起线程，批量 POST 到 Loki | 无需额外组件；链路短；不受文件系统限制 | 应用与 Loki 耦合；无落盘缓冲；无背压 |
| **C. Docker 日志驱动** | 配 `loki` logging driver | 零代码改动 | 容器重启后历史日志难保留；标签控制弱 |

### 最终选择

**B：应用直推 Loki**（保留 A 的配置文件 `实现/promtail/promtail.yml` 并注释说明）

### 选择理由

**不是因为 B 更好，而是因为 A 在 WSL 上跑不起来。**

实测过程：

```
$ docker run ... grafana/promtail:3.0.0 -config.file=/etc/promtail/promtail.yml
level=error msg="error creating promtail"
        error="failed to make file target manager: too many open files"
```

查根因：

```
$ cat /proc/sys/fs/inotify/max_user_instances
128
```

**WSL 的 `fs.inotify.max_user_instances` 只有 128**（宿主内核参数），而 Promtail 的文件发现机制要为被采集目录建 inotify 实例。加 `--privileged` 也无效——**inotify 限制来自宿主内核命名空间，不是容器能力**（实测：privileged 模式照样 `Exited (1)`）。

### 付出的代价

| 代价 | 具体表现 |
|---|---|
| **应用与 Loki 耦合** | 应用代码里硬编码了 `LOKI_URL`，换日志后端要改代码 |
| **无落盘缓冲** | 应用崩溃瞬间，队列里未发出的日志会丢（Promtail 有 positions 断点续传） |
| **无背压** | Loki 卡住时，推送线程会阻塞；本项目用 `queue.Full` 丢弃兜底，等于静默丢日志 |
| **丢失采集语义** | 生产环境的日志采集还承担多行合并、敏感信息脱敏等，直推全丢了 |

### 什么情况下该改选另一个

**只要是生产环境，就该选 A（Promtail）**，或者更现代的 **Grafana Alloy**。

本项目的 B 方案只在满足**全部**以下条件时才可接受：

1. 演示 / 教学 / 本地开发环境
2. 日志丢了无所谓
3. 无法修改宿主机的 inotify 参数

> **这个决策是本项目最值得记住的一条**：它示范了"选择"和"正确"不是一回事。
> 我选 B 不是因为 B 对，是因为 **A 在这个环境里根本跑不起来**——
> 把"不得不"如实标注为"不得不"，比把它包装成"我们权衡后认为更好"诚实得多。

**给学习者的判断练习**：如果你的环境是标准 Linux（inotify 上限 1024+），这个决策会翻转成什么？

## 决策 2：告警怎么设计？—— 症状型 vs 原因型，以及阈值怎么定

### 候选方案

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. 只告 P90 延迟**（症状型） | 只盯用户能感知的指标 | 告警少，不扰民；一定对应真实体验 | 只知"慢了"，不知"为什么慢" |
| **B. 只告错误率**（原因型） | 只盯系统内部状态 | 定位快 | 有些故障不报错只是慢，会漏报 |
| **C. 两类都告 + 分级路由** | 延迟→warning、错误率→critical、存活→critical 快通道 | 覆盖全；分级后不扰民 | 规则多，维护成本高；可能重复告警 |

### 最终选择

**C：三类告警 + 策略树分级**

| 规则 | 类型 | 阈值 | for | 级别 | 通知通道 |
|---|---|---|---|---|---|
| `shop-p90-latency` | 症状型 | P90 > 0.5s | 1m | warning | `shop-webhook`（group_wait 30s） |
| `shop-error-rate` | 原因型 | 错误率 > 3% | 1m | critical | `shop-catchall`（group_wait 10s） |
| `shop-down` | 可用性 | `up < 1` | 0s | critical | `shop-catchall`（group_wait 0s） |

### 选择理由

**核心理由：症状型和原因型回答的是不同的问题，缺一不可。**

- **症状型**回答"用户有没有受影响" —— 决定要不要半夜叫人
- **原因型**回答"系统哪里坏了" —— 决定叫醒谁、怎么修

只告症状型：值班人被叫醒后还得自己找原因，MTTI（平均定位时间）变长。
只告原因型：某些故障（如慢查询）不产生错误码，会漏报。

实测数据支撑这个设计：注入故障后，**checkout 的 P90 从 0.09s 涨到 2.6~4.3s（约 30~47 倍），而错误率稳定在 52%~61%**。

> 注意：**错误率高是因为故障注入本身让 checkout 大量失败**，这是刻意构造的极端场景。
> 真实业务里"慢但不报错"的故障，错误率往往接近 0——那才是延迟告警不可替代的场景。
> 反过来，错误率告警不可替代的场景是"快速失败"：请求 50ms 就返回 500，延迟指标完全看不出来。

### 付出的代价

| 代价 | 具体表现 |
|---|---|
| **同一故障产生多条告警** | 实测：一次故障同时触发了延迟 + 错误率两条（告警轰炸风险） |
| **阈值是拍的** | 0.5s / 3% 没有业务依据，是我按"看起来合理"定的 |
| **维护成本** | 3 条规则 × 3 个表达式，改一个要动 YAML 再重载 |
| **重复告警的风险** | 两条告警指向同一个根因，值班人会困惑"到底有几个问题" |

### 什么情况下该改选另一个

- **小团队 / 值班人少** → 砍到只剩 1 条（建议留症状型），宁可漏报也不扰民
- **有 SLO 体系** → 换成**多窗口多燃烧率告警**（课 7 提过），比固定阈值科学得多
- **告警太多已经没人看** → 先做减法（关掉一半规则），再谈分级

> **这个决策的争议点是真的**：不少 SRE 主张"告警必须可行动，否则就是噪音"，
> 按这个标准，P90 延迟告警"只说慢了不说哪慢"是不可行动的，应该删掉。
> 我保留它是因为**它是唯一能反映用户体感的信号**——这个权衡没有标准答案。

## 决策 3：配置怎么管理？—— 全量 provisioning vs UI 点击 + 导出

### 候选方案

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. 纯 UI 点击** | 在界面上配好一切 | 所见即所得，学习成本低 | 不可版本化；换机器要重配一遍；无法 review |
| **B. UI 配好后导出 JSON** | 点完导出，把 JSON 存进 git | 有备份 | 导出的是快照，改了 UI 不同步；人容易忘 |
| **C. 全量 provisioning** | 一切写 YAML/JSON，UI 只读 | 可版本化、可 review、可一键重建 | 上手慢；调试要重启容器；UI 改了会被覆盖 |

### 最终选择

**C：全量 provisioning**（数据源 + dashboard + 告警 + 通知策略，全部文件化）

### 选择理由

**本项目的验收标准里有一条"删掉容器，一条命令恢复全部配置"——只有 C 能满足。**

实测验证：

```bash
docker rm -f p3-grafana
docker run -d ... -v "$W/实现/provisioning:/etc/grafana/provisioning:ro" ...
# → 3 个数据源 + 9 面板 dashboard + 3 条告警规则 + 策略树，全部自动恢复
```

这个能力在真实场景里的价值：**灾备、多环境一致性、新人入职**。

课 10 已经实测过 UI 与 provisioning 的冲突规则（file provisioning 会在重启时覆盖 UI 改动），这里正是那个知识点的应用。

### 付出的代价

| 代价 | 具体表现 |
|---|---|
| **调试循环变长** | 改一个字段要重启容器（实测每次约 8 秒 + 配置校验） |
| **UI 变成只读** | 想在界面上试个查询可以，但保存了也不会持久化 |
| **YAML 语法负担** | 告警规则的 `model` 嵌套结构手写很容易出错（我第一次提交就 400） |
| **新人门槛高** | 直接点 UI 5 分钟能配完的东西，写 YAML 可能要 30 分钟 |

### 什么情况下该改选另一个

- **个人学习 / 一次性演示** → 选 A，别折腾 YAML
- **团队初期还没定规范** → 选 B 过渡，先把配置存下来
- **已有 CI/CD 且需要多环境** → 必须 C

> **一个务实的中间路线**（本项目没采用但值得知道）：
> **UI 里配 → 用 API 导出 → 转成 provisioning 文件**。
> 兼顾了"所见即所得"和"可版本化"。代价是需要维护转换脚本。

## 踩坑记录（这些不是决策，是硬事实）

| # | 坑 | 现象 | 正解 |
|---|---|---|---|
| 1 | exemplar 不自动挂 | Prometheus 查 `query_exemplars` 返回空 | `Histogram.observe(v, exemplar={'trace_id': ...})` 必须显式传 |
| 2 | 告警模板不渲染 | summary 原样输出 `{{ $labels.route }}` | 用 `$labels` / `$values.B.Value`；YAML 里别写成 `$$labels` |
| 3 | `$labels` 只含查询标签 | `{{ $labels.alertname }}` 取不到 | 内置标签（`alertname` 等）不在 `$labels` 里 |
| 4 | range query 不能直接取值 | `{{ $values.A.Value }}` 空 | 先加 reduce（refId=B），用 `$values.B.Value` |
| 5 | Promtail 在 WSL 起不来 | `too many open files` | inotify `max_user_instances=128`，换直推或改宿主参数 |
| 6 | contacts API 返回扁平列表 | 误以为 receivers 为空 | `/api/v1/provisioning/contact-points` 返回的是 receiver 扁平数组 |
| 7 | 告警不会立刻重发 | 改了模板但收不到新告警 | `repeat_interval` 5~10 分钟；想马上看效果要建新规则 |
| 8 | 分子为空导致告警模板报错 | 日志报 `humanizePercentage: can't convert <nil> to float` | 比率型表达式加 `or (分母 * 0)` 兜底，见下 |

### 踩坑 8 详解：比率型告警在「分子没数据」时会崩模板

这条是**本次一键重建核验时抓出来的**，之前 12 课和项目前几轮都没暴露——因为它只在**没有 500 错误**时才出现，而前面的测试几乎都在故障注入状态下跑。

**现象**：Grafana 日志里

```
level=error msg="Error in expanding template"
  error="... at <humanizePercentage $values.B.Value>:
         error calling humanizePercentage: can't convert <nil> to float"
```

**根因链**（四步，缺一不可）：

1. 表达式 `sum(rate(shop_requests_total{status="500"}[2m])) / sum(rate(shop_requests_total[2m]))`
2. 系统正常时 **`status="500"` 这个序列根本不存在**，分子是空
3. PromQL 里 `空 / 非空` = **空**（不是 0），整个表达式返回空结果
4. 下游 reduce（refId=B）拿到空 → `$values.B.Value` 为 `nil` → `humanizePercentage(nil)` 直接报错

**为什么这条坑特别值得记**：它**只在健康状态下出现**。绝大多数人测告警是在故障状态下测的（那时一切正常），于是这个错误一直潜伏，直到系统长期健康、某天第一次真的出错时，反而可能因为别的原因表现异常。

**实测修复**（两种写法都验证过）：

```promql
# 修复写法：给比率表达式加 or 兜底
(sum by (route) (rate(shop_requests_total{status="500"}[2m]))
  / sum by (route) (rate(shop_requests_total[2m])))
or (sum by (route) (rate(shop_requests_total[2m])) * 0)
```

| 场景 | 修复前 | 修复后 |
|---|---|---|
| 无 500（健康） | `[]`（空）→ 模板报错 | 5 条 route 全返回 `0` |
| 有 500（故障） | 0.6667 | 0.6667（不变） |

> **判断口诀**：**凡是写了「A / B」这种比率表达式的告警，都要问一句：A 没数据时会怎样？**
> 答案是"整个表达式变空"，而不是"变成 0"。
> 修法是 `or (B * 0)`——借用分母的标签维度补一个 0 值，既保证有数据，又保证标签维度一致。
