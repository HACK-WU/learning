>
> ```bash
> # ① 取一个带 trace_id 的 exemplar
> curl -s --noproxy '*' --data-urlencode 'query=shop_request_duration_seconds_bucket' \
>   http://localhost:3110/api/v1/query_exemplars
>
> # ② 用同一个 trace_id 去 Loki 捞日志
> #    Grafana → Explore → 选 Shop-Loki → {job="shop"} |~ "<tid>"

> # ③ 用同一个 trace_id 去 Jaeger 查链路

## 自测答案（[反例对照.md](反例对照.md) 末尾 5 题）

### 1. 可以在 Loki 里按 `user_id` 过滤，把 `user_id` 提升为标签吗？

**不可以。** 用和判断 trace_id 完全相同的标准：

> 这个字段的取值范围有多大？

`user_id` 和 `trace_id` 是同一类——**每个用户一个值，取值空间随用户数线性增长**，是典型的高基数字段。

提升为标签的后果也和 trace_id 一样：每个 user_id 一个 stream → 索引膨胀 → 查询变慢 → 最终 OOM。

**正确做法**：`user_id` 留在日志内容里，用 `|~ "user123"` 全文检索，或用 `|=` 子串匹配。

注意"高基数"不是看字段名字，是看**取值个数**：
- `level`（INFO/WARN/ERROR，3 个）→ 可以做标签 ✅
- `route`（本项目 5 个）→ 可以做标签 ✅
- `user_id`（几千到几百万）→ 只能做内容 ❌
- `trace_id`（每条请求一个）→ 只能做内容 ❌

### 2. 告警只配了"错误率 > 5%"，用户反馈"很卡"但告警没响，为什么？

**因为"卡"和"错"是两件不同的事。** 错误率告警只覆盖**失败请求**，慢请求是**成功返回**的——HTTP 200，只是用了 4 秒。

关键在**反过来的那半句**：**一个请求可以慢到用户崩溃，但一个错误都不产生。**

举个本项目之外的典型例子：数据库某个查询走了全表扫描，每个请求 3 秒但都成功返回。
这时错误率是 **0%**，错误率告警永远不会响——而用户已经在骂了。

本项目实测的数据反而要**反过来读**（这里容易搞混，注意看）：

| 场景 | P90 延迟 | 错误率 | 延迟告警 | 错误率告警 |
|---|---|---|---|---|
| 本项目故障注入 | 2.6~4.3s | 52%~61% | 响 ✅ | 响 ✅ |
| 真实的"慢查询"故障 | 3s | **0%** | **响 ✅** | **不响 ❌** |
| 真实的"快速失败"故障 | 0.05s | 40% | **不响 ❌** | **响 ✅** |

> 本项目的故障注入同时把**延迟和错误率都拉高了**（35% 下游超时 + 30% checkout 失败叠加），
> 所以两条告警都响。它演示的是"两条怎么配合"，**不是**"只配错误率就够"。
> 真正说明"只配错误率不够"的是中间那一行：慢但成功，错误率告警完全无感。

**结论**：
- 错误率告警回答的是"有多少请求失败了"
- 延迟告警回答的是"成功的请求有多慢"

**两者必须都配**，这就是 RED 三件套（Rate / Errors / Duration）为什么是三件套而不是一件。本项目配的 3 条规则正是：
- `shop-p90-latency`（Duration）
- `shop-error-rate`（Errors）
- `shop-down`（可用性，Rate 的极端情况）

附带一层：即使看延迟，**也不能用平均值**（见反例 2）——平均值会把 4 秒的长尾稀释成 0.17s，照样不响。

### 3. 配了 exemplar 但图上没有圆点，可能缺了哪些条件？（3 个）

三个条件**缺一不可**，缺任何一个圆点都不出现，且**都不报错**：

1. **应用侧显式传了 exemplar**
   `prometheus_client` **不会自动挂**。必须写成：
   ```python
   LATENCY.labels(...).observe(duration, exemplar={"trace_id": format_trace_id(ctx.trace_id)})
   ```
   验证：`curl '.../api/v1/query_exemplars?query=shop_request_duration_seconds_bucket'` 返回空数组 = 没传。

2. **Prometheus 开了 exemplar 存储**
   启动参数必须带 `--enable-feature=exemplar-storage`（本项目 `up.sh` 已带）。没开的话 exemplar 直接被丢弃。

3. **Grafana 数据源声明了 exemplar 去向**
   ```yaml
   jsonData:
     exemplarTraceIdDestinations:
       - name: trace_id
         datasourceUid: shop-jaeger
   ```
   没配的话，Grafana 拿到了 trace_id 也不知道该跳去哪儿。

**为什么排查这么难**：这三个条件分布在**应用 / Prometheus / Grafana** 三个不同的地方，
而且失败时**全部静默**——指标照常显示，P90 曲线画得漂漂亮亮，只是圆点不存在。
排查要按顺序从 1 查到 3：先查 Prometheus 有没有存（条件 1+2），再查 Grafana 能不能跳（条件 3）。

### 4. 改了告警模板，为什么等了 2 分钟还没收到新告警？

**因为 `repeat_interval`。**

告警从 Pending → Firing 后会发一次通知，之后**持续未恢复时按 `repeat_interval` 重发**，不是每次有新数据就发。本项目配置：

| 策略 | group_wait | repeat_interval |
|---|---|---|
| 默认（warning） | 30s | **10m** |
| severity=critical | 10s | **5m** |

所以改完模板要等**最多 10 分钟**才会重发一条。Grafana 认为"这条告警已经通知过了，5/10 分钟后再说"。

**三种处理方式**（选一）：

1. **等**：等到 repeat_interval 到了自然重发（最省事，但要耐心）
2. **让它先恢复再重新触发**：关掉故障注入 → 告警变 Resolved → 再开启故障 → 全新一轮通知，不受 repeat_interval 约束
3. **在 UI 上手动重发**：Alerting → 该条告警 → 触发一次测试通知

> 这是我踩过的坑：改完模板等了 2 分钟没动静，一度以为配置写错了，
> 实际上是**配置生效了，只是没到重发时机**。
> 判断口诀：**改了告警相关配置没立刻看到效果，先算 repeat_interval，别急着改第二遍。**

### 5. 服务全挂和接口变慢，应该走同一个通知通道吗？

**不应该。**

| | 服务全挂（`shop-down`） | 接口变慢（`shop-p90-latency`） |
|---|---|---|
| 严重度 | critical | warning |
| 期望响应 | 立刻，可能要半夜叫醒人 | 工作时间处理即可 |
| 通知方式 | 电话 / 短信 / 专用群 | 群消息 / 邮件 |
| 容忍等待 | 0 秒 | 攒一攒（30s）反而更好 |

塞进同一个通道的后果（反例 3）：

1. **告警疲劳**：两条通知长得差不多，值班人看一眼就划走
2. **critical 被淹没**：服务全挂和接口变慢在同一个通道里**无法区分优先级**
3. **无法自动化**：没法写"critical 打电话、warning 发群消息"这种规则

**本项目的做法**——策略树按标签路由：

```yaml
routes:
  - receiver: shop-catchall
    matchers: ['severity = critical']
    group_wait: 10s
    repeat_interval: 5m
    continue: false        # 匹配到就停，不再往下走
  - receiver: shop-catchall
    matchers: ['signal = availability']
    group_wait: 0s         # 服务挂了立刻发，一秒都不攒
    continue: false
```

实测：critical 走 `/critical`（10s 内到达），warning 走 `/alert`（23s 后到达），**路径不同**。

**关键细节**：子策略必须设 `continue: false`。不设的话一条 critical 告警会**同时**命中父策略和子策略，发给两个联系人，反而制造重复噪声。
