# 反例对照：能跑，但很糟

> 下面每一条都是**真的能跑出结果**的写法——不是语法错误，是设计错误。
> 它们之所以危险，正是因为"能跑"：跑通了你就以为是对的，直到生产出事。

---

## 反例 1：把 trace_id 提升成 Loki 标签

### ❌ 反例：看起来很方便

```yaml
pipeline_stages:
  - json:
      expressions:
        trace_id: trace_id
  - labels:
      trace_id:        # ← 把 trace_id 提升为标签
```

跑起来：**完全正常**。Grafana 里甚至能直接按 trace_id 过滤，看起来很方便。

### 为什么很糟

Loki 的索引是**按标签组合**建的。每个不同的标签组合 = 一个独立的 stream = 一份独立索引。

trace_id 是**每条请求都不一样**的高基数字段。往索引里塞 trace_id，等于给每一条日志建一个 stream。

| 指标 | 低基数（正确） | 高基数（反例） |
|---|---|---|
| stream 数 | 5 个（5 个 route） | **无限增长**（每请求一个） |
| 索引大小 | 几 KB | **随日志量线性膨胀** |
| 查询速度 | 快（先按标签筛 stream） | 慢（要先扫百万级 stream） |
| 内存占用 | 稳定 | **chunk 越多越吃内存，最终 OOM** |

**一个类比**：这就像给图书馆每本书都建一个独立的分类卡——索引比书还大，找书反而更慢。

### ✅ 正确做法

```yaml
pipeline_stages:
  - json:
      expressions:
        level: level
        route: route
        trace_id: trace_id     # 解析出来
  - labels:
      level:
      route:                   # 只提升低基数字段
      # trace_id 不提升！
```

trace_id 保留在**日志内容**里，用 `|~ "xxx"` 全文检索：

```
{job="shop"} |~ "8ce884d66358a902d6b0625d20b607ea"
```

实测：本项目里这条查询命中 2 条日志（同一请求的两条），耗时 18ms。

**完整闭环实测**（同一个 trace_id 在三个系统里都能找到，用脚本 `p3-drill-full.sh` 跑通）：

```
[第1跳] 指标 → 链路
   Prometheus query_exemplars：24 组 / 3063 个 exemplar，全部带 trace_id
   取其中一个：c57731cce9f6077bc0b628fd175563fa

[第2跳] 链路 → 日志
   Loki 查询 {job="shop"} |~ "c57731..."：
   命中 2 条
     - 处理 /checkout 成功
     - 调用下游 payment 成功

[第3跳] trace 内部
   Jaeger：spans=2
     - HTTP /checkout   2.71s（根 span）
     - call-payment     1.71s（子 span，占了 63%）
```

> **这三跳串起来的价值**：值班人从"P90 告警响了"到"是 payment 这个下游慢"，
> 全程**没有开第二个控制台，也没有手工换算过一次时间戳**——
> trace_id 是系统自动带过去的，这就是"3 分钟定位"能成立的技术底座。

### 代价对比

| | 反例 | 正解 |
|---|---|---|
| 查询写法 | `{job="shop",trace_id="xxx"}` | `{job="shop"} \|~ "xxx"` |
| 查询性能 | 标签多了反而慢 | 内容检索，毫秒级 |
| 存储成本 | 灾难级 | 可控 |

> **判断口诀**：*这个字段的取值范围有多大？* 有限且少（十几个以内）→ 可以做标签；
> 每条都不同（trace_id / user_id / order_id / IP）→ **只能做内容**。

## 反例 2：用平均值告警，不看分位数

### ❌ 反例：看起来很严谨

```promql
# 告警条件：平均响应时间 > 0.5s
sum(rate(shop_request_duration_seconds_sum[2m]))
  / sum(rate(shop_request_duration_seconds_count[2m])) > 0.5
```

跑起来：**完全正常**，数值也对。而且看起来比 P90 "更全面"（用了所有数据点）。

### 为什么很糟

**平均值会被长尾骗。** 看本项目实测的一组数据：

| 接口 | P50 | P90 | 平均 |
|---|---|---|---|
| /checkout（故障中） | — | **2.6 ~ 4.3s**（6 次采样） | ~0.9s |
| /home（正常） | 0.091s | 0.099s | ~0.09s |

假设 checkout 占 10% 流量：平均值 ≈ 0.9×10% + 0.09×90% ≈ **0.17s**。

**用户体感是"每 10 个下单就有 1 个要等 4 秒"，但平均延迟显示 0.17s，告警不响。**

这就是平均值告警的经典失效场景：**少数用户的极差体验被多数人的良好体验稀释掉了**。

### ✅ 正确做法

```promql
histogram_quantile(0.9,
  sum by (le, route) (rate(shop_request_duration_seconds_bucket[2m]))
) > 0.5
```

按 route 分组 + P90，才能看出"是哪一个接口慢"。

### 什么时候平均值反而合适

平均值**不是不能用**，它适合：

- **容量规划**（算总资源消耗时，平均值 × 总量 = 总量）
- **成本估算**
- **作为 P90 的补充**，一起看

**但不适合做唯一的告警判据。**

> **判断口诀**：*关心"典型用户"还是"最惨用户"？* 告警要盯最惨的那一批 → 用分位数。

## 反例 3：把所有告警塞进一个联系人，不分级别

### ❌ 反例：看起来很简单

```yaml
policies:
  - orgId: 1
    receiver: shop-webhook      # 所有告警都发这一个
    group_by: ['alertname']
```

跑起来：**每条告警都能收到**，一条不少。看起来"没毛病"。

### 为什么很糟

实测本项目的一次故障，同时触发了：

```
[04:11:23] → /critical   [Shop] 错误率过高   (critical)
[04:11:46] → /alert      [Shop] P90 延迟过高 (warning)
```

如果都发到一个通道，值班人会收到**两条内容重复、严重度不同**的通知。时间一长：

1. **告警疲劳**：反正都是"Shop 出问题了"，看一眼就划走
2. **真正的 critical 被淹没**：服务全挂和接口变慢，在同一个通道里长得一样
3. **无法自动化**：没法写"critical 打电话、warning 发群消息"的规则

### ✅ 正确做法

```yaml
policies:
  - orgId: 1
    receiver: shop-webhook
    group_by: ['team', 'alertname']
    group_wait: 30s
    routes:
      - receiver: shop-catchall          # 严重告警走快通道
        matchers: ['severity = critical']
        group_wait: 10s                  # 攒 10 秒就发，不等
        repeat_interval: 5m
        continue: false                  # 匹配到就停
      - receiver: shop-catchall
        matchers: ['signal = availability']
        group_wait: 0s                   # 服务挂了立刻发
        continue: false
```

实测效果：critical 告警 **10 秒内**到达，warning 走 30 秒攒批通道。

### 关键机制

| 机制 | 作用 | 本项目取值 |
|---|---|---|
| `group_wait` | 攒一攒再发，避免抖动误报 | warning 30s / critical 10s |
| `group_interval` | 同一组多久发第二次 | 2m |
| `repeat_interval` | 持续未恢复时多久重发 | 10m / critical 5m |
| `continue: false` | 匹配到就停止，防止重复路由 | 全部设 false |
| `group_by` | 哪些标签相同的算一组 | `['team','alertname']` |

> **踩过的坑**：`repeat_interval` 会让告警**不立刻重发**。
> 我改了告警模板后等了 2 分钟还没收到新告警，就是这个原因——
> 不是配置错了，是 Grafana 认为"这条告警已经通知过了，5 分钟后再说"。

## 反例 4：exemplar 忘了显式传，指标到链路的跳转是断的

### ❌ 反例：看起来指标很全

```python
LATENCY = Histogram("shop_request_duration_seconds", "...", ["service", "route"])

# 用的时候：
LATENCY.labels(service=..., route=...).observe(duration)
```

跑起来：**指标完全正常**。Prometheus 能查到 bucket，Grafana 能画 P90 曲线。
**一切看起来都对。**

### 为什么很糟

**`prometheus_client` 不会自动挂 exemplar。** 实测：

```bash
$ curl 'http://localhost:3110/api/v1/query_exemplars?query=shop_request_duration_seconds_bucket'
{"status":"success","data":[]}          # ← 空的
```

结果：**图上永远不会出现那个可点击的小圆点**，"指标 → 链路"这一跳**静默失效**。

这个坑特别阴险的地方在于：

- 不报错
- 指标数据完全正常
- P90 曲线画得漂漂亮亮
- **只有当你想点圆点跳链路时，才发现没有圆点**

### ✅ 正确做法

```python
from opentelemetry.trace import format_trace_id

span = trace.get_current_span()
ctx = span.get_span_context()
if ctx.is_valid:
    LATENCY.labels(service=..., route=...).observe(
        duration,
        exemplar={"trace_id": format_trace_id(ctx.trace_id)}   # ← 必须显式传
    )
```

修复后实测（跑 30 分钟后取样）：

```
exemplar 组数 = 24，exemplar 总数 = 3063，全部带 trace_id
  → 例如 trace_id = c57731cce9f6077bc0b628fd175563fa
```

> 组数会随运行时间增长（10 分钟时约 18 组），**只要非空就说明生效了**。

**另外两个前置条件**（缺一不可）：

1. Prometheus 启动带 `--enable-feature=exemplar-storage`
2. Grafana 数据源配 `exemplarTraceIdDestinations`

```yaml
jsonData:
  exemplarTraceIdDestinations:
    - name: trace_id
      datasourceUid: shop-jaeger
```

> **这条是本项目最大的坑**，因为它**完全静默**。
> 前三条反例至少还有"性能变差""告警不准"这些可观测的症状，
> 这条连症状都没有——**功能就是不存在，而你看不出来**。

## 反例 5：dashboard 手写 JSON，不用脚本生成

### ❌ 反例：看起来直接

手工写一个 800 行的 `shop-overview.json`。

跑起来：**完全能用**。Grafana 认，面板照常显示。

### 为什么很糟

| 问题 | 具体表现 |
|---|---|
| **改一个字段要全文找** | 9 个面板，改数据源 uid 要改 9 处 |
| **无法 review** | git diff 出来是几百行 JSON，人眼看不出改了什么 |
| **容易写错** | 漏个逗号、`gridPos` 算错导致面板重叠 |
| **不可复用** | 想加第 10 个面板，得手抄一份再改 |

### ✅ 正确做法

用脚本生成（本项目的 `实现/gen_dashboard.py`）：

```python
def panel(pid, title, ptype, targets, grid, extra=None):
    ...

panels.append(panel(
    1, "① 请求速率 QPS（按接口）", "timeseries",
    [{"refId": "A", "datasource": DS_PROM, "expr": '...'}],
    {"h": 8, "w": 8, "x": 0, "y": 0},
))
```

好处：

- 布局算出来，不会重叠
- 数据源 uid 集中定义，`DS_PROM` 改一处全盘生效
- git diff 看得出"加了一个面板"
- 想加面板只需 `panels.append(...)`

### 什么时候手写反而合适

- **从 UI 导出的一次性快照**（临时备份）
- **只有 2~3 个面板的小盘**（脚本的收益抵不上成本）

## 汇总：五条反例的共性

| # | 反例 | 为什么"能跑" | 真正的危害 | 发现难度 |
|---|---|---|---|---|
| 1 | trace_id 做标签 | 能查能过滤 | 索引爆炸，最终 OOM | 中（量大才暴露） |
| 2 | 平均值告警 | 数值完全正确 | 长尾故障漏报 | 高（要等出事） |
| 3 | 单通道告警 | 每条都收得到 | 告警疲劳，critical 被淹没 | 中（人会适应） |
| 4 | 忘传 exemplar | 指标完全正常 | 下钻功能静默失效 | **极高（无症状）** |
| 5 | 手写 dashboard | 面板正常显示 | 不可维护、不可复用 | 低（改的时候才发现） |

**共同点**：它们都不是"错"，是**"在你规模还小的时候看不出问题"**。

### 补充一条"只在系统健康时才暴露"的坑

前面五条反例都是"配置写得不好"，还有一类更难发现的：**配置写对了，但在特定数据状态下崩**。

本项目的错误率告警就踩了这个：

```promql
# 看起来完全正确的比率表达式
sum(rate(shop_requests_total{status="500"}[2m]))
  / sum(rate(shop_requests_total[2m]))
```

系统健康时**没有 500 错误**，分子为空 → `空 / 非空 = 空`（不是 0）→ reduce 得 `nil`
→ 模板 `humanizePercentage` 报 `can't convert <nil> to float`。

**它之所以危险**：

- 你测告警时一定是在**故障状态**下测的（那时分子有值，一切正常）
- 所以这个错误**只在你不复现故障的时候出现**——恰恰是你最不关注告警的时候
- 错误出现在**日志里**，界面上看不出来：规则存在、状态正常、就是模板展开失败

**修法**：

```promql
(... ) or (sum by (route) (rate(shop_requests_total[2m])) * 0)
```

> **判断口诀**：写了 `A / B` 就问一句"**A 没数据时会怎样**"。
> 答案是"整个表达式变空"，不是"变成 0"。空值会一路传染到模板，最后以一个
> 完全看不懂的 `can't convert <nil> to float` 报错收场。

详见 [设计决策.md](设计决策.md) 踩坑记录第 8 条。

> **这才是反例对照的意义**：不是教你避开关法错误（那些跑都跑不起来），
> 而是教你识别**"现在能跑、以后会炸"**的写法。

## 给学习者的自测

以下是 5 个真实场景，先自己判断，再看答案（答案在 [验收清单.md](验收清单.md) 末尾）：

1. 你想在 Loki 里按 `user_id` 过滤日志，把 `user_id` 提升为标签可以吗？
2. 告警只配了"错误率 > 5%"，某天用户反馈"很卡"但告警没响，为什么？
3. 你配了 exemplar，但图上没有圆点，可能缺了哪些条件？（3 个）
4. 改了告警模板，为什么等了 2 分钟还没收到新告警？
5. 服务全挂和接口变慢，应该走同一个通知通道吗？
