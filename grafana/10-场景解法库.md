## S1：新人接手一套 Grafana，配置从哪看起

### 🤔 先想一想

你要搞清楚"这套系统现在配了什么"。有三种入口，**它们的答案可能不一致**——先想清楚哪个才是真相。

<details>
<summary>💡 提示（想完再看）</summary>

关键在 **provisioning**：如果配置由文件管理，**文件才是真相**；UI 和 API 读到的可能只是"文件上次写进去的副本"，甚至可能已被人在 UI 上改过而即将被抹掉。

</details>

### 解法对照

| 解法 | 怎么做 | 代价 | 适用边界 |
|---|---|---|---|
| **A · 读 provisioning 文件** | 看 `provisioning/{datasources,dashboards,alerting}/` | 只能看到"文件里有的"，看不到 UI 临时改动 | ✅ **首选**。配置由文件管理时这是真相 |
| **B · 读 UI** | 页面上看 | 看不到 uid、看不到 provisioning 标记；可能已被改且将回滚 | 快速浏览，不作为依据 |
| **C · 读 API** | `GET /api/datasources`、`/api/search` | 要处理鉴权；返回的是数据库状态 | ✅ 想确认"当前运行时状态"时用 |
| **D · 直接读数据库** | 打开 `grafana.db` | ❌ **不推荐**——13.x 是 k8s 风格 `resource`/`resource_history`，序列化未公开 | 见下方"不推荐" |

> ⚠️ **别直接读数据库**：13.x 的存储格式未公开且易误判（课 5 就曾误判"value 是二进制"，实测首字节 `7b` 是明文 JSON，只是存的是内置资源）。可靠方法是 **API 读回**。

**推荐路径**：`A（看文件）` → `C（API 核对运行时）` → 两者不一致说明有人在 UI 改过，下次重启会被抹掉。

**知识点挂钩**：→ [课 1](stages/1-看得见/lessons/lesson-01-Grafana是谁：一个不存数据的看图工具.md)（配置才是资产）· [课 10](stages/4-管得住/lessons/lesson-10-Provisioning：把点击变成配置文件.md)（文件 vs 数据库）

## S2：一张图要服务 N 台机器

### 🤔 先想一想

同一个指标要看 N 台机器。三种做法都能出图，但**查询放大倍数**和**可维护性**差别巨大。

<details>
<summary>💡 提示（想完再看）</summary>

先算查询量：单盘+多值 = 1 条查询返回 N 条曲线；Repeat = **N 条查询**。N=20 时差 20 倍。

</details>

### 解法对照

| 解法 | 查询量 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| **A · 单盘 + 多值变量** | **1 条**（返回 N 帧） | 最省；一张图看全局 | 曲线多时挤成一团 | ✅ **默认首选** |
| **B · Repeat 面板** | **N 条** | 每台独立一张，清晰 | 查询放大 N 倍；JSON 只存 1 份模板 | 机器数少（≤10）且要逐台看 |
| **C · 每个机器一个 dashboard** | N 条（分盘） | 权限好控制 | 维护 N 份配置 | 机器归属不同团队 |

**实测数据**【课 6】：单面板 + All（`.*`）→ **21.8×** 查询放大；叠加 Repeat 推算约 65×（⚠️ 推算值，未实测）。

**决策判据**：

```
N ≤ 10 且要逐台对比 → B
N > 10 或只看趋势 → A
机器分属不同团队 → C
```

**必踩的坑**：多值变量必须用 `=~`，用 `=` 会**静默返回 0 条**【实测，课 3】。

**知识点挂钩**：→ [课 3](stages/1-看得见/lessons/lesson-03-变量与Dashboard组织：一张图服务N台机器.md) · [课 6](stages/2-查得到/lessons/lesson-06-变量进阶与动态仪表盘.md)

## S3：数据查出来了，但形状不对

### 🤔 先想一想

60 条序列想压成 3 行，或者两个查询想并排显示。**在哪一层加工，决定了流量和正确性。**

<details>
<summary>💡 提示（想完再看）</summary>

Transform 在**前端**——数据在那一跳就已原样到达浏览器，Transform 一件也没少买。所以能算的优先写进 PromQL。

</details>

### 解法对照

| 解法 | 执行位置 | 传输量 | 适用 |
|---|---|---|---|
| **A · 改 PromQL 聚合** | 数据源 | **小**（聚合后才传） | ✅ **首选**。能用 `avg by (instance)` 就别用 Transform |
| **B · Transform（reduce/groupBy）** | 前端浏览器 | **大**（原样传完再加工） | PromQL 做不到的（如两列并排 merge） |
| **C · 换个面板类型** | 前端 | 不变 | 只是显示形态不对时 |

**实测判据**【课 5】：60 条压成 3 行，字节数 **75842 → 3720**（约 **20 倍**差距）。

> **口诀**：**Transform 省的是你的眼睛，不是带宽。**

**注意聚合顺序不可交换**【实测】：先 mean 再平均 vs 直接 `avg()`，实测差 **0.0556**。别以为两种写法一样。

**不适用场景**：B 在"跨数据源合并"时是唯一选择（本环境仅 1 个数据源，未实测 ⚠️）。

**知识点挂钩**：→ [课 5](stages/2-查得到/lessons/lesson-05-Transformations：把查出来的数据捏成想要的形状.md)

## S4：告警要按团队 / 级别路由

### 🤔 先想一想

不同团队、不同严重度的告警要发给不同的人。**最容易犯的错是"配置看着对，但一条告警发了两遍"。**

<details>
<summary>💡 提示（想完再看）</summary>

子策略默认会**继续往下匹配**。不设 `continue: false`，一条 critical 会同时命中父策略和子策略。

</details>

### 解法对照

| 解法 | 做法 | 优点 | 陷阱 |
|---|---|---|---|
| **A · 单策略单通道** | 所有告警发一个 Contact point | 最简单 | ❌ 告警疲劳，critical 被淹没 |
| **B · 策略树 + `continue: false`** | 按标签分层路由 | ✅ **推荐** | 子策略必须设 `continue: false` |
| **C · 多 Contact point 平铺** | 每种类型一个，无树结构 | 简单直观 | 无法表达优先级，重复匹配 |

**推荐配置**（[实战项目实测](projects/从告警到定位/README.md)）：

```yaml
policies:
  - orgId: 1
    receiver: shop-webhook
    group_by: ['team', 'alertname']
    group_wait: 30s
    routes:
      - receiver: shop-catchall
        matchers: ['severity = critical']
        group_wait: 10s          # critical 不等，10 秒就发
        repeat_interval: 5m
        continue: false          # ← 关键：匹配到就停
      - receiver: shop-catchall
        matchers: ['signal = availability']
        group_wait: 0s           # 服务挂了立刻发
        continue: false
```

**实测效果**：critical **10 秒内**到达，warning 走 30 秒攒批通道。

**必知的坑**：

- **Reduce 决定收到几条**——按 `route` reduce → 每个 route 一条【实测，课 8】
- **`repeat_interval` 是下界不是闹钟**——配 1m 实测 90s，改完别急着改第二遍
- **Silence 删不掉，只能等过期**——删除后列表里还在，只是 `state` 变 `expired`

**知识点挂钩**：→ [课 8](stages/3-叫得醒/lessons/lesson-08-告警规则与通知策略实战.md)

## S5：打通指标 → 日志 → 链路三级下钻

### 🤔 先想一想

值班人从"告警响了"到"定位根因"，中间最好**不手工换算时间戳、不开第二个控制台**。三跳都要自动带上 trace_id。

<details>
<summary>💡 提示（想完再看）</summary>

三个跳分别靠三个机制，且**每个都可能静默失效**。关键在于：失败时不报错，只是功能不存在。

</details>

### 三跳机制对照

| 跳 | 机制 | 配置位置 | 失败表现 |
|---|---|---|---|
| 指标 → 链路 | **exemplar** | 应用 + Prometheus + Grafana 数据源 | **图上没有圆点，不报错** |
| 日志 → 链路 | **derivedFields** | Loki 数据源 `derivedFields` | 日志里的 trace_id 不可点 |
| 链路 → 日志 | **tracesToLogs** | Jaeger 数据源配置 | 链路里跳不到日志 |

**解法 A · 三跳全做（推荐）**

```yaml
# Loki 数据源：日志 → 链路
jsonData:
  derivedFields:
    - name: trace_id
      matcherRegex: '"trace_id":"(\w+)"'
      datasourceUid: shop-jaeger
```

```yaml
# Prometheus 数据源：指标 → 链路
jsonData:
  exemplarTraceIdDestinations:
    - name: trace_id
      datasourceUid: shop-jaeger
```

**解法 B · 只做两层（指标 + 日志）**

不做 exemplar，靠手工复制 trace_id。代价：每次下钻多 30 秒，**故障时这 30 秒很贵**。

**解法 C · 统一用 trace_id 关联，不做 exemplar**

在日志和链路里都带 trace_id，靠 Grafana 的变量传递。比 A 简单，但少了"点圆点直达"。

**实测闭环**【[实战项目](projects/从告警到定位/反例对照.md)】：

```
[第1跳] Prometheus query_exemplars：24 组 / 3063 个 exemplar，全部带 trace_id
        取 c57731cce9f6077bc0b628fd175563fa
[第2跳] Loki {job="shop"} |~ "c57731..." → 命中 2 条
[第3跳] Jaeger：spans=2
          根 HTTP /checkout   2.71s
          子 call-payment     1.71s（占 63%）
```

**三个必踩的坑**：

1. `prometheus_client` **不会自动挂 exemplar**，必须显式传且判空 `ctx.is_valid`
2. Prometheus 要开 `--enable-feature=exemplar-storage`
3. `exemplarTraceIdDestinations` **后端不校验**——写错 PUT 照样 200

**知识点挂钩**：→ [课 9](stages/3-叫得醒/lessons/lesson-09-日志与链路：指标之外的另外两只眼.md)

## S6：配置要跨环境迁移（开发 → 生产）

### 🤔 先想一想

开发环境配好的东西要搬到生产。**最容易翻车的是"引用断了"**——面板还在，但数据源指不到。

<details>
<summary>💡 提示（想完再看）</summary>

Grafana 靠 **uid** 引用数据源。不写死 uid 让系统自动生成，重建一次环境引用全断。

</details>

### 解法对照

| 解法 | 做法 | 可版本化 | 陷阱 |
|---|---|---|---|
| **A · 纯 UI + 导出 JSON** | 在 UI 配好，导出再导入 | 部分 | 手工操作易漏；uid 可能变 |
| **B · UI + provisioning 导出** | UI 配好后导出成文件 | ✅ | 单向：文件会覆盖 UI 改动 |
| **C · 全量 provisioning + 脚本生成** | 一切皆文件 | ✅✅ **推荐** | 学习成本高 |

**推荐：C**（[实战项目采用](projects/从告警到定位/设计决策.md)）

```
实现/
├── provisioning/
│   ├── datasources/ds.yaml        # uid 全部写死
│   ├── dashboards/dash.yaml       # provider，指向 JSON 目录
│   └── alerting/
│       ├── alert-rules.yaml
│       └── notify.yaml
├── gen_dashboard.py               # 脚本生成 JSON，不手写
└── up.sh / down.sh                # 一键启停，可重复重建
```

**三条硬规则**：

1. **uid 必须自己写死**——不写让 Grafana 生成 = 埋雷
2. **`allowUiUpdates: false`**——明确的失败好过静默的丢失
3. **dashboard JSON 用脚本生成**——手写 800 行 JSON 改一个字段要改 9 处，且 git diff 看不出改了什么

**必踩的坑**【实测，课 10】：先设 `allowUiUpdates: false`、再改 `true`（同实例）→ **HTTP 400**，数据库残留标记没清。症状是"改了配置不生效"。

**知识点挂钩**：→ [课 10](stages/4-管得住/lessons/lesson-10-Provisioning：把点击变成配置文件.md)

## S7：要给外部程序开放访问

### 🤔 先想一想

脚本 / CI / 其他系统要调 Grafana API。**注意：13.2.1 已经移除了 API Key 的创建接口。**

<details>
<summary>💡 提示（想完再看）</summary>

只剩 `api_key` 遗留表，创建接口已移除。程序访问改用**服务账号 + token**。

</details>

### 解法对照

| 解法 | 状态 | 适用 |
|---|---|---|
| **A · API Key** | ❌ **13.2.1 创建接口已移除** | 仅遗留系统兼容 |
| **B · 服务账号 + token** | ✅ **推荐** | 所有程序化访问 |
| **C · 匿名访问** | ⚠️ 谨慎 | 只给公开只读大盘 |

**服务账号实操**【课 11】：

```bash
# 1. 建服务账号（注意返回的 id，后续要用）
curl -X POST /api/serviceaccounts -d '{"name":"ci-bot","role":"Viewer"}'
# 2. 用 id 建 token（不是 id=1！）
curl -X POST /api/serviceaccounts/{id}/tokens -d '{"name":"ci"}'
# 3. ⚠️ key 只在这一次响应里出现，再列一次就没了
```

**三个必踩的坑**【实测，课 11】：

1. **建完服务账号别拿 `id=1` 去建 token**——要用返回的实际 id
2. **token 明文只出现一次**——落库为哈希，忘了就只能重建
3. **备份恢复后 token 会静默 401**——哈希在、明文没了，所有依赖它的程序一起挂

**权限模型**：**角色是入场券，文件夹权限是座位号**。角色决定"能不能做这个动作"，文件夹权限决定"能对哪些资源做"。

**知识点挂钩**：→ [课 11](stages/4-管得住/lessons/lesson-11-权限与服务账号：谁能看、谁能改、程序怎么访问.md)

## S8：dashboard 越来越慢

### 🤔 先想一想

慢了要优化。**但"拆盘"往往不是最优解**——先按正确顺序定位。

<details>
<summary>💡 提示（想完再看）</summary>

实测推翻了三个直觉：面板数影响**没有想象的大**（80 倍面板只慢 4.5 倍）；时间窗长**不会线性变慢**（`maxDataPoints` 封顶）。

</details>

### 排查与解法（按推荐顺序）

| 顺序 | 瓶颈 | 解法 | 实测依据 |
|---|---|---|---|
| 1 | **渲染** | 独立 renderer 实例 | 渲染是 CPU 密集 |
| 2 | **序列基数 / 响应体** | 降基数、加聚合 | 字节数 75842 → 3720 |
| 3 | **面板数** | 拆盘 | **80 倍面板只慢 4.5 倍** |
| 4 | **时间窗** | 通常不是它 | `maxDataPoints` 已封顶 |

**解法对照**

| 解法 | 适用 | 代价 |
|---|---|---|
| **A · 加 renderer 实例** | 慢在服务端渲染图片 | 多一个容器；⚠️ 必须设 `AUTH_TOKEN`，且两侧同名 |
| **B · 降基数 / 聚合下推** | 序列数爆炸 | 要改查询 |
| **C · 拆盘** | 面板确实极多 | 维护多份配置 |

**renderer 的两个坑**【实测，课 12】：① `GF_RENDERING_RENDERER_TOKEN` 不能用默认值，否则 Grafana **拒绝启动** ② renderer 侧也要设**同名** `AUTH_TOKEN`，否则渲染请求 401。

**知识点挂钩**：→ [课 12](stages/4-管得住/lessons/lesson-12-性能、高可用与升级运维.md)

## S9：团队从单人使用变成多人协作

### 🤔 先想一想

原来一个人用，现在整个团队用。**核心矛盾是"SQLite 文件无法共享"**——这是架构事实，不是性能问题。

<details>
<summary>💡 提示（想完再看）</summary>

换 Postgres **不是为了快**，是因为 SQLite 文件没法被多个实例同时读写。

</details>

### 解法对照

| 解法 | 适用 | 关键认知 |
|---|---|---|
| **A · 继续 SQLite** | 单人 / 单机 | 简单，但无法 HA |
| **B · 换 Postgres** | **团队 / 需要 HA** | ✅ **推荐**。为了共享不是快 |
| **C · 拆分 Org** | 多租户隔离 | 跨 Org 资源返回 **404 不是 403**（安全设计：不泄露存在性） |

**HA 的三个反直觉**【实测，课 12】：

- **会话默认随数据库共享**——不需要额外配 Redis
- **告警去重需要额外配置**——不能假设"共享数据库就自动去重"（⚠️ 该项未完整实测）
- **回滚 = 恢复备份**，不是把镜像换回旧版本

**迁移注意**【课 12】：Grafana **没有官方的 SQLite→Postgres 自动迁移工具**。实用做法是"导出 JSON + 重新导入"，且**服务账号 token 不可迁移**（哈希在、明文没了）。⚠️ 完整迁移未实测。

**知识点挂钩**：→ [课 12](stages/4-管得住/lessons/lesson-12-性能、高可用与升级运维.md)

## S10：要设计一套"能值班"的告警

### 🤔 先想一想

告警的目的是**半夜把人叫醒去处理**。所以判据不是"能不能触发"，而是"**触发时值班人能否 3 分钟内定位**"。

<details>
<summary>💡 提示（想完再看）</summary>

三个常见错误：用平均值（长尾被稀释）、所有告警一个通道（critical 被淹没）、比率忘了兜底（健康时崩）。

### 告警设计三要素

| 要素 | 要点 | 常见错误 |
|---|---|---|
| **查询** | 看什么 | 用平均值 → 长尾漏报 |
| **条件** | 什么算异常 | Reduce 维度决定收到几条 |
| **评估行为** | 多久看 / 持续多久 / 看不清怎么办 | `for` 真实延迟算错 |

### 解法对照：告警类型

| 类型 | 判据 | 优点 | 缺点 |
|---|---|---|---|
| **A · 原因型**（CPU 高、磁盘满） | 具体指标越界 | 定位快 | 覆盖不全，没想到的原因就漏 |
| **B · 症状型**（错误率高、P90 高） | 用户可感知的现象 | ✅ 覆盖全 | 只知道"有问题"，不知哪里 |
| **C · 分级混合** | 症状型触发 + 原因型辅助 | ✅✅ **推荐** | 配置复杂 |

**推荐：C**——用症状型保证不漏，用原因型加速定位，按 severity 分级路由。

**三个必须遵守的规则**

1. **用分位数不用平均值**
   ```
   ❌ sum(rate(..._sum)) / sum(rate(..._count)) > 0.5    # 长尾被稀释
   ✅ histogram_quantile(0.9, sum by (le, route)(rate(..._bucket[2m]))) > 0.5
   ```
   实测：checkout 故障中 P90 **2.6~4.3s**、平均 ~0.9s；占 10% 流量 → 整体平均 **0.17s**，告警不响【实战项目】

2. **比率表达式加兜底**
   ```promql
   (A / B) or (B * 0)     # A 没数据时返回 0，不是空
   ```
   否则健康时报 `can't convert <nil> to float`【实战项目实测】

3. **宕机场景单独配**
   ```
   up == 0 → 单独一条 critical
   ```
   **机器宕机走 Alerting（up=0），不走 No Data**——配了 `noDataState` 也不覆盖这个场景
