## 🔴 症状 1：数据源连不上（`connection refused` / 502）

**一眼识别**：数据源 health 检查报 `connection refused` 或 HTTP 502；但你在宿主机 `curl` 同一个地址却是通的。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 若刚部署，先确认依赖的服务容器都在跑 | 排除"目标根本没起" |
| 定位 1 | 看数据源 URL 写的是 `localhost` 还是容器名 | 写 `localhost` → **命中本症状** |
| 定位 2 | 确认 Grafana 与目标是否在**同一 docker network** | 不同网络 → 容器名也解析不了 |
| 定位 3 | 进 Grafana 容器内 `curl` 目标地址 | 通 → 配置问题；不通 → 网络问题 |
| 修复 | URL 改成**容器名** `grafana-prom:9090` | 200 |
| 若无效 | → 转「症状 12」（可能返回 200 但配到了别处） | — |

```bash
# 关键验证：从 Grafana 容器内部拨号（不是从宿主机）
docker exec grafana-lab sh -c 'wget -qO- http://grafana-prom:9090/-/healthy'
```

> **预防**：容器间一律用容器名，永远不写 `localhost`。
> **原理**：→ [08-实战经验.md](08-实战经验.md#故障模式-2url-写了-localhost数据源连不上)

## 🔴 症状 2：图空白，但完全不报错

**一眼识别**：面板一片空白，**一个字都不说**。这是**最难的故障**——至少要区分 4 种成因，UI 表现完全一样。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 先别改面板类型，也别改查询——**先取证** | 避免越改越乱 |
| 定位 1 | 打开面板 `{} JSON`（Inspect → Data 或 Query） | 看 `executedQueryString` |
| 定位 2 | 看内层状态码与帧数 | **外层 200 + 内层 200 + 0 点 = 静默失败** |
| 定位 3 | 把 `executedQueryString` 拿去数据源直接查 | 通 → Grafana 侧问题；不通 → 表达式问题 |
| 定位 4 | 检查是否**多值变量用了 `=`** | 改用 `=~` 即恢复 |
| 定位 5 | 检查是否**变量没替换**（还是 `$host` 字面量） | 前端替换失败 |
| 定位 6 | 检查标签是否真的存在 | Loki/Prom 对不存在的标签返回 200 + 0 行 |
| 修复 | 按上面定位结果改 | 有数据 |
| 若无效 | → 转「症状 3」（可能其实是报错但被吞了） | — |

**四种"图空白"的区分判据**（实测）：

| 成因 | 外层 | 内层 | 帧数 | 点数 | 是否报错 |
|---|---|---|---|---|---|
| 指标名不存在 | 200 | 200 | 1（空） | 0 | **否** |
| 时间窗内无数据 | 200 | 200 | 1（空） | 0 | **否** |
| 变量未替换 / 多值用 `=` | 200 | 200 | 1（空） | 0 | **否** |
| 语法错误 | **400** | 400 | 1 | — | 是 |
| datasource uid 不存在 | **404** | — | **0** | — | 是 |

> **预防**：把"查空白图先看 `executedQueryString`"定为团队约定。
> **原理**：→ [08-实战经验.md](08-实战经验.md#故障模式-4误以为-http-200-等于成功)

## 🟡 症状 3：面板报错 HTTP 400 但看不懂

**一眼识别**：面板报 HTTP 400，但错误信息像是"我写错了"，实际可能是后端不可达。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 确认是单条查询还是全部查询都 400 | 全部 → 后端问题 |
| 定位 1 | 拆开看**内层 status** | 内层 **502** = 后端不可达 |
| 定位 2 | 内层 502 → 查数据源配置与网络 | → 转「症状 1」 |
| 定位 3 | 内层 400 → 才是你查询写错了 | 改表达式 |
| 定位 4 | 看 `errorSource` 字段 | `downstream` = 数据源侧；`plugin` = 插件侧 |
| 修复 | 按内层 status 分流转 | — |
| 若无效 | → 转「症状 2」（可能其实是静默失败） | — |

```
外层 HTTP 说「批量请求办得成不」
内层 status 说「每条查询在下游出了什么事」
HTTP 400 里的 502 = 后端不可达（不是你写错了）
HTTP 400 里的 400 = 你写错了
```

> **原理**：→ [08-实战经验.md](08-实战经验.md#故障模式-4误以为-http-200-等于成功)

## 🟡 症状 4：告警响了，但比预期晚很多

**一眼识别**：配了 `for: 10s`，实际等了 1 分钟才响。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 若已确认故障，先按故障处理，不等告警 | 不依赖告警做应急 |
| 定位 1 | 查规则组的 `interval`（不是 `for`） | 默认 **1m** |
| 定位 2 | 算真实延迟 = `⌈for / interval⌉ × interval` | `for=10s, interval=1m` → **1 分钟** |
| 定位 3 | 确认 `minInterval` 只是**下限**，不是实际值 | 规则组默认 `interval=1m` |
| 修复 | 要更快就**同时**调小 `interval` 和 `for` | 只调 `for` 无效 |
| 若无效 | → 转「症状 5」（可能压根没触发） | — |

> **注意**：`for` 是"**连续**满足多久"，不是延迟。
> **原理**：→ [08-实战经验.md](08-实战经验.md#故障模式-5以为-for-是延迟多久通知)

## 🔴 症状 5：服务全挂了，告警却没响

**一眼识别**：服务彻底挂了、一个请求都没有 → 告警保持 Normal → 你以为服务正常。**这是最危险的一条。**

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 立即人工确认服务状态，别等告警 | 先止损 |
| 定位 1 | 查 `up` 指标 | 服务真挂时 `up=0`，**这是有数据的** |
| 定位 2 | 确认走的分支 | `up=0` → **Alerting 分支**，不是 No Data |
| 定位 3 | 查 `noDataState` 配置 | 若为 `KeepLast` → 指标消失时保持上一状态 |
| 定位 4 | 确认告警规则**是否覆盖了"指标消失"** | 很多规则压根没走到 NoData 分支 |
| 修复 | ① `up == 0` 单独配一条告警 ② `noDataState` 不能是 `KeepLast` | 宕机能响 |
| 若无效 | → 转「症状 4」（可能是延迟而非没触发） | — |

**关键认知**：**机器宕机 ≠ No Data**。服务彻底挂掉时 `up=0` 是有数据的，走 Alerting 分支；只有指标**整个消失**（如采集端挂了）才走 No Data。

> **典型事故**：配了 `noDataState=Alerting` 就以为覆盖了宕机——**其实压根没走到**。
> **原理**：→ [08-实战经验.md](08-实战经验.md#故障模式-5以为-for-是延迟多久通知)

## 🟡 症状 6：一次故障收到 N 条重复告警

**一眼识别**：一个故障，收件箱里躺着好几条内容相似的告警。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 先加一条临时 Silence，避免继续打扰 | 立刻安静 |
| 定位 1 | 查 `condition` 里的 **Reduce 节点** | 按 `route` reduce → 每个 route 一条 |
| 定位 2 | 确认这是不是你想要的 | 想按维度区分 → 保留；想合并 → 改成单值 |
| 定位 3 | 查通知策略子策略的 `continue` | 不是 `false` → 一条告警发两处 |
| 修复 | ① 调 Reduce 维度 ② 子策略全设 `continue: false` | 条数恢复预期 |
| 若无效 | → 转「症状 7」 | — |

**注意**：`classic_conditions` 里**没有 instance 标签**——它已被 reduce 掉了。别在那里找。

> **另一个坑**：Silence **删不掉，只能等它过期**。删除后列表里还在，只是 `state` 变成 `expired`。
> **原理**：→ [08-实战经验.md](08-实战经验.md#故障模式-6reduce-写法悄悄决定了告警条数)

## 🟡 症状 7：改了告警配置，迟迟看不到效果

**一眼识别**：改完模板 / 规则，等了 2 分钟还没动静，以为配置错了。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | **先别改第二遍**——多半只是没到时间 | 避免叠加改动 |
| 定位 1 | 查 `repeat_interval` | 配 1m **实测 90s**；配 40s **实测 60s** |
| 定位 2 | 查 `group_interval` | `repeat_interval` 会向上跳到它的检查点 |
| 定位 3 | 确认告警是否**已在 firing**（已通知过不再重发） | 新告警才走 `group_wait` |
| 修复 | 等够时间，或用新标签造一条**新告警**验证 | — |
| 若无效 | → 转「症状 6」（可能发到了别的通道） | — |

> **口诀**：`repeat_interval` 是**下界不是闹钟**。
> **原理**：→ [08-实战经验.md](08-实战经验.md#故障模式-7repeat_interval-被当成闹钟)

## 🟡 症状 8：图上没有 exemplar 圆点，指标跳不到链路

**一眼识别**：指标图正常、P90 曲线漂亮，但**永远没有可点击的小圆点**。**不报错、无症状。**

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 暂时改用手工复制 trace_id 查链路 | 保住下钻能力 |
| 定位 1 | Prometheus 有没有存：`/api/v1/query_exemplars?query=你的bucket指标` | 返回 `data:[]` → **没存** |
| 定位 2 | 应用是否**显式传了** exemplar | `prometheus_client` **不会自动挂** |
| 定位 3 | Prometheus 是否开了 `--enable-feature=exemplar-storage` | 没开 → 存不进去 |
| 定位 4 | Grafana 数据源 `exemplarTraceIdDestinations` 指向 Jaeger 的 uid | 指错 → 点了跳不过去 |
| 修复 | 三处逐个补齐（见下） | 圆点出现 |
| 若无效 | → 确认 `ctx.is_valid` 判空（trace_id 可能全 0） | — |

```bash
# 第 1 步：Prometheus 侧有没有存到
curl -s 'http://localhost:9090/api/v1/query_exemplars?query=shop_request_duration_seconds_bucket' | head -c 300
# {"status":"success","data":[]}  ← 空 = 没生效
```

```python
# 应用侧必须显式传（判空别忘了）
if ctx.is_valid:
    LATENCY.labels(...).observe(
        duration,
        exemplar={"trace_id": format_trace_id(ctx.trace_id)}
    )
```

```yaml
# Grafana 数据源（注意：写错后端不校验，PUT 照样 200）
jsonData:
  exemplarTraceIdDestinations:
    - name: trace_id
      datasourceUid: shop-jaeger
```

> **实测基准**：修复后 24 组 / **3063 个** exemplar，全部带 trace_id。

## 🔴 症状 9：Loki 内存暴涨 / 查询越来越慢

**一眼识别**：Loki 内存持续上涨最终 OOM；查询变慢。**初期完全正常，还能按该字段过滤。**

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 临时缩短 retention，或限流写入 | 先别 OOM |
| 定位 1 | 查 stream 数量是否**随日志量线性增长** | 是 → **命中高基数标签** |
| 定位 2 | 找出被提升为标签的高基数字段 | `trace_id` / `user_id` / `order_id` / IP |
| 定位 3 | 检查 promtail / pipeline 的 `labels:` 段 | 看哪些字段被提升了 |
| 修复 | 只保留**低基数**字段做标签，其余留在内容里用 `|~` 检索 | stream 数稳定 |
| 若无效 | → 检查是否还有别的高基数标签 | — |

```yaml
# ❌ 把高基数字段提升为标签
labels:
  trace_id:        # 每请求一个不同值 → 每请求一个 stream
```

```yaml
# ✅ 只提升低基数字段，高基数留在内容里
labels:
  level:
  route:
# trace_id 不提升！查询用：{job="shop"} |~ "c57731..."
```

> **判断口诀**：*这个字段的取值范围有多大？* 有限且少（十几个以内）→ 可做标签；每条都不同 → **只能做内容**。
> **实测**：`{job="shop"} |~ "c57731..."` 命中 2 条，耗时 **18ms**。
> **原理**：→ [08-实战经验.md](08-实战经验.md#故障模式-9把高基数字段提升成-loki-标签)

## 🟡 症状 10：告警模板报 `can't convert <nil> to float`

**一眼识别**：日志里报这个错；**界面上规则存在、状态正常，看不出异常**。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 若告警确实需要，先临时改模板去掉百分比 | 恢复通知 |
| 定位 1 | 找表达式里的 **`A / B` 比率** | 命中 |
| 定位 2 | 确认系统**健康时分子是否无数据** | 无 500 错误 → 分子为空 |
| 定位 3 | 确认 `空 / 非空 = 空`（不是 0） | 空值一路传染到 reduce → nil |
| 修复 | 加 `or (B * 0)` 兜底 | 见下 |
| 若无效 | → 检查 reduce 节点是否能处理空值 | — |

```promql
# ❌ 健康时分子为空 → 整个表达式变空 → nil
sum(rate(shop_requests_total{status="500"}[2m]))
  / sum(rate(shop_requests_total[2m]))

# ✅ 加兜底：分子为空时返回 0
(sum(rate(shop_requests_total{status="500"}[2m]))
  / sum(rate(shop_requests_total[2m])))
or (sum by (route) (rate(shop_requests_total[2m])) * 0)
```

> **为什么它长期潜伏**：测告警时一定在**故障态**（分子有值），所以**只在系统健康时暴露**。
> **口诀**：写了 `A / B` 就问一句"**A 没数据时会怎样**"——答案是"变空"，不是"变 0"。
> **原理**：→ [08-实战经验.md](08-实战经验.md#故障模式-10比率告警在系统健康时崩)

## 🟡 症状 11：UI 改的配置，重启后不见了

**一眼识别**：在 UI 上改了 dashboard / 数据源，下次重启发现改动没了。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 重要改动先导出 JSON 备份 | 别再丢一次 |
| 定位 1 | 确认该资源是否由 **provisioning** 管理 | 是 → 这是预期行为 |
| 定位 2 | 检查 `allowUiUpdates` | `true` 更危险：改了返回 200，重启悄悄回滚 |
| 定位 3 | 若改过 `allowUiUpdates`，检查**数据库残留** | 先 false 后 true（同实例）→ **HTTP 400** |
| 修复 | ① 改 provisioning **文件**而非 UI ② uid 全部写死 | 重启后保持 |
| 若无效 | → 转「症状 12」 | — |

> **核心认知**：Provisioning = **启动时的一次 INSERT**，然后文件就下班了。你在 UI 上改的是数据库，下次启动文件又把自己写进去。
> **推荐**：`allowUiUpdates: false`——**明确的失败好过静默的成功**。
> **原理**：→ [08-实战经验.md](08-实战经验.md#故障模式-11provisioning-的-ui-改动被静默抹掉)

## 🟡 症状 12：API 返回 200，但资源没到该去的地方

**一眼识别**：调用 API 返回 200，但资源没出现在你期望的位置。**这是"静默降级"，比报错危险。**

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 别信状态码，**立刻读回验证** | 确认真实落点 |
| 定位 1 | 建 dashboard 时检查 `folderUid` 位置 | Grafana 13 要求放在 **payload 顶层** |
| 定位 2 | 放在 dashboard 对象内部 → 返回 200 但落到默认文件夹 | 命中 |
| 定位 3 | 检查是否用 `hasAcl` 判断权限 | **恒为 false**，是遗留字段，别用 |
| 定位 4 | 跨 Org 访问返回的是 **404 不是 403** | 安全设计：不泄露资源存在性 |
| 修复 | `folderUid` 移到 payload 顶层 | 落到正确文件夹 |
| 若无效 | → 起干净对照（新建用户/实例）排除状态污染 | — |

```json
// ❌ folderUid 写在对象内部 → 200 但落到别处
{ "dashboard": { "folderUid": "abc", ... } }

// ✅ 放在 payload 顶层
{ "folderUid": "abc", "dashboard": { ... } }
```

> **纪律**：状态被污染时，**先起干净对照**。课 11 就靠新建 `dave` 从零验证才拿到可信结论。
> **原理**：→ [08-实战经验.md](08-实战经验.md#故障模式-12静默降级返回-200-但落到别处)

## ⚪ 症状 13：dashboard 打开很慢

**一眼识别**：dashboard 加载慢。**别一上来就数面板**——三个常见直觉都被实测推翻了。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 若是生产关键盘，先临时拆分或降采样 | 先可用 |
| 定位 1 | **先看是不是在渲染**（服务端渲染图片） | 是 → 加 renderer 实例 |
| 定位 2 | 看响应体大小和**序列基数** | 字节数 / 序列数才是关键 |
| 定位 3 | 数面板数 | **80 倍面板只慢 4.5 倍**——影响没那么大 |
| 定位 4 | 看时间窗 | `maxDataPoints` 已封顶，通常不是它 |
| 修复 | 按上面顺序针对性优化 | — |
| 若无效 | → 确认 `maxDataPoints` 是否设得过大；仍无效则抓 `/api/ds/query` 响应体定位，或 → 转 `debug` skill | — |

> **实测反直觉**：①"面板多就慢"——**80 倍面板只慢 4.5 倍**，不是线性的 ②"时间窗长→慢"——`maxDataPoints` 会封顶 ③"加机器能解决渲染慢"——渲染是 CPU 密集，要看渲染是不是瓶颈
> **原理**：→ [08-实战经验.md](08-实战经验.md#故障模式-13性能排查一上来就数面板)

## 🔴 症状 14：升级失败，换回旧镜像后 404

**一眼识别**：升级到新版本出问题，把镜像换回旧版本 → 面板 404 或数据不可见。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | **立刻停手**，不要再启动新版本写库 | 防止进一步污染 |
| 定位 1 | 确认数据库是否已被新版本**迁移改写** | 13.x 用 k8s 风格 `resource` 表 |
| 定位 2 | 降级后旧版本读不懂新表结构 | → 404 / 数据不可见 |
| 修复 | **恢复备份**（不是换镜像） | 数据回来 |
| 若无效 | → 检查备份是否包含完整数据库；仍无效则 → 转 `debug` skill 现场取证 | — |

> **核心认知**：**回滚 = 恢复备份**，不是把镜像换回旧版本。降级后库已经被改，旧版本读不了。
> **实测边界**：只证明了**反向（13→12）会导致数据不可见**；正向升级的自动迁移未实测，标注 ⚠️。
> **原理**：→ [08-实战经验.md](08-实战经验.md#故障模式-14把降级当成回滚)

## 🔴 症状 15：备份恢复后程序静默 401

**一眼识别**：数据库恢复成功，面板都在，但**依赖服务账号 token 的程序全部 401**。**不报错在明面上。**

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 临时用 admin 凭据顶替 | 先恢复功能 |
| 定位 1 | 确认 token 的存储方式 | **落库为哈希**，明文只在创建时出现一次 |
| 定位 2 | 确认备份是否包含 token 明文 | 哈希在、明文没了 → 命中 |
| 修复 | **重新创建服务账号 token**，更新到所有依赖方 | 401 消失 |
| 预防 | 备份清单里单列"服务账号 token 需重建" | — |
| 若无效 | → 确认是否拿错了服务账号 id（别用 `id=1`）；仍无效则 → 转 `debug` skill | — |

> **这是备份检查里最容易漏的一项**：备份恢复后 token 的哈希在、明文没了，所有依赖它的程序会**静默 401**。
> **原理**：→ [08-实战经验.md](08-实战经验.md#故障模式-15备份恢复后程序静默-401) · 另见[上线 Checklist](08-实战经验.md#上线-checklist)

## 通用排障纪律（每条症状都适用）

1. **先看实测数字，不看文档说法**——这门课里文档与实测打架过太多次
2. **别信状态码**——验证结果。返回 200 不代表落对了地方
3. **状态被污染时，先起干净对照**——新建用户 / 新实例从零验证
4. **脚本也不一定可信**——对"改动是否真的发生"做断言
5. **先验证再修**——确认问题真实存在再动手，别凭记忆或直觉改
