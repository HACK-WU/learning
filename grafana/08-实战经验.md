## 先记住这三句话

它们解释了本文件里绝大多数故障模式的成因：

| # | 口诀 | 它解释了什么 |
|---|------|------------|
| **①** | **先问「这一步在哪执行」** | 前端 / 后端 / 启动期——决定了改了会不会生效、会不会被抹掉 |
| **②** | **先问「状态存在哪」** | 数据库 / 文件 / 浏览器——决定了跨环境能不能迁 |
| **③** | **先问「它真的报错了吗」** | **不报错 ≠ 对**。静默降级比报错危险得多 |

### Grafana 的三种"不校验"形态（贯穿全课的主线）

| 形态 | 出现在 | 表现 | 危险度 |
|---|---|---|---|
| **运行时不校验** | 课 4 / 5 / 6 / 9 | 瞎编的值照收，HTTP 200 | 中 |
| **启动期严格校验** | 课 10 | alerting provisioning 写错**直接崩溃** | 低（当场发现） |
| **静默降级** | 课 11 | 返回 200，但结果不对 | **高** |

> 课 4 是起点，课 10 是反转，课 11 是升级。所以"Grafana 不校验"要加限定句。

## 故障模式 1：以为 Grafana 存了监控数据

**症状**：Grafana 挂了，以为历史监控数据全丢了；或者以为"面板能看到多久"受限于 Grafana。

**根因**：把"配置"和"数据"搞混。Grafana 存的是仪表盘配置，**不是时序数据**。【实测】

**实测证据**：把容器里的 `grafana.db` 拷出来数表——**92 张表全是配置，时序特征表 0 张**，新装实例仅 1.5 MB（课 1）。

**正解**

- Grafana 挂了 → 只是**看不了**，数据还在 Prometheus / Loki 里
- 能看多久 → 取决于**数据源的保留期**，与 Grafana 无关
- 但**配置会丢**——不挂卷重建容器，数据源从 1 个变 0 个【实测，课 2 实验 C/D】

**预防**：`docker run` 时挂数据卷到 `/var/lib/grafana`。

→ 这是认知问题不是故障，排障手册无对应条目。原理见[课 1](stages/1-看得见/lessons/lesson-01-Grafana是谁：一个不存数据的看图工具.md)

## 故障模式 2：URL 写了 localhost，数据源连不上

**症状**：数据源测试报 `connection refused` / HTTP 502。

**根因**：`access=proxy` 时，**拨号的是 Grafana 容器自己**，不是你的浏览器。写 `localhost` 容器会连它自己的 localhost。【实测，课 2】

**正解**：用**容器名** `grafana-prom:9090`，且两者要在同一 docker network。

```
❌ http://localhost:9090     → 连到 Grafana 容器自己 → 502
✅ http://grafana-prom:9090  → 容器名解析 → 200
```

**一个反直觉的点**：即使用 `direct`（Browser）模式，Grafana **后端仍会自己发请求**——证据是报错里写的是后端 `dial tcp` 失败，且 `User-Agent: Go-http-client/1.1`【实测，课 2 / 课 4】。所以**别以为 direct 模式能让浏览器绕过后端**。

→ [09 · 症状 1](09-排障速查手册.md#症状-1数据源连不上connection-refused-502)

## 故障模式 3：多值变量用 `=`，静默返回 0 条

**症状**：选了多台机器，图却是空的。**一个字都不报。**【实测，课 3】

**根因**：变量是**前端文本替换**。多值时 `$host` 被拼成 `a|b`，而 `up{instance="a|b"}` 是合法但永不匹配的 PromQL——Prometheus 对"合法但无匹配"返回**一个空 frame**，不报错。

```
❌ up{instance="$host"}      → 拼成 instance="a|b" → 恒不匹配 → 静默 0 条
✅ up{instance=~"$host"}     → 拼成 instance=~"a|b" → 正则匹配 → 正常
```

**实测对照**：`=~` → 3 帧 3 点；`=` → 1 帧 0 点，**都不报错**【课 3】。

**为什么它特别阴险**：图空白的原因至少有 4 种（指标名错 / 时间窗没数据 / 变量没替换 / 标签不匹配），**UI 表现完全一样**。必须自己去内层看 `executedQueryString`。

→ [09 · 症状 2](09-排障速查手册.md#症状-2图空白但完全不报错)

## 故障模式 4：误以为 `HTTP 200` 等于成功

**症状**：面板空白 / 功能不生效，但监控显示"接口都正常"。

**根因**：Grafana 的查询响应是**两层状态码**。外层 HTTP 说"批量请求办得成不"，内层 status 说"每条查询在下游出了什么事"。【实测，课 4】

| 外层 | 内层 | 含义 | 面板表现 |
|---|---|---|---|
| 400 | 502 | **后端不可达**（不是你写错了） | 报错 |
| 400 | 400 | 你查询写错了 | 报错 |
| 200 | 200 | 成功——**但可能 0 个点** | **空白，不报错** |
| 404 | — | datasource uid 不存在 | 报错 |

**判据**：`HTTP 200 + 0 点 = 静默失败`。必须自己去看 `{} JSON` 里的 `executedQueryString`。

**同类陷阱的另一面**【课 9】：Loki 推送成功是 **HTTP 204 且没有响应体**——这里反过来，**没有 body 才是成功**。如果你期待它回个 `{"status":"success"}`，会以为失败了。

> 两种方向的坑都有的话，就得记住：**判断成败要看状态码和内层，不是看"有没有报错"或"有没有回话"**。

→ [09 · 症状 2](09-排障速查手册.md#症状-2图空白但完全不报错) · [症状 3](09-排障速查手册.md#症状-3面板报错-http-400-但看不懂)

## 故障模式 5：以为 `for` 是"延迟多久通知"

**症状**：配了 `for: 10s`，告警却等了 1 分钟才响；或者指标在阈值附近抖动，告警反复触发又恢复。

**根因**：`for` 是**"连续满足多久"**，不是延迟。实际触发延迟 = `⌈for / interval⌉ × interval`，而 `interval` 默认 1m——所以 `for=10s` 实际是 **1 分钟**。【实测，课 7】

**更危险的不对称**：**恢复不受 `for` 约束**——条件一不满足立刻恢复。所以是"缓慢触发、快速恢复"。

**副作用**：指标在阈值附近抖动时，会反复"快速恢复、缓慢触发"→ 通知稀少但状态频繁跳变。解法在课 8 的分组与抑制。

**另一个致命误解**：**机器宕机走的是 Alerting（up=0），不是 No Data**。如果你以为"配了 `noDataState` 就覆盖了宕机"，其实压根没走到那个分支——服务彻底挂了、指标消失、`noDataState=KeepLast` → 告警保持 Normal → **你以为服务正常**。【实测，课 7】

→ [09 · 症状 4](09-排障速查手册.md#症状-4告警响了但比预期晚很多) · [症状 5](09-排障速查手册.md#症状-5服务全挂了告警却没响)

## 故障模式 6：Reduce 写法悄悄决定了告警条数

**症状**：一次故障，本该收到 1 条告警，结果收到 N 条；或者反过来，想按维度区分却只收到 1 条。

**根因**：`condition` 里的 Reduce 节点决定了"按什么维度聚合成几条告警"。【实测，课 8】

- 按 `route` reduce → **每个 route 一条**
- reduce 成单值 → 只有一条

**另一个坑**：`classic_conditions` 里**没有 instance 标签**——因为它已经被 reduce 掉了。别在 conditions 里找"为什么没有 instance"。

→ [09 · 症状 6](09-排障速查手册.md#症状-6一次故障收到-n-条重复告警)

## 故障模式 7：`repeat_interval` 被当成闹钟

**症状**：改了告警模板，等了 2 分钟还没收到新告警，以为配置错了，又改了一遍。

**根因**：`repeat_interval` 是**下界不是闹钟**。Grafana 只在 `group_interval` 的检查点上判断"够不够时间重发"，所以实际间隔会**向上跳到检查点**。【实测，课 8】

**实测**：配 1m 实际 90s；配 40s 实际 60s。

**正确做法**：改完配置先算一遍 `repeat_interval`，别急着改第二遍——**你很可能只是还没到时间**。

→ [09 · 症状 7](09-排障速查手册.md#症状-7改了告警配置迟迟看不到效果)

## 故障模式 8：exemplar 三缺一，且全部静默

**症状**：指标图正常、P90 曲线漂亮，但**图上永远没有那个可点击的小圆点**，"指标 → 链路"这一跳静默失效。【实测，课 9 + 实战项目】

**这是全课程最阴险的一条**——不报错、数据正常、只有你想点圆点跳链路时才发现没有圆点。

**三个条件缺一不可**：

| # | 条件 | 谁负责 | 怎么验 |
|---|---|---|---|
| ① | 应用**显式传** exemplar | 应用代码 | `/api/v1/query_exemplars` 非空 |
| ② | Prometheus 开 `--enable-feature=exemplar-storage` | 运维 | 同上 |
| ③ | Grafana 数据源配 `exemplarTraceIdDestinations` | Grafana 配置 | 指向 Jaeger 的 uid |

**关键事实**：`prometheus_client` **不会自动挂 exemplar**【实测】。必须：

```python
if ctx.is_valid:                      # ← 判空，否则 trace_id 全 0
    LATENCY.labels(...).observe(
        duration,
        exemplar={"trace_id": format_trace_id(ctx.trace_id)}
    )
```

**实测**：没传时 `/api/v1/query_exemplars` 返回 `{"status":"success","data":[]}`（空的）；修复后 24 组 / 3063 个 exemplar，全部带 trace_id。

**雪上加霜**：`exemplarTraceIdDestinations` 的 `name` / `datasourceUid` **后端不校验**——改成 `bogus_trace_field`、`no-such-uid`，PUT 照样 200 且原样保存【实测，课 9】。配错了不报错，只是点了跳不过去。

→ [09 · 症状 8](09-排障速查手册.md#症状-8图上没有-exemplar-圆点指标跳不到链路)

## 故障模式 9：把高基数字段提升成 Loki 标签

**症状**：Loki 内存持续上涨，最终 OOM；查询变慢。**初期完全正常，还能按该字段过滤，看起来很方便。**【实战项目】

**根因**：Loki 的索引**按标签组合**建。每个不同的标签组合 = 一个独立 stream = 一份独立索引。`trace_id` / `user_id` 每条请求都不一样 → 每请求一个 stream → 索引随日志量**线性膨胀**。

**判断口诀**：*这个字段的取值范围有多大？*
- 有限且少（十几个以内）→ 可以做标签
- 每条都不同（`trace_id` / `user_id` / `order_id` / IP）→ **只能做内容**，用 `|~` 检索

**正解**：`trace_id` 留在内容里，用 `{job="shop"} |~ "c57731..."`，实测命中 2 条、耗时 18ms。

→ [09 · 症状 9](09-排障速查手册.md#症状-9loki-内存暴涨-查询越来越慢)

## 故障模式 10：比率告警在"系统健康"时崩

**症状**：`humanizePercentage: can't convert <nil> to float`。规则存在、状态正常、界面看不出异常，错误只在日志里。【实战项目实测，前 12 课全漏】

**根因**：

```promql
sum(rate(shop_requests_total{status="500"}[2m]))   # 分子：健康时无数据 → 空
  / sum(rate(shop_requests_total[2m]))              # 空 / 非空 = 空，不是 0
```

空值 → reduce 得 `nil` → 模板函数报 `can't convert <nil> to float`。

**它为什么长期潜伏**：**测告警时你一定是在故障态测的**（那时分子有值，一切正常）。所以这个错误**只在系统健康时出现**——恰恰是你最不关注告警的时候。

**修法**：

```promql
(sum(rate(shop_requests_total{status="500"}[2m]))
  / sum(rate(shop_requests_total[2m])))
or (sum by (route) (rate(shop_requests_total[2m])) * 0)
```

> **口诀**：写了 `A / B` 就问一句"**A 没数据时会怎样**"。答案是"整个表达式变空"，不是"变成 0"。

→ [09 · 症状 10](09-排障速查手册.md#症状-10告警模板报-cant-convert-nil-to-float)

## 故障模式 11：Provisioning 的 UI 改动被静默抹掉

**症状**：在 UI 上改了 dashboard，下次重启发现改动没了。

**根因**：Provisioning = **启动时的一次 INSERT**。文件进数据库，然后文件就下班了。你在 UI 上改的是数据库，**下次启动文件又把自己写进去**。【实测，课 10】

**两个必须知道的细节**：

1. **uid 必须自己写死**。不写让 Grafana 生成 → 重建一次环境，所有引用全断。
2. **`allowUiUpdates: true` 比 `false` 更危险**——它让你以为改成功了（返回 200），结果下次重启悄悄回滚。**明确的失败好过静默的成功**。

**一个实测出来的真坑**：先设 `false`、再改 `true`（同实例）→ **HTTP 400**，因为数据库里旧的 provisioned 标记没清。症状是"改了配置不生效"。

→ [09 · 症状 11](09-排障速查手册.md#症状-11ui-改的配置重启后不见了)

## 故障模式 12：静默降级——返回 200 但落到别处

**症状**：调用 API 返回 200，但资源没出现在你期望的位置。

**根因**：Grafana 13 要求 `folderUid` 放在 **payload 顶层**，放在 dashboard 对象内部会**返回 200 但落到默认文件夹**。【实测，课 11】

**应对只有一条**：**验证结果，而不是看状态码**。

**本课还沉淀了一条纪律**：状态被污染时，**先起干净对照**。课 11 中途发现 `carol` 的状态被前面的实验污染（曾短暂是 Editor），新建 `dave` 从零验证才拿到可信结论。

**同类遗留坑**：`hasAcl` 恒为 `false`，是遗留字段，**不能用来判断有没有配权限**。

→ [09 · 症状 12](09-排障速查手册.md#症状-12api-返回-200但资源没到该去的地方)

## 故障模式 13：性能排查一上来就数面板

**症状**：dashboard 慢，第一反应是"面板太多，拆一下"。

**根因**：三个常见的性能直觉**都被实测推翻**【课 12】：

| 直觉 | 实测 |
|---|---|
| "面板多就慢" | **80 倍面板只慢 4.5 倍**——不是线性的 |
| "时间窗长 → 数据多 → 慢" | `maxDataPoints` 会**封顶**，窗口长不会线性变慢 |
| "降级 = 回滚" | 降级后 **404**，且**库已经被改**——降级不是回滚 |

**正确顺序**：**渲染 → 响应体/基数 → 面板数 → 时间窗**。

**另外两个反直觉**：

- **换 Postgres 不是为了快**，是因为 SQLite 文件**无法共享**——这是架构事实不是性能问题
- **回滚 = 恢复备份**，不是把镜像换回旧版本

→ [09 · 症状 13](09-排障速查手册.md#症状-13dashboard-打开很慢)

## 故障模式 14：把"降级"当成"回滚"

**症状**：升级到新版本出问题，把镜像换回旧版本 → 面板 404 或数据不可见。

**根因**：升级会**改写数据库结构**。降级后旧版本读不懂新表结构。【实测，课 12】

**实测证据**：13.x 用 k8s 风格 `resource` / `resource_history` 表，与旧版结构不同。本实验证明了**反向（13→12）会导致数据不可见**——降级后库已经被改，旧版本读不了。

**⚠️ 未实测边界**：没有测 12.x → 13.x 的**正向升级**是否自动完成数据迁移（理论上 13.x 会读老表并迁移）。只证明了反向会导致不可见。

**正解**：**回滚 = 恢复备份**，不是把镜像换回旧版本。

**另外两个备份盲区**【课 12】：

- 只备份数据库**不够**——还要备份 provisioning 文件与 dashboard JSON
- `database: ok` **不代表没事**——它只说明数据库连得上，不说明数据正确

→ [09 · 症状 14](09-排障速查手册.md#症状-14升级失败换回旧镜像后-404)

## 故障模式 15：备份恢复后程序静默 401

**症状**：数据库恢复成功，面板都在，但**依赖服务账号 token 的程序全部 401**。**明面上不报错。**

**根因**：token **落库为哈希**，明文只在创建时返回一次。备份恢复后哈希在、明文没了。【实测，课 11】

**实测**：创建 token 时 `key` 只在那一次响应里出现，**再列一次就没了**。

**为什么它容易被漏**：这是备份检查里最容易漏的一项——所有依赖它的程序会**静默 401**，而你在 Grafana 界面上完全看不出来。

**正解**：

1. 备份清单里单列"**服务账号 token 需重建**"
2. 恢复后**重新创建** token，更新到所有依赖方
3. 临时止血可先用 admin 凭据顶替

**配套的两个坑**【课 11】：

- 建完服务账号**别拿 `id=1` 去建 token**——要用返回的实际 id
- **`glsa_` 前缀的 token 别当密码到处放**——它是长期凭据，泄露即失控

→ [09 · 症状 15](09-排障速查手册.md#症状-15备份恢复后程序静默-401)

## 反模式清单（能跑，但很糟）

> 来自[实战项目反例对照](projects/从告警到定位/反例对照.md)。它们的共性：**不是语法错误，是"规模还小时看不出问题"的设计错误**。

| # | 反模式 | 为什么"能跑" | 真正的危害 | 发现难度 |
|---|---|---|---|---|
| 1 | trace_id 做 Loki 标签 | 能查能过滤 | 索引爆炸 → OOM | 中（量大才暴露） |
| 2 | 平均值告警 | 数值完全正确 | 长尾故障漏报 | 高（要等出事） |
| 3 | 单通道告警 | 每条都收得到 | 告警疲劳，critical 被淹没 | 中（人会适应） |
| 4 | 忘传 exemplar | 指标完全正常 | 下钻静默失效 | **极高（无症状）** |
| 5 | 手写 dashboard JSON | 面板正常显示 | 不可维护、不可复用 | 低（改时才发现） |
| 6 | 子策略不设 `continue: false` | 告警能发出去 | 一条 critical 发两处 | 中（重复噪声） |

**反模式 2 的实测支撑**（平均值 vs P90）：

| 接口 | P50 | P90 | 平均 |
|---|---|---|---|
| /checkout（故障中） | — | **2.6 ~ 4.3s** | ~0.9s |
| /home（正常） | 0.091s | 0.099s | ~0.09s |

checkout 占 10% 流量 → 平均值 ≈ **0.17s**，告警不响；但用户体感是"每 10 个下单有 1 个要等 4 秒"。

> 平均值不是不能用——适合**容量规划**和**成本估算**。但**不适合做唯一的告警判据**。

## 一个反复出现的元教训

> **看实测数字，不看文档说法。**

这门课里文档与实测打架出现过太多次——课 10 的 `allowUiUpdates`、课 11 的 `hasAcl`、课 12 的"面板多就慢"。

同样重要的是**脚本也不一定可信**：课 5 的档案回写脚本用 `str.replace` 改文件，锚点写错时**什么都不做也不报错**；课 2 的判据脚本 `grep` 恒假。两者症状不同，根因相同——**脚本没有对"改动是否真的发生"做断言**。

所以：**先验证，再下结论**——对文档如此，对脚本如此，对自己的记忆更是如此（课 6 就凭记忆误判过课 4 的结论）。
