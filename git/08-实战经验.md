# Git 实战经验

> **想理解"为什么"，看这份。** 12 个高频故障模式，每个都按「现象 → 根因 → 验证 → 修复 → 记住」五段展开。
> 出事要立刻定位看 [09-排障速查手册.md](09-排障速查手册.md)，想直接复制命令看 [10-场景解法库.md](10-场景解法库.md)。

**环境基准**：WSL Ubuntu 24.04 · bash 5.2.21 · **Git 2.43.0**（本机未装 git-lfs / git-filter-repo）
**数据来源**：结课项目 [wf-lab](projects/workflow-lab/README.md) 的全部演练与 68 条断言，均为本机实测。

| 项 | 本机值 | 说明 |
|---|---|---|
| Git | 2.43.0 | 默认分支名 `master`，哈希 SHA-1 |

## 🔥 高频故障模式

### 故障 1：钩子装了，但什么都没拦住

**现象**：团队明明装了 pre-commit，带着 `console.log` 的提交照样进了仓库。

**根因**（按出现频率排序）：

1. **没有执行位** — Git 只打印一行 hint，**提交照常成功（exit 0）**
2. **`--cached` 写错位置** — `git grep` 退出码 128，被 `if` 当成"没找到"，**静默放行**
3. **钩子"自咬"** — 钩子文件里含被检查的关键词，且不排除钩子目录，于是干净提交也被拦
4. **`core.hooksPath` 指向的目录不存在或没同步** — 换机器后 `.githooks` 没带过来

**验证**（实测）：

```
$ chmod -x .githooks/pre-commit
$ git commit -m 'chore: x'
hint: The '.githooks/pre-commit' hook was ignored because it's not set as executable.
[master abc1234] chore: x          ← 提交成功了
```

**修复**：安装后**必须自检**——造一个必然违规的提交，看退出码是不是非 0。
`wf-lab hooks <repo> --check-only` 就是干这个的。

```bash
# 自检的正确姿势：先证明探针进了索引，再判断有没有被拦
git add -f -- probe.js
git diff --cached --quiet -- probe.js || echo "探针已入索引，可以判断了"
git commit -m 'test: probe' && echo "❌ 钩子没生效" || echo "✅ 钩子拦住了"
```

**记住**：**"装了"和"生效"是两件事。** 检查文件存在、甚至检查有执行位，都不算数——只有"能不能拦住"算数。

### 故障 2：`--force-with-lease` 没保护住队友的提交

**现象**：用了 lease 而不是 `--force`，队友的提交还是被覆盖了。

> 场景记法：本文统一用 **Zhang Wei**（你）与 **Li Si**（队友）两个人名。
> Zhang Wei 在本地改写了历史，Li Si 的提交在远端。

**根因**：**对 lease 语义的普遍误解。**

> `--force-with-lease` 只保证「**我上次 fetch 之后，远端没有再被别人动过**」。
> 它**不检查**「我的历史是否包含远端的提交」。

**实测对照**（Git 2.43.0）：

| 场景 | 结果 |
|---|---|
| A：`origin/master` 等于远端 tip，但本地历史与远端**分叉** | **lease 放行** — `+ 2bd6a2c...81afde1 master -> master (forced update)` |
| B：fetch 之后，别人**又推了一个**提交 | **lease 拒绝** — `! [rejected] master -> master (stale info)` |
| C：用 `HEAD:master` 而非 `master:master` 推送 | **lease 退化为无条件 force**（本地侧无对应跟踪分支可比对） |

**修复**：

```bash
git fetch origin                              # ① 推送前先 fetch（这是前提）
git push --force-with-lease origin master:master   # ② 用分支名，别用 HEAD
```

**记住**：lease 不是"安全版 force"，它是「**我只覆盖我看到的那个版本**」。
不 fetch 就推、或者用 `HEAD:` 推，保护等于没有。真正的强制必须靠服务端 `pre-receive`。

### 故障 3：删掉大文件，仓库一点没小

**现象**：删了 1MB 的文件并提交，`.git` 体积不降反升。

**实测数字**：

```
基线 208 KB
  → 加入 1MB 随机文件      1256 KB    (+1048)
  → 删除该文件并提交        1264 KB    (+8，反而涨了)
  → git gc --prune=now     1220 KB    (-44，但大文件仍在历史里)
```

**根因**：Git 存的是**每一次提交的完整快照**。删除是一次**新提交**，它记录"这个文件没了"，
但之前的提交里那个 blob 还在。gc 只能清掉**没有任何引用**的对象。

**修复**：只有重写历史才能真正释放（三步缺一不可）：

```
重写前 1252 KB
  → filter-branch 后   1268 KB   ← ⚠️ 不降反升：refs/original 留了完整备份
  → 三步清理后          188 KB   ← 真正释放
```

三步清理：

```bash
git for-each-ref --format='%(refname)' refs/original/ | xargs -n1 git update-ref -d
git reflog expire --expire=now --all
git gc --prune=now --aggressive
```

**记住**：**`filter-branch` 跑完体积上升是正常的**，不是失败了。不看这一步会以为瘦身没效果而中途放弃。

### 故障 4：瘦身后队友合并不了，强行合并又把大文件拉回来了

**现象**：历史重写并强推后，队友 `git pull` 报 `refusing to merge unrelated histories`。

**根因**：重写历史让**每一个 commit id 都变了**。旧克隆与新历史**没有共同祖先**，Git 拒绝合并。

**实测**：强行 `--allow-unrelated-histories` 合并后，`big.bin` **回到了仓库里（YES）**——
因为队友的旧历史里那个 blob 还在，合并把两棵没有交集的树拼在了一起。**瘦身白做。**

**修复**：**所有协作者必须重新克隆**，没有第二条路。标准流程：

1. 通知全员暂停推送，把工作先 push 到各自的分支
2. 完成重写后强推
3. 全员 `rm -rf` 旧克隆，重新 `git clone`
4. 把之前的工作 `cherry-pick` 过来（必要时 `rebase --onto`）

**记住**：**历史重写是团队级事件，不是个人操作。** 动手前先问"有几个人克隆了这个仓库"。

### 故障 5：`reset --hard` 之后工作全没了

**现象**：`git reset --hard HEAD~1` 之后，那次提交的改动找不到了。

**根因**：`--hard` 同时移动 HEAD、重置索引、**覆盖工作区**。但**提交对象并没有被删除**，
只是没有引用指向它了——在 gc 之前（默认 90 天）都还在。

**修复**：reflog 是所有操作的飞行记录仪。

```bash
git reflog                                  # 找到那次提交
git reset --hard <sha>                      # 回去
```

**实测**：

```
删除后 lost.txt 不存在 ✓
reflog 找到: d3a0249（原 d3a0249，完全一致）
救援成功，内容=v1
```

**记住**：**只要提交过，就几乎丢不了。** `reset --hard` 最危险的情况是**没提交过**的工作——
那不进 reflog，只能靠 IDE 本地历史或文件系统恢复。

### 故障 6：误删分支，以为分支上的工作没了

**现象**：`git branch -D feature/x` 之后慌了。

**根因**：**分支是指针，不是容器。** 删掉的是指针，提交还在。

**修复**：reflog 里找那次提交，重建指针：

```bash
git reflog | grep 'commit: <那次提交的信息>'
git branch feature/x <sha>
```

**记住**：`-D` 删除的是「名字」，不是「内容」。只要能找到 sha，一秒钟重建。

### 故障 7：bisect 什么都不输出

**现象**：跑 `git bisect` 只看到 `git status`，或者报 `Bad rev input: HEAD~9`。

**根因**（三个连环坑，本项目全踩过）：

1. **探针脚本放在仓库里** — 变成未跟踪文件，bisect 要求工作区干净，`bisect start` 直接被拒，
   只打印 status，看起来像"bisect 没输出"。
   **修**：探针放仓库外（`mktemp`），用绝对路径读被测文件。

2. **每次提交内容没变** — 循环写 `good`/`bad` 两个固定值时，连续相同内容会让
   `git commit` 报 `nothing to commit`，**实际提交数少于预期**，`HEAD~9` 随即越界报 `Bad rev input`。
   **修**：内容里带上步号，保证每次都是真实提交。

3. **`bisect run` 找到坏提交时返回非 0** — 它用退出码表达"找到了"，`set -e` 下脚本立刻中断。
   **修**：`if ! out=$(git bisect run ...); then :; fi`。
   另外 `bisect log` 必须在 `bisect reset` **之前**取，reset 会清空状态。

**效率**（实测）：100 个提交中定位第 63 个坏提交，**6 步**（理论下界 log₂100 ≈ 6.64）。

**记住**：**bisect 的成本是 log₂(N)，不是 N。** 1000 个提交也只要约 10 步。

### 故障 8：合并冲突解决完，冲突标记被提交了

**现象**：冲突"解决了"，但代码里留着 `<<<<<<<` 编译不过。

**根因**：`git add` 只是把文件标记为已解决，它**不检查**内容里有没有残留标记。

**修复**：解决后必须确认：

```bash
grep -nE '^(<<<<<<<|=======|>>>>>>>)' -r . || echo "无残留标记"
```

更稳的做法是配 `merge.conflictStyle = diff3`，把共同祖先也显示出来，
能看出「对方改了什么、我改了什么、原来是什麼」——三方信息比两方好判断得多。

**记住**：**`git add` 的语义是"我确认过了"，不是"冲突已解决"。** 确认是你做的，不是 Git 做的。

### 故障 9：rebase 之后队友的历史对不上

**现象**：rebase 完强推，队友再 pull 出一堆重复提交。

**根因**：rebase **改写提交**（生成全新的 commit id）。你重写了已经推送的历史，
队友的本地还指向旧 id，一合并就出现"同一个改动的两个副本"。

**黄金法则**：**只 rebase 尚未推送给他人的提交。**

**实测对比**：

| 方式 | 最新提交父指针 | 历史形状 |
|---|---|---|
| `merge --no-ff` | 2 个 | 保留分叉，多一个合并提交 |
| `rebase` | 1 个 | 直线，无合并提交 |

**记住**：**判断标准不是"哪个更好"，是"这些提交有没有别人在用"。** 有，就只能 merge。

### 故障 10：`git log` 里找不到刚做的提交

**现象**：刚 rebase / reset 过，`git log` 看不到之前的提交了。

**根因**：`git log` 只沿 **HEAD 可达**的路径走。被 rebase 替换、被 reset 移开的提交不可达，就不显示。

**修复**：

```bash
git reflog                          # 所有操作记录（含已被移开的）
git log -g                          # reflog 的 log 视图
git fsck --lost-found               # 连 reflog 都过期后的最后手段
```

**记住**：**`git log` 看的是"当前历史"，`git reflog` 看的是"你做过什么"。** 找不到东西时先看后者。

### 故障 11：演示"大文件占空间"却看不出效果

**现象**：造了个 1MB 文件，仓库体积几乎没变，演示失败。

**根因**：**用了全零数据。** Git 会压缩，零字节的压缩比极高。

**实测**：

```
基线 208 KB
  → 加 1MB 零字节   236 KB   (增量  28 KB)
  → 加 1MB 随机数据 1284 KB  (增量 1048 KB)   ← 相差 37 倍
```

**修复**：造测试数据一律用随机源：

```bash
head -c 1048576 /dev/urandom > big.bin     # ✅
dd if=/dev/zero of=big.bin bs=1M count=1   # ❌ 会被压缩，演示失真
```

**记住**：**演示"体积"问题时，数据的可压缩性就是结论本身。** 用错数据源会得到完全相反的结论。

### 故障 12：钩子把不该拦的提交也拦了

**现象**：装了检查调试残留的钩子，干净提交也被拒。

**根因**：**钩子"自咬"** —— 钩子文件里写着 `console.log` 这个字符串，
而 `git grep` 扫的范围包含了钩子自己所在的目录。

**实测对照**：

| 写法 | 干净提交 | 含 `console.log` 的提交 |
|---|---|---|
| `git grep ... -- .` | ❌ 被拦（自咬） | ❌ 被拦 |
| `git grep ... -- . ':(exclude).git'` | ✅ 通过 | ❌ 被拦 ✅ |

**修复**：显式排除钩子目录（用 `core.hooksPath` 时尤其要注意，钩子在版本库里）：

```bash
git grep --cached -n -E -I -e 'console\.log' -- . ':(exclude).git'
```

**记住**：**用钩子检查"内容"时，先问一句"钩子自己会不会被检查到"。**
同理，检查提交信息的钩子要豁免 `Merge` / `Revert` 这类自动生成的信息，否则全是假阳性。

## 🧭 三条取证纪律

### 1. 判断"防护是否生效"前，先证明"有东西可拦"

自检探针没进索引时，`git commit` 会以 `nothing to commit` 失败（rc≠0）。
朴素判断会把**这个失败**误读成"钩子拦住了"。

**先确认探针真的在索引里，再判断提交结果**：

```bash
git add -f -- probe.js
git diff --cached --quiet -- probe.js && echo "❌ 探针没进去，结论无效" || echo "可以判断了"
```

这是本项目实测抓到的第一号 bug（DECISIONS D2）。

### 2. 用"退出码"反推结论时，先确认退出码的含义

`git bisect run` 找到坏提交返回非 0，`git push` 被 lease 拒绝也返回非 0，
`grep` 无匹配返回 1——**这些都是"成功"的信号**。

在 `set -e` 下必须用 `if cmd; then ... else ... fi` 捕获，
不能用 `cmd || true` 掩盖，更不能让它中断脚本。

### 3. 体积类结论必须用随机数据，且区分"重写前/重写后/清理后"

三个数字缺一不可：`filter-branch` 刚跑完体积**会上升**（`refs/original` 备份），
只有三步清理后才真正下降。只看前两个会得出"瘦身无效"的错误结论。

## 📊 速查：本机实测数字

| 场景 | 数字 |
|---|---|
| 空仓库 `.git` 基线 | 208 KB |
| 加 1MB 随机文件 | +1048 KB |
| 加 1MB 零字节 | +28 KB（压缩 37 倍） |
| 删除大文件后 | 体积**上升** 8 KB |
| gc --prune=now 后 | -44 KB（大文件仍在历史） |
| filter-branch 后 | **上升** 16 KB（refs/original） |
| 三步清理后 | 1252 → **188 KB** |
| bisect 定位（100 提交） | 6 步 |
| 钩子无执行位 | 提交 **exit 0**（只给 hint） |
| `grep` 位置参数后接 `--cached` | **exit 128** |
| `grep -e` 模式后接 `--cached` | exit 0（安全） |
