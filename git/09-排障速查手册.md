# Git 排障速查手册

> **出事时看这份。** 按症状倒查，30 秒内定位。
> 想理解原理看 [08-实战经验.md](08-实战经验.md)，想复制命令看 [10-场景解法库.md](10-场景解法库.md)。

**环境基准**：WSL Ubuntu 24.04 · bash 5.2.21 · **Git 2.43.0** · **git-lfs / git-filter-repo 未装**

---

## 🚨 前 60 秒：四板斧

不管什么症状，先做这四步——成本不到一分钟，能排除一大类问题。

```bash
git status                  # ① 三区到底什么状态
git reflog -20              # ② 你最近做了什么（这是"飞行记录仪"）
git log --oneline -10       # ③ 当前历史长什么样
git fsck --lost-found       # ④ 有悬空对象吗（reflog 都过期时的最后手段）
```

**⚠️ 第 ② 步是核心**：`git log` 看的是「当前历史」，`git reflog` 看的是「你做过什么」。
**找不到东西时，查的一定是后者。**

## 🔍 按症状倒查

### 症状：提交/改动"不见了"

| 检查 | 命令 |
|---|---|
| 是不是 reset 过 | `git reflog -20`（默认保留 90 天） |
| 是不是在别的分支 | `git branch -a` + `git log --all --oneline -20` |
| 是不是 stash 了 | `git stash list` |
| 是不是 detached HEAD | `git symbolic-ref HEAD` 或看 `git status` 首行 |
| 连 reflog 都过期了 | `git fsck --lost-found` |

**最常见成因**：`reset --hard` 或 `checkout` 到了别的分支。
**只要提交过，就几乎丢不了**——真正危险的是**从没提交过**的工作（不进 reflog）。

---

### 症状：误删了分支

```bash
git reflog | grep 'commit: <那次提交的信息>'    # 找 sha
git branch <原分支名> <sha>                     # 重建指针
```

**为什么能救**：分支是指针不是容器。删掉的是「名字」，提交还在。

---

### 症状：强推把队友的提交覆盖了

> 场景记法：本文统一用 **Zhang Wei**（你）与 **Li Si**（队友）两个人名。

**先别再推任何东西。**

```bash
git reflog                                  # 找被覆盖前的位置
git reset --hard <sha>
git push --force-with-lease origin <branch>  # 用 lease，不用 --force
```

**为什么是 lease 不是 force**：见下方「lease 语义」专项。

---

### 症状：`--force-with-lease` 没拦住

**不是 Git 的 bug，是对语义的误解。** lease 只保证「我上次 fetch 之后远端没再动过」，
**不检查**「我的历史是否包含远端提交」。

| 场景 | 结果 |
|---|---|
| `origin/master` == 远端 tip，但历史分叉 | **放行**（照样覆盖） |
| fetch 之后别人又推了 | **拒绝** `! [rejected] (stale info)` |
| 用 `HEAD:master` 推 | **退化为无条件 force** |

```bash
git fetch origin                                   # ① 先 fetch（前提）
git push --force-with-lease origin master:master   # ② 用分支名，别用 HEAD
```

### 症状：仓库太大 / 想瘦身

```bash
git rev-list --objects --all --reflog \         # 找历史里的大文件
  | git cat-file --batch-check='%(objecttype) %(objectname) %(objectsize) %(rest)' \
  | awk '$1=="blob" {print $3, $4}' | sort -rn | head -20
```

**关键认知**：**删文件不释放空间。** 实测数字：

```
基线 208 KB → 加 1MB 随机 1256 KB → 删除后 1264 KB（反而涨）→ gc 后 1220 KB（大文件仍在）
```

**真正的释放要重写历史 + 三步清理**（缺一不可）：

```
重写前 1252 KB → filter-branch 后 1268 KB（⚠️ 上升，正常）→ 三步清理后 188 KB
```

```bash
git filter-branch -f --prune-empty \
  --index-filter "git rm -r --cached --ignore-unmatch -- <path>" \
  --tag-name-filter cat -- --all
# ↓ 三步清理（少一步就前功尽弃）
git for-each-ref --format='%(refname)' refs/original/ | xargs -n1 git update-ref -d
git reflog expire --expire=now --all
git gc --prune=now --aggressive
```

**⚠️ 瘦身后**：所有协作者**必须重新克隆**。强行 `--allow-unrelated-histories` 合并
会把大文件原样拉回来（实测 YES），等于白做。

### 症状：钩子没生效

| 检查 | 命令 | 说明 |
|---|---|---|
| 有执行位吗 | `ls -l .git/hooks/pre-commit` | **没有执行位 → 提交照样成功（exit 0），只有一行 hint** |
| 装在哪 | `git config core.hooksPath` | 用 hooksPath 时要确认目录存在且已提交 |
| 真的能拦吗 | 造违规提交试一次 | **唯一算数的检验** |

```bash
# 自检：造一个必然违规的提交，看退出码
git add -f -- probe.js
git diff --cached --quiet -- probe.js && echo "❌ 探针没进索引，结论无效" || echo "可判断"
git commit -m 'test: probe' && echo "❌ 没拦住" || echo "✅ 拦住了"
```

**⚠️ 自检铁律**：**先证明探针进了索引，再判断有没有被拦。**
否则 `nothing to commit` 的失败（rc≠0）会被误读成"钩子拦住了"。

**`--cached` 位置**（实测 Git 2.43.0）：

```
git grep --cached -n -E 'x'          # ✓ rc=0
git grep -n -E 'x' --cached          # ✗ rc=128  fatal: must come before non-option arguments
git grep -n -E -e 'x' --cached       # ✓ rc=0   （-e 让模式成为选项，不是位置参数）
git grep -n -E -e 'x' --cached -- .  # ✓ rc=0   （有 -- 分隔）
```

**钩子"自咬"**：钩子文件里含被检查的关键词时，要排除钩子目录：
`git grep ... -- . ':(exclude).git'`

### 症状：合并冲突解决完代码坏了

```bash
grep -nE '^(<<<<<<<|=======|>>>>>>>)' -r .    # 查残留标记
git config merge.conflictStyle diff3          # 以后显示共同祖先，好判断得多
```

**记住**：`git add` 的语义是「我确认过了」，**不是**「冲突已解决」。它不检查内容。

---

### 症状：rebase 之后队友对不上

**黄金法则**：只 rebase **尚未推送**给他人的提交。

| 方式 | 父指针 | 形状 |
|---|---|---|
| `merge --no-ff` | 2 | 保留分叉 |
| `rebase` | 1 | 直线 |

已经推送了还想整理 → 只能用 `merge`，或者走强推流程（全员协调 + `force-with-lease`）。

---

### 症状：bisect 没输出 / 报 Bad rev input

三个连环坑（本项目全踩过）：

1. **探针在仓库里** → 未跟踪文件让 `bisect start` 被拒，只打印 status
   **修**：探针放仓库外，用绝对路径
2. **提交内容重复** → `nothing to commit`，实际提交数少于预期，`HEAD~N` 越界
   **修**：内容带步号
3. **`bisect run` 找到坏提交返回非 0** → `set -e` 下脚本中断
   **修**：`if ! out=$(git bisect run ...); then :; fi`；`bisect log` 要在 `bisect reset` **之前**取

**效率**：100 个提交定位坏提交只需 **6 步**（log₂100 ≈ 6.64）。成本是 log₂(N) 不是 N。

---

### 症状：造了"大文件"却看不出体积变化

**用了全零数据。** 实测：

```
加 1MB 零字节  →  +28 KB
加 1MB 随机数据 →  +1048 KB     ← 相差 37 倍
```

```bash
head -c 1048576 /dev/urandom > big.bin     # ✅
dd if=/dev/zero of=big.bin bs=1M count=1   # ❌ 会被压缩
```

### 症状：pull / push 被拒

| 提示 | 含义 | 怎么办 |
|---|---|---|
| `! [rejected] (fetch first)` | 远端有新提交 | 先 `git pull --rebase` 再推 |
| `! [rejected] (non-fast-forward)` | 你落后了 | 同上；确认没人强推过再考虑 lease |
| `! [rejected] (stale info)` | **lease 生效了** | 这是保护，先 fetch 再重新评估 |
| `refusing to merge unrelated histories` | 两边没有共同祖先 | 常见于历史被重写 → **重新克隆**，别硬合 |

---

### 症状：提交信息/内容不符合团队规范

```bash
git commit -m 'feat(api): 新增查询接口'      # ✅ type(可选 scope)!?: 描述
git commit -m '改了点东西'                    # ❌ 会被 commit-msg 拦
```

**豁免**：`Merge` / `Revert` 等自动生成的信息应当放行，否则全是假阳性。

## 📋 退出码速查

| 码 | 含义 | 注意 |
|---|---|---|
| 0 | 成功 | **但 0 ≠ 真的对**（钩子失效时提交也是 0） |
| 1 | 通用失败 / `grep` 无匹配 | 在 `if` 里它常被当成"没找到" |
| 128 | 用法错误（参数位置错等） | **钩子失效的头号元凶**：被 `if` 当"没找到"→ 静默放行 |

**⚠️ "非 0 = 成功"的三个命令**（`set -e` 下必须用 `if` 捕获）：

- `git bisect run` — 找到坏提交时返回非 0
- `git push` 被 lease 拒绝 — 返回非 0，且这是**期望结果**
- `grep` 无匹配 — 返回 1

## 🧰 取证命令速查

| 想看什么 | 命令 | 注意 |
|---|---|---|
| 三区状态 | `git status` | 第一步 |
| **做过什么** | `git reflog` | 与 `git log` 不同，找不到东西查这个 |
| 当前历史 | `git log --oneline --graph --all` | 看分支形状 |
| 悬空对象 | `git fsck --lost-found` | reflog 过期后的最后手段 |
| 历史大文件 | 见「仓库太大」段 | 记得加 `--reflog` |
| 谁改了这行 | `git blame -L 10,20 file` | |
| 这行什么时候出现 | `git log -S 'keyword' --oneline` | 用 `-G` 可传正则 |
| 钩子装哪 | `git config core.hooksPath` | 未设置则是 `.git/hooks` |
| 文件在哪个提交 | `git log --all --oneline -- <path>` | `--all` 覆盖所有分支 |
| 仓库体积 | `du -sk .git` | 用随机数据才准 |
| 分支跟踪关系 | `git branch -vv` | 排查 lease 问题必看 |

## ⚡ 三条取证纪律（会让结论完全相反）

1. **先证明"有东西可拦"，再判断"有没有拦住"** —— 探针没进索引时 `commit` 以 rc≠0 失败，
   会被误读成"钩子生效"。这是本项目实测抓到的第一号 bug。

2. **非 0 退出码不等于失败** —— `bisect run` 找到结果、`push` 被 lease 拒绝、`grep` 无匹配，
   都是"成功"信号。`set -e` 下必须 `if` 捕获，不能 `|| true` 掩盖。

3. **体积数字要给全三个（重写前 / 重写后 / 清理后）** —— `filter-branch` 刚跑完体积**会上升**，
   只看前两个会得出"瘦身无效"的错误结论，进而中途放弃。
