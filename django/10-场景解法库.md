## 1 业务规则该放哪

### 决策表

| 判据 | view | serializer | **service** | 数据库约束 |
|------|------|-----------|-------------|-----------|
| 需要被复用（多处调用） | | | ✅ | ✅ |
| 只跟某个接口的输入输出有关 | | ✅ | | |
| 需要构造 request 才能测 | ❌ | 部分 | ✅ 不用 | ✅ 不用 |
| 绕过它会出事 | ❌ | ❌ | ✅ | ✅ 最稳 |
| 要在一个事务里跨多张表 | | | ✅ | |

### 为什么（实测依据）

🔬 实测同一条规则（下单时库存必须足够）放在三处的差异：

```
【可测试性】
  view       -> 需构造 request：factory + user + post + Request 包装，实测 4 行
  serializer -> 需 data + context（context 还可能缺 request）
  service    -> 直接调函数，签名 create_order(*, user, items, remark='', idempotency_key=None)

【单次开销（同样跑 5 次）】
  service 直接调用 -> SQL 10 条, 耗时   0.1ms  （0.02 ms/次）
  经 HTTP 走 view  -> SQL 10 条, 耗时  70.6ms  （14.1 ms/次）
  → 差 700 倍，这是 HTTP 栈的成本，跟你的业务代码无关

> ⚠️ **别误读这个 700 倍**：它衡量的是「要不要经过 HTTP 栈」，**不是**「逻辑放在 view 还是 service」的差别。
> 把逻辑从 view 挪到 service **不会**让你的接口快 700 倍——HTTP 栈照样要走。
> 放 service 的真正收益是**可测试性**（不用构造 request）和**防绕过**（见下），性能只是附带。

【复用次数（本项目实测）】
  views.py    调用 service = 2 处
  services.py 调用 service = 8 处
```

🔬 **最关键的一条实测**（证明"绕过 view 就绕过规则"）：

```
库存 3，下单 5 件：
  经 HTTP（走 serializer）  -> HTTP 409 {"code":"out_of_stock", ...}    库存仍为 3 ✅
  绕过 view 直接 ORM 写库   -> 订单创建成功，库存 3 -> 3，明细数量 5 > 库存 3 ⚠️
```

> 数据库层只有 `quantity >= 0` 这类**单行**约束，**跨行**规则（数量 ≤ 库存）没有约束兜底。

### 选错了会怎样

放在 view 里 → 任何绕过 HTTP 的路径（管理脚本、数据修复、后台任务、未来的第二个接口）**都能创建出违反规则的数据**，且当时没有任何报错。

## 2 signal 还是显式调用

### 决策表

| 判据 | 用 signal | 用显式调用 |
|------|-----------|-----------|
| 横切关注点（与业务无关，如审计、缓存失效） | ✅ | |
| 需要"全覆盖、不许有人忘记" | ✅ | |
| 扩展你不拥有的代码（第三方 app） | ✅ | |
| **有外部副作用（短信/邮件/API）** | | ✅ |
| **属于核心业务流程** | | ✅ |
| **批量路径也要生效** | | ✅ |
| 需要按调用点传不同参数 | | ✅ |

### 为什么（实测依据）

🔬 **决定性实测**：批量操作到底发不发信号

```
instance.save()      (create) -> post_save x1
instance.save()      (update) -> post_save x1
queryset.update()            -> post_save x0   ⚠️
bulk_create() x3             -> post_save x0   ⚠️
bulk_update() x3             -> post_save x0   ⚠️
queryset.delete() 删 3 条    -> post_delete x3（逐对象发，会发）
```

> 注意一个常见误解：**`queryset.delete()` 是发信号的**（逐对象），不发的是 `update` 家族。

🔬 本项目的选择（实测源码）：

```
services.py:  post_save 出现 0 次, @receiver 出现 0 次, _write_audit 调用 4 次
apps.py:      ready() 保持空实现，不注册任何 signal
```

🔬 效果验证：

```
create_order(...)      -> AuditLog 条数 = 1  ✅ 写到了
bulk_create(...)       -> AuditLog 条数 = 0  （若用 signal 这里会丢）
```

### 选错了会怎样

用 signal 做核心业务 → 一旦有人把这条路径改成 `bulk_create`（大数据量下的必然选择），**业务副作用静默消失**，不报错、不失败，只是"没发生"。

## 3 外部副作用放在事务里还是外面

### 决策表

| 场景 | 结论 |
|------|------|
| 数据库副作用（写库） | 事务内，可回滚 |
| **外部副作用（短信/邮件/调用外部 API）** | **必须 `transaction.on_commit`** |
| 缓存失效 | `transaction.on_commit`（回滚后不该失效） |

### 为什么（实测依据）

🔬 实测：事务回滚时外部副作用能撤回吗

```
【写法 A】在事务内直接调用（signal 的默认行为）
  事务回滚后：订单数 = 0（回滚成功）
  事务回滚后：已发出的短信 = ['订单已创建']  ⚠️ 外部副作用退不回来

【写法 B】transaction.on_commit
  事务回滚后：订单数 = 0
  事务回滚后：已发出的短信 = []  ✅ 没发
```

🔬 **但要注意 `on_commit` 在无事务时的行为**：

```
无事务时执行顺序 = ['A: 先记一笔', 'B: on_commit 里的', 'C: 后记一笔']
→ 没有事务时 on_commit **当场同步执行**，不是"延后到某个时刻"
```

### 选错了会怎样

外部副作用放事务内 → 数据回滚了、短信发出去了，用户收到"下单成功"但订单不存在。

## 4 缓存该怎么加

### 决策表

| 层级 | 写法 | 适合 | 不适合 |
|------|------|------|--------|
| per-view | `@cache_page` | 公开、无身份差异的响应 | **任何私有数据** |
| 低层 API | `cache.get_or_set` | 一切需要精确控制的场景 | —— |
| 模板片段 | `{% cache %}` | —— | 前后端分离项目用不上 |

### 为什么（实测依据）

🔬 **先量化收益，再决定加不加**：

> 🚨 **87.6x 是本地 SQLite 的数字，不要直接引用。** 它衡量的是"跳过一次本地查询"，
> 而真实价值取决于**被缓存的 IO 有多贵**——外部 API 可能是 100x+，本地小表可能只有 2x。
> **在你的环境里先测一次，再决定加不加。**

```
本项目 get_product_cached（实测环境：SQLite 本地库）：
  未命中 20 次平均  = 0.302 ms/次
  命中后 200 次平均 = 0.003 ms/次
  → 加速比 87.6x（仅代表本环境）
```

> ⚠️ 这个数字是**本地 SQLite** 的。真实价值取决于被缓存的 IO 有多贵——外部 API 可能是 100x+，本地小表可能只有 2x。**先量化再决定**。

🔬 **缓存键串号实测**（`cache_page` 的两个身份头对比）：

```
【A】标准 Authorization 头（Django/DRF 有自动兜底）
  用户 1 看到: {'user': 1, ...}
  用户 2 看到: {'user': 2, ...}
  串号 = False  ✅

【B】自定义身份头 X-User-Id（没有自动兜底）
  两个用户的响应字节完全相同
  串号 = True   ⚠️ A 用户会看到 B 用户的数据
```

🔬 **`cache.get` 分不清"无键"与"值为 None"**：

```
键不存在：  cache.get -> None,  cache.has_key -> False
值设为 None：cache.get -> None ⚠️ 和上面一模一样,  cache.has_key -> True ✅
```

### 选错了会怎样

用 `@cache_page` 缓存私有数据 + 自定义身份头 → **用户 A 看到用户 B 的数据**，且不报错。防穿透用 `cache.get(...) is None` 判断 → 空值缓存形同虚设，穿透照旧（要用 `has_key` 或哨兵值）。

## 5 要不要上 async

### 决策表

| 场景特征 | 结论 |
|----------|------|
| 纯 ORM、无外部 IO | 别用 async，**收益为负** |
| 有 N 次**可并行**的外部 IO | 值得，收益 ≈ IO 时间 × (1 - 1/N) |
| **有同步阻塞调用** | 先改成异步客户端，否则**更慢** |
| 长连接（WebSocket / SSE） | 必须用 ASGI |

### 为什么（实测依据）

🔬 实测（5 个任务、每个阻塞 50ms）：

```
串行同步 x5（基准）                     252.0 ms
asyncio.gather(async 里调同步阻塞) x5    254.5 ms  ⚠️ 没并行，还多了事件循环开销
asyncio.gather(原生 async) x5             61.1 ms  ✅ 真并行（≈50ms + 开销）

→ 有同步阻塞时 async 比原生 async 慢 4.2x
```

### 选错了会怎样

`async def` 里调同步阻塞（requests、同步 ORM 之外的阻塞库）→ 一处阻塞，**整个事件循环陪它等**，吞吐可能比同步还差。

## 6 任务框架怎么选

### 决策表

| 你需要 | Django 6 内置 `django.tasks` | Celery |
|--------|------------------------------|--------|
| 简单的入队/执行 | ✅ | ✅ |
| **Beat（定时/周期）** | ❌ | ✅ |
| **重试** | ❌ | ✅ |
| **编排（chain / group / chord）** | ❌ | ✅ |

### 为什么（实测依据）

🔬 实测 Django 6 内置任务框架暴露的符号：

```
['BaseConnectionHandler', 'ConnectionProxy', 'DEFAULT_TASK_BACKEND_ALIAS',
 'DEFAULT_TASK_QUEUE_NAME', 'InvalidTaskBackend', 'Task', 'TaskBackendHandler',
 'TaskContext', 'TaskResult', 'TaskResultStatus', 'base', 'checks',
 'default_task_backend', 'exceptions', 'import_string', 'signals', 'task',
 'task_backends']

Beat/定时 = False, 重试 = False, 编排(chain/group) = False
```

> 🚨 **选型前必看的两个静默坑**（课 16 实测，与框架选择无关，两个框架都要注意）：
> 1. **默认后端 `enqueue()` 当场同步执行** —— 耗时**计入请求**，你以为异步了其实没有。
> 2. **任务异常塞进 `result.errors`，`enqueue` 不抛** —— 任务**静默失败**，调用方毫无察觉。
>
> 这两条决定了：光"能入队"不够，还要确认**失败能不能被看见**。

## 7 约束写在应用层还是数据库

### 决策表

| 约束类型 | 放哪 | 理由 |
|---------|------|------|
| 单行/单列（数量 ≥ 1、价格 ≥ 0） | **数据库 `CheckConstraint`** | 谁能拦住绕过 ORM 的写入 |
| 唯一性 | **数据库 `UniqueConstraint`** | 并发下应用层判重有竞态 |
| **跨行/跨表**（数量 ≤ 库存） | service 层 | 数据库表达不了 |
| 复杂业务规则 | service 层 | 同上 |

### 为什么（实测依据）

🔬 实测：用裸 SQL 绕过 ORM，看数据库约束拦不拦得住

```
本项目各表的约束（实测 sqlite_master）：
  shop_category          CHECK 0 处, UNIQUE=True
  shop_order             CHECK 0 处, UNIQUE=True
  shop_auditlog          CHECK 1 处
  shop_idempotencyrecord CHECK 0 处, UNIQUE=True
  shop_product           CHECK 2 处
  shop_orderitem         CHECK 2 处

裸 SQL 插入 quantity=0  -> 被拦 ✅ IntegrityError: ck_orderitem_qty_positive
裸 SQL 插入 quantity=-5 -> 被拦 ✅ IntegrityError: CHECK constraint failed: quantity
```

> 应用层校验（serializer / service）在这条路径上**完全不知情**——数据库约束是唯一还守着的。

## 8 索引该不该加

### 决策表

| 场景 | 结论 |
|------|------|
| 小表（万行以内） | 加索引收益**测不出来**，先别拿它论证 |
| 大表 + 高选择性字段 | 值得 |
| 大表 + 低选择性（如 status 只有 3 个值） | 单独建索引收益有限，**复合索引才有用** |
| 写多读少 | 每加一个索引都在拖慢写入 |

### 为什么（实测依据）

🔬 实测（2000 条订单，20 次取平均）：

```
shop_order 上的索引: ['shop_order_user_id_...', 'idx_order_status_created',
                     'idx_order_user_created', 'sqlite_autoindex_shop_order_1']
按 status 查（有索引）     : 0.59 ms/次
按 total_amount 查（无索引）: 1.69 ms/次
→ 差 1.11 ms
```

> ⚠️ **反过来说**：2000 行下只差 1ms，这个数字**不足以论证"该加索引"**。
> 索引的价值随数据量增长才显现，而且**选择性**才是关键（2000 行里 status 只有 3 种取值，命中率 1/3，索引帮助有限）。

🔬 **那该怎么判断？用 `EXPLAIN` 看有没有走索引，别只比耗时**：

```
EXPLAIN QUERY PLAN SELECT * FROM shop_order WHERE status = 'paid'
  -> SEARCH shop_order USING INDEX idx_order_status_created (status=?)   ✅ 走索引

EXPLAIN QUERY PLAN SELECT * FROM shop_order WHERE total_amount = 10.0
  -> SCAN shop_order                                                     ⚠️ 全表扫描
```

> 判据：输出里出现 `USING INDEX xxx` = 走索引；出现 `SCAN TABLE` = 全表扫描。
> ⚠️ 走索引也不代表更快——**选择性低时优化器会主动放弃索引**（实测 500 条与 5000 条都走了 `idx_order_status_created`，但提速有限，因为 status 只有 3 种取值）。

### 选错了会怎样

拿小表实验的下结论"索引没用" → 大表上线后慢查询；或反过来，给写多读少的表加一堆索引 → 写入变慢。

## 9 测试怎么提速

### 决策表

| 手段 | 省什么 | 什么时候有用 |
|------|--------|-------------|
| `--keepdb` | 建库时间 | 测试多、建库慢（迁移多） |
| `--parallel N` | 执行时间 | **测试基数大**（数百项以上） |
| 换更快的密码哈希器 | 每次创建用户的开销 | 大量测试要建用户 |
| `--skip-checks` | 启动自检 | ⚠️ 收益极小，不值得 |

### 为什么（实测依据）

🔬 实测（本项目 27 项测试，各跑一次）：

```
默认                     2003 ms   Ran ['2','27'] -> ['OK','OK']
--parallel 4             2779 ms   Ran ['2','27'] -> ['OK','OK']
--keepdb --parallel 4    2761 ms   Ran ['2','27'] -> ['OK','OK']

→ 27 项测试下，--parallel 4 反而慢 39%（2003ms -> 2779ms）
```

🔬 `--skip-checks` 的收益（各跑 5 次，取**中位数**）：

```
hello            中位数 448 ms（5 次：428, 592, 576, 441, 448）
hello --skip     中位数 422 ms（5 次：435, 431, 411, 422, 407）
→ 省 26ms（约 6%）
```

> ⚠️ **测这个的时候容易踩的坑**：取 `min` 会放大冷启动噪声，我第一版取 min 得到 **-59ms（负收益）** 的错误结论。多次运行应取**中位数**。

### 选错了会怎样

给 27 项测试开 `--parallel 4` → 慢 39%，且并行下测试间共享状态的问题会变得更难查。

## 10 序列化器字段怎么列

### 决策表

| 写法 | 结论 |
|------|------|
| **显式 `fields = [...]`** | ✅ 唯一推荐 |
| `fields = "__all__"` | ❌ 模型新增字段会**自动开放** |
| `exclude = [...]` | ❌ 同上，且更易漏 |

### 为什么（实测依据）

🔬 实测对比：

```
__all__     暴露: ['category','created_at','description','id','image',
                  'is_active','name','price','stock','updated_at']
显式声明    暴露: ['id','is_active','name','price','stock']
__all__ 多出来: ['category','created_at','description','image','updated_at']
```

> 模型以后**新增任何字段**，`__all__` 都会自动开放，无需改动序列化器——包括你不想暴露的内部字段。

🔬 本项目：所有 serializer 都显式列字段，且 `check_serializer_fields`（W002）检查这条约定（当前返回 0 条问题 = 项目内无违规）。

## 11 API 版本策略怎么选

### 决策表

| 策略 | 客户端会漏传吗 | 缓存/CDN 友好 | 适合 |
|------|---------------|--------------|------|
| **URL 前缀 `/api/v1/`** | ❌ 不可能（路径里必须带） | ✅ | 本项目的选择 |
| Query 参数 `?version=v1` | ✅ 会 | ⚠️ | 内部接口 |
| Accept header | ✅ 会 | ❌ | 严格要求 REST 语义时 |
| 域名/子域名 | ❌ | ✅ | 大型多版本并行 |

### 为什么（实测依据）

🔬 实测四种策略在"不传版本"时的行为：

```
URLPathVersioning        带 v1 -> 'v1'；不带 -> None（落 default_version）
QueryParameterVersioning 带 ?version=v1 -> 'v1'；不带 -> None
AcceptHeaderVersioning   带 version=v1 -> None（实测未解析出，需配合 accepted_media_type）
```

🔬 **但要注意本项目的实现方式**：

```
settings: DEFAULT_VERSIONING_CLASS = None, DEFAULT_VERSION = None
urls.py : path("api/v1/me/", ...)、router.register(r"api/v1/orders", ...)
```

> ⚠️ 本项目是**路由前缀硬编码**，不是用 DRF 的 versioning 框架。
> 好处：`/api/v1/` 就是普通路径，简单、可直接用 Nginx 按路径路由。
> 代价：**没有 `ALLOWED_VERSIONS` 校验**，也没有 `request.version` 可用；将来要拆 v2 得手工复制一套路由。

### 选错了会怎样

用 header / query 传版本 → 客户端漏传时**静默落到 default_version**，等到 v2 上线才发现有一批调用方根本没传版本。

## 12 错误结构怎么统一

### 决策表

| 做法 | 结论 |
|------|------|
| 全局 exception handler（本项目） | ✅ 一处定义，全项目一致 |
| 每个 view 自己 `try/except` 拼响应 | ❌ view 变胖，且必然漏 |

### 为什么（实测依据）

🔬 实测本项目四类错误的响应结构：

```
业务错误（库存不足）  HTTP 409  顶层键 = ['code','details','message','trace_id']
校验错误（缺字段）   HTTP 400  顶层键 = ['code','details','message','trace_id']
越权（改他人订单）   HTTP 405  顶层键 = ['code','details','message','trace_id']
404 路由不存在      HTTP 404  顶层键 = 非 JSON（框架默认页）
```

> 前三类由 `common/exceptions.py` 统一产出，结构完全一致，且**都带 `trace_id`**（实测 `exceptions.py` 里出现 6 次）。
> 404 是 Django 框架层拦截，不走 DRF handler——这是正常且可接受的边界。

🔬 实测 trace_id 真的带上了：

```json
{"code":"invalid_status_transition","message":"商品不存在或已下架",
 "details":{"missing_ids":[99999]},"trace_id":"44f7cca06416434aa6925f80c6b63f6e"}
```

### 选错了会怎样

各 view 自己拼错误响应 → 前端要写多套解析；且没有 `trace_id` 时，用户报"下单失败"你**在日志里根本找不到对应记录**。

## 13 这个活该放进命令还是请求

### 决策表

| 判据 | 进请求链路 | 做成管理命令 | 常驻进程 |
|------|-----------|------------|---------|
| **单次耗时 < 100ms** | ✅ | | |
| **启动开销占比过高**（≈400ms） | ❌ 塞不进请求链路 | ✅ 可定时跑 | ✅ 避免反复冷启动 |
| 需要定时执行 | | ✅（+ cron） | |
| 一次性数据修复 | | ✅（带 `--dry-run`） | |
| 需要被重放/回滚 | | ✅ | |

### 为什么（实测依据）

🔬 实测各命令的启动开销（3 次取最快）：

```
manage.py check      661 ms
manage.py hello      397 ms   ← 一个什么都不做的命令
manage.py testhealth 1140 ms
```

> 课 21 已实测拆解：Django 启动 402.5ms + system checks 272.9ms 占绝大部分。

🔬 `--skip-checks` 只能省一点点（实测中位数 448ms → 422ms，**省 26ms / 6%**）：

> **判据**：启动开销（≈400ms）远大于请求可接受延迟（通常 100ms 级）时，这个活**不能**进请求链路，只能做定时任务或离线批处理。

### 选错了会怎样

把 400ms 启动开销的进程塞进请求链路 → 每个请求先付 400ms；为了省这点时间加 `--skip-checks` → 只省 6%，却放弃了启动自检。

## 14 十一条跨场景的通用判据

前 13 节的每一条背后，其实是同一批判据在起作用。抽出来单独记：

| # | 判据 | 出处 |
|---|------|------|
| 1 | **会被复用的逻辑，不要放在只有一条路径能触发它的地方** | §1（绕过 view 就绕过规则） |
| 2 | **能被批量路径绕过的机制，不能用来承载核心业务** | §2（`bulk_*` 不发信号） |
| 3 | **外部副作用必须能撤回，或根本不发出** | §3（回滚后短信已发） |
| 4 | **缓存的键比缓存的值更容易错，且错了不报错** | §4（自定义身份头串号） |
| 5 | **异步的收益来自"可并行"，不是来自 `async def` 关键字** | §5（有阻塞反而慢 4.2x） |
| 6 | **选型看"你需要的那个能力有没有"，不看"主流用什么"** | §6（内置任务无 Beat/重试/编排） |
| 7 | **能下沉到数据库的约束就下沉**——应用层拦不住绕过 ORM 的写入 | §7（裸 SQL 测试） |
| 8 | **用小表实验论证索引价值，结论不可靠** | §8（2000 行只差 1ms） |
| 9 | **优化手段的收益随规模变化，小项目上可能是负收益** | §9（27 项测试开 parallel 慢 39%） |
| 10 | **`__all__` 是"以后自动开放"的意思** | §10 |
| 11 | **能漏传的配置项，一定会有人漏传** | §11（版本策略） |
