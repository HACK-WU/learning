## 一、适用边界清单

> 读法：左边是某一课给出的结论，右边是它的**成立前提**与**失效场景**。
> 判断依据只有一个：**这个结论解决的那个问题，你现在有吗？**

### 1.1 阶段 1：前后端分离本身（课 1-2）

| 结论 | 成立前提 | 失效 / 不划算的场景 |
|------|---------|-------------------|
| 渲染权交给前端 | 前端独立部署、独立迭代 | **内部运营后台、数据看板**——Admin 半天搞定，分离是纯开销 |
| 契约先行（先定 API 再写代码） | 前后端并行开发，或接口有外部消费方 | 单人全栈项目，契约文档的成本高于收益 |
| CORS 显式白名单 | 有跨域前端 | 同域部署（此时不需要 `CORS_ALLOWED_ORIGINS`） |
| 自定义用户模型（课 2） | **任何新项目** | 无例外。首次 `migrate` 之后再改代价极高 |

**课 1 最容易被误读的一条**：分离之后"退场"的那些能力（模板、Messages、Forms 渲染），**不等于被官方废弃**。核查于 2026-09：Django 6.1.1 发布说明仍在修复模板系统的回归 bug（#37257），官方维护是活跃的。它们退场只是因为**在本课程的架构里用不上**，不是因为不好。

### 1.2 阶段 2：DRF 三件套（课 3-7）

| 结论 | 成立前提 | 失效 / 不划算的场景 |
|------|---------|-------------------|
| 序列化器显式写 `fields`，不用 `__all__` / `exclude` | 模型会持续演进 | 一次性导出脚本、只读快照（但也要确认模型不再变） |
| 业务逻辑放 service，view 只做三件事 | 逻辑会被**多处**复用（API / 管理命令 / 异步任务） | 只有一处调用的简单 CRUD——放 service 只是多一层跳转 |
| `select_related` 治 N+1 | **正向关系**（FK、OneToOne） | 反向 / M2M——要用 `prefetch_related`（课 15） |
| URL 路径做版本 | 需要多版本并存、版本切换要显式可见 | 只有一种版本时，前缀就是纯粹的路径噪音 |
| 可写嵌套 serializer | 父子对象要**同一事务**内创建 | 父子可分开提交时，拆成两个接口更简单 |

**课 5 的路由遮蔽**（🔬 实测）：手写路径如果排在 `include(router.urls)` **之后**，会被 router 的 `{pk}`（`[^/.]+`）吃掉，返回**静默 404**。这条在结课项目里已经固化成 `checks.py` 的 E001。

### 1.3 阶段 3：认证、权限与鉴权（课 8-10）

| 结论 | 成立前提 | 失效 / 不划算的场景 |
|------|---------|-------------------|
| JWT（无状态） | 多端、跨域、不想存 session | **需要「立即踢人下线」**——无状态做不到，得配黑名单（课 8） |
| Session（有状态） | **同域单体**、需要即时吊销 | 跨域 / 多端（Cookie 带不过去） |
| 对象级权限 `has_object_permission` | **详情 / 操作路由** | 🔬 **列表路由一次都不调用它**——列表要靠 `get_queryset()` 过滤（课 9 实测，mock 记录为空） |
| 限流 | 记住真实配额 = 配置值 × **进程数** | 多进程部署时 5/min 实际是 5×N/min |
| `ScopedRateThrottle` | 需要按接口分档 | 用 `UserRateThrottle` + `throttle_scope` → 🔬 **静默失效**（课 9 实测 5 次全 200） |
| 白名单而非黑名单（防批量分配） | 模型会新增字段 | 无例外——🔬 黑名单会在模型新增敏感字段那天静默开放 |

**课 8 最实用的一条判断**：验证登出是否真的生效，方法是**拿登出前签发的 refresh 再调一次 `/token/refresh/`**。返回 401 才是真登出；返回 200 说明你的登出是摆设（不装 `token_blacklist` 时就是这样）。

### 1.4 阶段 4：数据层纵深（课 11-14）

| 结论 | 成立前提 | 失效 / 不划算的场景 |
|------|---------|-------------------|
| `F()` 表达式做原子更新 | 有并发写 | 单线程脚本——但用了也没坏处，建议默认就用 |
| `select_for_update()` | **PostgreSQL / MySQL** | 🔬 **SQLite 上静默失效**（SQL 里连 `FOR UPDATE` 子句都没有）。且与生产不同库类型时验证无意义 |
| 约束下沉到数据库 | 写入路径不止一条（API / 命令 / 手工 SQL） | 只有 API 一条路径时，Serializer 校验已够——但约束成本极低，建议还是加 |
| 连接池（5.1+） | PostgreSQL + psycopg3 + `CONN_MAX_AGE=0` | 🔬 写 `pool={}` **静默失效**（空字典是 falsy）；容量要按 `Σ(max_size) × 进程数` 算 |
| **上多库 / 主从** | 🔴 **90% 的项目不需要** | 先做完索引（课 12）、N+1（课 15）、缓存（课 16）再评估 |
| 历史模型（`apps.get_model`） | 数据迁移 | 直接 import 只在"碰到后来被改掉的字段"时才炸——CI 看不出，全新环境重放才炸 |

**「该不该上多库」的判据**（课 13，⚠️ **经验参考值，非 Django 官方建议**，必须自己压测）：

| 指标 | 经验参考 | 说明 |
|------|---------|------|
| 数据库 CPU | 长期 > 70% | 且慢查询已优化完，才说明是容量问题 |
| 读写比 | > 10:1 | 低于这个，主从收益有限 |
| 连接数 | 接近 `max_connections` 的 70% | 先按 `Σ(max_size) × 进程数` 算清 |
| 单表数据量 | 千万级以上且增长快 | 才考虑拆库/分区，而非主从 |

**课 13 的渐进式路径**（值得单独记）：单库优化 → 主从读扩展 → 延迟治理 → 按 app 分库 → 跨库引用。**每一步都能独立验证、独立回滚，做不到就停在上一步**。

### 1.5 阶段 5：性能与异步（课 15-17）

| 结论 | 成立前提 | 失效 / 不划算的场景 |
|------|---------|-------------------|
| 缓存 | 读多写少、能接受短暂不一致 | 写多读少——用**主动失效**（`on_commit` + `cache.delete`）而非调小 TTL |
| `cache_page` | 响应与用户身份无关 | 用了自定义身份头（如 `X-Tenant-Id`）→ 🔬 **A 用户看到 B 用户的数据**。Django 只对 `Authorization` 自动兜底 |
| `select_related` | 要复用关联对象的场景 | 🔬 它**不去重实例**：10 行 = 10 个 Python 对象 |
| `.iterator()` | 大批量遍历 | 🔬 Django 6.1 的 `FETCH_PEERS` 在 `.iterator()` 下**完全失效** |
| 信号 | **只保留两类**：审计日志、第三方扩展 | 业务副作用——改 service 显式调用（课 17） |
| `transaction.on_commit` | 任何**外部**副作用（短信 / 邮件 / HTTP） | 数据库内副作用（同一个 atomic 块内会自动回滚） |
| 异步 / 任务队列 | 有真实的耗时任务 | 🔬 `enqueue()` 默认**同步执行**（课 16 实测） |

**课 16 最重要的一句话**：改 TTL 只是把"不一致的时间窗"压短，**问题本身没解决**。正确做法是一致性与 TTL 解耦——TTL 设长（保命中率），写路径主动失效（保一致性）。

### 1.6 阶段 6：工程化与生产（课 18-22）

| 结论 | 成立前提 | 失效 / 不划算的场景 |
|------|---------|-------------------|
| 自定义中间件 | 需要横切逻辑（trace_id、日志） | 能用 service 解决的别用中间件——**顺序错了是"同一个请求两个答案且无报错"** |
| `contextvars` 存请求态 | 异步 / 线程池复用 | 🔬 `threading.local` 在生产线程池下**串号**（用户 A 的日志打上用户 B 的 trace_id） |
| `keepdb` | 🔬 **SQLite 上负收益**（0.87x） | 见下——而且它**照样跑 migrate** |
| `--parallel` | 🔬 盈亏平衡点 **≈1132ms**（约 850ms 固定开销） | 短任务用它 **0.99x，反而更慢** |
| 禁用迁移提速 | 能接受**数据迁移不执行**（表在但数据为 0，且不报错） | 有 `RunPython` 数据迁移的项目——禁了就静默丢数据 |
| System checks | 团队约定要能被**自动**检查 | 约定只在口头 / 文档里——那就等于没有 |
| 常驻进程（waitress / gunicorn） | 🔬 CPU 占比 > **5%** | 低频任务用常驻是浪费资源 |
| `--skip-checks` | 🔬 **只省 10%**，生产不值得用 | 所谓的"省 41%"是参数错误快速失败的假象 |

**课 21 的核心判据**（值得背下来）：**扩展点 ≠ 默认行为**。判断方法是把相关代码全删掉——没报错、只是"少了一点效果"，那是扩展点；报错或跑不起来，才是默认行为。

> ⚠️ **课 20 的一条反直觉结论**：测试提速的体检三段实测是**建库 78% / 造数 18% / 执行 4%**。执行只占 4%，所以一上来就优化"用例怎么写"最多省 4%。**先量后改**，别凭直觉。

## 二、高频故障模式：不报错的错误

这是贯穿 22 课的一条暗线，也是本文最重要的一章。

> 💡 **这个矛盾本身就是一个教学点**：它属于**类型 D（静默错值）的元形态**——**统计自己抓到多少个坑，这件事本身也会数错，而且数错了没人告诉你**。
> 各课是边写边计数的，后一课沿用了前一课的旧计数，没人回头重数一遍。
> 教训：**计数也需要可验证**。如果你在项目里维护类似的"已知问题清单"，记得给它配一个"总数是否与明细行数一致"的检查。

### 2.1 它们的共同形状

从课 1 到课 22，这些问题的形状高度一致：

```
你少了一层保护，但没有任何东西告诉你。
```

具体表现为五种：

1. **不抛异常** —— 返回值看起来是对的（课 11 `Subquery` 漏 `.values()` 给一组**错值**）。
2. **返回成功状态码** —— 接口 200/201，但什么都没做（课 19 不碰 `request.data` 的上传接口、课 8 假登出）。
3. **静默回落默认值** —— 你配的东西没生效，框架安静地用了兜底（课 7 越权排序、课 6 不写版本回落默认版本）。
4. **静默丢弃** —— 传进来的东西被扔了，不报错（课 3 `read_only` 字段、课 4 错拼字段名）。
5. **环境一变行为就变** —— 开发正常，生产翻车（课 18 线程串号、课 19 `DEBUG=False` 后 `/media/` 变 404）。

**这类问题的统一解药**（各课给的是同一个）：

> **把静默失败改成显式失败。**

落到手段上就是三条：①用 `raise` 让进程起不来（课 22 缺 `SECRET_KEY`）；②用 `check` 让 CI 拦得住（课 21 团队约定）；③用**探针/枚举**让"有没有生效"可被验证（课 17 数 receiver 数）。

### 2.2 按形状归类（40 余处的六类）

**归类规则先讲清楚**：下面六类是按「**你最可能从哪个症状发现它**」划分的，不是按根因划分。所以同一个现象可能同时属于两类（比如 `select_for_update` 在 SQLite 失效，既是"A 静默失效"也是"C 环境依赖"）——这是正常的，不必纠结唯一归属。

#### 🔴 类型 A：静默失效 —— 你配了，但它没生效

**识别特征**：配置合法、启动正常，但行为等同于"没配"。

| 现象 | 出处 | 怎么发现 |
|------|------|---------|
| `UserRateThrottle` + `throttle_scope` | 课 9 | 连打 N 次看是否 429 |
| 连接池 `pool={}` | 课 12 | 打印 `connection.pool` 是否为 None |
| `select_for_update()` 在 SQLite | 课 11 | 打印 SQL 里有没有 `FOR UPDATE` |
| check 模块没被 `ready()` import | 课 21 | 故意埋一条必报错的 check 看是否出现 |
| 信号 `ready()` 没 import | 课 17 | 枚举 `sig.receivers` 数个数 |
| `.iterator()` 下 `FETCH_PEERS` | 课 15 | SQL 计数对比 |
| 中间件顺序错了（追踪在认证前） | 课 18 | 同一请求里中间件与视图打印的用户名比对 |

**解药**：凡是"配了某个开关"的，上线前**手动验证它真的生效**——别只看配置，要制造一次触发。
**→ 结课项目复现**：见[第四章](#四从结课项目复现的六个真-bug) #2（`select_for_update` 死锁）、#3（元检查读错 registry 容器）。

#### 🔴 类型 B：静默丢弃 —— 传进来了，被扔了

**识别特征**：返回 200/201，但你以为写入的东西没写进去。

| 现象 | 出处 | 怎么发现 |
|------|------|---------|
| `read_only` 字段被传 | 课 3、10 | 传一个 `id=999` 看 `validated_data` |
| 动态字段裁剪时错拼字段名 | 课 4 | 传 `no_such_field`，输出只剩 `['id']` |
| 越权排序字段 | 课 7 | 传白名单外的字段，看是否回落默认排序 |
| 不配 `ordering_fields` | 课 7 | 等于允许按任意字段排序（这是**反向**的坑） |

> 💡 **双刃剑要记住**：`read_only` 静默丢弃的**好处**是前端把整个对象原样 PUT 回来不会炸；**隐患**是你以为写进去了其实没有。调试"某个字段改了没生效"，第一件事是检查它是不是被标成了 `read_only`。

#### 🔴 类型 C：环境依赖 —— 开发正常，生产翻车

**识别特征**：本地/测试全绿，上线后才暴露。**这类最贵。**

| 现象 | 触发条件 | 出处 |
|------|---------|------|
| `static()` 静默返回空列表 | `DEBUG=False`，`/media/` 变 404 | 课 19、22 |
| `threading.local` 串号 | 生产线程池复用 | 课 18 |
| Admin 无限流被爆破 | 生产暴露 Admin | 课 19 |
| `bool(os.getenv("DEBUG"))` 恒为 True | `"False"` 是非空字符串 | 课 22 |
| `select_for_update` 无效 | 生产是 SQLite（或与验证环境不同库） | 课 11 |
| 批量导入裸 `except Exception` | 字段名拼错 → 200 行全部静默跳过 | 课 15（必查项 #28） |

**解药**：**凡是你没法在上线前验证的东西，就把它设计成上线瞬间就会暴露的形状**。课 22 的 `raise`（缺密钥进程起不来）就是这个思路的极致。
**→ 结课项目复现**：见[第四章](#四从结课项目复现的六个真-bug) #4（E003 被测试运行器的 `DEBUG=False` 误判）。

#### 🔴 类型 D：静默错值 —— 不崩，但结果是错的

**识别特征**：**返回值存在且类型正确，只是数值不对**。最难查的一类。

| 现象 | 出处 | 怎么发现 |
|------|------|---------|
| `Subquery` 漏 `.values()` → 给错值 | 课 11 | 与手工计算的期望值对比 |
| `Count` 少 `distinct=True` → 笛卡尔积 | 课 11 | 多值关系上核对计数 |
| 跨库 FK 静默指向另一份数据 | 课 13 | 写入成功但业务全错，数据库不报错 |
| 模型字段赋值拼错 → 值进 `__dict__` 不进库 | 课 15 | 读回来那一刻才发现 |
| 同名文件被静默改名（+7 位随机后缀） | 课 19 | 用 `obj.file.name` 而非自己拼路径 |
| 缓存键漏了自定义身份头 → A 看到 B 的数据 | 课 16 | 两个用户先后请求，比对响应 |

#### 🔴 类型 E：假成功 —— 状态码告诉你成功了，其实没有

**识别特征**：接口返回 200，但功能没实现。**这类在验收时最容易被漏掉。**

| 现象 | 出处 | 怎么验证真伪 |
|------|------|-------------|
| 不装 `token_blacklist` 时登出永远 200 | 课 8 | 拿旧 refresh 再调 `/token/refresh/` |
| 不碰 `request.data` 的上传接口返回 200 | 课 19 | 视图第一行就取 `request.FILES` |
| 只写 `db_for_read` 导致写入只读库 | 课 13 | 写入后读主库核对 |
| 任务异常被塞进 `result.errors` | 课 16 | 断言 result 里没有 error |
| patch 打错位置，测试依然绿 | 课 20、21 | 早绑定必须 patch **使用处** |

#### 🔴 类型 F：残留与泄漏 —— 东西留下了，没人告诉你

**识别特征**：表面功能正常，资源/数据缓慢劣化。

| 现象 | 后果 | 出处 |
|------|------|------|
| 删数据库记录，磁盘文件 100% 残留 | 磁盘缓慢增长，查不到原因 | 课 19 |
| 事务回滚但缓存留着新值 | 不一致持续到 TTL 过期 | 课 16 |
| 迁移 `atomic=False` 失败留下半成品 | 既不能重跑也不能回滚 | 课 14 |
| 信号 receiver 在循环里定义 → 重复注册 | 通知发 N 遍，看似"功能正常" | 课 17 |
| 批量路径 `bulk_create` 漏触发业务逻辑 | 统计值对不上 | 课 17 |
| shim 期信号双触发 | 同上 | 课 17 |

### 2.3 一张自检表：你的项目里有没有这类问题

按顺序问自己这六个问题，**任何一个答"不知道"就值得立刻去查**：

| # | 问题 | 答"不知道"时的动作 |
|---|------|------------------|
| 1 | 项目里所有**已注册**的 receiver，能一键枚举出来吗？ | 写个命令枚举（结课项目的 `testhealth` 就是模板） |
| 2 | 所有**已注册**的 check，能一键列出并确认它们真的跑了吗？ | `manage.py check` + 故意埋一条必报错的 check |
| 3 | 生产配置下 `DEBUG` 真的是 `False` 吗？ | 用白名单 `env_bool()`，别用 `bool(os.getenv(...))` |
| 4 | 每个写路径，**外部副作用**都在 `on_commit` 之后吗？ | 全局搜 `on_commit` 与发短信/HTTP 调用的位置 |
| 5 | 每个循环的循环体里，有没有数据库/IO 操作？ | 这是必查项 #28 的自查手法 |
| 6 | 上传的文件，删记录时有清理动作吗？ | 写个 check 扫孤儿文件 |

## 三、落地 Checklist

> 按**时间顺序**组织。每阶段的检查项都给出判据与验证手段——**清单要求 X，就必须给"怎么验证 X"**（必查项 #11 的历史教训）。
> 想直接抄作业的，去 [projects/orderflow/](./projects/orderflow/README.md)，下面每一条基本都有对应实现。

### 3.1 写代码时（每个 PR 都该过）

> **优先级**：🔴 = 不做会出事（安全 / 数据正确性）；🟡 = 强烈建议；⚪ = 有余力再做。
> 时间只够做三件的话，做 🔴 那三条。

| # | 优先级 | 检查项 | 判据 | 怎么验证 |
|---|--------|--------|------|---------|
| 1 | 🔴 | Serializer 显式 `fields`，不用 `__all__` / `exclude` | 黑名单会在模型新增字段那天静默开放 | grep `fields = "__all__"` / `exclude` |
| 2 | 🔴 | 敏感字段（role / is_staff / 余额）不可写 | 批量分配提权是**返回 200 的** | 传敏感字段看是否生效 |
| 3 | 🔴 | 归属字段由 `request.user` 注入，不信任入参 | 伪造 author 能成功 | 换个用户试 |
| 4 | 🔴 | 并发写用 `F()` 或条件 update，不用"先读后写" | 丢失更新 | 并发测试 |
| 5 | 🟡 | 循环体里没有数据库 / IO 操作 | 必查项 #28：N 变 10 万会怎样 | 翻每个 for 循环 |
| 6 | 🟡 | 异常处理显式列出可预期类型，不用裸 `except Exception` | 编程错误会变静默跳过 | grep 裸 except |
| 7 | ⚪ | 业务逻辑在 service，view 只做三件事 | view 变胖会泄漏不一致的错误结构 | view 里搜 `if 业务规则` |
| 8 | 🔴 | 外部副作用在 `transaction.on_commit` 之后 | 回滚退不回来 | 断言回滚后外部调用次数 |

### 3.2 提交前（CI 该拦住的）

| # | 检查项 | 命令 | 说明 |
|---|--------|------|------|
| 1 | `manage.py check` 零 Error / Warning | `check --fail-level WARNING` | 🔬 **只有 Warning 时退出码是 0**，必须显式指定 |
| 2 | 测试全绿 | `manage.py test` | 提速手段先量后改（课 20） |
| 3 | 文档与代码同步 | `exportdocs --check` | 结课项目已做成命令 + W001 check |
| 4 | OpenAPI schema 零警告 | `spectacular --validate --fail-on-warn` | 结课项目实测零警告 |
| 5 | 自定义 check 真的注册了 | 埋一条必报错的 check | 🔬 **不注册退出码 0、一条不报**；且**元检查兜不住这种情况**（见下方说明） |
| 6 | 手写路径排在 router 之前 | 问 URL 解析器 `resolve()` | 只比下标会误报（课 21） |
| 7 | 团队约定都有对应 check | 逐条对照约定清单 | 课 21 核心动作 |

> ⚠️ **第 1 条最容易踩**：`--fail-level WARNING` 是**全局**的，会连你自己写的非安全 Warning 一起拦。想分开就加 `--tag security`（课 22 实测）。
> 🔴 **第 5 条的元检查有边界，2026-09-04 实测修正**：本项目的元检查 `check_checks_registered`（E002）**兜不住「`checks.py` 没被 `ready()` import」这种情况**——因为它自己就住在 `checks.py` 里，模块没被导入时它跟着一起消失，实测现象是 `manage.py check` 输出 `System check identified no issues`、退出码 0，**完全静默**。
> 所以第 5 条要配一条**不依赖 check 框架自身**的独立断言：
> ```bash
> python manage.py check --list | findstr orderflow
> # 期望输出 orderflow_docs / orderflow_meta / orderflow_routes；为空即未注册
> ```
> 详见 [09-排障速查手册.md §8](./09-排障速查手册.md)。

### 3.3 上线前（部署流水线里）

| # | 检查项 | 判据 | 怎么验证 |
|---|--------|------|---------|
| 1 | 缺密钥时进程起不来 | 用到签名才抛异常，太晚了 | settings 里 `raise` |
| 2 | `DEBUG` 用白名单解析 | `bool(os.getenv("DEBUG"))` 恒 True | 打印 `DEBUG` 自证 |
| 3 | 安全开关全套 | `SECURE_SSL_REDIRECT` 缺 `SECURE_PROXY_SSL_HEADER` 会**无限重定向** | `check --deploy` 零告警 |
| 4 | `ALLOWED_HOSTS` 已配 | 白名单外返回 **400 不是 403** | 用错误 Host 头试 |
| 5 | 静态资源有人服务 | `static()` 在 `DEBUG=False` 时返回空列表 | **上线后手动请求一个 `/static/` 和一个 `/media/` 的**真实文件**；别只看健康检查**（它通常只打 `/api/health/`） |
| 6 | 迁移已演练回滚 | `atomic=False` 失败会留半成品 | 在预发环境跑一遍反向 |
| 7 | 有备份与恢复演练 | 没演练过的备份等于没有 | 恢复后比对字节数 |
| 8 | 健康检查端点存在 | 但别只看健康检查 | 健康检查通常只打 `/api/health/` |

**课 22 的部署流水线四阶段**（可直接抄）：pre-deploy（check + 测试 + 备份）→ deploy（迁移 + collectstatic + 重启）→ post-deploy（**验证** + 冒烟）→ rollback（四个回滚点）。

### 3.4 上线后（持续关注）

| # | 检查项 | 为什么 | 手段 |
|---|--------|--------|------|
| 1 | trace_id 贯穿日志 / 异常响应 / 下游调用**三处** | 出事才能查 | 结构化日志（课 18） |
| 2 | 慢查询有「只记最慢 N 条 + SQL 截断」两道防线 | 全记会打满磁盘 | `execute_wrapper` |
| 3 | 敏感字段脱敏覆盖嵌套与列表 | 只脱顶层会完整泄漏 | 递归脱敏（课 18 实验 27） |

## 四、从结课项目复现的六个真 bug

> 这一节记录 [OrderFlow 结课项目](./projects/orderflow/README.md)（2026-09-04 交付）**真实跑出来**的六个 bug。
> 它们不是"讲义里的例子"，而是**照着讲义做对之后、在真实工程里依然会撞上的坑**——所以单独列出来。

| # | 现象 | 根因 | 属于哪一类 |
|---|------|------|-----------|
| 1 | `seed_demo` 第二次运行直接崩 | "先删后建"撞上 `on_delete=PROTECT` | **示例经不起重复使用**（必查项 #28 该抓的） |
| 2 | 并发测试 0 单成功 | `select_for_update()` 在 SQLite 上死锁 | 🔴 **类型 A**：而且它本来就是多余的，F() 条件 update 自身已原子 |
| 3 | check 明明全注册，E002 却报"一条都没注册" | 元检查读错了 registry 容器（应读 `registry.registry.registered_checks`） | 🔴 **类型 A**：检查检查者的代码本身也会错 |
| 4 | 一跑测试就报 3 条生产配置错误 | E003 写 `if settings.DEBUG: return []`，而测试运行器**强制** `DEBUG=False` | 🔴 **类型 C**：环境依赖 |
| 5 | schema 生成时匿名访问触发 queryset 抛错 | `get_queryset()` 里对 `request.user` 做了过滤 | **drf-spectacular 生成期与运行期上下文不同** |
| 6 | 验收脚本把 check 的检查代码本身误判为违规 | 静态检查分不清"检查 X 的代码"与"违反 X 的代码" | **工具自身的假阳性** |

> 💡 **第 3 条最值得记**：写"检查 check 是否注册"的元检查时，我自己读错了容器名。这说明**元检查不是免死金牌**——它自己也会写错，而且错了之后报出来的错误信息会把你带偏。

**这六个的避免方法，按第三章条目对照自查**：

| Bug | 对应 Checklist 条目 |
|-----|-------------------|
| #1 示例经不起重复使用 | 3.1 #5（循环体无数据库/IO）+ 必查项 #28 的"生产规模"检验 |
| #2 `select_for_update` 死锁 | 3.1 #4（并发写用 `F()` 或条件 update）+ 类型 A 的"验证它真生效" |
| #3 元检查读错容器 | 3.2 #5（埋一条必报错的 check 验证注册生效） |
| #4 测试环境被误判为生产 | 3.2 #1 + 用显式哨兵（如 `IS_PRODUCTION_DEPLOY`）而非 `DEBUG` 判断 |
| #5 schema 生成期上下文不同 | 3.2 #4（`--validate --fail-on-warn`）+ `get_queryset()` 对匿名用户做兜底 |
| #6 静态检查假阳性 | 评审时区分"检查 X 的代码"与"违反 X 的代码" |
