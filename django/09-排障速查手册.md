## 1 通用三板斧（任何故障先做这三件事）

| # | 动作 | 命令 | 为什么先做这个 |
|---|------|------|--------------|
| 1 | 确认改的真的是你以为的那个配置 | `python -c "import django;print(django.get_version())"` | 版本不对，后面全白查 |
| 2 | 让 Django 自己告诉你配置有没有问题 | `python manage.py check --fail-level WARNING` | 🔬 实测：**低于指定级别的问题不会导致非零退出码**。本项目默认只有 INFO（I001）时退出码是 0，必须显式指定级别才会拦 |
| 3 | 确认你改的代码真的被执行了 | 在可疑行加 `print` / 埋一条必报错的 check | 🔬 实测：check 没被 import 时输出 `no issues`、退出码 0，**完全静默** |

> 💡 **第 3 条是本文最重要的一条**。「配了但没生效」类故障占了本文近一半条目，而它们的验证手法都是同一个：**制造一次触发，看它是否真的响应**。

## 2 限流

### 2.1 配了限流却一次都不拦

**症状**：settings 里配了速率，视图上也写了 `throttle_scope`，但连打 N 次全是 200。

**可能条件**（按可能性排序）：

| # | 条件 | 判断依据 |
|---|------|---------|
| 1 | 用了 `UserRateThrottle` / `AnonRateThrottle`，却在**视图上**写 `throttle_scope` | 🔬 **实测确认**：`UserRateThrottle.scope` 是**类属性 = `'user'`**，它**根本不看**视图的 `throttle_scope` |
| 2 | 用了 `ScopedRateThrottle`，但视图上**没写** `throttle_scope` | 源码：`if not self.scope: return True`（直接放行） |
| 3 | 速率配在了 `DEFAULT_THROTTLE_RATES` 之外的键 | DRF 只读 `THROTTLE_RATES` |

**验证动作**（🔬 实测结果，可直接对照）：

```python
# 实验条件：probe_3pm = 3/min，user = 600/min，各打 6 次
UserRateThrottle + 视图 throttle_scope  -> [200,200,200,200,200,200]   429 x0   ← 静默失效
ScopedRateThrottle + 视图 throttle_scope -> [200,200,200,429,429,429]   429 x3   ← 生效
自定义类上写 scope                        -> [200,200,200,429,429,429]   429 x3   ← 生效
```

> 💡 **先跑哪一组？** 第①组只能证明"没拦住"，**定位不到原因**；第②组才能定位。
> **时间紧就只跑第②组（降 `user` 速率）**——如果改 `user` 速率时它的行为跟着变，就立刻证明了它读的是 `user` 速率。

**决定性验证**：把 `user` 速率也降到 `2/min`，再看谁开始拦：

```python
# THROTTLE_RATES = {'probe_3pm': '3/min', 'user': '2/min'}
UserRateThrottle + throttle_scope  -> [200,200,429,429,429,429]   429 x4  ← 跟着 user 变
ScopedRateThrottle + throttle_scope -> [200,200,200,429,429,429]   429 x3  ← 仍按 3/min
```

> 若改 `user` 速率时它的行为跟着变，**就证明它读的是 `user` 速率**——你在视图上写的 `throttle_scope` 对它完全无效。

**解药**（三选一，本项目用的是第 3 种）：

```python
# ❌ 错：视图写 scope，却配 UserRateThrottle
class MyView(APIView):
    throttle_classes = [UserRateThrottle]
    throttle_scope = "orders_create"      # 被忽略

# ✅ 对：视图写 scope + ScopedRateThrottle
class MyView(APIView):
    throttle_classes = [ScopedRateThrottle]
    throttle_scope = "orders_create"

# ✅ 对：自定义类上写 scope（本项目 OrderCreateThrottle 的写法）
class OrderCreateThrottle(SimpleRateThrottle):
    scope = "orders_create"               # SimpleRateThrottle.__init__ 会读它
    def get_cache_key(self, request, view): ...
```

**完整限流链路自检**（🔬 本项目实测，配置 `orders_create = 20/min`）：

```
连打 24 次 POST /api/v1/orders/ ->
[201 x20, 429 x4]，第一次 429 出现在第 21 次
```

### 2.2 接口直接 500，报 `No default throttle rate`

**症状**：接口 500，日志里 `django.core.exceptions.ImproperlyConfigured: No default throttle rate set for 'xxx' scope`。

**条件**：视图写了 `throttle_scope = "xxx"`，但 `DEFAULT_THROTTLE_RATES` 里**没有 `xxx` 这个键**。

**验证动作**（🔬 实测）：

```python
# THROTTLE_RATES 缺 probe_3pm
ScopedRateThrottle -> [500, 500]     ← 立刻 500
UserRateThrottle   -> [200, 200]     ← 反而正常（它压根没读这个 scope，又一次静默）
```

**解药**：把 `throttle_scope` 用到的**每一个**名字都加进 `DEFAULT_THROTTLE_RATES`。

> ⚠️ **注意这个反直觉现象**：配置缺失时，错误写法（`UserRateThrottle`）反而"看起来正常"，正确写法（`ScopedRateThrottle`）直接 500。**500 比静默失效好查得多**——这也说明为什么不该用 `UserRateThrottle` 配 scope。

### 2.3 限流配额对不上（多进程）

**症状**：配了 `20/min`，实际能打 40、80 次。

**条件**：用了 `LocMemCache`（本项目开发环境默认），配额计数存在**各进程自己的内存**里。

**公式**：`实际放行 = 配置值 × worker 进程数`

**解药**：换 Redis / Memcached 做缓存后端。本项目已在 `settings_prod.py` 标注。

## 3 权限：越权看得到别人的数据

**症状**：A 用户能看到 B 用户的订单/数据。

**可能条件**：

| # | 条件 | 判据 |
|---|------|------|
| 1 | **列表**路由靠 `has_object_permission` 防护 | 🔬 实测：`has_object_permission` 在列表路由上**一次都不调用** |
| 2 | `get_queryset()` 没按用户过滤 | 列表防护的唯一正确位置 |
| 3 | 序列化器用了 `fields = "__all__"` | 模型新增敏感字段时会静默开放 |

**验证动作**（🔬 本项目实测）：

```
stranger 取详情 /api/v1/orders/54/  -> 404      ← 对象级权限生效
stranger 取列表 /api/v1/orders/     -> 200, count=0  ← 由 get_queryset() 过滤
列表中是否含他人订单(54)             -> False
```

**解药**：

```python
# 列表：靠 get_queryset 过滤（这是唯一生效的位置）
def get_queryset(self):
    qs = super().get_queryset()
    if not self.request.user.is_authenticated:
        return qs.none()
    return qs.filter(user=self.request.user)

# 详情/操作：靠 has_object_permission
def has_object_permission(self, request, view, obj):
    return obj.user == request.user or request.user.is_staff
```

> ⚠️ **schema 生成期的坑**：`drf-spectacular` 生成文档时会调用 `get_queryset()`，此时 `request.user` 是 `AnonymousUser`。直接 `filter(user=request.user)` 会抛 `Field 'id' expected a number`。必须判空（本项目 `views.py` 已处理）。

## 4 路由：手写路径 404 / 405

**症状**：手写了一个 `/api/v1/orders/statistics/`，访问却 404 或 405，且没有报错。

**条件**：手写路径写在了 `include(router.urls)` **之后**。router 注册的 `<pk>` 默认匹配 `[^/.]+`，会把它吃掉。

**验证动作**（🔬 本项目实测，用 `resolve()` 问 URL 解析器，不要靠猜）：

```python
from django.urls import resolve
resolve("/api/v1/orders/statistics/")
# -> apps.shop.views.OrderViewSet  kwargs={'pk': 'statistics'}   ← 被 router 吃掉了！
resolve("/api/v1/orders/999/")
# -> apps.shop.views.OrderViewSet  kwargs={'pk': '999'}
```

> 💡 **判断方法**：看 `kwargs` 里是不是出现了 `'pk': 'statistics'`。如果是，说明它被当成详情路由处理了。

**解药**：手写路径排在 `include(router.urls)` 之前。本项目把它固化成了 check（`check_route_order`，分组 `orderflow_routes`）。

## 5 静态资源：上线后 `/media/`、`/static/` 全 404

**症状**：本地好好的，上线后图片/上传文件全部 404，**且没有任何报错**。

**条件**：`DEBUG=False` 时 `django.conf.urls.static.static()` **返回空列表**，媒体路由根本不存在。

**验证动作**（🔬 本项目实测，注意必须**独立进程**，原因见下）：

```
DEBUG=True  -> static() 返回 1 条 URL 模式 [<URLPattern '^media/(?P<path>.*)$'>]
DEBUG=False -> static() 返回 0 条 URL 模式 []
```

独立进程实测：

```
DEBUG=False: resolve('/media/probe.txt') -> Resolver404
             顶层 URL 模式数 = 6，含 media 模式 = False
DEBUG=True : resolve('/media/probe.txt') -> <function serve>
             含 media 模式 = True
```

> ⚠️ **测的时候容易踩的坑**：本项目的 `/media/` 路由在 `urls.py` **导入时**就根据 `settings.DEBUG` 决定，运行期用 `override_settings(DEBUG=False)` **改不动它**（URLconf 已缓存）。要复现生产行为，**必须用独立进程 + 真实 `DEBUG=False`**。

**解药**：生产环境由 Nginx / 对象存储托管 `/media/` 与 `/static/`，不要依赖 Django。

**上线后第一件事**：手动请求一个 `/static/` 和一个 `/media/` 的**真实文件**。别只看健康检查——它通常只打 `/api/health/`。

## 6 缓存：改了数据库，读到的还是旧的

**症状**：数据库已经更新，接口仍返回旧值。

**可能条件**：

| # | 条件 | 判据 |
|---|------|------|
| 1 | 写路径没有主动失效缓存，只靠 TTL | 改 TTL 只是把不一致窗口压短，问题没解决 |
| 2 | **事务回滚了，但缓存已经写入** | 🔬 实测：回滚后缓存里仍是新值 |
| 3 | 多进程用了 `LocMemCache` | A 进程改了缓存，B 进程看不到 |
| 4 | `cache_page` + 自定义身份头 | 🔬 A 用户看到 B 用户的数据（Django 只对 `Authorization` 自动兜底） |

**验证动作**（🔬 本项目实测）：

```python
cache.set(key, "旧值")
with transaction.atomic():
    cache.set(key, "新值")
    raise RuntimeError("模拟失败")
# 回滚后：cache.get(key) == "新值"   ← 数据库回滚了，缓存没有

# 正确写法
with transaction.atomic():
    transaction.on_commit(lambda: cache.set(key, "提交后新值"))
# 退出后：cache.get(key) == "提交后新值"   ← 只在真正提交后才失效
```

**解药**：一致性与 TTL 解耦——TTL 设长（保命中率），**写路径用 `transaction.on_commit` + 主动失效**（保一致性）。

## 7 并发：超卖 / 丢失更新

**症状**：库存扣多了（超卖）或扣少了（丢失更新），压测时尤其明显。

**条件**：用了「先读 → 计算 → 写回」而非原子更新。

**验证动作**（🔬 本项目实测，4 线程各扣 5 次）：

> ⚠️ **具体丢几次取决于线程调度，每次运行结果可能不同**（再跑一次可能是 35、38……）。
> **判据是"最终库存不等于 20"**（即没有扣满 20 次），**不是"必须等于 30"**。

```
【错误写法】先读后写：
  起点库存 40，应扣 20 次
  实际结果 = 30        ← 只扣了 10 次！丢了 10 次更新
  线程异常数 = 0        ← 而且完全没报错

【正确写法】F() 条件更新：
  库存 10 扣 3 -> 影响 1 行, 余 7
  库存  1 扣 3 -> 影响 0 行（库存不足，没扣）, 余 1   ← 不会超卖
```

**解药**：

```python
# ❌ 错：先读后写（读到的 stock 可能已被别的线程改过）
p = Product.objects.get(pk=pid)
if p.stock >= qty:
    p.stock -= qty
    p.save()

# ✅ 对：F() + 条件更新，检查与扣减在同一条 SQL
updated = Product.objects.filter(pk=pid, stock__gte=qty).update(stock=F("stock") - qty)
if updated == 0:
    raise BusinessError("库存不足")
```

> ⚠️ **SQLite 上别用 `select_for_update()`**：本项目环境实测它在 SQLite 上**不生成 `FOR UPDATE` 子句**（静默失效）。用 `F()` 条件更新即可，它本身已原子。

## 8 自定义 check：一条都不报，CI 从来不拦

**症状**：团队约定写了 check，但 `manage.py check` 从不报错。

**条件**：`checks.py` 没有被 `AppConfig.ready()` import。

**验证动作**（🔬 本项目实测，把 `ready()` 里的 import 注释掉后重跑）：

```
注释前：
  退出码 = 0
  ?: (orderflow.I001) OrderFlow 注册了 6 条自定义 check
  System check identified 1 issue

注释后（checks.py 不再被导入）：
  退出码 = 0
  System check identified no issues (0 silenced).   ← 完全静默！
```

> 🔴 **这是本文最重要的一条发现**：本项目的元检查 `check_checks_registered`（E002）**兜不住这种情况**——因为它自己也住在 `checks.py` 里，模块没被 import，它自己也一起消失了。**元检查无法检查自身的注册**。

**解药**（两层）：

1. **在 `ready()` 里 import，并写注释说明为什么**（本项目已做）。
2. **在 CI 里加一条独立的断言**，不依赖 check 框架自己：

```bash
python manage.py check --list | findstr orderflow
# 期望输出（🔬 本项目实测）：orderflow_docs / orderflow_meta / orderflow_routes 三组
# 若输出为空 -> checks.py 没被 ready() import，去检查 apps/shop/apps.py
```

🔬 本项目实测 `check --list` 输出包含：`orderflow_docs`、`orderflow_meta`、`orderflow_routes` 三组。

## 9 生产配置：起不来，或配了不生效

### 9.1 缺 SECRET_KEY

**症状**：🔬 实测缺 `SECRET_KEY` 时 `manage.py check --settings=config.settings_prod` **退出码 = 1**（直接抛异常中断）；给了 `SECRET_KEY` 后退出码 = 0。

**解药**：`settings_prod.py` 里缺密钥直接 `raise`——让它在**启动那一刻**失败，而不是等到用签名时才炸。

### 9.2 `bool(os.getenv("DEBUG"))` 恒为 True

**症状**：明明设了 `DEBUG=False`，生产却在开 DEBUG（泄漏堆栈、静态资源行为异常）。

**验证动作**（🔬 实测）：

```
PROBE_DEBUG='False'  -> 坏写法=True   好写法=False
PROBE_DEBUG='0'      -> 坏写法=True   好写法=False
PROBE_DEBUG='true'   -> 坏写法=True   好写法=True
```

**解药**：

```python
def env_bool(name, default=False):
    val = os.getenv(name)
    if val is None:
        return default
    return val.strip().lower() in ("1", "true", "yes", "on")
```

### 9.3 `--skip-checks` 不值得用于生产

🔬 课 22 实测：`--skip-checks` **只省 10%** 时间。生产环境不要为了这点时间放弃启动自检。

## 10 N+1：列表接口越来越慢

**症状**：列表接口随数据量增长明显变慢，或 SQL 日志里同一条查询重复出现。

**验证动作**（🔬 本项目实测，8 个订单）：

```
不用 prefetch_related：8 个订单 -> 9 条 SQL     (1 + 8，典型 N+1)
用 prefetch_related  ：8 个订单 -> 2 条 SQL
```

**解药**：

| 关系类型 | 用什么 |
|---------|--------|
| 正向（FK / OneToOne） | `select_related` |
| 反向 / M2M | `prefetch_related` |

> ⚠️ `.iterator()` 会让 Django 6.1 的 `FETCH_PEERS` **完全失效**，大批量遍历时注意。

## 11 schema 文档过期

**症状**：API 改了，文档没更新，前端照旧文档对接出错。

**验证动作**（🔬 本项目实测）：

```
exportdocs --check（文档同步时）      -> 退出码 0，"✅ 文档与代码同步（无差异）"
exportdocs --check（人为改动文档后）  -> 退出码 1  ← 检出过期
```

**解药**：把 `exportdocs --check` 放进 CI（本项目 `ci_check.sh` 第四道关）。

## 12 排障时的三条反直觉经验

这三条是本次实测中**推翻了直觉**的部分，值得单独记住：

| # | 直觉 | 实测结论 |
|---|------|---------|
| 1 | 「我配了 throttle_scope，限流就该生效」 | 配 `UserRateThrottle` 时它读的是 `user` 速率，**你的配置被完全忽略且不报错** |
| 2 | 「配置缺失会让接口报错」 | 只有正确写法会 500；错误写法反而"正常"——**500 比静默好查** |
| 3 | 「元检查能兜住 check 没注册」 | 兜不住。**元检查自己也在那个没被 import 的模块里**，会一起消失 |

**统一规律**：**凡是"配了某个开关"，都要制造一次触发来验证它真的生效**——别只读配置。
