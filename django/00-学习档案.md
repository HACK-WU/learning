### ⚠️ 已知兼容性陷阱（重要，课 2 会实测）

DRF **3.17.x 及以下**在 Django 6.1 上会因 `cc_delim_re` 从 `django.utils.cache` 移出而 **import 直接失败**：

```
ImportError: cannot import name 'cc_delim_re' from 'django.utils.cache'
```

- 来源：[ICHEC 工程记录](https://git.ichec.ie/platform-engineering/modules/web/ichec-django-core/-/work_items/75)（2026-08-06 实测）+ DRF 3.18.0 changelog 中 `Replace cc_delim_re usage with split_header_value for Django 6.1+ compatibility`（#9978）**互相印证**。
- **结论**：Django 6.1 **必须**配 DRF ≥ 3.18.0。若 pip 解析出 DRF 3.17.x，需显式写 `djangorestframework>=3.18`。

### ✅ 该陷阱已于课 2 实跑坐实（2026-09-02）

完整证据链（全部为真实执行输出，非推断）：

| 步骤 | 实测结果 |
|------|---------|
| ① Django 6.1 中 `from django.utils.cache import cc_delim_re` | `ImportError: cannot import name 'cc_delim_re'` —— **确实被移走** |
| ② 隔离安装 DRF 3.17.1，执行 `from rest_framework.views import APIView` | `ImportError: cannot import name 'cc_delim_re' from 'django.utils.cache'`（报错定位 `rest_framework/views.py` 第 10 行） |
| ③ Django 6.1 中 `from django.utils.cache import split_header_value` | 存在且可调用 —— DRF 3.18 的替代 API 有效 |
| ④ DRF 3.18.0 导入 `APIView` / `ListAPIView` | 成功 |

> ⚠️ **一个反直觉的细节（课 2 实测发现）**：`import rest_framework` **不会**报错——它只加载 `__init__.py`，`views.py` 根本没被导入。真正的失败发生在**你第一次写 `from rest_framework.views import APIView` 并启动项目**的那一刻。所以这个坑不是"装完就炸"，而是"写完第一个视图才炸"，排查时容易误判成自己的代码问题。

### 课 12 连接池硬性约束（核查于 2026-09）

Django 5.1+ 通过 `DATABASES["default"]["OPTIONS"]["pool"]` 支持连接池，两个已知硬约束：

1. **需 psycopg3**（psycopg2 不支持 pool）。
2. **启用 pool 时 `CONN_MAX_AGE` 必须为 0**，否则抛 `ImproperlyConfigured: Pooling doesn't support persistent connections`。
3. **池是按进程计算的**：4 个 worker × `max_size=10` = **40 条连接**，不是 10 条。这是生产容量估算的高频错误来源。

> 以上三条在课 12 **必须实跑验证**，尤其报错信息要实录。

### ✅ 课 12 实跑结论（2026-09-02）

三条全部坐实，并**新增第四条**（原档案未记）：

| # | 约束 | 实测结果 |
|---|------|---------|
| 1 | 需 psycopg3 | 门槛精确值是 **3.1.12**（`base.py:43`），非笼统的「3」；报错 `ImproperlyConfigured: Database pooling requires psycopg >= 3`（`base.py:287`） |
| 2 | `CONN_MAX_AGE` 必须为 0 | 实测 `ImproperlyConfigured: Pooling doesn't support persistent connections.`（`base.py:200`） |
| 3 | 池按进程计算 | `_connection_pools` 是**类属性**，每进程一份；4 worker × max_size=10 = 40 条 |
| 4 | 🆕 **`pool={}` 静默失效** | 源码判定 `not pool_options`，空字典为 falsy → 直接 `return None`，**不报错也不启池**。必须写 `pool=True` 或带键值的字典 |

本机已装 psycopg 3.3.5 + psycopg-pool 3.3.1，`is_psycopg3=True`。
另注：`max_size` 默认 `None`，但 `pool=True` 时实测得到 `max_size=4`（回落到 `min_size`），**不要依赖此行为**。

### 🆕 多库连接池容量公式（串联课 12 + 课 13）

课 12 已确立「池按进程计算」：`单库连接数 = max_size × 进程数`。多库下**每个库别名各有一份独立的连接池**：

```
总连接数 = Σ(每个库的 max_size) × 进程数
```

例：4 worker × 3 库（default/replica/logs）× `max_size=10` = **120 条**，而 PostgreSQL 默认 `max_connections=100` —— **直接超限**。

要点：从库的池**不是免费的**；`max_size` 每库单独配；预留量按**总连接数**算而非单库；超过 `max_connections` 的 70% 应上 PgBouncer（课 12 判据）。
