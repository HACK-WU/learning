## L1-①　第二幕缺"我怎么知道自己项目的顺序是对的"（已修）

**问题**：2.4 节给了速查表，2.5 节给了打印链条的脚本。但缺一个更直接的东西——
**我手上这个已有项目，怎么快速判断它的中间件顺序有没有问题？** 速查表是"新知识"，
而学员面对的是"已存在的、可能是前人写的配置"。

**已修**：在 2.5 节后面补了「三步自检法」，核心是一个可复制粘贴的检查脚本：

```python
# 一次性体检：哪些中间件其实该换个位置
must_be_before_auth = {"日志", "trace", "audit", "request_log", "tracking"}
```

并给出三条判据：
1. 名字里带 log/trace/audit/tracking 的中间件，**出现在 AuthenticationMiddleware 之前就是可疑的**
2. 有 `process_exception` 的中间件，不在前三位就**兜不住内层异常**
3. 跑一次登录请求，比对"中间件看到的 user"与"视图看到的 user"是否一致（实验 31 的同款手法）

## L1-②　第三幕缺"怎么确认 trace_id 真的串起来了"（已修）

**问题**：3.4 节教了怎么把 trace_id 注入日志，但没说**怎么验证它真的生效了**。
这是必查项 #11 的要求（关键结论须有可验证的自检手段）。学员配完 Filter 后，
最常见的困惑是"我怎么知道它真的写进去了？"

**已修**：在 3.4 节后补了「三分钟自检」：

```bash
# 1. 发一个带自定义 trace_id 的请求
curl.exe -i -H "X-Trace-Id: selftest-001" http://localhost:8000/api/orders/

# 2. 在日志里 grep 这个值
grep "selftest-001" logs/app.log

# 3. 应该看到：请求开始、SQL、请求完成，全都带同一个 id
#    如果只有"请求完成"有，说明 Filter 挂晚了或 logger 配错了
```

并补了三个"查不到"的排查方向（Filter 没挂到对应 logger / propagate 未关 /
日志格式器没引用 `%(trace_id)s`）。

## L1-③　第四幕缺"我该怎么定慢查询阈值"（已修）

**问题**：4.3 节给了 `execute_wrapper` 的实现，4.9 节的完整中间件里写了
`self.slow_threshold_ms = 5.0`。但**这个 5.0 是怎么来的**完全没解释。
学员照抄一个数字容易，但换了项目就不知道该调成多少——这属于"给了答案没给方法"。

**已修**：在 4.3 节后补了一段「阈值怎么定」：

1. **先量再定**：把阈值临时设成 0，跑一天生产流量，记下 SQL 耗时的分布
2. **取 P99 附近**：目标是"每天只抓几十条真正需要看的"，而不是几千条噪音
3. **不同接口可以有不同阈值**：报表类接口本来就慢，批量导入同理
4. **给出参考起点**：普通 API **50–100ms**；简单查询型 **10–20ms**；
   本课实验工程用 **5ms** 是为了在 SQLite 内存库上能演示到，生产不适用
