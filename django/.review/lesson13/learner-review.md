## 🚨 P0-1｜「按 app 分库」的示例会让学员照做后数据丢失

**位置**：3.6 的 `AppSplitRouter` 示例 + 实验 15

**问题**：示例给出的 `allow_relation` 实现是：

```python
def allow_relation(self, obj1, obj2, **hints):
    return obj1._meta.app_label == obj2._meta.app_label
```

这个写法对**跨 app 的外键一律返回 `False`**。但真实项目里，业务 app 的模型几乎必然要外键指向 `auth.User`（课 2 的自定义用户模型、课 8 的 JWT 都依赖它）。学员照抄这个示例后，`Article.author = request.user` 会**直接抛 `ValueError`**，而且是在运行时、在用户操作的那一刻，不是启动时。

讲义本身在 3.1 讲过 `allow_relation=False` 连同库都拦，但**没有把这个通用规则和这个具体示例连起来** —— 学员很可能复制示例代码去改自己的项目，然后在线上炸掉。

**建议**：
1. 在示例后立刻加一条醒目警告，说明"这个 `allow_relation` 会禁止业务表外键指向 `auth.User`，真实项目要放行这一条"。
2. 给出修正版写法（放行 auth/contenttypes，其余按 app 判定）—— 这也正好呼应官方文档示例中 `AuthRouter` 与 `PrimaryReplicaRouter` 分成两个路由器的真实意图。
3. 补一个实测：业务表外键指向 User 时，两种 `allow_relation` 写法的对照结果。

**理由**：这是"照着做会翻车"的问题，不是理解问题。课 3 评审时就抓过同类问题（我说"反向关系写进 fields 会报错"，实测不报错）—— 那次是结论错，这次是**示例会让学员踩坑**。都必须修。

## P1-1｜没有 PG 环境的学员，怎么验证自己真的学会了？

**位置**：全文，尤其第三幕与自检题

**问题**：讲义很贴心地说明了"不需要真的装 PostgreSQL"，这一点很好。但**自检题 8 道题全部是概念题**，没有一道是"去你的环境上跑一下看看"。学员做完题只能确认"我读懂了"，无法确认"我真的会了"。

课 12 的做法值得借鉴：那课的实操给了明确的验证入口（跑 `explain()` 看是否 `USING INDEX`），学员能立刻得到反馈。本课缺这样一个"我能自己验证"的动作。

**建议**：在「本课核心结论」前加一小节「怎么确认你真的会用」，给 2–3 个可在 SQLite 上立刻完成的验证动作，例如：
- 配一个只写 `db_for_read` 的路由器，跑一遍 `obj.save()`，看它到底写进了哪个文件（打开两个 sqlite 文件对比）
- 打印 `router.db_for_read(Model)` 与 `router.db_for_write(Model)`，确认二者都返回了你预期的值
- 在你的模型上找一遍有没有跨库外键，用实验 7 的报错文案去搜代码库

**理由**：课 4 评审时 learner 视角提过"缺自检手段"并被采纳（补了 DevTools 看 OPTIONS 请求）。本课同理 —— 概念题检验"读懂"，动手动作检验"会用"。

## P1-3｜"要不要上多库"的判断缺少可量化的抓手

**位置**：决策清单第一块

**问题**：四个问题（瓶颈 / 读写比 / 最终一致 / 团队能力）方向都对，但**全是定性判断**，学员看完仍然不知道自己的情况该不该上。比如"读多写少才值得做主从"—— 多少算多？"单库到瓶颈"—— 什么指标算瓶颈？

**建议**：补充可观测的判断依据，哪怕给经验值并明确标注是经验值。例如：
- CPU 长期 > 70% 且慢查询已优化完
- 读写比 > 10:1 才考虑主从
- 单表数据量 / 连接数接近上限

同时保持本课的诚实风格：**明确标注这些是经验参考不是阈值**，需要按自己的业务压测。

**理由**：本课已经在多处展现了"不给出未经实测的数字"的克制（延迟量级、LSN 部分），这个优点要保持。但完全定性会让决策清单落不了地 —— 可以标注为"业界常用经验值，非 Django 官方建议，需自行压测"。

## 我作为学员的真实困惑点（记录）

1. **`allow_relation` 和 `allow_migrate` 的 None 兜底相反** —— 这个点讲义强调得很到位，我读完记住了。但担心实际写的时候会记混，建议给一个记忆锚点（比如"`relation` 保守、`migrate` 激进"）。

## 结论

**P0 = 1，必须修完才能交付。** P0-1（AppSplitRouter 的 allow_relation 会让跨 app 外键炸掉）是"照着做会翻车"的问题，风险等级高于普通的内容错误。

P1-1（缺动手验证动作）与 P1-3（判断缺抓手）是实用性缺口，建议一并修。P1-2 为认知负荷优化。P2 两项可选。

本课在**诚实标注未验证部分**这一点上做得非常好，作为学员我更信任这份材料了 —— 因为它明确告诉我哪些是跑过的、哪些不是。
