## 🔴 P0-1：3.6 节的批量导入示例会让人写出 O(n) 事务，且异常处理是裸 `except Exception`

**位置**：自检题【8】的答案 + 3.6 节

**问题**：

给出的写法是：

```python
with transaction.atomic():                    # 外层
    for row in rows:
        try:
            with transaction.atomic():        # 内层 = savepoint
                import_row(row)
        except Exception:
            logger.warning("跳过 %s", row)    # 只回滚这一行
    # 外层正常提交
```

三个问题：

1. **裸 `except Exception` 会吞掉所有错误** —— 包括 `KeyboardInterrupt` 之外的编程错误（拼写错、字段不存在）。学员照抄后，导入逻辑里一个 typo 会被静默跳过 1000 次，日志里全是"跳过"，实际问题被完全掩盖。**这是"不报错的错误"的教科书案例，而讲义自己在收束节批判它。**

2. **savepoint 不是免费的** —— 正文没提。每开一个 savepoint，数据库要做一次额外记录。1000 行就开 1000 个 savepoint。课 14 刚讲过"大表回填要用 `iterator()` + `bulk_update()`"，但这里没衔接。

3. **`rows` 从哪来没说** —— 如果是 `Rows.objects.all()` 这种全量载入，100 万行直接 OOM。

**这与课 14 的 P0 是同一个模式**：课 14 的回填示例用了 `objects.all()`，被评审抓出"讲几百行练手永远不会暴露，照抄到 500 万行就 OOM"。本课在并发/批量场景上重蹈覆辙。

**建议**：改为显式捕获业务异常 + 分批提交 + 提示大批量场景：

```python
from django.db import transaction

BATCH = 500
with transaction.atomic():
    for i, row in enumerate(rows.iterator() if hasattr(rows, "iterator") else rows, 1):
        try:
            with transaction.atomic():
                import_row(row)
        except (ValueError, IntegrityError) as e:   # 只捕获"这一行数据有问题"
            logger.warning("第 %s 行跳过：%s", i, e)
        # 其他异常继续向外抛 —— 编程错误不该被静默
        if i % BATCH == 0:
            ...  # 见下方说明
```

并在正文补一段：

> ⚠️ **savepoint 有成本**。每开一个内层 `atomic`，数据库要记录一个回滚点。
> 导入 10 万行时，更好的做法是**分批提交**（每 500 行一个外层事务），
> 而不是在单个大事务里开 10 万个 savepoint。
> 数据源也要用 `.iterator()`，别把 100 万行读进内存（课 14 已讲）。

课 14 的做法是在讲义里给出关键模型片段。本课只在实验里用了，正文没有。

**建议**：在「怎么跑起来」之后补一个精简的模型定义块（只列字段与关系，去掉 Meta / __str__），让学员即使丢了实验工程也能重建：

```python
class Org(models.Model):
    name = models.CharField(max_length=50)

class Author(models.Model):
    name = models.CharField(max_length=50)
    org = models.ForeignKey(Org, on_delete=models.CASCADE, null=True)   # 可空 → LEFT OUTER JOIN

class Book(models.Model):
    title = models.CharField(max_length=100)
    author = models.ForeignKey(Author, on_delete=models.CASCADE, related_name="books")
    body = models.TextField(blank=True)
    tags = models.ManyToManyField("Tag", related_name="books", blank=True)

class Tag(models.Model):
    name = models.CharField(max_length=30)

class Review(models.Model):
    book = models.ForeignKey(Book, on_delete=models.CASCADE, related_name="reviews")
    rating = models.IntegerField(default=0)

class Product(models.Model):      # 库存
    name = models.CharField(max_length=50)
    stock = models.IntegerField(default=0)
```

**位置**：验证环境表 + 实验 23/24/26/32

**建议**：在第三幕开头（或实验 23 首次出现双 alias 时）加一句显式的"这不是多数据库"：

> ⚠️ **本节的两个 alias 不是课 13 的多数据库**。它们指向**同一个 SQLite 文件**，

> 掩盖真正的逻辑问题（课 11 的教训）。生产环境请按课 13 的方式配置。

### P2-2：`FETCH_RAISE` 的传播性可能让学员在生产环境误伤

**位置**：2.2 节 + 自检题【13】

**问题**：自检题【13】推荐"生产用 `FETCH_PEERS`，测试用 `FETCH_RAISE`"，这很好。但**没有警告 `FETCH_RAISE` 的传播性风险**——正文 2.2 提到它会传播到关联对象，但没说这会给生产带来什么。

如果有人在**生产**误用了 `FETCH_RAISE`，一个深层访问就会让整个接口 500，而不是慢一点。

**建议**：在自检题【13】答案里把警告说死：

> ⚠️ **`FETCH_RAISE` 只应在测试里用。** 它会传播到关联对象（实验 19），
> 生产环境一个意外访问就是 500，而不是"慢一点"。
> 生产要的是"兜底"（`FETCH_PEERS`），不是"拦截"（`FETCH_RAISE`）。

### P2-3：3.5 三方案对照表缺"并发量"维度

**问题**：表里有「丢失更新 / SQLite 可用 / 需要事务 / 适用」，但没有提**性能**。学员会问："既然 `F()` 这么好，为什么还要行锁？"

正文 3.5 最后一句说"只有判断逻辑没法写成 SQL 表达式时才用行锁"，这回答了**能力**问题，没回答**代价**问题。

**建议**：补一行说明代价：

> `select_for_update` 的代价：持有行锁期间**其他事务要等待**（或按 `NOWAIT`/`SKIP LOCKED` 立即失败）。
> 高并发下会形成锁等待队列。所以即便能力上能用，也只在**必须用**时才用。

建议新增必查项（**2026-09-03 用户确认，已固化**）：

> **#28：示例代码必须按"生产规模"检验一遍。**
> 凡是讲义中出现"循环处理 N 条"的示例，都要问一句：**N 变成 10 万会怎样？**
> 重点排查三类：①是否把全表/全量数据读进内存（应 `.iterator()`）；②是否是 O(N) 次数据库往返（应 `bulk_*` 或 `F()`）；③异常处理是否用裸 `except Exception`（会把编程错误变成静默跳过）。
> 历史：课 14 与课 15 连续两课在此栽跟头，说明单次修复不足以形成习惯，须固化为检查项。

**落地情况**：已写入 [00-评审清单.md](../../00-评审清单.md) 的「示例代码质量组（2026-09-03 新增）」，编号 **#28**（#27 已被课 8 的"讲义内部不自相矛盾"占用）。补充的判定标准：**示例里给学员的练手数据量必须小到能跑，但示例本身的写法必须大到 10 万行也不炸**——二者冲突时改写法，不改数据量。自查手法：翻到讲义里每一个 `for` 循环，问"循环体里有没有数据库/IO 操作"。
