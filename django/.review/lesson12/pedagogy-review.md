## P1（建议修改）

### P1-1：1.3 节"优化器未必选部分索引"削弱了 1.2 节"部分索引省 63%"

**问题**：1.2 刚用实测数据证明部分索引省 63% 空间、能消除排序，1.3 立刻说"SQLite 优化器不选它"。读者的自然反应是"那我到底建不建？"讲义没有给出决策依据。

**建议**：在 1.3 末尾补一段明确的决策指引，把"数据库类型"作为分支条件：

- PostgreSQL：优化器对部分索引识别成熟，可放心依赖，正常建
- SQLite：优化器保守，需要 `INDEXED BY` 或重新设计索引；但本地开发/测试用 SQLite、生产用 PG 是常见配置，此时**以 PG 的行为为准**
- MySQL / MariaDB：**不支持**，`condition` 参数被忽略（文档明示）
- Oracle：不支持部分索引，需用函数索引 + `Case` 模拟

来源：Django 官方文档 Model index reference 明确写了各后端的 `condition` 限制，讲义目前只在 1.1 提了"命名必填"，没讲后端差异。这是**知识的必要补全**，不是可选增强。

### P1-2：缺少"索引设计决策流程"的收口

**问题**：1.1–1.8 讲了八个小节，都是"是什么"，但学员合上讲义后面对真实需求（"这个列表页慢，我该怎么建索引？"）仍缺一个可执行的流程。

**建议**：在第一幕末尾加一个决策清单，形式可以是几步判断：

1. 这个查询高频吗？（不高频 → 不建）
2. `explain()` 现在走什么？（已经走索引 → 先看是不是别的问题）
3. 过滤条件是什么？选择性如何？（低选择性单列索引 → 考虑放进复合索引的后列）
4. 是不是只查热点子集？（是 → 部分索引）
5. 过滤涉及表达式吗？（是 → 函数索引，且写法要精确匹配）
6. 建完之后 `explain()` 再验一次

### P1-3：第三幕缺"什么时候不该用连接池"的判断依据

**问题**：3.5 给了表格，但读者无法判断自己属于哪一行。特别是"worker 数可控"这个说法没有量化。

**建议**：补一个简单的判据 —— 当 `总进程数 × max_size` 已经逼近 `max_connections` 的 70% 时，就该考虑外部代理了。这与 3.4 的容量公式直接衔接，学员能自己算。
