## 一、评审视角

假设我是一位要评审这份讲义的教学设计者，关注四件事：
1. **认知阶梯**——学员能不能一步步走上来，而不是被直接扔到结论里
2. **冲突的真实性**——"认知冲突"是真冲突，还是作者编出来的稻草人
3. **结论的可迁移性**——学完能不能用到自己的工程，还是只记住了一堆数字
4. **取舍有没有讲透**——每个"建议"背后的代价是否交代清楚

## 二、做得好的地方

### 2.1 五幕结构完整，冲突前置且真实

第二幕直接摆出"三个常识都是错的"，而且**每个都给了推翻过程**（放大迁移数验证、决定性实验、源码引用）。这比直接给结论强得多——课 19 的经验"预设被推翻时保留推翻过程作为教学点"在本课被完整继承并放大。

特别值得肯定的是**实验 21 的三级验证链**：
1. 先发现数字不对（0.87x）
2. 再放大迁移数量排除"任务太小"的解释（120 个迁移差距仍没拉开）
3. 最后做决定性实验（新增迁移被应用 + ROWS=1）

这是完整的排除法，**不是碰巧得到一个反直觉数字就下结论**。

### 2.2 "先量后改"这条主线立得住

体检三段（建库 78% / 造数 18% / 执行 4%）把"先量后改"从口号变成了可操作的方法。而且**讲义自己演示了这个方法的价值**：combo（74.8ms）比只禁迁移（60.2ms）还慢，恰好证明"不看数据就开三个开关"是无效的。

这个结构有个额外的好处：它让后文的**每个数字都有了归属**——学员知道 2.77x 是打在建库上的、144x 是打在执行上的、4.3x 是打在造数上的，不会把三个数字混成一锅粥。

### 2.3 环境依赖性交代得诚实

这是本课最值得表扬的一点。讲义反复强调：

> ⚠️ 这个结论**强依赖于数据库类型**。SQLite 建文件几乎不花钱，所以省不掉什么。换成 PostgreSQL / MySQL……keepdb 的收益会明显得多。**不要把这个数字直接搬到你自己的工程上**——它就是"先量后改"的最好注脚。

很多教程会把自己环境里的数字当普适真理讲出去。本课明确说了"850ms 是 Windows 数字，Linux 会低不少"、"keepdb 在 PG 上会转正"。**这种诚实本身就是教学内容**——它教的是方法，不是数字。

### 2.4 量化充分，且量化到了"决策"层面

不只是给了比值，还给了**决策判据**：
- 盈亏平衡点 ≈ 1132ms（可以直接判断该不该开并行）
- 迁移越多收益越大（2.77x → 2.93x）
- 三个基类的绝对耗时（0.4 / 2.7 / 153.7ms）

## 三、P1 级问题（应修）

### P1-① 第一幕缺"怎么知道自己的测试慢在哪"的入口

**问题**：1.2 节直接抛出体检结果（78% / 18% / 4%），但这是**本课工程的数字**。学员读到这里的自然反应是"那我的工程呢？"，而讲义要到实验 41（第四幕）才给出体检脚本长什么样。第一幕到第四幕之间隔了整整三幕，学员无法立刻动手。

**建议**：在 1.2 节补一段**最小可跑的体检代码**（10 行左右），让学员读完第一幕就能测自己的工程。完整的三段计时脚本仍留在第四幕。

**判定**：必修。第一幕的价值就是"让学员立刻对号入座"，没有动手入口就只是个故事。

### P1-② 第二幕和第 三幕有内容重复，读起来会"见过"

**问题**：2.1（keepdb 冲突）与 3.2.2（keepdb 手段）、2.2（parallel 冲突）与 3.2.4（parallel 手段）、2.3（危险组合）与 3.2.2 末尾，**三处内容高度重叠**。实验 21 的关键数据在第二幕写了一遍，第三幕又写一遍；`--parallel` 的两个门槛也是。

**影响**：读到第三幕会有"这个我见过了"的感觉，削弱第三幕"层层揭示"的功能。

**建议**：明确分工——**第二幕只摆冲突与推翻过程，第三幕只讲"怎么用"**。具体做法：第二幕保留冲突 + 证据链，第三幕改为引用（"回到 2.1 的发现——keepdb 照样跑 migrate，所以它的正确使用姿势是……"），不再重复数据。

**判定**：必修。这是结构问题，影响阅读节奏。

### P1-③ 决策表缺少"我怎么知道自己是哪种情况"的判据

**问题**：5.1 的三张表给得很清楚，但都隐含"你已经知道自己处在哪种情况"。比如表二第 2 步"建库慢 → 禁所有 app 的迁移"，学员得先知道"我的建库慢不慢"，而这又回到体检——但表二第 1 步只说了"跑体检脚本"，没说脚本在哪、长什么样。

**建议**：表二每一步补一个"怎么判断命中"的判据列。例如：
- 建库慢：`SETUP_MS` 占 `TOTAL_MS` 超过 50%
- 造数慢：用例里大量 `create_batch` 而没用 `bulk_create`
- 执行慢：用例里有真实 HTTP / sleep / 外部调用

**判定**：应修。决策表不给判据，就只是个清单。

### P1-④ 必查项 #28 的自查过程没有在讲义里呈现

**问题**：评审清单里写了"扫描 25 处 for 循环…唯一命中为数据迁移的逐条 `create()`，已改写为 bulk_create"，但**讲义正文完全没提这件事**。而课 19 的做法是把 #28 的自查结论写进讲义（明确标注 `update()` 不触发 signal 的代价）。

**影响**：学员看不到"示例代码也要按生产规模检验"这个示范。而且讲义自己在 3.1.4 讲 `create_batch` vs `bulk_create` 的 4.3x 差距，**却没指出本课自己的数据迁移就曾经是逐条 create**——这是个天然的教学点。

**建议**：在 3.1.4 末尾或 5.3 坑位清单里补一条：**本课自己的数据迁移原本是逐条 `create()`，#28 自查时改成了 `bulk_create` + `ignore_conflicts`**，并说明 3 条种子数据为什么也要这么写。

**判定**：应修。一致性问题——讲义教了 #28，自己就该展示 #28 的执行过程。

## 四、P2 级问题（建议修）

### P2-① `Timer` 与 `Check` 工具没有给代码

**问题**：4.1 节提到 `apps/labkit.py` 有 `Check` 断言器和 `Timer`，但讲义里没给代码。学员想自己搭实验工程时会卡住。

**建议**：在 4.1 或附录里给一个 20 行的最小版本。

### P2-② 自检题 A7 的答案依赖本机数字，可能让学员困惑

**问题**：A7 用了"本机 4 进程开销约 850ms，平衡点约 1130ms"，但学员自己的机器数字会不同。

**建议**：在答案里加一句"这个数字只对应本课实验环境，你自己的机器要先量出开销再算平衡点"——正好又是"先量后改"的一次演示。

### P2-③ 术语表可以再补两条

`spawn / fork`（Windows 与 Linux 的进程启动方式差异，讲了但没进术语表）、`subsuite`（parallel 切分单元，正文出现但没解释）。

## 五、结论

| 项目 | 结论 |
|---|---|
| P0（事实错误） | **0** |
| P1 | 4 条（①第一幕缺动手入口 ②二三幕内容重复 ③决策表缺判据 ④#28 自查未呈现） |
| P2 | 3 条 |

**总体评价**：本课是阶段 6 目前方法论价值最高的一课。"先量后改"这条主线贯穿全课，且**用 combo 比单一手段更慢这个反例自证了它的必要性**。五处预设被推翻全部保留了推翻过程，环境依赖性交代得异常诚实——这是很多教程做不到的。

主要问题集中在**结构**而非内容：第二幕与第三幕的分工不够清晰，导致关键数据被读两遍；决策表缺判据使其更像清单而非工具。这两点修正后，本课的可用性会有明显提升。

**是否放行**：P1 修正后放行。
