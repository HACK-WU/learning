## 二、学完能回答的问题（做得好的）

### 2.1 三个提速手段的账本非常清楚

5.1 节的表三是我最想保存下来的一张表：

| 手段 | 省什么 | 不省什么 | 代价 | SQLite 实测 |
|---|---|---|---|---|
| `--keepdb` | 删库 + 建文件 | **迁移照跑** | 模型改了会报错 | 0.87x（负收益） |
| 禁迁移 | 跑全部迁移 | 表照样建 | **数据迁移不执行** | 2.77x |
| `--parallel` | 执行时间 | 建库（每 worker 一份） | 850ms 开销 + 资源 ×N | 短 0.99x / 长 3.02x |

**"不省什么"这一列是全文最有价值的**——网上绝大多数教程只讲"省了什么"，讲代价的很少。我以前就是三个开关一起开，现在知道那样可能更慢。

### 2.2 "先量后改"改变了我的思路

1.2 节那个数字（执行只占 4%）让我意识到：我之前的优化方向可能一直是错的。我一直以为慢是因为"用例写得不好"，但实际上时间全在建库。

而且讲义**自己演示了这个错误的后果**：combo（全开 74.8ms）比只禁迁移（60.2ms）还慢。这个反例比任何说教都有力。

### 2.3 五处"预设被推翻"让我避开了五个坑

特别是这几条，我以前真的信：
- **`setUpTestData` 对象共享**——我一直小心翼翼地不在测试里改类级对象，现在知道 Django 6.1 有 deepcopy 保护
- **`--parallel=4` 快 4 倍**——我确实把 200 个用例塞在一个类里，等于没开
- **patch 定义在哪个模块就打哪个**——这个坑我踩过，讲义用四组对照把它讲透了

### 2.4 自检题质量高，答案详细

Q1-Q8 覆盖了全部关键决策点，答案不是一句话，而是带推理过程。特别是：
- **A6** 解释了为什么泄漏在 `AllFields` 更危险（不污染已发布组件 → 回归抓不到 → 人工漏审）
- **A7** 演示了盈亏平衡点的实际用法（900ms < 1130ms → 开并行净亏）
- **A8** 提醒结论依赖环境（PG 上 keepdb 会转正）

## 三、L1 级问题（学完会卡住）

### L1-① 第二幕说"先看两个前提"，但没说怎么查自己的工程有几个 TestCase 类

**问题**：2.2 节给出门槛一——并行按 TestCase 类切分。我立刻想知道"那我的工程有几个类、每个类多少个用例"，但讲义只给了实验数据（`SUBSUITE_COUNT = 1` / `EFFECTIVE_PROCESSES = 1`），没给**自查命令**。

**卡住的后果**：我知道了门槛存在，但没法判断自己有没有踩中。

**建议**：补一段自查方法，比如：

```bash
# 统计每个 TestCase 类下的用例数（找"巨无霸类"）
python manage.py test --collect-only -v 2 2>&1 | grep -c "test_"
# 或直接看 partition 结果
python -c "
from django.test.runner import DiscoverRunner
# 打印每个类的用例数分布
"
```

或者更简单：**跑一次 `--parallel=4 -v 2`，看输出里 worker 的数量**。

**判定**：必修。这是"知道"到"能做到"之间的缺口。

### L1-② 体检脚本给了数据，但没给代码

**问题**：1.2 节和 3.2.1 都引用了体检三段数据（78% / 18% / 4%），实验 41 也给了输出，但**讲义里没有体检脚本本身**。4.1 节的文件树里有 `probe_test_health.py`，但没展示内容。

**卡住的后果**：我认可"先量后改"，但不知道怎么量自己的工程。

**建议**：在 3.2.1 节直接给出体检脚本的核心代码（20-30 行：分别计时 `setup_databases()` / 造数 / `run_tests()`），或者至少给个最小版本。

**判定**：必修。这是全课方法论的落地入口，不给代码等于方法悬空。

### L1-③ `MIGRATION_MODULES` 禁哪些 app 要怎么枚举？

**问题**：3.2.3 给了正确写法（禁 5 个 app），并说明"只禁业务 app 无效因为 contrib 那 18 个照跑"。但我的工程 app 列表和课上的不一样，**我不知道该枚举哪些**。

**建议**：给一个动态生成的方法：

```python
# settings_test.py
from django.conf import global_settings
# 或者更简单：把 INSTALLED_APPS 全部映射为 None
MIGRATION_MODULES = {app.split(".")[-1]: None for app in INSTALLED_APPS}
```

并提醒：这样会把 contrib 全禁掉，如果有 app 依赖数据迁移要单独排除。

**判定**：应修。给了"禁所有"的结论，但没给"怎么算出所有"。

### L1-④ CI 的 schema 检查给了 YAML，但没说 Windows 上怎么写

**问题**：3.3.6 给了 GitHub Actions 风格的 YAML（bash 语法）。本课程全程用 Windows PowerShell，我照抄会跑不通。

**建议**：补一句 Windows 等价写法，或明确说明"这段是 Linux CI 语法，Windows 本地请用……"。

**判定**：应修。课程序列一直有"两套命令"的惯例（课 2 就补过）。

## 四、L2 级问题（建议改进）

### L2-① 术语表可以补三条

- **spawn / fork**：正文 3.2.4 提到 "Windows 的 spawn 模式进程启动开销显著高于 Linux 的 fork"，但术语表没收
- **subsuite**：2.2 节 `SUBSUITE_COUNT` 出现多次，没解释

### L2-② 5.3 坑位清单很有价值，但可以更醒目

坑 1（路由遮蔽）、坑 2（ROOT_URLCONF 不能传列表）、坑 6（PowerShell 改中文文件）都是**会浪费半天时间**的坑。建议在坑 6 和坑 1 上加更强的视觉标记——它们是纯环境问题，与 Django 知识无关，最容易被忽略却最费时间。

### L2-③ 4.3 实验清单表可以加一列"我要不要自己跑"

42 个实验不是每个都需要亲手跑一遍。建议标注哪些是"必跑"（如实验 24 的 parallel 对比、实验 21 的 keepdb 决定性实验）、哪些"看结论即可"。
