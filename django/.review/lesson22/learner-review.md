## L1-1　3.1.3 的 `raise` 代码块不能直接照抄到已有项目

**问题**：

```python
SECRET_KEY = os.environ.get("SECRET_KEY")

if not SECRET_KEY:
    if not DEBUG:
        raise RuntimeError(...)
    SECRET_KEY = "dev-only-insecure-key-do-not-use-in-production"
```

读者如果**直接粘到自己项目的 settings 里**，会发现 `DEBUG` 这行可能还没定义（取决于粘的位置）、`os` 是否导入也不确定。更关键的是：这段依赖 `DEBUG` 已经被正确解析（3.1.1 的 `env_bool`），如果读者跳过了 3.1.1 直接用 3.1.3，就有 `DEBUG` 恒为 True 时这段永不触发的风险。

**修复建议**：给一个完整的、可独立粘贴的最小片段，并标注依赖：

```python
# settings.py 顶部
import os

DEBUG = env_bool("DEBUG", False)      # ← 依赖 3.1.1 的 env_bool
SECRET_KEY = os.environ.get("SECRET_KEY")
if not SECRET_KEY:
    if not DEBUG:
        raise RuntimeError(...)
    SECRET_KEY = "dev-only-..."

# env_bool 的定义（若还没加）
def env_bool(name, default=False): ...
```

并明确写一句：**这段必须放在 `DEBUG` 定义之后。**

## L1-2　4.1 的环境变量说明会让读者以为"必须先设才能跑"

**问题**：4.1 里写"关键环境变量（`run_lab*.py` 会自己重置，手动跑命令时需要）"，然后给了三条 `$env:...`。但紧接着的"每条命令都跑一遍"块里，那些命令**需要这些环境变量**，读者如果只复制命令块就跑，会失败。

**修复建议**：调整顺序或加一句提示——"下面这一组命令依赖上面三条环境变量，请先执行"。或者在命令块前重复一次环境变量设置。

## L1-3　3.2.1 的拓扑图里 `/admin/` 的归属容易误解

**问题**：ASCII 图里画了 `/admin/* → Nginx → gunicorn → Django`，但紧接着说"只有 `/api/` 和 `/admin/` 走到 Django"。这两处一致，没问题。

真正的问题是：**Admin 依赖 `/static/`**（它的 CSS/JS）。读者可能配了 `/admin/` 转发却忘了配 `/static/`，结果 Admin 能打开但样式全丢——这是极常见的部署故障，而图里没有体现这个依赖。

**修复建议**：在拓扑图或 3.2.5 后补一句："`/admin/` 除了要转发到 Django，还必须能访问 `/static/`（Admin 的 CSS/JS 都在那里）。Admin 能打开但没样式，就是这个原因。"

## L1-4　3.3.3 的流水线没说"这些命令在哪台机器上跑"

**问题**：流水线列了 7 条命令，但没说执行环境。`check` 和 `collectstatic` 通常在 CI runner 上跑，`migrate` 在部署目标机上跑（或者在单独的 job 里），`testhealth` 在上线后的生产环境跑。

读者照抄会以为"按顺序在一台机器上跑一遍就行"。

**修复建议**：在流水线表格里加一列"在哪跑"：CI runner / 部署机 / 生产环境。
