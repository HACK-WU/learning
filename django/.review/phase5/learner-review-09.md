learner 视角对排障手册的唯一要求是：**我照着你的验证动作跑一遍，能不能复现出和你一样的输出**。本文每一条的验证动作都给了**期望输出**，读者可以直接比对——这是排障手册该有的样子，而不是"请检查你的限流配置"这种空话。

## 模拟三个真实场景

### 场景 A：凌晨两点，接口 500，日志里 `No default throttle rate`

**路径**：目录表 → 「接口 500 且报 ImproperlyConfigured」→ §2.2

**体验**：一步到位。§2.2 直接给了条件、实测输出、解药，30 秒内可解决。✅

### 场景 B：限流配了却没拦，怀疑配置没生效

**路径**：目录表 → 「限流配了却一次都不拦」→ §2.1

**体验**：条件表按可能性排序（最常见的原因排第一），这点做得好。验证动作有两组输出可对照。

**卡点**：两组实验（正常速率 / 降 user 速率）**没有说先跑哪个**。紧迫场景下读者可能跑完第一组就停了，而第一组只能证明"没拦"，**定位不到原因**。

### 场景 C：怀疑 check 没注册，但 `manage.py check` 说没问题

**路径**：目录表 → 「CI 不拦、check 不报」→ §8

**体验**：这是本文最有价值的一节。它给出了**推翻常识的结论**——元检查兜不住自身未注册。读者如果不知道这点，会一直以为"有元检查就安全了"。

**卡点**：§8 给出的兜底方案是 `check --list | findstr orderflow`，但没有说**期望输出是什么**（三组：`orderflow_docs`、`orderflow_meta`、`orderflow_routes`）。虽然正文后面提到了，但在解药代码块里没有直接给出来，紧迫时容易漏看。

## L1（建议修改，不阻塞）

### L1-1：§2.1 两组实验缺"先跑哪个"的指引

同 pedagogy 的 P1-2。紧迫场景下，读者需要的是**最短定位路径**，不是完整实验流程。

**建议**：明确写「时间紧就只跑第②组（降 user 速率）——它能直接定位原因；第①组只能证明问题存在」。

### L1-2：§8 的解药代码块里没有期望输出

原文：

```bash
python manage.py check --list | findstr orderflow   # 输出应有 orderflow_docs / orderflow_meta / orderflow_routes
```

注释里写了，但**如果输出为空意味着什么、该怎么做**没有说。紧迫场景下读者看到空输出会懵。

**建议**：补一句「若输出为空 → 说明 `checks.py` 没被 `ready()` import，去检查 `apps/shop/apps.py`」。

### L1-3：§7 并发的数字会让人以为自己跑错了

"起点 40，应扣 20，实际 30"——读者复现时**大概率得到不同的数字**（线程调度随机）。会误以为环境有问题。

**建议**：补一句「具体丢几次取决于线程调度，每次不同；**判据是"不等于 20"，不是"等于 30"**」。

## L2（可选优化）

1. **目录表的症状描述可以更口语**。读者在慌的时候，脑子里想的是"图片全挂了"而不是"静态资源 404"。可以在目录表里加一列"大白话"。
2. **§1 通用三板斧缺少"怎么最小化复现"**。三板斧讲的全是"确认配置"，但排障的关键一步往往是把问题缩小到最小可复现。可考虑加第 4 条。
3. **部分命令缺 Windows 前置条件提醒**。虽然开头提了 `PYTHONIOENCODING`，但 §8、§9、§11 的命令输出含中文，个别读者可能仍踩编码坑。
