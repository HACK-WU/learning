## 总体判断

**通过，P0 = 0。**

设计态文档最难的不是"给结论"，而是"给**可迁移的判据**"——读者面对的是自己的项目，不是 OrderFlow。本文在这一点上做得比前两件更成熟：每一节的判据都是从具体实测中抽象出来的，读者换到自己的项目上仍然能用。

与另两件的分工也干净：08 是"结论在什么前提下成立"（学习态），09 是"崩了怎么查"（使用态），本文是"要设计时怎么选"（设计态）。三者的索引互相指向，形成闭环。

## 做得特别好的三处

### 👍 1. 第 14 节「十一条跨场景通用判据」是本文最大的教学增量

前 13 节是决策表，第 14 节把它们背后的**共同判据**抽了出来。比如：

- 「会被复用的逻辑，不要放在只有一条路径能触发它的地方」（§1）
- 「能被批量路径绕过的机制，不能用来承载核心业务」（§2）
- 「异步的收益来自'可并行'，不是来自 `async def` 关键字」（§5）

这三条已经脱离了 Django，是可以带走的工程判断力。**这是收尾文档应有的样子**——不是把 22 课重讲一遍，而是给出可迁移的东西。

### 👍 2. 两次主动修正了错误的实测方法，并把教训写进文档

- **§9 的 `--skip-checks`**：第一版取 `min` 得到 **-59ms（负收益）** 的错误结论，改用中位数复测（5 次）得到 **+26ms（6%）**。文档里明确写了这个坑：「取 `min` 会放大冷启动噪声」。
- **§4 的判据坑**（probe_9）：测试结论 `OK` 写在 **stderr**，第一版只查 stdout 误判为"测试失败"。

这两处都是**方法错误而非事实错误**，作者没有掩盖，而是把它们作为"怎么测"的提示写进了正文。这比只给正确数字更有教学价值。

### 👍 3. §11 如实指出了本项目版本实现的局限

实测发现 `DEFAULT_VERSIONING_CLASS = None`，本项目其实**没有用 DRF 的 versioning 框架**，只是路由前缀硬编码。作者没有回避这个"不符合课本最佳实践"的事实，而是补了一句代价分析：

> 代价：**没有 `ALLOWED_VERSIONS` 校验**，也没有 `request.version` 可用；将来要拆 v2 得手工复制一套路由。

这种"如实标注自己项目不完美"的写法，比假装一切都符合最佳实践可信得多。

## P1（建议修改，不阻塞交付）

### P1-1：§1 的"700 倍"需要补一句口径说明

原文"service 0.02ms vs HTTP 14.1ms，差 700 倍"。这个数字容易被引申成"service 比 view 快 700 倍"，但这不是同一件事——**多出来的是 HTTP 栈成本，不是"放在 view 里"的代价**。

**建议**：补一句「这个差距衡量的是"要不要经过 HTTP 栈"，不是"逻辑放在 view 还是 service"。放在 service 里的收益主要是**可测试性与防绕过**，性能只是附带。」

### P1-2：§8 索引那节只给了"不值得"的半边结论

实测只证明了「2000 行下差 1ms」，但决策表标题是"该不该加"，读者真正需要的是**什么时候该加**。目前只有"小表别论证"，缺"大表该怎么判断"。

**建议**：补一句可操作的判据——「看 `EXPLAIN` 里有没有走索引（`SQLite: EXPLAIN QUERY PLAN`），而不是只比耗时；耗时在数据量小的时候说明不了问题」。若来不及补实测，就标 `⏳ 置信度：低`。

### P1-3：§13 的决策表缺少"启动开销"这一列

决策表三列是"进请求链路 / 做成管理命令 / 常驻进程"，但正文的核心判据是**启动开销**（400ms）。决策表里没有这一行，读者扫表时抓不到重点。

**建议**：在决策表里加一行「单次耗时 < 100ms → 进请求链路；> 启动开销（≈400ms）→ 只能做定时任务或常驻」。

## P2（可选优化）

1. **§6 任务框架的"静默坑"可以更突出**。`enqueue()` 当场同步执行、异常塞进 `result.errors` 不抛——这两条是选型时最容易踩的，目前放在引用块里，可考虑提到决策表正下方。
2. **§4 的 87.6x 加速比建议加个"这是本地 SQLite"的更醒目提示**。虽然正文有一句，但 87.6x 这个数字太抢眼，容易被直接引用。
3. **第 14 节可按"Failure Mode"再归一次类**。目前 11 条是按出处排的，若按"漏传型 / 绕过型 / 静默型"重新分组，会更容易记忆。
