# 综合实战项目：订单履约消息系统

## 一句话需求

> 用 RabbitMQ 搭一套**订单履约系统**：下单后异步驱动「扣库存 → 通知发货 → 发短信」，要求**消息不丢、业务不重复执行、失败能自动重试并最终有兜底**，且**单个节点宕机不影响整体可用**。

## 🎯 为什么要做这个项目

前面 12 课，每课的第四幕都只验证**单个知识点**：confirm 是不是真的回了、TTL 是不是惰性过期、quorum 切换要多久。但真实系统里这些知识点是**同时**起作用的——

- 你开了 confirm，还得同时想清楚**重试几次**、**失败去哪**
- 你选了 quorum 保证高可用，就得接受它**不接受 x-max-priority**、**吞吐只有 classic 的 1/3.7**
- 你做了幂等，还得判断**这次重复是生产侧的还是消费侧的**（两者 `redelivered` 长得不一样）

这些**交叉点**才是工程里真正会咬人的地方，而任何一课都不会单独讲它们。本项目就是把散装的知识点焊成一个能跑的系统。

## ⚠️ 先看这一条（能帮你省下几小时）

本项目里有**一个坑，坑倒了包括我在内的很多人**，它足够反直觉，值得放在最前面：

> **失败重试要用 `basic_reject`，不能用 `basic_nack`。**
>
> 这两个在老版本里等价，但 **4.3 起不再等价**：延迟退避和死信阈值都只看 `delivery-count`，
> 而 `delivery-count` **只在"投递失败"时递增** —— 只有 `reject` 算失败，`nack` 不算。
>
> 用 `nack` 写重试的后果：计数永远不动 → 延迟恒定 → 永远够不到 `delivery-limit`
> → **消息在队列里无限循环，永不进死信**。而系统看起来一切正常（日志在打重试）。
>
> 实测对照（100% 失败率）：
>
> | 动作 | delivery-count | 重试间隔 | 结局 |
> |------|----------------|----------|------|
> | `nack(requeue=True)` | 恒为 None | 恒定 1.04s | 无限循环 ⚠️ |
> | `reject(requeue=True)` | 1 → 2 → 3 | 1.04 / 2.09 / 3.02s | 超限转死信 ✅ |

完整分析见 [设计决策.md · 决策 3](./设计决策.md)。

## 📋 项目要求（验收的硬门槛）

| 类别 | 要求 |
|------|------|
| **功能** | 下单 → 扣库存 → 通知发货 → 发短信，四步异步驱动 |
| **功能** | 库存不足 / 下游超时等失败要能自动重试，重试耗尽进死信 |
| **非功能 1：可靠性** | 至少一次投递：publisher confirm + 手动 ack + 持久化三层全开 |
| **非功能 2：正确性** | 业务幂等：重复投递不重复扣款、不重复发货 |
| **非功能 3：可用性** | 任一 broker 节点宕机，系统继续可用、已确认消息不丢 |
| **非功能 4：可运维性** | 死信可观测、可按 order_id 追踪一条消息的全链路 |
| **工程约束 1：错误处理** | 不能有任何"静默失败"——所有失败必须有可观测出口 |
| **工程约束 2：可维护性** | 多文件模块划分，拓扑声明与业务代码分离 |

## 🚀 运行方式

### 环境要求

| 项 | 值 |
|----|-----|
| RabbitMQ | 4.3.5（三节点集群 rmq1/rmq2/rmq3，端口 5681/5682/5683） |
| Python | 3.x（WSL 内） |
| pika | 1.4.4 |
| 凭据 | `learn` / `learn123` |

> ⚠️ Windows 侧 pika 不可用，所有命令须在 **WSL** 内执行。

### 起集群（若尚未启动）

```bash
cd /mnt/d/projects/learning/rabbitmq/playground
bash l11-cluster-setup.sh
```

### 跑主流程

```bash
cd /mnt/d/projects/learning/rabbitmq/projects/订单履约消息系统/实现
python3 run_demo.py
```

预期看到：下单 → 库存扣减 → 发货通知 → 短信通知，四个环节依次完成。

### 跑故障演练

```bash
python3 run_chaos.py
```

脚本会提示你手动 `docker stop rmq1`，然后验证系统是否继续可用。**这是"可用性"这个非功能约束的唯一真实验证方式**——代码里写一百遍"高可用"，不如真停一个节点看看。

### 跑验收自检

```bash
python3 verify.py
```

逐项检查 12 条验收项，输出通过/失败。

## 📖 阅读顺序建议

**先跑起来，再读原理。** 顺序刻意如此——反例要"先见过正的"才有对比体感，
而 25 项知识点地图是**事后回查的索引**，不是开头要背的清单。

1. **先看本文件到「项目要求」为止**，搞清要做什么（知识点地图先跳过）
2. **跑 `run_demo.py`** —— 先看到系统真的动起来（约 40 秒）
3. **跑 `run_chaos.py --auto`** —— 真停一个节点，眼见消息不丢
4. **读 `反例对照.md`** —— 此时你已见过正解，再看那个"能跑但很糟"的版本才有冲击力
5. **读 `设计决策.md`** —— 重点看 5 个权衡点的「代价」部分，那是工程的真实面貌
6. **看 `实现/` 代码** —— 每个文件头部标注了对应知识点
7. **跑 `run_retry_drill_b.py`** —— 验证重试退避真的在递增
8. **跑 `verify.py`** —— 15 项自动检查
9. 最后回到 `验收清单.md` 逐项自查，其中 B6 / D5 / D6 三项**必须手工验证**
