# 验收清单：怎么确认自己真的做成了

> 使用方法：逐项做、逐项勾。**重点不在"代码写没写"，而在"机制有没有被真正触发过"**——
> 写了重试代码但从没见过重试发生，等于没做。
>
> 自动化项跑 `python3 verify.py`（15 项）；标记 🔧 的需手工验证，配套脚本已给出。

### 🔧 B6 强制宕机不丢消息（手工，最关键的一项）

```bash
# 终端 1：发布 20 条 confirm 消息
python3 run_chaos.py --auto
```

**判定标准**：
- 停掉 rmq1 后，队列深度**仍是 20**（不是 19、不是 0）
- 宕机期间仍可写入（5/5 confirm 成功）
- 恢复后能消费到全部 25 条，零丢失

> **为什么这项必须用 `--auto` 或真停容器**：
> `docker restart` 是优雅关机（SIGTERM），broker 退出前会把数据全部落盘——
> **连不该存活的数据都活过重启**，测出来的是假象。
> 必须 `docker stop`（模拟宕机）或 `docker kill -s KILL`（强制杀死）。
> 课 7 的方法学教训：第一次做这个实验时用 restart，三组配置全存活，得出了与生产完全相反的结论。

### 🔧 C4 生产侧重复也被挡住（手工）

手工发布两条**同 order_id、不同 message_id** 的消息，观察业务执行次数。

**判定标准**：业务只执行 1 次。

> **这是幂等设计里最容易漏的一格**。课 8 实测：生产侧重复的 `redelivered` 是
> `[False, False]`——broker 完全不知道这是重复。
> 如果你的幂等只靠 `redelivered` 判断，这一项会失败。

## D. 错误处理（工程约束 1：不能有静默失败）

- [ ] **D1** 业务失败路径用的是 `basic_reject`，**不是** `basic_nack`
- [ ] **D2** 主链路队列配了 `x-delivery-limit`
- [ ] **D3** 主链路队列配了死信交换机（DLX）
- [ ] **D4** 短信队列（classic）启用了应用层重试计数

> 自动化：verify.py 的「工程约束 1」3 项。

### 🔧 D5 重试退避真的在递增（手工，最容易被"看起来对"骗过）

```bash
python3 run_retry_drill_b.py
```

**判定标准**（本项目实测值）：

| 轮次 | delivery-count | 本轮间隔 |
|------|----------------|----------|
| 1 | None | - |
| 2 | 1 | ≈1.00s |
| 3 | 2 | ≈2.00s |
| 4 | 3 | ≈3.00s |
| → 死信 | - | `reason=delivery_limit` |

**如果你测出间隔恒定 1.04s、死信为空** → 你用了 `nack`。
这是本项目最隐蔽的陷阱：**系统看起来在工作**（日志在打重试），
实际上消息会永远循环下去。

### 🔧 D6 死信里能查到失败原因（手工）

检查死信队列消息的 `x-death` 头：

```python
# 期望看到
{'count': 1, 'reason': 'delivery_limit', 'queue': '...', ...}
```

**判定标准**：`reason` 为 `delivery_limit`（不是 `rejected`）。
`reason=rejected` 说明消息是被客户端主动 `requeue=False` 送进去的，
**不是重试超限**——两者含义不同，后者意味着你的 delivery-limit 没生效。

> 这项来自本项目的一次真实排查：演练时死信里混着 `reason=rejected` 的消息，
> 查下来是上一轮残留（队列没清干净）。
> **做死信演练前务必用专属队列名并先删除**，否则你会对着陈旧数据得出错误结论。

## G. 权衡理解决（设计决策的掌握度）

这一组**不是功能验收，是理解验收**——检验你是否真的懂了那 5 个决策。

- [ ] **G1** 为什么扣库存用同步 RPC、发货用异步消息？（决策 1）
- [ ] **G2** 主链路用 quorum 付出了哪些代价？至少说出两条。（决策 2）
- [ ] **G3** 为什么失败时必须用 `reject` 而不是 `nack`？用 `nack` 会发生什么？（决策 3）

- [ ] **G5** quorum 不支持 `x-max-priority`，VIP 订单怎么办？为什么不用 classic 换回优先级？（决策 5）

> 答不上来的，回到 [设计决策.md](./设计决策.md) 对应章节。

## 🏁 最终判定

**最低通过标准**：A + B + C + D + E + F 全部勾完，其中 **B6、D5、D6 三项手工项必须通过**。

这三项之所以设为硬性，是因为它们验证的不是"代码是否存在"，
而是**机制是否真的按预期工作过**——而它们恰好是最容易"看起来通过了"的三项：

| 项 | 容易出现的假象 |
|----|---------------|
| B6 | 用 `docker restart` 测 → 优雅关机落盘 → 假存活 |
| D5 | 用 `nack` 测 → 日志在打重试 → 实则永不进死信 |
| D6 | 队列没清干净 → 对着上一轮的残留数据下结论 |

**G 组（权衡理解）建议至少答对 4/5**再往下走——它决定你会不会把这个项目的做法
正确地迁移到下一个项目，而不会照抄参数。
