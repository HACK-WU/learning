# 反例对照：一个"能跑但很糟"的版本

> **建议阅读方式**：先别往下翻。假设你来写这个订单系统，花两分钟想想你会怎么写，
> 再来看下面这个版本——它大概率和你的第一版很像，**而它是错的**。

---

## 🔴 反例：看起来很合理的第一版

这是一个**真的能跑通**的实现。下单、扣库存、发货、发短信，功能一个不少，本地测试全绿。

```python
# ❌ 反例：bad_example.py（能跑，但生产上会出事）
import json
import pika

conn = pika.BlockingConnection(pika.ConnectionParameters('localhost', 5681,
        credentials=pika.PlainCredentials('learn', 'learn123')))
ch = conn.channel()

# 1. 队列：用默认类型（classic），什么都不配
ch.queue_declare(queue='order.work')

# 2. 发消息：不设任何属性
def place_order(order_id, sku, qty):
    ch.basic_publish(
        exchange='',
        routing_key='order.work',
        body=json.dumps({'order_id': order_id, 'sku': sku, 'qty': qty}),
    )
    print(f'订单 {order_id} 已提交')

# 3. 消费：auto_ack 最省事
def on_message(ch, method, props, body):
    data = json.loads(body)
    deduct_stock(data['sku'], data['qty'])   # 扣库存
    notify_warehouse(data['order_id'])       # 通知发货
    send_sms(data['order_id'])               # 发短信
    print(f'订单 {data["order_id"]} 处理完成')

ch.basic_consume(queue='order.work',
                 on_message_callback=on_message,
                 auto_ack=True)   # ← 自动确认，代码最简洁
ch.start_consuming()
```

**为什么它"能跑"**：单条消息、单机、网络正常、下游不超时——这个场景下它工作得完美无缺。
**这正是它危险的原因**：所有问题都只在**出事那一刻**才暴露，而那时你已经在生产环境了。

---

## ⚖️ 逐条对比：6 处致命差异

### 差异 1：`auto_ack=True` —— 一条崩溃损失的不止一条消息

| | 反例 | 正解 |
|---|---|---|
| 写法 | `auto_ack=True` | `auto_ack=False` + 业务成功后 `basic_ack` |
| 表面好处 | 代码少一行 | 代码多一行 |

**为什么糟**：`auto_ack` 下消息**投递即确认**。消费者拿到消息后，broker 立刻把它删除——
**此时业务代码可能还没开始执行**。

课 8 实测量化了这个后果：

> 投递 100 条，业务回调**只执行 1 条**就崩溃 → 队列剩余 **0 条**，丢失 100 条。
> 多出的 99 条死在 pika 的接收缓冲区里，**业务代码根本没见过它们**。

推论：**队列积压越多，一次崩溃损失越大**。这不是"可能丢一两条"，是"可能全丢"。

**更隐蔽的一层**：`prefetch` 对 `auto_ack` **完全无效**（课 6 P0 实测）。
很多人会给反例代码加上 `basic_qos(prefetch_count=1)` 以为就安全了——**没用**。
prefetch 约束的是"未确认消息数"，而 auto_ack 下永远不存在未确认态，限制无处施加。

---

### 差异 2：不开 publisher confirm —— 你根本不知道 broker 收没收到

| | 反例 | 正解 |
|---|---|---|
| 写法 | 直接 `basic_publish` | `ch.confirm_delivery()` + 处理 `NackError` |
| 表面好处 | 快（100 条 2.3ms → 开了 confirm 55.5ms，约 24 倍） | 慢，但知道结果 |

**为什么糟**：`basic_publish` 不抛异常 **不代表消息进了队列**。

- 消息不可路由（routing key 写错）→ 静默丢弃
- quorum 队列失去多数派 → **返回 NACK，而不是抛异常**（课 11 P0 实测）

第二条尤其危险：不开 confirm 时，NACK 这个信号你**完全接收不到**，
生产者以为发出去了，实际上消息从未落盘。

**代价说明**：confirm 慢 24 倍是 **pika 同步适配器**的实现特征
（`BlockingChannel.basic_publish` 逐条同步等 RTT），不是协议本身的性质。
要吞吐换异步客户端，而不是关掉 confirm。

---

### 差异 3：消息不设 `delivery_mode=2` —— 重启即丢

| | 反例 | 正解 |
|---|---|---|
| 写法 | `basic_publish(exchange, rk, body)` | 加 `properties=BasicProperties(delivery_mode=2)` |
| 表面好处 | 少写一行 | 多写一行 |

**为什么糟**：课 7 实测的三层持久化——**队列持久化 ≠ 消息持久化**。

对照实验（真实 `docker kill -s KILL` 强制宕机，不是优雅重启）：

| 配置 | 结果 |
|------|------|
| 队列 durable + `delivery_mode=2` | 消息存活 ✅ |
| 队列 durable + `delivery_mode=1` | **消息丢失** ❌ |

反例里连队列 durable 都没设（`queue_declare(queue='order.work')` 默认 `durable=False`），
是**两层都没做**。

> 补充一个 4.3 的坑：裸 `queue_declare(queue='x')` 在 4.3 上**直接报 541 并断开连接**
> （transient 非独占队列已被禁止）。所以反例代码在新版本上连跑都跑不起来。

---

### 差异 4：没有任何重试与死信 —— 失败就是消失

| | 反例 | 正解 |
|---|---|---|
| 写法 | 业务抛异常 → 消息已被 auto_ack 删除 → **没了** | reject + `x-delayed-retry-*` + `x-delivery-limit` + DLX |
| 表面好处 | 代码最简单 | 多一堆队列参数 |

**为什么糟**：反例里 `notify_warehouse()` 抛异常会怎样？

1. `auto_ack=True` → 消息早已被删除
2. 异常向上传播 → pika 打印一条日志
3. **订单永远不会被发货，且没有任何地方记录这件事**

这就是"静默失败"——系统看起来在运行，订单在丢失，没人知道。

**正解的三层兜底**（本项目实测，见 `run_retry_drill_b.py`）：

```
第 1 次失败 → reject → 退避 1.00s
第 2 次失败 → reject → 退避 2.01s
第 3 次失败 → reject → 退避 3.01s
第 4 次       → delivery-count 达到 limit → 自动转死信队列
```

死信队列里有消息是**好现象**——它证明失败有出口，而不是凭空消失。

**这里还有个 4.3 的语义陷阱**（决策 3）：必须用 `reject` 而不是 `nack`。
实测对照（100% 失败率）：

| 动作 | delivery-count | 重试间隔 | 结局 |
|------|----------------|----------|------|
| `nack(requeue=True)` | **恒为 None，不涨** | 恒定 1.04s | **无限循环，永不进死信** ⚠️ |
| `reject(requeue=True)` | 1 → 2 → 3 | 1.04 / 2.09 / 3.02s | 超限转死信 ✅ |

用 `nack` 写重试，系统**看起来在正常工作**（日志在打重试），
实际上那条坏消息会永远转下去。

### 差异 5：没有幂等 —— 至少一次语义下必然重复扣款

| | 反例 | 正解 |
|---|---|---|
| 写法 | 收到就处理 | 处理前查去重表，成功后记录 |
| 表面好处 | 无 | 多一个存储依赖 |

**为什么糟**：只要用了手动 ack（差异 1 的正解），就进入**至少一次**语义——
重复是**必然**的，不是可能的：

- 消费者处理成功但 ack 前崩溃 → 消息重投
- 网络抖动导致 ack 丢失 → 消息重投
- 生产者超时重发 → **两条独立消息**

**最危险的认知误区**：以为可以用 `redelivered` 标记识别重复。课 8 实测打脸：

> 生产侧重复（连发两条同单号）→ `redelivered` 序列是 **[False, False]**。
> broker 根本不知道这两条是同一笔业务。

`redelivered` 只能识别**消费侧**重复。**生产侧重复必须靠业务幂等键**。

反例里 `deduct_stock()` 被调用两次，就扣两次库存——这是资损，不是 bug。

---

### 差异 6：所有步骤塞进一个消费者 —— 耦合 + 无法分级

| | 反例 | 正解 |
|---|---|---|
| 写法 | 一个消费者串行做扣库存 + 发货 + 发短信 | 按步骤拆分，各自独立队列与消费者 |
| 表面好处 | 一个函数搞定，调用链清晰 | 拓扑复杂，要维护多个队列 |

**为什么糟**，三件事：

1. **失败粒度太粗**：短信网关超时 → 整个消费者抛异常 → 库存和发货被一起回滚/重投。
   已经扣成功的库存会**被重复扣**（叠加差异 5 的幂等缺失，直接资损）。
2. **无法分级**：短信丢了影响很小，库存错了是资损。
   但它们共享一个队列 → **被迫用同一种可靠性配置**。
   正解里短信用 classic（省 3.7 倍写代价），主链路用 quorum（高可用）——**按价值分级**。
3. **无法削峰**：三个步骤速度差异巨大（扣库存毫秒级、发货可能分钟级），
   挤在一个消费者里，慢步骤会堵死快步骤。

## 📊 反例 vs 正解 对照表

| 维度 | ❌ 反例 | ✅ 正解 | 出事时的差别 |
|------|---------|---------|-------------|
| 确认模式 | `auto_ack=True` | `auto_ack=False` + 手动 ack | 崩溃丢 1 条 vs **丢 100 条** |
| prefetch | 不设（且设了也无效） | `prefetch=10` | 先连上的消费者抢空队列 |
| 发布确认 | 不开 | `confirm_delivery()` | 失去多数派时**静默丢失** |
| 消息持久化 | 不设 | `delivery_mode=2` | 重启后消息全没 |
| 队列类型 | 默认 classic（单点） | 主链路 quorum | 宿主宕机 → NOT_FOUND 不可用 |
| 重试 | 无 | reject + 延迟退避 | 一次超时 = 订单永久丢失 |
| 死信 | 无 | DLX + delivery-limit | 失败消息凭空消失 |
| 幂等 | 无 | 幂等键 + 去重表 | 重复扣款（资损） |
| 步骤拆分 | 一个消费者全做 | 按步骤与 SLA 分级 | 短信超时拖垮库存 |
| 错误处理 | 异常向上抛 | 分层处理 + 兜底 | 静默失败 |

## 🎯 反例的"反面价值"

这个反例不是用来嘲笑的——**它是每个初次接触消息队列的人都会写出的代码**，
因为它的每一处简化单独看都"有道理"：

- `auto_ack=True`？反正消息处理很快，不会崩。
- 不开 confirm？本地测试从来没失败过。
- 不设持久化？我的 RabbitMQ 从来不重启。
- 不做幂等？重复是小概率事件。

**这些"有道理"的假设，全部只在"一切正常"时成立。**
消息队列的全部价值恰恰在于**处理不正常的情况**——
而反例把这部分价值全部丢掉了，只留下了复杂度。

> 💡 **一句话记住**：如果你不需要可靠性，那你根本不需要消息队列——
> 直接 HTTP 调用更简单。上 MQ 就是为了要那些"不丢不重"的保证，
> 而它们**没有一项是免费的、也没有一项是默认开启的**。
