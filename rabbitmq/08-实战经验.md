## 一、适用边界：先想清楚该不该用

工程里最贵的错误，往往不是"用错了功能"，而是**用错了工具**。
这一节的目的是让你在开始之前，就能判断"这个场景该不该上 RabbitMQ"。

### 1.1 RabbitMQ 真正擅长的四件事

| 能力 | 为什么它强 | 实测证据 |
|------|-----------|----------|
| **复杂路由** | exchange + binding 是**独立于消费者代码**的路由层。改一个 binding 就能改变消息流向，不用改任何一行业务代码 | 课 4 实测：`topic` 的 `*` / `#`、`headers` 的 `x-match`、AE 兜底、默认交换机 |
| **消息级可靠性** | 每条消息都有 ack / confirm / 重试 / 死信的**独立生命周期**，而不是"批次成功或失败" | 课 6/7/8 全套实测；实战项目 15 项自动验收 |
| **低延迟** | 消息进队即可被消费，典型亚毫秒到毫秒级 | 课 12 容量实测：1KB 消息平均 **2.19ms**、P95 **3.26ms** |
| **消息级延迟与调度** | 4.3 起 quorum 队列**原生**支持延迟重试，不需要插件 | 课 10 实测退避 3.06→6.11→9.15→12.01s 并封顶；实战项目 1.01/2.00/3.02s |

**一句话**：当你的需求是"**这条**消息必须可靠地送到**该去的地方**，并且失败要有出口"时，RabbitMQ 是对的选择。

### 1.2 四个不要上 RabbitMQ 的信号

> 这四条不是"要小心"，是**换工具**。

**信号 1：你要的是日志流 / 埋点采集，量在百万条每秒以上**

RabbitMQ 的目标场景是"可靠的业务消息"，不是"高吞吐的数据管道"。
队列是**消费后删除**的模型，扛不住也不该扛这种量。→ 用 Kafka / Pulsar。

**信号 2：你需要长期保留并反复回放历史消息**

普通队列消费即删。虽然 stream 队列可以回放（课 5 实测：三轮都能从头读到全部消息），
但它**不支持 AMQP 的 `basic.get`、不支持 TTL 与 max-length**，生态与工具链和主流 RabbitMQ 用法是两套。
如果你的核心诉求就是"历史可回放"，→ 用 Kafka 或专门的事件存储。

**信号 3：消息体经常超过 100KB**

课 12 实测最能说明问题：消息大 **1000 倍**（1KB → 1MB），条/秒只掉 **4.2 倍**（456 → 108），
但带宽涨 **242 倍**（0.45 → 107.7 MB/s）。
说明瓶颈在**每条消息的固定开销**（Raft 复制 + fsync + 网络往返），与大小几乎无关。

推论有两个，都反直觉：
- **把大消息拆碎通常更慢**——你为每条碎片多付了一次完整的固定开销。
- 超过 100KB 应走 **claim-check 模式**：消息里只放引用（对象存储的 key），数据走对象存储。

硬上限：`max_message_size` 默认 **16 MiB**（课 5 实测环境值），超限时**不入队**，以 channel 级 406 返回（连接仍存活）。

**信号 4：你要的是强一致（分布式事务）**

消息队列提供的是**最终一致**。实战项目的决策 1 已经暴露了这个边界：
扣库存成功后下单即返回成功，但发货消息可能最终进死信——
业务上必须有一个"已支付但未发货"的**对账巡检**来兜底。
这个不一致窗口**无法用消息系统本身消除**。

> 需要强一致 → 用分布式事务框架或 TCC 补偿，**不要指望 MQ**。

### 1.3 一个快速决策判据

```
问自己三个问题：
1. 这条消息丢了，会不会造成资损或用户可见的故障？
   ├─ 不会（埋点/日志/统计）→ 你可能不需要 RabbitMQ，甚至不需要 MQ
   └─ 会 → 继续
2. 处理它需要"用户立刻看到结果"吗？
   ├─ 需要（库存、支付、登录）→ 这一步走同步 RPC，不要异步化
   └─ 不需要 → 继续
3. 峰值吞吐会超过十万条每秒吗？
   ├─ 会，且允许少量丢失 → 考虑 Kafka
   └─ 不会 → RabbitMQ 是合适的选择
```

> 💡 最容易犯的错是**跳过第 2 问**：把"用户要等结果"的步骤也异步化，
> 然后被迫在前端做轮询或 WebSocket 推送。复杂度不降反升——这就是典型的"为了用 MQ 而用 MQ"。

## 二、8 个高频故障模式

> 每个模式用五段式：**现象 → 根因 → 怎么发现 → 怎么修 → 怎么防**。
> 排序按"踩中后的隐蔽程度"——越靠前越难察觉。

### 🔥 故障模式 1：用 `nack` 写重试 → 消息永远转下去，永不进死信

**严重度：★★★★★（本项目判定的头号陷阱）**

#### 现象

系统看起来完全正常：消息在被消费、日志在打"第 N 次重试"、队列深度稳定。
但**死信队列始终是空的**，那批坏消息永远不会被兜底捞出来。
直到某天有人去看队列深度，才发现有几条消息已经转了几天。

#### 根因

4.3 起 quorum 队列把"重试次数"拆成了**两个独立的计数器**：

| 计数器 | 什么时候涨 | 参与什么计算 |
|--------|-----------|-------------|
| `x-acquired-count` | **每次 requeue 都涨** | 什么都不参与（只是被取过的次数） |
| `delivery-count` | **只在"投递失败"时涨** | 延迟退避公式 + `x-delivery-limit` 死信阈值 |

而 4.3 的语义是：`nack` = "我取过，但没失败"；`reject` = "这条真的失败了"。
**只有 `reject` 会让 `delivery-count` 递增。**

于是 `nack` 的连锁后果是：计数不动 → 延迟恒为最小值 → 永远够不到 delivery-limit → 永不死信。

#### 怎么发现

跑一条 100% 失败的消息，观察**两个量**，只看一个会被骗：

| 观察量 | `nack` | `reject` |
|--------|--------|----------|
| `delivery-count` | **恒为 None** | 1 → 2 → 3 |
| 重试间隔 | **恒定 1.04s** | 1.04 / 2.09 / 3.02s |
| 最终结局 | 无限循环 ⚠️ | 超限转死信 ✅ |

> ⚠️ **只看"有没有在重试"会被骗**——`nack` 的日志和 `reject` 长得一模一样。
> 必须看**间隔是否递增**，或看死信里有没有出现 `reason=delivery_limit`。

#### 怎么修

把失败路径的 `basic_nack` 全部改成 `basic_reject(requeue=True)`。

```python
# ❌ 错：计数不动，永不进死信
ch.basic_nack(delivery_tag=tag, requeue=True)

# ✅ 对：delivery-count 递增，超限自动转死信
ch.basic_reject(delivery_tag=tag, requeue=True)
```

如果用的是 **classic 队列**，连 `reject` 也帮不了你——见故障模式 2。

#### 怎么防

1. **写进代码规范 + Code Review 清单**："失败重试用 reject，不用 nack"。一个人写错就埋一个死循环。
2. **给队列配 `x-delivery-limit` 并显式写死数值**，不要依赖默认值。
3. **监控死信队列深度**。死信长期为 0 且队列有积压，是"重试没生效"的强信号。

**唯一该用 `nack` 的场景**：你想表达"这条我暂时处理不了、请重新排队，**但不要消耗重试预算**"
（比如下游限流了）。但你必须同时准备另一条兜底路径（如消息自带过期时间），否则就是死循环。

### 🔥 故障模式 2：给 classic 队列配 `x-delivery-limit` → 声明直接崩，或配置静默失效

**严重度：★★★★☆（讲义未覆盖，本项目实测新发现）**

#### 现象

启动时直接抛异常，整个拓扑声明失败：

```
PRECONDITION_FAILED - invalid arg 'x-delivery-limit' for queue 'notify.sms'
... of queue type rabbit_classic_queue
```

#### 根因

`x-delivery-limit` 与整套 `x-delayed-retry-*`（`type` / `min` / `max`）**是 quorum 队列专属**。
逐个探测确认：

| 参数 | classic | quorum |
|------|---------|--------|
| `x-dead-letter-exchange` | ✅ 接受 | ✅ 接受 |
| `x-max-length` / `x-message-ttl` | ✅ 接受 | ✅ 接受 |
| `x-delivery-limit` | ❌ **406 拒绝** | ✅ 接受 |
| `x-delayed-retry-*` | ❌ **406 拒绝** | ✅ 接受 |

**这件事的工程含义比报错本身严重**：它意味着"选 classic 省下的资源（约 3.7 倍写吞吐、2.8-3.4 倍内存），
要用**代码复杂度**还回来"——你必须自己实现重试计数。

#### 怎么发现

部署/启动时就会炸，通常不会漏。真正的风险是**另一种失效形态**：
如果你是从老版本迁移过来的，某些客户端可能对不支持的参数**静默忽略**
（课 10 已实测过同类问题：`x-delayed-retry-type` 写成 `bogus_value` **不报错、静默失效**）。

> 判据：**不要相信"没报错"**。声明完队列后，用
> `rabbitmqctl list_queues name arguments` 回读，**确认参数真的在**。

#### 怎么修

classic 队列改走**应用层重试计数**：

```python
# classic 队列：broker 不帮你数，自己数
headers = dict(props.headers or {})
count = int(headers.get('x-app-retry-count', 0)) + 1

if count > APP_MAX_RETRY:
    ch.basic_reject(delivery_tag=tag, requeue=False)   # 超限送死信
    return

headers['x-app-retry-count'] = count
ch.basic_publish(exchange=method.exchange or '',
                 routing_key=method.routing_key,
                 body=body,
                 properties=pika.BasicProperties(
                     delivery_mode=2, headers=headers, ...))
ch.basic_ack(delivery_tag=tag)   # 旧消息确认掉，用"新消息"实现重试
```

注意这里用 **ack + 重发**而非 `requeue=True`：`requeue` 会原地插回队列，
计数写在消息头里也带不过去（broker 不会帮你保留修改后的 headers）。

#### 怎么防

1. **队列类型与重试策略绑成一个决策**，不要分开想。选 classic 就等于签下了"自己实现重试"这条附加条款。
2. 项目里把队列 arguments 收进**一个工厂函数**（实战项目的 `config.py::quorum_args()` / `classic_args()` 就是这么做的），
   让"哪类队列能配什么"在代码里被强制约束，而不是靠人记。

### 🔥 故障模式 3：`auto_ack=True` 下崩溃 → 丢的不止一条，是整批

**严重度：★★★★★（后果最严重，资损级）**

#### 现象

消费者崩了，重启后**队列是空的**。你以为只丢了正在处理那一条，实际上丢了一大批。

#### 根因

`auto_ack=True` 时，**消息投递即被 broker 删除**——此刻业务代码可能还没开始执行。
而 pika 会把 broker 一口气推过来的消息**缓存在接收缓冲区**里，再逐条交给你的回调。

课 8 的实测把这个后果量化得非常清楚：

> 投递 100 条，业务回调**只执行 1 条**就崩溃 → 队列剩余 **0 条**。
> 多出的 99 条**死在 pika 的接收缓冲区里，业务代码根本没见过它们**。

由此得到一条重要推论：

> **队列积压越多，一次崩溃损失越大。**

这不是"可能丢一两条"，是"可能全丢"。

#### 怎么发现

一个反直觉的**加重因素**，会让你的"补救措施"完全无效：

> ⚠️ **`prefetch` 对 `auto_ack` 完全无效**（课 6 P0 实测）。
> 设 `prefetch_count=1` 后发 10 条，依然被**一次全推走**。

原因：prefetch 约束的是"未确认消息数"，而 auto_ack 下投递即确认，**永远不存在未确认态**，限制无处施加。

所以判据很简单也很残酷：**只要代码里有 `auto_ack=True`，这条风险就存在，无法通过加 prefetch 缓解。**

#### 怎么修

```python
ch.basic_qos(prefetch_count=10)          # 先限流，且必须配手动 ack 才有效
ch.basic_consume(queue=Q,
                 on_message_callback=on_message,
                 auto_ack=False)         # 关掉自动确认

def on_message(ch, method, props, body):
    try:
        do_business(body)
        ch.basic_ack(delivery_tag=method.delivery_tag)   # 业务成功后才确认
    except Exception:
        ch.basic_reject(delivery_tag=method.delivery_tag, requeue=True)
```

#### 怎么防

1. **全局禁用 `auto_ack`**。把它写进代码规范，Code Review 时当红线。
2. prefetch 必须配手动 ack 才生效——这两件事是**一对**，不能只做一半。
3. 接受手动 ack 的必然结果：进入**至少一次语义**，重复是必然的 → 必须做幂等（见故障模式 5）。

### 🔥 故障模式 4：不开 publisher confirm → 消息没进去，你永远不知道

**严重度：★★★★☆（失败形态完全静默）**

#### 现象

生产者没有任何报错，`basic_publish` 正常返回。但消息**从未进入队列**。

#### 根因

`basic_publish` 不抛异常 **不代表消息进了队列**。两种典型丢失路径：

- **不可路由**：routing key 写错、没有匹配的 binding → 静默丢弃
- **quorum 失去多数派**：课 11 实测，三节点停掉两个后发布 → 返回 **NACK，而不是抛异常**

第二条尤其危险。不开 confirm 时，NACK 这个信号你**完全接收不到**——
生产者以为发出去了，实际上消息从未落盘。

#### 怎么发现

```python
ch.confirm_delivery()      # 开启 confirm
try:
    ch.basic_publish(...)
except pika.exceptions.NackError:
    # 只有开了 confirm，这里才会被触发
    ...
```

**不可路由**是另一条路，需要 `mandatory=True` + return 回调（课 9 实测这是"异常 + 回调"双路通知，
只捕获异常会拿不到退回的消息体）。

#### 怎么修

开 confirm。至于"confirm 太慢"这个反对意见——先把数据摆清楚：

> 课 9 实测：100 条持久化消息，不开 confirm **2.3ms**，开了 **55.5ms**，约 **24 倍**。

但这个"慢"是 **pika 同步适配器**的实现特征，不是协议本身的性质：
`BlockingChannel.basic_publish` 在 confirm 模式下执行 `_flush_output(..., is_ready)`，
**逐条同步等一次 RTT**（每条耗时 ÷ RTT ≈ 1.0，实测三角验证过）。

**正确应对是换异步客户端，而不是关掉 confirm。** 关掉 confirm 等于放弃可靠性这个上 MQ 的唯一理由。

#### 怎么防

1. confirm 是**默认项**不是可选项。
2. 配 `mandatory=True` + return 回调，把"不可路由"也变成可观测事件。
3. 对 confirm 超时/NACK 要有**重试或落库**策略，否则 confirm 只让你"知道"丢了，没让你"补上"。

### 🔥 故障模式 5：幂等只靠 `redelivered` → 生产侧重复完全失守

**严重度：★★★★★（资损级，且极难自查）**

#### 现象

消费者做了幂等判断，重复消息仍然被执行了两次，**扣了两次款**。

#### 根因

课 8 实测把 `redelivered` 的能力边界钉死了：

| 重复来源 | `redelivered` 序列 | 能否用 `redelivered` 识别 |
|----------|-------------------|--------------------------|
| **消费侧**（崩溃重投 / reject requeue） | `[False, True, True]` | ✅ 能 |
| **生产侧**（超时重发、连发两条同单号） | **`[False, False]`** | ❌ **不能** |

broker 根本不知道那两条是同一笔业务——在它眼里就是两条独立消息。

#### 怎么发现

手工发布两条 **同 `order_id`、不同 `message_id`** 的消息，观察业务执行次数。
执行了两次 → 说明你的幂等只挡住了消费侧重复。

> 这是幂等设计里**最容易漏的一格**，因为它需要你主动构造才会暴露，正常运行永远测不出来。
> 实战项目把它列为手工验收项 C4，就是这个原因。

#### 怎么修

幂等键必须用**业务标识**，不能用 broker 给的投递标记：

```python
def make_idempotency_key(order_id, step):
    # 业务单号 + 步骤名：不同步骤独立幂等，同一步骤多次投递命中同一把锁
    return f"{order_id}:{step}"
```

三步式去重表（实战项目 `idempotency.py` 的实现）：

| 步骤 | 动作 | 失败时 |
|------|------|--------|
| 1. 抢占 `acquire()` | 尝试插入 key | 已存在 → 说明处理过，**直接 ack 跳过** |
| 2. 业务成功 `mark_done()` | 标记完成 | — |
| 3. 业务失败 `release()` | **释放锁** | — |

> ⚠️ **第 3 步是最容易写错的地方**：失败时**必须 release**。
> 不释放的话，这条消息的重试会永远被自己的锁挡住 → **消息永久卡死，且看起来"消费成功了"**。

#### 怎么防

1. 幂等键的设计评审要过一关：**换个人看这个 key，能不能一眼说出它代表哪笔业务的哪个步骤**。
2. 去重记录要有**过期或清理策略**，否则表会无限膨胀。
3. 记住：只要用了手动 ack（故障模式 3 的正解），就进入至少一次语义，**重复是必然的，不是可能的**。

### 🔥 故障模式 6：队列 durable 了，消息还是丢了

**严重度：★★★☆☆（常见，但容易自愈式误解）**

#### 现象

`queue_declare(durable=True)` 明明写了，broker 重启后消息还是没了。

#### 根因

**队列持久化 ≠ 消息持久化。** 课 7 的真实强制宕机对照（`docker kill -s KILL`，非优雅重启）：

| 配置 | 结果 |
|------|------|
| 队列 durable + `delivery_mode=2` | 消息存活 ✅ |
| 队列 durable + `delivery_mode=1` | **消息丢失** ❌ |

精确计数佐证：`delivery_mode=2` → `messages=1 / messages_persistent=1`；
`delivery_mode=1` → `messages=1 / messages_persistent=0`。

#### 怎么发现

看 `messages_persistent` 这一列，而不是 `messages`：

```bash
rabbitmqctl list_queues name messages messages_persistent
```

> ⚠️ 取数踩坑（课 7 实测）：Management API 的单队列接口在本环境**取不到** `messages_persistent`
> （加 `?columns=` 也无效）。**用 `rabbitmqctl list_queues` 才是可靠来源。**

#### 怎么修

```python
ch.basic_publish(
    exchange=EX, routing_key=RK, body=body,
    properties=pika.BasicProperties(delivery_mode=2),   # 消息持久化
)
```

三处都要 durable：交换机、队列、消息。**缺任何一层都不成立。**

#### 怎么防

1. 把 `delivery_mode=2` 写进**生产者模板**的默认值，而不是每次发布时想起来才加。
2. 注意 4.3 的一个额外坑：裸 `queue_declare(queue='x')`（`durable=False` + 非独占）
   在 4.3 上**直接报 541 并断开整个连接**——这反而是好事，它让漏配无法悄悄通过。

### 🔥 故障模式 7：验证持久化时用了 `docker restart` → 得出与生产完全相反的结论

**严重度：★★★★☆（方法学错误，会让你自信地犯错）**

#### 现象

你做了持久化实验，三组配置**全部存活**，于是得出结论"持久化配置没问题"。
但生产上真的宕机时，消息丢了。

#### 根因

这是一个**测量方法错误**，而且有两层：

**第一层：`docker restart` 是优雅关机（SIGTERM）**，broker 退出前会把元数据全部落盘
——**连本不该存活的数据都活过了重启**。课 7 实测：连 `durable=False` 的交换机都活下来了。

**第二层（更隐蔽）：容器内 `pkill -9 -f beam.smp` 根本杀不掉**。
因为 broker 在容器内是 **PID 1，Linux 不允许 `kill -9` 杀 PID 1**，进程从未真正中断
（uptime 连续 94 秒）。你以为杀了，其实一秒都没停。

#### 怎么发现

**必须用硬校验指标**，不能凭"命令执行成功"判断：

| 校验项 | 期望 |
|--------|------|
| 容器 `StartedAt` | **发生变化** |
| `rabbitmqctl status` 的 uptime | **归零重算**（课 7 实测 125s → 12s） |

#### 怎么修

```bash
docker kill -s KILL <container>    # 强制杀死，不给落盘机会
docker start <container>
```

#### 怎么防

**把这条推广成一条通用原则**：

> **测量行为本身可能消除被测现象。**

课 7 的 fsync 窗口实验是这件事的极致体现：连做五版都测出零丢失，
最终发现——**为使测量准确而等待统计追平的 3 秒，恰好覆盖了 200ms 的落盘窗口**。

**"没测出来"不等于"不存在"。** 官方明确定性 classic 队列在发 confirm 前**不执行 fsync**，
本机因落盘太快未能稳定复现；需要强保证就选 quorum（协议层面保证确认前已 fsync 到多数派）。

同类的"测量工具污染数据"还有一次：课 8 的多线程吞吐测量因共享计数锁导致数据偏低
（4.2 倍 → 干净重测后 8.5 倍）。**测出反常识结果时，先怀疑测量工具，换独立方法交叉验证。**

### 🔥 故障模式 8：RPC 跨了信道 → 响应静默丢失，全程无任何报错

**严重度：★★★★☆（比报错更危险，因为无从查起）**

#### 现象

RPC 客户端发出请求，服务端**照常消费、照常回复**，但客户端永远收不到响应。
没有异常、没有日志、监控绿。

#### 根因

Direct Reply-To 有一条官方约束：**RPC 客户端必须用同一个连接和同一个信道**，
既从 `amq.rabbitmq.reply-to` 消费、又发布请求消息。

课 12 做了三组对照，判据是"响应是否真的到达"而**非**"有没有报错"：

| 组 | 做法 | 结果 |
|----|------|------|
| A | **跨信道**（信道 1 消费 / 信道 2 发布） | **不报错，6 秒内响应未到达** ⚠️ |
| B | 同信道，但先发布后注册 | 异步 `406 fast reply consumer does not exist` |
| C | 同信道 + 先注册后发布 | ✅ 响应到达 |

**A 组的危险性在于**：服务端照常消费、照常回复，broker 照常丢弃，**全程静默，无异常可查**。

#### 怎么发现

pika 还有一个叠加的坑：生成器式 `channel.consume()` 是**惰性**的，
只有第一次迭代（`next()`）时才真正发出 `basic.consume` 帧完成注册。
写成"先 publish 再 consume"必然掉进 B 组的 406。

正确姿势：

```python
# 单连接 + 单信道
gen = ch.consume('amq.rabbitmq.reply-to', auto_ack=True, exclusive=True)
next(gen)                      # ← 预热，让 basic.consume 帧真正发出去
ch.basic_publish(...)          # ← 注册完成后再发布
```

#### 怎么修

保证"消费"与"发布"在**同一信道**，且注册先于发布。

#### 怎么防

1. RPC 客户端封装成**一个类**，把"同信道 + next() 预热"固化在构造函数里，不给调用者犯错的空间。
2. 客户端必须有**超时**。这是所有 RPC 的兜底——没有超时，静默丢失就永远表现为"卡住"。

## 三、落地 Checklist

> 当体检表用。**打勾的依据不是"代码里写了"，而是"机制被真正触发过"**——
> 写了重试但从没见过重试发生，等于没做。

### 3.1 上线前必做（12 项）

**可靠性**

- [ ] 所有消费者 `auto_ack=False`，业务成功后才 `basic_ack`
- [ ] 所有队列 `durable=True`，所有消息 `delivery_mode=2`
- [ ] 生产者开 `confirm_delivery()`，且有 NACK / 超时的**重试或落库**策略
- [ ] 主链路队列类型为 quorum（不是 classic）
- [ ] 生产者配 `mandatory=True` + return 回调，不可路由可观测
- [ ] quorum 队列配 `x-consumer-timeout`（防"消费者卡住不 ack"；取值须大于业务最大处理耗时）

**正确性**

- [ ] 幂等键用**业务标识**（订单号 + 步骤名），**不依赖** `redelivered`
- [ ] 去重表三步齐全：acquire / mark_done / **release（失败必释放）**
- [ ] 手工验证过：同单号不同 message_id 的两条消息，业务只执行 1 次

**错误处理**

- [ ] 失败路径用 `basic_reject`，**不是** `basic_nack`
- [ ] 队列显式设置了 `x-delivery-limit`（不依赖默认值），并配了 DLX
- [ ] classic 队列已实现**应用层重试计数**（broker 不帮你数）
- [ ] 死信队列有**消费者或巡检**，不是只进不出

### 3.2 上线后必配（8 项监控）

| 监控对象 | 指标 / 手段 | 告警触发点 |
|----------|------------|-----------|
| **死信队列深度** | `rabbitmq_queue_messages_ready` | > 0 即告警（死信是"失败有出口"的证据，不为空说明有失败） |
| **队列积压** | `rabbitmq_queue_messages_ready` | 持续增长超过 N 分钟 |
| **未确认数** | `rabbitmq_queue_messages_unacked` | 长时间不降 → 消费者卡住 |
| **消费者数** | `rabbitmq_queue_consumers` | = 0 说明消费者全掉了 |
| **内存告警** | `rabbitmq_alarms_memory_used_watermark`（0/1） | = 1 |
| **磁盘告警** | `rabbitmq_alarms_free_disk_space_watermark`（0/1） | = 1 |
| **quorum 副本** | Management API 的 `online` 字段 | 在线副本 < 多数派 |
| **连接数** | `rabbitmq_connections` | 异常增长 → 连接泄漏 |

> ⚠️ **指标名版本敏感**（课 12 P0 实测）：4.3.5 的 `:15692/metrics` 端点里，
> `rabbitmq_node_mem_used` / `rabbitmq_node_mem_limit` / `rabbitmq_node_disk_free` / `rabbitmq_node_disk_free_limit`
> **全部不存在**——大量教程仍在用这些旧名，照抄会配出永远不触发的空告警。
> 真实名为 `rabbitmq_process_resident_memory_bytes` / `rabbitmq_resident_memory_limit_bytes` /
> `rabbitmq_disk_space_available_bytes` / `rabbitmq_disk_space_available_limit_bytes`，另有告警专用的 0/1 指标。

> ⚠️ **per-object metrics 保持默认关闭**：官方记录 8 万队列时会产生约 190 万条指标、
> 98 MB 响应、耗时 58 秒。仅在排查时临时打开。

### 3.3 演进时必查（4 项）

- [ ] **版本升级前**：`x-delivery-limit` 的默认值与计数语义在 4.x 内部变过（4.0 默认 20；
      4.3 起计数依据从 acquired-count 改为 delivery-count）。**不要照抄教程里的数字**，
      升级后用 `rabbitmqctl list_queues name arguments` 回读确认。
- [ ] **队列类型变更**：改类型等于改 arguments，已有队列会报 `inequivalent arg`。
      需要**新建队列 + 双写迁移**，不能原地改。
- [ ] **消费者扩容**：注意吞吐不是线性增长的。课 8 实测「4 消费者反而更慢」——
      但那次是**测量误差**（总耗时被进程启动开销主导，未跑到吞吐瓶颈），
      换来一条方法论：**测出反常识结果先怀疑测量工具**。
- [ ] **消息体变大**：超过 100KB 改走 claim-check，不要硬塞（见 1.2 信号 3）。

## 四、从课程到生产的 5 处认知落差

课程为了可教学做了简化。以下 5 处在生产里会变，**知道落差在哪，比记住课程结论更重要**。

| # | 课程里的简化 | 生产里的真实情况 |
|---|-------------|-----------------|
| 1 | 单机 / 单节点演示即可讲清机制 | 生产必须集群。集群带来多数派语义、leader 选举、副本同步——**失败形态从"报错"变成"NACK"**（课 11 实测），不开 confirm 完全感知不到 |
| 2 | 吞吐数字可以直接参考 | 所有本课程的吞吐绝对值都是**单客户端 + 跨 docker 网络**测出来的。价值在**相对趋势**（prefetch 曲线、消息大小影响），**绝对值不代表生产性能** |
| 3 | 参数配了就生效 | 存在**静默失效**：`x-delayed-retry-type` 写错枚举值不报错（课 10 实测）；classic 队列忽略 quorum 专属参数。配完必须回读验证 |
| 4 | 实验环境是干净的 | 生产有残留。实战项目演练时就遇到过：死信里混着 `reason=rejected` 的上一轮残留消息，导致对着陈旧数据下结论。**做验证前务必用专属队列名并先删除** |
| 5 | 官方客户端的行为就是标准 | **pika 是社区客户端，行为与官方客户端不同**。课 9 实测：心跳协商并非官方说的"取较小值"，而是**客户端填了值就无条件优先**（源码 `if client_value is None: server_value else: client_value`）。照抄官方客户端的文档会得出错误预期 |

> 💡 **第 5 条值得单独强调**：本课程用的是 Python + pika。
> 凡是涉及"客户端协商行为"的结论（心跳、confirm 的异步性、consume 的惰性注册），
> **换语言换客户端都要重新验证**，不要跨客户端套用。
