## 开场：最后一个问题，也是最难的一个

前面十一课，我们把 RabbitMQ 从"能发消息"一路学到了"三个节点扛住宕机"。

你已经会：声明队列、选交换机类型、开 confirm、配 prefetch、做幂等、用延迟重试、搭集群、让 leader 挂掉而消息不丢。

但现在，假设有个同事问你：

> "我们要做个实时数仓，每天几十亿条用户行为事件，还要能回放三个月前的任意一天。用 RabbitMQ 行不行？"

这个问题，前面十一课学到的所有技能都答不了。因为它的答案不是"怎么配"，而是——**不该用它**。

**"怎么用"是能力，"该不该用"是判断力。** 而判断力更难，因为它没有一个可以运行验证的确定答案，你需要在一堆各有优劣的选项之间做取舍。

本课就是来补上这块拼图的。三个部分：先看几种经典的消息**拓扑长什么样**（这是你画图时的词汇表），再横向对比**四个主流消息系统**（这是你选型时的依据），最后落到**生产上线要注意什么**（这是你交付时的清单）。

## 知识点 1：典型消息模式

### 第一幕：一个"很简单"的需求

某天，产品经理提了个需求：

> "用户下单后，要发短信、发邮件、扣库存、记积分。"

工程师 A 的代码：

```python
def create_order(order):
    save_to_db(order)          # 存订单
    send_sms(order.user)       # 发短信，耗时 200ms
    send_email(order.user)     # 发邮件，耗时 300ms
    deduct_stock(order.items)  # 扣库存，耗时 150ms
    add_points(order.user)     # 记积分，耗时 100ms
    return "下单成功"
```

总共 750ms，用户点完"提交订单"要干等近一秒。更糟的是：如果发邮件那步超时了，整个下单流程失败——**订单已经存了，但用户看到"下单失败"**。

于是工程师 A 引入了消息队列：

```python
def create_order(order):
    save_to_db(order)
    publish("order.created", order)   # 只发一条消息，5ms
    return "下单成功"
```

四个下游服务各自订阅 **order.created**，自己做自己的事。响应时间从 750ms 降到 5ms。

**但问题来了**：四个服务都要收到这条消息吗？还是只有一个服务处理？如果需要拿到处理结果呢？

这三个问题，对应三种完全不同的拓扑。选错了，系统根本跑不通。

### 三种拓扑的本质区别

一句话区分：

| 拓扑 | 一条消息被处理几次 | 典型场景 |
|---|---|---|
| **工作队列** | **恰好 1 次** | 任务分发、削峰 |
| **发布订阅** | **N 次**（N = 订阅者数） | 事件广播、通知 |
| **RPC** | 1 次 + 1 个**响应** | 需要拿到结果 |

差别看似简单，但在代码上的体现完全不同。

### 工作队列：竞争消费

```
生产者 ──► [ 队列 task_queue ] ──┬──► worker-1
                                  ├──► worker-2
                                  └──► worker-3
                        每条消息只被【一个】worker 拿到
```

多个消费者**抢**同一个队列。一条消息被谁拿到是不确定的，但**一定只有一个**拿到。

实测（`l12-message-patterns.py`，12 条任务、3 个 worker、速度故意不同）：

```
| worker | 处理耗时/条 | 处理条数 |
|--------|-------------|----------|
| worker-1 | 0.30s | 2 |
| worker-2 | 0.15s | 3 |
| worker-3 | 0.05s | 7 |

合计处理：12 条（原始 12 条）
✅ 无重复、无丢失 —— 每条消息只被【一个】worker 处理
队列残留：无 ✅
```

注意这个分配：**快的 worker 拿得多**（7 : 3 : 2）。这正是工作队列想要的效果——能者多劳。

> ⚠️ 这个"能者多劳"有个前提：**prefetch 必须设置为有限值**（课 6 讲过）。
> 如果 prefetch=0（不限），broker 会把消息一次性全推给第一个连上来的消费者，
> 快的 worker 可能反而拿不到活。课 6 实测过这个陷阱。

**适用场景**：耗时任务分发（图片处理、视频转码）、流量削峰、需要横向扩容消费者的场景。

### 发布订阅：广播

```
                             ┌──► [ sms 队列 ]   ──► 短信服务
生产者 ──► [ fanout 交换机 ] ├──► [ email 队列 ] ──► 邮件服务
                             └──► [ push 队列 ]  ──► 推送服务
                       一条消息，三个队列【各收一份】
```

实测：

```
  | 订阅队列 | 收到条数 | 内容 |
  |----------|----------|------|
  | l12.sub.sms | 3 | ['news-0', 'news-1', 'news-2'] |
  | l12.sub.email | 3 | ['news-0', 'news-1', 'news-2'] |
  | l12.sub.push | 3 | ['news-0', 'news-1', 'news-2'] |

✅ 三个订阅队列各收到完整的 3 条 —— 广播，不是竞争
   与工作队列的关键差异：这里每条消息被处理了 3 次（每个订阅者一次）
```

回到开场那个需求——**"下单后要发短信、发邮件、扣库存、记积分"就是发布订阅**。四个服务各收一份，互不干扰。

关键实现细节：`fanout` 交换机**忽略 routing_key**。实测时我传的是空字符串，照样三个队列都收到。

**适用场景**：事件通知、数据同步、一个动作触发多个下游。

### RPC：要拿结果

工作队列和发布订阅都是"发出去就不管了"（fire and forget）。但有些场景你需要**等结果**：

- 调用一个耗时计算，要拿返回值
- 查询另一个服务的数据
- 需要确认某个操作是否成功

RPC 的做法：

```
客户端 ──► [ rpc_queue ] ──► 服务端
   ▲                            │
   └──── 响应（带 correlation_id）┘
```

关键在于 **`correlation_id`**：客户端给每个请求生成唯一 ID，服务端处理完把**同一个 ID** 放回响应里。客户端靠它把响应和请求对上号——因为响应的到达顺序未必等于请求的发送顺序。

而响应发到哪儿，有两种做法。

#### 方案 A：Direct Reply-To（伪队列）

AMQP 0-9-1 有个巧妙设计：`reply_to = "amq.rabbitmq.reply-to"`。

这是个**伪队列**——不需要声明、不占 broker 资源，broker 直接把响应送回**发起请求的那条连接**。

听起来很省，但它有三条硬约束。前两条我一开始就撞上了，第三条是**官方文档里写着、但我一开始漏看了**的那一条，也是最关键的一条。

**约束 ①：伪队列绑死连接**

```
约束 ①：在【另一个连接】上访问伪队列 'amq.rabbitmq.reply-to'
  结果：❌ (404, "NOT_FOUND - no queue 'amq.rabbitmq.reply-to' in vhost '/'")
  → 伪队列【绑死连接】，其他连接看不见它
```

**约束 ②：必须有活跃的响应消费者**

否则服务端想回复时，会报：

```
(406, 'PRECONDITION_FAILED - fast reply consumer does not exist')
```

这个错误我在实验中遇到过两次——**它是异步返回的**，发布时不一定立刻抛异常，而是随后把 channel 关掉。排查时容易懵。

**约束 ③（最关键）：消费与发布必须在【同一条信道】**

这条来自官方文档的 Caveats 一节，原文大意是：RPC 客户端必须用**同一个连接和同一个信道**，
既从 `amq.rabbitmq.reply-to` 消费、又发布请求消息。

我一开始没注意这句，把"发请求"和"收响应"放在了两个信道上，结果——

> **没有任何报错，但响应永远收不到。**

这比报错更危险。我做了三组对照才把这件事彻底钉死（判据是"响应是否真的到达"，不是"有没有报错"）：

| 用法 | 是否报错 | 响应是否到达 |
|------|----------|--------------|
| A 跨信道（消费在 A、发布在 B） | **不报错** | ❌ **收不到（静默丢失）** |
| B 同信道，但先发布后注册消费者 | 异步 406 | ❌ 收不到 |
| C **同信道 + 先注册消费者后发布** | 无 | ✅ **收到** |

三组的结论：

- **跨信道是最阴的一种失败**——服务端照常消费、照常回复，broker 照常丢弃，全程静默。
  你会看到请求被消费了、服务端日志也打了，但客户端永远等不到响应，而且**没有任何异常可查**。
- **顺序错（先发后注册）至少还有 406** 能指路。
- 只有"同信道 + 先注册"才成立。

> ⚠️ 还有个 pika 特有的坑：生成器式 `consume()` 是**惰性**的，
> 必须**先迭代一次**（`next(...)`）让 `basic.consume` 帧真正发出去、完成消费者注册，
> 再发布请求。写成"先 publish 再 consume"就掉进上表的 B 组。

跑通之后，实测结果（4 个 fib 请求，独立进程的服务端 + 单线程客户端）：

```
  | 请求 | 期望 | 实际响应 |
  |------|------|----------|
  | fib(5) | 5 | 5 ✅ |
  | fib(10) | 55 | 55 ✅ |
  | fib(15) | 610 | 610 ✅ |
  | fib(20) | 6765 | 6765 ✅ |

  正确 4/4，耗时 0.01s
  ✅ 方案 A 完整往返成功
```

能跑通的最小骨架（注意信道只建**一个**）：

```python
conn = pika.BlockingConnection(...)
ch = conn.channel()                       # ← 全程只有这一个信道

# 1) 先注册：next() 触发真正的 basic.consume 帧
try:
    next(ch.consume('amq.rabbitmq.reply-to', auto_ack=True,
                    inactivity_timeout=0.1))
except StopIteration:
    pass

# 2) 再发布：同一条信道
ch.basic_publish(exchange='', routing_key=RPC_Q, body=str(n).encode(),
                 properties=pika.BasicProperties(
                     reply_to='amq.rabbitmq.reply-to',
                     correlation_id=cid))

# 3) 收响应：还是同一条信道
for method, props, body in ch.consume('amq.rabbitmq.reply-to',
                                      inactivity_timeout=15, auto_ack=True):
    if method is None:
        break
    ...
```

#### 方案 B：普通回调队列

客户端声明一个 `exclusive` 临时队列，把队列名放进 `reply_to`。

```python
qd = cb_ch.queue_declare(queue='', exclusive=True)
callback_queue = qd.method.queue      # 如 amq.gen-9fLshYUUx...
# 把 callback_queue 放进 reply_to
```

`exclusive=True` 意味着：连接一断，队列自动删除，不污染 broker。

实测（4 个 fib 请求）：

```
  | 请求 | 期望 | 实际响应 |
  |------|------|----------|
  | fib(5) | 5 | 5 ✅ |
  | fib(10) | 55 | 55 ✅ |
  | fib(15) | 610 | 610 ✅ |
  | fib(20) | 6765 | 6765 ✅ |

  正确 4/4，耗时 0.01s
  ✅ 方案 B 完整往返成功
```

#### 两种方案怎么选

| 维度 | Direct Reply-To | 普通回调队列 |
|------|-----------------|--------------|
| 是否要声明队列 | 否（伪队列） | 是（exclusive） |
| broker 资源占用 | 极低 | 每客户端一个临时队列 |
| 是否绑死连接 | **是（绑死）** | 否 |
| 信道要求 | **必须同一条信道**（跨信道静默丢失） | 无此要求 |
| 连接断开影响 | **在途响应丢失** | 队列随之删除，需重建 |
| 跨进程/跨服务中转 | ❌ 不行 | ✅ 可以 |
| 排错难度 | 高（跨信道时**不报错**） | 低 |
| 本环境完整往返 | ✅ 成功（4/4，0.01s） | ✅ 成功（4/4，0.01s） |

选择建议：

- **短连接、同进程、极致轻量、调用方自己收响应** → Direct Reply-To
- **跨服务中转、长任务、连接可能重连、希望出错时有明确信号** → 普通回调队列更稳

> 💡 **一条实操建议**：Direct Reply-To 的省，省在"不用为每个请求建临时队列"；
> 但它把"同信道"变成了隐形契约。一旦你的客户端做了连接池化、或者把发布与消费拆到不同模块
> （很常见的重构），它就会以**完全静默**的方式失效。
> 团队里若不能保证这条约束被长期遵守，**默认选普通回调队列**——慢一点，但出错时看得见。

#### RPC 的适用边界

能用 RPC，不代表该用 RPC。

**RPC 的隐性问题**：它把异步的消息系统当同步调用用了。调用方要等，就会有一堆超时、重试、雪崩的问题。

更本质地说：**如果你需要一个结果才能继续，往往说明这两件事不该解耦。**

经验判断：

- 需要结果才能继续，且耗时 < 100ms → **直接 HTTP 调用**，别绕消息队列
- 耗时较长但不需要立刻拿结果 → **工作队列 + 回调/状态查询**，别干等
- 确实要同步等、且必须走 MQ → RPC 可以，但**必须设超时**

### 事件驱动的边界

最后补一个容易被忽略的点：**不是所有"发消息"都叫事件驱动**。

真正的事件驱动，事件本身应该是**已成事实**的、不可变的历史：

| 好的事件 | 不好的"事件" |
|---|---|
| `OrderCreated`（订单已创建） | `CreateOrder`（去创建订单） |
| `PaymentReceived`（已收款） | `ProcessPayment`（去处理支付） |
| `UserRegistered`（已注册） | `RegisterUser`（去注册） |

区别：前者是**通知**（"我这儿发生了一件事，你爱怎么处理怎么处理"），后者是**命令**（"你去做这件事"）。

用消息发命令，等于把消息队列当成异步 RPC 用——你会开始关心"谁去执行""失败了怎么办""执行完了怎么告诉我"，复杂度陡增。

> **一句话记住**：事件是**通知**（已发生），命令是**指令**（要你做）。消息队列适合传通知。

## 知识点 2：选型对比

### 第二幕：四个都"能用"的选择

回到开场那个问题：几十亿条/天的用户行为事件，还要能回放三个月。

RabbitMQ 能做吗？技术上能——用 stream 队列，消息可以重复读。

**但这是它的主场吗？**

先看四个选手各自的身世和性格。

> 以下版本信息核查于 2026-09。

### 四位选手

#### RabbitMQ（本课程主角）

- **当前版本**：4.3.5（4.3 系列于 2026-04-23 发布）
- **出身**：2007 年，最初为金融系统做可靠消息投递
- **核心设计**：**智能 broker + 哑消费者**——broker 负责路由、确认、重试、死信
- **强项**：路由灵活（direct/topic/fanout/headers 四种交换机）、投递语义强
- **⚠️ 支持周期**：**4.3 社区支持 2026-11-30 结束**（核查于 2026-09，距今约 3 个月），商业支持至 2028-04-30

#### Kafka

- **当前版本**：4.3（2026-05-20）；4.2 于 2026-02-17 发布
- **出身**：LinkedIn 内部，为日志聚合而生
- **核心设计**：**分布式提交日志**——消息就是日志，可重复读，按 offset 定位
- **4.0 的重大变化**：**ZooKeeper 被彻底移除**，KRaft 成为唯一模式（核查于 2026-09）
- **4.2 的新变化**：KIP-932「Queues for Kafka」（Share Groups）**正式 GA**

#### RocketMQ

- **当前版本**：5.5.0（2026-04-10）；5.5.1 于 2026-08-20 进入投票
- **出身**：阿里巴巴，为双十一的万亿级流量而生
- **核心设计**：兼具队列与日志特性，事务消息是招牌
- **5.x 架构**：存算分离 + 无状态 Proxy，支持 gRPC/MQTT/AMQP/HTTP 多协议
- **5.5 新特性**：面向 AI 场景的 **LiteTopic**（百万级轻量会话通道）

#### Redis Stream

- **当前版本**：Redis 8.8（2026-06 发布），Stream 自 Redis 5.0（2018-10）引入
- **核心设计**：Redis 内存数据结构之一，append-only 日志 + 消费组
- **近年演进**：8.2 加 XACKDEL/XDELEX；8.6 加**幂等生产**（IDMP）；8.8 加 **XNACK**
- **强项**：**亚毫秒延迟**，且你大概率已经有 Redis 了

### 一张决策表

| 维度 | RabbitMQ | Kafka | RocketMQ | Redis Stream |
|---|---|---|---|---|
| **核心模型** | 队列（消费即删） | 日志（可重复读） | 队列 + 日志 | 内存日志 |
| **单机吞吐** | ~5 万/秒（quorum） | **百万级/秒** | **十万~百万/秒** | 十万级/秒 |
| **延迟** | 毫秒级 | 毫秒~十毫秒 | 毫秒级 | **亚毫秒** |
| **路由能力** | **最强**（4 种交换机 + 绑定） | 弱（按 topic 分区） | 中（tag 过滤） | 弱 |
| **消息回放** | stream 类型支持 | **原生支持** | 支持 | 支持 |
| **消息保留** | 消费后删除 | **按时间/大小保留** | 按时间保留 | 需手动裁剪 |
| **事务消息** | 弱 | 支持 | **强（两阶段提交）** | 无 |
| **运维复杂度** | 中 | **高** | 中高 | **低**（已有 Redis 时） |
| **内存/成本** | 中 | 高（要堆机器） | 中高 | **受内存容量限制** |

### 怎么读这张表

不要找"哪个最好"，要找**哪个在你的约束下最合适**。三个最关键的判断维度：

#### 维度 1：消息是"任务"还是"事实"？

| 你的消息是 | 选 |
|---|---|
| **任务**（处理完就销毁：发短信、生成报表） | RabbitMQ |
| **事实**（要留存、要回放：用户行为、交易流水） | Kafka |

这是最根本的分界线。RabbitMQ 的队列语义是"消费即删"；Kafka 的日志语义是"留存可重放"。用错了，后面全是别扭。

#### 维度 2：需要多复杂的路由？

RabbitMQ 的交换机是**独门绝技**：topic 交换机支持 `order.*.created` 这类多级通配，headers 交换机能按消息头任意匹配。

Kafka 只有 topic + partition，要做复杂路由得自己写流处理。

**如果你的核心需求是"一条消息要按规则送到不同的地方"，RabbitMQ 优势明显。**

#### 维度 3：数据量和团队

| 情况 | 建议 |
|---|---|
| 日消息量 < 千万级 | 四个都能扛，选团队最熟的 |
| 日消息量 > 十亿级 | Kafka 或 RocketMQ |
| 团队没有专职运维 | Redis Stream（若已有 Redis）或 RabbitMQ |
| 团队有大数据栈（Flink/Spark） | Kafka（生态天然衔接） |
| 需要事务消息（金融级） | RocketMQ |
| 已在用阿里云 | RocketMQ（阿里云托管成熟） |

### 回答开场的问题

> "实时数仓，每天几十亿条用户行为事件，要能回放三个月前的任意一天。用 RabbitMQ 行不行？"

**不行。** 三个理由：

1. **量级**：几十亿/天 ≈ 3 万+/秒 持续写入。RabbitMQ 的 quorum 队列扛得住但吃力，且成本远高于 Kafka
2. **回放**：这是决定性理由。要回放三个月前的某一天，需要**长期留存 + 按 offset 任意定位**——这是 Kafka 日志模型的核心能力，RabbitMQ 的队列模型根本不是为这个设计的
3. **生态**：实时数仓要接 Flink/Spark，Kafka 是这些框架的一等公民

**这个场景该用 Kafka。**

但反过来，如果需求是"订单创建后触发发短信、发邮件、扣库存"——每秒几百单，路由规则复杂——那 Kafka 是过度设计，**RabbitMQ 更合适**。

### 一个重要提醒：别抄网上的性能数字

你在各种对比文章里看到的"Kafka 百万 TPS""RabbitMQ 5 万 TPS"，**几乎都不可直接比较**，因为：

- 消息大小不同（1KB vs 100B 差十倍吞吐）
- 持久化配置不同（fsync 与否差一个数量级）
- 客户端数量不同（单客户端 vs 100 并发）
- 队列类型不同（同一篇 RabbitMQ 评测，classic / quorum / stream 能差几十倍）

本课的实测就是个例子——下表是本环境（单客户端、WSL/Windows、跨 docker 网络）的数据：

| 消息大小 | 吞吐（条/秒） |
|----------|--------------|
| 1 KB | 456 |
| 10 KB | 403 |
| 100 KB | 330 |
| 1 MB | 108 |

**456 条/秒**——和网上常说的"几万 TPS"差了两个数量级。因为这是**单客户端 + quorum 队列 + publisher confirms + 跨 docker 网络**的组合，每一条消息都要等三节点 Raft 确认。

这不是 RabbitMQ 慢，是**评测口径不同**。

> **一句话记住**：性能数字必须连同测试条件一起看。脱离条件比数字，得出的一定是错误结论。

## 知识点 3：生产落地清单

### 第三幕：上线前一天

功能都测通了，压测也过了。现在要上生产，你会担心什么？

有经验的工程师担心的不是"功能对不对"，而是：

- 磁盘会不会满？
- 出问题了怎么知道？
- 半夜挂了怎么办？

这部分就是把这些担心变成一张可勾的清单。

### 容量规划

#### 先测，再估

容量规划最大的错误是"拍脑袋"。正确做法是**先测出你自己的基线**，再按业务量推算。

本课实测的消息大小 vs 吞吐（三节点集群、quorum 队列、publisher confirms、单客户端）：

| 消息大小 | 吞吐（条/秒） | 带宽（MB/s） | 平均延迟（ms） | P95（ms） |
|----------|--------------|--------------|----------------|-----------|
| 1 KB | 456.1 | 0.45 | 2.19 | 3.26 |
| 10 KB | 402.6 | 3.93 | 2.48 | 3.48 |
| 100 KB | 329.7 | 32.19 | 3.03 | 4.24 |
| 1 MB | 107.7 | 107.70 | 9.28 | 13.42 |

#### 这张表怎么读

关键在下面这张相对值表：

| 消息大小 | 条/秒 相对值 | 带宽 相对值 |
|----------|-------------|-------------|
| 1 KB | 1.00x | 1.00x |
| 10 KB | 1.13x | 8.83x |
| 100 KB | 1.38x | 72.29x |
| 1 MB | 4.23x | 241.83x |

**消息大了 1000 倍，条/秒只掉了 4.2 倍，带宽却涨了 242 倍。**

这说明：**瓶颈不在字节数，而在每条消息的固定开销**——Raft 复制到三个节点、每次 fsync、每帧的网络往返。这些开销与消息大小基本无关。

由此得出两条工程结论：

1. **消息别太大**：超过 100KB 就该考虑 **claim-check** 模式——大对象放对象存储（S3/COS），消息里只传引用（URL/key）
2. **但也别为了省带宽把消息切得太碎**：攒批（batching）能显著降低每条的固定开销

#### 磁盘怎么估

三个要点：

- **消息会占磁盘直到被消费**。消费者挂了，消息就一直堆着
- **内存高水位**触发后，broker 会阻塞生产者（课 10 讲过）
  - ⚠️ 这个默认值**随版本变过**：3.x 是 **0.4**，**4.x 起改为 0.6**
  - 本环境实测：`rabbitmqctl environment` → `vm_memory_high_watermark, 0.6`
  - 网上大量教程仍写 0.4，直接抄会配错
- 经验值：按**峰值消息量 × 消息大小 × 预估堆积时长**估，再**乘 3 留余量**

#### 三个必须提前定的数

| 参数 | 建议 | 理由 |
|---|---|---|
| queue 类型 | 需可靠 → `quorum` | classic 不复制，宿主宕机即不可用（课 11 实测） |
| 副本数 | 3 或 5（奇数） | 偶数节点容忍故障数为 0~1，性价比低 |
| `x-max-length` | 建议设置 | 防止消费者挂掉后无限堆积拖垮 broker |

### 监控指标与告警

RabbitMQ 自带 Prometheus 端点（默认 **15692** 端口），Grafana 官方有现成看板。

#### 必看的六类指标

> 下面的指标名**不是抄来的**，是在本环境（RabbitMQ 4.3.5）真实抓取 `:15692/metrics` 核对过的。
> 你在网上常见到的 `rabbitmq_node_mem_used` / `rabbitmq_node_disk_free` 是**老版本的名字**，
> 4.3 的端点里已经不存在——照抄会配出永远不报警的告警规则。

| 类别 | 关键指标 | 含义 | 告警建议 |
|---|---|---|---|
| **队列深度** | `rabbitmq_queue_messages_ready` | 待投递消息数 | 持续上涨 → 消费者跟不上 |
| **消费者** | `rabbitmq_queue_consumers` | 队列上的消费者数 | 掉到 0 → 消费者全挂 |
| **未确认数** | `rabbitmq_queue_messages_unacked` | 已投递未确认 | 持续高位 → 消费者卡住 |
| **内存** | `rabbitmq_process_resident_memory_bytes` / `rabbitmq_resident_memory_limit_bytes` | 已用 / 高水位 | 比值 > 0.7 → 快到高水位了 |
| **磁盘** | `rabbitmq_disk_space_available_bytes` / `rabbitmq_disk_space_available_limit_bytes` | 剩余 / 低水位 | 接近 limit → 危险 |
| **消息速率** | `rabbitmq_channel_messages_published_total`、`rabbitmq_queue_messages_delivered_total`、`rabbitmq_queue_messages_acked_total` | 发布/投递/确认累计 | 速率突然归零 → 链路断了 |

还有两个**告警专用**指标，直接就是 0/1，比自己算比值省事：

| 指标 | 含义 |
|---|---|
| `rabbitmq_alarms_memory_used_watermark` | 内存告警是否生效（1=生效） |
| `rabbitmq_alarms_free_disk_space_watermark` | 磁盘告警是否生效（1=生效） |

> 💡 一点提醒：默认端点只暴露**聚合**指标。要拿到**按队列**的明细，需要开
> `prometheus.return_per_object_metrics = true`——官方文档明确说这在队列多时开销极大
> （有 8 万队列产生 190 万条指标、98 MB 响应、耗时 58 秒的实测记录），
> 生产环境请保持默认关闭，只在排查时临时打开。

#### 最重要的一条告警

**队列深度持续上涨**是所有故障里最常见的早期信号。

它不紧急，但它是几乎所有严重故障的前兆——消费者慢了、消费者挂了、下游卡了，都会先表现为队列变长。

**在它变成"磁盘告警 → 生产者被阻塞"之前处理掉，是性价比最高的运维动作。**

#### 别忘了监控"消息去哪了"

还有一类指标容易被忽略：

- **死信队列深度**：> 0 就值得看一眼，说明有消息在反复失败
- **未确认消息的年龄**：不是数量，是**最老的那条 unacked 多久了**——比数量更能反映真实卡顿

### 常见坑 Top 8

按"踩中概率 × 后果严重度"排序，每条都回扣本课程的课时。

| # | 坑 | 后果 | 怎么避 | 回扣 |
|---|---|---|---|---|
| 1 | **没开 publisher confirms** | 消息静默丢失，且你不知道 | 必须开。课 11 实测：失去多数派时失败形态是 **NACK**，不开 confirm 完全感知不到 | 课 6、课 11 |
| 2 | **auto_ack=True** | 消费者崩了消息就没了 | 全程手动 ack | 课 6 |
| 3 | **prefetch=0** | 消息全推给一个消费者，其余空转 | 设有限值（10~100 起步） | 课 6 |
| 4 | **以为 classic 队列有高可用** | 宿主节点宕机 = 队列不可用 | 4.0 起镜像队列已移除，需要高可用就用 **quorum** | 课 11 |
| 5 | **连接不断线重连** | 网络抖动后永久卡死 | 心跳 + 自动重连（课 9 模板） | 课 9 |
| 6 | **消费者不幂等** | 重复消费导致数据错乱 | 至少一次投递是常态，必须幂等 | 课 8 |
| 7 | **消息体塞大对象** | 吞吐暴跌、内存爆 | > 100KB 走 claim-check | 本课实测 |
| 8 | **偶数个节点** | 容忍故障数为 0，白花钱 | 3 或 5 个节点 | 课 11 |

### 该不该用 RabbitMQ：判断清单

最后，把"该不该用"变成可勾选的条件。

#### ✅ 适合用 RabbitMQ

满足 **3 条以上**就很合适：

- [ ] 需要**复杂路由**（按规则把消息送到不同队列）
- [ ] 消息是**任务**（处理完即销毁），不需要长期留存
- [ ] 需要**强投递保证** + 灵活的确认/重试/死信
- [ ] 需要**优先级队列**或**延迟消息**
- [ ] 吞吐需求在**每秒几万条以内**
- [ ] 团队规模小，**没有专职中间件运维**
- [ ] 需要多协议（AMQP / MQTT / STOMP）接入

#### ❌ 不该用 RabbitMQ

命中 **任意 1 条**就该重新考虑：

- [ ] 需要**回放历史消息**（这是 Kafka 的主场）
- [ ] 日消息量**超过十亿级**
- [ ] 需要**长期留存**消息（数月以上）
- [ ] 核心需求是**流处理**（要接 Flink/Spark 做实时计算）
- [ ] 需要**严格顺序**且吞吐要求高（Kafka 的分区顺序更合适）

#### 一个务实的提醒

> ⚠️ **RabbitMQ 4.3 的社区支持将于 2026-11-30 结束**（核查于 2026-09）。
>
> 如果你准备在生产上新部署 RabbitMQ，要清楚这一点：
> - 4.3 是当前的稳定系列，但社区支持窗口只剩约 3 个月
> - 商业支持（Tanzu RabbitMQ）至 2028-04-30
> - 这意味着：**新项目要么规划好升级节奏，要么考虑商业支持**
>
> 这不是"别用 RabbitMQ"的理由——它是成熟稳定的软件。
> 但"上线前不看支持周期"是真实的风险。

### 上线检查清单

投产前，逐项确认：

**可靠性**
- [ ] 队列类型：需要高可用的都是 `quorum`
- [ ] `delivery_mode=2`（持久化）
- [ ] 生产者开了 `confirm_delivery()` 并**处理 NACK**
- [ ] 消费者手动 ack + 有限 prefetch
- [ ] 配了死信交换机（DLX）
- [ ] 消费者逻辑幂等

**高可用**
- [ ] 集群节点数为**奇数**（3 或 5）
- [ ] 多数派可用性有告警
- [ ] 队列副本数符合预期

**可观测**
- [ ] Prometheus 端点已采集（:15692）
- [ ] 队列深度、消费者数、内存、磁盘四类告警已配
- [ ] 死信队列深度有告警

**容量**
- [ ] 已用**自己的消息大小**测过吞吐基线
- [ ] 磁盘按"峰值 × 堆积时长 × 3"预留
- [ ] 设置了 `x-max-length` 防止无限堆积

**运维**
- [ ] 有备份与恢复演练记录
- [ ] 知道怎么优雅关闭消费者（课 9）
- [ ] 版本支持周期在可控范围内

## 本课要点速查卡

| 主题 | 结论 |
|---|---|
| **工作队列** | 一条消息只被 1 个消费者处理；实测 12 条分给 3 个 worker，快的拿得多（7:3:2） |
| 工作队列前提 | prefetch 必须有限，否则消息全推给第一个连上的消费者（课 6） |
| **发布订阅** | fanout 广播，忽略 routing_key；实测 3 个订阅队列各收到完整 3 条 |
| **RPC 配对** | 靠 `correlation_id`，响应顺序未必等于请求顺序 |
| Direct Reply-To | 伪队列免声明，但**绑死连接**（实测另一连接 404 no queue） |
| Direct Reply-To 约束 | 无活跃消费者 → 异步 `406 fast reply consumer does not exist` |
| **Direct Reply-To 最关键约束** | 消费与发布必须**同一条信道**；跨信道**不报错、响应静默丢失** |
| 回调队列方案 | exclusive 临时队列；实测 4/4 往返成功，耗时 0.01s |
| 两种回调方案 | 两者都跑通（各 4/4）；跨服务/需重连 → 选普通回调队列，出错看得见 |
| RPC 边界 | 需要结果才能继续 → 往往说明不该解耦；< 100ms 直接 HTTP |
| 事件 vs 命令 | 事件是通知（OrderCreated），命令是指令（CreateOrder）；MQ 适合传通知 |
| **RabbitMQ 4.3** | 2026-04-23 发布，**社区支持 2026-11-30 结束**（核查于 2026-09） |
| **Kafka** | 4.3（2026-05）；4.0 移除 ZooKeeper，KRaft 唯一；4.2 起 Queues 特性 GA |
| **RocketMQ** | 5.5.0（2026-04）；5.x 存算分离；5.5 加 LiteTopic（AI 场景） |
| **Redis Stream** | Redis 8.8（2026-06）；8.6 幂等生产，8.8 XNACK；亚毫秒延迟 |
| 选型第一问 | 消息是**任务**（消费即删）还是**事实**（要回放）？任务→RabbitMQ，事实→Kafka |
| 路由能力 | RabbitMQ 最强（4 种交换机）；Kafka 只有 topic+partition |
| **消息大小实测** | 1KB→456 条/秒；1MB→108 条/秒（条/秒只掉 4.2x，带宽涨 242x） |
| 容量结论 | 瓶颈在每条消息的**固定开销**（Raft 复制+fsync），不在字节数 |
| 大消息方案 | > 100KB 用 claim-check：对象放 S3/COS，消息只传引用 |
| 性能数字 | 必须连同测试条件看；本课单客户端+quorum+confirm 只有 456 条/秒 |
| 监控必看 | 队列深度（最重要）、消费者数、unacked、内存、磁盘、速率 |
| **监控指标名** | 4.3 端点用 `rabbitmq_process_resident_memory_bytes` / `rabbitmq_disk_space_available_bytes`；老教程的 `rabbitmq_node_mem_used` / `rabbitmq_node_disk_free` **已不存在** |
| 内存高水位 | 4.x 默认 **0.6**（3.x 是 0.4）；本环境实测 0.6，抄老教程会配错 |
| 告警专用指标 | `rabbitmq_alarms_memory_used_watermark`、`rabbitmq_alarms_free_disk_space_watermark`（直接是 0/1） |
| 最重要的告警 | **队列深度持续上涨**——几乎所有严重故障的前兆 |
| 常见坑 No.1 | 没开 publisher confirms（失去多数派时是 NACK，不开完全感知不到） |
| 不该用 RabbitMQ | 需要回放历史 / 日超十亿级 / 长期留存 / 流处理 / 严格顺序+高吞吐 |

## 常见误区

| # | 误区 | 真相 |
|---|------|------|
| 1 | "工作队列会自动平均分给所有消费者" | 是**能者多劳**（快的拿得多），不是均分；且前提是 prefetch 有限 |
| 2 | "发布订阅和工作队列差不多，都是多个消费者" | 工作队列每条处理 **1 次**，发布订阅处理 **N 次**（N=订阅者数） |
| 3 | "RPC 就是消息队列版的 HTTP 调用" | MQ 的 RPC 要自己处理超时、重试、correlation_id 配对；< 100ms 直接用 HTTP 更好 |
| 4 | "Direct Reply-To 免声明，肯定更好" | 它**绑死连接**、且必须**同一条信道**；跨信道时**不报错、响应静默丢失**，比报错更难查 |
| 5 | "有了 correlation_id 就不用管顺序了" | correlation_id 正是为了解决"响应顺序 ≠ 请求顺序" |
| 6 | "Kafka 吞吐高，所以都该用 Kafka" | 做任务分发时 Kafka 的消费者模型更别扭，且路由能力弱得多 |
| 7 | "看到'百万 TPS'就知道该选谁" | 脱离测试条件的性能数字没有可比性（本课同环境实测仅 456 条/秒） |
| 8 | "消息越大越慢，所以要尽量切小" | 实测：消息大 1000 倍，条/秒只掉 4.2 倍——瓶颈是固定开销，盲目切碎反而增加条数 |
| 9 | "配好监控就高枕无忧了" | **队列深度持续上涨**才是关键信号，要在它变成磁盘告警前处理 |
| 10 | "RabbitMQ 是老牌软件，随便用没问题" | 4.3 社区支持 **2026-11-30** 结束，新部署要规划升级或考虑商业支持 |

## 🧪 小测

### Q1（单选）

你的团队要做一个"订单创建后触发多个动作"的功能：发短信、发邮件、扣库存、记积分。每个动作由独立服务处理，且**每个服务都要收到通知**。应该用哪种拓扑？

A 工作队列（一个队列 + 四个消费者）
B 发布订阅（fanout 交换机 + 四个队列）
C RPC
D 工作队列，但把一条消息发四次

<details><summary>答案</summary>

**B**。

关键在"每个服务都要收到通知"——四个动作是**四件不同的事**，不是同一件事的四个副本。

实测对照：

**发布订阅（fanout）**：
```
| 订阅队列 | 收到条数 | 内容 |
| l12.sub.sms | 3 | ['news-0', 'news-1', 'news-2'] |
| l12.sub.email | 3 | ['news-0', 'news-1', 'news-2'] |
| l12.sub.push | 3 | ['news-0', 'news-1', 'news-2'] |
✅ 三个订阅队列各收到完整的 3 条 —— 广播，不是竞争
```

**工作队列**：
```
合计处理：12 条（原始 12 条）
✅ 无重复、无丢失 —— 每条消息只被【一个】worker 处理
```

A 错：选 A 的话，一条订单消息只会被**一个**服务拿到（比如只有短信服务收到），邮件/库存/积分全都收不到——这正是两种拓扑的分界线。

C 错：RPC 是要拿结果的，这里下单接口不需要等四个服务的处理结果。

D 错：技术上能跑，但把"广播"这件事从 broker 挪到了生产者代码里。加第五个服务时要改生产者，且无法保证四条都发出去（部分失败会不一致）。用 fanout，加服务只需加一个绑定，生产者完全不用动。

</details>

### Q2（多选）

关于 Direct Reply-To（`reply_to = 'amq.rabbitmq.reply-to'`），下列哪些说法是本课**实测确认**的？（多选）

A 伪队列不需要声明
B 在其他连接上访问它会报 404 no queue
C 消费和发布必须在【同一条信道】，否则响应收不到
D 它是所有 RPC 场景的最优选择

<details><summary>答案</summary>

**A、B、C**。

**A 对**：伪队列免声明、不占 broker 资源，这正是它的设计目的。

**B 对**，实测：
```
约束 ①：在【另一个连接】上访问伪队列 'amq.rabbitmq.reply-to'
  结果：❌ (404, "NOT_FOUND - no queue 'amq.rabbitmq.reply-to' in vhost '/'")
  → 伪队列【绑死连接】，其他连接看不见它
```

**C 对**，这是本课最值得记住的一条。三组对照（判据是**响应是否真的到达**，不是"有没有报错"）：

| 用法 | 是否报错 | 响应是否到达 |
|------|----------|--------------|
| A 跨信道（消费在 A、发布在 B） | **不报错** | ❌ **收不到（静默丢失）** |
| B 同信道，但先发布后注册消费者 | 异步 406 | ❌ 收不到 |
| C **同信道 + 先注册后发布** | 无 | ✅ **收到** |

B 组的报错长这样：
```
(406, 'PRECONDITION_FAILED - fast reply consumer does not exist')
```
注意它是**异步返回**的——发布那一刻不一定抛异常，而是随后把 channel 关掉，排查时容易懵。

**D 错**：恰恰相反。因为它**绑死连接**、还要求**同信道**，所以：
- 连接一断，在途响应全丢
- **不能跨进程/跨服务中转**
- 跨信道时**静默失败**，比报错还难查

本课的实测结论是：**调用方自己收响应、短连接、同进程 → Direct Reply-To；
跨服务中转、可能重连、希望出错有信号 → 普通回调队列**。

</details>

### Q3（单选）

你看到两组性能数据：某篇评测说 RabbitMQ 能跑 5 万 TPS，你自己实测只有 456 TPS。最合理的解释是？

A 你的环境有问题，装错了
B RabbitMQ 实际性能就是很差，评测在吹牛
C 两组数据的**测试条件**不同，不能直接比较
D 456 是错的，应该多测几次取最大值

<details><summary>答案</summary>

**C**。

这是本课最重要的方法论之一。性能数字必须连同**测试条件**一起看，影响吞吐的关键变量至少四个：

| 变量 | 影响 |
|---|---|
| 消息大小 | 1KB vs 100B 差十倍吞吐 |
| 持久化配置 | fsync 与否差一个数量级 |
| 客户端数量 | 单客户端 vs 100 并发 |
| 队列类型 | 同一评测里 classic / quorum / stream 能差几十倍 |

本课的 456 条/秒，条件是：**单客户端 + quorum 队列 + publisher confirms + 跨 docker 网络（WSL/Windows）**。每一条消息都要等三个节点 Raft 确认再返回，这跟"多客户端 + 不 fsync + classic 队列"的评测完全不是一回事。

A 错：环境没装错，数据是可复现的（本课的容量实测跑了四组，趋势一致）。

B 错：这不是"谁在吹牛"，是口径不同。两类数字在各自条件下都可能是真的。

D 错：取最大值恰恰是错误做法——你应该**先对齐测试条件**，再比较。取最大值只会让数字更好看，不会让它更可比。

> 顺带一个实测反直觉的点：消息从 1KB 涨到 1MB（1000 倍），条/秒只从 456 掉到 108（**4.2 倍**），带宽却从 0.45 涨到 107.7 MB/s（**242 倍**）。
> 说明瓶颈在**每条消息的固定开销**（Raft 复制 + fsync），不在字节数。

</details>

### Q4（简答）

同事提议：新项目用 RabbitMQ 做实时数仓，每天几十亿条用户行为事件，要求能回放三个月前任意一天的数据。请给出你的判断和理由。

<details><summary>答案</summary>

**不应该用 RabbitMQ，这个场景该用 Kafka。**

三条理由，其中第二条是决定性的：

**1. 量级**
几十亿/天 ≈ 3 万+/秒持续写入。RabbitMQ 的 quorum 队列扛得住但吃力，成本远高于 Kafka。

**2. 回放（决定性理由）**
要回放三个月前的某一天，需要**长期留存 + 按 offset 任意定位**。

这是 Kafka **日志模型**的核心能力：消息按 offset 顺序写入、按时间或大小保留、消费者可以从任意 offset 重读。

而 RabbitMQ 的队列语义是**消费即删**——消息被确认后就从队列里移除了。虽然 RabbitMQ 有 stream 类型支持重复读，但"保留三个月、任意定位"不是它的设计目标。

**3. 生态**
实时数仓要接 Flink/Spark，Kafka 是这些框架的一等公民，connector 成熟。

---

**但要反过来想**：如果需求是"订单创建后触发发短信、发邮件、扣库存"——每秒几百单、路由规则复杂——那 Kafka 是**过度设计**，RabbitMQ 更合适（topic 交换机的路由能力是它的独门优势，Kafka 只有 topic + partition）。

**这才是选型的核心**：不是找"最好的"，是找"在你的约束下最合适的"。

判断的分水岭可以简化为一句话：
- 消息是**任务**（处理完即销毁）→ RabbitMQ
- 消息是**事实**（要留存、要回放）→ Kafka

这个场景里，用户行为事件是**事实**——它已经发生了，你可能要反复分析它。所以是 Kafka。

</details>

### Q5（简答）

你的 RabbitMQ 刚上生产，老板问"出问题了怎么办"。请给出监控方案中最重要的那条告警，并说明理由；再列出至少三条其他必看的告警。

<details><summary>答案</summary>

**最重要的告警：队列深度持续上涨。**

理由：它不紧急，但它是**几乎所有严重故障的共同前兆**。

故障的演进链条通常是这样的：

```
   消费者变慢/挂掉
    ↓
队列开始变长          ← 在这里发现，代价最小
    ↓
内存高水位触发（4.x 默认 0.6），broker 阻塞生产者
    ↓
磁盘告警触发           ← 到这里才发现，生产者已经被阻塞
    ↓
生产者被阻塞，上游服务雪崩
```

**在"队列变长"这一环处理掉，是性价比最高的运维动作。** 等到磁盘告警，业务已经受损了。

注意关键词是"**持续**上涨"——瞬时上涨可能是正常的批量任务（比如每天凌晨的对账）。要告警的是**趋势**，不是某个瞬时值。判断是否持续，可看 5~10 分钟的移动平均。

---

**其他必看的告警**：

1. **消费者数掉到 0**（`rabbitmq_queue_consumers`）
   消费者全挂了，消息只进不出。这个要立即处理。

2. **磁盘剩余空间**（`rabbitmq_disk_space_available_bytes` 对比 `rabbitmq_disk_space_available_limit_bytes`）
   接近低水位就该告警。磁盘告警一旦触发，**生产者会被阻塞**，是直接影响业务的严重事件。
   也可以直接看 `rabbitmq_alarms_free_disk_space_watermark == 1`。

3. **内存水位**（`rabbitmq_process_resident_memory_bytes` / `rabbitmq_resident_memory_limit_bytes`）
   比值超过 0.7 就该关注（4.x 默认高水位是 **0.6**，不是 3.x 的 0.4）。
   也可以直接看 `rabbitmq_alarms_memory_used_watermark == 1`。

4. **未确认消息的年龄**（不是数量）
   比"unacked 数量"更能反映真实卡顿：如果最老的一条 unacked 已经挂了 10 分钟，说明有消费者卡死或处理极慢，即使 unacked 总数不大。

5. **死信队列深度 > 0**
   说明有消息在反复失败。不紧急，但要有人看。

6. **消息速率突然归零**
   publish 或 deliver 速率骤降为 0，通常意味着链路断了（网络、客户端、或 broker 异常）。

---

**补充**：RabbitMQ 自带 Prometheus 端点（默认 **:15692**），Grafana 有官方现成看板，不需要自己造轮子。

</details>

### Q6（简答）

你们要把一批 500KB 的图片元数据通过 RabbitMQ 传给下游。有同事担心"消息太大会拖垮 MQ"，提议把每张图片拆成 50 条 10KB 的消息。请结合本课实测数据评价这个方案。

<details><summary>答案</summary>

**这个方案是把问题变糟了，不是变好了。**

先看实测数据（三节点集群、quorum 队列、publisher confirms、单客户端）：

| 消息大小 | 吞吐（条/秒） | 带宽（MB/s） |
|----------|--------------|--------------|
| 1 KB | 456.1 | 0.45 |
| 10 KB | 402.6 | 3.93 |
| 100 KB | 329.7 | 32.19 |
| 1 MB | 107.7 | 107.70 |

**关键洞察**——看相对值：

| 消息大小 | 条/秒 相对值 | 带宽 相对值 |
|----------|-------------|-------------|
| 1 KB | 1.00x | 1.00x |
| 1 MB | 4.23x | **241.83x** |

消息大了 **1000 倍**，条/秒只掉了 **4.2 倍**，带宽却涨了 **242 倍**。

**这说明瓶颈不在字节数，而在每条消息的固定开销**——Raft 复制到三个节点、每次 fsync、每帧网络往返。这些开销与消息大小基本无关。

---

**所以"拆成 50 条"的问题在哪？**

拆成 50 条 = 把固定开销**付 50 次**。

粗略估算：1 条 500KB 消息的开销 ≈ 1 次固定开销 + 500KB 传输；
50 条 10KB 消息 = **50 次固定开销** + 同样 500KB 传输。

在总字节数相同的情况下，条数从 1 变成 50，**多付了 49 次 Raft 复制与 fsync**。吞吐会更差，不是更好。

而且还有两个额外代价：
- **顺序**：50 条消息到达顺序不保证，下游要自己做重组和排序
- **原子性**：部分失败时，下游可能只收到 20 条，要处理"半张图片"的状态

---

**正确的做法是什么？**

方向一：**如果 500KB 确实必须走 MQ**
直接传 1 条 500KB 消息，别拆。实测显示 100KB 时仍有 330 条/秒、32 MB/s，是可用的。

方向二（更推荐）：**claim-check 模式**
```
1. 图片/大对象存到对象存储（S3 / COS / MinIO）
2. MQ 里只传引用：{"bucket": "imgs", "key": "a1b2.jpg", "size": 512000}
3. 下游收到后自己去对象存储取
```
消息体从 500KB 降到不到 1KB，吞吐回到 456 条/秒的档位，且对象存储天生适合放大文件、成本更低。

---

**一句话总结**：本课的实测说明"消息越大越慢"是对的，但**慢得远比直觉慢**（大 1000 倍只慢 4.2 倍）。因此把大消息**拆碎**通常是错的方向——要么直接传，要么用 claim-check 把大对象挪出 MQ。

</details>
