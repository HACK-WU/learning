# 设计决策：两个真权衡点

> 判定"真权衡"的标准：**换个人来可能选另一个方案，且也有道理**。下面两个决策都满足——没有唯一正确答案，只有"在你的约束下更合适"。

---

## 决策 1：整体交付语义——「至少一次 + 消费端幂等」vs「精确一次事务」

### 候选方案对比

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| **A. 至少一次 + 消费端幂等**（选这个） | `acks='all'` + 幂等生产者 + 手动提交位移；下游用业务主键去重 | 吞吐高、实现简单、跨外部系统（数据库）也能成立 | 消费端必须写去重逻辑，代码有额外负担 |
| **B. 精确一次事务（Kafka EOS）** | 生产者事务 + `read_committed` 消费者 + `send_offsets_to_transaction` | 语义最强、消费端不用写去重 | 吞吐下降（100ms 提交间隔约降 15%–30%，Confluent 2017 基准）；**事务只覆盖 Kafka 内部**，一旦要写数据库就失效 |
| **C. 最多一次** | `acks=0` / 提交先于处理 | 最快、实现最简单 | 会丢消息——订单场景不可接受 |

### 最终选择

**A 为主（积分/审计服务），B 仅用于风控服务。**

### 选择理由

1. **事务的边界决定了它不能包打天下**：课 8 讲过，Kafka 事务只覆盖 topic 与 `__consumer_offsets`。积分服务要写数据库、审计服务要写对象存储，**事务的原子性到不了这些外部系统**——用了事务照样要写幂等，白付性能代价。
2. **风控服务是例外，值得付代价**：风控是「读风控规则 → 判定 → 写出判定结果」的纯 Kafka 内闭环（输入输出都在 topic 里），事务能真正生效，且判定结果重复会造成误拦截，语义要求最高。
3. **至少一次的代价是可控的**：消费端幂等只需一张"已处理事件 ID"表（本项目用 `processed_events` 字典模拟），成本远低于事务的吞吐损失。

### 为此付出的代价

- 积分/审计服务**每个**都要写幂等去重逻辑，且去重表本身要清理（否则无限膨胀）。
- 无法向业务方承诺"绝对不重复"，只能承诺"重复了结果也对"——**正确性从"不重复"降格为"重复无害"**，需要文档向上下游说清楚。

### 什么情况下该改选 B（全量事务）

当**所有下游的处理都在 Kafka 内部闭环**（比如纯 Streams/Flink 的流处理拓扑，不写外部数据库），且业务对重复的容忍度极低时。反过来，一旦任何一环要写数据库、调 HTTP，就该回到 A——因为事务到不了那儿。

## 决策 2：坏消息处理——「DLQ 旁路」vs「原地重试」

### 候选方案对比

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| **A. DLQ 旁路**（选这个） | 处理失败 N 次后投递到 `orders.DLQ`，主分区继续前进 | 一条坏消息不会拖垮整个分区 | 需要额外的 DLQ topic 与监控；坏消息要人工介入 |
| **B. 原地重试直到成功** | 不提交位移，反复重试同一条 | 实现最简单，无需额外 topic | **毒药消息（poison pill）会永久阻塞整个分区**——且会触发再均衡→全组暂停→积压扩散的恶性循环 |
| **C. 失败就丢弃** | 捕获异常后直接提交位移跳过 | 代码最短 | 静默丢消息，订单场景不可接受 |

### 最终选择

**A：失败 3 次后进 DLQ。**

### 选择理由

1. **B 的失败模式是灾难性的且反直觉**：一条格式错误的消息会让消费者卡死 → 超过 `max.poll.interval.ms` 被踢出组 → 触发再均衡 → **该组所有分区全部暂停** → 积压扩散到全 topic → 重平衡后坏消息被分配给下一个消费者，再次卡死。这是一个正反馈死循环，教科书级的生产事故（见 [08-实战经验.md](../../08-实战经验.md) 故障模式 2）。
2. **可观测性**：DLQ 的积压量本身就是"有多少坏消息"的指标，而 B 只能靠日志猜。
3. **A 保留了数据**：坏消息进了 DLQ 就没丢，修好消费者后可以重放回去。

### 为此付出的代价

- 多一个 topic 要运维，且**必须有人看 DLQ**——否则 DLQ 变成"没人管的垃圾场"，等于换了个地方的静默丢弃。
- 重试次数（3 次）是拍的：设太低会把偶发抖动（如下游超时）误判为坏消息；设太高会拉长主链路的延迟尾巴。

### 什么情况下该改选 B（原地重试）

当失败原因是**明确可自愈的瞬时故障**（如下游限流、网络抖动），且**消息本身一定格式正确**时——可以用退避重试原地处理，不必进 DLQ。判据很简单：**如果是消息内容有问题（必然重复失败）→ DLQ；如果是环境有问题（重试可能成功）→ 退避重试**。生产上常常两者结合：先退避重试，超过 N 次仍失败才进 DLQ（本项目即此策略）。
