# 验收清单：怎么确认自己真的做成了

> 逐项勾选。**任何一项勾不上，说明那个知识点还没真正落地**，回去看对应的课。

---

## A. 跑通与可观测

- [ ] `init_topics.py` 执行成功，能看到 `orders` / `orders.DLQ` / `risk.result` 三个 topic
- [ ] 生产者发送 30 条事件，**每条都打印了发送成功**（partition 与 offset 都有值）
- [ ] 三个消费者终端同时运行，各自打印自己的处理日志，**互不干扰**
- [ ] 用 `kafka-consumer-groups.sh --list` 能看到 `points-service` / `risk-service` / `audit-service` 三个组

## B. 核心机制是否真的生效

- [ ] **组间广播**：积分、风控、审计三个服务都收到了**全部**事件（不是各收三分之一）
- [ ] **同 key 保序**：同一个 `user_id` 的事件都落在同一个 partition（看日志里的 partition 值）
- [ ] **不丢消息**：审计服务的留痕条数 = 生产者发送的条数
- [ ] **消费端幂等**：把 `points_consumer.py` 重启一次（Ctrl+C 再跑），积分账本的**最终数值不变**（重复投递没导致重复加分）
- [ ] **坏消息进 DLQ**：用下面的命令能看到 DLQ 里有消息，且积分服务**没有被卡住**（仍在继续处理后续消息）

```powershell
docker exec kafka /opt/kafka/bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic orders.DLQ --from-beginning --max-messages 5
```

- [ ] **事务可见性**：风控服务跑完后，用 `read_committed` 的消费者读 `risk.result` 能看到判定结果条数 = 事件条数

## C. 理解层面的验收（不看代码，口头回答）

- [ ] 说出本项目**为什么**积分服务用「至少一次 + 幂等」而风控服务用事务（提示：事务的边界在哪）
- [ ] 说出**为什么不按消费方建 topic**（`to-points-service` 的后果是什么）
- [ ] 解释 `send_offsets_to_transaction` 这一行的作用——去掉它会发生什么
- [ ] 解释为什么坏消息**不能**原地无限重试（会触发什么连锁反应）
- [ ] 对照 [反例对照.md](反例对照.md) 的 5 个坏味道检查项，逐条说出自己代码里对应怎么做对的

## D. 加分项（可选挑战）

- [ ] 把 `orders` 的分区数从 3 改成 6，观察消费者分配发生什么变化
- [ ] 启动**两个** `points_consumer.py` 实例（同组），观察分区被分摊（组内分摊 vs 组间广播）
- [ ] 在积分服务里加一个 `max.poll.interval.ms` 过小的配置，亲手制造一次再均衡风暴，看日志里 `Revoking previously assigned partitions` 长什么样
