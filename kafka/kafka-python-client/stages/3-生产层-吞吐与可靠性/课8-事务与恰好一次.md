# 课 8 · 事务与恰好一次

> 一句话：**幂等保证"不重复写"，事务保证"读-处理-写-提交偏移"四步原子**；前者的代价可以忽略，后者的代价是数量级的。

## 一、先纠一个预设：事务不是 librdkafka 独占

阶段 3 概览原本写着："事务 EOS 是 librdkafka 独占能力，kafka-python 给不了"。

**这句是错的，已被本课实测推翻。**

`hasattr` 核验（三库）：

| 方法 | confluent-kafka 2.15.1 | kafka-python 3.0.11 | kafka-python-ng 2.2.3 |
|---|---|---|---|
| `init_transactions` | ✅ | ✅ | ❌ |
| `begin_transaction` | ✅ | ✅ | ❌ |
| `commit_transaction` | ✅ | ✅ | ❌ |
| `abort_transaction` | ✅ | ✅ | ❌ |
| `send_offsets_to_transaction` | ✅ | ✅ | ❌ |

`kafka-python 3.0.11` **五个事务方法全在**，`kafka-python-ng 2.2.3` **一个都没有**。

但 `hasattr` 全 True 不等于真能用——可能只是 API 空壳。所以必须实测：

### 实测：kafka-python 3.0.11 事务是真实现

| 操作 | `read_uncommitted` | `read_committed` |
|---|---|---|
| `commit_transaction()` 后 | 5 条 | **5 条** |
| `abort_transaction()` 后 | 5 条 | **0 条** |

abort 后 `read_committed` 读到 0 条——**语义完全正确，是真事务**。

> 📌 这个发现改变了选型结论：如果你已经用 `kafka-python 3.0.11`，**不需要为了事务换库**。但如果你用的是 `kafka-python-ng`，事务这条路直接堵死——它连 `transactional_id` 配置项都没有。

## 二、幂等 vs 事务：边界在哪

课 6 讲过幂等的边界：**只在单会话内有效**。生产者重启后 PID 变化，跨会话的重复它管不了。

事务解决的是另一个问题：

```
幂等  : 写 -> 写 -> 写          多条写入不重复（单分区、单会话）
事务  : 读 -> 处理 -> 写 -> 提交偏移   四步原子（跨分区、跨会话）
```

关键差异在第四步。**消费偏移的提交和生产消息的写入，必须要么都生效、要么都不生效**。

如果分两步做（先写再手动 commit offset）：

```python
# ❌ 错误：这不是原子操作
producer.send(dst, transform(msg))
producer.flush()
consumer.commit()          # <- 这一步如果失败，消息会被重复消费
```

`commit()` 失败 → offset 没提交 → 下次重新消费 → **目标 topic 出现重复**。

事务把 offset 提交纳入事务，四步变成一个原子动作。

## 三、全链路 EOS：两库可运行实现

### kafka-python 3.0.11

```python
from kafka import KafkaProducer, KafkaConsumer, OffsetAndMetadata

producer = KafkaProducer(
    bootstrap_servers=BOOTSTRAP,
    transactional_id="my-tx-id",      # 必须，否则 init_transactions 抛 IllegalStateError
    enable_idempotence=True,
    acks="all",
)
producer.init_transactions()

consumer = KafkaConsumer(
    SRC_TOPIC, group_id="my-group",
    enable_auto_commit=False,          # 必须关自动提交，交给事务管
    isolation_level="read_committed",  # 必须，否则会读到未提交/已回滚的消息
    auto_offset_reset="earliest",
)

while True:
    batch = consumer.poll(timeout_ms=5000, max_records=500)
    if not batch:
        break
    try:
        producer.begin_transaction()
        for tp, msgs in batch.items():
            for m in msgs:
                producer.send(DST_TOPIC, value=transform(m.value), key=m.key)
        producer.send_offsets_to_transaction(
            {tp: OffsetAndMetadata(msgs[-1].offset + 1, None)
             for tp, msgs in batch.items()},
            consumer.group_metadata(),    # ⚠️ 是【方法】，必须加括号
        )
        producer.commit_transaction()
    except Exception:
        producer.abort_transaction()
        raise
```

### confluent-kafka

```python
from confluent_kafka import Producer, Consumer

producer = Producer({
    "bootstrap.servers": BOOTSTRAP,
    "transactional.id": "my-tx-id",
    "enable.idempotence": True,
    "acks": "all",
    "transaction.timeout.ms": 60000,
})
producer.init_transactions()

consumer = Consumer({
    "bootstrap.servers": BOOTSTRAP,
    "group.id": "my-group",
    "enable.auto.commit": False,
    "isolation.level": "read_committed",
    "auto.offset.reset": "earliest",
})
consumer.subscribe([SRC_TOPIC])

while True:
    msgs = consumer.consume(500, timeout=5.0)
    if not msgs:
        break
    try:
        producer.begin_transaction()
        for m in msgs:
            if m.error():
                continue
            producer.produce(DST_TOPIC, value=transform(m.value()), key=m.key())
        producer.send_offsets_to_transaction(
            consumer.position(consumer.assignment()),
            consumer.consumer_group_metadata(),   # ⚠️ 是【属性】，不加括号
        )
        producer.commit_transaction()
    except Exception:
        producer.abort_transaction()
        raise
```

### 实测结果（10 条源数据）

| 库 | 事务批次数 | 目标 topic 条数 | 去重后 | 结论 |
|---|---|---|---|---|
| kafka-python 3.0.11 | 2 批（8 + 2） | 10 | 10 | ✅ 零重复 |
| confluent-kafka | 1 批（10） | 10 | 10 | ✅ 零重复 |

> kafka-python 的 `poll()` 把 10 条切成了 8+2 两批——**这正好说明为什么必须用事务**：如果不是原子的，中途失败就会留下 8 条脏数据且 offset 状态不一致。

### ⚠️ 两个库的 API 命名陷阱（极易踩）

| 陷阱 | kafka-python | confluent-kafka |
|---|---|---|
| 消费组元数据 | `consumer.group_metadata()` **方法，加括号** | `consumer.consumer_group_metadata()` 名字不同，是**属性** |
| 事务方法超时参数 | **无参数**，超时靠 `max_block_ms` | `init_transactions(timeout=30)` **有参数** |
| offset 类型 | `OffsetAndMetadata(offset, None)` 对象 | `consumer.position(...)` 返回的对象 |
| 传错后果 | 传成 bound method → `TypeError: expects group_metadata to be a ConsumerGroupMetadata or a group_id str` | — |

> 这两处是我实测时**真实踩到**的，不是抄文档。第一个坑（`group_metadata` 漏括号）会让整个事务静默回滚，目标 topic 得到 0 条。

## 四、僵尸实例 fencing

事务的核心护城河：同一个 `transactional_id` 启动新实例时，旧实例必须被 fence 掉，防止"僵尸生产者"提交过期数据。

### 实测：同 `transactional_id` 双实例

| 步骤 | kafka-python 3.0.11 | confluent-kafka |
|---|---|---|
| p1 init → 发送（不提交） | OK | OK |
| p2 init（同 txid，epoch bump） | OK | OK |
| p2 提交 | OK | OK |
| **p1 提交** | **`ProducerFencedError`** | **`KafkaException` code=`_FENCED` val=-144** |
| `read_committed` 最终可见 | `['from-p2']` | `['from-p2']` |

两库 fencing 都正确工作，被 fence 的旧实例无法提交，其数据对 `read_committed` 消费者不可见。

confluent 的报错原文：

```
KafkaError{FATAL,code=_FENCED,val=-144,
  str="Failed to end transaction: Local: This instance has been fenced by a newer instance"}
```

> 这也是为什么 `transactional_id` 必须**稳定且唯一**：容器重启复用同一个 id 才能 fence 掉上一代；如果每次随机生成，就失去了 fencing 保护。

## 五、事务的代价（本课最重要的表）

2 万条 1KB 消息，`acks=all`，6 分区 3 副本：

| 事务粒度 | confluent-kafka | kafka-python 3.0.11 | confluent 相对无事务 | kp 相对无事务 |
|---|---|---|---|---|
| 无事务 | **35,491** msg/s | **6,830** msg/s | 1.00x | 1.00x |
| 每 100 条一事务 | 3,674 msg/s | 848 msg/s | **9.7x 慢** | **8.1x 慢** |
| 每 10 条一事务 | 362 msg/s | 87 msg/s | **98x 慢** | **78x 慢** |
| 每 1 条一事务 | 48.8 msg/s | 9.2 msg/s | **727x 慢** | **742x 慢** |

单事务固定开销（每 1 条一事务档反推）：

| 库 | 单事务均摊耗时 |
|---|---|
| confluent-kafka | **20.5 ms** |
| kafka-python 3.0.11 | **108.5 ms** |

**结论：事务的代价不在"事务本身"，而在"事务次数"。**

每个事务有约 20~108 ms 的固定开销（多次网络往返：AddPartitionsToTxn → Produce → TxnOffsetCommit → EndTxn）。所以：

- **每 100 条一事务**：代价摊薄到可接受的 8~10 倍
- **每 1 条一事务**：吞吐量级崩塌到个位数

> ⚠️ 上一轮实测踩的坑：`每1条一事务` 按 2 万条跑需 **20 万秒**（约 55 小时）跑不完。已改为小样本（N=1000）外推。**这是"先探路再立项"的又一次验证**——不探路就会挂等一个跑不完的任务。

### 这条数据怎么指导选型

| 你的场景 | 建议 |
|---|---|
| 吞吐优先，能容忍重复 | 不要事务，用幂等 + 消费端去重（课 6 讲过） |
| 需要 EOS，但能攒批 | 上事务，**批量至少 100 条**，代价 8~10 倍 |
| 需要 EOS，无法攒批（实时单条） | **慎重**：48.8 msg/s（confluent）可能根本撑不住你的量，考虑重新设计成批处理 |
| 已用 kafka-python-ng | 事务不可用，要么换 3.0.11，要么换 confluent |

## 六、事务的边界（它保证不了什么）

事务常被误认为"端到端恰好一次"。**它不是。**

| 边界 | 说明 |
|---|---|
| 只覆盖 Kafka 内部 | 写数据库、调外部 API **不在事务内**。事务提交成功但 DB 写入失败，依然不一致 |
| 读已提交的消费者才受益 | 消费者必须用 `isolation_level=read_committed`，否则会读到已回滚的消息 |
| 事务超时会回滚 | 默认 `transaction_timeout_ms=60000`（kafka-python）/ `transaction.timeout.ms=60000`（confluent）。处理超过 60s 会被 broker 主动 abort |
| `transactional_id` 必须稳定 | 随机生成 = 失去 fencing 保护 |
| 消费端仍需幂等兜底 | 事务失败回滚后重试，若外部副作用已发生，仍会重复执行 |

> 真正的端到端 EOS 需要：**Kafka 事务 + 外部系统幂等**（如 DB 唯一键、去重表）。Kafka 事务只解决了"Kafka 内部"这一半。

## 七、两库能力矩阵（本课收口）

| 能力 | confluent-kafka 2.15.1 | kafka-python 3.0.11 | kafka-python-ng 2.2.3 |
|---|---|---|---|
| 幂等生产者 | ✅ | ✅（KIP-679 默认开） | ❌ |
| 事务 API | ✅ | ✅ | ❌ |
| 事务真能跑（实测） | ✅ | ✅ | ❌ |
| consume-transform-produce EOS | ✅ | ✅ | ❌ |
| 僵尸实例 fencing | ✅ | ✅ | ❌ |
| 单事务开销 | **20.5 ms** | 108.5 ms | — |
| `max.poll.interval` 类保护 | ✅ librdkafka 层 | ⚠️ 纯 Python，长处理需手动 `pause()` | ❌ |

**选型结论**：

- **要事务且要性能** → `confluent-kafka`（单事务开销 20.5 ms vs kafka-python 108.5 ms，**快 5.3 倍**）
- **要事务但量不大，且已用 kafka-python** → **不必换库**，3.0.11 事务是真实现，把批量调到 100+ 即可
- **用 kafka-python-ng** → 事务这条路上不了，这是它相对 3.0.11 的硬伤

## 一句话记住

**事务的代价不在事务本身，而在事务次数——每个事务 20~108 ms 固定开销，所以批量攒到 100 条以上才谈得上实用。**

## 常见误区

| 误区 | 事实 |
|---|---|
| "事务是 librdkafka 独占，kafka-python 没有" | **错**（实测推翻）：3.0.11 五个事务方法全在且能真跑；没有的是 `kafka-python-ng` |
| "事务开销主要在 CPU/压缩" | 错：在**网络往返次数**。每 1 条一事务比无事务慢 700+ 倍，与消息大小无关 |
| "开了事务就端到端 EOS 了" | 错：只覆盖 Kafka 内部；写 DB/调 API 不在事务内 |
| "`isolation_level` 不设也行" | 错：默认 `read_uncommitted`，会读到已 abort 的消息 |
| "`transactional_id` 随机生成更安全" | 错：必须稳定唯一，否则失去 fencing 保护 |
| "事务失败重试就安全了" | 错：外部副作用已发生时，重试仍会导致重复执行 |

### 本轮自查修正的两个脚本缺陷

1. **`group_metadata` 漏括号**：kafka-python 是方法，写成属性 → 传 bound method → `TypeError` → 事务静默回滚，目标 topic 得 0 条。
2. **重复 commit 触发状态机错误**：脚本循环末尾对已 `READY` 的事务再 `commit_transaction()`，抛 `Invalid transition from state READY to COMMITTING_TRANSACTION`。顺带实测证伪了"状态机惰性进入"假设——`begin_transaction()` 后状态**立即**变 `IN_TRANSACTION`。
