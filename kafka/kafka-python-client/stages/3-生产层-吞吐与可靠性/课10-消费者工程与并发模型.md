# 课 10 · 消费者工程与并发模型

> 核心问题：**消费端怎么扩，GIL 怎么绕**
> 库：`confluent-kafka 2.15.1`（阶段 3 主线）
> 实测环境：WSL2 / Docker / 3 节点 KRaft（复用课 9 集群）/ Python 3.12.14 / 20 核

---

## 〇、本课要解决什么

你的消费者跑起来了，但消费速度跟不上生产速度。你想到两个办法：加线程、加实例。

这两个办法**都有一个硬上限，而且上限的原因完全不同**：

- 加线程的上限是 **GIL**——CPU 密集时线程完全不加速，实测 0.88x
- 加实例的上限是 **分区数**——消费者数超过分区数就空转，实测 6 实例抢 4 分区，2 个空转

更要命的是第三个坑：并发处理会让**位移提交乱序**，造成消息静默丢失。这个坑不报错、不告警，只在崩溃时暴露。

---

## 一、GIL 到底锁住了什么

### 先测清楚：GIL 在不在、影响多大

实测本机环境（Python 3.12.14，20 核）：

```
sysconfig Py_GIL_DISABLED : None        # 不是 free-threading 构建
```

CPU 密集任务，`N=12,000,000` 固定总量：

| 模型 | 耗时 | 加速比 |
|---|---|---|
| 串行 | 0.39 ~ 0.42s | 1.00x |
| **4 线程** | **0.42 ~ 0.44s** | **0.90 ~ 1.00x** |
| **4 进程** | **0.12 ~ 0.14s** | **2.74 ~ 3.54x** |

> 数值为多次采样区间。线程加速比在 1.0 附近**上下浮动**（有时略低于 1，
> 因为多了线程切换开销），但**始终没有并行收益**——这是判读的关键。

**4 线程加速比始终在 1.0 附近**——不是"提升有限"，是**几乎没有并行收益**。GIL 让 CPU 密集的多线程退化成串行。

### 但 IO 期间会释放 GIL

这是关键区别。同样固定总量，四种并发模型对照（`M=2000`）：

> 数值为 5 次采样区间。绝对值因机器而异，**加速比的相对关系稳定**。

**A. 纯 CPU 密集（每条约 6000 次乘加）**

| 模型 | worker | 加速比（5 次采样区间） |
|---|---|---|
| 串行 | 1 | 1.00x |
| 线程 | 2 | 0.88 ~ 1.00x |
| 线程 | 4 | **0.91 ~ 1.04x** |
| 进程 | 2 | 1.71 ~ 1.85x |
| 进程 | 4 | **2.67 ~ 3.34x** |

**B. CPU + IO 混合（CPU 部分 + 0.2ms sleep）**

| 模型 | worker | 加速比（5 次采样区间） |
|---|---|---|
| 串行 | 1 | 1.00x |
| 线程 | 2 | 1.44 ~ 1.95x |
| 线程 | 4 | **1.58 ~ 2.02x** |
| 进程 | 2 | 2.02 ~ 2.38x |
| 进程 | 4 | **3.64 ~ 4.11x** |

> **区间不重叠 = 结论稳定**：A 场景线程最高 1.04x < 进程最低 2.67x，
> 两者区间完全不相交，所以「CPU 密集必须上进程」这个结论是稳的，不是采样噪声。

**判读**：

1. 纯 CPU 时线程 **0.91~1.04x**——**没有并行收益**（多线程只增加了切换开销）
2. 有 IO 时线程 **1.58~2.02x**——IO 等待期间释放 GIL，其他线程能跑
3. 进程在两种场景都有效，且 worker 越多越接近核数
4. 混合场景进程（3.64~4.11x）> 纯 CPU（2.67~3.34x），因为 sleep 期间还能调度

> 📌 一句话记住：**GIL 锁 CPU 不锁 IO**。处理逻辑是 CPU 密集 → 必须多进程；
> 是 IO 密集（查库、调 HTTP）→ 线程就够，且更轻。

## 二、坑：多进程没跑赢，可能是 chunksize 的锅

这是本课最容易踩、也最容易被误判的坑。

### 事故现场

第一次跑实验①，得到这个结果：

```
A. CPU 密集
  串行（基线）     1       4,523    1.00x
  进程 x2          2       4,817    1.06x     <- 几乎没加速？
  进程 x4          4       4,796    1.06x     <- 加进程也没用？
```

看起来"多进程也没用"。但同一台机器，探路脚本测出 4 进程 **3.54x**。**两个结果矛盾，必有一个是错的。**

### 核验过程

第一步怀疑"任务粒度太小，IPC 开销吃掉了收益"。控制总工作量不变，只改单 task 粒度：

| 每 task 量 | task 数 | 串行 | 4 进程 | 加速比 |
|---|---|---|---|---|
| 6,000 | 2000 | 0.62s | 0.20s | 3.06x |
| 60,000 | 200 | 0.60s | 0.21s | 2.91x |
| 600,000 | 20 | 0.65s | 0.18s | 3.69x |
| 3,000,000 | 4 | 0.56s | 0.16s | 3.43x |

**假设被推翻**——粒度不是原因，6000/task 也能跑 3.06x。

第二步锁定唯一差异：核验脚本传了 `chunksize`，原始脚本没传。

**5 次采样区间**（这是修正后的数据，见下方勘误）：

| chunksize | 加速比（5 次采样区间） |
|---|---|
| **1（默认值）** | **1.19 ~ 1.89x** |
| 10 | 3.05 ~ 3.85x |
| 50 | 3.05 ~ 3.85x |
| 125 | 2.80 ~ 3.52x |
| 500 | 2.80 ~ 3.08x |

**确认**：`ProcessPoolExecutor.map()` 的 `chunksize` **默认是 1**，即**每条消息一次 IPC**。
默认值的加速比区间 **1.19~1.89x** 与最优区间 **3.05~3.85x** **完全不重叠**——
**chunksize 的影响是真实的、稳定的**，能差出 **2 倍**。

> ⚠️ **勘误（复审修正）**
>
> 首版讲义写的是 `chunksize=1` 只有 **0.71x（比串行还慢 30%）**。
> 复审 5 次采样跑出 **1.19~1.89x**，**从未低于 1.0**。
> 那个 0.71x 是单次采样中的极端值，**"比串行慢"的说法不成立**。
>
> 修正后的准确表述是：**默认 chunksize 让并行收益损失约一半**（1.19~1.89x vs 3.05~3.85x），
> 而不是"倒挂到比串行还慢"。结论方向不变，但程度必须如实。
>
> 这是我在课 9 刚犯过的同类错误（把单点采样当确定值）的第 3 次复发。

### 正确写法

```python
from concurrent.futures import ProcessPoolExecutor

# ❌ 默认 chunksize=1，每条消息一次 IPC
with ProcessPoolExecutor(max_workers=4) as ex:
    ex.map(process_msg, items)

# ✅ 显式指定：批量派发
cs = max(1, len(items) // workers // 4)
with ProcessPoolExecutor(max_workers=4) as ex:
    ex.map(process_msg, items, chunksize=cs)
```

> ⚠️ 这个坑的危险在于**它不会报错**：代码跑得通、结果是对的，只是慢。
> 你会得出"多进程对我的场景没用"的错误结论，然后放弃正确的方案。

## 三、扩容天花板：分区数决定一切

### 实测：6 个实例抢 4 个分区

Topic 4 分区，逐步增加消费者实例（同 group.id），稳定后读各自 `assignment()`：

| 实例数 | 各实例分到的分区 | 空转实例 |
|---|---|---|
| 1 | `[[0,1,2,3]]` | 0 |
| 2 | `[[2,3],[0,1]]` | 0 |
| 4 | `[[0],[2],[1],[3]]` | 0 |
| **6** | `[1,1,1,1,0,0]` | **2** |

**6 个实例，2 个分不到任何分区，完全空转。**

### 为什么

Kafka 的消费组协议规定：**一个分区在同一时刻只能被组内一个消费者消费**。

所以：

```
有效消费者数 <= 分区数
```

超过的部分不是"变慢"，是**一点活都干不了**——不报错、不告警，进程正常健康，只是永远收不到消息。

> 📌 "消费慢就加实例"的硬上限 = **分区数**。
> 要继续扩，必须先增加分区数；而**分区数只能增不能减**（减分区会丢数据）。
> 所以建 topic 时分区数要给足余量——这是不可逆的架构决策。

## 四、最危险的坑：并发让位移提交乱序

### 事故复现

1 分区 topic，20 条消息，其中 `i%5==0` 的 4 条是"慢消息"（0.6s vs 0.05s）。4 线程并发处理，**谁先处理完谁提交**：

```
处理线程    offset   耗时     提交offset
wid=1       1       0.05s    2
wid=2       2       0.05s    3
wid=3       3       0.05s    4
wid=0       4       0.05s    5
...（快消息先跑完）
wid=0       0       0.6s     1        <- 慢消息最后才完成
wid=1       5       0.6s     6
wid=2       10      0.6s     11
wid=3       15      0.6s     16
```

**关键看过程**：offset 1 完成时已经提交了 `2`，而 offset 0 还在处理中。

**此时若进程崩溃**——offset 0 被永久跳过。它既没被处理，也不会被再次消费，因为 committed 已经越过它了。

最终态 `committed = 16`，用新 group 从头消费仍能拿到 20 条——**数据没丢，丢的是处理机会**。

### 根因

```
offset 在分区内是【有序】的
并发处理让【完成顺序】变成无序
```

提交了一个"超前"的 offset，等于向 Kafka 声明"这个 offset 之前的我都处理完了"——而实际上没有。

### 三种正解

**正解一：只提交连续水位线**（推荐）

维护"已连续完成的最大 offset"，中间有空洞就不提交：

```python
import threading

class OffsetTracker:
    def __init__(self):
        self.lock = threading.Lock()
        self.done = set()
        self.watermark = -1

    def mark_done(self, offset):
        with self.lock:
            self.done.add(offset)
            # 推进水位线：只走连续的
            while (self.watermark + 1) in self.done:
                self.watermark += 1
        return self.watermark

    def committable(self):
        with self.lock:
            return self.watermark + 1 if self.watermark >= 0 else None
```

空洞（未完成的慢消息）会卡住水位线，直到它完成才整体推进。牺牲一点提交及时性，换正确性。

**正解二：处理与提交分离**

单一消费线程负责 poll 和提交，把消息丢进队列；worker 只处理不提交。

**正解三：业务侧幂等**（最根本）

即使重复消费也不出错。这与课 6「幂等管写不管读」、课 8 EOS 的结论呼应——**端到端的正确性最终要靠业务侧保证**。

## 五、并发模型怎么选

| 场景 | 推荐模型 | 理由 |
|---|---|---|
| 处理是 CPU 密集（解析、计算、加密） | **多进程** | 线程被 GIL 锁死，实测 0.88x |
| 处理是 IO 密集（查库、调 HTTP） | **线程池** | IO 期间释放 GIL，实测 1.66x，比进程轻 |
| 想扩到多机 | **多实例 + 消费组** | 但要受分区数限制 |
| 单分区但处理慢 | **进程内多进程处理 + 连续水位线提交** | 加实例无效（分区只有 1 个） |

### 单分区慢消费怎么办

这是常见困局：分区数固定（比如按 key 保序必须单分区），加实例没用。

两条路：

1. **进程内多进程/多线程处理**——拉取仍单线程（保序），处理并行。提交用连续水位线
2. **业务侧拆 topic**——如果保序要求只针对部分 key，可拆分

## 六、踩坑清单（本课新增）

| # | 坑 | 现象 | 正解 |
|---|---|---|---|
| 1 | 线程加速 CPU 密集任务 | 实测 0.91~1.04x，**无并行收益** | 改用多进程 |
| 2 | `ProcessPoolExecutor.map` 默认 `chunksize=1` | 收益损失约一半（1.19~1.89x vs 3.05~3.85x） | 显式传 `chunksize` |
| 3 | 消费者数超过分区数 | 多出的实例**空转**，不报错 | 扩容上限 = 分区数 |
| 4 | 并发处理各自提交 offset | **静默丢消息**，只在崩溃时暴露 | 连续水位线提交 |
| 5 | 分区数建少了 | 后期扩不动（只能增不能减） | 建 topic 时留余量 |

## 七、本节结论

1. **GIL 锁 CPU 不锁 IO**：CPU 密集线程 0.91~1.04x（无收益）→ 必须多进程（2.67~3.34x）；
   IO 密集线程 1.58~2.02x 就够，且比进程轻
2. **多进程要显式给 `chunksize`**，默认的 1 让收益损失约一半（区间不重叠），且不报错
3. **扩容硬上限是分区数**：实例数超过分区数就空转，实测 6 实例 2 空转
4. **并发处理 + 各自提交 = 静默丢消息**，正解是连续水位线
5. 端到端正确性最终靠**业务侧幂等**，与前序课结论一致

## 八、诚实标注

- 本课所有数字均为本机实测（WSL2 / Docker / 3 节点 KRaft / 20 核），**非引用文档**
- **所有加速比均标注为 5 次采样区间**，不以单点值呈现。本机负载波动明显（同脚本重跑可差 80%）
- **复审修正 1 处方向性错误**：`chunksize=1` 首版记为 0.71x（比串行慢），复审 5 次采样为 1.19~1.89x，
  **"比串行慢"不成立**，已改为"收益损失约一半"。详见第二节勘误
- 实验①的处理负载是**合成的**（6000 次乘加 + 0.2ms sleep），非真实业务；结论的**定性部分**
  （GIL 锁 CPU、chunksize 影响）普适，定量部分仅供参考
- 实验③用 1 副本（rf=1）加速建 topic，生产环境应 rf>=3
- **未实测**：协程（asyncio）模型——留给课 11 三方对照；`max.poll.interval.ms` 与并发的交互——课 5 已覆盖单条超时，未覆盖并发下的批量超时
- 多进程实验曾因 8 worker × 20 核 fork 导致 WSL 连接中断，已下调至 4 worker
