# 课 13 · 结课综合实战：把能跑通的脚本，做成敢上生产的长驻程序

> 一句话定位：不是再学新知识，而是把阶段 1–4 的能力**串成一个能真跑起来的服务**，并在跑的过程中，把自己对"性能"的直觉打碎重造。

## 开场：这一课真正要教的东西

前 12 课你学会了：建 topic、确认语义、吞吐调优、事务、Schema、并发模型、asyncio 集成、可观测与测试。课 13 按理该是"把这些用起来"——搭个服务，跑通，收工。

**但实际发生的事比这有价值得多。**

我在搭这个服务的过程中，对"为什么消费这么慢"连续下了**三次诊断，三次全错**，还据此做了两次"修复"，每次修复后数值都变得更糟。最后才发现：**服务从头到尾就没有性能问题**。

这一课因此分成两部分：

- **上半场**：工程本身——一个零新增依赖、能 `docker compose up` 的订单服务，覆盖 6 个核心能力
- **下半场**：三次误诊的完整复盘——这是本课最值钱的部分，因为它暴露的是**测量方法的缺陷**，而不是 Kafka 的缺陷

## 一、工程长什么样

```
capstone/
├── app/
│   ├── config.py        # 所有参数集中，每个都标注"来自哪一课"
│   ├── schema.py        # 契约：JSON + 手写校验（课 9）
│   ├── metrics.py       # 手写 Prometheus 文本格式（课 12）
│   ├── kafka_client.py  # 幂等建 topic / 生产 / lag 采集（课 3/6/7/12）
│   ├── worker.py        # 消费 + 手动提交 + DLQ + 优雅退出（课 6/10）
│   └── main.py          # FastAPI 入口（课 11）
├── tests/
│   ├── test_unit.py         # L1 纯逻辑，16 项，0.004 秒
│   ├── test_integration.py  # L2 真服务 + 真集群
│   └── test_final.py        # 最终验收
├── Dockerfile
└── docker-compose.yml
```

**零新增依赖**是刻意的设计约束：`prometheus_client` 和 `pytest` 都没装，前者手写了文本格式协议，后者用标准库 `unittest`。理由有两条——不用装包就能跑；**手撕一遍协议才知道 scrape 到底发生了什么**。

| # | 能力 | 落地位置 | 对应课程 |
|---|---|---|---|

## 二、几个值得单独讲的设计决定

### 2.1 坏消息必须"仍提交"，好消息失败才"不提交"

这是最容易搞反的一处：

```python
try:
    order = OrderEvent.from_json(raw)
except ValidationError:
    self._to_dlq(raw, str(e))   # 进 DLQ
    self._commit(msg)            # ← 坏消息也要提交！
    return
try:
    self._process_fn(order)
except Exception:
    return                       # ← 处理失败不提交，会被重投
```

**为什么**：坏消息重试一万次也不会成功。不提交它，消费者就永远卡在这条"毒丸消息"上，后面的好消息一条也消费不到。而处理失败通常是下游抖动，**重试有意义**，不提交才能重新消费。

单元测试 `test_bad_message_goes_to_dlq_and_still_commits` 与 `test_processing_error_does_not_commit` 把这两条反向语义各自钉死。

### 2.2 `/health` 与 `/ready` 必须分离

```python
@app.get("/health")   # 存活：进程活着就 True，**不查 Kafka**
@app.get("/ready")    # 就绪：能服务才 True，查 worker 与分区
```

**为什么**：k8s 的 liveness 失败会**重启容器**，readiness 失败只是**摘流量**。Kafka 抖动三秒，你希望的是"这 3 秒先别给它流量"，而不是"把全部实例重启一遍"——后者是典型的雪崩放大器。

同理，`is_healthy()` 里**不把 lag 大小作为判据**：lag 高是"忙"不是"病"，用 lag 做健康判据会导致扩容时所有实例被误杀。

### 2.3 优雅退出必须处理 SIGTERM

```python
def install_signal_handlers(worker):
    for sig in (signal.SIGTERM, signal.SIGINT):
        signal.signal(sig, lambda s, f: worker.stop())
```

容器 `stop` 先发 SIGTERM，**默认 10 秒后 SIGKILL**。不处理的话，在途消息和未提交位移全丢。`stop()` 的顺序是：停止拉新 → 等当前批次处理完 → **同步提交一次** → close。最后那次提交不能省。

## 三、下半场：三次误诊（本课核心）

### 3.1 症状

服务跑起来后，消费慢得离谱。我测到的数字一路下滑：

| 轮次 | 我"修复"了什么 | 测到的消费速率 |
|---|---|---|
| 初版 | — | 0.7 条/秒 |
| 修复 1 | lag 采集改为 5 秒节流 | 16.6 条/秒 |
| 修复 2 | commit 改异步 | 11.1 条/秒 |
| 修复 3 | lag 移出消费线程 | 3.8 条/秒 |

**每次"修复"之后数字都变差**。这是最强的信号——说明诊断方向根本不对。但我当时没读懂这个信号，而是继续找"下一个瓶颈"。

### 3.2 三次误诊分别是怎么错的

**误诊一：把测量错误当成性能瓶颈**

第一次用"总 poll 耗时 ÷ 消息数"算每条 poll 耗时，得出 **5007ms/条**的耸人听闻结论。但分子里包含了**所有空 poll 的时间**，分母却只是消息数。空 poll 本来就占 1 秒超时——这个数字从算法上就是错的。

**误诊二：把环境干扰当成代码缺陷**

我做了四组对照实验，得出"同步 commit 让吞吐掉 710 倍"的结论。但实验里所有消费者都用 `config.consumer_conf()`，其中 `group.id` 是**固定的 `capstone-svc`**——而运行中的服务正在用同一个组。测试脚本每次 subscribe 都触发 rebalance，把服务踢来踢去。数据是 rebalance 的产物，不是 commit 的产物。

**误诊三：把尾部等待当成稳态速率**

最后三轮测量高度一致地显示 33 条/秒，我当时以为终于稳定了。但注意这个指纹：**1999/2000 条 + 耗时整 60 秒**（正好是超时上限）。

### 3.3 真相

```
produce 2000 条，真实分布：
  分区0:   1 条    分区1:   0 条
  分区2: 1995 条   分区3:   4 条

消费计时：
  前 10 条耗时  : 0.0 ms
  第 1998 条到达: 0.002 秒
  95% 消息到达  : 0.002 秒  →  1,122,145 条/秒
```

**1999 条消息在 2 毫秒内全部消费完，然后循环卡在等那条永远不会来的第 2000 条，直到超时。**

33 条/秒 = 1999 条 ÷ 60 秒。这个"速率"里，59.998 秒是在**空等**。

**为什么最后一条永远不来**：分区倾斜。独立复审实测到极端情况——

```
分区分布: {0: 0, 1: 2000, 2: 0, 3: 0}
```

**2000 条全挤在分区 1，其余三个分区为空。** 裸 `produce()` 不传 key 时，librdkafka 不是我以为的"按条轮询分区"，而是**按 batch 批量发往同一分区**（`linger.ms=5` 期间攒的批整体落到一个分区）。空分区的 fetch 永远拿不到数据，于是 `while n < N` 就永远差那几条。

三次误诊的共同根因：**我在用"等 N 条完成"的测法，去测一个"最后几条可能永远不来"的系统**。分区严重倾斜（1995 条挤在一个分区、一个分区为空）让最后一条消息迟迟不出现，于是每次测量都吃满超时。

### 3.4 正确的测法

```python
# ✗ 错误：等 N 条完成，会吃满超时
while n < N and time.time() - t0 < 60:
    ...
rate = n / (time.time() - t0)          # 分母含空等时间

# ✓ 正确：固定时间窗，数到达量；或用分位数看真实分布
deadline = t0 + 10
while time.time() < deadline:
    ...
rate = n / 10                           # 分母是确定的
# 更稳：看 95 分位到达时间，识别"尾部等待"
```

配套的两条纪律：

1. **吞吐测量必须使用独立 `group.id`**，绝不能与运行中的服务共用——否则触发持续 rebalance，数据全是 rebalance 的
2. **看到"差几条 + 耗时正好等于超时上限"**，先怀疑测量方法，别急着优化代码

### 3.5 我留下的痕迹

代码里这两处注释被保留下来，作为诚实记录：

- `worker._run` 上方：说明"这里曾有过一次误诊"，并澄清独立 lag 线程与异步提交的真实理由是**解耦**，不是性能修复
- `worker._commit` 的 docstring：明确标注"那个 710 倍的数字来自被污染的实验，请勿引用"

> 课 12 固化的铁律是「先核验再下结论」。本课是它的反面案例：**核验了，但核验方法本身是错的**。所以铁律要补一条——**先核验你的测量方法，再核验被测对象**。

## 四、实测数据（这些是可信的）

### 4.1 L1 单元测试：16/16 通过，0.004 秒

```
Ran 16 tests in 0.004s
OK
```

重点覆盖：`bool 是 int 的子类`这个 Python 陷阱（`amount=True` 必须被拒）、坏消息进 DLQ 且仍提交、处理失败不提交、Prometheus HELP 文本转义、lag 必须是 gauge。

### 4.2 L2 集成实测：11/12 通过

| 能力 | 结果 |
|---|---|
| 批量投递 200 条 + 全部确认 | `remaining=0` |
| 消费成功 + 位移提交 | `ok=42 committed=42` |
| 坏消息 422 拦截 | 负金额 / 非法币种 / 非 JSON 全拦 |
| 坏消息进 DLQ | `dlq=1 validation_error=1` |
| lag 指标是 gauge | `# TYPE capstone_consumer_lag gauge` |
| 文本格式无非法行 | Prometheus 可解析 |

### 4.3 真实吞吐

**1,122,145 条/秒**（1998 条在 2 毫秒内到达，本地缓存命中场景）。

这个数字本身不重要——它测的是"消息已经在客户端缓冲区"的情况。重要的是**它和 33 条/秒测的是同一份代码、同一个集群**。差 3 万倍的不是代码，是测量方法。

## 五、踩坑清单

| # | 坑 | 表现 | 正确做法 |
|---|---|---|---|
| 1 | **用"等 N 条完成"测吞吐** | 数字被尾部等待污染，差 3 万倍 | 固定时间窗数到达量，看分位数 |
| 2 | **测试与服务共用 group.id** | 持续 rebalance，吞吐打到个位数 | 测试用独立 group |
| 3 | **空 poll 时间算进每消息耗时** | 得出 5007ms/条 的假结论 | 分子分母口径必须一致 |
| 4 | `create_topics` 对已存在 topic 报错 | 服务每次重启都崩 | 已存在即成功（课 3） |
| 5 | 新 topic 首次 commit 无位移 | `KafkaError{code=_NO_OFFSET}` | 先消费几轮再 commit，或捕获忽略 |
| 6 | `docker exec` slim 镜像无 `ps`/`pkill` | 清理脚本静默失效，留僵尸进程 | 扫 `/proc`，且匹配式要排除脚本自身 |
| 7 | 分区倾斜（裸 produce 不传 key，按 batch 落同一分区） | 复审实测 `{0:0, 1:2000, 2:0, 3:0}`，导致空分区永远等不到数据 | 生产必须传 key；**压测尤其要按 key 分布** |
| 8 | 三条反直觉的提交语义 | 见 2.1 | 坏消息仍提交，好消息失败不提交 |

**坑 6 值得多说一句**：我写的清理脚本用 `/proc` 扫描匹配 `uvicorn`，但执行脚本的 `sh -c` 自身 cmdline 里也含这个字符串，结果**杀了自己、漏了目标**，留下僵尸进程持续占着消费组。这个僵尸进程正是误诊二的干扰源之一。

## 七、结论清单

| # | 结论 | 证据 |
|---|---|---|
| 1 | 坏消息要**提交**并进 DLQ，处理失败**不提交** | `test_unit.py` 两条反向用例 |
| 2 | `/health`（存活）与 `/ready`（就绪）必须分离 | Kafka 抖动应摘流量而非重启 |
| 3 | 优雅退出须处理 SIGTERM，且退出前同步提交 | `install_signal_handlers` |
| 4 | 吞吐测量**必须用独立 group.id** | 共用组触发 rebalance，数据全废 |
| 5 | **"等 N 条完成"是错误测法**，会吃满超时 | 1999/2000 + 整 60s 的指纹 |
| 6 | 同一份代码可测出 33/s 与 112 万/s，差 3 万倍 | `_count.py` 分位数计时 |

| 8 | 零新增依赖可行：Prometheus 文本格式 <150 行 | `metrics.py` |
