### 三、本线专属：多库 API 正确性（新增，最高优先级）

> 立项依据：预研期实测发现 `commitSync()` 在真 kafka-python 3.0.11 下不存在（主教程应用实战 09 曾写错）。**换库时"看起来一样"的 API 必须先核验**。

11. **API 存在性核验**：示例中每个方法调用都必须实测确认在该库该版本下存在。核验方法：
    - 方法：`hasattr(Cls, 'method_name')` 或 `dir(Cls)`
    - 配置项：读 `Cls.DEFAULT_CONFIG`，**不要**用 `inspect.signature(__init__)`（用 `**configs` 收参，会误报"不存在"）
    - 签名：`inspect.signature(Cls.method)`
12. **参数名核验**：关键字参数名逐库不同（`timeout` vs `timeout_ms`、`compression_type` 传 `None` 还是 `"none"`）
13. **库名一致性**：全文库名统一，不出现 `kafka-python-ng` 与 `kafka-python` 混用
14. **跨库对照表准确**：若列出对照表，每一项都要实测确认，不凭文档推断
15. **默认值不臆断**：涉及"某库默认值是 X"的表述，必须实测读 `DEFAULT_CONFIG` 确认

### 四、本线专属：实测纪律（新增）

16. **结论必须本机实测**：吞吐、延迟、版本号、配置项默认值、行为差异——一律实测，不抄网上数字
17. **性能数字标注环境**：消息大小、分区数、acks、副本数、轮次、取值区间
18. **波动如实说明**：跑 3-5 次取范围，不取单次最优值充当结论
19. **不采信网上跑分**：公开基准数据互相矛盾（预研期已发现），只报本机实测值
20. **修不好的东西不留着假装修好**：显式记录"未修复 + 原因 + 替代方案"

### 四·补、测量方法核验（2026-09-23 课 13 新增）

> 立项依据：课 13 结课实战连续 **三次误诊**，全部源于"核验了，但核验方法本身是错的"。既有铁律「先核验再下结论」（mem_274a28_d4e6f35）只约束"要不要核验"，不约束"核验工具对不对"，此处补上。

- **M1 算速率前先确认分子分母**：曾把"空 poll 的时间"算进分子、"消息条数"当分母，得出"每条 poll 耗时 5007ms"的伪结论。速率 = 时间窗内到达量 ÷ 窗口长度，不是"等够 N 条的总耗时 ÷ N"。
- **M2 基准测试必须独占消费组**：测试脚本若复用运行中服务的 `group.id`，会触发持续 rebalance，吞吐被压到 1/700 以下。测吞吐一律用**独立 group.id**，并确认同组无其他成员（`list_consumer_groups` / `describe`）。
- **M3 "等够 N 条"是测量陷阱**：指纹是「N-1 条 + 恰好跑满超时上限」。课 13 实测 1999 条在 **0.002 秒**内到达，剩下 60 秒全在等那条永不到来的最后一条 —— 报出来的"33 条/秒"是假象，真实吞吐 112 万/秒。改用**固定时间窗统计到达量**。
- **M4 分区倾斜会让空分区拖死等待**：裸 `produce` 不传 key 时按 batch 落分区，实测 2000 条全落分区 1（`{0:0, 1:2000, 2:0, 3:0}`）。兜底等待前先 `get_watermark_offsets` 看各分区分布。
- **M5 数字异常时先怀疑尺子**：同一份代码换个测法，67/秒 vs 897564/秒（差 1.3 万倍）。**先复现测量方法，再优化被测代码**。
- **M6 无效修复必须回滚或改写注释**：课 13 基于误诊加了 lag 节流、异步提交两处改动，数字反降。保留的改动须把理由改回**解耦**等真实收益，并在注释里写明「曾误诊，勿引用该性能数字」。
