# 场景 8：我要"任务队列"语义（经典设计题）

**场景描述**：通知服务要消费"发送短信/推送"任务。需求是：① 处理失败的**单条**任务要重试，而不是整个分区卡住；② 消费者要能扩到 50 个实例，而 topic 只有 12 个分区；③ 失败的任务要能延迟 5 分钟后重投。

**🔒 先自己想 30 秒**：50 个消费者订阅 12 个分区的 topic，会有多少消费者在空转？"单条确认"在 Kafka 的位移模型里靠什么近似实现？

<details><summary>💡 提示（分维度想）</summary>

- **模型**：Kafka 的消费进度是**分区级位移**，不是"每条消息一个状态"。这个差别决定了什么？
- **阻塞**：一条消息失败就在本地无限重试，对同一分区后面的消息意味着什么？
- **新工具**：Kafka 4.x 有没有补上"队列语义"的官方方案？

</details>

<details><summary>📖 展开解法</summary>

### 解法一览（效果按题定制：单条确认 / 保序性）

| 解法 | 单条确认 / 保序性 | 代价 | 适用边界 |
|------|------------------|------|---------|
| **A · 重试 topic + 死信队列（DLQ）** | 单条确认：**近似**——失败单条被"搬走"而非就地确认，主干道不阻塞；保序性：**每分区内保序，但失败消息被抽出后重新入队，该条的相对顺序丢失** | 需要额外 topic 与投递逻辑；重试 topic 的延迟靠"消费者定时暂停/恢复"或分级 topic 近似实现，不是精确定时 | **通用正解**，几乎所有需要失败重试的场景都该有 |
| **B · Share Groups（KIP-932）** | 单条确认：**原生**——逐条 ack/nack，不再依赖分区级位移；保序性：**不保证**（同一分区可被多个消费者并发分片消费） | Kafka 4.2 官方升级说明已标为 production-ready；仍需核对客户端支持、`share.version`、内部 topic 副本因子/最小 ISR 与队列语义差异 | 已确认目标版本与客户端支持，且确有队列型负载 |
| **C · 换用传统 MQ 承接任务语义** | 单条确认：**原生**（ack 语义）；保序性：**按队列/路由键可控**（需选队列类型） | 多一个组件；事件流与任务队列分离，架构复杂度上升 | 任务语义是核心诉求（精确延迟、优先级、超高并发实例数） |
| **D · 消费者 `pause()` / `resume()` + 本地重试队列** | 单条确认：**无**（仍是分区级位移，靠"停下来"模拟）；保序性：**严格保序**（本分区不前进，后面全部等待） | **会阻塞该分区**——暂停期间后面的消息全部等待，与吞吐直接冲突 | 必须严格保序的小流量场景 |
| **E · 分级延迟 topic**（`retry-1m`、`retry-5m`、`retry-30m` + 到点才消费） | 单条确认：**近似**（同 A，失败单条转投另一 topic）；保序性：**跨档位后顺序不保证**（各档位独立消费） | 延迟粒度固定，不精确；需要按等级建 topic 并控制消费时机 | 可接受固定档位延迟的重试策略 |

**重试链路（A）的典型形态**：

```mermaid
flowchart TD
    A[(orders.notify<br/>主 topic)] --> B[消费者处理]
    B -->|成功| C[提交位移]
    B -->|可重试失败| D[(orders.notify.retry<br/>重试 topic)]
    B -->|不可恢复 / 超次数| E[(orders.notify.DLQ<br/>死信队列)]
    D -->|重试消费者<br/>延迟后再处理| B
    E --> F[人工/自动补偿<br/>必须有监控]
```

> 读图指引：主 topic 的消费者**永远不因单条失败而停下**——失败就转投别处并继续前进。这是与"本地死循环重试"最本质的区别。

### 各解法详解（思路 + 关键代码）

#### 解法 A · 重试 topic + 死信队列（通用正解）

**思路**：失败不阻塞主分区。主消费者遇到失败就转投重试 topic 并**提交位移继续前进**；重试 N 次仍失败则进 DLQ。

```mermaid
flowchart LR
  subgraph MAIN["主分区 P0（位移一路向前）"]
    M1["offset 100 处理失败"] --> M2["转投 retry topic"] --> M3["offset 101 继续"]
  end
  M2 --> R["orders.notify.retry<br/>attempt+1"]
  R --> R1{"attempt 是否超上限"}
  R1 -->|"未超"| R2["重新处理该单条"]
  R1 -->|"已超"| D["orders.notify.DLQ"]
  M3 -.->|"位移已前进<br/>重投的那条不再回到 P0 原位"| X["失效点：失败消息被抽离原分区后重新入队<br/>该条相对原分区的顺序丢失"]
  style X fill:#c62828,color:#ffffff
```

> 读图指引：正常路径是上排——第 100 条失败**不阻塞**，转投重试 topic 后立刻推进到 101，分区不会卡住；重试 topic 按 attempt 计数决定「再试一次」还是「进 DLQ」。**红框处为什么失效**：转投意味着这条消息离开了原分区，重投回来时是作为一条**新消息追加在重试 topic 尾部**的，它与原分区后续消息的先后关系不再成立——所以 A 拿到的是"单条重试"，代价是**丢掉该条与原分区的顺序**。

```java
// 主消费者：失败不重试，转投重试 topic 并提交位移
for (ConsumerRecord<String, Task> r : records) {
    try {
        process(r.value());
    } catch (RetryableException e) {
        int attempt = retryCount(r) + 1;
        if (attempt > MAX_RETRY) {
            // 超次数 → 死信队列，必须有监控告警
            dlqProducer.send(new ProducerRecord<>("orders.notify.DLQ", r.key(),
                withError(r.value(), e)));
            log.error("sent to DLQ after {} attempts, key={}", attempt, r.key());
        } else {
            retryProducer.send(new ProducerRecord<>("orders.notify.retry", r.key(),
                withAttempt(r.value(), attempt)));
        }
    }
    // 无论成功还是转投，都继续前进
}
consumer.commitSync();     // 关键：异常路径也要提交位移，否则毒药消息卡死分区
```

```java
// 重试消费者：消费 retry topic，失败则再投回 retry（次数 +1）
// 延迟通过"定时暂停"近似实现，不是精确定时
for (ConsumerRecord<String, Task> r : retryRecords) {
    try {
        process(r.value());
    } catch (RetryableException e) {
        if (retryCount(r) + 1 > MAX_RETRY) {
            dlqProducer.send(new ProducerRecord<>("orders.notify.DLQ", r.key(), r.value()));
        } else {
            retryProducer.send(new ProducerRecord<>("orders.notify.retry", r.key(),
                withAttempt(r.value(), retryCount(r) + 1)));
        }
    }
}
```

> ⚠️ **最关键的一行是 `commitSync()` 放在 catch 之外**：异常路径不提交位移 = 毒药消息死循环，整个分区卡死。这是本场景排名第一的坑。

#### 解法 B · Share Groups（KIP-932，状态与启用条件需核验）

**思路**：Kafka 4.2 起，KIP-932 的 share groups 作为 production-ready 能力提供队列语义——消费者数可超过分区数，支持单条确认。它改变的是消费模型本身，不能按传统 consumer group 的经验直接推断。

![分区级位移与记录级认领的差别](assets/scene-08-b-share-group-lock.svg)

> 读图指引：左右两边是同一批记录、同一批消费者，差别只在**"进度的单位"**——左边进度挂在**分区**上（P0 整体归 C0，位移只能整分区提交，所以并行度上限就是分区数 12）；右边进度挂在**记录**上（每条被某个消费者认领并 ack/nack，并行度由可认领记录数决定，单条失败只让这一条重投）。**红框处为什么失效**：确认粒度降到单条，就等于放弃了"同一分区内串行"这个前提——同一分区的记录会被不同消费者并发处理，**分区内顺序不再保证**；它换来的正是"消费者数可超过分区数 + 单条确认"。

```java
// 消费端：group.protocol 改为 share，而非传统的 consumer
props.put(ConsumerConfig.GROUP_PROTOCOL_CONFIG, "share");
props.put(ConsumerConfig.GROUP_ID_CONFIG, "notify-share-group");
// 单条确认模型：逐条 ack/nack，不再依赖分区级位移
```

```properties
# 目标版本确认支持并按官方要求启用 share groups 后参考
# 4.3 broker config 页面列出以下配置；生产前仍需核对 share.version 与内部 topic 条件
group.share.delivery.count.limit=5     # 投递次数上限，默认 5，范围 2-10
group.share.record.lock.duration.ms=30000
```

> ⚠️ 三条限制：① 需要 Kafka 4.2+，4.0/4.1 的 early access / preview 只是历史阶段；② 语义与传统 consumer group 不同，客户端需按 share group 协议接入，并确认 `share.version` 与 `__share_group_state` 的副本条件；③ 仍可能重复投递，消费端幂等照常需要。KIP 页面显示 Accepted 属提案状态，不应与官方 4.2 production-ready 说明混为一谈。

#### 解法 C · 换用传统 MQ 承接任务语义

**思路**：精确延迟、优先级、超高并发实例数是传统 MQ 的主场。硬用 Kafka 实现会得到一堆脆弱的自制组件。

```mermaid
flowchart LR
  P["订单服务"] -->|"事件广播给多个下游"| K["Kafka<br/>orders topic"]
  K --> K1["数据分析"]
  K --> K2["风控"]
  K --> K3["搜索索引"]
  P -->|"发短信/推送任务<br/>需要精确延迟 5 分钟、优先级、单条 ack"| MQ["传统 MQ<br/>延迟交换机 / 定时消息"]
  MQ --> W["通知 worker 池"]
  MQ -.->|"失效点：多一套中间件<br/>事件流与任务队列分离"| X["两套系统的可靠性边界、监控、升级<br/>各自维护，且跨系统一致性没人负责"]
  style X fill:#c62828,color:#ffffff
```

> 读图指引：正常路径是**同一条业务事实分流到两种载体**——订单事件作为"事件流"进 Kafka 广播给多个独立下游；"发短信"作为"命令/任务"进传统 MQ，由它承担精确延迟、优先级和单条 ack。**红框处为什么失效**：这个方案不是配置项能解决的，它把系统从"一套中间件"变成"两套"，于是多出一条没人负责的边界——Kafka 里的事件和 MQ 里的任务之间的**一致性、监控与升级节奏**都要额外设计；选它的判断标准是"任务语义是不是核心诉求"，而不是"Kafka 能不能凑出来"。

```java
// 事件流用 Kafka，任务队列用 MQ —— 各司其职
// 订单事件（流式，多下游广播）→ Kafka
producer.send(new ProducerRecord<>("orders", orderId, event));

// 发短信任务（队列语义，单条确认 + 延迟）→ RabbitMQ / RocketMQ
mqTemplate.convertAndSend("notify.delay.exchange", "notify.sms",
    smsTask, msg -> {
        msg.getMessageProperties().setDelay(5 * 60 * 1000);   // 精确延迟 5 分钟
        return msg;
    });
```

> ⚠️ 多一个组件 = 多一份运维。但对"精确延迟 / 优先级"这类需求，自研的复杂度远超引入一个 MQ。

#### 解法 D · pause()/resume() + 本地重试队列

**思路**：必须严格保序的小流量场景，暂停分区做本地重试。代价是**该分区完全停滞**。

```mermaid
flowchart TD
  N["P0 上第 100 条处理失败"] --> PAUSE["pause(P0)<br/>该分区停止拉取"]
  PAUSE --> L1["本地重试第 1 次"]
  L1 --> L2["本地重试第 2 次"]
  L2 --> L3["本地重试第 3 次"]
  L3 --> OK{"成功？"}
  OK -->|"成功"| RES["resume(P0)<br/>继续拉取 101、102…"]
  OK -->|"仍失败"| DLQ["sendToDlq(第 100 条)"]
  DLQ --> RES
  PAUSE -.->|"等待的正是 101、102…<br/>它们一直没被消费"| X["失效点：暂停时长计入 max.poll.interval.ms<br/>超时被踢出组 → 触发再均衡，停顿从 1 个分区扩散到全组"]
  style X fill:#c62828,color:#ffffff
```

> 读图指引：正常路径是"失败 → 暂停 → 本地重试 → 无论成功失败都 resume"，**顺序被完整保住**：第 100 条没处理完，101 之后的绝不放行。**红框处为什么失效**：pause 期间消费者没有真正处理新记录，一旦"暂停 + 本地重试"的总耗时超过 `max.poll.interval.ms`，这个实例会被踢出组并触发再均衡——本来是**一个分区**的等待，会变成**全组**的停顿，规模越大越糟。所以它只在小流量、且确实必须严格保序时才用。

```java
// 遇到失败：暂停该分区，本地重试
consumer.pause(List.of(partition));
try {
    retryLocally(record, 3);      // 本地重试 3 次
    consumer.resume(List.of(partition));
} catch (Exception e) {
    // 仍失败：不能一直停着，会超 max.poll.interval.ms 被踢出组
    sendToDlq(record);
    consumer.resume(List.of(partition));    // 必须恢复
}
```

> ⚠️ `pause()` 期间**后面的消息全部等待**，与吞吐直接冲突；且暂停时间计入 `max.poll.interval.ms`，超时会被踢出组引发再均衡。仅限小流量 + 必须保序的场景。

#### 解法 E · 分级延迟 topic

**思路**：用"到点才消费"的固定档位 topic 近似延迟重投。

![延迟档位与时间区间的对应关系](assets/scene-08-e-tiered-delay-tiers.svg)

> 读图指引：从下往上看——时间轴被切成**若干个区间**，每个区间对应一个档位 topic，失败次数 +1 就**往右跳一档**；上排用两个例子点出关键：想等 1 分 10 秒和想等 4 分 50 秒的两个任务，**会被压进同一个 5m 档**。**红框处为什么失效**：延迟精度不是"定时器精度"，而是**档位宽度**——档位一旦定了就锁死，业务要的"任意时间"表达不出来；而且档位越多，topic 和消费者就越多，运维面同步膨胀。它真正的价值在右下那句：不阻塞主分区、失败有出口，延迟只是"够用的近似"。

```bash
# 建固定档位的重试 topic
kafka-topics.sh --bootstrap-server localhost:9092 --create --topic notify.retry.1m  --partitions 6 --replication-factor 3
kafka-topics.sh --bootstrap-server localhost:9092 --create --topic notify.retry.5m  --partitions 6 --replication-factor 3
kafka-topics.sh --bootstrap-server localhost:9092 --create --topic notify.retry.30m --partitions 6 --replication-factor 3
```

```java
// 失败第 N 次投递到对应档位
String retryTopic = switch (attempt) {
    case 1 -> "notify.retry.1m";
    case 2 -> "notify.retry.5m";
    default -> "notify.retry.30m";
};
producer.send(new ProducerRecord<>(retryTopic, key, withAttempt(task, attempt)));

// 各档位的消费者用定时器控制"到点才消费"，实现近似延迟
```

> ⚠️ 延迟粒度固定（1m/5m/30m），做不到任意时间；档位 topic 数量会膨胀。

### 替代路线（非 Kafka 技术栈）

| 替代方案 | 思路 | 与 Kafka 方案的差异 |
|---|---|---|
| **RabbitMQ** | 用 ack、延迟交换机/插件、死信和消费者并发直接表达任务语义 | 单条确认、路由和延迟更自然；不适合把同一事件长期广播给多个独立下游 |
| **RocketMQ** | 使用消息重试、死信和定时消息承接投递任务 | 任务能力更完整，但需要接受另一套客户端、存储和运维模型 |

### 推荐路径

1. **先把 A 做扎实**：主 topic + 重试 topic + DLQ 三件套，配合"失败 N 次进 DLQ 并提交位移"的检测逻辑。这是**无论用不用 share groups 都该有的基线**。
2. **确认瓶颈是分区数限制**再考虑 B：如果消费者需要显著超过分区数，使用 Kafka 4.2+ 时按官方文档核对客户端、`share.version`、内部 topic 副本因子/最小 ISR，再做隔离验证（注意它改变的是消费模型，不只是“多几个实例”）。
3. **延迟需求**：E（分级延迟 topic）够用就用；需要精确到秒的任意延迟 → 走 C。
4. **D 仅限必须严格保序的小流量**：务必算清楚暂停时间对 `max.poll.interval.ms` 的影响。

### 什么情况下此方案不适用

- **需要精确延迟（任意时间）/ 优先级队列 / 大量消费者实例**：这些是传统 MQ 的主场。硬用 Kafka 实现会得到一堆脆弱的自制组件——回看 [08-实战经验.md](../08-实战经验.md) 的适用边界表，Kafka 在"纯任务队列"上本就不是最优解。
- **要求严格的逐条确认且不重复**：share groups 提供单条确认，但仍需消费端幂等兜底（至少一次语义下重复是必然）。

### 做错会踩的坑

- 失败就在本地无限重试 → 超过 `max.poll.interval.ms` 被踢出组，再均衡把停顿扩散到全组（[故障模式 7](../08-实战经验.md)）。
- 异常路径不提交位移 → 毒药消息死循环，整个分区卡死（[故障模式 2](../08-实战经验.md)）。
- DLQ 没有监控与告警 → 换个地方静默丢弃，问题被推迟到业务投诉时才暴露。
- 加消费者实例到 50 个却发现只有 12 个在工作 → 超出分区数的实例完全闲置（[故障模式 1](../08-实战经验.md)）。
