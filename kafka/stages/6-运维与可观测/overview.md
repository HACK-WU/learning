## 阶段目标

前 14 课解决的是「**消息怎么可靠、安全地流动**」，本阶段解决的是「**流动起来之后怎么盯着它、以及怎么在不中断服务的前提下改动它**」。

一句话概括：**从「敢上生产」走到「上生产之后活得下去」**。

| 端口 | 用途 |
|------|------|

| 17071-17073 | JMX Exporter HTTP（Prometheus 抓取） |
| 19990 | Prometheus UI |
| 13000 | Grafana UI |

> ⚠️ 端口选择避开了本机已被占用的端口段（9092-9094、19090 等被其他课程环境占用）。**如果你的机器上这些端口仍冲突，改 compose 里的映射即可**。

**关键实测数据**（均写入讲义）：

| 场景 | 实测结果 |
|------|----------|
| 单 broker 指标数量 | **1511** 个（随 topic 数增长；初创无 topic 时约 834） |
| 健康态 URP / ActiveControllerCount | **0** / **1** |
| 停一个 broker 后 URP | **0 → 53** |
| 停一个 broker 后 ISR | `1,2,3` → `1,2` |
| 停一个 broker 后优先副本不均衡 | **36** |
| 恢复后 URP | **0** |
| 分区重分配 | generate / execute / verify **三步全通** |
| 环境 Java 版本 | **21.0.6 LTS**（镜像内置；官方 4.3 推荐最新 LTS，撰写时为 25） |

## 核心结论

- **指标不缺，缺的是优先级**：一个 broker 暴露 834 个指标，官方已经标注了哪些「正常值应为 0」——**照这张表配告警就够了**，不需要全部监控。
- **`ActiveControllerCount` 的正常值是「恰好一个 broker 为 1」**，不是 0。写成 `> 0` 告警会一直触发。
- **消费延迟 lag 不在 broker 指标里**：broker 不维护消费者的实时读进度，需用 CLI（`consumer-groups --describe`）或客户端 `records-lag` 指标计算。
- **远程 JMX 默认禁用且默认无认证**：开启后未授权者不仅能监控**还能控制** broker，生产必须配安全。
- **加机器 ≠ 扩容**：新 broker 不会自动分到分区，必须显式执行重分配。
- **限流有两个坑**：①不跑 `--verify` 限流会**永久残留**；②限流值低于写入速率会导致复制**永不推进**。
- **官方推荐禁用应用级 fsync**：持久性靠副本而非本地磁盘同步，副本提供的保证强于本地刷盘。
- **XFS 优于 EXT4**（160ms vs 250ms+，且免调优）；EXT4 的性能选项在故障场景下不安全。
