## 第一幕 · 场景引入：一杯咖啡换来的 ErrImagePull

你本地写了个服务，`docker build -t myapp:1.0 .` 构建成功，`docker run myapp:1.0` 也跑得好好的。于是你顺手：

```bash
kubectl run myapp --image=myapp:1.0
kubectl get pod myapp
NAME    READY   STATUS         RESTARTS   AGE
myapp   0/1     ErrImagePull   0          15s
```

**宿主机明明有这个镜像，集群却说找不到。** 你去 `docker images` 再确认一遍——在啊。

这一课要回答的就是这个"明明"背后到底发生了什么。

本机实测的完整报错（真跑出来的）：

```text
Events:
  Normal   Scheduled  12s   Successfully assigned default/lab3-fail to kind-lab2-worker
  Normal   Pulling    11s   kubelet  Pulling image "kind-lab3-demo:1.0"
  Warning  Failed     10s   kubelet  Failed to pull image "kind-lab3-demo:1.0": failed to pull and unpack image
                                      "docker.io/library/kind-lab3-demo:1.0": failed to resolve reference
                                      "docker.io/library/kind-lab3-demo:1.0": pull access denied,
                                      repository does not exist or may require authorization:
                                      server message: insufficient_scope: authorization failed
  Warning  Failed     10s   kubelet  Error: ErrImagePull
  Normal   BackOff    10s   kubelet  Back-off pulling image "kind-lab3-demo:1.0"
  Warning  Failed     10s   kubelet  Error: ImagePullBackOff
```

请注意报错里那条完整路径：**kubelet 去 `docker.io/library/kind-lab3-demo:1.0` 找**。它**去公网找了一个不存在的仓库**，而不是去你的宿主机 Docker 找。

## 第二幕 · 认知冲突：三个"仓库"坐在不同的机器上

### 冲突：镜像到底存在哪？

先说清一个经常被混淆的事实：`docker build` 出来的镜像，存在**宿主机的 Docker 引擎**里。而 kubelet 要起 Pod 时，是从**节点自己的 containerd** 里找镜像的。

这两者之间**没有任何自动同步通道**。

```
宿主机 Docker 引擎                      节点容器（kind-lab2-worker）
/var/lib/docker                        /var/lib/containerd
┌──────────────────────┐               ┌──────────────────────┐
│  kind-lab3-demo:1.0  │  ← 没有连线 →  │    (空空如也)         │
└──────────────────────┘               └──────────────────────┘
       你 build 在这里                        kubelet 在这里找
```

本机实测的"空空如也"证据：Pod 失败时，两个节点内的计数都是 `0`：

```bash
docker exec kind-lab2-control-plane ctr -n k8s.io images ls -q | grep -c kind-lab3-demo   # 0
docker exec kind-lab2-worker          ctr -n k8s.io images ls -q | grep -c kind-lab3-demo   # 0
```

### 那 kubelet 为什么去公网找？

因为 `imagePullPolicy` 是 `IfNotPresent`（本机实测首启 Pod 的确切值）：

```bash
kubectl --context kind-kind-lab2 get pod lab3-fail -o jsonpath='{.spec.containers[0].imagePullPolicy}'
# IfNotPresent
```

`IfNotPresent` 的语义是：**本地没有就去 registry 拉**。本地（节点 containerd）没有 → 去 `docker.io` 拉 → 那里当然没有你私有的 `myapp:1.0` → `ErrImagePull`。

> 📌 注意 `myapp:1.0` 这种不带 registry 前缀的名字会被补全成 `docker.io/library/myapp:1.0`。这是 Docker 的默认规则，kind 只是继承了它。

### 关键区分：`ErrImagePull` vs `ErrImageNeverPull`

本机实测，把策略改成 `Never` 后报错完全不同：

```yaml
spec:
  containers:
  - name: c
    image: kind-lab3-nonexistent:9.9
    imagePullPolicy: Never
```

```text
NAME         READY   STATUS              RESTARTS   AGE
lab3-never   0/1     ErrImageNeverPull   0          8s

Events:
  Warning  ErrImageNeverPull  8s  kubelet  Container image "kind-lab3-nonexistent:9.9"
                                           is not present with pull policy of Never
```

**这是本课最实用的一条判据**：

| 状态 | 含义 | 说明什么 |
|------|------|---------|
| `ErrImagePull` | 本地没有，**去 registry 拉也失败了** | 节点有网络，但 registry 上没这个镜像（含鉴权问题） |
| `ErrImageNeverPull` | 本地没有，**且策略禁止拉取** | kubelet 根本**没去网络**，问题 100% 在你没把镜像送进去 |

看到 `ErrImageNeverPull`，你可以**立刻排除**网络与鉴权问题——它连试都没试。看到 `ErrImagePull`，说明网络通、请求发出去了，是"仓库那边没有"。

> 🎯 这条区分能省掉大量"是不是网络问题"的反复猜测。

## 第三幕 · 层层揭示：五种把镜像送进去的方式

| 方式 | 命令 | 送到哪 | 本课实测 |
|------|------|--------|---------|
| ① `kind load docker-image` | `kind load docker-image IMG --name CLUSTER` | **集群所有节点** | ✅ 实测 |
| ② `kind load image-archive` | `kind load image-archive IMG.tar --name CLUSTER` | **集群所有节点** | ⚠️ 未实测（机制同 ①，只是输入换成 tar） |
| ③ `ctr import`（手动） | `docker save` → 拷进节点 → `ctr -n k8s.io images import` | **仅指定节点** | ✅ 实测 |
| ④ 节点内 `ctr pull` | `ctr -n k8s.io images pull REGISTRY/IMG` | **仅指定节点** | ✅ 实测 |
| ⑤ 本地 registry | 起 registry 容器 + 配置节点信任 + 正常 push | 集群可拉取 | ⚠️ 未实测 |

### 方式 ①：`kind load docker-image`（主力）

本机实测：

```bash
kind load docker-image kind-lab3-demo:1.0 --name kind-lab2
```

输出（stderr）：

```text
Image: "kind-lab3-demo:1.0" with ID "sha256:b922c8..." not yet present on node "kind-lab2-worker", loading...
Image: "kind-lab3-demo:1.0" with ID "sha256:b922c8..." not yet present on node "kind-lab2-control-plane", loading...
real    0m1.398s
```

三个要点：

- **它送往集群里所有节点**（输出里 worker 和 control-plane 各一行）。这就是为什么 load 完后两个节点都数到 `1`。
- **耗时 1.398 秒**（一个 6.78 MB 的镜像）。镜像越大越慢，但同机传输比从公网拉快得多。
- `--name` 指定集群名。不指定则用默认集群名 `kind`（大概率不是你要的），**这是个常见误用**。

`kind load docker-image --help` 的完整参数（本机实测）：

```text
Flags:
  -h, --help            help for docker-image
  -n, --name string     the cluster context name (default "kind")
      --nodes strings   comma separated list of nodes to load images into
```

注意 `--nodes`：如果只想送到部分节点（比如你明确知道 Pod 会调度到哪），可以用它。默认是全部。

### 方式 ③：`docker save` + `ctr import`（精准投放）

这条路适合"只想把镜像放到某一个节点"。本机实测的完整流程与一个**踩坑**：

```bash
# 1. 保存为 tar
docker save kind-lab3-alt:2.0 -o /root/kind-lab3-alt.tar

# 2. 拷进节点 —— ⚠️ 本机实测 docker cp 静默失败（见下）
#    改用 stdin 管道，成功
cat /root/kind-lab3-alt.tar | docker exec -i kind-lab2-worker sh -c "cat > /tmp/piped.tar"

# 3. 节点内导入（注意命名空间！）
docker exec kind-lab2-worker ctr -n k8s.io images import /tmp/piped.tar

# 4. 确认
docker exec kind-lab2-worker ctr -n k8s.io images ls -q | grep kind-lab3-alt
# docker.io/library/kind-lab3-alt:2.0
```

导入输出（本机实测）：

```text
docker.io/library/kind-lab3-alt:2.0   saved
application/vnd.oci.image.index.v1+json sha256:2ecca82a...
Importing  elapsed: 0.1 s  total: 0.0 B
```

**关于 `docker cp` 的坑（本机实测）**：`docker cp /root/x.tar kind-lab2-worker:/tmp/` 返回退出码 **0**（报告成功），但节点内 `ls /tmp/` 是空的——文件根本没进去。改用 `cat | docker exec -i ... sh -c "cat > /tmp/x.tar"` 立刻成功。这是本机 Docker 环境的一个静默失败，不一定是 kind 的问题，但**你应该知道 cp 不一定可靠，且它不会报错**。

> ⚠️ 这条属本机环境特性，换环境未必复现，故不上升为通用结论，仅作"若 cp 后节点内找不到文件，改用管道"的提示。

**最关键的差异（本机实测）**：`ctr import` 只影响**你指定的那个节点**：

```bash
docker exec kind-lab2-control-plane ctr -n k8s.io images ls -q | grep -c kind-lab3-alt   # 0
docker exec kind-lab2-worker          ctr -n k8s.io images ls -q | grep -c kind-lab3-alt   # 1
```

所以用它起 Pod 时，**必须钉住 nodeName**（本机实测用 `--overrides='{"spec":{"nodeName":"kind-lab2-worker"}}'`），否则调度到另一个节点就会 `ErrImagePull`。

### 方式 ④：节点内 `ctr pull`（借用节点的网络出口）

节点容器**有独立的网络出口**，可以自己从公网拉。本机实测：

```bash
docker exec kind-lab2-worker ctr -n k8s.io images pull docker.io/library/alpine:3.20
```

输出（本机实测）：

```text
Completed pull from OCI Registry (docker.io/library/alpine:3.20)  elapsed: 7.8 s  total: 3.5 Mi (459.0 KiB/s)
```

耗时 7.8 秒、3.5 MiB、约 459 KiB/s——**这就是它相比 `kind load` 的代价**：走公网，慢得多，且受网络影响。

**这条路的价值**在于：镜像太大不适合 `kind load`（load 需要先把整个镜像从 Docker 导出再灌进去，大镜像会非常慢），或者你本来就该从 registry 拉（比如 CI 场景）。

### 五种方式的取舍表

| 场景 | 推荐 | 原因 |
|------|------|------|
| 本地开发，镜像不大（< 100 MB） | ① `kind load docker-image` | 一条命令送到所有节点，最快 |
| 镜像很大（GB 级） | ④ 节点内 `ctr pull`，或 ⑤ 本地 registry | `kind load` 的导出/导入开销随体积线性增长 |
| 只想放到特定节点 | ③ `ctr import` + `nodeName` | 精准，但要自己钉节点 |
| 多节点集群 + 只想省一次网络传输 | ④ 在**每个**节点各 pull 一次 | 注意：`ctr pull` 不跨节点同步 |
| 团队/CI 复现 | ⑤ 本地 registry | 唯一"标准"方案，但配置最重 |

> ⚠️ 方式 ⑤ 本课**未实测**（需要起 registry 容器 + 配 `containerdConfigPatches`——属环境改动，本课未做）。取舍表里对它的描述是基于机制推断，标 `⚠️ 未实测`。

## 第四幕 · 实操验证：从 ErrImagePull 到 Running

> 🔐 **环境改动声明**：本幕在 `kind-lab2` 上真实构建镜像、起 Pod、加载镜像。**不触碰**其他集群。幕末附清理命令。

### 第 1 步：构建一个自定义镜像

```bash
mkdir -p /tmp/kind-lab3
cat > /tmp/kind-lab3/Dockerfile << 'DOCKERFILE'
FROM busybox:1.36
RUN mkdir -p /app && echo "hello from kind-lab3 custom image" > /app/message.txt
CMD ["sh", "-c", "cat /app/message.txt && sleep 3600"]
DOCKERFILE
docker build -t kind-lab3-demo:1.0 /tmp/kind-lab3
```

本机实测结果：

```text
-- 宿主机镜像确认 --
kind-lab3-demo:1.0 | 6.78MB | b922c8315656

-- 镜像内容验证（在宿主机跑一下）--
hello from kind-lab3 custom image
```

> 📌 **踩坑提示**：我第一次写 Dockerfile 时漏了 `mkdir -p /app`，直接 `echo ... > /app/message.txt`——构建报 `exit code: 1`。**busybox 的 `/app` 目录不存在，重定向会失败**。这个小坑与 kind 无关，但很典型。

### 第 2 步：确证节点内没有这个镜像

```bash
docker exec kind-lab2-control-plane ctr -n k8s.io images ls -q | grep -c kind-lab3-demo   # 0
docker exec kind-lab2-worker          ctr -n k8s.io images ls -q | grep -c kind-lab3-demo   # 0
```

**两个 0**。这就是"宿主机有、集群没有"的直接证据。

### 第 3 步：直接 run，复现 ErrImagePull

```bash
kubectl --context kind-kind-lab2 run lab3-fail --image=kind-lab3-demo:1.0 --restart=Never
sleep 12
kubectl --context kind-kind-lab2 get pod lab3-fail
kubectl --context kind-kind-lab2 describe pod lab3-fail
```

本机实测输出：

```text
NAME        READY   STATUS         RESTARTS   AGE   IP           NODE
lab3-fail   0/1     ErrImagePull   0          12s   10.244.1.2   kind-lab2-worker
```

`describe` 的 Events 见第一幕引用的那段。**注意报错里的 `docker.io/library/kind-lab3-demo:1.0`**——kubelet 去了公网。

### 第 4 步：`kind load` 送进去

```bash
kind load docker-image kind-lab3-demo:1.0 --name kind-lab2
```

本机实测 1.398 秒完成，两个节点各一行 `loading...`。

### 第 5 步：观察 Pod 自动恢复

`imagePullPolicy` 是 `IfNotPresent`，所以镜像到位后 kubelet 会在 backoff 重试时用本地镜像。本机实测的恢复过程（每 10 秒探测一次）：

```text
第 1 次探测: phase=Pending state={"waiting":{"reason":"ErrImagePull"}}
第 2 次探测: phase=Pending state={"waiting":{"reason":"ErrImagePull"}}
第 3 次探测: phase=Running
```

```text
NAME        READY   STATUS    RESTARTS   AGE
lab3-fail   1/1     Running   0          52s
```

容器日志（验证跑的是**我们自己的镜像内容**）：

```bash
kubectl --context kind-kind-lab2 logs lab3-fail
# hello from kind-lab3 custom image
```

> 🎯 **闭环完成**：`ErrImagePull`（本地没有 + 去公网失败）→ `kind load`（送进所有节点）→ kubelet backoff 重试时发现本地已有 → `Running`，日志打出我们自己写进去的字符串。
>
> **注意它自动恢复了，不需要删 Pod 重建**。因为 `IfNotPresent` 在下次重试时会重新检查本地。这是个容易忽视的好消息——很多人失败后急着删 Pod，其实等一等就好。

### 第 6 步：验证 `ErrImageNeverPull`

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: lab3-never
spec:
  containers:
  - name: c
    image: kind-lab3-nonexistent:9.9
    imagePullPolicy: Never
```

本机实测：

```text
lab3-never   0/1     ErrImageNeverPull
Events:
  Warning  ErrImageNeverPull  kubelet  Container image "kind-lab3-nonexistent:9.9"
                                        is not present with pull policy of Never
```

对比第 3 步的 `ErrImagePull`——**报错名字不同，含义完全不同**。前者是"没去网络直接判死"，后者是"去了网络但失败"。

### 第 7 步：`ctr import` 精准投放（含 `docker cp` 的坑）

```bash
# 造第二个镜像
docker build -t kind-lab3-alt:2.0 /tmp/kind-lab3alt
docker save kind-lab3-alt:2.0 -o /root/kind-lab3-alt.tar
ls -lh /root/kind-lab3-alt.tar
# -rw------- 1 root root 2.2M

# 拷进节点：docker cp 静默失败，改用管道
cat /root/kind-lab3-alt.tar | docker exec -i kind-lab2-worker sh -c "cat > /tmp/piped.tar"
docker exec kind-lab2-worker ls -lh /tmp/piped.tar
# -rw-r--r-- 1 root root 2.2M

# 导入
docker exec kind-lab2-worker ctr -n k8s.io images import /tmp/piped.tar
```

导入成功后确认、起 Pod（必须钉 worker）：

```bash
kubectl --context kind-kind-lab2 run lab3-alt --image=kind-lab3-alt:2.0 --restart=Never \
  --overrides='{"spec":{"nodeName":"kind-lab2-worker"}}' \
  --command -- sh -c "cat /app/message.txt && sleep 3600"
```

本机实测：

```text
NAME       READY   STATUS    RESTARTS   AGE
lab3-alt   1/1     Running   0          10s
# 日志：hello from ALT image v2
```

**同时也验证了"只进了一个节点"**：

```bash
docker exec kind-lab2-control-plane ctr -n k8s.io images ls -q | grep -c kind-lab3-alt   # 0
docker exec kind-lab2-worker          ctr -n k8s.io images ls -q | grep -c kind-lab3-alt   # 1
```

### 第 8 步：节点内 `ctr pull`

```bash
docker exec kind-lab2-worker ctr -n k8s.io images pull docker.io/library/alpine:3.20
```

本机实测 7.8 秒拉到（3.5 MiB），随后用 alpine 起 Pod 也 `Running`，日志 `hello from alpine via ctr pull`。

### 第 9 步：`extraPortMappings`（课 2 遗留项的兑现）

课 2 说"NodePort 暴露到宿主机"归课 3 做。这里补上，配置文件：

```yaml
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
name: kind-lab3port
nodes:
  - role: control-plane
    extraPortMappings:
      - containerPort: 30080
        hostPort: 30080
        listenAddress: "127.0.0.1"
        protocol: TCP
```

创建后端口映射（本机实测）：

```bash
docker port kind-lab3port-control-plane
# 6443/tcp  -> 127.0.0.1:35743
# 30080/tcp -> 127.0.0.1:30080
```

起 Pod + Service（**关键：把 `nodePort` 固定成 30080**，与映射对齐）：

```yaml
apiVersion: v1
kind: Service
metadata:
  name: web
spec:
  type: NodePort
  selector:
    run: web
  ports:
    - port: 80
      targetPort: 80
      nodePort: 30080
```

本机实测，从宿主机访问：

```bash
curl -s http://127.0.0.1:30080/
# NODEPORT-OK
```

> 📌 **这里我踩过一次坑，值得记**：第一次验证时我没固定 `nodePort`，kubelet 把 NodePort 分配成了 `30585`，而我映射的是 `30080`——`curl` 失败。`extraPortMappings` 映射的是**固定的容器端口**，所以你必须让 Service 的 `nodePort` 与之对齐（或用 `nodePort` 范围映射）。**映射端口和实际分配端口不一致时，映射等于没做。**

验证完立即 `kind delete cluster --name kind-lab3port`。

```bash
kubectl --context kind-kind-lab2 delete pod lab3-fail lab3-never lab3-alt lab3-alpine
```

## 第五幕 · 体系收束

### 一条因果链（背下来）

```text
docker build  →  镜像只在宿主机 Docker
                      ↓（没有自动通道）
                 节点 containerd 没有
                      ↓
        kubelet 按 imagePullPolicy 决定：
         ├─ IfNotPresent → 去 docker.io 找 → ErrImagePull（私有镜像必然失败）
         └─ Never        → 不去网络 → ErrImageNeverPull
                      ↓
        修复：kind load（送所有节点）或 ctr import/ctr pull（送单个节点）
```

### 三条判据

第一，看到 `ErrImageNeverPull` 就**别查网络了**，问题一定是镜像没送进去。看到 `ErrImagePull` 才是"去了网络但没找到"。

第二，`kind load` 送**所有节点**，`ctr import` / `ctr pull` 只送**当前节点**。用后者时记得钉 `nodeName`。

第三，**报错里出现的完整镜像名是重要线索**。如果你看到 `docker.io/library/myapp:1.0`，说明 kubelet 在往公网找你的私有镜像，问题在"镜像没送进去"，不在 YAML。

### 一句话记住

> **`docker build` 和 `kubectl run` 之间没有自动管道——镜像必须被显式送进节点；送进去之后别忘了 `imagePullPolicy` 决定 kubelet 会不会又跑去找公网。**

### 常见误区

1. **"`docker images` 里有，集群就能用"** —— 错。两个独立仓库（课 1 已证，本课再证）。
2. **"`kind load` 要指定节点"** —— 默认送**所有**节点。要精确控制才用 `--nodes`。
3. **"Pod 报 ErrImagePull 就要删掉重建"** —— 不一定。`IfNotPresent` 下，镜像到位后 kubelet 会在下次 backoff 重试时自动恢复（本课实测第 5 步）。
4. **"`ctr import` 和 `kind load` 等价"** —— 差在**作用范围**：前者单节点，后者全节点。
5. **"`ctr` 命令不用管命名空间"** —— 必须 `-n k8s.io`。用 `default` 命名空间导入了，kubelet 也看不见（本课实测 `default` 命名空间恒为 0）。
6. **"NodePort 配了 `extraPortMappings` 就能从宿主机访问"** —— 还要让 Service 的 `nodePort` 与映射端口**对齐**（本课实测踩坑）。

### 小测（自测，做完再看课 4）

1. Pod 状态是 `ErrImageNeverPull`，你应该优先检查什么？为什么不用查网络？
2. 三节点集群，你用 `ctr import` 把镜像导入了 worker1，然后起 Pod，Pod 被调度到 worker2 会怎样？
3. `kind load docker-image` 和 `ctr pull` 在"耗时"上的根本差异来自哪里？
4. 你配了 `extraPortMappings: containerPort: 30080`，但 Service 分配到的 NodePort 是 `31234`，从宿主机能访问吗？

<details>
<summary>参考答案</summary>

1. 优先检查"镜像有没有被送进这个节点"（`ctr -n k8s.io images ls`）。因为 `Never` 策略下 kubelet **不会发起任何网络请求**，网络/鉴权问题在这个状态下不可能存在——报错本身就是"我没去试，因为策略禁止"。
2. worker2 上没有这个镜像，`imagePullPolicy: IfNotPresent` 会去公网拉 → `ErrImagePull`。修法：给 Pod 加 `nodeName`/`nodeSelector` 钉住 worker1，或改用 `kind load`（送所有节点）。
3. `kind load` 走**本机传输**（Docker 导出 → 灌进节点 containerd，实测 6.78 MB 用 1.4 秒）；`ctr pull` 走**公网**（实测 3.5 MiB 用 7.8 秒，约 459 KiB/s）。差异来自"是否经过网络、是否受带宽限制"。
4. 不能。`extraPortMappings` 映射的是容器的 `30080` 端口，而流量实际到达的是 `31234`——**端口不对齐，映射无效**。要让 Service 的 `nodePort` 固定为 `30080`。

### 本次实验中踩的坑（对学员可见）

- **Dockerfile 漏建父目录**：`echo ... > /app/message.txt` 在 busybox 下因 `/app` 不存在而 `exit code: 1`。修法：`RUN mkdir -p /app && echo ...`。
- **`docker cp` 静默失败**（本机环境特性）：退出码 `0` 但节点内无文件。改用 `cat <tar> | docker exec -i <node> sh -c "cat > /tmp/x.tar"` 立即成功。此坑不上升为通用结论（换环境未必复现），已在讲义中标为"本机环境特性"。
- **`extraPortMappings` 与 NodePort 不对齐**：第一次没固定 `nodePort`，实际分配 `30585` 而映射的是 `30080`，`curl` 失败。**映射端口必须与 Service 的 `nodePort` 一致**。

### 补充说明（复审新增）

**如何自查"镜像是否真的进去了"**：对比节点内镜像数。Pod 用过的镜像会**留在节点内**（本机实测 `kind-lab2` 的 worker 从 24 增至 30）。所以：

```bash
docker exec kind-lab2-worker ctr -n k8s.io images ls -q | wc -l
```

这个数字只增不减（除非手动删），可作为"我确实送进去了"的旁证。

### 复验脚本的坑（供后续课程复用）

- **WSL 管道传脚本的行尾 `\r` 会污染重定向文件名与带数字参数的命令**（课 2 已记，本课再次遇到）。本课改用**写 `.sh` 到 Windows 侧 → `wsl -e bash /mnt/d/.../.xx.sh`** 的方式，规避彻底。
- **`docker save -o` 的路径由 WSL 侧解析，而 `docker cp` 的源路径由 Docker 守护进程解析**——两者视角不一致时会出现"文件明明在"却 cp 不上去的现象。
