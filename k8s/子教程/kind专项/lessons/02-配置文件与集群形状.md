## 第一幕 · 场景引入：命令行 flag 的天花板

课 1 你学会了这么建集群：

```bash
kind create cluster --name demo
```

但很快你会撞上三堵墙：

1. **想要三节点**——`--name` 之外还能传什么？翻 `--help`，只有 `--image` / `--kubeconfig` / `--name` / `--retain` / `--wait`（本机实测全量 flag）。**没有任何一个能指定节点数**。
2. **想要固定 K8s 版本**——`--image` 能换镜像，但版本和镜像 tag 的对应关系得自己去查，且一旦忘了传，集群就悄悄用了 latest。
3. **想从宿主机 `localhost:30080` 访问集群里的 NodePort**——命令行**完全做不到**。

所以 kind 的正确用法是：**命令行 flag 只负责"最小可用"，一切形状问题交给配置文件。**

本机实测的 flag 全集：

```bash
kind create cluster --help
```

```text
      --config string       path to a kind config file
  -h, --help                help for cluster
      --image string        node docker image to use for booting the cluster
      --kubeconfig string   sets kubeconfig path instead of $KUBECONFIG or $HOME/.kube/config
  -n, --name string         cluster name, overrides KIND_CLUSTER_NAME, config (default kind)
      --retain              retain nodes for debugging when cluster creation fails
      --wait duration       wait for control plane node to be ready (default 0s)
```

**注意 `--config` 这一行**——它就是本节课的全部内容。另外注意 `--name` 的说明里有个 **`overrides ... config`**：命令行的 `--name` 会**覆盖**配置文件里的 `name`。这个优先级关系后面会专门踩一次。

## 第二幕 · 认知冲突：配置文件不是"参数补充"，而是"期望状态"

### 冲突一：为什么要这么重的一个配置文件？

看一个最小配置文件：

```yaml
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
name: kind-lab2
nodes:
  - role: control-plane
  - role: worker
```

不过六行，但有三件事值得停下来想：

- **`kind: Cluster` + `apiVersion`**：这是标准的 **K8s 风格声明式对象**（和 `kind: Pod` / `kind: Deployment` 同一套 schema 机制）。kind 复用了 K8s 的"声明期望状态"哲学，而不是发明一套自己的 `--node-count` 参数。
- **`nodes` 是个列表**，元素是**角色**而非容器：`role: control-plane` / `role: worker`。你声明"我要一个控制面和一个工作节点"，kind 负责翻译成两个容器。
- **列表长度就是节点数**。想要五节点？写五个 `- role: worker`。

### 冲突二：既然是"声明期望状态"，能不能改了就生效？

这是 kind 最容易踩的坑，也是**本课的核心结论**：

> **配置文件只在 `create` 那一刻被读取一次。集群建好之后，改配置文件对现有集群毫无影响。**

原因在课 1 已经埋好了：集群的"形状"被**物理固化**成了容器集合。控制面容器的数量、它们挂在 `kind` 网络上的拓扑、kubeconfig 里的条目——这些都是一次性产物。kind **没有**"给运行中集群加一个节点"的命令。

所以 kind 的配置变更流程永远是三步：

```text
改 YAML → kind delete cluster --name X → kind create cluster --config X.yaml
```

> ⚠️ 注意这与 `kubeadm join` 的思维完全不同。真机集群可以动态加节点，kind 集群只能重建。这也是课 1 说的"容器伪装"的代价。

### 冲突三：`--name` 和配置文件里的 `name`，谁赢？

`--help` 里写着 `--name` **overrides ... config**。本机实测的间接证据：我用配置文件 `name: kind-lab2` 建集群，随后 `kind get clusters` 输出里是 `kind-lab2`——但生成的 **context 名是 `kind-kind-lab2`**（双 `kind-` 前缀）。

这说明 name 在多个环节被拼接使用：集群名 `kind-lab2`、容器名 `kind-lab2-control-plane`、context 名 `kind-kind-lab2`。**记住这条拼接规律，课 4 排查"context 连错集群"时会用到。**

## 第三幕 · 层层揭示：配置文件字段地图

`kind: Cluster` 配置文件的顶层字段（按使用频率排序）：

| 字段 | 作用 | 本课是否实操 |
|------|------|-------------|
| `name` | 集群名（可被 `--name` 覆盖） | ✅ 实测 |
| `nodes[].role` | 节点角色，决定是控制面还是工作节点 | ✅ 实测 |
| `nodes[].image` | 单节点级镜像覆盖（不写则用全局默认） | ⚠️ 未实测 |
| `nodes[].extraPortMappings` | 宿主机端口 → 节点端口映射（NodePort 场景核心） | ⚠️ 未实测 |
| `nodes[].labels` | 给节点打 K8s label | ⚠️ 未实测 |
| `nodes[].kubeadmConfigPatches` | 注入 kubeadm 配置片段（改 kubelet 参数等） | ⚠️ 未实测 |
| `networking.ipFamily` | IPv4 / IPv6 / dual | ⚠️ 未实测 |
| `networking.podSubnet` | Pod 网段（默认 `10.244.0.0/16`） | ⚠️ 未实测 |
| `networking.serviceSubnet` | Service 网段（默认 `10.96.0.0/16`） | ⚠️ 未实测 |
| `networking.apiServerPort` | 固定宿主机映射端口（默认**随机**） | ⚠️ 未实测 |
| `featureGates` | 特性门控 | ⚠️ 未实测 |

> ⚠️ 上表除 `name` 与 `nodes[].role` 外，**均为本课未逐项实测的字段**。课 2 只把"形状"讲透；端口映射的完整实操会在课 3 与镜像链路一起做（届时需要真实起 Pod 才能验证 `extraPortMappings`）。上表仅作**字段地图**给出，让你知道"想要的效果该改哪个键"，不代表已验证可用。

### `role` 的语义（本课实测）

建的 `kind-lab2` 集群，两个节点的 label 实测如下：

```bash
kubectl --context kind-kind-lab2 get nodes --show-labels
```

```text
kind-lab2-control-plane   ... node-role.kubernetes.io/control-plane=,node.kubernetes.io/exclude-from-external-load-balancers=
kind-lab2-worker          ... kubernetes.io/hostname=kind-lab2-worker,kubernetes.io/os=linux
```

差异非常干净：

- 控制面节点带 `node-role.kubernetes.io/control-plane=`——所以 `kubectl get nodes` 的 `ROLES` 列显示 `control-plane`。
- 工作节点**只有基础 label**（arch/os/hostname），没有任何 role label——所以 `ROLES` 列显示 `<none>`。

> 📌 `<none>` **不是错误**。它是"这个节点没有被打 role label"的正常表现。默认情况下 kind 的工作节点上**可以调度普通 Pod**——因为控制面才带 taint，工作节点不带。

## 第四幕 · 实操验证：从零建一个两节点集群

> 🔐 **环境改动声明**：本幕会**真实创建**一个名为 `kind-lab2` 的新集群（1 控制面 + 1 工作节点），占用约 3 GB 磁盘（两个节点容器）。**不触碰**你已有的 `k8s-c1` / `k8s-c1-calico` / `otel-l11`。幕末附删除命令。

### 第 1 步：写配置文件

```bash
mkdir -p /tmp/kind-lab2
cat > /tmp/kind-lab2/kind-2node.yaml << 'YAML'
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
name: kind-lab2
nodes:
  - role: control-plane
  - role: worker
YAML
```

### 第 2 步：创建集群

```bash
kind create cluster --config /tmp/kind-lab2/kind-2node.yaml --wait 60s
```

`--wait 60s` 让 kind 等控制面就绪（最多 60 秒）再返回，省去你手敲 `kubectl get nodes` 轮询。

本机实测输出（关键阶段）：

```text
Creating cluster "kind-lab2" ...
 • Ensuring node image (kindest/node:v1.34.0) 🖼  ...
 ✓ Ensuring node image (kindest/node:v1.34.0) 🖼
 • Preparing nodes 📦 📦   ...
 ✓ Preparing nodes 📦 📦
 • Writing configuration 📜  ...
 ✓ Writing configuration 📜
 • Starting control-plane 🕹️  ...
 ✓ Starting control-plane 🕹️
 • Installing CNI 🔌  ...
 ✓ Installing CNI 🔌
 • Installing StorageClass 💾  ...
 ✓ Installing StorageClass 💾
 • Joining worker nodes 🚜  ...
 ✓ Joining worker nodes 🚜
 • Waiting ≤ 1m0s for control-plane = Ready ⏳  ...
 ✓ Waiting ≤ 1m0s for control-plane = Ready ⏳
 • Ready after 10s 💚
Set kubectl context to "kind-kind-lab2"
```

**这段输出本身就是教案**，七个阶段对应七件事：

| 阶段 | 做了什么 | 观察点 |
|------|---------|--------|
| Ensuring node image | 拉/复用 `kindest/node:v1.34.0` | 镜像本地已有则跳过 |
| Preparing nodes | 起容器、配网络 | 📦📦 两个盒子 = 两个节点 |
| Writing configuration | 生成 kubeadm 配置与证书 | 对应课 1 的 `/etc/kubernetes/` |
| Starting control-plane | 起 apiserver / etcd / scheduler | |
| Installing CNI | 装 kindnetd | 默认 CNI，够用但功能薄（对比 `k8s-c1-calico`） |
| Installing StorageClass | 装 local-path-provisioner | 对应课 1 节点内看到的 `local-path-provisioner` 镜像 |
| Joining worker nodes | 工作节点 `kubeadm join` | 多节点专属阶段 |

注意最后一行 `Set kubectl context to "kind-kind-lab2"`——**kind 会自动切换你的当前 context**。这是个"惊喜"也是个坑：你建完新集群，`kubectl` 就指向它了，之前在看 `k8s-c1` 的终端会默默换台。

### 第 3 步：验证节点数 = 配置文件的列表长度

```bash
kind get clusters
docker ps -a --filter "label=io.x-k8s.kind.cluster=kind-lab2" \
  --format "{{.Names}} | {{.Status}}"
```

本机实测输出：

```text
k8s-c1
k8s-c1-calico
kind-lab2
otel-l11
```

```text
kind-lab2-worker        | Up 29 seconds
kind-lab2-control-plane | Up 29 seconds
```

**两个容器，对应配置文件里的两个列表项**。课 1 学的 label 过滤在这里第一次派上实战用场：用 `io.x-k8s.kind.cluster=kind-lab2` 精确捞出这一个集群的节点，不受其他三个集群干扰。

### 第 4 步：验证节点就绪与 role 语义

```bash
kubectl --context kind-kind-lab2 get nodes
```

本机实测输出：

```text
NAME                      STATUS   ROLES           AGE   VERSION
kind-lab2-control-plane   Ready    control-plane   36s   v1.34.0
kind-lab2-worker          Ready    <none>          26s   v1.34.0
```

三个观察：

- `ROLES` 列的 `control-plane` vs `<none>` 就是第三幕讲的那个 label 差异。
- 工作节点 `AGE 26s` 比控制面 `36s` 小 10 秒——**这就是"Joining worker nodes"阶段在时间轴上的投影**。
- 两个节点 `VERSION` 都是 `v1.34.0`——来自同一个 `kindest/node:v1.34.0` 镜像。

### 第 5 步：验证端口是动态分配的

```bash
grep -n "server:" ~/.kube/config
```

本机实测输出（四个集群，四个不同端口）：

```text
5:    server: https://127.0.0.1:36757     ← 某集群
9:    server: https://127.0.0.1:40271     ← 某集群
13:    server: https://127.0.0.1:45145    ← k8s-c1（课 1 主角）
17:    server: https://127.0.0.1:36343    ← kind-lab2（本次新建）
```

**结论**：kind 每个集群都分一个**随机的宿主端口**（默认行为）。这带来两个实际后果：

- 端口每次重建都会变。你做端口转发、写脚本、配 CI 缓存时，**不能硬编码端口**。
- 想要固定端口？配置文件的 `networking.apiServerPort` 是答案（本课未实测，标 `⚠️ 未实测`）。

配合验证：

```bash
docker port kind-lab2-control-plane
# 应输出：6443/tcp -> 127.0.0.1:36343
```

（此条与课 1 的闭环一致：`docker port` 的输出必然等于 kubeconfig 里的 `server` 端口。）

### 第 6 步：验证跨集群操作

```bash
kubectl --context kind-kind-lab2 get nodes
kubectl --context kind-k8s-c1 get nodes
```

用 `--context` 显式指定，可以在同一终端里操作不同集群，互不干扰。注意 context 名的拼接规则是 **`kind-<集群名>`**——`kind-lab2` 对应 `kind-kind-lab2`，那个重复的 `kind-` 不是笔误。

### 第 7 步：删除（本课必须动手）

```bash
kind delete cluster --name kind-lab2
```

确认清理干净：

```bash
kind get clusters          # kind-lab2 应消失，其余三个保留
kubectl config get-contexts  # kind-kind-lab2 条目应消失
docker ps -a --filter "label=io.x-k8s.kind.cluster=kind-lab2"  # 应为空
```

> ⚠️ **`kind delete` 也会顺手把你的 context 切走**（如果删的正是当前 context，kind 会切到另一个）。删完最好重新 `kubectl config use-context <你要的>`，别以为终端没变。

## 第五幕 · 体系收束

### flag 与 config 的分工

| 需求 | 用什么 |
|------|--------|
| 起个最小集群（1 控制面） | `kind create cluster --name X` |
| 指定节点数 / 角色分布 | **配置文件**（`nodes` 列表） |
| 钉死 K8s 版本 | `--image kindest/node:vX.Y.Z` 或配置文件的 `image` |
| NodePort 暴露到宿主机 | **配置文件**（`extraPortMappings`） |
| 固定 apiserver 端口 | **配置文件**（`networking.apiServerPort`） |
| 改 kubelet 启动参数 | **配置文件**（`kubeadmConfigPatches`） |

**一句话**：命令行 = 快捷方式，配置文件 = 唯一能表达"形状"的地方。

### 三条决策规则

1. **改形状 = 重建**。kind 没有动态加节点能力，别指望 `kubectl edit` 能改出物理节点。
2. **版本钉死写在配置文件里**，别依赖 `--image` 每次手打（忘了就悄悄用默认镜像）。
3. **端口不要硬编码**，除非你显式配了 `apiServerPort`。

### 一句话记住

> **kind 的集群形状（节点数、角色、网络、端口）是配置文件在 `create` 那一刻一次性固化的产物；配置文件是"施工图"，不是"遥控器"。**

### 常见误区

1. **"改配置文件后 `kind create` 一下就会更新"** —— 错。同名集群已存在时会**报错**，必须先 `delete`。
2. **"`ROLES` 显示 `<none>` 说明节点有问题"** —— 错。那是工作节点的正常表现（没有 role label）。
3. **"`--name` 和配置文件的 `name` 可以随便写"** —— 不建议。`--name` 会覆盖配置文件的 `name`，两者不一致时容易把自己绕晕（容器名、context 名全按覆盖后算）。
4. **"建完新集群，我的终端还在看老集群"** —— 错。kind 会自动切换 context 指向新集群，这是很多"为什么我的 Pod 不见了"的根源。

### 复验脚本的坑（供后续课程复用）

- **PowerShell here-string 通过管道传给 `wsl bash -s` 时，行尾会带上 `\r`**。对多数命令无害，但对 `tail -3`（报 `option used in invalid context -- 3`）和 `cat /tmp/x.log`（文件名变成 `x.log\r`）会直接失败。
- **结论**：需要读取"重定向产生的文件"或使用"带数字参数的选项"时，**不要走管道**，改用 `wsl -e bash -c "命令"` 直接执行，或先在 WSL 内落一个 `.sh` 再 `bash` 它。
- **首行 BOM 问题**（课 1 已记）：管道方式会让首个 `echo` 报 `command not found`，属正常噪声，不影响其余命令。
