## 一、全局 flag

全局 flag 的权威清单是 `kubectl options`，v1.34 共 **35 个**（含单字符别名）。下面按用途分四类，**每个都实测**。

### 1.1 连接类：决定「连哪个集群」

#### `--server` / `-s`

**是什么**：直接覆盖 API Server 地址，绕过 kubeconfig 里的 `cluster.server`。

**实测**：

```console
$ kubectl --server=https://127.0.0.1:1 --request-timeout=3s get nodes
E1009 ... memcache.go:265] "Unhandled Error" err="couldn't get current server API group list: Get \"https://127.0.0.1:1/api?timeout=3s\": dial tcp 127.0.0.1:1: connect: connection refused"
```

注意报错是 **`memcache.go` 的 Unhandled Error** 而不是干净的一行 error——因为 kubectl 启动时要先拉 discovery 缓存（`get` 任何资源都要先知道 GVK），连不上就刷三条。

**什么时候用**：临时连另一个 API Server 做验证，不想改 kubeconfig。

**坑**：`-s` 只换地址，**认证信息还是当前 context 的 user**。地址换了但证书不对，会报 TLS 错误而不是连不上。✅ 实测。

---

#### `--kubeconfig`

**是什么**：指定用哪个 kubeconfig 文件，覆盖 `KUBECONFIG` 环境变量与默认路径 `~/.kube/config`。

**实测**：

```console
$ kubectl --kubeconfig=/tmp/nonexistent-kubeconfig.yaml get nodes
error: stat /tmp/nonexistent-kubeconfig.yaml: no such file or directory

$ kubectl --kubeconfig=/root/.kube/config get nodes --no-headers
k8s-c1-control-plane   Ready   control-plane   11d   v1.34.0
```

**坑**：文件不存在是**直接 error 退出**，不是回退到默认配置。脚本里路径写错会硬失败。✅ 实测。

---

#### `--cluster`

**是什么**：指定 kubeconfig 里的某个 `clusters` 条目，覆盖 context 里指向的集群。

**实测**：

```console
$ kubectl config get-clusters
NAME
kind-k8s-c1
kind-k8s-c2
kind-kind-lab2
kind-otel-l11

$ kubectl --cluster=nonexistent-cluster --request-timeout=3s get nodes
error: no server found for cluster "nonexistent-cluster"
```

**坑**：`--cluster` 只换集群条目，**不换 user**。如果你用它指向另一个集群，认证凭据还是原来那个——两个 kind 集群的 CA 不同，通常会 TLS 失败。要同时换，用 `--context`。✅ 实测。

---

#### `--context`

**是什么**：切换 context（集群 + 用户 + 命名空间的组合）。课 1 已讲，这里补**错误值的表现**：

```console
$ kubectl --context=nonexistent-ctx get nodes
Error in configuration: context was not found for specified context: nonexistent-ctx
```

**坑**：报错前缀是 `Error in configuration:`（配置层错误），区别于服务端返回的 `Error from server (...)`。看前缀能快速判断是**本地配置问题**还是**集群问题**。✅ 实测。

---

#### `--insecure-skip-tls-verify`

**是什么**：跳过 API Server 证书校验。

**实测**：

```console
$ kubectl --insecure-skip-tls-verify=true get nodes --no-headers
k8s-c1-control-plane   Ready   control-plane   11d   v1.34.0
```

连接成功。kind 集群本来就是自签证书，跳过校验也能连（因为认证走的是 client cert，不是靠校验服务端证书）。

**什么时候用**：临时连自签证书集群、排障时排除证书问题。

**坑**：**中间人攻击风险**。只用于本地/测试，生产禁用。这条**不会**跳过你的身份认证。✅ 实测。

---

#### `--certificate-authority`

**是什么**：指定 CA 证书文件去校验 API Server，覆盖 kubeconfig 里的 `certificate-authority-data`。

**实测**（故意给一个非 PEM 文件）：

```console
$ echo hello > /tmp/fake-ca.crt
$ kubectl --certificate-authority=/tmp/fake-ca.crt get nodes
error: unable to load root certificates: unable to parse bytes as PEM block
```

**坑**：**覆盖而非追加**。指定后 kubeconfig 里原有的 CA 就失效了。多集群场景下别指望"两个 CA 都认"。✅ 实测。

---

#### `--tls-server-name`

**是什么**：TLS 握手时用的 SNI（Server Name Indication），用于服务端证书 SAN 不包含你访问的地址时。

**实测**（故意给错的 SNI）：

```console
$ kubectl --tls-server-name=wrong.example.com get nodes
Unable to connect to the server: tls: failed to verify certificate: x509: certificate is valid for k8s-c1-control-plane, kubernetes, kubernetes.default, kubernetes.default.svc, kubernetes.default.svc.cluster.local, localhost, not wrong.example.com
```

这条报错**信息量很大**——它把证书里所有合法 SAN 全列出来了。排障时用它反查"这个证书到底签给谁的"很好用。

**什么时候用**：通过代理/负载均衡访问，地址与证书 SAN 不一致时。✅ 实测。

---

#### `--request-timeout`

**是什么**：单个 API 请求的超时时间，**默认 `0`（永不超时）**。

**实测（两种报错，取决于失败阶段）**：

```console
$ kubectl --request-timeout=1ms get nodes
Unable to connect to the server: context deadline exceeded
```

复验时另一次得到的是：

```console
Unable to connect to the server: net/http: request canceled while waiting for connection (Client.Timeout exceeded while ...)
```

**同一条命令两种报错**——取决于超时发生在「建连接前（context deadline）」还是「等连接时（Client.Timeout）」。两者含义一样（都是超时），但**文案不同**，写 grep 断言别只认一种。

成功场景：

```console
$ kubectl --request-timeout=30s get nodes --no-headers
k8s-c1-control-plane   Ready   control-plane   11d   v1.34.0
```

**坑（重要）**：默认 `0` = **永不超时**。集群网络出问题时，`kubectl get pods` 会**永远挂着**，在 CI/脚本里表现为"卡住不返回"。

**建议**：脚本里显式写 `--request-timeout=30s`。这是最容易被忽略又最有用的全局参数之一。✅ 实测。

### 1.2 认证类：决定「以谁的身份」

> **本节最关键的实测结论：`--token` 会被 client-certificate 覆盖，静默失效。**

#### `--token`

**是什么**：用 Bearer Token 认证。

**实测 1：当前 context 自带 client-cert 时，假 token 竟然成功了**

```console
$ kubectl --token=fake-token-123 get nodes
NAME                   STATUS   ROLES           AGE   VERSION
k8s-c1-control-plane   Ready    control-plane   11d   v1.34.0
```

**假 token 也能成功？** 深挖一下当前的认证方式：

```console
$ kubectl config view --minify -o jsonpath='{.users[0].user}'
{"client-certificate-data":"DATA+OMITTED","client-key-data":"DATA+OMITTED"}
```

当前 context 用 **client certificate** 认证。所以 `--token` **被忽略了**——kubectl 构建认证时，client cert 优先级更高，token 根本没用上。

**实测 2：构造一个只有 token 的干净 config，验证 `--token` 确实生效**

```console
$ kubectl --kubeconfig=/tmp/tok-user.yaml --token=fake-token-123 get nodes
error: You must be logged in to the server (Unauthorized)
```

同一个假 token，在没有 client cert 的 config 下**立刻 401**。

**结论（认证优先级，实测）**：

```text
client-certificate / client-certificate-data   ← 最高优先级，存在即生效
        ↓ 不存在时才用
--token
        ↓ 都没有时
交互式索要用户名密码（Please enter Username:）
```

**坑**：`--token` **静默失效**——不报错、不警告，你以为在用新身份，其实还是老身份。这在"我用测试账号验证权限"场景下会导致**完全错误的结论**。

**验证方法**：`kubectl auth whoami` 看实际身份（v1.34 支持）。✅ 实测。

---

#### `--client-certificate` / `--client-key`

**是什么**：指定客户端证书与私钥做双向 TLS 认证。

**实测（坑）**：当 kubeconfig 已有 `client-certificate-data` 时，再给 `--client-certificate`：

```console
$ kubectl --client-certificate=/tmp/empty.crt --client-key=/tmp/empty.key get nodes
Error in configuration:
* client-cert-data and client-cert are both specified for kind-k8s-c1. client-cert-data will override.
* client-key-data and client-key are both specified for kind-k8s-c1; client-key-data will override
```

**注意措辞**：`client-cert-data will override` —— **kubeconfig 里的 data 赢了，命令行参数被无视**。

换成没有 data 的干净 config：

```console
$ kubectl --kubeconfig=/tmp/clean-ctx.yaml --client-certificate=/tmp/empty.crt --client-key=/tmp/empty.key get nodes
E1009 ... cert_rotation.go:172] "Loading client cert failed" err="tls: failed to find any PEM data in certificate input" key="key"
Unable to connect to the server: tls: failed to find any PEM data in certificate input
```

这次是真的用了你给的文件（空文件 → PEM 解析失败）。

**坑**：这跟 `--token` 是**相反的方向**——token 是命令行输给 kubeconfig，cert 是 kubeconfig 赢过命令行。两条规则不一致，容易记混。✅ 实测。

---

#### `--username` / `--password`

**是什么**：HTTP Basic 认证。

**实测**：干净 config 且完全不给认证时：

```console
$ kubectl --kubeconfig=/tmp/clean-ctx.yaml get nodes
Please enter Username: error: EOF
```

kubectl **会交互式索要用户名**。非交互环境（脚本/CI）里直接 `EOF` 失败。

**坑**：大多数现代集群（含 kind）不开 Basic 认证，这两个参数实际很少用。真正要"无认证访问"得配 `system:anonymous`。⚠️ 未实测（Basic 认证在本集群未启用）。

---

#### `--as` / `--as-group` / `--as-uid`

**是什么**：**身份伪装（impersonation）**——告诉 API Server"请以某用户身份处理这个请求"。RBAC 排障神器。

**实测**：

```console
$ kubectl --as=system:anonymous get pods
Error from server (Forbidden): pods is forbidden: User "system:anonymous" cannot list resource "pods" in API group "" in the namespace "default"

$ kubectl --as=nonexistent-user get pods
Error from server (Forbidden): pods is forbidden: User "nonexistent-user" cannot list resource "pods" in API group "" in the namespace "default"

$ kubectl get pods --no-headers
web-6d689fbfdf-7cjqq   1/1   Running   0     176m
web-6d689fbfdf-hpkqh   1/1   Running   0     176m
```

同样一条命令，加 `--as` 就 Forbidden，不加就正常——证明伪装生效。

再测伪装成 SA：

```console
$ kubectl --as=system:serviceaccount:kube-system:default get pods
Error from server (Forbidden): pods is forbidden: User "system:serviceaccount:kube-system:default" cannot list resource "pods" in API group "" in the namespace "default"
```

**注意**：伪装**不存在的用户也能成功发出请求**（API Server 不需要该用户真实存在），区别只在 RBAC 是否授权。上例 `nonexistent-user` 报的是 `Forbidden`（认证通过了、授权没过），不是 `Unauthorized`。

**`--as-group` / `--as-uid` 实测**：

```console
$ kubectl --as=system:anonymous --as-group=system:unauthenticated get pods
Error from server (Forbidden): pods is forbidden: User "system:anonymous" cannot list resource "pods" ...

$ kubectl --as=system:anonymous --as-uid=12345 get pods
Error from server (Forbidden): pods is forbidden: User "system:anonymous" cannot list resource "pods" ...
```

**坑**：`--as-group` 的错误信息里**只显示 User，不显示 Group**——看不出 group 是否生效。要确认 group 是否带上，得看 API Server 审计日志。⚠️ group 生效性未直接实测（错误信息不回显 group）。

**`--as` 需要权限**：你自己要有 `impersonate` 权限，否则报 Forbidden。kind 的 `kubernetes-admin` 有。✅ 实测。

### 1.3 行为类：改变 kubectl 自身的行为

#### `--warnings-as-errors`

**是什么**：把告警变成错误（非零退出码）。

**实测（分两种告警，结果相反）**：

**① 客户端告警（kubectl 自己产生的）** —— 先删掉 `last-applied` 注解再 apply：

```console
$ kubectl apply -f /tmp/rd.yaml -n kcp-lab
Warning: resource deployments/roll-demo is missing the kubectl.kubernetes.io/last-applied-configuration annotation which is required by kubectl apply. ...
deployment.apps/roll-demo configured
  >> 退出码=0
```

加 `--warnings-as-errors=true`：

```console
$ kubectl apply -f /tmp/rd.yaml -n kcp-lab --warnings-as-errors=true
Warning: resource deployments/roll-demo is missing the kubectl.kubernetes.io/last-applied-configuration annotation ...
deployment.apps/roll-demo configured
  >> 退出码=0
```

**Warning 照样打印、对象照样 configured、退出码照样 0 —— 对客户端告警无效。**

**② 服务端告警（API Server 返回的）** —— 触发一条已废弃 API 的告警：

```console
$ kubectl apply -f /tmp/vdir/ -n kcpv-lab --prune -l pv=true
Warning: v1 Endpoints is deprecated in v1.33+; use discovery.k8s.io/v1 EndpointSlice
（成功）

$ kubectl apply -f /tmp/vdir/ -n kcpv-lab --prune -l pv=true --warnings-as-errors=true
  >> 退出码=1
```

**对服务端告警有效——退出码变成 1。**

**结论（实测，且修正了本轮首测的以偏概全）**：

| 告警来源 | 例子 | `--warnings-as-errors` 是否生效 |
|---|---|---|
| **服务端**（API Server 返回的） | `v1 Endpoints is deprecated` | ✅ **生效**，退出码=1 |
| **客户端**（kubectl 自己产生的） | `missing the last-applied-configuration annotation` | ❌ **无效**，退出码仍 0 |

> **本轮我犯的错**：首测只跑了客户端告警就下结论"该 flag 无效"，复验时跑了服务端告警才发现**它对服务端告警是有效的**。这是「用单一实验否定整体」的测量错误——**一个 flag 有两种告警来源时，必须两类都测**。
>
> 判断告警来源的方法：看有没有 `Warning:` 前缀且内容是否来自 API Server 的废弃策略（deprecated API 告警必定是服务端）。

⚠️ 客户端告警为何不生效的**根因未取证**（未查源码，可能是走不同的输出路径）。

**实践建议**：想在 CI 卡告警，别只依赖这个 flag —— 自己 `2>&1 | grep -qi '^Warning'` 判断更可靠。

✅ 两种告警均实测。

#### `--cache-dir`

**是什么**：kubectl 的客户端缓存目录，默认 `~/.kube/cache`。

**实测**：

```console
$ kubectl --cache-dir=/tmp/kc-cache-demo get nodes --no-headers
k8s-c1-control-plane   Ready   control-plane   11d   v1.34.0

$ find /tmp/kc-cache-demo -type f | head -5
/tmp/kc-cache-demo/discovery/127.0.0.1_45145/lesson07.example.com/v1/serverresources.json
/tmp/kc-cache-demo/discovery/127.0.0.1_45145/authentication.k8s.io/v1/serverresources.json
/tmp/kc-cache-demo/discovery/127.0.0.1_45145/autoscaling/v1/serverresources.json
/tmp/kc-cache-demo/discovery/127.0.0.1_45145/autoscaling/v2/serverresources.json
/tmp/kc-cache-demo/discovery/127.0.0.1_45145/events.k8s.io/v1/serverresources.json
```

**这解释了课 1 的一个重要现象**：`kubectl` 每次执行都要先做 **API discovery**（这个集群有哪些 GVK），结果按 `host_port/group/version/` 分目录缓存。

**坑**：集群装了新 CRD 后，缓存可能让你**看不到新资源**。此时删缓存目录或等缓存过期（默认 10 分钟）。

**排障价值**：`kubectl get foo` 报「`the server doesn't have a resource type "foo"`」但 CRD 明明装了 → 先怀疑缓存。✅ 实测。

#### `--disable-compression`

**是什么**：请求不带 `Accept-Encoding: gzip`，不让服务端压缩响应。

**实测**：

```console
$ kubectl --disable-compression=true get nodes --no-headers
k8s-c1-control-plane   Ready   control-plane   11d   v1.34.0
```

**什么时候用**：大列表（`get pods -A`）在慢网络下，压缩+解压可能比直接传还慢；或者要抓包看明文响应时。日常不用管。✅ 实测（成功执行，未做性能对比）。

---

#### `--match-server-version`

**是什么**：要求客户端版本与服务端**完全一致**，不一致就报错。

**实测**：

```console
$ kubectl --match-server-version=true get nodes --no-headers
k8s-c1-control-plane   Ready   control-plane   11d   v1.34.0
```

本例成功，因为 client 与 server 都是 v1.34.0。

**坑**：K8s 官方只保证 **±1 个 minor 版本**兼容。开了这个 flag，客户端小版本差异也会硬失败。生产脚本慎用。⚠️ 版本不一致时的报错原文未实测（本机两端版本恰好一致）。

---

#### `--profile` / `--profile-output`

**是什么**：对 kubectl 自身做性能剖析（pprof），输出到文件。

**实测**：

```console
$ kubectl --profile=cpu --profile-output=/tmp/kc.prof get nodes --no-headers
k8s-c1-control-plane   Ready   control-plane   11d   v1.34.0

$ ls -la /tmp/kc.prof
-rw-r--r-- 1 root root 216 Oct  9 19:29 /tmp/kc.prof
```

生成了 216 字节的 pprof 文件。

**什么时候用**：`kubectl` 本身很慢（不是集群慢）时，剖析客户端。极少用。✅ 实测。

---

#### `--log-flush-frequency`

**是什么**：日志刷盘间隔，默认 `5s`。

### 2.3 `kubectl apply`

`apply` 共 **26 个 flag**，四课讲了 10 个（38%）。

#### `--prune`（重点，坑最多）

**是什么**：删除「上次 apply 创建、但本次 apply 不再包含」的对象——让 `apply` 能**真正同步**目录与集群。

**坑 1：必须配合 `--prune-allowlist`，且格式是 `group/version/kind`**

我第一次写 `v1/ConfigMap`（省了 group），报错：

```console
$ kubectl apply -f /tmp/prunedir/ -n kcp-prune --prune -l pd=true --prune-allowlist=v1/ConfigMap
error: invalid GroupVersionKind format: v1/ConfigMap, please follow <group/version/kind>
```

正确写法是 **`core/v1/ConfigMap`**（core 组的 group 名是 `core`，不能省）：

```console
$ kubectl apply -f /tmp/pd2/ -n kcp-prune --prune -l pd=true --prune-allowlist=core/v1/ConfigMap
Warning: resource configmaps/keep-a is missing the kubectl.kubernetes.io/last-applied-configuration annotation ...
configmap/keep-a configured
```

**坑 2：不加 `-l` 会拒绝执行（安全设计）**

```console
$ kubectl apply -f /tmp/pd2/ -n kcp-prune --prune --prune-allowlist=core/v1/ConfigMap --dry-run=client
error: all resources selected for prune without explicitly passing --all. To prune all resources, pass the --all flag. If you did not mean to prune all resources, specify a label selector
```

这是**保护措施**：不带标签的 prune 可能误删命名空间里所有对象。要真这么做必须显式加 `--all`。

**坑 3（最反直觉）：prune 的依据是「上次的集合」而非「标签」**

实测：目录里同时有 `a.yaml` 和 `b.yaml`：

```console
$ kubectl apply -f /tmp/pz/ -n kcp-prune2 --prune -l pz=true --prune-allowlist=core/v1/ConfigMap
configmap/pz-a created
configmap/pz-b created
```

从目录**删掉 b.yaml** 再 apply：

```console
$ kubectl apply -f /tmp/pz/ -n kcp-prune2 --prune -l pz=true --prune-allowlist=core/v1/ConfigMap
configmap/pz-a unchanged
configmap/pz-b pruned          ← b 被删了
```

**反证**：用 `kubectl create` 建的 `pz-c`（带同样的 `pz=true` 标签，但**从未被 apply 过**）：

```console
$ kubectl apply -f /tmp/pz/ -n kcp-prune2 --prune -l pz=true --prune-allowlist=core/v1/ConfigMap
configmap/pz-a unchanged

$ kubectl get cm -l pz=true -n kcp-prune2
pz-a   1     1s
pz-c   1     0s                ← c 还在！
```

原因看注解：

```console
$ kubectl get cm pz-a -n kcp-prune2 -o jsonpath='{.metadata.annotations.kubectl\.kubernetes\.io/last-applied-configuration}'
{"apiVersion":"v1","data":{"k":"v"},"kind":"ConfigMap","metadata":{...,"name":"pz-a",...}}

$ kubectl get cm pz-c -n kcp-prune2 -o jsonpath='{.metadata.annotations.kubectl\.kubernetes\.io/last-applied-configuration}'
（空）
```

**结论**：prune 只能删**带 `last-applied` 注解**的对象（即被 apply 管理过的）。`create` 建的对象没有这个注解，**永远不会被 prune**。

**`-l` 标签的真实作用**：限定 prune 的**搜索范围**，不是"删除依据"。

✅ 以上全部实测。

---

#### `--validate`

**是什么**：校验 YAML 字段的严格程度。

**实测**（YAML 里有 `unknownField`）：

```console
$ kubectl apply -f /tmp/bad.yaml --validate=strict
Error from server (BadRequest): ... strict decoding error: unknown field "unknownField"
  >> 退出码=1

$ kubectl apply -f /tmp/bad.yaml --validate=true
```

**结论**：v1.34 的**默认行为已等价于 strict**（`--validate=true` 与 `strict` 表现一致）。`--validate=ignore` 才会放过未知字段。

**坑**：`--validate=ignore` 放过后，那个未知字段**静默丢弃**（不会存进集群）。你以为配上了，其实没有。

⚠️ 补充：`--validate=strict` 的报错前缀是 `Error from server`——说明这是**服务端**校验，不是客户端。课 3 讲的 `--dry-run=server` 能拦未知字段是同一机制。✅ 实测。

#### `--cascade` / `--grace-period`（apply 上的删除语义）

**实测帮助文本**：

```console

	Must be "background", "orphan", or "foreground". Selects the deletion cascading strategy for the dependents (e.g. Pods created by a ReplicationController). Defaults to background.
```

**为什么 apply 会有删除参数**：因为 `--prune` 会触发删除，这两个参数控制**删从属对象**的方式。

| `orphan` | 只删主对象，**从属对象变成孤儿保留** |

### 3.1 `kubectl exec`（出现 202 次，0 覆盖）

#### 基本用法

```console
$ kubectl exec -n kcp-lab lab-pod -c app -- ls /usr/share/nginx/html

index.html
```

#### 坑 1：不写 `--` 直接报错

```console
$ kubectl exec -n kcp-lab lab-pod -c app ls
error: exec [POD] [COMMAND] is not supported anymore. Use exec [POD] -- [COMMAND] instead
See 'kubectl exec -h' for help and examples
```

**这是 v1.34 的硬性要求**：命令必须用 `--` 分隔。`--` 之后的所有内容**原样传给容器**，不再被 kubectl 解析。

**为什么必须有 `--`**：没有它，`ls -l` 的 `-l` 会被 kubectl 当成自己的 flag 解析，报错或行为异常。

✅ 实测。

---

#### 坑 2：多容器不写 `-c` 会静默选一个

```console
$ kubectl exec -n kcp-lab lab-pod -- ls /
Defaulted container "app" out of: app, sidecar
bin
dev
```

**不报错**，只打一行 `Defaulted container "app" out of: app, sidecar` 然后执行。

**危险**：本例中 `app` 是 nginx、`sidecar` 是 busybox——两个容器的文件系统完全不同。你以为在 sidecar 里执行，实际在 nginx 里。

**跟课 4 的 `logs` 坑是同一个模式**：kubectl 在多容器场景下**默认选第一个**而不是报错。✅ 实测。

---

#### `-i` / `-t`

```console
$ echo 'from-stdin' | kubectl exec -i -n kcp-lab lab-pod -c sidecar -- cat
from-stdin
```

| flag | 作用 |
|---|---|
| `-i` / `--stdin` | 保持 stdin 打开（管道输入必需） |
| `-t` / `--tty` | 分配伪终端（交互式 shell 必需） |

**`-it` 组合**：进交互式 shell（`kubectl exec -it pod -- sh`）。

**`-t` 与 CRLF —— 一条被实测推翻的说法（2026-10-10 更正）**：

> ❌ **旧结论（错误，已作废）**："-t 会把输出转成终端格式（CRLF、控制字符），污染管道数据。"
>
> 这条是**凭推断写的，没有实测**。课 5 用 `od -c` 逐字节比对，加 `-t` 与不加 `-t` 的输出**完全一致，结尾都是 `\n` 而非 `\r\n`**：
>
> ```console
> $ kubectl exec -n kce-lab epod -c side -- echo hi | od -c
> 0000000   h   i  \n
> $ kubectl exec -t -n kce-lab epod -c side -- echo hi | od -c
> 0000000   h   i  \n
> ```
>
> ✅ 实测（三次一致）：**`-t` 不会把 `\n` 改成 `\r\n`**。

**那 `-t` 的真实影响是什么？** 是**分配 TTY** 本身（见课 5 第三幕）：进程会认为自己连着终端，`isatty()` 返回真，于是启用彩色输出、交互式提示、列宽自适应。这是**程序行为**变化，不是 kubectl 改字节。

**脚本里的真实取舍**（结论保留，理由改写）：非交互脚本只加 `-i` 不加 `-t`，理由是——

1. **卡住**：无 TTY 的一方在等 stdin，而 `-t` 已分配终端，容易挂住不放手；
2. **程序行为分叉**：有 TTY 时程序可能输出颜色转义序列、进度条、交互式确认，这些才是真正"污染管道数据"的东西（但不是 CRLF）；
3. **无收益**：脚本不需要终端语义。

**教训**：区分"结论对"和"理由对"。本节结论（脚本里别加 `-t`）成立，但原来给的理由（CRLF）是错的。详见 [05-进到容器里.md](lessons/05-进到容器里.md)。

### 3.4 `kubectl rollout`（子命令族）

```console
$ kubectl rollout --help | sed -n '/Available Commands/,/^$/p'
Available Commands:
  history       View rollout history
  pause         Mark the provided resource as paused
  restart       Restart a resource
  resume        Resume a paused resource
  status        Show the status of the rollout
  undo          Undo a previous rollout
```

#### `status` — 等 rollout 完成

```console
$ kubectl rollout status deployment/roll-demo -n kcp-lab
deployment "roll-demo" successfully rolled out
```

**退出码实测**：

```console
$ kubectl rollout status deployment/nonexistent-dep -n kcp-lab --timeout=5s
Error from server (NotFound): deployments.apps "nonexistent-dep" not found
  >> 退出码=1
```

**脚本价值**：`rollout status` **会阻塞到完成**，退出码 1 表示失败。CI 里用它替代 `sleep 30`。

**必配 `--timeout`**：默认超时可能很长；不配的话失败场景会挂很久。

---

#### `history` / `undo` — 版本回滚

```console
$ kubectl rollout history deployment/roll-demo -n kcp-lab
deployment.apps/roll-demo
REVISION  CHANGE-CAUSE
1         <none>
2         <none>
```

**坑**：`CHANGE-CAUSE` 是 `<none>`——因为创建时没加 `--record`。**看不出每个版本改了什么**。

> ⚠️ **`--record` 已废弃**：老教程教的 `kubectl apply --record` 在新版本已移除。替代方案是手动写 `kubernetes.io/change-cause` 注解。**本轮未实测该注解的效果**。

**回滚实测**：

```console
$ kubectl rollout undo deployment/roll-demo -n kcp-lab
deployment.apps/roll-demo rolled back

$ kubectl get deployment roll-demo -n kcp-lab -o jsonpath='{.spec.template.spec.containers[0].image}'
nginx:1.25-alpine
```

回滚前镜像是 `nginx:1.26-alpine`（用 `set image` 改过），undo 后回到 `1.25-alpine`。✅ 实测。

**`--to-revision=N`**：回到指定版本（不写就是上一版）。✅ 已实测（课 6），三条要点：

1. **回滚会创建新 revision 号**，不是退回旧号。回滚到 rev4 的内容，当前号会变成 26 这样的新数字——`history` 里看到的是"新号 + 旧内容"。
2. **指定不存在的号会明确报错、退出码 1**，不是静默失败：

   ```console
   $ kubectl rollout undo deployment/rdep -n kcr-lab --to-revision=999
   error: unable to find specified revision 999 in history
   $ echo $?
   1
   ```

   被 `revisionHistoryLimit`（默认 10）淘汰的旧号同样如此——**`revision 1 in history` 报错**。
3. **指定"当前版本"是幂等成功，退出码 0**：`skipped rollback (current template already matches revision N)`。

> ⚠️ 注意 `--to-revision` 与"上一版"的区别：不写参数是回滚到上一个 revision 的内容，写了是回滚到指定 revision 的内容，**两者都不复用旧号**。

### 3.8 `kubectl wait`

#### 基本用法与退出码

⚠️ 未实测——理论上 `--for=delete` 对不存在的资源应立即返回 0（因为"已删除"条件满足），但**我没有跑这个场景，不编造**。

| `--timeout` | **30s** | 超时时间 |
| `--all` | false | 等待所有选中资源 |

**坑**：默认超时 **30 秒**。镜像拉取慢的场景（大镜像、冷启动）30 秒不够，必须显式加长。

✅ 以上退出码全部实测（**修正了首轮用管道导致 `rc` 恒为 0 的测量错误**）。

## 四、退出码与脚本陷阱

### 4.1 实测退出码总表

| 场景 | 退出码 | 实测命令 |
|---|---|---|
| `rollout status` 资源不存在 | **1** | `rollout status deployment/nonexistent --timeout=5s` |
| `wait` 资源不存在 | **1** | `wait --for=condition=Ready pod/nonexistent --timeout=3s` |
| `wait` 超时 | **1** | `wait --for=condition=Ready pod/never-ready --timeout=8s` |
| `wait --for=delete` 超时 | **1** | `wait --for=delete pod/never-ready --timeout=3s` |
| `get` 资源不存在 | **1** | `get pod/nonexistent-xyz` |
| `apply` 严格校验失败 | **1** | `apply -f bad.yaml --validate=strict` |
| `apply --validate=ignore` 含未知字段 | **0** | 字段**静默丢弃** |
| `apply` 带 Warning（**服务端**告警） | **1** | 加 `--warnings-as-errors=true` |
| `apply` 带 Warning（**客户端**告警） | **0** | 加 `--warnings-as-errors=true` **也无效** |
| `prune` 缺 `--prune-allowlist` 格式错 | **1** | `--prune-allowlist=v1/ConfigMap` |

### 4.2 陷阱 1：管道会吃掉退出码

**这是我在本轮实测中自己犯的错**（既有铁律「测量方法核验」重犯一次）：

```bash
# ❌ 错误：$? 拿到的是 head 的退出码，永远是 0
kubectl get pod/nonexistent 2>&1 | head -3; echo "rc=$?"
# 输出：rc=0    ← 假的！

# ✅ 正确：先存输出再判退出码
OUT=$(kubectl get pod/nonexistent 2>&1); RC=$?
echo "$OUT" | head -3; echo "rc=$RC"
# 输出：rc=1    ← 真的
```

**首轮探测中，`rollout status`、`wait`、`validate` 三个退出码全部因为管道被误报为 0**，第二轮才纠正。

**规则**：脚本里要判退出码，**不要让 kubectl 进管道**。

---

**Warning 不影响退出码**（除非它是服务端告警且你加了 `--warnings-as-errors`）：

```console
$ kubectl apply -f rd.yaml
Warning: resource deployments/roll-demo is missing the ... annotation ...
deployment.apps/roll-demo configured
  >> 退出码=0
```

**想让 CI 可靠地卡住告警**，必须自己判断：

```bash
OUT=$(kubectl apply -f app.yaml 2>&1); RC=$?
if echo "$OUT" | grep -qi '^Warning'; then
  echo "发现告警，人工确认"; exit 1
fi
[ $RC -ne 0 ] && exit $RC
```

⚠️ 注意：`--warnings-as-errors=true` **实测无效**（见 1.3），别指望它。

---

### 4.4 陷阱 3：`--request-timeout=0` 会永久挂起

默认 `0` = 永不超时。脚本里**必须显式设置**：

```bash
kubectl --request-timeout=30s get pods
```

---

### 4.5 陷阱 4：`diff` 有差异退出码为 1

课 3 已讲，此处复核：`kubectl diff` 发现差异时退出码 **1**，`set -e` 脚本会中断。

```bash
kubectl diff -f app.yaml || true    # 必须兜底
```

✅ 课 3 已实测。

## 五、反直觉结论清单

实测推翻直觉的 8 条，按"危险程度"排序：

### 1. `--token` 会被 client-cert 静默覆盖

假 token 也能成功执行命令——因为 kubectl 用了 kubeconfig 里的 client cert，**token 根本没用上**。

**后果**：你以为在用低权限账号验证，实际还是 admin。**权限验证结论完全错误**。

**验证方法**：`kubectl auth whoami`。

---

### 2. `--prune` 不删未被 apply 过的对象

带同样标签、但用 `create` 建的对象**永远不会被 prune**——因为 prune 依据 `last-applied` 注解，不是标签。

**后果**：你以为 `apply --prune` 会清理干净，实际残留一堆。

---

### 3. `--warnings-as-errors=true` **只对服务端告警生效**

**服务端**告警（如 `v1 Endpoints is deprecated`）→ 退出码变 **1**，生效。
**客户端**告警（如缺 `last-applied` 注解）→ 退出码仍 **0**，无效。

**后果**：你以为加了它就卡住所有告警，实际漏掉客户端那一类。

> **测量教训**：我首测只跑了客户端告警就断言"该 flag 无效"，是**用单一实验否定整体**。复验补测服务端告警才纠正。

---

### 4. `exec` / `logs` / `cp` 多容器不写 `-c` 都静默选第一个

三个命令**都不报错**，只打一行 `Defaulted container "xxx" out of: a, b`。

**后果**：在 sidecar 场景下，你执行的容器可能完全不是你想的那个。

---

### 5. `exec` 不写 `--` 直接报错

```text
error: exec [POD] [COMMAND] is not supported anymore. Use exec [POD] -- [COMMAND] instead
```

老教程里 `kubectl exec pod ls` 的写法在 v1.34 **已完全不可用**。

---

### 6. `--chunk-size` 调小会大幅增加请求数

`--chunk-size=1` 时 `get pods -A` 发 **26 次**请求，默认只发 **1 次**。

**后果**：为了"避免超时"而调小，反而把 API Server 打得更惨。

---

### 7. `--validate=ignore` 会静默丢弃字段

不报错、退出码 0，但你的字段**没进集群**。

---

### 8. `rollout history` 的 `CHANGE-CAUSE` 是 `<none>`

因为 `--record` 已废弃。老教程教的 `kubectl apply --record` 在 v1.34 不存在。
