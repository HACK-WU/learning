## 1. 怎么用这份解法库

**每道题的结构**：

```
场景（一段真实需求）→ 要求 → 【先自己想】→ 分析思路 → 参考方案 → 权衡与陷阱 → 怎么验证
```

**建议流程**：

1. 只读**场景与要求**，不看后面
2. 自己在纸上列出：用什么资源、为什么、有什么风险
3. 再看**分析思路**，对比你漏了什么
4. 最后看**权衡与陷阱**——这部分往往比方案本身更有价值

> 💡 **评分标准不是「答对」，而是「你有没有问出关键问题」**。
> 很多题没有唯一正确答案，**权衡的合理性**才是评判点。

## 2. 设计题 T1-T5

### T1：一个「跑批任务」要上 k8s

> **场景**：团队有个每天凌晨 2 点跑的数据报表任务，单机脚本跑 40 分钟。现在要迁到 k8s。
> **要求**：每天定时执行；失败了要能知道；**不能重复跑**；资源不能影响白天业务。

<details>
<summary>【思考点】先自己想 5 分钟</summary>

提示：用什么工作负载？失败重试怎么配？「不能重复跑」对应哪个字段？

</details>

**分析思路**：

1. **工作负载选型**：定时任务 → **CronJob**（课 6）。不是 Job（Job 是一次性，不含调度）
2. **不能重复跑**：`concurrencyPolicy: Forbid`（默认 `Allow` 会允许并发）
3. **失败重试**：`backoffLimit` + `restartPolicy: OnFailure`（**注意：CronJob 的 Job 模板不能用 `Always`**）
4. **不影响白天业务**：`resources.requests/limits` + 可考虑**专用节点池**（生产）或至少限制资源
5. **失败了要能知道**：Job 失败**不会自动告警**——需要额外监控（`kube_job_status_failed`）
6. **必须设 TTL**：`ttlSecondsAfterFinished`——**每分钟的 CronJob 一年攒 50 万个对象**（课 6）

**参考方案要点**：

```yaml
spec:
  schedule: "0 2 * * *"
  concurrencyPolicy: Forbid          # ← 防重跑
  startingDeadlineSeconds: 300        # ← 错过太久就别补了
  jobTemplate:
    spec:
      backoffLimit: 3
      ttlSecondsAfterFinished: 86400  # ← 必须设！
      template:
        spec:
          restartPolicy: OnFailure    # ← 不能是 Always
          containers:
            - resources:
                requests: {cpu: "1", memory: "2Gi"}
                limits:   {cpu: "2", memory: "4Gi"}
```

**权衡与陷阱**：

| 陷阱 | 说明 |
|---|---|
| **忘设 TTL** | Job 对象永久残留，etcd 被撑爆（课 6） |
| `concurrencyPolicy` 默认 Allow | 上次没跑完，这次又起一个 → **重复跑** |
| `restartPolicy: Always` | CronJob **不支持**，会报错 |
| 40 分钟任务的优雅终止 | 节点维护时会收到 SIGTERM，要考虑能不能续跑 |
| **失败无告警** | Job 失败是**静默**的，必须自己接监控 |

**怎么验证**：手动 `kubectl create job --from=cronjob/<name>` 触发一次，观察；再验证 TTL 是否真的清理。

### T2：服务要支持「灰度发布」（10% 流量给新版本）

> **场景**：一个 Web 服务，想让新版本先接 10% 流量，观察无异常再全量。
> **要求**：可逐步调比例；出问题能快速回滚；不能中断现有流量。


<details>
<summary>【思考点】先自己想 5 分钟</summary>

提示：用哪种入口资源做流量切分？权重怎么表达？数据库兼容怎么办？

</details>

**分析思路**：

1. **入口选型**：Gateway API（课 9）——⚠️ **Ingress 已冻结**，新项目不该用
2. **流量切分**：`HTTPRoute` 的 `backendRefs` **权重**（`weight: 10` / `weight: 90`）
3. **两个版本共存**：两个 Deployment（不同 label）+ 一个 Service 或各自 Service
4. **快速回滚**：把权重改回 `0/100`，**秒级生效**（比改镜像 tag 快得多）
5. **不能中断**：两个版本的 **readiness 探针都必须查依赖**（反例 9）

**参考方案要点**：

```yaml
# 两个 Deployment：app-v1（weight 90）/ app-v2（weight 10）
backendRefs:
  - name: app-v1-svc
    weight: 90
  - name: app-v2-svc
    weight: 10
```

**权衡与陷阱**：

| 陷阱 | 说明 |
|---|---|
| **会话保持** | 权重是**按比例随机**，同一用户可能跳版本 → 需要会话亲和则另配 |
| **数据库兼容** | 两个版本同时写同一个库 → **schema 必须双向兼容** |
| 只按流量比例，不看业务指标 | 错误率上升不会自动回滚 → 需要人工或额外自动化 |
| 权重总和不等于 100 | Gateway API 会**按相对比例**归一化，不是报错 |

**怎么验证**：连续请求 100 次，统计落到 v2 的比例（**注意：不会精确等于 10%**，是概率分布）。

### T3：一个服务只能被另一个服务访问，其他都不行

> **场景**：`api` 服务要访问 `db`，但**其他任何 Pod 都不允许访问 db**。
> **要求**：默认全拒；只放行 api → db；不能影响 DNS。


<details>
<summary>【思考点】先自己想 5 分钟</summary>

提示：默认策略是什么？用什么选中 Pod？为什么必须放行 DNS？

</details>

**分析思路**：

1. **NetworkPolicy 白名单模型**（课 10）：**先默认全拒，再逐条放行**
2. **两条策略**：db 侧「只允许来自 api 的入站」+ 可选 api 侧「只允许出站到 db」
3. **必须放行 DNS**（53 端口）——**反例 4 实测踩过的坑**
4. **确认 CNI 支持**（课 10 实测 kindnet **支持**，但很多 CNI 不支持 → 配了不生效且无报错）

**参考方案要点**：

```yaml
# 1. 默认全拒
podSelector: {}          # 选中所有
policyTypes: [Ingress, Egress]

# 2. 放行 DNS（否则全挂！）
egress:
  - to:
      - namespaceSelector: {}
        podSelector:
          matchLabels: {k8s-app: kube-dns}
    ports:
      - {protocol: UDP, port: 53}
      - {protocol: TCP, port: 53}

# 3. db 入站：只放行 api
ingress:
  - from:
      - podSelector: {matchLabels: {app: api}}
    ports:
      - {protocol: TCP, port: 5432}
```

**权衡与陷阱**：

| 陷阱 | 说明 |
|---|---|
| **忘放行 DNS** | 所有服务名解析失败，**整个应用不可用**（反例 4） |
| **用 `ipBlock` 指 ClusterIP** | **实测无效**——DNS 请求经 Service 转发后目的 IP 不是 ClusterIP |
| CNI 不支持 | 配了完全不生效，**且无任何报错**（陷阱四） |
| 只做入站不做出站 | 被攻破的 db 可主动外连 → 生产应双向限制 |

**怎么验证**：从 api 访问应成功；**从其他 Pod 访问应失败**——**两个方向都要测**。

### T4：一个服务在滚动更新时用户会看到 502

> **场景**：每次发版，总有少量请求返回 502。
> **要求**：找到根因并消除。


<details>
<summary>【思考点】先自己想 5 分钟</summary>

提示：Pod 被摘除与容器停止之间有时差吗？探针查的是什么？

</details>

**分析思路**：

这是**经典题**，根因通常有三层，逐层排查：

1. **Pod 被摘_endpoint_ 与容器停止有时差**
   - Service 移除 endpoint 需要时间传播到所有 kube-proxy
   - **解决**：`preStop` 休眠几秒，等 endpoint 传播完（课 4）
2. **readiness 探针没查依赖**
   - 新 Pod 还没预热完就被标记为 Ready → 接流量 → 502（反例 9）
   - **解决**：readiness 查真实依赖
3. **优雅终止时间不够**
   - 30 秒默认 grace period，慢请求被硬杀（课 4）
   - **解决**：调大 `terminationGracePeriodSeconds` + `preStop`

**参考方案要点**：

```yaml
lifecycle:
  preStop:
    exec:
      command: ["sleep", "5"]        # ← 等 endpoint 传播
terminationGracePeriodSeconds: 60    # ← 给足收尾时间
readinessProbe:
  httpGet: {path: /ready, port: 8080}  # ← 必须是查依赖的端点，不是 /healthz
```

**权衡与陷阱**：

| 陷阱 | 说明 |
|---|---|
| 只加 `preStop` 不改探针 | 新 Pod 仍可能未就绪就接流量 |
| readiness 和 liveness 同一端点 | liveness 查依赖会**导致正常 Pod 被杀** |
| `preStop` sleep 太长 | 拖慢发布速度，需在两者间权衡 |
| 502 也可能是应用自身问题 | 先看日志确认是「连接被拒」还是「应用报错」 |

**怎么验证**：滚动更新期间**持续压测**，观察错误率（只看 Pod 状态看不出来）。

### T5：要给一个「有状态服务」做备份

> **场景**：StatefulSet 跑的数据库，需要定期备份且能恢复。
> **要求**：不影响线上；能恢复到指定时间点；备份要能验证有效。


<details>
<summary>【思考点】先自己想 5 分钟</summary>

提示：快照备份和逻辑备份各有什么代价？备份怎么才算有效？

</details>

**分析思路**：

1. **备份方式选择**：
   - **卷快照**（CSI VolumeSnapshot，课 20 补充讲义）——快，但依赖 CSI 支持
   - **逻辑备份**（`pg_dump` 等）——慢，但可移植、可验证
2. **不影响线上**：从**从库**备份，或用快照（快照对性能影响小）
3. **恢复到指定时间点**：逻辑备份 + WAL/binlog 归档
4. **备份要能验证**：**定期做恢复演练**——没验证过的备份等于没有备份


**参考方案要点**（本环境下的推荐取舍）：

| 维度 | 卷快照（VolumeSnapshot） | 逻辑备份（`pg_dump`） |
|---|---|---|
| 速度 | 快（秒级） | 慢（大数据量分钟~小时级） |
| 可移植性 | 依赖 CSI 与存储后端 | ✅ 高，纯文件 |
| 可验证 | 需恢复成卷才能验证 | ✅ 可直接导入验证 |
| 时间点恢复 | 需配合 WAL | ✅ 天然支持 |

**推荐**：**逻辑备份为主 + 快照为辅**。
- 日常用逻辑备份（可验证、可移植、支持时间点恢复）
- 大体量全量用快照（快），但**必须定期演练恢复**
- **备份必须存到集群外**（异地/对象存储），否则集群没了备份也没了

**权衡与陷阱**：

| 陷阱 | 说明 |
|---|---|
| **从没验证过备份** | 最常见问题：真要恢复时发现备份是坏的 |
| 快照 ≠ 应用一致性 | 快照时可能正在写 → **需先 quiesce 或用应用感知快照** |
| 备份存同一集群 | 集群没了备份也没了 → **异地/跨集群存储** |
| 忘记备份 **Secret / 配置** | 只有数据没有配置，恢复不出来 |

**怎么验证**：**真跑一次恢复**（这是唯一可信的验证）。

## 3. 设计题 T6-T10

### T6：配置改了，希望 Pod 自动滚动更新

> **场景**：ConfigMap 改了，希望引用它的 Deployment 自动滚动重启。
> **要求**：不能手动删 Pod；不能误触发（内容没变时不重启）。


<details>
<summary>【思考点】先自己想 5 分钟</summary>

提示：k8s 原生会因为这个变更触发滚动吗？怎么让 Pod 模板「变」？

</details>

**分析思路**：

1. **k8s 原生不支持**——ConfigMap 更新**不会**触发 Deployment 滚动
2. **卷挂载会更新**（10~100 秒，课 11 实测）但**应用未必重新读取**
3. **环境变量永不更新**（课 11 实测）
4. **方案**：**checksum 注解**——把配置内容的哈希写进 Pod 模板注解，配置变 → 注解变 → Pod 模板变 → 触发滚动（本项目**决策 11**）

**参考方案要点**：

```yaml
# Kustomize：configMapGenerator 自动加 hash 后缀
# Helm：
annotations:
  checksum/config: {{ include (print $.Template.BasePath "/cm.yaml") . | sha256sum }}
```

**权衡与陷阱**：

| 陷阱 | 说明 |
|---|---|
| 用 `kubectl rollout restart` | 能用，但**每次都会重启**，且无法感知「内容是否真变了」 |
| 只靠卷挂载更新 | 应用必须支持热加载，否则白更新 |
| 加密/敏感配置也这么做 | Secret 变化也会触发滚动，注意是否会因无关字段变化误触发 |

**怎么验证**：

1. 改一次 ConfigMap 内容 → 观察是否触发滚动：`kubectl get pod -w`（应看到新 Pod 起来）
2. **再改回原内容** → 观察**是否不滚动**（checksum 相同则不该重启——这是关键，证明没有误触发）
3. 确认新 Pod 真的读到了新配置：`kubectl exec <pod> -- cat /etc/config/xxx`

> 🔑 **第 2 步才是重点**：只验证「改了会滚」不够，**还要验证「没改不会滚」**。

### T7：多环境（dev / staging / prod）配置管理

> **场景**：同一套应用要部署到三个环境，只有少量配置不同。
> **要求**：不要复制三份 YAML；环境差异要清晰可见。


<details>
<summary>【思考点】先自己想 5 分钟</summary>

提示：Helm 和 Kustomize 的分工边界在哪？差异放哪一层？

</details>

**分析思路**：

1. **选型**：Kustomize（**base + overlay**）—— 本项目决策
2. **Helm vs Kustomize**（课 14）：
   - 要**分发给别人装** → Helm（有版本台账）
   - 要**改自己的配置** → Kustomize（无模板逻辑，更直观）
3. **base 放共性，overlay 放差异**


**参考方案要点**：

```
base/                    # 共性：Deployment / Service / 配置骨架
  kustomization.yaml
overlays/
  dev/    kustomization.yaml   # resources: ../../base + 少量 patch
  staging/kustomization.yaml
  prod/   kustomization.yaml   # prod 额外：replicas / resources / PDB
```

**关键约束**：
- 差异只用 **patch** 表达，不复制整个文件
- **prod 叠加更严的配置**：`replicas ≥ 2`、resources 更大、PDB、PSA restricted
- **慎用 `commonLabels`**——它会注入 selector（**反例 5**），需要统一标签时改用 `labels` + `includeSelectors: false`

**权衡与陷阱**：

| 陷阱 | 说明 |
|---|---|
| **`commonLabels` 一把梭** | 会注入 selector 导致失配 + **后续无法更新**（**反例 5 实测**） |
| 用 Helm 但把环境差异写成 if/else | 模板越来越难维护 |
| 三个环境配置漂移 | 应定期 diff base 与各 overlay |

**怎么验证**：

1. `kustomize build overlays/dev` 与 `kustomize build overlays/prod` → **diff 两份输出**，确认只有预期字段不同
2. 确认**没有意外注入**：检查 `selector` 是否被 `commonLabels` 污染（**反例 5**）
3. 逐个环境 `kubectl apply -k` 并验证服务可用

> 🔑 **diff 是最有效的验证**——环境差异应该「一眼看完」，如果 diff 有几十行，说明 base/overlay 划分不合理。

### T8：服务突然变慢，怀疑是资源不够

> **场景**：用户反馈接口变慢，Pod 状态正常、日志无报错。
> **要求**：判断是不是资源问题，怎么定位与解决。


<details>
<summary>【思考点】先自己想 5 分钟</summary>

提示：`kubectl top` 有输出吗？退出码是多少？requests 是怎么写的？

</details>

**分析思路**：

1. **先看有没有数据**：`kubectl top` 有没有输出 → **没输出说明 metrics-server 没装**（课 13）
2. **看是不是 OOM**：退出码 **137** = OOMKilled（排障手册 3.3）
3. **看是不是 CPU throttle**：容器被限流（需要 cgroup 指标）
4. **看是不是 requests 写错**：
   - 只写 limits → requests 自动 = limits → **超订 + HPA 失真**（反例 6）
   - requests 写实测量，limits 留余量
5. **看 HPA 是否在扩**：`kubectl get hpa` 看 TARGETS


**参考方案要点**（定位顺序，不是一上来就调大资源）：

1. **先确认数据来源**：`kubectl top pod` 有输出吗？**没有 = metrics-server 未装**，先装它
2. **看退出码**：`137` → OOMKilled → 内存 limits 太小或应用有泄漏
3. **对比 requests 与实际用量**：
   - 实际用量远低于 requests → **requests 写虚高了**（反例 6），按实测量下调
   - 实际接近 limits → 真的不够，上调 limits
4. **HPA 若在扩但仍慢**：检查 `maxReplicas` 是否封顶、节点是否还有容量
5. **CPU throttle**：需要查 cgroup 指标（`container_cpu_cfs_throttled_seconds_total`）

**资源写法原则**：`requests` 按**实测常态**写，`limits` 留 **1.5~2 倍**余量。

**权衡与陷阱**：

| 陷阱 | 说明 |
|---|---|
| **只看 CPU 不看内存** | 内存不足的表现是 OOMKill，不是变慢 |
| 盲目调大 limits | 掩盖问题 + 浪费资源 |
| HPA 不扩 | 检查 metrics-server；**HPA 扩得快缩得慢（300 秒稳定窗口）** |
| 单副本无 HPA | 任何抖动都直接体现为用户可感知的慢 |

**怎么验证**：

1. `kubectl top pod` **有没有输出**（没输出 = metrics-server 未装，后面的判断都不可信）
2. 看退出码：`kubectl get pod -o jsonpath='{.status.containerStatuses[0].lastState.terminated.exitCode}'` → **137 = OOMKilled**
3. 对比 requests 与实际用量：实际远低于 requests 说明**写虚高了**（反例 6）
4. HPA 状态：`kubectl get hpa` 看 TARGETS 是否有值、是否在扩

> 🔑 **先确认「有没有数据」再分析数据**——metrics-server 没装时，所有结论都是猜的。

---

### T9：要给集群加一个「自定义资源」

> **场景**：想让 k8s 管理一种自研中间件实例（声明即可创建）。
> **要求**：`kubectl get mymiddleware` 能看到；声明后真的会创建实例。


<details>
<summary>【思考点】先自己想 5 分钟</summary>

提示：声明了 CRD 之后，谁去真正创建实例？有没有现成的 Operator？

</details>

**分析思路**：

1. **CRD 只是「菜单」，不是「后厨」**（课 20）——**声明 CRD 不会自动创建任何东西**
2. **必须有控制器**（Operator）去 reconcile
3. **选型**：
   - 能找到现成 Operator → **优先用现成的**
   - 没有 → 问「**升级手册能不能写在一页纸上**」——能就用 Helm，不能才写 Operator
4. **CRD vs 聚合层**（课 20）：CRD 简单，聚合层灵活（自定义存储/API 行为）


**参考方案要点**：

**决策树**（不要直接写 Operator）：

```
有现成 Operator？ ── 有 ──> 直接用（优先）
       │
       无
       ↓
升级手册能写在一页纸上？ ── 能 ──> 用 Helm / Kustomize
       │
       不能（需要持续调谐、有状态运维知识）
       ↓
   写 Operator（接受复杂度税）
```

**若确需 CRD，注意三件事**：
1. **CRD 只是 schema**——必须配控制器去 reconcile，否则创建 CR 什么都不会发生
2. **`status` 字段要写进 schema**，否则 `observedGeneration` 会被 **pruning 静默删除**（课 20 实测）
3. 提前设计**版本转换**（`conversion` webhook），否则后续升级无法迁移

**权衡与陷阱**：

| 陷阱 | 说明 |
|---|---|
| **以为配了 CRD 就会自动创建** | 最常见误解——CRD 只是 schema |
| **`observedGeneration` 被 pruning 吞掉** | 课 20 实测：`observedGeneration` 不在 schema 里 → **被静默删除** |
| 一上来就写 Operator | 复杂度税很高（课 20），先问能不能用现成的 |
| CRD 升级无迁移 | 版本转换要提前设计（`conversion` webhook） |

**怎么验证**：

1. `kubectl get crd` 确认 CRD 已建立
2. **创建一个 CR 实例** → 观察是否真的有东西被创建（**没有 = 缺控制器**，这是最常见的误解）
3. 检查 `status` 字段是否被控制器回填：`kubectl get mymiddleware -o yaml`
4. **关键**：确认 `observedGeneration` **没被 pruning 吞掉**（课 20 实测：不在 schema 里会被静默删除）
5. 删除 CR → 确认清理逻辑（finalizer）正常工作

> 🔑 **第 2 步是分水岭**：CRD 只是菜单，**创建了 CR 却什么都没发生 = 你还没做后厨**。

### T10：Pod 调度失败，但节点明明有资源

> **场景**：Pod 一直 Pending，但 `kubectl describe node` 显示节点资源充足。
> **要求**：找出所有可能的原因。


<details>
<summary>【思考点】先自己想 5 分钟</summary>

提示：调度器看的是实际用量还是 requests？除了资源还有哪些约束？

</details>

**分析思路**（这是**多选题**，考察你是否想到多种可能）：

| 可能原因 | 判据（Events 原文） |
|---|---|
| **污点不容忍** | `had untolerated taint` |
| **nodeSelector / 亲和性不匹配** | `didn't match Pod's node affinity/selector` |
| **PVC 未绑定** | `persistentvolumeclaim not found` |
| **ResourceQuota 超额** | 命名空间配额满（**是拒绝创建，不是 Pending**） |
| **节点被 cordon** | `node.kubernetes.io/unschedulable` |
| **requests 过大** | `Insufficient cpu`（注意：这里看的是 **requests 之和**，不是实际用量！） |

> 🔑 **最关键的一条**：调度器看的是 **requests**，不是实际使用量。
> 节点「看起来很闲」但所有 Pod 的 requests 之和已满 → **依然调度不上**。
> 这正是反例 6（只写 limits）的后果：**requests 被自动补成 limits 的虚高值**。


**权衡与陷阱**：

| 陷阱 | 说明 |
|---|---|
| **只看实际用量，不看 requests** | 最致命——调度器按 requests 记账，**节点很闲也可能调度不上** |
| 把 `Insufficient` 当成加节点的唯一信号 | 可能只是 requests 写虚高了（反例 6），**先降 requests 更省钱** |
| 加了节点仍未调度 | 可能是**污点 / 亲和性 / 选择器**问题，加节点解决不了「资格问题」 |
| ResourceQuota 超额被误判为 Pending | 配额超额是**拒绝创建**（Pod 根本没生成），不是 Pending |
| 只看自己这个 Pod | 可能是**别的 Pod 占满了** requests，要看全局分配 |

**怎么验证**：

1. `kubectl describe pod <pod>` 看 Events 原文——**逐字读**，区分是 `Insufficient` 还是 `didn't match`
2. 算一下节点上所有 Pod 的 **requests 之和**（不是实际用量）：
   `kubectl describe node | grep -A10 "Allocated resources"`
3. 检查污点：`kubectl describe node | grep Taint`
4. 检查节点是否 cordon：`kubectl get nodes`（看 `SchedulingDisabled`）
5. 检查 PVC：`kubectl get pvc`（是否 Bound）
6. 检查配额：`kubectl describe resourcequota`

> 🔑 **第 2 步最关键**：调度器看 requests，**节点「看起来很闲」但 requests 之和已满 → 依然调度不上**。


**参考方案要点**（按发生频率排序的排查清单）：

| 排查项 | 命令 | 判据 |
|---|---|---|
| 1. 读 Events 原文 | `kubectl describe pod` | 区分 `Insufficient` / `didn't match` / `untolerated taint` |
| 2. **requests 之和** | `kubectl describe node \| grep -A10 Allocated` | 看 **requests 之和**，不是实际用量 |
| 3. 污点 | `kubectl describe node \| grep Taint` | 有污点则加 toleration |
| 4. cordon 状态 | `kubectl get nodes` | 有 `SchedulingDisabled` 则 uncordon |
| 5. PVC | `kubectl get pvc` | 是否 Bound |
| 6. 配额 | `kubectl describe resourcequota` | 超额是**拒绝创建**不是 Pending |

> 🎯 **最高频的真相**：节点「看起来很闲」，但**所有 Pod 的 requests 之和已满**。
> 这正是反例 6（只写 limits → requests 被自动补成虚高值）的后果。

## 4. 设计题 T11-T15

### T11：要限制某个团队的权限

> **场景**：给外部团队访问某 namespace 的权限，只能看 Pod 和日志，不能改任何东西。
> **要求**：最小权限；不能访问其他 namespace；不能看 Secret。


<details>
<summary>【思考点】先自己想 5 分钟</summary>

提示：Role 还是 ClusterRole？日志是哪个子资源？Secret 要不要给？

</details>

**分析思路**：

1. **RBAC 默认拒绝**（课 15）——只加不减，符合预期
2. **Role（不是 ClusterRole）** + **RoleBinding**（限制在单 namespace）
3. **verbs**：`get`/`list`/`watch` + **日志**（`pods/log` 是**子资源**，必须显式写在 `resources` 里，只给 `pods` 看不了日志）
   > 📄 `pods/log` 子资源属 k8s 通用机制，**本课程讲义未展开**，此处按官方文档标注。
4. **不给 `get secret`**

**参考方案要点**：

```yaml
rules:
  - apiGroups: [""]
    resources: ["pods", "pods/log"]   # ← log 是子资源，必须显式写
    verbs: ["get", "list", "watch"]
```

**权衡与陷阱**：

| 陷阱 | 说明 |
|---|---|
| **忘写 `pods/log`** | 能 get pod 但看不了日志 |
| 用 ClusterRoleBinding | 权限会**跨所有 namespace** |
| 给了 `list secret` | Secret 只是 base64，**一行还原明文**（课 11） |
| **没关 `automountServiceAccountToken`** | 该团队的 Pod 自动拿到 API 身份（反例 3） |

**怎么验证**：

1. **正向**：用该身份执行允许的操作，应成功
2. **反向（更重要）**：执行禁止的操作，**必须失败** —— 至少测三项：
   - `kubectl get secret`（应 403）
   - `kubectl delete pod`（应 403）
   - `kubectl get pod -n <其他namespace>`（应 403）
3. 用 `kubectl auth can-i` 快速核对：
   `kubectl auth can-i get pods/log --as=system:serviceaccount:<ns>:<sa>`
4. 确认该 SA 的 Pod **没有自动挂载 token**（`automountServiceAccountToken: false`）

> 🔑 **只测「能做什么」是不够的**——**必须测「不能做什么」**，否则你不知道边界在哪。

### T12：要让 Pod 满足「restricted」安全档

> **场景**：命名空间开了 PSA restricted，Pod 起不来。
> **要求**：改造 Pod 使其满足 restricted。


<details>
<summary>【思考点】先自己想 5 分钟</summary>

提示：restricted 要求哪几项？镜像本身会不会成为阻碍？

</details>

**分析思路**：

**restricted 四件套**（课 16）：

```yaml
securityContext:
  runAsNonRoot: true                 # ① 非 root
  allowPrivilegeEscalation: false    # ② 禁提权
  capabilities: {drop: ["ALL"]}      # ③ 丢掉所有能力
  seccompProfile: {type: RuntimeDefault}  # ④ seccomp
```


**参考方案要点**：

```yaml
securityContext:
  runAsNonRoot: true                      # ① 非 root
  runAsUser: 1000                         #    需与镜像 USER 或文件权限匹配
  allowPrivilegeEscalation: false         # ② 禁提权
  capabilities: {drop: ["ALL"]}           # ③ 丢掉所有能力
  seccompProfile: {type: RuntimeDefault}  # ④ seccomp
```

**若镜像本身以 root 为 USER**：
- 优先**改镜像**（加 `USER 1000`）——这是根治
- 无法改镜像时指定 `runAsUser`，但要确认**文件权限**允许该 uid 读写

**若应用确实需要某个 capability**（如 `NET_BIND_SERVICE` 绑 80 端口）：
- 更好做法：**改用 8080 等非特权端口**，在 Service 层做端口映射
- 而不是降档 PSA

**权衡与陷阱**：

| 陷阱 | 说明 |
|---|---|
| **restricted 是「全或无」** | 少一项就整体不通过，没有「部分满足」 |
| 镜像以 root 为 USER | 必须改镜像或指定 `runAsUser` |
| 应用需要某个 capability | 只能**降档到 baseline**，或重新设计 |
| 只配了 Pod 级没配容器级 | 两者都可配，**容器级优先** |

**怎么验证**：

1. `kubectl apply` → 观察是否被 PSA 拒绝（拒绝时会有明确提示缺哪一条）
2. 确认 Pod 真的起来了且是**非 root**：
   `kubectl exec <pod> -- id`（uid 应 ≠ 0）
3. 确认 capabilities 已清空：`kubectl exec <pod> -- capsh --print`（如镜像支持）
4. **在命名空间级打标签后再测一遍**，确认是 PSA 生效而非侥幸：
   `kubectl label ns <ns> pod-security.kubernetes.io/enforce=restricted`

> 🔑 **别只在「没开 PSA」的环境里测**——那样你只会得到一个虚假的通过。

### T13：节点要做维护，怎么保证服务不中断

> **场景**：要重启一台节点打补丁。
> **要求**：服务不中断；维护完能恢复。


<details>
<summary>【思考点】先自己想 5 分钟</summary>

提示：cordon / drain / PDB 分别管什么？drain 成功就等于安全吗？

</details>

**分析思路**：

1. **三件套**：`cordon`（封新调度）→ `drain`（优雅驱逐）→ `PDB`（限制同时驱逐）
2. **drain 的三个坑**（课 19 实测）：**DaemonSet / emptyDir / 裸 Pod**
3. **PDB 只管自愿驱逐**（反例 8）：挡不住 `kubectl delete`、节点宕机、OOM
4. **drain 成功 ≠ 服务活着**（必须主动验证）


**参考方案要点**：

```bash
# 1. 先确认 PDB 合理（关键！）
kubectl get pdb
#  ALLOWED 必须 > 0，否则 drain 会卡住
#  minAvailable 必须 < 副本数，否则永远不满足

# 2. 封住新调度
kubectl cordon <node>

# 3. 优雅驱逐（两个 -- 都是必需的）
kubectl drain <node> --ignore-daemonsets --delete-emptydir-data

# 4. 【不可省略】drain 期间持续验证服务
while true; do curl -s -o /dev/null -w "%{http_code} " <service>; sleep 1; done

# 5. 维护完成后恢复
kubectl uncordon <node>
```

**PDB 配法**：`minAvailable: 1` 或 `maxUnavailable: 1`（二选一），
**且副本数必须 ≥ 2**，否则 PDB 会让 drain 永远卡死。

**权衡与陷阱**：

| 陷阱 | 说明 |
|---|---|
| **PDB 配得比副本数还严** | `minAvailable: 2` 但只有 2 副本 → **drain 永远卡住** |
| 没配 PDB | drain 会把所有副本同时腾空 |
| 有 emptyDir 的 Pod | 数据会丢（drain 默认拒绝，需 `--delete-emptydir-data`） |
| 只看命令返回值 | **必须验证服务存活** |

**怎么验证**：

1. drain **之前**：确认 PDB 存在且合理 → `kubectl get pdb`（对比 `ALLOWED` 与副本数）
2. drain **期间**：**持续请求服务**，观察错误率（**这才是真正的验证**）
3. drain **之后**：确认 Pod 已在其他节点 Running，且服务仍可访问
4. 恢复：`kubectl uncordon <node>`
5. **反向验证**：故意把 PDB 配得比副本数严（如 `minAvailable: 2` 但只有 2 副本），观察 drain **是否卡住**（应该卡住——这证明 PDB 真的在工作）

> 🔑 **第 2 步不可省略**：`drain` 返回成功**只说明驱逐完成**，**不说明服务活着**。

### T14：集群要升级，怎么规划

> **场景**：要把集群从 1.32 升到 1.34。
> **要求**：不停机；可回滚。


<details>
<summary>【思考点】先自己想 5 分钟</summary>

提示：能直接 1.32 → 1.34 吗？升级前必须先做什么？

</details>

**分析思路**：

1. **不能跳次版本**（课 19）：1.32 → **1.33 → 1.34**，逐个升
2. **顺序**：先控制面，再节点
3. **先备份 etcd**（课 19：etcd 3.6 起用 **etcdutl**，不再是 etcdctl）
4. **证书**：组件证书 **1 年**，升级时顺便检查
5. **弃用 API**：升级前用 `kubectl deprecations` 之类工具扫一遍


**参考方案要点**：

```
1.32 ──> 1.33 ──> 1.34      # 逐个次版本，不能跳
```

**每轮升级的标准动作**：

| 顺序 | 动作 | 注意 |
|---|---|---|
| 0 | **备份 etcd**（etcd 3.6 起用 **etcdutl**） | 唯一的退路 |
| 0 | 扫已弃用 API | 升级后旧 API 对象可能失效 |
| 0 | 检查证书有效期（组件 **1 年**） | 顺便轮换 |
| 1 | 升控制面 | 先 control-plane |
| 2 | **逐节点**升工作节点 | 每次一台，drain → 升 → uncordon |
| 3 | 验证核心服务 | 全 Ready + 业务可用 |

> ⚠️ **绝不一次升所有节点**——滚动是 HA 的前提。

**权衡与陷阱**：

| 陷阱 | 说明 |
|---|---|
| **跳版本升级** | 不支持，且可能静默失败 |
| 没备份就升 | 升级失败无法回退 |
| 一次升所有节点 | 应**逐节点**滚动 |
| 忽略 API 弃用 | 升级后旧 API 对象可能失效 |

**怎么验证**：

1. **升级前**：`kubectl get nodes -o jsonpath='{.items[*].status.nodeInfo.kubeletVersion}'` 记录当前版本
2. **升级前**：确认 etcd 备份**已完成且可恢复**（没验证过的备份等于没有）
3. **升级前**：扫一遍是否用到已弃用 API
4. **升级中**：每个次版本升完都验证 `kubectl get nodes` 全 Ready + 核心服务可用
5. **升级后**：`kubectl get nodes` 确认版本已到目标，且**没有跳级**
6. 检查证书：`kubeadm certs check-expiration`

> 🔑 **第 2 步是底线**：升级失败时，**备份是唯一的退路**。

### T15：到底该不该上 k8s

> **场景**：一个 5 人团队，2 个后端服务，日活几千，流量平稳。**要不要上 k8s？**
> **要求**：给出判断，不是列举优缺点。


<details>
<summary>【思考点】先自己想 5 分钟</summary>

提示：用六个信号对照，命中几条「不该用」？「以后可能会扩展」算不算理由？

</details>

**分析思路**：

用 [课程手册 第 4 章决策清单](final-课程手册.md#4-决策清单) 的六个信号对照：

**「不该用」信号命中**：

- ✅ **全部能装进一台机器**（2 个服务）
- ✅ **流量可预测**（日活几千、平稳）
- ✅ **团队少于 3 人碰基础设施**（5 人团队，碰基础设施的更少）
- ✅ **单体/少服务**
- ✅ **没有专职平台 owner**
- ✅ **预算有限**

**命中 6 条「不该用」** → **明确不建议上 k8s**。

**推荐**：托管 PaaS（Render / Railway / Fly.io）或单机 Docker Compose + 完善备份。

**必须破除的两个误区**：

- ❌ 「我们以后可能会扩展」——**这是愿望，不是负载**
- ❌ 「大公司都在用」——基础设施要匹配**当前**的运维复杂度

> 🎯 **核心判据**：**k8s 从应用运维中消除的复杂度，必须大于运维 k8s 本身引入的复杂度。**

**如果 CTO 坚持要上**：那至少用**托管 k8s**（EKS/GKE/AKS），**绝不自建**。


**权衡与陷阱**：

| 陷阱 | 说明 |
|---|---|
| **「以后可能会扩展」** | 这是**愿望，不是负载**（[课程手册 4.4](final-课程手册.md#44-两条假信号业界反复强调)） |
| **「大公司都在用」** | 基础设施要匹配**当前**的运维复杂度，不是 aspirational 的规模 |
| 只看技术不看人 | **没有 owner 是最大的风险**——k8s 会腐化 |
| 忽略「运维税」 | 升级、证书、监控、备份**一样不少**，只是被标准化了 |
| 自建 vs 托管混淆 | 若最终决定上，**必须用托管**；自建等于你成了一家基础设施公司 |

**怎么验证**：

1. 用六个信号**逐条对照**并**记录命中几条**（不要凭感觉）
2. 问团队三个问题并拿到真实答案：
   - 「谁负责 k8s 本身的运维？」——**答不上来 = 无 owner，命中「不该用」**
   - 「现在的服务能装进一台机器吗？」——**能 = 命中「不该用」**
   - 「流量峰谷差多少倍？」——**3 倍以内 = 命中「不该用」**
3. 若有争议，**用最小代价试**：先在**非核心业务**上试 3 个月，再决定是否扩大

> 🔑 **验证方式不是技术动作，是诚实回答**——很多人上 k8s 的真实理由是「简历好看」或「以后可能会扩展」，
> **后者是愿望不是负载**（[课程手册 4.4](final-课程手册.md#44-两条假信号业界反复强调)）。


**参考方案要点**（本题的「方案」是决策结论，不是 YAML）：

**明确结论：不建议上 k8s。**

| 命中信号 | 本题情况 |
|---|---|
| 全部能装进一台机器 | ✅ 2 个服务 |
| 流量可预测（峰谷差 3 倍内） | ✅ 日活几千、平稳 |
| 团队少于 3 人碰基础设施 | ✅ 5 人团队 |
| 单体/少服务 | ✅ 只有 2 个 |
| 无专职平台 owner | ✅ |
| 预算有限 | ✅ |

**6/6 全部命中「不该用」** —— 这是很清晰的信号。

**推荐替代**：托管 PaaS（Render / Railway / Fly.io）或单机 Compose + 完善备份。

**若 CTO 坚持**：至少用**托管 k8s**（EKS/GKE/AKS），**绝不自建**——
自建等于「你成了一家基础设施公司」（[课程手册 4.5](final-课程手册.md#45-方案对比与渐进路径)）。

## 5. 通用设计框架

> 做完 15 题后，提炼出**面对任何新要求都能用的思路**。

### 5.1 五问法

拿到任何需求，先问这五个问题：

| # | 问题 | 作用 |
|---|------|------|
| 1 | **这是什么类型的工作负载？**（无状态/有状态/每节点/一次性） | 决定控制器（课 5/6） |
| 2 | **它要被谁访问？从哪访问？** | 决定 Service / Gateway / NetworkPolicy（课 7-10） |
| 3 | **它的配置和状态放哪？** | 决定 ConfigMap / Secret / PVC（课 11-12） |
| 4 | **它需要多少资源？会波动吗？** | 决定 requests/limits / HPA（课 13） |
| 5 | **谁能访问它？它需要什么权限？** | 决定 RBAC / PSA / SA（课 15-17） |

### 5.2 三个「必问」（来自十大反例的共同模式）

> 这三条覆盖反例里 **7/10 的坑**（实战经验 1.1 节）。

1. **副本变 2 会怎样？** → 抓共享 PVC、无滚动更新（反例 1、7）
2. **依赖挂了会怎样？** → 抓探针不查依赖、DNS 被墙（反例 9、4）
3. **跑第二遍会怎样？** → 抓不幂等、标签注入（反例 10、5）

**再加两条**：

4. **被 RCE 了会怎样？** → 抓 SA token、Secret 明文（反例 3、2）
5. **有人手滑 delete 会怎样？** → 抓 PDB 的边界（反例 8）

### 5.3 方案输出模板

```
1. 资源清单：用什么（Kind + 关键字段）
2. 为什么：相对替代方案的权衡
3. 风险与陷阱：什么情况下这个方案会失效
4. 怎么验证：具体命令 / 观察什么
5. 回滚方案：出问题怎么退回
```

> 💡 **第 3、4 条最容易漏**——但**它们恰恰是「设计」与「抄配置」的区别**。
