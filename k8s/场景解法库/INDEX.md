## 通用设计框架

做完场景后，提炼出**面对任何新要求都能用的思路**（完整版见每篇场景末尾的「知识点挂钩」）。

### 五问法

| # | 问题 | 作用 |
|---|------|------|
| 1 | **这是什么类型的工作负载？**（无状态 / 有状态 / 每节点 / 一次性） | 决定控制器 |
| 2 | **它要被谁访问？从哪访问？** | 决定 Service / Gateway / NetworkPolicy |
| 3 | **它的配置和状态放哪？** | 决定 ConfigMap / Secret / PVC |
| 4 | **它需要多少资源？会波动吗？** | 决定 requests/limits / HPA |
| 5 | **谁能访问它？它需要什么权限？** | 决定 RBAC / PSA / SA |

### 五个「必问」

1. **副本变 2 会怎样？** → 抓共享 PVC、无滚动更新
2. **依赖挂了会怎样？** → 抓探针不查依赖、DNS 被墙
3. **跑第二遍会怎样？** → 抓不幂等、标签注入
4. **被 RCE 了会怎样？** → 抓 SA token、Secret 明文
5. **有人手滑 delete 会怎样？** → 抓 PDB 的边界

### 集群视角的三个「必问」（场景 5-8）

> 应用视角问「我的服务」，集群视角问「**这个集群养得活吗**」。共同点：**平时完全看不出问题，只在出事那天一次性结算**。

6. **出事救得回吗？** → 抓无备份、备份没演练、备份存本集群（场景 6）
7. **租户管得住吗？** → 抓只做 namespace 就以为隔离了（场景 5）
8. **到期 / 升级会炸吗？** → 抓证书无台账、升级无 etcd 备份（场景 8）

### 方案输出模板

```
1. 资源清单：用什么（Kind + 关键字段）
2. 为什么：相对替代方案的权衡
3. 风险与陷阱：什么情况下这个方案会失效
4. 怎么验证：具体命令 / 观察什么
5. 回滚方案：出问题怎么退回
```

> 💡 **第 3、4 条最容易漏**——但**它们恰恰是「设计」与「抄配置」的区别**。
