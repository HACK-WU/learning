# 设计决策：三层 Web 应用生产化部署

> 本文回答「**为什么这么选**」。每条决策都附本机实测依据（kind v1.34.0，2026-09-14），
> 未实测项显式标注「文档结论」。

---

## 决策 1：数据库用 StatefulSet，不用 Deployment

**选择**：`StatefulSet` + `volumeClaimTemplates` + headless Service。

**理由**：
1. **稳定标识**：StatefulSet 的 Pod 名固定（`db-0`），重建后名字不变。Deployment 的 Pod 名带随机后缀，每次重建都变——而数据库需要被稳定寻址。
2. **独享卷**：`volumeClaimTemplates` 给每个副本一份**独立** PVC。Deployment 下所有副本共享同一个 PVC，多个数据库实例写同一份数据 = 数据损坏。
3. **有序启停**：StatefulSet 按序创建/删除，对有状态服务是必需的。

**实测证据**：删掉 `db-0` 后，StatefulSet 重建的 Pod **仍叫 `db-0`**，且 PVC `data-db-0` 重新挂载，表里数据 `before-delete` 完好无损（验收 3）。

**代价**：StatefulSet 扩缩容比 Deployment 慢且需人工介入（本例 `replicas: 1`，Postgres 主从不在本课范围）。

## 决策 2：入口用 Gateway API，不用 Ingress

**选择**：`Gateway` + `HTTPRoute`（`gatewayClassName: eg`）。

**理由**：
1. **Ingress 已功能冻结**，不再接受新特性（课 9 已述）。
2. **`ingress-nginx` 于 2026-03-24 EOL**，继续用等于把入口建在已停止维护的组件上。
3. **Gateway API 已进入 CKA 2025 考纲**，是面向未来的标准。
4. **角色分离更清晰**：Gateway 由平台方持有，HTTPRoute 由应用方持有——符合多团队分工。

**实测证据**：Gateway `Accepted=True`，HTTPRoute `attachedRoutes=1`，经 NodePort 外部访问返回 **HTTP 200**，响应体完整包含三层信息（`web` → `api` → `db_host`）。

**⚠️ 实测坑**：kind 没有 LoadBalancer 实现，Envoy 数据面 Service 的 `EXTERNAL-IP` 永远是 `<pending>`，因此 Gateway 的 `Programmed=False`。
**这不是故障**。真实访问走 NodePort（本例 `31790`）即可。验收脚本已按此处理，不再把 `Programmed=False` 判为失败。

## 决策 3：PSA 强制 restricted 档，而不是 baseline

**选择**：命名空间标签 `pod-security.kubernetes.io/enforce: restricted`。

**理由**：`restricted` 是当前最严格档，强制非 root、禁提权、丢全部 capability、seccomp RuntimeDefault。课 16 已述 baseline 只挡「碰宿主机」，restricted 才是「全或无」。

**实测代价与解决**：
- `postgres:16-alpine` 以 **uid 999** 运行，必须显式设 `runAsUser: 999` + `fsGroup: 999`，否则数据目录属主不匹配，启动失败。
- 应用层用 `python:3.12-slim`，显式设 `runAsUser: 10001/10002`。

**实测证据**：5 个容器全部通过 restricted 四件套检查；容器内 `id -u` 实测 `10002`（非 0）。

## 决策 4：Secret 走环境变量，不挂卷；权限 `defaultMode` 不适用

**选择**：Secret 通过 `secretKeyRef` 注入环境变量。

**理由**：本例应用只需要读连接密码，环境变量够用且简单。

**⚠️ 诚实说明**：课 11 实测指出「Secret 卷挂载默认 0644，需 `defaultMode: 0400`」——该结论**针对卷挂载形式**。本例用环境变量注入，**不涉及文件权限**，故无需 `defaultMode`。
环境变量形式的真实风险是：**`kubectl describe pod` 和容器内 `env` 都能看到明文**。生产环境应使用外部密钥管理（Vault / KMS + Secret Store CSI Driver）。

**实测证据**：`kubectl exec` 里 `echo $DB_PASSWORD` 能直接打出 `Sh0p-Secret-2026!`——这恰恰证明了「Secret 不是加密」。

---

## 决策 5：全部关闭 `automountServiceAccountToken`

**选择**：Pod spec 与 ServiceAccount 上均设 `automountServiceAccountToken: false`。

**理由**：课 15 已实测——默认挂载 SA token 是**最易忽略的提权风险**。拿到 Pod 内 shell 就等于拿到一个 API 身份。本例应用**不需要访问 API Server**，所以直接关掉。

**实测证据**：容器内 `/var/run/secrets/kubernetes.io/serviceaccount` 目录**不存在**（验收 5）。

**注意**：`rbac.yaml` 里仍然定义了 Role/RoleBinding，这是为了**演示最小权限的写法**。本例实际未挂载 token，故该 Role 暂未被使用。若将来应用需要读 ConfigMap，把 `automount` 改回 `true` 即可生效。

---

## 决策 6：NetworkPolicy 默认全拒 + 逐条放行

**选择**：`default-deny-all` + 5 条精确放行。

**理由**：课 10 核心结论——k8s 默认**全通**，一个 Pod 被攻破就能横扫整个集群。零信任必须从「默认拒绝」开始。

**⚠️ 实测踩坑（本项目最大的坑）**：

1. **DNS 放行必须用 `namespaceSelector` + `podSelector` 组合**，不能用 `ipBlock` 指向 kube-dns 的 ClusterIP。
   - **实测**：`ipBlock: 10.96.0.10/32` → DNS **仍然失败**（`Temporary failure in name resolution`）。
   - **根因**：DNS 请求经 Service 转发，实际目的 Pod IP 不是 ClusterIP，`ipBlock` 匹配不到。
   - **正确写法**：`namespaceSelector: {kubernetes.io/metadata.name: kube-system}` + `podSelector: {k8s-app: kube-dns}`。

2. **不要用 Kustomize `commonLabels` 给所有资源注入标签**。
   - **实测**：注入 `app.kubernetes.io/part-of: shop3t` 后，NetworkPolicy 的 `podSelector: {matchLabels: {app: web}}` **匹配不到** Pod，策略静默失效。
   - **根因**：`commonLabels` 会同时改 Pod 模板标签，导致 selector 与标签不一致；且 Deployment 的 `spec.selector` **不可变**，二次 apply 直接报 `field is immutable`。
   - **解决**：本项目 `kustomization.yaml` 中**刻意不使用** `commonLabels`。

**实测证据**：默认拒绝后，`db` 访问 `api:8000` 被拦（未授权路径）；同时业务 DNS 解析正常（放行规则生效）。

## 决策 7：HPA 目标 50% CPU，`minReplicas: 2`

**选择**：`averageUtilization: 50`，min 2 / max 6，扩容立即、缩容 60 秒稳定窗口。

**理由**：
- **`minReplicas: 2`** 是高可用底线——单副本没有滚动更新可言。
- **50%** 留出缓冲，避免流量突增时来不及扩容。
- **缩容稳定窗口 60s**（演示用，生产默认 300s）：课 13 已实测「扩得快缩得慢」，防止抖动导致反复扩缩。

**实测证据**（`hpa-test.sh`）：CPU `3% → 118% → 214%`，副本 `2 → 4 → 6`，两次 `SuccessfulRescale` 事件：
```
New size: 4; reason: cpu resource utilization (percentage of request) above target
New size: 6; reason: cpu resource utilization (percentage of request) above target
```

**⚠️ 字段变迁坑**：旧字段 `status.currentCPUUtilizationPercentage` 在 v1.34 **已不再填充**（实测为空），应读 `status.currentMetrics[0].resource.current.averageUtilization`。验收脚本初版因此误判 FAIL，已修正。

## 决策 8：PDB `minAvailable: 1`

**选择**：web 与 api 各一个 PDB，`minAvailable: 1`。

**理由**：课 19 核心结论——**PDB 只管自愿驱逐**（drain / 节点维护），**挡不住 `kubectl delete pod`**。

**实测证据**：`disruptionsAllowed = currentHealthy - desiredHealthy`。本例 6 个 web Pod、`minAvailable=1` 时 `allowed=5`（可同时驱逐 5 个，留 1 个）。该公式与课 19 完全一致。

**⚠️ 单节点局限**：本集群只有 1 个节点，drain 会驱逐所有 Pod 且无处可调度。故 `pdb-test.sh` 只做 **dry-run 与状态读取**，不真正执行 drain。这一点在脚本中显式说明，不假装在单节点上验证了节点级容灾。

**✅ 但 PDB 的阻断能力已用 Eviction API 真实验证（2026-09-14 补验）**：
把 `web-pdb` 临时改成 `maxUnavailable: 0`（`allowed` 恒为 0），再调 Eviction API，拿到决定性拒绝证据：

```json
HTTP 429  reason: TooManyRequests
"Cannot evict pod as it would violate the pod's disruption budget."
```

测试后已恢复 `minAvailable: 1`。**PDB 确实会拦截自愿驱逐**——不再是「只验到公式」的推测。

**两个必须知道的手法坑**（否则你自己复现会失败）：

1. **`kubectl delete pod` 永远拿不到 429**——它不走 Eviction API，**不受 PDB 约束**。要验 PDB 必须经 `kubectl proxy` 调 `/eviction` 子资源，或用 `kubectl drain`。
2. **`minAvailable: N` 构造不出稳定的 `allowed=0`**——删一个 Pod 后控制器立刻补新的，`currentHealthy` 马上恢复。必须用 **`maxUnavailable: 0`** 才能让 `allowed` 恒为 0，稳定拿到拒绝。

## 决策 9：数据库设 Guaranteed，应用层设 Burstable

**选择**：DB `requests == limits`（Guaranteed）；web/api `requests < limits`（Burstable）。

**理由**：
- **数据库**是最不能被驱逐的组件，Guaranteed 档给它最高保护。
- **应用层**允许资源弹性，Burstable 更经济。

**⚠️ 诚实标注**：课 13 已联网核查官方文档——**kubelet 不用 QoS 类决定驱逐顺序**，QoS 仅可「估计」最可能的顺序。真实依据是「用量是否超过 requests」+ 优先级 + 超出程度。所以 Guaranteed **不等于**绝对安全。

## 决策 10：不启用 PodAntiAffinity

**选择**：**不配** `PodAntiAffinity`（讲义中提及但不启用）。

**理由**：**单节点集群**上，硬性反亲和会导致第 2 个副本永远 Pending（无处可放）。这是本环境最容易被「照抄生产配置」踩到的坑。

**诚实标注**：生产多节点环境**应该**配反亲和，否则所有副本可能挤在同一节点，节点一挂全挂。本项目因环境限制不启用，并在 README 中显式说明这一局限。

**实测证据（2026-09-14 补验）**：建了一个 `requiredDuringSchedulingIgnoredDuringExecution` + `topologyKey: kubernetes.io/hostname` 的 2 副本测试 Deployment，结果如预期：

```
anti-affinity-test-86c77ff7b-mqnz2   1/1   Running   10.244.0.43
anti-affinity-test-86c77ff7b-8wkw7   0/1   Pending  <none>
```

事件明确给出原因：

```
FailedScheduling  0/1 nodes are available:
  1 node(s) didn't match pod anti-affinity rules.
  preemption: 0/1 nodes are available: 1 No preemption victims found for incoming pod.
```

**踩到的附加坑**：这个测试第一次**完全建不出 Pod**（ReplicaSet 报 `FailedCreate`），原因不是反亲和，而是 **LimitRange 最小约束**（`minimum cpu usage per Container is 50m, minimum memory usage per Container is 64Mi`）——我给的 `10m/32Mi` 被拒。这反倒额外证明了**决策里的 LimitRange 是真实生效的**。把请求调到 `60m/96Mi` 后测试才跑起来。

## 决策 11：配置用 ConfigMap，靠 checksum 注解触发滚动

**选择**：ConfigMap 存配置，Deployment 模板带 `checksum/config` 注解。

**理由**：课 11 实测——**改 ConfigMap 不会自动触发滚动更新**。Kustomize 的 `configMapGenerator` 会用内容哈希改名从而自然触发滚动（课 14 已实测），但本项目 ConfigMap 是静态的，故用 checksum 注解作为替代方案。

**⚠️ 诚实标注**：本项目 `checksum/config` 当前值为占位符 `PLACEHOLDER`，**未接自动生成**。生产应改用 Kustomize `configMapGenerator`（内容哈希自动改名），这是更可靠的方案。此处保留注解是为了演示该模式。

---

## 决策 12：用内联 Python 起服务，不额外构建镜像

**选择**：`command: ["python", "-c"]` 内联脚本，直接用 `python:3.12-slim`。

**理由**：项目目标是**验证 k8s 的生产化配置**，不是教容器构建。内联脚本保证「`kubectl apply` 即可跑」，无需 `docker build` + `kind load`，降低读者复现门槛。

**代价**：内联脚本不适合生产。真实项目应构建专用镜像并固定 digest（课 16 已述供应链安全）。这一点显式标注，不假装这是生产级做法。

---

## 一句话总结

> 这些决策的共同点：**每一项都用实测数据支撑，每一项都标注了它的代价与边界**。
> 生产化不是「把所有最佳实践堆上去」，而是**在明确约束下做可解释的取舍**——这正是课 20 决策清单的核心。
