# 反例对照：能跑，但很糟

> 本文展示同一个三层应用的「**反面写法**」。每条都标注：
> **现象**（看起来没事）→ **真相**（实际风险）→ **后果**（什么时候炸）。

全部对照均基于本课程已实测的结论，未新做实验的部分标注「课 N 已实测」。

---

## 反例 1：用 Deployment 跑数据库

```yaml
# ❌ 反面
apiVersion: apps/v1
kind: Deployment
metadata:
  name: db
spec:
  replicas: 1
  template:
    spec:
      containers:
        - name: postgres
          image: postgres:16-alpine
          volumeMounts:
            - name: data
              mountPath: /var/lib/postgresql/data
      volumes:
        - name: data
          persistentVolumeClaim:
            claimName: db-data     # ← 所有副本共享同一个 PVC
```

**现象**：单副本时完全正常，能写能读。

**真相**：Deployment 的 Pod 名带随机后缀（`db-7d9f8-x2k9p`），重建后**名字变了**；且所有副本**共享同一份 PVC**。

**后果**：一旦扩容到 2 副本，两个 Postgres 实例同时写同一份数据目录 → **数据损坏**。而且没有稳定 DNS 名，上层无法可靠寻址。

**正确做法**：`StatefulSet` + `volumeClaimTemplates`（本项目决策 1）。

## 反例 2：Secret 用环境变量就算「安全」了

```yaml
# ❌ 反面：以为用了 Secret 就安全
env:
  - name: DB_PASSWORD
    valueFrom:
      secretKeyRef:
        name: shop-secret
        key: DB_PASSWORD
```

**现象**：密码确实没写进镜像，也没写进 Git。

**真相**：
1. Secret 只是 **base64**，不是加密——`kubectl get secret shop-secret -o jsonpath='{.data.DB_PASSWORD}' | base64 -d` **一行还原明文**（课 11 实测）。
2. 环境变量形式下，容器内 `env` / `kubectl describe pod` **都能看到明文**。
3. etcd 里默认**明文存储**，除非开启静态加密（课 17）。

**后果**：任何人只要有 `get secret` 权限，或能进 Pod，就能拿到数据库密码。

**正确做法**：生产用外部密钥管理（Vault / 云厂商 KMS）+ Secret Store CSI Driver，并对 etcd 开启静态加密。本项目仅作可运行演示，已在决策 4 显式标注。

## 反例 3：默认挂载 ServiceAccount token

```yaml
# ❌ 反面：什么都不写，token 就自动挂进来了
spec:
  containers:
    - name: api
      image: python:3.12-slim
  # 没写 automountServiceAccountToken，默认 true
```

**现象**：应用跑得好好的，从没用过 API。

**真相**：容器内 `/var/run/secrets/kubernetes.io/serviceaccount/token` **默认存在**。拿到 Pod shell = 拿到一个 API 身份。

**后果**：应用被 RCE 后，攻击者直接拿这个 token 调 API Server——如果 SA 绑了高权限（很多人图省事绑 `cluster-admin`），**整个集群沦陷**。这是课 15 明确的「最易忽略的提权风险」。

**正确做法**：`automountServiceAccountToken: false`（本项目决策 5，已实测目录不存在）。

## 反例 4：NetworkPolicy 只放行业务端口，忘了 DNS

```yaml
# ❌ 反面：只放行业务端口，没有 DNS 放行
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-dns-egress
spec:
  podSelector: {}
  policyTypes: [Egress]
  egress:
    - to:
        - ipBlock:
            cidr: 10.96.0.10/32      # ← 直接指 kube-dns 的 ClusterIP
      ports:
        - protocol: UDP
          port: 53
```

**现象**：策略 apply 成功，没有报错。

**真相**：**本项目实测踩到的坑**——`ipBlock` 指向 ClusterIP **无效**，DNS 请求经 Service 转发后实际目的 IP 不是 ClusterIP。

**后果**：所有服务名解析失败（`Temporary failure in name resolution`），**整个应用不可用**，而你会以为策略配对了。

**正确做法**：用 `namespaceSelector` + `podSelector` 组合（本项目决策 6，已实测有效）：
```yaml
egress:
  - to:
      - namespaceSelector:
          matchLabels:
            kubernetes.io/metadata.name: kube-system
        podSelector:
          matchLabels:
            k8s-app: kube-dns
    ports:
      - protocol: UDP
        port: 53
```

## 反例 5：Kustomize `commonLabels` 一把梭

```yaml
# ❌ 反面
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
commonLabels:
  app.kubernetes.io/part-of: shop3t      # ← 污染所有资源
resources:
  - web.yaml
  - networkpolicy.yaml
```

**现象**：第一次 apply 全部成功。

**真相**（**本项目实测**）：
1. `commonLabels` 会同时改 Pod 模板标签，导致 NetworkPolicy 的 `podSelector: {matchLabels: {app: web}}` **匹配不到** Pod → 策略**静默失效**（不报错，就是不生效）。
2. Deployment 的 `spec.selector` **不可变**，第二次 apply 直接报 `field is immutable`。

**后果**：安全策略形同虚设，且后续无法更新——**两个问题叠加，还都很难查**。

**正确做法**：不给 NetworkPolicy 注入额外标签（本项目 `kustomization.yaml` 已刻意移除 `commonLabels`）。

## 反例 6：只写 limits 不写 requests

```yaml
# ❌ 反面
resources:
  limits:
    cpu: 500m
    memory: 256Mi
  # 没写 requests
```

**现象**：Pod 正常跑，看起来限制住了。

**真相**：k8s 会**自动把 requests 补齐为 limits 的值**（课 13 实测）。于是这个 Pod 调度时按 500m CPU 预留——**调度器以为它要吃满 500m**。

**后果**：节点资源被严重超订，实际用不到那么多却占着坑位，导致其他 Pod 调度不上。HPA 还会按这个虚高的 requests 算百分比，**扩容判断失真**。

**正确做法**：显式写 requests（本项目三层均写全，验收 9 会检查）。

## 反例 7：HPA 不写 minReplicas

```yaml
# ❌ 反面
spec:
  maxReplicas: 10
  # 没写 minReplicas，默认 1
```

**现象**：流量低时缩到 1 个副本，省钱。

**真相**：单副本时**没有滚动更新可言**——更新必然中断服务；且该 Pod 一挂，服务整体不可用。

**后果**：夜里缩到 1 个副本，早上这个 Pod OOM 了 → 服务全挂，且 HPA 扩容需要时间。

**正确做法**：`minReplicas: 2`（本项目决策 7）。

## 反例 8：以为 PDB 能防住一切中断

```yaml
# ❌ 误解：以为配了 PDB 就高枕无忧
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: web-pdb
spec:
  minAvailable: 1
  selector:
    matchLabels:
      app: web
```

**现象**：配了 PDB，觉得维护时不会中断。

**真相**：课 19 已实测——**PDB 只管自愿驱逐**（drain、节点维护），**挡不住 `kubectl delete pod`**、挡不住节点突然宕机、挡不住 OOM。

**后果**：有人手滑 `kubectl delete pod --all`，PDB 一声不吭，服务照样全挂。

**正确做法**：PDB 是**必要条件不是充分条件**。还要配：多副本 + 反亲和（多节点）+ 就绪探针 + 优雅终止。

## 反例 9：配了探针但都是同一个端点

```yaml
# ❌ 反面：三个探针全都打 /healthz
startupProbe:
  httpGet: { path: /healthz, port: 8080 }
readinessProbe:
  httpGet: { path: /healthz, port: 8080 }
livenessProbe:
  httpGet: { path: /healthz, port: 8080 }
```

**现象**：应用健康，探针全绿。

**真相**：`/healthz` 只证明「进程活着」，**不证明依赖可用**。数据库连不上时，`/healthz` 照样 200。

**后果**：数据库挂了，但这个 Pod 仍被当作就绪 → 流量继续打进来 → **全部请求 500**，而不是把流量摘走。

**正确做法**：**readiness 探针必须检查真实依赖**。本项目的 API 层 `/readyz` 会**真的 TCP 连一下数据库**，连不上就返回 503，从 Service 摘除。（课 3 已述探针三兄弟的职责分工。）

**决定性实测**（2026-09-14，本项目）：把数据库 StatefulSet 缩到 0 副本后——

| 观测点 | 结果 |
|--------|------|
| `/readyz` 返回 | **HTTP 503 Service Unavailable** |
| API Pod 就绪态 | `1/1` → **`0/1`** |
| EndpointSlice 后端 | `ready=true` → **`ready=false`** |

即：**依赖一挂，Pod 自动从 Service 摘除，流量不再打进来**。这就是「readiness 检查真实依赖」与「只打 `/healthz`」的**可观测差异**——后者在数据库挂掉时仍返回 200，流量继续灌入，全部请求失败。

## 反例 10：删 Pod 验证持久化，但不做幂等

```bash
# ❌ 反面：验收脚本直接 INSERT，不清理
psql -c "CREATE TABLE IF NOT EXISTS t (id int, note text); INSERT INTO t VALUES (1,'x');"
psql -tAc "SELECT note FROM t WHERE id=1;"
```

**现象**：第一次跑输出 `x`，断言通过。

**真相**（**本项目实测踩到**）：第二次跑时表里已有数据，`INSERT` 又插一行 → `SELECT` 返回**两行** → 拼接成 `xx` → **断言失败**。

**后果**：「能跑但只能跑一次」——读者照抄跑第二遍就挂，是最典型的可照抄性缺陷。

**正确做法**：先 `DELETE` 再 `INSERT`，并用 `LIMIT 1` 保证单值（本项目 `verify.sh` 已修）。

## 一句话总结

> 这 10 个反例的共同模式：**配置写下去不报错，看起来也在工作，但真实语义和你以为的不一样**。
> 唯一可靠的验证方式是——**在真实环境里把它跑一遍，并观察状态而不是看命令有没有报错**。
> 这正是课 18「工具会骗人，状态才是真相」、课 19「`drained` 成功 ≠ 服务活着」、课 20「kubectl 报错可能来自客户端」贯穿三课的同一条暗线。
