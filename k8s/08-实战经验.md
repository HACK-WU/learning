## 1. 十大反例：能跑，但很糟

> 完整 YAML 对照见 [反例对照.md](projects/三层Web应用生产化部署/反例对照.md)。
> 这里提炼**每条的可迁移教训**——换个场景你还能认出它。

| # | 反例 | 现象（看起来没事） | 真相 | 什么时候炸 |
|---|------|------------------|------|-----------|
| 1 | **用 Deployment 跑数据库** | 单副本完全正常 | Pod 名带随机后缀、所有副本**共享同一 PVC** | **扩容到 2 副本时数据损坏** |
| 2 | **Secret 用环境变量＝安全** | 密码没进镜像也没进 Git | base64 不是加密；`kubectl describe pod` 可见明文 | 有 `get secret` 权限的人拿到库密码 |
| 3 | **默认挂载 SA token** | 什么都没配 | `/var/run/secrets/.../token` **默认存在** | 应用被 RCE → 拿 token 调 API（若绑 cluster-admin → **集群沦陷**） |
| 4 | **NetworkPolicy 忘了放行 DNS** | 策略看起来配对 | **`ipBlock` 指向 ClusterIP 无效**（本项目实测） | 服务名全部解析失败，**整个应用不可用** |
| 5 | **Kustomize `commonLabels` 一把梭** | 标签统一了，很整洁 | 标签被注入到 selector，导致 selector 失配 | 安全策略形同虚设 + **后续无法更新** |
| 6 | **只写 limits 不写 requests** | 能跑 | k8s **自动补齐 requests = limits**（课 13 实测） | 节点严重超订、HPA 按虚高值算百分比 → **扩容判断失真** |
| 7 | **HPA 不写 minReplicas** | 能跑 | 单副本**没有滚动更新可言** | 夜里缩到 1 副本，早上 OOM → **服务全挂** |
| 8 | **以为 PDB 能防住一切中断** | 配了 PDB 就高枕无忧 | PDB **只管自愿驱逐**，挡不住 `kubectl delete` | 有人手滑 `delete pod --all` → PDB 一声不吭，照样全挂 |
| 9 | **三个探针打同一个端点** | 探针都配了 | `/healthz` 只证明**进程活着**，不证明依赖可用 | DB 挂了但 Pod 仍被当就绪 → 流量继续打 → **全部 500** |
| 10 | **验收脚本不做幂等** | 第一次跑通过 | 第二次 `INSERT` 又插一行 → 断言失败 | **「能跑但只能跑一次」**——最典型的可照抄性缺陷 |

### 1.1 这 10 条的共同模式

> 🎯 **值得单独记**：10 条里有 **7 条属于同一类**——**「单副本/单环境/单次数下看不出问题，一变就炸」**。

| 触发条件 | 对应反例 |
|----------|----------|
| **副本数从 1 变多** | 反例 1（共享 PVC 损坏）、反例 7（无滚动更新） |
| **流量/依赖出异常** | 反例 9（探针不查依赖）、反例 4（DNS 被墙） |
| **被人攻击** | 反例 3（SA token）、反例 2（Secret 明文） |
| **跑第二遍 / 换环境** | 反例 10（不幂等）、反例 5（标签注入）、反例 6（虚高 requests） |
| **有人误操作** | 反例 8（PDB 挡不住 delete） |

**推论**：**「我在单机上试过了没问题」几乎不构成证据。**
真正要问的是：**「副本变 2 会怎样？依赖挂了会怎样？被 RCE 会怎样？跑第二遍会怎样？」**

> 💡 这与「示例必须按生产规模检验一遍」是同一条原则（Django 课程评审必查项 #28）：
> **示例的数据量可以小，但写法必须大到 10 万行也不炸。**

## 2. 五类认知陷阱

> 这些不是「知识点记错了」，而是**思维层面的系统性偏差**。课程中反复以不同面貌出现。

### 陷阱一：把「没报错」当成「没问题」

**表现**：`kubectl apply` 返回 `created`、Pod 是 Running、命令没报错 → 认为配置正确。

**实际案例**：

| 场景 | 「没报错」 | 真相 |
|------|-----------|------|
| Service 匹配不到后端 | Service 创建成功 | **EndpointSlice 是空的**，服务不通（课 7） |
| NetworkPolicy 未生效 | 策略创建成功 | **CNI 压根不执行策略**（课 10） |
| `kubectl patch ns` | 返回 `patched (no change)` | **修改无效**，ns 仍卡 Terminating（课 18） |
| Job 完成 | 任务成功 | **对象永久残留**，一年攒 50 万个（课 6） |

**守则**：**「成功」只说明 API 接受了你的请求，不说明达成你要的效果。建立独立验证的习惯。**

### 陷阱二：把「工具说的」当成「系统状态」

**表现**：kubectl 输出什么就信什么。

**三个真实案例**（课 18 / 19 / 20 实测）：

```
kubectl patch ns <ns> -p '{"spec":{"finalizers":[]}}'
  → 返回 "patched (no change)"     ← 工具说：成功
  → 实际：namespace 仍 Terminating  ← 真相：无效，须用 /finalize 子资源

kubectl apply 报未知字段错误
  → 看起来是服务端校验失败          ← 工具说：服务端拒绝
  → 实际：客户端 strict decoding 先拦的（须 --validate=false 才能验证服务端 pruning）

kubectl drain 返回成功
  → 看起来节点已安全腾空            ← 工具说：完成
  → 实际：服务可能已经中断（PDB 未覆盖或副本不足）
```

**守则**：**kubectl 是某一层的视图，不是系统状态本身。关键操作后用第二条独立路径交叉验证。**

### 陷阱三：把「默认配置」当成「安全配置」

**表现**：以为 k8s 默认就是安全的/合理的。

**实测的默认行为**（课 15 / 16 / 17）：

| 默认 | 实际风险 |
|------|----------|
| **SA token 自动挂载** | 每个 Pod 白送一个 API 身份 |
| 容器以 **root** 运行 | 逃逸风险 |
| 容器带 **14 项 capabilities** | 权限过大 |
| Secret 文件权限 **0644** | 同 Pod 其他容器可读 |
| PV 回收策略 **Delete** | 删 PVC 即删数据 |
| **审计日志关闭** | 出事无法溯源 |
| NetworkPolicy **默认全通** | 无隔离 |

**守则**：**k8s 的默认取向是「能跑起来」，不是「安全」。安全配置 100% 要你自己加。**

### 陷阱四：把「抽象层」当成「实现层」

**表现**：以为配好了抽象（Ingress / NetworkPolicy / PVC）就等于功能生效。

**真相**：抽象只是**声明**，执行靠**实现方**——而实现方可能压根不存在。

| 抽象 | 需要有实现方 | 没装会怎样 |
|------|-------------|-----------|
| Ingress | Ingress Controller | **配了完全不生效，且无任何报错** |
| NetworkPolicy | 支持策略的 CNI | 同上（课 10 实测 kindnet **支持**，但很多 CNI 不支持） |
| PVC / StorageClass | CSI 驱动 | PVC 一直 Pending |
| GatewayClass | Gateway 实现 | Gateway 不 ACCEPTED |

**守则**：**排障先问「这一层的实现方在不在、活着吗」。**（课 18 五层模型的核心）

### 陷阱五：把「能解决」当成「该用」

**表现**：「k8s 能解决我的问题，所以用 k8s」。

**这是课 20 决策清单的核心**——详见 [课程手册 第 4 章](final-课程手册.md#4-决策清单)。

一句话：**能解决 ≠ 该用。要看净收益（消除的复杂度 − 引入的复杂度）。**

## 3. 配置默认值清单（改之前先知道默认是什么）

> 这一节回答：**「我什么都没配的时候，k8s 到底会怎么做？」**
> 全部为本机实测（✅）或官方文档结论（📄）。

### 3.1 安全相关

| 项 | 默认值 | 建议 |
|----|--------|------|
| ServiceAccount token | **自动挂载** | 不需要时 `automountServiceAccountToken: false` |
| 运行用户 | **root** | `runAsNonRoot: true` + 指定 uid |
| capabilities | **14 项** | `drop: ["ALL"]` |
| 特权提升 | **允许** | `allowPrivilegeEscalation: false` |
| seccomp | **Unconfined** | `RuntimeDefault` |
| Secret 文件权限 | **0644** | 卷挂载时 `defaultMode: 0400` |
| etcd 静态加密 | **关闭** | 开启（生产推荐 KMS v2） |
| 审计日志 | **关闭** | 开启，Secret 别用 `RequestResponse` |
| NetworkPolicy | **默认全通** | 默认全拒 + 逐条放行 |
| RBAC | **默认拒绝** | ✅ 这个默认是安全的，保持即可 |

### 3.2 调度与资源

| 项 | 默认值 | 说明 |
|----|--------|------|
| 只写 limits | **requests 自动 = limits** | 导致超订 + HPA 失真（课 13 ✅） |
| 不写 requests/limits | BestEffort | 最先被驱逐 |
| HPA 缩容稳定窗口 | **300 秒** | 扩得快、缩得慢（课 13 ✅） |
| HPA `minReplicas` | **1**（不写的话） | 单副本无滚动更新（反例 7） |
| 优雅终止 | **30 秒** | 慢应用要调大 |
| 非计划关机 Pod 容忍 | **5 分钟** | 节点宕机后 5 分钟才强制删除（课 19 📄） |
| 节点优雅关闭 | **0s（未启用）** | 生产应启用（课 19 📄） |

### 3.3 存储与配置

| 项 | 默认值 | 说明 |
|----|--------|------|
| PV 回收策略 | **Delete** | **删 PVC 会删数据**（课 12） |
| ConfigMap 卷挂载更新 | **10~100 秒** | 四次实测：10/50/70/100 秒（课 11 ✅） |
| ConfigMap 环境变量 | **永不更新** | 改配置不会自动生效 |
| emptyDir | 随 Pod 删除 | 活过容器重启，**活不过删 Pod**（课 12 ✅） |
| Job 完成后 | **不自动清理** | 每分钟的 CronJob **一年攒 50 万个对象**（课 6） |

### 3.4 运维

| 项 | 默认值 | 说明 |
|----|--------|------|
| 组件证书 | **1 年** | 到期会整个集群不可用（课 19 📄） |
| CA 证书 | **10 年** | — |
| 版本升级 | **不能跳次版本** | 必须逐个次版本升（课 19 📄） |
| HA 控制面 | **最少 3 节点** | 偶数无意义（课 19 📄） |
| etcd 3.6 备份工具 | **etcdutl** | 不再是 etcdctl（课 19 📄） |

## 4. 二十条实战守则

> 每条都是**可执行的动作**，不是原则。按「什么时候会想起它」分组。

### 写 YAML 时

1. **每个 Pod 都显式写 `automountServiceAccountToken`**——不写就是 true
2. **requests 和 limits 都写**，且 requests 按**实际用量**写，不是按 limits 抄
3. **三个探针用不同端点**：startup 查启动、liveness 查进程、readiness **必须查依赖**
4. **HPA 一定写 `minReplicas`**，且 ≥ 2
5. **有状态服务用 StatefulSet**，别用 Deployment + PVC
6. **Job/CronJob 一定设 `ttlSecondsAfterFinished`**
7. **PSA 至少 baseline，能上 restricted 就上**（四件套：非 root / 禁提权 / drop ALL / RuntimeDefault）

### 部署时

8. **先确认依赖的实现方在不在**——Ingress Controller、CNI、CSI、metrics-server
9. **NetworkPolicy 一定放行 DNS**（53 端口），且别用 `ipBlock` 指 ClusterIP
10. **Secret 别用环境变量存高敏值**；需要文件权限时显式 `defaultMode: 0400`
11. **Kustomize 慎用 `commonLabels`**——它会注入 selector
12. **配置变更靠 checksum 注解触发滚动**，不是靠手改

### 上线前

13. **问一句「副本变 2 会怎样」**——共享 PVC / 无滚动更新会在这时炸
14. **问一句「跑第二遍会怎样」**——验收脚本必须幂等
15. **问一句「依赖挂了会怎样」**——readiness 不查依赖 = 流量继续打
16. **确认 PDB 覆盖所有关键服务，且副本数 > PDB 要求**

### 出问题时

17. **服务不通，第一个看 EndpointSlice**，不是看 Service
18. **删除卡住看 finalizer**；真卡死用 `/finalize` 子资源（`kubectl patch ns` 无效）
19. **`kubectl drain` 成功 ≠ 服务活着**——drain 完要主动验证
20. **集群突然全挂，先看证书是否过期**

## 5. 运维视角：七个"养集群"的反例

> 🆕 2026-09-20 补入，来源：[运维专项子教程](子教程/运维专项/overview.md) 课 1-7 实测。
> 第 1 章 10 个反例是**应用视角**（我的服务写得对不对）；这 7 个是**运维视角**（这个集群养得活吗）。
> **关键差别**：应用反例炸的时候只影响一个服务；运维反例炸的时候**整个集群一起完**。

| # | 反例 | 现象（看起来没事） | 真相 | 什么时候炸 |
|---|------|------------------|------|-----------|
| 11 | **没做 etcd 备份** | 集群跑得好好的 | 本机实测 **CronJob 全集群 = 0** | **控制面数据损坏那天**——没得救 |
| 12 | **导出 YAML 当备份** | 有文件、能 restore | 只覆盖 7.7MB，etcd 快照 32MB（**差 4.2 倍**）；Lease/节点状态等集群自维护对象**不在导出里** | 整集群重建时**缺一半** |
| 13 | **备份了从不演练** | "我们有备份" | 恢复后 **uid 必变**，PV 的 `claimRef.uid` 绑死旧 PVC uid | **数据还在盘上，但挂不上** |
| 14 | **备份含系统自维护资源** | 整 ns 导出最省事 | `kube-root-ca.crt` / `default` SA 被 apiserver 自动重建 → 恢复 **Conflict** | 恢复脚本报错，你以为恢复失败了 |
| 15 | **不管证书到期** | 集群正常 | 组件证书 **1 年**（实测 residual 361d），CA 10 年（实测 9y） | **到期那天整个集群不可用**，且不是渐进的 |
| 16 | **节点不留余量** | Pod 都调度上了 | 无 `kube-reserved`/`system-reserved` 预留 → 系统进程与 Pod 抢资源 | 节点 **NotReady**，上面所有 Pod 一起驱逐 |
| 17 | **准入只开默认** | 集群能用 | 实测只开 `NodeRestriction`，**无 VAP / 无 PSA / 无配额** | 任何人能建特权 Pod、能打满集群资源 |

### 5.1 反例 11 与 13 的关系：备份≠可恢复

> 🎯 **这是运维侧最贵的一条教训**，课 7 用真实演练拆开的。

**实测数据**（本机 kind v1.34.0，2026-09-20）：

| 备份方式 | 体量 | 覆盖 | 恢复后 |
|---------|------|------|--------|
| **etcd 快照** | 32 MB | **819 个 key**（含节点、Lease、集群状态） | 原样还原，uid 不变 |
| **YAML 导出** | 7.7 MB | 只有 API 对象 | **uid 全变**（实测 `518414f1` → `2a688fc2`） |

**为什么 uid 变了会致命**：

```text
PV 的 spec.claimRef.uid = 旧 PVC 的 uid
        ↓
应用级恢复生成了新 PVC，uid 变了
        ↓
PV 认不出新 PVC（uid 不匹配）→ 处于 Released/Failed
        ↓
数据在盘上，但挂不上
```

> 🔑 **有状态应用不能靠 YAML 导出恢复**。要恢复有状态数据，只有两条路：**卷快照**，或 **etcd 整库还原**。

**备份污染实测**（反例 14）：

```bash
kubectl -n demo get configmap -o yaml > backup.yaml   # 含 kube-root-ca.crt
kubectl -n demo delete configmap kube-root-ca.crt     # 删掉
kubectl apply -f backup.yaml
# → Error from server (Conflict): the object has been modified
```

**真相**：删掉后 apiserver **立刻自动重建**了它，你再 apply 旧版本就撞车。
**正解**：备份时**剔除系统自维护资源**（`kube-root-ca.crt`、`default` SA、`kubernetes` Service），实测剔除后 Conflict **从 2 个降到 0**。

> 💡 与第 1 章反例 10「验收脚本不幂等」是同一个模式：**只验证过"第一次跑通"，没验证过"第二次还行"**。
> 备份是"第二次"属性最强的操作——**没演练过的备份等于没备份**。

## 6. 运维视角：三类新认知陷阱

> 第 2 章五个陷阱是**应用层**的思维偏差；这三个是**集群层**的，且更隐蔽——因为**日常完全看不出问题**。

### 陷阱六：把「备份了」当成「能恢复」

**表现**：备份任务在跑、文件在增长 → 认为灾备没问题。

**实测拆解**（课 7）：

| 你以为的 | 实测真相 |
|---------|---------|
| 有备份文件 = 能恢复 | 恢复出来的 **uid 必变**，有状态应用挂不上盘 |
| 覆盖全了 | YAML 导出只有 etcd 的 **1/4.2**，Lease/节点状态不在内 |
| 恢复会成功 | 含系统资源 → **Conflict**（实测 2 个） |
| RPO 很小 | 本机 **CronJob=0** → **RPO = ∞**（从没自动备份过） |

**RPO 的实测算法**（课 7 首创，用 etcd revision 外推）：

```bash
# 测两次 revision，算 30 秒增量，外推到备份间隔
rev_t0 = 832908
rev_t30 = 832992
30s 增量 = 84
→ 1 小时备份窗口，丢失约 10080 次写入（84 × 120）
```

> 🔑 **RPO 不是"我配置里写的 1 小时"，而是"两次备份之间真实丢了多少写入"。**
> 算不出来就说明你没测过——**那 RPO 就是无穷大**。

**守则**：**每个备份都必须配一次恢复演练**，且演练要真的删掉东西再恢复。备份的成功率不是"备份任务 exit 0"，是"**恢复演练 exit 0**"。

### 陷阱七：把「集群能跑」当成「集群可交付」

**表现**：`kubectl get nodes` 全 Ready、Pod 都 Running → 认为集群交付完成。

**实测对照**（本机 2026-09-20）：

| 检查项 | 本机实测值 | 能跑吗 | 可交付吗 |
|--------|-----------|--------|---------|
| **自动备份（CronJob）** | **0 个** | ✅ | ❌ |
| **准入插件** | 仅 `NodeRestriction` | ✅ | ❌（无 VAP/PSA/配额） |
| **PSA 标签** | `default` 命名空间**无标签** | ✅ | ❌ |
| **ResourceQuota** | **0 个** | ✅ | ❌ |
| **证书剩余** | 361 天 | ✅ | ⚠️（有台账才能管） |
| 审计日志 | ✅ 已开 | ✅ | ✅ |
| 静态加密 | ✅ 已开 | ✅ | ✅ |

> 🔑 **kubeadm 交付的是"能跑"，不是"能养"**（课 1）。
> CNI、存储、入口、监控、备份、高可用——**这六项 kubeadm 一项都不给**。

**守则**：交付集群时按**清单**验收，不是按"能不能跑 Pod"验收。清单见 [子教程课 1](子教程/运维专项/lessons/lesson-01-集群交付：从裸机到可交付.md)。

### 陷阱八：把「指标在涨」当成「指标是对的」

**表现**：Grafana 有曲线、Prometheus 在采 → 认为监控没问题。

**三个实测反例**：

| 现象 | 真相 |
|------|------|
| 曲线一直在**单调上升** | 那是 **Counter 累积值**，不是瞬时值——告警 `< 0.3` 永不触发 |
| `kubectl top` 有数据 | 只覆盖 **Pod/节点**；控制面组件（apiserver/etcd）要另取 |
| 装箱率 2.93% | 那是 **requests 口径**；实际用量只有 0.68%，**CPU 虚高 4.3 倍** |
| **告警在 Alertmanager 里 `state=active`**（2026-09-21 实测） | **receiver 是 `null`** → 永远无人收到。**告警"活着"不等于"会响"** |

**取数方式的坑**（课 5 实测）：

```bash
kubectl get --raw /metrics      # ✅ 带正确身份，取到 31659 行
curl -sk $APISERVER/metrics     # ❌ Forbidden —— "身份不对"
```

> 🔑 与既有铁律一致（**任何指标写进告警前先核验语义**，mem_274a28_126d48b）：
> **看到一条曲线，先问"这是 Counter 还是 Gauge、单位是什么、谁在报"**，再决定怎么用。

**守则**：**装箱率按实际用量算，不按 requests 算**——否则你会为了根本不存在的负载去买机器。

### 6.1 进阶：告警"活着"≠ 告警"会响"（2026-09-21 实测）

> 🎯 **这是监控系统里最贵的一类失效**：不报错、状态正常、链路通畅——**但永远不会有人收到通知**。
> 前三类失效你查一下能查出来；这一类，**查状态查不出来**。

**实测怎么做的**（本机 `monitoring` 命名空间跑着 kube-prometheus-stack）：

```yaml
- alert: VerifyAlertFiresAlways
  expr: vector(1)          # 恒为真，必然 firing
  labels:
    severity: P1           # ← 一个"看起来很合理"的值
```

**结果对照**（同一条告警，只改一个标签值）：

| severity | Prometheus | Alertmanager state | **receiver** | 实际通知 |
|----------|-----------|-------------------|--------------|---------|
| `P1` | `firing` | **`active`** ✅ | **`null`** ❌ | **永远没有** |
| `warning` | `firing` | `active` ✅ | `echo-warning` ✅ | 正常投递 |

```json
// severity: P1 的真实返回
{"alertname":"VerifyAlertFiresAlways","severity":"P1",
 "receivers":[{"name":"null"}],      // ← 断在这里
 "status":{"state":"active"}}        // ← 但状态是好的
```

**根因**：AlertmanagerConfig `ops-routing` 的路由只认三类值——

```yaml
route:
  receiver: echo-default              # 根路由（兜底）
  routes:
  - matchers: [{name: alertname, value: Watchdog}]  → echo-default
  - matchers: [{name: severity,  value: critical}]  → echo-critical
  - matchers: [{name: severity,  value: warning}]   → echo-warning
```

`P1` 不在其中，且子路由 `continue: false` → 不匹配任何子路由，也不回落到根 receiver，落进**无接收器分支**。

> ⚠️ **反直觉点**：它**不是报错，也不是丢弃**——告警在 AM 里正经排队、正经分组、正经显示 `active`。
> 你打开 AM UI 看到一片绿，会以为监控在正常工作。**这正是它比"没配告警"危险的原因**：没配告警你知道要补，这个你连补的机会都没有。

**为什么"查状态"查不出来**（这是关键）：

| 你查的 | 看到 | 结论（错的） |
|--------|------|-------------|
| Prometheus `/api/v1/alerts` | `state: firing` | "告警正常" |
| AM `/api/v2/alerts` | `state: active` | "送达了" |
| AM UI | 告警列表里有它 | "在管" |
| **AM `/api/v2/alerts` 的 `receivers`** | **`[{"name":"null"}]`** | **✅ 只有这一项能抓出来** |

**验收告警的三步（缺一不可）**：

```bash
# ① Prometheus 侧：确认规则被加载且 firing
curl -s http://prometheus-operated:9090/api/v1/alerts | grep 你的告警名

# ② Alertmanager 侧：关键看 receiver，不是看 state ← 最常漏
curl -s http://<alertmanager>:9093/api/v2/alerts | grep -o '"receivers":\[.*\]'
# 判据：receivers[0].name 绝不能是 "null"

# ③ 接收端：真的收到没
kubectl logs -n monitoring deployment/am-echo --tail=20
```

> 💡 **投递还有延迟**：`groupWait=30s` + `groupInterval=5m`，所以第 ③ 步**要等 5 分钟以上**才能看到。
> 我第一次只等了 90 秒就下"没投递"的结论——**那是错的，是等待不够**，不是链路断了。

**守则（并入守则 20 之后）**：**配完告警必须验证 receiver 不是 `null`。**
告警的完成度不是"规则写对了"，是"**有人真的收到了**"。severity 这类标签**必须落在路由认得的取值集合内**，否则整条链路断在最后一米——**而这和 Counter 配静态阈值是同一类失效：系统全在跑，告警永不响**。

## 7. 运维默认值清单与守则 21-30

### 7.1 运维侧默认值（✅ 本机 kind v1.34.0 实测，2026-09-20）

| 项 | 默认值 / 实测值 | 风险 |
|----|----------------|------|
| **自动备份 CronJob** | **0 个** | RPO = ∞ |
| **准入插件** | 仅 `NodeRestriction` | 无策略约束 |
| **VAP（ValidatingAdmissionPolicy）** | **0 个** | 不拦任何自定义规范 |
| **ResourceQuota / LimitRange** | **0 个** | 单租户可打满集群 |
| **PSA（default 命名空间）** | **无标签** | 可建特权 Pod |
| 组件证书 | **1 年**（实测 361d 剩余） | 到期集群全挂 |
| CA 证书 | **10 年**（实测 9y） | — |
| 装箱率（requests 口径） | 1%~3%（60 核用 1.66 核） | 虚高 4.3 倍 |
| etcd revision 增速 | 30 秒 **84** 次 | 1 小时窗口丢 ~10080 写入 |
| 控制面组件 | 静态 Pod，**kubelet 自动重启** | 删了会自动回来 |
| etcdctl 位置 | **在 etcd Pod 内**，不在控制面容器 | `docker exec` 报 not found |
| etcd 容器 | **distroless**（无 `ls`/`rm`/`tar`） | 常规命令全部失效 |

### 7.2 守则 21-30（运维侧）

> 承接第 4 章的 20 条。前 20 条是"写好 YAML、部署对"，这 10 条是"**别把集群养死**"。

**备份与恢复**

21. **备份必须配恢复演练**——没演练过的备份等于没备份（uid 必变、PV 挂不上，只有练过才知道）
22. **备份剔除系统自维护资源**（`kube-root-ca.crt`、`default` SA、`kubernetes` Service）——否则恢复必 Conflict
23. **有状态应用只认两种备份**：卷快照，或 etcd 整库还原。**YAML 导出救不了有状态数据**
24. **RPO 要算出来，不是配出来**——用 etcd revision 增量外推；算不出 = 没测过 = ∞

**准入与治理**

25. **新准入策略先上 Warn，观察一周再转 Deny**——直接 Deny 会在半夜拦住别人的发布
26. **VAP 用 `namespaceSelector` 锁定范围**——集群级策略一次写错，全集群建不了 Pod
27. **配额要配 LimitRange**——否则不声明 resources 的 Pod 直接 `must specify` 被拒，用户一脸懵

**证书与升级**

28. **建证书台账**（谁、哪天到期、怎么续）——1 年期限不是告警是事实，台账才是解法
29. **升级前备份 etcd**——升级**没有 undo**，实测还会静默删掉手工 patch（课 4 实测 12 处）

**容量**

30. **装箱率按实际用量算，不按 requests 算**——按 requests 会虚高数倍，白买机器
