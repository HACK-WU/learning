## 1. 全课一张图

### 1.1 六个阶段在解决什么问题

整个课程是一条故事线：**一个想「稳稳跑起来」的服务，从单个容器走向生产化**。

| 阶段 | 故事章节 | 核心问题 | 课 |
|------|----------|----------|-----|
| **1 · 心智模型** | 单机时代的终结 | 容器自己不会自愈、不会调度——**谁**来管？ | 1-3（+课 4） |
| **2 · 工作负载** | 让它自己活着 | 不同类型的应用，该用**哪种控制器**？ | 5-6 |
| **3 · 网络** | 让别人找得到它 | Pod IP 会变，**怎么稳定寻址**？外部怎么进来？内部怎么隔离？ | 7-10 |
| **4 · 配置存储资源** | 让它可配置、能持久、会伸缩 | 配置怎么外置？数据存哪？资源够不够？ | 11-14 |
| **5 · 安全** | 别让它被攻破 | 谁能访问？容器权限多大？密钥怎么保护？ | 15-17 |
| **6 · 排障运维扩展** | 出问题怎么办、要不要扩展 | 怎么定位？怎么维护？要不要自己造轮子？ | 18-20 |

> **阶段间的依赖**：1（心智）→ 2（能跑起来）→ 3（能访问）→ 4（能配置能扩）→ 5（安全）→ 6（排障与决策）。
> 但**决策线是独立的**：课 1 埋种子 → 课 9 / 课 14 练选型 → 课 20 收口 → 本手册第 4 章汇总。

### 1.2 20 课全景表

| 课 | 标题 | 一句话核心 | 最有价值的那条实测 |
|----|------|-----------|-------------------|

| 2 | 声明式 API 与调谐 | **声明期望状态**，控制器负责收敛 | 绕过 Deployment 改 RS 被自动纠正 |

| 18 | 系统化排障 | 五层模型 + 三纪律 | **工具会骗人，状态才是真相** |

| 20 | 扩展机制与决策收口 | CRD / 聚合层 / CNI-CRI-CSI / **该不该用** | `observedGeneration` 被 pruning 静默吞掉 |

## 2. 六大心智模型

这六条**不是某一课的知识点**，而是贯穿多课的「暗线」。学完后如果只记住六件事，应该是这六件。

### 模型一：声明式与调谐（课 2 建立，全程复用）

**一句话**：你声明「要什么」，控制器持续对比「现在是什么」，不一致就动作。

**为什么重要**：它解释了 k8s 里**一切自动行为的来源**——自愈（课 1）、滚动更新（课 5）、HPA 扩缩（课 13）、Operator（课 20）都是同一个循环的不同实例。

**反直觉点**：你手动改下层对象（如直接改 ReplicaSet 的 replicas），会被上层控制器**改回去**。这不是 bug，是调谐在工作。

### 模型二：抽象与实现分离（课 7 / 8 / 12 / 20）

**一句话**：k8s 大量使用「接口 + 实现」分层——你声明抽象，具体谁来做由实现方决定。

| 抽象 | 实现 | 出处 |
|------|------|------|
| Service | kube-proxy（iptables / IPVS） | 课 7 |
| Ingress | Ingress Controller（nginx / traefik…） | 课 8 |
| GatewayClass | Gateway 实现（Envoy Gateway…） | 课 9 |
| PVC / StorageClass | CSI 驱动 | 课 12 |
| NetworkPolicy | CNI 插件 | 课 10 |
| RuntimeClass | CRI 运行时（containerd…） | 课 20 |

**排障价值**：出问题时先问「**这一层的实现方在不在**」。Ingress 配好不通 → 可能压根没装 Controller；NetworkPolicy 不生效 → CNI 可能不执行策略（**这两条都在课 10 实测过**）。

### 模型三：标签与选择器是黏合剂（课 7）

**一句话**：k8s 没有「资源树」，对象之间的关联**全靠标签匹配**。

Service 找 Pod、Deployment 管 ReplicaSet、NetworkPolicy 选中 Pod、HPA 关联目标——**全部是标签匹配**。

**常见故障**：标签写错一个字母 → Service 匹配不到后端 → EndpointSlice 为空 → 服务不通，**但 Service 本身创建成功、无任何报错**。这是课 7 与课 18 共同强调的排障要点。

### 模型四：状态与终态分离（课 5 / 6 / 18）

**一句话**：区分「你声明的期望」「对象的当前状态」「观察到的事实」三层。

- `spec` = 你要什么
- `status` = 控制器认为现在是什么
- **真实情况** = 可能两者都不是

**典型场景**：`kubectl drain` 返回成功（spec 层动作完成），但服务已经挂了（真实情况）。课 19 的「drained 成功 ≠ 服务活着」就是这个模型。

### 模型五：安全是叠加的，不是一次性的（课 15 / 16 / 17）

**一句话**：4C 模型（Cloud / Cluster / Container / Code）——**每一层都要做，且互不替代**。

容器的 `securityContext` 做得再好，也挡不住一个 `cluster-admin` 的 ServiceAccount；RBAC 收得再紧，root 运行的容器仍可能逃逸。

**最易忽略的一条**：**默认挂载 ServiceAccount token** —— 一个「什么都没配」的 Pod，已经拿到了访问 API 的凭证。

### 模型六：工具会骗人，状态才是真相（课 18）

**一句话**：kubectl 的输出是**某一层的视图**，不一定等于系统状态。

三个真实案例（都是课程中实测到的）：

| 现象 | 工具说的 | 真相 |
|------|----------|------|
| `kubectl patch ns` 返回 `patched (no change)` | 修改成功 | **无效**，namespace 仍卡 Terminating（须用 `/finalize`） |
| kubectl 报未知字段错误 | 服务端校验失败 | **可能是客户端 strict decoding 先拦的**（须 `--validate=false` 才能验证服务端 pruning） |
| `kubectl drain` 成功 | 节点已安全腾空 | 服务可能已中断（PDB 未覆盖或副本不足） |

> 🎯 **这三条构成贯穿课 18 / 19 / 20 的同一条暗线**：**先取证、再下结论**。

## 3. 按场景反查表

> **用法**：遇到具体问题，从左边找场景 → 直接跳到对应课。这是本手册最常用的部分。

### 3.1 「我要做一件事」

| 我想… | 去哪课 | 关键决策点 |
|-------|--------|-----------|
| 跑一个无状态服务 | **课 5** Deployment | 副本数、`maxSurge`/`maxUnavailable` |
| 跑一个有状态服务（数据库） | **课 6** StatefulSet | 独享卷、稳定标识；**别用 Deployment + PVC** |
| 每台机器上跑一个（日志/监控） | **课 6** DaemonSet | 无需指定副本数，随节点增减 |
| 跑一次就结束的任务 | **课 6** Job / CronJob | **务必设 TTL**，否则残留堆积 |
| 让服务被集群内访问 | **课 7** Service | ClusterIP / NodePort / LoadBalancer 选型 |
| 让服务被外部访问 | **课 9** Gateway API | ⚠️ Ingress 已冻结，新项目用 Gateway API |
| 切分流量做灰度 | **课 8 / 课 9** | Gateway API 的 `weight` 更原生 |
| 限制 Pod 之间的访问 | **课 10** NetworkPolicy | 白名单模型；**先确认 CNI 支不支持** |
| 把配置从镜像里拿出来 | **课 11** ConfigMap | 环境变量不热更新，卷挂载会（50~100s） |
| 存密码/凭证 | **课 11 + 课 17** Secret | **base64 不是加密**；`defaultMode: 0400` |
| 让数据删 Pod 不丢 | **课 12** PVC | 回收策略默认 Delete，**删 PVC 会删数据** |
| 限制 CPU/内存 | **课 13** requests/limits | 只写 limits 会自动补齐 requests |
| 让它自动扩缩 | **课 13** HPA | 需 metrics-server；**缩容有 300s 稳定窗口** |
| 给命名空间设上限 | **课 13** ResourceQuota | 超额是**拒绝创建**，不是 Pending |
| 管理多环境配置 | **课 14** Kustomize | base + overlay，**无模板逻辑** |
| 打包分发应用 | **课 14** Helm | 有版本台账可回滚；**release 是 Secret** |
| 限制谁能调 API | **课 15** RBAC | 默认拒绝；注意 SA token 默认挂载 |
| 收紧容器权限 | **课 16** PSA | restricted 四件套（非 root / 禁提权 / 丢能力 / seccomp） |
| 加密 etcd 里的 Secret | **课 17** | `identity` 必须最后；生产推荐 KMS v2 |
| 记录谁动了集群 | **课 17** 审计 | **默认关闭**；Secret 别用 `RequestResponse` |
| 自定义一种资源 | **课 20** CRD | CRD 是**菜单不是后厨**，还得写控制器 |
| 自己造一个运维机器人 | **课 20** Operator | 先问「能不能用现成的」 |

### 3.2 「出问题了」

| 现象 | 先看哪课 | 第一反应命令 |
|------|----------|-------------|
| Pod 起不来（Pending） | **课 13** | `kubectl describe pod` 看 Events：资格问题 vs 容量问题 |
| Pod 反复重启 | **课 3 + 课 18** | 看退出码 + `kubectl logs --previous` |
| Pod 一直 NotReady | **课 3** | 探针配置错误？`kubectl describe` 看 readiness 失败原因 |
| 服务不通（集群内） | **课 7 + 课 18** | `kubectl get endpointslice` —— **后端列表是不是空的** |
| 服务不通（外部） | **课 9** | Gateway 是否 ACCEPTED？HTTPRoute 是否匹配？ |
| DNS 解析失败 | **课 7** | CoreDNS Pod 状态 + `/etc/resolv.conf` |
| NetworkPolicy 不生效 | **课 10** | **先确认 CNI 是否执行策略**（kindnet 实测支持） |
| 扩容没反应 | **课 13** | metrics-server 装了吗？`kubectl top` 有数据吗？ |
| 删除卡住（Terminating） | **课 18** | finalizer 非空 → 用 `/finalize` 子资源 |
| 节点维护后服务挂了 | **课 19** | PDB 算过吗？副本数够吗？ |
| 集群突然全挂 | **课 19** | **先看证书是否过期** |
| 配置改了没生效 | **课 11** | 环境变量永不更新；卷挂载要等 50~100s |
| 权限被拒（403/401） | **课 15** | 401 = 坏 token；403 = 无 token（anonymous） |
| 忘了改了什么 | **课 5 / 课 14** | Deployment 有历史；Helm 有 REVISION |

## 4. 决策清单

> 这是全课程的收口。**20 课教你「怎么用」，这一章回答「该不该用」。**
> 原始出处：[课 20 知识点 5](stages/6-排障运维与扩展/lessons/lesson-20-扩展机制与决策收口.md)（决策课，无命令可跑，判据来自业界分析与官方生产考量，**标 📄**）

### 4.1 核心判据

> **k8s 最有价值的时刻，是它从应用运维中消除的复杂度，大于运维 k8s 本身引入的复杂度。**

**两种问法的差别**（这是整个决策的关键）：

| 问法 | 答案 | 是否有用 |
|------|------|----------|
| ❌ 「我的应用**能不能**跑在 k8s 上？」 | 几乎总是**能** | **没用** |
| ✅ 「这个系统的运维复杂度，**配得上** k8s 的运维复杂度吗？」 | 视情况 | **这才是要回答的** |

**一句话类比**：k8s 是**载重卡车**——自动装卸、车队调度、故障自愈都很强。但如果你每天只送一箱牛奶去隔壁街，**骑电动车 10 分钟就到了**，卡车还要驾照、保险、停车位和保养。

> **问题从来不是「卡车能不能送牛奶」，而是「送牛奶该不该开卡车」。**

### 4.2 六个「该用」信号

满足 **3 条以上**，认真考虑：

| # | 信号 | 说明 |
|---|------|------|
| 1 | **多个服务需独立扩缩容** | 高流量 API 与低流量后台要分开扩 |
| 2 | **有真正的高可用要求** | 不能有单点，需跨节点分布 |
| 3 | **多团队需要隔离与自助** | namespace + RBAC 提供逻辑隔离 |
| 4 | **部署频繁**（一天多次） | 滚动更新、健康门禁成为刚需 |
| 5 | **流量波动大且不可预测** | HPA 按指标扩缩真的省钱 |
| 6 | **有专人/团队负责平台** | **k8s 没有 owner 会腐化** |

### 4.3 六个「不该用」信号

满足 **2 条以上**，请三思：

| # | 信号 | 说明 |
|---|------|------|
| 1 | **全部能装进一台机器** | 调度器没东西可调 |
| 2 | **流量可预测**（峰谷差 3 倍内） | 自动扩缩容没价值 |
| 3 | **团队少于 3 人碰基础设施** | 学习曲线风险先于价值到来 |
| 4 | **单体应用** | 单进程几乎得不到编排收益 |
| 5 | **没有专职平台 owner** | 版本偏差、CNI 升级、证书轮换会自己找上门 |
| 6 | **预算有限**（< $5000/月） | 最小生产配置起步几百美元/月 |

### 4.4 两条「假信号」（业界反复强调）

> ⚠️ 这两条最常见，也最容易误导决策：
>
> - ❌ **「我们以后可能会扩展」** —— 这是**愿望，不是负载**
> - ❌ **「大公司都在用 / 投资人期待」** —— 基础设施要匹配**当前**的运维复杂度，不是 aspirational 的规模

### 4.5 方案对比与渐进路径

| 方案 | 运维负担 | 适合 | 主要缺点 |
|------|----------|------|----------|
| **托管 PaaS**（Render / Railway / Fly.io） | 极低 | 1-10 服务、小团队 | 单价高、平台锁定 |
| **单机 + Docker Compose** | 低 | 副项目、内部工具、MVP | 手动扩缩、单点故障 |
| **VM + systemd** | 低-中 | 长期单体、负载可预测 | 自己管 OS 与部署脚本 |
| **ECS / Fargate** | 中 | 已投入 AWS、服务数中等 | AWS 专有、IAM 复杂 |
| **托管 k8s**（EKS/GKE/AKS） | 高 | 多服务、真要扩缩容、有平台团队 | **运维税重、配置面大** |
| **自建 k8s** | **极高** | 特定合规/硬件需求 | **你等于成了一家基础设施公司** |

**渐进路径**（业界推荐）：

```
单机 Compose →（服务变多）→ Swarm / Kamal / Nomad →（8-12+ 服务、要真扩缩容、有 owner）→ k8s
```

> 💡 **推荐做法**：**先用托管容器服务跑 6-12 个月**。很多团队会发现「够用了」，迁移问题自然消失。

### 4.6 用这 20 课的证据回答「值不值」

你有权要求回答这个问题——**因为你已经知道它真实的价格**：

| 你学到的 | 它意味着的**持续成本** |
|----------|----------------------|
| 课 13：污点、亲和、requests/limits | 调度规则要设计，资源要压测 |
| 课 19：drain 三坑、PDB 计算 | 每次维护都是一次需小心设计的操作 |
| 课 19：证书 1 年、etcd 3.6 换 etcdutl | **备份脚本会随版本失效** |
| 课 19：HA 最少 3 节点 | 最小生产配置就不是「一台机器」 |
| 课 18：finalizer 卡删除 | 需要懂内部机制才能修 |
| 课 19：StatefulSet 卡 Terminating | 有状态负载是真正的难点 |
| 课 20：Operator 复杂度税 | 「要不要自己写」又是一道决策题 |

> 🎯 **把这些加起来**：
> **k8s 不是「装上就完事」的工具，是一份长期的运维契约。**
> 换给你的是：**标准化、可移植、自愈、生态**。
> 要你付出的是：**学习曲线、持续升级、专人维护**。
>
> **这笔交易在大规模下非常划算，在小规模下通常是亏的。**

### 4.7 两个必须破除的误区

> 🐞 **误区 1**：「k8s 能解决我的问题，所以该用。」
> **能解决 ≠ 该用。** 要看**净收益**（消除的复杂度 − 引入的复杂度）。

> 🐞 **误区 2**：「用了 k8s 就不用管运维了。」
> **恰恰相反**——它把运维工作**标准化**了，但**没有减少**它。升级、证书、监控、备份一样不少。

## 6. 延伸阅读

> 这七个主题**刻意不占课时**——属 v1.34 新特性、需要特定硬件/多节点，或对「入门偏进阶」定位偏深。
> 位置：作为「知道有这回事、知道什么时候去查」的路标，不做深入讲解。
>
> | # | 主题 | 一句话定位 | 何时去查 |
> |---|---|---|---|
> | 6.1 | DRA 动态资源分配 | GPU/FPGA 等参数化设备 | 要在 k8s 跑 AI 训练、切分 GPU |
> | 6.2 | PodGroup 成组调度 | "要么全起，要么都别起" | 任务永远起不全、部分 Pod 空转 |
> | 6.3 | Windows 容器 | .NET Framework 等 Windows 负载 | 存量 Windows 业务要容器化 |
> | 6.4 | API 流控 APF | 保护控制面不被打挂 | `kubectl` 卡顿、控制面变慢 |
> | 6.5 | `kubectl debug` 临时容器 | distroless 镜像的排障入口 | `exec` 进去发现没有 shell |
> | 6.6 | 拓扑分布约束 | 跨故障域均匀分布副本 | 上多可用区集群、副本挤在一台 |
> | 6.7 | Server-Side Apply | 多控制器协作的字段归属 | `apply` 覆盖了别人的改动 |

### 6.1 DRA（Dynamic Resource Allocation，动态资源分配）

**解决什么**：传统 `resources` 只能声明 CPU / 内存 / 少量扩展资源。**GPU、FPGA、RDMA 这类「需要参数化配置」的设备**表达不了——DRA 就是为此设计的第三代设备插件机制。

**为什么没占课时**：需要真实硬件（或厂商驱动）才能体现价值，kind 上无法实操。

**什么时候去查**：你要在 k8s 上跑 AI 训练、需要把一块 GPU 切成多份共享给多个 Pod 时。

### 6.2 PodGroup 成组调度

**解决什么**：默认调度器**一个一个**调度 Pod。但 **MPI / 分布式训练**这类任务要求「**要么全部起，要么都别起**」——只起了 3/8 个 worker，剩下的等资源，先起的那 3 个白占着资源（死锁）。

**为什么没占课时**：需要额外安装调度器插件（如 Volcano / Koordinator / SAI），且属批处理与 AI 场景，超出本课程定位。

**什么时候去查**：你遇到「任务永远起不全、部分 Pod 空转等资源」时。

### 6.3 Windows 容器

**解决什么**：让 **.NET Framework 等 Windows 专有负载**也能进 k8s，与 Linux 工作负载混部。

**为什么没占课时**：镜像体积大（GB 级）、版本兼容性矩阵复杂（宿主 OS 与容器 OS 版本须匹配）、且需 Windows 节点——本机环境不具备。

**什么时候去查**：你有必须跑在 Windows 上的存量业务要容器化时。**先确认节点 OS 与容器基础镜像的版本兼容矩阵**，这是最常见的坑。

### 6.4 API 流控（API Priority and Fairness）

**解决什么**：API Server 是**所有组件的中枢**。早期只能靠 `--max-requests-inflight` 做粗粒度限流——一个失控的客户端（比如写错的 List-Watch）**能把整个控制面打挂**。APF 提供**按优先级与公平性**的细粒度流控。

**为什么没占课时**：单节点学习集群不会遇到；且默认配置已足够（k8s 自带 `system`、`leader-election`、`workload-low` 等 FlowSchema）。

**什么时候去查**：**控制面变慢、`kubectl` 卡顿**且怀疑是某个客户端在疯狂请求时。
快速判断：`kubectl get flowschemas` / `kubectl get prioritylevelconfigurations`。

### 6.5 `kubectl debug` 与临时容器（Ephemeral Containers）

**解决什么**：生产 Pod 常常用**精简镜像**（distroless / scratch），里面**没有 shell、没有 curl、没有 ps**——`kubectl exec` 进去什么都干不了。临时容器让你往**正在运行的 Pod 里**临时插一个带完整工具链的调试容器（v1.25 起 GA）。

```bash
kubectl debug -it <pod> --image=busybox:1.37 --target=<container>   # 共享进程命名空间
kubectl debug node/<node> -it --image=busybox                       # 调试节点（自动建宿主 Pod）
```

**为什么没占课时**：课 18 排障课聚焦**分层定位方法论**（五层模型 + 三纪律），工具层面只覆盖了 `logs` / `describe` / `events` / `exec`；临时容器属"工具箱扩展"，且需要镜像拉取，在离线环境不便演示。

**什么时候去查**：你 `kubectl exec` 进生产 Pod 发现**没有 shell 或缺少诊断命令**时。这是 distroless 镜像的标准排障入口。

> 💡 与课 18 的关系：临时容器是**第五层（容器内）**排障的补强手段，不改变分层定位的思路本身。

### 6.6 Pod 拓扑分布约束（Topology Spread Constraints）

**解决什么**：`podAntiAffinity` 只能表达"不要和同类 Pod 挤一起"，粒度粗。拓扑分布约束可以声明"在 zone / node 这些故障域之间**尽量均匀**，且允许指定**最大倾斜度**"：

```yaml
spec:
  topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: topology.kubernetes.io/zone
    whenUnsatisfiable: DoNotSchedule      # 或 ScheduleAnyway
    labelSelector:
      matchLabels: { app: my-app }
```

**为什么没占课时**：它的价值在**多节点 / 多可用区**才体现，而本机学习集群是**单节点 kind**（实测 `kubectl get nodes` = 1），无法演示分布效果，讲了也只能停留在 YAML 层面。

**什么时候去查**：你上多可用区生产集群，需要控制副本分布、或遇到"副本都挤在同一台机器"时。CKA「Workloads & Scheduling」明确考纲项。

### 6.7 Server-Side Apply（服务器端应用）

**解决什么**：`kubectl apply` 默认用 **last-applied annotation** 记录字段归属，多控制器协作改同一对象时会**互相覆盖**。Server-Side Apply 把字段归属权记在**服务端**（`metadata.managedFields`），谁是哪个字段的 owner 一清二楚（v1.22 起 GA，**特性门控已移除**，不可关闭）。

```bash
kubectl apply --server-side -f manifest.yaml
kubectl get <res> <name> -o yaml | grep -A20 managedFields
```

**为什么没占课时**：日常单人操作感知不到差异；它的价值在**多人/多控制器协作**（如 GitOps 工具与手动修改并存）时才显现，属"知道有这回事"层级。

**什么时候去查**：你发现 `kubectl apply` **把别人的改动覆盖掉了**，或需要排查"这个字段到底是谁设的"时。
