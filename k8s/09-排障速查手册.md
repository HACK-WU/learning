## 1. 三条纪律（比命令更重要）

> 🔑 出自 [课 18](stages/6-排障运维与扩展/lessons/lesson-18-系统化排障分层定位法.md)（第 231 行）。**这三条比任何命令都重要。**

**纪律一：先取证，后动手。**
在搞清楚原因之前，**不要重启、不要删 Pod**。重启会**销毁现场**——CrashLoopBackOff 的容器一旦被删，`--previous` 日志就没了。

**纪律二：一次只改一处。**
同时改三处，就算修好了也不知道是哪个起的作用，下次还会犯。

**纪律三：读懂原文再下结论。**
Events 里写的是 `Insufficient cpu` 还是 `didn't match node affinity`，**是两个完全不同的问题**。别扫一眼就猜。

## 2. 五层模型：自顶向下逐层排除

> **为什么必须逐层**：没有医生会跳过生命体征直接做 CT。如果节点全 NotReady，你去查 Pod 日志毫无意义。

| 层 | 问句 | 核心命令 | 判据（正常应该是什么） |
|---|---|---|---|
| **L0 集群整体** | 只有我坏了，还是全坏了？ | `kubectl get nodes`、`kubectl get pods -A` | 节点全 `Ready`；kube-system 全 `Running` |
| **L1 节点** | 承载它的机器还好吗？ | `kubectl describe node <n>` | 四项压力 `False` + `Ready=True` |
| **L2 控制面** | 调度与决策还工作吗？ | `kubectl get pods -n kube-system` | apiserver/scheduler/cm/etcd 全 `1/1 Running` |
| **L3 工作负载** | Pod 卡在哪一步？ | `kubectl describe pod`、`kubectl logs` | 见下方四态判据 |
| **L4 网络与存储** | 别人访问得到它吗？ | `kubectl get endpointslice`、`kubectl exec -- wget` | EndpointSlice 有后端；能连通 |

### 2.1 跳层的代价（真实案例）

假设故障是**节点磁盘满了**（L1）。如果你直接跳到 L3 查 Pod 日志：

- 日志可能因为磁盘满而**写不进去** → 你看到的是空日志
- 你可能判断「应用没输出」 → 去查应用代码
- **真正的原因（L1 磁盘）被完全忽略**

而如果先查 L1：`kubectl describe node` 一眼看到 `DiskPressure=True`，**30 秒定位**。

### 2.2 关键节点判据

> 🔑 **`Ready=True` 且另外三项全 `False`，节点才算健康。** 任一项为 True，kubelet 会开始驱逐 Pod。

四项条件：`MemoryPressure` / `DiskPressure` / `PIDPressure` / `Ready`

| 条件 | True 意味着 | 常见原因 |
|---|---|---|
| `MemoryPressure` | 节点内存不足 | Pod 内存泄漏 / limits 设太高 |
| `DiskPressure` | 磁盘不足 | 镜像堆积、日志未轮转、emptyDir 写满 |
| `PIDPressure` | 进程数耗尽 | fork 炸弹 |
| `Ready` | 是否可调度 | kubelet 挂了 / 网络插件异常 / **上面三项任一为 True** |

## 3. 按症状速查

### 3.1 Pod 起不来（Pending）

```bash
kubectl describe pod <pod>          # 看 Events（最重要）
kubectl get pod <pod> -o wide       # 看在哪个节点
```

| Events 原文 | 根因 | 解决 |
|---|---|---|
| `Insufficient cpu / memory` | 资源不够 | 降低 requests / 加节点 |
| `didn't match Pod's node affinity/selector` | nodeSelector / 亲和性不匹配 | 检查标签 |
| `had untolerated taint` | 污点不容忍 | 加 toleration（课 13） |
| `persistentvolumeclaim not found` | PVC 未绑定 | 检查 PVC / StorageClass（课 12） |

> ⚠️ **注意**：`Insufficient cpu` 是**容量问题**，`didn't match node affinity` 是**资格问题**——**两者解决方向完全不同**，别看混了。

### 3.2 Pod 拉不到镜像（ImagePullBackOff）

| 状态 | 含义 |
|---|---|
| `ErrImagePull` | **正在**尝试拉取且失败了（第一次/重试中） |
| `ImagePullBackOff` | 失败多次，**退避等待**后再试 |

`ErrImagePull` → `ImagePullBackOff` 是「从失败到放弃挣扎」的过程。

| Events 关键词 | 根因 |
|---|---|
| `not found` / `manifest unknown` | 镜像名或 tag 错了 |
| `unauthorized` / `authentication required` | 私有仓库没配 `imagePullSecrets` |
| `connection refused` / `i/o timeout` | 网络不通/被墙 |

### 3.3 Pod 反复重启（CrashLoopBackOff）

```bash
kubectl logs <pod>                  # 当前这次
kubectl logs <pod> --previous       # 上一次（关键证据！）

# 看退出码
kubectl get pod <pod> -o jsonpath='{.status.containerStatuses[0].lastState.terminated.exitCode}'
```

**退出码判据**：

| 退出码 | 含义 | 方向 |
|---|---|---|
| **1** | 应用自己报错退出 | 看日志，查配置/代码 |
| **137** | `128+9` = **被 SIGKILL** | 通常是 **OOMKilled**（内存超限） |
| **143** | `128+15` = **被 SIGTERM** | 优雅终止/被驱逐 |
| **127** | 命令找不到 | `command` 写错 |

> ⚠️ **`--previous` 不是任何时候都能拿到**——容器重启策略、日志轮转都可能让它消失。**所以纪律一说：先取证再动手，别急着删 Pod。**

### 3.4 服务不通

```bash
kubectl get endpointslice -A                        # ← 第一个看这个
kubectl get svc <svc> -o yaml                       # selector 对不对
kubectl -n kube-system get pods -l k8s-app=kube-dns # CoreDNS 活着吗
```

> 🎯 **服务不通，第一个看 EndpointSlice，不是看 Service。**
> Service 创建成功但 selector 写错 → **EndpointSlice 是空的** → 服务不通，**且无任何报错**。

**EndpointSlice 判据**：`endpoints: null` = **无后端** = selector 没匹配到 Pod。

### 3.5 DNS 解析失败

> ⚠️ **反直觉实测（课 18）**：**`nslookup` 说 DNS 坏了，但应用跑得好好的。**

```bash
$ kubectl exec curl-test -- nslookup kubernetes.default
# → 可能报 NXDOMAIN（假警报）
```

**真相**：busybox 的 `nslookup` 是**独立实现的诊断工具**，它不按 glibc 的方式补全 search 域。
应用走 glibc 解析器（会正确补全），`nslookup` 走自己的逻辑。

> 🔑 **用 `nslookup` 的 NXDOMAIN 判定「DNS 坏了」，很可能是一次假警报。**
> 真要验证，用**应用实际的方式**访问（比如 `wget`），或用带完整 FQDN 的名字（`kubernetes.default.svc.cluster.local`）。

### 3.6 删除卡住（Terminating）

```bash
kubectl get ns <ns> -o json | jq '.spec.finalizers'
```

finalizer 非空 → 资源在等某个控制器做清理。**真卡死时用 `/finalize` 子资源**（见第 5 章）。

### 3.7 权限问题（401 / 403）

| 状态码 | 含义 |
|---|---|
| **401** | **坏 token**（凭证无效/过期） |
| **403** | **无 token**（以 anonymous 身份访问，RBAC 默认拒绝） |

```bash
kubectl auth can-i <verb> <resource> --as=system:serviceaccount:<ns>:<sa>
```

### 3.8 集群突然全挂

> 🎯 **先看证书是否过期**（课 19：组件证书 **1 年**）。

```bash
kubeadm certs check-expiration     # 自建集群
kubectl get pods -n kube-system    # 控制面还活着吗
```

## 4. 判据速查表

> 「我看到了这段输出，这算正常还是异常？」

### 4.1 节点

| 输出 | 判定 |
|---|---|
| `Ready=True` + 四项压力全 `False` | ✅ 健康 |
| 任一项压力 `True` | ❌ kubelet 会开始驱逐 Pod |
| `Ready=Unknown` | 节点失联（网络/ kubelet 挂了） |

### 4.2 Pod

| 状态 | 含义 | 下一步 |
|---|---|---|
| `Pending` | 没被调度 | 看 Events（3.1） |
| `ImagePullBackOff` | 镜像拉不到 | 看 Events 关键词（3.2） |
| `CrashLoopBackOff` | 启动就退出 | 看退出码（3.3） |
| `Running` 但 `0/1 Ready` | 探针没过 | 看 readiness 配置 |
| `Terminating` 卡住 | finalizer | 看 3.6 |

### 4.3 网络

| 输出 | 判定 |
|---|---|
| EndpointSlice `endpoints: null` | ❌ 无后端（selector 失配） |
| EndpointSlice 有内容 | ✅ 后端正常，问题在别处 |
| Gateway `ACCEPTED=False` | ❌ GatewayClass 实现方不在 |
| 所有服务名解析失败 | 检查 NetworkPolicy **是否放行 DNS** |

### 4.4 资源

| 输出 | 判定 |
|---|---|
| `kubectl top` 无数据 | metrics-server 未装 → HPA 不会工作 |
| HPA 一直不扩容 | 检查 metrics + `minReplicas`/`maxReplicas` |
| 扩容快、缩容慢 | ✅ 正常（缩容稳定窗口 **300 秒**） |

## 5. 急救命令

> ⚠️ 这些是**最后手段**。用之前确认你理解后果（纪律一：先取证）。

### 5.1 强制删除卡住的 namespace

```bash
# ❌ 无效（实测）：kubectl patch ns <ns> -p '{"spec":{"finalizers":[]}}'
#    返回 "patched (no change)"，但 ns 仍卡 Terminating

# ✅ 有效：用 /finalize 子资源
kubectl get ns <ns> -o json > /tmp/ns.json
python3 - <<'PY'
import json
d = json.load(open('/tmp/ns.json'))
d['spec']['finalizers'] = []
json.dump(d, open('/tmp/ns.json','w'))
PY
kubectl replace --raw /api/v1/namespaces/<ns>/finalize -f /tmp/ns.json
```

> 🔑 **不依赖 `jq`**——课 20 补充讲义复审时特意去掉了 jq 依赖。

### 5.2 拿回 CrashLoopBackOff 的最后一次日志

```bash
kubectl logs <pod> --previous
# 若已被删除则拿不到了 —— 所以别急着删 Pod
```

### 5.3 节点维护三件套

```bash
kubectl cordon <node>     # 封住新调度
kubectl drain <node> --ignore-daemonsets --delete-emptydir-data
# PDB 限制同时驱逐的数量（需提前配好）
```

> ⚠️ **drain 的三个坑**（课 19 实测）：**DaemonSet / emptyDir / 裸 Pod**。
> ⚠️ **`drain` 成功 ≠ 服务活着**——drain 完必须主动验证。

## 6. 四个「工具骗人」的真实案例

> 这四个案例构成贯穿课 18 / 19 / 20 的同一条暗线：**先取证、再下结论**。

### 案例一：`kubectl patch ns` 的假成功

```bash
$ kubectl patch ns stuck -p '{"spec":{"finalizers":[]}}'
namespace/stuck patched (no change)     # ← 看起来成功了
$ kubectl get ns stuck
NAME    STATUS        AGE
stuck   Terminating   10m               # ← 实际没用
```

**真相**：`patch` 走的是普通资源路径，finalizer 需要通过 **`/finalize` 子资源**修改。
**教训**：**返回成功 ≠ 达成效果**。

### 案例二：kubectl 的未知字段报错，未必来自服务端

```bash
$ kubectl apply -f cr.yaml
error: unknown field "spec.foo"        # ← 看起来是服务端拒绝
```

**真相**：可能是**客户端 strict decoding 先拦下的**。要验证服务端行为（如 CRD pruning），得加 `--validate=false`。
**教训**：**先搞清楚报错来自哪一层**。

### 案例三：`kubectl drain` 成功，但服务已经挂了

```bash
$ kubectl drain node-1 --ignore-daemonsets
node/node-1 drained                     # ← 成功
```

**真相**：PDB 未覆盖或副本不足时，drain 会把服务**一起腾空**。
**教训**：**drain 完必须主动验证服务存活**，不能只看命令返回值。

### 案例四：`kubectl run --overrides` 被静默吞掉（2026-09-15 新增）

验证准入类行为（如引用不存在的 PriorityClass 应报 `Forbidden`）时：

```bash
# 写法 A：-- sleep 写在 --overrides 之前
$ kubectl run pc-bad --image=busybox:1.37 --restart=Never -- sleep 3600 \
    --overrides='{"spec":{"priorityClassName":"pc-not-exist", ...}}'
pod/pc-bad created          # ← 没报错！但 overrides 根本没生效

# 写法 B：用 YAML
$ kubectl apply -f - <<'EOF'   # spec.priorityClassName: pc-not-exist
EOF
Error from server (Forbidden): pods "pc-bad" is forbidden:
  no PriorityClass with name pc-not-exist was found     # ← 真实行为
```

**真相**：`-- <命令>` 之后的**所有内容都被当作容器启动参数**，`--overrides` 被吃掉，Pod 建出来 `spec.priority` 是 0，自然不触发校验。
**教训**：**验证准入/校验类行为，用 YAML 文件，别用 `kubectl run` 拼参数**——它会用"成功"骗过你。这属于「看起来通过、实际没测到」的最危险一类。

> 📌 出处：[课 13 知识点 6](stages/4-配置存储资源工程化/lessons/lesson-13-资源调度扩缩容.md)。这是讲义复验时发现的——首轮用 `kubectl run` 测出的"Forbidden"结论碰巧正确，但复验同款命令却不报错，**追查后才发现是参数位置在捣鬼**。
