## 1. 三条纪律（比命令更重要）

> 🔑 出自 [课 18](stages/6-排障运维与扩展/lessons/lesson-18-系统化排障分层定位法.md)（第 231 行）。**这三条比任何命令都重要。**

**纪律一：先取证，后动手。**
在搞清楚原因之前，**不要重启、不要删 Pod**。重启会**销毁现场**——CrashLoopBackOff 的容器一旦被删，`--previous` 日志就没了。

**纪律二：一次只改一处。**
同时改三处，就算修好了也不知道是哪个起的作用，下次还会犯。

**纪律三：读懂原文再下结论。**
Events 里写的是 `Insufficient cpu` 还是 `didn't match node affinity`，**是两个完全不同的问题**。别扫一眼就猜。

## 2. 五层模型：自顶向下逐层排除

> **为什么必须逐层**：没有医生会跳过生命体征直接做 CT。如果节点全 NotReady，你去查 Pod 日志毫无意义。

| 层 | 问句 | 核心命令 | 判据（正常应该是什么） |
|---|---|---|---|
| **L0 集群整体** | 只有我坏了，还是全坏了？ | `kubectl get nodes`、`kubectl get pods -A` | 节点全 `Ready`；kube-system 全 `Running` |
| **L1 节点** | 承载它的机器还好吗？ | `kubectl describe node <n>` | 四项压力 `False` + `Ready=True` |
| **L2 控制面** | 调度与决策还工作吗？ | `kubectl get pods -n kube-system` | apiserver/scheduler/cm/etcd 全 `1/1 Running` |
| **L3 工作负载** | Pod 卡在哪一步？ | `kubectl describe pod`、`kubectl logs` | 见下方四态判据 |
| **L4 网络与存储** | 别人访问得到它吗？ | `kubectl get endpointslice`、`kubectl exec -- wget` | EndpointSlice 有后端；能连通 |

### 2.1 跳层的代价（真实案例）

假设故障是**节点磁盘满了**（L1）。如果你直接跳到 L3 查 Pod 日志：

- 日志可能因为磁盘满而**写不进去** → 你看到的是空日志
- 你可能判断「应用没输出」 → 去查应用代码
- **真正的原因（L1 磁盘）被完全忽略**

而如果先查 L1：`kubectl describe node` 一眼看到 `DiskPressure=True`，**30 秒定位**。

### 2.2 关键节点判据

> 🔑 **`Ready=True` 且另外三项全 `False`，节点才算健康。** 任一项为 True，kubelet 会开始驱逐 Pod。

四项条件：`MemoryPressure` / `DiskPressure` / `PIDPressure` / `Ready`

| 条件 | True 意味着 | 常见原因 |
|---|---|---|
| `MemoryPressure` | 节点内存不足 | Pod 内存泄漏 / limits 设太高 |
| `DiskPressure` | 磁盘不足 | 镜像堆积、日志未轮转、emptyDir 写满 |
| `PIDPressure` | 进程数耗尽 | fork 炸弹 |
| `Ready` | 是否可调度 | kubelet 挂了 / 网络插件异常 / **上面三项任一为 True** |

## 3. 按症状速查

### 3.1 Pod 起不来（Pending）

```bash
kubectl describe pod <pod>          # 看 Events（最重要）
kubectl get pod <pod> -o wide       # 看在哪个节点
```

| Events 原文 | 根因 | 解决 |
|---|---|---|
| `Insufficient cpu / memory` | 资源不够 | 降低 requests / 加节点 |
| `didn't match Pod's node affinity/selector` | nodeSelector / 亲和性不匹配 | 检查标签 |
| `had untolerated taint` | 污点不容忍 | 加 toleration（课 13） |
| `persistentvolumeclaim not found` | PVC 未绑定 | 检查 PVC / StorageClass（课 12） |

> ⚠️ **注意**：`Insufficient cpu` 是**容量问题**，`didn't match node affinity` 是**资格问题**——**两者解决方向完全不同**，别看混了。

### 3.2 Pod 拉不到镜像（ImagePullBackOff）

| 状态 | 含义 |
|---|---|
| `ErrImagePull` | **正在**尝试拉取且失败了（第一次/重试中） |
| `ImagePullBackOff` | 失败多次，**退避等待**后再试 |

`ErrImagePull` → `ImagePullBackOff` 是「从失败到放弃挣扎」的过程。

| Events 关键词 | 根因 |
|---|---|
| `not found` / `manifest unknown` | 镜像名或 tag 错了 |
| `unauthorized` / `authentication required` | 私有仓库没配 `imagePullSecrets` |
| `connection refused` / `i/o timeout` | 网络不通/被墙 |

### 3.3 Pod 反复重启（CrashLoopBackOff）

```bash
kubectl logs <pod>                  # 当前这次
kubectl logs <pod> --previous       # 上一次（关键证据！）

# 看退出码
kubectl get pod <pod> -o jsonpath='{.status.containerStatuses[0].lastState.terminated.exitCode}'
```

**退出码判据**：

| 退出码 | 含义 | 方向 |
|---|---|---|
| **1** | 应用自己报错退出 | 看日志，查配置/代码 |
| **137** | `128+9` = **被 SIGKILL** | 通常是 **OOMKilled**（内存超限） |
| **143** | `128+15` = **被 SIGTERM** | 优雅终止/被驱逐 |
| **127** | 命令找不到 | `command` 写错 |

> ⚠️ **`--previous` 不是任何时候都能拿到**——容器重启策略、日志轮转都可能让它消失。**所以纪律一说：先取证再动手，别急着删 Pod。**

### 3.4 服务不通

```bash
kubectl get endpointslice -A                        # ← 第一个看这个
kubectl get svc <svc> -o yaml                       # selector 对不对
kubectl -n kube-system get pods -l k8s-app=kube-dns # CoreDNS 活着吗
```

> 🎯 **服务不通，第一个看 EndpointSlice，不是看 Service。**
> Service 创建成功但 selector 写错 → **EndpointSlice 是空的** → 服务不通，**且无任何报错**。

**EndpointSlice 判据**：`endpoints: null` = **无后端** = selector 没匹配到 Pod。

### 3.5 DNS 解析失败

> ⚠️ **反直觉实测（课 18）**：**`nslookup` 说 DNS 坏了，但应用跑得好好的。**

```bash
$ kubectl exec curl-test -- nslookup kubernetes.default
# → 可能报 NXDOMAIN（假警报）
```

**真相**：busybox 的 `nslookup` 是**独立实现的诊断工具**，它不按 glibc 的方式补全 search 域。
应用走 glibc 解析器（会正确补全），`nslookup` 走自己的逻辑。

> 🔑 **用 `nslookup` 的 NXDOMAIN 判定「DNS 坏了」，很可能是一次假警报。**
> 真要验证，用**应用实际的方式**访问（比如 `wget`），或用带完整 FQDN 的名字（`kubernetes.default.svc.cluster.local`）。

### 3.6 删除卡住（Terminating）

```bash
kubectl get ns <ns> -o json | jq '.spec.finalizers'
```

finalizer 非空 → 资源在等某个控制器做清理。**真卡死时用 `/finalize` 子资源**（见第 5 章）。

### 3.7 权限问题（401 / 403）

| 状态码 | 含义 |
|---|---|
| **401** | **坏 token**（凭证无效/过期） |
| **403** | **无 token**（以 anonymous 身份访问，RBAC 默认拒绝） |

```bash
kubectl auth can-i <verb> <resource> --as=system:serviceaccount:<ns>:<sa>
```

### 3.8 集群突然全挂

> 🎯 **先看证书是否过期**（课 19：组件证书 **1 年**）。

```bash
kubeadm certs check-expiration     # 自建集群
kubectl get pods -n kube-system    # 控制面还活着吗
```

## 4. 判据速查表

> 「我看到了这段输出，这算正常还是异常？」

### 4.1 节点

| 输出 | 判定 |
|---|---|
| `Ready=True` + 四项压力全 `False` | ✅ 健康 |
| 任一项压力 `True` | ❌ kubelet 会开始驱逐 Pod |
| `Ready=Unknown` | 节点失联（网络/ kubelet 挂了） |

### 4.2 Pod

| 状态 | 含义 | 下一步 |
|---|---|---|
| `Pending` | 没被调度 | 看 Events（3.1） |
| `ImagePullBackOff` | 镜像拉不到 | 看 Events 关键词（3.2） |
| `CrashLoopBackOff` | 启动就退出 | 看退出码（3.3） |
| `Running` 但 `0/1 Ready` | 探针没过 | 看 readiness 配置 |
| `Terminating` 卡住 | finalizer | 看 3.6 |

### 4.3 网络

| 输出 | 判定 |
|---|---|
| EndpointSlice `endpoints: null` | ❌ 无后端（selector 失配） |
| EndpointSlice 有内容 | ✅ 后端正常，问题在别处 |
| Gateway `ACCEPTED=False` | ❌ GatewayClass 实现方不在 |
| 所有服务名解析失败 | 检查 NetworkPolicy **是否放行 DNS** |

### 4.4 资源

| 输出 | 判定 |
|---|---|
| `kubectl top` 无数据 | metrics-server 未装 → HPA 不会工作 |
| HPA 一直不扩容 | 检查 metrics + `minReplicas`/`maxReplicas` |
| 扩容快、缩容慢 | ✅ 正常（缩容稳定窗口 **300 秒**） |

## 5. 急救命令

> ⚠️ 这些是**最后手段**。用之前确认你理解后果（纪律一：先取证）。

### 5.1 强制删除卡住的 namespace

```bash
# ❌ 无效（实测）：kubectl patch ns <ns> -p '{"spec":{"finalizers":[]}}'
#    返回 "patched (no change)"，但 ns 仍卡 Terminating

# ✅ 有效：用 /finalize 子资源
kubectl get ns <ns> -o json > /tmp/ns.json
python3 - <<'PY'
import json
d = json.load(open('/tmp/ns.json'))
d['spec']['finalizers'] = []
json.dump(d, open('/tmp/ns.json','w'))
PY
kubectl replace --raw /api/v1/namespaces/<ns>/finalize -f /tmp/ns.json
```

> 🔑 **不依赖 `jq`**——课 20 补充讲义复审时特意去掉了 jq 依赖。

### 5.2 拿回 CrashLoopBackOff 的最后一次日志

```bash
kubectl logs <pod> --previous
# 若已被删除则拿不到了 —— 所以别急着删 Pod
```

### 5.3 节点维护三件套

```bash
kubectl cordon <node>     # 封住新调度
kubectl drain <node> --ignore-daemonsets --delete-emptydir-data
# PDB 限制同时驱逐的数量（需提前配好）
```

> ⚠️ **drain 的三个坑**（课 19 实测）：**DaemonSet / emptyDir / 裸 Pod**。
> ⚠️ **`drain` 成功 ≠ 服务活着**——drain 完必须主动验证。

## 6. 四个「工具骗人」的真实案例

> 这四个案例构成贯穿课 18 / 19 / 20 的同一条暗线：**先取证、再下结论**。

### 案例一：`kubectl patch ns` 的假成功

```bash
$ kubectl patch ns stuck -p '{"spec":{"finalizers":[]}}'
namespace/stuck patched (no change)     # ← 看起来成功了
$ kubectl get ns stuck
NAME    STATUS        AGE
stuck   Terminating   10m               # ← 实际没用
```

**真相**：`patch` 走的是普通资源路径，finalizer 需要通过 **`/finalize` 子资源**修改。
**教训**：**返回成功 ≠ 达成效果**。

### 案例二：kubectl 的未知字段报错，未必来自服务端

```bash
$ kubectl apply -f cr.yaml
error: unknown field "spec.foo"        # ← 看起来是服务端拒绝
```

**真相**：可能是**客户端 strict decoding 先拦下的**。要验证服务端行为（如 CRD pruning），得加 `--validate=false`。
**教训**：**先搞清楚报错来自哪一层**。

### 案例三：`kubectl drain` 成功，但服务已经挂了

```bash
$ kubectl drain node-1 --ignore-daemonsets
node/node-1 drained                     # ← 成功
```

**真相**：PDB 未覆盖或副本不足时，drain 会把服务**一起腾空**。
**教训**：**drain 完必须主动验证服务存活**，不能只看命令返回值。

### 案例四：`kubectl run --overrides` 被静默吞掉（2026-09-15 新增）

验证准入类行为（如引用不存在的 PriorityClass 应报 `Forbidden`）时：

```bash
# 写法 A：-- sleep 写在 --overrides 之前
$ kubectl run pc-bad --image=busybox:1.37 --restart=Never -- sleep 3600 \
    --overrides='{"spec":{"priorityClassName":"pc-not-exist", ...}}'
pod/pc-bad created          # ← 没报错！但 overrides 根本没生效

# 写法 B：用 YAML
$ kubectl apply -f - <<'EOF'   # spec.priorityClassName: pc-not-exist
EOF
Error from server (Forbidden): pods "pc-bad" is forbidden:
  no PriorityClass with name pc-not-exist was found     # ← 真实行为
```

**真相**：`-- <命令>` 之后的**所有内容都被当作容器启动参数**，`--overrides` 被吃掉，Pod 建出来 `spec.priority` 是 0，自然不触发校验。
**教训**：**验证准入/校验类行为，用 YAML 文件，别用 `kubectl run` 拼参数**——它会用"成功"骗过你。这属于「看起来通过、实际没测到」的最危险一类。

> 📌 出处：[课 13 知识点 6](stages/4-配置存储资源工程化/lessons/lesson-13-资源调度扩缩容.md)。这是讲义复验时发现的——首轮用 `kubectl run` 测出的"Forbidden"结论碰巧正确，但复验同款命令却不报错，**追查后才发现是参数位置在捣鬼**。

## 7. 集群运维层五查

> 🆕 2026-09-20 补入，来源：[运维专项子教程](子教程/运维专项/overview.md) 课 1-7。
>
> **什么时候用这层，而不是第 2 章**：
> 第 2 章五层模型回答「**某个 Pod / 服务**为什么不对」。
> 当现象是**集群级**的——全部 Pod Pending、全部请求被拒、整个集群不可用、所有人的操作都失败——
> 那不是某个应用的问题，是**集群本身**的问题。这时查第 7 章。

| 查 | 问句 | 核心命令 | 健康判据 |
|---|---|---|---|
| **① 节点账本** | 还有余量吗？ | `kubectl describe node` | 装箱率合理 + 四项压力 `False` |
| **② etcd** | 数据层活着吗？ | 见 7.2 | `has_leader=1`、DB SIZE 未逼近配额 |
| **③ 证书** | 是不是到期了？ | `kubeadm certs check-expiration` | 组件证书剩余 > 30 天 |
| **④ 准入** | 是不是被策略拦的？ | `kubectl get vap,vapb` | 无异常 Deny 策略 |
| **⑤ 备份** | 出事救得回吗？ | `kubectl get cronjob -A` | **有定时备份 + 演练过** |

### 7.1 ① 节点账本：Capacity / Allocatable / Allocated 三者的差

```bash
kubectl get nodes -o custom-columns='NAME:.metadata.name,CPU_CAP:.status.capacity.cpu,CPU_ALLOC:.status.allocatable.cpu,MEM_ALLOC:.status.allocatable.memory'
kubectl describe node <n> | sed -n '/Allocated resources/,/Events/p'
```

**三个数必须分清**（课 2）：

| 概念 | 含义 | 谁用 |
|------|------|------|
| **Capacity** | 机器总量 | 账本第一列 |
| **Allocatable** | Capacity − **预留**（kube/system-reserved）− eviction hard | **调度器**用这个算 |
| **Allocated** | 已分配的 requests 之和 | 装箱率的分母 |

**实测（本机 3 节点，2026-09-20）**：

```text
节点          CPU requests   MEM requests
control-plane  790m (3%)      286Mi (0%)
worker         380m (1%)      918Mi (2%)
worker2        490m (1%)      1262Mi (3%)
```

> ⚠️ **装箱率 1%~3% 是 requests 口径，不是实际用量**。
> 课 6 实测：requests 口径 2.93%，**实际用量只有 0.68%**——CPU 虚高 **4.3 倍**。
> **排障时判断"资源够不够"，要按实际用量（`kubectl top`），不按 requests。**

**快速判断**：

| 现象 | 根因 |
|------|------|
| Pod Pending + `Insufficient cpu` | 真的没余量了（Allocatable 用完） |
| 节点 `NotReady` + 压力 True | 系统资源被抢（**没配预留**） |
| requests 看着满，实际很空 | 虚高，别急着加机器 |

### 7.2 ② etcd：三件事

**ⓐ 工具在哪**（课 3/7 实测的坑）：

```bash
# ❌ 控制面容器里没有 etcdctl
docker exec k8s-c1-control-plane etcdctl version
# → exec: "etcdctl": executable file not found in $PATH

# ✅ 在 etcd Pod 内
kubectl -n kube-system exec etcd-<node> -- etcdctl version
# → etcdctl version: 3.6.4
```

**ⓑ 快照与取出**（etcd v3.6 用 `etcdctl`，不是 `etcdutl`）：

```bash
kubectl -n kube-system exec etcd-<node> -- etcdctl \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key \
  snapshot save /tmp/snap.db

docker cp <node>:/tmp/snap.db ./snap.db      # 取出到宿主机
```

> ⚠️ **etcd 容器是 distroless**（实测无 `ls` / `rm` / `tar`），容器内没法 `ls` 看大小、没法 `rm` 清理。
> 取文件用 `docker cp`；**`kubectl cp` 在本环境实测失败**（Pod 名解析问题）。

**ⓒ 健康判据**：

> ⚠️ **2026-09-21 实测更正**：下面这条**取不到数**，`kubectl get --raw /metrics` 是 **apiserver 自己**的指标，etcd 是独立进程，不在里面。

```bash
# ❌ 错误路径（实测取不到）
kubectl get --raw /metrics | grep -E '^etcd_server_has_leader|^etcd_db_total_size_in_bytes'
# → 空。很多人据此"确认 etcd 没问题"，其实压根没查到
```

```bash
# ✅ 正确路径：etcdctl（etcd Pod 内，见 ⓐ）
kubectl -n kube-system exec etcd-<node> -- etcdctl \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key \
  endpoint status --write-out=table

kubectl -n kube-system exec etcd-<node> -- etcdctl \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key \
  endpoint health --write-out=table
```

**实测输出**（本机 2026-09-21）：

```text
ENDPOINT                  DB SIZE  IN USE  PERCENTAGE NOT IN USE  IS LEADER  RAFT INDEX
https://127.0.0.1:2379    33 MB    13 MB   61%                    true       1157656

ENDPOINT                  HEALTH  TOOK
https://127.0.0.1:2379    true    4.09ms
```

| 判据 | 健康 | 异常 |
|------|------|------|
| `IS LEADER` / `endpoint health` | `true` | `false` = **脑裂/失主**，集群只读 |
| `DB SIZE` | 远小于配额（默认 2Gi） | 逼近配额 → **alarm，拒绝写入** |
| `etcdctl alarm list` | **空** | 非空 = 已进 alarm |
| `endpoint health` 的 `ERROR` 列 | 空 | 非空即故障 |

> 🔑 **etcd 一进 alarm，整个集群不可写**——表现为「所有变更操作都失败」，但读操作正常。
> 这是最容易被误判为"apiserver 挂了"的故障。

> ⚠️ **distroless 里管道会断**：`kubectl exec POD -- sh -c 'wget ... | grep x'` 会报 `grep: command not found`
> ——管道右侧的命令在**容器内**执行，而容器里没有 grep。
> **把 grep 放容器外**（`kubectl exec -- etcdctl ... | grep`），或用 `--write-out`。

> ⚠️ **etcd 容器内 `wget`/`curl` 也没有**（实测 2026-09-21：`wget MISSING / curl MISSING / grep MISSING`，只有 `etcdctl`）。
> 所以 **7.2 里不要用 `/metrics` 路径取 etcd 指标**，老实用 `etcdctl endpoint status/health`。

**两个必须分清的概念**（实测本机：占用 1%，碎片率 61%）：

| 概念 | 算法 | 后果 |
|------|------|------|
| **占用配额** | `dbSize / 2Gi` | 逼近 100% → **alarm，拒绝写入** |
| **碎片率** | `(dbSize − dbSizeInUse) / dbSize` | 只是磁盘浪费，**不影响写入** |

> 🔑 碎片率 61% 看着吓人，但**不触发 alarm**——真会拒写的是"占用配额"。
> ⚠️ `endpoint status` 输出的 **`QUOTA` 列不可信**（本机显示 `0 B`，etcdctl 3.6.4 的 JSON 里没这个字段）；
> 要么用指标 `etcd_server_quota_backend_bytes`，要么按**默认 2Gi 手算**。

#### 🔴 实测发现：etcd 告警默认可能**全是死的**（2026-09-21）

```bash
# 验一次"指标有没有数据"，别只看规则在不在
# （PROM_POD = prometheus-<release>-prometheus-0）
kubectl -n monitoring exec "$PROM_POD" -c prometheus -- sh -c \
  "wget -qO- 'http://localhost:9090/api/v1/query?query=etcd_server_has_leader'"
# → result: []   空！
kubectl -n monitoring exec "$PROM_POD" -c prometheus -- sh -c \
  "wget -qO- 'http://localhost:9090/api/v1/query?query=up{job=\"kube-etcd\"}'"
# → 0
```

**本机实测**：etcd 的 10 个告警指标（`etcd_server_has_leader`、`etcd_server_quota_backend_bytes`、`etcd_mvcc_db_total_size_in_bytes` …）**全部为空**，`up{job="kube-etcd"}=0`，而 `apiserver_request_total` 有大量数据（采集链路本身通）。

**根因**：etcd 启动参数 `--listen-metrics-urls=http://127.0.0.1:2381` **只监听回环**，Pod IP 上没监听 → Prometheus 从 Pod IP 抓 `Connection refused`（`scrape_duration_seconds` 仅 `0.0004s`，是**连接被拒**不是超时；NetworkPolicy 已排除）。
**kind 默认如此**——意味着默认装出来的 kube-prometheus-stack，etcd 告警全废，而 **UI 上毫无提示**。

**修复与闭环验证**（2026-09-21 授权后实测，跑完已还原）：

```bash
docker exec <cp> sed -i 's|--listen-metrics-urls=http://127.0.0.1:2381|--listen-metrics-urls=http://0.0.0.0:2381|' \
  /etc/kubernetes/manifests/etcd.yaml      # kubelet 自动重建 etcd Pod
```

| 指标 | 修复前 | 修复后 |
|------|--------|--------|
| `up{job="kube-etcd"}` | `0` | **`1`** |
| `etcd_server_has_leader` | 空 | **`1`** |
| `etcd_mvcc_db_total_size_in_bytes` | 空 | **`33189888`** |
| `etcd_server_quota_backend_bytes` | 空 | **`2147483648`** |

占用率终于算得出：`db_total_size / quota_backend_bytes * 100 = **1.55%**`，
且与 etcdctl 的 `dbSize` **完全一致**（33189888）——两个口径互证，指标可信。

#### ✅ 永久修复已执行（2026-09-21 授权后）

监听已改为 `http://0.0.0.0:2381` 并写入静态清单（重启仍生效），**13 条 etcd 告警规则全部复活**
（`etcdNoLeader` / `etcdDatabaseQuotaLowSpace` / `etcdHighNumberOfLeaderChanges` 等，修复前因指标为空全部静默失效）。

**🔴 代价要同时知道：2381 是无认证 HTTP，现已暴露。** 集群内任意 Pod 无需凭据即可读到完整指标（实测已验证）。

| 端口 | 认证 | 说明 |
|------|------|------|
| 2379 | ✅ 客户端证书 | 本就监听节点 IP，靠 TLS 保护 |
| **2381** | ❌ **无认证** | **本次新增暴露面** |

**改之前必须先探 `hostNetwork`**：etcd 是 `hostNetwork=true`，Pod IP 即节点 IP——
改 `0.0.0.0` 是在**宿主机**上开无认证端口，不是只在 Pod 网络里开窗。

**🚫 加固试过 NetworkPolicy，实测无效**（探针仍 exit=0 能读到）：hostNetwork 静态 Pod 走宿主机网络栈，
Calico 策略作用于 Pod 的 veth，而它根本没有 veth。策略已删除回滚，**不留假装修好的配置**。
可行方向：① 节点 iptables 限源（hostNetwork 场景正解）② 保持回环 + sidecar 转发（最安全）。**均需授权。**

**两个易误判点**：
- 修复后 `etcd_network_peer_sent_failures_total` **仍为空**——**这是对的**：单节点集群没有 peer，该指标本就不存在。**判断指标是否死的，先确认它在该拓扑下是否应该存在。**
- 修复后 `leader_changes_seen_total=1`（raft_term 2→3）——是刚才重启留下的证据，**反证该指标真能记录事件**，不是恒 0。

> ✅ 还原后 `up` 回到 `0`：改了活、还原就死，**唯一变量确认是监听地址**。
> ⚠️ 是否**永久**改属环境决策（已还原，备份留在 `/tmp/etcd.yaml.orig`），按规矩由用户定。

## 8. 运维症状速查与判据

### 8.1 所有变更操作都失败（能读不能写）

```bash
# ✅ 用 7.2 的 etcdctl（下面这行已过时，取不到数，勿用）
# kubectl get --raw /metrics | grep etcd_server_has_leader
kubectl -n kube-system exec etcd-<node> -- etcdctl \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key \
  alarm list
```
# 0 → 失主
# 或 DB SIZE 逼近配额 → alarm
```

| 判据 | 根因 |
|------|------|
| `has_leader=0` | etcd 失主/脑裂 |
| DB SIZE 逼近 2Gi | **配额 alarm，拒绝写入** |
| 读正常、写失败 | 典型 etcd alarm 表现 |

### 8.2 全部 Pod Pending，且 Events 是 `Insufficient`

```bash
kubectl describe node <n> | sed -n '/Allocated resources/,/Events/p'
```

- 若 **Allocatable 已用完** → 真的该加节点
- 若 **requests 高但实际用量很低** → 虚高，降 requests（课 6：CPU 虚高 4.3 倍）

### 8.3 恢复备份时 Conflict

```text
Error from server (Conflict): Operation cannot be fulfilled on configmaps
  "kube-root-ca.crt": the object has been modified
```

**根因**：备份里含**系统自维护资源**（`kube-root-ca.crt` / `default` SA / `kubernetes` Service）。
删掉后 apiserver **立刻自动重建**，再 apply 旧版本即冲突。

**正解**：备份时剔除这三类 → 实测 Conflict **从 2 个降到 0**。

### 8.4 恢复后 Pod 起不来，PVC 一直 Pending

> 🎯 **数据还在，但挂不上**——运维侧最痛的一类。

**根因**：PV 的 `spec.claimRef.uid` 绑死了旧 PVC 的 uid；应用级恢复生成了**新 uid**，PV 认不出。

| 现象 | 判定 |
|------|------|
| PV 状态 `Released` / `Failed` | uid 不匹配 |
| PVC 一直 Pending | 找不到可绑定的 PV |

**正解**：有状态应用恢复**只能用卷快照或 etcd 整库还原**，YAML 导出救不了。

### 8.5 配额相关两个报错（实测区分）

```text
# ① 不声明 resources
pods "no-res" is forbidden: failed quota: drill-quota: must specify requests.cpu

# ② 真的超了
pods "x" is forbidden: exceeded quota: drill-quota, requested: pods=1, used: pods=2, limited: pods=2
```

| 报错 | 含义 | 解法 |
|------|------|------|
| `must specify ...` | **没声明 resources**，配额无法计算 | 配 **LimitRange** 自动注入默认值 |
| `exceeded quota` | 真的超了 | 调配额或减副本 |

> ⚠️ **LimitRange 不回溯**：实测先建的 Pod 不会被补默认值，只有之后建的才注入。
> 加上 LimitRange 后，**存量 Pod 仍是原样**——别以为加了就全补齐了。

### 8.6 证书过期的集群（全部操作 401 / x509）

```bash
kubeadm certs check-expiration
kubeadm certs renew all          # 续期
```

> ⚠️ 续期后需重启控制面静态 Pod（kubelet 会自动拉起）。

### 8.7 运维侧判据速查表

| 输出 | 判定 |
|------|------|
| `kubectl get cronjob -A` 空 | ❌ **无自动备份，RPO=∞** |
| `--enable-admission-plugins=NodeRestriction` | ⚠️ 仅默认，无自定义策略 |
| `etcd_server_has_leader=0` | ❌ 失主 |
| `etcdctl version` 在控制面容器 not found | ✅ 正常（**在 etcd Pod 内**） |
| PSA 报 4 项 restricted 违规 | ✅ 正常拦截（**不是故障**） |
| `must specify requests.cpu` | 缺 LimitRange，非真的超配额 |
| 装箱率 1%~3% | ⚠️ requests 口径，实际可能低 4 倍 |
| 恢复后 PV `Released` | ❌ uid 变了，需卷快照/整库还原 |
