# 设计决策

> 本项目有 3 个**真权衡**决策点——每个都不是"唯一正确答案"，换个人来可能选另一个方案，且也有道理。
> 每个决策按五段式写：候选方案 → 最终选择 → 选择理由 → 为此付出的代价 → 什么情况下该改选另一个。

---

## 决策点 1：长期存储选谁 —— Thanos / Mimir / VictoriaMetrics

### 候选方案

课 9 实测过三条路线（详见 [lesson-09](../../stages/3-规模化与生态/lessons/lesson-09-长期存储选型.md)）：

| 方案 | 架构本质 | 实测数据 | 多租户 | 对象存储依赖 |
|------|----------|----------|--------|--------------|
| **Thanos** | 给 Prometheus 加外挂 | sidecar 传 block，需额外 3-4 组件 | ❌ 无租户概念 | 硬依赖 |
| **Mimir** | 拆微服务 | 单体模式 **1 容器 / 8 秒 ready / 72.68MiB** | ✅ **唯一原生多租户** | 硬依赖 |
| **VictoriaMetrics** | 换存储引擎 | 单节点 55MB，最轻 | 集群版按 tenant 路径区分 | ❌ 不依赖 |

### 最终选择：Mimir（单体模式 + filesystem 后端）

### 选择理由

决定性因素是**多租户是存储级隔离，不是查询过滤**。

课 9 实测：Mimir 开启 `multitenancy_enabled` 后，无 `X-Scope-OrgID` 头**直接 401**，跨租户查询 0 条。这意味着三个环境的数据在**存储层就分开了**——即使某个租户的查询写错了，也拿不到别人的数据。

本项目是"多集群统一平台"，三套环境的数据天然需要隔离：
- dev 的工程师不该有 prod 数据的读权限
- 某个环境基数爆炸时，不该拖垮其他环境（Mimir 的 `max_global_series_per_user` 是按租户限流的）

另外两个次要理由：
1. **单体模式足够轻**：1 容器 8 秒 ready，单机演示不必拆微服务
2. **Prometheus 兼容 API**：`/prometheus/api/v1/query` 路径，采集端无需改代码

**为什么不要 Thanos**：它没有租户概念。三个环境的数据混在一个 bucket 里，隔离只能靠外部约定（比如不同的 bucket），那就退化成"手动多租户"了。

**为什么不要 VM**：它是换存储引擎，Prometheus 只当采集器，与课程主线（Prometheus 本体）偏离。且集群版查询必须加 `/select/<tenantID>/` 前缀，Grafana 数据源和告警规则 URL 全要改——迁移成本被低估。

### 为此付出的代价

1. **对象存储是硬依赖，本演示用了 filesystem 后端规避**——生产必须换成 S3/GCS/Azure。filesystem 后端**不支持横向扩展**，多副本 Mimir 会各自写各自的盘。这是本项目为了"单机可运行"做的最大的妥协。
2. **Mimir 3.x 只有 distroless 镜像**——容器内没有 sh/bash/wget，出问题时无法 `docker exec` 进去排查，只能看日志和 HTTP 接口。本次开发中就撞上了：想查字段名只能 `docker run --rm ... -help`。
3. **配置字段比 Thanos 更严格**——写了不存在的字段**直接启动失败**（本次就踩了 `max_series_per_user`）。Thanos 对未知字段相对宽松。
4. **多租户带来额外的运维负担**——每个请求都要带租户头，remote write/read 都得配 `headers`。忘了就是 401，且排查时容易误判成网络问题。

### 什么情况下该改选另一个

- **已经有对象存储 + 不需要多租户 + 已有大量 Prometheus 实例** → 选 **Thanos**。它的 sidecar 模式对现有 Prometheus 侵入最小，不用改采集配置。
- **没有对象存储 + 想要最轻量的方案 + 能接受换查询语法** → 选 **VictoriaMetrics**。单节点 55MB，不依赖 S3，中小规模性价比最高。
- **规模到了千万序列 + 需要长期留存（>1 年）** → 三个都不是最优解，该考虑商业方案或 ClickHouse-based 方案。

## 决策点 2：全局视图用联邦还是远端读

### 候选方案

课 8 讲过两条路：

| 方案 | 工作方式 | 课 8 实测结论 |
|------|----------|---------------|
| **联邦（federation）** | 上层 Prometheus 定期从下层抓 `/federate` | 解决的是**聚合视图**，不是容量问题；大规模下会打垮下层 |
| **远端读（remote read）** | 上层查询时直接从长期存储拉历史 | 代价约 **2.69x**（本地 1.6ms vs 远端 4.4ms）；**失败是静默的** |

### 最终选择：远端读

### 选择理由

1. **联邦不解决容量问题**——这是课 8 的核心结论。联邦只是让上层能查到下层的**当前值**，历史数据还是在各个下层实例里。本项目要的是"查三个月前的数据"，联邦做不到。
2. **数据已经在 Mimir 里了**——既然 remote write 已经把数据送进长期存储，全局视图直接读存储即可，何必再让每个采集端额外承担联邦查询的压力？
3. **联邦会给采集端加负载**——每次上层抓取，下层都要执行一次查询。三套环境 × 每次全局查询，采集端压力翻倍。

### 为此付出的代价（本次实测发现的最有价值的一个坑）

**远端读的 `external_labels` 陷阱——查不到数据，且不报任何错。**

开发时我在全局层配置里写了：

```yaml
global:
  external_labels:
    cluster: global      # ← 这行是错的
```

结果全局查询**永远返回空**，`status` 仍是 `success`，`warnings` 也是空的。

根因是 external_labels 的**三段式行为**（课 9 讲过，但讲的是 remote write 侧）：

1. remote write 时：附加到所有出站样本
2. **remote read 时：附加到查询的选择器上** ← 就是这里
3. 返回前：剥离

所以实际发出的查询是 `{__name__="up", cluster="global"}`，而真实数据的 cluster 值是 `prod-shanghai` / `staging-shanghai` / `dev-shanghai`——**永远匹配不上**。

这个坑的危险性在于**完全静默**：
- Prometheus 日志无任何错误
- 查询返回 `status: success`、`warnings: []`
- 只有去翻 Mimir 的访问日志才能看到真相：
  ```
  path=/prometheus/api/v1/read
  param_matchers_0="{__name__=\"up\",cluster=\"global\"}"   ← 罪魁祸首
  response_series_count=0
  status=success                                             ← 它说成功了
  ```

**修复方法**：全局层**不要写 external_labels**。这反直觉——直觉上"全局视图应该有自己的标识"，但 remote read 场景下这个标识会污染查询。

### 什么情况下该改选另一个

- **只需要看当前状态、数据量很小（<10 万序列）** → 联邦更简单，没有静默失败的风险，延迟也更低。
- **能接受每个集群独立查询、不需要真正统一的视图** → 干脆用 Grafana 多数据源，比两者都简单。
- **远端读延迟不可接受（2.69x）** → 在 Mimir 前面加 query-frontend 缓存，或改用 Thanos Query（它有专门的查询优化）。

## 决策点 3：告警是按环境分层，还是全局统一

### 候选方案

| 方案 | 做法 |
|------|------|
| **A. 全局统一** | 所有环境同一套规则、同一阈值、同一接收端 |
| **B. 规则里写死 severity** | 每个规则按环境判断，标注不同 severity |
| **C. 路由树按 env 分流**（本方案） | 规则只管"发生了什么"，路由树决定"通知谁、多快、多频繁" |

### 最终选择：C（路由树按 env 分流）

### 选择理由

**关注点分离**：规则回答"发生了什么"，路由回答"该通知谁"。两者混在一起会导致规则文件里塞满环境判断逻辑，改一个环境的策略要动所有规则。

本项目的具体设计：

```yaml
# 规则侧：只声明事实，不写 severity
- alert: HighErrorRate
  expr: ... > 0.05
  labels:
    team: platform        # 注意：没有 severity

# 路由侧：按 env 决定处置强度
routes:
  - matchers: [env = "prod"]      → pager（group_wait 10s，repeat 1h）
  - matchers: [env = "staging"]   → chat（group_wait 30s，repeat 4h）
  - matchers: [env = "dev"]       → silent（只记录）
```

这样做的直接好处：**加一个新环境不用改任何规则**，只需在路由树加一条。

实测验证（2026-09-07）：
- dev 的 `HighErrorRate` → 进 `silent.log`（2 条）
- staging 的 `HighLatencyP99` → 进 `chat.log`（1 条）
- 停掉 app-prod 触发 `TargetDown` → 62 秒后进 `pager.log`（1 条，severity=critical）

**为什么不要 A（全局统一）**：dev 环境错误率本来就高（本项目 app.py 里设了 12%），统一告警会让值班手机被 dev 噪声淹没，最终结果是**所有告警都被忽略**——包括真正重要的 prod 告警。

**为什么不要 B（规则里写死）**：规则文件会变成 `if env == "prod" then severity=critical else ...` 的垃圾场，且每加一个环境要改所有规则。

### 为此付出的代价

1. **路由树的 matcher 依赖 external_labels**——如果某个采集端忘了配 `env` 标签，它的告警会掉到 `default` 接收端，静默消失。本项目用 webhook 落盘来暴露这个问题。
2. **规则里看不到 severity**——排查时看到一条告警，不知道它会不会呼叫值班，得去看路由树。可维护性略差。
3. **路由是"命中即停"**（课 5 知识点）——第一条匹配后不再往下走。如果不小心把 `env` 的 matcher 写宽了，后面的分支永远不会执行。本项目每条都显式写了 `continue: false`。

### 什么情况下该改选另一个

- **只有一套环境，或者所有环境同等重要** → 方案 A 更简单，没必要引入路由树复杂度。
- **告警数量很少（<10 条规则）且环境固定** → 方案 B 也够用，规则里直接写 severity 反而更直观。
- **需要按"业务线"而非"环境"分流** → 同样的路由树思路，把 matcher 从 `env` 换成 `team` 或 `service` 即可，本质不变。

## 补充：一个不算决策但很重要的设计 —— 监控链路本身

本项目额外加了两条规则监控"监控链路自己"：

```yaml
- alert: RemoteWriteStalled
  expr: prometheus_remote_storage_samples_pending > 5000

- alert: RemoteWriteFailing
  expr: rate(prometheus_remote_storage_samples_failed_total[2m]) > 0
```

**为什么必须有**：remote write 卡住时，各采集端的**本地数据看起来完全正常**（up=1、业务指标在涨），但全局视图已经停止更新了。这是最危险的盲区——你以为监控在工作，其实它三天前就断了。

课 7 的实测结论在这里起了作用：**WAL 截断与发送确认是解耦的**，所以"发送失败"不会立刻反映在数据上，必须主动监控队列指标。

**这不是一个"选择"，而是必需项**——任何 remote write 架构都应该有这两条告警。
