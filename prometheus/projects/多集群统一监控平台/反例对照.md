# 反例对照

> **这一版 `docker compose up` 能起来、指标能查到、告警也能送达——但它在生产环境会出事。**
> 每一条差异都附了「为什么糟」，以及「什么时候才暴露」。
>
> 诚实预告：它不是"完全查不出问题"——`verify.sh` 会抓出其中 3 项。
> 但**最致命的两条（告警疲劳、链路自监控缺失）脚本一项都测不出来**。

## 反例版本（能跑，但很糟）

下面是一个"省事版"配置——少写了很多东西，抄起来更快，`docker compose up` 也能起来，指标也能查到。

```yaml
# ❌ 反例：prometheus-global.yml（省事版）
global:
  scrape_interval: 60s
  external_labels:
    cluster: global          # ❌ 差异 1：给全局层加了标识

remote_read:
  - url: http://mimir:8080/prometheus/api/v1/read
    read_recent: true        # ❌ 差异 2：没加租户头（靠 Mimir 关多租户）
```

```yaml
# ❌ 反例：mimir-config.yml（省事版）
multitenancy_enabled: false  # ❌ 差异 3：关掉多租户，省得每个请求带租户头

blocks_storage:
  backend: filesystem
  filesystem:
    dir: /data/blocks
# ❌ 差异 4：没配任何 limits
```

```yaml
# ❌ 反例：rules/alerts.yml（省事版）
groups:
  - name: availability
    rules:
      - alert: HighErrorRate
        expr: sum(rate(http_requests_total{status="500"}[2m])) / sum(rate(http_requests_total[2m])) > 0.05
        for: 1m
        labels:
          severity: critical    # ❌ 差异 5：所有环境统一 severity
        annotations:
          summary: "错误率超过 5%"
# ❌ 差异 6：没有监控 remote write 的规则
```

```yaml
# ❌ 反例：alertmanager.yml（省事版）
route:
  receiver: default          # ❌ 差异 7：所有告警一个接收端
  group_by: [alertname]

receivers:
  - name: default
    webhook_configs:
      - url: http://webhook-logger:8080/default
```

## 逐条对比

### 差异 1：全局层加了 `external_labels: cluster: global`

| | 正例 | 反例 |
|---|---|---|
| 写法 | 不写 external_labels | `external_labels: {cluster: global}` |

**看起来没问题**：给全局视图打个标识很合理啊，Prometheus 官方文档也建议给每个实例配 external_labels。

**为什么糟**：remote read 时，external_labels 会被**附加到查询选择器**上。实际发出的查询是 `{__name__="up", cluster="global"}`，而真实数据 cluster 是 `prod-shanghai` 等——**永远查不到**。

**什么时候暴露**：**立刻**，但**你看不出来**。查询返回 `status: success`、空 `warnings`、空结果。大多数人会以为是"还没数据"或"时间范围不对"，然后反复调整，浪费半天。

**本项目实测证据**：Mimir 访问日志
```
path=/prometheus/api/v1/read
param_matchers_0="{__name__=\"up\",cluster=\"global\"}"
response_series_count=0
status=success              ← 它说成功了
```

**危害等级**：🔴 高。全局视图完全失效，且静默。

---

### 差异 2：remote read 没加租户头

| | 正例 | 反例 |
|---|---|---|
| 写法 | `headers: {X-Scope-OrgID: tenant-demo}` | 不写 headers（配合差异 3 关闭多租户） |

**看起来没问题**：反例同时关了 Mimir 的多租户（差异 3），所以不带头也能跑通，不会有 401。

**为什么糟**：这其实是"用降级安全换便利"——为了让配置简单，把隔离能力关掉了。

**什么时候暴露**：当你需要第二个租户时。届时你要么改配置开启多租户（然后所有 remote write/read 全 401，全部返工），要么永远保持单租户。

**危害等级**：🟡 中。短期能跑，长期返工。

---

### 差异 3：关掉 Mimir 多租户

| | 正例 | 反例 |
|---|---|---|
| 写法 | `multitenancy_enabled: true` | `multitenancy_enabled: false` |

**看起来没问题**：单租户场景下完全够用，还省了每处配置 headers 的麻烦。

**为什么糟**：课 9 实测结论——Mimir 的多租户是**存储级隔离**，不是查询过滤。关掉它，三个环境的数据在存储层就混在一起了。后果：
- dev 工程师能查到 prod 数据
- 没法按环境限流（一个环境基数爆炸拖垮全部）
- 想加隔离时只能重新规划存储

**什么时候暴露**：需要隔离时才暴露，而那时数据已经混了，迁移成本极高。

**危害等级**：🟡 中高。取决于是否真的需要隔离——**如果三套环境数据敏感度相同，这一条其实可以接受**（这就是它"看起来能跑"的原因）。

---

### 差异 4：不配 limits

| | 正例 | 反例 |
|---|---|---|
| 写法 | `limits: {max_global_series_per_user: 500000, ...}` | 不配 limits |

**看起来没问题**：演示环境数据量小，配限流纯属多余。

**为什么糟**：**没有上限就是最大的风险**。课 10 讲基数爆炸时说过——一次错误的代码发布（比如把 user_id 塞进标签）可以在几分钟内产生百万级新序列。没有 limits 的话，Mimir 会被单租户的基数爆炸拖垮，**所有环境一起挂**。

**什么时候暴露**：基数爆炸的那一刻。而那一刻通常伴随着"业务刚上线 + 大家都在看监控"，最需要监控系统活着的时候它挂了。

**危害等级**：🔴 高。这是"没有出事时看不出问题，出事时致命"的典型。

---

### 差异 5：所有环境统一 `severity: critical`

| | 正例 | 反例 |
|---|---|---|
| 写法 | 规则不写 severity，靠路由树按 env 分流 | 规则里写死 `severity: critical` |

**看起来没问题**：统一标准，简单直接。而且 dev 环境错误率 12%，确实会触发——你会"看到"告警在工作。

**为什么糟**：**告警疲劳**。dev 的 12% 错误率是设计出来的（本项目 app.py 刻意设置），它每分钟都会触发。值班手机被 dev 噪声淹没后，真正重要的 prod 告警会被**习惯性忽略**。

这是监控领域最经典的失效模式：**不是告警没配，而是告警太多导致没有人看**。

**什么时候暴露**：第一次真正 prod 故障时——如果那时候值班已经对告警麻木了，监控系统等于不存在。

**危害等级**：🔴 高。而且这个是"温水煮青蛙"，不会立刻出事。

---

### 差异 6：没有监控 remote write 的规则

| | 正例 | 反例 |
|---|---|---|
| 写法 | 有 `RemoteWriteStalled` / `RemoteWriteFailing` 两条规则 | 没有 |

**看起来没问题**：各采集端本地数据好好的，`up=1`，业务指标在涨——监控系统"看起来"很健康。

**为什么糟**：**这是最危险的盲区**。remote write 卡住时，本地数据完全正常，但全局视图已经停止更新。你以为监控在工作，其实它三天前就断了。

课 7 实测结论：WAL 截断与发送确认**解耦**，所以"发送失败"不会立刻反映在数据上——必须主动监控队列指标才能发现。

**什么时候暴露**：**永远不会自动暴露**。只有当你需要查历史数据、发现查不到时才后知后觉——而那时丢失的数据已经找不回来了。

**危害等级**：🔴🔴 极高。静默失效，且不可逆。

---

### 差异 7：所有告警一个接收端

| | 正例 | 反例 |
|---|---|---|
| 写法 | 路由树按 env 分流到 pager/chat/silent | 单一 `default` 接收端 |

**看起来没问题**：告警确实都送达了，webhook 日志里有记录。

**为什么糟**：与差异 5 同源——无法按严重程度区分处置强度。而且它**让差异 5 的后果无法挽回**：即使规则里写了不同的 severity，没有路由树也无从分流。

另外，反例的 `group_by: [alertname]` 也太粗——三套环境同名告警会被合并成一条，你分不清是哪个环境出的事。正例用 `group_by: [alertname, cluster]`。

**什么时候暴露**：第一次多环境同时告警时，一条合并通知里混着三个环境的信息，无法快速定位。

**危害等级**：🟡 中。主要是可定位性差。

## 为什么"能跑"不等于"对"

把上面 7 条差异归结一下，反例的问题分三类：

| 类型 | 差异 | 特征 |
|------|------|------|
| **静默失效** | 1、6 | 系统说"成功"，实际什么都没做。危害最大 |
| **温水煮青蛙** | 5、7 | 短期正常，长期让人麻木，真出事时已失效 |
| **省小钱花大钱** | 2、3、4 | 演示时省事，需要扩展时返工 |

**共同点**：它们在演示环境（数据量小、只跑几分钟、只有你一个人看）全都表现正常。这正是"反例对照"存在的意义——**验收脚本测不出的东西，才是真正要教的东西**。

> ⚠️ **关于「反例能通过验收脚本吗」——诚实说明**：
> 我没有真去跑一遍反例版本（那需要另起一套环境、耗时较长），所以**不给未经实测的结论**。
> 按 `verify.sh` 的断言逐条推演，反例会让 **A7（多租户 401）、A8（全局三集群）、A10（dev 进 silent）** 这 3 项 FAIL——
> 听起来反例"会被抓出来"。但请注意两点：
> ① 剩下 9 项（容器、就绪、targets、数据入库、有告警等）**仍会通过**，
>    给人"基本没问题、只是小瑕疵"的错觉；
> ② **真正致命的差异 5（告警疲劳）和差异 6（链路自监控缺失），脚本一项都测不出来**——
>    反例在这两项上拿满分。
>
> 所以：脚本能抓到的是"配置错"，抓不到的是"设计错"。后者才是反例要讲的重点。
