# Prometheus 排障速查手册

> **怎么用**：出事了别从头读。按索引表找**症状**，翻到对应条目照做。
> **想懂为什么**：每个条目末尾有原理链接，事后再看 [08-实战经验.md](08-实战经验.md)。
> **查不到**：→ 转 `debug` skill 现场取证。
>
> 紧急度：🔴 立即处理（业务已受损）｜ 🟡 尽快处理（有风险未爆发）｜ ⚪ 有时间再看（体验 / 优化）

## 排障第一原则

> **先确认「数据本该存在」，再查「为什么没有」。**

本课程体系里**至少 5 次**把「0 条」误读成「生效了」（recording rule 未生效、webhook DNS 失败、
remote read 路径不支持、external_labels 污染、`tools bucket` 掩盖报错）。
每次的根因都是：跳过了"本该有"这一步，直接去查"为什么没有"。

配套两条：

- **别用可能出错的工具验证可能出错的组件**（`up=1` 不代表健康、`check config` 过了不代表配置对）
- **失败常常是静默的**：`status=success` + 空结果，是 Prometheus 生态最常见的故障形态

## 🔴 症状 1：面板 No Data，但接口说 success

**一眼识别**：Grafana 显示 "No Data"；直接查 API 返回 `{"status":"success","result":[]}`；**没有任何报错**。

> 这是 Prometheus 生态**最常见**的故障形态。先别急着查配置，按下面顺序走。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **第 0 步** | **先确认数据本该存在**：用另一条路径查同一个指标（如直查长期存储） | 若另一条路径有数据 → 是本层问题；若都没有 → 可能真的没采集到 |
| 定位 1 | 看**完整 JSON 响应**，特别是 `warnings` 字段 | 有 warnings → 转症状 2 |
| 定位 2 | 检查指标名拼写、`job` / `instance` 是否收窄 | 选择器匹配不到返回 0 行且不报错 |
| 定位 3 | 检查时间范围——数据可能落在保留窗口外 | 本地默认只留 15 天 |
| 定位 4 | 若用了 `le`，先 `count by (le) (...)` 确认桶存在 | 桶不存在 = 静默失败 |
| 若无效 | → 转症状 3（external_labels 污染） | — |

```promql
# 确认指标是否存在（不带任何匹配器）
count(http_requests_total)

# 确认标签取值（避免匹配器匹配到不存在的组合）
count by (job, instance) (http_requests_total)
```

> **原理**：→ [08-实战经验.md](08-实战经验.md) · 元陷阱 1「0 条 ≠ 生效」

## 🔴 症状 2：remote read 返回空，接口却说 success

**一眼识别**：配了 remote read，查历史数据返回空；`status` 仍是 `success`；原因只在 `warnings` 里。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 先直查远端原生 API 确认数据存在 | 有数据 → 是 remote read 链路问题 |
| 定位 1 | **看完整响应体的 `warnings` 字段**，不要只看 status | 课 7 实测：VM 单节点返回 400 `unsupported path requested` |
| 定位 2 | 确认后端支持 `/api/v1/read` 路径 | 不是所有后端都支持 |
| 修复 | 换后端，或改走远端原生 API（Grafana 数据源直连） | 能查到历史数据 |
| 若无效 | → 转症状 3 | — |

```bash
# 关键：看完整响应，别只看 status
curl -s 'http://localhost:9090/api/v1/query' --data-urlencode 'query=up' | python3 -m json.tool
# 重点看 warnings 字段，而不是 status
```

> ⚠️ **不要给 Grafana 配 remote_read 做日常仪表盘**：查询放大（课 7 实测 2.69x 起），
> 且远端返回原始样本后本地还要再算一遍聚合。remote read 是"偶尔调卷"，不是"日常办公"。
>
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 2

## 🔴 症状 3：全局视图空，但 Mimir 里数据都在

**一眼识别**：直查长期存储有数据；全局查询层查同样的指标返回 0 条；`status=success` 且 `warnings` 为空。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 确认长期存储侧数据存在（带租户头直查） | 有数据 → 问题在全局层 |
| 定位 1 | **看后端访问日志**，找 `param_matchers` 字段 | 这是唯一能看到真实查询条件的地方 |
| 定位 2 | 对比日志里的 matcher 是否多了你没写的标签 | 多出 `cluster="global"` 之类 → 就是它 |
| 定位 3 | 打开全局层配置，检查 `global.external_labels` | 查询层不该给自己贴身份标签 |
| 修复 | **删掉全局层的 `external_labels`**，重启 | 全局视图恢复 |

```bash
# 实战项目实测抓到的 Mimir 访问日志（根因在此）
# param_matchers_0="{__name__="up",cluster="global"}"  response_series_count=0  status=success

# 直查长期存储确认数据存在（注意租户头）
curl -s -H "X-Scope-OrgID: tenant-demo" \
  'http://localhost:19510/prometheus/api/v1/query' --data-urlencode 'query=count by (cluster) (up)'
```

**external_labels 三段式**（记住这张表，能省你半天）：

| 阶段 | 行为 |
|------|------|
| remote **write** 时 | 附加到**发出的样本** |
| remote **read** 时 | 附加到**查询选择器**（本症状成因） |
| 返回客户端时 | 从结果中**剥离** |

> **口诀**：**写入方贴标签，查询方不贴。**
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 3

## 🔴 症状 4：数据没写进长期存储，但没有任何报错

**一眼识别**：长期存储里查不到近期数据；Prometheus 日志**没有 error**；targets 全绿。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 先确认后端是否存活（curl 后端 `/ready`） | 后端挂了 → 先恢复后端 |
| 定位 1 | 查 `prometheus_remote_storage_samples_failed_total` | >0 = **真丢数据** |
| 定位 2 | 查 `prometheus_remote_storage_samples_retried_total` | 增长 = 后端在返回可重试错误 |
| 定位 3 | 查 `prometheus_remote_storage_pending_samples` **的趋势** | 持续上涨才是问题，瞬时高不算 |
| 修复 | 恢复后端；积压会自动追平 | 课 7 实测：1199 → 100 以下约 30 秒 |
| 若无效 | → 检查 WAL 是否已被截断（那部分数据回不来） | — |

```promql
prometheus_remote_storage_samples_failed_total    # 永久失败，真丢数据
prometheus_remote_storage_samples_retried_total   # 重试，后端在报错
prometheus_remote_storage_pending_samples         # 队列积压，看趋势
```

> ⚠️ **三个必须知道的语义**：
> 1. 后端返回 **500 是可重试错误**，`failed_total` **不计数**（课 7 实测 `failed = 0`）
> 2. **队列满不丢数据**——外面还有 WAL 兜底（实测 `pending` 可达 1199 > capacity 1000）
> 3. **不要用 `in - sent` 算丢失**：口径不同，实测有约 **-1450 的恒定偏移**
>
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 1

## 🔴 症状 5：服务挂了，告警一条都没响

**一眼识别**：服务不可用，Alertmanager 里空空如也；或 Prometheus 显示 firing 但没人收到通知。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 人工确认故障，别等告警 | 先止损 |
| 定位 1 | **先区分**：是"没产生告警"还是"产生了没送达"？查 Prometheus `/api/v1/rules` 状态 + AM `/api/v2/alerts` | 定位在哪一侧 |
| 定位 2a | 规则没触发 → 检查用的是 `up` 还是业务指标 | 业务指标在抓取失败时**消失**，不会变 0 |
| 定位 2b | 规则没触发 → 检查 target 是否还在列表 | 从 SD 消失的 target **连 `up=0` 都不写** |
| 定位 2c | 规则 firing 但 AM 没有 → 查 Prometheus 日志的推送失败 | Alertmanager 地址/网络问题 |
| 修复 | 存活判断改用 `up == 0`；可能消失的目标补 `absent()` | 告警正常触发 |

```promql
up{job="myjob"} == 0                    # ✓ 存活判断用 up
absent(up{job="myjob"})                 # ✓ 目标可能消失的场景
my_metric == 0                          # ✗ 抓取失败时序列消失，永远不成立
```

> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 4

## 🔴 症状 6：内存持续上涨 → OOM，但 targets 全绿

**一眼识别**：Prometheus 内存缓慢上涨，某天凌晨 OOM 被 kill；期间所有 target `up=1`；**没有任何告警报"基数爆炸"**。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 重启能恢复，但会再犯；优先定位是哪个指标在涨 | 先恢复服务 |
| 定位 1 | 查 `prometheus_tsdb_head_series`（**必须先配 self-scrape**） | 得到当前序列数 |
| 定位 2 | `topk(10, count by (__name__)({__name__=~".+"}))` | 找出最大头的指标 |
| 定位 3 | `count by (job) (up)` 定位是哪个 job 在涨 | 缩到具体服务 |
| 定位 4 | 检查最近有没有上线新标签 | 加一个 1000 取值的标签 = 序列数 ×1000 |
| 修复 | 抓取端 drop 高基数标签 / `sample_limit` / `label_limit` | 序列数回落 |
| 若无效 | → 可能是 histogram 桶放大：一个 histogram 展开成 N 条序列 | — |

```promql
prometheus_tsdb_head_series                                  # 当前序列数（需 self-scrape）
topk(10, count by (__name__)({__name__=~".+"}))              # 最大头的 10 个指标
count by (job) (up)                                          # 按 job 分布
```

> ⚠️ **两个易踩的点**：
> - **必须先配 self-scrape**，否则 `prometheus_tsdb_*` 全查不到（课 10/11 亲历：配了之后指标数 6 → 328）
> - **`sample_limit` / `label_limit` 是熔断不是限流**：触发后整个 target `up=0`；
>   且 `label_limit` 是 **per-target 全局**的，会误伤标签多的正常指标
> - **日常监控不要用 `count({__name__=~".+"})`**，它扫全库
>
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 5

## 🟡 症状 7：delete_series 返回 204，磁盘一点没小

**一眼识别**：调用删除接口返回成功（204），但 `df` 显示磁盘占用没变化。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **认知** | 删除只写 **tombstone**，物理删除要等 **compaction** | 这是设计，不是 bug |
| 定位 1 | 确认 tombstone 确实存在 | 有 → 等 compaction 或强制清理 |
| 定位 2 | 用 admin API `cleanTombstones` 强制清理（需 `--web.enable-admin-api`） | 磁盘释放 |
| 修复 | `cleanTombstones` + 等 compaction | 磁盘下降 |
| 若无效 | → 检查 retention：保留**按整个 block 删**，块内有新数据时会被多留 | — |

```bash
# 强制清理 tombstone（需启用 admin API）
curl -X POST 'http://localhost:9090/api/v1/admin/tsdb/clean_tombstones'
```

> ⚠️ **"精确保留 N 天"是不可能的**：保留按整个 block 删（课 3 实测 61 个 block 设 `retention.time=2h` 后剩 5 个），
> 所以磁盘占用会在 block 周期上波动，容量规划必须留余量。
>
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 6

## 🟡 症状 8：所有 sum 查询翻倍，且不报错

**一眼识别**：`sum` / `avg` / `count` 结果都是预期的两倍；没有任何报错；数据看起来"很正常"。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 先确认是不是真翻倍：找一个已知答案的指标，对比单副本 vs 当前 | 确认问题 |
| 定位 1 | 检查 HA 去重的配置是否存在（如 Thanos `--query.replica-label`） | 漏配 → 就是它 |
| 定位 2 | 检查副本是否都带着区分标签（如 `replica="0"/"1"`） | 没有区分标签没法去重 |
| 修复 | 补上 replica-label 配置 | 课 9 实测：124347 → 62162 |
| 若无效 | → 确认三个方案的去重语义不同（Thanos/Mimir/VM 不等价） | — |

> ⚠️ **验证去重生效时，别把「0 条」当成功**：0 条可能是去重成功，也可能是查询根本没生效。
> 课 9 实测：设对了 `sum = 62162`，漏配 `sum = 124347`——**用已知答案验证，别用"有没有数据"验证**。
>
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 7

## 🟡 症状 9：改了配置却不生效

**一眼识别**：reload 成功、日志无报错，但行为没变。

| 现象 | 原因 | 怎么办 |
|------|------|--------|
| retention 改小不生效 | **retention 不支持热加载** | 必须重启 |
| 新规则查不到数据 | 新增规则要等**一个完整 `interval`** | 课 6 实测 `interval:5s` 要等约 45 秒 |
| 规则完全没加载 | `rule_files` 没在 `prometheus.yml` 声明 | 补声明后 reload |
| `check config` 过了但 relabel 无效 | 它**不查元标签是否存在**（实测放行 `__meta_nonexistent__`） | 人工核对元标签名 |
| remote write 字段写错却没报错 | 只在启动/reload 时报错，之后**静默用默认值** | 用 `promtool` 预检 |
| `scrape_timeout > scrape_interval` | **启动即失败** | 改配置（好消息是不会带病运行） |

```bash
promtool check config prometheus.yml     # 预检配置（但不查元标签是否存在）
promtool check rules rules.yml           # 预检规则
curl -X POST http://localhost:9090/-/reload   # 热加载（retention 不适用）
```

> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 8

## 🔴 症状 10：容器显示 Up，但端口 Connection refused

**一眼识别**：`docker ps` 显示 `Up`；`curl localhost:<port>` 报 `Connection refused`；端口探测返回 `000`。

> 这是**真实发生过**的排查：容器状态"Up"，但目标端口不通。

| 步骤 | 动作 | 预期 |
|------|------|------|
| 定位 1 | **查真实端口映射**：`docker port <container>` | 你以为的端口可能根本不是它 |
| 定位 2 | 看日志尾部是否有 `See you next time!` + 随后重启的日志 | 进程重启过，看重启原因 |
| 定位 3 | 逐个探测候选端口 | 找到真正监听的那个 |
| 修复 | 用 `docker port` 给出的真实端口访问 | 连通 |

```bash
docker port <container>                    # ← 关键：查真实映射，别凭印象
docker logs --tail 40 <container>          # 看是否重启过
curl -s -o /dev/null -w '%{http_code}\n' --max-time 5 http://localhost:<real_port>/-/ready
```

> ⚠️ **教训**：`docker ps` 的 `Up` 只说明容器**进程存在**，不代表**服务在监听**。
> 而且 `Up About an hour` 这种状态可能掩盖了中途的重启（日志里能看到 `See you next time!` 后重新 `Starting Prometheus`）。
>
> **原理**：容器状态 ≠ 服务可用，同"up=1 ≠ 健康"。

## 🔴 症状 11：up=0 了

**一眼识别**：Targets 页面 `health=down`；`up{job="x"} == 0`。

| 步骤 | 动作 | 预期 |
|------|------|------|
| 定位 1 | 看 Targets 页面的 `lastError` 字段 | 直接给出失败原因 |
| 定位 2 | 常见原因分类（见下表） | 对号入座 |
| 定位 3 | 手动 curl target 的 `/metrics` | 确认 target 自身是否正常 |
| 修复 | 按原因处理 | `up` 回到 1 |

| `lastError` 关键字 | 含义 |
|-------------------|------|
| `connection refused` | target 没监听 / 端口错 |
| `context deadline exceeded` | 超时，查 `scrape_timeout` 与网络 |
| `sample limit exceeded` | **触发了 `sample_limit` 熔断**（课 10 实测） |
| `label limit exceeded` | 触发 `label_limit`（per-target 全局，会误伤） |
| 解析类报错 | 暴露格式不合规（如 Help 行后无换行导致样本被静默丢弃） |

> ⚠️ **`scrape_duration_seconds` 在 target down 时不可信**：超时时它被截断
> （课 12 实测：指标显示 1.0009s，源站真实耗时 5.99s）。
>
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 元陷阱 2

## 🟡 症状 12：查询很慢 / Prometheus 变卡

**一眼识别**：面板加载慢；Prometheus 内存/CPU 飙升；严重时打不开页面。

| 步骤 | 动作 | 预期 |
|------|------|------|
| 定位 1 | **先数点数**：用 `/api/v1/query_range` 跑一次，数 `values` 总长度 | 点数才是成本主因 |
| 定位 2 | 检查时间范围 × step | 课 6 实测：点数从 133 万降到 2 万（67 倍），耗时降 6.7 倍 |
| 定位 3 | 检查选择器是否命中过多序列 | 命中全库才真的贵（实测 0.12s → 0.36s） |
| 定位 4 | 检查是否有并发查询 | 课 11 实测：并发峰值是稳态的 **2.96 倍** |
| 修复 | 加大 step / 缩短时间窗 / 上 recording rule 预聚合 | 课 6 实测预聚合降 26%~56% |

> ⚠️ **三个被实测推翻的"常识"**：
> 1. **「正则慢，避免 `.*`」→ 错**：等值 126.2ms vs 无界正则 123.5ms，差 2.7ms，远小于 10ms 标准差。
>    真正贵的是**命中多少条序列**
> 2. **「慢就减标签基数」→ 不完整**：一条查 1 条序列但 step=1s / 15 天的查询，
>    可能比查 20000 条序列 / step=60s / 5 分钟的**慢得多**
> 3. **「用自监控指标度量单次查询成本」→ 不可行**：那些 counter 按 `scrape_interval` 批量更新，
>    无法归因到单次查询（课 6 实测：连跑 5 次只有 1 次采到增量）
>
> **测量方法的正确姿势**：墙钟耗时 + 返回点数 + **重复采样取中位数**，
> 并先测噪声基线（课 6 实测中位数 131.5ms，波动 ±27ms），再把负载放大到远超噪声带。
>
> **原理**：→ [课 6 查询引擎](stages/2-规则与告警/lessons/lesson-06-查询引擎与查询成本.md)

## 附：排障时的自我检查清单

每次排障前过一遍，能避免大部分弯路：

- [ ] 我有没有先确认「数据本该存在」？（防"0 条 ≠ 生效"）
- [ ] 我的判断依据本身，会不会也在故障影响范围内？（防"用坏工具验证坏组件"）
- [ ] 我看到的是**完整响应**（含 `warnings`）还是只有 `status`？
- [ ] 我做对照实验了吗？两组真的触发了不同代码路径吗？
- [ ] 这个数字是我**实测**的还是**推演**的？我有没有把推演写成实测？
- [ ] 容器 `Up` 就等于服务可用吗？我查过 `docker port` 的真实映射吗？
- [ ] `up=1` 就等于健康吗？（基数可以在全绿的时候涨到 OOM）
