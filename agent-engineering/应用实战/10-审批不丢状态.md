# 第 10 课实战 · 审批不丢状态

> 所属课程：[课 10：持久执行](../stages/3-执行与协作/lessons/10-持久执行.md) ｜ 索引：[应用实战 INDEX](./INDEX.md)
> 实战目标：把"sleep 等审批"改造成"挂起 + checkpoint 恢复"，并让它在服务重启后仍然正确。
> 覆盖知识点：interrupt 等人工 / 为什么不轮询

## 🎯 你要解决什么

一个下单 Agent 需要人批准才能真正扣款。你最初这么写：

```ts
const ok = await waitForApproval(orderId)   // 内部 setInterval 轮询数据库
if (ok) await placeOrder(orderId)
```

跑得通，但有两个真实故障：

1. **占资源**：等人 1 小时，这 1 小时里那个 worker 一直在轮询，还占着一条数据库连接。
2. **重启即丢**：部署发布时进程重启，内存里的 `waitForApproval` Promise 消失。审批人点通过，系统找不到等待者——**审批结果被丢弃**。

这篇实战把这段代码改成"挂起式等待"，并验证它在重启后仍然正确。

## 📐 设计图

### 图 1：改造前后的等待方式

```mermaid

    A->>CP: interrupt() → 写 checkpoint

    H->>Sys: 点"通过"（interactionId 匹配）

    end
```

> **看图**：上半段的红色区块不是"慢"，是"错"——错误在重启那一刻才暴露。下半段的关键动作是 `interrupt()` 后面那句"进程可死"。

## 🧱 第一跳：先把等待改成 interrupt

核心替换：

```ts
// 改造后：挂起等审批
const result = await awaitAgentInvocation(api, invocationId, register)
```

但直接用还不够——你要理解它到底做了什么，否则会踩三个坑。

**坑 1：以为 interrupt 之后代码会停在那里**。实际上函数会**抛出去**。所以：

```ts
// ❌ 错：以为 interrupt 之后还能执行
interrupt({ type: 'approval', ... })
console.log('审批完了')   // ← 不会执行，或恢复后重复执行

// ✅ 对：interrupt 返回值才是决策
const decision = interrupt({ type: 'approval', interactionId, ... })
if (decision.approved) { ... }
```

**坑 2：在 interrupt 之前做了不可重复的操作**。因为恢复时函数从头重跑，`interrupt` 之前的代码会**再执行一遍**：

```ts
// ❌ 危险：每次恢复都会重复扣库存
await reserveStock(orderId)
const decision = interrupt({ ... })

// ✅ 安全：扣库存放到 interrupt 之后，或者做成幂等
const decision = interrupt({ ... })
if (decision.approved) await reserveStock(orderId)   // 幂等键由课11 的 callId 保证
```

**坑 3：不校验 interactionId**。如果一个流程会问两个问题（先问"要不要查"，再问"要不要扣款"），用户对第一个问题的"同意"不能被当成对第二个问题的同意：

```ts
const parsed = decision.safeParse(resumed)
if (parsed.success && parsed.data.interactionId === current.interaction.id) {
    await api.respond(id, parsed.data.interactionId, parsed.data.response)
}
// ← 没有 else：不匹配就静默重问
```

## 🔀 第二跳：让"重启"变成正常路径

改造完，跑一个真实的故障注入：**在 interrupt 之后 kill 掉进程**。

```bash
# 终端 1：触发一个需要审批的调用
curl -X POST /api/invocation -d '{"input":"帮我下单 #123"}'
# 观察日志：出现 interrupt，checkpoint 已写

# 终端 2：直接杀掉进程
kill -9 <pid>

# 终端 1（或新实例）：审批通过
curl -X POST /api/invocation/<id>/respond -d '{"interactionId":"...","response":{"approved":true}}'
```

期望结果：调用从 checkpoint 恢复，继续执行下单，**不重复扣库存**（因为扣库存在 interrupt 之后，只在决策为 approved 时执行一次）。

如果你看到"找不到 invocation"，检查两件事：

| 症状 | 可能原因 |
|---|---|
| 重启后 `unknown` | checkpoint 没落库，或被清理了 |
| 恢复后重复执行副作用 | 副作用写在了 interrupt 之前，且不幂等 |
| 恢复后拿到旧的审批结果 | `interactionId` 没校验，错配了 |

## 🏗 第三跳：加一个"等待不占资源"的验收指标

改完了要能证明"真的不占资源"。一个可测的判据：

```
在 interrupt 之后、审批之前，观察指标：
- worker 活跃数：应为 0（该执行不占槽位）
- 模型调用次数：应为 0（没有"问好了吗"的轮询）
- DB 查询次数：只有审批到来时的那 1 次读
```

把它变成一个断言，放进测试：

```ts
// 伪代码：挂起期间不应产生模型调用
const before = metrics.modelCalls
await triggerApprovalFlow()             // 停在 interrupt
await sleep(5000)                       // 等 5 秒
expect(metrics.modelCalls).toBe(before) // 这 5 秒里 0 次模型调用
expect(metrics.activeWorkers).toBe(0)   // 不占 worker
```

这个断言会立刻抓住"偷偷轮询"的回归——只要有人把挂起改回 `sleep` 循环，它就红了。

## ✅ 验收：改造后要能回答的五个问题

| 问题 | 改造前 | 改造后 |
|---|---|---|
| 等人 1 小时占资源吗 | 占 worker + 连接 | 0 占用 |
| 服务重启会丢进度吗 | 会 | 不会，从 checkpoint 续 |
| 审批结果会错配给别的问题吗 | 可能 | 不会，`interactionId` 校验 |
| 副作用会重复执行吗 | 重启后可能 | 放在 interrupt 之后即只执行一次 |
| 重复点"通过"会出问题吗 | 可能重复下单 | 终态幂等 + `callId` 去重 |

## 🎯 练一练

1. 把你手上任何一个"等外部确认"的逻辑（审批、回调、人工复核）画成两条时间线：一条进程一直活着，一条中间重启过。找出所有"只活在内存里的状态"。
2. 检查你的代码里 `interrupt`（或等价挂起点）之前的语句，逐条判断"重复执行一次会不会出事"。
3. 写一个断言：挂起期间模型调用次数为 0。这是判断"你是真挂起还是假挂起"的唯一硬标准。
