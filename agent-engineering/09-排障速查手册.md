# Agent 工程 · 排障速查手册（使用态）

> **这份手册怎么用**：崩了先查索引表 → 找到症状 → 按表里的步骤走。**每条第一步都是止血，不是查根因**。
> 手册只给动作，不给原理——想懂为什么，点每条末尾的经验层编号。
> 查不到当前症状 → `use_skill("debug")` 现场取证。
>
> 基线：Node 22 / `@langchain/langgraph` 1.6.0 / `@langchain/core` 1.3.2。版本不同则命令可能有差异。

## 🔴 A. 定义被运行时改掉

**一眼识别**：`Object.isFrozen(def) === true` 但 `Object.isFrozen(def.tools) === false`；或同一个进程内 `def.tools.length` 会变。

| 步骤 | 动作 | 预期 |
|------|------|------|
| 止血 | 回滚到上一个版本；若无法回滚，在定义出厂后立刻 `structuredClone` 一份给运行时用 | 行为恢复稳定 |
| 定位 1 | 打印 `Object.isFrozen(def)` 与 `Object.isFrozen(def.tools)` | 第二个 `false` = 浅冻结 |
| 定位 2 | `rg "\.tools\.(push|splice|unshift)" -g '!*test*'` | 有命中即为改写点 |
| 定位 3 | `rg "\.tools\[" -g '!*test*'` 看有无下标赋值 | 有即为改写点 |
| 修复 | 改成 `Object.freeze({ ...def, tools: [...def.tools] })`，多层嵌套逐层复制 | `Object.isFrozen(rt.tools)` 为 `true`，`push` 抛 `TypeError` |
| 若无效 | → 转 [B. 并发写数据静默丢失](#b-并发写数据静默丢失)（症状类似但根因在通道）；仍不定位 → `debug` 现场取证 | — |

**预防**：冻结收敛成一个 `toRuntime()` 函数，CI 加 `Object.isFrozen(runtime.tools)` 断言。
**原理**：→ [08-实战经验.md](./08-实战经验.md) · 故障模式 1

## 🔴 B. 并发写数据静默丢失

**一眼识别**：不报错、不稳定、并发越高复现率越高；典型是标题/审批决策"回退"成更旧的值，或消息条数少于预期。

| 步骤 | 动作 | 预期 |
|------|------|------|
| 止血 | 对出问题的通道临时加串行锁（或把并发请求排队），先保住正确性 | 数据不再回退 |
| 定位 1 | 列出所有通道，逐个标注"丢历史有后果吗 / 并发两个该谁赢" | 出现"该追加却写成取新"的通道 = 病灶 |
| 定位 2 | 读该通道的 reducer 实现 | 确认是否 last-write-wins |
| 定位 3 | 构造两个并发写同一通道的最小复现 | 追加型两次都在、取新型只剩最后一个，即验证成立 |
| 修复 | 改 reducer 语义：messages/result 用追加（带同 id 替换），title/approval 保持取新 | 并发两次写入后两条都在 / 只剩正确的那个 |
| 若无效 | → 转 [K. 工具结果错位](#k-工具结果错位)（若是"结果内容错"而非"条数少"）；仍不定位 → `debug` | — |

**预防**：每个通道定义旁写一行"语义 + 为什么"，评审逐条读。
**原理**：→ [08-实战经验.md](./08-实战经验.md) · 故障模式 2

## 🔴 C. 越权调用没被拦住

**一眼识别**：审计日志里有"未被允许的工具"执行成功；而中间件层的拒绝计数为 0（或远小于审计里的成功数）。

| 步骤 | 动作 | 预期 |
|------|------|------|
| 止血 | 停掉批量/迁移/管理类入口（这类最常绕过中间件）；把危险工具临时下线 | 越权执行停止 |
| 定位 1 | `rg "工具函数名" -g '!*test*'` 列出所有直接引用点 | 有引用不在中间件包装之下 = 绕过点 |
| 定位 2 | 查执行器内部有没有"身份 / 参数 / 路径"的二次校验 | 没有 = 第二层缺失 |
| 定位 3 | 构造"绕过中间件直调"的用例，看是否被拒 | 中间件计数 0、执行器拒绝 1 次 = 两层都在 |
| 修复 | 执行器内部自取可信上下文（宿主注入，非模型输出）重新校验；把工具实现改成不直接导出 | 直调用例被拒 |
| 若无效 | → 转 [I. 沙箱逃逸](#i-沙箱逃逸)（若是文件路径类越界）；仍不定位 → `debug` | — |

**预防**：工具实现不导出、只经工厂返回包装版；"两层权限"写进编码规范。
**原理**：→ [08-实战经验.md](./08-实战经验.md) · 故障模式 3

## 🔴 D. 恢复后副作用重复

**一眼识别**：用户收到两条相同审批通知；下游系统被扣两次款；日志里同一条"发送通知"出现两次，中间隔着一个 `resume`。

| 步骤 | 动作 | 预期 |
|------|------|------|
| 止血 | 关掉通知/扣费的下游开关（或切到 dry-run），先止住重复副作用 | 不再产生新副作用 |
| 定位 1 | 找到 `interrupt()` 调用，读它上方整个函数体 | 列出所有有外部副作用的语句 |
| 定位 2 | 对照日志：恢复那一次是否重新打印了"节点进入" | 打印了 = 节点确实从头重跑 |
| 修复 | 副作用挪到 `interrupt()` 之后；无法挪的做成幂等（唯一键写入 / 去重表） | 恢复两次只有一次副作用 |
| 若无效 | → 转 [J. 重试重复执行 / 僵尸账本](#j-重试重复执行--僵尸账本)（若重复发生在重试而非恢复）；仍不定位 → `debug` | — |

**预防**：节点入口打轨迹日志；"节点必须可重入"写进规范。
**原理**：→ [08-实战经验.md](./08-实战经验.md) · 故障模式 4

## 🔴 E. 恢复值与预期不符

**一眼识别**：批的是"允许"，代码拿到的却是"拒绝"；或两个 `interrupt` 只有一个被恢复，另一个永远等不到；两次运行的 `interrupt` 调用次数不同。

| 步骤 | 动作 | 预期 |
|------|------|------|
| 止血 | 停下来人工核对受影响的那几条决策（不要继续自动恢复） | 错批的操作被撤回 |
| 定位 1 | 数一次完整运行里 `interrupt()` 的调用次数与顺序 | 记下 N 与顺序 |
| 定位 2 | 换一个输入再跑一次，再数 | 次数不同 = 存在条件性跳过 |
| 定位 3 | 搜 `if (...)` 包住 `interrupt(` 的写法 | 命中即病灶 |
| 修复 | `interrupt` 无条件、顺序固定；把判断挪到 `interrupt` 之后（先拿决策再决定用不用） | 每次运行调用次数一致，恢复值对得上 |
| 若无效 | → 转 [F. 判不到挂起](#f-判不到挂起)（若是"没恢复成功"而非"恢复错值"）；仍不定位 → `debug` | — |

**预防**：把 `interrupt` 当"必须走到的站点"；评审专问"什么情况下会少走一个 interrupt"。
**原理**：→ [08-实战经验.md](./08-实战经验.md) · 故障模式 5

## 🔴 F. 判不到挂起

**一眼识别**：挂起后接口返回"已完成"；或恢复接口报"没有可恢复的内容"；代码里判断挂起用的是 `state.pendingWrites` 或 `tasks[].interrupts`。

| 步骤 | 动作 | 预期 |
|------|------|------|
| 止血 | 临时改成"只要有未完成调用就允许 resume"，先让人能继续操作 | 恢复流程可用 |
| 定位 1 | 挂起后**新起一个进程**，打印 `graph.getState(cfg)` 的 `next` / `pendingWrites` / `tasks` | 只有 `next` 非空 |
| 定位 2 | 搜 `pendingWrites` / `tasks[].interrupts` 被用作挂起判据的地方 | 命中即病灶 |
| 定位 3 | 检查 `__interrupt__` 事件的读取方式（应为数组，元素 `{id, value}`） | 形状对不上 = 另有问题 |
| 修复 | 挂起判定统一改成 `getState(cfg).next` 非空；封装成 `isSuspended(cfg)` 全项目只走这一处 | 跨进程能正确判到挂起 |
| 若无效 | → 转 [E. 恢复值与预期不符](#e-恢复值与预期不符)；仍不定位 → `debug` | — |

**预防**：禁止各处自己判断挂起，只调一个封装函数。
**原理**：→ [08-实战经验.md](./08-实战经验.md) · 故障模式 6

## 🔴 G. 预算没拦住

**一眼识别**：账单远超预期但预算告警一次没响；某些租户用量统计长期为 0；日志里这些调用的 `tokenUsage` 是 `undefined`/`null`。

| 步骤 | 动作 | 预期 |
|------|------|------|
| 止血 | 立刻把出问题的租户/调用方降级或停用；把全局预算阈值临时下调 | 花费停止增长 |
| 定位 1 | 搜预算判断处，看有没有 `?? 0` | 有 = 把未知当零，病灶 |
| 定位 2 | 传 `undefined` / `NaN` 进判断函数，看是否拒绝 | 被放过 = fail-open |
| 定位 3 | 查 `used` 来源：模型返回无 usage 字段时走哪条路 | 走"当作 0" = 病灶 |
| 修复 | 改成 `if (!Number.isFinite(used) \|\| used + estimate > limit) reject` | `undefined`/`NaN` 均被拒 |
| 若无效 | → 转 [J. 重试重复执行 / 僵尸账本](#j-重试重复执行--僵尸账本)（若是重试导致的翻倍计费）；仍不定位 → `debug` | — |

**预防**：所有限额判断统一走 `budgetCheck()`（内部强制 fail-closed），单测必含 undefined/NaN 用例。
**原理**：→ [08-实战经验.md](./08-实战经验.md) · 故障模式 7

## 🟡 H. 上下文被切坏

**一眼识别**：压缩后模型引用一个它从没见过的工具结果；或对某个 `tool` 消息问"这是什么"；或反复重调已调过的工具。不报错。

| 步骤 | 动作 | 预期 |
|------|------|------|
| 止血 | 关掉压缩（或把阈值调到几乎不触发），先恢复可用 | 对话恢复正常 |
| 定位 1 | 压缩后的消息数组里，检查每个 `tool_call.id` 是否有对应 `tool` 消息 | 有缺失 = 配对被拆 |
| 定位 2 | 反向检查每个 `tool` 消息的 `tool_call_id` 能否找到发起它的 `tool_call` | 有缺失 = 同上 |
| 定位 3 | 看压缩是否压到了系统提示或首尾消息 | 压到了 = 另有违规 |
| 修复 | 压缩以"配对"为最小单位（整对保留或整对换摘要）；保留系统提示；只压中段 | 孤儿检测 0 条 |
| 若无效 | → 转 [B. 并发写数据静默丢失](#b-并发写数据静默丢失)；仍不定位 → `debug` | — |

**预防**：压缩函数出口强制跑配对断言，失败直接抛。
**原理**：→ [08-实战经验.md](./08-实战经验.md) · 故障模式 8

## 🔴 I. 沙箱逃逸

**一眼识别**：文件写到了沙箱外；安全检查曾"通过"（只测了 `../`）；或路径判定代码里出现 `startsWith` 判目录。

| 步骤 | 动作 | 预期 |
|------|------|------|
| 止血 | 停用该 Agent 的文件写入能力；排查已越界写入的文件（按审计时间窗） | 不再产生越界写入 |
| 定位 1 | 跑三条用例：`../` 穿越、软链接指向外部、同级同名目录（`u1` vs `u1-evil`） | 哪条通过 = 缺哪种防御 |
| 定位 2 | 看解析是否先规范化（resolve `..` 与软链，取真实路径） | 没规范化 = 病灶 |
| 定位 3 | 看边界判定是 `startsWith` 还是"等于根 或 根+分隔符开头" | 前者 = 病灶 |
| 修复 | 规范化后再做边界判定；解析收敛成唯一入口函数 | 三条用例全部拦截 |
| 若无效 | → 转 [C. 越权调用没被拦住](#c-越权调用没被拦住)；仍不定位 → `debug` | — |

**预防**：沙箱解析唯一入口 + 固定三条测试用例；评审看到 `startsWith` 判路径就要求改。
**原理**：→ [08-实战经验.md](./08-实战经验.md) · 故障模式 9

## 🔴 J. 重试重复执行 / 僵尸账本

**一眼识别**：失败重试后下游收到两条记录；账本里有永远 RUNNING 的记录；已成功的调用被重复提交后出现两条成功记录。

| 步骤 | 动作 | 预期 |
|------|------|------|
| 止血 | 暂停重试队列；对已重复的下游记录做人工核对/冲正 | 不再产生新重复 |
| 定位 1 | 查幂等入口：同键同输入返回旧结果吗 | 没返回 = 缺基本幂等 |
| 定位 2 | 同键异输入是否拒绝（指纹比对） | 没拒绝 = 会静默覆盖 |
| 定位 3 | 执行前是否判 `finishedAt`；异常路径是否写终态 | 缺任一 = 病灶 |
| 修复 | 三件套：返回旧账本 / 指纹拒绝 / 终态前置判断；异常路径写 failed | 四条用例（首次/重放/冲突/终态后重放）全对 |
| 若无效 | → 转 [D. 恢复后副作用重复](#d-恢复后副作用重复)；仍不定位 → `debug` | — |

**预防**：账本状态机画出来贴在代码旁，每个转移注明"谁写、什么条件下写"。
**原理**：→ [08-实战经验.md](./08-实战经验.md) · 故障模式 10

## 🔴 K. 工具结果错位

**一眼识别**：A 工具的结果出现在 B 工具的槽位里；并行调用时结果与预期不符但**不报错**；单工具调用时一切正常。

| 步骤 | 动作 | 预期 |
|------|------|------|
| 止血 | 把并行调用改成串行（临时），保正确性 | 结果不再错位 |
| 定位 1 | 看回填逻辑是按返回**顺序**还是按 `tool_call_id` | 按顺序 = 病灶 |
| 定位 2 | 构造"两个工具、第二个先返回"的用例 | 结果互换 = 验证成立 |
| 定位 3 | 看是否用 `Promise.all`（一个 reject 全丢）而非 `allSettled` | 用 `all` = 另有隐患 |
| 修复 | 按 `tool_call_id` 回填；失败也产出带 id 的结果（错误喂回模型） | 乱序返回仍对位 |
| 若无效 | → 转 [L. 单点失败拖垮全局](#l-单点失败拖垮全局)；仍不定位 → `debug` | — |

**预防**：回填函数签名强制要求 `toolCallId`，从类型上堵住"按顺序塞"。
**原理**：→ [08-实战经验.md](./08-实战经验.md) · 故障模式 11（含于"静默失败"清单）

## 🟡 L. 单点失败拖垮全局

**一眼识别**：一个工具超时/报错，整轮调用直接失败；日志里能看到其他工具已经成功但结果没被使用。

| 步骤 | 动作 | 预期 |
|------|------|------|
| 止血 | 给该工具加超时与熔断；把非关键工具临时从清单移除 | 其他工具恢复可用 |
| 定位 1 | 看并行执行用的是 `Promise.all` 还是 `allSettled` | `all` = 一个失败全丢 |
| 定位 2 | 看失败结果是否被喂回模型（而不是抛出去中断整轮） | 没喂回 = 模型无法自行绕开 |
| 修复 | 用 `allSettled`；每项产出 `{toolCallId, ok, content\|error}`；错误作为工具结果喂回 | 一个失败时其余结果仍生效 |
| 若无效 | → 转 [M. MCP 部分能力失败导致整体不可用](#m-mcp-部分能力失败导致整体不可用)；仍不定位 → `debug` | — |

**预防**：工具执行器统一走一个 `runToolCalls()`，不各写各的。
**原理**：→ [08-实战经验.md](./08-实战经验.md) · 上线 checklist 第 12 项

## 🟡 M. MCP 部分能力失败导致整体不可用

**一眼识别**：外部 MCP 服务端某个能力（如 resources）报错，整个 Agent 起不来或工具清单为空；日志里 `initialize` 成功但后续某类探测失败。

| 步骤 | 动作 | 预期 |
|------|------|------|
| 止血 | 在配置里关掉该服务端（或只保留 tools 一类能力），先恢复启动 | Agent 能起来 |
| 定位 1 | 看能力发现是否"任一失败即整体退出" | 是 = 病灶 |
| 定位 2 | 看失败是否有 `errors` 收集（"有什么用什么"） | 没有 = 缺降级 |
| 定位 3 | 看工具数量是否做了过滤（34 个全塞给模型） | 没过滤 = 另有隐患 |
| 修复 | 能力发现逐项 try，失败的记进 `errors` 继续；工具按白名单/相关性过滤到个位数 | 一个能力坏时其余可用 |
| 若无效 | → 转 [L. 单点失败拖垮全局](#l-单点失败拖垮全局)；仍不定位 → `debug` | — |

**预防**：能力发现写成"容忍部分失败"的采集器；对外部服务端默认不信任。
**原理**：→ [08-实战经验.md](./08-实战经验.md) · 上线 checklist 第 14 项

## 升级出口

三个条件任一成立，停止按本手册操作，转 `debug` 现场取证：

1. 按条目走完"修复"仍未恢复，且症状可稳定复现
2. 症状在索引表里找不到对应条目（宁可新开一条，不要硬套）
3. 涉及数据损坏 / 资金损失 / 数据出圈——先止损再取证，不要在线上边查边改

> 手册与经验层是同一批素材的两种形态：这里给动作，[08-实战经验.md](./08-实战经验.md) 给原理。两边编号一一对应。
