## 一、适用边界：什么时候别用这套

这一节比后面所有故障模式都值钱。课程讲的四层骨架、声明式定义、编译、checkpoint、账本、预算——**每一个都有明确的入场券**，没到那个规模就上，是拿复杂度换进度。

**不该做声明式定义的场景**：Agent 只有 1-2 个，配置三个月不变，改一次代码就发一次版也能接受。这时"定义即数据"换来的是"多一层间接"：你要维护 schema、写校验、写迁移，而收益（不改代码加 Agent）一次都用不上。判据：**如果"新增一个 Agent"这件事一年发生不到 3 次，硬编码更直接**。

**不该上编译层的场景**：图结构是固定的、分支是写死的。编译的价值在"定义变了图跟着变"，定义都不变，编译就是每次启动多花一次翻译。判据：**如果图的结构在代码里就写完了、且不打算让用户改，跳过编译，直接 `StateGraph`**。

**不该上 checkpoint + interrupt 的场景**：没有人工介入，也没有跨进程恢复需求。checkpoint 会带来持久化开销与"状态里有什么"的持续维护成本；没有恢复需求时，它只是个更慢的内存变量。判据：**如果一次调用能在一次 HTTP 请求内跑完、失败就整体重试，别上**。

**不该上账本与预算的场景**：单用户、自己付费、调用量小。账本的价值在"多人多租户要分摊、要限流、要审计"，一个人用的时候它只是日志。判据：**如果"这次调用花了谁的钱"不是一个需要回答的问题，别上**。

**不该上中间件策略层的场景**：工具少于 5 个、没有任何横切关注点（权限 / 日志 / 注入）。策略层的价值在"能力数增长时避免组合爆炸"——6 个 if 有 64 种路径，5 个工具没有这个问题。判据：**如果加第 6 个工具时你只需要再写一个 `if`，别上策略层**。

**一个反直觉的边界**：课程强调"两层权限"（中间件 + 执行器），但如果你的工具全都是只读查询、没有任何写操作，第二层可以省。**两层权限是为"有副作用的操作"准备的**，纯读场景加第二层只是仪式。

## 二、高频故障模式

### 故障模式 1：定义在运行时被悄悄改掉了

**症状（可观测）**：同一份定义，第一次跑正常，第二次跑多了一个工具；或者"新增工具"的表现是"重启后又没了"。日志里定义对象的 `tools.length` 在同一个进程生命周期内会变。

**根因**：`Object.freeze` 只冻结对象自身属性，不冻结属性指向的数组。`Object.freeze(def)` 之后 `def.tools` 仍是原数组引用，任何拿到它的代码 `push` 一下都能改。这是"不可变"的假象，比完全不冻结更危险——因为团队相信它不可变，于是不再检查。

**排查路径**：在定义出厂处打一行 `console.log(Object.isFrozen(def), Object.isFrozen(def.tools))`。第二个 `false` 就是病灶。再全局搜 `.tools.push(` / `.tools.splice(` / `.tools[` 赋值。

**修复**：连数组一起复制再冻结：`Object.freeze({ ...def, tools: [...def.tools] })`。有多层嵌套时逐层复制（或用 `structuredClone` 后冻结）。✅ 实测：`verify/verify-core.ts` 段 1 里，浅冻结版本在 `push` 后长度从 2 变 3，深复制版本 `push` 抛 `TypeError`。

**预防**：把"冻结"写成一个函数（`toRuntime`），所有人只能通过它拿到运行时对象；在 CI 里加一条断言——`Object.isFrozen(runtime.tools)` 必须为 `true`。

### 故障模式 2：通道语义选错，并发下数据"随机"回退

**症状（可观测）**：并发两个请求写同一个会话，其中一个的标题被另一个覆盖；审批场景里同一个 tool_call 收到两次决策，最后生效的是第一次（旧的那个）。症状特点是**不报错、不稳定、复现概率随并发上升**。

**根因**：所有通道都用了"取新值"（last-write-wins）语义。取新语义本身没错——`title` / `approval` 这类"只有一个正确当前值"的字段就该取新。错的是把"该追加的"也做成取新：`messages` 一旦取新，并发两次调用就只剩最后一次的对话，前面全丢。

**排查路径**：列出所有通道，逐个问两个问题——"这个字段丢了历史会有后果吗""并发写两次，哪个应该赢"。第一个答"会"的必须是追加型；答不出"哪个该赢"的说明语义没定义清楚。再看代码里 reducer 的实际实现是否与答案一致。

**修复**：按语义分四类——追加（messages / result / 事件流）、取新（title / approval / 当前状态）、浅合并（环境元信息）、分层归约（容器类：合并对象 + 内部数组追加）。✅ 实测：`verify/verify-core.ts` 段 3 用两个并发写验证——追加型两次都在、取新型只剩最后一个。

**预防**：在每个通道的定义旁写一行注释"语义 + 为什么"，评审时逐条读。这条注释比文档有用，因为它长在代码上。

### 故障模式 3：越权调用只拦在中间件层

**症状（可观测）**：审计日志里出现了"未被允许的工具"执行记录，但中间件层的拒绝计数是 0。或者：模型调用被正常拒绝，但某次批量任务里同一个工具被成功执行了。

**根因**：中间件层拦的是"模型主动发起、经过工具调用包装的路径"。任何绕过中间件直调工具实现（自家代码里的 `tool.invoke()`、批处理脚本、迁移工具、内部管理接口）都不经过这一层。这是**两层权限**里第二层缺失的典型后果。

**排查路径**：搜工具实现被直接引用的地方——`rg "executeSql|runShell" -g '!*test*'`，看每个引用点是否都在中间件的包装之下。再查执行器内部有没有"身份 / 参数 / 路径"的二次校验。

**修复**：在执行器内部加闸——不信任调用方传来的身份与参数，自己从可信上下文（宿主注入的 invocation 上下文，不是模型输出）重新取一遍再校验。✅ 实测：`verify/verify-core.ts` 段 4 构造"绕过中间件直调"，中间件层计数 0、执行器内部拒绝 1 次。

**预防**：把工具实现做成"不可直接调用"的形态（不导出、只通过工厂返回包装后的版本），让绕过变成一件需要刻意为之的事。**真正的越权往往来自自家代码，不是模型**。

### 故障模式 4：`interrupt` 之前的副作用被重复执行

**症状（可观测）**：用户收到两条一模一样的审批通知；或者一次审批通过后，下游系统被扣了两次款。日志里同一条"发送通知"出现两次，中间隔着一个 `resume`。

**根因**：官方硬语义——**恢复时被中断的节点从头重跑**，不是从 `interrupt()` 那一行继续。所以 `interrupt()` 之前的任何代码都会再执行一遍。把"发通知""写审计""扣额度"放在 `interrupt()` 之前，恢复一次就多一份副作用。

**排查路径**：找到 `interrupt()` 调用，把它上面整个函数体读一遍，列出所有有外部副作用的语句（网络请求、写库、发消息、计费）。有一个就算命中。

**修复**：把副作用挪到 `interrupt()` 之后（拿到决策再执行），或者做成幂等（带唯一键的写入 / 去重表）。📖 依据：[LangGraph interrupts](https://docs.langchain.com/oss/javascript/langgraph/interrupts) 明确"节点会重新执行"。✅ 实测：`verify/verify-core.ts` 段 5 用执行轨迹数组证明——"节点进入"这行在恢复时打印了两次。

**预防**：把"节点必须可重入"写进编码规范；在节点入口处打一行轨迹日志，评审时看恢复场景的日志里是否出现重复的入口行。

### 故障模式 5：条件性跳过 `interrupt`，恢复值错位

**症状（可观测）**：审批场景里明明批的是"允许"，恢复后拿到的却是上一次的"拒绝"；或者两个 `interrupt` 只有一个被恢复，另一个永远等不到。表现像"决策串台"。

**根因**：同节点多次 `interrupt` 的恢复值**按索引严格匹配**。如果代码里写了 `if (needApproval) interrupt(...)`，某次运行跳过了第一个，索引就整体前移一位——第二个 `interrupt` 拿到的是本该给第一个的恢复值。这个错误不抛异常，只是"批错了"。

**排查路径**：数一次完整运行里 `interrupt()` 被调用的**次数与顺序**，再看每次的恢复值是否符合预期顺序。两次运行次数不同 → 命中。

**修复**：让 `interrupt` 的调用**无条件且顺序固定**——需要判断时，把判断放在 `interrupt` **之后**（先拿到决策，再决定用不用）。📖 依据：同上官方文档，恢复值按 `interrupt` 调用顺序索引匹配。

**预防**：把 `interrupt` 当成"必须走到的站点"，不做条件分支；评审时专门问一句"这段代码在什么情况下会少走一个 interrupt"。

### 故障模式 6：用 `pendingWrites` 判断"图是否在等人"

**症状（可观测）**：审批挂起后，接口返回"已完成"；或者恢复接口报"没有可恢复的内容"，但图明明停在审批节点。代码里判断挂起用的是 `state.pendingWrites` 或 `tasks[].interrupts`。

**根因**：`pendingWrites` 在"由 interrupt 导致的挂起"场景下框架**根本不写**；`tasks[].interrupts` 在跨进程读取时拿不到（它属于当次执行的内存结构）。两个判据在单进程演示里可能碰巧成立，一旦跨进程就全错。

**排查路径**：挂起后新起一个进程，打印 `graph.getState(cfg)` 的 `next` / `pendingWrites` / `tasks`，看哪个真的有值。✅ 实测：`verify/verify-run.ts` 段 6 打印三者——只有 `next` 非空。

**修复**：唯一可靠判据是 `getState(cfg).next` 非空（图说"我还有下一步没走"）。要拿中断载荷，读 `state.tasks[].interrupts` 里当次执行写入的部分，或直接从 `__interrupt__` 事件（数组，元素 `{id, value}`）里取。

**预防**：把"判挂起"封装成一个函数（`isSuspended(cfg)`），全项目只走这一处，禁止各处自己判断。

### 故障模式 7：预算 fail-open，读不到用量就当 0

**症状（可观测）**：月度账单远超预期，但预算告警一次没触发；或者某些租户的用量统计长期为 0。日志里这些调用的 `tokenUsage` 是 `undefined` / `null`。

**根因**：预检写成了 `if (used > limit) reject`。当 `used` 是 `undefined` 或 `NaN` 时，比较结果为 `false`，于是"没超限"——读不到用量被当成了"没用量"。这是典型的 fail-open：**最不确定的时候放得最松**。

**排查路径**：搜预算判断处，看有没有 `Number.isFinite` 或 `?? 0` 这类处理。有 `?? 0` 就是病灶（把未知当零）；再看 `used` 的来源——模型返回里没有 usage 字段时走哪条路。

**修复**：改成 fail-closed——`if (!Number.isFinite(used) || used + estimate > limit) reject`。读不到用量不等于没用量。✅ 实测：`verify/verify-run.ts` 段 7 用 `undefined` 与 `NaN` 两个输入验证——两者都被拒绝。

**预防**：所有"限额 / 配额 / 权限"判断统一走一个 `budgetCheck()`，函数内部强制 fail-closed；单测里必须有"输入为 undefined / NaN"的用例。

### 故障模式 8：上下文压缩把 `tool_call` 与结果拆开

**症状（可观测）**：压缩之后模型开始"凭空说话"——引用一个它从没见过的工具结果，或者对某个 `tool` 消息问"这是什么"。也可能表现为模型反复要求重调一个已经调过的工具。不报错。

**根因**：一条 AI 消息里的 `tool_call` 与后续 `tool` 消息是**配对**关系（按 `tool_call_id`）。压缩时按"消息条数"或"token 位置"截断，很容易把配对切开：留下 `tool_call` 删掉结果，或留下结果删掉 `tool_call`。模型看到没有来由的结果，只能自己编解释。

**排查路径**：压缩后的消息数组里，检查每个 `tool_call.id` 是否有对应的 `tool` 消息，以及每个 `tool` 消息的 `tool_call_id` 是否能找到发起它的 `tool_call`。任一方向缺失即命中。

**修复**：压缩以"配对"为最小单位——要么整对保留，要么整对替换成一句摘要（"调用了 executeSql，返回 3 行"）。另外两条铁律：保留系统提示不动、只压中段（首尾不压）。✅ 实测：`verify/verify-run.ts` 段 8 的 `assertNoOrphanToolMessages` 在违规样本上报出 2 条孤儿。

**预防**：压缩函数出口强制跑一次配对断言，失败直接抛（宁可报错也别让模型看到残缺上下文）。

---

### 故障模式 9：沙箱只防了 `../`

**症状（可观测）**：安全检查通过（只测了 `../../etc/passwd`），但事后发现文件写到了沙箱外。典型是有人用了一个指向外部的符号链接，或者目录名恰好是 `u1-evil` 而边界判断用了 `startsWith("u1")`。

**根因**：路径逃逸有三种，只测第一种等于没测。`../` 归约、符号链接解析、前缀同名（`/data/u1` 与 `/data/u1-evil`）。前缀判定的经典错误是字符串 `startsWith` 而不是"路径分隔符边界"。

**排查路径**：三条用例依次跑——`../` 穿越、软链接指向外部、同级同名目录（`u1` vs `u1-evil`）。第三条最容易漏，因为它看起来"正常"。

**修复**：先规范化（resolve 掉 `..` 与符号链接，取真实路径），再做**边界判定**（等于根目录，或以 `根目录 + 分隔符` 开头）。✅ 实测：`verify/verify-run.ts` 段 9 三条用例全部拦截，其中 `u1-evil` 在朴素 `startsWith` 实现下会漏。

**预防**：把沙箱解析做成唯一入口函数，测试里固定三条用例；代码评审时看到 `startsWith` 判路径就要求改成边界判定。

### 故障模式 10：幂等只做了"同键同输入"，没做"终态幂等"

**症状（可观测）**：失败重试场景下同一次操作被执行两次（下游收到两条记录）；或者一个已经成功完成的调用，被重复提交后账本里出现两条成功记录。

**根因**：幂等实现只覆盖了"查到同键就返回旧结果"，漏了两件事：一是**终态判断**（`if (ledger.finishedAt) return ledger`——已经结束的就别再往下走），二是**异常路径也落定**（抛异常时不写终态，留下一个永远 RUNNING 的僵尸，下次重试会当成"还在跑"而跳过或重复）。

**排查路径**：看幂等入口，问三个问题——同键同输入返回旧结果吗？同键异输入拒绝吗？已经成功的同键再来一次，会不会又执行一遍？

**修复**：三件套——同键同输入返回旧账本；同键异输入按 sha256 指纹拒绝；进入执行前先判 `finishedAt`。异常路径也要写终态（failed），否则僵尸永远 RUNNING。✅ 实测：`verify/verify-run.ts` 段 7 的四条用例（首次 / 重放 / 冲突 / 终态后重放）。

**预防**：账本状态机画出来贴在代码旁；每个状态转移都要有"谁写的、什么条件下写"的注释。

## 三、上线前 Checklist

按"没做会怎样"排序，不是按重要性排序。每条都能在课程里找到对应机制。

| # | 检查项 | 没做的后果 | 怎么查 |
|---|---|---|---|
| 1 | 运行时定义深度冻结（含数组） | 定义被运行时改写，行为不可复现 | `Object.isFrozen(rt.tools)` 断言 |
| 2 | 每个通道写明语义与理由 | 并发下数据静默丢失 | 逐通道读注释 |
| 3 | 执行器内部有第二层校验 | 绕过中间件的越权无人拦 | 搜工具实现的直接引用 |
| 4 | `interrupt` 之前无不可重入副作用 | 恢复时通知/扣费重复 | 读 `interrupt` 上方函数体 |
| 5 | `interrupt` 调用无条件、顺序固定 | 恢复值错位，批错 | 数每次运行的调用次数 |
| 6 | 挂起判定只用 `getState().next` | 跨进程判不到挂起 | 新进程打印 `state.next` |
| 7 | 预算判断 fail-closed | 账单失控且不告警 | 传入 `undefined` 看是否拒绝 |
| 8 | 压缩出口有 tool 配对断言 | 模型看到残缺上下文后胡编 | 跑孤儿检测 |
| 9 | 沙箱三条逃逸用例全覆盖 | 文件写到沙箱外 | `../` / 软链 / 同名前缀 |
| 10 | 账本终态幂等 + 异常落定 | 重试重复执行 / 僵尸 RUNNING | 四条幂等用例 |
| 11 | 工具结果按 `tool_call_id` 回填 | 结果错位且不报错 | 乱序返回的用例 |
| 12 | 工具并行执行单点失败不拖垮 | 一个工具坏了整轮失败 | 一个工具抛错的用例 |
| 13 | 上下文压缩保留系统提示 | 人格/规则丢失 | 压缩后看首条消息 |
| 14 | MCP 能力发现容忍部分失败 | 一个能力缺失导致整体不可用 | 模拟一个能力报错 |

## 四、一条元经验

这十条故障里有 **6 条是"静默失败"**：定义被改（1）、通道丢数据（2）、越权未被拦（3）、恢复值错位（5）、挂起判不到（6）、结果错位（按 id 回填那条）。它们的共同点是——**不抛异常、不报错、日志里看起来一切正常**。

所以在这类系统里，"跑通了"这个信号的价值极低。真正有价值的验证是**构造反例**：并发两个写、绕过中间件直调、恢复两次、把用量设成 undefined、把路径写成 `u1-evil`。课程 `verify/` 里的 14 段脚本，本质上就是这 14 个反例的固化——这也是为什么它比"读一遍源码"更有用。
