# 反例对照

> "能跑但很糟"的版本 + 逐条对比。反例的价值在于让"为什么这样设计"从抽象论述变成可感知的代价。

## 反例版本：单文件、内存等待、无状态机

```typescript
// 反例：全部塞进一个函数，30 行"跑通"
async function run(userInput: string) {
  const messages = [new HumanMessage(userInput)];

  while (true) {
    const res = await model.invoke(messages);
    messages.push(res);

    if (!res.tool_calls?.length) return res.content;

    for (const call of res.tool_calls) {
      if (call.name === 'executeSql') {
        console.log('等待审批...');
        let approved = false;
        // 轮询等待，最多等 10 分钟
        for (let i = 0; i < 600; i++) {
          await sleep(1000);
          if (await checkApproved(call.id)) { approved = true; break; }
        }
        if (!approved) throw new Error('审批超时');
      }
      const result = await tools[call.name].invoke(call.args);
      messages.push(new ToolMessage({ content: result, tool_call_id: call.id }));
    }
  }
}
```

## 逐条对比

| # | 反例的问题 | 后果 | 本项目的做法 |
|---|---|---|---|
| 1 | 轮询等待审批，最多 10 分钟 | 审批人下班，请求直接失败；进程全程占一个 worker | interrupt 挂起，进程可退出，无时长上限 |
| 2 | 审批状态靠 `checkApproved` 外部查询 | 只能靠轮询感知，无法"事件驱动"恢复 | checkpoint 记录恢复点，审批到达时主动恢复 |
| 3 | 无状态机 | 进程崩溃后无法知道"跑到哪了" | Invocation 状态机 + 终态幂等 |
| 4 | 权限判断内联在循环里 | 新增一个写操作就要改这个函数 | 中间件策略统一拦截 `wrapToolCall` |
| 5 | `messages` 无限增长 | 多轮审批后上下文超限 | 压缩策略 + 独立 approval 通道 |
| 6 | 工具名硬编码字符串 | 拼写错误在运行期才暴露 | 工具注册表 + 类型约束 |
| 7 | 没有拒绝路径 | 审批拒绝直接抛异常，用户看到 500 | 拒绝是正常终态，返回结构化结果 |
| 8 | 无幂等 | 重复提交导致同一条 SQL 执行两次 | request_id 去重 |

## 关键对照：轮询与挂起的资源账

假设审批平均等待 30 分钟，每天 200 次审批：

| 方案 | 并发占用 | 日累计 worker 占用 |
|---|---|---|
| 轮询（每秒查一次） | 30 分钟内占 1 个 worker | 200 × 30 分钟 = 100 worker·小时 |
| 轮询（每分钟查一次） | 同上 | 同上（worker 仍被占），只是查询次数降为 30 次/请求 |
| 挂起 | 等待期间 0 占用 | 仅恢复时短暂占用 |

> 注意第二行：**降低轮询频率并不能释放 worker**，只是减少查询开销。这是"轮询似乎也能优化"的常见误判——只要还在 `await` 循环里，worker 就一直被占。真正的解法只有挂起。

## 反例里唯一值得保留的东西

反例的 while 循环结构本身是对的（模型 → 工具 → 回模型）。它错的是"在循环里做等待"，而不是"用循环驱动 Agent"。区分"结构对但做法错"与"整个思路都错"，是约束还原法的一部分。
