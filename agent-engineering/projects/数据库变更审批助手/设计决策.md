# 设计决策

> 本项目至少需要两个真实权衡。每个权衡按「选项对比 → 选择 → 理由 → 代价」四段写。

## 决策一：审批用 interrupt 挂起，还是用轮询等待

### 选项对比

| 维度 | interrupt 挂起 | 轮询等待 |
|---|---|---|
| 实现复杂度 | 高（需 checkpoint 存储 + 恢复入口） | 低（一个 while + sleep） |
| 进程占用 | 挂起期间不占 worker | 全程占用一个 worker |
| 进程重启 | 可恢复 | 状态丢失，需重来 |
| 等待时长容忍 | 无上限（隔天也行） | 受进程生命周期限制 |
| 调试难度 | 高（跨越进程边界） | 低（单进程内可断点） |

### 选择

interrupt 挂起。

### 理由

审批的真实等待时长不可控（可能几小时到几天），"进程一直活着"这个前提在部署环境里不成立。轮询方案在本地演示完全够用，但它把"等待时长"和"进程生命周期"绑死了，而这个绑定在生产里必然被打破。

### 代价

- 必须引入持久化 checkpoint 存储（本课程用文件版 `FileSaver`，生产应换 Postgres/Redis）
- 恢复路径需要额外设计：谁来触发恢复、如何校验审批人身份、重复恢复如何幂等
- 调试变难：一次完整流程被拆成两个进程，无法单步走完

## 决策二：工具来源用统一抽象，还是直接用 LangChain 的 `tool()` 逐个定义

### 选项对比

| 维度 | 统一 provider 抽象 | 逐个 `tool()` 定义 |
|---|---|---|
| 初期成本 | 高（要先定抽象、写适配层） | 低（写完就能用） |
| 新增一个工具源 | 加一个 provider | 每个工具都要改注册代码 |
| 权限挂载点 | 统一在 provider 层拦 | 散落在每个工具内 |
| 类型可表达性 | 受抽象约束，特殊能力要开旁路 | 完全自由 |
| 适合规模 | 工具数 > 10 或有多种来源 | 工具数少、来源单一 |

### 选择

统一 provider 抽象（但只做两层：`builtin` 与 `remote`，不追求覆盖所有来源）。

### 理由

本项目的核心是验证"暴露与授权分离"，如果工具定义散落各处，权限拦截点就无法统一。统一抽象让"哪些工具需要审批"成为一个集中的配置，而不是散在 N 个文件里的 if。

### 代价

- 抽象本身有学习成本，工具数少时明显过度设计
- 特殊工具的能力（如流式返回、长任务）难以用统一 schema 表达，需要旁路
- 抽象一旦定错，后续所有工具都受影响（这是本项目刻意把抽象做小的原因）

## 一个"选择不做"的决策

**不迁移状态通道化到 10 个通道的粒度。** 本项目只用 3 个通道（messages / approval / result）。

理由：通道化的收益来自"多路写入需要独立合并"，本项目只有审批结果和消息两条写入路径，再细拆只是增加心智负担。这是"可迁移设计需按约束裁剪"的具体例子——照抄粒度等于没理解。
