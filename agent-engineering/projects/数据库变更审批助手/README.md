# 结课综合实战项目 · 需求与覆盖地图

> 本项目是课程制 Phase 3 的收尾产物，跨阶段整合前 15 课的知识点。
> 复杂度门槛：≥2 个设计决策权衡 + 反例对照 + 可运行实现 + 验收清单。**不要求重写标本系统**，要求重建一条最小但完整的链路。

## 需求

用当前版本的 LangGraph（不使用标本系统的 0.4.x 版本），重建一条最小可运行的 Agent 工程链路，覆盖"定义 → 编译 → 执行 → 中断 → 恢复"五步。

选定场景：一个需要人工审批的**数据库变更助手**。用户提出变更需求，Agent 生成 SQL 并请求审批，审批通过后才执行，执行结果回写对话。

> 场景选它的理由：天然需要 interrupt（审批）、天然有工具边界（写操作 vs 读操作）、天然需要 checkpoint（审批可能隔天）。

## 目标

- 跑通五步链路，每步都能独立验证
- 至少做两个真实的设计权衡，并写清代价
- 有一个"能跑但很糟"的反例版本，逐条对照说明为什么糟

## 覆盖知识点地图

| 阶段 | 知识点 | 在本项目中的落点 |
|---|---|---|
| 1 | 四层职责划分 | 目录结构按「定义 / 编译 / 执行 / 记录」分区 |
| 1 | 一次请求的完整旅程 | `README` 中画出请求链路 |
| 2 | 一份定义包含什么 | `config/agent.yaml` 描述 Agent |
| 2 | 定义与实例分离 | 定义文件与运行时实例分离，支持改定义不改代码 |
| 2 | 编译入口与分支路由 | `compile.ts` 把定义编译成图 |
| 2 | 通道划分 | 状态至少 3 个通道（messages / approval / result） |
| 2 | reducer 与并发 | 自定义 reducer 合并审批结果 |
| 2 | 策略接口 | 一个"写操作需审批"的中间件策略 |
| 2 | 六个钩子职责 | 用 `wrapToolCall` 拦截写操作 |
| 3 | 工具从哪来 | 内置工具 + 一个模拟的外部工具源 |
| 3 | 授权与暴露分离 | 读操作直接跑，写操作走审批 |
| 3 | checkpoint | 审批挂起后进程可退出 |
| 3 | interrupt 等人工 | 审批挂起与恢复 |
| 3 | 为什么不轮询 | `README` 中对比挂起与轮询的资源账 |
| 3 | Invocation 生命周期 | 一条变更请求的状态机 |
| 4 | 上下文压缩 | 多轮审批后的历史压缩策略 |

## 运行方式

```bash
npm install
npm run demo        # 跑通完整链路（含一次审批）
npm run demo:reject # 审批拒绝路径
```

> 实现细节见 `实现/`，设计权衡见 `设计决策.md`，反例见 `反例对照.md`，自测见 `验收清单.md`。
