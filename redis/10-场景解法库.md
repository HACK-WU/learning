## 场景 1：大促流量翻 10 倍，数据库先扛不住

**场景描述**：平时 QPS 500，大促期间涨到 5000。接口开始超时，监控显示数据库连接池打满，慢查询激增。Redis 已经在用，但命中率只有 60%。

**🔒 先自己想 30 秒**：第一反应是加缓存？扩容数据库？还是限流？——想一想命中率只有 60% 意味着什么：还有 40% 的请求在打数据库，那 40% 才是压垮数据库的元凶。

<details><summary>💡 提示（分层 / 分维度想）</summary>

按三层想：
- **入口层**：能不能挡掉一部分请求？
- **缓存层**：命中率为什么只有 60%？是缓存没覆盖、还是失效太快、还是根本没命中？
- **数据层**：数据库扛不住时，是加从库读、还是加机器、还是改查询？

再想一个关键问题：**这 40% 的未命中，是正常的冷数据回源，还是被穿透/击穿了？** 两者的解法完全不同。

</details>

<details><summary>📖 展开解法</summary>

### 解法一览

| 解法 | 能解决到 | 代价 | 适用边界 |
|------|---------|------|---------|
| **A · 提高缓存命中率**（查清 miss 原因 + 预热 + TTL 抖动） | 命中率提到 95%+，数据库压力降一个数量级 | 要分析 miss 原因；预热需要提前跑 | 读多写少、数据可缓存 |
| **B · 数据库读写分离 + 加从库** | 读压力分散到多个从库 | 主从延迟带来不一致；主库仍是写瓶颈 | 读远多于写，且能接受秒级延迟 |
| **C · 应用层限流 + 降级** | 保证系统不崩，牺牲部分请求 | 部分用户看到降级页 | 任何场景的最后防线 |
| **D · 数据库垂直扩容 / 分库分表** | 根本性提升容量 | 成本高、改造大、周期长 | 长期方案，不适合大促前临时做 |

### 推荐路径（递进，不是一次全上）

1. **先查 miss 原因**（成本最低，收益最大）。`INFO stats` 看 `keyspace_hits/misses`，再抽样分析 miss 的是哪些 key——如果是同一批 key 反复 miss，那不是冷数据，是**缓存被击穿或没写进去**。
2. **上预热 + TTL 抖动**。大促开始前把热点数据灌进缓存；TTL 加随机值避免集体失效。
3. **补防护**：穿透（空值缓存/布隆）、击穿（互斥锁/逻辑过期）、雪崩（抖动）——三件套补齐。
4. **仍不够再加从库**，把读压力摊开。
5. **最后上限流降级**，保证不死。扩容分库分表属于长期规划，不该在大促前两周动。

### 知识点挂钩

- 命中率分析 → 阶段 4 课 9（性能诊断四层模型）
- 穿透 / 击穿 / 雪崩 → 阶段 4 课 8
- 预热与 TTL 抖动 → 阶段 4 课 8；本项目 `cache_layer.py` 的 `warmup()` 与 `_ttl()`
- 读写分离 → 阶段 3 课 6
- 大 key 导致的额外延迟 → 阶段 4 课 9

### 什么情况下此方案不适用

- **强一致场景不能粗暴加缓存**（如余额、库存扣减）——缓存带来的一致性窗口不可接受，应走 Lua 原子操作 + 数据库事务。
- 数据是**写多读少**时，加缓存收益极低，反而增加一致性维护成本。

### 做错会踩的坑

- 只加缓存不查 miss 原因 → 命中率提不上去，白做
- 预热时把 TTL 设成同一个值 → 大促开始瞬间集体失效，直接雪崩（故障模式 6）
- 忽略大 key → 单个 key 的读取就拖垮整体（故障模式 3）

</details>

## 场景 2：数据量翻 100 倍，单机内存不够了

**场景描述**：数据从 5GB 涨到 500GB。单机 Redis 内存已经顶到上限，加内存条也到头了。

**🔒 先自己想 30 秒**：买更大的机器？做集群分片？还是——先问一句：这 500GB 里有多少是**真的需要放在内存里的**？

<details><summary>💡 提示</summary>

两个方向，先分清再选：
- **横向扩展**：数据太多一台装不下 → 分片
- **纵向瘦身**：数据其实没那么热 → 冷数据下沉、过期清理、编码优化

关键判断：**数据的访问分布是什么样的？** 如果 80% 的请求集中在 20% 的数据上，那根本不需要把 500GB 全放内存。

</details>

<details><summary>📖 展开解法</summary>

### 解法一览

| 解法 | 能解决到 | 代价 | 适用边界 |
|------|---------|------|---------|
| **A · Redis Cluster 分片** | 容量随节点线性扩展 | 多 key 操作受限（必须同槽）；运维复杂度上升；跨片事务不支持 | 数据量大且增长明确 |
| **B · 客户端分片 / 代理分片** | 同样能扩展，且对多 key 限制更灵活 | 客户端要引入分片逻辑；扩缩容要手动迁移 | 想绕开 Cluster 限制时 |
| **C · 冷热分离**（Redis 只存热数据，冷数据下沉到数据库/对象存储） | 内存占用大幅下降，成本最优 | 需要识别冷热；冷数据访问变慢 | 访问有明显冷热分布 |
| **D · 垂直扩容（加内存）** | 最简单，零改造 | 有物理上限；成本非线性增长；fork 时间随内存变长 | 数据量只是略超当前配置 |

### 推荐路径

1. **先做数据瘦身**（成本最低）：查有没有该过期却没过期的 key、有没有大 key、有没有重复数据。本项目实测：一个 100 万字段的 Hash 拆成 1000 个小 Hash 后，删除阻塞从 113ms 降到 0.61ms——结构优化不只是省内存，还直接影响可用性。
2. **做冷热分离**：只把真正热的放进 Redis，其余下沉。这一步常常能把容量需求砍掉一个数量级。
3. **仍不够再上 Cluster**：规划好 key 的 hash tag，让需要一起操作的数据落在同一槽。
4. **垂直扩容作为过渡**，不是终局。

### 知识点挂钩

- Redis Cluster 哈希槽与 CRC16 → 阶段 4 课 7
- 多 key 与 Lua 的同槽限制 → 阶段 4 课 7；本项目 `inventory.py` 的 Lua 只用 1-2 个 key，天然满足
- 大 key 拆分与 UNLINK → 阶段 4 课 9
- 内存淘汰策略 → 阶段 4 课 8
- 冷热判断（OBJECT FREQ 需 LFU 策略）→ 阶段 4 课 9

### 什么情况下此方案不适用

- 如果业务**强依赖多 key 事务且无法用 hash tag 归拢**，Cluster 会带来大量改造——此时优先考虑冷热分离 + 垂直扩容。
- 数据量增长不可预测且需要频繁扩缩容时，Cluster 的槽迁移成本要提前评估。

### 做错会踩的坑

- 上 Cluster 但 key 设计没考虑 hash tag → 大量 `CROSSSLOT` 错误
- 只扩容不做瘦身 → 成本失控，且 fork 时间随内存增长，RDB 备份越来越慢

</details>

## 场景 3：要做实时排行榜，数据量百万级

**场景描述**：需要实时展示销量 Top 100，参与商品百万级，更新频繁（每秒数千次）。

**🔒 先自己想 30 秒**：用数据库 `ORDER BY` 查？用 Redis ZSet？还是自己维护一个堆？——想一想"实时"和"百万级"叠在一起意味着什么。

<details><summary>💡 提示</summary>

三个关键问题：
1. Top N 的 N 是大还是小？（只要前 100 名，还是要任意人的排名？）
2. 更新频率有多高？
3. 单个 key 会有多大？——**百万成员的 ZSet 是不是变成了大 key？**

</details>

<details><summary>📖 展开解法</summary>

### 解法一览

| 解法 | 能解决到 | 代价 | 适用边界 |
|------|---------|------|---------|
| **A · 单个 ZSet 全量排行** | 实时更新、取 TopN 都是 O(logN)，任意排名 O(logN) | **单 key 会很大**，是大 key 风险源；无法分片 | 十万级以内、单 key 可控 |
| **B · 按维度拆分 ZSet + 定期合并** | 每个 key 都很小，可分散到不同槽 | 取全局 TopN 要合并计算，非严格实时 | 百万级、可按类目/时段拆分 |
| **C · ZSet 存 TopN + 数据库存全量** | Redis 只扛热点，容量可控 | 落榜数据要从数据库查，逻辑复杂 | 只关心头部排名 |
| **D · 用数据库物化视图定时刷新** | 实现简单 | 非实时（分钟级延迟）；刷新时数据库压力大 | 实时性要求不高 |

### 推荐路径

1. **先上 A**（单 ZSet），最直白。用 `ZINCRBY` 更新、`ZREVRANGE` 取 TopN、`ZREVRANK` 查排名。
2. **监控单 key 大小**。`MEMORY USAGE` + `OBJECT ENCODING`——注意 ZSet 元素超过 `zset-max-listpack-entries`（默认 128）会从 listpack 转为 skiplist，**内存会发生数量级跳变**。
   本机实测（Redis 8.10.1，7203 实例）：128 个成员时 1721 字节（13.4 字节/元素），
   加到 129 个立刻变成 11821 字节（91.6 字节/元素）——**总内存跳变 6.87 倍，每元素开销涨 6.8 倍**。
   这不是"翻倍"，是**数量级差异**，容量规划时必须按转换后的口径估算。
3. **过大就拆**（方案 B）：按类目、时段、地区拆成多个小 ZSet，全局榜通过合并计算或异步聚合。
4. **加过期清理**：日榜用 `stats:daily:{day}` 这类带日期的 key，自然过期，不用手动删（本项目 `DailyStats` 即如此）。

### 知识点挂钩

- ZSet 跳表 + 哈希表双结构 → 阶段 2 课 4
- ZSet 编码转换（listpack → skiplist）与内存跳变 → 阶段 2 课 4、阶段 4 课 9
- 大 key 风险与拆分 → 阶段 4 课 9
- 集群分片 → 阶段 4 课 7
- 本项目 `inventory.py` 的 `RankBoard` → 单 ZSet 实现，配合 `ZINCRBY`

### 什么情况下此方案不适用

- **要求严格一致的全局实时排名且数据量极大** → 单 ZSet 成大 key，拆分后又难保证严格实时。此时应重新审视"实时"的真实要求（秒级？分钟级？）。
- 排名需要按多个维度自由组合筛选时，ZSet 无法胜任，应交给搜索引擎或 OLAP 引擎。

### 做错会踩的坑

- 单 ZSet 塞百万成员 → 大 key，删除/过期时阻塞（故障模式 3）
- 忽略编码转换 → 128→129 个成员时内存跳变 6.87 倍，容量估算全错并触发 OOM（故障模式 2）

</details>

## 场景 4：秒杀，100 件商品 10 万人抢

**场景描述**：限量 100 件，开抢瞬间 10 万请求涌入。要求：不超卖、一人一单、响应快。

**🔒 先自己想 30 秒**：用数据库事务？用 Redis 扣减？还是消息队列排队？——想一想"不超卖"的硬要求，到底该在哪一层保证。

<details><summary>💡 提示</summary>

三个子问题分开想：
1. **库存扣减的原子性**在哪一层保证？（应用层的 if 判断够吗？）
2. **一人一单**用什么数据结构去重？
3. **10 万请求里的绝大部分注定抢不到**——怎么让它们**快速失败**，而不是全挤到 Redis？

</details>

<details><summary>📖 展开解法</summary>

### 解法一览

| 解法 | 能解决到 | 代价 | 适用边界 |
|------|---------|------|---------|
| **A · Redis Lua 原子扣减**（本项目采用） | 不超卖；性能极高（万级 TPS）；一人一单可用 Set 去重 | 库存数据最终要落库，需异步同步；Redis 宕机期间不可用 | 绝大多数秒杀场景 |
| **B · 数据库悲观锁 / 乐观锁** | 绝对可靠，无需担心缓存一致性 | 性能差（千级 TPS），高并发下锁竞争严重 | 库存量小、并发不高 |
| **C · Redis 预扣 + 消息队列异步下单** | 削峰填谷，系统解耦 | 架构复杂；用户要异步等待结果 | 超大规模、允许异步返回 |
| **D · 分层拦截**（前端限流 + 网关限流 + Redis 令牌桶） | 把无效请求挡在最外层 | 需要多层配合 | 任何秒杀都该做，是 A 的前置 |

### 推荐路径

1. **先做分层拦截**（方案 D）——10 万请求里 99.9% 注定失败，让它们打到 Redis 都是浪费。前端按钮置灰、网关按 UID 限流、令牌桶控制放行量。
2. **库存扣减用 Lua**（方案 A）。把「判断库存 → 扣减 → 记入已购 Set」合成一个原子操作。本项目 `inventory.py` 的 `LUA_SECKILL` 即此实现，实测 500 并发抢 100 件，账目完全对平。
3. **注意接口设计**：返回值要能区分「扣完剩 0」「库存不足」「已购买过」——本项目初版用 `0` 同时表示前两者，导致误判，已改为 `-2`/`-3` 区分。
4. **异步落库**：Redis 扣减成功后发消息，由消费者创建订单并同步数据库。
5. **超大规模再上消息队列**（方案 C）。

### 知识点挂钩

- Lua 脚本原子性与集群 key 限制 → 阶段 4 课 7
- Set 去重（一人一单）→ 阶段 2 课 4
- 缓存与数据库一致性（异步落库）→ 阶段 4 课 8
- 接口返回值设计的歧义陷阱 → 本项目 [设计决策.md](projects/电商大促数据层/设计决策.md) 决策 3
- 本项目 `inventory.py` 的 `seckill()` → 完整实现

### 什么情况下此方案不适用

- **要求绝对零丢失**（如金融交易）→ 纯 Redis 方案不够，需要数据库事务兜底或 TCC 分布式事务。
- 库存需要支持**复杂的预留/释放/超时归还**时，Lua 脚本会变得很复杂，应改用专门的库存服务。

### 做错会踩的坑

- 应用层 if 判断扣减 → 超卖（故障模式 9）
- Lua 返回值歧义 → 业务逻辑分叉错误（本项目实测）
- 不做分层拦截 → Redis 被无效请求淹没，反而拖垮正常业务

</details>

## 场景 5：要给运营开数据后台，得防止他们误操作

**场景描述**：运营需要一个后台，能查缓存数据、手动清理某些 key。但你担心他们执行 `KEYS *` 或 `FLUSHALL` 把生产搞挂。

**🔒 先自己想 30 秒**：只靠"培训+提醒"够吗？给一个只读账号？还是干脆不给直连，做一个后台服务中转？

<details><summary>💡 提示</summary>

从三个层面想：
1. **权限层**：Redis 的 ACL 能做什么？能限制命令吗？能限制 key 前缀吗？
2. **架构层**：是不是根本不该让人直连 Redis？
3. **兜底层**：万一还是出事了，怎么把损失降到最小？

另外一个容易忽略的点：**收紧权限后，运维自己还能不能查问题？**

</details>

<details><summary>📖 展开解法</summary>

### 解法一览

| 解法 | 能解决到 | 代价 | 适用边界 |
|------|---------|------|---------|
| **A · ACL 分角色最小权限**（本项目采用） | 从权限层面禁掉危险命令，且能限制 key 前缀 | 配置复杂；容易过度收紧 | 所有生产环境都应做 |
| **B · 后台服务中转**（不直连 Redis，走 API） | 完全可控，可加审计日志、操作审批 | 要开发后台服务 | 有多人需要访问数据时 |
| **C · 只读从库** | 查询类操作完全不影响主库 | 从库有延迟；写操作另走主库 | 以查询为主的场景 |
| **D · 独立实例隔离** | 最彻底，出问题不影响主业务 | 数据要同步；成本翻倍 | 有合规/审计强要求 |

### 推荐路径

1. **ACL 是底线**（方案 A），不管用不用别的方案都要做。本项目实测的完整基线：
   - `user default off` —— 出厂默认是 `nopass + @all`，等于裸奔
   - 应用账号：限定 key 前缀 + 禁危险命令 + **回补运维只读命令**
   - 只读账号：给运营/报表，注意 `+@read` 默认**包含 KEYS**，必须显式 `-KEYS`
   - 复制账号：单独的 `replicator`（关掉 default 后不建这个，从库会连不上）
2. **运营查询走只读从库**（方案 C），写操作必须走后台服务。
3. **有开发能力就做后台中转**（方案 B），加上操作审计与二次确认。
4. 定期 `ACL LIST` 审计。

### 知识点挂钩

- ACL 权限模型与角色设计 → 阶段 4 课 9
- `+@read` 包含 KEYS 的陷阱 → 阶段 4 课 9 实测
- `-@dangerous` 会误伤 INFO → 本项目实测，见 [设计决策.md](projects/电商大促数据层/设计决策.md) 决策 5
- 从库只读 → 阶段 3 课 6

### 什么情况下此方案不适用

- **只有一个人维护的内部系统** → 全套 ACL 配置可能是过度设计，设个强密码 + 禁掉 FLUSHALL 就够了。别为了严谨牺牲效率。
- 需要执行 `DEBUG`、动态改配置的场景 → 这些本来就不该给运营账号。

### 做错会踩的坑

- `-@dangerous` 一刀切 → INFO/SLOWLOG 全废，出问题查不了（故障模式 8）
- 先关 default 再建账号 → 把自己锁在外面，只能重启（故障模式 7）
- 以为 `+@read` 很安全 → 它包含 KEYS，照样能拖垮实例

</details>

## 场景 6：Redis 该不该上？团队在纠结选型

**场景描述**：新项目要做技术选型，有人提议用 Redis，有人提议直接上数据库，还有人听说 Redis 改许可证了，担心合规风险。

**🔒 先自己想 30 秒**：先把"要不要用"和"用哪个发行版"分开——这是两个完全不同的问题。前者是技术选型，后者是法务选型。

<details><summary>💡 提示</summary>

先问三个问题：
1. **访问模式**：读多写少？有热点数据？能不能接受数据丢失？
2. **数据特征**：数据量多大？需要按字段查询吗？需要强一致吗？
3. **合规约束**：你们公司会不会把 Redis 作为**服务对外提供**？——这一条直接决定许可证风险。

</details>

<details><summary>📖 展开解法</summary>

### 解法一览（要不要用）

| 解法 | 能解决到 | 代价 | 适用边界 |
|------|---------|------|---------|
| **A · Redis 作为缓存层**（数据库仍是主） | 扛读压力、降低延迟 | 要维护一致性；缓存可用性影响体验 | 读多写少、有热点 |
| **B · 只用数据库**（不上 Redis） | 零额外组件，零一致性问题 | 扛不住高并发读 | 数据量小、QPS 低 |
| **C · Redis 作为主存储** | 极致性能 | 持久化与高可用要精心设计；仍可能丢数据 | 能接受极小丢失窗口的特定场景 |
| **D · 换专用引擎**（ES / ClickHouse / 时序库） | 按场景最优化 | 多一份运维成本 | 需要检索/分析/时序能力时 |

**判断清单**——以下任一答案为"是"，就该认真考虑别用 Redis：

- 需要按任意字段筛选/聚合？→ 用数据库或 ES
- 数据量超过内存容量？→ 先冷热分离，否则用数据库
- 强一致、绝对不能丢？→ 用数据库
- 需要复杂事务与回滚？→ 用数据库
- 只有冷数据、QPS 很低？→ 直接数据库，别引入额外组件

### 解法一览（用哪个发行版）

| 解法 | 能解决到 | 代价 | 适用边界 |
|------|---------|------|---------|
| **A · Redis 8 官方版** | 功能最全（内置 JSON/搜索等模块） | 8.0+ 为三许可（RSALv2 / SSPLv1 / AGPLv3）；SSPL 标签带来法务沟通成本；8.0 本身 2026-12-01 停止支持 | 自用、不对外提供 Redis 服务（走 AGPLv3 条款） |
| **B · Valkey**（Linux 基金会） | 保持 BSD（分叉自最后一个 BSD 版 7.2.4），零许可顾虑 | 分叉时间短，生态与托管覆盖仍在追赶 | 对外提供 Redis 服务；法务对 SSPL 敏感 |
| **C · 云厂商托管版** | 免运维，自带高可用备份 | 成本高、厂商绑定、部分命令受限 | 无专职运维且预算允许 |

### 推荐路径

1. **先回答"要不要用"**——用上面的判断清单过一遍。很多时候正确答案就是"别用 Redis"。
2. **再选发行版**：
   - 自用、需要完整功能 → Redis 8（**选 AGPLv3 条款**；自用不对外提供、且不修改源码时无实质约束）
   - **把 Redis 作为服务对外售卖**（云厂商、PaaS）→ 必须 Valkey（RSALv2/SSPLv1 直接禁止这种用法）
   - 法务对 SSPL/AGPL 一律否决 → Valkey
   - 没运维、有预算 → 云托管（顺带确认云厂商提供的是 Redis 还是 Valkey 引擎）
   - 已在生产跑 Redis 7.4~7.8 或 8.0 → 查支持周期：7.2 已于 2026-02-28 EOL，8.0 于 2026-12-01 停止支持，应规划升到 8.8+
   - 纯缓存、追求极致多线程吞吐 → 可评估 Dragonfly（BSL 1.1，2029-03-01 转 Apache 2.0；**独立实现非分叉**，命令兼容性需单独验证）
3. **定下后写进技术文档**，包括为什么选它、什么情况下要重新评估。

> 📌 许可证事实核查于 2026-09（详见 [设计决策.md](projects/电商大促数据层/设计决策.md) 决策 6 的核查表）。

### 知识点挂钩

- 许可证变迁（BSD → source-available → 三许可）→ 阶段 4 课 9
- Valkey 分叉背景 → 阶段 4 课 9
- 生态与竞品（Memcached / Dragonfly）→ 阶段 4 课 9
- 适用边界判断 → 阶段 1 课 1（Redis 不是什么）
- 本项目选型理由 → [设计决策.md](projects/电商大促数据层/设计决策.md) 决策 6

### 什么情况下此方案不适用

- 只因"Redis 快"就上 → 快是有代价的（一致性、容量、运维复杂度）。**先证明数据库扛不住，再上 Redis。**

### 做错会踩的坑

- 把 Redis 当数据库用且不开持久化 → 重启数据全丢，雪崩打到数据库
- 忽略许可证，把 Redis 封装成服务对外售卖 → 合规风险（RSALv2/SSPLv1）
- 不设 `maxmemory` → 用到 OOM 被系统杀掉
