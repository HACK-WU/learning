# Redis 排障速查手册

> **怎么用**：出事了别从头读。按索引表找**症状**，翻到对应条目照做。
> **想懂为什么**：每个条目末尾有原理链接，事后再看 [08-实战经验.md](08-实战经验.md)。
> **查不到**：→ 转 `debug` skill 现场取证。
>
> 适用版本：Redis 8.x（命令与参数基于 8.10.1 实测；6.x / 7.x 大部分通用）。

## 🔴 症状 1：KEYS 阻塞事件循环

**一眼识别**：P99 从毫秒级涨到秒级；`instantaneous_ops_per_sec` 骤降但 `connected_clients` 很高；`SLOWLOG GET` 里出现 KEYS 且耗时数百毫秒以上。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | `CLIENT LIST` 找 `cmd=KEYS` 且 `idle=0` 的连接 → `CLIENT KILL ID <id>` | 该连接断开，Redis 恢复响应 |
| 定位 1 | `SLOWLOG GET 10` | 出现 KEYS 及耗时 → 确认是它 |
| 定位 2 | `INFO commandstats` 查 `cmdstat_keys` | `calls>0` 即生产有代码在用，必须改 |
| 定位 3 | 若数据库也告警 → 已雪崩，对数据库限流/扩容 | 数据库 QPS 回落 |
| 修复 | 业务代码把 `KEYS` 全替换为 `SCAN`（**注意游标要解码后比较**） | 不再出现 KEYS |
| 若无效 | → 转 `debug` 现场排查，或查是否是 Lua 脚本 / 大 Value 导致 | — |

> **预防**：用 ACL 禁用 KEYS（需管理员账号执行）：`ACL SETUSER appuser -KEYS`。
> 应用账号本身不应拥有 ACL 管理权限——本项目实测：appuser 执行 `ACL SETUSER` 会返回
> `NOPERM ... no permissions to run the 'acl|setuser' command`，这正是期望的行为。
> 已加固的实例，这类变更要走运维流程。
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 1

## 🔴 症状 2：内存满且无法淘汰（写入被拒）

**一眼识别**：应用报错 `OOM command not allowed when used memory > 'maxmemory'`；`INFO stats` 的 `evicted_keys=0`。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | `CONFIG SET maxmemory-policy allkeys-lru` | 立即恢复写入（代价：可能淘汰想保留的 key） |
| 定位 1 | `INFO memory` | 看 `used_memory` vs `maxmemory`、`maxmemory_policy` |
| 定位 2 | `redis-cli --bigkeys` | 找出最大的 key |
| 定位 3 | `MEMORY USAGE <key>` + `OBJECT ENCODING <key>` | 编码是 `skiplist`/`hashtable` 说明已发生编码转换（实测 ZSet 跨 128 阈值时内存跳变 6.87 倍） |
| 修复 | 清理异常数据；必要时临时扩容 | 内存回落，写入正常 |
| 若无效 | 若 `noeviction` 改不动 → 检查是否有没设 TTL 的 key（volatile-* 策略下无 TTL key 不可淘汰） | — |

> **预防**：缓存场景不要用 `noeviction`；对大集合做单 key 大小巡检。
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 2

## 🔴 症状 3：大 key 同步删除造成卡顿

**一眼识别**：每隔一段时间一次全局延迟尖刺；`LATENCY LATEST` 有 `command` 事件；尖刺期间**所有**命令都慢。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 停止正在执行的删除任务 / cron | 尖刺消失 |
| 定位 1 | `LATENCY LATEST` 或 `LATENCY HISTORY command` | 看到延迟尖刺的时间与幅度 |
| 定位 2 | `redis-cli --bigkeys` | 定位大 key |
| 定位 3 | `MEMORY USAGE <key>` | 精确测量大小 |
| 修复 | 删除统一改用 `UNLINK`；分批删（如 `ZREMRANGEBYRANK`） | 删除不再阻塞 |
| 若无效 | → 转「症状 1」排查是否是其他 O(N) 命令 | — |

> **预防**：写入时就拆小，别养成大 key；删除一律 `UNLINK`。
> **实测**：删 100 万字段 Hash 阻塞其他请求 113.66ms；拆成小 key 后 0.61ms；`UNLINK` 0.45ms。
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 3

## 🟡 症状 4：用户说慢，但慢查询日志是空的

**一眼识别**：`SLOWLOG GET` 返回空或耗时都很小，但客户端 P99 很高。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 若怀疑大 Value：对返回大对象的接口做分页/裁剪 | 客户端耗时下降 |
| 定位 1 | `SLOWLOG GET 10` | 空 → 排除命令执行慢 |
| 定位 2 | `INFO stats` 看 `instantaneous_output_kbps` | 很高 → 出口带宽瓶颈（大 Value） |
| 定位 3 | 查客户端：连接池等待、GC 停顿、跨机房 RTT | 定位到排队环节 |
| 修复 | 大 Value 拆小/分页；连接池扩容；就近部署 | P99 回落 |
| 若无效 | → 转 `debug` 抓客户端侧火焰图 | — |

> **预防**：不要只用 SLOWLOG 判断健康度——它不含网络传输与排队时间。
> **实测**：`HGETALL` 在 SLOWLOG 里只记 36.6ms，客户端却等了 1501ms。
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 4

## 🟡 症状 5：缓存与数据库不一致

**一眼识别**：直接对比缓存值与数据库值，两者不同，且**持续到 key 过期才恢复**。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | `DEL` 掉不一致的缓存 key | 下次读回源，拿到最新值 |
| 定位 1 | 查更新路径代码：是「删缓存」还是「更新缓存」 | 「更新缓存」就是病根 |
| 定位 2 | 查删除是否失败被静默吞掉（try/except 没打日志） | 找到静默失败点 |
| 修复 | 改为「先更库、再**删**缓存」；删除失败要有补偿 | 更新后缓存不再残留旧值 |
| 若无效 | 检查是否多服务共用缓存且模型不同步 → 转 `debug` | — |

> **预防**：删缓存失败必须显式报错，不能静默。
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 5

## 🔴 症状 6：缓存雪崩

**一眼识别**：某个时刻数据库 QPS 暴涨数十倍，接口大面积超时；Redis 命中率断崖下跌。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 应用层限流 / 降级；必要时临时把部分请求切到读数据库 | 数据库不再被打爆 |
| 定位 1 | 抽样看一批同类 key 的 `TTL` | 值几乎相同 → 确认是集体失效 |
| 定位 2 | 对比数据库 QPS 尖峰时刻与 TTL 失效时刻 | 吻合即确认 |
| 修复 | TTL 改为 `base + random(0, jitter)` | 失效时刻分散 |
| 若无效 | 检查是否是缓存服务整体宕机（那是另一个问题）→ 转「症状 2」 | — |

> **预防**：预热时就加抖动；重要 key 用「逻辑过期」而非物理过期。
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 6

## 🔴 症状 7：从库复制断开（NOPERM psync）

**一眼识别**：从库日志 `NOPERM User xxx has no permissions to run the 'psync' command`；`master_link_status:down`。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 若因 ACL 变更导致：先给复制账号补权限，恢复复制 | `master_link_status:up` |
| 定位 1 | `tail -f <从库日志>` | 看 NOPERM 的具体命令名（psync / replconf） |
| 定位 2 | `ACL GETUSER <user>` | 确认缺哪些权限 |
| 修复 | **用管理员账号**执行：`ACL SETUSER replicator on '>密码' ~* +psync +replconf +ping +info`；从库 `CONFIG SET masteruser replicator` + `CONFIG SET masterauth '密码'` | 复制恢复，`master_repl_offset` 追平 |
| 若无效 | 若已把 default 关掉且无任何可用账号 → **只能重启**（在配置里配好账号再启动） | — |

> ⚠️ **注意权限**：`ACL SETUSER` 需要管理员权限。用应用账号执行会返回
> `NOPERM User appuser has no permissions to run the 'acl|setuser' command`——
> 这是**正确的**最小权限设计（应用账号不该能改账号），不是故障。
>
> **那到底用谁执行？** 在本课程的实验环境里，`default` 用户在 `rebuild.sh` 第 4 步已被 `ACL SETUSER default off` 关闭，
> 所以重建账号有两条路：
> 1. **学习/演练时**：改回 `ACL SETUSER default on nopass ~* +@all` 临时开门，改完再关（**仅限本地实验**）；
> 2. **正规做法**：在配置文件里预置一个带 `+ACL` 的运维账号，或走运维变更流程。
>
> 这也正是本条故障想教的事：**关 default 之前，先确认你手里还有一把能开 ACL 的钥匙。**

> **预防**：**先建账号、再关 default**。顺序反了就把钥匙锁屋里了。
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 7

## 🟡 症状 8：加固后运维命令全被禁

**一眼识别**：执行 `INFO` / `MEMORY USAGE` / `SLOWLOG` / `OBJECT` 返回 `NOPERM`。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 用仍有权限的账号（或本地连接）补权限 | 诊断能力恢复 |
| 定位 1 | `ACL GETUSER <user>` 看 commands 字段 | 确认被 `-@dangerous` 误伤 |
| 定位 2 | 逐个执行诊断命令，记录哪些返回 NOPERM | 列出待加回清单 |
| 修复 | **用管理员账号**执行：`ACL SETUSER appuser +INFO +CONFIG +CLIENT +MEMORY +SLOWLOG +LATENCY +OBJECT +SCAN +TTL +TYPE +DBSIZE` | 诊断命令可用，危险命令仍被拒 |
| 若无效 | 若连 default 都关了且无其他账号 → 重启加载配置 | — |

> **预防**：最小权限 ≠ 一刀切。收紧后必须回补运维只读命令。
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 8

## 🔴 症状 9：秒杀超卖

**一眼识别**：库存变成负数；`成功下单数 > 初始库存`；`成功数 + 剩余库存 != 初始库存`。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 暂停秒杀活动；人工核对订单与库存 | 阻止继续超卖 |
| 定位 1 | 查代码是否把「读库存 → 判断 → 扣减」拆成三步 | 三步走就是病根 |
| 定位 2 | 压测复现：并发 >> 库存，看账目是否对平 | 复现即确认 |
| 修复 | 改用 Lua 把判断+扣减合成原子操作 | `成功数 + 剩余 = 初始`，库存不为负 |
| 若无效 | 检查 Lua 脚本是否真用了 `KEYS`/单 key（集群下要同槽）；检查集群是否跨槽执行失败 | — |

> **预防**：接口设计要区分失败原因——别用 `0` 同时表示「扣完剩 0」和「库存不足」。
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 9

## 🟡 症状 10：`NOAUTH Authentication required`

**一眼识别**：连接后执行任何命令都返回 `NOAUTH Authentication required`。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 用正确的账号密码连接：`redis-cli --user <user> --pass <pwd>` | 命令正常执行 |
| 定位 1 | `ACL LIST`（需有权限） | 看 default 是否被 `off` |
| 定位 2 | 检查客户端配置的账号密码 | 找到配置错误处 |
| 修复 | 修正连接配置；若密码忘记 → 改配置重启 | 应用恢复 |
| 若无效 | 若所有账号都不可用 → 改配置重启，加载 `users.acl` | — |

> **预防**：改 ACL 前先确认有可用账号，并 `ACL SAVE` 持久化。

## ⚪ 症状 11：`READONLY You can't write against a read only replica`

**一眼识别**：向从库执行写命令时返回此错误。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 把写操作改发到主库 | 写入成功 |
| 定位 1 | `INFO replication` 确认 `role:slave` | 确认连的是从库 |
| 定位 2 | 检查客户端是否被错误配置了从库地址 | 找到配置问题 |
| 修复 | 写走主库、读走从库（读写分离） | 写入正常 |
| 若无效 | 若本意就是读写分离 → 这是**预期行为**，不是故障 | — |

> **预防**：`replica-read-only` 默认 `yes`，从库只读是设计如此，不要去关它。

## 🚑 通用止血动作（不确定是哪类问题时，先把损失停下）

| 场景 | 止血动作 | 代价 |
|------|----------|------|
| 刚改了 ACL / 配置就出问题 | 回滚配置（改前先记原值） | 回到旧的安全状态 |
| 单个客户端在跑危险命令 | `CLIENT KILL ID <id>` 掐掉该连接 | 该客户端业务中断 |
| 内存满导致写入被拒 | `CONFIG SET maxmemory-policy allkeys-lru` | 可能淘汰想保留的 key |
| 缓存雪崩打到数据库 | 应用层限流 / 降级 | 部分请求失败 |
| Redis 完全无响应且无法恢复 | 故障转移到从库（**不要**先重启——重启会丢队列命令并引发冷启动雪崩） | 主库切换 |
