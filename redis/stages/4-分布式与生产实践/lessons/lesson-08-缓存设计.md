## 本课要解决的三个问题

前七课讲的是"Redis 怎么用"，本课讲"**缓存用不好会怎么死**"。

这是 Redis 最经典的一课，也是面试和线上事故最高发的一课。三个问题都很具体：

1. **缓存失效的三种死法分别怎么治？** —— 穿透 / 击穿 / 雪崩
2. **缓存和数据库不一致时怎么办？** —— 缓存与数据库一致性
3. **内存满了 Redis 会做什么？** —— 内存淘汰与过期策略

先说一个贯穿全课的立场：**这三个问题都没有"一劳永逸的解法"**。所有方案都是"降低概率"或"缩小影响范围"，真正的工程能力体现在——你能说清每个方案在什么条件下失效，以及失效后的兜底是什么。

## 第一幕：场景引入 —— 三个真实的凌晨三点

### 困境一：数据库被"不存在的数据"打爆

监控报警：DB CPU 100%，RT 从 5ms 涨到 3 秒。

排查发现请求全是这种：

```
GET /user/99999999
GET /user/-1
GET /user/abc
```

**这些 id 在数据库里根本不存在。** 缓存查不到（没有），数据库也查不到（没有）。查不到就没法写缓存——于是**每一次请求都老老实实打到数据库**。

你加了缓存，但缓存对这些请求完全不起作用。这就是**缓存穿透**：数据根本不存在，缓存形同虚设。

狠一点的情况是有人故意刷。正常的业务查询，不存在的 key 占比很低；恶意攻击可以做到 100% 都是不存在的 key。

### 困境二：一个热点 key 过期，几千个请求同时冲进数据库

大促商品详情页，QPS 2 万。这个商品的信息缓存在 Redis 里，TTL 5 分钟。

**TTL 到期的那一瞬间**：

```
第 299.999 秒：缓存命中，一切正常
第 300.000 秒：缓存过期，key 消失
第 300.001 秒：几千个并发请求同时 miss，全部去查数据库
```

这些请求做的是同一件事——查同一个商品、写同一个 key。但因为缓存此刻是空的，它们**谁也不知道别人已经在查了**，于是全部涌向数据库。

这就是**缓存击穿**：单个热点 key 过期的瞬间，海量并发直接穿透到数据库。

### 困境三：凌晨整点，所有缓存同时失效

更糟的情况。为了保证数据新鲜，团队给所有缓存统一设置了 1 小时 TTL，并且都是整点写入的。

于是每天凌晨 0:00、1:00、2:00……**几十万个 key 在同一秒集体过期**。数据库承受的不是"一个热点 key"的压力，而是"整个缓存层"的压力。

或者更直接：Redis 集群挂了。**整个缓存层消失**，所有流量瞬间转嫁给数据库。

这就是**缓存雪崩**：大面积 key 同时失效，或缓存层整体不可用。

### 三个困境的定性区别

这是本课第一件要记牢的事——三种故障**成因不同、解法也不同**，混淆就会用错药：

| | 穿透 | 击穿 | 雪崩 |
|---|---|---|---|
| 数据存在吗？ | **DB 里没有** | DB 里有，只是缓存没了 | DB 里有，大批缓存没了 |
| 影响范围 | 分散的无效 key | **单个**热点 key | **大批** key / 整个缓存层 |
| 触发原因 | 恶意攻击、参数非法 | 热点 key 恰好过期 | 批量 key 同时过期、Redis 宕机 |
| 一句话 | 查无此物，两头都空 | 单点热点，过期瞬间 | 集体失效，全军覆没 |

## 第二幕：认知冲突 —— 四个"想当然"的崩塌

### 冲突一：缓存空值解决不了穿透，它只挡得住"重复攻击"

最常见的穿透解法是"缓存空值"：DB 查不到，就往缓存里写个占位值。

```python
v = redis.get(key)
if v is None:
    val = db.get(key)
    if val is None:
        redis.set(key, '__NULL__', ex=60)   # 空值占位，短 TTL
    else:
        redis.set(key, val, ex=300)
```

**这个方案有个被普遍忽略的前提**：它只对"重复打同一批 id"有效。

本课实测（2000 次攻击，全部是不存在的随机 id）：

```
第 1 轮（2000 个不同 id）：DB 查询 1999 次  ← 全部穿透
第 2 轮（重复打相同 id） ：DB 查询    0 次  ← 被占位挡住
```

攻击者如果每次都用**新的随机 id**，空值缓存就完全失效——每个 id 都是第一次见，每个都要查一次 DB，然后还在 Redis 里留下一堆垃圾占位 key（实测第 1 轮后缓存从 500 涨到 2499 个 key）。

**真正能挡住随机 id 攻击的是布隆过滤器**，因为它的判断不依赖"这个 id 之前有没有被查过"，而依赖"这个 id 在不在全量集合里"。

### 冲突二：布隆过滤器说"存在"不一定存在，说"不存在"就一定不存在

布隆过滤器是个**有方向性误差**的结构，这点必须记死：

- **说"不存在" → 一定不存在**（假阴性为 0）—— 这是它能用来防穿透的根本原因
- **说"存在" → 可能存在**，有一定概率是误判（假阳性）

本课实测：声明误判率 0.1% 的过滤器，在 50000 个确定不存在的 id 上实测误判 **28 次 = 0.056%**；对 500 个真实存在的 id，**误拦 0 次**。

误判的后果是什么？请求放行进去了，查缓存、查 DB，发现确实没有——**只是一次无效查询，不是数据错误**。所以误判是可接受的，代价可控。

还有一个反直觉的点：**标准布隆过滤器不支持删除**。因为多个元素共用 bit 位，删掉一个会把别人的位也清零，从而产生"假阴性"——这是绝对不允许的。需要删除场景改用**布谷过滤器**（`CF.*`，本机实测 `CF.ADD` / `CF.EXISTS` / `CF.DEL` 均可用）。

### 冲突三：互斥锁能救击穿，但会拖垮性能——不是所有场景都该用

击穿的标准解法是互斥锁：只让一个线程去重建缓存，其他线程等待。

实测（200 并发、DB 重建 50ms）：

```
无防护          ：DB 查询 114 次，瞬时并发 106
互斥锁 SET NX   ：DB 查询   1 次，瞬时并发   1
```

看起来完美。但代价是：**199 个线程在等待**。等待意味着线程阻塞、连接池占用、RT 变长。

在真正的秒杀场景（几万并发），让几万个线程阻塞在锁上，比让它们直接打 DB 可能更糟——**线程池耗尽会导致整个服务不可用，而 DB 慢只是变慢**。

所以还有第二种解法：**逻辑过期**。key 物理上永不过期，value 里存一个业务过期时间戳。读到"逻辑过期"时，抢到锁的线程去异步刷新，其他线程**直接返回旧值，不等待**。

实测对比：

```
互斥锁  ：DB 查询 1 次，199 个线程等待，耗时 0.097s
逻辑过期：DB 查询 1 次，199 个线程立刻返回旧值，耗时 0.084s
```

**选哪个？** 取决于业务能否接受"短暂返回旧数据"：

- 能接受（商品详情、新闻、排行榜）→ 逻辑过期，性能更好
- 不能接受（库存、余额）→ 互斥锁，宁可等，也不能返回错的数

注意这两句话是**权衡的两面，不是谁更优**：互斥锁的"等待"在数万并发下可能耗尽线程池（所以秒杀场景要慎用），逻辑过期的"返回旧值"在库存场景就是超卖。**选型依据是业务对陈旧数据的容忍度**。

### 冲突四：`noeviction` 是默认值，而它在生产上几乎总是错的

Redis 出厂配置的淘汰策略是 `noeviction`——内存满了**不淘汰**，直接让写命令报错。

本课实测：

```
写入成功: 21048 次
写入失败: 50 次
首次报错 : OOM command not allowed when used memory > 'maxmemory'.
```

如果你把 Redis 当缓存用，却忘了配 `maxmemory-policy`，那么内存满时**写请求会突然大面积失败**，而读请求还完全正常。这种"能读不能写"的诡异状态，排查起来很费时间。

更隐蔽的坑在后面（知识点 3 会实测）：**`volatile-*` 系列策略在没有 key 设 TTL 时，会退化成 `noeviction`**。

## 第三幕：层层揭示 —— 三个知识点

## 知识点 1：穿透 / 击穿 / 雪崩

### 1.1 穿透：数据不存在，缓存永远填不上

**根因**：缓存的写入依赖"数据库能查到数据"。查不到 → 不写缓存 → 下次还是查不到。这是一个**自我维持的死循环**。

#### 解法一：缓存空值（占位）

```python
val = db.get(key)
if val is None:
    redis.set(key, '__NULL__', ex=60)    # TTL 要短
```

**实测效果**：

| 场景 | DB 查询次数 | 说明 |
|------|------------|------|
| 无防护 | 2000 | 全穿透 |
| 缓存空值·首轮（随机 id） | 1999 | **几乎无效** |
| 缓存空值·重复（同批 id） | 0 | 完全挡住 |

**代价**：缓存中会堆积大量无效占位 key（实测 500 → 2499 个）。TTL 必须设短（建议 30~120 秒），否则既浪费内存，又可能在数据真实产生后造成"查得到占位、查不到真值"的不一致。

**适用**：攻击者重复使用少量 id；或业务侧能确定"不存在 id 的枚举空间很小"。

#### 解法二：布隆过滤器（前置拦截）

在查缓存之前，先问过滤器"这个 key 可能存在吗"。

Redis 8 把 Bloom 做成了内置模块，本机实测 **`bf` 模块默认可用**：

```bash
127.0.0.1:7101> MODULE LIST
1) 1) "name"
   2) "bf"
   3) "ver"
   4) (integer) 81001
```

> ⚠️ **注意**：`MODULE LIST` 里能看到 `bf`，不代表命令一定可用。本课实测中，用 `redis-server` 直接启动的实例**没有**加载该模块，`BF.RESERVE` 报 `ERR unknown command`。需要显式加载：
>
> ```bash
> redis-server --port 7101 --loadmodule /usr/lib/redis/modules/redisbloom.so
> ```
>
> 另外 `MODULE LOAD` 运行时加载默认被禁用（报 `ERR MODULE command not allowed`），需在配置里设 `enable-module-command yes`。

**核心命令**：

```bash
BF.RESERVE user:bloom 0.001 500     # 误判率 0.1%，预期 500 个元素
BF.ADD     user:bloom 1001
BF.EXISTS  user:bloom 1001          # → 1（可能存在）
BF.EXISTS  user:bloom 9999999       # → 0（一定不存在）
BF.INFO    user:bloom               # 看容量、层数、已插入数量
```

**实测数据**（500 个真实 id，2000 次随机不存在 id 攻击）：

```
攻击请求数      : 2000
DB 查询次数     : 3          ← 只有误判的 3 次穿透
误判率实测      : 28 / 50000 = 0.0560%（声明 0.1%）
存在的 id 被拦  : 0 / 500 = 0.00%   ← 假阴性为 0
过滤器内存      : 1120 字节（1.09 KB），存 500 个 id
平均每 id 开销  : 2.24 字节
```

**2.24 字节 / id**——这就是布隆过滤器的核心价值。存 1 亿个 id 只要约 224 MB，而存完整的 id 集合至少要几 GB。

**参数怎么定**（官方文档公式）：

| 误判率 | 哈希函数数 | 每元素位数 |
|--------|-----------|-----------|
| 1% | 7 | 9.585 |
| 0.1% | 10 | 14.378 |
| 0.01% | 14 | 19.170 |

**三个必须知道的使用要点**：

1. **`capacity` 要预留冗余**（实际数量的 1.3~1.5 倍）。估小了，过滤器会自动扩容成"多层子过滤器"，查询延迟随层数**线性增长**。
2. **不支持删除**（`BF.DEL` 实测报 `ERR unknown command`）。需要删除用 `CF.*` 布谷过滤器。
3. **需要预热**。过滤器里得先有全量 id 才能工作，通常的做法是启动时从 DB 批量加载，或写入时同步 `BF.ADD`。

#### 解法三：参数校验 + 限流（最前置、最便宜）

在最外层就拦掉非法请求：`id <= 0`、格式不对、非数字，直接返回。再加接口限流和 IP 黑名单。

这一层**成本最低、效果最直接**，属于"能不做的工作就不做"。别一上来就上布隆过滤器。

#### 穿透解法怎么选

| 方案 | 挡随机 id | 挡重复 id | 成本 | 副作用 |
|------|----------|----------|------|--------|
| 参数校验 + 限流 | 部分 | 是 | 极低 | 几乎无 |
| 缓存空值 | **否** | 是 | 低 | 占位 key 占内存 |
| 布隆过滤器 | **是** | 是 | 中 | 有误判、不支持删除、需预热 |
| 布谷过滤器 `CF.*` | 是 | 是 | 中 | 支持删除，内存略高 |

**生产推荐组合**：参数校验（最外层）→ 布隆过滤器（拦随机 id）→ 缓存空值（兜底重复 id）。

### 1.2 击穿：热点 key 过期的那一瞬间

**根因**：缓存 miss 之后的"重建"动作没有被并发控制。所有线程同时发现缓存没了，同时去重建。

**关键认知**：击穿和穿透的本质区别是——**击穿的数据是真实存在的**。所以解法不是"拦住请求"，而是"**控制重建的并发度**"。

#### 解法一：互斥锁（SET NX）

```python
v = redis.get(key)
if v is None:
    # 原子抢锁：只有抢到的去重建
    if redis.set('lock:'+key, '1', ex=10, nx=True):
        try:
            val = db.get(key)
            redis.set(key, val, ex=300)
        finally:
            redis.delete('lock:'+key)
    else:
        time.sleep(0.05)
        return redis.get(key)      # 重试读缓存
```

**实测（200 并发，DB 重建 50ms）**：

```
拿到锁的线程数  : 1        ← 只有它查了 DB
等待后重读的    : 199
DB 查询次数     : 1        ← 从 114 降到 1
DB 瞬时最大并发 : 1        ← 从 106 降到 1
```

**必须用 `SET key val NX EX` 一条命令完成加锁+超时**，不能分两步（`SETNX` 然后 `EXPIRE`）。分两步的话，加锁后崩溃会导致锁永不释放——死锁。

**代价**：未抢到锁的线程要等待或重试，高并发下会占用大量线程资源。

#### 解法二：逻辑过期（永不过期 + 异步刷新）

value 里存业务过期时间，**Redis 层面不设 TTL**：

```python
# 写入
payload = {'value': 'xxx', 'expire_at': time.time() + 300}
redis.set(key, json.dumps(payload))      # 注意：没有 ex 参数

# 读取
v = redis.get(key)
obj = json.loads(v)
if obj['expire_at'] > time.time():
    return obj['value']                   # 未过期，直接返回
# 已过期：抢锁异步刷新，本线程先返回旧值
if redis.set('lock:'+key, '1', ex=10, nx=True):
    threading.Thread(target=refresh, args=(key,)).start()
return obj['value']                       # 返回旧值，不阻塞
```

**实测**：

```
执行刷新的线程  : 1
返回旧值的线程  : 199      ← 全部立刻拿到数据
DB 查询次数     : 1
总耗时          : 0.084s   ← 无任何线程阻塞
物理 TTL 仍为   : -1       ← 永不过期
```

#### 两种解法怎么选

| | 互斥锁 | 逻辑过期 |
|---|--------|---------|
| DB 查询次数 | 1 | 1 |
| 未命中线程的行为 | **等待**，直到缓存就绪 | **立刻返回旧值** |
| 数据新鲜度 | 强一致（拿到的一定是新的） | 短暂陈旧（可能返回旧数据） |
| 线程资源 | 阻塞，高并发下有风险 | 不阻塞 |
| 额外复杂度 | 低 | 高（要维护逻辑过期字段 + 刷新任务） |

**决策依据就一条**：业务能不能接受"短暂返回旧数据"。

- 商品详情、文章内容、排行榜、配置信息 → **逻辑过期**
- 库存、余额、限量资格 → **互斥锁**（宁可等，也不能返回错的数）

#### 补充：永不过期 + 后台定时更新

还有一种更简单的做法：核心热点 key 干脆不设过期，由定时任务（如每分钟）主动刷新。

**风险**：如果所有 key 都永不过期，内存会持续膨胀，触发淘汰机制——而**淘汰可能会把热点 key 踢掉**（见知识点 3）。所以只对真正的少量核心热点这么做，并做好冷热分离。

### 1.3 雪崩：大面积失效，或缓存层整体没了

**两种成因**：

1. **批量 key 同时过期**：TTL 设置得过于整齐（都是 3600 秒、都是整点写入）
2. **缓存层整体不可用**：Redis 宕机、集群故障、网络分区

#### 实测：统一 TTL vs 随机 TTL

3000 个 key，200 QPS 常驻读流量，观察 26 秒：

**A. 统一 TTL（全部 15 秒过期）**：

```
DB 峰值        : 189 次/秒（发生在第 16 秒）
DB 均值        : 60.0 次/秒
峰值/均值      : 3.1 倍

每秒 DB 查询分布:
   0-13s |     0 |                        ← 前 14 秒完全零查询
   14s   |    16 | ####
   15s   |   188 | #####################
   16s   |   189 | ######################  ← 尖峰
   ...
   25s   |   110 | #############
```

**B. 随机 TTL（15 秒 + 0~60 秒随机抖动）**：

```
DB 峰值        : 27 次/秒
DB 均值        : 6.9 次/秒

每秒 DB 查询分布:
   0-14s |     0 |
   15s   |     3 | #####
   17s   |    14 | #########################
   ...
   25s   |    23 | ####################################
```

**对比结果：DB 峰值降低 7.0 倍（189 → 27），总查询降低 8.7 倍（1561 → 180）。**

注意 A 组的分布形态：前 14 秒是**完全的零查询**，第 15 秒突然跳到 188。这就是雪崩的特征——**不是均匀的压力，是一个尖峰**。数据库通常不是被"平均压力"打垮的，是被这种尖峰打垮的。

#### 实测：Redis 宕机（第二种成因）

```
已执行: redis-cli -p 7101 shutdown nosave
确认 Redis 不可用: ConnectionRefusedError
Redis 连接失败次数: 2395（每次失败都降级查 DB）
DB 峰值: 200 次/秒（全程持续，等于全部流量）
```

**这是最坏的情况**：压力不是尖峰，而是**持续满载**，直到 Redis 恢复。缓存层的作用此刻为 0，数据库必须能扛住 100% 的流量——通常扛不住。

#### 雪崩的防御是分层的

| 层次 | 措施 | 针对哪种成因 |
|------|------|-------------|
| **预防** | TTL 加随机抖动（基础 TTL + random） | 批量过期 |
| **预防** | Redis 高可用（哨兵 / 集群） | 缓存层故障 |
| **预防** | 缓存预热（发布后提前加载热点） | 冷启动 |
| **兜底** | 多级缓存（本地 Caffeine + Redis） | 两种都管 |
| **兜底** | 限流 / 熔断 / 降级 | 保护数据库 |
| **兜底** | 数据库侧的慢查询保护、连接池上限 | 保护数据库 |

**最容易被忽略的一条**：本地缓存。Redis 挂了，本地进程内缓存还能扛一段时间，这是最后一道防线。

**TTL 抖动的写法**（就这么简单，但很多人不做）：

```python
ttl = 3600 + random.randint(0, 600)     # 基础 1 小时 + 0~10 分钟随机
redis.set(key, val, ex=ttl)
```

### 1.4 三种故障的解法对照总表

| | 穿透 | 击穿 | 雪崩 |
|---|---|---|---|
| 根因 | 数据不存在，缓存填不上 | 热点 key 过期，并发重建无控 | 大批 key 同时失效 / 缓存层挂了 |
| 核心思路 | **拦住**无效请求 | **控制**重建并发 | **打散**失效时间 + **兜底**流量 |
| 主力方案 | 布隆过滤器 | 互斥锁 / 逻辑过期 | TTL 随机化 |
| 辅助方案 | 缓存空值、参数校验、限流 | 热点永不过期 + 后台刷新 | 高可用、多级缓存、限流熔断 |
| 别用错 | 拿互斥锁治穿透没用（数据不存在，锁了也没得重建） | 拿布隆过滤器治击穿没用（数据在 DB 里，过滤器会放行） | 拿布隆过滤器治雪崩也没用（问题不是 key 不存在） |

## 知识点 2：缓存与数据库一致性

### 2.1 Cache Aside：事实上的标准模式

先说清楚标准做法，因为后面所有讨论都基于它。

**Cache Aside（旁路缓存）** 的读写规则：

```
读：先读缓存 → 命中则返回 → 未命中则读 DB → 写入缓存 → 返回
写：更新 DB  → 删除缓存
```

实测的正常路径（无并发）是完全一致的：

```
初始: DB=v1, 缓存=v1
写操作: UPDATE DB=v2 → DELETE 缓存
  删除后缓存: None
读操作: miss → 查 DB(v2) → 回填缓存
最终: DB=v2, 缓存=v2  ✅ 一致
```

**为什么是"删缓存"而不是"更新缓存"？** 这个问题 2.5 节专门讲，先记住结论：**删除比更新安全**。

### 2.2 两种写顺序，都有不一致窗口

"先更新 DB 再删缓存"还是"先删缓存再更新 DB"？这是个经典争论。**答案是：两种都会不一致，区别在窗口的长度和后果。**

#### 顺序 A：先更新数据库，再删缓存

**不一致场景**（实测复现）：

```
  writer  DB=v2
  reader  read=v1        ← 读到旧值
  writer  DEL cache
```

读线程在"DB 已更新、缓存尚未删除"的窗口里读到了 v1。

- **窗口长度**：仅"更新 DB"到"删除缓存"之间，通常**毫秒级**
- **是否自愈**：**会**。缓存删除后，下一次读会回填 v2
- **触发条件**：需要并发读恰好落在这个极窄的窗口里

#### 顺序 B：先删缓存，再更新数据库

**不一致场景**（实测复现）：

```
  writer  DEL cache
  reader  read DB=v1     ← DB 还没更新，读到旧值
  reader  回填 cache=v1  ← 把旧值写回缓存！
  writer  DB=v2

最终状态: DB=v2, 缓存=v1  ❌
```

- **窗口长度**：从"删缓存"到"更新 DB"，**取决于 DB 更新有多慢**
- **是否自愈**：**不会**。缓存停在 v1，要等 TTL 到期或下次写操作
- **触发条件**：删缓存后、更新 DB 前有并发读。这个窗口比顺序 A 宽得多

#### 结论：顺序 A 优于顺序 B

| | 先更新 DB 再删缓存 | 先删缓存再更新 DB |
|---|---|---|
| 窗口长度 | 毫秒级（两次操作间隔） | 等于 DB 更新耗时 |
| 是否自愈 | **会**（下次读回填新值） | **不会**（缓存停在旧值） |
| 后果 | 短暂读到旧值 | 缓存长期脏数据 |

**推荐顺序 A（先更新 DB，再删缓存）**，原因是它能自愈。但仍然不是"保证一致"。

### 2.3 延迟双删：它是兜底，不是保证

延迟双删的思路：既然顺序 B 的问题是"旧值被回填"，那我在更新完 DB 之后**再删一次**，把回填的旧值清掉。

```
删缓存 → 更新 DB → sleep 一小会儿 → 再删缓存
```

**实测（300 次并发尝试）**：

```
第二次删除前缓存已是旧值 : 300 次（100.0%）← 双删要修的正是这个
双删后缓存与 DB 不一致   :   0 次（0.0%）
双删后缓存为空（会自愈） : 300 次
```

**怎么读这份数据**：第二次删除确实把旧值清掉了，本轮 300 次尝试最终残留不一致 0 次。但这不代表它"保证一致"，因为它依赖两个假设：

1. **回填发生在第二次删除之前**。如果读线程因为网络抖动、GC 停顿、DB 慢查询而**晚于**第二次删除才回填，旧值仍会残留。实测中 100% 的轮次都是在第二次删除前完成回填的——因为我的测试环境很快，而这恰恰是它在生产上失效的典型原因。
2. **第二次删除本身成功**。如果这次删除失败（网络问题、Redis 超时），兜底就没了。

所以准确的说法是：**延迟双删用一次额外删除把不一致窗口收窄，属于"降低概率"，不是"保证一致"。**

**那 sleep 多久？** 没有标准答案，通常的经验值是"略大于一次读请求的耗时（读 DB + 写缓存）"，比如 100ms~1 秒。这是个拍脑袋的数字，也是这个方案不够优雅的地方。

### 2.4 真正的兜底：TTL + 重试 + binlog 订阅

既然没有方案能保证一致，工程上要做的是**限定不一致的持续时长**和**提高修复概率**。

#### 兜底一：TTL（最重要、最便宜）

**给所有缓存 key 设 TTL**。这是最后一道防线——即使发生了上述任何一种不一致，最长也就持续一个 TTL 周期。

```
不一致持续时间 ≤ TTL
```

这也是为什么"永不过期"的热点 key 方案要慎用：它**放弃了这个兜底**。

#### 兜底二：删除失败要重试

实测的删除失败场景：

```
DB 更新为 v2，但删除缓存的操作失败（网络抖动 / 超时）
结果: DB=v2, 缓存=v1  ❌ 不一致，且会持续到 TTL 到期
```

如果删除失败了就不管，只能等 TTL。改进方式：

- 删除失败丢进**重试队列**（MQ），异步重试
- 设置**重试次数上限**，超过就告警（可能是系统性故障）

#### 兜底三：订阅 MySQL binlog 异步删除

这是目前业界最强的方案（典型实现：Canal + MQ）：

```
业务代码：只更新 DB，完全不碰缓存
Canal：订阅 MySQL binlog，感知到数据变更
     → 发消息到 MQ
消费者：收到消息，删除对应缓存
```

**优势**：

- 业务代码与缓存解耦，不会因为业务代码崩溃而漏删
- MQ 自带重试、持久化，删除失败会自动重投
- 不侵入业务，老系统也能加

**代价**：架构复杂度显著上升（多了一个中间件 + 一个消费者服务），且**仍然存在延迟**（binlog → MQ → 消费者 → 删缓存）。

### 2.5 为什么"删缓存"优于"更新缓存"

这是个值得单独说的点，因为它是**并发写下的正确性问题**，不只是性能问题。

#### 更新缓存的乱序问题（实测复现）

两个线程并发写，各自"更新 DB + 更新缓存"：

```
场景 1（并发，实测）:
  A: DB=v2
  B: DB=v3
  B: cache=v3
  A: cache=v2          ← A 的缓存更新最后到

最终: DB=v3, 缓存=v2  ❌
```

确定性构造的乱序：

```
场景 2（单线程按危险顺序执行）:
  A 更新 DB      → DB=v2, 缓存=v1
  B 更新 DB      → DB=v3, 缓存=v1
  B 更新缓存     → DB=v3, 缓存=v3
  A 更新缓存     → DB=v3, 缓存=v2  ❌ 永久不一致

触发条件：两个写线程的 DB 写入顺序 与 缓存写入顺序 相反
```

**根因**：缓存更新是有"值"的操作，值会互相覆盖，覆盖顺序错了就永久错。

#### 删除为什么不会乱序

**删除没有"值"，只有"状态"（有 / 无）**。无论 A、B 谁先谁后，最终缓存都是"空"，不存在顺序问题。下一次读必然回源 DB，而 DB 已是最后写入的值 → **最终一致**。

#### 另一个理由：避免无效计算

"更新缓存"意味着每次写操作都要计算出完整的缓存值。如果这笔数据写完 100 次都没人读，那就白算了 100 次——而"删除"的代价是恒定的 O(1)。

#### 什么时候"更新缓存"反而更好

只有一种场景：写极少、读极多、且**缓存值计算非常昂贵**（比如要聚合多张表）。这时让每次 miss 都重算的代价太高。但**必须配合并发控制**（分布式锁或版本号 CAS），否则会有上面的乱序问题。

### 2.6 一致性方案全景与选型

| 方案 | 一致性强度 | 复杂度 | 适用场景 |
|------|-----------|--------|---------|
| Cache Aside（先更新 DB 再删缓存）+ TTL | 最终一致，窗口毫秒级 | 低 | **绝大多数业务的默认选择** |
| 延迟双删 | 比上面好一点，仍不保证 | 中 | 对一致性要求略高，能接受 sleep |
| 分布式锁（读写串行化） | 强一致 | 高 | 金融、库存等不能出错的场景 |
| binlog 订阅（Canal） | 最终一致，可靠性最高 | 很高 | 大型系统、老系统改造 |

**一个必须建立的认知**：在"缓存 + 数据库"这个架构下，**强一致性是要付出巨大代价的**（通常意味着写操作要加锁串行化，吞吐量大幅下降）。

真正的工程问题是：**你的业务能接受多久的不一致？**

- 商品详情、文章内容：几秒甚至几分钟都行 → Cache Aside + TTL
- 库存、余额：不能接受 → 要么加锁，要么不用缓存（直接读库，用其他手段扛压力）

## 知识点 3：内存淘汰与过期策略

### 3.1 先分清两件事：过期删除 vs 内存淘汰

这是最高频的混淆点，两者**目标不同、触发条件不同**：

| | 过期删除 | 内存淘汰 |
|---|---------|---------|
| 目标 | 清理**已到 TTL** 的 key | 内存达到 `maxmemory` 时腾空间 |
| 触发条件 | key 的 TTL 到期 | 已用内存 ≥ `maxmemory` |
| 作用范围 | **只处理设了 TTL 的 key** | 按策略可能是全部 key |
| 关系 | 第一道防线 | 兜底（过期清理后仍超限才触发） |

### 3.2 过期删除：惰性 + 定期，两条路径

Redis 采用**惰性删除 + 定期删除**的组合。为什么不用"定时删除"（TTL 到期立刻删）？因为那需要为每个 key 建定时器，大量 key 时 CPU 扛不住。

#### 路径一：惰性删除（访问时检查）

访问 key 时先检查是否过期，过期则删除并返回 nil。

**怎么验证它真的存在？** 定期删除会干扰观察，所以我用 `DEBUG SET-ACTIVE-EXPIRE 0` 把定期删除关掉（需要启动时加 `--enable-debug-command local`）来隔离验证：

```
关闭定期删除后，写入 3 个 TTL=2s 的 key
等 3.5 秒（已过期）:
  DBSIZE = 3              ← key 还在！因为定期删除被关了
  EXISTS lazy:a = 0       ← 但 EXISTS 认为它不存在

主动 GET lazy:a:
  DBSIZE = 2              ← 被删掉了（惰性删除生效）
GET lazy:b:
  DBSIZE = 1

未被访问的 lazy:c:
  DBSIZE = 1              ← 仍占着内存
  KEYS '*' = （空）        ← KEYS 会跳过过期 key

重新开启定期删除:
  DBSIZE = 0              ← 被回收了
```

**这组数据说明三件事**：

1. 过期 key 不会自动消失，**访问才会触发删除**（惰性）
2. 没人访问的过期 key **会一直占着内存**（这就是"内存泄漏"风险）
3. `KEYS` / `SCAN` 这类遍历命令**会跳过过期 key**，所以你用 KEYS 看不到它们，但它们确实占着空间

**单独观察惰性删除的计数器**（不关定期删除时）：

```
过期后未访问: GET lazy0 = None, expired_keys=8
访问后:      expired_keys=8（+=0）
```

这行数据要小心解读：`expired_keys` 没有增加，是因为**定期删除已经抢先把它删了**，访问时 key 已经不在了。所以单看这个计数器无法证明惰性删除——这才需要上面那个 `DEBUG` 隔离实验。

#### 路径二：定期删除（后台抽样）

Redis 后台周期性执行 `activeExpireCycle`：

- 每秒运行 `hz` 次（默认 `hz=10`，即每 100ms 一次）
- 每次从过期字典**随机抽样 20 个 key**，删除其中已过期的
- 若这批中过期比例 **> 25%**，则再抽一轮（循环）
- 单次执行有 **CPU 时间上限**（约 25% 的 CPU 预算），避免阻塞主线程

**实测它的"抽样"特性**——10 万个 key 里只有 1000 个已过期：

```
写入 100000 个 key（1000 个 TTL=1s，其余 TTL=3600s）
5 秒内回收过期 key: 15 个（共 1000 个已过期）
剩余 dbsize=99959
当前 hz = 10
```

5 秒只回收了 15 个。**这不是 bug，是取舍**：定期删除要在"清理及时性"和"不阻塞主线程"之间平衡。

可以粗略验算一下这个数量级是否合理：10 万个 key 里有 1000 个已过期，随机抽 20 个，**抽中过期 key 的数学期望是 `20 × (1000/100000) = 0.2` 个**。5 秒共运行约 50 次（hz=10），理论上限约 `0.2 × 50 = 10` 个——实测 15 个与之同数量级（略高是因为有"过期比例 > 25% 就再抽一轮"的循环，以及快/慢两种周期）。

所以 **15 个不是异常，是抽样机制的必然结果**。这也说明：过期 key 占比越高，定期删除回收得越快（更容易触发循环）；反之，少量过期 key 散落在海量 key 里，回收就会很慢。

**这个特性带来的风险**：如果有大批 key 同时过期，定期删除可能清理不过来，内存会短暂超出预期。此时如果 `maxmemory` 设得紧，会连带触发内存淘汰。

### 3.3 内存淘汰：8 种策略

内存达到 `maxmemory` 时，Redis 按 `maxmemory-policy` 淘汰 key。共 8 种，分三类：

#### 第一类：不淘汰（1 种）

**`noeviction`**（**出厂默认值**）：不淘汰，写命令直接报错。

实测：

```
写入成功: 21048 次
写入失败: 50 次
首次报错 : OOM command not allowed when used memory > 'maxmemory'.
```

**注意**：读命令（GET）仍然正常，只有"会让内存增长的写命令"失败。

#### 第二类：全体 key 中淘汰（3 种）

| 策略 | 行为 |
|------|------|
| `allkeys-lru` | 淘汰**最久未访问**的 |
| `allkeys-lfu` | 淘汰**访问频率最低**的（Redis 4.0+） |
| `allkeys-random` | **随机**淘汰 |

#### 第三类：只在设了 TTL 的 key 中淘汰（4 种）

| 策略 | 行为 |
|------|------|
| `volatile-lru` | 有 TTL 的 key 中，淘汰最久未访问的 |
| `volatile-lfu` | 有 TTL 的 key 中，淘汰访问频率最低的 |
| `volatile-random` | 有 TTL 的 key 中随机淘汰 |
| `volatile-ttl` | 有 TTL 的 key 中，淘汰**剩余 TTL 最短**的 |

#### 实测横评（关键：先标定容量）

> 📌 **实验设计说明**：第一轮实验我把 `maxmemory` 设成 8mb，结果 20000 个 key 只占 3.91MB，**从未触发淘汰**，8 种策略命中率全是 100%，实验完全无效。
>
> 修正后先做**容量标定**：实测 2mb 时淘汰 12219 个、3mb 时淘汰 5635 个、**4mb 及以上淘汰 0 个**。据此选定 **2mb** 作为能稳定触发淘汰的容量，才得到下面这组有效数据。

**测试流程**（顺序很重要）：先写热 key 并访问它们建立统计 → 再灌入 18000 个冷 key 触发淘汰 → 最后按 Zipf 分布访问测命中率。

> ⚠️ **读表前必看**：`volatile-*` 这一组在测试中被特殊对待——**只给冷 key 设了 TTL**（模拟"部分 key 有过期时间"）。这直接决定了它们的结果，详见表格下方的解读 ①。

| 策略 | 热 key 存活 | 命中率 | 淘汰数 |
|------|------------|--------|--------|
| `noeviction` | 2000/2000 | 86.8% | 0 |
| `allkeys-lru` | **25/2000** | **9.4%** | 12380 |
| `volatile-lru` | 2000/2000 | 85.4% | 13150 |
| `allkeys-lfu` | **1920/2000** | **83.7%** | 12249 |
| `volatile-lfu` | 2000/2000 | 85.7% | 13131 |
| `allkeys-random` | 466/2000 | 26.7% | 12368 |
| `volatile-random` | 2000/2000 | 85.4% | 13200 |
| `volatile-ttl` | 2000/2000 | 85.5% | 13158 |

> **这张表不能直接用来排名策略优劣。** 它只能说明"在这种特定设定下各策略的行为"，原因见下面两条解读。

**这组数据有两个反直觉之处，必须解释清楚，否则会得出错误结论**：

**① `volatile-*` 看起来全面优于 `allkeys-*`，这是测试设计的假象**

因为测试只给**冷 key** 设了 TTL，`volatile-*` 策略**只能淘汰冷 key**，热 key 自然全部存活（2000/2000）。这不是策略更聪明，是**它别无选择**。

真实生产中，如果你给所有 key 都设了 TTL，`volatile-lru` 和 `allkeys-lru` 的表现会接近。**这张表里 `volatile-lru` 的 85.4% 不代表它比 `allkeys-lru` 强**，只代表"它没得选"。

**② `allkeys-lru` 只有 9.4%，而 `allkeys-lfu` 有 83.7%——LRU 真的这么差吗？**

不是。这是**扫描式冲刷**场景：一次性灌入 18000 个新 key。在 LRU 语义下，新写入的 key 都是"最近访问"的，它们会把老的热数据全部挤出去。这是 **LRU 的真实弱点**（一次全表扫描就能污染整个缓存），但这个测试场景**放大了这个弱点**，用它比较策略优劣并不公平。

### 3.4 LRU 与 LFU 的公平对照（重要）

我补了一组对照实验，区分两种真实场景：

#### 场景 A：扫描式冲刷（先建热点，再一次性灌入 18000 个冷 key）

| 策略 | 热 key 存活 | 命中率 |
|------|------------|--------|
| `allkeys-lru` | **15/2000** | **8.2%** |
| `allkeys-lfu` | **1921/2000** | **82.3%** |
| `allkeys-random` | 474/2000 | 25.2% |

#### 场景 B：稳定负载（读写交替 30 轮，更接近真实线上流量）

| 策略 | 热 key 存活 | 命中率 |
|------|------------|--------|
| `allkeys-lru` | **1998/2000** | **87.3%** |
| `allkeys-lfu` | 2000/2000 | 87.3% |
| `allkeys-random` | 1964/2000 | 85.9% |

**这才是完整的结论**：

- **LRU 不是差，是有特定弱点**。稳定负载下它和 LFU 几乎一样好（1998/2000 vs 2000/2000）；但在"一次性灌入大量新 key"时会崩（15/2000）。
- **LFU 抗扫描污染能力强得多**（1921/2000 vs 15/2000），因为它看的是**历史访问频次**，而不是"最近一次访问时间"。新灌入的 key 频次还很低，不会挤掉老热点。
- **`allkeys-random` 在这种测试里反而"还行"**，是因为我的冷 key 也是随机访问的。真实业务如果有明显冷热区分，random 会明显更差。

**什么时候选 LFU 而不是 LRU**：

- 有定时任务、全表扫描、批量导入等"偶发大批量访问"的业务
- 热点相对稳定、不随时间剧烈变化的业务
- 反之，如果访问模式随时间快速变化（比如热点每小时都换），LRU 更合适，因为 LFU 的历史频次会"记住"过期的热点

### 3.5 LRU / LFU 的实现：都是近似算法

Redis **不维护全局的 LRU 链表**——那太耗内存。它用的是**抽样 + 候选池**：

```
淘汰时随机抽 maxmemory-samples 个 key（默认 5）
  → 与候选池（eviction pool，大小 16）中的条目比较
  → 选出"最该淘汰"的那个淘汰
```

候选池跨越多次淘汰保留候选，提高了近似精度。

#### 实测：samples 的影响

在**扫描式冲刷**场景下：

```
samples=1   → 热key存活 1827/2000，命中率 79.9%
samples=3   → 热key存活   93/2000，命中率 12.1%
samples=5   → 热key存活   25/2000，命中率  9.2%
samples=10  → 热key存活    2/2000，命中率  8.7%
samples=20  → 热key存活    0/2000，命中率  8.5%
samples=50  → 热key存活    0/2000，命中率  8.2%
```

**注意：这个结果和官方文档的说法相反，需要正确解读。**

官方文档说"samples=10 已非常接近真实 LRU"。那是针对**淘汰精度**而言——samples 越大，选出的淘汰对象越接近"真正最久未访问的"。

但在我这组测试里，samples 越大**热 key 存活越少**。原因是：这个场景的正确答案是"淘汰刚写入的冷 key、保留热 key"，而**真实 LRU 恰恰会做相反的事**（新写入的冷 key 是"最近使用"的，LRU 要保留它们、淘汰热 key）。所以 samples 越大越"忠实执行 LRU"，热 key 就死得越干净。

**关于 `samples=1` 那一行的异常（必须解释，否则会误读）**：

它存活了 1827/2000，看起来"效果最好"，但这**不是因为 LRU 更准**。补测数据揭示了真相：

| 策略 | samples | 冷 key 写入数 | 淘汰数 | 热 key 存活 |
|------|---------|--------------|--------|------------|
| `allkeys-lru` | 1 | **6909** | **1095** | 1768 |
| `allkeys-lru` | 2 | 18000 | 12374 | 171 |
| `allkeys-lru` | 5 | 18000 | 12303 | 502 |
| `allkeys-random` | 5 | 18000 | 12375 | 449 |

`samples=1` 时**只写入了 6909 个冷 key 就写不动了**（其余 11000 个写入失败），淘汰数也只有 1095，远低于其他组。原因是每次只抽样 1 个 key，**单次腾出的空间太少**，跟不上写入速度，于是大量 `SET` 直接返回 OOM 错误——冲刷根本没完成，热 key 自然剩得多。

所以 `samples=1` 不是"淘汰更准"，而是"**淘汰太慢导致写入提前失败**"。这在生产上是个明确的负面信号：写请求大面积报错。

**由此得出两点结论**：

1. samples 调大提高的是"**算法执行精度**"，**不是业务效果**。如果 LRU 这个模型本身不适合你的访问模式，调大 samples 只会让它错得更精确。
2. **samples 调得太小会拖垮写入吞吐**。默认值 5 是精度与 CPU 开销的平衡点，官方建议需要时调到 10，不建议再高；也不要低于默认值。

#### LFU 的实现：24 位字段的对数计数器

LRU 和 LFU 复用同一个 24 位字段（`redisObject.lru`）：

```
LRU 模式：24 位存"最后访问时间戳"（秒级，约 194 天回绕）
LFU 模式：高 16 位 = 最后衰减时间（分钟），低 8 位 = 频率计数器（0~255）
```

**LFU 计数器不是访问次数，是概率性对数计数器（Morris counter）**：

```
每次访问时：
  1. 生成 0~1 的随机数 R
  2. 概率 P = 1 / (当前值 × lfu-log-factor + 1)
  3. 只有 R < P 时，计数器 +1
```

官方 `redis.conf` 给出的对照表（factor=10 为默认）：

| factor | 100 次 | 1000 次 | 100K 次 | 1M 次 | 10M 次 |
|--------|--------|---------|---------|-------|--------|
| 0 | 104 | 255 | 255 | 255 | 255 |
| 1 | 18 | 49 | 255 | 255 | 255 |
| **10** | **10** | **18** | **142** | **255** | **255** |
| 100 | 8 | 11 | 49 | 143 | 255 |

**实测验证**（`OBJECT FREQ` 可直接查看）：

```
probe:hot  （访问 200 次）OBJECT FREQ = 10     ← 不是 200！
probe:cold （未访问）    OBJECT FREQ = 5       ← 新 key 初值 5，不是 0
相关配置：lfu-log-factor=10, lfu-decay-time=1
```

三个要点：

1. **FREQ 不是访问次数**。访问 200 次只得到 FREQ=10——这就是对数增长。
2. **新 key 初值是 5**（`LFU_INIT_VAL`），不是 0。这是为了让新 key 有机会累积访问，不至于刚写入就被淘汰。
3. **计数器会衰减**。`lfu-decay-time=1`（分钟）意味着 N 分钟没访问，计数器就减 N。这解决了"曾经的热点永远占着内存"的问题。

LRU 模式下可以用 `OBJECT IDLETIME` 看空闲秒数（实测访问过的 key 是 0 秒，未访问的是 1 秒）。

### 3.6 `volatile-*` 的致命陷阱（实测）

这是本课最该记住的一条**生产事故点**。

`volatile-*` 策略只在**设了 TTL 的 key** 中淘汰。如果**没有任何 key 设 TTL**，它就找不到可淘汰对象，于是**退化为 `noeviction`**。

**实测**：

```
--- 策略 volatile-lru，写入的 key 全部【不设 TTL】 ---
  写入成功 21059 次，失败 20 次
  报错: OOM command not allowed when used memory > 'maxmemory'.
  ❌ volatile-lru 找不到可淘汰的 key，等价于 noeviction，写入直接失败

--- 策略 allkeys-lru，写入的 key 全部【不设 TTL】 ---
  写入成功 200000 次，失败 0 次
  ✅ 淘汰正常，写入未受阻碍
```

官方文档也明确写了这一点：

> The volatile-xxx policies behave like noeviction if no keys have the expire field set to true.

**这意味着**：你选了 `volatile-lru`，以为"内存满了会淘汰"，但某个业务忘了设 TTL，结果就是**缓存层变成不可写**。而且这个故障是**渐进的**——一开始有 TTL 的 key 能淘汰，一切正常；等这些 key 都被淘汰完了，突然就写不进去了。

**怎么避免**：

- 选 `volatile-*` 就必须保证"**至少一部分 key 有 TTL**"，并加监控
- 监控 `evicted_keys` 与 `used_memory`，当内存接近 `maxmemory` 且 `evicted_keys` 停止增长时告警

### 3.7 淘汰策略怎么选

| 场景 | 推荐策略 | 理由 |
|------|---------|------|
| **纯缓存**（数据可从 DB 重建） | `allkeys-lru` | 默认首选，符合幂律分布 |
| 纯缓存 + 有批量扫描/定时任务 | `allkeys-lfu` | 抗扫描污染（实测 1921 vs 15） |
| 访问分布均匀（如循环扫描） | `allkeys-random` | LRU 的管理开销白花 |
| Redis 混存缓存 + 持久数据 | `volatile-lru` | 只给缓存 key 设 TTL，持久数据受保护 |
| 能预估哪些 key 该先走 | `volatile-ttl` | 用 TTL 长短表达优先级 |
| 数据绝对不能丢（如做存储用） | `noeviction` | 宁可写失败也不丢数据，但要做好容量规划 |

**官方文档的选型建议**（原文翻译）：

- 预期"少数元素被访问得远多于其他"→ `allkeys-lru`。**这是最常见的情况（帕累托法则），不确定时选它**
- 预期"所有 key 访问概率大致相等"（如循环扫描）→ `allkeys-random`
- 想用 TTL 给 Redis 提示"哪些该先淘汰"→ `volatile-ttl`

**两个补充要点**：

1. **设 TTL 是有内存成本的**。官方指出，`allkeys-lru` 比 `volatile-lru` 更省内存，因为它不需要 key 带 expire 信息。
2. **从库不主动淘汰**。从库的淘汰由主库的 DEL 命令同步驱动。所以从库也要配相同的 `maxmemory`，否则可能从库先 OOM。

### 3.8 内存相关的监控指标

| 指标 | 来源 | 含义 |
|------|------|------|
| `used_memory` | `INFO memory` | 实际使用内存 |
| `maxmemory` | `INFO memory` | 配置上限 |
| `mem_fragmentation_ratio` | `INFO memory` | 碎片率，> 1.5 需关注 |
| `evicted_keys` | `INFO stats` | 累计淘汰数，**持续增长说明内存不够** |
| `keyspace_hits` / `keyspace_misses` | `INFO stats` | 命中率 = hits/(hits+misses) |
| `expired_keys` | `INFO stats` | 累计过期删除数 |
| `mem_not_counted_for_evict` | `INFO memory` | 复制/AOF 缓冲区，**不计入 maxmemory** |

**命中率是最直观的健康指标**：

```
命中率 = keyspace_hits / (keyspace_hits + keyspace_misses) × 100%
```

一般要求 **> 50%**，缓存场景通常应 > 90%。命中率低且 `evicted_keys` 高，说明**缓存太小**，需要扩容而不是调策略。

**最后一条来自官方的建议**：如果用了复制或持久化，`maxmemory` 要**留出缓冲空间**给复制/AOF 缓冲区——这部分内存不计入 `maxmemory` 的比较。保守做法是系统可用内存比 `maxmemory` 多留 20%。

## 第五幕：体系收束

### 本课核心结论

**知识点 1：穿透 / 击穿 / 雪崩**

三者成因不同，必须分清：穿透是"数据根本不存在"（解法是拦住），击穿是"单个热点 key 过期"（解法是控制重建并发），雪崩是"大批 key 同时失效"（解法是打散 + 兜底）。缓存空值只挡得住重复 id，挡随机 id 攻击必须靠布隆过滤器——实测 2000 次随机攻击下，空值仍然穿透 1999 次，布隆只穿透 3 次（误判）。布隆过滤器的误差是有方向的：说"不存在"一定不存在（假阴性为 0），说"存在"可能有误判——这个方向性正是它能防穿透的原因。

**知识点 2：缓存与数据库一致性**

Cache Aside（先更新 DB，再删缓存）是事实标准。它仍有不一致窗口，但**会自愈**；反过来"先删缓存再更新 DB"窗口更长且**不自愈**（旧值会被回填）。延迟双删是兜底不是保证——实测 300 轮最终残留 0 次，但它依赖"回填早于第二次删除"和"第二次删除成功"两个假设。真正的兜底是 TTL（限定不一致时长）+ 删除重试 + binlog 订阅。删缓存优于更新缓存，因为删除没有"值"、不会乱序，且代价恒定。

**知识点 3：内存淘汰与过期策略**

过期删除（惰性 + 定期）与内存淘汰（8 种策略）是两套机制。定期删除是抽样式的、有 CPU 预算的，实测 10 万个 key 里 1000 个过期，5 秒只回收了 15 个——过期 key 会短暂占着内存，这是设计上的取舍。淘汰策略按"是否限定 TTL key"分三类，`volatile-*` 在**无 key 设 TTL 时会退化为 `noeviction`**，这是最常见的线上事故点之一。LRU 和 LFU 都是近似实现（抽样 + 候选池 / Morris 计数器）；LFU 抗扫描污染能力强得多（实测 1921 vs 15），但稳定负载下两者几乎无差异。

| 持久化 | 课 5 RDB / AOF | 持久化实例要预留复制缓冲区，不计入 maxmemory |
| 过期 | 课 2 key 设计与过期 | 本课展开过期删除的两条路径 |

**一个跨课的联动**：课 7 讲过哈希标签 `{}` 能把相关 key 钉在同一槽。本课的**互斥锁**如果用在集群里，锁 key 和业务 key 最好用哈希标签保证同槽，否则脚本化的"检查锁 + 删缓存"操作会触发 `CROSSSLOT`。

### 常见误区

1. **"缓存空值能防穿透"** —— 只能防重复 id。随机 id 攻击下实测仍穿透 1999/2000，还会留下一堆占位 key 占内存。

2. **"布隆过滤器有误差，所以不保险"** —— 它的误差是**单向**的：说"不存在"**一定**不存在（实测 500 个真实 id 零误拦）。误判只是让请求多查一次库，不是数据错误。

3. **"击穿就用互斥锁"** —— 秒杀级并发下，几万个线程阻塞在锁上比打 DB 更危险（线程池耗尽）。能接受旧数据的场景应该用逻辑过期。

4. **"延迟双删能保证一致"** —— 它依赖"回填早于第二次删除"这个假设。GC 停顿、网络抖动、DB 慢查询都会打破它。它是降低概率，不是保证。

5. **"`volatile-lru` 会自动淘汰"** —— 只在**有 key 设了 TTL** 时成立。没有 TTL key 时它等价于 `noeviction`，写请求会直接 OOM 报错（实测）。

6. **"LRU 比 LFU 差"** —— 只在批量冲刷场景成立（实测 15 vs 1921）。稳定负载下两者几乎一样（1998 vs 2000）。选型的依据是**你的访问模式**，不是谁更"高级"。

7. **"过期 key 到点就消失"** —— 实测关闭定期删除后，过期 key 会一直占着内存直到被访问。`KEYS` 也看不到它们（会跳过），所以容易误判内存没问题。

8. **"命中率高就说明缓存健康"** —— 还要看 `evicted_keys`。命中率低 + 淘汰数高 = 缓存太小，调策略没用，得扩容。

## 小测（5 题）

### Q1

某接口遭受攻击，攻击者用脚本持续请求大量**随机生成的、数据库里不存在**的商品 ID。团队已经上线了"缓存空值"方案（DB 查不到就缓存 `__NULL__`，TTL 60 秒）。关于这个方案的效果，下列说法正确的是？

A. 完全能防住，因为空值缓存会让后续请求命中缓存
B. 完全无效，因为空值缓存根本不生效
C. 只能防住"重复使用相同 ID"的攻击，对随机 ID 攻击几乎无效
D. 能防住，但会导致数据库被大量写入 `__NULL__` 记录

<details>
<summary>答案</summary>

**C**

缓存空值的工作方式是：第一次查询某个不存在的 id → 查 DB → 写占位 key。它的防护效果**依赖于"同一个 id 会被重复请求"**。

本课实测（2000 次随机不存在的 id）：

```
第 1 轮（2000 个不同 id）：DB 查询 1999 次  ← 几乎全部穿透
第 2 轮（重复打相同 id） ：DB 查询    0 次  ← 完全挡住
```

攻击者每次用**新的随机 id**，每个 id 都是第一次见，都会老老实实查一次 DB。而且这还会在 Redis 里留下一堆垃圾占位 key（实测缓存从 500 涨到 2499 个）。

- A 错误：把"重复 id 有效"当成了"普遍有效"。
- B 错误：说法太绝对。对重复 id 攻击它是有效的（实测 0 次穿透）。
- D 错误：`__NULL__` 写的是 Redis，不是数据库。数据库没有任何写入。

**正确做法**：随机 id 攻击要靠**布隆过滤器**（实测 2000 次攻击只穿透 3 次，且这 3 次是误判）。生产上通常是"参数校验 → 布隆过滤器 → 缓存空值"三层组合。
</details>

### Q2

关于 Redis 布隆过滤器（`BF.*`），下列说法**正确**的是？

A. 布隆过滤器说"不存在"时，有一定概率该元素其实存在
B. 布隆过滤器说"存在"时，该元素一定存在
C. 布隆过滤器不支持删除元素，因为删除会引入假阴性
D. 布隆过滤器的内存开销约为每个元素几十字节

<details>
<summary>答案</summary>

**C**

C 正确：多个元素共用 bit 位，删除某个元素会把其他元素依赖的位也清零，从而产生**假阴性**（把存在的说成不存在）。假阴性是布隆过滤器绝对不能接受的——这会让正常请求被误拦。需要删除能力时改用布谷过滤器（`CF.ADD` / `CF.EXISTS` / `CF.DEL`，本课实测均可用）。

- A 错误：**方向反了**。布隆过滤器说"不存在"是**100% 确定**的（假阴性为 0）。这是它能用于防穿透的根本原因。本课实测 500 个真实 id 被误拦 0 次。
- B 错误：说"存在"只是"**可能**存在"，存在误判率。本课实测声明 0.1% 的过滤器实测误判 0.056%。误判的后果只是多查一次库，可接受。
- D 错误：实测平均每 id 只有 **2.24 字节**（500 个 id 共 1120 字节），远小于"几十字节"。这正是它的核心价值——存 1 亿个 id 约 224 MB。
</details>

### Q3

某热点 key 在过期瞬间有大量并发请求。团队实测了两种方案：

```
无防护          ：DB 查询 114 次，瞬时并发 106
互斥锁 SET NX   ：DB 查询   1 次，199 个线程等待后重读
逻辑过期        ：DB 查询   1 次，199 个线程立刻返回旧值
```

关于这两种方案如何选型，下列说法正确的是？

A. 逻辑过期在所有场景下都优于互斥锁，因为它不阻塞线程、耗时更短
B. 互斥锁在所有场景下都优于逻辑过期，因为它保证拿到的是最新值
C. 选型的关键依据是"业务能否接受短暂返回旧数据"：能接受用逻辑过期，不能接受用互斥锁
D. 两种方案都无法降低数据库压力，必须靠布隆过滤器前置拦截

<details>
<summary>答案</summary>

**C**

两种方案的 DB 压力完全一样（都是 1 次查询），**差别不在性能，而在未命中线程拿到什么**：

- 互斥锁：未抢到锁的线程**等待**，直到缓存重建完成后读到新值 → 数据一定是最新的
- 逻辑过期：未抢到锁的线程**立刻返回旧值**，不阻塞 → 数据可能短暂陈旧

所以选型只看一件事：**这个业务能不能接受"短暂返回旧数据"**。

- 能接受（商品详情、新闻、排行榜、配置）→ **逻辑过期**，性能更好且不阻塞线程
- 不能接受（库存、余额、限量资格）→ **互斥锁**，宁可让请求等，也不能返回错的数

- A 错误：逻辑过期返回的是**旧值**。对库存而言返回旧值意味着超卖，是业务错误，不是"更优"。
- B 错误：互斥锁让大量线程阻塞等待。在数万并发的场景下，线程阻塞可能耗尽线程池导致整个服务不可用——代价并不总是比"慢一点"小。
- D 错误：两种方案都实测把 DB 查询从 114 次降到 1 次，效果是确凿的。布隆过滤器治的是**穿透**（数据不存在），这里的数据在 DB 里真实存在，过滤器会全部放行，完全不起作用。

**注意**：A 和 B 的错误是同一个——都在找"哪个方案更好"，而正确答案取决于**业务对陈旧数据的容忍度**。这也是本课反复强调的立场：缓存设计里很少有普适的最优解，只有"在你的约束下最合适"的解。
</details>

### Q4

关于"先更新数据库再删缓存"与"先删缓存再更新数据库"，下列说法正确的是？

A. 前者完全不会有不一致问题，后者才会
B. 后者更好，因为先删缓存能保证下次一定读到新值
C. 前者更好，因为它会自愈；后者可能把旧值回填进缓存且不自愈
D. 两种等价，随便选一个

<details>
<summary>答案</summary>

**C**

**先更新 DB 再删缓存**（推荐）的不一致窗口：

```
  writer  DB=v2
  reader  read=v1        ← 读到旧值
  writer  DEL cache
```

窗口只有"更新 DB"到"删除缓存"之间，**毫秒级**。而且**会自愈**——缓存删除后，下一次读会回填 v2。

**先删缓存再更新 DB** 的不一致窗口：

```
  writer  DEL cache
  reader  read DB=v1     ← DB 还没更新
  reader  回填 cache=v1  ← 旧值被写回缓存！
  writer  DB=v2

最终: DB=v2, 缓存=v1  ❌
```

窗口长度等于 DB 更新的耗时，且**不会自愈**——缓存停在 v1，要等 TTL 到期或下次写操作。

- A 错误：前者也有窗口，只是更短且能自愈。没有任何方案"完全没有"不一致窗口。
- B 错误：恰恰相反。先删缓存时，并发读会在 DB 更新前把**旧值**回填进缓存。
- D 错误：两者后果不同（一个自愈、一个不自愈），不能随便选。
</details>

### Q5

某服务使用 `maxmemory-policy volatile-lru`，运行几个月后突然大面积报 `OOM command not allowed when used memory > 'maxmemory'.`。排查发现**写入的 key 都没有设置 TTL**。最可能的原因是？

A. `maxmemory` 设置得太小，需要调大
B. `volatile-lru` 只在设了 TTL 的 key 中淘汰，无 TTL key 时退化为 `noeviction`
C. Redis 的 LRU 算法有 bug，无法识别热点数据
D. 内存碎片率过高，触发了保护机制

<details>
<summary>答案</summary>

**B**

`volatile-*` 系列策略（volatile-lru / volatile-lfu / volatile-random / volatile-ttl）只在**设置了过期时间的 key** 中挑选淘汰对象。当**没有任何 key 带 TTL** 时，它找不到可淘汰对象，行为就等价于 `noeviction`——写命令直接报 OOM。

本课实测：

```
--- 策略 volatile-lru，写入的 key 全部【不设 TTL】 ---
  写入成功 21059 次，失败 20 次
  报错: OOM command not allowed when used memory > 'maxmemory'.

--- 策略 allkeys-lru，写入的 key 全部【不设 TTL】 ---
  写入成功 200000 次，失败 0 次
```

官方文档也是这么写的：

> The volatile-xxx policies behave like noeviction if no keys have the expire field set to true.

**为什么是"运行几个月后突然发生"**：这个故障是渐进的。早期可能有一部分 key 带 TTL，淘汰正常；等这些带 TTL 的 key 被淘汰完了，就突然写不进去了。

- A 错误：调大 `maxmemory` 只是推迟问题，根因是策略选错。而且如果这是缓存场景，正确做法是改用 `allkeys-lru`。
- C 错误：LRU 没问题，它压根没机会执行——没有符合"带 TTL"这个前提的候选 key。
- D 错误：碎片率高会影响内存利用率，但不会导致 `volatile-lru` 无法淘汰。碎片问题要看 `mem_fragmentation_ratio`。

**修复**：改用 `allkeys-lru`（缓存场景），或确保所有可淘汰的 key 都设置了 TTL。
</details>
