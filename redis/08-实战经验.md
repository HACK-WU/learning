## 🚫 适用边界与反模式

### 什么时候不该用 Redis

> "不该用"比"怎么用"更值钱——这是从"会用"到"用对"的分界线。

| 场景 | 为什么不适合 | 该用什么替代 |
|------|-------------|-------------|
| **需要按任意字段筛选/聚合查询** | Redis 只有 key 一种索引。按字段筛选只能全量取回在客户端过滤 | PostgreSQL / MySQL / Elasticsearch |
| **数据量超过内存容量** | Redis 是内存数据库，超出即淘汰或拒绝写入（课 8 已实测 noeviction 下写入失败 13 万次） | 分库分表的数据库，或 Redis 只存热数据子集 |
| **强一致、不能丢的账务数据** | 主从复制是异步的，主库宕机瞬间未同步的写入永久丢失（课 6） | 关系型数据库 + 事务 |
| **需要复杂事务与回滚** | Redis 事务无隔离级别、无回滚（课 7 集群下更受限） | 数据库事务 |
| **超大规模冷数据归档** | 内存成本远高于磁盘，冷数据放内存是浪费 | 对象存储 / 数据湖 |
| **多 key 强关联的紧密事务** | 集群模式下多 key 必须同槽，业务受限（课 7） | 单实例 Redis（若数据量允许）或数据库 |

> 📌 一个可量化的判据（阶段 4 课 9 实测）：当你需要"按某个字段筛选"时，如果用 Redis 原生命令做，
> 就只能全量取回在客户端过滤——**10 万条订单里找 `amount > 9000`，命中 9990 条（9.99%），
> 命中率 10% 却要传输 100% 的数据**（耗时 0.26 s，而走索引的数据库是毫秒级）。
> 结论不是"命中率低"，而是**传输量与命中率严重不成比例**：你要为 10% 的有效数据付 100% 的传输成本。

### 高频反模式（能跑，但迟早出事）

1. **用 `KEYS` 做前缀统计**：数据量小的时候秒回，上千万 key 时会让 Redis 阻塞数秒到数十秒，期间所有请求排队。
   → 用 `SCAN`，或更好——**用 ACL 禁用 KEYS**，从源头杜绝。
2. **`maxmemory` 不设或用 `noeviction`**：默认无上限，会一直用到 OOM 被系统杀掉；设了 `noeviction` 则内存满后拒绝所有写入。
   → 必须设 `maxmemory` + 匹配业务的淘汰策略（缓存用 `allkeys-lru`）。
3. **把缓存当数据库用，不开持久化**：Redis 重启后数据全空，缓存雪崩直接打到数据库。
   → 纯缓存场景可以不开持久化，但**必须接受冷启动回源**并做预热；当数据库用则必须开 AOF。
4. **大 key 用 `DEL` 直接删**：删除百万元素的集合会让主线程阻塞数百毫秒。
   → 用 `UNLINK`（异步删除）。本课实测：删大 key 阻塞其他请求 **113.66ms**，同样数据量的小 key 只阻塞 **0.61ms**（185.7 倍差距）。
5. **多线程共用一个 Redis 连接**：RESP 是请求-响应严格配对的流式协议，并发共用一个 socket 会让响应串位。
   → 用连接池（`redis-py`、Lettuce 等自带）。
6. **TTL 全部设成同一个值**：会在同一秒集体失效，引发雪崩。
   → 加随机抖动（本项目 `cache_layer.py` 用 0~120 秒抖动）。
7. **`SCAN` 的游标不解码直接比较**：游标返回是 `bytes`（`b'0'`），写 `if cur == 0` 永远不成立，导致死循环。
   → 本项目实测踩坑：一次全量扫描触发 **566 万次** SCAN 调用，诊断工具反而把实例压垮了。

## 🔥 高频故障模式

> 每条固定五段式：症状 → 根因 → 排查路径 → 修复 → 预防。
> **症状必须可观测**。

### 故障模式 1：KEYS 命令阻塞引发全链路雪崩

- **症状（可观测）**：P99 延迟从 5ms 瞬间涨到数秒；`instantaneous_ops_per_sec` 骤降但 `connected_clients` 很高（典型阻塞特征）；`SLOWLOG` 里出现 `KEYS` 且耗时数百毫秒以上。
- **根因**：Redis 命令执行是单线程的。`KEYS` 是 O(N) 全量遍历且**原子阻塞**，执行期间不处理任何其他命令。缓存不可用后请求全部穿透到数据库，数据库连接池耗尽，进而雪崩。
- **排查路径**：
  1. `SLOWLOG GET 10` — 看是否有 KEYS 及耗时
  2. `INFO commandstats` — 看 `cmdstat_keys` 的 calls 与 `usec_per_call`
  3. `CLIENT LIST` — 找 `cmd=KEYS` 且 `idle=0` 的连接，定位是谁发的
- **修复**：`CLIENT KILL` 掉该连接；业务代码把 `KEYS` 全替换为 `SCAN`；已雪崩则先对数据库限流。
- **预防**：用 ACL 禁用 KEYS（本项目 appuser 已禁用，实测执行返回 `NOPERM`）；生产环境禁止 `MONITOR` 常开。

> 对应速查条目：[09-排障速查手册.md · 症状 1](09-排障速查手册.md)

- **来源**：[百度智能云 · Redis KEYS 命令引发的数据库灾难复盘](https://cloud.baidu.com/article/4115610)（核查于 2026-09，链接可达性已验证）

### 故障模式 2：写入被拒 `OOM command not allowed when used memory > 'maxmemory'`

- **症状（可观测）**：应用大量写入报错 `OOM command not allowed when used memory > 'maxmemory'`；`INFO stats` 里 `evicted_keys=0`；内存达到 `maxmemory` 上限。
- **根因**：`maxmemory-policy` 设为 `noeviction`（或内存已满但无可淘汰 key，如 `volatile-lru` 下所有 key 都没设 TTL）。此时 Redis 不淘汰任何 key，直接拒绝所有需要新内存的写入。
- **排查路径**：
  1. `INFO memory` — 看 `used_memory` / `maxmemory` / `maxmemory_policy`
  2. `INFO stats` — `evicted_keys` 为 0 说明淘汰没生效
  3. `redis-cli --bigkeys` 或 `MEMORY USAGE <key>` — 找占内存的大头
  4. `OBJECT ENCODING <key>` — 看是否发生编码转换（如 listpack → skiplist，内存跳变）
- **修复**：`CONFIG SET maxmemory-policy allkeys-lru` 立即恢复写入；再清理异常数据。
- **预防**：缓存场景不要用 `noeviction`；对 ZSet/Hash/Set 建立单 key 大小巡检（编码转换会让内存产生数量级跳变，实测 ZSet 跨 128 阈值时达 6.87 倍）。

> 对应速查条目：[09-排障速查手册.md · 症状 2](09-排障速查手册.md)

### 故障模式 3：大 key 删除造成周期性卡顿

- **症状（可观测）**：每隔一段时间出现一次全局延迟尖刺；`LATENCY LATEST` 里有 `command` 事件；尖刺期间所有命令变慢，而非单个命令慢。
- **根因**：`DEL` 一个大集合（百万元素的 Hash/Set/ZSet）是同步操作，释放内存的过程阻塞主线程。数据量越大阻塞越久。
- **排查路径**：
  1. `LATENCY LATEST` / `LATENCY HISTORY command` — 确认延迟尖刺
  2. `redis-cli --bigkeys` — 找出大 key
  3. `MEMORY USAGE <key>` — 精确测量
- **修复**：改用 `UNLINK`（异步删除）；HLL/ZSet 用 `ZREMRANGEBYRANK` 分批处理。
- **预防**：**写入时就避免大 key**——拆分（本项目把排行榜按商品维度存，避免单 key 膨胀）；删除统一用 `UNLINK`。

> 本课实测（Redis 8.10.1，20 核）：删一个 100 万字段的 Hash，其他客户端被阻塞 **113.66ms**；同样数据拆成 1000 个小 Hash 后只阻塞 **0.61ms**；用 `UNLINK` 则降到 **0.45ms**。

> 对应速查条目：[09-排障速查手册.md · 症状 3](09-排障速查手册.md)

### 故障模式 4：慢查询日志为空，但用户反馈很慢

- **症状（可观测）**：`SLOWLOG GET` 返回空，但应用侧 P99 很高；客户端测得的耗时远大于 SLOWLOG 记录值。
- **根因**：**SLOWLOG 只记录命令在 Redis 内的执行耗时，不含网络传输、客户端排队、连接池等待**。课 9 实测：`HGETALL` 在 SLOWLOG 里只记 **36.6ms**（原始值 36633 us），客户端却等了 **1501ms**（差约 40 倍）——差异全在传输与排队。
- **排查路径**：
  1. `SLOWLOG GET` 为空 → 排除命令本身慢
  2. 查网络：`ping` / 连接池等待时间 / 客户端到 Redis 的 RTT
  3. 查大 value：命令执行快但返回数据量大，`INFO` 的 `instantaneous_output_kbps` 会很高
  4. 查客户端：是否 GC 停顿、是否连接池耗尽
- **修复**：按实际瓶颈处理——大 value 拆小或分页；连接池扩容；跨机房则考虑就近部署。
- **预防**：不要只依赖 SLOWLOG 判断健康度；同时监控 `LATENCY`（含网络视角）与客户端侧埋点。

> 对应速查条目：[09-排障速查手册.md · 症状 4](09-排障速查手册.md)

### 故障模式 5：缓存与数据库长期不一致

- **症状（可观测）**：数据库已更新，但接口持续返回旧值，且**一直持续到 key 自然过期才恢复**。
- **根因**：更新时只改了数据库没删缓存；或用了"更新缓存"而非"删除缓存"，并发下写脏。本项目第三幕实测：数据库已改为 888，缓存仍返回 999。
- **排查路径**：
  1. 直接对比：`GET` 缓存值 vs 数据库值
  2. 查代码更新路径：是"删缓存"还是"更新缓存"
  3. 查删除是否失败：删缓存的网络异常有没有被吞掉
- **修复**：更新数据库后**必须删缓存**（不是更新）；删除失败要有补偿（重试或消息队列）。
- **预防**：`update_good()` 这类函数里，删缓存失败要显式报错而非静默；关键业务可加延迟双删。

> 对应速查条目：[09-排障速查手册.md · 症状 5](09-排障速查手册.md)

### 故障模式 6：缓存雪崩——同一时刻大量 key 集体失效

- **症状（可观测）**：某个整点时刻，数据库 QPS 突然暴涨数十倍，接口大面积超时；Redis 命中率断崖式下跌。
- **根因**：大量 key 用相同的 TTL（如都是"预热时设为 5 分钟"），在同一秒集体过期，全部请求同时回源。
- **排查路径**：
  1. 抽样看一批同类 key 的 `TTL` — 如果值几乎相同就是病因
  2. 看数据库 QPS 曲线是否与失效时刻吻合
- **修复**：紧急时可在应用层限流；长期必须给 TTL 加随机抖动。
- **预防**：`TTL = base + random(0, jitter)`。本项目 `cache_layer.py` 用 `BASE_TTL=300 + random(0,120)`，
  主程序第二幕会抽查 20 个 key 打印「最小 / 最大 / 跨度」，实测跨度在 100 秒量级（抖动上限 120 秒，具体数值每次运行不同）。

> 对应速查条目：[09-排障速查手册.md · 症状 6](09-排障速查手册.md)

### 故障模式 7：关闭 default 用户后从库连不上

- **症状（可观测）**：从库日志持续刷 `MASTER aborted replication with an error: NOPERM User xxx has no permissions to run the 'psync' command`；`master_link_status:down`。
- **根因**：ACL 安全加固时关闭了 `default` 用户，但复制所需的 `psync` / `replconf` 命令没有授权给任何账号。应用账号不应该有这些权限，需要单独建复制账号。
- **排查路径**：
  1. `tail -f` 从库日志，看 NOPERM 的具体命令名
  2. `ACL LIST` / `ACL GETUSER <user>` 确认权限
- **修复**：`ACL SETUSER replicator on '>密码' ~* +psync +replconf +ping +info`，从库 `CONFIG SET masteruser replicator`。
- **预防**：**先建账号、再关 default**——顺序反了就只能重启（本项目实测踩坑：关门后无法在线建号）。

> 对应速查条目：[09-排障速查手册.md · 症状 7](09-排障速查手册.md)

---

### 故障模式 8：`-@dangerous` 收紧后运维命令全废

- **症状（可观测）**：加固后 `INFO` / `MEMORY USAGE` / `SLOWLOG` / `OBJECT` 全部返回 `NOPERM`，出问题什么都不了。
- **根因**：`INFO` 等运维只读命令也属于 `@dangerous` 类别，一刀切 `-@dangerous` 会把可观测能力一起禁掉。本项目实测踩坑。
- **排查路径**：`ACL GETUSER appuser` 看 commands 字段；执行 `INFO` 看报错。
- **修复**：收紧后**显式加回**运维只读命令：
  `+INFO +CONFIG +CLIENT +MEMORY +SLOWLOG +LATENCY +OBJECT +SCAN +TTL +TYPE +DBSIZE`
- **预防**：最小权限 ≠ 一刀切。安全基线应保证"可观测性不被削弱"。

> 对应速查条目：[09-排障速查手册.md · 症状 8](09-排障速查手册.md)

### 故障模式 9：秒杀超卖

- **症状（可观测）**：库存变成负数；成功下单数 > 实际库存；账目对不平。
- **根因**：把"读库存 → 判断 → 扣减"拆成三步在应用层做，高并发下多个请求读到同一个库存值，都判定"够"，各扣一次。
- **排查路径**：
  1. 查代码是否是三步走而非 Lua
  2. 压测：并发数远大于库存，看 `下单成功数 + 剩余库存` 是否等于初始库存
- **修复**：用 Lua 把「判断 + 扣减」合成一个原子操作。
- **预防**：**接口设计也要注意**——本项目实测踩坑：初版 Lua 用返回值 `0` 同时表示"扣完剩 0"和"库存不足"，
  两种业务含义完全不同（要发券 vs 要提示售罄）却无法区分，一度导致误判为超卖。
  正确做法是用负数区分失败原因（`>=0` 成功、`-2` 库存不足、`-3` 已购买）。

> 对应速查条目：[09-排障速查手册.md · 症状 9](09-排障速查手册.md)

## ✅ 落地 Checklist

> 投产 / 上线前逐项打勾。

**内存与淘汰**

- [ ] 已设 `maxmemory`（默认无上限，会用到 OOM 被系统杀掉）
- [ ] 已设匹配的 `maxmemory-policy`（缓存用 `allkeys-lru`；不要长期用 `noeviction`）
- [ ] 已对 ZSet / Hash / Set 做过单 key 大小巡检（编码转换会让内存产生数量级跳变）

**持久化与高可用**

- [ ] 明确了这个实例是"缓存"还是"数据库"，并据此决定开不开持久化
- [ ] 若开 AOF，`appendfsync` 策略与可接受的丢失窗口已对齐
- [ ] 主从复制链路健康（`master_link_status:up`），且复制账号权限已配置
- [ ] 已想清楚"主库宕机瞬间会丢多少数据"

**安全**

- [ ] `default` 用户已关闭或设了强密码（出厂默认是 `nopass + @all`）
- [ ] 已按角色建账号（应用 / 只读 / 复制），且**先建号再关 default**
- [ ] `KEYS` / `FLUSHALL` / `FLUSHDB` / `DEBUG` / `SHUTDOWN` 已对应用账号禁用
- [ ] 收紧后已**加回** INFO / CONFIG / MEMORY / SLOWLOG 等运维只读命令
- [ ] 实例不直接暴露公网（绑定内网 IP + 防火墙）
- [ ] ACL 已 `ACL SAVE` 持久化

**可观测性**

- [ ] `slowlog-log-slower-than` 已调到生产可用值（建议 1ms 级）
- [ ] `latency-monitor-threshold > 0`（**出厂默认是 0，即关闭**）
- [ ] 已配置内存、命中率、连接数、主从延迟的告警

**缓存设计**

- [ ] 有穿透防护（空值缓存 / 布隆过滤器）
- [ ] 有击穿防护（互斥锁 / 逻辑过期）
- [ ] 有雪崩防护（TTL 随机抖动）
- [ ] 更新路径是"先更库、再**删**缓存"，且删除失败有补偿
- [ ] 有大促前的缓存预热方案

**上线预案**

- [ ] 回滚预案已就绪（改配置前先记下原值）
- [ ] 已知晓哪些命令不能在线执行（含 `KEYS`、大 key `DEL`）
- [ ] ⚠️ 明确：**不要**在生产环境执行 `SHUTDOWN` / `DEBUG SLEEP` / `MONITOR` 常开

## 📰 真实事故案例复盘

### 案例 1：生产执行 KEYS 引发数据库雪崩

- **经过**：运维为清理过期会话数据，在生产 Redis 执行 `KEYS user_session_*` 做统计。实例承载 200 万+ key，主线程阻塞 12 秒。
- **根因**：`KEYS` 是 O(N) 且原子阻塞的命令，执行期间 Redis 不响应任何请求；缓存命中率归零后请求全部穿透到数据库。
- **损失**：数据库 QPS 从 5000 飙至 15 万，连接池打满，两次宕机（分别持续 3 分 27 秒与 11 分 15 秒），恢复后性能下降 60%。
- **教训**：一个"只是想看看有多少 key"的操作，代价是全站不可用。**正确做法是用 ACL 从权限层面禁用 KEYS**——靠人记住不执行是不可靠的。
- **来源**：[百度智能云 · Redis KEYS 命令引发的数据库灾难复盘](https://cloud.baidu.com/article/4115610)（核查于 2026-09）

### 案例 2：别的应用误连 Redis 疯狂执行 KEYS

- **经过**：周一上午页面加载极慢，Redis CPU 100%，QPS 从 1000 涨到 6000，连接数从 0 涨到 3000。
- **根因**：`SLOWLOG GET 10` 显示排前十的慢命令全是 `keys *`，但本应用并未暴露该接口——排查后发现是**另一个应用配置错误，指向了这个 Redis 实例**并做数据爬取。
- **损失**：服务响应时间严重劣化，临时方案是另租实例 + 改配置重启。
- **教训**：① `INFO commandstats` 里出现非零的 `cmdstat_keys` 就是红线告警；② 实例间要有隔离与鉴权，否则"被别人连错"无从防御。
