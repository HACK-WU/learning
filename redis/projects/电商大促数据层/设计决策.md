# 设计决策 · 电商大促数据层

> 每个决策点必须**真有争议**——换个人来可能选另一个方案，且也有道理。

## 决策 1：缓存更新用 Cache Aside，还是 Write Through / Write Behind？

**候选方案**

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| A · **Cache Aside**（旁路缓存） | 读时未命中才回源写入；更新时**删缓存**而非更新缓存 | 实现简单；只有被真正访问的数据才进缓存，内存利用率高；缓存挂了不影响写入 | 首次读必然 miss；删缓存后到下次读取之间有一致性窗口 |
| B · Write Through（写穿） | 更新时同时写库和缓存，都由应用保证成功 | 缓存命中率高，写入后立即可见 | 每次写两个存储，写延迟叠加；大量冷数据也会进缓存，浪费内存 |
| C · Write Behind（写回） | 只写缓存，异步批量刷回数据库 | 写性能极高 | 缓存宕机就丢数据；实现复杂，要处理失败重放 |

**最终选择**：A · Cache Aside

**选择理由**：
本项目的读多写少场景（商品详情被读成千上万次，改价一天几次）正是 Cache Aside 的主场。写穿会让每次改价都多一次 Redis 写且把冷数据塞进内存；写回则引入数据丢失风险，对库存和价格这类数据不可接受。

**为此付出的代价**：
1. 缓存删除后、下次读取前存在不一致窗口（本项目第三幕演示了这个窗口有多危险）
2. 首次访问必然回源，冷启动瞬间数据库压力大 —— 所以配套做了 `warmup()` 预热
3. 删缓存失败会导致长期脏数据，必须在代码里处理这个失败分支（见 `update_good()` 的补偿逻辑）

**什么时候该改选另一个**：
- 数据写完立刻会被高频读，且能接受写延迟 → 选 B（如用户会话）
- 写入量极大、能容忍秒级丢失 → 选 C（如点赞计数、浏览数）

## 决策 2：更新时"删缓存"还是"更新缓存"？

这个决策常被当成 Cache Aside 的细节，但它是独立的权衡点，且**答案反直觉**。

**候选方案**

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| A · **删除缓存** | `UPDATE db; DEL cache_key;` | 不会写脏；下次读自然回源 | 下一次读要回源，有一次额外开销 |
| B · 更新缓存 | `UPDATE db; SET cache_key new_value;` | 下次读直接命中，无回源 | **并发写时会写脏** |

**最终选择**：A · 删除缓存

**选择理由**：
更新缓存在并发下会产生经典的脏数据时序——

```
线程 A：UPDATE db (price=100)  ────────────────► SET cache price=100
线程 B：      UPDATE db (price=200) ──► SET cache price=200
最终：数据库 price=100（B 后写覆盖了？）  实际取决于交织顺序
```

只要两个更新线程的交织顺序与数据库提交顺序不一致，缓存里就会留下旧值，**且这个旧值会一直存在到 key 自然过期**。删除缓存则没有这个问题：删了就是没了，下次读一定拿数据库的最新值。

**为此付出的代价**：
每次更新后紧接着的那次读要回源（多一次数据库查询）。对改价这类低频操作完全可接受。

**什么时候该改选另一个**：
几乎不应该。除非你的更新是单线程的、或者你用了分布式锁把同一 key 的更新串行化——但那时复杂度已经超过收益了。

> 📌 本项目第三幕用实测演示了这个差异：只改库不删缓存，缓存持续返回旧值 999，而数据库已是 888。

## 决策 3：Lua 脚本的返回值怎么设计？

这是本轮**实测踩坑**得来的决策，最容易被忽略。

**候选方案**

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| A · 用 `0` 表示"库存不足" | `if stock <= 0 then return 0 end` | 直觉、简洁 | **返回值有歧义**：扣减成功且扣完剩 0，也返回 0 |
| B · **用负数区分失败原因** | 成功返回剩余（≥0），`-1` key 不存在，`-2` 库存不足，`-3` 已购买 | 调用方能精确区分业务分支 | 返回值语义需要写进文档 |

**最终选择**：B · 用负数区分失败原因

**选择理由**：
方案 A 的 `0` 有两种完全不同的业务含义：

- 「你抢到了，而且是最后一个」→ 应该给用户发券、创建订单
- 「你来晚了，早就卖完了」→ 应该提示已售罄

两者后续处理完全不同，返回值却一样，调用方无从判断。本项目实测中就因为这个歧义，把统计口径搞错了——一度误判成"超卖"，实际上 Lua 的原子性完全正确（返回值是 19,18,17…1,0 每个只出现一次，证明没有任何两次扣减看到同一个库存值）。

**为此付出的代价**：
返回值语义变复杂，必须写进注释和文档；调用方要判断多个负数值。

**什么时候该改选另一个**：
如果你的业务里"扣到 0"和"本来就 0"的处理完全一样（比如只展示一个数字），方案 A 够用。但只要涉及订单创建、发券这类有副作用的动作，就必须区分。

## 决策 4：多线程压测时，共用连接还是每线程独立连接？

同样是本轮**实测踩坑**。

**候选方案**

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| A · 所有线程共用一个连接 | 全局一个 `Redis` 对象，多线程直接调用 | 省连接、代码简单 | **RESP 协议下响应会串位** |
| B · **每线程独立连接** | 每个线程 `conn_master()` 建自己的连接 | 线程安全，响应不会串 | 连接数随线程数增长 |
| C · 用连接池 | 池化管理，每次从池里借 | 兼顾安全与开销 | 要引入额外依赖（本项目纯标准库，故未采用） |

**最终选择**：B · 每线程独立连接（生产上应选 C）

**选择理由**：
RESP 是「请求-响应严格配对」的流式协议——一个 socket 在同一时刻只能承载一个未完成的请求-响应对。多个线程并发往同一个 socket 写命令，响应返回时不带标识，谁先读谁就拿走，**A 线程可能读到 B 线程的返回值**。本项目第一版就用了共用连接，导致库存统计出现"成功 200 且失败 101"这种总数超过线程数的荒谬结果。

**为此付出的代价**：
500 线程就是 500 个 TCP 连接，仅适合压测场景。真实服务必须用连接池（`redis-py` 自带，或 Java 的 Lettuce/Jedis），本项目受限于纯标准库未实现。

**什么时候该改选另一个**：
- 单线程应用 → 共用连接没问题
- 生产服务 → 必须用连接池（方案 C），不要自己造轮子

## 决策 5：ACL 收紧到什么程度？

**候选方案**

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| A · 只设密码 | `requirepass` 或给 default 加密码 | 改动最小，一劳永逸 | 一把钥匙开所有门，任何泄露都是全量泄露；无法按人授权 |
| B · **分角色最小权限** | default off + appuser / readonly / replicator 三个角色 | 权限边界清晰，泄露影响可控 | 配置复杂，且**容易过度收紧把自己锁在外面** |
| C · 最小权限 + 完全禁 dangerous | 在 B 基础上 `-@dangerous` 且不回补 | 最严格 | **运维命令全被禁，出问题什么都查不了** |

**最终选择**：B · 分角色最小权限（并在 B 内部做了回补）

**选择理由**：
本轮实测踩了两个坑，正好说明 B 与 C 的边界在哪：

1. **坑一：关掉 default 后从库连不上**。日志里是 `NOPERM User appuser has no permissions to run the 'psync' command`——复制需要 `psync`/`replconf`，应用账号不该有这些。解法是单独建 `replicator` 角色。这印证了"分角色"的必要性：一个账号承担不了所有职责。
2. **坑二：`-@dangerous` 把 INFO 也禁了**。实测 `INFO` 属于 dangerous 类别，一刀切之后诊断层完全瘫痪，`MEMORY USAGE` / `SLOWLOG` / `OBJECT` 全部 NOPERM。解法是收紧后**显式加回运维只读命令**：`+INFO +CONFIG +CLIENT +MEMORY +SLOWLOG +LATENCY +OBJECT +SCAN +TTL +TYPE +DBSIZE`。

最终的权限基线是：**默认拒绝 + 按角色授权 + 运维必需命令显式加回**。

**为此付出的代价**：
1. 配置复杂度显著上升，一个角色配错就会打断业务（坑一就是实例）
2. 必须先建账号再关 default——顺序反了就"把钥匙锁在屋里"，只能重启
3. 运维命令加回后仍有残留风险，需要定期审计 `ACL LIST`

**什么时候该改选另一个**：
- 内部系统、单人维护、无合规要求 → 方案 A 够用，别为了严谨牺牲效率
- 有安全审计要求、多团队共用 → 必须 B，且要配 `ACL SAVE` 持久化
- 方案 C 不建议在任何生产环境使用：可观测性归零等于故障时用盲飞

## 决策 6：用哪个 Redis？

这是"决策参考"目标的核心决策，也是本轮唯一需要联网核实的决策点。

**候选方案**

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| A · **Redis 8 官方版**（本项目选择） | 用 `packages.redis.io` 官方源的 Redis 8.10.1 | 功能最全（内置 JSON / 搜索 / 时间序列等模块）；AGPLv3 是 OSI 认证的自由软件许可 | 8.0+ 采用三许可（RSALv2 / SSPLv1 / AGPLv3），对部分企业的法务审查构成负担 |
| B · Valkey（Linux 基金会） | 用 2024 年从 Redis 7.2.4 分叉的 Valkey（现 9.x） | 保持 BSD 许可，无任何使用限制；社区治理，厂商中立 | 分叉时间较短，生态与托管服务覆盖仍在追赶；部分 Redis 8 新特性不同步 |
| C · 云厂商托管版 | 用云 Redis / 云 Valkey 服务 | 免运维，自带高可用与备份 | 成本显著高于自建；被单一云厂商绑定；部分高级命令受限 |

**最终选择**：A · Redis 8 官方版

**选择理由**：
1. 这是**学习项目**，目标是覆盖最完整的功能面，Redis 8 内置的模块生态（本项目虽未用，但课 9 已实测 RediSearch 能力）能让学习路径不中断
2. 三许可中的 **AGPLv3 是 OSI 认证的自由软件许可**——对绝大多数自用场景（不对外提供 Redis 作为服务）没有实质约束
3. 本机官方源直接可装，无需编译

**为此付出的代价**：
1. 若未来要把本项目商业化封装成"Redis 托管服务"对外售卖，RSALv2 / SSPLv1 会构成实质限制，届时必须切换到 AGPLv3 条款或改用 Valkey
2. 企业法务审查时，"SSPL"这个标签本身就会引发额外沟通成本

**什么时候该改选另一个**：
- 你的公司把 Redis 作为**服务对外提供**（如云厂商、PaaS 平台）→ 必须选 B（Valkey，BSD 无限制）
- 你们法务对 SSPL 类许可一律否决 → 选 B
- 没有专职运维、且预算允许 → 选 C，把精力放在业务上
- 只需简单 KV 缓存、且是多线程纯缓存场景 → 也可评估 Memcached / Dragonfly

> 📌 **许可证事实核查（联网核查于 2026-09）**
>
> | 时间 | 版本 | 许可证 | 是否 OSI 开源 |
> |------|------|--------|:------------:|
> | 2009 – 2024.03 | ≤ **7.2.4** | BSD 3-Clause | ✅ 是（**7.2.4 是最后一个 BSD 版本**） |
> | 2024.03 – 2025.05 | 7.4 ~ 7.8 | RSALv2 或 SSPLv1 | ❌ source-available |
> | 2025.05 起 | **8.0+** | RSALv2 / SSPLv1 / **AGPLv3** 三选一 | ✅ 走 AGPLv3 则是 |
>
> - **AGPLv3 的实际约束比直觉窄**：运行**未修改**的 Redis 不触发 copyleft；只有「修改后作为网络服务对外提供」才需要公开被修改部分的源码。所以**自用场景选 AGPLv3 条款基本无负担**。
> - **Valkey**：2024-03 从仍为 BSD 的 Redis 7.2.4 分叉，Linux 基金会托管，BSD 3-Clause 至今未变。
> - **当前版本（2026-09 核查）**：Redis 8.10（2026-07，本机实测 8.10.1）／Redis 8.8.0（2026-05）／Valkey 9.1.1（2026-07）。
> - **支持周期**：Redis Software 7.2 已于 2026-02-28 EOL；**Redis 8.0 将于 2026-12-01 停止支持**——若在生产用 8.0，应尽快规划升级到 8.8+。
> - **Dragonfly**（若评估）：BSL 1.1，约定 2029-03-01 转 Apache 2.0；是**独立实现**而非 Redis 分叉，命令兼容性需单独验证。

## 附：本轮实测踩坑清单

这些不是设计决策，但都是真机跑出来的，记在这里避免重犯。

| # | 坑 | 现象 | 根因 | 修法 |
|---|-----|------|------|------|
| 1 | SCAN 死循环 | 诊断时 SCAN 被调用 566 万次，实例被拖慢 | SCAN 返回的游标是 `bytes`（`b'0'`），代码写 `if cur == 0` 永远不成立 | 解码后再比较：`cur_str = raw.decode()`，`if cur_str == '0'` |
| 2 | 关闭 default 后复制中断 | 从库日志刷 `NOPERM ... 'psync'` | 应用账号无复制所需命令 | 单建 `replicator` 角色：`+psync +replconf +ping +info` |
| 3 | `-@dangerous` 误禁 INFO | 诊断层全部 NOPERM，查不了任何指标 | INFO 属 dangerous 类别 | 收紧后显式加回 `+INFO +CONFIG +MEMORY +SLOWLOG +LATENCY +OBJECT ...` |
| 4 | 配置文件 ACL 续行报错 | Redis 启动失败：`Unresolved Configuration(s) Detected` | conf 里 user 行用 `\` 续行，Redis 8 解析失败 | 改用 `ACL SETUSER` 动态创建 + `ACL SAVE` 落盘 |
| 5 | 多线程共用连接 | 统计出"成功 200 且失败 101"，总数超线程数 | RESP 请求-响应串位 | 每线程独立连接（生产用连接池） |
| 6 | Lua 返回值歧义 | 误判为"超卖"，实际原子性没问题 | `0` 同时表示"扣完剩 0"和"库存不足" | 用 `-2`/`-3` 区分失败原因 |
| 7 | 诊断工具比业务更耗资源 | 全量 SCAN 打满实例 | 大 key 扫描无采样上限 | 加 `sample` 参数限制扫描数量 |
