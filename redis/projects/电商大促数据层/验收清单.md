# 验收清单 · 电商大促数据层

> 逐项自测。**全部勾选才算真的做成了**——不是"跑起来就行"。

## 功能验收

- [ ] 跑通 `python3 main.py`，七幕演示全部输出，无异常堆栈
- [ ] 第一幕显示缓存提速（预期约 100 倍量级：20ms → 0.2ms 以下）
- [ ] 第二幕穿透防护：查 50 次不存在的 id，数据库只被查 **1 次**
- [ ] 第二幕击穿防护：30 线程并发打刚失效的热点 key，数据库只被查 **1 次**
- [ ] 第二幕雪崩防护：抽查的 TTL 有明显跨度（预期 90 秒以上），不是同一个值
- [ ] 第三幕：更新后重新读取能拿到新值（价格变成 999）
- [ ] 第三幕 3.2：能清楚说出"只改库不删缓存"为什么会产生脏数据
- [ ] 第四幕秒杀：成功数 + 剩余库存 = 初始库存（100 + 0 = 100）
- [ ] 第四幕分类合计 = 参与线程数（100 售罄 + 400 成功 = 500）
- [ ] 排行榜能取到 TopN，销量数值与实际成功下单数一致
- [ ] 第七幕：主库写入后从库能读到；从库写入被拒（READONLY）

## 非功能验收

- [ ] **性能**：商品查询 P50 < 5ms（数据库基线 20ms）
- [ ] **正确性**：`left >= 0` 且账目对平 —— 无超卖
- [ ] **安全**：appuser 执行 `KEYS *` / `FLUSHALL` / `DEBUG SLEEP` / `SHUTDOWN` 全部被拒
- [ ] **安全**：appuser 写非业务前缀 key（如 `evil:hack`）被拒，写 `cache:*` 成功
- [ ] **安全**：无认证连接 7201 返回 NOAUTH
- [ ] **可维护性**：大 key 扫描有 `sample` 上限，不会因诊断把实例压垮
- [ ] **可观测**：`latency-monitor-threshold > 0`（本项目设为 100 毫秒）

## 🔬 动手验证（比勾选更有说服力）

```bash
# 1. 验证安全边界：这四条都应该被拒绝
redis-cli -p 7201 --user appuser --pass 'AppPass123!' KEYS '*'
redis-cli -p 7201 --user appuser --pass 'AppPass123!' FLUSHALL
redis-cli -p 7201 --user appuser --pass 'AppPass123!' SET evil:hack 1
redis-cli -p 7201 PING                    # 无认证，应 NOAUTH

# 2. 对比出厂默认的危险程度（7203）
redis-cli -p 7203 FLUSHALL                # 无认证直接成功

# 3. 验证 Lua 原子性：反复跑，账目必须每次都对平
cd projects/电商大促数据层/实现 && python3 main.py | grep -A3 '成功数 + 剩余'

# 4. 验证 SCAN 游标陷阱（本项目踩过的坑）
python3 debug_scan.py                     # 看游标返回的真实类型
```
