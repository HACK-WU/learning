# 反例对照 · 电商大促数据层

> 不是"错误示例"，而是**看起来能跑、实际很糟**的版本——只有这样才能教会"为什么最佳实践是最佳实践"。
> 下面每一条都能跑通，甚至在开发环境"看起来正常"。

---

## 反例 1：用 String 存 JSON，而不是 Hash 存对象

```python
# ❌ 反例：把整个商品对象序列化成 JSON 存 String
import json
r.set('cache:good:1', json.dumps({'id':1,'name':'商品1','price':52,'stock':1000}), ex=300)

# 业务要改价格，只能整对象读改写
obj = json.loads(r.get('cache:good:1'))
obj['price'] = 999
r.set('cache:good:1', json.dumps(obj), ex=300)   # 整对象重写
```

> 它**能跑通**，甚至初看更简洁（一行 set，不用管字段）。

## 反例 2：扣库存不用 Lua，用"读-判断-写"三步

```python
# ❌ 反例：分三步，应用层判断
stock = int(r.get('inventory:stock:1001'))
if stock > 0:
    r.decr('inventory:stock:1001')
    create_order(uid)      # 认为自己抢到了
else:
    return 'sold_out'
```

> 单线程跑完全正常，测试环境根本发现不了问题。

## 反例 3：用 KEYS 做前缀统计

```bash
# ❌ 反例：统计商品缓存数量
redis-cli KEYS 'cache:good:*' | wc -l
```

> 数据少的时候秒回，看起来比 SCAN 还方便。

## 反例 4：缓存更新时"更新缓存"而不是"删除缓存"

```python
# ❌ 反例：更新数据库后，顺手把新值写进缓存
db.update(gid, price=999)
r.hset('cache:good:%d' % gid, 'price', 999)    # 直接更新，不删除
```

> 单次操作看不出问题，缓存里确实是新值，测试也通过。

## 反例 5：默认配置直接上生产

```bash
# ❌ 反例：出厂默认，什么都不配
redis-server --port 6379
```

> 起来了，能连通，能读写，一切正常。

## 🔍 逐条对比

| # | 维度 | ❌ 反例 | ✅ 正确做法 | 为什么糟 |
|---|------|---------|------------|----------|
| 1 | **存储结构** | String 存 JSON：改一个字段要读整个对象→反序列化→改→序列化→写回 | Hash 存对象，`HSET` 只改 price 字段，`HINCRBY` 原子增减 | ① 改价时整对象读改写，并发下后写的会覆盖先写的（丢更新）② 每次改一个字段都要传输整个 JSON，网络与 CPU 开销随字段数线性增长 ③ 无法对单个字段做原子增减 |
| 2 | **原子性** | 读-判断-写三步 | Lua 脚本一步完成 | 高并发下两个请求同时读到 `stock=1`，都判定"够"，各扣一次变成 `-1` —— **超卖**。本项目实测：不用 Lua 时账目必然对不平；用了 Lua，500 并发抢 100 件，返回值是 19,18,17…1,0 每个只出现一次，账目完全对平 |
| 3 | **遍历方式** | `KEYS` 一次性遍历 | `SCAN` 游标分批 | KEYS 在十万级 key 时让 Redis 停顿数百毫秒，**期间所有其他请求排队**。本项目已通过 ACL 从权限层面禁用 KEYS，杜绝误用 |
| 4 | **一致性** | 更新缓存 | 删除缓存 | 并发更新时，两个线程的交织顺序与数据库提交顺序可能不一致，缓存里留下旧值，**且会一直存在到 key 自然过期**。本项目第三幕实测：只改库不删缓存，缓存持续返回 999，而数据库已是 888 |
| 5 | **安全基线** | `redis-server --port 6379` | default off + 分角色最小权限 | 出厂默认是 `user default on nopass ~* +@all`——**无需认证、可读写全部 key、可执行 FLUSHALL**。本项目 7203 实例实测：无密码直接 `SET` 成功、`FLUSHALL` 成功 |

---

## 💡 一句话教训

**能跑通 ≠ 能扛住；差别在于并发时和出故障时怎么表现。**

上面五个反例在单线程、小数据量、开发环境里全部"正常"。它们的代价只在三个时刻显现：流量上来时（反例 1、2、3）、数据变脏时（反例 4）、被人盯上时（反例 5）。
