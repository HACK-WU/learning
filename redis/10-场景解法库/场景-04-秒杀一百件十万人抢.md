# 场景 04：秒杀，100 件商品 10 万人抢

> 类型：规模压力题 + 经典设计题 ｜ 回索引：[场景解法库](./INDEX.md)

## 场景描述

限量 100 件，开抢瞬间 10 万请求涌入。要求：**不超卖**、**一人一单**、响应快。

## 🔒 先自己想 30 秒

用数据库事务？用 Redis 扣减？还是消息队列排队？——想一想"不超卖"的硬要求，到底该在哪一层保证。

<details><summary>💡 提示</summary>

三个子问题分开想：

1. **库存扣减的原子性**在哪一层保证？（应用层的 if 判断够吗？）
2. **一人一单**用什么数据结构去重？
3. **10 万请求里的绝大部分注定抢不到**——怎么让它们**快速失败**，而不是全挤到 Redis？

</details>

<details><summary>📖 展开解法</summary>

### 解法一览

| 解法 | 能解决到 | 代价 | 适用边界 |
|------|---------|------|---------|
| **A · Redis Lua 原子扣减** | 不超卖；性能极高（万级 TPS）；一人一单可用 Set 去重 | 库存数据最终要落库，需异步同步；Redis 宕机期间不可用 | 绝大多数秒杀场景 |
| **B · 数据库悲观锁 / 乐观锁** | 绝对可靠，无需担心缓存一致性 | 性能差（千级 TPS），高并发下锁竞争严重 | 库存量小、并发不高 |
| **C · Redis 预扣 + 消息队列异步下单** | 削峰填谷，系统解耦 | 架构复杂；用户要异步等待结果 | 超大规模、允许异步返回 |
| **D · 分层拦截**（前端限流 + 网关限流 + Redis 令牌桶） | 把无效请求挡在最外层 | 需要多层配合 | 任何秒杀都该做，是 A 的前置 |

### 推荐路径

1. **先做分层拦截**（方案 D）——10 万请求里 99.9% 注定失败，让它们打到 Redis 都是浪费。前端按钮置灰、网关按 UID 限流、令牌桶控制放行量。
2. **库存扣减用 Lua**（方案 A）。把「判断库存 → 扣减 → 记入已购 Set」合成一个原子操作。本项目 `inventory.py` 的 `LUA_SECKILL` 即此实现，实测 500 并发抢 100 件，**账目完全对平**。
3. **注意接口设计**：返回值要能区分「扣完剩 0」「库存不足」「已购买过」——本项目初版用 `0` 同时表示前两者，导致误判，已改为 `-2` / `-3` 区分。
4. **异步落库**：Redis 扣减成功后发消息，由消费者创建订单并同步数据库。
5. **超大规模再上消息队列**（方案 C）。

### 关键代码


> 代码约定：以下片段中的 `r` 为已连接的 Redis 客户端，`db_query` / `db_update` 为数据库查询占位函数，均未重复定义，照抄时需自备。
```lua
-- LUA_SECKILL：判断库存 -> 扣减 -> 记入已购 Set，三步一个原子操作
-- KEYS[1]=库存key  KEYS[2]=已购Set  ARGV[1]=用户ID
-- 返回值：剩余库存(>=0) / -2=库存不足 / -3=已购买过
if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then
    return -3
end
local stock = tonumber(redis.call('GET', KEYS[1]))
if stock == nil then
    return -2
end
if stock <= 0 then
    return -2
end
redis.call('DECR', KEYS[1])
redis.call('SADD', KEYS[2], ARGV[1])
return stock - 1
```

```python
# 完整可运行：脚本与调用放在一起，照抄即可跑
LUA_SECKILL = """
if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then
    return -3
end
local stock = tonumber(redis.call('GET', KEYS[1]))
if stock == nil or stock <= 0 then
    return -2
end
redis.call('DECR', KEYS[1])
redis.call('SADD', KEYS[2], ARGV[1])
return stock - 1
"""

def seckill(user_id: str, stock_key: str = "seckill:stock",
            bought_key: str = "seckill:bought"):
    """返回：剩余库存（>=0）/ -2 库存不足 / -3 已购买过"""
    return int(r.eval(LUA_SECKILL, 2, stock_key, bought_key, user_id))

# 初始化库存后即可并发调用
# r.set("seckill:stock", 100)
# seckill("user:1")  -> 99 ；重复调用同一用户 -> -3 ；库存耗尽 -> -2
```

> 注意：Lua 里的 key 必须通过 `KEYS[]` 传入（而非拼在脚本里），否则在 Cluster 下会 `CROSSSLOT`；本脚本只涉及 2 个 key，可用 hash tag 保证同槽。

### 什么情况下此方案不适用

- **要求绝对零丢失**（如金融交易）→ 纯 Redis 方案不够，需要数据库事务兜底或 TCC 分布式事务。
- 库存需要支持**复杂的预留 / 释放 / 超时归还**时，Lua 脚本会变得很复杂，应改用专门的库存服务。

### 非 Redis 的替代路线

- **数据库乐观锁**：`UPDATE stock SET n = n - 1 WHERE id = ? AND n > 0` + 判断影响行数——零额外组件、绝对可靠，千级 TPS 足够时就别上 Redis
- **数据库悲观锁**：`SELECT ... FOR UPDATE`——正确但并发下锁等待严重，只适合低并发
- **消息队列串行化**：把所有请求写入 MQ，单消费者顺序扣减，天然无超卖；代价是延迟高、用户要异步等结果（对应方案 C）
- **预分配 / 号段**：开抢前把 100 件生成 100 个 token 放进队列或已分配的号段表，抢到即得——适合"先到先得"语义明确的活动

### 做错会踩的坑

- 应用层 if 判断扣减 → 超卖
- Lua 返回值歧义 → 业务逻辑分叉错误（本项目实测）
- 不做分层拦截 → Redis 被无效请求淹没，反而拖垮正常业务
