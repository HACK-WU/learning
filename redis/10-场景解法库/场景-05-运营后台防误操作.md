# 场景 05：给运营开数据后台，防误操作

> 类型：经典设计题 ｜ 回索引：[场景解法库](./INDEX.md)

## 场景描述

运营需要一个后台，能查缓存数据、手动清理某些 key。但你担心他们执行 `KEYS *` 或 `FLUSHALL` 把生产搞挂。

## 🔒 先自己想 30 秒

只靠"培训 + 提醒"够吗？给一个只读账号？还是干脆不给直连，做一个后台服务中转？

<details><summary>💡 提示</summary>

从三个层面想：

1. **权限层**：Redis 的 ACL 能做什么？能限制命令吗？能限制 key 前缀吗？
2. **架构层**：是不是根本不该让人直连 Redis？
3. **兜底层**：万一还是出事了，怎么把损失降到最小？

另外一个容易忽略的点：**收紧权限后，运维自己还能不能查问题？**

</details>

<details><summary>📖 展开解法</summary>

### 解法一览

| 解法 | 能解决到 | 代价 | 适用边界 |
|------|---------|------|---------|
| **A · ACL 分角色最小权限** | 从权限层面禁掉危险命令，且能限制 key 前缀 | 配置复杂；容易过度收紧 | 所有生产环境都应做 |
| **B · 后台服务中转**（不直连 Redis，走 API） | 完全可控，可加审计日志、操作审批 | 要开发后台服务 | 有多人需要访问数据时 |
| **C · 只读从库** | 查询类操作完全不影响主库 | 从库有延迟；写操作另走主库 | 以查询为主的场景 |
| **D · 独立实例隔离** | 最彻底，出问题不影响主业务 | 数据要同步；成本翻倍 | 有合规 / 审计强要求 |

### 推荐路径

1. **ACL 是底线**（方案 A），不管用不用别的方案都要做。实测的完整基线：
   - `user default off` —— 出厂默认是 `nopass + @all`，等于裸奔
   - 应用账号：限定 key 前缀 + 禁危险命令 + **回补运维只读命令**
   - 只读账号：给运营 / 报表，注意 `+@read` 默认**包含 KEYS**，必须显式 `-KEYS`
   - 复制账号：单独的 `replicator`（关掉 default 后不建这个，从库会连不上）
2. **运营查询走只读从库**（方案 C），写操作必须走后台服务。
3. **有开发能力就做后台中转**（方案 B），加上操作审计与二次确认。
4. 定期 `ACL LIST` 审计。

### 关键代码


> 代码约定：以下片段中的 `r` 为已连接的 Redis 客户端，`db_query` / `db_update` 为数据库查询占位函数，均未重复定义，照抄时需自备。
```bash
# 基线：先关 default，再建各角色（顺序不能反，否则把自己锁在外面）
ACL SETUSER default off

# 应用账号：限定前缀 + 禁危险命令 + 回补运维只读命令
ACL SETUSER appuser on >AppP@ss ~cache:* +@read +@write -@dangerous +INFO +SLOWLOG +CLIENT

# 运营只读账号：注意 +@read 默认含 KEYS，必须显式 -KEYS，并禁掉 SCAN 族的滥用风险
ACL SETUSER ops_ro on >OpsP@ss ~* +@read -KEYS -FLUSHALL -FLUSHDB +INFO

# 复制账号：关掉 default 后没有它，从库连不上
ACL SETUSER replicator on >RepP@ss +PSYNC +REPLCONF +PING

# 审计
ACL LIST
ACL WHOAMI
```

```python
# 运营后台绝不能把 KEYS 暴露成按钮；要查 key 用 SCAN 游标分批
def safe_scan(pattern: str, count: int = 500):
    """用 SCAN 代替 KEYS，游标分批，不阻塞主线程"""
    cursor = 0
    while True:
        cursor, keys = r.scan(cursor=cursor, match=pattern, count=count)
        for k in keys:
            yield k
        if cursor == 0:
            break
```

### 知识点挂钩

- ACL 权限模型与角色设计 → 阶段 4 课 9
- `+@read` 包含 KEYS 的陷阱 → 阶段 4 课 9 实测
- `-@dangerous` 会误伤 INFO → 本项目实测，见 [设计决策.md](../projects/电商大促数据层/设计决策.md) 决策 5
- 从库只读 → 阶段 3 课 6
- `SCAN` 替代 `KEYS` → 阶段 4 课 9

### 什么情况下此方案不适用

- **只有一个人维护的内部系统** → 全套 ACL 配置可能是过度设计，设个强密码 + 禁掉 FLUSHALL 就够了。别为了严谨牺牲效率。
- 需要执行 `DEBUG`、动态改配置的场景 → 这些本来就不该给运营账号。

### 非 Redis 的替代路线

- **不给直连，只给 API**（方案 B 的极端形态）：后台服务封装"按 id 查缓存""清某个前缀"等具体动作，Redis 连接串不出现在任何客户端 —— 这是最彻底也最推荐的形态
- **用现成的 Redis 管理平台**：RedisInsight、CacheCloud、云厂商控制台——自带权限、审计与只读模式，比自研后台便宜
- **数据库侧授权代替**：若运营要的其实是业务数据，正确做法是给他们**业务库的只读账号 / BI 报表**，而不是 Redis 权限
- **堡垒机 + 命令审计**：必须直连时，走堡垒机做命令级白名单与录屏审计，作为 ACL 之外的第二道闸

### 做错会踩的坑

- `-@dangerous` 一刀切 → INFO / SLOWLOG 全废，出问题查不了
- 先关 default 再建账号 → 把自己锁在外面，只能重启
- 以为 `+@read` 很安全 → 它包含 KEYS，照样能拖垮实例
