# 场景 03：百万级实时排行榜

> 类型：规模压力题 ｜ 回索引：[场景解法库](./INDEX.md)

## 场景描述

需要实时展示销量 Top 100，参与商品百万级，更新频繁（每秒数千次）。

## 🔒 先自己想 30 秒

用数据库 `ORDER BY` 查？用 Redis ZSet？还是自己维护一个堆？——想一想"实时"和"百万级"叠在一起意味着什么。

<details><summary>💡 提示</summary>

三个关键问题：

1. Top N 的 N 是大还是小？（只要前 100 名，还是要任意人的排名？）
2. 更新频率有多高？
3. 单个 key 会有多大？——**百万成员的 ZSet 是不是变成了大 key？**

</details>

<details><summary>📖 展开解法</summary>

### 解法一览

| 解法 | 能解决到 | 代价 | 适用边界 |
|------|---------|------|---------|
| **A · 单个 ZSet 全量排行** | 实时更新、取 TopN 都是 O(logN)，任意排名 O(logN) | **单 key 会很大**，是大 key 风险源；无法分片 | 十万级以内、单 key 可控 |
| **B · 按维度拆分 ZSet + 定期合并** | 每个 key 都很小，可分散到不同槽 | 取全局 TopN 要合并计算，非严格实时 | 百万级、可按类目 / 时段拆分 |
| **C · ZSet 存 TopN + 数据库存全量** | Redis 只扛热点，容量可控 | 落榜数据要从数据库查，逻辑复杂 | 只关心头部排名 |
| **D · 用数据库物化视图定时刷新** | 实现简单 | 非实时（分钟级延迟）；刷新时数据库压力大 | 实时性要求不高 |

### 推荐路径

1. **先上 A**（单 ZSet），最直白。用 `ZINCRBY` 更新、`ZREVRANGE` 取 TopN、`ZREVRANK` 查排名。
2. **监控单 key 大小**。`MEMORY USAGE` + `OBJECT ENCODING`——注意 ZSet 元素超过 `zset-max-listpack-entries`（默认 128）会从 listpack 转为 skiplist，**内存会发生数量级跳变**。
   本机实测（Redis 8.10.1）：128 个成员时 **1721 字节**（13.4 字节/元素），加到 129 个立刻变成 **11821 字节**（91.6 字节/元素）——**总内存跳变 6.87 倍，每元素开销涨 6.8 倍**。
   这不是"翻倍"，是**数量级差异**，容量规划时必须按转换后的口径估算。
3. **过大就拆**（方案 B）：按类目、时段、地区拆成多个小 ZSet，全局榜通过合并计算或异步聚合。
4. **加过期清理**：日榜用 `stats:daily:{day}` 这类带日期的 key，自然过期，不用手动删。

### 关键代码


> 代码约定：以下片段中的 `r` 为已连接的 Redis 客户端，`db_query` / `db_update` 为数据库查询占位函数，均未重复定义，照抄时需自备。
```python
# 方案 A：单个 ZSet，写入即有序
def vote(item_id: str, delta: int = 1):
    r.zincrby("leaderboard", delta, item_id)      # 服务端原子自增，无并发覆盖

def top_n(n: int = 10):
    return r.zrevrange("leaderboard", 0, n - 1, withscores=True)

def rank_of(item_id: str):
    rank = r.zrevrank("leaderboard", item_id)
    return None if rank is None else rank + 1

# 方案 B：按维度拆分，全局榜合并（用 ZUNIONSTORE 落到一个临时 key）
def global_top(categories: list, n: int = 100):
    keys = [f"leaderboard:{c}" for c in categories]
    r.zunionstore("leaderboard:tmp:global", keys, aggregate="SUM")
    return r.zrevrange("leaderboard:tmp:global", 0, n - 1, withscores=True)
```

```bash
# 监控编码转换这个"内存跳变点"
redis-cli OBJECT ENCODING leaderboard     # listpack -> skiplist 即已跳变
redis-cli MEMORY USAGE leaderboard
redis-cli CONFIG GET zset-max-listpack-entries
```

### 知识点挂钩

- ZSet 跳表 + 哈希表双结构 → 阶段 2 课 4
- ZSet 编码转换（listpack → skiplist）与内存跳变 → 阶段 2 课 4、阶段 4 课 9
- 大 key 风险与拆分 → 阶段 4 课 9
- 集群分片 → 阶段 4 课 7

### 什么情况下此方案不适用

- **要求严格一致的全局实时排名且数据量极大** → 单 ZSet 成大 key，拆分后又难保证严格实时。此时应重新审视"实时"的真实要求（秒级？分钟级？）。
- 排名需要按多个维度自由组合筛选时，ZSet 无法胜任，应交给搜索引擎或 OLAP 引擎。

### 非 Redis 的替代路线

- **数据库窗口函数**：PostgreSQL / MySQL 8 的 `ROW_NUMBER() OVER (ORDER BY score DESC)`——数据量小、实时性要求低（分钟级）时最省事，零额外组件
- **OLAP 引擎**：ClickHouse / Doris 做预聚合 + 定时刷新物化视图，可支撑亿级明细且支持多维筛选；代价是非实时
- **搜索引擎**：Elasticsearch 的排序与聚合同样能做榜，且天然支持多维筛选组合；代价是写入到可见有延迟
- **流处理**：Flink 实时聚合排行榜——"每秒数千次更新"且要精确到毫秒时，这是正解；Redis ZSet 在极高写入下会成为瓶颈

### 做错会踩的坑

- 单 ZSet 塞百万成员 → 大 key，删除/过期时阻塞
- 忽略编码转换 → 128→129 个成员时内存跳变 6.87 倍，容量估算全错并触发 OOM

</details>
