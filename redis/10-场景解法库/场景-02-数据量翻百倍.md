# 场景 02：数据量翻 100 倍，单机内存不够了

> 类型：规模压力题 ｜ 回索引：[场景解法库](./INDEX.md)

## 场景描述

数据从 5GB 涨到 500GB。单机 Redis 内存已经顶到上限，加内存条也到头了。

## 🔒 先自己想 30 秒

买更大的机器？做集群分片？还是——先问一句：这 500GB 里有多少是**真的需要放在内存里的**？

<details><summary>💡 提示</summary>

两个方向，先分清再选：

- **横向扩展**：数据太多一台装不下 → 分片
- **纵向瘦身**：数据其实没那么热 → 冷数据下沉、过期清理、编码优化

关键判断：**数据的访问分布是什么样的？** 如果 80% 的请求集中在 20% 的数据上，那根本不需要把 500GB 全放内存。

</details>

<details><summary>📖 展开解法</summary>

### 解法一览

| 解法 | 能解决到 | 代价 | 适用边界 |
|------|---------|------|---------|
| **A · Redis Cluster 分片** | 容量随节点线性扩展 | 多 key 操作受限（必须同槽）；运维复杂度上升；跨片事务不支持 | 数据量大且增长明确 |
| **B · 客户端分片 / 代理分片** | 同样能扩展，且对多 key 限制更灵活 | 客户端要引入分片逻辑；扩缩容要手动迁移 | 想绕开 Cluster 限制时 |
| **C · 冷热分离**（Redis 只存热数据，冷数据下沉到数据库 / 对象存储） | 内存占用大幅下降，成本最优 | 需要识别冷热；冷数据访问变慢 | 访问有明显冷热分布 |
| **D · 垂直扩容（加内存）** | 最简单，零改造 | 有物理上限；成本非线性增长；fork 时间随内存变长 | 数据量只是略超当前配置 |

### 推荐路径

1. **先做数据瘦身**（成本最低）：查有没有该过期却没过期的 key、有没有大 key、有没有重复数据。本项目实测：一个 100 万字段的 Hash 拆成 1000 个小 Hash 后，删除阻塞从 **113ms 降到 0.61ms**——结构优化不只是省内存，还直接影响可用性。
2. **做冷热分离**：只把真正热的放进 Redis，其余下沉。这一步常常能把容量需求砍掉一个数量级。
3. **仍不够再上 Cluster**：规划好 key 的 hash tag，让需要一起操作的数据落在同一槽。
4. **垂直扩容作为过渡**，不是终局。

### 关键代码


> 代码约定：以下片段中的 `r` 为已连接的 Redis 客户端，`db_query` / `db_update` 为数据库查询占位函数，均未重复定义，照抄时需自备。
```bash
# 1) 找大 key：不要 KEYS *，用 --bigkeys 或 MEMORY USAGE 抽样
redis-cli --bigkeys

# 2) 看 key 的编码与真实占用
redis-cli OBJECT ENCODING big:hash
redis-cli MEMORY USAGE big:hash

# 3) 冷热判断（需 maxmemory-policy 为 *-lfu）
redis-cli OBJECT FREQ some:key        # 访问频次计数器，0~255

# 4) 大 key 用异步删除，别用 DEL
redis-cli UNLINK big:hash             # 后台线程回收，不阻塞主线程
```

```python
def split_big_hash(big_key: str, shard_size: int = 1000):
    """把百万字段的大 Hash 拆成若干小 Hash：删除阻塞从 113ms 降到 0.61ms"""
    cursor = 0
    idx = 0
    while True:
        cursor, items = r.hscan(big_key, cursor=cursor, count=500)
        for field, value in items.items():
            shard = f"{big_key}:shard:{int(field) // shard_size}"
            r.hset(shard, field, value)
        if cursor == 0:
            break
    r.unlink(big_key)          # 异步删除，主线程不阻塞
```

### 什么情况下此方案不适用

- 如果业务**强依赖多 key 事务且无法用 hash tag 归拢**，Cluster 会带来大量改造——此时优先考虑冷热分离 + 垂直扩容。
- 数据量增长不可预测且需要频繁扩缩容时，Cluster 的槽迁移成本要提前评估。

### 非 Redis 的替代路线

- **先问"是否必须内存"**：冷数据下沉到 PostgreSQL / MySQL 或对象存储（COS / S3）——成本差一个数量级，代价是冷数据访问从微秒涨到毫秒
- **换存储引擎**：数据量大且需要磁盘承载时，KV 场景可评估 RocksDB（嵌入式、LSM、容量远超内存）、或 ScyllaDB / Cassandra（分布式宽表，容量线性扩展）
- **换数据模型**：如果"数据量大"其实是因为把明细都塞进了 Redis，正确做法是只存聚合结果 + 明细留在 OLAP 引擎
- **分库分表中间件**：若最终一致性可接受且要保留 SQL 能力，数据库侧分库分表（ShardingSphere 等）是另一条路

### 做错会踩的坑

- 上 Cluster 但 key 设计没考虑 hash tag → 大量 `CROSSSLOT` 错误
- 只扩容不做瘦身 → 成本失控，且 fork 时间随内存增长，RDB 备份越来越慢
