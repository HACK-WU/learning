# 场景 01：大促流量翻 10 倍，数据库先扛不住

> 类型：规模压力题 ｜ 回索引：[场景解法库](./INDEX.md)

## 场景描述

平时 QPS 500，大促期间涨到 5000。接口开始超时，监控显示数据库连接池打满，慢查询激增。Redis 已经在用，但**命中率只有 60%**。

## 🔒 先自己想 30 秒

第一反应是加缓存？扩容数据库？还是限流？——想一想命中率只有 60% 意味着什么：还有 40% 的请求在打数据库，**那 40% 才是压垮数据库的元凶**。

<details><summary>💡 提示（分层 / 分维度想）</summary>

按三层想：

- **入口层**：能不能挡掉一部分请求？
- **缓存层**：命中率为什么只有 60%？是缓存没覆盖、还是失效太快、还是根本没命中？
- **数据层**：数据库扛不住时，是加从库读、还是加机器、还是改查询？

再想一个关键问题：**这 40% 的未命中，是正常的冷数据回源，还是被穿透 / 击穿了？** 两者的解法完全不同。

</details>

<details><summary>📖 展开解法</summary>

### 解法一览

| 解法 | 能解决到 | 代价 | 适用边界 |
|------|---------|------|---------|
| **A · 提高缓存命中率**（查清 miss 原因 + 预热 + TTL 抖动） | 命中率提到 95%+，数据库压力降一个数量级 | 要分析 miss 原因；预热需要提前跑 | 读多写少、数据可缓存 |
| **B · 数据库读写分离 + 加从库** | 读压力分散到多个从库 | 主从延迟带来不一致；主库仍是写瓶颈 | 读远多于写，且能接受秒级延迟 |
| **C · 应用层限流 + 降级** | 保证系统不崩，牺牲部分请求 | 部分用户看到降级页 | 任何场景的最后防线 |
| **D · 数据库垂直扩容 / 分库分表** | 根本性提升容量 | 成本高、改造大、周期长 | 长期方案，不适合大促前临时做 |

### 推荐路径（递进，不是一次全上）

1. **先查 miss 原因**（成本最低，收益最大）。`INFO stats` 看 `keyspace_hits/misses`，再抽样分析 miss 的是哪些 key——如果是同一批 key 反复 miss，那不是冷数据，是**缓存被击穿或没写进去**。
2. **上预热 + TTL 抖动**。大促开始前把热点数据灌进缓存；TTL 加随机值避免集体失效。
3. **补防护**：穿透（空值缓存 / 布隆）、击穿（互斥锁 / 逻辑过期）、雪崩（抖动）——三件套补齐。
4. **仍不够再加从库**，把读压力摊开。
5. **最后上限流降级**，保证不死。扩容分库分表属于长期规划，不该在大促前两周动。

### 关键代码


> 代码约定：以下片段中的 `r` 为已连接的 Redis 客户端，`db_query` / `db_update` 为数据库查询占位函数，均未重复定义，照抄时需自备。
```bash
# 1) 先看命中率的真实数字，别凭感觉
redis-cli INFO stats | grep -E 'keyspace_(hits|misses)'
# 命中率 = hits / (hits + misses)；60% 意味着 40% 的请求还在打数据库

# 2) 抽查看 miss 的到底是哪些 key（MONITOR 有性能损耗，只短时采样）
redis-cli --stat -i 1        # 观察每秒命令数的整体趋势
redis-cli SLOWLOG GET 10     # 慢查询是不是集中在大促期间才出现

# 3) 预热：大促前把热点灌进去，TTL 打散，避免集体失效
```

```python
import random

BASE_TTL = 3600
JITTER = 300

def warmup(ids):
    """大促前预热：TTL 打散，避免同一时刻集体失效"""
    for pid in ids:
        product = db_query(pid)
        if product is None:
            continue
        r.setex(f"product:{pid}", BASE_TTL + random.randint(0, JITTER),
                json.dumps(product))
```

### 什么情况下此方案不适用

- **强一致场景不能粗暴加缓存**（如余额、库存扣减）——缓存带来的一致性窗口不可接受，应走 Lua 原子操作 + 数据库事务。
- 数据是**写多读少**时，加缓存收益极低，反而增加一致性维护成本。

### 非 Redis 的替代路线

别把"扛读压力"等同于"上 Redis"，同场景还有这些路：

- **数据库侧**：加从库 / 读写分离（方案 B）、连接池与慢查询治理、上查询结果缓存（如 MySQL Query Cache 的替代：应用层本地缓存）
- **进程内缓存**：Caffeine（Java）、`functools.lru_cache` / cachetools（Python）——**零网络开销**，比 Redis 更快；代价是各实例间不一致、容量受堆内存限制。热点极集中时这是最优解
- **CDN / 边缘缓存**：静态或半静态内容直接下沉到 CDN，请求根本到不了应用
- **换引擎**：读压力来自复杂聚合查询时，正确做法是上 OLAP 引擎（ClickHouse / Doris）做预聚合，而不是加缓存

### 做错会踩的坑

- 只加缓存不查 miss 原因 → 命中率提不上去，白做
- 预热时把 TTL 设成同一个值 → 大促开始瞬间集体失效，直接雪崩
- 忽略大 key → 单个 key 的读取就拖垮整体
