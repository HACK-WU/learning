# 09 · 排障速查手册

> **认知状态**：使用态。**线上出事了来翻这份——本手册只给动作，不给原理。**
> 想搞懂原理去 [08-实战经验.md](08-实战经验.md)；想学怎么设计去 [10-场景解法库.md](10-场景解法库.md)。

**适用版本**：Elasticsearch 9.5.1（本机实测，2026-09-01）
**环境**：9201 三节点集群（`http://localhost:9201`）／9200 单节点集群（`https://localhost:9200`）

## 怎么用这份手册

1. 看下面的**症状索引表**，按你看到的**报错关键字或现象**找到条目编号
2. 翻到该条目，**从上往下执行**，第一条永远是**止血**
3. 每条末尾有「若无效 →」的升级出口，不会走进死胡同

> ⚠️ **两条通用铁律**
> **① 先止血，后定位。** 线上没时间先搞清楚再动手——先恢复服务，再查根因。
> **② 不要为了消除报错而调高限制。** 熔断、水位、队列上限都是保护机制。调高它们等于把"报错"换成"宕机"。

## 🔴 E1 磁盘水位触发只读块

**一眼识别**：写入全部失败，报错含 `FORBIDDEN/12/index read-only / allow delete (api)`，类型 `cluster_block_exception`。

> 💡 块名里的 `allow delete` 是关键——**删除仍然允许**，这是 ES 故意留的逃生通道。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血 1** | `curl.exe -s "http://localhost:9201/_cat/allocation?v"` | 看到哪个节点磁盘逼近 100% |
| **止血 2** | 删掉最旧的、可从别处重建的索引：<br/>`curl.exe -s -X DELETE "http://localhost:9201/<最旧索引>"` | 磁盘降到 95% 以下，ES **自动**解除块 |
| **止血 3**（等不及自动解除时） | 临时上调水位 + 手动清块（两个 JSON 见下） | 写入立即恢复 |
| **定位** | `curl.exe -s "http://localhost:9201/_cat/indices?v&s=store.size:desc"` | 找出占空间最大的索引 |
| **修复** | 配 ILM 自动删除 + SLM 定期快照（课 11/13/15） | 磁盘不再涨到水位 |
| **若无效** | → 转 [E2 集群 red](#-e2-集群-red主分片未分配)（磁盘满常伴随分片未分配） | — |

```json
// raise-watermark.json（临时，用完要还原）
{ "persistent": {
    "cluster.routing.allocation.disk.watermark.low": "90%",
    "cluster.routing.allocation.disk.watermark.high": "95%",
    "cluster.routing.allocation.disk.watermark.flood_stage": "97%" }}
```
```json
// clear-block.json
{ "index.blocks.read_only_allow_delete": null }
```
```powershell
curl.exe -s -X PUT "http://localhost:9201/_cluster/settings" `
  -H "Content-Type: application/json" --data-binary "@raise-watermark.json"

curl.exe -s -X PUT "http://localhost:9201/*/_settings?expand_wildcards=all" `
  -H "Content-Type: application/json" --data-binary "@clear-block.json"
```

**预防**：磁盘告警设 80%；ILM/SLM 跑起来。**磁盘满是可以 100% 避免的问题。**

**原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 6

## 🔴 E2 集群 red（主分片未分配）

**一眼识别**：`GET /_cluster/health` 的 `status` 为 `red`，`unassigned_shards > 0`；搜索和写入部分失败。

> 🚨 **red = 有主分片没分配 = 那部分数据已经不可读写。** 这是最高优先级。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血 1** | 若有节点宕机 → **先重启该节点** | 节点回来后 ES 自动分配（默认延迟 1 分钟） |
| **止血 2**（不想等 1 分钟） | `curl.exe -s -X POST "http://localhost:9201/_cluster/reroute"` | 立即开始分配（后台异步） |
| **定位 1** | `curl.exe -s "http://localhost:9201/_cat/shards?v&h=index,shard,prirep,state,node,unassigned.reason&s=state"` | 列出 UNASSIGNED 分片，`unassigned.reason` 给出线索 |
| **定位 2** | `curl.exe -s "http://localhost:9201/_cluster/allocation/explain?pretty"` | **真相来源**：逐节点列出为什么不能分配 |
| **修复** | 按 `explain` 的结论对号入座（见下表） | 分片分配成功，转 green |
| **若无效** | → 确认是否真的丢盘。若是，只能接受数据丢失：<br/>`POST /_cluster/reroute` + `allocate_stale_primary`（**会丢数据**，最后手段） | — |

**按 `unassigned.reason` 对号入座**：

| reason | 含义 | 动作 |
|--------|------|------|
| `NODE_LEFT` | 节点离开过 | 节点回来即可；不想等就 `reroute` |
| `INDEX_CREATED` | 新建索引还没分配 | 检查是否有足够节点/磁盘 |
| `ALLOCATION_FAILED` | 分配重试耗尽（默认 5 次） | `POST /_cluster/reroute?retry_failed=true` |
| `REROUTE_CANCELLED` | 被 reroute 命令取消 | 重新 `POST /_cluster/reroute` |
| `NEW_INDEX_RESTORED` / `EXISTING_INDEX_RESTORED` | 刚恢复的快照 | 等待自动分配 |
| `REPLICA_ADDED` | 刚加了副本 | 加节点，或降副本数 |

**常见根因与修复**：

| 根因 | 判定方法 | 修复 |
|------|---------|------|
| 分配被禁用 | `GET /_cluster/settings` 看 `cluster.routing.allocation.enable` | `PUT /_cluster/settings {"persistent":{"cluster.routing.allocation.enable": null}}` |
| 磁盘水位 | 见 [E1](#-e1-磁盘水位触发只读块) | 先解决磁盘 |
| 分配过滤/感知规则配错 | `explain` 里 `filter` / `awareness` decider 报 NO | 检查 `index.routing.allocation.*` 设置 |
| 节点数 < 副本数+1 | 副本数 ≥ 节点数 | 加节点，或降副本数（**生产慎用**） |

**预防**：至少 3 个 master 候选节点；副本 ≥ 1；磁盘告警 80%。

**原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 5

## 🔴 E3 熔断触发（HTTP 429）

**一眼识别**：HTTP **429**，报错含 `Data too large`，类型 `circuit_breaking_exception`。

> ⚠️ **熔断跳了是"事故差点发生"的告警，不是误报。** 不要调高阈值。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血 1** | `curl.exe -s "http://localhost:9201/_tasks?detailed=true&actions=*search*"` | 找出耗时最长的查询 |
| **止血 2** | `curl.exe -s -X POST "http://localhost:9201/_tasks/<task_id>/_cancel"`（**只取消这一个**） | 内存压力下降 |
| **止血 3** | 若 fielddata 占用高：<br/>`curl.exe -s -X POST "http://localhost:9201/_cache/clear?fielddata=true"` | 腾出堆空间（查询会短暂变慢） |
| **定位** | `curl.exe -s "http://localhost:9201/_nodes/stats/breaker?pretty"` | 看**哪个**熔断器在跳 + 跳了多少次 |
| **修复** | 按跳的熔断器对号入座（见下表） | 根因消除 |
| **若无效** | → 转 [E9 深分页超限](#-e9-深分页超过-max_result_window)（大查询常同时是深分页） | — |

**按哪个熔断器在跳来定位**（这张表是最快的路径）：

| 熔断器 | 说明什么 | 动作 |
|--------|---------|------|
| **fielddata** | 在 **text 字段上聚合/排序** | → 转 [E4](#-e4-text-字段聚合排序失败)，改用 keyword 子字段 |
| **request** | 单个查询太大（聚合桶过多） | 降聚合 `size`、加前置过滤 |
| **parent** | 整体内存压力大 | 降并发 / 加堆 / **减分片数** |
| **in_flight_requests** | 请求体过大 | 拆小 bulk（每批 1000~5000 条）和 search |
| **accounting** | 分片或段太多 | 减分片、forcemerge（课 15） |

**默认阈值**（供对照）：parent 95%、fielddata 40%、request 60%、in_flight 100%、accounting 100%（均为 JVM 堆百分比）。

**预防**：堆使用率持续 > 85% 就该扩容或优化；fielddata 长期应接近 0。

**原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 7

## 🟡 E4 text 字段聚合/排序失败

**一眼识别**：查询报 `search_phase_execution_exception`，root_cause 含 **`Fielddata is disabled on [字段名]`** 和 `Please use a keyword field instead`。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 临时开启 fielddata（**仅应急，吃堆内存**）：见下方 JSON | 查询立刻可用 |
| **定位** | `curl.exe -s "http://localhost:9201/<索引>/_mapping?pretty"` | 确认该字段是 `text`，有无 `.keyword` 子字段 |
| **修复** | 建带 keyword 子字段的新索引 → reindex → 别名切换 | 根治（课 11 + 课 15） |
| **若无效** | → 转 [E3 熔断触发](#-e3-熔断触发http-429)（开了 fielddata 后很可能接着熔断） | — |

```json
// enable-fielddata.json（应急用，非根治）
{ "properties": { "<字段名>": { "type": "text", "fielddata": true } } }
```
```powershell
curl.exe -s -X PUT "http://localhost:9201/<索引>/_mapping" `
  -H "Content-Type: application/json" --data-binary "@enable-fielddata.json"
```

> ⚠️ **这只是争取时间**。开启 fielddata 会把整列词项加载进 JVM 堆，是 OOM 头号来源。**根治必须改映射。**

**预防**：建索引时就规划——分词搜索用 `text`，聚合排序用 `keyword`，两者都要就配 multi-fields（课 5）。

**原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 1

## 🟡 E5 写入报类型解析失败

**一眼识别**：`document_parsing_exception`，reason 含 `failed to parse field [xxx] of type [xxx]`，caused_by 是 `For input string: "..."`。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血 1** | 若写入链路被整批卡住 → 先给该字段加 `ignore_malformed: true` | 写入恢复（脏字段被跳过） |
| **定位** | `curl.exe -s "http://localhost:9201/<索引>/_mapping?pretty"` | 看到字段声明类型 vs 实际传入值 |
| **修复** | **首选修数据源**（脏数据不该进 ES）；次选用 pipeline 转换（课 11） | 根治 |
| **若无效** | → 转 [E6 bulk 部分失败](#-e6-bulk-部分失败被静默吞掉)（确认失败范围） | — |

```json
// ignore-malformed.json
{ "properties": { "<字段名>": { "type": "long", "ignore_malformed": true } } }
```

> ⚠️ **实测坑**：加了 `ignore_malformed` 后，脏值**不进索引（搜不到、聚合不到）但原封不动留在 `_source` 里**。会造成"数据看起来存进去了但就是搜不到"的困惑。

**预防**：生产用 `dynamic: strict`；配 `ignore_malformed` 兜底；**监控写入失败率**（静默丢弃比报错更危险）。

**原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 2

## 🟡 E6 bulk 部分失败被静默吞掉

**一眼识别**：批量写入后条数对不上，但**程序没抛异常**——因为 bulk 整体返回 **HTTP 200**。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 检查响应的 `errors` 字段（见下方代码） | 拿到 `true` 则确有失败 |
| **定位** | 遍历 `items`，筛出 `status >= 400` 的项 | 得到失败 id 与原因 |
| **修复** | 修复数据后重投失败项；失败项进死信队列，不静默丢弃 | 数据补齐 |
| **若无效** | → 转 [E5 写入类型不匹配](#-e5-写入报类型解析失败)（最常见根因） | — |

```javascript
const resp = await client.bulk({ operations })
if (resp.errors) {                    // ← 不写这行，失败就被吞了
  for (const item of resp.items) {
    const op = item.index || item.create
    if (op.error) console.error(op._id, op.error.type, op.error.reason)
  }
}
```

**预防**：**所有 bulk 调用必须判 `errors`。** 这是 ES 客户端集成的第一条铁律。

**原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 3

## ⚪ E7 改字段类型被拒

**一眼识别**：`illegal_argument_exception`，reason 为 `mapper [字段名] cannot be changed from type [X] to [Y]`。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 无——这是设计限制，不是故障。应用继续用旧索引 | 服务不受影响 |
| **修复** | ① 建新索引（正确映射）② reindex ③ 别名原子切换 ④ 删旧索引 | 新映射生效，应用零改动（前提：应用认别名） |
| **若无效** | → 检查是否**新增字段**而非改类型（新增字段是允许的） | — |

**预防**：映射显式声明 + 用索引模板固化（课 5 + 课 15）+ **应用只认别名**。

**原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 4

## ⚪ E8 集群 yellow（副本未分配）

**一眼识别**：`GET /_cluster/health` 的 `status` 为 `yellow`；主分片全在，缺的是副本。

> 💡 **yellow 不影响读写**，但**失去高可用**——此刻再挂一个节点就可能变 red。**别无视它。**

| 步骤 | 动作 | 预期 |
|------|------|------|
| **定位** | `curl.exe -s "http://localhost:9201/_cat/shards?v&h=index,shard,prirep,state,unassigned.reason&s=state"` | 确认 `prirep = r` 的副本未分配 |
| **修复 A**（单节点学习环境） | `PUT <索引>/_settings` 设 `number_of_replicas: 0` | 立刻 green（**生产不要这么做**） |
| **修复 B**（生产） | 加数据节点，让副本有地方放 | 副本分配成功 |
| **若无效** | → 转 [E2 集群 red](#-e2-集群-red主分片未分配) 用 `allocation/explain` 查真相 | — |

```json
// replicas0.json
{ "index.number_of_replicas": 0 }
```

**预防**：单节点环境建索引时**显式写 `"number_of_replicas": 0`**（课 3 起反复强调）；生产至少 1 副本。

**原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 5

## ⚪ E9 深分页超过 max_result_window

**一眼识别**：报错含 `Result window is too large`，root_cause 给出具体数字（如 `[10] but was [10000]`）。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 减小 `from` 值，先恢复查询 | 查询可用 |
| **定位** | 确认 `index.max_result_window`（本机实测默认 **10000**） | 知道上限在哪 |
| **修复** | 改用 `search_after`（见下）；或 `scroll`/`PIT` 做全量导出 | 分页深度不再受限 |
| **若无效** | → 转 [E3 熔断触发](#-e3-熔断触发http-429)（大分页常伴随内存问题） | — |

```json
// search-after.json：用上一页最后一条的排序值做游标
{
  "size": 10,
  "query": { "match_all": {} },
  "sort": [{ "price": "asc" }, { "_id": "asc" }],
  "search_after": [12345, "last-id"]
}
```

> 💡 **`search_after` 的两个要点**：① `sort` 必须包含**唯一键**（如 `_id`）做 tie-breaker，否则翻页会漏数据；② 它**不能跳页**，只能一页一页往后翻。

**预防**：需要"跳到第 N 页"的产品需求，本身就该重新设计（用户体验也差）。用 `search_after` + 无限滚动。

**原理**：→ 课 12（实测 `search_after` 连翻 4 页不受限）

## ⚪ E10 刚写入的数据搜不到

**一眼识别**：写入返回 `created`，立刻搜索返回 0 条；等一会儿又能搜到。

> 💡 **这不是故障，是 ES 的近实时（NRT）特性。** 但经常被误报成 bug。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **确认** | 用 `GET /_doc/<id>` 直接取 | **能取到** → 数据确实写进去了，只是还没进可搜索的段 |
| **修复 A**（要立刻可见） | 写入时加 `?refresh=true` | 立即可搜（**每次 refresh 都产生新段，别高频用**） |
| **修复 B**（批量导入） | 导入完成后调一次 `POST /<索引>/_refresh` | 一次性可见 |
| **修复 C**（测试代码） | 等待 1~2 秒再查 | 稳定通过 |
| **若无效** | → 检查 `refresh_interval`（若被设为 `-1`，则永不自动 refresh） | — |

**实测对照**（课 14 五连测）：
```
写后立刻搜 → 0 条
等 1.2s    → 1 条
refresh=true → 立刻可见
GET /_doc/{id} → 实时可见（走 translog，不依赖段）
refresh_interval=-1 → 等多久都搜不到
```

**预防**：**别在写入路径里高频用 `refresh=true`**，这是性能杀手。要实时读，用 `GET /_doc/{id}`。

**原理**：→ 课 3（近实时）＋ 课 14（五连测）

## ⚪ E11 并发写冲突 409

**一眼识别**：HTTP **409**，`version_conflict_engine_exception`。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **修复 A**（覆盖式写入） | 更新请求带 `if_seq_no` + `if_primary_term`（乐观锁） | 版本匹配才写入 |
| **修复 B**（允许重试） | `POST <索引>/_update/<id>?retry_on_conflict=3` | 自动重试 N 次 |
| **修复 C**（串行化） | 把同一文档的更新串行化（队列 / 单写者） | 彻底避免冲突 |
| **若无效** | → 检查是否有多个写入方同时更新同一文档 | — |

> ⚠️ **边界**：ES 的乐观锁**只到单文档级别**，没有跨文档事务。需要多文档原子性 → 用关系库。

**原理**：→ 课 14（实测过期 `_seq_no` 返回 409）

## 🟡 E12 别名无写索引，写入失败

**一眼识别**：`illegal_argument_exception`，reason 含 **`no write index is defined for alias [别名]`**。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **定位** | `curl.exe -s "http://localhost:9201/_cat/aliases/<别名>?v"` | 看别名指向几个索引、`is_write_index` 是谁 |
| **修复** | 给要写入的那个索引标 `is_write_index: true`（JSON 见下） | 写入恢复；搜索仍跨全部索引 |
| **若无效** | → 确认别名是否指向了**不存在的索引**（那样会自动建索引，行为不符预期） | — |

```json
// write-index.json
{ "actions": [{ "add": { "index": "<索引名>", "alias": "<别名>", "is_write_index": true } }] }
```

**原理**：→ 课 15（实测：指定后只写那一个，搜仍跨全部）

## ⚪ E13 破坏性操作被拒

**一眼识别**：通配符删除/关闭报 `illegal_argument_exception`，提示要求显式指定名字（本机 `action.destructive_requires_name=true`）。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **修复** | 用**精确索引名**删除，不用通配符 | 操作成功 |
| **批量删除** | 先 `GET /_cat/indices` 拿到列表，再逐个精确删除 | 安全 |
| **删别名** | 用 `_aliases` 的 `remove`，**不要用 `DELETE /别名`**（实测会被拒） | 别名删除成功 |

> ⚠️ **这是保护机制，别去关它。** 一个手滑的通配符删除就能清空整个集群。

**原理**：→ 课 15（实测 `DELETE /别名` 被拒：`matches an alias, specify the corresponding concrete indices instead`）

## 🟡 E14 ILM 配了但 rollover 不滚动

**一眼识别**：`_ilm/explain` 里 `step` 卡在 `ERROR`，`step_info.reason` 是下面三种之一。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **定位** | `GET /<索引>/_ilm/explain?pretty` 看 `step_info.reason` | 拿到确切原因 |
| **因①** | 报错 `rollover_alias [...] does not point to index [...]` → 别名没带 `is_write_index` | 重建写入索引并显式指定 |
| **因②** | 报错 `found duplicated alias [...] in index template [...]` → **模板里写了 `template.aliases`** | 把 `template.aliases` 去掉 |
| **因③** | 报错 `rollover target is a [concrete index] but one of [alias,data_stream] was expected` → 直接对具体索引 rollover | 改成对别名操作 |
| **验证** | 灌数据超过 `max_docs`，等一个轮询周期 | 自动出现 `-000002` |

正确配法（**三条同时满足**）：

```powershell
# ① 模板里只写 rollover_alias，不要写 template.aliases
# ② 建第一个索引时显式指定 is_write_index
curl.exe -s -X PUT "http://localhost:9201/<索引>-000001" `
  -H "Content-Type: application/json" `
  -d "{\"aliases\":{\"<别名>\":{\"is_write_index\":true}}}"
# ③ 应用只写别名，不写具体索引名
```

> ⚠️ **`_ilm/explain` 刚建好时是没有 `phase` 字段的**，只有 `managed: true`。要等 ILM 第一次轮询跑过才出现 `phase`/`action`/`step`。看到没有 `phase` 别以为配错了。

> ⚠️ **改模板不影响存量索引**：给老索引补挂 ILM 要单独 `PUT /<索引>/_settings` 设 `index.lifecycle.name` + `index.lifecycle.rollover_alias`。

**原理**：→ 课 15（三种报错原文均为本机 9.5.1 实测）

## 通用诊断命令（不知道从哪下手时，按顺序敲）

```powershell
# 1. 集群整体健康（第一步永远看这个）
curl.exe -s "http://localhost:9201/_cluster/health?pretty"

# 2. 未分配分片 + 原因
curl.exe -s "http://localhost:9201/_cat/shards?v&h=index,shard,prirep,state,node,unassigned.reason&s=state"

# 3. 分配真相（分片问题的唯一权威来源）
curl.exe -s "http://localhost:9201/_cluster/allocation/explain?pretty"

# 4. 磁盘
curl.exe -s "http://localhost:9201/_cat/allocation?v"

# 5. 堆内存与熔断
curl.exe -s "http://localhost:9201/_cat/nodes?v&h=name,heap.percent,ram.percent,cpu"
curl.exe -s "http://localhost:9201/_nodes/stats/breaker?pretty"

# 6. 正在跑的任务（找昂贵查询）
curl.exe -s "http://localhost:9201/_tasks?detailed=true&actions=*search*"

# 7. 线程池拒绝情况
curl.exe -s "http://localhost:9201/_cat/thread_pool/search?v&h=node_name,active,queue,rejected"
curl.exe -s "http://localhost:9201/_cat/thread_pool/write?v&h=node_name,active,queue,rejected"

# 8. 索引级别：哪些索引最大
curl.exe -s "http://localhost:9201/_cat/indices?v&s=store.size:desc"

# 9. ILM 状态（配了 ILM 却没动静时看这个）
curl.exe -s "http://localhost:9201/<索引>/_ilm/explain?pretty"
```

> 💡 **PowerShell 用户注意**：本机**没有 Git Bash**，过滤请用 `Select-String`（`grep` 不可用）。复杂 JSON 一律 `--data-binary @文件.json`。

## 查不到怎么办

本手册覆盖 **13 个** ES 高频症状。如果这里没有你遇到的症状：

1. 用上面的「通用诊断命令」收集现场信息
2. 走 `_cluster/allocation/explain`（分片类）或 `_tasks`（查询类）拿具体原因
3. 仍无解 → 现场取证排查（`debug` skill）

**本手册不负责定位具体 bug**——它只覆盖领域典型症状的预案。
