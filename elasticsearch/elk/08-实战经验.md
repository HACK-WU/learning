## 🚫 适用边界与反模式

### 什么时候不该用 ELK

> **"不该用"比"怎么用"更值钱**——这是从"会用"到"用对"的分界线。

| 场景 | 为什么不适合 | 该用什么替代 |
|------|-------------|-------------|
| **只按标签筛、几乎不做全文检索** | 你为倒排索引和分片付出了成本，却只用了它的标签过滤能力 | Loki / ClickHouse 等标签或列式方案；云厂商日志服务 |
| **日志量极小（几台机器、每天几百 MB）** | 一套 ES + Kibana 的常驻内存、运维与升级成本，远超"找个地方存日志"的收益 | 先归档（对象存储 / 冷备）+ `grep`/`journalctl`；等量级上来再迁移 |
| **日志只是"留痕"，几乎没人查** | 索引与分片资源买了却不用，属于纯浪费 | 采集后直写对象存储，按需批量导入 |
| **强合规要求"日志只追加、不可改不可删"** | ES 的索引可被删除/覆盖，**默认没有 WORM 能力**；快照仓库也只是文件 | 专门的合规归档系统；或至少在 ES 之外保留一份不可变副本 |
| **团队里没人愿意维护它** | 集群要滚版本、要调分片/ILM、要盯磁盘水位线——**它是个需要人管的系统，不是个装完就忘的软件** | 托管服务（云日志 / Elastic Cloud）把运维外包 |
| **只在容器/K8s 里跑、没有常驻机器** | Beats 的设计前提是"本机 + 常驻 + 单一数据类型"，容器会漂移 | 容器侧采集器（DaemonSet 式 / OTel Collector） |
| **已有成熟可观测体系（已上 OTel / 已有云日志）** | 再引入第二套采集与存储 = 双倍成本 + 数据不一致 | 跟现有体系走，只在确有缺口时补 |

> 一句话：**ELK 擅长"全文检索 + 多字段组合查询 + 已有 Elastic 生态"；离开这三条就要重新算账。**
> 更完整的选型对比见 [final-课程手册.md](final-课程手册.md) 第九章 9.1，以及 [10-场景解法库.md](10-场景解法库.md) 场景 8。

### 高频反模式（能跑，但迟早出事）

1. **用 `latest` 标签** —— 某次重启后版本悄悄变了，四件套还可能互相不兼容。**版本钉死**（本教程全程 9.5.3）
2. **把重解析放在采集端** —— Beats processors 能力弱、CPU 还花在业务机上。清理、打标记可以；grok/多输出/缓冲交给 Logstash 或 Ingest
3. **把 registry 当临时文件** —— 它是**状态**不是缓存。容器一 `recreate` 就没了，Filebeat 会从头重读整个文件（见故障模式 2）
4. **只在 UI 里手点配置** —— Data View / 索引模板 / ILM / 连接器 / 规则全点一遍，**没有代码化就不可重建、不可回滚**。本教程的结课项目把全部资产压进 `bootstrap.py` 幂等重放
5. **把指标和日志塞进同一个 data stream** —— 两者字段形态与保留策略完全不同（指标是周期驱动、数值为主）。按 `event.dataset` 分开
6. **让 Kibana 用 `elastic` 超管账号连 ES** —— 违反最小权限。用 `kibana_system`（本课程课 2 的实测：`down -v` 后该密码一并失效，Kibana 报 401）
7. **一个索引通吃所有来源** —— 不按 `<type>-<dataset>-<namespace>` 分，就失去了按来源定保留期、定分片、定权限的能力
8. **以为"关了 TLS = 安全关了"，或反过来"开了 TLS = 安全了"** —— 认证与授权是另一回事；反过来，TLS 也不等于授权做对了（见案例 1）
9. **备份只备日志，不备 `.kibana`** —— 日志可重采，**看板/规则/连接器才是不可再生的资产**（见案例 2 的同类教训）
10. **把 ES 直接暴露到公网** —— 这是 2020 年 Meow 攻击吃掉数千个数据库的直接原因（见案例 1）。**9200/9300 不对公网开放**，这是红线
11. **告警阈值拍脑袋** —— "`>0` 就报" + 1 分钟轮询 = 告警风暴，值班会迅速学会忽略它（见故障模式 10）
12. **副本数设 0 图省空间** —— 单节点上能省一点，但那是把"可恢复"换成了"没有冗余"。日志可重采≠可以不要副本

### ⚠️ 被误判为故障的正常现象

> 这一类"假故障"吞噬的排障时间最多。**先确认它是不是正常**，再动手。

| 现象 | 其实是正常的 | 判据 |
|------|-------------|------|
| 集群 health 是 **yellow** | 单节点 + 1 副本必然 yellow——副本无处安放，**数据一条不少** | `_cat/indices` 看 `pri`/`rep`；节点数 ≥ 2 才会 green |
| 采集端"卡住"、延迟变大 | **背压**：下游慢 → 队列积压 → 采集端减速。短期是**延迟**不是丢数据 | 看 Logstash 队列指标与 ES 写入耗时；恢复下游后自动追上 |
| ES 恢复后**查不到刚写的日志** | 队列还在排空，事件一条条刷出，不是丢了 | 等一会儿（本课程实测：刚 healthy 时仍是旧计数，稍后刷全 13 条） |
| `@timestamp` 和日志里写的时间**差 1 小时** | 默认 `@timestamp` = **采集时间**，不是事件时间 | 本课程实测差 **1 小时 6 分**；配 Logstash `date` 或 Ingest `date` 后对齐 |
| 字符串字段出现 `text` + `.keyword` 两个 | 动态映射的默认行为（`text` 分词可搜 + `.keyword` 可聚合） | 想只要 keyword，用动态模板把 string 收敛为 keyword（本课程课 10 实测） |
| `_source` 里有值，但 `term` 查不到 | `ignore_dynamic_beyond_limit: true`（`logs@settings` 默认）**不建索引** | 对照 `_source` 与 `_mapping`；"能存"不等于"能查" |
| 同版本 Filebeat，`ecs.version` 不一样（`1.12.0` vs `8.0.0`） | 它是**数据遵循的 ECS 规范版本**，不是组件版本 | 本课程课 9 实测现象；成因未深究，只作现象记录 ⏳ |
| event log 体积是业务数据的几倍 | 里面绝大部分是**定时任务心跳**（本课程实测：`.ds-.kibana-event-log-ds-*` **288,379 条 / 59 MB**，是业务数据的 **600 倍体积**，其中 **140,516 条**来自 taskManager 心跳） | 查 `.kibana-event-log-ds` 的 `event.action` 分布 |
| 配好 ILM 后**不立刻生效** | 默认 **10 分钟**轮询一次 | `GET /<ds>/_ilm/explain` 看 `check-rollover-ready`；`_cluster/settings` 的 `poll_interval` |
| 单节点上"冷热迁移"后数据没挪窝 | 单节点角色 `cdfhilmrstw` 同时具备所有 tier，迁移只是改 `_tier_preference` 标记 | `_cat/nodes` 看角色；真冷热需要多节点 |

## 🔥 高频故障模式

> 每条固定**五段式**：症状（可观测）→ 根因 → 排查路径 → 修复 → 预防。
> **症状必须可观测**：写"服务很慢"无效，要写"某字段 term 查询恒为 0 命中，且 `_source` 里有值"。
> 已收录 **10 条**（候选 15 条按「踩中概率 × 后果严重度」筛出，淘汰项见文末）。

### 故障模式 1：索引模板缺 `composed_of`，告警永远不触发（本项目最凶险）

- **症状（可观测）**：
  - 告警规则的状态一直是 `OK`，**从来不 FIRING**，且**全程不报任何错**
  - 用 `term` 精确查 `log.level: "ERROR"` → **0 命中**；但 `_source.log.level` 明明写着 `ERROR`
  - `GET /<data-stream>/_mapping` → `log.level` 的类型是 **`text`**（正常应为 `keyword`）
  - Kibana Lens 里拖 `log.level` 维度 → 报 `match_only_text fields do not support sorting and aggregations` 一类错误（`text` 不可聚合）
- **根因**：自定义索引模板 `priority=200` **顶掉**了内置 `logs` 模板（`priority=100`）；由于没声明 `composed_of`，内置模板的组件模板（`logs@settings` / `ecs@mappings` / `logs@mappings`）**全部不生效** → ECS 字段映射丢失 → `log.level` 被**动态映射**猜成 `text` → `term` 精确查询命中不了 → 告警的查询条件恒为空 → **静默失效**。
  失效链：`缺 composed_of` → `ECS 映射失效` → `log.level 退化为 text` → `term 命中 0` → `告警静默`
- **排查路径**：
  1. `GET /_index_template/<你的模板>` → 看 `priority` 是否 > 100、**`composed_of` 是否为空**
  2. `GET /<data-stream>/_mapping` → 看关键字段是 `keyword` 还是 `text`
  3. `GET /<data-stream>/_search` 用 `term` 查一次已知存在的值 → 命中 0 即确诊
- **修复**：模板里**显式声明** `composed_of`（至少包含 `logs@settings` / `logs@mappings` / `ecs@mappings`，再叠加自己的组件模板）；改完让**新代后备索引**生效（`POST /<ds>/_rollover`），或删掉 data stream 重灌——**旧分片的映射不可改**
- **预防**：任何自定义索引模板**必须** `composed_of` 引用内置模板；上线前做一次"`term` 精确查询冒烟"（能命中才算通过）
- **来源**：**【实测】** 本课程结课项目（两个坑叠加才被发现，修复后两代映射才一致）

> 对应速查条目：**[09-排障速查手册.md](09-排障速查手册.md) · 症状 1**

### 故障模式 2：Filebeat registry 未持久化，容器重建后数据翻倍

- **症状（可观测）**：
  - `docker compose up -d`（recreate）之后，文档数**翻倍**：本课程实测 **1000 条 → 2420 条**
  - 同一份日志出现两份甚至多份；`log.offset` 出现重复值
  - 数据没丢、查询也不报错，**只是每个数字都变大**（所以最难发现）
  - `docker compose exec filebeat ls /usr/share/filebeat/data/registry` → 空或不存在
- **根因**：registry（记录"每个文件读到第几字节"）默认写在**容器可写层**。容器 `recreate` 后这一层没了 → Filebeat 认为所有文件都是**全新文件** → 从头重读一遍。
  ⚠️ 注意：这不是 Filebeat 的 bug，是**你没给它一个能活过重建的家**。
- **排查路径**：
  1. `docker inspect <filebeat容器> --format '{{json .Mounts}}'` → 看 `/usr/share/filebeat/data` 是否挂了卷
  2. 对数：文件实际行数 vs 文档数（本课程就是靠"1000 行长 vs 2420 文档"抓到的）
  3. `docker compose exec filebeat ls -la /usr/share/filebeat/data/registry/filebeat/` → 看 registry 是否存在
- **修复**：
  1. compose 里把 registry 落到**命名卷**：`- filebeat-registry:/usr/share/filebeat/data`
  2. 已经翻倍的数据：按时间范围清重复，或直接删 data stream 重新灌
- **预防**：**registry 必须持久化**——它是 at-least-once 语义的前提，不是缓存
- **来源**：**【实测】** 本课程结课项目（1000 → 2420）

> 对应速查条目：**[09-排障速查手册.md](09-排障速查手册.md) · 症状 2**

### 故障模式 3：默认 ILM 没有 delete 阶段，磁盘被日志慢慢写满

- **症状（可观测）**：
  - 磁盘使用率**只涨不降**，`_cat/allocation` 显示某节点逼近水位线
  - 某个 data stream 的后备索引一路长：`...-000001` … `...-0012xx`，**从没有一个被删掉**
  - `GET /_ilm/policy/filebeat` → `phases` 里**只有 `hot`**，没有 `delete`
  - 最后写入开始报错：`index [...] blocked by: [TOO_MANY_REQUESTS/12/disk usage exceeded flood-stage watermark]`（或索引被置 `index.blocks.read_only_allow_delete`）
- **根因**：Filebeat 与 `logs` 两个默认策略**实测完全相同**——只有 `hot` 阶段，`rollover(max_age=30d, max_primary_shard_size=50gb)`，**没有 warm / cold / delete**。
  → **日志永不自动删除**；而且小集群上 `50gb` 阈值可能一年都碰不到，等于**连滚动都不会发生**。
  → 磁盘涨到 **95%（flood stage，官方默认阈值）** 时，ES 会给该节点上所有含分片的索引加只读块，**写入被阻塞**（磁盘降回 90% 以下自动解除）。
- **排查路径**：
  1. `GET /_ilm/policy/<name>` → 数 `phases` 里有几个阶段、有没有 `delete`
  2. `GET /<ds>/_ilm/explain` → 看当前 `phase` / `action`（`check-rollover-ready` = 在等条件）
  3. `GET _cat/allocation?v` + `GET _cluster/settings?include_defaults=true&filter_path=*.cluster.routing.allocation.disk.watermark.*` → 看磁盘与水位线
- **修复**：
  1. **应急**：`GET _cluster/allocation/explain` 定位 → 加磁盘 / 手动删旧后备索引 / 临时抬高水位线（**只是止血，不是解法**）
  2. **根治**：自建 ILM 策略（`hot: rollover` → `warm: forcemerge + 降副本` → `delete: 保留 N 天`），通过索引模板的 `index.lifecycle.name` 绑到 data stream
- **预防**：**ILM 上线前必须检查 `phases` 里有没有 `delete`**；给 85% / 90% / 95% 三档水位线配告警（官方默认值）
- **来源**：**【实测】** 本课程课 10（默认策略 phases 只有 hot）＋ **【官方】** 水位线阈值 85% / 90% / 95%、flood stage 行为（[cluster shard allocation settings](https://www.elastic.co/guide/en/elasticsearch/reference/current/modules-cluster.html)）

> 对应速查条目：**[09-排障速查手册.md](09-排障速查手册.md) · 症状 3**

### 故障模式 4：字段爆炸——整条日志被拒，或"能存不能查"

- **症状（可观测）**——两种形态：
  - **严格模式**：写入直接报 `document_parsing_exception: Limit of total fields [20] has been exceeded while adding new fields [22]`（**整条日志被拒**）
  - **宽松模式**：写入**成功**，但 `GET /<idx>/_mapping` 只收了少数字段；`_search` 搜 `custom.field_25` → **0 命中**，而 `_source` 里**有值**（本课程课 10 实测）
- **根因**：动态映射会给**每个新字段名**建一条 mapping entry。日志里一旦有高基数内容被当成字段名（把整个 JSON 当键、用 trace-id / 用户输入当字段名），字段数就会暴涨。
  `logs@settings` 里默认 `ignore_dynamic_beyond_limit: true` → **不报错但不建索引**，于是变成"数据在、查不到"这种最难查的形态。
  ⚠️ 阈值：Filebeat 默认 `index.mapping.total_fields.limit = 12500`（超了拒写）。
- **排查路径**：
  1. `GET /<idx>/_mapping` → 数字段数量级，找可疑的高基数字段名
  2. `GET /<idx>/_settings?include_defaults=true&filter_path=*.total_fields.limit` → 看上限
  3. 对照 `_source` 与 `_mapping` → **在 `_source` 有、在 `_mapping` 无 = 被静默丢弃**
- **修复**：
  1. 在处理链上 `remove_field` 掉高基数/无用字段（**首选**，治本）
  2. `dynamic_templates` 把 string 收敛为 `keyword`（避免 `text` + `.keyword` 双份）
  3. 抬高 `total_fields.limit` —— **只是止血**，字段数还会继续涨
- **预防**：上线前梳理字段清单；定期 `_field_caps` 体检字段数趋势；**禁止把 ID 类值当字段名**
- **来源**：**【实测】** 本课程课 10（严格/宽松两模式对照）

> 对应速查条目：**[09-排障速查手册.md](09-排障速查手册.md) · 症状 4**

### 故障模式 5：`add_field` 是**追加**不是覆盖，`host.name` 被污染成数组

- **症状（可观测）**：
  - 一条文档的 `host.name` 是**数组**：`["09d21480270c", "web-01"]`
  - 按主机做 terms 聚合时桶数不对（真实主机 + 容器 ID 混在一起）
  - 告警按 `host.name` 分组时分组错乱
- **根因**：ECS 的 `[host][name]` **已由 Filebeat 写入**（容器里是容器 ID）；Logstash 的 `mutate` / `add_field` 是**追加**语义，同名就变数组。
  更隐蔽的一点：`add_field` 是 mutate 的**通用选项、在同一 mutate 块里最后执行**——你以为能让靠前的 `convert` 先跑，实际顺序不听你的。
- **排查路径**：
  1. `GET /<idx>/_search` 抽一条文档 → 看 `host.name` 是字符串还是数组
  2. 做一次 `terms` 聚合 → 看桶名里有没有混进容器 ID（`09d21480270c` 这种 12 位十六进制）
- **修复**：先 `remove_field => ["[host][name]"]` **再写**真实主机名。
  ⚠️ 更该先想一步：**生产环境 Filebeat 是每台机器一个，`host.name` 本来就是对的**——本项目之所以要覆盖，是因为采集器跑在容器里（容器名不是业务机名）。**别画蛇添足。**
- **预防**：写 ECS 已有字段之前，先确认目标字段"存不存在、是追加还是覆盖"
- **来源**：**【实测】** 本课程结课项目（4 个生产级坑之一）

> 对应速查条目：**[09-排障速查手册.md](09-排障速查手册.md) · 症状 5**

### 故障模式 6：multiline pattern 覆盖不全，日志行被吞或粘连

- **症状（可观测）**：
  - **行数对不上**：文件 1000 行，只落成 700 条文档（或反过来，一段堆栈被切成 9 条）
  - 抽一条文档看 `message`：**里面含多行**，且含不该在一起的两条日志（比如一行 JSON 被并进了上一行文本日志）
- **根因**：multiline 的 pattern 语义是「**不匹配 pattern 的行 = 上一行的续行**」。
  只写 `'^[0-9]{4}-[0-9]{2}-[0-9]{2}'`（日期开头）时，**以 `{` 开头的 JSON 行不被认为是"新事件"**，于是被并进上一行 → JSON 行"消失"。
- **排查路径**：
  1. **先对数**：`wc -l` 文件行数 vs 文档数（这是最快的入口）
  2. 抽文档看 `message` 是否含多行、含多条日志
  3. `filebeat test config` 校验 multiline 配置语法
- **修复**：pattern 里**把每一种"新事件行首"都写进去**：`pattern: '^([0-9]{4}-[0-9]{2}-[0-9]{2}|\{)'`（日期开头 **或** `{` 开头）
- **预防**：多格式混排的日志源，先把所有行首枚举出来再写 pattern；配好后**必须做一次计数对照**
- **来源**：**【实测】** 本课程结课项目（4 个生产级坑之一）

> 对应速查条目：**[09-排障速查手册.md](09-排障速查手册.md) · 症状 6**

### 故障模式 7：自定义索引名与模板不匹配，data stream 建不起来、链路完全不进数据

- **症状（可观测）**：
  - Filebeat 启动后**反复**报：`could not put data stream: 400 Bad Request: illegal_argument_exception: no matching index template found for data stream [demo-app]`
  - `_cat/indices` 是空的，**整条链路一条数据都没进**
- **根因**：9.x 下你写的自定义 `index:` 名（如 `demo-app-%{+yyyy.MM.dd}`）会被当作 **data stream 名**；而 data stream 必须匹配某个索引模板的 `index_patterns`，且那个模板必须声明 `data_stream: {}`。只设 `setup.template.name` 是**不够**的。
- **排查路径**：
  1. 看 Filebeat 日志原文（`docker compose logs filebeat`）
  2. `GET /_index_template/<name>` → 看 `index_patterns` 与 `data_stream` 字段
  3. 比对：模板 pattern 能不能覆盖你写的那个名字
- **修复**：最小链路阶段**用 Filebeat 默认行为**（自带模板 + 默认 data stream），先跑通再加复杂度；确实要自定义，就**完整写模板**（`data_stream: {}` + `index_patterns` + `composed_of` + ILM）
- **预防**：**改索引名 = 改整套模板契约**，不是改一个字符串
- **来源**：**【实测】** 本课程课 3（真实翻车记录，已原样写进讲义）

> 对应速查条目：**[09-排障速查手册.md](09-排障速查手册.md) · 症状 7**

### 故障模式 8：ECS 兼容模式重命名字段，照抄老教程的字段名静默失效

- **症状（可观测）**：
  - `%{COMMONAPACHELOG}` 解析后，`clientip` / `verb` / `bytes` 这些字段"**找不到**"
  - 后面的 `convert => {"bytes" => "integer"}` 或 `if [clientip]` **不报错也不生效**
  - ES 里能查到 `source.address`，查 `clientip` 是 0 命中
- **根因**：9.x Logstash 默认 `pipeline.ecs_compatibility: v8`，内置 grok 模式的**输出字段名已按 ECS 改名**：
  `clientip`→`source.address`、`verb`→`http.request.method`、`request`→`url.original`、`httpversion`→`http.version`、`response`→`http.response.status_code`、`bytes`→`http.response.body.bytes`
- **排查路径**：
  1. `--config.test_and_exit` 的输出里会有一行 `Pipeline 'main' is configured with 'pipeline.ecs_compatibility: v8'` —— **这是最早的提示**
  2. output 里临时加 `stdout { codec => rubydebug }`，看**真实字段名**长什么样
- **修复**：改用 ECS 新名（推荐）；或显式 `pipeline.ecs_compatibility: disabled`（**不推荐**，会与整个生态脱节）
- **预防**：**照抄老教程的 grok 字段名 = 定时炸弹**；配完先用 rubydebug 看一遍真实字段再写下游逻辑
- **来源**：**【实测】** 本课程课 7（本课最重大发现，含 `convert` 空操作实证）

> 对应速查条目：**[09-排障速查手册.md](09-排障速查手册.md) · 症状 8**

### 故障模式 9：处理链改变了字段名，`when` 条件静默失效

- **症状（可观测）**：
  - 配了 `when.contains.message: "ERROR"` 的 processor / 过滤分支**永远不生效**，而且**不报任何错**
  - 文档里 `message` 字段**不见了**，多了一个 `event.original`
  - 采集端打标记（`tags`）、丢字段等动作"像没执行过"
- **根因**：Filebeat 模块（或 Ingest pipeline 的 `rename` 处理器）会把原始文本从 `message` **改存到 `event.original`**（本课程课 5 / 课 9 实测：模块路径下 `message` 消失、`event.original` 出现）。任何依赖 `message` 的条件因此**静默失效**。
- **排查路径**：
  1. 抽一条文档 → 看有没有 `message`、有没有 `event.original`
  2. `GET /<idx>/_mapping` → 确认字段实际叫什么
  3. 逐条检查处理链里每个 `when` 依赖的字段，**在那一刻**是否还存在
- **修复**：条件改用 `event.original`（或 `[log][original]`）；或调整处理顺序，在 rename **之前**处理
- **预防**：任何 `when` 条件上线前，确认被判断的字段**在当前处理链的那个位置**确实存在——**静默失效是最难查的一类问题**
- **来源**：**【实测】** 本课程课 5 / 课 9

> 对应速查条目：**[09-排障速查手册.md](09-排障速查手册.md) · 症状 9**

### 故障模式 10：告警配置四连坑——动作被清空 / 导入不生效 / 静默 404 / 告警风暴

- **症状（可观测）**——四种形态：
  - **A**：改了规则之后，规则里的 `actions` **全没了**（不再发通知）
  - **B**：导入的规则**不生效**，查一下发现 `enabled: false`
  - **C**：调实例静默接口 → **404**
  - **D**：每天大量重复告警，值班开始忽略它（"狼来了"）
- **根因**：
  - **A**：PUT 规则是**整体替换**不是 merge，漏带 `actions` 就被清空（本课程实测坑）
  - **B**：官方明示 **"Rules are disabled on export"** —— 导出即禁用，导入后默认 `enabled: false`
  - **C**：实例 id 是 **`kibana.alert.instance.id`**（`groupBy: all` 时即动作组名，如 `query matched`），**不是**告警文档的 `_id`
  - **D**：阈值写成"`>0` 就报" + 短轮询；且**没配 `recovered` 动作组**（修好了没人说，值班一直 P0）
- **排查路径**：
  1. `GET /api/alerting/rules/_find` → 看规则的 `actions` 与 `enabled`
  2. `GET /.alerts-*/_search` → 看告警文档里的 `kibana.alert.instance.id`（官方推荐在**告警索引别名**上查，`groupBy: all` 时该字段即动作组名）
  3. 看告警实例数随时间的变化趋势 → 判断是不是风暴
- **修复**：
  - **A**：改规则 = **GET 全量 → 改 → PUT 全量**
  - **B**：导入后调 `_enable`
  - **C**：静默用 `kibana.alert.instance.id`
  - **D**：阈值改"**持续 N 分钟超 M**" + `alert_delay` 防抖；**`recovered` 动作组永远要配**；计划内变更用**维护窗口**（本课程实测：维护窗口内照常检测、**零投递**）
- **预防**：**告警三件套缺一不可**——阈值防抖 / 恢复通知 / 维护窗口；再加静默，共四道闸门
- **来源**：**【实测】** 本课程课 12 / 结课项目 ＋ **【官方】** "Rules are disabled on export"

> 对应速查条目：**[09-排障速查手册.md](09-排障速查手册.md) · 症状 10**

## 📰 真实事故案例复盘

> ⚠️ 两个案例均**联网核查**并标注来源与时点。**找不到可信来源就不写**——虚构事故比没有更糟。

### 案例 1：Meow 攻击——未加认证的 Elasticsearch 被批量清库（2020-07）

- **经过**：2020 年 7 月初出现一个自动化脚本（社区称 "Meow attack"），它**扫描公网**寻找**无需认证**即可访问的数据库，找到后**删光全部数据**，再建一个名字末尾带 `-meow` 的随机索引作为"签名"。**5 天内超过 3,000 个数据库被清空**；到 7 月底，受影响实例**超过 4,000 个**。截至 7 月 22 日，主要受害类型是 **Elasticsearch（1,395 个）**、MongoDB（383 个）、Redis（54 个）。公开报道的受害方包括一家 VPN 服务商，以及一个 30TB / 约 120 亿条记录的 Elasticsearch 集群（被删掉大半）。
- **根因**：**把未加认证的 Elasticsearch 实例暴露在公网**上。攻击者不需要破解任何密码——没有密码可破。
- **损失**：数据被**永久删除**（攻击者既没留勒索信、也没留后门，纯粹是销毁）；公开案例中一个集群约 4TB 数据被删除。⚠️ 注意：这**不是**某个版本的漏洞，而是**配置疏忽**。
- **厂商回应（说明"这跟版本漏洞无关"）**：Elastic 时任产品管理副总裁 Steve Kearns 对媒体表示——**"就我们所知，受 Meow 攻击影响的集群，都没有开启我们免费的或付费的任何安全特性"**，并强调 **Elastic Cloud 上安全默认开启且不可关闭**。MongoDB 方面也说明受影响的是**社区版的错误配置**，不是企业版/Atlas。
  → 这句话把责任边界划得很清楚：**不是"某个版本的洞"，是"没人去开那个开关"。** 9.x 默认开安全，正是对这一类事故的正面回应。
- **教训（可迁移的一条）**：**"能连上"和"该让谁连上"是两件事。** 本课程反复强调的 `9200/9300 不对公网开放` + `9.x 默认开安全` + 最小权限，正是针对这一类事故；而上线 Checklist 里的"安全检查"不是形式——**它的反面是数据被永久删掉**。
- **来源**：[New 'Meow' attack has deleted almost 4,000 unsecured databases（BleepingComputer, 2020-07-25 更新）](https://www.bleepingcomputer.com/news/security/new-meow-attack-has-wiped-dozens-of-unsecured-databases) ｜ [Purr-fect storm of 3,000+ insecure databases（The Register, 2020-07-24）](https://www.theregister.com/2020/07/24/meow_database_attack/) ｜ ['Meow' attacks wipe more than 1,000 exposed databases（TechTarget，含 Elastic 官方回应）](https://www.techtarget.com/cybersecurity/news/252486611/Meow-attacks-wipe-more-than-1000-exposed-databases)（**三来源交叉核查于 2026-09**）

### 案例 2：GitLab 2017-01-31 数据库事故——五套备份全部失效

- **经过**：2017-01-31 约 23:30 UTC，GitLab.com 一名工程师在处理主从复制故障时，**误在 primary（`db1.cluster.gitlab.com`）**上执行了清空 PostgreSQL 数据目录的操作——他以为自己在 secondary。发现错误后 1~2 秒内就终止了命令，但 **约 300GB 生产数据已经没了**（约 5,000 个项目、5,000 条评论、700 个新建账号受影响，约 6 小时的数据丢失）。
- **根因**：单点误操作只是**导火索**，真正的根因是**五套备份/复制机制没有一套能用**：
  1. **`pg_dump` → S3 每日备份**：脚本调用的是 PostgreSQL **9.2** 的二进制，而库是 **9.6**，`pg_dump` 直接报错退出 → **每天静默失败**，S3 桶里只剩零字节文件（旧文件已被生命周期清掉）
  2. **失败告警邮件**：脚本本来会发失败邮件，但当时组织内的 **DMARC 变更**导致收信端静默拒收 → **告警失效数月无人察觉**（"没有失败邮件"和"成功"是同一个信号）
  3. **LVM 快照**：生产库**根本没有计划内**的 LVM 快照策略；唯一存在的那个，是当天 17:20 工程师为了**另一个无关项目**（给 staging 测连接池）临时手动打的
  4. **Azure 磁盘快照**：只对 **NFS 服务器**开启，**数据库服务器没开**（当时的判断是"有其他备份就够了"）
  5. **WAL 归档**：**从未配置** → 时间点恢复（PITR）这条路本来就不存在
  最终靠那个**与备份无关的、6 小时前的临时 LVM 快照**恢复；恢复耗时约 **18 小时**（受网络存储 60 Mbps 带宽拖累）。
- **损失**：约 18 小时停机 + 约 6 小时数据丢失。GitLab 全程**直播恢复过程**并公开了内部聊天记录与详细 postmortem，成为业界最常被引用的运维公开文档之一。
- **教训（可迁移的一条）**：**"有备份"和"能恢复"是两件事。** 备份**没有被监控、没有被演练**，就等于没有备份。
  → 映射到 ELK：**快照 `SUCCESS` 不等于能恢复**；**只备日志不备 `.kibana`（看板/规则/连接器）**等于把不可再生的资产留在了外面。你会做本课程课 12 那个 **Saved Objects 误删复生演练**（导出 → 删 → 导入 `successCount=3` → 规则回来但 `enabled=false`），正是这个教训的实践版。
- **来源**：[GitLab 官方 postmortem（2017-02-10）](https://about.gitlab.com/2017/02/10/postmortem-of-database-outage-of-january-31/) ｜ [GitLab 官方事故说明（2017-02-01）](https://about.gitlab.com/2017/02/01/gitlab-dot-com-database-incident/) ｜ [Databarracks：The GitLab recovery - what can we learn?](https://www.databarracks.com/blog/the-gitlab-recovery-what-can-we-learn)（**核查于 2026-09**）
