# 设计决策

> 判定标准：**换个人来做，可能选另一个方案，而且他也有道理**。
> 下面 4 个决策点都是从"真跑踩出来的"——每个都写清「选了什么 / 为什么 / 放弃的方案差在哪 / 付出了什么代价 / 什么情况下该改选」。

---

## 决策点 1：日志解析放在哪一层？

### 候选方案对比

| 维度 | A. Filebeat processors | B. Logstash filter | C. ES Ingest Pipeline |
|------|----------------------|-------------------|---------------------|
| 额外组件 | 无（采集端自闭环） | +1 个 JVM 服务（约 900MB 驻留） | 无（ES 自带） |
| 解析能力 | 只有 `dissect`/`script`/`grok` 的弱化版；**没有 date 插件的时区校准**，没有条件分支的完整表达 | 最强：grok / json / date / mutate / dissect / 条件分支 / 失败打标签全套 | 中：pipeline processor 齐全，但改一次要 reload pipeline |
| 调试体验 | 最差：改了要重启 Filebeat，看不到中间态 | 最好：`stdout { codec => rubydebug }` 能逐字段打印 | 中：`_simulate` API 可离线试，但不能看真实事件 |
| 失败可观测性 | 弱 | 强：`tag_on_failure` 给失败文档打标签，Kibana 里一眼可见 | 中：有 `on_failure` 但配置繁琐 |
| 水平扩展 | 天然随采集端扩展 | 需要单独扩 Logstash 实例 | 随 ES 节点扩展 |
| 运维复杂度 | 最低 | 高（多一个有状态服务要养） | 低 |

### 最终选择

**B. Logstash filter**，且解析逻辑全部集中在一个文件（`实现/logstash/pipeline/shop-api.conf`）。

### 选择理由

1. **本项目有两种格式 × 两个来源 = 4 条解析路径**。只有 Logstash 能用条件分支把它们写在同一个文件里，且每条路径**独立打失败标签**（`_json_parse_failed` / `_grok_parse_failed` / `_nginx_parse_failed` / `_path_host_failed`）。方案 A 和 C 要么表达不了，要么会很别扭。
2. **`date` 插件的时区校准在本项目里是硬需求**。日志里写的是 `+08:00` 的本地时间，必须用 `timezone => "Asia/Shanghai"` 精确转成 UTC 存进 `@timestamp`。Filebeat 的 `timestamp` processor 没有等价能力，用方案 A 会得到**偏移 8 小时的时间轴**——这种错在 Dashboard 上表现为"白天没日志、凌晨全是日志",很难第一眼发现。
3. **教学价值**：课 7/8/9 三个课时的核心就是"管道三件套 + 可靠性 + 放在哪"，主线落在 Logstash 上，实战项目跟着主线走，知识才连得起来。

### 付出的代价

- **多一个有状态服务**：Logstash 实测驻留 891MB，还得给它配持久化队列卷；`docker compose` 从 3 个服务变 4 个。
- **多一跳网络**：Filebeat → Logstash → ES，比直连 ES 多一次序列化与网络往返。
- **多一个故障点**：实测中 Logstash 重启会让 Filebeat 报 `Failed to publish events caused by: write ... connection reset by peer`——虽然最终会重试成功，但**日志里会留下红色错误**，不明就里的人会以为数据丢了。

### 什么情况下该改选另一个

- **只有一种格式、无时区校准需求**（比如日志本身就是 UTC ISO8601）→ 改选 **A**，去掉 Logstash 这一跳，省 900MB 内存和一整类运维问题。
- **已经是纯 Elastic Cloud 托管、不想运维任何中间件** → 改选 **C**，Ingest Pipeline 随集群走，零额外组件。
- **吞吐大到单个 Logstash 扛不住、又不想养 Logstash 集群** → 也倾向 **C**，让 ES 的数据节点承担解析。

## 决策点 2：`host.name` 该保留 Filebeat 的容器主机名，还是覆盖成真实业务机？

### 候选方案对比

| 维度 | A. 原样保留（容器 ID） | B. 直接 add_field 覆盖 | C. 先删后写（本项目选） | D. 干脆换个字段名 |
|------|---------------------|---------------------|---------------------|-----------------|
| 实现难度 | 零 | 一行 | 两行（两个 mutate 块） | 改字段名 + 改 Dashboard + 改告警 |
| 实测结果 | `host.name = "09d21480270c"`，**600 条文档全部落进这个桶** | 变成**数组** `["09d21480270c","web-01"]` | `host.name = "web-01"`，干净 | `app.host = "web-01"`，干净但非 ECS |
| 对 Dashboard 的影响 | "按主机下钻"多出一个假主机，且它命中 100% 文档 | 同样污染：聚合里容器 ID 与真实主机并列 | 正确 | 正确，但 Kibana 上的既有图表全部要重建 |
| 与 ECS 规范的关系 | 符合 ECS（`host.name` 就是机器名） | 破坏字段类型（string vs array 混用） | 符合 ECS | **偏离 ECS**，以后对接其它 ECS 工具要额外映射 |

### 最终选择

**C. 先 `remove_field [host][name]`，再由日志内容写入真实主机名**，两条解析分支都写同一个字段。

### 选择理由

1. **方案 A 的问题是"没报错所以没人发现"**。`host.name` 有值、查询不报错、图表能画——只是**多了一个假主机，而且它命中 100% 的文档**，把真实主机的占比全部稀释。这类"静默失真"比报错危险得多。
2. **方案 B 会踩 Logstash 的一个隐蔽语义**：`add_field` 遇到已存在的字段时**不是覆盖而是追加**，于是同名字段变成数组。实测 `host.name = ["09d21480270c", "web-01"]`。字段类型从 string 变 array，虽然 ES 不报错（多值是合法的），但后面所有 `terms` 聚合、Lens 拆分、告警分组都会把两个值当成两个独立主机。
3. **方案 D 虽然干净，但放弃了 ECS**。本项目的主线是"按 ECS 规范落地"，为了绕开一个字段冲突就自造字段名，等于把问题留给下一个人。

### 付出的代价

- **多一次字段删除操作**：每次事件多一个 `remove_field`，代价可忽略，但**配置里多了一处"必须理解上下文才能看懂"的代码**——所以在 `实现/logstash/pipeline/shop-api.conf` 里写了 12 行注释解释它为什么存在。
- **强依赖"部署形态"这个前提**：这条规则**只在"一台 Filebeat 收多台机器日志"时成立**。如果把 Filebeat 换成每台机器一个 DaemonSet，容器 `host.name` 本来就是对的，**这条规则会变成有害的**——它会把正确的主机名删掉。
- **和编排强耦合**：换部署形态时必须回来同步改这条规则，属于"容易忘"的隐性契约。

### 什么情况下该改选另一个

- **Filebeat 是 DaemonSet / 每台机器一个实例** → 改选 **A**，`host.name` 天然正确，**必须删掉本项目那条 remove_field**。
- **日志里根本没有主机名，但采集端知道**（比如按目录区分实例）→ 改选 **C 的变体**：不是从日志内容取，而是从 `log.file.path` 反推（本项目 nginx 分支正是这么做的）。
- **团队已有成熟的非 ECS 字段约定** → 改选 **D**，但要接受"和生态工具对接时要额外做字段映射"的长期成本。

## 决策点 3：ILM 策略怎么绑到 data stream 上？

### 候选方案对比

| 维度 | A. 用内置 `logs` 模板，不自定义 | B. 自定义模板但不管 `composed_of` | C. 自定义模板 + 显式 `composed_of`（本项目选） | D. 不建模板，直接改 backing index |
|------|---------------------------|-------------------------------|------------------------------------------|------------------------------|
| 配置量 | 零 | 少（一个 template） | 中（多一行 composed_of） | 每次 rollover 都要改 |
| 滚动/保留策略 | 只能跟随 Elastic 默认（30d/50GB） | 生效 | 生效 | 生效但只对当前分片 |
| ECS 字段映射 | 正确继承 | ❌ **全部丢失** | 正确继承 | 正确（但每次新分片都要重来） |
| 实测后果 | 保留期不可控 | `log.level` 退化成 `text` → **告警永远 0 条** | 两代映射完全一致 ✓ | 无法自动化 |

### 最终选择

**C. 自定义索引模板 `logs-shopapi`（priority=200）并显式声明 `composed_of: ["logs@mappings","logs@settings","ecs@mappings"]`**，把 ILM 策略 `shopapi-7d` 写进 `template.settings.index.lifecycle.name`。

### 选择理由

1. **本项目要的不是"能滚动"，而是"按我的规则滚动"**：hot 阶段 `rollover(1gb, 1d)`、warm 阶段 `forcemerge`、delete 阶段 `7d`。内置策略不可改，方案 A 直接出局。
2. **方案 B 是这次实战里最惨痛的一课**。自定义模板的 priority 一旦高于内置 `logs`（内置是 100），它会**顶掉**内置模板；此时不写 `composed_of`，内置那套 ECS 字段映射（`logs@mappings` / `ecs@mappings`）就全部不生效，`log.level` 退回 ES 的默认动态映射（`text` + keyword 子字段）。
   现象极具迷惑性——实测：
   - 全时段 `term log.level=ERROR` → **118 条**
   - 近 5 分钟全部文档 → **50 条**
   - **两者取交集 → 0 条**
   因为新一代索引里 `log.level` 是 `text`（小写化），`term` 精确匹配 `"ERROR"` 永远不中。于是**告警规则每次执行都算 0，永远不触发**。不报错、不告警，只是永远没有数据。
3. **方案 D 破坏了 data stream 的意义**：data stream 的价值就在于"策略跟模板走、新分片自动继承"，手工改分片等于把自动化拆掉。

### 付出的代价

- **配置多了一个必须理解的概念**：`composed_of` 这行看起来像样板代码，删掉"好像也没事"——直到某天 rollover 出新分片，字段类型静默变了。这是**典型的"删一行代码，三个月后炸"**。
- **历史分片不会自动纠正**：发现时 gen2 已经带着错映射写进去了。ES 的字段映射**不可改**，只能再 rollover 一次（gen3）让新分片用对映射，或者整个 data stream 删掉重灌。本项目采用了**后者**——重置后所有分代映射才完全一致。
- **对内置模板的版本依赖**：`logs@mappings` / `ecs@mappings` 是 Elastic 提供的组件模板，跨大版本升级时它们的名字或内容若有变化，这行要跟着改。

### 什么情况下该改选另一个

- **完全能接受默认保留期**（30d/50GB 够用）→ 改选 **A**，一行配置都不写，也永远不会踩 `composed_of` 的坑。
- **只需要改分片数、replica 数这类设置，不碰 ILM** → 也可以走 **A** + 在 data stream 层面覆盖，风险更小。
- **用 Elasticsearch 的 `_lifecycle` 与自定义模板都想省、又要自动化** → 没有第三个选项，方案 D 的"手工改分片"在规模化下不可行。

## 决策点 4：告警结果往哪落？

### 候选方案对比

| 维度 | A. `.index` 连接器（本项目选） | B. Webhook | C. Email | D. Slack / Teams |
|------|---------------------------|-----------|----------|------------------|
| 许可要求 | **basic 即可** | **gold** 起 | gold 起 | gold 起 |
| basic 许可实测 | ✅ 可用 | ❌ 创建时 403 | ❌ 403 | ❌ 403 |
| 落地形态 | 文档写回 ES 索引，可再用 Kibana 查 | HTTP 推送到外部 | 邮件 | 群消息 |
| 可验证性 | 最高：`_search` 就能看见渲染结果 | 需要一个接收端才能验证 | 需要收件箱 | 需要群 |
| 适合什么 | 教学 / 自建平台 / 与其它系统通过 ES 集成 | 已有 IM 网关 | 已有邮件网关 | 已有 IM |

### 最终选择

**A. `.index` 连接器**，把告警文档写回 `shopapi-alerts` 索引。

### 选择理由

1. **这是 basic 许可下的现实约束，不是偏好**。实测 `GET /api/actions/connector_types` 返回 73 种类型，basic 许可下 **enabled 的只有两个**：`.index` 与 `.server-log`。想用 webhook / email / Slack，必须上 gold 许可。
2. **可验证性对教学项目是硬指标**。告警"发出去了没有"必须能**当场拿证据**——`.index` 连接器把渲染后的文档直接落进索引，`_search` 一次就能看到 `{{context.value}}` 渲染成了多少条、命中的是哪台主机。webhook 方案还需要额外搭一个接收端，教学成本陡增。
3. **它顺带展示了"告警可与其它系统通过 ES 集成"这个真实模式**：把告警当数据写回 ES，再由自建平台消费，是很多公司在 basic 许可下的实际做法。

### 付出的代价

- **人不会主动收到通知**。写回 ES 索引 = "可查"而不是"会响"。生产上真要靠它叫人，还得再加一个"轮询 `shopapi-alerts` 索引"的外发程序——本项目没做，这是**明确的功能缺口**。
- **告警索引会无限增长**。本项目**没有给 `shopapi-alerts` 配 ILM**，长期跑会一直涨。生产上必须补一条保留策略。
- **连接器选择反过来限制了规则类型**：为了让动作组语义清晰，规则类型选 `.es-query`（只有 `query matched` / `recovered` 两个动作组）；换成其它规则类型时动作组语义不同，payload 也要跟着改。

### 什么情况下该改选另一个

- **已经买了 gold 许可、且有 IM 网关** → 改选 **D**，告警要"能叫人"才有意义；`.index` 可保留作为"留痕"的第二动作（一条规则挂多个动作是支持的）。
- **有自建事件总线** → 改选 **B**，webhook 直接打到自家的告警聚合平台。
- **只是想知道告警有没有触发、不需要通知人**（比如做数据质量监控的巡检）→ **A 就够了**，不用加许可成本。

## 附：被否决但曾认真考虑过的两个点

| 决策 | 曾考虑 | 为什么没选 |
|------|-------|-----------|
| Kibana 是否加密 saved object | 不配 `XPACK_ENCRYPTEDSAVEDOBJECTS_ENCRYPTIONKEY`，靠默认 | 不配的话连接器与规则**创建直接 500**（它们是加密 saved object）。必须配，且**这个 key 一旦更换，已存的连接器密码全部解不开**——所以它不是"随便填一个"的字段，生产上要走密钥管理 |
| 告警通知口径 | 用默认的 `onActionGroupChange` | 默认口径下，告警从 `untracked → active` 只通知**一次**；之后一直 `active` 就不再重复通知。实测时很容易误判为"告警没生效"。本项目改成 `onActiveAlert`——**但要清楚这是为了演示方便**，生产上 `onActionGroupChange` 才是防打扰的正解 |
