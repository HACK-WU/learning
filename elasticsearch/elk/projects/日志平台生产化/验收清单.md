# 验收清单

> 用法：**逐条跑命令、对期望**，做对了打勾。全部勾完 = 你真的把这套东西做成了。
> 所有命令的当前目录都是 `实现/`（`cd 实现` 之后执行）。
> 认证信息统一 `elastic / ELKlearn2026`；Kibana 端口 5601，ES 端口 9200。

---

## A 组：起得来、起得对（3 项）

### A1 ☐ 四个容器都在跑，且 ES 是 healthy

```bash
docker compose ps --format "table {{.Name}}\t{{.Status}}"
```

**期望**：`cap-es` 的 Status 里含 **`(healthy)`**；`cap-kibana` / `cap-logstash` / `cap-filebeat` 都是 `Up`。
**没通过怎么办**：ES 不是 healthy → `docker logs cap-es | tail -30`。端口被占（`playground/07-reliability` 没关）→ 先 `cd ../../playground/07-reliability && docker compose down`。

---

### A2 ☐ Kibana 的状态是 `available`（不是 `unavailable`）

```bash
curl -s -u elastic:ELKlearn2026 localhost:5601/api/status | python3 -c "import json,sys;print(json.load(sys.stdin)['status']['overall']['level'])"
```

**期望**：输出 **`available`**。
> ⚠️ 这一步是本项目**最容易被"容器 Up 就以为没事"骗过去**的地方。`cap-kibana` 显示 `Up` 但内部可能一直认证失败：

```bash
docker logs cap-kibana 2>&1 | grep -i "unable to authenticate"
```

**若出现上述报错** → `kibana_system` 密码没设上，执行 `docker compose up -d setup` 然后 `docker compose restart kibana`。
**没通过怎么办**：`docker logs cap-kibana 2>&1 | tail -30`。

---

### A3 ☐ 三个命名卷都存在

```bash
docker volume ls --format "{{.Name}}" | grep elk-capstone
```

**期望**：出现 **3 个**：`elk-capstone_es-data`、`elk-capstone_logstash-queue`、`elk-capstone_filebeat-registry`。
**为什么是 3 个**：少任何一个都会导致"重建即失真"——少 `es-data` 数据丢、少 `logstash-queue` 队列丢、少 `filebeat-registry` **数据翻倍**。

## B 组：采集与解析（6 项）—— 本项目的主战场

### B1 ☐ 造数据脚本能跑，两个来源都产出

```bash
python3 scripts/gen-logs.py 600 180 --nginx 400
wc -l logs/*.log | tail -1
```

**期望**：输出两行（应用日志 600 条 / 访问日志 400 条），`wc -l` 合计 **1000**。
**注意**：脚本是**追加**写文件，想从零开始先 `rm -f logs/*.log`。

---

### B2 ☐ 文件与落库的条数一致

```bash
curl -s -u elastic:ELKlearn2026 'localhost:9200/logs-shopapi-default/_count'
```

**期望**：`"count"` 等于文件总行数。
**若落库数明显偏多** → 命中了"registry 没落卷"，见 A3 / 反例对照 ⑦。

---

### B3 ☐ ⭐ 解析零失败（本项目的核心验收点）

```bash
curl -s -u elastic:ELKlearn2026 'localhost:9200/logs-shopapi-default/_search' \
  -H 'Content-Type: application/json' \
  -d '{"size":0,"aggs":{"t":{"terms":{"field":"tags","size":20}}}}' \
  | python3 -c "
import json,sys
for b in json.load(sys.stdin)['aggregations']['t']['buckets']:
    print(f\"  {b['key']:36s} {b['doc_count']}\")"
```

**期望**：**只有一行** `beats_input_codec_plain_applied 1000`。
**出现任何 `_` 开头的标签都不合格**：`_json_parse_failed`（多行 pattern 吞行）、`_grok_parse_failed`（文本格式对不上）、`_mutate_error`（mutate 块顺序）、`_date_parse_failed`（时间格式/时区）、`_nginx_parse_failed`、`_path_host_failed`（`WORD` 不认连字符）。

> 注意：**聚合字段是 `tags` 不是 `tags.keyword`** —— `tags` 在 dynamic mapping 下直接就是 `keyword` 类型，写 `tags.keyword` 会得到空结果，容易误判成"没有标签"。

---

### B4 ☐ 两条应用分支都真的解析了（不是"看起来有数据"）

```bash
# JSON 分支：应该有 app.* 字段，且 duration_ms 是数字
curl -s -u elastic:ELKlearn2026 'localhost:9200/logs-shopapi-*/_search' -H 'Content-Type: application/json' \
  -d '{"size":1,"query":{"exists":{"field":"app.trace_id"}},"fields":["log.level","host.name","url.path","duration_ms","http.response.status_code","@timestamp"],"_source":false}' | python3 -m json.tool

# 文本分支：应该有 logger / thread 字段
curl -s -u elastic:ELKlearn2026 'localhost:9200/logs-shopapi-*/_search' -H 'Content-Type: application/json' \
  -d '{"size":1,"query":{"exists":{"field":"logger"}},"fields":["log.level","host.name","url.path","duration_ms"],"_source":false}' | python3 -m json.tool
```

**期望**：
- JSON 分支：`duration_ms` / `http.response.status_code` 是**数字**（不是字符串），`@timestamp` 是日志里的**事件时间**。
- 文本分支：`logger` = `com.shop.XxxService`、`thread` = `http-nio-8080-exec-N`，`log.level` 有值。

> 别用 `_source` 里 `h.get('log.level')` 这种取值——`log.level` 是**嵌套对象**，`_source` 里是 `{"log":{"level":...}}`，取值会得到 `None`，很容易误判成"字段没落"。用 `fields` 参数或 `_source:false` + `fields` 才是准的。

---

### B5 ☐ nginx 分支解析正确，且没有污染业务字段

```bash
curl -s -u elastic:ELKlearn2026 'localhost:9200/logs-shopapi-*/_search' -H 'Content-Type: application/json' \
  -d '{"size":1,"query":{"exists":{"field":"http.request.method"}},"fields":["source.address","http.request.method","url.original","http.response.status_code","http.response.body.bytes","host.name"],"_source":false}' | python3 -m json.tool
```

**期望**：`source.address`（客户端 IP）、`http.request.method`、`url.original`、`http.response.status_code`、`http.response.body.bytes` 都有值，`host.name` 是从**文件路径**反推出来的 `web-0X`。

---

### B6 ☐ `host.name` 里没有假主机

```bash
curl -s -u elastic:ELKlearn2026 'localhost:9200/logs-shopapi-default/_search' -H 'Content-Type: application/json' \
  -d '{"size":0,"aggs":{"h":{"terms":{"field":"host.name","size":20}}}}' \
  | python3 -c "
import json,sys
for b in json.load(sys.stdin)['aggregations']['h']['buckets']:
    print(f\"  {b['key']:20s} {b['doc_count']}\")"
```

**期望**：**只有 web-01 / web-02 / web-03 三个桶**，且三者之和 = 文档总数。
**若出现一串 12 位十六进制（如 `09d21480270c`）且它的计数 = 总文档数** → 容器 `host.name` 没清掉（见 `设计决策.md` 决策点 2）。

## C 组：存储与生命周期（3 项）

### C1 ☐ 数据流分代存在，且绑定了自定义 ILM 策略

```bash
curl -s -u elastic:ELKlearn2026 'localhost:9200/_data_stream/logs-shopapi-default' \
  | python3 -c "
import json,sys;d=json.load(sys.stdin)['data_streams'][0]
print('generation =',d['generation'],'| ilm_policy =',d.get('ilm_policy'))"
```

**期望**：`generation` ≥ 2，`ilm_policy` = **`shopapi-7d`**（不是内置的 `logs`）。

---

### C2 ☐ ⭐ 两代 backing index 的映射完全一致（踩过第 4 个坑的验证）

```bash
python3 - <<'PY'
import json,subprocess
m = json.loads(subprocess.check_output(
  ["curl","-s","-u","elastic:ELKlearn2026","http://localhost:9200/.ds-logs-shopapi-default-*/_mapping"]).decode())
for idx in sorted(m):
    p = m[idx]["mappings"]["properties"]
    print(f"{idx[-6:]}: log.level={p['log']['properties']['level']['type']}  host.name={p['host']['properties']['name']['type']}")
PY
```

**期望**：每一代的 `log.level` 都是 **`keyword`**。
**若某代显示 `text`** → 索引模板缺 `composed_of`（见 `设计决策.md` 决策点 3 / 反例对照 ⑧）。此时该代数据**无法用 `term` 精确匹配**，告警会永远算 0 条。

---

### C3 ☐ ILM 处于正确阶段

```bash
curl -s -u elastic:ELKlearn2026 'localhost:9200/.ds-logs-shopapi-default-*/_ilm/explain' \
  | python3 -c "
import json,sys
for k,v in json.load(sys.stdin)['indices'].items():
    print(f\"{k[-6:]}: policy={v.get('policy')} phase={v.get('phase')} action={v.get('action')}\")"
```

**期望**：写索引（最新那代）`policy=shopapi-7d phase=hot action=rollover`；老一代可能 `action=complete`。

## D 组：消费与告警（4 项）

### D1 ☐ Kibana 侧的资产都建好了

```bash
python3 scripts/bootstrap.py --check
```

**期望**：ES 可达、Kibana `available`。
再确认三样东西存在（`bootstrap.py` 会打印"已存在"）：

```bash
curl -s -u elastic:ELKlearn2026 localhost:5601/api/data_views -H 'kbn-xsrf: true' \
  | python3 -c "import json,sys;print([d['title'] for d in json.load(sys.stdin)['data_view']])"
curl -s -u elastic:ELKlearn2026 localhost:5601/api/actions/connectors -H 'kbn-xsrf: true' \
  | python3 -c "import json,sys;print([(c['name'],c['connector_type_id']) for c in json.load(sys.stdin)])"
curl -s -u elastic:ELKlearn2026 'localhost:5601/api/alerting/rules/_find?per_page=10' -H 'kbn-xsrf: true' \
  | python3 -c "import json,sys;print([(r['name'],r['enabled']) for r in json.load(sys.stdin)['data']])"
```

**期望**：Data View `logs-shopapi-*`；连接器 `capstone-index`（类型 `.index`）；规则 `shopapi ERROR 激增` 且 `enabled=True`。

---

### D2 ☐ 告警窗口里真的能查到数据（不是 0）

```bash
python3 scripts/gen-logs.py 40 1 --burst
sleep 20
curl -s -u elastic:ELKlearn2026 'localhost:9200/logs-shopapi-*/_count' -H 'Content-Type: application/json' \
  -d '{"query":{"bool":{"filter":[{"term":{"log.level":"ERROR"}},{"range":{"@timestamp":{"gte":"now-5m"}}}]}}}'
```

**期望**：`"count"` **大于 5**（规则阈值是 >5）。
**若返回 0**，按顺序排查：① 灌数据落了没有（B2）；② `log.level` 类型对不对（C2）；③ 时间窗口——`--burst` 写的是"此刻"，**超过 5 分钟就滑出窗口了**。

---

### D3 ☐ ⭐ 告警真的落盘了，且 mustache 变量渲染正确

```bash
sleep 60   # 规则 schedule 是 1m
curl -s -u elastic:ELKlearn2026 'localhost:9200/shopapi-alerts/_search?pretty'
```

**期望**：能查到告警文档，形如：

```json
{
  "rule": "shopapi ERROR 激增",
  "group": "query matched",
  "instance": "query matched",
  "hit_count": "37",
  "hit_host": "web-01",
  "hit_level": "ERROR",
  "hit_path": "/health"
}
```

> `hit_count` 的数字**随你实际灌入的 ERROR 条数变化**（这里只是示意），关键看四个 `hit_*` 字段都被**渲染成了真实值**、而不是空字符串或未替换的 `{{...}}` 占位。

**说明**：`group` 与 `instance` 都是 `query matched` 是**正常**的——`.es-query` 规则的动作组固定就这两个，且 `groupBy: all` 时实例 id 就等于动作组名。
**查不到怎么办**：① 看规则有没有执行（`GET /api/alerting/rule/{id}` 里的 `execution_status`）；② 注意 `notify_when` 口径，`onActionGroupChange` 时告警从 active 再变 active **不会**重复通知。

---

### D4 ☐ 备份能建、能导出

```bash
# 快照
curl -s -u elastic:ELKlearn2026 'localhost:9200/_snapshot/capstone-fs/_all?pretty' \
  | python3 -c "import json,sys;print([(s['snapshot'],s['state'],s['shards']['successful'],s['shards']['total']) for s in json.load(sys.stdin)['snapshots']])"

# Saved Objects 导出（alert 是隐藏类型，但可导出；alerting-rule 这个名字是错的）
curl -s -u elastic:ELKlearn2026 -X POST localhost:5601/api/saved_objects/_export \
  -H 'kbn-xsrf: true' -H 'Content-Type: application/json' \
  -d '{"objects":[{"type":"alert","id":"<规则id>"}],"includeReferencesDeep":true}' -o /tmp/exp.ndjson -w "%{http_code}\n"
```

**期望**：快照 `state=SUCCESS`、分片成功数 = 总数；导出 `200`，且 `/tmp/exp.ndjson` 里**除了 `alert` 还自动带上了它的 `action` 连接器**（`includeReferencesDeep` 的作用）。

## E 组：可重建性（2 项）—— 这一组决定"这套东西是不是你的"

### E1 ☐ 配置是代码，不是"手点出来的"

```bash
grep -c "curl" scripts/bootstrap.py
```

**期望**：能数出多条。**判据**：把 `bootstrap.py` 重跑一遍（`python3 scripts/bootstrap.py`），所有资产都显示"已存在/已更新"而**不报错**——说明它幂等、且是唯一事实源。
**反面**：如果这些资产只能在 Kibana 界面上点出来，那么换台机器你就得重新点一遍，且**点错了没有任何记录**。

---

### E2 ☐ 干净重建一次，结果可复现

```bash
docker compose down                                   # 不加 -v，保留数据卷
docker compose up -d
sleep 40
curl -s -u elastic:ELKlearn2026 'localhost:9200/logs-shopapi-default/_count'
```

**期望**：文档数**不变**（`es-data` 卷保住了数据），且 **`filebeat-registry` 卷让 Filebeat 不重读历史文件** → 计数不会翻倍。
**若翻倍** → 检查 compose 里 filebeat 是否挂了 `filebeat-registry:/usr/share/filebeat/data`。
