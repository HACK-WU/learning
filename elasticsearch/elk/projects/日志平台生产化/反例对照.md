# 反例对照

> 下面这版代码**能跑起来、也能在 Kibana 里搜到日志**——这正是它危险的地方。
> 它会在你"看不出问题"的状态下，让数据静默失真、告警永不触发、磁盘慢慢撑爆。
> 逐条对照，看它和 `实现/` 里那版的差别在哪、以及**为什么这个差别要命**。

---

## 反例版本（"看起来能跑"的 4 个文件）

```yaml
# ── 反例 filebeat.yml ──────────────────────────────────────────────
filebeat.inputs:
  - type: filestream
    paths:
      - /var/log/shop/*.log
    parsers:
      - multiline:
          type: pattern
          pattern: '^\d{4}-\d{2}-\d{2}'      # ❌ 只认日期开头
          negate: true
          match: after
    fields_under_root: true                   # ❌ 摊平到根
    fields:
      log_type: app

output.logstash:
  hosts: ["logstash:5044"]
# ❌ 没有 processors、没有 registry 卷（compose 里也没挂）
```

```ruby
# ── 反例 shop-api-naive.conf ───────────────────────────────────────
input { beats { port => 5044 } }

filter {
  grok {
    match => { "message" => "%{COMBINEDAPACHELOG}" }
    tag_on_failure => []                      # ❌ 解析失败不打标签
  }
  mutate {                                    # ❌ add_field 与 convert 同块
    add_field => { "log.level" => "%{level}" }
    convert   => { "duration_ms" => "integer" }
  }
}

output {
  elasticsearch {
    hosts => ["http://elasticsearch:9200"]
    index => "shop-%{+yyyy.MM.dd}"            # ❌ 手工日期后缀
  }
}
```

```yaml
# ── 反例 docker-compose.yml（filebeat 段）────────────────────────────
  filebeat:
    image: docker.elastic.co/beats/filebeat:9.5.3
    volumes:
      - ./filebeat.yml:/usr/share/filebeat/filebeat.yml:ro
      - ./logs:/var/log/shop:ro
      # ❌ 没有 registry 卷
```

```json
// ── 反例：自定义 ILM 模板（不写 composed_of）──────────────────────
{
  "index_patterns": ["logs-shopapi-*"],
  "data_stream": {},
  "priority": 200,
  "template": { "settings": { "index.lifecycle.name": "shopapi-7d" } }
}
```

## 逐条对照（8 条差异）

### ① 多行合并的 pattern 只认日期开头 —— 70% 的日志被吞

| | 反例 | 本项目 |
|---|------|-------|
| 写法 | `pattern: '^\d{4}-\d{2}-\d{2}'` | `pattern: '^([0-9]{4}-[0-9]{2}-[0-9]{2}|\{)'` |
| 实测结果 | 781 条文档里 **130 条 `_json_parse_failed`**——JSON 行全被并进前一条文本日志，`message` 成了多行拼接 | 1000 条文档，**失败标签 0** |

**为什么糟**：多行合并的语义是"**不匹配 pattern 的行 = 上一行的续行**"。只认日期开头，就意味着"以 `{` 开头的行"被当作续行——可它恰恰是新事件的开始。于是 ES 里看到的是"一条文档塞了三四行日志"，JSON 解析当然全失败。
**这个错误极其隐蔽**：文档总数看着差不多，搜索也能搜到内容，只有**去看 `tags` 聚合**才会发现 130 条解析失败。
**判据**：只要你的日志里存在**两种以上"行首特征"**（日期、`{`、`[`、IP……），pattern 就必须把它们都列进去。

---

### ② `fields_under_root: true` 导致 `log.type` / `service.name` 与 ECS 字段撞车

| | 反例 | 本项目 |
|---|------|-------|
| 写法 | `fields_under_root: true` + `fields: {log_type: app}` | 不用 `fields_under_root`，保持 `fields.log_type` |
| 实测结果 | `log.type` 与 ECS 的 `log.type`（日志类型，取值如 `event`/`access`）语义冲突；`service.name` 同理会被 Filebeat 自身的 service 字段覆盖 | `fields.log_type` 独立命名空间，Logstash 里读 `[fields][log_type]` 分流 |

**为什么糟**：`fields_under_root` 的本意是"少一层嵌套、好写查询"，但 ECS 已经把常用字段名占了。摊平之后你和 Elastic 的官方字段**抢同一个名字**，谁赢取决于处理顺序——最后得到的是一个"有时是访问日志类型、有时是 Elastic 自己语义"的字段。
**判据**：**自定义字段一律加前缀或用 `fields.` 命名空间**，别往根上摊。真正配 `fields_under_root` 的场合是"你确定这个名字 ECS 没有、且团队全局统一"。

### ③ `tag_on_failure => []` —— 解析失败静默消失

| | 反例 | 本项目 |
|---|------|-------|
| 写法 | `tag_on_failure => []` | `tag_on_failure => ["_json_parse_failed"]` 等四类标签 |
| 实测结果 | 解析失败时**什么都不发生**：文档照常入库，字段一片空白，`tags` 干净得像没出过事 | 聚合 `tags` 一眼看出哪类解析失败、失败多少条 |

**为什么糟**：这是本题材里最容易犯的错——"把 `tag_on_failure` 关掉，日志看起来就干净了"。**干净的是标签，不是数据。**失败文档以"字段缺失"的形态混在正常数据里，之后你要在 Dashboard 上看到"为什么 `log.level` 有 30% 是空的"时，已经无从查起。
**判据**：`tag_on_failure` **永远不要清空**。它的成本是一行配置，收益是"脏数据可见"。

---

### ④ `add_field` 与 `convert` 写在同一个 mutate 块 —— 类型转换静默失效

| | 反例 | 本项目 |
|---|------|-------|
| 写法 | 一个 `mutate` 块里同时 `add_field` + `convert` | 拆成**两个 `mutate` 块**：先 `add_field`，再 `convert` |
| 实测结果 | 报 `invalid value for BigDecimal(): "%{[app][duration_ms]}"`，`duration_ms` 仍是字符串 | `duration_ms: 568`（integer），`http.response.status_code: 500`（integer） |

**为什么糟**：`add_field` 是 mutate 的**通用选项，在过滤器内最后才执行**。写在同一个块里时，`convert` 先跑——此时字段还不存在，于是转换空转、报错、并且**不中断管道**。结果是"字段看着有值，类型却是字符串"，后续做数值聚合（求 P95、做数值范围查询）全部失效。
**判据**：只要一个 mutate 块里既有"造字段"又有"改字段类型"，**立刻拆块**。

---

### ⑤ `index => "shop-%{+yyyy.MM.dd}"` —— 手工日期后缀

| | 反例 | 本项目 |
|---|------|-------|
| 写法 | 输出到 `shop-2026.09.10` 这种手工拼的索引名 | `data_stream => "true"` + dataset/namespace，由 ES 生成 `logs-shopapi-default` |
| 附属能力 | 需要自己写脚本删老索引 | ILM 策略 `shopapi-7d` 自动 rollover / forcemerge / delete |
| 实测结果 | 索引数随天数线性增长，**没人知道什么时候该删** | rollover 出 gen2，`_ilm/explain` 显示 `phase=hot action=rollover` |

**为什么糟**：手工索引名把三个问题一起引进来了——**① 索引数量无限增长**；**② 分片数每个索引一份**，日积月累压垮集群状态；**③ 想改策略只能对未来生效**。而且这个名字是"写死在管道里"的，改策略要动 Logstash 配置。
**判据**：日志类数据**默认走 data stream**。只有在"按业务线物理隔离、需要不同策略"时才考虑多 data stream，而不是按日期切索引。

### ⑥ 不清理 Filebeat 带进来的容器 `host.name` —— 假主机污染一切聚合

| | 反例 | 本项目 |
|---|------|-------|
| 写法 | 直接 `add_field` 写真实主机名 | `remove_field => ["[host][name]"]` **先删**，再由日志内容写 |
| 实测结果 | `host.name` 聚合出 **4 个桶**：`09d21480270c`（**600 条，命中全部文档**）+ web-01/02/03 | 3 个桶：web-01 374 / web-02 339 / web-03 287 |

**为什么糟**：Filebeat 在容器里跑，它的 `host.name` 是**容器 ID**。这个值和"日志来自哪台业务机"毫无关系，却会命中**每一份**文档。于是"按主机下钻"的饼图上永远有一块 100% 的假主机，真实主机的占比被稀释成看不出差异。
**更隐蔽的是**：直接 `add_field` 覆盖**不会**覆盖，Logstash 的 `add_field` 遇到已存在字段是**追加**，字段会变成数组 `["09d21480270c", "web-01"]`——ES 不报错、图表能画，但每个文档在两个桶里各算一次。
**判据**：**部署形态决定 `host.name` 该不该清**。一台 Filebeat 收多台机器 → 必须清；每台机器一个 DaemonSet → **绝对不能清**（那时容器名就是对的主机名）。

### ⑦ registry 不落卷 —— 容器重建一次，数据翻一倍

| | 反例 | 本项目 |
|---|------|-------|
| 写法 | `volumes` 里只有配置和日志目录 | 多挂一个 `filebeat-registry:/usr/share/filebeat/data` |
| 实测结果 | 改完配置 `docker compose down && up -d` 后，文档数 **1000 → 2420** | 重建后按 offset 续读，不重复 |

**为什么糟**：registry 记录"每个文件读到第几字节"，默认只存在**容器可写层**。容器被 `recreate`（改配置、`down` 再 `up`、升级镜像）时 registry 一起消失，Filebeat 认为所有文件都是新的，**把整个文件从头重读一遍**。
这个坑最阴的地方是：**数据没丢、查询不报错、数字看着也合理**——只是每个数都翻倍。等你在 Grafana / Kibana 上发现"流量曲线突然翻倍但业务没变"，已经查了很久。
**判据**：**任何有状态的采集器，状态目录一律落命名卷。** 同一个道理适用于 Logstash 的 `data/`（持久化队列）。

### ⑧ 自定义 ILM 模板不写 `composed_of` —— 字段类型漂移，告警永不触发

| | 反例 | 本项目 |
|---|------|-------|
| 写法 | `{"priority": 200, "data_stream": {}, "template": {...}}` | 加一行 `"composed_of": ["logs@mappings","logs@settings","ecs@mappings"]` |
| gen1 `log.level` | `keyword` | `keyword` |
| gen2 `log.level` | **`text` + keyword 子字段** | `keyword` |
| 实测后果 | 全时段 `term log.level=ERROR` = **118 条**；近 5 分钟 = **50 条**；**取交集 = 0 条** → 告警窗口里永远是 0，**永远不触发** | 两代映射完全一致，告警正常触发并落盘 |

**为什么糟**：自定义模板 priority 高于内置 `logs`（100）时会**顶掉**内置模板；不写 `composed_of`，内置的 ECS 字段映射就全部不生效，`log.level` 退回 ES 默认动态映射（`text`）。而 ES 的字段映射**创建后不可改**——同一 data stream 的不同 generation 从此带着**不同类型**的同一个字段，跨代查询直接失效（`term` 精确匹配在 `text` 字段上永远不中）。
**这是本项目里唯一一个"不报错、不告警、数字还看着合理"的故障**，也正因如此它最值得记。
**判据**：**自定义索引模板时，先 `GET /_index_template/logs` 看内置模板 `composed_of` 了什么，照抄进来。**

## 一句话总结

反例版的每一行**单看都"没错"**：

- 多行 pattern 认日期——本来就要认日期；
- `fields_under_root` 是官方支持的选项；
- `tag_on_failure => []` 是合法写法；
- `add_field` + `convert` 同块是常见写法；
- 手工索引名是官方文档里的示例；
- `add_field` 覆盖一个字段，直觉上就该覆盖；
- registry 不落卷是默认行为；
- 模板不写 `composed_of`——它甚至不是必填字段。

**但它们组合起来，产出的是"能跑、能搜、数字还好看"的错误系统。** 这正是本实战项目要训练的东西：**不是"能不能跑起来"，而是"跑起来之后，我怎么知道它是对的"。**
