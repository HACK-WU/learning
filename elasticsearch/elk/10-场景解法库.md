## 场景 1：日志量翻 10 倍，集群快撑不住

**场景描述**：业务扩容 + 新接入 3 个服务，日志量从 **5 GB/天 涨到 50 GB/天**。可观测到的现象：磁盘使用率**两周内从 40% 涨到 78%**；`_bulk` 写入耗时从 30ms 涨到 **400ms**；Kibana 查 1 小时窗口从 1s 变成 **8s**。

**🔒 先自己想 30 秒**：第一反应是"加盘"？还是"加节点"？——有没有更便宜的招，是**先把数据变少**？

<details><summary>💡 提示（分四层想，从便宜到贵）</summary>

- **入口层**：这些日志**都有人看吗**？DEBUG 级、健康检查、完整 request body，各自被查过几次？
- **处理层**：一条文档里有多少字段是**从不被查**的？（大字段：完整 stacktrace、原始 JSON、超长 URL）
- **存储层**：热数据和老数据需要**同样的存储成本**吗？副本、段合并、压缩编码，你调过哪个？
- **架构层**：写入的**峰值**和**均值**差多少？需不需要一个"水池"把峰谷拉平？

> 还有一层：**这 50 GB 是真的业务量，还是字段爆炸制造的"假体量"**？先排除后者（见场景 1 的"不适用边界"）。
</details>

<details><summary>📖 展开解法</summary>

### 解法一览（含代价与边界）

| # | 解法 | 能解决到 | 代价 | 适用边界 |
|---|------|---------|------|---------|
| A | **砍掉低价值数据**：采样、丢 DEBUG、`remove_field` 大字段 | 直接砍 **30–60%** 体量（取决于日志构成） | 丢失部分可观测性；**事后想查就没了** | 日志有明显"没人看"的部分；**不适用于审计/合规类** |
| B | **ILM 分层 + `delete`**：hot → warm（forcemerge + 降副本）→ cold → delete | 老数据不再挤占热节点内存与 IO；段合并显著降低查询开销 | 冷数据查询变慢；配置复杂度上升 | 数据有明确"热/冷"划分；**这是本课基本盘，必做** |
| C | **压缩优化**：`index.codec: best_compression`、缩短字段名、只留必要字段 | 磁盘占用下降（官方：以更高压缩比换 CPU） | 写入/查询 CPU 上升 | 磁盘是瓶颈、CPU 有余量时 |
| D | **加缓冲层（Kafka）把采集与写入解耦** | 峰值不再打崩 ES；数据可重放 | 多一个组件要运维；端到端延迟增加 | 写入抖动/峰值明显；团队能运维 Kafka（→ 课 8.3） |
| E | **横向扩容**：加数据节点 / 加盘 | 容量近乎线性提升 | 成本；分片重分布期间有开销 | A–D 都用过仍不够，且预算允许 |
| F | **（反例）抬高 `total_fields.limit` / 只加盘不修 ILM** | 短期让写入恢复 | **制造故障模式 3/4**，把爆炸时间往后挪 | 仅作为**止血**，不可当解法 |

### 推荐路径（递进，不是一次全上）

1. **先砍（A）** —— 成本最低、当天见效。先跑一次"字段被查询频次"盘点，再决定砍什么
2. **定保留期 + 上 ILM 分层（B）** —— 这一步不做，前面砍多少都会被慢慢写满（**这是硬化前提，不是优化**）
3. **压缩优化（C）** —— 磁盘仍紧时再上
4. **还不够 → 缓冲层（D）** —— 把峰值解耦，顺便获得重放能力
5. **最后才是加机器（E）**

### 知识点挂钩

- A → 阶段 2 课 5《模块与处理器》＋ 阶段 3 课 9《该在哪处理》
- B → 阶段 4 课 10《日志的存储策略》(知识点 2/3)
- C → 阶段 4 课 10
- D → 阶段 3 课 8《可靠性与吞吐》(知识点 3：Kafka 缓冲层)
- E → 阶段 4 课 10（分片与副本）＋ ES 主课相关章节

### 什么情况下此方案不适用

- **审计 / 合规类日志不能采样**（A 直接出局）
- **"体量大"其实是字段爆炸造成的**：先去症状 4 确认 `_mapping` 字段数是否在异常增长——先修根因，别急着扩容
- 单节点 Compose 环境上**"冷热迁移"只是改标记**（本课程实测：单节点角色含所有 tier），真分层需要多节点

### 做错会踩的坑

→ 只加盘不修 ILM = [08-实战经验.md](08-实战经验.md) **故障模式 3**（磁盘慢慢满 → flood stage 写不进去）
→ 采样后告警查询条件恒为空 = **故障模式 1**（换了字段/条件但没做冒烟）
→ 抬高字段上限就以为修好了 = **故障模式 4**
</details>

## 场景 2：采集端要停机升级，要求"一条都不丢、也不要重复"

**场景描述**：Filebeat 要从当前版本升级 + 换配置，需停机约 **30 分钟**。业务要求：升级期间产生的日志**一条都不丢**，升级后**不出现重复**。

**🔒 先自己想 30 秒**：日志是写在**文件里**的，所以"采集器停了"是不是等于"日志丢了"？真正决定"丢不丢"的是哪一样东西？

<details><summary>💡 提示（分三段想）</summary>

- **停之前**：有什么**状态**是采集器"记住读到哪了"的？它在哪、能不能活过这次重启？
- **停的期间**：文件会继续长吗？如果会，谁来记住"长到哪了"？
- **起来之后**：它是从**断点续读**，还是把文件当**新文件**从头读？
</details>

<details><summary>📖 展开解法</summary>

### 解法一览（含代价与边界）

| # | 解法 | 能解决到 | 代价 | 适用边界 |
|---|------|---------|------|---------|
| A | **先把 registry 落到命名卷**（若还没落），再升级 | **零丢失、零重复** | 需要 compose 改动 + 一次重建 | **标准答案，先做这个** |
| B | **升级前备份 registry**（`docker cp` 出容器） | 升级失败可回滚到断点 | 手工步骤，容易忘 | A 的补充保险 |
| C | **先让日志轮转 / 短暂停写业务**，再停采集器 | 避免"采集器停了但文件在猛长" | 需业务配合；停写窗口未必有 | 有轮转机制、窗口短 |
| D | **多采集器滚动升级**（每机一个，天然滚动） | 不停采 | 需要多实例；多实例读同一文件会冲突 | 生产环境的多机常态 |
| E | **靠下游缓冲兜**（Kafka / Logstash 持久化队列） | 采集端可短暂停，缓冲顶住 | 组件复杂度 | 已有缓冲层 |
| F | **先备份日志文件 + 清掉 registry 重灌** | 零遗漏 | **必然重复**（at-least-once），要按时间清重 | 日志量小、能接受去重 |

### 推荐路径（递进）

1. **先确认 registry 持久化（A）** —— 没落卷就**先落卷**（这本身就是故障模式 2 的修复）
2. **备份 registry（B）** —— 留一条回滚路
3. **停 Filebeat → 升级 → 起来** —— 靠 registry 从断点续读
4. **对数验收**：升级前后的文档增量 = 文件新增行数（这是**必须做的最后一步**）

### 知识点挂钩

- A / B → 阶段 2 课 4《Filebeat 把文件读进来》（registry 与 offset）
- C → 阶段 2 课 4（文件轮转与 inode）
- D → 阶段 2 课 6《Beats 家族与采集选型》
- E → 阶段 3 课 8《可靠性与吞吐》（持久化队列 / `queue.type: persisted`）
- 「不丢不重」的语义 → 阶段 2 课 4（at-least-once）

### 什么情况下此方案不适用

- **别以为 "`stop` 了就不会重复"** —— registry 没持久化时，重启 = **从头重读整个文件**
- **别用 `tail -f` 的心智模型理解 Filebeat** —— 它记录的是 **offset**，不是"跟着尾巴走"
- **别在升级的同时改 multiline pattern** —— 两个变量一起动，出问题时你分不清是哪个（→ 故障模式 6）

### 做错会踩的坑

→ registry 未持久化 = [08-实战经验.md](08-实战经验.md) **故障模式 2**（实测 **1000 → 2420**）
→ 顺手改了 multiline pattern = **故障模式 6**（行数对不上，你会以为是丢数据）
</details>

## 场景 3：新服务明天上线，要求"当天就能在 Kibana 查到日志"

**场景描述**：一个新服务明天上线，要求：日志进现有平台、在 Kibana 能查、并接入现有告警。你希望这次接完，**以后每接一个服务都不用重新踩坑**。

**🔒 先自己想 30 秒**：这题考的不是"敲哪些命令"，而是**怎么把一个临时任务变成可重复的流程**。想想：配置放在哪？谁负责改？怎么验证接对了？

<details><summary>💡 提示（分三问）</summary>

- **可重建吗**：环境被删了，你能不能在 10 分钟内原样重建出来？
- **可回滚吗**：接错了，能不能回到上一个已知良好状态？
- **可验证吗**：怎么证明"真的接对了"，而不是"看起来有数据"？
</details>

<details><summary>📖 展开解法</summary>

### 解法一览（含代价与边界）

| # | 解法 | 能解决到 | 代价 | 适用边界 |
|---|------|---------|------|---------|
| A | **手工接入**：拷一份 `filebeat.yml` → 改路径 → 重启 → Kibana 手点 Data View / 手点规则 | 当天能上 | **不可重建、不可回滚**；下个服务再踩一遍 | 只有一两个服务、临时验证 |
| B | **模板化接入**：抽象出 `filebeat.yml` 模板 + 索引模板 + ILM + Data View，参数化服务名 | 后续接入 = 填参数 | 前期设计成本；模板要有人维护 | 服务数 ≥3 的常态 |
| C | **代码化幂等重放**：全部资产压进一个脚本（本课程结课项目的 `bootstrap.py`） | 环境可一键重建、可回滚、可进 CI | 要写脚本 + **保证幂等**（查重后不重复创建） | 本课程结课项目的做法 ✅ |
| D | **平台侧自助接入**：业务提交服务名 → 自动生成配置与 Data View | 业务自助，运维不排队 | 要投入做平台；权限与配额要设计 | 服务多、接入频繁 |

### 推荐路径（递进）

1. **先做 B（模板化）** —— 当天就能交付，把"参数"和"结构"分开
2. **再做 C（代码化幂等）** —— 让"重建"从不可能变成可能；这一步顺带把故障模式 1/7 的坑固化进模板
3. **有需要再上 D** —— 接入量大到"运维排队"时才有价值

### 知识点挂钩

- Filebeat 配置 → 阶段 2 课 4
- 处理器 / 模块 → 阶段 2 课 5《模块与处理器》
- 索引模板 + data stream → 阶段 4 课 10
- Data View → 阶段 4 课 11《Kibana 从 Discover 到 Dashboard》
- 告警规则与连接器 → 阶段 4 课 12
- 幂等重放 → 结课项目 [projects/日志平台生产化/README.md](projects/日志平台生产化/README.md)

### 什么情况下此方案不适用

- **正式接入一律代码化**——"只在 UI 里手点"违反反模式 4，代价是**不可重建、不可回滚**
- 一次性实验可以走 A，但**别把 A 当流程**

### 做错会踩的坑

→ 自定义索引名与模板不匹配 = **故障模式 7**（`no matching index template found for data stream`，**一条数据都进不来**）
→ 模板缺 `composed_of` = **故障模式 1**（接进来了，但 `log.level` 退化成 `text`，**告警静默**）
→ 照抄老教程的 grok 字段名 = **故障模式 8**（`clientip` / `bytes` 找不到，`convert` 空跑）
→ 条件分支还在判断 `message`，而模块已把它改存 `event.original` = **故障模式 9**（分支静默失效）
→ 用 `add_field` 写 ECS 已有字段（如 `host.name`）= **故障模式 5**（字段变数组，聚合分组错乱）
→ 只在 UI 手点 = [08-实战经验.md](08-实战经验.md) **反模式 4**
</details>

## 场景 4：一套 ELK 给多个团队共用，且互相看不到对方数据

**场景描述**：公司 3 个团队（A / B / 运维）共用一套 ELK。要求：A 只能看 `teamA-*` 的日志，B 看不到 A 的；各团队能建自己的看板；运维能看全部。

**🔒 先自己想 30 秒**：把"隔离"拆成两层——**能看见哪些数据**（数据可见性）和**能用哪些功能**（功能可见性）。这两层分别在 ES 侧还是 Kibana 侧解决？

<details><summary>💡 提示（分两轴 × 两位置）</summary>

- **数据轴**：能不能靠**索引命名**就把团队分开？如果数据混在同一索引里呢？
- **功能轴**：看板、Data View、告警规则，这些"资产"怎么隔开？
- **ES 侧**手段 vs **Kibana 侧**手段，分别是什么？
- 最后一条：**你会把 `elastic` 超管账号发给团队吗？**（如果会，前面做的隔离全白做）
</details>

<details><summary>📖 展开解法</summary>

### 解法一览（含代价与边界）

| # | 解法 | 能解决到 | 代价 | 适用边界 |
|---|------|---------|------|---------|
| A | **索引前缀 + Kibana 角色（index pattern 权限）** | 粗粒度隔离，配置简单 | 同一索引内无法区分团队；**命名纪律必须做死** | 团队数据天然分索引（最常见） |
| B | **Kibana Spaces** + 角色绑定 Space | 界面层面彻底隔离，各团队互不干扰 | ⏳ **需 Gold 及以上许可**；Spaces **不隔离底层数据** | 想给每个团队"一个门户" |
| C | **文档级安全（DLS）+ 字段级安全（FLS）** | 同一索引内按字段值过滤（如 `team: "A"`），**真·多租户** | ⏳ 需更高许可；**DLS 改写查询、有性能开销**；排查不直观 | 数据混在同一索引、必须按行隔离 |
| D | **物理隔离**（每团队一套集群 / 至少独立索引 + 独立 Space） | 最强隔离，互不影响 | 成本最高、运维翻倍 | 合规/安全要求极高 |
| E | **只做"礼貌共享"**：共用 Kibana、靠约定不看别人的 | 零成本 | **这不是隔离** | 内部互信小团队 |

### 推荐路径（递进）

1. **先把索引命名纪律做死** —— `logs-<dataset>-<namespace>`，`namespace` = 团队（→ 课 10）
2. **用角色 + 索引前缀做第一层隔离（A）** —— 成本最低、覆盖 80% 需求
3. **界面隔离上 Spaces（B）** —— 需要时再加
4. **确实要同行隔离才上 DLS（C）** —— 它是"最强但最贵"的一张牌

### 知识点挂钩

- 索引命名 `logs-<dataset>-<namespace>` → 阶段 4 课 10
- Data View / Space → 阶段 4 课 11
- 账号与最小权限（`kibana_system` 而非 `elastic`）→ 阶段 1 课 2 ＋ 阶段 4 课 12
- 备份与权限 → 阶段 4 课 12

### 什么情况下此方案不适用

- **DLS 不是"免费的隔离"** —— 它改写查询、有开销，且**不隔离 `.kibana` 资产**（看板/规则仍要靠 Spaces 或权限管）
- **把 `elastic` 超管账号发给团队 = 隔离白做**（[08-实战经验.md](08-实战经验.md) 反模式 6）
- ⏳ **Spaces / DLS 的具体许可门槛因版本而异**，本课程 **basic 环境未实测**——落地前先核对你的许可

### 做错会踩的坑

→ 用超管账号 = **反模式 6**
→ "内部网络所以不用认证" = **案例 1**（Meow 攻击的根因就是"能连上就当自己人"）
</details>

## 场景 5：审计要求日志留 1 年，但最近 7 天要能秒查

**场景描述**：合规要求日志保留 **365 天**；业务要求**最近 7 天**的查询必须在 **2 秒内**返回。当前全部数据都在热节点，磁盘**装不下 1 年**。

**🔒 先自己想 30 秒**：先算一笔账——**1 年到底要多少盘**？然后问：1 年前的数据**多久被查一次**？查的时候**能等多久**？

<details><summary>💡 提示（分三层 + 一个算式）</summary>

- **热层**（天天查、要秒回）：放多少天？
- **温/冷层**（偶尔查、能等）：降到什么配置？
- **归档层**（几乎不查）：能不能放到**比磁盘更便宜**的介质上？
- 算式：`日增量 × 365 × 膨胀系数 × (1 + 副本数)` —— 先算出来，可能你根本不需要"分层"
</details>

<details><summary>📖 展开解法</summary>

### 解法一览（含代价与边界）

| # | 解法 | 能解决到 | 代价 | 适用边界 |
|---|------|---------|------|---------|
| A | **ILM 分层**：hot（7 天）→ warm（forcemerge + 降副本）→ cold → delete（365 天） | 热数据快、冷数据省、到期自动删 | 冷层查询变慢；节点角色要规划 | **本课基本盘**（课 10）✅；单节点也能配策略（但物理上还是同一块盘） |
| B | **冻结索引（frozen / partially mounted）** | 冷数据几乎不占内存，可在快照上查 | 需要快照仓库 + 更高许可；**首次查询慢** | 极少查、可接受冷启动 |
| C | **searchable snapshots（可搜索快照）** | 冷数据直接在对象存储上查，**本地存储可省近半**（无副本） | ⚠️ **需 Enterprise 许可**（本课程 basic **用不了**）；查询延迟高 | 付费版、冷数据占比极高 |
| D | **对象存储归档 + 按需批量导入** | 成本最低 | 查一次要导入一次，**不能秒查** | 一年只可能查一两次的极端冷数据 |
| E | **减小单条体积**（去冗余字段、只留必要字段、缩短 stacktrace） | 同样的盘能多装 2–3 倍时间 | 丢失部分调试信息 | 日志里有大量冗余 |

### 推荐路径（递进）

1. **先算容量账** —— 也许你不需要分层，只是需要**配 `delete`**
2. **上 ILM 分层（A），`delete` 必须配** —— 不做这一步，磁盘只会一直涨
3. **仍吃不下 → 冻结索引（B）**
4. **付费版才考虑 searchable snapshots（C）**

### 知识点挂钩

- ILM 分层 / 滚动 / 保留 → 阶段 4 课 10（知识点 2/3）
- forcemerge、降副本 → 阶段 4 课 10
- 快照仓库与 SLM → 阶段 4 课 12
- 命名与 `event.dataset` 区分 → 阶段 4 课 10

### 什么情况下此方案不适用

- **不要把 searchable snapshots 当"免费的分层"** —— 它有**许可门槛（Enterprise）**，而且查询**不是"秒查"**
- **不要只配 hot 不配 delete** —— 那就是故障模式 3 的起点
- ⏳ **各方案"省几倍成本"的具体倍数不要采信单一数字**（受保留天数、压缩比、副本数影响极大）——只采信**架构性差异**（如 searchable snapshot 无副本 → 本地存储可省近半）

### 做错会踩的坑

→ ILM 无 `delete` = [08-实战经验.md](08-实战经验.md) **故障模式 3**（磁盘慢慢满 → flood stage 写不进去）
→ 自定义模板忘了 `composed_of`，把 ILM 一起顶掉 = **故障模式 1 / 7**
</details>

## 场景 6：设计一套"不误报、不漏报、不刷屏"的告警

**场景描述**：现有告警有 3 个毛病：① 每天几十条**重复告警**，值班开始忽略；② 出错后 **5 分钟**才收到，太慢；③ **修好了没人通知**，值班一直以为还坏着。

**🔒 先自己想 30 秒**：别急着调阈值。先把告警拆成三件事——**判什么**（条件）、**什么时候说**（时机）、**跟谁说、说完了怎么收尾**（动作与恢复）。

<details><summary>💡 提示（三轴定位，别混在一根轴上调）</summary>

- **判什么**：阈值看的是"瞬时"还是"持续"？只看一个维度还是多个？
- **什么时候说**：有没有抖动缓冲？调度间隔和阈值的单位匹配吗？
- **怎么收尾**：修好了谁通知？计划内变更期间怎么办？临时要闭嘴怎么办？
</details>

<details><summary>📖 展开解法</summary>

### 解法一览（含代价与边界）

| # | 解法 | 能解决到 | 代价 | 适用边界 |
|---|------|---------|------|---------|
| A | **阈值从"瞬时"改"持续 N 分钟超 M" + `alert_delay` 防抖** | 消除瞬时抖动导致的**误报** | 检出**变慢**（要等满 N 分钟） | 解决①，**代价就是延迟** |
| B | **配 `recovered` 动作组 + 明确 `notify_when` 口径** | 修好了会通知；值班知道"已恢复" | 通知量增加（但这是必要的） | 解决③；`onActionGroupChange` 下 active→active 不重复通知 |
| C | **缩短轮询间隔 / 提高调度频率** | 检出更快 | 对 ES 查询压力上升；对短时抖动更敏感 | 解决②，**必须和 A 一起调**（否则误报回来了） |
| D | **维护窗口**：计划内变更走窗口（**照常检测、零投递**，本课程实测） | 变更期不打扰人，且**不丢检测** | 要提前排期登记 | 解决①的"变更期刷屏" |
| E | **静默**（规则级 `_mute_all` / 实例级） | 临时止血 | **真实故障也会被静音** → 必须设回顾时间 | 短期应急，**不是长期方案** |
| F | **（进阶）多维度复合条件**：同时看"错误率"和"错误量级" | 减少低量级噪声触发 | 规则复杂度上升 | 错误量与错误率都要看时 |

### 推荐路径（递进）

1. **先配 `recovered`（B）** —— 成本最低、收益最直接（"修好了没人说"是最容易被忽略的坑）
2. **阈值改成"持续 N 分钟超 M"（A）** —— 一次性解决刷屏与误报
3. **配合调调度间隔（C）** —— 让"检出快"和"不误报"同时成立
4. **建维护窗口流程（D）** —— 把"变更期刷屏"变成流程问题而不是技术问题
5. **静默（E）只留给应急**

### 知识点挂钩

- 告警规则 / 连接器 → 阶段 4 课 12（知识点 1）
- 动作组与恢复 / `notify_when` → 阶段 4 课 12
- 维护窗口 / 静默 / `kibana.alert.instance.id` → 阶段 4 课 12
- 查询与 KQL → 阶段 4 课 11
- 决策口径 → [final-课程手册.md](final-课程手册.md) 9.5

### 什么情况下此方案不适用

- **别用"永久静音"当解决方案** —— 它只是把"没告警"伪装成"没问题"
- ⚠️ **basic 许可下可用的连接器只有 `.index` 与 `.server-log`**（本课程实测：73 种类型里 enabled 的只有这两个）。要 webhook / 邮件 / Slack，需 **Gold 及以上**许可——**告警设计必须先确认出口可用**
- 调度间隔不能无限缩短：告警查询本身会占 ES 资源

### 做错会踩的坑

→ 改规则漏带 `actions` = **故障模式 10A**（动作被整体替换清空）
→ 导入规则不 `_enable` = **故障模式 10B**（官方明示 "Rules are disabled on export"）
→ 静默用告警文档 `_id` 而非 `kibana.alert.instance.id` = **故障模式 10C**（404）
→ 阈值写"`>0` 就报" + 不配 `recovered` = **故障模式 10D**（告警风暴）
</details>

## 场景 7：单机 Compose 演示环境，业务要求"生产可用"

**场景描述**：现在整套 ELK 跑在一台 Mac 的 Docker Compose 上。业务要求"上生产，**不能因为一台机器挂了就没日志看**"。要做哪些改造，按什么顺序？

**🔒 先自己想 30 秒**：把"生产可用"拆成**六个维度**：单点、冗余、容量、备份、恢复、安全。哪一个是**红线**（不做就是事故）？从哪个开始投入产出比最高？

<details><summary>💡 提示（六维度，按"不做会死"排序）</summary>

- **安全**：你的 9200 现在谁能连上？
- **单点**：几个节点？一台挂了会怎样？
- **冗余**：副本数是多少？单节点上"配副本"有没有意义？
- **备份**：备了什么？**演练过恢复吗**？（"备份成功" ≠ "能恢复"）
- **不可再生资产**：日志之外，还有什么丢了就没了？
- **容量**：保留期写下来了吗？水位线告警配了吗？
</details>

<details><summary>📖 展开解法</summary>

### 解法一览（含代价与边界）

| # | 解法 | 能解决到 | 代价 | 适用边界 |
|---|------|---------|------|---------|
| A | **安全基线**：9.x 默认开安全；强密码；最小权限；**9200/9300 不对公网**；跨网络开 TLS | 直接堵住**案例 1** 那一类"被批量清库"的事故 | 要管证书与账号 | **红线，不可省，第一个做** |
| B | **加节点到 2–3 台 + 副本数 ≥1** | 数据有冗余；health 才**可能** green | 成本 ×N；集群管理复杂度 | 生产底线，**第二件做** |
| C | **快照仓库 + SLM 定期快照 + 恢复演练** | 能应对误删/事故 | 需要 S3 兼容仓库；`path.repo` 是**静态设置**，改完**要重启节点** | **必做**，且**必须演练**（案例 2 的教训） |
| D | **备份 `.kibana` 的 Saved Objects**（看板 / 规则 / 连接器） | 不可再生资产有兜底 | 要定期导出 + **演练导入** | 常被遗漏，必须做 |
| E | **容量与保留规划**：ILM `delete` + 85/90/95% 水位线告警 | 不会**默默**写满 | 要算准 | → 场景 5 |
| F | **节点角色分工**（专用 master / data_hot / data_warm / ingest） | 职责分离，故障域更清晰 | 至少 5–7 个节点才分得开；复杂度上升 | 规模上来之后，**不是起点** |

### 推荐路径（递进，按投入产出比）

1. **安全基线（A）** —— 红线，先做
2. **多节点 + 副本（B）** —— 可用性底线
3. **快照 + 恢复演练（C）** —— 注意是"**演练**"，不是"配置成功"
4. **备份 `.kibana`（D）** —— 不可再生资产
5. **ILM 保留期 + 水位线告警（E）**
6. **最后才考虑角色分工（F）**

### 知识点挂钩

- 容器起栈 / 多节点 → 阶段 1 课 2《把 ELK 跑起来》
- 认证与最小权限 → 阶段 1 课 2 ＋ 阶段 4 课 12
- 副本与分片 → 阶段 4 课 10
- 快照仓库与 SLM / Saved Objects 导出 → 阶段 4 课 12
- 水位线 85/90/95% → 阶段 4 课 10

### 什么情况下此方案不适用

- **单节点上"配了副本"不等于有冗余** —— 副本**无处安放**，集群只能一直 yellow（[08-实战经验.md](08-实战经验.md) 假故障表）
- **"备份成功"不等于"能恢复"** —— 案例 2 里五套备份机制**没有一套能用**，全靠一个 6 小时前的临时快照
- 别跳过 A 直接去堆节点、配高可用 —— **不安全的高可用只是"更大的一块靶子"**

### 做错会踩的坑

→ 暴露公网 + 无认证 = **案例 1**（Meow 攻击，5 天超 3000 个数据库被清）
→ ILM 无 `delete` = **故障模式 3**
→ 只备日志不备 `.kibana` = **案例 2 的同类教训**
</details>

## 场景 8：公司已有 OTel / 其他可观测体系，还要不要上 ELK？上到哪一步？

**场景描述**：团队已经有 OpenTelemetry Collector + 一个后端。现在有人提"再上一套 ELK 做日志"。怎么判断该不该上？如果要上，**上哪几段**？

**🔒 先自己想 30 秒**：先别比产品。先问三个问题：现在的体系**缺什么**（查询形状？保留期？可视化？告警？）→ ELK 补的**是不是这个缺口** → 多一套体系的代价（**双倍成本 + 数据不一致 + 双倍学习成本**）值不值？

<details><summary>💡 提示（先做"缺口盘点"，再谈方案）</summary>

- 把"**查不到 / 查得慢 / 留不住 / 看不到 / 报不出**"五类痛点各写几条，看它们属于哪一类
- 如果痛点大多是"**全文检索 + 多字段组合查询**"→ ELK 是对症药
- 如果痛点只是"标签筛得慢"或"存不起"→ **换个存储引擎可能更便宜**
- 最后一问：**同一份数据被两套工具采集**会发生什么？
</details>

<details><summary>📖 展开解法</summary>

### 解法一览（含代价与边界）

| # | 解法 | 能解决到 | 代价 | 适用边界 |
|---|------|---------|------|---------|
| A | **什么都不加，跟现有体系走** | 零新增成本、无数据不一致 | 可能有能力缺口没补上 | **默认答案**：现有体系已能覆盖查询需求 |
| B | **只加"存储 + 可视化"一段**（日志仍由现有采集器送 ES） | 补上 ES 擅长的全文检索/聚合；**不重复采集** | 两套存储，要统一"数据一致性口径" | 现有采集强、检索弱（**最常见的好选择**） |
| C | **只加"采集"一段**（Beats 进现有后端） | 补上采集覆盖面 | 若后端不擅长日志检索，收益有限 | 现有后端强、采集弱 |
| D | **全链路新增 ELK**（采集 → 处理 → 存储 → 可视化 → 告警） | 能力最全 | 成本最高；**最容易出现"同一份数据被两套工具重复采集"** | 现有体系确实撑不住，且团队愿意长期维护 |
| E | **换掉现有体系，做单一栈** | 无重复、口径统一 | 迁移成本与风险最大 | 只做一次、长期收益最大 |

### 推荐路径（递进）

1. **先做缺口盘点** —— 把五类痛点落到具体场景（哪条日志、谁在查、等多久）
2. **缺口不是"全文检索类"就别上 ELK** —— 换存储引擎可能便宜得多
3. **缺口是 → 先上 B（只加存储 + 可视化）** —— 收益集中、不引入重复采集
4. **采集重复的问题必须先解决，否则不要上 D**

### 知识点挂钩

- 该不该用 / 用在哪些环节 → 阶段 1 课 1《一条日志的旅程》＋ 阶段 4 课 12 知识点 3 ＋ [final-课程手册.md](final-课程手册.md) 9.1
- 采集端选谁（Beats / Logstash / Fluentd / OTel Collector）→ 阶段 2 课 6 知识点 2 ＋ 手册 9.2
- 解析放在哪一层 → 阶段 3 课 9 ＋ 手册 9.3
- 存储策略怎么定 → 阶段 4 课 10 ＋ 手册 9.4

### 什么情况下此方案不适用

- **ELK 擅长"全文检索 + 多字段组合查询 + 已有 Elastic 生态"**；**离开这三条就要重新算账**（[08-实战经验.md](08-实战经验.md) 适用边界表）
- **"两套体系"不等于"双保险"** —— 数据不一致时，你连**哪个是对的**都不知道
- 采集端前提：**Beats 的主场是"本机 + 常驻 + 单一数据类型"**；容器/K8s 或应用内链路追踪场景，优先考虑别家

### 做错会踩的坑

→ 用 `latest` 标签导致版本悄悄漂移 = **反模式 1**
→ 把指标和日志塞进同一个 data stream = **反模式 5**（字段形态与保留策略完全不同）
→ 同一份数据被两套工具重复采集 = 手册 9.2 的**禁忌项**
</details>
