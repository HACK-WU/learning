# ELK 排障速查手册

> **定位：使用态 · 机长 QRH 式**——你正处在"业务已经出问题"的状态，**只要答案，不要原理**。
> **怎么用**：出事了**别从头读**。先在下面「症状倒查索引」里找到你**一眼看到的那句话**，翻到对应条目照做。
> **想懂为什么**：每个条目末尾有原理链接，**事后再看** [08-实战经验.md](08-实战经验.md)。紧急时不占认知带宽。
> **查不到**：→ 转 [`debug`](../../../../.workbuddy/skills/debug/SKILL.md) 现场取证（本手册只预演**领域典型**失败模式，不定位你眼前这个具体 bug）。
>
> **版本基线**：Elastic Stack **9.5.3** ｜ **环境**：macOS arm64 + Docker Compose（**license = basic**）
> **证据纪律**：本手册**只收确定项**——每条「症状—根因—修复」可溯源（官方文档 / 联网核查 / 本课程实测 / 领域公认实践）。
> 拿不准的留在 [08-实战经验.md](08-实战经验.md) 并标 `⏳ 置信度：低`，**不进本手册**（不确定的动作不允许出现在紧急流程里）。
>
> **条目编号 = 经验层故障模式编号**：症状 N ↔ [08-实战经验.md](08-实战经验.md) 故障模式 N，一一对应，方便事后回读原理。

## 🔎 症状倒查索引

> 这是**检索入口**，不是目录。**按你屏幕上看到的原文**找行，别看分类。

| 一眼看到的现象 / 报错关键字 | 紧急度 | 翻到 |
|--------------------------|:------:|------|
| `log.level` 的 mapping 是 **`text`**；`term` 查 `log.level:"ERROR"` **恒 0 命中**（但 `_source` 里有值）；告警**永远 `OK`、从不 FIRING** 且不报错 | 🔴 | **症状 1**：模板缺 `composed_of`，告警静默失效 |
| 写入报 `disk usage exceeded flood-stage watermark`；或索引被置 `index.blocks.read_only_allow_delete`，**写不进去** | 🔴 | **症状 3**：磁盘打满，写入被阻塞 |

| Filebeat 反复报 `no matching index template found for data stream [...]`；`_cat/indices` **空**，一条数据都没进 | 🔴 | **症状 7**：data stream 建不起来 |

| `_source` 里**有** `custom.xxx`，`_search` 搜它是 **0 命中**，`_mapping` 里**没有**这个字段 | 🟡 | **症状 4**：字段爆炸（宽松模式 / 能存不能查） |
| **文档数是文件行数的 2 倍**（如 1000 行 → 2420 文档）；`log.offset` 出现重复值 | 🟡 | **症状 2**：registry 未持久化，重读全量 |
| `host.name` 变成了**数组**（`["09d21480270c","web-01"]`）；terms 聚合桶里混进容器 ID | 🟡 | **症状 5**：`add_field` 是追加不是覆盖 |
| 文件 **1000 行只落 700 条**文档（或一段堆栈被切成 9 条）；某条 `message` 里**含多行 / 含两条日志** | 🟡 | **症状 6**：multiline pattern 覆盖不全 |
| 老教程字段名 `clientip` / `verb` / `bytes` **找不到**；`convert`、`if [clientip]` 不报错也不生效 | 🟡 | **症状 8**：ECS 兼容模式已改字段名 |
| 依赖 `message` 的 processor / `when` 分支**永不生效且不报错**；文档里 `message` **消失**、多了 `event.original` | 🟡 | **症状 9**：字段被 rename，条件静默失效 |
| 改过规则之后，规则里 `actions` **全没了**（不再发通知） | 🟡 | **症状 10**：告警四连坑（A） |
| 导入的规则**不生效**，一看 `enabled: false` | 🟡 | **症状 10**：告警四连坑（B） |
| 调实例静默接口 → **404** | 🟡 | **症状 10**：告警四连坑（C） |
| 每天几十上百条**重复告警**，值班开始忽略它 | ⚪ | **症状 10**：告警四连坑（D） |
| 集群 health **yellow** ／ 查不到刚写的日志 ／ `@timestamp` 差 1 小时 ／ 字符串有 `text` + `.keyword` 两份 | ⚪ | **先看下面的「假故障」表，多半不用动手** |

## ⚠️ 动手前 10 秒：先确认这不是"假故障"

> 这一类**吞噬的排障时间最多**。**先确认它是不是正常**，再动手——否则你会在一个没坏的系统上修半天。

| 你看到的 | 其实是正常的 | 怎么确认 |
|------|-------------|---------|
| 集群 health **yellow** | 单节点 + 1 副本必然 yellow——副本无处安放，**数据一条不少** | `_cat/indices?v` 看 `pri` / `rep` 两列；节点数 ≥ 2 才会 green |
| 采集端"卡住"、延迟变大 | **背压**：下游慢 → 队列积压 → 采集端自动减速。短期是**延迟**不是丢数据 | 看 Logstash 队列指标 + ES 写入耗时；下游恢复后自动追上 |
| ES 刚恢复，**查不到刚写的日志** | 队列还在排空，事件一条条刷出，不是丢了 | 等一会儿再看（本课程实测：刚 healthy 时仍是旧计数，稍后刷全 13 条） |
| `@timestamp` 比日志里写的时间**差 1 小时** | 默认 `@timestamp` = **采集时间**，不是事件时间 | 本课程实测差 **1 小时 6 分**；配 Logstash `date` 或 Ingest `date` 后对齐 |
| 字符串字段出现 `text` + `.keyword` 两份 | 动态映射的默认行为（`text` 可搜 + `.keyword` 可聚合） | 想只要 keyword，用 dynamic template 把 string 收敛（课 10 实测） |
| 配好 ILM **不立刻生效** | 默认 **10 分钟**轮询一次 | `GET /<ds>/_ilm/explain` 看 `check-rollover-ready`；`indices.lifecycle.poll_interval` |
| event log 体积像"多出来的一大块" | 里面绝大部分是**定时任务心跳**，不是你的业务日志（实测：`.ds-.kibana-event-log-ds-*` **288,379 条 / 59 MB**，是业务数据的 **600 倍体积**，其中 **140,516 条**来自 taskManager 心跳） | 查 `.kibana-event-log-ds` 的 `event.action` 分布 |
| 单节点上"冷热迁移"后数据没挪窝 | 单节点角色含所有 tier，迁移只改 `_tier_preference` 标记 | `_cat/nodes` 看角色；真冷热需要多节点 |

> 完整版（含 `ecs.version` 不一致、`ignore_dynamic_beyond_limit` 这类）见 [08-实战经验.md](08-实战经验.md) 的「被误判为故障的正常现象」。

## 🔴 症状 1：索引模板缺 `composed_of`，告警静默失效

**一眼识别**：`log.level` 的 mapping 是 **`text`**（不是 `keyword`）；`term` 查一个**已知存在**的 `log.level:"ERROR"` → **0 命中**；告警规则状态**恒定 `OK`**，从不 FIRING，且**全程无任何报错**。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 改规则查询条件**绕开失效字段**：用 `event.original: "ERROR"` 或 `message: "ERROR"`（全文匹配不依赖 mapping 类型）；条件仍查 `log.level` 就先手工定时核对 | 规则能进入 FIRING → **监控真空先堵上**（本症状的危害就是"没告警"，不是"报错") |
| 定位 1 | `GET /_index_template/<你的模板>` | `composed_of` 为**空** 且 `priority` > 100 → 确诊：你顶掉了内置 `logs` 模板 |
| 定位 2 | `GET /<ds>/_mapping` | 关键字段是 `text` 而非 `keyword` → ECS 映射已丢失 |
| 定位 3 | `GET /<ds>/_search` 用 `term` 查一次已知存在的值 | 命中 `0` → 三处证据闭合，确诊 |
| 修复 | 模板里**显式声明** `composed_of`（至少含 `logs@settings` / `logs@mappings` / `ecs@mappings`）→ `PUT /_index_template/<name>` → `POST /<ds>/_rollover` 建**新代**后备索引 | 新代索引的 `_mapping` 里 `log.level` 是 `keyword`；`term` 冒烟查询**能命中** |
| 若无效 | → 转「症状 4」（字段能存不能查）／ 转「症状 7」（data stream 本身没建起来） | — |

> **预防**：任何自定义索引模板**必须** `composed_of` 引用内置模板；上线前做一次「`term` 精确查询冒烟」，能命中才算通过。
> ⚠️ **旧分片的映射改不了**——修复只对**新代**生效；需要回填就重灌 data stream。
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 1

## 🟡 症状 2：registry 未持久化，容器重建后数据翻倍

**一眼识别**：`docker compose up -d`（recreate）之后**文档数翻倍**（本课程实测 **1000 → 2420**）；同一份日志出现多份；`log.offset` 有重复值。**数据没丢、查询不报错，只是每个数字都变大**——所以最难发现。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | `docker compose stop filebeat` | 文档数**停止增长**（先掐断重复写入，再决定清哪些） |
| 定位 1 | `docker inspect <filebeat容器> --format '{{json .Mounts}}'` | `/usr/share/filebeat/data` **没有挂载** → 确诊 |
| 定位 2 | `docker compose exec filebeat ls -la /usr/share/filebeat/data/registry/filebeat/` | 空或不存在 → registry 随容器一起没了 |
| 定位 3 | 对数：`wc -l` 文件行数 vs 文档数 | 文档数 ≈ 行数 × 读取次数 → 确认翻倍不是别的（如 multiline）造成 |
| 修复 | compose 里把 registry 落到**命名卷**：`- filebeat-registry:/usr/share/filebeat/data`（并在 `volumes:` 顶部声明该卷）→ `docker compose up -d` | 重建后文档数**不再翻倍**；registry 目录里有内容 |
| 若无效 | 已翻倍的历史数据：按时间范围 `_delete_by_query` 清重复，或删掉 data stream 重灌 | 计数与文件行数一致 |
| 若无效（其二） | → 转「症状 6」（数量不符也可能来自 multiline 吞行/粘行） | — |

> **预防**：**registry 必须持久化**——它是 at-least-once 语义的**前提**，不是缓存。
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 2

## 🔴 症状 3：磁盘打满触发 flood stage，写入被阻塞

**一眼识别**：写入报 `index [...] blocked by: [TOO_MANY_REQUESTS/12/disk usage exceeded flood-stage watermark]`；或索引被置 `index.blocks.read_only_allow_delete`，**写不进去**。

**🟡 前置预警（此时还没坏，但要马上处理）**：磁盘使用率**只涨不降**；某个 data stream 的后备索引一路长到 `-0012xx` **从没被删过**；`GET /_ilm/policy/filebeat` 的 `phases` 里**只有 `hot`**。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血 1** | **腾空间**：删最旧的后备索引（`DELETE /<ds>-0000NN`）或给磁盘扩容 | 磁盘使用率降回 **90%（high）以下** |
| **止血 2** | 若索引已被置只读，降回水位以下后**自动解除**；要立即恢复写入就显式解除：`PUT /<idx>/_settings {"index.blocks.read_only_allow_delete": null}` | 写入恢复（`_bulk` 不再 429） |
| ⚠️ 止血 3 | 临时抬高水位线（`cluster.routing.allocation.disk.watermark.*`）**只是把爆炸时间往后挪**——磁盘还是在涨，别把它当解法 | 争取到处理时间，**不是**恢复 |
| 定位 1 | `GET /_ilm/policy/<name>` | `phases` 只有 `hot`、**没有 `delete`** → 确诊「日志永不自动删除」 |
| 定位 2 | `GET /<ds>/_ilm/explain` | 看当前 `phase` / `action`；`check-rollover-ready` = 在等条件（说明滚动条件一直没满足） |
| 定位 3 | `GET _cat/allocation?v` ＋ `GET /_cluster/settings?include_defaults=true&filter_path=*.cluster.routing.allocation.disk.watermark.*` | 看是哪个节点、离水位线还有多远；官方默认 **low 85% / high 90% / flood_stage 95%** |
| 修复 | **根治**：自建 ILM 策略（`hot: rollover` → `warm: forcemerge + 降副本` → `delete: 保留 N 天`），经索引模板的 `index.lifecycle.name` 绑到 data stream | 后备索引**开始被自动删除**；`_ilm/explain` 能走到 `delete` 阶段 |
| 若无效 | → 转「症状 4」（字段爆炸/索引膨胀也会顶满磁盘）／ 转「症状 1」（若新增的是自定义模板，可能把 ILM 也一起顶掉了） | — |

> **预防**：**ILM 上线前必须检查 `phases` 里有没有 `delete`**；给 **85% / 90% / 95%** 三档水位线配告警。
> ⚠️ 小集群上默认的 `max_primary_shard_size: 50gb` 可能一年都碰不到——**等于连滚动都不会发生**。
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 3

## 🔴 症状 4：字段爆炸——整条日志被拒，或"能存不能查"

**一眼识别**：
- **严格模式（🔴 写入被拒）**：`document_parsing_exception: Limit of total fields [20] has been exceeded while adding new fields [22]`
- **宽松模式（🟡 能存不能查）**：写入**成功**，但 `_search` 搜 `custom.field_25` → **0 命中**，而 `_source` 里**有值**

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | **仅严格模式需要**：临时抬高上限 `PUT /<idx>/_settings {"index.mapping.total_fields.limit": 20000}` | 写入恢复（`_bulk` 不再拒单）——⚠️ **只是止血**，字段数还会继续涨 |
| **止血（宽松模式）** | 无需止血（**没有丢数据**，只是没建索引）；直接进定位 | — |
| 定位 1 | `GET /<idx>/_mapping` ＋ `GET /<idx>/_settings?include_defaults=true&filter_path=*.total_fields.limit` | 数字段量级、找可疑高基数字段名；看上限（Filebeat 默认 **12500**） |
| 定位 2 | 对照 `_source` 与 `_mapping`：某字段**在 `_source` 有、在 `_mapping` 无** | = 被 `ignore_dynamic_beyond_limit: true` **静默丢弃** → 确诊宽松模式 |
| 定位 3 | `GET /<idx>/_field_caps?fields=*` | 看字段总数与类型分布，定位是哪一类内容在制造新字段名 |
| 修复 | **首选治本**：在处理链上 `remove_field` 掉高基数 / 无用字段；再补 `dynamic_templates` 把 string 收敛为 `keyword`（避免 `text` + `.keyword` 双份）；最后把 limit 改回原值 | 字段数**停止增长**；关键字段 `term` 可查 |
| 若无效 | → 转「症状 5」（若污染源是 `add_field`）／ 转「症状 8」（若字段名异常来自 grok 改名） | — |

> **预防**：上线前梳理字段清单；定期用 `_field_caps` 体检字段数趋势；**禁止把 ID 类值（trace-id / 用户输入 / 整段 JSON 的键）当字段名**。
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 4

## 🟡 症状 5：`add_field` 是追加不是覆盖，`host.name` 被污染成数组

**一眼识别**：一条文档的 `host.name` 是**数组**（`["09d21480270c","web-01"]`）；按主机做 terms 聚合时**桶数不对**（真实主机名 + 容器 ID 混在一起）；按 `host.name` 分组的告警分组错乱。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 把依赖 `host.name` 的**告警分组 / 看板维度临时切走**（如改按 `container.name` 或 `log.file.path`），避免继续产生误判 | 分组结果先恢复可信；容器 ID 不再混入 |
| 定位 1 | `GET /<idx>/_search?size=1` 抽一条文档，看 `host.name` | 是**数组**而不是字符串 → 确诊 |
| 定位 2 | 对 `host.name` 做一次 `terms` 聚合 | 桶名里出现 **12 位十六进制**（容器 ID）→ 确认污染源 |
| 定位 3 | 检查处理链里的 `mutate` / `add_field` 块 | 存在对 `[host][name]` 或其它 **ECS 已有字段**的写入 → 确认写法 |
| 修复 | 先 `remove_field => ["[host][name]"]` **再**写真实主机名；或**根本不覆盖**——生产环境 Filebeat 每机一个，`host.name` **本来就是对的** | `host.name` 回到**字符串**；terms 桶数 = 真实主机数 |
| 若无效 | → 转「症状 9」（也可能是处理链顺序问题，字段在那一刻还不存在/已改名） | — |

> **预防**：写 ECS 已有字段之前，先确认目标字段**存不存在、是追加还是覆盖**。
> ⚠️ 本项目之所以要覆盖，是因为**采集器跑在容器里**（容器名不是业务机名）。**别画蛇添足。**
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 5

## 🟡 症状 6：multiline pattern 覆盖不全，日志行被吞或粘连

**一眼识别**：**行数对不上**——文件 1000 行只落成 700 条文档（或反过来，一段堆栈被切成 9 条）；抽一条文档看 `message`，**里面含多行**，且含**不该在一起的两条日志**（如一行 JSON 被并进了上一行文本日志）。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 无（已落的数据修不回来）——**先把 pattern 修对**，阻止继续产生错数据 | 不再产生新的粘连文档 |
| 定位 1 | **先对数**：`wc -l` 文件行数 vs 文档数 | 差值大 → 确诊方向（这是最快的入口） |
| 定位 2 | 抽一条文档看 `message` 是否含多行 / 含多条日志 | 含多行 → 确认是"并行了"而非"丢行了" |
| 定位 3 | `filebeat test config`（改完再跑一次） | 校验 multiline 配置语法正确 |
| 修复 | pattern 里**把每一种"新事件行首"都写进去**：`pattern: '^([0-9]{4}-[0-9]{2}-[0-9]{2}\|\{)'`（日期开头 **或** `{` 开头）→ 重灌 | 文档数 = 文件行数 |
| 若无效 | → 转「症状 2」（重复读取也会让数量对不上）／ 转「症状 9」（若 JSON 行整条不见了） | — |

> **预防**：多格式混排的日志源，**先把所有行首枚举出来**再写 pattern；配好后**必须做一次计数对照**。
> ⚠️ 机制是「**不匹配 pattern 的行 = 上一行的续行**」——只写日期开头时，以 `{` 开头的 JSON 行**不被认为是新事件**，于是被并进上一行，JSON 行就"消失"了。
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 6

## 🔴 症状 7：data stream 建不起来，链路完全不进数据

**一眼识别**：Filebeat 启动后**反复**报 `could not put data stream: 400 Bad Request: illegal_argument_exception: no matching index template found for data stream [demo-app]`；`_cat/indices` **空**，**整条链路一条数据都没进**。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 去掉自定义 `index:` 名与 `setup.template.*`，**回归 Filebeat 默认行为**（自带模板 + 默认 data stream），让数据先进来 | `_cat/indices` 出现 `filebeat-9.5.3` 之类；文档数 > 0 |
| 定位 1 | `docker compose logs filebeat` | 看报错**原文**——`no matching index template found for data stream [X]` → 确诊 |
| 定位 2 | `GET /_index_template/<name>` | 看 `index_patterns` 与 **`data_stream` 字段**（有没有 `data_stream: {}`） |
| 定位 3 | 比对：模板的 `index_patterns` **能不能覆盖**你写的那个名字 | 覆盖不到 → 确诊 |
| 修复 | 确实要自定义，就**完整写模板**：`data_stream: {}` + `index_patterns` + `composed_of` + ILM，一个都不能少 | Filebeat 日志不再报错；`_cat/indices` 出现你的 data stream |
| 若无效 | → 转「症状 1」（模板建起来了但**字段还是不对**——这正是"两个坑叠加"里的第二个） | — |

> **预防**：**改索引名 = 改整套模板契约**，不是改一个字符串；最小链路阶段先用默认行为跑通，再加复杂度。
> ⚠️ 9.x 下自定义 `index:` 名会被当作 **data stream 名**，而 data stream **必须**匹配某个声明了 `data_stream: {}` 的索引模板。只设 `setup.template.name` 是**不够**的。
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 7

## 🟡 症状 8：ECS 兼容模式已改字段名，照抄老教程的写法静默失效

**一眼识别**：`%{COMMONAPACHELOG}` 解析后，`clientip` / `verb` / `bytes` 这些字段**找不到**；后面 `convert => {"bytes" => "integer"}` 或 `if [clientip]` **不报错也不生效**；ES 里能查到 `source.address`，查 `clientip` 是 **0 命中**。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 无（静默失效不产生坏数据，只是下游逻辑空转）——直接进定位，改完重跑 | — |
| 定位 1 | `logstash --config.test_and_exit`（或管道启动日志） | 出现 `Pipeline 'main' is configured with 'pipeline.ecs_compatibility: v8'` → **这是最早的提示** |
| 定位 2 | output 里临时加 `stdout { codec => rubydebug }`，重跑一次 | 看**真实字段名**长什么样（`source.address` / `http.request.method` / `http.response.body.bytes`） |
| 定位 3 | `GET /<idx>/_mapping` | 确认落库的字段名，与下游查询/告警用的名字对不对得上 |
| 修复 | 下游逻辑与查询**改用 ECS 新名**（推荐）；或显式 `pipeline.ecs_compatibility: disabled`（**不推荐**，会与整个生态脱节） | `convert` / `if` 生效；字段能查到 |
| 若无效 | → 转「症状 9」（若你依赖的是 `message` 而不是 grok 字段） | — |

> **预防**：**照抄老教程的 grok 字段名 = 定时炸弹**；配完先用 `rubydebug` 看一遍真实字段，再写下游逻辑。
> **对照表（9.x 默认）**：`clientip`→`source.address`｜`verb`→`http.request.method`｜`request`→`url.original`｜`httpversion`→`http.version`｜`response`→`http.response.status_code`｜`bytes`→`http.response.body.bytes`
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 8

## 🟡 症状 9：字段被 rename，`when` 条件静默失效

**一眼识别**：配了 `when.contains.message: "ERROR"` 的 processor / 过滤分支**永远不生效**，而且**不报任何错**；文档里 `message` 字段**不见了**，多了一个 `event.original`；采集端打标记（`tags`）、丢字段等动作"像没执行过"。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 无（静默失效不产生坏数据）——直接进定位 | — |
| 定位 1 | `GET /<idx>/_search?size=1` 抽一条文档 | 有 `event.original`、**没有 `message`** → 确诊字段被改存 |
| 定位 2 | `GET /<idx>/_mapping` | 确认字段**实际叫什么**（`event.original` 还是 `[log][original]`） |
| 定位 3 | 逐条检查处理链里**每个** `when` 依赖的字段，在**那一刻**是否还存在 | 找到"条件判断时字段已改名"的那一处 → 确诊具体位置 |
| 修复 | 条件改用 `event.original`（或 `[log][original]`）；或调整处理顺序，在 rename **之前**处理 | 条件分支开始生效（`tags` 出现 / 字段被丢） |
| 若无效 | → 转「症状 8」（若字段名是被 ECS 兼容模式改掉的） | — |

> **预防**：任何 `when` 条件上线前，确认被判断的字段**在当前处理链的那个位置**确实存在——**静默失效是最难查的一类问题**。
> ⚠️ 成因：Filebeat 模块（或 Ingest pipeline 的 `rename` 处理器）会把原始文本从 `message` **改存到 `event.original`**。
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 9

## 🟡 症状 10：告警四连坑——动作被清空 / 导入不生效 / 静默 404 / 告警风暴

**一眼识别**：四种形态，**各自独立**，按下表对号入座。

### A. 改了规则之后 `actions` 全没了 🟡

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 立刻补回动作：**GET 全量规则 → 改 → PUT 全量** | 规则恢复发通知 |
| 定位 | `GET /api/alerting/rules/_find` | `actions` 数组为空 / 缺项 → 确诊 |
| 修复 | 之后一律「**GET 全量 → 改 → PUT 全量**」——PUT 规则是**整体替换**不是 merge | 改完 `actions` 仍在 |
| 若无效 | → 转 [Kibana 告警页面] 手改，或转 `debug` | — |

### B. 导入的规则不生效，`enabled: false` 🟡

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | `POST /api/alerting/rule/{id}/_enable` | 规则开始执行（`execution_status` 有值） |
| 定位 | 看规则对象的 `enabled` 字段 | `false` → 确诊（**不是**你导入失败） |
| 修复 | 导入后**必须**显式 `_enable` | 规则按调度执行 |
| 若无效 | → 检查规则还有没有别的坑（如 actions 被清空 → 见本条 A） | — |

> 官方明示：**"Rules are disabled on export"** —— 导出即禁用，导入后默认 `enabled: false`。

### C. 调实例静默接口 → 404 🟡

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 换用正确 id：`GET /.alerts-*/_search` 取 `kibana.alert.instance.id`（官方推荐在告警索引**别名**上查，如 Stack 规则的 `.alerts-stack.alerts-default`） | 静默接口返回 **204**（不再 404） |
| 定位 | 对比你用的 id 与 `kibana.alert.instance.id` | 你用的是告警文档的 `_id` → 确诊 |
| 修复 | 实例级静默用 `kibana.alert.instance.id`；`groupBy: all` 的规则下它就是动作组名（实测值 `query matched`） | 静默生效：`kibana.alert.muted: true`，仍评估但不发通知 |
| 若无效 | → 用规则级静默先顶上：`POST /api/alerting/rule/{id}/_mute_all`（实测 204） | 该规则全部通知静默 |

### D. 每天大量重复告警，值班开始忽略它 ⚪

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 先静音：`POST /api/alerting/rule/{id}/_mute_all` | 停止骚扰值班（**注意：静音不等于修好了**） |
| 定位 | 看告警实例数随时间的变化趋势＋规则的阈值配置 | 阈值是"`>0` 就报" + 短轮询 → 确诊 |
| 修复 | ① 阈值改成"**持续 N 分钟超 M**"＋配 `alert_delay` 防抖；② **必须**配 `recovered` 动作组（修好了要有人说）；③ 计划内变更走**维护窗口**（本课程实测：窗口内**照常检测、零投递**）；④ 解除静音 | 告警条数降到可处理量；恢复时也能收到通知 |
| 若无效 | → 转 `debug` 现场排查（可能是上游数据本身在抖） | — |

> **预防**：**告警四道闸门**——阈值防抖 / 恢复通知 / 维护窗口 / 静默，缺一不可。
> **原理**：→ [08-实战经验.md](08-实战经验.md) · 故障模式 10

## 🚑 通用止血动作（不确定是哪类问题时，先把损失停下）

> 上面的条目是"已知症状 → 已知处方"。**不知道是什么问题**时，先用这几招把局面稳住，再进定位。

| 场景 | 止血动作 | 代价 |
|------|----------|------|
| **刚变更就出问题** | 回滚到上一个已知良好状态（配置回滚 / `docker compose` 换回旧镜像标签 / 恢复索引模板的上一版） | 丢失新功能，但把"新引入"这个变量排除掉 |
| **写入被阻塞（只读 / 429 / 拒单）** | 先**解除只读**、再**腾磁盘**：`PUT /<idx>/_settings {"index.blocks.read_only_allow_delete": null}` + 删最旧后备索引 | 可能删掉还没归档的日志 |
| **数据在被污染（重复 / 字段错乱）** | 掐断入口：`docker compose stop filebeat` / `stop logstash` | 新日志**停止入库**（先保"存量不再变脏"） |
| **告警在刷屏** | `POST /api/alerting/rule/{id}/_mute_all` | 真实故障也会被静音 → **必须设定回顾时间** |
| **单个下游组件异常** | 隔离它：停掉 Logstash / Kibana，保留 ES 可用 | 处理链或可视化不可用，但存储不丢 |
| **磁盘真的要满了，来不及修 ILM** | 加盘 / 立刻删最旧后备索引 | 数据保留期缩短 |
| **完全判断不出来** | **别在生产上试**：复制一份配置到本地 Compose 环境复现 → 转 [`debug`](../../../../.workbuddy/skills/debug/SKILL.md) | 花时间，但不扩大事故面 |
