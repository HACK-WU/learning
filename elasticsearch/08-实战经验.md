## 一、适用边界与反模式：什么时候别用 ES

**"不该用"比"怎么用"更值钱。** 这一节是全文最该读的部分。

### 1.1 明确别用的六个场景

| 场景 | 为什么别用 | 该用什么 |
|------|-----------|---------|
| **作为唯一数据源 / 原始账本** | ES 是**索引副本**。极端情况下会丢数据（课 10 实测：销毁 node-3 数据盘后副本未覆盖的分片**永久丢失**） | 关系库 / 对象存储存原始数据，ES 只做索引 |
| **需要跨表 JOIN 的复杂关联查询** | ES 无 JOIN。ES\|QL 的 JOIN 实测报 `parsing_exception`（课 14 实测） | 宽表冗余；或在应用层拼装 |
| **强事务 / 需要回滚的多文档操作** | ES 的乐观锁**只到单文档级别**（课 14 实测：过期 `_seq_no` 返回 409），没有跨文档事务 | 关系库 |
| **频繁更新的单条记录** | ES 更新是"标记删除 + 新增"，更新越频繁段越碎，查询越慢 | 关系库；或接受延迟，批量重建 |
| **数据量小、查询简单的精确匹配** | 杀鸡用牛刀。ES 的运维成本远高于收益 | 关系库 + 索引 |
| **需要严格一致的实时读** | ES 是**近实时**：写后立刻搜可能搜不到（课 14 实测：0 条 → 等 1.2s 得 1 条）。`GET /_doc/{id}` 才是实时 | 关系库；或用 `refresh=true`（有性能代价） |

### 1.2 六个反模式（能跑，但迟早出事）

**反模式一：把 ES 当主库**
```
应用 → 只写 ES → 没有别的地方存原始数据
```
出事那天你会发现：数据丢了没法重建。**课 14 的核心结论**：数据丢了能否重建？能就大胆用，不能就别当唯一数据源。

**反模式二：一个索引写到天荒地老**
商品索引两年长到 800 GB 才有人发现（课 15 开场场景）。**正确做法**：一开始就上 Data Stream 或别名 + rollover，让索引定期"换本子"。

**反模式三：映射全靠动态推断**
本课实测：字符串 `"很便宜"` 写进 `long` 字段直接报错；数字 `19.9` 写进 `integer` 被静默截断成 `19`。**生产上用 `dynamic: strict`**，让脏数据直接报错而不是悄悄污染数据。

**反模式四：分片数拍脑袋**
课 14 实测：同样 3000 条数据，50 分片比 1 分片的**存储多 4.7 倍**（77.3 kb → 361.9 kb）、**p95 慢 2.2 倍**（16.58 ms → 35.90 ms），而且**聚合结果失真**（误差上界从 0 涨到 82）。分片不是越多越好。

**反模式五：为"省事"关闭熔断或调高熔断阈值**
熔断是保护机制，不是障碍。触发熔断说明查询或映射有问题，**调高阈值只会把"查询失败"变成"节点 OOM"**。
> 📚 来源：[Circuit breaker errors（官方文档）](https://www.elastic.co/docs/troubleshoot/elasticsearch/circuit-breaker-errors)（核查于 2026-09）

**反模式六：没有快照就上 ILM 的 delete 阶段**
课 15 实测：ILM 的 delete 阶段**真的会把索引删掉，没有任何确认步骤**。快照没跑起来的话，这就是定时删库。

## 二、高频故障模式（七条）

> 每条按「症状 → 根因 → 排查路径 → 修复 → 预防」五段式。
> **症状都是可观测的**：写"服务很慢"无效，要写"P95 从 50ms 涨到 3s"。
> **证据标注**：`【本机实测】` = 本集群真跑出来的；`【官方文档】` = 有官方来源但本机未复现。

### 故障模式 1：对 text 字段做聚合/排序 → 查询直接失败

**【本机实测】**

**症状**：一个带 `terms` 聚合或 `sort` 的查询突然失败，HTTP 400，报错类型 `search_phase_execution_exception`，`reason` 是 `all shards failed`。

**一眼识别**：报错原文里必有这一段——
```
Fielddata is disabled on [字段名]. Text fields are not optimised for operations
that require per-document field data like aggregations and sorting, so these
operations are disabled by default. Please use a keyword field instead.
```

**根因**：`text` 字段默认**关闭 fielddata**（课 5 讲过）。聚合和排序需要"按文档取字段值"，text 字段被分词后无法高效做这件事，ES 直接禁止。

> 💡 **为什么要禁止**：开启 fielddata 会把整个字段的所有词项**加载进 JVM 堆**，是 OOM 的头号来源。这不是限制你，是保护你。

**排查路径**：
```powershell
# 1. 看字段到底是什么类型
curl.exe -s "http://localhost:9201/<索引>/_mapping?pretty"

# 2. 确认是不是 text（且有没有 .keyword 子字段）
```

**修复**（两条路，选一）：

| 方案 | 做法 | 代价 |
|------|------|------|
| ✅ **推荐**：用 keyword 子字段 | 建索引时给字段配 multi-fields（课 5），聚合用 `字段.keyword` | 需要 reindex 存量数据 |
| ⚠️ 临时：开 fielddata | `PUT <索引>/_mapping` 设 `fielddata: true` | 吃堆内存，官方明确警告"significant memory"，**不是正解** |

**预防**：建索引时就规划好——**要分词搜索的用 text，要聚合排序的用 keyword，两者都要就配 multi-fields**。

📚 官方文档：[fielddata mapping parameter](https://www.elastic.co/docs/reference/elasticsearch/mapping-reference/fielddata-mapping-parameter)

### 故障模式 2：写入报 `document_parsing_exception`，脏数据卡住整条链路

**【本机实测】**

**症状**：写入部分失败，报错——
```
type    = document_parsing_exception
reason  = [1:10] failed to parse field [price] of type [long] in document with id '1'.
          Preview of field's value: '很便宜'
caused_by = illegal_argument_exception → For input string: "很便宜"
```

**根因**：字段类型与数据不匹配。ES 严格校验类型，不符合就拒收。

**排查路径**：
```powershell
# 看这个字段当前是什么类型
curl.exe -s "http://localhost:9201/<索引>/_mapping?pretty"
```

**修复**（按业务容忍度选）：

| 方案 | 做法 | 适用场景 |
|------|------|---------|
| ① 修数据源（根治） | 让上游传数字 | **首选**。脏数据不该进 ES |
| ② `ignore_malformed` | 映射里加 `"ignore_malformed": true` | 能容忍丢字段，要保证整体写入不中断 |
| ③ Ingest Pipeline 兜底 | 用 `convert` + `on_failure` 处理（课 11） | 需要转换而不是丢弃 |

> ⚠️ **`ignore_malformed` 有个反直觉的行为，我实测踩到了**：
> 加了 `ignore_malformed` 后写入"成功"了，但去看文档——
> ```
> 文档内容 = {"price2":"很便宜"}
> ```
> **脏值没进索引（不能用它检索/聚合），但原封不动留在 `_source` 里**。所以你搜这个字段搜不到，GET 出来却能看到脏值。**这会造成"数据看起来存进去了但就是搜不到"的困惑。**

**预防**：生产用 `dynamic: strict`，配 `ignore_malformed` 作兜底，同时**监控写入失败率**——静默丢弃比报错更危险。

### 故障模式 3：bulk 部分失败，但错误被吞掉

**【本机实测】**

**症状**：批量写入后数据条数对不上，但程序没抛异常。

**一眼识别**：**bulk 的响应是 HTTP 200**。失败信息藏在响应体的 `items` 数组里：
```
bulk errors = true
  id=1 status=201 OK
  id=2 status=400 ERROR: document_parsing_exception / ... Preview of field's value: '不是数字'
  id=3 status=201 OK
落库条数 = 2 （3 条里成功 2 条）
```

**根因**：bulk 是**逐条独立处理**的，部分失败不影响其他条目，因此整体仍返回 200。

**排查路径**：
```javascript
// 客户端必须自己检查 errors 字段
const resp = await client.bulk({ operations })
if (resp.errors) {                       // ← 这行不写，失败就被吞了
  for (const item of resp.items) {
    const op = item.index || item.create
    if (op.error) console.error(op._id, op.error.type, op.error.reason)
  }
}
```

**修复**：
1. 检查 `resp.errors`，遍历 `items` 找出失败项
2. 失败项单独记录（死信队列），不要直接丢弃
3. 修复数据后重投

**预防**：**所有 bulk 调用必须判 `errors`**。这是 ES 客户端集成的第一条铁律（课 12 也强调过）。

### 故障模式 4：改字段类型 → `illegal_argument_exception`

**【本机实测】**

**症状**：想把 `long` 改成 `text`，报错——
```
type   = illegal_argument_exception
reason = mapper [price] cannot be changed from type [long] to [text]
```

**根因**：**映射是婚前协议**（课 5 核心结论）。字段类型一旦定下就不能改，因为倒排索引已经按旧类型建好了。

**修复**（唯一路径）：
```mermaid
flowchart LR
    A["建新索引<br/>正确映射"] --> B["reindex<br/>搬数据"]
    B --> C["_aliases 原子切换<br/>别名指向新索引"]
    C --> D["删除旧索引"]
    style C fill:#fff4e0
```
详见课 11（reindex）与课 15（别名切换）。

**预防**：
- 建索引时**显式写映射**，别靠动态推断
- 用**索引模板**固化正确配置（课 15），让未来每个索引都不出错
- 应用**只认别名**，为未来的切换留好后路

### 故障模式 5：集群 yellow / red，分片未分配

**【本机实测 · 课 10 真跑过：销毁 node-3 数据盘】**

**症状**：`GET /_cluster/health` 返回 `yellow` 或 `red`，`unassigned_shards > 0`。
- **yellow** = 主分片都在，缺**副本** → 数据没丢，但失去高可用
- **red** = 有**主分片**没分配 → **部分数据不可读写**

**根因**（按出现频率排序）：

| 根因 | 典型场景 |
|------|---------|
| 节点下线 / 重启中 | 滚动重启、节点崩溃、GC 停顿过长被踢出 |
| 副本数 ≥ 节点数 | 单节点集群默认 1 副本 → 永远 yellow（课 3 踩过） |
| 磁盘水位 | 节点磁盘超 85% 不再分配新分片 |
| 分配被手工禁用 | 运维时关了 `cluster.routing.allocation.enable` 忘了开 |
| 分配重试耗尽 | `ALLOCATION_FAILED` 重试 5 次后不再自动尝试 |

**排查路径**（三步，顺序不能乱）：
```powershell
# 1. 看哪些分片没分配，什么状态
curl.exe -s "http://localhost:9201/_cat/shards?v&h=index,shard,prirep,state,node,unassigned.reason&s=state"

# 2. 问 ES 为什么不分（最关键的一步）
curl.exe -s "http://localhost:9201/_cluster/allocation/explain?pretty"

# 3. 看磁盘
curl.exe -s "http://localhost:9201/_cat/allocation?v"
```

> 💡 **`_cluster/allocation/explain` 是这类问题的唯一真相来源**。它会明确列出每个节点上每个 decider 的判定结果。别猜，问它。

**修复**（按根因对号入座）：

| 根因 | 修复 |
|------|------|
| 节点下线 | 重启节点，等待自动恢复（ES 默认延迟 1 分钟开始分配）；不想等就 `POST /_cluster/reroute` |
| 单节点 + 有副本 | 学习环境：`PUT <索引>/_settings {"index.number_of_replicas": 0}`。**生产不要这么做** |
| 磁盘水位 | 删旧索引 / 加磁盘 / 加节点。临时可上调水位，但只是缓兵之计 |
| 分配被禁用 | `PUT /_cluster/settings {"persistent":{"cluster.routing.allocation.enable": null}}` |
| 重试耗尽 | `POST /_cluster/reroute?retry_failed=true` |

**预防**：
- 生产**至少 3 个 master 候选节点**
- 单节点学习环境建索引时**显式写 `"number_of_replicas": 0`**（课 3 就强调过，这条规则救过我好几次）
- 磁盘水位告警设在 80%，别等 85%

📚 官方文档：[Red or yellow cluster status](https://www.elastic.co/docs/troubleshoot/elasticsearch/red-yellow-cluster-status)（核查于 2026-09）

### 故障模式 6：写入被拒绝 —— 磁盘水位触发只读块

**【官方文档】**（本机磁盘充足，未实测触发）

**症状**：写入全部失败，报错——
```
type   = cluster_block_exception
reason = index [xxx] blocked by: [FORBIDDEN/12/index read-only / allow delete (api)]
```

**一眼识别**：报错原文含 `FORBIDDEN/12/index read-only`。

**根因**：节点磁盘达到 **flood-stage 水位（默认 95%）**，ES 自动给该节点上有分片的索引加上 `read_only_allow_delete` 块，**保护集群不至于把磁盘写满**。

> 💡 **注意这个块的名字**：`read-only / allow delete` —— **允许删除**。所以你还能删索引腾空间，这是故意留的逃生通道。

**实测确认的三个水位默认值**（本机 `GET /_cluster/settings?include_defaults=true`）：
```
low          = 85%     （超过就不再往这个节点分配新分片）
high         = 90%     （超过就把分片往别的节点迁）
flood_stage  = 95%     （超过就加只读块，禁止写入）
```

**修复**（先止血，再根治）：
```powershell
# 止血：临时上调水位 + 解除只读块
# 注意：这只是争取时间，不解决磁盘满的根本问题
curl.exe -s -X PUT "http://localhost:9201/_cluster/settings" `
  -H "Content-Type: application/json" --data-binary "@raise-watermark.json"

curl.exe -s -X PUT "http://localhost:9201/*/_settings?expand_wildcards=all" `
  -H "Content-Type: application/json" --data-binary "@clear-block.json"
```
```json
// raise-watermark.json
{ "persistent": {
    "cluster.routing.allocation.disk.watermark.low": "90%",
    "cluster.routing.allocation.disk.watermark.high": "95%",
    "cluster.routing.allocation.disk.watermark.flood_stage": "97%" }}
```
```json
// clear-block.json
{ "index.blocks.read_only_allow_delete": null }
```

**根治**：删旧索引、加磁盘、加节点。做完记得把水位改回 `null` 恢复默认。

**预防**：**ILM/SLM 自动清理 + 磁盘告警**。磁盘满是可以完全避免的问题——只要提前让数据有地方去、有规则删。

📚 官方文档：[Fix common cluster issues](https://www.elastic.co/docs/troubleshoot/elasticsearch/fix-common-cluster-issues)（核查于 2026-09）

### 故障模式 7：熔断触发 —— `[parent] Data too large`

**【官方文档】**（本机数据量小，未实测触发）

**症状**：请求失败，HTTP **429**，报错——
```
type   = circuit_breaking_exception
reason = [parent] Data too large, data for [] would be [123848638/118.1mb],
         which is larger than the limit of [123273216/117.5mb],
         real usage: [120182112/114.6mb], new bytes reserved: [3666526/3.4mb]
```

**一眼识别**：HTTP 429 + 报错含 `Data too large`。

**根因**：ES 的**熔断器**估算出这个操作会让 JVM 堆超限，于是**主动拒绝**以保护节点不 OOM。默认阈值：

| 熔断器 | 默认限制 |
|--------|---------|
| parent（总） | **95%** JVM 堆 |
| fielddata | 40% JVM 堆 |
| request | 60% JVM 堆 |
| in_flight_requests | 100% JVM 堆 |
| accounting | 100% JVM 堆 |

**排查路径**：
```powershell
# 各熔断器的用量与触发次数
curl.exe -s "http://localhost:9201/_nodes/stats/breaker?pretty"

# 堆使用率
curl.exe -s "http://localhost:9201/_cat/nodes?v&h=name,heap.percent,heap.max,ram.percent"

# 找出正在跑的昂贵查询
curl.exe -s "http://localhost:9201/_tasks?detailed=true&actions=*search*"
```

**按是哪个熔断器触发来定位根因**（这条最实用）：

| 哪个熔断在跳 | 说明什么 | 怎么修 |
|-------------|---------|--------|
| **fielddata** | 在 text 字段上聚合/排序 | 改用 keyword 子字段（见故障模式 1） |
| **request** | 单个查询太大（聚合桶太多） | 降 `size`、加前置过滤、分页 |
| **parent** | 整体内存压力大 | 降并发 / 加堆 / 减分片数 |
| **in_flight_requests** | 请求体过大 | 拆小 bulk / search 请求 |
| **accounting** | 分片或段太多 | 减分片数、forcemerge（课 15） |

**修复**：
1. **紧急止血**：`POST /_tasks/<task_id>/_cancel` 取消昂贵任务；`POST /_cache/clear?fielddata=true` 清 fielddata 缓存
2. **根治**：按上表修查询或映射

> ⚠️ **绝对不要做的事**：调高熔断阈值来"消除报错"。熔断跳了是**事故差点发生**的告警，不是误报。调高阈值 = 把"查询失败"换成"节点 OOM 被杀"。

**预防**：堆使用率**持续超过 85% 就该处理**；fielddata 用量应长期接近 0（现代 ES 用 doc_values，不该有 fielddata）。

📚 官方文档：[Circuit breaker errors](https://www.elastic.co/docs/troubleshoot/elasticsearch/circuit-breaker-errors)（核查于 2026-09）

## 三、落地 / 上线 Checklist

投产前逐项打勾。**这份清单的每一条都对应前面某个故障模式**。

### 3.1 索引设计

- [ ] 映射**显式声明**，不用动态推断（生产建议 `dynamic: strict`）
- [ ] 需要聚合/排序的字段**配了 keyword 子字段**（故障模式 1）
- [ ] 分片数**按容量规划**设定，不是默认值（课 10；故障模式见 1.1 反模式四）
- [ ] 单节点环境显式写了 `"number_of_replicas": 0`；生产至少 1 副本（故障模式 5）
- [ ] 字段总数有上限意识（默认 `index.mapping.total_fields.limit = 1000`，本机实测确认）
- [ ] 用了**索引模板**固化以上配置（课 15）

### 3.2 写入链路

- [ ] **所有 bulk 调用都判了 `errors`**（故障模式 3）
- [ ] 有失败重试与**死信队列**，失败数据不静默丢弃
- [ ] 写入有**速率控制**（bulk 每批 1000~5000 条，不是越大越好）
- [ ] 脏数据有处理策略（`ignore_malformed` / pipeline 兜底），且**知道脏值会留在 `_source`**（故障模式 2）
- [ ] 幂等：`_id` 由业务侧生成，重跑不产生重复（课 12 实测 `_id` 幂等）

### 3.3 查询链路

- [ ] 没有对 text 字段做聚合/排序（故障模式 1）
- [ ] 深分页用 `search_after`，不用 `from/size` 翻到很深（本机实测 `max_result_window = 10000`）
- [ ] 聚合有 `size` 上限，不会生成无限桶
- [ ] 有慢查询日志或超时设置

### 3.4 运维与数据安全

- [ ] **快照（SLM）在跑**，且验证过**能恢复**（课 11 实测跨集群恢复成功）
- [ ] 时序数据上了 **Data Stream 或别名 + rollover**（课 13 / 课 15）
- [ ] **ILM 策略已配**，且确认 delete 阶段**只在快照就位后**才启用（故障模式 6 / 反模式六）
- [ ] ILM 的 `poll_interval` 已知晓（默认 10 分钟，不是实时的）（课 15）
- [ ] 磁盘告警 < 80%
- [ ] 堆内存告警 < 85%（故障模式 7）
- [ ] **别名的删除用 `_aliases` remove，不用 `DELETE /别名`**（课 15 实测后者会被拒绝）

### 3.5 架构层面

- [ ] **ES 不是唯一数据源**，原始数据能从别处重建（反模式一）
- [ ] 数据源到 ES 的同步链路有监控与告警
- [ ] 应用**只认别名**，不认具体索引名（课 15）

## 四、真实事故案例复盘

> **纪律**：本节要求案例可溯源。**本机学习集群没有真实生产事故**，以下为课程实测中真实发生的两次"事故级"教训，均来自本课程的实测记录，非虚构。

### 案例一：销毁 node-3 数据盘 → 分片永久丢失（课 10 实测）

**发生了什么**：为验证故障转移，我停掉 node-3 并删除其数据目录，模拟磁盘永久损坏。

**结果**：
- 有副本的索引（`l9_orders`，3 主 1 副）→ 集群转 **yellow**，数据未丢，副本自动提升为主分片
- 0 副本的索引 → 集群转 **red**，该节点上的主分片**数据永久丢失**

**教训**：
1. **副本不是性能选项，是数据安全选项**。0 副本 = 接受数据丢失。
2. 这与故障模式 5 完全对应——red 状态下部分数据不可读写，只能靠 reroute 强制分配空分片（**等于接受数据丢失**）。

**可执行的结论**：生产索引 `number_of_replicas` 至少为 1；同时**快照必须在跑**（副本防的是节点故障，快照防的是"删库跑路"级别的误操作）。

### 案例二：元数据损坏 → 数据其实还在（课 11 实测）

**发生了什么**：9200 单节点集群因 `elasticsearch.yml` 被误改为 node-3 配置，重启后报 `CorruptStateException`。

**抢救路径**（真实执行成功）：
1. 全量备份 `data` 目录
2. 清空 `data/_state`
3. 重启
4. `GET /_dangling` 列出孤儿索引
5. `POST /_dangling/<uuid>?accept_data_loss=true` 逐个恢复

**教训**：**元数据坏了不等于数据坏了**。慌张之下直接清 data 目录 = 真丢数据。

**可执行的结论**：遇到 `CorruptStateException` 第一反应是**备份**，不是重装。
