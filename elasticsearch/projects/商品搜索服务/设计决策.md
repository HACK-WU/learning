# 设计决策：5 个权衡点

> 每个决策都按五段式写：**候选方案对比 → 最终选择 → 选择理由 → 付出的代价 → 什么情况下该改选另一个**。
> 判断一个决策是不是"真权衡"的标准很简单：**换个人来，可能选另一个，而且也有道理**。

---

## 决策 1：分词器组合——索引 `ik_max_word` + 搜索 `ik_smart`

### 候选方案

| 方案 | 索引分析器 | 搜索分析器 | 特点 |
|------|-----------|-----------|------|
| A | `ik_smart` | `ik_smart` | 索引体积小、查询快，但**召回差**：「小米笔记本」只切成「小米/笔记本」，索引里没有「笔记」「本」，用户搜"笔记"就搜不到 |
| B | `ik_max_word` | `ik_max_word` | 召回最好，但**精度差**：查询词被切碎，碎片词单独命中大量无关文档 |
| C | `ik_max_word` | `ik_smart` | 索引侧保留全部切分（召回），搜索侧合并成粗粒度（精度） |
| D | C + 同义词/拼音扩展 | `ik_smart` | 召回更广，但要维护词表，且同义词会稀释相关性 |

### 最终选择：**C**

### 理由

索引和搜索**目的相反**：索引时希望"多切一点，别漏"，搜索时希望"切得准，别误命中"。这两件事用同一个分析器做不到，所以必须分离。

本项目用「小米笔记本」实测了 A/B/C 的行为差异：

```
方案 B（两边都 max_word）：查询切成 小米 | 笔记 | 本 | 笔记本
方案 C（索引 max_word + 搜索 smart）：查询切成 小米 | 笔记本
```

在默认 OR 语义下，方案 B 多出的碎片词「本」会命中所有 description 里带"本商品"的配件文档。
实测 `cap_products_v1`（B）命中 **23 条**，`cap_products_v2`（C）命中 **19 条**，
v1 独有的 4 条**全部是配件**——它们跟"小米笔记本"毫无关系。

### 付出的代价

- 索引体积更大（`max_word` 把每个交叉词都存进倒排表）
- 查询词变化时，索引侧的词项可能永远用不上（冗余）
- 分析器一旦定下就属于映射，**改它必须 reindex**（这正是决策 3 要解决的问题）

### 什么时候该改选

- **短文本精确匹配为主**（品牌名、SKU、状态枚举）→ 改用 `keyword` + `term`，根本不该走全文检索
- **搜索词以错别字、简称、口语为主** → 上方案 D，并配合 `fuzziness`（课 7 实测过代价）
- **索引体积是硬约束**（TB 级冷数据）→ 退回方案 A，牺牲召回换存储

## 决策 2：分片与副本规划——1 主 1 副

### 候选方案

| 方案 | 主分片 | 副本 | 适用场景 |
|------|-------|------|---------|
| A | 1 | 0 | 单节点学习环境；生产上等于裸奔 |
| B | **1** | **1** | 中小数据量（单分片 20–50 GB 以内） |
| C | 3 | 1 | 数据量更大或写入并发更高 |
| D | 50 | 1 | ❌ 拍脑袋"分片多点更快" |

### 最终选择：**B（1 主 1 副）**

### 理由

本项目只有 38 条商品，按官方"单分片 20–50 GB"的建议，1 个主分片绰绰有余。选 1 主还顺带避开两个实测过的坑：

1. **多分片会让聚合不准**：课 9 / 课 14 实测，50 分片的 `terms` 聚合 `doc_count_error_upper_bound` 高达 **82**，而单分片恒为 0
2. **多分片的代价在长尾而非均值**：课 14 实测 1/3/50 主分片（同样 3000 条数据）p95 = 16.58 / 16.48 / **35.90** ms，而 p50 几乎没差别

副本给 1 而不是 0：课 10 用真删数据盘的方式验证过——**0 副本 + 节点永久损毁 = 那部分数据永久消失**。副本是数据的第二份存在，不是性能优化。

### 付出的代价

- 单分片意味着**失去了并行扩容能力**，数据涨到几百 GB 后必须 `split` 或重新 reindex
- 副本让存储翻倍，写入要等主副都成功（`successful: 2/2`）

### 什么时候该改选

- 数据量超过单个分片 50 GB → 按 `总量 / 30GB` 重新规划，且分片数取数据节点数的整数倍
- 单节点学习环境 → 改方案 A（副本注定无处安放，yellow 是物理必然，设 0 反而干净）
- 读多写少、要求高可用 → 副本加到 2–3

## 决策 3：索引结构变更策略——别名 + reindex 原子切换

### 候选方案

| 方案 | 停服？ | 改代码？ | 数据风险 |
|------|-------|---------|---------|
| A | 停服重建 | 否 | 重建期间服务不可用 |
| B | 改索引名 + 发版 | **是** | 切换窗口内新旧不一致 |
| C | 双写双索引 + 灰度切流 | 是 | 实现复杂，但可随时回退 |
| D | **别名 + reindex + 原子切换** | 否 | 切换是原子的，回退就是一个请求 |

### 最终选择：**D**

### 理由

- 应用**只认别名 `cap_products`**，永远不知道背后是哪个具体索引 —— 这是零停机的技术前提
- `remove` + `add` 放在**同一个 `_aliases` 请求**里，ES 保证原子生效，不存在"两边都没有"的中间态（课 15 实测）
- 切换前先 **reindex 到新索引并单独验证**，确认没问题了才动别名；文档数不一致就**拒绝切换**（`reindex-switch.js` 里写死了这个保护）
- 回退成本极低：`npm run switch -- --to=v1`，一个请求切回去

### 付出的代价

- **磁盘要能同时放下新旧两个索引**（切换期翻倍）
- reindex 期间的数据变更**不会自动跟过来**（本项目切换很快，可接受；生产要配合双写或按时间戳追赶）
- 别名多了一层间接性，排查时要先确认"别名现在指向谁"

### 什么时候该改选

- **TB 级索引**：停机窗口和磁盘都不允许翻倍 → 上方案 C（双写 + 增量追赶 + 灰度切流）
- **需要跨集群迁移**：用 `reindex` 的 `remote` 源，或走快照恢复
- **只是加字段、不改已有字段类型**：根本不用 reindex，直接 `PUT /index/_mapping` 加字段即可（课 5 实测：新增字段允许，改类型不允许）

## 决策 4：分面筛选的实现——`post_filter` 而不是 `filter`

### 候选方案

| 方案 | 做法 | 后果 |
|------|------|------|
| A | 品牌/分类条件放进 `query.filter` | 分面里只剩被选中的那个品牌，用户看不到"华为还有 4 件"，无法一键改选 |
| B | **条件放进 `post_filter`** | 聚合基于"除该维度外的其他条件"，返回结果才被筛选 |
| C | 发两次请求（一次带筛选取结果、一次不带取分面） | 逻辑清晰但要发两次，且两次结果可能对不上 |

### 最终选择：**B**

### 理由

分面统计存在的意义就是**告诉用户"你还能选什么"**。方案 A 会把它变成"你选了什么"，直接废掉这个功能。
`post_filter` 在查询之后、聚合之后才作用于返回的 hits，正好是这个语义。

实测（选品牌=苹果之后）：品牌分面仍然显示 苹果 5 / 华为 4 / 小米 4 件，而返回的样例 hits 只有苹果的商品。

### 付出的代价

- 多一层概念，读代码的人容易困惑"这个条件到底生效了没"
- `post_filter` 不参与打分也不参与聚合，写错位置（放进 query）行为完全不同且**不报错**

### 什么时候该改选

- 分面维度之间是**互斥且不需要反选**的（例如时间范围）→ 用方案 A 更简单，还能利用 filter 缓存
- 需要**完全不同的聚合条件** → 只能用方案 C

## 决策 5：深分页方案与决胜键——`search_after` + `sku`

### 候选方案

| 方案 | 上限 | 适用场景 |
|------|------|---------|
| A | `from` + `size` | 10000 条硬上限；且 `from` 越大越慢（每个分片都要先算 `from+size` 条再丢弃） |
| B | `scroll` | 无上限，但持有的是**发起那一刻的快照**，数据变了看不见 |
| C | **`search_after`** | 无上限，每次只算当前页，看到的是最新数据 |
| D | PIT + `search_after` | C 的加强版：用 `keep_alive` 保证多页之间的一致性视图 |

**决胜键（tie-breaker）的三选一**：

| 选项 | 可行性 |
|------|--------|
| `_id` | ❌ ES 9.5.1 禁止排序：`Fielddata access on the _id field is disallowed`（课 7 实测） |
| `_doc` | ⚠️ 最快，但它是 Lucene 内部顺序，**reindex 之后会变**，导出结果不可复现 |
| **业务主键 `sku`（keyword）** | ✅ 稳定、可复现，跨索引重建保持一致 |

### 最终选择：**C + 业务主键 `sku` 做决胜键**

### 理由

- 用户翻页要看到最新数据 → 排除 B（scroll 是快照）
- 数量可能超过 10000 → 排除 A
- 决胜键必须稳定，否则排序值相同的文档会在翻页时重复或丢失 → 排除 `_doc`，`_id` 又不能排
- 本项目只有 38 条、单次导出瞬间完成，还没到需要 PIT 的程度（数据量上去后再加）

### 付出的代价

- `search_after` **不能跳页**，只能一页一页往后翻（"直接跳到第 50 页"做不到）
- 排序字段组合必须唯一确定顺序，否则游标失效
- 游标是上一页最后一条的 sort 值，客户端要一直带着它

### 什么时候该改选

- 需要**全量导出且耗时很长**（几分钟以上）→ 方案 D（PIT），保证过程中数据变化不影响结果
- 需要**任意跳页**（如后台管理列表）→ 方案 A，但要接受 10000 上限并把它暴露给产品
- 需要**离线全量备份** → 走快照而不是查询导出

## 决策之间的依赖

```
决策 1（分析器分离）
   └─→ 分析器属映射，改它必须重建索引 ──→ 决策 3（别名 + reindex 原子切换）
                                              └─→ 切换前后要能对比效果 ──→ 探针查询用默认 OR 语义
决策 2（1 主 1 副）
   └─→ 单分片天然规避了多分片聚合误差 ──→ 决策 4 的分面计数是准的
决策 5（search_after + sku）
   └─→ 决胜键用业务主键 ──→ 即使走了决策 3 的 reindex，导出顺序依然可复现
```
