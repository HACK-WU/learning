# 反例对照：能跑，但很糟

> 下面这个版本**能跑通、能出结果、不报错**——这正是它危险的地方。
> 它和正确版本的差别，全都要等数据量涨上去、或者线上出问题那天才会暴露。
>
> 对照着看，比看十遍"最佳实践"记得牢。

## 反例代码

```js
// ❌ 反面教材：一个"能跑"的商品搜索服务
import { Client } from '@elastic/elasticsearch';

const client = new Client({ node: 'http://localhost:9201' });

// ① 用 superuser 连集群，密码硬编码
const client2 = new Client({
  node: 'https://localhost:9200',
  auth: { username: 'elastic', password: '9PvhcGNNc86uFZb_ePAN' }
});

// ② 不建映射，让 ES 自己猜
async function syncBad(products) {
  for (const p of products) {
    await client.index({ index: 'shop', document: p });   // ③ 一条一条写
  }
}

// ④ 所有条件塞进 must；⑤ 全表拉回来在应用层过滤
async function searchBad(keyword, brand, minPrice) {
  const res = await client.search({
    index: 'shop',
    size: 10000,                                           // ⑤ 一次拉一万条
    query: {
      bool: {
        must: [
          { match: { name: keyword } },
          { term: { brand } },
          { range: { price: { gte: minPrice } } }
        ]
      }
    }
  });

  // ⑤ 分页靠 JS 切片
  const page = 0, pageSize = 10;
  return res.hits.hits.slice(page * pageSize, (page + 1) * pageSize);
}

// ⑥ 改索引结构 = 改代码里的索引名 + 重新发版
async function rebuild() {
  await client.indices.create({ index: 'shop_v2' });
  await client.reindex({
    source: { index: 'shop' },
    dest: { index: 'shop_v2' }
  });
  // 应用里把 'shop' 改成 'shop_v2'，然后发版
}
```

## 逐条对比

### ① 用 superuser 跑应用服务

| | 反例 | 正确做法 |
|---|---|---|
| 写法 | `auth: { username: 'elastic', password: '...' }` | 建只读角色 + 应用账号（见 `ops/security.js`） |
| 后果 | 一个 SQL/日志泄露就是整集群权限；删库只需一行代码 | 应用账号只能读 `cap_products*`，写入直接 403 |

**为什么糟**：`elastic` 是超级用户，没有任何权限边界。而且密码硬编码在源码里，进了 git 就永久留痕。
本项目实测过正确做法：只读账号读成功、写入被拒 **403**、错密码 **401**——权限边界是被验证过的，不是"配了应该就行"。

---

### ② 不建映射，让 ES 猜

| | 反例 | 正确做法 |
|---|---|---|
| 写法 | 直接 `index(document)`，不建 mapping | 组件模板 + 索引模板 + `dynamic: strict` |
| 后果 | 字段类型由第一条数据决定，之后来啥都往里塞 | 类型显式声明，未知字段直接拒收 |

**为什么糟**：动态映射猜错了**不报错**。课 5 实测过两个真实后果：

- 字段猜成 `long`，写入 `19.9` → `_source` 保留 19.9，但索引里是 `19`，**静静地算错**
- 字符串默认生成 `text` + `keyword` 双字段，全字段都加会让索引体积明显膨胀

本项目的 `dynamic: strict` 实测效果：多写一个 `color` 字段 → `strict_dynamic_mapping_exception` 整篇拒收，错误在同步阶段就暴露，不会带着脏数据上线。

---

### ③ 一条一条写

| | 反例 | 正确做法 |
|---|---|---|
| 写法 | `for (const p of products) await client.index(...)` | `client.bulk({ operations })` 分批 |
| 后果 | 38 条 = 38 次 HTTP 往返；每条都要等网络 | 分 2 批，2 次往返 |

**为什么糟**：网络往返是这里最大的开销，跟 ES 处理能力无关。数据量涨到 10 万条时，反例要跑几万次往返。

更重要的是**部分失败的处理**。反例里一条失败就抛异常，前面写进去的不会回滚，也没人知道写到了哪。
正确做法是检查 `res.errors` 并遍历 `items`——课 12 实测：`errors=true` 时**成功项已经落库了**，
必须逐项区分"可重试（429/503）"和"数据本身有病（解析失败）"，后者重试一万次也没用。

---

### ④ 所有条件塞进 `must`

| | 反例 | 正确做法 |
|---|---|---|
| 写法 | 关键词、品牌、价格全在 `must` | 打分条件进 `must`，筛选条件进 `filter` |
| 后果 | 筛选条件污染相关性分数 | 分数只由用户真正搜的东西决定 |

**为什么糟**：用户搜"手机"、只想看苹果品牌——品牌条件放进 `must` 后，分数从 **0.7262 涨到 1.6706**（课 6 实测）。
这个分数对用户毫无意义（他搜的是"手机"不是"苹果"），而且会让后续的相关性调优失去基准：
你调了半天 boost，其实调的是筛选条件带来的噪声。

---

### ⑤ 全表拉回应用层过滤 + JS 切片分页

| | 反例 | 正确做法 |
|---|---|---|
| 写法 | `size: 10000`，`hits.slice()` 在 JS 里分页 | `search_after` 游标分页，每页只取 10 条 |
| 后果 | 每次查询传输并反序列化一万条文档；翻页越深越浪费 | 每次只算当前页 |

**为什么糟**：三个层面都错。

1. **传输**：一万条文档从 ES 传到应用，网络和序列化成本远超查询本身
2. **上限**：`from + size` 超过 10000 直接报错——`Result window is too large, from + size must be less than or equal to: [10000] but was [10005]`（本项目实测复现）
3. **语义**：在应用层做筛选，等于放弃了 ES 的倒排索引，把搜索引擎当数组用

正确做法实测：4 页导出 38 条，排序单调性校验通过，且完全不受 10000 限制。

---

### ⑥ 改索引结构 = 改代码 + 发版

| | 反例 | 正确做法 |
|---|---|---|
| 写法 | 建 `shop_v2` → reindex → 改代码里的索引名 → 发版 | 应用只认别名，切换在一个 `_aliases` 请求里原子完成 |
| 后果 | 需要发版；切换窗口内新旧索引不一致；回退要再发一次版 | 零停机；回退就是一个请求 |

**为什么糟**：

- **耦合**：索引是运维层面的事，不该要求业务代码跟着改
- **风险**：发版期间如果有请求打到旧索引，新旧数据不一致
- **回退成本**：发现 v2 有问题，要再走一遍发版流程

本项目实测的完整链路：建 v2 → reindex（**核对文档数不一致就拒绝切换**）→ 对比切换前后效果 → 原子切换 → 验证 → 可一键回滚，全程应用代码一行没改。

## 还有几个没写进代码但同样常见的坑

| 坑 | 为什么糟 | 正确做法 |
|---|---------|---------|
| 分片数拍脑袋给 20/50 | 课 14 实测：50 分片 p95 慢 2.2 倍、存储 4.7 倍、聚合误差上界 **82** | 按"单分片 20–50 GB"规划，宁小勿大 |
| 用 `text` 字段做聚合 | 报 `Fielddata is disabled`；就算开 `fielddata` 也会得到"苹""果"这种碎桶 | 聚合/排序一律用 `keyword` |
| 报错只看最外层 | 外层常是 `search_phase_execution_exception`，等于什么都没说 | 一律读 `error.root_cause`（本项目 `es/client.js` 已封装） |
| 深分页去调 `max_result_window` | 把上限从 1 万调到 100 万，只会让集群更容易被打垮 | 换 `search_after` |
| 拿 `_id` 当排序决胜键 | ES 9.5.1 直接拒绝：`Fielddata access on the _id field is disallowed` | 用业务主键（本项目用 `sku`） |
| 把 ES 当唯一数据源 | 数据丢了重建不了 | ES 是索引副本，不是原始账本 |

## 一句话总结

反例的每一条单独看都是"小问题"，但它们共享同一个根因：**把 ES 当成了一个"存 JSON 的地方"**，
而不是一个需要你先想清楚数据形状、再让它干活的系统。

本项目做的所有设计，本质上都是在回答三个问题：
**数据长什么样（映射/分析器）**、**怎么问才准（查询/分面/分页）**、**改错了怎么救（模板/别名/reindex）**。
