## 一、适用边界与反模式

**"不该用 Celery"比"怎么用 Celery"更值钱。** 先说清楚什么场景别上。

### 别用 Celery 的五种情况

| 场景 | 为什么别用 | 该用什么 |
|------|-----------|---------|
| **任务必须在请求里同步拿到结果** | Celery 是异步的，你绕一圈回来延迟只会更高 | 直接同步调用 |
| **任务量极小且不着急**（每天几十条） | 多一套 broker + worker 的运维成本不划算 | cron + 管理命令 |
| **需要严格顺序**（同一用户的操作必须按序） | Celery 只保证投递不保证顺序，并发下必然乱序 | 单队列 + 单并发，或数据库状态机 |
| **需要秒级精度的延迟任务** | ETA 任务存在 worker 内存，且受可见性超时影响 | 数据库轮询（见故障模式 6、10） |
| **需要 exactly-once（严格一次）** | Celery 只有 **at-least-once（至少一次）** 语义 | 靠业务幂等补，见故障模式 3 |

> 【官方】Celery 官方明确：任务可能被投递多次，设计上不做 exactly-once 保证。
> 这不是缺陷，是分布式系统里"网络分区不可判定"的必然结果 —— 你说不清"超时"到底是"没执行"还是"执行了但没回"。

### Celery 新手最常见的三个反模式

**反模式 1：把 Celery 当数据库用**
```python
# ❌ 错：想靠 result backend 长期存业务数据
result = task.delay(order_id)
Order.objects.filter(id=order_id).update(celery_result_id=result.id)
# 默认 result_expires=1 天，明天这个 id 就废了
```
【官方】`result_expires` 默认 1 天。业务数据的唯一真相源只能是数据库，result backend 是**临时通道**不是存储。

**反模式 2：任务里查出一个对象，改完再存回去**
```python
# ❌ 错：读-改-写之间有窗口，并发下互相覆盖
order = Order.objects.get(id=order_id)
order.amount += 100
order.save()
```
正确做法见故障模式 3 —— 用 CAS 条件更新，让数据库帮你判断"该不该改"。

**反模式 3：所有任务共用一个队列**
一张表全塞一个队列，一个跑 2 小时的对账任务能把 5000 个发短信任务堵死。
【实测】这是本项目决策 1 的核心动因，队列隔离的实测见 [设计决策](projects/电商订单履约系统/设计决策.md)。

### 故障模式 1 · 任务发了但永远没人执行（静默挂死）

**症状**（可观测）：
`task.delay()` 返回成功、`task_id` 拿得到，但任务永远停在 `PENDING`。
**日志里没有任何报错** —— worker 安安静静，什么都不做。
`redis-cli LLEN default` 显示有积压，且数字不减。

**根因**：
任务被投递到了某个队列，但**没有任何 worker 在消费这个队列**。
最常见的触发原因：该任务**没配 `task_routes`**，于是落到了默认队列 `default`，而你的 worker 只消费业务队列。

> 【实测】本项目踩过两次，且第二次我**误判了根因**：
> 第一次是 `issue_coupon` 漏配路由 → chord 的 header 凑不齐 → 永不回调。
> 第二次是 `fulfill_order`（**chord 的编排入口**）漏配路由 → 整个编排根本没开始。
> 第二次我一度以为是"chord 的解锁任务走了 default 队列"，甚至据此得出错误结论"worker 必须消费 default"。
> 详见 [设计决策 · 决策 4（已修正）](projects/电商订单履约系统/设计决策.md)。

**排查路径**：
```bash
# ① 看每个 worker 在消费哪些队列（最关键的一步）
celery -A proj inspect active_queues

# ② 看各队列积压
redis-cli -n 0 LLEN default
redis-cli -n 0 LLEN fast
redis-cli -n 0 LLEN slow

# ③ 🔥 别猜积压的是什么，直接解出来看任务名
python -c "
import redis, json
r = redis.Redis(port=6379, db=0)
print(json.loads(r.lindex('default', 0))['properties']['task'])
"
```
第 ③ 步是我推翻自己错误结论的关键 —— **能用一条命令把事实取出来看，就不要用三段逻辑推断出来**。

**修复**：
```python
# 补上漏配的路由（治本）
CELERY_TASK_ROUTES = {
    'orders.tasks.fulfill_order': {'queue': 'fast'},   # ⭐ 编排入口也要配！
    ...
}
```
> ⚠️ **不要**用"让 worker 多消费一个 default 队列"来绕过。
> 它能解决症状，但会**永久掩盖漏配路由这个真因**，以后每次新加任务漏配都发现不了。

**预防**：
- 新增任务的 PR 模板里加一条：配了 `task_routes` 吗？
- 起 worker 时**故意不消费 default**，让漏配立刻暴露而不是潜伏

### 故障模式 2 · chord 永不回调

**症状**：
chord 的 header 任务全部 `succeeded`，但 body 回调**永远不执行**，也不报错。
`chord_result.get()` 一直阻塞到超时。

**根因**（分两种，必须区分）：

| 类型 | 触发条件 | 占比 |
|------|---------|------|
| **A · 编排入口没跑**（最常见） | 入口任务漏配路由，整个 chord 没开始 | 高 |
| **B · backend 无原生协调** | 用了不支持原生 chord 的 backend，`celery.chord_unlock` 轮询任务没人消费 | 低 |

【官方】Celery 的 **Redis backend 实现了原生 chord 协调**：
`apply_chord()` 时用 `ZADD` 把 header 成员登记进有序集合，每个成员完成时 `ZADD` 标记 + `ZCOUNT` 计数，
**计数一达标就直接 `callback.apply_async()`** —— 中间不需要任何任务。
`celery.chord_unlock` 这个轮询任务**只在不提供原生协调的 backend 上**作为兜底出现。

> 【实测】本项目用的是 Redis，修复路由后日志中 `chord_unlock` 出现 **0 次** —— 印证了原生协调路径。

**排查路径**：
```bash
# ① 先确认 chord 到底开始了没有（查入口任务是否执行过）
grep 'fulfill_order' logs/worker.log

# ② 看有没有 chord_unlock（有 → 走的是兜底轮询路径）
grep -c 'chord_unlock' logs/worker.log

# ③ 确认 header 任务的结果有没有存下来
redis-cli -n 1 KEYS 'celery-task-meta-*' | head
```

**修复**：
- 类型 A：给编排入口任务补路由（同故障模式 1）
- 类型 B：确保 `celery.chord_unlock` 所在队列有人消费，或换用支持原生协调的 backend

**预防**：
- **chord 的 header 任务绝不能设 `ignore_result=True`** —— 【官方】原话 "Tasks used within a chord must not ignore their results"，
  结果存不下来就没法计数，回调永远不会触发
- 这与"不需要结果就别存"的通用建议**直接冲突**，是必须记住的例外

### 故障模式 3 · 任务重复执行导致重复扣款（最贵的一种）

**症状**：
同一笔订单扣了两次款 / 库存被回滚多次 / 用户收到多条短信。
日志里同一个业务 id 出现**多条 task_id 不同**的执行记录。

**根因**：
Celery 是 **at-least-once（至少一次）** 投递。以下任一情况都会重投：
- worker 进程被 `SIGKILL`（OOM、强制重启、机器宕机）
- 任务耗时超过 `visibility_timeout`（**且超过重投检查周期**，见下）
- 【实测】本项目 SIGKILL worker 后，任务**重新投递并执行**，START 次数 = 2

**排查路径**，先分清是哪种重投：
```python
# 在任务里打这两行，一眼区分
logger.info(f'task_id={self.request.id} retries={self.request.retries}')
```
| 特征 | broker 重投 | Celery autoretry |
|------|------------|-----------------|
| `retries` | **始终 0** | 递增（1、2、3…） |
| `task_id` | **相同** | 相同 |
| 任务状态 | 无 RETRY 态 | 变 `RETRY` |
| 日志 | 无 retry 提示 | 有 `Retry in Ns` |

**修复**，三种幂等方案（本项目实测对比，同一关单任务执行 3 次）：

| 方案 | 实测结果 | 适用 |
|------|---------|------|
| 无幂等 | 库存 **10 → 13**（多回滚 2 次 = 超卖）❌ | — |
| **CAS 状态机** | `[1, 0, 0]`，库存 **11** ✅ | **首选**，有状态字段时 |
| Redis SET NX | 库存 **11** ✅ | 无状态字段 / 跨服务 |

```python
# 首选：CAS 条件更新 —— 让数据库替你判断"该不该改"
updated = Order.objects.filter(
    id=order_id, status='PENDING'      # ⭐ 条件带状态
).update(status='CLOSED')
if updated == 0:
    logger.info('状态已变更，跳过（幂等生效）')
    return
# 只有 updated == 1 才继续执行副作用
```

**预防**：
- **任何有副作用的任务，写完第一版就要加幂等** —— 不是等出事故再加
- Redis SET NX **必须带 `ex`**：【实测】忘设时 `TTL = -1`（永不过期），
  若任务在抢锁后、业务完成前崩溃 → 这个订单**永远无法再被关单**（死锁）

### 故障模式 4 · 幂等锁变成永久死锁

**症状**：
某个订单/任务**永远不再被执行**，日志里每次都显示"已被处理过，跳过"。
`redis-cli TTL <lock_key>` 返回 **-1**。

**根因**：
用 Redis 做幂等锁时**忘了设过期时间**：
```python
# ❌ 致命：没有 ex
r.set(f'lock:close_order:{order_id}', '1', nx=True)
```
【实测】本项目实测 `TTL = -1`（永不过期）。一旦任务在抢锁之后、业务逻辑完成之前崩溃，
这个锁就**永远不会被释放** —— 该订单再也无法关单。

**排查路径**：
```bash
redis-cli TTL lock:close_order:12345   # -1 = 永不过期（就是它了）
redis-cli KEYS 'lock:*' | wc -l        # 锁是否在持续堆积
```

**修复**：
```python
# ✅ 正确：NX + EX 必须成对出现
ok = r.set(f'lock:close_order:{order_id}', '1', nx=True, ex=3600)
if not ok:
    return '已被处理过，跳过'
try:
    do_business()
finally:
    r.delete(...)   # 或用 Lua 脚本校验 token 再删，防误删别人的锁
```
`ex` 取值要 **大于任务最坏执行时间**，但要**小于**你希望的最长阻塞容忍。

**预防**：
- 代码审查把 `nx=True` 和 `ex=` 绑在一起查，缺一即拦
- 优先用 CAS 状态机（故障模式 3），它没有"锁"这个额外实体，也就没有锁泄漏

### 故障模式 5 · 任务读到未提交的数据（on_commit 缺失）

**症状**：
任务偶尔报 `DoesNotExist`，或读到的字段值是**旧值**。
诡异的是：手动重跑一次就好了 —— 典型的竞态特征。

**根因**：
```python
# ❌ 错：事务还没提交就发任务
with transaction.atomic():
    order.save()              # 还在事务里
    send_notification.delay(order.id)   # worker 可能比事务提交更快
```

**排查路径**：
看发任务的位置是否在 `transaction.atomic()` 块内，或用 `connection.in_atomic_block` 自查。

**修复**：
```python
# ✅ 正确：事务提交后再发
transaction.on_commit(lambda: send_notification.delay(order.id))
```

**预防**：
- 团队约定：**Django 项目里发任务一律走 `on_commit`**，不允许裸 `delay()`
- 【实测】本项目 `verify.sh` 检查⑥会专门验这一项

### 故障模式 6 · 任务静默消失

**症状**：
`delay()` 没报错，但任务**从来没执行过**，而且队列里也**找不到积压**（区别于故障模式 1）。

**根因**（按概率排序）：

| 原因 | 机制 |
|------|------|
| **ETA/countdown 任务 worker 重启** | ETA 任务存在 **worker 内存**里，重启即丢 |
| 用了 `expires` 且过期 | 到点未执行就被丢弃 |
| Redis 内存满触发 key 驱逐 | 【官方】会报 `InconsistencyError: Probably the key ... has been removed` |
| 没有 result backend 却调 `.get()` | 结果无处可存 |

【官方】"ETA tasks are stored in worker memory until their ETA arrives" —— 这是 Celery 与 RabbitMQ 延迟队列的关键差异。

**排查路径**：
```bash
celery -A proj inspect scheduled    # 看 ETA 任务是否还在
redis-cli INFO memory               # 看 Redis 内存是否接近 maxmemory
redis-cli CONFIG GET maxmemory-policy   # 若为 allkeys-lru 就会驱逐 key
```

**修复**：
- Redis 配置 `maxmemory-policy noeviction`（【官方】推荐，Celery 的 key 不能被驱逐）
- 重要延迟任务改**数据库持久化 + 轮询**，不要依赖 ETA

**预防**：
- 重要任务发完后记一条"待执行"流水到数据库，靠对账发现丢失
- 监控 Redis 内存与队列长度

### 故障模式 7 · 定时任务重叠执行

**症状**：
对账/结算跑了两次，数据翻倍；或者任务实例越来越多，最后拖垮数据库。

**根因**：
**beat 到点就发，不管上一次跑完没有。** 它没有"上次还在跑就跳过这一轮"的内置判断。

【实测】本项目实测：`schedule=3 秒`、任务耗时 `8 秒`，26 秒观察窗口内
**START = 8 次，END = 6 次** —— 明确重叠（有 2 个在窗口结束时仍未结束）。

**排查路径**：
```bash
celery -A proj inspect active     # 看同一任务是否同时有多个实例在跑
```

**修复**，三选一：
```python
# 方案 A：分布式锁（最可靠）
@app.task
def reconcile():
    if not r.set('lock:reconcile', '1', nx=True, ex=3600):
        return '上一轮还在跑，跳过'
    try:
        do_reconcile()
    finally:
        r.delete('lock:reconcile')
```
```python
# 方案 B：expire 兜底（简单但不精确）
beat_schedule = {'reconcile': {'task': 'x', 'schedule': 300, 'options': {'expires': 290}}}
```
```python
# 方案 C：把周期拉长到远大于任务耗时
```

**预防**：
- 任何周期性任务，都要先问一句：**"如果它跑了 3 倍时间，会发生什么？"**
- beat 本身是单点，生产要配存活监控（它挂了是**静默**的）

### 故障模式 8 · 慢任务堵死快任务

**症状**：
发短信要等 10 分钟才发出，但对账任务跑得好好的。
队列总长度在涨，但 `inspect active` 显示 worker 都在忙。

**根因**：
所有任务共用一个队列 + 一个 worker。前面排着 3 个 2 小时的对账任务，
后面 5000 个发短信任务只能干等 —— **经典的队头阻塞**。

【公认】这是队列隔离（决策 1）要解决的核心问题。

**排查路径**：
```bash
redis-cli LLEN default          # 队列积压
celery -A proj inspect active   # 正在跑的是什么任务、跑了多久
```

**修复**：
```python
# 按耗时拆分队列
CELERY_TASK_ROUTES = {
    'app.tasks.send_sms':    {'queue': 'fast'},
    'app.tasks.reconcile':   {'queue': 'slow'},
}
```
```bash
# 专属 worker，快慢互不干扰
celery -A proj worker -Q fast -c 20 --prefetch-multiplier=1
celery -A proj worker -Q slow -c 4  --prefetch-multiplier=1
```

**预防**：
- 任务按耗时分档，从一开始就分队列
- 长任务配 `prefetch_multiplier=1`（否则一个 worker 会一次抓一堆长任务，加剧不均）

### 故障模式 9 · worker 内存持续上涨直到 OOM

**症状**：
worker 进程 RSS 随时间单调上升，几天后被系统 OOM kill。
被 kill 时**正在执行的任务会丢失并重投**（回到故障模式 3）。

**根因**：
长时间运行的 Python 进程常见的内存泄漏：全局缓存、未释放的大对象、C 扩展泄漏、循环引用。

**排查路径**：
```bash
ps -o pid,rss,etime,cmd -C celery    # 看 RSS 随 etime 的增长
```

**修复**：
```bash
# 让 worker 子进程执行 N 个任务后自我替换（内存归零）
celery -A proj worker --max-tasks-per-child=1000

# 或设内存上限
celery -A proj worker --max-memory-per-child=512000   # KB
```

**预防**：
- 生产**必须**配 `max-tasks-per-child`（本项目用 1000）
- 任务里别用全局字典当缓存

### 故障模式 10 · revoke 拦不住已开跑的任务

**症状**：
明明调了 `revoke(task_id)`，任务还是跑完了，副作用照样发生。

**根因**：
【实测】`revoke(terminate=False)`（默认）**只是把 task_id 记进内存里的"已撤销"集合**。
任务已经开跑的话，worker 不会去检查这个集合，任务会正常跑完。

`revoke(terminate=True)` 能强杀，但它会**死在任何一行代码上** ——
如果你的关单任务执行到一半（库存已回滚、订单状态还没改）被杀，就留下了一个**不一致的中间态**。

**排查路径**：
```python
AsyncResult(task_id).state   # 若为 STARTED 说明已开跑，revoke 无效
```

**修复**：
- **别依赖 revoke 做业务撤销**。业务撤销要靠**业务状态检查** —— 任务内部在执行前先查状态是否仍然有效。

```python
@app.task
def close_order(order_id):
    order = Order.objects.get(id=order_id)
    if order.status == 'PAID':        # ⭐ 用户已支付，不该关了
        logger.info('订单已支付，放弃关单')
        return
    ...
```
> 【实测】这正是本项目决策 2 放弃"ETA 延迟关单"、改用 **beat 轮询**的核心依据：
> 用户第 14:59 支付、关单任务同时开跑，ETA 方案下已支付的订单照样被关；
> 而轮询方案的"撤销"是**天然免费**的 —— 订单一支付就不再满足扫描条件，任务根本不会被发出。

**预防**：
- 任何延迟执行的操作，执行前都要**重新校验前置条件**（不要相信发出任务时的世界）

### 故障模式 11 · 长任务超过检查周期被重投

**症状**（可观测）：
任务耗时 **> 约 90 秒**，被**同一个 task_id** 执行了两次，
两次开始时间相隔约 **88.8 秒**，且 `self.request.retries` 始终为 **0**。

**根因**：
【官方】Redis 的可见性超时机制：任务在 `visibility_timeout` 内未 ack，broker 会把它重新投递。
但**这里有个官方文档没说的隐藏前提** —— 重投不是"超时即触发"，而是**周期性检查**：

```python
# kombu 5.6.2 transport/redis.py
# 第 1382 行：每 10 秒调用一次
loop.call_repeatedly(10, cycle.maybe_restore_messages)

# 第 410 行 restore_visible(start=0, num=10, interval=10) 内部：
if (self._vrestore_count - 1) % interval:   # interval = 10
    return                                   # ⭐ 前 9 次直接返回，什么都不做
```
**实际检查周期 = 10 秒 × 10 ≈ 100 秒**（实测 88.8 秒）。

**精确实测**（4 组对照，`visibility_timeout = 5` 秒）：

| 任务耗时 | 执行次数 | 重投间隔 |
|---------|---------|---------|
| 30 秒 | 1 次 | — |
| 70 秒 | 1 次 | — |
| **110 秒** | **2 次** | **88.8 秒** |
| **150 秒** | **2 次** | **88.8 秒** |

**临界点在 70 ~ 110 秒之间。**

> 🔬 **这条结论我纠错过一次，过程值得看**：
> 前两次实验（20 秒任务）都没复现重投，我一度判定"这个说法在本环境不成立"。
> 后来读源码发现 `interval=10` 这个隐藏参数，才设计出跨过阈值的正确实验。
> **教训：实测没复现 ≠ 机制不存在**，很可能只是实验参数没跨过真实触发阈值。

**排查路径**，先分清是 broker 重投还是 Celery 重试：
```python
logger.info(f'task_id={self.request.id} retries={self.request.retries}')
```
| 特征 | broker 重投 | Celery autoretry |
|------|------------|-----------------|
| `retries` | **始终 0** | 递增 |
| 间隔 | 约 88.8 秒 | 按 backoff 计算 |
| 日志 | 无 retry 提示 | 有 `Retry in Ns` |

**修复**：
```python
# 调大 visibility_timeout 到大于任务最坏耗时（止血）
broker_transport_options = {'visibility_timeout': 14400}
result_backend_transport_options = {'visibility_timeout': 14400}
```
同时**必须加幂等**（治本，见故障模式 3）—— 超时调得再大，也挡不住 worker 真崩溃后的重投。

⚠️ **权衡**：调太大会延长"真·丢失任务"的重新可见时间。官方建议优先让任务变短或变幂等。

**预防**：耗时可能 > 90 秒的任务，一开始就调大 `visibility_timeout` 并加幂等。

## 三、一个流传很广但需要修正的说法

> 上面故障模式 11 讲的其实就是这个说法，这里补充**它为什么容易被人误判为"不成立"**。

官方文档写得很肯定（【官方】）：

> If a task isn't acknowledged within the Visibility Timeout the task will be redelivered to another worker and executed.

**但很多人在测试环境怎么试都复现不出来**（我也是）。原因就是上面那个隐藏的约 90 秒检查周期 ——
如果你的测试任务只跑几十秒，它会在第一次检查到来之前就正常 ack 掉，**永远观测不到重投**。

**实践建议不变**（"长任务要调大 visibility_timeout"仍然正确），
但**触发的时间尺度比文档给的要粗得多**。

> 🔬 **方法论教训**（这条比结论本身更重要）：
> "实测没复现"不等于"机制不存在"，很可能只是**实验参数没跨过真实的触发阈值**。
> 我前两次实验用的任务都是 20 秒，都没到 88.8 秒的检查周期。
> **是读源码找到 `interval=10` 才让我设计出正确的实验** —— 先有源码线索，才有有效实验。

**真实机制与精确实测数据见 [故障模式 11](#故障模式-11--长任务超过检查周期被重投)**，这里不重复。

但**触发的时间尺度比文档给的要粗得多** —— 这解释了为什么很多人在测试环境怎么试都复现不出来。

## 四、上线 Checklist

投产前逐条过（本项目 `verify.sh` 自动化了其中 6 项）。

### 可靠性

- [ ] `task_acks_late = True`（任务执行完才 ack，崩溃可重投）
- [ ] `task_reject_on_worker_lost = True`（worker 被强杀时任务重回队列）
- [ ] 所有有副作用的任务都有幂等保护
- [ ] Redis 幂等锁的 `nx=True` 都配了 `ex=`
- [ ] 长任务的 `visibility_timeout` 已调大（参考阈值：任务耗时 > 90 秒就要调）
- [ ] 发任务一律走 `transaction.on_commit`

### 配置

- [ ] `accept_content = ['json']`（**绝不含 pickle**）
- [ ] `task_serializer = 'json'`、`result_serializer = 'json'`
- [ ] Redis 的 `maxmemory-policy = noeviction`
- [ ] 所有任务都配了 `task_routes`（起 worker 时不消费 default，让漏配立刻暴露）
- [ ] 每个任务都有 `soft_time_limit` 和 `time_limit`

### 运维

- [ ] `max-tasks-per-child` 已配（防内存泄漏）
- [ ] 队列按耗时分档，快慢隔离
- [ ] 长任务队列 `prefetch_multiplier=1`
- [ ] beat 有存活监控（它挂了是**静默**的）
- [ ] 慢任务/失败任务有告警
- [ ] worker 与 beat 的日志分开落盘，且**用绝对路径**（相对路径会因 cwd 变化失效）

### 安全

- [ ] 任务参数只传 id / 基础类型，**不传 ORM 对象和 QuerySet**
- [ ] broker 不对外网暴露
- [ ] 任务不做权限校验的假设（worker 拿不到 request.user）
