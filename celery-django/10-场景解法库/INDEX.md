# Celery + Django 场景解法库

> **怎么用**：每个场景是一道**开放设计题**。先自己想 30 秒，再展开看解法——**先想后看，能力才长出来**。
> 🖼 **每个解法都配一张机制图**：图上画清该解法的数据流 / 组件关系，底部红色虚线框标出它的**失效点与代价**。判断一张图是否合格的标准是——**把它搬到本场景另一个解法下面，它就不成立了**。
> 配套：[08-实战经验.md](../08-实战经验.md)（为什么会崩，学习态）｜ [09-排障速查手册.md](../09-排障速查手册.md)（出错了怎么办，使用态）｜本库（新要求来了怎么设计，设计态）。
> 证据纪律：每条解法均标注来源 —— `【实测】`本机跑出来的、`【官方】`文档/源码、`【公认】`领域通行实践。核查于 2026-09。
> 默认配置值以 **Celery 5.6.3 / kombu 5.6.2 / Django 6.1 / Redis 7.0.15（WSL2 Ubuntu）** 为准。

## 🧭 遇到没见过的场景？六问思考框架

上面 11 个场景会过时，框架不会。新要求来了，按这六个维度依次过一遍：

| # | 维度 | 要问的问题 | 回指场景 |
|---|------|-----------|---------|
| 1 | **量** | 峰值多少？瓶颈在 worker、broker 还是下游数据库？ | [场景 1](场景-01-流量翻10倍.md) |
| 2 | **粒度** | 一个任务多大？拆细还是合并？失败成本与总开销怎么权衡？ | [场景 2](场景-02-数据量翻100倍.md) |
| 3 | **时长** | 任务跑多久？超过可见性超时会怎样？能否拆阶段？ | [场景 3](场景-03-一个任务跑2小时.md) |
| 4 | **重复** | 重投会怎样？幂等靠什么保证（状态机 / 唯一约束 / 外部幂等键）？ | [场景 4](场景-04-不重复扣款.md)、[场景 5](场景-05-部署不丢任务.md) |
| 5 | **顺序与速率** | 要优先级吗？要限流吗？限流是全局的还是 per-worker？ | [场景 7](场景-07-VIP插队.md)、[场景 8](场景-08-第三方限流.md) |
| 6 | **故障与证据** | Broker 挂了会怎样？失败消息去哪？测试是否真的经过 broker、worker 与目标队列？ | [场景 9](场景-09-Broker故障切换与任务语义.md)、[场景 10](场景-10-重试耗尽后的死信与安全重放.md)、[场景 11](场景-11-测试通过但生产路由失效.md) |

> **可靠性维度贯穿全部六问**——每个方案都要问一句“worker 现在被 `kill -9` 会怎样”（[场景 5](场景-05-部署不丢任务.md)）。

## 🔑 十一个场景的共同规律

回头看这 11 个场景，推荐路径里反复出现的是几条边界：

| 出现在这几个场景 | 共同的解法 |
|-----------------|-----------|
| 1、2、7、8 | **队列拆分 / 隔离** |
| 2、3、4、6 | **幂等** |
| 3、5 | **ack 与停机语义** |
| 4、5、6 | **状态机 / 执行记录** |
| 9、10、11 | **先定义故障语义，再设计恢复与验收证据** |

**队列隔离 + 幂等 + 可观测的恢复证据**是 Celery 生产落地的地基。
它们不性感，但大量生产问题都能追溯到“队列隔离、幂等或恢复证据”没有做，或做错了。

## 📚 证据与版本边界

- Celery 文档稳定版基线：5.6（本库核查于 2026-09；本机实测版本为 5.6.3）。
- Broker、任务确认、路由、测试与安全相关结论优先回指 [Celery 官方文档](https://docs.celeryq.dev/en/stable/)。
- `【实测】` 只代表本机 WSL2 / Redis 7.0.15 / kombu 5.6.2 的观察，不外推为所有部署的保证；新场景中的方案差异明确写出验证动作。
