# 场景 7：VIP 用户要插队（任务优先级，经典设计题）

**场景描述**：客服工单系统，普通用户提交工单后进入处理队列，平均等待 10 分钟。现在要求：**VIP 用户的工单必须优先处理，且 VIP 内部还要分等级**（钻石 > 黄金 > 白银）。当前：单队列，`-c 8`，Redis broker。

**🔒 先自己想 30 秒**：Redis broker 上"优先级"是怎么实现的？它和 RabbitMQ 的原生优先级是一回事吗？想清楚这一点，才知道该不该用 `priority` 参数。

<details><summary>💡 提示（关键事实：Redis 没有原生优先级）</summary>

- Celery 在 Redis 上是**模拟**优先级（拆多个子队列按序消费）。这意味着什么？
- 模拟的优先级在什么时候会失效？（提示：worker 已经预取了一批任务时）
- `prefetch_multiplier` 大的时候，优先级还有效吗？
- 除了 `priority` 参数，还有没有别的做法？（提示：队列隔离）

还有一个业务问题：**VIP 插队会不会导致普通工单饿死**？

</details>

<details><summary>📖 展开解法</summary>

### 解法一览

| 解法 | 能解决到 | 代价 | 适用边界 |
|------|---------|------|---------|
| **A · `priority` 参数** | 软性优先 | Redis 上是**模拟**的，不可靠 | 官方不推荐；RabbitMQ 上才可靠 |
| **B · 多队列 + 加权 worker** | 语义明确的差异化服务 | 运维复杂度 | **推荐** |
| **C · 多队列 + 顺序消费** | 简单有效 | 可能饿死低优先级 | 简单场景 |
| **D · 队列内排序（自维护有序集合）** | 精确优先级 | 实现复杂 | 极致要求时 |
| **E · 换 RabbitMQ** | 原生 `x-max-priority` | 引入新组件 | 优先级是核心需求时 |

### 各解法详解

![队列隔离对比：优先级同样依赖队列隔离与 prefetch=1](./assets/场景-队列隔离对比.svg)

#### 解法 A · `priority` 参数（先看清楚限制）

```python
process_ticket.apply_async(args=[tid], priority=9)
```

【官方】Redis 上 Celery 的优先级是**模拟实现**（拆成多个子队列按序消费）。
官方文档直接说：**推荐用 routing 而不是 priority 来保证服务质量。**

> ⚠️ **模拟优先级在 `prefetch_multiplier > 1` 时明显失效**——worker 已经预取了一堆低优先级任务，
> 新来的高优先级任务只能排在预取批次之后。这是"配了却完全没生效且无感知"的典型。

#### 解法 C · 多队列 + 顺序消费（推荐做法）

```python
# settings.py
CELERY_TASK_ROUTES = {
    'tickets.tasks.process_vip':    {'queue': 'vip'},
    'tickets.tasks.process_normal': {'queue': 'normal'},
}
```
```bash
# worker 同时消费两个队列，vip 写在前面会优先被轮询到
celery -A proj worker -Q vip,normal -c 8 --prefetch-multiplier=1
```

> ⚠️ `--prefetch-multiplier=1` 是**关键**——不设的话 worker 会一次抓一批，优先级形同虚设。

#### 解法 B · VIP 内部分级（拆三个队列 + 不同并发）

```bash
celery -A proj worker -Q vip_diamond -c 4 ...
celery -A proj worker -Q vip_gold,vip_silver -c 3 ...
celery -A proj worker -Q normal -c 1 ...     # ⭐ 保证普通工单不会被完全饿死
```

#### 隐藏陷阱：低优先级饿死

如果 VIP 流量持续很大，普通队列可能**永远排不上**。两个必须做的动作：

1. 给低优先级队列**保留最小并发**（如上例 normal 留 1 个）；
2. **监控队列等待时长**（最老消息的入队时间），超过阈值就临时扩容或告警。

### 非本栈替代路线（什么时候别用 Celery 做优先级）

| 诉求 | Celery 的边界 | 该用什么 |
|------|--------------|---------|
| **严格优先级 + 不许饿死** | Redis 模拟优先级没有饥饿保护 | **RabbitMQ**（原生 `x-max-priority`）或**加权公平队列**（如 Kafka share groups） |
| **优先级是核心业务诉求** | 模拟实现不可靠，且随 prefetch 失效 | 换 broker，或**自建调度层**：按优先级从数据库捞任务 |
| **需要"等待时长 SLA"保证** | Celery 没有排队时延保证 | 数据库存单 + **按优先级 + 入队时间排序捞取**（`ORDER BY priority DESC, created_at ASC`） |
| **SLA 等级特别多**（十几档） | 每档一个队列，运维爆炸 | 用两条队列（高/低）+ 队列内按分数排序（解法 D） |

> 💡 最后那条最实用：**数据库侧排序**往往是性价比最高的方案——
> 你本来就要存工单，加一个 `(priority, created_at)` 的复合索引，让 worker 按序捞，既不饿死也不引入新组件。

### 推荐路径（递进）

1. **第一步（先看清限制）**：不要用 `priority` 参数作为唯一手段（Redis 上不可靠）。
2. **第二步（推荐）**：C —— 多队列 + `--prefetch-multiplier=1`。
3. **第三步（VIP 内部分级）**：B —— 拆三个队列配不同并发，并给 normal 保留最小并发。
4. **第四步（防饿死）**：监控队列等待时长，超阈值告警或临时扩容。

### 效果对比：怎么验证这一步真的有效

| 维度 | 怎么看 | 期望变化 |
|------|--------|---------|
| **VIP 工单 P95 等待时长** | 记录入队到开始执行的时间 | 隔离后**显著下降**，且不受普通任务量影响 |
| **普通工单是否被饿死** | 监控 `normal` 队列最老消息年龄 | 有**上界**（如 < 15 分钟），而不是单调增长 |
| **优先级是否真的生效** | 同时投 100 VIP + 100 普通，统计完成顺序 | VIP 完成序在前的比例 **接近 100%**（`prefetch=1` 时） |

> ⚠️ 第三个维度是最容易造假的：如果 `prefetch_multiplier > 1`，VIP 优先比例会明显下降——
> **这个测试本身就是验证 prefetch 配置是否正确的手段**。

### 什么情况下此方案不适用

- **解法 A 单独用**：Redis 上不可靠，尤其 `prefetch_multiplier > 1` 时基本失效。
- **解法 C 的 `-Q` 顺序**：这不是严格的优先级保证，只是轮询偏好，高负载下会稀释。
- **解法 E（换 RabbitMQ）**：只为优先级换 broker 通常不划算，除非优先级是核心业务诉求。

### 做错会踩的坑

- 用了 `priority` 却没设 `prefetch_multiplier=1` → **优先级完全失效且无感知**。
- 只顾 VIP → 普通工单饿死（不在 11 条故障模式内，需监控队列等待时长发现）。
- 拆了队列但漏配路由 → [故障模式 1（静默挂死）](../08-实战经验.md)。
