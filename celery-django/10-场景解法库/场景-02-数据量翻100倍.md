# 场景 2：数据量翻 100 倍，批处理从 1 万到 100 万条（规模压力题）

**场景描述**：每晚对账批处理，原来处理 1 万条跑 3 分钟。业务增长后变成 **100 万条**，同样的代码现在要跑 **5 小时**，而且中途经常 OOM。代码大致是：

```python
@app.task
def reconcile():
    orders = Order.objects.filter(date=today)      # 100 万条
    for order in orders:                            # 全量加载进内存
        process(order)
```

**🔒 先自己想 30 秒**：直接把 5 小时拆成 100 个并行任务？先想清楚：**拆了之后数据库的压力会变成什么样**？

<details><summary>💡 提示（四个方向都要想）</summary>

- **内存**：一次性加载 100 万条到内存——这是 OOM 的直接原因吗？
- **粒度**：一个大任务 vs 1000 个小任务，各自的问题是什么？（小任务总开销 vs 大任务失败成本）
- **数据库**：拆成 1000 个并行任务 = 1000 个并发查询，数据库扛得住吗？
- **失败恢复**：跑 5 小时的任务在第 4 小时崩了，你要从头再跑吗？

关键权衡：**拆得越细，单条失败影响越小、但总开销越大**。

</details>

<details><summary>📖 展开解法</summary>

### 解法一览

| 解法 | 能解决到 | 代价 | 适用边界 |
|------|---------|------|---------|
| **A · 分页流式处理** | 解决 OOM | 只能解决 OOM，不解决耗时 | 必须做，但不够 |
| **B · chunks 拆并行** | 大幅缩短总耗时 | 数据库并发压力上升 | 数据库有余量时 |
| **C · 快慢队列隔离** | 批处理不影响在线任务 | 运维复杂度 | **必做** |
| **D · 分阶段 + 可续跑** | 崩溃后从断点继续 | 要写进度状态 | 任务耗时 > 30 分钟时必做 |
| **E · 换技术栈** | 千万级以上数据量的吞吐 | 引入新组件 | 数据量到了千万级 |

### 各解法详解

#### 解法 A · 流式处理（止血第一步）

**思路**：`.iterator()` 让 Django 分批取，不一次性加载。

```python
# ❌ 错：filter() 返回 QuerySet，for 循环触发一次性求值，100 万条全进内存
for order in Order.objects.filter(date=today):
    process(order)

# ✅ 对：iterator 分批取（服务端游标 / 分块）
for order in Order.objects.filter(date=today).iterator(chunk_size=1000):
    process(order)
```

> ⚠️ **`.iterator()` 的边界**：它解决**内存**，不解决**耗时**——总时间还是 5 小时。
> 另外 `iterator()` 与 `prefetch_related` 不兼容（后者需要一次性拉齐），用了会静默退化成 N+1。

#### 解法 C · 放 slow 队列（隔离）

```python
CELERY_TASK_ROUTES = {
    'reconcile.tasks.reconcile_chunk': {'queue': 'slow'},
}
```
```bash
celery -A proj worker -Q slow -c 2 --prefetch-multiplier=1
```

5 小时的对账任务绝不能和在线任务抢队列。

#### 解法 B · chunks 拆并行（提速，但要控并发）

```python
from celery import chord

# 先捞 id 列表（只捞 id，不捞对象，省内存）
ids = list(Order.objects.filter(date=today).values_list('id', flat=True))

# 每 1000 条一个子任务
job = chord(
    [reconcile_chunk.s(ids[i:i+1000]) for i in range(0, len(ids), 1000)]
)(reconcile_finish.s())
job.apply_async()
```

> ⚠️ **拆之前先确认数据库余量**：1000 个并发查询可能把主库打挂。
> 保守做法：用 `rate_limit` 或分批 `apply_async` 控制同时在跑的子任务数。

#### 解法 D · 幂等 + 可续跑（可靠性必做）

```python
@app.task(bind=True)
def reconcile_chunk(self, chunk_id, id_range):
    # ⭐ 幂等：已处理过就直接跳过，可重复执行
    if Progress.objects.filter(chunk_id=chunk_id, done=True).exists():
        return '已处理，跳过'
    process_range(id_range)
    Progress.objects.update_or_create(chunk_id=chunk_id, defaults={'done': True})
```

跑 5 小时的任务一定要能续跑，否则第 4 小时崩溃 = 全部重来。
【实测】本项目关单任务执行 3 次 → `[1, 0, 0]`，库存只回滚 1 次（CAS 幂等生效）。

### 非本栈替代路线（什么时候别用 Celery）

| 数据量 / 诉求 | Celery 的边界 | 该用什么 |
|--------------|--------------|---------|
| **千万级以上** | Celery 是任务队列，不是计算框架；1000 个子任务的协调开销显著 | **Spark / Flink**，或数据仓库（ClickHouse / Doris）侧直接跑 SQL |
| **本来就是 SQL 能算完的聚合** | 把数据搬到 Python 再算，白白多一次网络往返 | **数据库内聚合 + 物化视图**，Celery 只负责触发 |
| **需要跨表 JOIN 的复杂对账** | Python 里逐条比对，O(N²) 风险 | 交给 **SQL 的 FULL OUTER JOIN**，Celery 只做调度 |
| **频繁的全量重算** | 每次全量 5 小时 | **增量对账**：只算 T-1 到现在的变化部分 |

> 💡 本场景的判断线：**100 万条其实还不到需要 Spark 的量级**。引入新组件的运维成本远高于收益，优先在 SQL 侧优化 + chunks 拆分。

### 推荐路径（递进）

1. **第一步（止血）**：解法 A —— `.iterator(chunk_size=1000)`。改一行，先解决 OOM。
2. **第二步（隔离）**：解法 C —— 放 `slow` 队列。
3. **第三步（提速）**：解法 B —— `chunks` 拆并行。**先确认数据库余量**。
4. **第四步（可靠性）**：解法 D —— 加进度记录，支持续跑。

### 效果对比：怎么验证这一步真的有效

| 维度 | 怎么看 | 期望变化 |
|------|--------|---------|
| **峰值内存** | worker 进程 RSS（`/proc/<pid>/status` 的 `VmHWM`） | 从"几 GB 持续增长"变为"稳定在百 MB 级" |
| **单块耗时** | 每个 chunk 任务的 `date_done - date_start` | 各块耗时**均匀**（不均匀说明有热块，需再拆） |
| **重跑代价** | 中途 kill 掉再重投，看已完成 chunk 数 | 已完成的**直接跳过**，总重跑时间显著小于首次 |

> ⚠️ 第二个维度容易被忽略：如果拆完发现某几个 chunk 耗时是其他的 10 倍，说明**数据分布不均**（比如某个大客户占了 30% 的订单），要按实际量而非固定条数分块。

### 什么情况下此方案不适用

- **解法 B（chunks）**：数据库已是瓶颈时**千万别拆**并行，会让情况更糟。
- **解法 E（换 Spark）**：100 万条不到量级，引入成本远大于收益。
- **大任务本身**：任何跑超过 90 秒的任务都要注意 [故障模式 11（长任务被重投）](../08-实战经验.md)。

### 做错会踩的坑

- 拆并行打挂数据库 → 新故障（连接耗尽 / 主库延迟）。
- 忘了幂等导致崩溃重跑时重复处理 → [故障模式 3（重复执行）](../08-实战经验.md)。
- 用 `.iterator()` 又配 `prefetch_related` → 静默退化成 N+1，比原来更慢。
