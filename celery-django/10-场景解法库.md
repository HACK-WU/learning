## 场景 1 · 流量翻 10 倍（QPS 500 → 5000）

**场景描述**：
你们的订单系统平时峰值 500 QPS，每个订单会触发 3 个异步任务（发券、通知、写流水）。
明天大促，预计峰值 **5000 QPS**，即每秒 **15000 个任务**。
当前配置：2 台机器，各 1 个 worker，`-c 8`，共用一个 `default` 队列，Redis 单实例。
监控显示：平时队列长度稳定在 100 以内，任务 P95 延迟 200ms。

🔒 **先自己想**（想 2 分钟再往下）
第一反应是加机器？加并发？还是别的？—— 先问一句：**瓶颈到底在哪**？
是 worker 算力不够、broker 扛不住、还是数据库先崩？

<details>
<summary>💡 提示（思考方向，不是答案）</summary>

分三层想，别只盯一层：

- **生产端**：Django 每收到一个请求就 `delay()` 三次 —— 这三次网络往返本身是开销吗？
- **Broker 端**：Redis 单实例每秒能扛多少写入？15000/s 是什么量级？
- **消费端**：16 个进程（2 台 × 8）每秒能处理多少任务？如果每个任务 50ms，理论上限是多少？
- **下游**：worker 变快之后，谁会先扛不住？（提示：通常是数据库）

还有一个容易被忽略的：**任务粒度**。3 个任务能不能合成 1 个？
</details>

<details>
<summary>📖 展开解法</summary>

### 解法一览

| 解法 | 做法 | 代价 | 适用边界 |
|------|------|------|---------|
| **A · 加机器/加并发** | 扩到 10 台 × `-c 16` | 线性成本；数据库连接数暴涨 | 任务确实 CPU/IO 密集时 |
| **B · 批量合并任务** | 3 个任务合成 1 个，或用 `chunks` 批处理 | 异步粒度变粗，单个失败影响面变大 | 任务间无依赖、可容忍短延迟 |
| **C · 队列拆分 + 专属 worker** | 快慢分离，避免队头阻塞 | 运维复杂度上升 | **必做**，几乎无副作用 |
| **D · 削峰：任务攒批** | 攒够 N 条或 T 秒再发，用 `chunks` | 增加延迟 | 可容忍秒级延迟的场景 |
| **E · 降级：非核心任务丢弃/延迟** | 大促期间关掉"写流水"这类非核心任务 | 功能降级 | 有明确的非核心任务 |

### 推荐路径（递进，不是一次全上）

**第一步（先做，零风险）**：解法 C —— 拆分队列。
大促时最怕的不是算力不够，是**一个慢任务把 15000 个快任务堵死**。这个改动纯配置，立刻见效。

**第二步（性价比最高）**：解法 E —— 降级。
先把非核心任务关掉，可能直接削掉 1/3 的量（写流水那类），成本为零。

**第三步（真不够再上）**：解法 A —— 加机器。
但**加之前先算下游**：16 个 worker 进程 = 16 个数据库连接，扩到 160 个就是 160 个连接。
很多人加完 worker 发现数据库先崩了。

**第四步（最后考虑）**：解法 B/D —— 改任务粒度。
这是**侵入式改动**，要改代码、要回归测试，非到万不得已不要在大促前一周做。

### 知识点挂钩

| 解法 | 回指课程 |
|------|---------|
| C · 队列拆分 | 课 9《生产部署与并发模型》· 路由与队列隔离；本项目[决策 1](../projects/电商订单履约系统/设计决策.md) |
| B/D · 批处理 | 课 8《canvas 任务编排》· chunks |
| A · 并发模型 | 课 9 · prefork / threads / gevent 选型 |
| E · 降级 | 课 10《监控、排查与上线清单》 |

### 不适用边界

- **解法 A（加机器）**：如果瓶颈在数据库，加 worker 只会**加速数据库崩溃**，必须同时看下游
- **解法 D（攒批）**：订单支付回调这种"用户正在等结果"的场景不能用，延迟不可接受
- **整个场景**：如果任务本身是 CPU 密集（如图片处理），`-c` 超过 CPU 核数反而变慢

> ⚠️ **做错会引发**：只加并发不看下游 → [故障模式 8（队列阻塞）](../08-实战经验.md)；
> 数据库连接打满 → 新的一类故障（连接耗尽），不在本手册 11 条内，要现场排查。
</details>

## 场景 2 · 数据量翻 100 倍（批处理从 1 万到 100 万条）

**场景描述**：
每晚的对账批处理，原来处理 1 万条数据，跑 3 分钟。
业务增长后变成 **100 万条**，同样的代码现在要跑 **5 小时**，而且中途经常 OOM。
代码大致是：
```python
@app.task
def reconcile():
    orders = Order.objects.filter(date=today)      # 100 万条
    for order in orders:                            # 全量加载进内存
        process(order)
```

🔒 **先自己想**
直接把 5 小时拆成 100 个并行任务？先想清楚：**拆了之后数据库的压力会变成什么样**？

<details>
<summary>💡 提示（思考方向，不是答案）</summary>

四个方向都要想：

- **内存**：`Order.objects.filter(...)` 一次性加载 100 万条到内存 —— 这是 OOM 的直接原因吗？
- **粒度**：一个大任务 vs 1000 个小任务，各自的问题是什么？（提示：小任务的总开销 vs 大任务的失败成本）
- **数据库**：拆成 1000 个并行任务 = 1000 个并发查询，数据库扛得住吗？
- **失败恢复**：跑 5 小时的任务在第 4 小时崩了，你要从头再跑吗？

关键权衡：**拆得越细，单条失败影响越小、但总开销越大**。
</details>

<details>
<summary>📖 展开解法</summary>

### 解法一览

| 解法 | 做法 | 代价 | 适用边界 |
|------|------|------|---------|
| **A · 分页流式处理** | `.iterator(chunk_size=1000)` 逐批取，不一次性加载 | 只能解决 OOM，不解决耗时 | 必须做，但不够 |
| **B · chunks 拆并行** | `reconcile.chunks(ids, 1000).apply_async()` | 数据库并发压力上升 | 数据库有余量时 |
| **C · 快慢队列隔离** | 批处理放 `slow` 队列，不影响在线任务 | 运维复杂度 | **必做** |
| **D · 分阶段 + 可续跑** | 记录处理进度，崩了从断点继续 | 要写进度状态 | 任务耗时 > 30 分钟时必做 |
| **E · 换技术栈** | 批处理改用 Spark / 数据仓库 | 引入新组件 | 数据量到了千万级以上 |

### 推荐路径

**第一步（止血）**：解法 A —— `.iterator(chunk_size=1000)`。
先把 OOM 解决掉，这是纯改一行代码的事。

**第二步（隔离）**：解法 C —— 放 `slow` 队列。
5 小时的对账任务绝不能和在线任务抢队列。

**第三步（提速）**：解法 B —— `chunks` 拆并行。
但**拆之前先确认数据库余量**：1000 个并发查询可能把主库打挂。
保守做法：分批提交，控制同时在跑的子任务数（用 `rate_limit` 或分批 `apply_async`）。

**第四步（可靠性）**：解法 D —— 加进度记录。
跑 5 小时的任务一定要能续跑，否则第 4 小时崩溃 = 全部重来。
```python
@app.task(bind=True)
def reconcile_chunk(self, chunk_id, id_range):
    if Progress.objects.filter(chunk_id=chunk_id, done=True).exists():
        return '已处理，跳过'          # ⭐ 幂等，可重复执行
    process_range(id_range)
    Progress.objects.update_or_create(chunk_id=chunk_id, defaults={'done': True})
```

### 知识点挂钩

| 解法 | 回指课程 |
|------|---------|
| A · 流式处理 | 课 6《Django 事务与 ORM 的坑》· worker 里的数据库连接 |
| B · chunks | 课 8《canvas 任务编排》· chunks |
| C · 队列隔离 | 课 9 · 路由与队列隔离 |
| D · 幂等续跑 | 课 5《确认机制与重试策略》· 幂等性设计 |

### 不适用边界

- **解法 B（chunks）**：数据库已经是瓶颈时**千万别拆**并行，会让情况更糟
- **解法 E（换 Spark）**：100 万条其实还不到需要 Spark 的量级，引入新组件的运维成本远高于收益
- **大任务本身**：任何跑超过 90 秒的任务都要注意 [故障模式 11（长任务被重投）](../08-实战经验.md)

> ⚠️ **做错会引发**：拆并行打挂数据库 → 新故障；
> 忘了幂等导致崩溃重跑重复处理 → [故障模式 3（重复执行）](../08-实战经验.md)。
</details>

## 场景 3 · 一个任务要跑 2 小时

**场景描述**：
视频转码任务，单个任务耗时 **30 分钟 ~ 2 小时**（取决于视频大小）。
当前 `visibility_timeout` 是默认 3600 秒（1 小时），Redis broker。
现象：任务经常被**跑两次**，两个 worker 同时转同一个视频。
有人说"把 visibility_timeout 调大到 24 小时就好了"，但你也担心调太大有副作用。

🔒 **先自己想**
调大 visibility_timeout 是不是最优解？如果不调，有没有别的办法让任务不被重投？

<details>
<summary>💡 提示</summary>

先搞清楚"重投"的判定机制：
- 谁决定"这个任务超时了"？（提示：broker，不是 Celery）
- 多久检查一次？（提示：实测约 **88.8 秒** 一次）
- `visibility_timeout` 调大之后，**真正的 worker 崩溃**会怎样？（提示：任务要等多久才重新可见？）

然后想：除了调超时，能不能让任务**根本不需要那么久**，或者**重投也无害**？
</details>

<details>
<summary>📖 展开解法</summary>

### 解法一览

| 解法 | 做法 | 代价 | 适用边界 |
|------|------|------|---------|
| **A · 调大 visibility_timeout** | 设为 2 倍最坏耗时（如 4 小时） | **真崩溃时任务要等 4 小时才重新可见** | 简单，但有权衡 |
| **B · 加幂等，让重投无害** | 用 CAS/锁保证转码只做一次 | 要改代码 | **治本，推荐** |
| **C · 拆成多阶段短任务** | 转码拆成：下载→分片转码→合并，每片 < 5 分钟 | 编排复杂度上升 | 可拆分的长任务 |
| **D · 进度心跳 + 主动续期** | 任务定期上报进度，检测到重复执行则主动退出 | 实现复杂 | 兜底方案 |
| **E · 换 broker** | 用 RabbitMQ（有真正的 ack 机制） | 引入新组件 | 长任务是核心场景时 |

### 推荐路径

**第一步（立刻）**：解法 A —— 先把 `visibility_timeout` 调大到覆盖最坏耗时。
止血优先，这是一行配置。
```python
broker_transport_options = {'visibility_timeout': 14400}        # 4 小时
result_backend_transport_options = {'visibility_timeout': 14400}
```

**第二步（治本）**：解法 B —— 加幂等。
**这是唯一真正可靠的解法**。因为 visibility_timeout 再大，也挡不住 worker 真崩溃后的重投。
```python
@app.task
def transcode(video_id):
    updated = Video.objects.filter(id=video_id, status='PENDING').update(status='RUNNING')
    if updated == 0:
        return '已在转码或已完成，跳过'     # ⭐ 重投直接无害
    ...
```

**第三步（架构优化）**：解法 C —— 拆阶段。
2 小时的任务拆成多个 5 分钟的子任务，每个子任务独立幂等，失败只需重试一小段。

**关于解法 A 的权衡**（这是本场景的核心权衡）：
> `visibility_timeout` 调得越大，**真正的 worker 崩溃**后任务要等越久才重新可见。
> 调到 4 小时意味着：worker 挂了，这个视频要 4 小时后才有人接手。
> **所以 A 只能作为止血，不能作为终态** —— 终态必须靠 B（幂等）。

### 知识点挂钩

| 解法 | 回指课程 |
|------|---------|
| A · visibility_timeout | 课 5《确认机制与重试策略》· ack 时机与可见性超时 |
| B · 幂等 | 课 5 · 幂等性设计；本项目[决策 3](../projects/电商订单履约系统/设计决策.md) |
| C · 拆分编排 | 课 8《canvas 任务编排》· chain / chord |
| E · 换 broker | 课 3《第一个 Celery + Django 项目》· Broker 选型 |

### 不适用边界

- **解法 A 单独用**：不够，只止血不治本
- **解法 E（换 RabbitMQ）**：如果长任务只是边缘场景，不值得为它引入新组件
- **解法 C（拆分）**：转码这种"原子操作"未必能拆，拆了可能引入中间态问题

> ⚠️ **做错会引发**：只调 visibility_timeout 不加幂等 → 崩溃时仍会重复；
> 重投 → [故障模式 11](../08-实战经验.md) 与 [故障模式 3](../08-实战经验.md)。
</details>

## 场景 4 · 必须保证不重复扣款（金融级幂等）

**场景描述**：
支付回调触发扣款任务。要求：**同一笔订单绝对不能扣两次**。
当前已加 `task_acks_late=True`（保证不丢任务），但这也意味着**可能重复投递**。
团队里有人说"用 Redis 加锁"，有人说"用数据库唯一约束"，还有人说"先查再写就行"。

🔒 **先自己想**
"先查再写"（`if not exists: create`）为什么不够？—— 想清楚**并发下的检查-执行窗口**。

<details>
<summary>💡 提示</summary>

三个层次的保证，强度递增：

1. **应用层检查**（先查再写）：两个请求同时查到"不存在"，然后都去写 —— 这就是竞态
2. **Redis 分布式锁**：能挡住，但锁本身有可靠性问题（锁过期了任务还没完？）
3. **数据库约束**（唯一索引 / CAS）：**由数据库保证**，最可靠

还有一个维度：**扣款是调用外部 API**，外部 API 本身可能超时但实际成功了 —— 这怎么防？
</details>

<details>
<summary>📖 展开解法</summary>

### 解法一览

| 解法 | 做法 | 代价 | 适用边界 |
|------|------|------|---------|
| **A · 先查再写** | `if not exists: charge()` | ❌ **有竞态，不可用** | 仅限无并发场景 |
| **B · Redis SET NX 锁** | 抢锁才执行 | 锁需配 `ex`；跨服务好用 | 无 DB 状态字段时 |
| **C · CAS 条件更新** | `filter(status='PENDING').update(status='CHARGED')` 看影响行数 | 需要状态字段 | **首选** |
| **D · 数据库唯一约束** | 给 `(order_id, op_type)` 加 unique，靠 IntegrityError 拦截 | 要加索引 | **最强保证** |
| **E · 外部幂等键** | 调用外部 API 时传幂等键，由对方去重 | 依赖对方支持 | 调第三方支付时必做 |

### 推荐路径

**第一步（基础）**：解法 C —— CAS 状态机。
```python
updated = Order.objects.filter(id=order_id, status='PENDING').update(status='CHARGING')
if updated == 0:
    return '状态已变更，跳过（幂等生效）'
```
【实测】本项目关单任务执行 3 次 → `[1, 0, 0]`，库存只回滚 1 次。

**第二步（加强）**：解法 D —— 唯一约束兜底。
CAS 能挡住并发，但挡不住"同一个订单被不同业务路径处理"。
给扣款流水表加 `unique(order_id, type)`，让数据库做最终裁判：
```python
try:
    Charge.objects.create(order_id=order_id, amount=amount, type='PAY')
except IntegrityError:
    return '已扣过款（唯一约束拦截）'
```

**第三步（外部调用）**：解法 E —— 调第三方支付必须传幂等键。
**这一层最关键**：你的数据库挡不住这种情况 ——
请求发到支付网关、网关扣款成功、但响应超时了，你不知道到底成功没有。
只能用同一个幂等键重试，让网关自己去重。

**关于解法 B（Redis 锁）的定位**：
它适合**跨服务、无共享数据库**的场景。如果已经在一个数据库里，**优先用 D（唯一约束）**，
因为它没有"锁过期"这个额外的失效模式。

### 知识点挂钩

| 解法 | 回指课程 |
|------|---------|
| C · CAS | 课 5《确认机制与重试策略》· 幂等性设计；本项目[决策 3](../projects/电商订单履约系统/设计决策.md) |
| B · Redis 锁 | 课 5 · 幂等；[故障模式 4（锁死锁）](../08-实战经验.md) |
| D · 唯一约束 | 课 6《Django 事务与 ORM 的坑》 |
| E · 外部幂等键 | 课 5 · 重试策略（外部调用） |

### 不适用边界

- **解法 A（先查再写）**：并发场景下**直接不可用**，不要因为"看起来能跑"就上线
- **解法 B（Redis 锁）**：锁的 `ex` 必须大于任务最坏耗时，否则锁过期后第二个请求进来 ——
  而设太长又会让真崩溃的订单长期卡死（[故障模式 4](../08-实战经验.md)）
- **任何解法**：都挡不住"外部 API 扣款成功但响应超时"，必须靠 E

> ⚠️ **做错会引发**：用 A → [故障模式 3（重复执行）](../08-实战经验.md)；
> 用 B 忘设 `ex` → [故障模式 4（死锁）](../08-实战经验.md)。
</details>

## 场景 5 · 部署时不能丢任务（滚动发布）

**场景描述**：
每次发版要重启 worker。当前做法是 `kill -9` 然后拉起。
现象：发版后**总有零星任务丢失**，用户投诉"我提交的单子没处理"。
要求：发版时**一个任务都不丢**，且尽量不影响正在处理的任务。

🔒 **先自己想**
`kill -9` 和 `kill -15`（TERM）在 Celery 里行为差别很大。先想清楚：
**正在执行的任务**和**还在队列里没开始的任务**，分别会怎样？

<details>
<summary>💡 提示</summary>

Celery 的停机有四档语义（课 9 学过）：Warm / Cold / Soft / Hard。

- `TERM` 是哪种？`QUIT` 是哪种？
- "优雅停机"保证的是**正在跑的任务跑完**，还是**队列里的任务不丢**？
- 如果配置了 `task_acks_late=True`，正在跑但没 ack 的任务会怎样？
- ETA/countdown 任务存在哪里？重启会丢吗？
</details>

<details>
<summary>📖 展开解法</summary>

### 解法一览

| 解法 | 做法 | 代价 | 适用边界 |
|------|------|------|---------|
| **A · 用 TERM（warm shutdown）** | `kill -TERM`，等任务跑完再退出 | 停机时间 = 最长任务耗时 | **必做** |
| **B · 配 soft shutdown** | `worker_soft_shutdown_timeout`，限时宽限后转 cold | 要配超时值 | 长任务场景 |
| **C · `task_acks_late=True`** | 任务执行完才 ack，崩溃后重回队列 | 可能重复执行（要幂等） | **必做** |
| **D · 停止消费 → 等空 → 停机** | 先 `cancel_consumer`，等 active 归零再 TERM | 停机流程变长 | 最稳的做法 |
| **E · ETA 任务改持久化** | 延迟任务存数据库 + 轮询 | 要改代码 | 用了 ETA 时必须做 |

### 推荐路径

**第一步（配置层，必做）**：A + C。
```python
task_acks_late = True              # 执行完才 ack，崩溃可重投
task_reject_on_worker_lost = True  # worker 被强杀时任务重回队列
```
停机一律用 `TERM`，**禁止 `kill -9`**。

**第二步（流程层）**：D —— 三步停机法。
```bash
# ① 停止消费新任务（队列里的会安全留在 broker）
celery -A proj control cancel_consumer <queue>
# ② 等正在跑的任务结束
while [ "$(celery -A proj inspect active | grep -c task_name)" -gt 0 ]; do sleep 2; done
# ③ 优雅退出
kill -TERM <worker_pid>
```

**第三步（长任务场景）**：B —— 配 soft shutdown。
如果任务可能跑很久，warm shutdown 会一直等，需要限时：
```python
worker_soft_shutdown_timeout = 300   # 宽限 300 秒后转 cold
```

**关于 ETA 任务（最容易漏的一点）**：
【官方】ETA/countdown 任务存在 **worker 内存**里，**重启即丢**。
如果你用 `countdown` 做延迟关单，每次发版都会丢一批 —— 这与停机姿势无关。
解法：重要延迟任务改数据库持久化 + 轮询（本项目决策 2 正是这么选的）。

### 知识点挂钩

| 解法 | 回指课程 |
|------|---------|
| A/B · 停机语义 | 课 9《生产部署与并发模型》· 进程管理与优雅停机 |
| C · acks_late | 课 5《确认机制与重试策略》· ack 时机 |
| E · ETA 持久化 | 课 4《调用任务与取回结果》· countdown/eta；本项目[决策 2](../projects/电商订单履约系统/设计决策.md) |

### 不适用边界

- **解法 A**：任务跑几小时时，TERM 会卡很久 —— 此时要用 B（soft shutdown 限时）
- **`task_acks_late=True`**：必须**同时**有幂等，否则崩溃重投会造成重复扣款（回到场景 4）
- **解法 D**：等待 active 归零的循环要有超时，否则任务卡死会导致发布流程永远挂住

> ⚠️ **做错会引发**：`kill -9` → 正在跑的任务丢失；
> 配了 `acks_late` 但没幂等 → [故障模式 3（重复执行）](../08-实战经验.md)。
</details>

## 场景 6 · 定时任务必须不重不漏（对账/结算）

**场景描述**：
每天凌晨 2 点跑全量对账，要求：**必须跑，且只能跑一次**。
当前现象：
- 有时跑到一半机器重启了，第二天才发现**对账没跑**（漏了）
- 有时**跑了两遍**，数据翻倍

🔒 **先自己想**
"不重"和"不漏"是两个**相反方向**的需求：
- 防漏 → 失败了要重试 → 但重试可能导致"重"
- 防重 → 加锁 → 但锁住了崩溃的那个，就"漏"了

先想清楚：**你怎么知道一个周期任务是"成功了"还是"根本没跑"？**

<details>
<summary>💡 提示</summary>

核心矛盾在于**缺少执行记录**。破解方法是引入第三方状态：

- 谁来判断"今天跑过了没"？（提示：不能依赖 beat 的内存状态，它重启就没了）
- 如果任务跑了一半崩溃，状态该是什么？（提示：需要"进行中"这个中间态）
- 崩溃后重启，看到"进行中"该怎么处理？（提示：是接着跑，还是判定失败重跑？）

另外：beat 自己挂了是**静默**的 —— 没人会告诉你"今天没调度"。
</details>

<details>
<summary>📖 展开解法</summary>

### 解法一览

| 解法 | 做法 | 代价 | 适用边界 |
|------|------|------|---------|
| **A · 执行记录表（状态机）** | 建 `JobExecution(date, status)`，PENDING/RUNNING/SUCCESS | 要建表 | **必做，治本** |
| **B · 分布式锁防重** | Redis SET NX，抢到才跑 | 锁过期判定复杂 | 配合 A 使用 |
| **C · beat 存活监控** | 监控 beat 进程 + 最后调度时间 | 要配监控 | **必做**（防静默失效） |
| **D · 幂等 + 可重跑** | 对账逻辑本身幂等，跑两次结果一样 | 要改业务逻辑 | 最省心的兜底 |
| **E · 外部调度器** | 用 K8s CronJob / Airflow 替代 beat | 引入新组件 | 有基建时 |

### 推荐路径

**第一步（防漏的基础）**：C —— beat 存活监控。
beat 挂了是**静默**的，没有告警你根本不知道今天没跑。
至少监控两件事：beat 进程在不在、最后成功调度时间距今多久。

**第二步（治本）**：A —— 执行记录表。
```python
@app.task
def daily_reconcile(date):
    rec, created = JobExecution.objects.get_or_create(
        date=date, job='reconcile',
        defaults={'status': 'RUNNING'},
    )
    if not created:
        if rec.status == 'SUCCESS':
            return '今天已成功，跳过'          # 防重
        if rec.status == 'RUNNING':
            # 进行中：判断是不是崩溃残留（如 updated_at 超过 2 小时）
            if rec.updated_at < now() - timedelta(hours=2):
                rec.status = 'RUNNING'        # 判定为崩溃，接管重跑
                rec.save()
            else:
                return '上一轮还在跑，跳过'    # 防重
    try:
        do_reconcile(date)
        rec.status = 'SUCCESS'
        rec.save()
    except Exception:
        rec.status = 'FAILED'
        rec.save()
        raise                                  # 让告警能触发
```
这张表同时解决了"不重"（状态为 SUCCESS 就跳过）和"不漏"（能看到 FAILED/PENDING）。

**第三步（兜底）**：D —— 让对账本身幂等。
即使真的跑了两次，结果也是对的。这是最后一道防线。

**关于 B（分布式锁）的定位**：
锁能防重，但**锁无法告诉你"今天根本没跑"**。所以 B 不能替代 A，只能作为 A 的补充
（防止状态机判断之前的极短窗口内并发）。

### 知识点挂钩

| 解法 | 回指课程 |
|------|---------|
| A · 状态机 | 课 5《确认机制与重试策略》· 幂等；本项目[决策 2/3](../projects/电商订单履约系统/设计决策.md) |
| B · 分布式锁 | 课 5 · 幂等；[故障模式 7（定时器重叠）](../08-实战经验.md) |
| C · beat 监控 | 课 7《beat 与周期性任务》· 定时任务的可靠性 |
| E · 外部调度 | 课 7 · beat 单点问题 |

### 不适用边界

- **只靠 B（锁）**：防得住重，防不住漏 —— 崩溃后锁释放了，但没人再调度，今天就漏了
- **解法 A 的"接管重跑"超时值**：设太短会在任务正常运行时误判崩溃，设太长会延迟恢复；
  要基于任务的历史耗时分布来定
- **解法 E**：小团队没有 K8s/Airflow 时，引入成本远大于收益

> ⚠️ **做错会引发**：只加锁不记状态 → 漏跑且无感知；
> 重叠执行 → [故障模式 7](../08-实战经验.md)。
</details>

## 场景 7 · VIP 用户要插队（任务优先级）

**场景描述**：
客服工单系统，普通用户提交工单后进入处理队列，平均等待 10 分钟。
现在要求：**VIP 用户的工单必须优先处理，且 VIP 内部还要分等级**（钻石 > 黄金 > 白银）。
当前：单队列，`-c 8`，Redis broker。

🔒 **先自己想**
Redis broker 上"优先级"是怎么实现的？它和 RabbitMQ 的原生优先级是一回事吗？
想清楚这一点，才知道该不该用 `priority` 参数。

<details>
<summary>💡 提示</summary>

关键事实：**Redis 没有原生优先级**，Celery 是**模拟**出来的（拆多个子队列）。
这意味着什么？

- 模拟的优先级在什么时候会失效？（提示：worker 已经预取了一批任务时）
- `prefetch_multiplier` 大的时候，优先级还有效吗？
- 除了 `priority` 参数，还有没有别的做法？（提示：想想第 8 章的队列隔离）

还有一个业务问题：**VIP 插队会不会导致普通工单饿死**？
</details>

<details>
<summary>📖 展开解法</summary>

### 解法一览

| 解法 | 做法 | 代价 | 适用边界 |
|------|------|------|---------|
| **A · `priority` 参数** | `apply_async(priority=9)` | Redis 上是**模拟**的，不可靠 | 软性优先，RabbitMQ 上才可靠 |
| **B · 多队列 + 加权 worker** | VIP 队列配更多并发 / 专属 worker | 运维复杂度 | **推荐**，语义明确 |
| **C · 多队列 + 优先级消费** | `-Q vip,normal` 让 worker 先消费 vip | 可能饿死低优先级 | 简单有效 |
| **D · 队列内排序** | 自己维护有序集合，按优先级取 | 实现复杂 | 极致要求时 |
| **E · 换 RabbitMQ** | 用原生 `x-max-priority` | 引入新组件 | 优先级是核心需求时 |

### 推荐路径

**第一步（先看清限制）**：
【公认】Redis 上 Celery 的优先级是**模拟实现**（拆成多个子队列按序消费），
官方文档直接说：**推荐用 routing 而不是 priority 来保证服务质量**。
而且模拟优先级在 `prefetch_multiplier` 大时会明显失效 —— worker 已经预取了一堆低优先级任务。

**第二步（推荐做法）**：C —— 多队列 + 顺序消费。
```python
CELERY_TASK_ROUTES = {
    'tickets.tasks.process_vip':    {'queue': 'vip'},
    'tickets.tasks.process_normal': {'queue': 'normal'},
}
```
```bash
# worker 同时消费两个队列，vip 写在前面会优先被轮询到
celery -A proj worker -Q vip,normal -c 8 --prefetch-multiplier=1
```
`prefetch_multiplier=1` 是**关键** —— 不设的话，worker 会一次抓一批，
优先级就形同虚设。

**第三步（VIP 内部分级）**：B —— 拆三个队列，配不同并发。
```bash
celery -A proj worker -Q vip_diamond -c 4 ...
celery -A proj worker -Q vip_gold,vip_silver -c 3 ...
celery -A proj worker -Q normal -c 1 ...     # 保证普通工单不会被完全饿死
```

**关于"饿死"问题**（这是本场景的隐藏陷阱）：
如果 VIP 流量持续很大，普通队列可能**永远排不上**。
必须给低优先级队列保留最小并发（如上例中 normal 留 1 个），
或者监控队列等待时长，超过阈值就临时扩容。

### 知识点挂钩

| 解法 | 回指课程 |
|------|---------|
| A · priority 与 Redis 模拟 | 课 9《生产部署与并发模型》· 路由与队列隔离 |
| B/C · 多队列 | 课 9 · 路由与队列隔离；本项目[决策 1](../projects/电商订单履约系统/设计决策.md) |
| prefetch 影响 | 课 2《Celery 架构全景》；课 9 · 并发模型 |

### 不适用边界

- **解法 A 单独用**：Redis 上不可靠，尤其在 `prefetch_multiplier > 1` 时基本失效
- **解法 C 的 `-Q` 顺序**：这不是严格的优先级保证，只是轮询偏好，高负载下会稀释
- **解法 E（换 RabbitMQ）**：只为优先级换 broker 通常不划算，除非优先级是核心业务诉求

> ⚠️ **做错会引发**：用了 `priority` 却没设 `prefetch_multiplier=1` → 优先级完全失效且无感知；
> 只顾 VIP → 普通工单饿死（不在本手册故障模式内，需监控队列等待时长发现）。
</details>

## 场景 8 · 第三方 API 限流（每秒最多 10 次）

**场景描述**：
要调用第三方短信/物流 API，对方限制 **每秒最多 10 次**，超了返回 429 并且可能封 IP。
当前有 5 万个待发任务，worker 有 20 个并发。
现象：大量任务收到 429，重试后又 429，形成**重试风暴**。

🔒 **先自己想**
第一反应可能是"加 `rate_limit='10/s'`"。先想清楚：
**这个 rate limit 是全局的，还是每个 worker 进程各自算的？**
（提示：这决定了 20 个并发下实际 QPS 是多少）

<details>
<summary>💡 提示</summary>

Celery 的 `rate_limit` 是**每个 worker 实例**维度的，不是全局的。
20 个并发 = 实际 QPS 可能是 200，而不是你设的 10。

那怎么做到全局限流？几个方向：
- 让并发数本身就等于限流值？（简单粗暴但有效）
- 用外部令牌桶？（Redis 实现）
- 用队列串行化？

还有：**收到 429 之后该怎么重试**？立即重试会让情况更糟。
</details>

<details>
<summary>📖 展开解法</summary>

### 解法一览

| 解法 | 做法 | 代价 | 适用边界 |
|------|------|------|---------|
| **A · `rate_limit='10/s'`** | 任务装饰器和参数 | ⚠️ **per-worker 生效**，多 worker 会翻倍 | 单 worker 场景 |
| **B · 控制并发数 = 限流值** | 专属队列 + `-c 10` + 任务足够快 | 吞吐受限 | **简单可靠** |
| **C · Redis 令牌桶** | 任务里抢令牌，抢不到就 `retry(countdown=...)` | 要写代码 | **推荐**，真正的全局限流 |
| **D · 指数退避 + jitter** | `retry_backoff=True` + `retry_jitter=True` | 拉长总耗时 | **必做**（防重试风暴） |
| **E · 批量接口** | 改调批量 API，一次发 100 条 | 依赖对方支持 | 首选（如果对方有） |

### 推荐路径

**第一步（先看有没有批量接口）**：E。
如果第三方提供批量 API，一次发 100 条，5 万条只需 **500 次**调用 ——
限流问题直接消失。这是最优解，但取决于对方。

**第二步（并发控制）**：B —— 专属队列 + 精确并发。
```bash
# 给限流任务单独一个队列，并发严格等于限流值
celery -A proj worker -Q sms -c 10 --prefetch-multiplier=1
```
注意 `-c 10` 不等于 10 QPS，还要看单次任务耗时。
若单次耗时 100ms，10 并发 = 100 QPS（超限）；若单次耗时 1.5s，10 并发 ≈ 6.7 QPS（安全）。
**所以 B 只对"任务耗时稳定"的场景可靠。**

**第三步（真正的全局限流）**：C —— Redis 令牌桶。
```python
import time, redis
r = redis.Redis()

def acquire_token(key, rate=10, burst=10):
    """令牌桶：返回 True 表示拿到令牌"""
    now = time.time()
    pipe = r.pipeline()
    pipe.hset(key, mapping={'rate': rate, 'burst': burst, 'last': now})
    # 简化实现：用 INCR + EXPIRE 做每秒计数
    cnt = r.incr(f'{key}:{int(now)}')
    r.expire(f'{key}:{int(now)}', 2)
    return cnt <= rate

@app.task(bind=True, autoretry_for=(RateLimitError,), retry_backoff=True,
          retry_jitter=True, max_retries=10)
def send_sms(self, phone, content):
    if not acquire_token('sms_api', rate=10):
        raise RateLimitError('达到限流，稍后重试')   # 触发带退避的重试
    call_sms_api(phone, content)
```

**第四步（必做）**：D —— 指数退避 + jitter。
【公认】429 的正确处理是**退避重试**，立即重试只会让情况恶化。
`retry_jitter=True` 是关键 —— 没有 jitter，所有被限流的任务会在同一时刻重试，形成新的尖峰。

### 知识点挂钩

| 解法 | 回指课程 |
|------|---------|
| A · rate_limit | 课 9《生产部署与并发模型》· 并发模型 |
| C · 令牌桶 | 课 5《确认机制与重试策略》· 重试策略（429 属可重试异常） |
| D · 退避 + jitter | 课 5 · backoff / jitter |
| B · 队列隔离 | 课 9 · 路由与队列隔离；本项目[决策 1](../projects/电商订单履约系统/设计决策.md) |

### 不适用边界

- **解法 A 单独用**：多 worker 下限流值会按 worker 数翻倍，形同虚设
- **解法 B**：任务耗时波动大时不可靠（耗时变短 → QPS 飙升）
- **解法 D（退避）**：只是让重试"温和"，不解决限流本身，必须配合 B 或 C
- **任何解法**：如果对方 429 后就封 IP，单纯退避可能不够，要先降并发

> ⚠️ **做错会引发**：只加 `rate_limit` 不控 worker 数 → 限流失效 → 429 风暴；
> 重试无 jitter → 尖峰叠加 → [故障模式 3 的 cousin（重试风暴）](../08-实战经验.md)。
</details>

## 收尾 · 八个场景的共同规律

回头看这 8 个场景，有一半的推荐路径里都出现了同一件事：

| 出现在这几个场景 | 共同的解法 |
|-----------------|-----------|
| 1、2、7、8 | **队列拆分/隔离** |
| 2、3、4、6 | **幂等** |
| 3、5 | **ack 与停机语义** |
| 4、5、6 | **状态机/执行记录** |

**这两件事（队列隔离 + 幂等）是 Celery 生产落地的地基。**
它们不性感，但 80% 的生产问题都能追溯到"这两件事没做或做错了"。
