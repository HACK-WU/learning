### 本机实测数据（课 9，2026-08-31）

> 环境：WSL2 Ubuntu / Python 3.12.3 / **Celery 5.6.3** / kombu 5.6.2 / **Redis 7.0.15**（端口 6380，与既有 6379 实例隔离）/ nproc=20

| 实验 | 结果 | 脚本 |
|------|------|------|
| CPU 密集（8 任务，-c 8） | prefork **0.56s** vs threads **2.46s**（threads 慢 4.4×） | `playground/l9-bench-cpu.sh` |
| IO 密集（200 任务，同为 -c 8） | prefork 12.62s / gevent 12.89s / threads **19.69s**（最慢） | `playground/l9-bench-io-fair.sh` |
| IO 密集（200 任务，-c 200） | gevent **0.91s** / threads **0.92s** | `playground/l9-bench-io-fair.sh` |
| 队头阻塞 | 默认队列 **10.03s** → 队列隔离 **0.51s**（快 20×） | `playground/l9-bench-headblock.sh` |
| Warm（TERM） | 12s 任务跑完 **12/12**，worker 12s 后退出 | `playground/l9-bench-shutdown.sh` |
| Cold（QUIT） | 任务停在第 **3/12** 秒，worker 1s 内退出 | `playground/l9-bench-shutdown.sh` |
| Soft（15s 宽限） | 日志 `Initiating Soft Shutdown, terminating in 15.0 seconds` → 16s 退出 → `Restoring 1 unacknowledged message(s)`，队列残留 1（未丢失） | `playground/l9-bench-soft2.sh` |
| `--max-tasks-per-child=2` | 子进程 PID 每 2 个任务换一批（对照组 PID 恒定） | `playground/l9-bench-maxchild2.sh` |
| 配置注入可靠性 | `CELERY_WORKER_SOFT_SHUTDOWN_TIMEOUT` 环境变量**未被 worker 读取**（仍为 `0.0`，静默失效）；改 `app.conf` / `--include` 注入后生效 | `playground/l9-diag-soft2.sh` |

### 本机实测数据（Phase 5 实战经验与排障手册，2026-08-31）

> 环境同 Phase 3：WSL2 Ubuntu / Python 3.12.3 / **Celery 5.6.3** / kombu 5.6.2 / **Django 6.1** / Redis 7.0.15
> 产物：`08-实战经验.md` / `09-排障速查手册.md` / `10-场景解法库.md`

| 实验 | 结果 | 脚本 |
|------|------|------|
| **长任务 vs visibility_timeout（4 组对照）** | vt=5 秒，任务 30s→**1 次**；70s→**1 次**；**110s→2 次（间隔 88.8s）**；**150s→2 次（间隔 88.8s）**。临界点在 **70~110 秒之间** | `playground/l11-measure-interval.sh` |
| 上述现象的源码根因 | kombu 5.6.2 `transport/redis.py`：**第 1382 行** `loop.call_repeatedly(10, cycle.maybe_restore_messages)` 每 10 秒调用一次；**第 410 行** `restore_visible(interval=10)` 内部 `if (self._vrestore_count - 1) % interval: return` 前 9 次直接返回。**实际检查周期 = 10s × 10 ≈ 100 秒**（实测 88.8s） | `playground/l11-inspect-kombu.sh`、`l11-inspect-ack.sh` |
| beat 定时任务重叠 | schedule=3 秒、任务耗时 8 秒，26 秒窗口内 **START=8 / END=6** → 明确重叠，调度器到点就发不管上次跑没跑完 | `playground/l11-verify-beat.sh` |
| chord 挂死根因（**纠错**） | 解出 `default` 队列积压消息，**task = `orders.tasks.fulfill_order`**（编排入口自己），**不是** `chord_unlock`。补上路由后 worker **不带 default** 也跑通，日志中 `chord_unlock` 出现 **0 次** | `playground/l11-diag-queue.sh`、`l11-verify-hypothesis.sh` |

> 🔴 **重要纠错（Phase 3 结论被推翻）**：
> Phase 3 曾记录"chord 的解锁任务会走 default 队列，worker 必须消费 default"——**这是错的**。
> Celery 的 **Redis backend 有原生 chord 协调**（`apply_chord` 用 `ZADD` 登记成员、`ZCOUNT` 计数，
> 达标时直接 `callback.apply_async()`），**不产生任何中间任务**；`celery.chord_unlock` 轮询任务
> **只在 backend 无原生协调时**作兜底。真正的根因是**编排入口 `fulfill_order` 漏配了路由**。
>
> **更值得记的教训**："让 worker 消费 default"这个修复**确实有效**，但它会**永久掩盖漏配路由的真因**。
> 已改回补路由方案，并把整个纠错过程写进
> [设计决策 · 决策 4（已修正）](projects/电商订单履约系统/设计决策.md)。

> 🔬 **方法论沉淀**：
> ① "实测没复现" ≠ "机制不存在" —— 长任务重投我前两次用 20 秒任务都没复现，
>    是**读源码发现 `interval=10`** 才设计出跨过阈值的正确实验；
> ② 一个修复方案有效 ≠ 对根因的判断正确，尤其"扩大范围兜底"型修复
>    （多消费队列 / 加大超时 / 吞异常）会**同时消灭症状和证据**；
> ③ 遇到"队列积压没人消费"，**别猜积压的是什么**，直接解出消息看任务名：
>    `json.loads(redis.lindex('default',0))['properties']['task']`
