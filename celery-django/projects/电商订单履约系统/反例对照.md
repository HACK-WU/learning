# 反例对照 · 电商订单履约系统

> 不是"错误示例"，而是**看起来能跑、实际很糟**的版本——只有这样才能教会"为什么最佳实践是最佳实践"。
> 下面这个反例**功能完全正常**，在本机跑得通，甚至代码量比正确版本少一半。

---

## ❌ 反例：一个"能跑通"的关单 + 履约实现

```python
# orders/views.py（反例版本）
from django.http import JsonResponse
from django.db import transaction
from .models import Order, Stock
from .tasks import close_order, send_notification, write_reconciliation

@transaction.atomic
def create_order(request):
    """创建订单：扣库存 + 发关单任务"""
    sku = request.POST['sku']
    stock = Stock.objects.get(sku=sku)
    stock.quantity -= 1
    stock.save()

    order = Order.objects.create(
        sku=sku, user_id=request.user.id, status='PENDING'
    )

    # ❌ 反例 1：事务还没提交就发任务
    close_order.apply_async(args=[order.id], countdown=900)

    return JsonResponse({'order_id': order.id})


def pay_order(request, order_id):
    """支付成功：改状态 + 取消关单任务 + 发履约任务"""
    order = Order.objects.get(id=order_id)
    order.status = 'PAID'
    order.save()

    # ❌ 反例 2：以为 revoke 就万事大吉
    from celery import current_app
    current_app.control.revoke(order.close_task_id)

    # ❌ 反例 3：直接串行调用三个任务
    send_notification.delay(order.id)
    write_reconciliation.delay(order.id)

    return JsonResponse({'ok': True})
```

```python
# orders/tasks.py（反例版本）
from celery import shared_task
from .models import Order, Stock

@shared_task
def close_order(order_id):
    """❌ 反例 4：没有任何幂等检查"""
    order = Order.objects.get(id=order_id)
    order.status = 'CLOSED'
    order.save()

    stock = Stock.objects.get(sku=order.sku)
    stock.quantity += 1          # ❌ 重复执行就会重复回滚
    stock.save()
    return 'closed'

@shared_task
def send_notification(order_id):
    """❌ 反例 5：外部调用不重试、不超时"""
    import requests
    order = Order.objects.get(id=order_id)   # ❌ 反例 6：传 id 查对象是对的，但下面会踩别的坑
    requests.post('https://sms-api.example.com/send',
                  json={'phone': order.user.phone})   # 没有 timeout，没有重试
    return 'sent'

@shared_task
def write_reconciliation(order_id):
    """对账任务，每件 2 秒"""
    import time
    time.sleep(2)
    return 'done'
```

```python
# settings.py（反例版本）
CELERY_BROKER_URL = 'redis://localhost:6379/0'
# ❌ 反例 7：只配了 broker，其他全是默认值
```

> 它**能跑通**：下单 → 扣库存 → 15 分钟后关单 → 支付后发通知。功能测试全绿，代码量还比正确版少一半。

## 🔍 逐条对比

| # | 维度 | ❌ 反例 | ✅ 正确做法 | 为什么糟 |
|---|------|---------|------------|----------|
| 1 | **事务边界** | 事务内直接 `apply_async` | `transaction.on_commit(lambda: ...)` | 事务一旦回滚（库存不足、并发冲突），**任务已经发出去了**。worker 拿着一个不存在的 `order_id` 去查库 → `DoesNotExist` 报错；更糟的是若 id 被复用，会**关掉别人的订单**（课 6） |
| 2 | **撤销竞态** | 支付后 `revoke(task_id)` 就不管了 | 改用轮询方案，或在关单任务里做 CAS 校验 | ⭐ **实测**：`revoke(terminate=False)` **拦不住已开跑的任务**（DONE 次数 = 1）。用户第 14:59 支付、任务同时开跑 → **已支付的订单被关掉**，资损 |
| 3 | **幂等** | 直接 `status=CLOSED` + `stock+=1` | `UPDATE ... WHERE status='PENDING'` 判影响行数 | ⭐ **实测**：重复执行 3 次 → 库存 **10→13**（多回滚 2 次，超卖）。而实测证明 worker 被 SIGKILL 后任务**确实会重投执行**（START=2），这不是理论风险 |
| 4 | **错误处理** | `requests.post(...)` 无 timeout 无重试 | `autoretry_for` + 指数退避 + 超时 | 短信服务抖动 → 任务永久失败，用户永远收不到通知；**没有 timeout 的话，一个卡住的 HTTP 调用会永久占用 worker 槽位**（僵尸任务，课 10 实测：2 个卡死任务就能让快任务 6 秒排不上） |
| 5 | **队列隔离** | 通知和对账混在一个队列 | `task_routes` 拆 `fast` / `slow` + 专属 worker | 课 9 实测：20 个慢任务会把快任务从 0.51s 拖到 **10.03s**（20 倍）。零点对账批量涌入时，用户支付成功的通知会延迟十几秒 |
| 6 | **序列化安全** | 全用默认值 | `accept_content = ['json']` | 默认值下 worker **仍可能接受 pickle 消息** → 反序列化即执行代码 = **RCE**。能访问 broker 的攻击者可以拿下整台 worker 机器（课 10） |
| 7 | **超时保护** | 没配 `time_limit` | 所有任务配 `soft_time_limit` / `time_limit` | 一个卡死的任务**永久占用槽位**，且**没有任何报错**（课 10 实测：快任务 6 秒拿不到结果）。不配超时 = 埋地雷 |
| 8 | **可观测性** | 日志里只有任务名 | 信号钩子打 `task_id` | 用户投诉"我的订单没关"时，你无法把**这条投诉**和**那次任务执行**关联起来，只能在几千行日志里大海捞针（课 10） |

---

## 💡 一句话教训

> **能跑通 ≠ 能扛住；差别在于失败时怎么表现。**

功能测试全绿的代码，在**宕机、重试、并发、攻击**这四种场景下会暴露完全不同的问题。反例版本的所有问题，在 happy path 下都看不出来。

## 🧪 反例的实测佐证

> 本文所有"实测"均在本机 Celery 5.6.3 + Redis 7.0.15 环境验证（2026-08）。

### 佐证 1：无幂等 → 超卖（`playground/l10-test-idempotent.sh`）

```
方式 ① 无幂等（反例）：
  执行 3 次后 → 库存 = 13（初始 10，多回滚了 2 次！）

方式 ② CAS（正确）：
  执行 3 次 → 返回值 [1, 0, 0]（1=真关了，0=被拦截）
             库存 = 11（只回滚 1 次 ✅）
```

### 佐证 2：revoke 拦不住已开跑的任务（`playground/l10-test-cancel.sh`）

```
步骤 1：发 countdown=25 的关单任务
步骤 2：5 秒后 revoke
步骤 3：等 30 秒
  → 执行记录：(无)  执行次数 = 0  ✅ 未开跑的任务能撤销

步骤 4（对照）：发一个执行 20 秒的任务，等它开跑后 revoke
  → 15:28:14 START running_task
  → 15:28:14 DONE  running_task
  → DONE 次数 = 1  ❌ 已开跑的任务拦不住
```

**这正是反例第 2 条（撤销竞态）的可怕之处**：撤销在"任务还没开始"时有效，但**你无法保证用户支付时任务还没开始**。

### 佐证 3：worker 崩溃 → 任务重投（`playground/l10-test-kill.sh`）

```
发送执行 30 秒的任务 → 8 秒后 SIGKILL 整个 worker（模拟宕机/OOM）
  → 重启 worker
  → 15:26:07 START kill_mid   ← 第一次
  → 15:26:20 START kill_mid   ← 第二次（重投！）
  → START 次数 = 2
```

**这证明反例第 3 条不是理论风险**：`acks_late` 保住了"不丢"，但代价是"可能重复"—— 所以幂等是**必选项**不是可选项。

### 佐证 4：僵尸任务占满槽位（`playground/l10-bench-hang.sh`）

```
worker -c 2，投 2 个死循环任务占满槽位，再投 1 个快任务：
  → 6秒内没拿到结果（槽位被卡死任务占满）: TimeoutError
  → inspect active 显示 acknowledged: True 且 time_start 停滞
```

**反例第 4、7 条的合力效果**：没有 timeout + 没有重试上限 = 一个卡住的外部调用就能拖垮整个 worker。
