# 设计决策 · 电商订单履约系统

> 每个决策点都**真有争议**——换个人来可能选另一个方案，且也有道理。唯一正确答案不算决策点。
> 本文所有"实测"数据均来自本机 Celery **5.6.3** + kombu **5.6.2** + Redis **7.0.15** 环境（2026-08）。

## 决策 1：快慢任务要不要拆队列？

**背景**：履约链路里，发通知（~50ms）和写对账（每件 2s）混在一个队列。零点大促时，对账任务会把通知任务全堵在后面。

**候选方案**：

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| A · **不拆，统一队列** | 所有任务进 `celery` 队列，用一个 `-c 16` 的 worker 消费 | 部署最简单，一个 worker 搞定；无路由配置 | 慢任务堵死快任务（队头阻塞）；无法针对快慢分别调优并发模型 |
| B · **拆分队列 + 专属 worker** | `fast` 队列用 gevent `-c 200`，`slow` 队列用 prefork `-c 8`，各自独立 worker | 快慢互不干扰；可分别选并发模型；可独立扩缩容 | 多一套路由配置和运维复杂度；worker 总数变多，内存占用上升 |
| C · **拆分队列，但共用 worker** | 一个 worker `-Q fast,slow`，靠 prefetch 缓解 | 部署比 B 简单 | ⚠️ **无效**：单 worker 内部 `-Q` 多队列是**轮流取**（round-robin），不是优先级，慢任务照样占槽位（课 9 实测） |

**最终选择**：**B（拆分队列 + 专属 worker）**

**选择理由**：
1. **课 9 已有实测数据支撑**：同样是 20 个慢任务 + 5 个快任务，不隔离时快任务**等 10.03s**，隔离后**等 0.51s**（相差 20 倍）。
2. **本项目有明确的快慢差异**：通知 50ms vs 对账 2s，相差 40 倍，且零点时对账任务会批量涌入 —— 这正是队头阻塞最容易发作的场景。
3. **C 方案是伪优化**：实测证明单 worker 多队列是 round-robin，起不到隔离效果，必须用独立 worker。

**为此付出的代价**：
- 运维复杂度上升：要起 2 类 worker（fast / slow），发版时要分别重启
- 内存占用上升：prefork 每子进程 100~200MB（课 9 实测），多起 worker 就多占内存
- 需要额外维护 `task_routes` 路由表，新增任务时要想清楚"这个该进哪个队列"，**路由写错等于没拆**

**什么时候该改选另一个**：
- 若你的任务**耗时都在同一量级**（比如全是 100ms 级），拆队列就是纯粹的过度设计 → 选 A
- 若任务量很小（每天几百个），队头阻塞根本不会发作 → 选 A，省下运维成本
- 若你只有**一台小内存机器**（如 2GB），多起 worker 会 OOM → 选 A，或只拆队列不拆 worker（接受 C 的局限）

## 决策 2：15 分钟超时关单，用 ETA 还是 beat 轮询？

**背景**：用户下单后 15 分钟未支付要自动关单。经典方案有两个：下单时发一个 `countdown=900` 的延迟任务（ETA），或用 beat 每 30 秒扫一次超时未支付的订单。

**候选方案**：

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| A · **ETA 延迟任务** | 下单时 `close_order.apply_async(countdown=900)` | 精准（误差 < 1s）；无空转扫描，省资源；订单量小的时候几乎零成本 | ⚠️ **撤销有竞态**：用户支付后要 `revoke`，但**已开跑的任务拦不住**（实测）；任务量大时 broker 积压大量延迟消息（Redis 的 ETA 消息在主队列里，会拖慢消费）；worker 重启后延迟任务依赖 broker 持久化 |
| B · **beat 周期轮询** | 每 30 秒扫 `status=PENDING AND created_at < now-15min` | 实现简单直观；天然幂等（靠 SQL 条件过滤）；**撤销是免费的**——订单一支付就不再满足扫描条件；不依赖 broker 持久化延迟消息 | 有时间误差（最长 30 秒）；订单量巨大时扫描有 DB 压力（需加索引）；beat 挂了是**静默**的（课 7） |
| C · **两者结合** | ETA 做精准触发，beat 做兜底扫描（扫漏掉的） | 既精准又可靠 | 复杂度最高，两套逻辑都要维护 |

**最终选择**：**B（beat 轮询）为主**

**选择理由**：

1. **⭐ 实测发现 ETA 方案有个致命的竞态**：
   ```
   实测（l10-test-cancel.sh）：
   ① 发 countdown=25 的关单任务 → 用户 5 秒后支付 → revoke
      → 结果：执行 0 次 ✅ 撤销成功
   ② 发一个执行 20 秒的任务 → 任务开跑后 revoke(terminate=False)
      → 结果：DONE 次数 = 1 ❌ 拦不住！
   ```
   **含义**：撤销请求和任务执行之间存在竞态。如果用户恰好在第 14 分 59 秒支付，而 ETA 任务同时开始执行，**`revoke` 拦不住已经开跑的任务** —— 这个订单会在"已支付"的状态下被关单。
   用 `terminate=True` 能强杀，但**强杀会让任务死在任何一行代码上**，关单逻辑可能只做了一半（库存回滚了但订单状态没改），反而更糟。

2. **轮询方案的"撤销"是天然免费的**：订单一支付，`status` 就变成 `PAID`，下一轮扫描的条件 `status=PENDING AND created_at<...` 自动就不满足了。**不需要任何取消逻辑，也就不存在竞态。**

3. **15 分钟的精度要求本来就不高**：晚关单 30 秒对业务没有实质影响，但"把已支付的订单关掉"是**资损级**事故。用精度换正确性，这笔账划算。

**为此付出的代价**：
- 关单时机有最多 30 秒延迟（业务可接受，但要在文档里写清楚，别让运营来问）
- beat 挂了是**静默故障** —— 必须配心跳监控（课 7 讲的），否则关单会悄悄停掉，直到用户投诉才发现
- 大表扫描有 DB 压力，必须给 `(status, created_at)` 加联合索引
- 每 30 秒扫一次，即使没有超时订单也要查库（轻量，但要接受这点空转）

**什么时候该改选另一个**：
- 若关单时间**精确到秒**是硬需求（如秒杀 30 秒不支付就释放）→ 选 A，因为 30 秒轮询误差相对 30 秒窗口太大
- 若订单量**极小**（每天几十单）且你已经有 beat 在跑别的事 → 选 A 更省事，但**必须在关单任务里做幂等状态检查**（回到决策 3）
- 若你是**金融级**场景，既不能晚也不能错 → 选 C（ETA 精准触发 + 轮询兜底），两套都上，靠幂等保证重复执行无害

> ⚠️ **顺带纠正一个广为流传的说法**：
> 网上常说"ETA 任务的 `countdown` 超过 `visibility_timeout` 就会被重复执行"。
> **本机实测没有复现**：`countdown=20` 配 `visibility_timeout=1`（差 20 倍），任务**仍只执行 1 次**。
> 推测原因是 kombu 新版对 Redis broker 有 visibility 续期机制。
> ⏳ **置信度：中** —— 这是本机 5.6.3 环境的观测结果，不排除旧版本或不同 broker 有差异。
> **但请不要因为这个"没复现"就掉以轻心** —— 真正的重复执行风险来自下面这个场景（实测确实发生了）：
> ```
> 实测（l10-test-kill.sh）：worker 执行任务中途被 SIGKILL（模拟宕机/OOM）
> → 任务被重新投递执行，START 次数 = 2  ← 重复执行真实存在
> ```
> **结论：重复执行的风险是真实的，只是触发条件不是"countdown 太长"，而是"worker 崩溃"。** 所以决策 3 的幂等设计无论如何都不能省。

## 决策 3：幂等用 CAS 状态机还是 Redis SET NX？

**背景**：由决策 2 的实测可知，任务**确实会被重复执行**（worker 崩溃重投）。关单任务每次执行都会"关单 + 回滚库存"，重复 3 次就会把库存多回滚 2 次 —— 这是超卖。

**候选方案**：

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| A · **不做幂等**（反例） | 任务里直接 `order.status=CLOSED; stock+=1` | 代码最简单 | ❌ **超卖**：实测重复 3 次后库存 10→13 |
| B · **CAS 状态机**（DB 层） | `UPDATE ... WHERE status='PENDING'`，用返回的影响行数判断是否真执行 | 幂等和业务状态**统一**，不会因为缓存失效而失效；不引入新组件；天然支持"只有 PENDING 才能关单"的业务语义 | 高并发下依赖 DB 行锁，有锁竞争；需要 DB 事务配合；复杂场景要写 Lua 或 `SELECT FOR UPDATE` |
| C · **Redis SET NX 去重** | 执行前 `SET idem:close_order:{id} 1 NX EX 600`，抢到才执行 | 性能高（内存操作）；实现简单；与业务表解耦 | ⚠️ **多一个组件要维护**：Redis 挂了/清库了幂等就失效；⚠️ **忘了设 `ex` 会死锁**（实测 TTL=-1）；锁过期时间设短了，长任务会重复执行 |
| D · **两层都用** | CAS 做最终防线 + Redis 挡住绝大部分重复请求 | 最稳 | 复杂度最高，两套逻辑要保持一致 |

**最终选择**：**B（CAS 状态机）**

**选择理由**：

1. **⭐ 实测数据**：三种方式跑 3 次重复执行的结果——
   ```
   方式 ① 无幂等：库存 = 13（10→13，回滚了 3 次）❌ 超卖
   方式 ② CAS  ：返回值 [1, 0, 0]，库存 = 11 ✅
   方式 ③ SET NX：[(1,执行), (0,跳过), (0,跳过)]，库存 = 11 ✅
   ```
   两种幂等方案**都有效**，所以这不是"对错"问题，而是"哪个更适合"的权衡。

2. **CAS 的幂等和业务状态是一份数据，不会不一致**。SET NX 的幂等标记在 Redis 里，业务状态在 DB 里 —— 一旦 Redis 清库、主从切换丢数据、或者 TTL 过期，幂等标记消失，但订单已经是 CLOSED 了。**两个真相来源迟早会打架。**

3. **本项目的并发量撑得住 DB 行锁**。关单是按订单 id 单条更新，行锁竞争极小。SET NX 的性能优势在这个场景体现不出来。

4. **CAS 天然表达了业务语义**。"只有 PENDING 的订单才能被关闭"这句话，用 CAS 就是 `WHERE status='PENDING'`，一个条件同时表达了幂等和业务规则。

**为此付出的代价**：
- 高并发热点行（如同一个爆款商品的库存行）会有行锁竞争，QPS 极高时可能成为瓶颈
- 需要配合 DB 事务使用，代码比 SET NX 略复杂（要写 `filter().update()` 并判断影响行数）
- 每次幂等判断都要查库，比 Redis 慢一个数量级（本场景无所谓）

**什么时候该改选另一个**：
- 若你的幂等对象**不是数据库里的状态**（比如"发送短信"这种外部副作用，没有状态字段可用）→ 只能选 C（SET NX），因为没有状态机可依赖
- 若 QPS 极高（每秒上万）且 DB 已成瓶颈 → 选 D（Redis 挡前面，CAS 兜底）
- 若用的是 NoSQL / 无事务的数据库 → 选 C

> 🐞 **如果选了 C，必须记住这个坑**（实测）：
> ```python
> # ❌ 死锁陷阱：忘了 ex
> r.set(f'idem:close_order:{order_id}', '1', nx=True)     # TTL = -1，永不过期
> # 若任务抢到锁后、业务逻辑完成前崩溃 → 这个订单永远无法再被关单
>
> # ✅ 正确：必须有过期时间
> r.set(f'idem:close_order:{order_id}', '1', nx=True, ex=600)
> ```
> 实测输出：`TTL = -1 ← 永不过期`。**`nx=True` 和 `ex=` 必须成对出现。**

## 决策 4（已修正）：chord 挂死，是让 worker 消费 `default` 兜底，还是去补漏配的路由？

> 🔴 **本节是一次真实纠错的完整记录。** 我在 Phase 3 给出的第一个结论是**错的**，
> 这里保留错误结论与推翻它的实验，因为"怎么发现自己错了"比"直接给正确答案"更有教学价值。

### 4.1 当时的现象

做完决策 1（队列隔离）后，worker 配成只消费 `fast,slow`。结果 chord 编排**永远不回调**——不报错，header 任务全部 `succeeded`，就是一直等。

### 4.2 我的第一个结论（❌ 错的）

> "chord 的解锁任务（unlock）不是你写的任务，不受 `task_routes` 控制，
> 它会走 `CELERY_TASK_DEFAULT_QUEUE`（默认 `default`）。所以只要用了 chord，
> 就必须有人在消费默认队列。"

配套"修复"：让 worker 额外消费 `default`（`-Q fast,slow,default`）。实测 chord 确实跑通了。

**这看起来自洽，但它错了** —— 而且错得特别有迷惑性，因为**修复方案确实有效**。

### 4.3 为什么它是错的（官方源码 + 决定性实验）

**第一，官方机制不支持这个说法。** Celery 的 Redis backend 实现了**原生 chord 协调**：
`apply_chord()` 时用 `ZADD` 把每个 header 成员登记进有序集合，每个成员完成时 `ZADD` 标记 + `ZCOUNT` 计数，
**当计数等于总数时直接 `callback.apply_async()`** —— 不需要任何中间任务。
`celery.chord_unlock` 轮询任务**只在不提供原生协调的 backend 上**作为兜底出现。

**第二，决定性实验推翻了它。** 设计两组对照：

| 实验 | 做法 | 结果 |
|------|------|------|
| 取证 | 解出 `default` 队列积压消息的真实内容 | `task = orders.tasks.fulfill_order` —— **是编排入口任务自己**，不是 `chord_unlock` |
| 判定 | 给 `fulfill_order` 补上路由，**worker 仍不带 `default`** | chord **跑通**，对账记录 = 1，`default` 积压 = 0，日志中 `chord_unlock` 出现 **0 次** |

**真正的根因**：`CELERY_TASK_ROUTES` 里配了 6 个任务，**唯独漏了 `fulfill_order`（chord 的编排入口）**。
它进了 `default` 队列没人消费 → 整个编排**根本没开始** → 自然不会有回调。

### 4.4 为什么"让 worker 消费 default"是个坏修复

它**能解决症状，但会永久掩盖真因**：

| | 补路由（正确） | 让 worker 消费 default（错误） |
|---|---|---|
| 当前 chord | 跑通 | 跑通 |
| 漏配路由的 bug | 暴露并修掉 | **被 default 队列悄悄消化，永远发现不了** |
| 队列语义 | 每条任务路由明确 | `default` 变成"垃圾桶队列"，违背决策 1 的隔离初衷 |
| 下次新加任务漏配 | 会立刻挂死、立刻暴露 | 静默进 default，可能长期无人察觉 |

**这才是真正的决策点**：遇到"任务没人消费"，是**补上缺失的路由**，还是**扩大 worker 的消费范围去兜底**？
后者每次都"work"，代价是系统的显式性一点点流失，直到某天没人说得清哪个队列该有什么。

### 4.5 最终选择

**补路由**（`fulfill_order` → `fast`），worker 保持 `-Q fast,slow`，**不消费 `default`**。

**为此付出的代价**：
- 新增任务时**必须记得配路由**，否则立刻挂死（这是有意的：让错误在第一时间暴露，而不是潜伏）

**什么时候该改选"让 worker 消费 default"**：
- 你**明确知道**有任务会走默认队列，且这是设计意图（比如用 `send_task()` 动态发送、任务名在运行时才知道）
- 或者你的 backend **没有原生 chord 协调**（此时 `chord_unlock` 真的会出现，且真的走默认队列）——
  判断方法：看日志里有没有 `chord_unlock`，或查 backend 是否实现 `apply_chord`

> 🔥 **通用排查手法（比结论更重要）**：
> 遇到"队列有积压但没人消费"，**别猜积压的是什么**，直接把消息解出来看任务名：
> ```python
> import redis, json
> r = redis.Redis(port=6380, db=7)
> env = json.loads(r.lindex('default', 0))
> print(env['properties']['task'])   # 真实任务名
> ```
> 我就是靠这一手把错误结论推翻的 —— 在此之前我已经"验证"过一次，而且它看起来是对的。

**与其他决策的呼应**：这正是决策 1「所有任务都显式路由」的价值所在——
它让"漏配"变成**立刻可见的失败**，而不是潜伏的隐患。

## 决策 5：外部服务调用怎么做到"既真实又可跑通"？

**背景**：`send_notification` 要调短信服务。但学习者拿到代码时没有 API 密钥，直接跑必然失败；而失败的 chord 会让整条履约链路卡住，看不出是"编排错了"还是"外部服务不通"。

**两种做法**：

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| A · 直接写真实 URL | `requests.post('https://sms-api.example.com/send')` | 代码看起来"真实" | ❌ demo 开箱即挂；学习者分不清是编排错了还是服务不通 |
| B · **可注入的 mock** | 读环境变量 `SMS_API_URL`，没设就走 MOCK 分支直接返回 | 开箱即跑通；保留了真实的重试/超时代码路径；生产设个环境变量就切真实调用 | 多一个分支，代码稍长 |

**最终选择**：**B（可注入 mock）**

**选择理由**：
1. 初版按 A 写，**实测直接把 chord 拖超时**（`requests` 调用不存在的域名），浪费了大量排障时间才定位到"不是编排问题，是外部调用问题"。
2. mock 分支**不削弱教学价值** —— 重试装饰器、timeout 参数、僵尸任务防护这些关键代码都在真实分支里，学习者能完整看到。
3. 切换成本极低：设一个环境变量即可，不需要改代码。

**为此付出的代价**：
- 代码多一个 `if not api_url` 分支，不是"最简形式"
- 学习者可能误以为"mock 模式就是生产写法" —— 已在注释里明确标注

**什么时候该改选另一个**：
- 若这是**生产代码**不是教学项目 → 不该有 mock 分支，直接依赖注入一个 client 对象更干净

| # | 决策点 | 选择 | 放弃了什么 | 翻转条件 |
|---|--------|------|-----------|---------|
| 1 | 队列隔离 | 拆队列 + 专属 worker | 运维简单度、内存 | 任务耗时同量级 → 不拆 |
| 2 | 超时关单 | beat 轮询 | 秒级精度 | 关单窗口 < 1 分钟 → 改 ETA |
| 3 | 幂等实现 | CAS 状态机 | 极致性能 | 无状态字段可用 → 改 SET NX |
| 4 | chord 挂死的修法 | **补漏配的路由** | "让 worker 消费 default 兜底"这个诱人的捷径 | 用了无原生 chord 协调的 backend → 真需要消费 default |
| 5 | 外部服务调用 | 可注入 mock | 代码最简 | 生产代码 → 依赖注入 client |

## 🔗 决策之间的关联

这三个决策**不是孤立的**，它们咬合成一条链：

```
决策 2 选了轮询（有延迟） → 关单可能晚 30 秒
        ↓ 但这换来了"撤销免费"，不存在 ETA 的竞态
        ↓
决策 3 的幂等仍然不能省 → 因为实测证明 worker 崩溃会重投（START=2）
        ↓
决策 1 的队列隔离 → 保证关单这种慢任务不会堵住支付回调这种快任务
```

**如果决策 2 改选 ETA**，那么决策 3 就从"防崩溃重投"升级为"还要防撤销竞态"，幂等的重要性进一步提高 —— 这也从侧面说明 **幂等是整个系统里最不该省的那一项**。
