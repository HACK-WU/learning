## 1 · 任务发了但没人执行

**一眼识别**：`delay()` 成功返回，`AsyncResult.state` 永远 `PENDING`，
`redis-cli LLEN <队列>` 有积压且**不减少**，日志无报错。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 若积压的是可重发任务：先停 producer，避免继续堆积 | 积压停止增长 |
| 定位 1 | `celery -A proj inspect active_queues` | 看每个 worker 消费哪些队列 |
| 定位 2 | `redis-cli -n 0 LLEN default` 等各队列 | 找出积压在哪个队列 |
| 定位 3 | **解出积压消息的任务名**（别猜）：<br>`python -c "import redis,json;r=redis.Redis(port=6379);print(json.loads(r.lindex('default',0))['properties']['task'])"` | 得到真实任务名 |
| **修复** | 给该任务补 `task_routes` 路由配置 | 任务被正确路由 |
| 验证 | 重发任务，队列积压归零，状态变 SUCCESS | — |
| 若无效 | → 转 [2 · chord 永不回调](#2--chord-永不回调) / 转 `debug` 现场排查 | — |

> ⚠️ **不要用"让 worker 多消费 default 队列"绕过** —— 它掩盖真因，以后漏配都发现不了。

**预防**：起 worker 时故意不消费 `default`，让漏配立刻暴露。
**原理** → [08-实战经验 · 故障模式 1](../08-实战经验.md)

## 2 · chord 永不回调

**一眼识别**：header 任务全部 `succeeded`，body 回调不执行，`chord.get()` 阻塞到超时，无报错。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 若业务允许，先手动触发一次回调任务（用 header 的结果手工调用 body），避免数据一直不完整 | 数据补齐 |
| 定位 1 | `grep 'chord_unlock' logs/worker.log \| wc -l` | 0 → 走原生协调路径（正常）；>0 → 兜底轮询路径 |
| 定位 2 | `grep '<编排入口任务名>' logs/worker.log` | 有 → 编排开始了；无 → **入口没跑** |
| 定位 3 | 检查 `CELERY_TASK_ROUTES` 里有没有**编排入口任务** | 常漏的就是它 |
| **修复 A**<br>（入口没跑） | 给编排入口任务补路由 | 编排开始执行 |
| **修复 B**<br>（chord_unlock 无人消费） | 让 worker 消费 `chord_unlock` 所在队列，或换支持原生协调的 backend | — |
| 检查项 | 确认 header 任务**没有** `ignore_result=True` | 有就必须去掉 |
| 若无效 | → 转 [1 · 任务没人执行](#1--任务发了但没人执行) | — |

**预防**：chord 的 header 任务绝不能 `ignore_result=True`。
**原理** → [08-实战经验 · 故障模式 2](../08-实战经验.md)

## 3 · 任务重复执行

**一眼识别**：同一业务 id 出现**多条不同 task_id** 的执行记录；扣款/库存/短信出现重复。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 立即停掉相关队列的 worker（`celery -A proj control cancel_consumer <queue>`） | 停止继续产生副作用 |
| 止血 2 | 核对业务数据（对账），确认多做了多少 | 拿到影响面 |
| 定位 | 在任务里打 `retries={self.request.retries}` | **0** = broker 重投；**递增** = Celery autoretry |
| 修复（重投） | 加幂等：<br>`updated = Model.objects.filter(id=x, status='PENDING').update(status='CLOSED')`<br>`if updated == 0: return` | 重复执行被拦截 |
| 修复（autoretry 过频） | 收窄 `autoretry_for` 的异常白名单，只保留可重试异常 | — |
| 验证 | 手动重发同一任务 3 次，副作用只发生 1 次 | ✅ |
| 若无效 | → 转 [11 · 长任务被重投](#11--长任务超过检查周期被重投) | — |

**预防**：有副作用的任务，第一版就要带幂等。
**原理** → [08-实战经验 · 故障模式 3](../08-实战经验.md)

## 4 · 幂等锁变成永久死锁

**一眼识别**：某订单/任务**永远不再执行**，日志一直"已被处理过，跳过"；
`redis-cli TTL <lock_key>` 返回 **-1**。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | `redis-cli DEL <lock_key>`（确认业务不该被跳过后） | 任务可再次执行 |
| 定位 | `redis-cli TTL lock:close_order:<id>` | `-1` = 永不过期，确认是它 |
| 定位 2 | 搜索代码里的 `nx=True` 是否缺 `ex=` | 找到漏设点 |
| **修复** | `r.set(key, '1', nx=True, ex=3600)`（**nx 与 ex 必须成对**） | 锁会自然过期 |
| 验证 | 再查 TTL，应返回正数 | ✅ |
| 若无效 | → 转 `debug` 现场排查 | — |

**预防**：代码审查把 `nx=True` 和 `ex=` 绑定检查。
**原理** → [08-实战经验 · 故障模式 4](../08-实战经验.md)

## 5 · 任务读到未提交的数据

**一眼识别**：任务偶尔 `DoesNotExist`，或读到**旧值**；手动重跑一次就好了（典型竞态）。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 对失败的任务手工重跑一次（这类错误重跑通常即成功）；若批量失败，先暂停触发源 | 业务暂时恢复 |
| 定位 | 检查发任务处是否在 `transaction.atomic()` 块内 | 在块内 = 中招 |
| 自查 | 在发任务前打 `connection.in_atomic_block` | `True` = 在事务里 |
| **修复** | 改为 `transaction.on_commit(lambda: task.delay(id))` | 提交后才发 |
| 验证 | 连续快速创建 + 触发 20 次，无 DoesNotExist | ✅ |
| 若无效 | → 转 `debug` 现场排查 | — |

**预防**：Django 项目发任务一律走 `on_commit`。
**原理** → [08-实战经验 · 故障模式 5](../08-实战经验.md)

## 6 · 任务静默消失

**一眼识别**：`delay()` 没报错，任务从未执行，**队列里也找不到积压**（区别于第 1 条）。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 若任务可重发：从业务流水里找出"发了但没执行"的任务，手工补发 | 业务补齐 |
| 定位 1 | `celery -A proj inspect scheduled` | 看 ETA 任务还在不在 |
| 定位 2 | `redis-cli INFO memory` + `CONFIG GET maxmemory-policy` | `allkeys-lru` = 会驱逐 key |
| 定位 3 | 查日志有无 `InconsistencyError: Probably the key ... removed` | 有 = Redis 驱逐导致 |
| **修复 A**（ETA 丢失） | 重要延迟任务改**数据库持久化 + 轮询**，别依赖 ETA | 重启不丢 |
| **修复 B**（Redis 驱逐） | `maxmemory-policy noeviction` | key 不再被驱逐 |
| **修复 C**（无 backend） | 配 `result_backend` | 结果有处可存 |
| 若无效 | → 转 `debug` 现场排查 | — |

**预防**：Redis 设 `noeviction`；重要任务发完记"待执行"流水，靠对账发现丢失。
**原理** → [08-实战经验 · 故障模式 6](../08-实战经验.md)

## 7 · 定时任务重叠执行

**一眼识别**：对账/结算跑两次、数据翻倍；`inspect active` 里同一任务有多个实例。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 停 beat：`pkill -f 'celery.*beat'` | 停止继续派发 |
| 止血 2 | `celery -A proj inspect active` 看有几个实例在跑，让多余的跑完或撤销 | — |
| 定位 | 对比 `schedule` 周期与实际任务耗时 | 耗时 > 周期 = 必然重叠 |
| **修复** | 加分布式锁：<br>`if not r.set('lock:task','1',nx=True,ex=3600): return '跳过'`<br>`try: ... finally: r.delete(...)` | 同一时刻只有一个实例 |
| 修复（简单版） | `beat_schedule` 加 `'options': {'expires': 周期-10}` | 过期任务被丢弃 |
| 验证 | 把任务耗时人为拉长到 3 倍周期，观察是否仍只跑一次 | ✅ |
| 若无效 | → 转 `debug` 现场排查 | — |

**预防**：所有周期任务先问"如果它跑了 3 倍时间会怎样"；beat 要配存活监控。
**原理** → [08-实战经验 · 故障模式 7](../08-实战经验.md)

## 8 · 慢任务堵死快任务

**一眼识别**：快任务延迟飙升（发短信等 10 分钟），慢任务正常；队列总长在涨。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 为快任务单独起一个 worker 消费新队列；producer 改路由 | 快任务立刻恢复 |
| 定位 | `redis-cli LLEN <queue>` + `inspect active` 看在跑什么 | 确认是长任务堵的 |
| **修复** | 拆分队列 + 专属 worker：<br>`celery -A proj worker -Q fast -c 20 --prefetch-multiplier=1`<br>`celery -A proj worker -Q slow -c 4 --prefetch-multiplier=1` | 快慢隔离 |
| 验证 | 压测：慢任务满载时，快任务 P95 应基本不变 | ✅ |
| 若无效 | → 转 [9 · worker OOM](#9--worker-内存持续上涨) | — |

**预防**：任务按耗时分档，一开始就分队列；长任务队列配 `prefetch_multiplier=1`。
**原理** → [08-实战经验 · 故障模式 8](../08-实战经验.md)

## 9 · worker 内存持续上涨

**一眼识别**：`ps -o rss,etime` 显示 RSS 随时间单调上升；worker 被系统 OOM kill。
**副作用**：被 kill 时正在跑的任务会丢失并重投 → 可能触发第 3 条。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 重启 worker（**用 warm shutdown：`TERM`**，别 `kill -9`） | 内存归零 |
| 止血 2 | 确认被 kill 的任务是否有副作用残留 → 走第 3 条核对 | 数据一致 |
| 定位 | `ps -o pid,rss,etime,cmd -C celery` 观察增长曲线 | 确认单调上升 |
| **修复** | 加 `--max-tasks-per-child=1000`（或 `--max-memory-per-child=512000`） | 子进程定期自我替换 |
| 验证 | 观察 24 小时，RSS 应呈锯齿状（涨→换→归零）而非单调上升 | ✅ |
| 若无效 | → 用 tracemalloc / objgraph 查具体泄漏点 | — |

**预防**：生产必配 `max-tasks-per-child`；任务里别用全局字典当缓存。
**原理** → [08-实战经验 · 故障模式 9](../08-实战经验.md)

## 10 · revoke 拦不住已开跑的任务

**一眼识别**：调了 `revoke(task_id)`，任务仍跑完，副作用照样发生。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 若任务已跑完且产生了不该有的副作用，走**业务补偿**（如反向操作/人工订正），不要指望再撤销一次 | 影响可控 |
| 定位 | 查撤销时的 `AsyncResult(task_id).state` | `STARTED` = 已开跑，revoke 无效 |
| 判断 | 要不要强杀？ | `terminate=True` 会死在**任意一行**上，可能留下不一致中间态 |
| **修复** | **别依赖 revoke 做业务撤销**，改在任务内部校验前置条件：<br>`if order.status == 'PAID': return '放弃关单'` | 业务层真正拦住 |
| 验证 | 让任务在开跑后才撤销，确认副作用不发生 | ✅ |
| 若无效 | → 转 `debug` 现场排查 | — |

**预防**：延迟执行的操作，执行前都要**重新校验前置条件**。
**原理** → [08-实战经验 · 故障模式 10](../08-实战经验.md)

## 11 · 长任务超过检查周期被重投

**一眼识别**：任务耗时 **> 约 90 秒**，被**同一个 task_id** 执行了两次，
两次间隔约 **88.8 秒**，且 `retries` 始终为 0。

> 这是最容易误判的一条：很多人以为"任务只要超过 visibility_timeout 就会重投"，
> 实测**不是** —— 重投检查约每 88.8 秒才发生一次，短任务根本轮不到被检查。

| 步骤 | 动作 | 预期 |
|------|------|------|
| **止血** | 先停掉正在重复执行的实例（`revoke` 或停消费者），并核对已产生的副作用（如重复转码、重复写文件） | 防止继续放大 |
| 定位 | 看两次执行的 `task_id` 是否相同、`retries` 是否为 0 | 同 id + retries=0 = **broker 重投**（不是 Celery 重试） |
| 测量 | 记录两次 START 的时间差 | 约 88.8 秒 = 命中检查周期 |
| **修复** | 调大 `visibility_timeout` 到**大于任务最坏耗时**：<br>`broker_transport_options={'visibility_timeout': 43200}`<br>`result_backend_transport_options={'visibility_timeout': 43200}` | 不再被重投 |
| 修复（治本） | 任务加幂等（同第 3 条），重投也不产生副作用 | 重投无害 |
| 权衡 | 调大后会延长"真·丢失任务"的重新可见时间 | 见下方注意 |
| 若无效 | → 转 [3 · 任务重复执行](#3--任务重复执行) | — |

⚠️ **注意**：`visibility_timeout` 调太大，worker 硬崩溃后任务要等很久才重新可见。
官方建议是**优先让任务变短或变幂等**，调大超时只是权宜。

**预防**：耗时可能 > 90 秒的任务，一开始就调大 `visibility_timeout` 并加幂等。
**原理** → [08-实战经验 · "一个流传很广但需要修正的说法"](../08-实战经验.md)

